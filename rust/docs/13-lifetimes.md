# 13 · 生命周期 ⭐

> 对应示例：`examples/13_lifetimes/`
>
> 生命周期不是"让引用活得久一点"的黑魔法，而是**给编译器看的标注**：
> 声明"哪个引用必须活到哪"，编译器验证它没撒谎。95% 的场景被省略规则覆盖，
> 剩下 5% 才需要你动笔——那 5% 都在本章。

## 13.1 它防止什么

```rust
// fn dangle() -> &str {
//     let s = String::from("x");
//     &s                        // ← 编译错：返回的引用活不过 s（数据先死）
// }
```

所有权的铁律 2（05 章）：引用不得超过数据。编译器怎么知道"超不超过"？**每个引用都有生命周期**——一段它被保证有效的区间。多数时候推断搞定；推断不出来的签名，需要你标注。

关键认知：**`'a` 不创建、不改变、不延长任何东西**——它是函数签名里的**约束声明**（"调用方必须保证这些引用至少同时活到 'a 这么久"），编译器在每个调用点检查这个约束成立。

## 13.2 省略规则：为什么平时看不见

编译器按三条规则自动填充（都填不上才要你写）：

1. 每个引用参数各得一个生命周期参数；
2. 只有一个引用入参 → 它赋给全部返回引用；
3. 方法（有 `&self`/`&mut self`）→ self 的赋给全部返回引用。

```rust
fn first_word(s: &str) -> &str { ... }        // 规则 2：返回借自 s
fn area(r: &Rect) -> f64 { ... }              // 没有引用返回，无事发生
impl<'a> Excerpt<'a> { fn part(&self) -> &str }  // 规则 3：借自 self
```

所以新手写很久代码都碰不到 `'a`——直到写下面两种东西。

## 13.3 需要标注的场景一：多引用入参决定返回

```rust
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}
```

读法：返回值借自 x、y 中**较短命的那个的区间**（'a 是两者的交集）。为什么必须写：返回的到底是 x 还是 y 运行期才知道，编译器要求一个对两种情况都成立的合同。它带来的**保护**是真实的：

```rust
let s1 = String::from("长字符串");
let r;
{
    let s2 = String::from("短");
    r = longest(&s1, &s2);
    println!("{r}");      // ✔ s2 还活着
}
// println!("{r}");       // ← 编译错：r 的区间被约束进 s2 的寿命
```

把内部 println 删掉，最后一行又能过——NLL 按最后使用点收窄（05 章）。

## 13.4 需要标注的场景二：结构体持有引用

```rust
struct Excerpt<'a> {
    part: &'a str,        // Excerpt 实例不得活过它借用的文本
}
let novel = String::from("很久以前。还有后文。");
let ex = Excerpt { part: novel.split('。').next().unwrap() };
```

`'a` 在 struct 上 = "这个结构体**借用**了外面的东西"。编译器保证：novel 死后 ex 不能再用——悬垂引用在结构体层面也无路可走。**能拥有的尽量拥有**（`String` 而不是 `&str` 字段）——借用型结构体通常出现在解析器/视图层（零拷贝场景），那是它们的正当战场。

## 13.5 impl 块与约束叠加

```rust
impl<'a> Excerpt<'a> {
    fn longest_inside(&self, other: &'a str) -> &'a str {
        longest(self.part, other)
    }
}

fn longest_with_announcement<'a, T>(x: &'a str, y: &'a str, ann: T) -> &'a str
where T: Display { ... }          // 生命周期参数 + 泛型 + trait 约束同台
```

## 13.6 'static：程序全程有效

```rust
let s: &'static str = "编译进二进制的字面量";   // 字面量天然 'static
static GREETING: &str = "静态项";              // 同上
```

- `&'static str` 是"要么字面量、要么泄漏(leak)出来的"——`Box::leak`、`lazy_static`/`OnceLock` 造 'static 数据；
- 约束里的 `T: 'static` 意思不同："**T 不含非 static 的借用**"（拥有的数据才配装箱常驻）——不是"T 永远活着"。

```rust
fn boxed_copy<T: Clone + 'static>(v: T) -> Box<T> { ... }
```

## 13.7 与编译器吵架的正确姿势

1. **从最小标注开始**：先写 `&'a`，编译器嫌"活得不够久"（借得太短）就放宽输入标注；它反过来嫌调用点不满足，就缩短使用点。
2. **识别反模式**：返回引用指向函数内新建的数据 → 改返回值（String/结构体本身）；自引用结构体（字段引用自己）安全代码写不出 → 改索引/偏移/Rc。
3. **别用裸 'static 糊弄**：把 'static 写上去等于承诺"调用方保证数据常驻"——把检查负担推给所有调用方，通常是设计错了。

## 13.8 坑位清单

1. **`'a` 不延长寿命**：它只描述关系；数据该死还是死，只是编译器提前拦住你用已死的引用。
2. **两个入参取交集**：`longest` 的 'a 是较短者——想"跟长的那个活"就别在一个返回值里同时依赖两者。
3. **struct 用了引用，整个 struct 的寿命跟着缩**：结构体比字段先死的次序保证反过来不成立。
4. **`T: 'static` 误解率最高**：是"无短命借用"不是"永生"（13.6）。
5. **文档注释（///）后空行**：rustc 的 `empty_line_after_doc_comments` 警告——doc 注释要么紧贴条目，要么用普通注释 `//`（示例实测改法）。
6. **len()==0 被 clippy 劝改 is_empty**：顺手的 `assert!(s.len() > 0)` 在零警告纪律下要写 `!s.is_empty()`。
7. **编译器建议的"加 'static"先想三秒**：多数时候正确答案是重构数据流向，而不是常驻化。
