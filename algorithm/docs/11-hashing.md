# 11 · 散列表

> 对应 CLRS 第 11 章 *Hash Tables*（英文 3rd ed. pp.253–285）。字典问题
> （INSERT/SEARCH/DELETE）在「比较」框架下最快 Θ(lg n)（第 12–13 章的树）；
> 散列表直接把期望压到 **Θ(1)**——代价是**最坏**没保证（除非全域散列 +
> 完美散列）。「期望 O(1)、最坏看人品」这条主线贯穿本章。

## 学习目标

1. 能推链址法在装填因子 α 下的期望查找代价 Θ(1+α)；
2. 会实现开地址三法（线性/二次/双重）并解释**一次聚集/二次聚集**；
3. 能陈述定理 11.6（均匀散列：不成功查找期望探查 ≤ 1/(1−α)）并读懂
   装填因子实验的实测对照；
4. 理解全域散列的动机（消灭「被杀手键域打死」）与定理 11.5 的含义；
5. 知道「绝不遍历打印 unordered 容器」背后的哈希序不确定性（本教程
   高压线）；
6. 能把定长字符串做**进位制无损编码**塞进整数（2 bit/字符），推导并实现
   滚动递推 $v_{i+1}=(v_i-c_iB^{N-1})B+c_{i+N}$ 把 Θ(len·N) 降到 Θ(len)，
   并会做 $B^N$ 的**先判后乘**溢出检查，在位图 / `unordered_set` /
   Monte Carlo 三种去重方案之间正确取舍；
7. 会用两张散列表对「分组计数 + 违规成员剔除」做一趟流式聚合，维护
   计数不变量，并能处理输入行的语法分类。

## 动机：直接寻址的省内存版

键域 U 巨大（比如 64 位整数）但实际键只有 n 个时，直接寻址表
`T[k]`（|U| 个槽）浪费天文数字的空间。散列函数 **h: U → {0..m−1}**
把槽压到 m 个（m = Θ(n)）——代价是**碰撞**（两键同槽）不可避免
（鸽笼原理）。处理碰撞的两大流派：**链址**（每槽一条链）与
**开地址**（碰撞了就按探查序列找别的槽）。

## 散列函数（§11.3）

- **除法法**：h(k) = k mod m。m 别取 2 的幂（低比特全是重复模式），
  取不接近 2 的幂的**素数**最稳；
- **乘法法**：h(k) = ⌊m·(k·A mod 1)⌋，A ≈ (√5−1)/2（黄金分割），m 取
  2 的幂也无妨；
- **字符串**：多项式滚动 h = h·31 + c（Java 的经典做法）。

## 链址法（§11.2）

槽放链表，插入头插 O(1)，查找沿链扫描。CLRS 图 11.3 数据实测
（m=9，除法散列）：

```
T[1] → 28 19 10
T[2] → 20
T[3] → 12
T[5] → 5
T[6] → 15 33
T[8] → 17
```

简单均匀散列假设下，链长期望 α = n/m；**不成功**查找期望探查
Θ(1 + α)，**成功**查找 Θ(1 + α/2)（多扫半个链）。示例：
search(19) 恰好 2 次探查（链 {28,19,10} 第二个命中）。

**删除**在链址法下是 O(1)（双链）或 O(1)（单链但删的是刚查到的
节点——给指针即删）。这为开地址法做不到的 O(1) 删除埋下伏笔。

## 开地址法（§11.4）

所有元素住表内，碰撞沿**探查序列** ⟨h(k,0), h(k,1), …⟩ 前进：

- **线性探查** h(k,i) = (h′(k)+i) mod m：一次聚集（primary clustering）——
  连续占用块越长越容易更长，雪崩；
- **二次探查** h(k,i) = (h′(k)+i²) mod m：二次聚集（同 h′ 的键走同一
  条序列），且 m ≡ 3 (mod 4) 才保证访遍全表（示例的 m=103 特意挑的）；
- **双重散列** h(k,i) = (h₁(k) + i·h₂(k)) mod m：h₂ 与 m 互素时接近
  均匀散列，Θ(m) 条序列——聚集基本消失。

m=13、键 ⟨79,69,98,72,14,50⟩ 的实测（示例 11.2）：三种方法的表状态
几乎一致（稀疏表差异不明显），探查 8/8/10 次；真正的分水岭在装填因子：

```
α=0.50（n=51）：线性 插入1.6/查失3.5  二次 插入1.8/查失1.8  双重 插入1.6/查失2.0  （理论 ≤ 1.98）
α=0.70（n=72）：线性 插入2.8/查失6.6  二次 插入2.2/查失3.4  双重 插入2.0/查失3.1  （理论 ≤ 3.32）
α=0.89（n=92）：线性 插入6.0/查失32.9 二次 插入2.9/查失8.2  双重 插入2.3/查失8.9  （理论 ≤ 9.36）
```

读法：**双重散列贴着理论线**（8.9 vs 9.36），二次因聚集高出一线，
线性在 α=0.89 时查失 32.9 次——一次聚集的雪崩实测。工程结论：
开放定址的表要**保持 α < 0.7**（满了就 rehash 扩容）。

**定理 11.6**（均匀散列假设）：开地址表不成功查找的期望探查 ≤ 1/(1−α)。
α=0.9 时 10 次、α=0.99 时 100 次、α→1 爆炸——这就是「负载阈值」的
理论根据。

## 全域散列（§11.4universal，定理 11.5）

任何**固定**的 h 都存在杀手键域（把键全挤进一个槽——对手知道 h 就能
构造）。全域散列把随机性搬进函数选择：

H = { h_{a,b}(k) = ((a·k + b) mod p) mod m : a ∈ {1..p−1}, b ∈ {0..p−1} }

p 是大于 |U| 的素数。**定理 11.5**：从 H 均匀随机取 h，任两不同键碰撞
的概率 ≤ 1/m。于是**对手无法构造杀手键域**（他不知道 a、b）——与第 7
章随机化快排、第 9 章随机选择同一个思想：把最坏情形从「输入的属性」
变成「硬币的属性」。

实测（示例 11.4，p=10007、m=13、100 键 4950 对、每对换随机 (a,b)）：

```
全域类碰撞率 = 0.0758（理论 ≤ 1/m = 0.0769）
固定 k mod m 碰撞率 = 0.0859（键取自 0..999，与 m=13 的公倍结构有关）
```

全域版 0.0758 卡在理论上界之内；固定函数这组键域恰好偏高（0.0859）——
换更坏的键域（比如全为 13 的倍数）它会冲到 1.0，而全域版纹丝不动。

（§11.5 完美散列是收尾：两级散列、m = n² 的二级表，**最坏 O(1)** 查找、
空间 O(n)——静态键域（编译器关键字表）的专用兵器。）

## 定长字符串的进位制编码：从 Θ(len·N) 到 Θ(len)

前面四节都在讲「怎么设计散列函数」。这一节换一个角度：**键本身是短字符串
时，能不能把字符串直接变成整数键**——从而不需要哈希函数、完全避开碰撞。

### 核心观察：定长字符串就是「进位制整数」

字符集大小 B，把每个字符动态编号成 0..B−1，则**长度恰为 N 的字符串**
与区间 $[0, B^N)$ 中的整数**一一对应**：

$$v = c_0\cdot B^{N-1} + c_1\cdot B^{N-2} + \cdots + c_{N-1}$$

这个映射是**单射**（编码相同 ⟺ 字符串相同），前提是「**定长**」——
变长串需要额外编码长度，否则 "AB" 与 "A\0B" 会撞车。

一旦编码完成，「字符串去重」就变成「整数去重」，而整数可以直接当散列表
的键（整数的 identity hash 是完美的，O(1) 无碰撞）。

### ① 无损定长编码：2 bit/字符

DNA 的字符集只有 4 个字母，每字符 2 bit 足够（A→00, C→01, G→10, T→11）。
长度 m 的串用 2m bit：

$$v = \sum_{i=0}^{m-1} \mathrm{code}(s_i)\cdot 2^{2i}$$

m ≤ 32 时 2m ≤ 64 bit，整串塞进 `std::uint64_t`（位移量 ≤ 62，安全）。
这一步是**完全无损**的——它不是哈希，不存在碰撞。

实测（示例输出，8 个 DNA 串）：

```
① 2 bit/字符的无损编码（ACGT 定长，m ≤ 32 装得进 uint64_t）：
    动态编号（只统计实际出现的字符，按字符值升序）: A=0 C=1 G=2 T=3
    ⟹ 该串用了 4 个字符，B = 4，编码空间 B^m = 4^4
    编码: 27 27 228 27 165 228 27 165
    单射性：ACGT→27，AACC→5，ACAC→17（定长 ⟹ 编码与串一一对应）
    不同串 3 个，计数（编码×出现次数）: 27×4 228×2 165×2
    恰好有 i 个副本的人数: 0 2 0 1 0 0 0 0
    读法：4 个副本的 1 人、2 个副本的 2 人、1 个副本的 1 人
```

计数与分桶都是 Θ(n)：`cnt[v]++`，最后「恰好有 i 个副本的人数」就是
把每个不同 v 的计数往桶 i 里投一票。复杂度 **Θ(nm)**（读入本身就要 nm 个
字符，已是下界），空间 Θ(n)。

### ② 滚动递推：Θ(len·N) → Θ(len)

上一段是「定长整串」的编码。若要求的是「长度为 N 的**不同子串**个数」，
就得给每个位置算一个编码——而**朴素做法把每个子串重新编码一遍**，
代价 Θ(len·N)。

关键在于相邻窗口**只差一个字符**，可以直接递推。把 $v_i$ 的定义式
$c_i B^{N-1} + \cdots + c_{i+N-1}$ 按「高位左移、低位补新字符」展开：

$$v_{i+1} \;=\; \bigl(v_i - c_i\cdot B^{N-1}\bigr)\cdot B \;+\; c_{i+N}$$

预先算好 $B^{N-1}$，每次转移**3 条整数运算** ⟹ Θ(1)/步，全串扫描
**Θ(len)**——读入长度的下界。

```cpp
void roll(std::string_view text, std::size_t i) {
    const auto ci = static_cast<std::uint64_t>(code[(unsigned char)text[i]]);
    const auto cn = static_cast<std::uint64_t>(code[(unsigned char)text[i + width]]);
    v = (v - ci * powTop) * B + cn;      // powTop = B^{N-1}
}
```

**「补入的是 c_{i+N} 而不是 c_{i+N−1}」**是个真实的易错点：写错会让滚动
**原地不动**地重复第一个窗口（本示例实测翻车：daa 滚成 0，答案从 5 变 1）。

### ③ 去重：位图 vs散列表 vs 混合哈希

| 方案 | 确定性 | 时间 | 空间 |
|---|---|---|---|
| **位图** `vector<uint64_t>` | **确定性**（无碰撞） | Θ(len) | Θ(B^N/8) 字节 |
| `unordered_set<uint64_t>` | 期望（依赖哈希） | 期望 Θ(len) | Θ(不同子串数) |
| 64 位混合哈希 | **Monte Carlo**（有极小碰撞概率，会漏计） | Θ(len) | Θ(B^N/8) 字节或固定 |

位图的写法有一个小技巧：**计数在置位时自增，不要扫全表**——

```cpp
bool Bitmap::set(std::uint64_t v) {      // 返回 true 表示首次置位
    std::uint64_t& w = word[v >> 6];
    const std::uint64_t bit = std::uint64_t{1} << (v & 63);
    if (w & bit) { return false; }
    w |= bit; ++count;return true;
}
```

实测的四组数据（示例输出）：

```
② 进位制滚动编码 + 位图（长度为 N 的不同子串计数，Θ(len)）：
     N text        len 不同子串   位图字节
     3 daababac      8        5          8
     2 aaaa          4        1          8
     1 abcd          4        4          8
     3 abcdef        6        4         32
    递推式 v_{i+1} = (v_i - c_i·B^{N-1})·B + c_{i+N}——每步 3 条整数运算
```

与朴素解法对账（示例输出）：

```
    对账：文本 daababac、N=3
      朴素（排序 + 去重）：5 个不同子串，每次比较要逐字符比 O(N) 次
      滚动编码 + 位图：5 个 ⟹ 一致 = true
      朴素枚举的不同子串: aab aba bab bac daa
```

注意朴素做法的真实代价：字符串比较是 O(N) 次**字符**比较，每次插入还要
Θ(lg len) 次比较 ⟹ 总 Θ(len·N·lg len)。而滚动编码版**一次字符都不重复读**
（每个字符恰好进窗口一次、出窗口一次）。

### 两条纪律

**① 字符要动态编号，不要硬编码。** 只给**实际出现**的字符发号（按字符值
升序），B 最小、编码空间最省。样例里「a→0, b→1, c→2, d→3」是**样例特例**
——真实文本可能只用到 2~3 个字符，硬编码 4 个只是浪费空间（4 倍），
更糟的是把某些字符的编号顶到 B 之外，破坏单射性。

**② 先判 $B^N$ 是否放得下，再定方案。** 这是**溢出检查**，不是可选项：

```cpp
powTop = 1;
for (int i = 0; i + 1 < n; ++i) {
    if (powTop > UINT64_MAX / B) { powTop = 0; break; }   // B^N 放不下
    powTop *= B;
}
bool fits() const { return powTop != 0 || width == 1; }
```

**关键是用除法预先探测，而不是先算出来再判断**——后者本身就是溢出
（UB）。实测（示例输出）：

```
溢出检查（先判 B^N 是否放得下，再定方案）：
    文本长 20、B = 4、N = 10 ⟹ B^N = 4^10 = 2^20 = 1048576 bit = 128 KB
    N = 33 时 B^N = 4^33 = 2^66 > 2^64 ⟹ fits() = false ⟹ 必须换方案
    （可行替代：unordered_set<u64> 存滚动编码，或截断哈希。）
```

$B^N$ 装不下时的三条退路，按优先级：

1. **`unordered_set<uint64_t>`** 存滚动编码 —— 期望 O(len)，空间只跟
   实际不同子串数走（往往远小于 B^N）；
2. 对编码取一个 64 位混合哈希再存 —— Monte Carlo，要明确告知「有极小
   概率碰撞导致漏计」；
3. 换算法：后缀自动机（SAM，第 33 章）对「不同子串数」是 Θ(len) 时间、
   Θ(len) 空间，且不需要任何编码空间。

### 与本章主线的联系

这一节其实是本章开篇那个问题的**另一个极端解法**：

- 开篇方案：**压缩键域**（散列函数把 U 压到 m = Θ(n) 个槽）——有碰撞；
- 本节方案：**无损编码**（把短字符串精确塞进一个整数）——无碰撞，但
  要求「定长 + 字符集小 + 长度 ≤ 32」。

两者的取舍很清楚：**键短且规整时用无损编码，键长或不规整时才用散列**。
第33 章的字符串哈希、多项式滚动 h = h·31 + c 都是「不要求单射」的版本——
它们允许碰撞，所以必须老老实实处理冲突链。

## 散列表流式聚合：开源项目签到

### 问题

各项目负责人把签到表贴在墙上：**项目名以大写字母开头**占一行，下面
每行一个**以小写字母开头**的学生标识，学生可以在同一项目下重复签到。
汇总规则：

1. 同一项目内重复签到只算一次；
2. 一个学生若在两个或更多不同项目下签到，则在**所有**项目中被取消资格；
3. 输出每行「项目名 + 有效人数」，按人数**降序**排列；人数相同按项目
   名字典序升序。

注意一处文本矛盾：问题文字曾写成按人数「升序」，但样例与算法过程都
是降序——以样例为准。

### 建模：两张散列表、一趟扫描

这是典型的「分组计数 + 违规成员剔除」聚合。需要按键快速存取的两个
集合：

- `student`：学生标识 → `{首次签到的项目, 是否已取消资格}`；
- `count`：项目名 → 当前有效人数。

扫描时维护关键不变量：

> **count[p] 始终等于「到目前为止，只在项目 p 下签过到的学生数」。**

每行按首字符分类后落入四种情形之一：

| 情形 | 处理 |
|---|---|
| 学生标识第一次出现 | 登记 `student[id]={当前项目, false}`，当前项目 `count++` |
| 在同一项目下再次出现 | 忽略（重复签到） |
| 在另一个项目下出现、尚未被取消资格 | 把**首次项目**的 `count--`，标记已取消资格 |
| 已取消资格后又在别处出现 | 忽略 |

第三种情形是算法的核心：学生跨项目签到被发现时，他早先在**首个**项目
贡献的那 1 次计数必须撤回；而第二个以及之后的项目从来没有为他加过
计数，什么都不用做。学生的状态只会变坏这一次，之后的出现全部忽略。
于是一趟扫描、每张表只做期望 O(1) 的查找/插入，总期望时间 O(L)，
L 为行数。

样例的执行结果（paeinstein 在两个项目下签到，两边都不计；j97lee 在
YOUBOOK 重复签到，只算一次）：

```
  YOUBOOK 2
  LIVESPACE BLOGJAM 1
  UBQTS TXT 1
  SKINUX 0
```

### 对账：事后集合重算

流式版本依赖「撤回方向正确」这一微妙不变量，因此配一个不依赖处理
顺序的重算版：先为每个学生收集他签过的**不同项目**集合，集合大小
恰为 1 的学生才在对应项目计数，最后同样按（人数降序、项目名升序）
排序。3000 个随机生成的案例（项目数、学生数、每项目签到人次都随机）
两版逐行一致。

## C++23 语言点

- `std::vector<int> slot(m, -1)` 用 −1 当空标记（CLRS 的 NIL 化身）；
- 探查序列写成 `h(k, i)` 一个函数，三法一个 switch——对比实验只需换
  枚举值；
- **`std::hash` 与 `std::unordered_map` 的可移植性边界**：桶序、扩容
  时机都是实现自由——本教程全程不遍历打印 unordered 容器（docs/01 纪律），
  实验一律用自造表 + 整数探查计数；
- 散列表只承担聚合、不承担输出顺序：`unordered_map` 统计完后把结果
  抽进 `vector`，显式排序再打印。

| 开地址表 | 无直接对应（`std::flat_map` VS18 新落、内部是排序向量，且被本教程禁用） | 自写 |
| 全域散列 | 无 | 密码学场景用 SipHash 等更现代的方案 |

`unordered_map` 的工程要点：reserve 预留（避免中途 rehash）、自定义
hash 时注意键域对抗性（服务端用随机化种子防 HashDoS——全域散列的
工程化身）、最坏 O(n) 查找在实时系统里要掂量。

## 坑位清单

1. **二次探查在 m ≡ 1 (mod 4) 时装到一半就「假满」**
   （现象：表明明还有空槽，insert 却返回失败；原因：k+i² 模 m 只能访问
   (m+1)/2 个位置——全覆盖要求 m ≡ 3 (mod 4) 或 m 为 2 的幂+特殊处理；
   后果：α 不到 0.6 就插入失败；对策：m 选 103 这类 3 mod 4 素数——
   本例最初用 m=101（≡1 mod 4）装 92 个键，推演时发现必炸而改。）
2. **开地址法做「删除」直接置空槽**
   （现象：删除后同槽线索上的其他键查找失踪；原因：探查序列被空槽
   截断——中间的洞让后继探查提前「未找到」终止；后果：静默丢数据；
   对策：删除标记（DELETED 哨兵值）或改链址法；插入可复用 DELETED，
   查找遇 DELETED 继续走。）
3. **遍历打印 unordered 容器**
   （现象：三通道输出不一致，对账必炸；原因：桶序由哈希函数与扩容
   历史决定，跨实现/跨版本不同；后果：文档输出块无法对账；对策：
   排序后再打印或换 `std::map`（本教程高压线，示例全部用自造表+计数）。）
4. **m 取 2 的幂 + 键有低位规律**
   （现象：程序员姓名表全挤进几个桶；原因：k mod 2^r 只看低 r 位，
   键的低比特高度相关时等于没散列；后果：链长暴涨，退化成链表扫描；
   对策：m 取素数（除法法）或先乘法混合（乘法法/万能 h）。）
5. **α 不监控、不扩容**
   （现象：负载爬到 0.95 后服务延迟毛刺百倍；原因：1/(1−α) 在 α→1
   处爆炸（0.95→ 20 次、0.99 → 100 次）；后果：性能悬崖无预警；
   对策：装填阈值（典型 0.7~0.75）触发 rehash，容量翻倍重散列。）
6. **字符编号硬编码成「a=0, b=1, c=2, d=3」**
   （现象：编码空间白白大 4 倍；更糟的是当文本实际只用到部分字符时，
   某些字符的编号可能超出 B，破坏「编码 ↔ 定长串」的单射性，不同串
   撞成同一个整数；原因：把**样例特例**当成了通用规则；后果：静默
   丢数据（去重结果偏小）；对策：**动态编号**——只给实际出现的字符
   按字符值升序发号，让 B = 实际种数。第 8 章的逆序对计数里同一个坑
   出现过一次（「按首次出现顺序编号」把大小关系弄反）。）
7. **滚动递推里补入的字符取错下标**
   （现象：滚动后编码不变，每个窗口都算成第一个子串，「不同子串数」
   恒为 1（本示例实测：daababac 的答案是 5，错成 1）；原因：递推式
   是 $v_{i+1}=(v_i-c_iB^{N-1})B+\mathbf{c_{i+N}}$，补入的是**新窗口
   最右端** c_{i+N}，写成 c_{i+N−1} 就原地打转；后果：答案偏小，且
   因为「不越界、不崩溃」极难发现；对策：照着递推式逐项写，并用
   「与朴素枚举对账」断言把它钉住。）
8. **先算出 B^N 再判断是否溢出**
   （现象：B^N 超出 uint64 时已经发生了溢出，得到一个看似合理实则
   错误的编码（或直接 UB）；原因：「先乘后判」本身就是溢出——正确
   做法是「先判后乘」；后果：静默错误，或两通道行为不一致；对策：
   连乘时用 `if (powTop > UINT64_MAX / B) { 放不下; break; }` **预先
   探测**（除法判断不产生溢出），并在 B^N 放不下时改走
   `unordered_set` / 混合哈希 / 后缀自动机。实测 N=33 时
   B^N = 2^66 越界，`fits()` 正确返回 false。）
9. **`std::unique` 之后忘记真正截断 vector**
   （现象：去重计数「对得上」（用返回的迭代器算），但随后遍历该
   vector 时多出一堆空串/重复项，本示例实测直接触发 assert；原因：
   `std::unique` 只把尾部元素**移动成空串**并返回新逻辑末尾，
   `size()` 不变；后果：逻辑末尾与容器末尾混淆，后续统计全错；
   对策：要么 `v.erase(std::unique(v.begin(), v.end()), v.end())`
   真正截断，要么只使用返回的迭代器范围。）
10. **取消资格时改错项目的账**
   （现象：跨项目学生被发现后计数仍偏大；原因：学生首次出现时只有
   **首个项目**为他加过 1——撤回必须作用在首个项目上；第二个项目
   从未记账，无账可撤；后果：静默多计；对策：学生记录保存
   `first_project`，违例时 `--count[first_project]`（本例写法），
   并用「事后集合重算」随机对账钉住方向。）
11. **排序方向跟着题面文字走**
   （现象：输出顺序整段反、评测 WA；原因：题面文字写「升序」，但
   样例与算法过程都是**降序**——题面自相矛盾；对策：题面、样例、
   裁判三者冲突时以可执行的样例为准（本例按人数降序、同人数名字
   升序），并在文档中注明矛盾。）
12. **按「是否含空格/数字」区分两类输入行**
   （现象：学生 id（如 j97lee）含数字、项目名含空格，任何内容特征
   都不可靠；原因：格式唯一硬保证的是**首字符大小写**——项目名大写
   开头、学生标识小写开头；对策：只判 `line[0]` 的大小写区间（本例
   写法），并先在样例上核对分类。）
