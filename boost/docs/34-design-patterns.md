# 34 · Boost 与设计模式：23+4 个模式在库里怎么长出来

> 本章无独立例程——素材全部来自前 33 章的例程与库源码，按 GoF 的模式清单重新组织一遍。参考系是《设计模式》（GoF 1994）+ 罗剑锋第 5 版第 14 章。

学设计模式最有效的路径不是背 UML，而是看**真实的库怎么用它们**。Boost 恰好是"模式密度"最高的 C++ 代码库之一——这章把前面 30+ 章见过的组件按模式归位，你会发现"原来那些库的接口为什么长那样"有了统一答案。

三个提醒（也是 GoF 自己的提醒）：

1. **模式的区分常在意图不在结构**——代理和装饰的代码结构可以一模一样，区别在"控制访问"还是"增加职责"；
2. **泛型编程把许多模式做成了编译期机制**——基类链（策略）不需要运行时多态；
3. **有模式感 ≠ 要显式写模式**——`shared_ptr` 代理了裸指针，但你从来不需要写"Proxy"这个词。

## 34.1 创建型模式：对象从哪来

| 模式 | 意图 | Boost 里的实例 | 见 |
|---|---|---|---|
| 抽象工厂 | 一个接口产一族对象 | `xpressive::regex_compiler`（按名产各种正则对象；用模板而非继承实例化具体工厂） | 20 章 |
| 工厂方法 | 一个函数产一种对象 | `make_shared`/`make_optional`/`regex::compile`/`sregex::compile`——Boost 里**工厂方法泛滥成灾**，这是好品味 | 03/12/20 章 |
| 生成器 | 分步装配复杂对象 | `multi_array` 的 `extents[2][3][4]`（模板定维数→逐维给尺寸→成形）；`boost::format` 的 `%` 喂参也是装配 | 22/14 章 |
| 原型 | 拷贝自身产新对象 | `enable_current_exception()`/`exception_ptr` 的 clone 能力；指针容器要求元素的 `clone()` | 11 章 |
| 单件 | 全局唯一实例 | `singleton_pool<Tag, Size>`（Tag 就是"哪个单件"的身份证）；多数 Boost 库用 Meyers 单件（函数内 static） | 21 章 |

创建型的共同主题：**把 `new` 从业务代码里赶出去**。第 3 章讲过的"工厂 + 保护析构 + shared_ptr"三件套是最完整的实践——用户连 delete 的权利都没有，对象只能从工厂出来、由智能指针管到底。

## 34.2 结构型模式：对象怎么组合

| 模式 | 意图 | Boost 里的实例 | 见 |
|---|---|---|---|
| 适配器 | 接口转换后复用 | `array`（把 C 数组适配成 STL 容器）；`multi_array_ref`（把裸内存适配成多维数组）；`lockable_adapter`（把普通类适配成可锁定对象） | 05/22/09 章 |
| 桥接 | 抽象与实现分离 | **pimpl 惯用法**（`sample` + `shared_ptr<impl>`——接口稳定、实现任意换）；`random_device` 的 pimpl 后端可换硬件源 | 03/06 章 |
| 组合 | 部分-整体的树形结构 | `property_tree`（每个子节点也是 ptree——透明接口）；`multi_array`（每维是低一维的 multi_array）；xpressive 静态正则（小正则组合成大正则再组合） | 30/22/20 章 |
| 装饰 | 动态加职责 | `operators` 的**基类链**（每个概念"装饰"前一个基类的操作符集——不过它是编译期的）；`circular_buffer_space_optimized`（装饰 circular_buffer 的内存策略） | 05/21 章 |
| 外观 | 给子系统一个简化门面 | `variate_generator`（把引擎+分布两个子系统包成一个 `()`）；`auto_cpu_timer`（把三只表+格式化包成一行） | 06/07 章 |
| 享元 | 共享细粒度对象 | `flyweight` 库（本体）；`regex_compiler` 的正则池（按名缓存编译结果——20 章例程第 9 段） | 22/20 章 |
| 代理 | 控制对对象的访问 | **`smart_ptr` 全家**（代理裸指针：控制生命周期）；`bind`/`function`/`optional`（代理可调用物/值——控制"何时真正访问"） | 03/04/12 章 |

结构型里最值得琢磨的是**代理/装饰/适配器三胞胎**：结构都是"包一层"，意图分别是**控制访问 / 加职责 / 换接口**。`shared_ptr` 不是适配器（没换接口）也不是装饰（没加职责——它加的是"控制"：什么时候删）。

## 34.3 行为模式：对象怎么通信

| 模式 | 意图 | Boost 里的实例 | 见 |
|---|---|---|---|
| 职责链 | 请求沿链传递 | `assign` 的 `list_inserter`（`+=`/`()` 把插入请求串成链逐个处理）；`iostreams` 的 filter 链 | 21 章 |
| 命令 | 请求封装成对象 | `boost::exception`（错误信息封装进异常对象沿栈传递直到被 catch）；`function`（把"调用"本身当值存） | 11/04 章 |
| 解释器 | 小语言的文法+求值 | xpressive（正则 DSL）、spirit（EBNF 解析器生成）、proto/yap（表达式模板——C++ 嵌入式 DSL 的地基）、wave（C++ 预处理器）、`program_options`（命令行微型文法） | 20/27/29 章 |
| 迭代器 | 顺序访问不暴露表示 | STL 本身 + Boost 的迭代器工厂（`stl_interfaces`/` iterators`）；`date_iterator`/`find_iterator`/`split_iterator` 都是"这个概念比标准迭代器更宽"的证据 | 15/07/19 章 |
| 中介者 | 集中管理对象间通信 | `io_context`（asio 里所有异步对象的汇合点——handler 之间不认识，只认识它） | 28 章 |
| 备忘录 | 捕获并外存状态 | `io_state_savers`（流状态快照、析构还原）；引擎拷贝 = 随机数状态快照（06 章复现测试的抓手） | 06 章 |
| 观察者 | 一对多通知 | **`signals2`**（C++ 观察者模式的完成态：组号排序、合并器、连接管理、track 自动断连） | 31 章 |
| 状态 | 状态切换改变行为 | `statechart`/`msm`（UML 状态机的库化——把 if-else 状态分支变成显式的状态转移表） | 31 章 |
| 策略 | 算法可替换 | **Boost 的呼吸方式**：比较器（set 的模板参数）、分配器（pool_allocator）、合并器（signal 的第二参）、时钟（basic_ptimer 的模板参）、删除器（shared_ptr）——"模板类型参数 = 编译期策略注入" | 全书 |
| 模板方法 | 父类定骨架子类填步骤 | Boost.Test 的夹具体系（框架管安装/清理/报告的骨架，你只写测试函数）；`static_visitor`（框架管分派，你只写 operator() 重载） | 32/12 章 |
| 访问者 | 在不改类的前提下加操作 | `variant` + `apply_visitor`（编译期穷尽分派）；tuple 的 `visit_tuple` 递归模式（05 章 cons 链遍历） | 12 章 |

行为型里 Boost 的最大贡献是**把"策略"做成了 C++ 的默认表达**：任何第三、四个模板参数几乎都是策略位。GoF 的策略模式在面向对象语言里要建类层次，在泛型 C++ 里是一个模板参数——这就是"范式吞掉模式"的典型。

## 34.4 GoF 之外的四个常用模式

**空对象（Null Object）**：给"没有"一个行为一致的代表。`tuple` 的 `null_type`（cons 链的终点哨兵，"空元组"参与递归而不需要特判）；`null_mutex`（signals2 的线程安全开关——把"不锁"做成锁的形状）；`tribool` 的第三态某种意义上也是"语义上的空对象"。

**对象池（Object Pool）**：预分配 + 复用，摊薄构造成本。`pool` 库四兄弟（21 章）、`thread_group`（简版线程池）、网络编程里的连接池——凡是"构造贵、生灭频繁"的东西都配一个池。

**包装外观（Wrapper Facade）**：把底层 C API 包成面向对象门面且不损失性能（inline + 具体类型，不做虚函数多态）。`system`（errno/GetLastError 的分类包装）、`atomic`/`thread`/`asio`（各自 OS 原语的跨平台包装）——Boost 的可移植层几乎全是这个模式。

**前摄器（Proactor）**：异步事件分发。asio 的核心架构——`io_context`（前摄器）+ OS 异步机制（操作处理器）+ 完成事件队列 + handler（完成处理器）。它解释了 asio 为什么能"不用多线程获得并发"：等待交给内核，线程只处理完成事件。std::execution（C++26）是这个模式的标准化。

## 34.5 模式视角的三个总结论

1. **Boost 是模式的教学现场**：每章的"为什么这么设计"几乎都能落回某个模式意图。反过来说，理解了模式意图，Boost 的接口就"理应如此"——不用背 API，能推出来。
2. **C++ 的范式演进在吞掉模式的实现**：策略 → 模板参数；命令 → lambda；生成器 → initializer list；访问者 → overload/`std::visit`。模式意图不死，实现形态一直在换代。
3. **模式是重沟通工具不是代码模板**：说"这里用享元"比贴三段代码更快让同事明白设计意图——这也是 GoF 的本意（"给同行交流的词汇"）。
