# 01 · 全景：Ruby 是什么，为什么值得学

> 本章无示例（从第 02 章起每章配一个可运行示例）。

## 1.1 一段话定位

Ruby 是一门**为人而非机器优化、把表达力放在第一位的纯面向对象动态语言**——设计者松本行弘（Matz）的原话是「Ruby is designed to make programmers happy」。它给你脚本语言的即时反馈（一个 `puts` 就是完整程序、无需编译、REPL 随开随用），底层却是彻底的纯 OOP：**一切值都是对象，`1` 是 Integer，`nil` 是 NilClass，连 `+` 都是方法调用**（`3 + 4` 只是 `3.+(4)` 的语法糖）。再加上块（block）与元编程这两件大杀器，Ruby 写出来的代码常常接近自然语言的句子——Rails 生态就是建立在这套表达力之上。

一句话：**Ruby = Smalltalk 的纯 OOP + Perl 的文字处理手感 + Lisp 的元编程 + 「程序员快乐」优先的设计取向**。它不为高性能数值计算而生，但在 Web 后端、DSL、脚本自动化、原型验证领域是「代码即意图」的标杆。

「程序员快乐」不是营销词，它有可验证的技术含义：同一件事 Ruby 通常给你最短的表达路径（`%w[a b]` 造词数组、`#{}` 插值、后置 `if`），并且**很少强迫你写仪式性代码**——没有入口函数（02 章）、没有类型声明、没有字段声明（06 章）。代价是自由度外包给了纪律：魔法注释、命名约定（`?`/`!` 后缀）、社区惯例承担了原本由语法强制的工作，本书的坑位清单里相当一部分坑就是「惯例被忽略」的坑。

## 1.2 设计哲学：把坑当第一等公民的前提

理解 Ruby 的行为差异，先记住四条设计取向，后面 23 章几乎每个「坑」都能追到这里：

| 取向 | 做法 | 教学上的后果 |
|---|---|---|
| 一切皆对象、一切皆方法 | `1.even?`、`nil.to_a`、`3.+(4)` 全是消息传递 | 没有基本类型/包装类型二分，但 `1 == 1.0` 与 `1.eql?(1.0)` 的差异要专门讲（06 章） |
| 一切皆表达式 | `if`/`case`/`while`/块都有值，能直接赋值（02.7） | `while` 里 `break 100` 可以把值带出来（04 章） |
| 最少惊讶（MINASWAN） | API 按「直觉上应该怎样」设计，甚至替你多想一步 | 直觉有时会骗人：`7 / -2 == -4`（商向负无穷取整）、`"abc".to_i == 0`（宽容解析）都是「体贴」出来的坑（03 章） |
| 透明优先于性能 | 运行时全开放：`method_missing`、`define_method`、`instance_variables`（05/15 章） | 内省能力是一等公民，性能要靠后置优化（16 章） |

真值语义是最容易踩的一条：**只有 `false` 和 `nil` 是假，`0`、`""`、`[]` 全为真**——与 C、JavaScript、Python 都不同（4.2 节专门立节讲）。

「一切皆方法」值得用一个探针亲眼验证（实测于 4.0.7 `-e` 探针）：

```ruby
p 3.+(4)              # => 7    —— + 就是 Integer#.+ 方法
p 1.class             # => Integer
p nil.class           # => NilClass
p 1.frozen?           # => false —— 连「冻结状态」都是对象的方法
p "abc".respond_to?(:upcase)   # => true —— 能力查询也是消息
```

这决定了本书讲任何语法都优先问「它是哪个对象上的哪个方法」：运算符重载（5.7）、`attr_*` 宏（6.2）、内省（6.8）、元编程（15 章）全是这句话的展开。

「最少惊讶」也要辩证地看：Matz 的原意是「对**写 Ruby 的人**最少惊讶」，不是「对 C 程序员最少惊讶」——所以 `7 / -2 == -4` 在 Ruby 的数系里自洽（floor 除法），却让 C 老手大跌眼镜。本书凡遇这类「有立场的设计」，都会把立场本身讲清楚，坑位清单只收录「立场之外」的真意外。

## 1.3 版本演进小史：1.8 → 3.0 → 4.0

Ruby 的版本史就是一部「把历史包袱逐个还清」的历史。挑几个与本书直接相关的里程碑：

| 版本 | 年份 | 关键变化（与本书相关） |
|---|---|---|
| 1.8 | 2003 | 经典老版（本机留有 1.8.7 化石作参照，见 1.6 节）：无编码概念、`Fixnum`/`Bignum` 二分、字符串默认可变且无冻结约定 |
| 1.9 | 2007 | 换 YARV 虚拟机、引入编码（Encoding）、Hash 保持插入序、`Fixnum` 语义开始统一 |
| 2.0 | 2013 | 关键字参数登场、`frozen_string_literal` 魔法注释出现、Refinements |
| 2.4 | 2016 | `Fixnum`/`Bignum` 正式合并为 `Integer`（3.1 节的出发点） |
| 2.7 | 2019 | `case/in` 模式匹配（实验性）、编号块参数 |
| 3.0 | 2020 | **关键字参数与位置哈希彻底分离**（5.2 节重点）、Ractor 并行、模式匹配转正 |
| 3.2 | 2022 | `Data` 不可变值对象登场（6.5 节） |
| 3.4 | 2024 | **Prism 成默认解析器**；chilled strings 首次引入（未声明 `frozen_string_literal` 的文件里裸改字面量开始发弃用告警） |
| 4.0 | 2025 | Prism 已是完全默认的解析器（`ruby -v` 直接标 `+PRISM`）、chilled strings 继续收紧（方向：未来版本字面量默认冻结） |

**这意味着：网上大量旧教程（1.8/2.x 时代写法）在 4.0 上有静默差异或直接报错**——`Fixnum` 已不存在、位置哈希塞给关键字参数直接抛 `ArgumentError`、裸改字符串字面量开始告警。本书所有代码在 **Ruby 4.0.7（2026-09-15 revision 229531a6cf +PRISM, x86_64-darwin23）** 实测，每章末尾「坑位清单」收录实测差异。

两个影响全书的关键点展开说：

**Prism 解析器**。Ruby 的解析器几十年都长在 `parse.y` 里，历史包袱沉重。Prism 是重写的错误恢复友好、可嵌入的新解析器，3.4 起成为默认，4.0 上已是唯一主线（`ruby -v` 里的 `+PRISM` 就是标记）。对学习者的直接意义：报错信息更准、`case/in` 这类新语法以 Prism 行为为准——比如「`case/in` 的 `in` 前必须换行」这条语法事实（4.6 节）就是在 4.0.7 + Prism 下实测的。

**chilled strings（冷却字符串）**。方向是「字符串字面量未来默认冻结」，执行分三档：

| 文件写法 | 4.0 行为 |
|---|---|
| 写了 `# frozen_string_literal: true` | 字面量即冻结，改动抛 `FrozenError` |
| 没写魔法注释 | 裸改字面量**照常执行**，但 stderr 发弃用告警（"chilled"） |
| `ruby --debug-frozen-string-literal` | 告警升级为完整来源信息，便于排查 |

第二档的告警原文（实测于 4.0.7 `-e` 探针，`s = "abc"; s << "x"`）：

```text
-e:1: warning: literal string will be frozen in the future (run with --debug-frozen-string-literal for more information)
```

本书示例全带魔法注释、验证层把「stderr 非空」直接判负——所以每章坑位清单里凡涉及字符串原地修改，答案都是 `+"abc"` 或 `.dup`。

每章的固定结构：章导语 → 与示例 `sec` 一一对应的 `## N.M` 小节（代码 + 实测输出 + 为什么）→ 坑位清单（8–12 条实测坑，每条标注出处小节号）→ 上一章/下一章导航。示例输出一律从 `build/NN.out` 逐字节摘录，与你自己跑出来的结果应当完全一致——不一致就是你环境的问题，先查 `ruby -v`。

动笔约定（写给将来改这本书的人，也是读代码时的路标）：示例里凡引用实测输出必标「实测」或直接摘自 build 快照；探针验证的内容标「实测于 -e 探针」；示意性伪码绝不冒充实测——三种来源在正文里一眼可辨。

## 1.5 全书约定：目录结构、示例规约与双层验证

仓库目录结构（本书只碰 `examples/` 与 `docs/`）：

```text
ruby/
├── examples/NN_topic/     # 每章一个目录：main.rb + runtests.rb
├── docs/NN-topic.md       # 本教程文档（章号与目录号一致）
├── build/NN.out / NN.err  # 验证脚本捕获的 stdout/stderr 快照
├── run-all.sh             # shell 验证入口（macOS/Linux）
└── build.ps1              # PowerShell 验证入口（Windows 等价）
```

每个示例 `main.rb` 遵守一套硬性规约，写它们就是为了「可被机器判定」：

1. **`# frozen_string_literal: true` 魔法注释**：文件里所有字符串字面量即冻结。要可变副本用 `+"abc"` 或 `.dup`（5.3、6.7 节）。这不是洁癖——4.0 对「裸改字面量」只发弃用告警（chilled strings），我们把标准定得更严：**stderr 必须完全为空**。
2. **`sec("N.M 标题")` 分节**：每节开头打一行 `---- N.M 标题 ----`，节号与本书 `## N.M` 小节一一对应。
3. **结束标记 `==== NN 结束 ====`**：stdout 最后一行，验证脚本靠它确认输出完整。
4. **六条判定**（`./run-all.sh` 逐条查）：退出码 0、stderr 为空、stdout 非空、无多余控制字符、含结束标记、无 Ruby 诊断字样。
5. **双层验证**：运行层（`ruby main.rb`，查六条判定）+ 测试层（`ruby runtests.rb`，独立 minitest 套件）。两层全绿才算通过。

每个 `main.rb` 顶部自带两个逐字相同的助手——`sec` 就是上面第 2 条的实现，`ok` 是断言自检：

```ruby
# 分节标记：与文档的 ## N.M 一一对应，验证脚本靠 stdout 里这些行定位
def sec(title)
  puts("\n---- #{title} ----")
end

# 断言自检：失败即抛错（走 stderr、退出码非 0），验证脚本直接判负
def ok(cond, msg = "断言失败")
  raise(msg) unless cond
end
```

六条判定逐条说清「为什么」：只查退出码会漏掉「进程没执行到业务代码」的假阳性（所以 stdout 必须非空）；告警全走 stderr，stderr 为空等价于零告警（所以 warn、实验特性告警在示例里都要用 StringIO 或 `$VERBOSE = nil` 圈起来）；结束标记保证输出没被中途截断；诊断字样兜底拦的是行首 `error/warning/Traceback` 与独词 `Error`，而 `ZeroDivisionError` 这类 CamelCase 异常类名出现在演示输出里不算违规。

学法与 julia 教程相同：读讲解 → 跑示例 → 改代码再跑。改了示例就重跑 `./run-all.sh NN`，六条判定 + minitest 会替你把关。两个入口（`run-all.sh` 与 `build.ps1`）判定逻辑逐条一致，`build/` 目录里的 `NN.out`/`NN.err`/`NN.test` 快照就是每次验证留下的现场——本书各章引用的实测输出都来自这些快照。验证脚本定位工具链时带 `LC_ALL=C`，规避 BSD 用户态工具在 UTF-8 locale 下对非法字节报错截断的老问题，中文输出照常参与判定。

为什么坚持双层？运行层只能证明「这次跑没炸」，测试层（独立 minitest 套件，不依赖 main.rb 的输出）才能证明「行为确实符合预期」——比如某示例把 `ok` 断言删了但打印照旧，运行层全绿，测试层立刻红。教程代码配上机器判定的验证，是本仓库所有语言教程共同的底线。

1. 缺现代语法的关键部分：无编码系统、无 `frozen_string_literal`、关键字参数语义完全不同——示例代码大多直接报错或行为迥异；
2. 2011 年就停止维护，安全层面不可用；
3. 留着它的唯一用途是**演进史参照**：1.3 节那张表里的每个变化点，都对应一次「从 1.8 的写法到 4.0 的写法」的迁移。想亲眼看看化石，下面几行探针（实测于本机 ruby1.8）足以说明它离现代 Ruby 有多远：

```ruby
# 实测于本机 ruby1.8（1.8.7, 2013 年编译）
p RUBY_VERSION                       # => "1.8.7"
p "abc".respond_to?(:force_encoding) # => false —— 1.9 之前没有编码系统
def f(a: 1); end                     # => syntax error, unexpected ':'
                                     #    —— 2.0 之前没有关键字参数
```

还有一条本教程自己的纪律：**凡「4.0 行为」的断言必须与示例代码或 build 产物一致，拿不准的先跑 `ruby -e` 探针再写**。本页的 chilled strings 告警、1.2 节的「一切皆方法」、上面这段 1.8 探针都是这么来的。

## 1.7 与本仓库其他语言教程的横向定位

本仓库有一整套同风格的语言教程（julia、haskell、elixir、prolog、cpp20 等），Ruby 这本在其中的定位：

- **与 julia 教程**：同为动态语言，julia 的主线是「多重派发 + JIT 性能」，Ruby 的主线是「一切皆对象 + 表达力」。对照着看最有趣的是两边的镜像设计：julia 字符串拼接用 `*`（拼接在数学上像乘法），Ruby 用 `+`；julia 有正式的 `@main` 入口宏，Ruby 没有入口概念，`ruby main.rb` 从第一行执行到最后一行（02 章）；julia 的函数按全部实参类型多重派发，Ruby 的方法按接收者单派发、靠 `case/in` 与 duck typing 补足分支（04/06 章）。风格约定（示例目录、章末导航、「把坑当第一等公民」的写法）两边一致，交叉阅读没有换挡成本。
- **与 elixir 教程**：两者都重度使用模式匹配，但方向相反——Elixir 的模式匹配是函数头的派发机制（多子句函数定义），Ruby 的 `case/in` 只是控制流的一种（4.6 节）。Ruby 有可变状态、传统的类与实例变量，Elixir 靠不可变数据与 actor 进程；从 Elixir 过来的读者要警惕的正是 Ruby 的默认可变性（6.5 节的 `Struct` vs `Data` 就是这条光谱的两端）。
- **与 haskell 教程**：Ruby 的块/lambda 是「够用的函数式」——没有柯里化、没有纯度保证、没有类型系统兜底，但 `map(&:upcase)` 的链式高阶函数风格与 Haskell 血缘相同（5.6 节），`Proc` 与 lambda 的语义差异（5.5 节）在 Haskell 世界里对应的正是「函数是一等值」需要付出的一致性代价。
- **与 prolog 教程**：几乎无直接交集，唯一共振是「声明式描述意图，把怎么做留给实现」——Ruby 的 DSL 能力（15 章）常被用来在命令式语言里嵌入声明式子语言（路由表、配置规则），这是 Prolog 把整门语言都押上去的那条路的小型化。
- **与 cpp20 教程**：性能光谱两端。cpp20 的信条是「零成本抽象」——抽象不付运行时代价；Ruby 恰好相反，**抽象有成本且成本可见**：每个方法调用都是消息查找，每个块都是对象（16 章有实测对比）。这不是贬低 Ruby——知道成本在哪，才知道什么时候该为表达力买单。
- **横向读法建议**：学完 04 章后对照各家控制流章，理解「同一概念（模式匹配、真值语义、表达式化）在不同语言里被放到了哪个层级」；学完 06 章后对照 julia 的派发章，看「按类型分派」与「按对象分派」如何殊途同归。
