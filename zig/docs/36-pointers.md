# 36 · 指针与内存深水区

11 章讲过分配器五件套（`alloc` / `free` / `resize` / `create` / `destroy`）和各分配器的定位，本章不再重复。本章专攻**指针本身**——那些 06 章讲切片时按下不表的深水区：`volatile`、指针与整数互转、两种"重解释"的分工、零尺寸类型、`anyopaque`、强转与 peer 类型解析的完整规则、`[*c]T` 之祸、位对齐指针。取材《Learning Zig》第 9 章（Memory Management）与第 12 章（Sophisticated Topics）的指针半区，原书是 0.15 时代写法，本章全部按 **0.17.0 实测**重写——其中三条结论（`[*]T` 的算术语法、ZST 的地址、`@ptrFromInt` 的对齐检查时机）跟旧资料都不一样，都以本机实测为准。示例在 `examples/36_pointers/main.zig`，11 个 test 块钉住每节语义。

## 36.1 显式可变性：可变性写进指针类型

Zig 的指针把"能不能写"编码在类型里：`&const变量` 得到 `*const T`，`&var变量` 得到 `*T`。这不是 lint 建议，是编译期强制的类型规则——`total` 收 `[]const i32` 就永远改不了元素，`bump` 收 `*i32` 才能 `p.* += 1`（示例 36.1 的两个函数）。想从 `*const T` 里"解锁"出写权限，语言层面没有路。

这个设计值什么？**读签名就知道副作用**。C 里 `void f(int *p)` 改不改 `*p` 只能看实现；Zig 里看类型就够。06 章的切片同理：`[]T` 与 `[]const u8` 是两种类型，后面 36.9 会看到"加 const"是合法的隐式强转，反向永远不行。

## 36.2 volatile：给"内存之外的世界"看的读写

正常指针的读写，编译器有权优化：连着读两次同一块内存，第二次可以用第一次的寄存器缓存；循环里条件不变，可以把判断提出循环。99% 的情况这正是你要的。但如果那块内存**会被 CPU 之外的东西改**——硬件寄存器（MMIO）、中断服务例程、DMA 引擎——优化就变成 bug：你写的"轮询状态寄存器"被优化成"读一次然后死循环"。

`volatile` 就是给编译器的禁令：**对这个指针的每次 load/store 都必须按源码原样发生**，不缓存、不合并、不重排。示例 36.2 模拟了一台最小设备：

```zig
fn waitReady(status: *volatile u32, max_spin: usize) bool {
    var i: usize = 0;
    while (i < max_spin) : (i += 1) {
        if (status.* != 0) return true; // 每一圈都是一次真内存读
    }
    return false;
}
```

`status.*` 在循环体里每圈都真去内存拿。测试里用一根普通指针扮演"设备侧"把 `dev.status` 从 0 写成 1——对编译器来说，`waitReady` 拿到的 volatile 指针意味着"我无法证明没人动它"，于是循环不会被提升成一次读取。没有 `volatile`，ReleaseFast 下这个循环就是教科书级的优化事故。

### ⚠️ volatile 不是并发工具

这是原书专门一节、也是面试高频坑：`volatile` **不保证原子性、不建立线程间可见性、不防数据竞争**。`p.* = p.* + 1` 拆成一读一写两次访问，两个线程同时做照样丢更新。分工表：

| 场景 | 工具 |
|---|---|
| 硬件寄存器 / 中断改的内存 | `*volatile T` |
| 线程间共享标志 / 计数器 | `std.atomic.Value(T)`（19.7） |
| 线程间共享复杂结构 | `std.Io.Mutex` 等锁原语（19.5） |

C/C++ 老兵特别容易把 volatile 当线程同步用——那是 C11 之前就澄清过的误会，Zig 里没有任何理由复活它。

## 36.3 指针 ↔ 整数：`@intFromPtr` 与 `@ptrFromInt`

地址就是个整数，`@intFromPtr(&x)` 拿到它（`usize`）；反向 `@ptrFromInt(addr)` 把整数当地址用。正当场景：系统级调试打印地址、内存映射硬件的固定地址（`@ptrFromInt(0x4000_0000)` 这种）、侵入式数据结构里做地址运算。示例 36.3 的测试做了个往返：地址出去、指针回来，值还是 42。

### ⚠️ 0.17 实测：`@ptrFromInt` 当场查对齐

探针把 `0x...3`（4 的倍数都不是）喂给 `@ptrFromInt` 当 `*u32`，**panic 发生在转换那一行，不是解引用那一行**：

```
thread 21800 panic: incorrect alignment
F:\tmp\probe36\p7.zig:6:21: 0x7ff8... in main
    const p: *u32 = @ptrFromInt(n);
                    ^
```

即：0.17 在安全模式下给 `@ptrFromInt` 内建了对齐检查——目标类型要求 4 对齐，地址不是 4 的倍数，立刻 panic。这跟旧资料"指针错了等解引用才炸"的描述不同：炸得更早，栈回溯直接指到罪魁祸首。（ReleaseFast/Small 下检查消失，对齐违规降级为 UB——安全模式的检查是训练轮，不是保险。）

## 36.4 `@ptrCast` + `@alignCast`：按别的类型重解释**内存**

经典场景：网络包、文件头、硬件寄存器块——手里一串字节，要按结构去看它。原书的"战利品箱"例子：4 个字节 `[4]u8{0x78,0x56,0x34,0x12}` 当小端 `u32` 读出来是 `0x12345678`。示例 36.4 的 `readU32LE` 就是这件事：

```zig
const p: *align(4) const u8 = &buf[0];
const w: *const u32 = @ptrCast(@alignCast(p));
```

### 为什么两个内建必须配对

- `@ptrCast` 只改"怎么解释这块内存"：`*u8` → `*u32`，它**不管对齐**。
- `u32` 要求地址 4 对齐。谁来保证？`@alignCast`——它是你对编译器签的**对齐断言**："我知道这个地址满足目标对齐。"

拆开的用意是**把危险显式化**：看到 `@ptrCast` 你知道有重解释，看到 `@alignCast` 你知道有人在对对齐拍胸脯。拍错了呢？0.17 实测（探针 fail5）：对奇数地址 `@alignCast` 成 `*u32` 后解引用，Debug 下当场 `panic: incorrect alignment`，栈回溯指向 `@ptrCast(@alignCast(p))` 那一行。

那什么时候 `@alignCast` 不是撒谎？示例里 `buf` 声明为 `[8]u8 align(4)`——**对齐是花钱买来的**：声明处多付了对齐，转换处的断言就是真话。判据一句话：`@alignCast` 的正当性永远来自**内存来源处的对齐证据**，不是来自"我试了没崩"。

> 更稳的替代：`std.mem.bytesAsSlice` / `std.mem.bytesToValue` / `std.mem.asBytes` 在 0.17 都还在（mem.zig 4429/4576/4596 行）。它们在类型系统里走一遍，不用裸 `@ptrCast`。需要把字节缓冲区当 `[]T` 用时优先这条路，`@ptrCast` 留给它们表达不了的场合。

## 36.5 `@bitCast`：按别的类型重解释**值**

另一个内建，另一件事。`@bitCast` 不碰内存：输入一个值，输出同样位数的另一个类型的值，位模式原样搬运。`f32(1.0)` 的位是 `0x3F800000`（示例 36.5），RGBA 打包、协议编解码、哈希搅拌都靠它。

两个内建的分工判据（原书给出、本章实测成立）：

| | `@ptrCast` | `@bitCast` |
|---|---|---|
| 作用对象 | 一块**内存**（经指针） | 一个**值**（拷贝语义） |
| 宽度要求 | 指针永远同宽 | 源与目标**位数必须相等** |
| 编译期可算 | 否 | **是**（示例：`comptime f32Bits(2.0)`） |
| 典型危险 | 对齐撒谎 | 位数不符编译就拒 |

能说出"我要重解释的是一个值"就别用指针——`@bitCast` 更简单也更安全。⚠️ 0.17 的一个收紧：`@bitCast` 拒绝裸结构体（17 章记过），结构体位级搬运要走 `std.mem.asBytes` 或先 `packed`/`extern` 化。

## 36.6 单项、多项、数组指针：0.17 的下标新规

三种指针形态的能力表：

| 类型 | 解引用 | 下标 | 算术 | 长度 |
|---|---|---|---|---|
| `*T` | `p.*` | ✗ | ✗ | 恒为 1 |
| `*[N]T` | `p.*` | `p[i]` | ✗ | 编译期知 N |
| `[*]T` | `p.*` | `p[i]` | **只能经下标**（0.17 新规） | 不知道，你保证 |

### ⚠️ 0.17 实测：`[*]T` 不再接受 `(p + 2).*`

旧代码和旧书都写 `(p + 2).*`，0.17 直接编译错误：

```
error: index syntax required for unknown-length pointer type '[*]i32'
    try std.testing.expectEqual(@as(i32, 30), (p + 2).*);
                                              ~~~~~~~^~
```

报错信息本身就是修法：写 `p[2]`。语言层面的用意是**把"多项指针上的移动"统一成一种语法**，`p[i]` 等价于旧的 `(p + i).*`。手写指针算术的场景（解析器、环形缓冲）照写 `p[i]`，语义不变。

`[*]T` 的长度全靠自己保证；想让长度归语言管，尽早切片化：`p[1..3]` 得到 `[]i32`（示例 36.6）。原书还有一条纪律值得背：**别徒手改 `slice.ptr` 而不同步改 `len`**——造出来的"说谎切片"越界检查也救不了你，因为它的长度本来就是假的。切片是胖指针（地址+长度），胖就胖在这两个字段必须同生同死。

## 36.7 零尺寸类型：不占内存的类型公民

`@sizeOf(T) == 0` 的类型是一等公民：`void`、`u0`/`i0`、`[0]T`、字段全是 ZST 的结构体、单标签枚举。示例 36.7 的测试逐个钉住了四个：

```zig
try std.testing.expectEqual(@as(usize, 0), @sizeOf(void));
try std.testing.expectEqual(@as(usize, 0), @sizeOf(struct {}));
try std.testing.expectEqual(@as(usize, 0), @sizeOf([0]u8));
try std.testing.expectEqual(@as(usize, 0), @sizeOf(u0));
```

### 实测：零尺寸变量的地址都是 1

main 里打印了两个零尺寸局部变量的地址：

```
@sizeOf(void)=0；两个零尺寸变量地址：0x1 / 0x1
```

不占内存的东西不需要真地址，0.17 干脆给它们一个常量地址 `0x1`。**别对 ZST 的地址做任何假设**——语言不承诺相同也不承诺不同，它压根没有"地址"这个概念下的资源。

### 用途一：`HashMap(K, void)` 就是 Set

哈希表的值位填 `void`——不存值、只占键——立刻得到一个零成本的集合：

```zig
var set = std.StringHashMap(void).init(std.testing.allocator);
try set.put("apple", {});
try std.testing.expect(set.contains("apple"));
```

没有 `void` 你就得发明 `put("apple", true)` 这种"值位是装饰"的丑写法，或者引一个专门的 Set 类型。37 章 FileGuard 的"路径分配台账"用的正是这个手法。

### 用途二：泛型里的"优化掉"

写泛型容器时，某个字段/参数在特定实例化下没有意义，就让它变成 `void`——编译期整个蒸发，运行期零开销。这是 Zig 泛型"单态化 + ZST"组合拳的标准招式。

### `void` ≠ `anyopaque`

一对容易混的概念：**`void` 是"确定什么都没有"（零尺寸）；`anyopaque` 是"有东西但我不说是什么"（未知类型，非零尺寸）**。前者是终点，后者是隧道——隧道通向下一节。

## 36.8 anyopaque：类型擦除的通用指针

C 的 `void*` 在 Zig 里的对应物是 `*anyopaque`：任何单项指针都能隐式强转过去，类型信息到此为止。示例 36.8 建了个最小"异质登记处"——`Entry{ ptr: *anyopaque, type_name: []const u8 }`，一个 `i32` 一个 `f64` 混在同一张表里。

找回类型靠 `@ptrCast(@alignCast(...))` 转回来，**正确性全由调用方负责**——`anyopaque` 自己什么都不记得，转错类型就是 36.4 那条 panic 或 UB。所以惯例是像示例那样**成对登记类型名**（`@typeName` 是编译期字符串，零成本），或者带函数指针做 vtable。C 互操作里的回调 `user_data`、通用容器里的元素指针，都是它的正当岗位。

## 36.9 强转（coercion）与 peer 类型解析

### coercion 的白名单哲学

Zig 的隐式强转是**白名单制**：编译器证明无损失才放行。白名单上的条目：整数/浮点宽化、加 const、降对齐要求、定长数组 → 切片、`T` → `?T`、`T` → `E!T`、同质元组 → 数组。不在名单上的一律编译错误，逼你写显式内建：`@intCast`（装不下运行期 panic）、`@floatCast`（可能丢精度）、`@truncate`、`@intFromFloat`（截断不是四舍五入，03 章记过）、`@floatFromInt`。

这套设计的回报是**代码的可读性分级**（原书的精彩论点）：看到裸赋值 `u8 → u16` 就知道绝对安全；看到 `@intCast` 就知道此处有截断风险，review 时该多看一眼。**危险全部有名字**。

### peer 类型解析：给分支找公共类型

`if`/`switch` 表达式、块的多个 `break`、数组字面量，都要求各分支能折向**同一个类型**——编译器替各分支找一个大家都能安全 coerce 进去的公共超类型，这就是 peer 类型解析。示例 36.9 的测试钉住了七种能成的格局（全部 0.17 实测）：

| 格局 | 例子 | 结果类型 |
|---|---|---|
| ① 同型 | `u8` 与 `u8` | `u8` |
| ② 字面量折向 | `u8` 与 `comptime_int 20` | `u8` |
| ③ 数值宽化 | `i16` 与 `u8` | `i16` |
| ④ 整→浮 | `u8` 与 `f32` | `f32` |
| ⑤ 值与 null | `u8` 与 `null` | `?u8` |
| ⑥ 值与错误 | `u8` 与 `error.Boom` | `E!u8` |
| ⑦ 可变性宽化 | `[]u8` 与 `"字符串字面量"` | `[]const u8` |

找不到公共类型就是硬编译错误，报错把两宗类型都指给你看：

```
error: incompatible types: 'u8' and 'bool'
    const v = if (blk.v) @as(u8, 1) else true;
              ^~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
note: type 'u8' here / note: type 'bool' here
```

### ⚠️ 实测坑一：`_ = if...` 的结果位置是 void

写探针时我一度以为 peer 解析"失灵"了——`if (blk.v) @as(u8, 1) else true` 居然编译通过。真相：**`_ =` 给了表达式一个 void 结果位置**，两个分支只需各自 coerce 到 void，而任何类型都能 coerce 到 void，于是解析根本不会发生。结论：peer 解析是**结果位置驱动**的，想观察/依赖它，必须给表达式一个真实类型上下文（`const v: T = ...` 或 `const v = ...` 后用 `@TypeOf`）。

### ⚠️ 实测坑二：comptime 已知条件下，走不到的分支不参与解析

`const cond = true; if (cond) @as(u8,1) else @as(f32,1.5)` 的结果类型是 **u8**——条件编译期已知，分支直接折叠，f32 那支从未参与解析，结果类型就是被选中那支的类型。把条件换成运行期才知（示例用全局变量 `runtime_flag`），同样的表达式结果类型立刻变成 f32。**教学/调试时别用 comptime 常量当探针条件**，你测到的不是解析规则，是分支折叠。

## 36.10 [*c]T：C 指针的四宗罪与进门转换纪律

`[*c]T` 是 translate-c 为对齐 C 的宽松指针语义保留的类型——0.17 实测它依然健在：`zig translate-c` 一个 `int* get_ptr(int *p, int n)` 头文件，产物照旧是：

```zig
pub extern fn get_ptr(p: [*c]c_int, n: c_int) [*c]c_int;
```

它对 C 忠诚的方式就是四宗罪（示例 36.10 逐条演示）：

1. **可下标**——`p[1]` 越界没人拦；
2. **可算术**——`p + 2` 随便走；
3. **可空**——`[*c]c_int` 可以直接赋 `null`，然后被解引用；
4. **与整数/其他指针自由互转**——C 的那套"指针即整数"乱象照单全收。

手写 Zig 代码**几乎永远不该用** `[*c]T`（它的唯一岗位是 translate-c 的产物忠实匹配 C 源码）。从 C 边界拿到 `[*c]T` 的纪律是**进门立刻转换**：判空（非空才继续）→ 判对齐（必要时 `@alignCast`）→ 转成带长度的切片（`p[0..len]`）或真 Zig 指针，之后全部按 Zig 规矩玩。28 章直调 Winsock、32 章直链 SQLite 全是这个姿势。

## 36.11 位对齐指针：packed 结构体字段的地址

`packed struct { a: u3, b: u5 }` 总共 1 字节，`a` 占第 0–2 位。对 `a` 取址得到什么？示例 36.11 实测：

```
&f.a 的类型：*align(1:0:1) u3
```

类型里那组三元参数 `align(1:0:1)` 逐位读：**字节对齐 1、宿主字节内的位偏移 0、宿主宽度 1 字节**。普通 `*u3` 表达不了"字节中间开始的字段"，所以语言给位对齐指针单独开了一档类型。读写都合法——`pa.* = 6` 由编译器生成"读宿主字节、改位段、写回"的完整序列，测试同时钉住了**邻居字段不被撞**（改 `a` 后 `b` 还是 17）。

这就是为什么 `packed struct` 的字段不能随便把地址递给收 `*u3` 的函数——类型对不上，编译期就拦下。位对齐指针是协议解析和硬件寄存器映射的精密工具，代价是每次访问都是一次读-改-写，别在高频热路径上当普通指针挥霍。

## 36.12 坑位清单

1. `volatile` 只管"每次真读真写"，**不是并发原语**；线程间共享用原子或锁（19 章）。
2. `@ptrFromInt` 在 0.17 安全模式下**转换当场查对齐**——panic 提前到罪魁祸首那一行；ReleaseFast/Small 无此检查。
3. `@ptrCast` 必须配 `@alignCast` 才有对齐保证；`@alignCast` 的正当性来自内存来源的对齐证据（如 `align(4)` 声明），撒谎在安全模式 panic、在快模式 UB。能用 `std.mem.bytesAsSlice/bytesToValue/asBytes` 就别裸 cast。
4. 重解释**值**用 `@bitCast`（同宽、可 comptime）；重解释**内存**用 `@ptrCast` 系。0.17 `@bitCast` 拒裸结构体。
5. 0.17 的 `[*]T` **必须下标语法** `p[i]`，`(p + i).*` 编译错误。
6. 别徒手改 `slice.ptr` 不同步 `len`——说谎的切片连越界检查都是假的。
7. ZST 的地址无意义（0.17 实测全是 `0x1`）；`HashMap(K, void)` 是标准 Set 写法。
8. `void`（确定没有）与 `anyopaque`（有但不说）是两回事；`anyopaque` 找回类型的正确性全在调用方。
9. peer 解析由**结果位置**驱动：`_ =` 给 void 位置时解析不发生；comptime 已知条件下未选中分支不参与解析——做实验时这两件事都会骗你。
10. `[*c]T` 只该出现在 translate-c 产物里；进门立刻"判空→判对齐→切片化"。
11. 位对齐指针 `*align(1:0:1) u3` 与普通 `*u3` 类型不通，访问是读-改-写，热路径慎用。
