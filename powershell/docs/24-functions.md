# 24 函数与作用域——把命令装进名字里

> 本章是扩充章（原书第 21 章的函数小节 + 第 27 章"学无止境"指路清单的展开）。第 22 章结尾预告过：脚本之上是函数。函数让"一串命令"变成"一个名字"，是工具制作的第一块积木。

## 24.1 从脚本到函数：一步之遥

第 22 章的 `Get-DiskInventory.ps1` 换个壳就是函数：

```powershell
function Get-DiskInventory {
    param(
        [string]$ComputerName = 'localhost',
        [int]$DriveType = 3
    )
    Get-CimInstance -ClassName Win32_LogicalDisk -Filter "DriveType=$DriveType" |
        Select-Object DeviceID,
            @{ Name = '空闲(GB)'; Expression = { [math]::Round($_.FreeSpace / 1GB, 1) } }
}
```

三处变化：文件名变函数名（**沿用 Verb-Noun**，`Get-Verb` 里的批准动词）；`param()` 进函数体；命令序列原封不动。从此 `Get-DiskInventory -DriveType 3` 像原生命令一样调用——**你已经给自己造了一个 Cmdlet 的雏形**。

函数的解剖：`function 名字 { param(...); 主体 }`。param 依然是第一句（函数体内的第一句可执行代码）；主体里可以用第 23 章的全部武器（验证属性、注释帮助、CmdletBinding——25 章主角）。

## 24.2 返回值的真相：函数输出一切

PowerShell 函数的返回值规则与多数语言**根本不同**，吃透它省掉一类经典困惑：

> **函数输出"进入管道的一切东西"。`return` 只是"输出并退出"的语法糖。**

看对照：

```powershell
function Get-One {
    '管道里的这句会输出'
    Write-Host '直写屏幕的这句不算输出'
    Get-Process -Id $PID          # 这句的结果也进输出！
    return '最后一句 return'
}
$r = Get-One
@($r).Count      # 3！——三段"进管道"的东西都在
```

三个输出源（裸字符串、命令结果、return 的值）**汇成一个输出流**；`Write-Host` 直写屏幕不掺和。这条规则的两个推论：

- **函数里每一行都在决定输出**——误写一行裸表达式（比如调试用的 `$var`），它的值就悄悄混进返回值，调用方拿到多余对象。这就是第 21 章"丢弃要显式"的根源：不想输出的语句要 `$null =` 或 `| Out-Null`。
- **`return 5` 与裸写 `5` 等价**（都把 5 放进管道），return 的价值在"顺便退出"。要"只返回一个东西"的函数，主体里管好每一条会产生输出的语句。

## 24.3 作用域：变量的楼层规则

**作用域（scope）是变量的"楼层"**：全局层（会话级）、脚本层（.ps1/函数调用级）、局部层（函数/脚本块内）。三条规则讲完全部日常：

**规则一：读向下透，写不透。** 函数里读一个外面定义的变量——沿楼层**向下找**（局部 → 脚本 → 全局），找得到就能用；但在函数里**赋值**只写当前楼层（**遮蔽**，shadowing）：

```powershell
$x = 'outer'
function Set-X { $x = 'inner'; "函数里：$x" }
Set-X               # 函数里：inner
$x                  # outer —— 外面的 $x 没被动过
```

**规则二：要跨层写，用作用域修饰符。** `$script:x`（写脚本层）、`$global:x`（写全局层）、`$local:x`（显式当前层，少见）：

```powershell
function Set-X2 { $script:x = 'changed' }
Set-X2
$x                  # changed —— 修饰符让写入穿透楼层
```

**规则三：函数看不到调用者的局部变量**——它的"下层视野"取决于**它定义/加载的位置**，不是调用的位置（词法作用域）。实践含义：**函数要什么就通过参数拿**，别依赖"碰巧在外面有个同名变量"。

`$using:`（第 15/16 章）就是这套规则的远程版：跨环境（进程/runspace）时连"读向下透"都不成立，必须显式传值。

## 24.4 函数库的组织：从零散到文件

函数写在会话里，关窗即失。三种持久化形态按成熟度排：

**形态一：函数库脚本（lib.ps1）+ 点源**。把一批函数放进一个文件，用第 22 章的点源加载：

```powershell
. .\MyLib.ps1          # 库里所有函数进入当前会话
```

简单直接，小团队够用。缺点：没有版本、没有依赖声明、必须记得点源。

**形态二：模块（.psm1）**——自动发现与加载，函数的"正规编制"，第 27 章主角。

**形态三：profile 常驻**。最常用的三五个函数写进 `$PROFILE`（第 02 章），每次开 Shell 即可用——个人效率工具的标准归宿。

选择路径：**先在会话里把函数调通 → 稳定了进库文件 → 团队要用了升级成模块**。函数代码本身一字不改，只是"住处"升级——这正是函数与脚本相比的架构优势。

## 24.5 写好函数的六条纪律

1. **Verb-Noun 命名**，名词带产品前缀（`Get-InvMachine`）防撞名（第 07 章）；
2. **参数化一切变化**：函数体里不写死"会变的东西"（机器名、阈值、路径）；
3. **输出对象**（Select-Object 结果），不输出 Format-*（第 23 章的理由原样有效）；
4. **不想输出的语句显式丢弃**（`$null =`），守住返回值纯净；
5. **依赖通过参数进来**，不依赖外层变量（规则三）；
6. **给每个函数写注释帮助**——哪怕只有 SYNOPSIS，三个月后你会感谢自己。

## 24.6 本章高频坑位

| 现象 | 原因 | 对策 |
|---|---|---|
| 函数返回值多出莫名其妙的对象 | 主体里有裸表达式/命令结果混进管道 | 逐行审"这行输出吗"；不要的 `$null =` |
| 函数里改变量外面没变 | 写不透楼层（遮蔽） | `$script:`/`$global:` 修饰符或改用返回值 |
| `return $a; return $b` 只拿到一个 | return 即退出 | 返回数组 `return $a, $b`；或分开输出 |
| 函数在别人机器上"少函数" | 库没加载/模块没装 | `#Requires -Modules`（23 章） |
| 函数名与内置命令撞了 | 命名没带前缀 | 函数优先级高于 Cmdlet（第 04 章）会遮蔽内置——加前缀 |
| 递归函数变量互相踩 | 同名局部层 | 每层用自己的参数与局部变量（递归靠参数传状态） |

## 24.6.1 调试函数的三招

函数写错时的三个定位招式（从轻到重）：

**招一：Write-Debug / Write-Verbose 植桩**。在可疑位置插 `"到这里 x=$x"` 的 verbose 输出，调用时 `-Verbose` 点亮——比裸 Write-Host 规范（不污染输出流），比注释掉的调试语句优雅（不用删）。

**招二：Set-PSBreakpoint 断点**。命令行调试器（ISE/VS Code 有图形版，这里给纯命令形态）：

```powershell
Set-PSBreakpoint -Command Get-DiskInventory     # 命令断点：调用即停
Set-PSBreakpoint -Script .\lib.ps1 -Variable x -Mode Write   # 变量写入断点：x 一被赋值就停
Get-PSBreakpoint; Remove-PSBreakpoint           # 管理断点
```

停下后进入调试提示符，`c` 继续、`v` 单步、`?` 看全部命令——排"变量为什么是这个值"类问题的利器。

**招三：拆段验证**。函数体复制到临时脚本，param 换成硬编码值，逐段 F8 跑（第 22 章）——把"函数调用链"压平成"裸脚本"，排除作用域与绑定因素的干扰。

## 24.6.2 常见问答

**问：函数名可以覆盖内置命令吗？**
可以且常见（你早就在这么干：`mkdir`、`cd` 都是函数覆盖/包装），但要**有意为之**：会话里定义 `Get-Process` 函数会遮蔽内置 Cmdlet（第 04 章优先级）。规范做法仍是前缀命名（`Get-TutProcess`），真要包装内置命令就保留动词名词并在帮助里说明差异。

**问：函数里定义函数（嵌套）可以吗？**
语法允许（内层函数只在外层作用域可见），但**读代码的人会痛**。需要复用的小工具提到库层，需要隐藏的实现拆文件——嵌套定义留给"真的只在一处用"的场景。

**问：参数太多怎么办（十几个）？**
两个方向：合并成对象参数（`[pscustomobject]$Config`——配置类参数的集合）；或拆成参数集（`ParameterSetName`，第 03/25 章）。更根本的答案：**参数多往往是函数职责太杂**——拆函数比加参数健康。

## 24.6.3 函数设计的三个层级

用同一份"磁盘查询"需求看函数的三个成熟层级（也是本章到 25/27 章的路线图）：

```powershell
# 层级一：参数化脚本（22-23 章）——一个文件一个任务
.\Get-DiskInventory.ps1 -ComputerName SRV1

# 层级二：函数（本章）——进会话、可组合、可入库
Get-DiskInventory -ComputerName SRV1 | Where-Object 空闲比 -lt 0.2

# 层级三：管道化高级函数 + 模块（25/27 章）——与 Cmdlet 平权
'srv1','srv2','srv3' | Get-InvDiskInfo -MinFreePct 10 | Export-Csv report.csv
```

每升一级，**调用方的表达力**上一个台阶：层级一只能"执行"，层级二能"组合"，层级三能"流入流出一整条流水线"。判断你该停在哪级的标尺是**复用面**：自己用三次以内→层级一；自己天天用→层级二；团队要用/要进管道→层级三。 premature 的架构是浪费，缺位的封装是债务——两头都别占。

## 24.7 本章要点

- 函数=带名字的脚本：`function Verb-Noun { param(); 主体 }`，命名与参数规则全部继承。
- **输出真相：一切进管道的都是返回值**；return 是语法糖；不想输出要显式丢弃。
- 作用域三规则：读向下透、写不透（`$script:` 可穿透）、函数不依赖调用者局部变量。
- 组织三级：会话 → 库文件点源 → 模块（27 章）→ 常用进 profile。
- 六条纪律：前缀命名、参数化、输出对象、显式丢弃、参数依赖、随手写帮助。

**动手实验**：① 把第 22 章的磁盘脚本改写成函数并调用；② 写 `Get-One` 验证"三源汇流"（数返回值个数）；③ 复现 24.3 的遮蔽实验，再用 `$script:` 穿透；④ 建一个 `MyLib.ps1` 放两个函数，点源后调用；⑤ 在函数里故意留一行裸 `$debug`，观察它如何污染返回值。

实验参考：②`@($r).Count` 是 3——Write-Host 那句屏幕可见但不在 `$r` 里；⑤污染的对象在返回数组末尾——这类 bug 的典型症状是"调用方 `| Select-Object -First 1` 拿到意外对象"。
