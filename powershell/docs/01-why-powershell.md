# 01 为什么是 PowerShell——背景与心智模型

> 本章对应原书第 1 章"背景介绍"，并补充了原书出版（2017 年）之后的版本史与现代工具链。

在动手敲第一条命令之前，值得先回答一个问题：为什么值得花一个月的午餐时间学 PowerShell？答案不是"因为它预装在 Windows 里"，而是**它能改变你完成工作的方式**。本章把这个心智模型立起来，后面 33 章都建立在这个模型之上。

## 1.1 没有 PowerShell 的世界：GUI 的三个死穴

Windows 管理员的直觉是打开图形界面（GUI）：展开"计算机管理"、点开向导、勾选复选框。GUI 当然有它的价值——**它是学习工具**。作者 Don Jones 回忆自己第一次展开 Active Directory 用户和计算机时，通过点按钮、看提示、右键菜单，很快摸清了这个工具能做什么。GUI 把"能做的一切"摊在你眼前，这是它无可替代的优点。

但 GUI 作为**生产工具**有三个结构性缺陷，每一个都无法靠"更熟练地使用 GUI"弥补。

**死穴一：不可自动化。** 设想在 Active Directory 里新建一个用户需要 5 分钟——填写姓名、登录名、密码、所属组等一系列表单。第 100 个用户仍然需要 5 分钟：100 个用户就是 500 分钟。你的手速不会因为重复而变快，因为瓶颈根本不在你，而在"必须由人点完这个向导"本身。GUI 把每个任务都钉死成一次性的手工劳动。

**死穴二：一致性差。** 人会疲劳、会走神。同一个任务做 100 遍，第 87 遍时少勾了一个选项、第 93 遍时把用户名拼错了。GUI 依赖人的可靠性，而人恰恰是最不可靠的执行者。命令行恰好相反：**同一条命令重复执行一万次，结果完全一致**——这不是纪律问题，是机制问题。

**死穴三：不可组合。** GUI 向导是一个个孤岛："新建用户"向导不能把"导出 CSV 里的账号清单"和"给每个账号发欢迎邮件"串起来。命令天然是可以组合的：一条命令的输出可以直接喂给下一条命令，像水管一样接起来。

微软并非没有尝试过解决这些问题。批处理（Batch）、KiXtart、VBScript 都是先行者，其中 VBScript 最成功：花一小时写一段 VBScript 把 CSV 文件里的新用户导入 Active Directory，之后每次几秒钟就能完成同样的工作。但 VBScript 有个致命伤——微软从未把"所有管理功能都可被脚本访问"作为硬性要求。你想用 VBScript 改网卡 IP，可以；想查网络连接速度，不行，因为没有人记得把这个功能暴露给脚本。PowerShell 的架构师 Jeffrey Snover 把这种现象称为**"最后一英里"问题**：旧的脚本技术总能在离终点一步之遥的地方让你失望。

PowerShell 就是微软对"最后一英里"的正面回答：**微软承诺 Windows 的一切管理功能都可以通过这个 Shell 完成**。

## 1.2 GUI 反过来跑在 PowerShell 之上

理解 PowerShell 地位的最好方式，是看方向反转：不是"PowerShell 补充 GUI"，而是"GUI 跑在 PowerShell 之上"。

从 Exchange Server 2007 开始，微软多个产品线采取了同一套开发方法：**先实现 PowerShell 命令，再在命令之上搭建 GUI**。Exchange 管理控制台里点一个按钮，底层执行的是一条 PowerShell 命令——GUI 的按钮甚至会在界面上把这条命令显示给你。SharePoint 2010、System Center 全家、Office 365、Windows 自身的大量组件都走了这条路。Windows Server 2012 之后的版本，几乎每个管理界面都能找到对应的 PowerShell 实现。

这个方向反转带来两个直接后果：

1. **GUI 里有的，命令行里一定有**。你不会遇到"这个设置只能通过向导修改"的尴尬——如果有，那是产品缺陷而不是常态。反过来，命令行里有的，GUI 里不一定有：GUI 为了简洁会隐藏大量选项，命令行才是功能全集。
2. **自动化是"原生能力"而不是"外挂"**。既然 GUI 都建立在命令之上，把命令串成脚本、交给计划任务半夜执行，就是顺理成章的事。

Don 在 2010 年微软 TechEd 大会有句流传很广的话，大意是：未来的 Windows 工程师会分成两类，会用 PowerShell 的和不会用的——后者可以去问问"还要不要来包炸薯条"。玩笑归玩笑，背后的判断已经被验证：DSC（Desired State Configuration）、Azure 管理、Microsoft 365 运维，今天的 Windows 生态里 PowerShell 无处不在。

## 1.3 PowerShell 是 Shell，其次才是脚本语言

这是全书最重要的一个认知，也是原书作者反复强调的出发点。

2006 年 PowerShell 1.0 发布时，学习者大多是 VBScript 老用户，教材自然按"脚本语言"的套路教：先讲变量、再讲循环、再讲函数。但作者们在 2009 年前后发现，越来越多**没有编程背景**的人开始学 PowerShell，旧教法失灵了。原因很简单：

> **PowerShell 首先是一个命令行 Shell（运行命令的环境），脚本只是使用它的方式之一。**

这和 bash、zsh 在 Unix 世界的地位一样：你可以十年不用写一个 .sh 文件，但每天都离不开 shell。学习 PowerShell 的正确顺序因此不是"先学语法再学命令"，而是：

1. **先学会用命令**：查到命令、看懂参数、把结果过滤排序（本教程第 1–12 章）；
2. **再学会跨机器、跨任务地用命令**：远程处理、后台作业、批量操作（第 13–19 章）；
3. **然后才把命令固化成脚本**：变量、输入输出、参数化（第 20–23 章）；
4. **最后把脚本做成别人能用的工具**：函数、模块、错误处理、测试（第 24–33 章）。

你会发现"写脚本"到第 20 章才出现——这不是编排失误。当你能把一串命令在命令行里调通之后，把它抄进 .ps1 文件就是"脚本"了，那天你不需要学任何新语法。过早陷入语法学习的人，往往写出"能跑但用不好管道"的脚本，绕开了 PowerShell 最有价值的部分。

## 1.4 对象的 Shell，不是文本的 Shell

传统 Unix shell（bash 等）里，命令之间传递的是**纯文本**：`ps aux | grep nginx` 里 grep 拿到的是一行行字符串，靠"按空格切分"的约定去猜哪一段是进程名。文本是人读的，不是机器用的，所以 Unix 世界配套诞生了 awk、sed、cut 这一整族"文本整形"工具。

PowerShell 从设计上换掉了这个地基：**命令之间传递的是对象**——有类型、有属性、有方法的结构化数据。`Get-Service` 吐出的不是"一行服务描述文本"，而是一个个 `ServiceController` 对象，`.Name`、`.Status` 都是明确定义的属性，取值不需要切字符串，排序、过滤都直接作用于属性本身。

先建立一个直观印象。下面这条命令统计本机处于"运行中"状态的服务数量：

```powershell
(Get-Service | Where-Object Status -eq 'Running').Count
```

它为什么能这样写？因为 `Get-Service` 输出的每个对象都带 `Status` 属性，`Where-Object` 拿到的不是文本行而是完整对象，过滤后仍是对象集合，`.Count` 是集合自带的属性。整条链路里没有一处"解析文本"。如果这在 bash 里做，你得先想办法让 `service --status-all` 的输出里数 `[+]` 号的个数——一旦输出格式微调，脚本就碎。

对象这个地基是后面 8 章（06–12）的主角，这里只需要记住一句话：**在 PowerShell 里，数据永远是结构化的，你整形数据的方式是选属性，而不是切字符串**。

## 1.5 版本史：从 Windows PowerShell 到 PowerShell 7

PowerShell 的历史有一条清晰的分界线，本教程的"双版本"叙述都源于此。

**2006–2016：Windows PowerShell 时代（v1–5.1）。** v1（2006）确立对象管道；v2（2009）带来远程处理（Remoting）与后台作业；v3（2012，随 Windows 8/Server 2012）带来可更新的帮助系统与工作流；v5/5.1（2015–2017，随 Windows 10/Server 2016）加入类（class）、枚举等语言特性。5.1 是这条线的终点——**它随 Windows 出厂、永远只做维护性修复，不再有新功能**。原书第 3 版正是以这一代为背景写的。

**2016 至今：开源跨平台的 PowerShell 7。** 2016 年 8 月，微软宣布 PowerShell 开源并登陆 Linux 与 macOS（这份"不敢想象的步子"原书作者专门用一节描述）。2018 年 1 月，跨平台版以 6.0 之名正式发布（基于 .NET Core）；2020 年 3 月的 7.0 完成与 5.1 的高度兼容并进入稳定迭代；此后每年 11 月发布一个 7.x，其中 7.2、7.4 为长期支持（LTS）版本。本教程落笔时最新为 7.6。

于是今天机器上通常有**两个 PowerShell 并存**：

| | Windows PowerShell 5.1 | PowerShell 7+ |
|---|---|---|
| 可执行文件 | `powershell.exe` | `pwsh.exe` |
| 随附 | Windows 内置，不用装 | 需单独安装（`winget install Microsoft.PowerShell`） |
| 运行时 | .NET Framework | 现代 .NET（跟随版本升级） |
| 平台 | 仅 Windows | Windows/Linux/macOS |
| 状态 | 维护模式，不再新增功能 | 活跃开发 |

本教程以 **PowerShell 7 为讲解主线**，同时在每个行为分岔处标注 5.1 的差异——因为大量企业环境里 5.1 仍然在场，且它"开机就有"。两者的日常命令绝大多数一致，差异集中在：5.1 缺少新语法（如 `&&`、三元运算符）、部分老命令（如 `Get-WmiObject`）在 7 中被移除、默认编码不同（第 17 章有编码专题）。

随时可以这样查看自己所在的引擎与版本：

```powershell
$PSVersionTable
```

输出是一张表：`PSVersion` 是版本号；`PSEdition` 显示 `Desktop`（5.1）或 `Core`（7+）；`OS` 行在 7+ 里直接标明操作系统，5.1 里则没有这一项——这也是快速分辨两个引擎的办法之一。注意**版本号永远不要靠猜**，`$PSVersionTable` 是权威答案。

把这条时间线连起来看（记不记无所谓，混个眼熟即可，遇到老资料时知道它在哪个年代）：

| 年份 | 版本 | 里程碑 |
|---|---|---|
| 2006 | 1.0 | 对象管道、Verb-Noun 命名诞生 |
| 2009 | 2.0 | 远程处理（Remoting）、后台作业、高级函数雏形 |
| 2012 | 3.0 | 可更新帮助、工作流，随 Server 2012 全面铺开 |
| 2013–2015 | 4.0 / 5.0 | DSC；class、enum 进入语言 |
| 2017 | 5.1 | Windows PowerShell 线终点，随 Win10/Server 2016 出厂 |
| 2016–2018 | 开源 → 6.0 | GitHub 开源、登陆 Linux/macOS（基于 .NET Core） |
| 2020 | 7.0 | 与 5.1 高度兼容的稳定跨平台版 |
| 2021– | 7.1/7.2/…/7.6 | 年度迭代，7.2/7.4 为 LTS |

## 1.6 三类读者，一条路线

PowerShell 团队把使用者分为三类，本教程按同样的顺序覆盖：

1. **命令行使用者**：用命令和第三方工具完成日常管理——见效最快，第 1–19 章的目标；
2. **工具制作者**：把常用流程封装成带参数的工具，交给团队里经验较浅的同事直接使用——第 20–33 章的目标；
3. **工具开发者**：开发可复用的模块与程序——本教程打地基，方向在第 33 章指明。

原书（一本入门书）主要服务第一类人；本教程把第二类也完整覆盖进来，因为"能自动化自己"和"能给别人做工具"之间隔着的正是函数、模块、错误处理、测试这几块硬骨头。即使你最终目标是第三类，也必须从第一类开始——不懂 Shell 运行机制的人写出来的工具，在 Shell 里用起来总是别扭的。

## 1.7 动手环境与现代编辑器

原书落笔时，Windows 上的主力编辑器还是自带的 ISE（集成脚本环境）。**ISE 已随 5.1 一起停止演进，不再支持 PowerShell 7**，今天的选择是：

- **终端**：Windows Terminal（Windows 11 内置）配色、分页、字体都远胜老式控制台窗口；
- **编辑器**：Visual Studio Code + 官方 **PowerShell 扩展**——语法高亮、断点调试、集成终端、PSScriptAnalyzer 实时提示，一处搞定。

你只需要保证两件事：一，能打开一个 pwsh 会话（本教程示例都假设 `pwsh` 可直接运行）；二，写脚本时有基本的高亮。实验环境用你自己的开发机即可——本教程所有示例都设计成**只读或自清理**，不会留下垃圾、更不会改系统配置；涉及系统级配置（如启用远程处理）的章节只讲清楚步骤，由你在自己的实验机器上决定是否执行。

## 1.8 本章要点与坑位预告

- GUI 是学习工具，命令行是生产工具：**可自动化、一致、可组合**是 Shell 的三大结构性优势。
- "最后一英里"催生了 PowerShell 的承诺：一切管理功能皆可用命令完成；如今 GUI 跑在命令之上。
- **先当 Shell 用户，再当脚本作者**——脚本只是命令的存档，第 20 章之前请忍住不写 .ps1。
- PowerShell 传递**对象**而非文本；整形数据靠选属性，不靠切字符串。
- 版本二分：5.1（`powershell.exe`，内置、维护模式）与 7+（`pwsh`，跨平台、活跃开发）；`$PSVersionTable` 是身份证明。

两个坑先记下，后面章节会展开：**中文 Windows 的控制台默认代码页是 GBK**，与工具链交换 UTF-8 文本时要显式设置编码（第 05 章起会看到处理办法）；**含中文的 .ps1 文件必须存成 UTF-8 带 BOM**，否则 5.1 会按 ANSI 解析出乱码甚至语法错误（第 17 章专题）。

## 1.9 常见误解快问快答

初学阶段值得提前拆掉的几个误解，都是原书作者在教学一线反复被问到的：

**问：PowerShell 就是"蓝色的 cmd"吧？**
不是。cmd 是文本 Shell（还是 1980 年代 DOS 的直系后代），PowerShell 是对象 Shell，有自己的语言、自己的命令体系和自己的远程协议。它们唯一的相似是"都在终端窗口里敲字"。

**问：那 cmd 和批处理是不是要被淘汰了？**
没有。cmd 仍会长期存在（大量老安装脚本、系统任务依赖它），你也不需要"戒掉"它。正确的关系是：PowerShell 能做 cmd 能做的一切，还多做很多——所以新任务、新脚本没有理由再选 cmd。

**问：PowerShell 是编程语言吗？我要先学 C# 吗？**
PowerShell 有一门完整的语言（第 20 章起系统讲），但如本章所述，**先做使用者**，语言是后期需求。C# 不是前置条件；反过来，懂 .NET 会让你的 PowerShell 上限更高（第 08 章会看到两者如何在对象层面无缝衔接），但那是锦上添花。

**问：听说 PowerShell 是黑客工具，开启它不安全？**
"PowerShell 无所不能"指的是**在你已有权限的范围内**——它不会提权、不会绕过 ACL（第 17 章专题讲安全模型）。攻击者爱用它恰恰因为它在管理员手里太好用；防御思路是日志与执行策略，而不是禁用它。

**问：学 5.1 还是学 7？**
按本教程的主线学 7，差异处都有标注。7 是 5.1 的超集（个别老命令除外），学会 7 回头用 5.1 几乎零成本；反过来则会带着旧习惯踩新坑。

**问：除了管 Windows，它还有什么用？**
它是一门通用自动化语言：Azure/Microsoft 365 的管理面几乎全是 PowerShell（Az 模块、Microsoft Graph）；CI/CD 流水线里的构建脚本、Windows 上的开发环境配置、日常文件批处理都是它的地盘。7 跨平台之后，"同一套脚本管 Windows 服务器和 Linux 容器"也成为现实场景。

## 1.10 提前看一眼"组合"的力量

为了给"可组合"一个具体画面，这里提前用一次管道（第 06 章正式讲），你现在不需要理解语法，只需要感受任务形态。需求：找出本机处于"运行中"的服务里名字以 W 开头的，按显示名排序，只取名字和状态两列。

```powershell
Get-Service |
    Where-Object { $_.Status -eq 'Running' -and $_.Name -like 'W*' } |
    Sort-Object DisplayName |
    Select-Object DisplayName, Status
```

把四个命令竖着排（行尾的 `|` 是续行），一眼能看出这是**四个各司其职的小命令接力**：

- `Get-Service` 只负责"取全部服务"；
- `Where-Object` 只负责"按条件筛"（`$_` 代表当前流经的对象）；
- `Sort-Object` 只负责"排序"；
- `Select-Object` 只负责"挑两列"。

输出大约长这样（你机器上的条目会不同）：

```
DisplayName                                    Status
-----------                                    ----__
Windows Audio                                 Running
Windows Event Log                             Running
Windows Management Instrumentation            Running
```

逐行读这张输出：表头是两个属性名——因为 `Select-Object` 挑的就是 `DisplayName` 和 `Status` 两个属性；每行是一个服务对象被格式化后的样子。**重要的一点**：这条命令在 GUI 里的等价操作是"打开 services.msc → 点状态列排序 → 肉眼找 W 开头的 → 手抄成表"——三分钟的手工活变成了一条可复用、可存档、可发给同事的命令。而需求变化时（比如改成"停止的、按名字排"）只改两处参数，这就是"可组合"在日常工作里的样子。

这一步也埋下了全书最重要的一条纪律：**每个命令只做一件事，把"做哪件事"的选择权留给管道的下一段**。反面教材是一行百来个字符的"巨命令"——功能一样，但没人读得懂、没人敢改。

**动手实验**：打开 pwsh，运行 `$PSVersionTable`，确认 `PSVersion` 与 `PSEdition`；再运行 `(Get-Service).Count` 与 `(Get-Process).Count`，感受"一条命令得到结构化答案"；把上面 1.10 的组合命令抄进去跑一遍，再试着把 `'W*'` 改成你自己名字的首字母；最后试试 `Get-Date | Get-Member -MemberType Property`，你会看到"日期对象有哪些属性"的完整清单——不要求看懂，先感受"一切都是对象"。

对应示例（可选）：`examples/01_why_powershell/`——用一组命令演示"批量创建、重复执行结果一致、自动清理"的自动化闭环。
