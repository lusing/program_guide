# 01 · 开篇：为什么 C++ 程序员要重学设计模式

## 意图与动机

如果你写过三年以上的 C++，多半遇到过这样的场景：一个函数已经膨胀到八百行，里面 `if (type == A) ... else if (type == B) ...` 层层嵌套；你想加一种新的处理方式，却发现要同时改五个地方；你把某个类的头文件改了一个私有成员，整个工程二十个编译单元全部重编，链接错误铺满屏幕。

这些问题的共同名字叫**变化**。软件唯一的常态是需求会变，而设计模式（Design Patterns）就是前人总结出来的、应对变化的**复用方案目录**。它不是银弹，也不是必须遵守的法律——它是一份"什么问题大概可以用什么形状解决"的经验索引。

那么，为什么 C++ 程序员还需要"重学"设计模式？因为市面上绝大多数设计模式教材——包括本教程参考的《设计模式之禅》和刘伟《设计模式》——用的是 Java。Java 是一门"一切皆对象、一切皆引用、一切皆 late binding"的语言，GoF 的 23 个模式在 Java 里几乎是自然生长的。而 C++ 不一样：

1. **C++ 有值语义**。Java 里 `Shape s = new Circle()` 天生多态，C++ 里 `Shape s = Circle()` 是**对象切片**（object slicing）——圆形部分被硬塞进长方形的空间里，运行时行为直接错掉。不懂值语义的人按 Java 教材写 C++，第一步就会踩坑。
2. **C++ 有编译期多态**。模板、concepts、CRTP、`constexpr`，这些 Java 完全没有的机制，让"策略""模板方法""访问者"这类模式可以有**零虚表开销**的替代写法。
3. **C++ 有所有权**。Java 的对象都是垃圾回收的，C++ 的模式必须回答"谁负责 delete"。1995 年的 GoF 书里到处是 `delete this` 和裸指针，直接照搬到今天就是内存泄漏的配方。
4. **C++ 标准库本身就是模式书**。`std::variant` + `std::visit` 是访问者模式的标准化封装，迭代器模式直接长在语言规范里（C++20 ranges），pImpl 是桥接模式的工程变体。C++23 程序员每天都在"用"模式，缺的只是把日用习惯和模式名词对上号。

所以本教程的立场是：**每个模式先按 GoF 经典写法讲透——那是所有教材的公共语言；然后立刻给出 C++23 现代写法，并回答"什么时候该用哪种"**。只学经典会写出 1995 年风格的 C++，只学现代则读不懂别人的代码和三本参考书。

## 三本书怎么用

本教程以三本书为纲，三者角色互补：

| 书 | 角色 | 强项 |
|---|---|---|
| 《设计模式之禅（第2版）》（秦小波） | **叙事主线** | 用连续的故事场景把"坏代码 → 演化 → 模式"讲活，最贴近教程写法 |
| 刘伟《设计模式（第2版）》（清华大学出版社） | **定义与角色表** | 每个模式的动机、定义、结构图、优缺点、适用环境整理得最规范，适合查表 |
| GoF《设计模式：可复用面向对象软件的基础》 | **权威出处** | 每个模式的原始动机、实现要点与"特定语言的变化和问题"（含 C++ 专节） |

三本书都讲 23 个模式，但侧重完全不同。之禅第 1 部分用 6 章讲六大原则，第 2 部分按"定义—应用—扩展"展开每个模式；刘伟把 23 个模式拆成 27 章（多出 UML、设计原则、概述三章基础）；GoF 则是 1 章引言、1 章文档编辑器实例研究、3 章模式（创建型/结构型/行为型）、1 章结论。本教程的章节安排以之禅的叙事顺序为骨架，补入刘伟的规范定义，并在每个模式章末尾标注三书对应章节，方便你延伸阅读原文。

## 23 个模式的地图

GoF 把 23 个模式按**目的**分成三类。创建型关心"对象怎么造出来"，结构型关心"类和对象怎么拼成更大的结构"，行为型关心"职责怎么分、对象之间怎么通信"：

- 创建型（5 个）：抽象工厂、建造者、工厂方法、原型、单例
- 结构型（7 个）：适配器、桥、组合、装饰、外观、享元、代理
- 行为型（11 个）：职责链、命令、解释器、迭代器、中介者、备忘录、观察者、状态、策略、模板方法、访问者

## 你可能早就在用：标准库里的模式

学 23 个名字之前先建立一个直觉：这些模式不是三本书发明的，它们是对**早已存在的工程实践**的命名。C++ 标准库里就有大量现成的模式实现，列一张对照表，后面各章讲到一个模式就回来补一行：

| 模式 | 标准库中的化身 | 关系 |
|---|---|---|
| 迭代器 | `begin()/end()`、`std::iterator_traits`、C++20 ranges | 语言级标准化，GoF 版只是其子集 |
| 策略 | 比较器模板参数（`std::sort` 的 `Compare`）、`std::function` | 编译期/运行期两种策略形态 |
| 适配器 | `std::stack`/`std::queue`（容器适配器）、`std::reverse_iterator` | 换接口不改实现的标准示范 |
| 装饰 | 流缓冲（`std::ostream` 包 `streambuf`）、自定义分配器层层包装 | 运行期/编译期两种链式包装 |
| 桥 | pImpl 惯用法（大量标准库实现的内部结构） | 编译防火墙即桥的实现维 |
| 享元 | 短字符串优化（SSO）、`std::string_view` 共享只读内容 | 共享不可变数据 |
| 观察者 | 无直接对应（信号槽在 boost.signals2 等库） | 标准库唯一明显缺席的模式 |
| 单例 | `std::locale::classic()` 等惰性全局；`std::ios_base::Init` | 少见但有 |
| 备忘录 | `std::filesystem::copy_file` 前的备份；事务库的快照 | 标准库留给应用层 |
| 访问者 | `std::visit` + `std::variant` | 现代替代方案已成首选 |

读这张表的正确姿势不是背，而是留一个印象：**"这个需求标准库是不是已经有轮子了"应该是设计模式学习全程挂在嘴边的问题**。GoF 写书时 C++ 还没有标准库（1995，STL 尚未纳入），他们不得不手写 List、Set、Iterator（GoF 附录 C"基本类"整整 5 页就是这些自造轮子）；今天的读者天然站在标准库肩膀上，同一模式的实现代码量往往只有原书的几分之一。这也是本教程"经典写法 + 现代写法"双线结构的又一重理由——很多"现代写法"其实只是"标准库替你写好了的那部分经典"。

这张清单固定印在本教程示例的输出里，作为全书的主索引。等 40 章走完，你可以回到本章对照下面这段真实运行输出，检查自己是否对每个名字都有了"一句话意图"级别的理解：

```text
创建型(5): 抽象工厂 建造者 工厂方法 原型 单例
结构型(7): 适配器 桥 组合 装饰 外观 享元 代理
行为型(11): 职责链 命令 解释器 迭代器 中介者 备忘录 观察者 状态 策略 模板方法 访问者
三书分工: 之禅=叙事 | 刘伟=定义/角色表 | GoF=出处/经典实现
本教程主线: 每模式 = 经典写法 + C++23 现代写法 + 取舍结论
自检通过
```

输出前两行来自程序里的一个分组表，每组是一个"个数 + 名称列表"的聚合体；第三行是三书分工的固定提示。程序用 `static_assert` 在**编译期**断言 `5 + 7 + 11 == 23`——这不是表演，而是想让你在第一章就尝到 C++ 区别于 Java 的味道：**能放在编译期的约束就别放到运行期**。`assert(total == 23)` 在运行期再把总数验一遍，两道关卡对应两种校验哲学。

另一个细节是 C++ 标准档的断言写法。MSVC 用 `_MSVC_LANG` 报告语言标准（`/std:c++latest` 时为 `202302L`），clang/gcc 用 `__cplusplus`，所以程序里用条件编译兼容两者：

```cpp
#if defined(_MSVC_LANG)
    static_assert(_MSVC_LANG >= 202302L, "需要 C++23");
#else
    static_assert(__cplusplus >= 202302L, "需要 C++23");
#endif
```

这段代码出现在开篇而不是某个模式章，是因为它定义了全书的"海拔"：后面所有代码都假定编译器站在 C++23 上。你的构建环境只要满足：MSVC（VS 2022 17.10+，配 `/std:c++latest`）或 clang 19+（配 `-std=c++23`），两个通道都能零告警编译本书全部 40 个示例。

## 本教程的编码约定

全书示例遵循一套固定约定，先在这里立好规矩，后面不再重复解释：

1. **命名空间 `dp`**（design patterns）。所有手搓类型都在 `namespace dp` 里，避免和标准库、读者的业务代码撞名。
2. **RAII 是底线**。示例里没有裸 `new`/`delete`，所有权一律走 `std::unique_ptr`/`std::shared_ptr`/值语义。GoF 原书的裸指针写法会在讲到对应模式时逐一点名修正。
3. **错误处理双轨**：编程错误（越界、空容器弹出）抛标准异常；可预期失败（未注册的产品名、解析失败）返回 `std::expected`。每处选型都在正文说明理由。
4. **输出确定性**。示例输出不允许出现地址、时间戳、容器容量这类平台相关的值——凡是要断言"两个对象相同"，比较的是逻辑状态或布尔结论，不打印指针。
5. **每章一个可运行示例**。正文把要讲的代码全部内嵌，示例工程是同一份代码的完整可编译版本，指路放在每章末尾。

## 一个必须先讲清的坑：对象切片

既然动机里点名了值语义，第一章就把这个 Java 程序员最容易踩的坑提前拆掉。Java 代码：

```java
Shape s = new Circle(1.0);   // s 是引用，指向堆上的圆
double a = s.area();          // 调用的是 Circle::area —— 天经地义
```

C++ 里如果你写：

```cpp
Shape s = Circle(1.0);        // 切片！s 是一个 Shape 对象
double a = s.area();           // 调用的是 Shape::area —— 编译都过不了（Shape 是抽象类）
```

`Circle(1.0)` 构造出来的圆，只有 `Shape` 子对象的部分被拷进了 `s`——半径字段被丢掉了，虚表指针指向 `Shape` 的虚表。这就是**切片**：赋值发生的是"按静态类型的内存布局拷贝"，多态信息不在拷贝范围内。如果 `Shape` 是抽象类（有纯虚函数），编译器直接报错，算是不幸中的万幸；但如果 `Shape::area` 不是纯虚的，这行代码会**安静地算出错误结果**，比崩溃难查十倍。

C++ 里要多态，正确姿势只有三种，它们恰好构成本教程第 29 章的主题：

```cpp
Circle c(1.0);
Shape& ref = c;                                    // 1. 引用：无所有权，零开销
Shape* ptr = &c;                                   // 2. 指针：无所有权，可为空
auto up = std::unique_ptr<Shape>(                  // 3. 智能指针：拥有堆上对象
    std::make_unique<Circle>(1.0));
```

三种的共同点是**通过间接层访问对象**——多态寄居在"我只持有对象的地址，不持有对象本身"这个语义上。全书所有经典模式代码都建立在这个前提之上，记住它，后面 30 多章的 `virtual`、`override`、`std::unique_ptr<Base>` 才有锚点。

而现代写法里出现的 `std::variant`（C++17 起）提供了第四种可能：**不继承、不虚函数，把"可能是 A 或 B 或 C"编码进类型本身**。它和继承体系的取舍是贯穿全书的第二条暗线，第 13、25、28 章会正面交锋。

## 模式的四个要素

GoF 第 1 章给每个模式定了四个组成部分，读三本书时可以拿这把尺子对齐各家讲法：

1. **模式名称（name）**：一个词汇级的标签。"工厂方法""观察者"这些名字让"把创建逻辑封装到子类""状态变了要通知一堆人"这类长句压缩成两个词——好的命名本身就是设计沟通的一部分。
2. **问题（problem）**：什么场景下会出现这个模式。同一个模式在不同教材里配的问题场景不同（之禅用报表/女娲造人，刘伟用电视机/电器工厂，GoF 用文档编辑器），但问题的**形状**一致：变化点在哪、谁依赖谁、哪种需求反复出现。
3. **解决方案（solution）**：描述问题的要素（类、接口、职责、协作关系）以什么抽象结构组织起来，而不锁死具体实现。GoF 用 OMT 类图 + 交互图，本教程用 ASCII 图示 + 代码内嵌讲解。
4. **效果（consequences）**：用了这个模式赢在哪、付出什么。刘伟书的"模式优缺点/模式适用环境"两节是四要素中"效果"的最佳查表来源。

有一个常见的误读要先纠正：模式**不是**"代码模板"。你不能复制粘贴一个 Singleton 类就"用了单例模式"——模式解决的是特定上下文中的设计权衡，脱离上下文套模板正是第 39 章"过度设计"的病根。GoF 自己在第 1 章末尾就引用 Alexander 的话强调：模式是"在具体环境中解决问题的方法"。

## 按范围再分：类模式与对象模式

GoF 还有第二套分类轴：**范围（scope）**。类模式处理类与子类的关系（靠继承，编译期定死），对象模式处理对象间的关系（靠组合，运行期可变）：

- 类模式只有 4 个：工厂方法（类版）、适配器（类版）、解释器、模板方法——它们的共同点是都依赖继承机制。
- 其余 19 个都是对象模式。

C++23 的视角下这套分类轴有了第三种可能：模板和 concepts 提供了"编译期的对象组合"——既不用继承，也不付运行期开销。本教程讲每个类模式（模板方法、工厂方法）时都会补一版"编译期等价物"，读者可以把它当作对 GoF 分类轴的现代扩展。

## 教程怎么读

三种读法，按需选择：

- **线性通读**（1→40）：设计模式的知识网是递归的——讲适配器会引用组合，讲状态机会引用策略。第一遍线性走一遍，网才不会破。
- **按篇跳读**：急着用的读者可以直接跳到需要的模式章。每章的"经典写法"部分是自足的，不依赖前面章节的示例代码。
- **对照查阅**：第 40 章收官有 23 模式速查表和三书章节对照总表，写代码卡壳时直接翻。

每章正文的结构是固定的：意图与动机场景 → 朴素写法的坏处 → 经典模式逐段讲解 → C++23 现代写法 → 两版取舍 → 陷阱清单。其中"经典写法"保证你读得懂任何一本设计模式书和大多数历史代码，"现代写法 + 取舍"才是本教程对你的 C++ 工程实践真正负责的部分。

关于示例工程的组织再说一句：本仓库每个示例都自带一个 `main.cpp`（以及若干 `.hpp`），末行固定打印"自检通过"并全程用 `assert` 自校验；构建脚本会用 MSVC 与 clang 两套编译器分别编译、运行、比对输出——**双通道全绿**是每章代码的及格线，正文里出现的输出都是从真实运行结果里原样抄录的，不是手写的"理想输出"。你在自己的环境里复现时若发现输出不一致，优先怀疑编译器版本差异，而不是怀疑正文。

## 环境搭建

跟着敲代码需要的全套工具，Windows 上一小时内能配完：

1. **编译器（二选一即可，全要更好）**：
   - MSVC：安装 Visual Studio 2022 17.10 以上（本教程写作时用 VS 18），勾选"使用 C++ 的桌面开发"。编译参数固定为 `/std:c++latest /EHsc /utf-8 /W4`——`/utf-8` 一项不能省，否则中文源码在 GBK 代码页下编译直接报错；`/W4` 让编译器替你盯住未初始化、类型收窄这些模式实现里最常犯的错。

非 Windows 读者（macOS：MacPorts clang-23 / Linux：gcc 15 或 clang）同样能跑全套示例，`run-all.sh` 会自动适配平台差异——这层适配已经写进构建脚本，正文不再赘述。

代码之外只有一个硬性提醒：**中文注释/字符串一律 UTF-8 保存**。Windows 记事本旧版默认存 ANSI（GBK），MSVC 报 C4819 警告或直接乱码；用 VS Code 把编码固定成 UTF-8 一了百了。

## 三个开篇常见问题

**Q1：现代 C++ 都有这些语言特性了，设计模式是不是过时了？**
反过来读更准确：现代 C++ 把一部分模式**下沉成了语言设施**（variant 访问者、ranges 迭代器），把另一部分模式的价值**抬高了**（依赖注入、类型擦除因为要手动管理所有权而更需要模式思维）。23 个模式里大约 1/3 的实现形态被 C++23 显著改写，但 3/3 的**问题**——变化点在哪里、依赖往哪个方向指——一个都没变。过时的是答案，不是问题。

**Q2：要不要先把三本书读完再跟着写？**
不需要，顺序应该是"教程正文 → 卡壳时查书"。之禅的故事适合通读但信息密度低，刘伟适合查定义，GoF 适合追出处——三者都是工具书用法。本教程每章末尾给了三书对应章节，按需跳读即可。

**Q3：23 个模式里哪些最值得优先学？**
按工程出现频率，前四名大致是：策略（包括它的现代形态 `std::function`/lambda）、观察者、工厂方法（含简单工厂）、访问者（尤其 `variant` 版）。本书在批次安排上也给了同样的权重：创建型与行为型各给了最厚的篇幅，第 29–38 章的现代专题与实战全部围绕高频模式展开。

## 三书对应关系
