# 39 · 反模式三幕：模式的滥用现场

教程前 38 章都在讲"怎么用好"，收官前必须讲"怎么用坏"——**模式用错比不用更贵**：不用只是局部重复，用错是给全项目安装一套永久骨架。本章三幕各演一个高频滥用：一幕"创建逻辑硬上 AbstractFactory"（骨架超过肉）、一幕"编译期固定组合硬上 Decorator"（运行期机制解决编译期问题）、一幕"全局单例当配置中心"（进程级状态污染测试）。每幕都有可运行的**症状实证**与**可断言的改法**——反模式章的反，要落在代码上不落在口号上。

## 意图与动机

三个反例的共性：**模式的成本结构被忽略了**。每个模式都有骨架成本（类数、间接层、装配代码），红利必须覆盖成本才值得付——前 38 章每章"什么时候不该用"一节都在说这件事，本章把最常见三种做成完整现场。判别能力比记忆能力重要：读完本章应该能在一屏代码里认出"这个骨架没有对应的复杂度"。

## 第一幕：AbstractFactory 反例

**症状**：两种按钮（深色/浅色）的创建，硬上一套完整工厂体系——Button 接口 + 2 个具体按钮 + Factory 接口 + 2 个具体工厂，**6 个类型干一件 if 的事**（`examples/39_antipatterns/main.cpp` 的 `bad` 命名空间）：

```cpp
namespace bad {
struct Button { virtual std::string render() const = 0; virtual ~Button() = default; };
struct DarkButton final : Button { std::string render() const override { return "[btn]"; } };
struct LightButton final : Button { std::string render() const override { return "(btn)"; } };
struct Factory { virtual std::unique_ptr<Button> make() const = 0; virtual ~Factory() = default; };
struct DarkFactory final : Factory { std::unique_ptr<Button> make() const override { return std::make_unique<DarkButton>(); } };
struct LightFactory final : Factory { std::unique_ptr<Button> make() const override { return std::make_unique<LightButton>(); } };
}  // namespace bad
```

**判别**：AbstractFactory 的红利是"产品族成套创建 + 运行期切换整套族"——本例只有两种取值、一族产品、创建逻辑一行。骨架成本（6 类型 + unique_ptr 间接）对红利（零）全亏。**改法**：

```cpp
// 改法：创建逻辑收敛为一个 lambda（策略语义没有变）
auto make_button = [](bool dark) { return dark ? std::string("[btn]") : std::string("(btn)"); };
assert(make_button(true) == "[btn]");
assert(make_button(false) == "(btn)");
```

一个 lambda，两种取值各就各位。什么时候该退回工厂体系：**产品族成套**（深色按钮+深色滚动条+深色窗口一起换）、**创建跨库**（第 35 章插件式工厂）、**创建过程昂贵需缓存**——三条全无，就是 lambda。

## 第二幕：Decorator 反例

**症状**：`" hi "` 要做 trim 再大写——两步**编译期就固定**的加工，却拟用装饰器体系（StringOps 接口 + TrimDecorator + UpperDecorator + 装配代码）。判别一句话：**装饰器的红利是"运行期任意叠放"**，编译期固定的组合没有这个需求——组合写死的那一刻，Decorator 的存在理由就没了。**改法**：

```cpp
auto tidy = [trim, upper](std::string s) { return upper(trim(std::move(s))); };
assert(tidy("  hi ") == "HI");
assert(tidy(" x ") == "X");
```

两行函数组合，行为等价。本例的示例 main 还保留了干净的版本边界：单步 `upper(trim(...))` 与具名组合 `tidy` 都在——**从内联两步到具名组合的升级点是"第二处使用出现"**，不是"要显得专业"。装饰器的真甜区（第 9 章讲过）是"行为叠放由配置决定"：日志 sink 的前缀、加密/压缩的流处理层——叠放组合在运行期开放，骨架才回本。

## 第三幕：单例反例

**症状**（`bad2` 命名空间，可运行实证）：

```cpp
namespace bad2 {
struct Config { int port = 8080; };
inline Config& instance() { static Config c; return c; }   // 全局态：进程级活账本
}

// main 里的症状实证：
bad2::instance().port = 9999;                          // "测试一"改了全局
const bool polluted = bad2::instance().port != 8080;   // "测试二"期望默认值
assert(polluted);   // 污染真实发生（症状成立，仅演示）
```

两个"测试"共用一个进程级单例：前一个的副作用变成后一个的前提——**测试顺序依赖**、并行测试互相污染、生产代码里谁都能改全局（改了没人知道）。这是单例的**结构问题**（全局可变状态）不是实现问题（Meyers 懒加载解决不了它）。**改法**：

```cpp
// 改法：把配置作为参数注入——两份配置互不干扰，测试可以各造各的
struct Config { int port = 8080; };
auto healthy_test = [](const Config& c) { return c.port; };
const Config a{};            // 默认 8080
const Config b{9999};        // 各造各的
assert(healthy_test(a) == 8080);
assert(healthy_test(b) == 9999);
```

注入 Config& 后，"两份配置互不污染"成为类型系统的性质而非纪律。单例仍合法的地盘（第 8 章讲过）：**真全局资源**（日志器、注册表）+ **不可变语义**（配置只在启动期写、运行期只读）——第 35 章 Registry 的哨兵注册是"启动期写完、运行期只读"的合规用法，本章反例是"运行期任意写"的违规用法。**同一个单例模板，合法性取决于写时点**——这是三幕里最值得带走的一句话。

## 判别的三个问题（三幕通用）

三幕的判别可以压成同一套三问，比背三条例子更可迁移。**第一问：红利场景存在吗？**——AbstractFactory 要产品族成套切换、Decorator 要运行期叠放、Singleton 要全局只读真资源；把该模式的"适用性"第一条拿出来对照，不存在就别上。**第二问：骨架比肉重吗？**——数一数模式骨架的类数/间接层数与实际业务逻辑的行数之比，6 个类型干 1 件 if 的事（第一幕）就是肉骨倒挂；比值的经验红线很难定死，但"骨架可读时长超过肉"基本就是红灯。**第三问：简化形态等价吗？**——lambda 能不能替类层次（第一/二幕）、参数注入能不能替全局（第三幕）；多数情况能，且第 29-32 章的现代专题给了全套压缩工具。三问全过才付模式的骨架成本——**模式是工具不是勋章**，GoF 原书 1.2 节的原话级告诫。

## 模式结构（三幕共用的判别框架）

```text
   模式的骨架成本（类数/间接层/装配代码）
        │ 须被红利覆盖
        v
   红利 = 模式解决的问题在你的场景里存在吗？
        ├─ AbstractFactory：产品族成套切换？   无 -> lambda/直接构造
        ├─ Decorator：        运行期叠放组合？   无 -> 函数组合
        └─ Singleton：        全局只读 + 真全局？ 否 -> 注入引用
```

## 测试法

反模式章的测试法正好倒过来：**症状用实证、改法用断言**。本例 main 里 polluted 断言（症状成立）与 healthy_test 断言（改法正确）并排出现——把"为什么不用单例"变成一段可以跑给质疑者看的代码，是反模式教学最有效的一步。三幕各自的改法断言全部固定文本（无随机、无时间），双编译器逐字节一致。另有一条元规则：**反例断言允许"断言坏行为成立"**（polluted==true），这是全书唯一一处断言写"坏事发生了"的地方——因为反模式章的合同就是"症状真实存在"，其余 39 章的断言全部写"好行为成立"。

## 评审清单：三分钟拦住一个反模式

把三幕的判别折成评审时的速查清单，六项有任一项命中即展开讨论：

- **类数与取值数同步增长**（每加一种枚举值加一个类——第一幕的工厂反例）；
- **接口只有一个实现 + 没有扩展计划**（单实现抽象是预付没有回报的成本）；
- **"Decorator"出现在编译期固定的组合里**（叠放组合写死 = 装饰器失格，第二幕）；
- **任何函数都能写的可写全局单例**（运行期可写 = 全局变量，第三幕）;
- **测试间共享进程级状态且无清场**（测试顺序依赖 = 全局态的外部症状）；
- **为"将来可能"预建的抽象**（YAGNI：抽象等到第二个真实取值出现再建）。

清单的用法注意与第 35/38 章的合规用法对表：Registry 是"启动期写、运行期只读"的合法单例，别把清单第 3/4 条误伤到它——**反模式知识的正确用法是提高警觉，不是一刀切**。

清单的另一个用法是**反向自检**：给已有的"合法"用法过一遍六条，全不命中再安心——合规不是自称的，是过筛过的。

## 本章示例的断言面

三幕六组断言的分工：

- 第一幕：症状侧（工厂体系 render=="[btn]"）+ 改法侧（lambda 两种取值）——功能等价是收敛前提；
- 第二幕：改法断言两种输入（"  hi "与" x "）——组合函数的行为面；
- 第三幕：症状断言 polluted==true（污染实证）+ 改法断言两份配置互不干扰——一正一反各一次。

反例代码（bad/bad2 命名空间）与改法代码在同一个 main 里对跑，**改前改后的行为面同时可断言**——这是反模式教学与正模式教学的本质区别：正模式验证"这样用有效"，反模式验证"那样用确实坏、改完确实好"。

## 三幕的深水区：各自的真实边界

反模式不是"永远别用"的同义词，三幕各有翻转条件——边界写清楚，判别才完整。

**第一幕翻回工厂**的三个信号：产品族成套（按钮+滚动条+窗口一起换肤）、创建跨库（插件注册进工厂）、创建昂贵需缓存（连接对象）——第 5-7 章的判据原样适用，本章反例只是"三条全无"的形态。

**第二幕翻回装饰器**的信号：叠放组合由配置决定（运行期才知道挂几层、挂哪些）、装饰层来自不同模块（互不知晓却要叠放）、流式处理（层与层之间是管道语义）。判断要点在"谁决定组合"——编译期代码决定就组合，运行期配置/用户决定才装饰。

**第三幕翻回单例**的信号：三条判据（真全局、启动期写、运行期只读）全占——第 35 章 Registry 是标准正例。灰色地带（日志器可写级别、Registry 支持运行期 add）用"写窗口"标注：写窗口越窄越像合法单例，全生命周期可写就是全局变量。

## 三幕之外的高频反模式速览

模式滥用之外，还有几个与模式相关的经典反模式，一张表备查（本教程正文有对应的"正确打开方式"章节）：

| 反模式 | 症状 | 正确章节 |
|---|---|---|
| God Object | 一个类管状态/逻辑/装配/IO 全链 | 02 章单一职责 |
| Anemic Domain Model | 类只有字段没行为，逻辑全在外面过程 | 02 章职责归属 |
| Sequence Diagrams in Code | 调用链 5 层以上只为转发 | 15 章外观 / 04 章迪米特 |
| Singleton Sprawl | 单例互相调用形成隐网 | 08 章 / 22 章中介者 |
| Pattern Enforcer | 强制一切新功能"必须用模式" | 本章三问 |

表里最后一条是元反模式：把模式从工具升格为纪律的那一刻，滥用就制度化了 —— 反模式章的真实目标是**让判别能力内化，而不是让清单变成新的教条**。若读者在真实代码里发现表外的新形态，判别框架照用：先问红利场景，再数骨架，最后找简化形态——三问本身就是开放集合的扩展点。

## 症状 → 对策速查表

三幕的判别与改法压成一张表，评审现场对号入座：

| 症状（一眼可见） | 所属幕 | 根因（一眼不可见） | 对策（改法一句话） |
|---|---|---|---|
| 类型数 ≫ 取值数，每枚举值一个类 | 一 | 骨架没有对应复杂度 | 收敛为 lambda / 直接构造 |
| 接口唯一实现且无扩展计划 | 一 | 预付无回报的抽象 | 删抽象，具体类直用 |
| 装饰链在源码里写死挂法 | 二 | 编译期问题用了运行期机制 | 具名函数组合 |
| "Strategy"只有一个策略 | 一/二 | 面向将来预建（YAGNI） | 等第二个取值出现再抽 |
| 测试必须按序跑、并行即炸 | 三 | 进程级可写全局态 | 注入 Config&，各造各的 |
| 改全局状态后行为悄悄变化 | 三 | 单例结构问题非实现问题 | 写窗口收窄到启动期 |

表的第一栏是**症状层**——评审时最先看到的；第二栏才是根因——反模式诊断的完整动作是"从症状下探到根因再上浮到对策"，跳步（只看症状就骂"别用模式"）是 39 章陷阱 7 的来源。

## 扩展练习

把判别能力练成肌肉的四个练习，由易到难：

- **反例普查**：在本教程 1-32 章的示例里找"如果少一个维度就该进 39 章"的边界案例——确认各章"什么时候不该用"一节都拦住了它们（30 分钟）；
- **改写演练**：把本章第一幕的 6 类型工厂**先改对再改回**——正反两个方向都亲手走一遍，骨架成本才有体感（20 分钟）；
- **真代码对照**：拿自己项目的任一目录，用评审清单六条扫一遍，找出至少一处"骨架超过肉"并写 100 字判别依据（1 小时）；
- **写出第 41 章**：选一个本章没覆盖的滥用形态（如 Command 反例"只有一个操作的对象化"、Memento 反例"快照存了不该存的引用"），仿三幕结构写一幕——写出来说明判别框架已经可迁移。判别依据的写法参考本章三问的句式：红利存在吗 / 骨架比肉重吗 / 简化形态等价吗。

## 陷阱清单

1. **把"模式"当正确性依据**（现象：评审时一句"这是标准模式"挡住简化提议；原因：模式合法性脱离成本结构单独成权威；后果：骨架永久化。对策：每次模式评审附带一问"它解决的问题在这里存在吗"——本章三幕的判别句就是模板）。
2. **反例只删不用**（现象：代码库里留着"以后可能用上"的工厂体系；原因：删除有心理成本；后果：骨架代代相传。对策：改法落地时骨架当次删除——git 历史会记住它，代码库不必）。
3. **单例改注入只改一半**（现象：Config 注入了，但日志器还是全局可变单例，测试照样串台；原因：只清理了被告发的那个；后果：污染换了个地方。对策：按"运行期可写"清单全量清查——只读单例（Registry/日志器）可以留，可写单例一个不留）。
4. **为消除模式而消除**（现象：第 35 章的 Registry 被当成单例反例拆掉，换成到处传参；原因：反模式知识无差别应用；后果：把合规用法也拆坏。对策：回看该章判据——启动期写/运行期只读/真全局，三条全占才是合法单例）。
5. **症状演示进生产**（现象：本章 bad/bad2 命名空间被人 include 进真实代码；原因：反例代码与正例代码同库；后果：反例成真。对策：反例放独立示例目录并命名 bad*/antipattern*，构建脚本不把它编进任何被依赖的产物——本例 main.cpp 自包含，无 hpp 可引）。
6. **把"模式"与"好设计"划等号**（现象：评审给用了模式的方案加分而非减分；原因：模式数量的信号价值被高估；后果：正向激励反模式。对策：评审问"这段代码的复杂度来自业务还是来自模式"，前者过、后者重走三问）。
7. **反模式判据无差别套用**（现象：Registry/日志器这类"启动期写、运行期只读"的合法单例被顺手拆掉换成到处传参；原因：三幕知识一刀切；后果：合规用法被误伤。对策：先过判据三条再动刀——本章是"提高警觉的工具"不是"一刀切的命令"）。

## 三书对应

- 之禅：全书"面向对象六大原则"总纲（单一职责/开闭/依赖倒置的**误用**在之禅各章"最佳实践"小节反复警示——本章三幕是三处警示的具体化）；另见第 8 章单例模式 8.4"单例模式的注意事项"（"单例对象如果持有可变状态，就是全局变量"——第三幕的原话级依据）。
- 刘伟：各章"模式的缺点"小节（Abstract Factory 的"添加新产品族容易、添加新等级结构难"、Decorator 的"多层装饰增加复杂度"、Singleton 的"不利于测试"——本章三幕分别对应三处缺点小节的真实化）。
- GoF：第 1 章 1.2 节对"设计模式不是万金油"的告诫（GoF 原文明确"模式是工具不是目的"）；5.x 各模式"适用性"小节的第一条不满足时即是本章三幕——反模式不过是适用性清单的实证部分。
