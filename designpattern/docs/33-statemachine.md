# 33 · 状态机实战：一张表，两种执行

实战篇第一章，把第 25 章的状态模式倒过来看。状态模式的"状态即对象"适合**行为随状态变化、状态内部逻辑重**的场景；但很多状态机的行为就是"查表跳转"——事件来了，从 (当前状态， 事件) 查出下一状态，别无其他。这时每个状态一个类就是税：四行逻辑撑起一个类文件。表驱动状态机把状态知识收进**一张 constexpr 数据表**，同一个表既在运行期被解释器走、又在编译期被 static_assert 验——数据替代代码，是实战篇的第一个组合拳。

## 意图与动机

还是售货机：idle --coin--> paid --crank--> dispensing，外加两处 reset 回 idle。第 25 章的写法里，Idle 类、HasCredit 类各自持有"收到事件怎么办"的成员函数，状态转移知识散在类间。本章的问题：转移知识能不能**只存在一份**？答案是把它变成数据：

```text
   状态 = 枚举值（St），事件 = 枚举值（Ev）
   转移 = 三元组 (from, ev, to)
   状态机 = 转移表 + 查表函数
```

表的性质决定了这份写法的天花板：constexpr 表能在编译期被求值（static_assert 钉死关键转移），运行期解释器只是"对同一张表的另一批调用"。**知识单份、双时态执行**——这是表驱动相对状态模式的根本优势；代价是行为表达能力受限（见"什么时候别用表"一节）。

## 经典写法：constexpr 表 + 双执行

示例 `fsm.hpp`。枚举、转移与表：

```cpp
enum class Ev { coin, crank, reset };
enum class St { idle, paid, dispensing };

struct Trans { St from; Ev ev; St to; };

// 全局转移表：constexpr——既供运行期解释，也供编译期断言。
inline constexpr Trans kTable[] = {
    {St::idle,       Ev::coin,  St::paid},
    {St::paid,       Ev::crank, St::dispensing},
    {St::paid,       Ev::reset, St::idle},
    {St::dispensing, Ev::reset, St::idle},
};
```

查表函数与编译期验证：

```cpp
// 查表：from+ev 唯一定位一条转移；查不到 = 非法事件，返 nullopt。
constexpr std::optional<St> find_next(std::span<const Trans> table, St from, Ev ev) {
    for (const auto& t : table)
        if (t.from == from && t.ev == ev) return t.to;
    return std::nullopt;
}

// 编译期验证——表错了在编译期就报，不用等运行。
static_assert(find_next(kTable, St::idle, Ev::coin) == St::paid);
static_assert(find_next(kTable, St::paid, Ev::crank) == St::dispensing);
static_assert(!find_next(kTable, St::idle, Ev::crank).has_value());   // 非法转移也编译期可验
```

三条 static_assert 的第三条最值钱：**非法转移也在编译期可断言**——"crank@idle 必须被拒"从口口相传的需求变成编译期事实。运行期解释器：

```cpp
// 运行期解释器：按事件序列走表。非法事件 = 拒绝，停原地。
inline std::vector<St> walk(std::span<const Trans> table, St init, std::span<const Ev> evs) {
    std::vector<St> path{init};
    St cur = init;
    for (const Ev ev : evs) {
        if (auto next = find_next(table, cur, ev)) {
            cur = *next;
            path.push_back(cur);
        }   // 非法：不前进、不记录——拒绝次数 = evs 数 - 消耗数
    }
    return path;
}
```

运行侧（`main.cpp`）：

```cpp
const std::vector<Ev> main_evs{Ev::coin, Ev::crank};
const auto path = walk(kTable, St::idle, main_evs);
assert((path == std::vector<St>{St::idle, St::paid, St::dispensing}));

const std::vector<Ev> evs2{Ev::crank, Ev::coin, Ev::crank};
const auto path2 = walk(kTable, St::idle, evs2);
assert((path2 == std::vector<St>{St::idle, St::paid, St::dispensing}));
const int rejected =
    static_cast<int>(evs2.size()) - (static_cast<int>(path2.size()) - 1);
assert(rejected == 1);                 // crank@idle 被拒了一次
```

非法事件的处理合同是**拒绝、停原地**（第 25 章的售货机同款语义：余额不足不出货），拒绝次数从"事件数减消耗数"推出来——不引入额外计数器，路径本身就是记录。运行输出：

```text
主路径: coin,crank -> idle,paid,dispensing（与断言一致）
拒绝线: crank@idle 被拒 1 次，其余事件照常推进
回退线: 两处 reset 均回 idle，路径与断言一致
自检通过
```

## 模式结构（表驱动的双时态执行）

```text
              constexpr Trans kTable[]（唯一的状态知识）
               │                        │
        编译期执行                  运行期执行
        static_assert               walk(table, init, events)
        （表写错 = 编译失败）        （path 记录走过的状态）

   状态模式（25 章）：状态知识 = N 个状态对象的成员函数（知识分散、行为可复杂）
   表驱动（本章）  ：状态知识 = 1 张数据表          （知识集中、行为受限查表）
```

## 三版演化：表驱动 vs 状态对象 vs variant

同一台售货机的三种实现，各有地盘。**状态对象**（第 25 章）：每状态一个类、事件是虚函数——行为可以任意复杂（crank 里查余额、拼输出、算找零），状态间可以持有差异化数据；代价是类爆炸与转移知识分散。**表驱动**（本章）：转移集中、可静态验证、加一条转移 = 加一行数据；代价是行为只有"跳转"一种——转移前后的动作（entry/exit action、转移 action）表本身表达不了。**variant 状态**（第 25 章 variant_state.hpp）：状态是 variant 备选项、visit 分派——比状态对象轻，比表驱动能装（visit 的 lambda 里可以写任意逻辑）。选型判据按序问：**转移后有没有"动作"？**没有（纯跳转）→ 表驱动最省；有但简单 → variant 版（lambda 里一两行）；动作重、状态数据异构 → 状态对象。三者可混合：外层表驱动定骨架、个别状态用 variant/对象精修——实战代码里这比纯某种形态更常见。

## 什么时候别用表驱动

表的平坦性是能力边界。三种情况表会露馅：**转移带条件**（crank 时"余额 >= 25 才出货"——表只能枚举条件分支或引入守卫列，行数按条件组合爆炸）；**状态带数据**（余额记在哪个状态上？表只认枚举不认负载）；**层次状态**（子状态机、历史状态——flat 表没有嵌套概念，强写就是表里复制粘贴）。这些正是第 25 章状态对象版的甜区。反过来说，**协议状态机、UI 向导流程、订单生命周期**这类"状态少、转移清、动作挂在转移外"的场景，一张表 + static_assert 就是最省的答案——表还能直接画进文档（它本来就是文档格式）。

## 两版对照表：知识放哪、行为放哪

把第 25 章与本章同一台售货机的两版实现并排放，选择时对照读：

| | 状态对象（25 章） | 表驱动（本章） |
|---|---|---|
| 状态知识位置 | 分散在 N 个状态类 | 集中于一张 kTable |
| 每状态可带数据 | 天然（成员变量） | 不能（St 只是枚举） |
| 转移动作（entry/exit） | 随意写进成员函数 | 表达不了（表只有三元组） |
| 编译期验证 | 有限（类层次可查） | 强（static_assert 直查表） |
| 加一条转移 | 加类/改类 + 接线 | 加一行数据 |
| 转移覆盖检查 | 靠测试 | 表可穷举 (状态×事件) 验重与验漏 |
| 可读性 | 行为即代码 | 表即文档 |

表的最后一行值得展开：表驱动状态机最大的隐性红利是**可解释性**——审查者、测试工程师、非程序员都能直接读表，"系统有哪些状态、哪些事件、怎么走"一目了然；状态对象版要读懂 N 个类才能画出这张图。反过来，表的第二、三行是硬天花板：状态带负载或转移动作一复杂，表立刻退化——这也是两版在实战里经常共存的根源。

## 本章示例的断言面

main.cpp 的断言覆盖了表驱动状态机的完整行为面：

- 主路径全等：`{coin, crank}` 走出 `{idle, paid, dispensing}`（比终点更严，中间站错也逃不掉）；
- 拒绝计数：crank@idle 混入序列，`rejected == 1` 且后续推进不受影响；
- 两处 reset：paid→idle 与 dispensing→idle 两条出边各走一遍；
- 编译期三条 static_assert：两条合法转移 + 一条非法转移——运行期断言之外的双保险。

## 扩展方向：带动作的转移

表驱动最常见的成长需求是"转移时做点事"（出货、退币、打日志）。最小侵入的升级是把三元组扩成四元组——加一个动作枚举或函数指针：

```cpp
struct Trans2 { St from; Ev ev; St to; void (*act)(); };   // act 可为 nullptr
```

解释器在跳转前调 `if (t.act) t.act();`——动作与转移一对一，表仍然集中。再往上是 **entry/exit 动作**（进出状态各一次，含自环转移的语义选择），那已经是 UML 状态机的领地，表结构从 `Trans[from][ev]` 走向 `State{entry, exit, 转移表}` 的混合体——**表管拓扑、状态结构体管动作**，这一步之后离第 25 章的状态对象版其实只差"动作写进成员函数"了。升级路线的启示：表驱动不是状态对象的对立面，而是它的一层底座——动作需求长到哪一层，就从表里长出哪一层结构。

表驱动的甜区清单（满足两条以上就值得上表）：

- **协议/连接状态机**：TCP 式的握手-建立-关闭，状态少、转移清、无负载；
- **UI 向导**：步骤页之间的前进后退，回退是 reset 事件；
- **订单/工单生命周期**：created-pending-shipped-closed，非法转移就是业务错误；
- **权限门禁的粗粒度流程**：未登录-已登录-已锁定（细粒度规则归第 38 章的管道）;
- **硬件/驱动序列**：上电-自检-就绪-故障，事件是中断或轮询结果。

这些场景的共同点：状态图能**画在一页纸上**——图能画出来的，表就能写出来，static_assert 就能验出来。状态图画不出一页纸的系统，先考虑分解成子状态机再决定用不用表。

## 陷阱清单

1. **表里有重叠转移**（现象：同一 (from, ev) 出现两行，find_next 返回先扫到的那条，改表序结果就变；原因：查表用 first-match，表数据没查重；后果：静默的错误转移。对策：debug 构建加一次 O(n²) 唯一性自检（或开发生命周期里用测试钉死），把"表合法"变成测试合同）。
2. **static_assert 忘了写**（现象：表手改错一个枚举，运行期才暴雷；原因：表是数据，编译器不查语义；后果：转移悄悄错。对策：主路径 + 关键非法转移至少各一条 static_assert（本章三条），改表时编译器兜底）。
3. **非法事件的合同没定**（现象：一版实现拒绝停原地、另一版直接 advance 或抛异常，测试互相对不上；原因：nullopt 的语义没有文档化；后果：集成时行为分歧。对策：合同写进函数注释（本章"拒绝、停原地"）并用 rejected 计数断言钉死）。
4. **walk 里持有跨事件的隐式状态**（现象：解释器 lambda 捕获了局部余额变量，同一表跑出两套行为；原因：状态机 = 状态枚举 + 显式负载，负载没进参数；后果：表不再是唯一知识源。对策：负载显式化——要么并入 St（枚举扩容），要么 walk 收一个状态结构体，表只管枚举跳转）。
5. **表被两处各写一份**（现象：文档里一张表、代码里一张表，改了代码忘了文档（或反过来）；原因：表的可读性诱人手抄；后果：两张表漂移。对策：文档里只画骨架（本章 ASCII），细节指向 kTable；或从代码生成文档表）。

## 表的维护工程

表驱动系统真正的长期成本不在写表，在**改表**。三条维护纪律让表十年不烂：**表的变更走数据评审**——一行 Trans 三枚举值，评审者一眼看全（类版改动的评审要读函数体）；**表的合法性用测试锁**——除 static_assert 的主路径外，测试里留一个"穷举合法性"用例（无重叠、出边可达、终点合法），改表后跑一遍就知有没有写坏；**表的演化有版本**——状态机升级加状态时，旧事件在旧表与新表上的行为对照是回归测试的第一批用例。这三条的本质是：表把状态知识从"代码"降为"数据"，数据就该用数据的办法管——版本、校验、评审，而不是 code review 一把抓。第 25 章的类版没有这个负担（也没有这个红利）：它的知识分散在类里，改哪处影响哪处要靠读代码判断。

## 测试法

- **编译期断言**：主转移 + 非法转移各钉一条 static_assert——表级合同零运行成本。
- **路径全等断言**：walk 输出整条 path 与期望向量比较（不是只比终点）——中间状态错了也逃不掉。
- **拒绝计数**：非法事件混进正常序列，`事件数 - (path 长度 - 1) == 拒绝数`——拒绝合同不引入额外状态就有断言。
- **回退路径**：两处 reset 分别从 paid/dispensing 回 idle（本例 evs3/evs4）——转移表的"出边"每条至少走一遍。
- **表覆盖完备性**：开发期用一次 O(状态×事件) 的穷举对照表验证"每条出边都能走到"（本章 kTable 只有 4 行，穷举成本为零）——表的可验证性正是它优于 switch-散写的根本理由。
- **确定性序列**：同一事件序列重复 walk 两次，path 逐元素相等——解释器无隐式状态（陷阱 4 的回归哨兵）。
