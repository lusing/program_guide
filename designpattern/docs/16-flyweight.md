# 16 · 享元

结构型篇里唯一以"省内存"为首要目标的模式。GoF 4.6 节的定义：**运用共享技术有效地支持大量细粒度的对象**。名字难读（flyweight 是拳击最轻量级——"轻到不能再轻的对象"），思想极简：**一百万个相同的东西，只需要存一份**。

## 意图与动机

文字编辑器是 GoF 的原始场景：一个文档一百万个字符，每个字符有字体、字号、位置。朴素 OOP 让每个字位一个对象：一百万个对象，其中**绝大多数字段相同**（字符 'a' + 字体 1 的"字型"全文档可能就一两百种）——重复数据占掉 99% 的内存。

享元的解法是把每个字位的属性拆成两类：

- **内蕴状态（intrinsic）**：字符是什么、什么字体——不随上下文变，**可以共享**。收进享元对象，全文档只存一份。
- **外蕴状态（extrinsic）**：出现在第几行第几列——随上下文变，**不能共享**。不进享元对象，由使用现场（渲染循环）在调用时传入。

一百万个字位 → 共享约两百个字型对象 + 一百万次"查表 + 传位置"的调用。内存从 O(100 万 × 对象大小) 降到 O(200 × 对象大小)，代价是每次使用多一次查表。

## 经典写法：字型池

示例 `flyweight.hpp`。享元与工厂：

```cpp
// Flyweight：内蕴状态（字符 + 字型）——所有"同字同型"的字位共享这一份。
struct Glyph {
    char ch;
    int font;
    [[nodiscard]] std::string describe() const {
        return std::format("glyph({},{})", ch, font);
    }
};

// FlyweightFactory：按 (ch, font) 查表，没有才造——池只增不减、键唯一。
// get() 标 const：取字位在语义上是只读操作，池是"缓存位"（mutable）。
class GlyphFactory {
public:
    const Glyph& get(char ch, int font) const {
        auto key = std::make_pair(ch, font);
        auto it = pool_.find(key);
        if (it == pool_.end()) {
            it = pool_.emplace(key, std::make_unique<Glyph>(Glyph{ch, font})).first;
        }
        return *it->second;
    }
    [[nodiscard]] size_t pool_size() const { return pool_.size(); }
private:
    mutable std::map<std::pair<char, int>, std::unique_ptr<Glyph>> pool_;
};
```

三个要点：

1. **工厂返回 `const Glyph&` 而不是值或 `unique_ptr`**。返回值会拷贝（共享失效——100 万份拷贝回到解放前）；返回裸指针的所有权归谁说不清；**共享的享元必须是"借"的**：`const Glyph&` 从类型签名上宣告"这不是你的，别改"。享元对象通常也不该可变（共享可变对象 = 一个线程改、所有"拥有者"都变——享元最经典的崩溃来源，见陷阱 2）。
2. **`mutable` 池 + const `get()`**：查表补表在语义上是只读操作（"给我这个字型"），池是缓存性质的实现细节。这与第 8 章单例章 mutable 的用法同一逻辑：**逻辑 const、物理写入**。
3. **`unique_ptr` 存池保证引用稳定**：`map` 的节点地址本来就稳定，但直接存 `Glyph` 值的话 `&pool_.find(key)->second` 在并发下没有独占保障；`unique_ptr` 让"对象地址"与"容器结构"彻底解耦，`const Glyph&` 的借出承诺才立得住。

渲染函数——注意外蕴状态怎么传：

```cpp
inline size_t render_text(std::string_view text, int font, const GlyphFactory& f,
                          std::string& out) {
    for (size_t i = 0; i < text.size(); ++i) {
        const Glyph& g = f.get(text[i], font);   // 内蕴：共享读，从池取
        out += g.describe() + "@" + std::to_string(i) + " ";  // 外蕴：位置 i 现场出现
    }
    return text.size();
}
```

位置 `i` 是外蕴状态：**它从不出现在 Glyph 里**，只在渲染循环的每一拍临时出现。运行输出：

```text
享元: 'a' 两次 get 同对象=是，池大小=2
享元: 渲染 100 字符，池大小 26（未为 100 个字位各造对象）
外蕴: glyph(a,1)@0 glyph(b,1)@1 glyph(a,1)@2
```

断言验证三件事：同字同型两次 `get` 拿到同一对象（`&g1 == &g2` 转布尔断言——共享的真实发生）；100 字符渲染后池只有 26 项（`pool_size() <= 26`）；第三行输出里 `glyph(a,1)` 出现两次（@0 和 @2）——**同一个对象，两个位置**，内蕴共享与外蕴独立同时成立。

## 算一笔内存账

享元的合理性要算出来，不是感觉出来的。设：字位对象大小 S 字节（含 vtable 指针、字符、字体、样式），文档 100 万字位，去重后享元种类 200：

- **朴素**：100 万 × S。S=48 时 48 MB。
- **享元**：200 × S（池）+ 100 万 × 位置数据。位置若只需行列各 2 字节 = 4 MB + 约 10 KB。**省 90%**。
- **平衡点**：当"种类数 ≈ 总数"（每个字位都独一无二）时享元只剩查表开销——**享元是给"种类少、实例多"准备的**。种类数达到总数的 30% 以上就要重新算账（查表 + 指针间接的成本开始超过省下的内存）。

GoF 在"何时使用"节给的判据正是这四个条件：应用使用大量对象、对象太多导致存储开销大、对象的大多数状态可外部化、删除外蕴状态后可以用较少的共享对象取代很多组对象。四条全中才用。

## 现代视角：你早就见过享元

C++ 标准库和日常代码里享元无处不在，认出它们比新写一个重要：

```cpp
// ① std::string 的 SSO 之外的另一面：短字符串在实现里常驻小缓冲
//    （这不是享元，但" intern 表"是——见②）

// ② 字符串驻留（interning）：编译器符号表、Lua VM 的字符串表
//    同一串内容全局只存一份，比较退化为指针比较
std::unordered_map<std::string, std::unique_ptr<Symbol>> symtab;   // 编译器符号表

// ③ constexpr 字面量表：编译期把常用常量放进只读段，全程序共享
inline constexpr std::array<int, 256> kAsciiClass = { /*…*/ };

// ④ 不可变配置对象按值共享：shared_ptr<const Config>
std::shared_ptr<const Config> cfg = std::make_shared<Config>(...);  // 各处共享只读
```

②③④的共同点：**共享的是不可变数据**。这正是现代 C++ 对享元的最大改写——GoF 时代共享靠"小心别改"，现代 C++ 靠**类型系统把可变性锁死**：`const Glyph&` 返回、`shared_ptr<const T>` 传递、`constexpr` 进只读段。**享元 + 不可变 = 无锁共享**；一旦享元带可变状态，就得配同步（陷阱 2 的主题），多数情况下那说明状态分类没做对——可变的那部分大概率是外蕴状态，该挪出去。

## 两版取舍

| 维度 | 手写享元池 | 值语义/驻留表替代 |
|---|---|---|
| 对象模型 | 指针共享 + 外蕴传参 | 值拷贝（SSO 小对象）或 intern 键 |
| 线程安全 | 池要加锁或用 immutable | 值天然安全；intern 表加锁一次 |
| 内存账 | 最省（种类数 × 大小） | 省（值小）或不省（值大但简单） |
| 适用 | 大对象、种类少、实例巨多 | 小对象直接值拷贝更划算 |

反向判据一句话：**对象小（≤16 字节）直接拷贝，共享的复杂度不值；对象大且种类少，享元赚**。`std::string_view` 也是这个家族的成员——它"指向共享的字符数据，自己只存指针和长度"，是"内蕴共享、外蕴（生命周期）外部管"的现代形态。

## 复合享元：共享里的层级

GoF 的"实现"节还给了享元一个组合形态：**复合享元（composite flyweight）**——享元本身由享元组成。棋盘上的"一行棋子"可以作为一个单元引用（行享元持有一组棋子享元的引用），行享元自身也可共享（相同的行布局共享一行对象）：

```text
Glyph（叶子享元，内蕴：字符+字体）      ← 全文档共享
   ↑ 被引用
RowGlyph（复合享元，持 vector<const Glyph*>） ← 相同行布局共享
   ↑ 被引用
PageGlyph（复合享元）                    ← 相同页面布局共享
```

规则只有一条：**复合享元的"组成"是内蕴的才可共享；一旦复合结构依赖上下文，它就退化成普通组合对象**。这个形态与第 13 章组合模式自然合体——组合的树节点如果按内容去重入池，就是复合享元。C++ 实现上没有任何新机制（还是 `map<key, unique_ptr<T>>`），新的是"键"的复杂度：叶子享元的键是 `(ch, font)`，复合享元的键是"全部成员的键序列"——键本身要能哈希且稳定。

## 享元、单例、对象池：三个"省对象"模式的分工

三个模式都让"对象数变少"，极易混淆。分界看两个问题：**谁共享、共享什么**：

| | 享元 | 单例（第 8 章） | 对象池（第 34 章） |
|---|---|---|---|
| 对象数量 | 每种内蕴状态一份（n 份） | 全局 1 份 | 固定池容量，**借还复用** |
| 共享单位 | 状态相同就共享 | 状态整体唯一 | 状态不共享，**时序错开** |
| 关键操作 | `get(key)` 查表 | `instance()` | `acquire()/release()` |
| 典型对象 | 字型、符号、模板 | 配置、日志器 | 连接、线程、大缓冲 |

一句话记法：**享元按"内容"去重（同时用），单例按"身份"唯一（同时用），对象池按"时间"复用（错开用）**。对象池的每个对象同一时刻只服务一个使用者，状态归使用者——这与享元的"状态不可变、人人可同时用"正好相反；把连接池叫"享元池"是常见的术语错误，第 34 章会再回到这张表。

## 刘伟 15.3 的网站共享实例：外蕴状态的完整形态

刘伟的例子把外蕴状态的传递路线讲得很完整：一个"企业网站搭建系统"要给 N 个客户建网站，网站分 4 种模板（博客/电商/官网/论坛）。朴素做法每个客户一套完整网站对象（N 套），享元做法**模板是内蕴的**（4 份共享），**客户数据是外蕴的**（每次请求传入）：

```cpp
// Flyweight：网站模板（内蕴：模板类型 + 布局代码）
struct WebSite {
    std::string category;                     // "blog" / "shop" / "home" / "bbs"
    [[nodiscard]] std::string serve(std::string_view user, std::string_view page) const {
        return std::format("[{}] {} 的 {} 页面", category, user, page);
    }
};

// Factory：按类别查池——同类别全系统一份
class WebSiteFactory {
    mutable std::map<std::string, std::unique_ptr<WebSite>> pool_;
public:
    const WebSite& get(std::string_view category) const { /* 查表补表同 GlyphFactory */ }
};

// 使用：4 份模板服务 N 个客户
auto& factory = WebSiteFactory::instance();
factory.get("shop").serve("客户A", "商品列表");
factory.get("shop").serve("客户B", "商品列表");   // 同一个 WebSite 对象
```

这个例子同时是享元"何时用"四条件的教学版：对象大量（N 客户 × M 页面次请求）、种类少（4 模板）、大部分状态可外部化（用户、页面都是请求参数）、去重后可用少数共享对象取代大量对象。把 `serve` 的参数表想成"外蕴状态包"——真实系统里这个参数包常是一个"上下文对象"（用户会话、渲染上下文），第 8 章陷阱 5 提醒过的"上下文显式传递"在这里找到了模式级归宿。

## 陷阱清单

1. **内蕴外蕴分错**（现象：把位置/时间戳存进 Glyph；原因：字段顺手就写了；后果：种类数爆炸（每位置一种"享元"），共享彻底失效。对策：写享元前先做状态分类表，只收"不随上下文变"的）。
2. **共享可变享元**（现象：Glyph 带可变样式位，一个字位被"加粗"全体 'a' 跟着变粗；原因：没意识到共享的全部代价；后果：诡异联动 bug。对策：享元严格不可变（const 返回 + 无 setter）；可变需求一律外蕴化）。
3. **池无限增长**（现象：键空间大（URL、时间戳当键），池百万项只增不减；原因：享元池没有淘汰机制；后果：内存泄漏式增长。对策：键空间有限（枚举、字符集）才用享元；键空间无限的换 LRU 缓存——那是缓存问题不是享元问题）。
4. **引用悬空**（现象：`const Glyph&` 借出后池被并发清理/重构；原因：享元"只增不减"的约定被打破；后果：悬垂引用。对策：保持"只增不减"（本例做法），或清理时配 `shared_ptr` + 弱引用计数——GoF"实现"节讨论过后者）。
5. **忘了算账**（现象：对象种类 50 万也上享元池；原因：模式先行；后果：查表+间接的成本超过省的内存。对策：先测种类数与实例数的比例，比例 <30% 才值得——"何时使用"四条件缺一不可）。

## 确定性输出的一个技巧：享元池的遍历顺序

本书约定输出可预测（第 1 章），享元池若要打印内容就有一个隐藏要求：**遍历顺序稳定**。`std::map` 按 key 字典序遍历——`std::pair<char,int>` 的比较是先比字符再比字体，`(a,1)` 排在 `(b,1)` 前，顺序天然确定。若用 `std::unordered_map`，同一次运行内顺序固定、跨运行（不同哈希种子/实现）可能不同——教学代码与需要"逐字节一致"验证的场景一律选 `std::map`。这不是性能建议（unordered 通常更快），是**验证策略**：能被测试逐字节比对的输出，其数据来源的每个环节都必须有序。第 5 章注册表选 `std::map` 是同一条原则的第一次出现，这里是第二次——全书会反复用到，值得现在记住理由。
