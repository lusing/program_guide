# 08 · 单例

23 个模式里最简单也最招黑的一个。刘伟 9.1.2 节的定义：**确保一个类只有一个实例，并提供一个全局访问点**。一半教材教你怎么写对它，另一半教材劝你别用它——本章两边都讲，因为 C++ 的单例恰好是理解"语言保证"和"全局状态危害"这两个主题的最佳教具。

## 意图与动机

有些东西天然就该全局唯一：配置中心、日志器、连接池、随机数引擎（每线程一个）。它们要满足两个诉求：**恰好一个实例**（两个配置中心会打架）和**随处可得**（三十层调用栈深处也要能读配置）。朴素写法用一个全局变量：

```cpp
Config g_config;                    // 全局变量：全局唯一 ✓ 随处可得 ✓
```

两个问题：初始化顺序（多个全局变量的构造顺序跨编译单元不确定，`g_config` 若依赖另一个全局对象就悬了）；不可控访问（谁能改？何时改？没有任何门禁）。单例模式要解决的就是这两个问题的"受控版"。

## 经典写法：C++ 的标准答案——Meyers 单例

示例 `singleton.hpp`：

```cpp
class Config {
public:
    static Config& instance() {
        static Config inst;      // 首次执行到此才构造，且并发安全
        return inst;
    }

    void set(std::string k, std::string v) { kv_[std::move(k)] = std::move(v); }
    [[nodiscard]] std::string get(std::string_view k) const {
        auto it = kv_.find(std::string{k});
        return it == kv_.end() ? "" : it->second;
    }
    [[nodiscard]] size_t count() const { return kv_.size(); }

    Config(const Config&) = delete;
    Config& operator=(const Config&) = delete;

private:
    Config() = default;
    std::unordered_map<std::string, std::string> kv_;
};
```

六行骨架承载了全部机制，逐条拆解：

1. **`static Config inst`（局部静态变量）是唯一实例**。C++11 标准保证：局部 static 的初始化"恰好发生一次，即使并发调用也安全"（[stmt.dcl]/4，实现上通常是编译器生成的双检锁 + 守卫变量）。这就是 **magic static**，C++ 单例的现代标准答案——GoF 书里用 C++ 手写的"双检锁 + 静态指针"版本在 C++11 之后已经不需要手写（而且手写双检锁极易写错内存序，GoF 的写法按今天的标准是有数据竞争的）。
2. **惰性构造**：`inst` 在第一次调用 `instance()` 时才构造——不用它就不付构造成本，初始化顺序问题自动消失（它依赖谁，谁已经在这次调用之前初始化好了，除非依赖也是惰性的且成环）。
3. **删除拷贝**：`delete` 拷贝构造和拷贝赋值，把"唯一"从约定升级成编译期法律。没有这一步，任何拿到 `Config` 值的地方都能复制出第二份。
4. **构造函数私有**：`Config() = default` 藏进 private，外界无法 `new`/栈上构造——实例只能从 `instance()` 出。
5. **返回引用**：`Config&` 而不是 `Config*`（引用不可空，语义干净）也不是 `Config`（返回值会拷贝出第二个实例——虽然拷贝已 delete，但返回值类型正确性本身就是文档）。

Java 教材里篇幅最长的"线程安全的单例怎么写"（饿汉/懒汉/双检锁/内部类/枚举五连），在 C++ 里被 magic static 一行收编——这是本教程"语言设施下沉模式"主题的第一例大满贯。

运行输出：

```text
单例: 两次 instance() 是同一对象=是
```

验证代码取布尔结论而非打印地址：

```cpp
Config& a = Config::instance();
Config& b = Config::instance();
bool same = (&a == &b);                  // 只取布尔结论，不打印地址
assert(same);
a.set("theme", "dark");
assert(b.get("theme") == "dark");        // 一个写，另一个立刻看见：同一对象
```

`&a == &b` 的布尔值进入断言和输出，地址本身从不打印——本书的确定性约定（指针值因运行而异）在这里第一次实践。

## 带参数的单例：call_once

magic static 有个限制：构造不收参数（收也只收首调用者给的）。当单例的初始化需要"第一个调用者提供配置"时，`std::call_once` 版本登台（`once_singleton.hpp`）：

```cpp
class NamedPool {
public:
    // 首调者给名字，之后所有人共享同一实例——构造参数只生效一次。
    static NamedPool& instance(std::string name) {
        static NamedPool* inst = nullptr;
        static std::once_flag flag;
        std::call_once(flag, [&] { inst = new NamedPool(std::move(name)); });
        return *inst;
    }

    [[nodiscard]] const std::string& name() const { return name_; }

private:
    explicit NamedPool(std::string name) : name_(std::move(name)) {}
    std::string name_;
};
```

`std::call_once` + `std::once_flag` 保证 lambda 全程只执行一次（并发安全），实例指针在 lambda 里赋值。运行输出：

```text
call_once: 实例名=main-pool, 二次传参被丢弃
```

第二个调用者传的 `"another-name"` 被丢弃——**单例的构造参数只属于首调用者**，这是 call_once 单例的语义本质。示例代码旁边的注释还指出一条更简路线：局部 static 可以直接带参 `static NamedPool inst(std::move(name))`，C++11 起"首调用者参数生效"同样成立；call_once 版的价值在需要**自定义清理时机**（配合 atexit 之外的删除策略）或更复杂的初始化逻辑时显现。注意 `new` 出来的实例在本示例里故意不释放——进程生命周期对象由 OS 回收；若实例有析构副作用（关连接、刷盘），要换成显式 `unique_ptr` + 有序清理，正文明说这是教学简化。

## 饿汉与懒汉：C++ 里还要分吗

Java 教材（刘伟 9.5 节）用大篇幅区分"饿汉"（类加载即构造）与"懒汉"（首次使用才构造），C++ 里这对概念对应两种语法：

```cpp
// "饿汉"形态：命名空间级静态对象——main 之前构造，顺序跨编译单元不定
namespace eager {
    inline Config g_config;            // inline 变量，多 TU 共享一份
}

// "懒汉"形态：函数内局部 static——首次调用构造，顺序确定（调用时序决定）
Config& config() {
    static Config inst;
    return inst;
}
```

C++ 的建议只有一个字：**懒**。命名空间级全局对象有"静态初始化顺序灾难"（TU A 的构造函数摸了 TU B 还没构造的全局对象——未定义行为），而局部 static 没有这个问题：它依赖的任何东西在你调用 `config()` 时都已就绪。GoF 时代用"静态指针 + 首次 new"模拟懒汉，C++11 起 magic static 就是懒汉本身。除非对象构造极重且几乎必然使用（比如巨大的跳表），否则不要为"提前构造"付出顺序风险。

还有一个边角形态值得认识：**Nifty Counter（计数器法）**——用一个静态计数对象在 main 前抢跑构造、保证任何 TU 静态期访问单例都不悬空。它在日志这类"全局对象析构前都能用"的场景里有真实需求，实现较绕（两个头文件 + 内联计数器），本教程不展开；需要时记住关键词即可。普通业务单例，magic static + 惰性 + 不可变或加锁，就到头了。

## 单例的现代反思：它到底好不好

GoF 把单例列进 23 模式时是 1995 年；2020 年代的主流工程意见（之禅 7.5"最佳实践"也提了一句）是：**单例是披着模式外衣的全局变量**。三宗罪：

1. **隐藏依赖**。函数体里一句 `Config::instance().get(...)`，签名上看不出任何依赖——单元测试要跑通它，得先伺候好全局配置。依赖注入（第 3 章）把依赖写在参数里，单例把它埋进实现里。
2. **测试污染**。单例在测试间共享状态：A 用例改了 `"theme"`，B 用例"莫名"读到新值。除非给单例加 reset 接口——那等于承认它是个可变全局。
3. **并发放大器**。全局可变状态是数据竞争的温床，单例把它集中了起来：现在所有线程竞争同一把锁。

工程结论（第 31/34 章实战会反复兑现）：

- **真全局且不可变**（常量表、类型注册表）：单例无害，magic static 一步到位。
- **真全局但可变**（连接池）：单例 + 明确的并发策略，或注入到需要的地方。
- **只是"暂时全局"**（为了图方便）：别用。改成构造注入，依赖链清晰可测。

刘伟 9.5 节"单例模式扩展"里列的多例（有限实例池）与本章 NamedPool 同构；之禅 7.4 的扩展（有上限的多例）同理——它们的可测性比单例好不到哪去，别用"多例"骗自己。

## 单例的可测试性：一个折中方案

"单例毁测试"（本章三宗罪之二）在实际工程里有个常见折中：**给单例留一个显式的内容重置口**——实例不动（唯一性不破），状态清零（测试间隔离）：

```cpp
class Config {
    // ... instance()/set()/get() 同前 ...
    // 仅供测试使用：清空状态，不销毁实例
    void reset_for_testing() { kv_.clear(); }
};
```

要诚实地说清这个方案的边界：它治的是"状态泄漏到下一个用例"，治不了"隐藏依赖"（被测函数签名里照样看不出它用了 Config），也治不了并发（测试里的多线程用例互相仍可见）。所以它配两条纪律：`reset_for_testing` 只在测试代码里调用（可以放 `#ifdef` 或测试专用头）；新代码默认走依赖注入，单例只留给"真全局"（第 31 章日志实战会给日志器单例留同样的口子，理由相同——日志器是真全局且测试时想静音）。

另一种更彻底的折中是 **monostate（单状态）**：允许多个实例存在，但它们全部读写同一份静态状态。C++ 写起来就是一个普通类加 static 成员。它的好处是可测试性好得多（可以直接构造新对象、状态重置走 static 成员清零），坏处是"唯一性"从类型系统退成了约定（没人拦你造两个"实例"），而且静态成员的初始化顺序问题回来了。工程里 monostate 常见于"无状态的策略类共享一张只读表"——那其实是单例三宗罪的第三条路：**既不唯一也不全局，只是共享只读数据**，此时普通的 `shared_ptr<const Table>` 传参可能比两者都干净。

## 多例：单例的自然推广

刘伟 9.5 节与之禅 7.4 节都把**多例模式（Multiton）**作为单例的扩展：不是恰好一个实例，而是**有限 n 个**——每个实例挂一个 key，按 key 取。游戏里"四种属性池"（火/水/土/风各一个池对象）、连接池按数据库名分组的场景都是它的形态：

```cpp
class ElementPool {
public:
    static ElementPool& instance(Element e) {   // key 进了访问函数
        static std::array<ElementPool, 4> pools;  // 固定 4 份，编译期定死
        return pools[static_cast<size_t>(e)];
    }
private:
    ElementPool() = default;
};
```

注意它与"单例注册表"（第 5 章）的区别：注册表是**无限槽位**的（add 多少有多少），多例是**槽位固定**的（枚举定死 n）。C++ 里多例几乎不需要专门的"模式"——`static std::array` 或 magic static 数组一行就够；真正要想清楚的是第 8 章老问题在新衣下的重现：**4 个全局单例的可测试性是一个单例的 4 倍差**。所以多例的判断标准比单例更严：这 n 个对象必须都是"真全局且最好不可变"。可变的多例（每 key 一份可变池）在并发下等于 n 份全局状态，第 34 章对象池实战会把"共享池"改成"按 key 的多例 + 各自加锁"的结构，那时再权衡锁粒度与全局性。

## 陷阱清单

1. **手写双检锁**（现象：自己 `if (!inst) { lock; if (!inst) inst = new T; }`；原因：从 2011 年前的教材抄的；后果：缺 acquire/release 内存序，另一线程看到"非空但未构造完"的对象。对策：magic static 或 call_once，把正确性交给标准库）。
2. **单例之间的构造依赖**（现象：`A::instance()` 构造时调 `B::instance()`，B 又调 A；原因：惰性初始化成环；后果：死循环或半构造对象。对策：依赖关系改为显式注入，或在唯一入口按序初始化）。
3. **静态析构顺序炸弹**（现象：单例析构时用到另一个已析构的全局对象；原因：全局对象析构顺序跨编译单元不确定；后果：程序退出时崩溃。对策：单例尽量无析构副作用；确有清理需求，做显式 `shutdown()` 而不是依赖析构）。
4. **delete 拷贝但忘了 delete 移动**（现象：`Config c = std::move(Config::instance());`；原因：声明了拷贝构造会抑制隐式移动？不——没有声明拷贝时移动是隐式的，声明了拷贝（含 delete）则移动不生成；但为防未来改动，显式全删；后果：实例被"偷"走。对策：拷贝/移动一起 delete，一行的事）。
5. **用单例传"上下文"**（现象：`Session::instance().userId()` 满天飞；原因：函数签名偷懒；后果：多用户/多会话需求出现时全代码重写。对策：上下文作为参数或"环境对象"显式传递——第 3 章 DIP 的教训在单例上重演）。

## 与依赖注入的分界线

本章反复拿单例和依赖注入（第 3 章）对比，收尾把分界线画清楚。判断一个对象该不该是单例，问三个问题：

1. **生命周期是进程级吗？** 几乎不创建、不销毁、伴随程序始终——是。
2. **依赖方向朝"下"吗？** 它是最底层的基础设施（配置、日志、时钟），不反过来依赖业务对象——是。
3. **测试需要替换它吗？** 需要注入测试替身、需要按用例换状态——不是。

三条全"是"才轮到单例；任何一条"否"都指向构造注入。反向清单同样有用：业务服务（有依赖、有生命周期）、会话对象（多份并存）、策略对象（测试要换实现）——这些永远不该做成单例，哪怕"目前只有一个使用方"。"目前只有一个"和"只能有一个"是两句话，把前者写成单例就是把一个偶然冻结成一个决定。
