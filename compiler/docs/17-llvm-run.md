# 第 17 章　LLVM IR 与 ORC JIT：让 TIP 真正跑起来

## 17.1 为什么静态分析需要一条"具体执行"通道

前七章把前置工作全部做完了：TIP 文本被解析成 parse tree，再被提炼成抽象语法树，
树上的每个变量使用点也绑定到了它的静态声明。从下一章起，本书就要进入正题——
在这棵树上做类型分析、数据流分析、指针分析。这些分析有一个共同的承诺形式：
它们不执行程序，却要对程序**所有可能的运行**下结论。例如符号分析会声称
"在程序点 4，变量 x 一定非负"，这句话断言的是：无论 input 流取什么值，
只要执行真的到达程序点 4，x 的具体值就落在预测的抽象集合里。

这里立刻出现一个方法论问题：我们凭什么相信自己写的分析兑现了这个承诺？
第 2 章讨论过，程序的输入集合通常无穷，穷举测试在数学上永远不够；
但"测试不够"不等于"测试无用"。设想分析声称 x ∈ {正}，而我们随便挑一组输入
真实执行程序，发现到达该点时 x = −3——一次反例就足以证明分析是不可靠的。
反过来，执行一千组输入全部符合预测，虽然不能证明可靠性，却能给我们
捕捉实现笔误的现实机会：类型系统搞错了约束方向、数据流传递函数写反了边，
这些错误在精心挑选的几组输入下几乎必然现形。

因此本书为全部分析配备三条验证通道，本章先把其中第二条的基础设施建起来：

1. **输出对账**：分析程序对固定程序集的输出与 `expected/` 逐字节一致，
   保证结果可复现；
2. **具体执行检验**：用 LLVM 的 JIT 把 TIP 程序真实跑起来，
   逐一核对"具体值 ∈ 预测的抽象集合"——本章先实现"真实跑起来"本身，
   第 32 章起再把抽象预测接进来；
3. **工业界对照**：用 LLVM 中端已有的分析（如稀疏条件常量传播）跑同一程序，
   与我们的教学实现互相印证。

本章只做一件纯粹的事：把 TIP 翻译成 LLVM IR，并用 ORC JIT 执行它。
暂时不出现任何"抽象"。理解这一点很重要——本章是后续可靠性实验的**量具**，
量具本身必须先被信任。所以本章对生成器的要求格外严格：每个生成的模块
都要通过 LLVM 自带的结构校验，运行结果要与人工计算逐一吻合。
量具准了，后面的实验才有意义。

### 17.1.1 "让程序跑起来"的三种方案横评

要获得具体执行能力，技术上至少有三条路，本书的选择值得说明理由。

- **AST 解释器**：直接遍历语法树，用一张环境表模拟变量与运算。实现最短，
  但解释器要独自承担全部语义：运算、调用栈、输入输出次序，任何语义都由
  我们手写代码保证；且它与 LLVM 中端完全隔离，第 37 章讨论优化时没有
  共同平面。
- **自写代码生成**：自己发射机器指令。最接近"造编译器"，但把大量精力
  消耗在寄存器分配、指令编码、ABI 细节上，与静态分析主题无关。
- **翻译到 LLVM**：语义由成熟的后端保证，我们的代码只剩少量组合性的翻译
  规则；同一份 IR 既能 JIT 执行，又能交给 LLVM 的分析与优化 pass——
  一条通道同时服务于可靠性检验与工业界对照。

代价是要接受 LLVM 的概念体系（SSA、基本块、所有权模型），这正是本章
篇幅所在；但这些概念一次学完，第三篇以后全部复用。

### 17.1.2 JIT 与"先编译成 exe 再运行"差在哪里

ORC 是 JIT（Just-In-Time）设施：编译发生在 tipa 进程内部、运行的前
一刻，产物是进程内存里的本机代码，不落盘、不产生 exe。这与传统的
AOT（Ahead-Of-Time）编译形成对照，区别对本书很重要。JIT 下生成的
函数可以与 tipa 自身的函数（tip_input、tip_output）住在同一地址
空间、直接以函数指针互相调用，因此"把程序的 I/O 接到宿主"只需注册
符号，无须进程间通信；一次 tipa 调用可以顺序执行几十组输入，每组
一个全新模块，进程不重启。JIT 也不要求链接操作系统的程序入口
（CRT 启动代码）——tip_entry 由我们手工调用，这就是 17.7 节回避
main 名字的原因。代价是 JIT 编译的代码与宿主共享命运：宿主崩溃则
执行中断，且平台相关的后端必须在进程内初始化。对教学实验台而言，
这些代价恰好都是优点：快、可脚本化、可注入。

## 17.2 为什么选 LLVM：一次选择，两个角色

第 1 章交代过三件工具的知识边界，这里把 LLVM 在本书中的角色再说具体。
LLVM 在我们的教程里同时承担两个不同的工作，它们恰好对应 LLVM 项目的两个层面。

**第一个角色是中间表示（IR）的提供者。** LLVM 的核心是一套精心设计的
低级中间语言：它比 C++ 简单得多（没有类、没有模板，只有类型化的值、
指令和基本块），又比汇编抽象（指令带类型、保留无限多的虚拟寄存器）。
我们把 TIP 翻译成 IR，得到的是一份可读、可打印、可被机器校验的文本——
它让"TIP 程序到底如何运行"变得可见。第 12 章用 pretty-printer 观察 AST，
本章用 IR 观察程序的运行形状：每个局部变量在哪里分配、循环回边怎样连接，
在 IR 文本里一目了然。

**第二个角色是执行引擎的提供者。** LLVM 不仅能生成 IR，还能在同一进程内
把 IR 编译成当前机器的本机代码并立即执行，这就是 JIT（Just-In-Time）编译。
ORC（On-Request Compilation）是 LLVM 新一代的 JIT 框架，它允许我们把模块
逐个交给编译器、还允许我们把自己定义的 C 函数"注入"给被执行的程序。
TIP 的 `input` 与 `output` 没有操作系统意义上的标准流绑定，正好通过这种注入
机制由宿主程序（我们的 tipa）提供数据、收集结果。

为什么不用直接解释执行 AST 的方式实现"具体运行"？技术上完全可行，
但有三个理由让我们选择 LLVM。其一，解释器需要我们自己模拟机器整数的
全部运算语义，而翻译成 IR 后，语义由 LLVM 与本机指令集保证，
生成规则可以保持很少。其二，JIT 执行的是经过编译的本机代码，
当我们在第 37 章以后讨论"分析结果如何指导优化"时，IR 正是优化 pass
工作的真实平面——读者可以用同一份 IR 手工运行 LLVM 自带的优化，
观察分析与优化之间的关系。其三，把"可执行的语义"建立在工业级基础设施上，
我们的教学代码只需关注翻译规则本身。

### 17.2.1 IR 与汇编、字节码的异同

IR 常被说成"低级表示"，但它与汇编、Java 字节码的定位并不相同，辨析
有助于建立正确期待。它像汇编之处在于：指令是显式的 load、store、跳转，
控制流是基本块图，没有高级语言的作用域与嵌套表达式。它不像汇编之处有三：
指令带类型（i32 加与 i64 加是不同指令）、寄存器无限（用虚拟名字，
分配发生在后端）、以及保留无限 SSA 值的符号定义。与字节码相比，字节码
通常为解释执行设计（基于操作数栈、变量按索引访问），而 LLVM IR 为编译
优化设计：显式的 def-use 边、支配关系使得优化 pass 可以直接分析。因此
"翻译成 IR"既获得了接近机器的精确性，又保留了可供分析的结构——
这正是它在本书中一身二任的基础。

### 17.2.2 我们实际链接了 LLVM 的哪些子库

构建脚本通过 llvm-config 按组件取链接参数，本章实际使用的组件各有
明确职责，了解分工有助于理解错误来自哪一层。`core` 提供 IR 的全部
数据结构（类型、指令、模块、基本块）与校验器，是生成器的基础；
`support` 提供命令行、字符串、原生流等通用设施（如 raw_ostream）；
`orcjit` 提供 LLJIT、JITDylib、符号定义与 ThreadSafeModule；
`native` 让本机目标信息可用；`analysis`、`passes` 本章虽未直接调用，
但第 33 章与 opt 对照时属于同一平面。llvm-config 的好处是依赖只按
实际使用的组件引入，不与特定安装目录绑定——换一份 LLVM 安装，
脚本不变。链接 LLVM 共享库时运行需要对应的 DLL 在 PATH 上（UCRT64
环境），这也是 run-all 显式设置 PATH 的原因之一。

### 17.2.3 文本 IR 与内存 IR：同一份东西的两个面孔

IRBuilder 构造的是内存中的对象图（Module 拥有 Function，Function
拥有 BasicBlock……），而 --emit-ir 打印的文本是它的序列化形式。
关键事实：二者严格互逆——文本可经 llvm-as 重新解析为等价模块，
内存模块任何时刻都可打印。因此本书可以放心用文本讲解，读者看到的
每条文本指令都对应生成器里一个确定的 CreateXxx 调用，没有"只能
程序构造、文本写不出来"的暗角。这也让 17.14 节的输出对账可行：
打印输出只依赖模块内容与 LLVM 版本，版本固定（22.1.8）后，指令
的打印样式、块注释的排列都稳定，跨机器逐字节一致才有基础。版本
升级时 expected/output.txt 需要整体重生成——这是有意的成本：它
强迫我们审视新版本究竟改变了哪个打印细节，而不是默默漂移。

## 17.3 LLVM IR 的世界观：四个必须先建立的心像

在看生成代码之前，先建立 LLVM IR 的四个基本心像。后面每条生成规则
都是这些心像的直接落地，先有整体图景，代码就不再是需要记忆的清单。

**第一，所有值都有类型，TIP 的整数世界对应 `i32`。** IR 里每个值
都静态携带一个类型：`i32` 是 32 位整数，`i1` 是一位布尔，`ptr` 是指针。
本章只处理整数核心，TIP 函数的参数、返回值、局部变量全部用 `i32` 承载
（第 3 章声明过的"机器 int"取舍在这里落地）。比较运算在 TIP 里产出
整数 0 或 1，因此它在 IR 里分两步：先产出 `i1` 的谓词，再零扩展成 `i32`。

**第二，IR 是 SSA 形式：每个值只被定义一次。** SSA（Static Single
Assignment）意味着每个虚拟寄存器只被赋值一次，指令引用值时直接引用
定义它的指令。算术表达式因此天然是树：`a + b * c` 中乘法指令先定义
一个值，加法指令再引用它。可程序里的变量明明会被反复赋值——`n = n - 1`
在 SSA 里怎么说？答案是把"变量"与"值"分开：变量驻留在内存槽位里
（`alloca` 指令在栈上开一块），每次读取是 `load`、每次写入是 `store`，
而 load/store 之间流动的 SSA 值仍然满足单一定义。这是一种朴素但完全
正确的 SSA 使用方式；工业编译器会进一步把槽位提升成 SSA 寄存器，
但教学阶段保留槽位，规则最简单，且语义毫厘不差。

**第三，函数由基本块组成，基本块以终结指令结尾。** 一个基本块是一串
顺序执行的指令，最后一条必须是终结指令：`ret` 返回、`br` 跳转
（无条件跳一个块，或按 `i1` 条件在两个块间分叉）。控制流在 IR 里
不再是树——基本块之间的跳转可以形成任意的图，包括环。第 16 章 CFG
上的边在这里一一对应成可能的块间跳转。生成 if/while 的全部工作，
就是创建正确的基本块并用 `br` 把它们按 CFG 的形状连起来。

**第四，模块是自包含的编译单元。** 一个 LLVM 模块装着若干函数定义与
外部声明。本章生成的模块里，`tip_input`、`tip_output` 只有声明
没有定义——它们的定义在 JIT 执行时由宿主提供。模块可以打印成文本、
可以被重新解析，也可以直接交给编译器。IRGen 自始至终构造的就是
这样一个模块对象。

### 17.3.1 一个版本细节：不透明指针与带类型的 load

读者在 IR 文本里会看到 `alloca i32` 的结果类型写作 `ptr`、store/load
指令上显式写出 i32。这反映了 LLVM 15 以后的**不透明指针**设计：指针
不再携带它指向什么的类型，所有指针统一是 `ptr`；指针指向的元素类型
改由使用指针的指令（load/store/GEP）显式给出。于是 load 必须写成
"从 ptr 加载一个 i32"，生成代码里每个 CreateLoad 的第一个参数就是
该类型。这个变化对本章的生成规则影响很小——槽位存什么类型在创建
alloca 时已经知道，load 时原样给出即可；但它解释了为什么不能像更老
的教程那样只写一句无类型的 load。类型信息的位置从指针本身移到了
指针的每个使用点。

### 17.3.3 SSA 与可变变量：phi 的伏笔

本章用 alloca/load/store 处理可变变量，绕开了 SSA 最微妙的部分。读者
或许会问：SSA 声称每个值只定义一次，那循环后 x 的"新值"怎么用 SSA
表达？答案有两种。朴素方式即本章：变量活在内存、值由 load 定义，每个
load 就是一次单一定义，规则无须知道控制流。工业方式是把槽位提升为
SSA 寄存器：在控制流汇合处插入 phi 指令——phi 根据控制来自哪个前驱
块选择对应的值，于是"if 两个分支各自定义的 x"在 merge 处合成一个
定义。phi 的插入本身需要支配边界分析（一个小数据流问题），本章不引入；
但先埋下概念：第 32 章以后分析都在 CFG 上进行，汇合点正是信息合并
发生之处，phi 不过是把这种合并落实为指令。理解了 phi 是"按路径选择
值"，第四篇的路径敏感分析就有了直觉基础。

### 17.3.2 alloca 策略的一个边界说明

"每个变量一个栈槽、一律经 load/store 访问"是前端编译器最朴素的代码
形状（clang 在 -O0 时也几乎如此）。它的优点是规则与源程序一一对应、
无须任何数据流分析就能正确生成；代价是生成的代码包含大量冗余访存——
`f * n` 明明刚算出过值，下一次使用仍要重新 load。本章刻意保留这种冗余：
优化不是本章的任务，而且冗余代码反而便于读者把每条源码语句与指令逐行
对应。第 17.9 节之后 LLVM 中端的 mem2reg、SROA 等 pass 正是用来消除
这类槽位的；读者对同一份模块加一次 -O2 就能看到槽位如何被提升成 SSA
寄存器。先有正确的朴素形状，才看得懂优化在做什么。

### 17.3.4 块参数式 IR：一个我们没有采用的方向

近年部分编译器 IR（如 Cranelift、MLIR 的某些方言、Swift 中期的 SIL
讨论）用**块参数**取代 phi：控制流汇合时，跳转指令直接把值"作为
实参"传给目标块，目标块在块头声明形参接收，从而无须独立的 phi
指令。LLVM 坚持 phi 方案。两者表达力等价——块参数与 phi 可以互译，
但代码生成的手感不同：块参数要求跳转点就知道目标块的形参序列，
前向构造时更顺手；phi 则允许先生成块图、后填选择项，适合 LLVM
这种 pass 分阶段改写 CFG 的管线。本章两种都不直接使用（alloca
策略绕开了汇合问题），但提明这条流派之分，读者日后看其他编译器
输出时不会把块参数误读为普通调用。更重要的是，它再次展示了第四篇
的核心母题：**汇合点的信息如何合并**——phi 按前驱选、块参数由
跳转携带、alloca 经内存共享，三种机制解决同一个问题。

### 17.3.5 IR 文本里的名字：局部值、全局符号与编号

读 IR 文本时先分清两套名字。全局符号以 `@` 开头：`@tip_main`、
`@tip_entry`、`@tip_input` 是函数，模块级可见、可以被前向引用——
这也是 gen() 能先创建全部函数再逐个填函数体的原因。局部值以 `%`
开头：指令的结果、基本块都在内。我们创建 alloca/基本块时给的名字
（如 `f`、`then`、`wh.cond`）只是提示性的符号名；匿名指令
（add、load 等）在打印时由 LLVM 按出现次序编为 `%5`、`%6` 这样的
数字名。读输出时不要把 `%5` 误读为"第 5 行"：它只是该函数内的
第 5 个无名值，函数不同则重新编号。理解这一点，17.14 节的输出就
不会显得跳跃。另外，名字冲突时 LLVM 会自动加数字后缀，因此生成器
无须检查重名——但为了输出可读，我们给块和槽位起的名字都直接取自
源程序标识符。

## 17.4 生成策略总览：接口、所有权与顺序

本章 IRGen 的结构定义在 irgen.hpp，完整实现在第 17.15 节逐行给出，
下面先解释其中四个关键设计决定。

注意 IRGen 把上下文、模块、构建器三者都声明为 unique_ptr 成员，
而不是像常见示例那样直接声明为值成员。这是本章第一个刻意的设计。
原因在于所有权流向：JIT 在执行时需要**接管**模块与其上下文的所有权
（ORC 的编译发生在模块被添加之后，上下文必须活到编译完成）。
LLVMContext 不可拷贝也不可移动，把它放在 unique_ptr 里，我们就能
把整个 IRGen 的成果原样移交给 JIT，无须复制模块。打印 IR 不消耗
模块，所以 --emit-ir 与生成后的校验都可以在移交之前完成。

第二个设计是生成顺序：`gen` 先遍历程序一次、把所有函数（含函数类型）
创建出来，然后才逐个生成函数体。这样做是为了支持前向调用——
main 的函数体里调用 helper 时，helper 的 IR 函数已经存在于模块中，
解析名字后可以直接拿到声明。这与第 14 章符号表的两遍结构如出一辙：
先注册，再使用。类型信息在创建函数时就固定：每个 TIP 函数都翻译成
"参数为若干 i32、返回 i32"的函数类型。

第三个设计是局部槽位表 `locals`：它把第 14 章解析出的 `Symbol*`
映射到该符号在当前函数入口处创建的 `alloca` 槽位。键选择 Symbol*
而不是变量名字符串，是因为同一函数内名字唯一但跨函数重名普遍，
而符号表已经为每个声明建立了稳定的身份；VarRef 在第 14 章被绑定到
Symbol*，生成表达式时一次查表就能定位槽位，不必重新做名字解析。
这也意味着 IR 生成严格建立在第 14 章的输出之上——前端链条的每一层
都被下一层直接消费。

第四个设计是本章的覆盖范围：IRGen 只实现整数核心。对指针解引用、
记录字段、以及被调位置不是函数名的间接调用，expr/stmt 直接抛出异常。
这不是偷工：TIP 的这些构造需要内存模型与过程间分析的支撑，第 27、28
章建立指针分析后才自然。把"暂不支持"做成显式报错，错误会在生成期
立刻暴露，而不是默默生成错误的代码。本章的两个示例程序 ite.tip 与
outputs.tip 都只使用整数核心。

### 17.4.1 链接性质与符号可见性的取舍

创建函数时使用 ExternalLinkage：函数名进入模块的外部符号表，可被其他
模块或按名查找引用。这对本章是必需的——JIT 按名查找 tip_entry、
tip_main 也要被入口函数引用。辅助函数若只在模块内使用，可以设
InternalLinkage 让它获得类似 C static 的待遇（可被优化、名字不导出）；
本章不区分，因为所有 TIP 函数都可能被调用或作为分析对象，统一外部
链接最简单。运行时函数 tip_input/tip_output 以声明而非定义存在，
其 ExternalLinkage 声明只记录签名——解析引用时由 JITDylib 提供定义。
这样模块自身不假设定义来源：AOT 场景可以链接一个提供这两个符号的
运行时库，JIT 场景由宿主注册，IR 文本完全相同。

`verify` 与 `dump` 是两个观察口：前者调用 LLVM 的模块校验器检查
结构良构（每个块都有终结指令、调用签名匹配等），后者把模块打印成
文本。接下来三节分别看表达式、语句、函数的生成规则，所有规则都以
真实源码为准。

### 17.4.2 为什么用 IRBuilder 而不是手工构造指令

理论上每条指令都能直接 new 出来再手工挂到基本块末尾；本章一律经
IRBuilder。差别不只是省事。IRBuilder 维护"插入点"——新指令该落在
哪个块的什么位置，CreateXxx 系列在构造指令的同时完成插入并自动维护
指令链表，指令次序因此永远与生成次序一致；它还集中处理类型推导
（CreateAdd 检查两侧是否同型）、名字生成、以及各种便利谓词。手工
插入则要自己保证"终结指令之后不许再有指令"等不变量，漏一处就得到
一个 verifyModule 才能发现的畸形模块。可以把 IRBuilder 理解为 IR
这层数据结构的"写入端 API"：生成器只表达语义意图（加、存、跳），
结构细节由它兜底。第 17.6 节的插入点移动（SetInsertPoint）之所以
足以表达全部控制流，正是因为 builder 把位置抽象成了可随时切换的
光标。

## 17.5 表达式生成：从 AST 节点到 SSA 值

`expr` 吃一个表达式节点，返回一个 IR 值。它的结构是一条按节点类型
分派的链，每种节点对应一条固定的生成规则。下面逐一讲解，对照第
17.15 节的 irgen.cpp 阅读。

**整数字面量**：IntLit 节点携带 C++ 整数，生成 `i32` 常量。
常量不占运行时指令，它直接出现在引用处。

**变量引用**：VarRef 先经第 14 章的绑定表查到 Symbol*，再在槽位表
里找到该变量的 alloca 槽位，一条 load 指令取出当前值。这里能清楚
看到第 17.3 节"变量与值分离"的心像：变量活在内存里，load 产出的
SSA 值才是算术运算的操作数。同一函数里同一个变量被读取多次时，
每次产生一条独立的 load、得到一个独立的 SSA 值——这是正确的，
因为两次读取之间变量可能已被写入新值。

**input**：InputE 生成对外部函数 `tip_input` 的调用，无实参、返回
i32。它的定义在 JIT 执行时由宿主提供（第 17.10 节）。语义上它是
"任意整数"的来源，这个性质在第 32 章分析时至关重要——但在生成
层面它与一次普通函数调用没有任何区别。

**二元算术**：Binop 先递归生成左右两个 i32 值，再按运算符生成
一条指令：Add/Sub/Mul 分别对应整数加、减、乘；Div 对应 `sdiv`
（有符号除法）。这里用有符号除法而非无符号，是因为 TIP 整数
可以为负（负号被翻译成 `0 - E`），有符号语义与语言定义一致。
运算的类型由操作数决定：两个 i32 进、一个 i32 出，无须额外标注。

**比较运算**：Gt 与 Eq 是本章最值得细看的规则，因为它跨越了
i1 与 i32 两个类型。TIP 的 `>` 与 `==` 产出整数 0/1，而 LLVM
的比较指令 `icmp` 产出的是一位谓词 i1。生成因此分两步：先
`sgt`（有符号大于）或 `eq` 得到 i1，再 `zext`（零扩展）成 i32。
谓词为真时扩展得到 1、为假得到 0，恰好是 TIP 规定的比较结果。
为什么不直接比较成 i32？因为 LLVM 的类型系统刻意区分"布尔"与
"整数"——这层区分让条件跳转可以直接消费 i1，语义更清晰；我们
只在 TIP 的整数世界边界上做这一次显式转换。

**直接函数调用**：CallE 的被调表达式必须是一个 VarRef，且它绑定
到函数符号。生成时按函数的发射名（main 改作 tip_main）从模块中
取出 IR 函数，递归生成全部实参，一条 call 指令完成调用，结果是
被调函数返回的 i32。若被调位置不是名字（变量里装着函数值），
生成器抛异常——那是一等函数值的间接调用，需要第 52 章 0-CFA
先行确定"可能调用哪些函数"。

表达式生成的一个总体性质是**局部性**：每种节点的规则只依赖其子
表达式生成的值与符号绑定，不引用程序其他位置的信息。这让正确性
论证可以按表达式结构归纳进行（第 17.13 节），也让节点种类与规则
一一对应、没有遗漏。函数末尾对未覆盖的节点类型抛异常，保证任何
"忘记写规则"都会在生成期被发现而不是静默生成错值。

### 17.5.1 算术生成的两个细节

除法与溢出标志两处值得专门说明。其一，有符号除法 sdiv 对负数的行为是
向零截断（如 −7/2 = −3），这与 TIP 整数语义及 C++ 习惯一致；若误用
无符号 udiv，−1 会被当作极大无符号数。其二，生成算术指令时刻意**不**
加 nsw/nuw（有符号/无符号不溢出）标志：这些标志是向优化器承诺"结果
不溢出"，违背承诺时行为未定义；本章不做这种承诺——溢出的处理属于
8.13.4 所说的论证边界，程序约定在 i32 范围内，但 IR 本身保持最保守、
最普通的指令形式。比较指令同样不附加操作数范围假设：sgt 对任意 i32
都有定义，包括负数。

### 17.5.2 为什么不在生成阶段做常量折叠

`1 + 2` 完全可以在生成时直接折成常量 3，本章刻意不做。常量折叠是一种
分析驱动的变换——它需要先知道"两个操作数在此处确定为常量"，而这正是
第 33 章常量传播要回答的问题。在生成阶段手折，等于把未经论证的分析
塞进翻译器：折叠规则要自己枚举、且与源程序的朴素对应被破坏。保持
"一条构造对应一组指令"，生成器保持纯粹；折叠交给 IR 上的优化 pass
（读者可以用 -sccp 对同一模块观察真正的工业级折叠）。

### 17.5.3 表达式树的深度与指令序列

expr 的递归深度等于 AST 表达式树的深度，生成的指令数等于树的内部
节点数：每个二元构造恰好产出一条（比较产出两条）指令，叶子
（字面量、变量、input）产出零或一条（变量有 load）。这种一一对应
给了我们不依赖执行的成本估计：读源程序就能数出生成多少条指令，
17.14 节 IR 的指令总数因此完全可手工核对。也要注意一个边界：嵌套
过深的表达式在真实编译器里可能触及递归栈或后端的解析限制，但
TIP 教学程序都很浅；这与 8.6.3 的终止性问题不同——深度是语法
事实、可由前端直接计数，不是不可判定问题。指令的排列严格按
"先左子树、后右子树、最后本节点"，因此 IR 块里阅读指令序列，
就是表达式树的一次后序遍历。读 8.14 的 IR 时用这条规律，就不会
在嵌套算术里迷失：从最后一条指令往回读，遇到的操作数定义依次
向上展开。

### 17.5.4 比较为什么分两条指令：谓词世界与数值世界的分层

`x > 0` 的翻译是 `icmp sgt` 产出 i1、再 `zext` 扩成 i32，多了一条
指令。为什么 LLVM 不直接产出整数？因为 LLVM 把"逻辑真值"与"整数
数值"分成两个类型世界：分支指令只认 i1，算术只认整数类型，两个世界
不混用。TIP 站在数值世界一侧（比较结果能参与算术，如 `(x > 0) + 1`），
因此每次比较都要明确地从谓词世界"升格"到数值世界；反过来条件分支
处又要把整数"降格"为谓词（8.6 的 `icmp ne ... 0`）。这两条转换
指令看似啰嗦，实则把 TIP"非零即真、比较产 0/1"的两条约定显式化：
zext 保证谓词 true 恰好变成整数 1 而不是任意非零值，`icmp ne 0`
精确表达非零即真。若语言把布尔做成独立类型（如 C 的 _Bool 之后的
现代语言），其中一侧的转换就不再需要——读得懂这两条指令，就读懂了
TIP 类型设计的一个具体后果。有符号谓词 sgt/eq 的选择同样来自 TIP
语义：整数是数学整数的机器化身，比较按带符号解释；无符号谓词 ugt
对负数会给出相反答案，不能混用。

## 17.6 语句生成：store、output 与基本块编织

`stmt` 吃一个语句节点，不返回值——它的作用是在当前插入点所在的
基本块里追加指令，或创建新的基本块改变控制流。五种语句各有规则。

**赋值**：AssignS 的目标必须是 VarRef（经指针或字段写入留待第 53 章）。生成顺序是先递归算出右值表达式，再把结果 store 进目标符号
的槽位。注意"先算值后写入"的次序：右值里可能就引用了被赋值的
变量本身（`n = n - 1`），先 load 出旧值、完成减法、最后 store
新值，语义由此正确。一次赋值不产生 SSA 结果——它的效果落在内存
槽位上，后续 load 才能观察到。

**输出**：OutputS 递归算出表达式，把它作为实参调用 `tip_output`。
该运行时函数无返回值；一次执行中所有 output 调用的值序列就是
TIP 语义定义的输出流，JIT 运行时由宿主逐一收集。

**条件语句**：IfS 是第一条需要创建基本块的语句。生成器先取得
当前所在函数，依次创建 then、else、merge 三个块。条件表达式算出
的 i32 先与 0 比较（`icmp ne`）得到 i1，一条条件分叉 `br i1`
在 then/else 间选择。然后插入点移到 then 块、递归生成 then 语句；
若生成完该块仍没有终结指令，补一条无条件跳到 merge。else 块同理：
有 else 语句就递归生成，没有就直接跳 merge。最后插入点落在 merge
块——这意味着紧接 if 之后的语句会生成在 merge 块里，控制流自然
汇合。条件表达式为什么还要先与 0 比一次？因为分支指令只消费 i1，
而 TIP 的条件是任意整数表达式，约定非零即真，`icmp ne ... 0`
正是这个约定。

**循环语句**：WhileS 创建三个块：header（条件）、body、exit。
生成器先从当前块跳转到 header，在 header 里把条件与 0 比成 i1、
条件分叉到 body 或 exit；body 块里递归生成循环体，结束后跳回
header——这条 `body → header` 的边就是图论意义上的**回边**，
循环因此成立。最后插入点落在 exit 块，循环之后的语句生成在这里。
对比第 16 章 CFG 的 while 规则（header→body、body→header、
header→succ），三条边在 IR 块间一条不少。

**块语句**：BlockS 只是按顺序对每条子语句调用 stmt。它不创建
IR 块——花括号在 TIP 里的作用是第 14 章的作用域，不是控制流
边界，顺序语句本就可以共存在同一个基本块里。这也解释了为什么
第 12 章保留嵌套 BlockS 而 IR 生成无视嵌套：两层表示各取所需。

每条语句规则结束时，插入点要么仍在当前块（顺序语句），要么落在
语句的"汇合/退出"块（if/while）。这种统一约定让语句可以任意
嵌套：外层语句递归生成内层语句后，总能在正确的块里继续。第 8.15
节 irgen.cpp 中 IfS/WhileS 的代码只有三十余行，但每一行都对应
上面一条边的构造，读者可以逐行核对。

### 17.6.1 "插入点"约定为什么是正确性的关键

stmt 各分支靠一个共享约定协同：任何语句生成结束后，插入点位于该语句
语义上的"下一条指令位置"——顺序语句留在当前块，if 落在 merge，while
落在 exit。这个约定看似只是实现技巧，实则是嵌套能正确生成的全部秘密。
考虑嵌套 `if (a) while(b) ... ; x = 1;`：生成 while 后插入点在其 exit
块（属于 if 的 then 流），该块尚未终结，随后补跳 if 的 merge；而
`x = 1` 生成在 merge。若没有统一约定，外层就要知道内层创建了几个块、
出口在哪，嵌套层数一多必然出错。约定把"出口"抽象成插入点本身，
语句之间只通过它通信。8.13.3 的控制流对应论证，本质上就是证明这个
约定与语义"第一后续配置"一致。

### 17.6.2 终结指令的局部构造方式

生成器不预先规划全部块，而是**就地**创建：处理 if 时当场建三个块，
先放条件分叉，再依次填充。这种局部构造的好处是代码顺序与思维顺序一致——
想到分支就建分支，无须先建空块再回填；每条 condBr 写出时，目标块都
已经存在。块的嵌套归属（getParent）在创建时由当前插入点所在函数确定，
因此即便函数里有几十处分支，每个块都属于正确的函数。verifyModule
随后检查"非末条不可能是终结指令"等条件，漏补跳转立刻暴露。

### 17.6.3 终止性从哪里来：回边与"每次迭代有进展"的错觉

生成器忠实地造了回边，却没有对循环的终止性做任何保证——也不可能
保证。`while (1) ...` 在 IR 里就是一个没有出口可达的环，完全合法。
这里要澄清一个常见错觉：看到回边并不意味着循环会终止，终止性是
不可判定的（第 2 章的结论之一），任何编译器都不回答它。翻译器
的职责只到"块图与源程序的控制结构同构"：源程序能走的路径，块间
跳转一条不缺；源程序走不到的路径（如条件恒假的分支），翻译器也
不擅自删除——注意 8.5.2 的不折叠原则与此一致：**翻译器不分析，
只对应**。终止性、不可达分支等判断是第三、四篇分析的输出，而不是
生成器的输入。把这条分工记住，就不会期待 IRGen 报告"这个循环可能
是死循环"。

## 17.7 函数、入口与运行时声明

函数级的生成在 `genFun`，加上构造函数里的运行时声明与最后的
入口包装，共三处，合起来看完整的模块形状。

**运行时声明**：IRGen 构造时，模块还是空的，第一件事是声明两个
外部函数：`tip_input` 是无参、返回 i32；`tip_output` 吃一个 i32、
无返回。它们在模块里只有声明、没有定义。把声明放在最前面，后续
生成的函数体就可以直接引用。

**函数创建**：gen 第一遍为每个 TIP 函数创建 IR 函数：函数类型是
"若干 i32 参数、i32 返回"，参数个数严格来自 TIP 声明。名字按
发射规则转换：TIP 的 main 命名为 tip_main。

**函数体**：genFun 先创建入口块，然后处理参数与局部变量。每个
形参在入口处开一个 i32 槽位、把收到的实参值 store 进去；每个
var 声明也开一个槽位并零初始化——零初始化不是 TIP 语义要求
（TIP 允许未初始化变量），但它保证程序在错误地提前读取时行为
确定，便于教学观察。槽位连同符号登记进 locals。之后生成函数体
语句，最后用 return 表达式的值作为函数的 ret 终结指令。

**入口块 tip_entry**：TIP 程序没有规定 main 的参数从哪里来。我们
生成一个无参的入口函数：按 TIP main 的形参个数，依次调用
tip_input 取值，再把这些值传给 tip_main，返回其结果。JIT 运行时
执行的就是这个入口。

**为什么入口不命名为 main**：这是本章一个由目标平台决定的取舍。
LLVM 面向 MinGW 目标时，会自动在名为 main 的函数开头插入一条
对 CRT 内部符号 `__main` 的调用（用于运行全局初始化），而 JIT
模块里没有这个符号、物化时就会失败。把入口命名为 tip_entry，
既绕开了与 CRT 启动约定的耦合，也让"JIT 执行的是我们自己的
入口"这件事在 IR 文本里一目了然。

### 17.7.1 调用约定：为什么不手工指定

生成的函数全部使用 LLVM 默认调用约定。对进程内 JIT 而言，调用方与
被调方由同一编译器按同一目标生成，默认约定必然自洽，无须标注。手工
指定 fastcc 等约定属于优化手段，且要求调用两侧同步——本章没有这种
需求。形参不做零扩展/符号扩展注解：LLVM 知道参数是 i32、调用两侧
类型一致，扩展与否由后端按需要决定。返回值统一 i32，与 TIP 只有整数
函数的世界一致。签名层面唯一"多余"的工作是 var 槽位的零初始化——
如前所述它服务于教学确定性而非 TIP 规范。

### 17.7.2 槽位为什么一律开在入口块

形参与 var 的 alloca 全部生成在函数的入口块、任何分支之前。这不是
排版偏好，而是一条结构性约束的落地：alloca 在 LLVM 语义里只在执行
流经过它时分配槽位，若把某个 var 的 alloca 放进 then 块，else 流
里对该变量的 load 就会引用一个从未执行分配的指针——模块虽能通过
部分检查，运行行为却未定义。全部开在入口块保证槽位的**支配性**：
函数内任何引用点都被入口块支配，槽位在一切可能路径上均已就绪。
注意这条规则与 8.3.3 的 phi 伏笔呼应：工业 mem2reg pass 正是依赖
"alloca 位于入口块、只被直接 load/store"这一形状才能把槽位提升为
SSA 寄存器；我们把槽位摆在最有利的位置，后续 -O2 才能干净地工作。
入口块在存完形参后顺序接函数体第一条语句的生成，因此 ite 的 IR
里 entry 块同时含 n 的槽位与 f 的槽位，没有多余跳转。

## 17.8 verifyModule：生成器的第一道自动化测试

生成器本身是一段会写错的程序。在把模块交给 JIT 之前，我们先用
LLVM 自带的校验器做结构检查：`verify` 调用 verifyModule，它检查
一长串良构条件——每个基本块是否都以终结指令结尾、终结指令是否
在块末、call 的实参类型与个数是否匹配被调函数类型、引用的值是否
定义在同一函数内、SSA 定义是否支配引用，等等。校验通过才返回。

这道检查的定位要讲清楚：它检查的是**模块的结构良构性**，不是
"翻译是否符合 TIP 语义"。一个语义错误但结构合法的模块（例如把
Gt 翻译成无符号比较、把减法两个操作数写反）会顺利通过校验，却
在运行时给出错误结果。因此本章实际有两道防线：verifyModule
挡住结构错误（忘记补跳转、类型不匹配），JIT 运行结果与人工计算
的对照挡住语义错误。main.cpp 在生成后立即调用 verify，失败则
中止，不让坏模块进入执行阶段。

这个"生成即校验、失败即中止"的习惯在后续章节会一直保留：每一个
分析都先检查自己的中间产物，再产出结论。工具链提供的机械检查
越前置，留给人工核对的范围就越小。

### 17.8.1 校验器到底查什么：一份最小清单

verifyModule 检查的是"结构良构"而非"程序正确"，了解其边界才不会
误用。它会发现：基本块没有终结指令或终结指令不在块尾；终结指令后
仍有指令；指令引用了别的函数里的局部值；ret/调用的参数类型与签名
不符；phi 的前驱与所在块的实际前驱不一致；使用了畸形类型组合。它
**不会**发现：循环不终止、除以可能为零的值、溢出、逻辑写反（如
误选了 sgt 而非 sge）、不可达分支。一句话：凡能用局部结构规则判定
的，校验器负责；凡需要分析程序行为的，校验器沉默。这个边界对读
者理解全书很关键——它恰好是"翻译正确性"中机械可查部分与必须
论证部分的分界线：8.13 的归纳论证覆盖的，大多是校验器沉默的区域。

## 17.9 ORC JIT：模块是怎样被消费的

IR 模块只是一份静态文本。要让它真正运行，需要一个能把 IR 编译成
本机指令、解析符号、并把它们链接在一起的执行系统。本章使用 LLVM
新一代 JIT 框架 ORC，其具体入口是 LLJIT——一个为"在当前进程内
立即执行"量身定制的高层封装。先理解 ORC 的三个核心概念，jitrun.cpp
的每一步都是它们的操作。

**JITDylib（动态库）**：ORC 不把符号放进一个扁平的全局表，而是
模仿动态链接，把符号组织成若干 JITDylib。每个库有自己的符号集合，
并按一定顺序在其他库里查找未解析的引用。LLJIT 默认创建一个主库，
我们既可以向主库里添加 IR 模块（模块中的函数定义成为库符号），也
可以直接向主库注册已经在当前进程内存里的符号（宿主函数）。当一个
模块引用了 tip_input，链接器就在主库里找到我们注册的那个定义。

**惰性物化（materialization）**：添加模块并不等于立即编译全部函数。
ORC 为每个符号建立一个"待物化"条目，只有当查找真的请求该符号
（或被它依赖的符号）时，才触发编译：IR 经编译层变成本机目标码，
再链接进进程。对本章这种小程序，查找 tip_entry 会牵连其引用的
tip_main、再牵连运行时调用，全部相关函数一次编译完成。理解物化
有助于读懂可能出现的错误信息：JIT 的符号缺失错误发生在物化阶段，
即真正调用之前。

**符号解析与名称修饰**：编译器层面的名字（tip_input）在链接时
要经过目标平台的名称修饰（mangling），例如 C++ 会编码参数类型，
部分平台的 C 名字还会加前缀。直接按字符串注册容易与修饰规则失配。
LLJIT 的 mangleAndIntern 方法替我们完成这件事：输入未修饰名，
返回与模块内部引用完全一致的符号键。本章注册宿主函数时一律通过
它取名，因此生成的 IR 可以自然书写 tip_input，无须关心平台约定。

与 LLVM 旧一代 JIT（MCJIT）相比，ORC 的关键进步正是这种显式的
库—符号模型：宿主函数注入从"提前设置全局符号表"变成"向指定库
定义符号"，多个模块、多次执行的组合变得清晰。本章只用到一个库、
一次添加，但同一套接口在第 52 章需要为多次分析反复执行程序时
仍然适用。

### 17.9.1 本机目标初始化与编译路径

runJit 在创建 LLJIT 之前先做一次进程内初始化：InitializeNativeTarget
注册本机后端、InitializeNativeTargetAsmPrinter 注册目标代码发射所需的
机器函数生成。二者必须发生在任何编译之前，因此用一个函数内静态标志
保证全局只执行一次。初始化的含义值得说清：ORC 编译模块时，要为
"当前运行的这台机器"选择目标三元组与调度模型；这些信息在初始化后
由进程内注册的目标提供，LLJIT 据此把 IR 降低为本机目标码、再经进程内
链接把跳转与调用连到真实地址。整条路径——IR 函数 → 目标机器指令 →
内存中可直接调用的函数指针——完全不产生磁盘文件，这正是 JIT 与
"AOT 编译再运行"的区别，也是它适合交互式实验的原因。

### 17.9.2 ThreadSafeModule：所有权交接的标准包装

把模块交给 JIT 使用 ThreadSafeModule：它把 unique_ptr<Module> 与
unique_ptr<LLVMContext> 绑在一起，并为上下文配一把递归互斥锁，使
模块的销毁与编译不会在多线程下与上下文使用重叠。本章的 IRGen 恰好
以 unique_ptr 持有这两样东西，于是一次移动即可构造出 ThreadSafeModule，
IRGen 一侧不再保留任何引用。这解释了第 17.4 节的所有权设计为什么是
必需而非偏好：ORC 的接口单元就是"模块连同其上下文"的所有权，
生成器的结构顺应这个接口，交接处没有任何复制或悬空风险。

### 17.9.3 LLVM 的 Error 模型：错误是必须被消费的值

jitrun.cpp 里每个可能失败的调用都返回 llvm::Expected<T> 或
llvm::Error，检查后用 takeError() 取出、经 toString 转成普通文本
再抛异常。这与 C++ 异常风格不同：LLVM 的错误是**普通返回值**，
未检查、未消费的 Error 在析构时会主动终止程序——编译器强制你
面对每一个失败点，不可能像忽略异常规格那样忽略它。这与构建时
过滤掉 -fno-exceptions 的取舍互补：LLVM 自身在编译时禁用异常，
用 Error 值替代；我们的胶水层在边界处把它转换成 C++ 异常，使
main.cpp 可以用统一的 try 边界报告。理解这套模型就能读懂为什么
每个 `if (!x) fail(x.takeError())` 都不能省：省略检查不仅放过
错误，未消费的 Error 对象本身就是一次进程中止。把错误处理做成
类型系统强制的义务，是大型 C++ 代码库在无异常条件下保持可靠的
标准做法——这个小细节也是"可靠性"思想在工程风格上的投影。

## 17.10 宿主函数注入：把 TIP 的 I/O 接到 tipa 进程

TIP 的 input/output 是抽象的整数流，没有操作系统层面的绑定。本章
不把它们实现成读写控制台，而是让被 JIT 的程序与 tipa 进程通过两个
普通 C 函数交换数据，jitrun.cpp 中这部分设计如下。

**数据队列**：每次运行前，调用方提供一个整数向量作为输入、准备一个
空向量接收输出。两个文件内指针指向它们，并记录当前读取位置。

**tip_input**：每被调用一次，从输入向量当前位置取一个整数返回；
输入耗尽时返回 0。注意"耗尽返回 0"是一个保护性约定——TIP 程序
读取次数由程序自身决定，规范的 .inputs 文件会保证供给数量恰好。
把耗尽行为做成确定值，错误的输入文件不会导致越界，只会让输出
暴露异常。

**tip_output**：把收到的整数追加进输出向量。执行结束后，这个向量
就是本次运行按调用顺序产生的全部输出。

**注册**：runJit 用 ExecutorSymbolDef 把两个函数的进程内地址连同
符号标志打包，经 absoluteSymbols 定义进主库；符号键由
mangleAndIntern 取得。这样模块物化、链接 call 指令时，引用就解析
到了这两个函数本体——被 JIT 的代码与正常的动态链接代码在调用形式
上没有任何区别。

为什么必须是 `extern "C"`？因为模块里的引用按 C 名修饰查找，C++
默认会对函数名做类型编码；extern "C" 保证符号名与我们注册的键
一致。函数签名只使用定宽的 int32_t：IR 里的 i32 与之一一对应，
避免宿主编译器 int 宽度假设。

这套注入机制的意义不止 I/O。它演示了 ORC 最实用的能力：JIT 程序
可以与宿主共享任意的进程内函数与数据。第 32 章的可靠性检验正是
利用同一条通道——执行一次真实程序，把每个观察点的具体值与分析
预测的抽象集合当场比对。本章先把通道修好、用最简单的输出值验证
它通畅。

### 17.10.1 宿主状态为什么每次运行前显式重置

runJit 开头把两个队列指针与读取位置重新绑定到本次调用的向量。这一步
不能省：JIT 本身是进程内长期对象（目标初始化只做一次），而宿主函数
通过文件内变量与它隐式共享状态。若不显式重置，第二次 --run 会从上次
耗尽的位置继续读、或把新输出追加到旧向量之后。把"每次执行的输入/输出
状态"局限在一次 runJit 调用里、与 JIT 的长期生命分离，多次执行才彼此
独立。这个设计也提示了注入机制的一般纪律：宿主函数若依赖上下文，
上下文必须显式装配，不能依赖静态残留。

### 17.10.2 为什么不把 I/O 直接连到标准流

让 tip_input 读 stdin、tip_output 写 stdout 也能工作，本书没有这样做。
原因有三：自动化批量执行需要在不触碰控制台的情况下喂入多组输入；
输出需要以结构化整数向量的形式交给后续比对，而不是重新解析文本；
以及同一进程可以并发地容纳多套独立队列（第三篇以后多程序、多批次
检验时需要）。把 I/O 抽象成两个普通调用，程序语义与 I/O 载体彻底
解耦——本章载体是向量，换成文件或网络也只改宿主一侧，IR 不变。

### 17.10.3 JITDylib、惰性物化与符号查找次序

ORC 不是简单地"把模块整体编译再调用"，理解它的三个机制，输出与
错误信息就都可解释。第一，**JITDylib** 是一个符号命名空间：宿主
符号定义在主库里，模块加入时也落在主库，`tip_entry` 的查找因此能
同时看到二者。第二，**惰性物化**：模块加入时不编译任何函数，只登记
"哪个符号由哪个模块提供"；lookup("tip_entry") 才触发编译——从入口
沿调用关系只编译实际到达的函数，未被调用的函数永远不编译。这解释
了两件事：一个含有可疑指令但从未被调用的函数不会导致运行失败；
反过来，宿主符号漏注册时，错误也只在入口真正调用到它的那一刻才以
"Symbols not found" 报出。第三，**查找按库的链接次序进行**，主库
先于添加的模块；我们把宿主函数与生成函数放在同一个库里靠名字区分
（tip_input/tip_output 不会与用户函数撞名，因为 TIP 程序由
06 章的词法规则保证标识符集合但命名仍建议避开 tip_ 前缀——tipa
不强制，因为宿主符号与模块符号同名时定义阶段就会报重复定义）。
mangleAndIntern 做的"名字修饰"也值得一提：C++ ABI 下符号名在链接
层会被修饰，用它得到的键与模块内函数的链接名严格一致，手工拼写
必然在某平台出错。

### 17.10.4 宿主状态为什么是文件作用域指针而非单例对象

两个队列指针以匿名命名空间（文件作用域）的裸指针形式存在，每次
runJit 开头显式重置。也可以做成单例对象或 std::any 式注册表，本章
刻意从简。理由有三：JIT 出的代码通过 extern "C" 的普通函数访问
状态，状态的访问路径必须是无参全局的——它无法携带对象指针；
文件作用域把这套全局状态严格限制在本编译单元，外部不可见，避免
与其他运行时符号冲突；显式重置（而非依赖构造）让"每次执行互不
污染"成为一段看得见的代码，而不是隐含在对象生命周期里。裸指针
不持有所有权，队列的所有权在 main 的调用栈帧上、生命周期严格
覆盖 JIT 调用，因此不存在泄漏——这是一个所有权经过推演的简化，
而非随手的偷懒。多线程执行同一 JIT 时这套设计不适用，但本章所有
执行都是顺序的。

## 17.11 一次 --run 的完整生命周期

把前面各节串起来，跟踪 `tipa --run program.tip runs.inputs` 从
启动到结束的完整过程。main.cpp 的实现可以逐步对照。

第一步，解析命令行并打开输入脚本。脚本里以 # 开头的行与空行被
跳过，每个其余行代表一次执行，行内按空白切成若干整数，作为该次
执行的输入序列。同一份脚本因此可以描述多次独立运行，输出按
`run k:` 编号。

第二步，对每一行，重新走一遍完整前端：源文件解析成 AST、名字
解析得到绑定（若语法或语义有错，在这一步以退出码 2/3 中止），
然后构造一个全新的 IRGen：生成全部函数、立刻 verify。为什么每次
执行都重新生成、而不是复用模块？因为 JIT 在添加模块时取得所有权、
物化后模块与其上下文由 JIT 管理，复用需要额外的复制语义；重新生成
成本极低（这类程序的生成是毫秒级），且保证每次执行彼此完全独立、
不共享任何内存状态。这也是一种简单性取舍：用一点重复生成换取
清晰的所有权边界。

第三步，调用 runJit：初始化本机目标（进程内只做一次），创建 LLJIT，
注册两个宿主函数，把模块移入 ThreadSafeModule 并添加到主库，查找
tip_entry 的地址、转成函数指针、直接调用。从这一行起，控制权进入
JIT 编译出的本机代码：它按 main 形参个数回调 tip_input（即宿主
队列），执行 tip_main，遇到 output 回调 tip_output，最后返回。

第四步，tipa 取出输出向量，按 `run k: v1, v2` 的固定格式打印。
输出值之间以逗号空格分隔，没有输出时行就是 `run k:`。脚本的全部
行处理完，进程结束。

理解这个生命周期，关键在看清"谁在执行谁"：tipa 是宿主，JIT 出的
代码运行在同一进程、通过两个回调把 I/O 交回宿主；程序的全部可观察
行为就是这两个回调上的交互。因此"运行结果正确"可以精确核对——
给定输入序列，输出序列唯一确定，我们逐字节对账。

### 17.11.1 为什么输入脚本是独立文件而不是命令行参数

多组输入也可以直接写在命令行（如 `--run p.tip -- "5" "0" "3"`）。
本书坚持独立脚本文件，理由来自使用场景：第三篇以后一次检验常常
包含几十组输入，且输入本身带注释（每组输入对应什么测试情形），
命令行既无法承载注释，长度也受 shell 限制；脚本文件可与源程序
一起存档、diff、复现，命令行历史不能。此外脚本按行切分的格式
让"第 k 次执行 ↔ 第 k 行 ↔ 输出 run k"的对应一目了然，失败时
直接定位是哪组输入证伪了预测。文件解析还能统一处理编码与空白
（只接受十进制整数、任意空白分隔），命令行解析则要面对各 shell
的引号差异。一个工具链约定的选择标准是：**产物与输入都应是普通
文本文件，命令行只表达意图**——本章三个子命令都遵循此标准。

### 17.11.2 出错时的三条路径与退出码

运行前与运行中的错误分三类，tipa 的行为分层固定，自动化脚本据此报告
失败位置。语法错误在解析期收集、退出码 2，根本不会进入生成；语义错误
（未声明、重声明）在名字解析后、生成前中止，退出码 3；生成期遇到超出
整数核心的构造则以异常形式抛出，被 main 的调用边界转换为失败信息——
这类错误在本教程程序集里不出现，但保留显式通道。JIT 物化阶段若有符号
解析失败（如开发中漏注宿主函数），错误以 "JIT session error" 文本在
调用前报告。把四类失败的文本与退出码固定，run-all 才能在任何一层
漂移时准确定位，而不是只看到一个非零退出。

## 17.12 命令行协议：三个子命令与退出码

本章 tipa 的命令行协议在此汇总，后续章节会在其上增加子命令，但
已有约定不再改变。

- `tipa --check FILE`：解析、名字解析、生成并校验模块，通过后打印
  未优化的 IR 文本。它与 --emit-ir 等价：保留两个名字是因为从第 24 章起 --check 的语义将变为"运行该章分析并打印结果"，而需要观察
  IR 的章节使用 --emit-ir。
- `tipa --emit-ir FILE`：显式打印 IR。
- `tipa --run FILE INPUTS`：按 INPUTS 逐行执行，打印每次输出。

退出码约定分层固定：0 成功；1 用法或文件错误；2 语法错误；3 语义
错误（未声明、重复声明）。自动化脚本据此区分失败层级。一个实现细节
是所有诊断同时汇总到标准输出侧（check_example 将 stdout 与 stderr
合并对账），错误信息文本只依赖源程序内容、不含绝对路径等环境信息，
因此任何机器上的产物逐字节一致。输入脚本本身不是 TIP 程序：# 注释、
每行一次运行、行内空白分隔整数，这一约定在第 32 章的可靠性脚本中
继续沿用。

### 17.12.1 预告：--run 将怎样承担可靠性检验

本章 --run 只打印输出值；第 32 章起它会在不改变协议的前提下承担更多。
预先交代检验的形式，读者能明白本章协议为何如此设计。设想分析给每个
程序点上的每个变量一个抽象预测（如符号集合 {正}），检验时对每一行
输入执行程序，并在每个被观察点把具体值与预测当场比对：具体值 ∈
预测集合则记通过，否则该分析被一次反例证伪。为支持这一点，本章的
执行通道已经具备两个必要条件：输入序列完全由 .inputs 控制（可复现）、
每次执行彼此独立（重新生成模块）。第 32 章只需在生成的模块里插入
观察回调，或在关键语句后取回槽位值——槽位地址在 locals 表里已经
可得。本章建立的是"可控制、可观察、可重复"的执行；可靠性逻辑是
在其上加一层断言。这个分层也解释了为什么本章不把 input 绑定到真实
控制台：自动化的批量检验需要完全脚本化的输入。

### 17.12.2 退出码为什么是 tipa 契约的一部分

退出码不只是给人看的提示，它是自动化脚本与 tipa 之间的稳定接口：
run-all 依据退出码判断"这是预期的错误对账（错误程序应以指定码
失败）还是真正的构建事故"。因此退出码的分配满足两个条件：相互
排斥且分层稳定——用法/文件类 1 发生在最早，语法 2 使程序根本
没有 AST，语义 3 使 AST 不被生成阶段消费；成功路径恒为 0。错误
对账文件（第 14 章的 errors/*.txt）同时记录错误文本与退出码的
期望，任何一侧漂移都失败。一个推论：新增子命令时退出码语义不得
改动，只能在现有层级内细化——这与"已有命令行约定不再改变"
（8.12 开头）是同一条冻结原则的两面。接口一经发布即冻结，是
整个前端链条（以及任何要被脚本驱动的工具）可长期演化的前提。

## 17.13 正确性论证：翻译保语义

verifyModule 保证模块结构良构，JIT 运行保证代码能在本机执行，但本章
真正需要论证的性质更强：**生成的程序与 TIP 源程序语义一致**——给定
相同的输入序列，二者产生相同的输出序列。这是后续一切可靠性实验的前提：
如果连"执行的是不是源程序"都无法保证，"具体值是否落入抽象预测"的
检验就失去了意义。本节给出这条性质的形式化轮廓与论证思路。和第 12 章
一样，论证覆盖无穷的程序集合，经验运行只作现实旁证。

### 17.13.1 先给 TIP 一个最小的语义轮廓

要论证"翻译保语义"，先把"语义"说清楚。TIP 整数核心的语义可以用
配置之间的求值/执行关系刻画，只需三个组件：

- **状态** σ 由三部分组成：内存 m（变量名到整数的映射，对应执行到当前
  时刻各槽位的内容）、剩余输入序列 ι、已产生输出序列 ο。
- **表达式求值**是关系 `⟨E, σ⟩ ⇓ ⟨v, σ′⟩`：在状态 σ 下求 E，得到整数
  v 与（可能被 input 改变了的）新状态 σ′。各构造的规则是通常的算术
  语义：字面量求自身；变量在内存中取值；input 取输入序列首项并令剩余
  序列前移；二元运算先求左、再求右、按运算符合成（比较按 0/1）；
  调用先求实参与被调函数、在新的局部内存中执行函数体。
- **语句执行**是关系 `⟨S, σ⟩ ⇓ σ′`：赋值先求右值再把内存中该变量
  更新；output 求值后把结果追加到输出序列；if 按条件是否非零选择
  执行分支；while 在条件非零时执行循环体后重新判断，为零时结束；
  块顺序执行。

这只是轮廓而非完整定义，但已足够支撑翻译论证：IR 程序恰好是这组关系
的一种具体化——内存 m 对应函数栈帧上的各 alloca 槽位，ι、ο 对应宿主
维护的两个向量，求值/执行规则对应生成的指令序列。

### 17.13.2 表达式翻译：按结构归纳

有了语义轮廓，表达式翻译的正确性可表述为一条引理：

> 对任意表达式 E 与状态 σ，若 `⟨E, σ⟩ ⇓ ⟨v, σ′⟩`，则 IRGen 在对应
> 槽位状态下生成 E 的代码执行后，返回的 i32 值在数值上等于 v，且对
> 输入序列的消耗与 σ′ 一致。

证明按表达式结构归纳。归纳假设：E 的所有子表达式的翻译都满足引理。
逐构造检验：

- 字面量生成 i32 常量，求值规则也是字面量本身，直接成立。
- 变量生成 load，取出的正是内存 m 中该名字当前值，与求值规则一致。
- input 生成 call tip_input，宿主按读取位置返回首项并前移，语义规则
  做的正是同一件事；两侧对输入序列的消耗相同。
- 二元算术递归生成左右值（归纳假设保证其值与求值顺序正确），生成的
  add/sub/mul/sdiv 与算术语义逐运算对应；比较多一步 i1→i32 零扩展，
  谓词真假映射为 1/0，恰好是比较规则。
- 直接调用的实参按序递归（归纳假设），call 进入的函数类型与 TIP 声明
  一致，返回值即函数体语义给出的结果。

每个分支成立，归纳完成。这里值得注意的是论证依赖的**组合性**：复合
表达式的语义由其子表达式语义组合而成，而生成代码也是由子表达式代码
组合而成——两种结构同构，归纳才得以进行。这也是第 12 章坚持 AST
节点种类与语言构造一一对应的深层回报。

### 17.13.3 语句翻译：控制流的对应

语句层面的引理：

> 若 `⟨S, σ⟩ ⇓ σ′`，则生成的语句代码从对应块执行后到达的块与槽位
> 状态，恰好表达 σ′。

逐类说明。赋值：右值翻译给出 v（8.13.2），store 更新槽位，与内存
更新规则一致；且先算后写的次序保证自引用正确。output：求值后调用
tip_output，宿主追加顺序与语义的输出序列一致。if：生成的 `icmp ne 0`
重述了"非零即真"的条件语义，条件分叉选择的块与语义选择的分支一致，
两分支最终都到 merge——这正对应"if 执行完后控制流汇合"。while：
语义上是"条件非零则执行体、回到判断"，生成的块图恰好有 body→header
回边与 header→exit 的离开边；对循环的严格论证可用循环不变式进行：
若每次沿回边回到 header 时槽位状态与按语义迭代相应次数后的状态一致，
则退出时状态一致。块语句顺序生成，与顺序执行规则对应。

控制流论证中 merge、exit 块扮演了语义"第一个后续配置"的角色：内层
语句执行完后到达的静态位置，正是下一条语句生成的位置。第 17.6 节
"每条语句规则结束时插入点位置"的统一约定，就是这条对应关系在实现
里的落点。

### 17.13.4 可观察行为等价，以及论证的边界

把两层引理接到函数入口：tip_entry 按 main 形参个数从同一输入序列取值、
调用 tip_main，与 TIP 程序从输入流读取参数的规则一致。于是得到本章的
总体结论：

> 对任意输入序列，JIT 执行生成程序产生的输出序列，与按 TIP 语义执行
> 源程序产生的输出序列相同。

这是一个可观察行为意义上的等价。要诚实地指出论证的边界：它依赖两个
本章程序都满足的条件。其一，所有算术结果在 i32 范围内——TIP 整数
理论上任意精度，溢出时 C++ 有符号运算与我们的 IR 指令都不提供 TIP
语义保证；教学程序刻意避开溢出。其二，除法除数非零——除零在两侧都
没有规定结果。把这两个条件写明，论证才不是空话；第 32 章的可靠性
讨论也会用同样的方式处理"分析对未定义行为不承担责任"。

### 17.13.5 论证与运行的分工（再次强调）

和第 12 章一样，本章同时有形式化论证与经验运行。论证覆盖全部程序但
假设实现无笔误；JIT 运行只覆盖 ite、outputs 两个程序，却能抓住参数
顺序写反、谓词选错符号这类现实错误。本章两个程序的运行结果（阶乘
120/1/6；加法 7、乘法 6）全部与人工计算一致，是论证在这批具体程序上
的兑现——不是替代论证。读者在第 24 章将看到完全同构的三层结构：
类型规则（规范）、约束求解（实现）、程序清单上的推导结果（经验核对）。

### 17.13.6 一个配置演算的工作示例

形式化规则容易显得抽象，用一次真实的小演算把它们走一遍。跟踪 ite 程序
输入 3 的前几步，配置写作 `(内存; 剩余输入; 输出)`。

- 入口：tip_input 取首项，main 以 n=3 启动；配置 `(n=3; []; [])`。
  函数体为 f 开槽位并赋 1：`(n=3, f=1; []; [])`。
- 第一次判断：3 > 0 求值得 1，进入循环体。先求 `f * n`：左 1、右 3，
  乘法得 3，写入 f；再求 `n - 1` 得 2 写入 n。配置变 `(n=2, f=3; []; [])`。
- 沿回边第二次判断：2 > 0 成立，f 变 6、n 变 1：`(n=1, f=6; []; [])`。
- 第三次：1 > 0 成立，f 变 6、n 变 0：`(n=0, f=6; []; [])`。
- 第四次判断：0 > 0 求值得 0，退出循环；output 追加 6：`(n=0, f=6; []; [6])`；
  返回 6。

每一步都可以同时对照三样东西：源程序的语句、上节的语义规则、以及 IR
文本里对应的 load/算术/store/跳转序列——三者描述同一次状态迁移。这正是
翻译论证在一个具体输入上的可视化：语义配置中的内存映射，就是 IR 执行
到相应块时各槽位的内容；配置序列经过的判断次数，就是沿 header 回边
迭代的次数。手工演算一次小输入，是检验生成器最直接的办法；第 32 章
检验抽象预测时，我们也会用同样的配置跟踪，只是每个具体值旁多记一个
"是否落在预测集合里"。

### 17.13.7 求值次序：一个被翻译固定下来的细节

TIP 语义对子表达式的求值次序有所规定（先左后右、调用时先求被调再按序
求实参）。这在有 input 参与时不可忽略：`input + input` 的结果取决于
先后次序。生成器按固定次序递归、生成的指令在基本块里顺序排列，因此
次序被翻译**原样固定**——两次 call tip_input 在指令流中的先后就是
消费顺序。这个细节也说明翻译论证为什么必须逐构造规定递归次序，而不能
只论证最终值：对纯算术交换次序不改变结果，但对含 input 的表达式，
次序本身就是可观察行为。第 17.5 节"按从左到右递归"的约定承担的就是
这条语义。

### 17.13.8 与 LLVM 中端的接口：opt 通道怎样用

本章生成的模块是标准 LLVM IR，可以直接交给命令行工具 opt 运行中端
分析与变换，这是本书第三条验证通道的入口。两种典型用法在此说明，
第 33 章会实际使用。其一，运行分析类 pass（如 `-passes=print<sccp>`
或 `-passes='print<da>'`）让工业实现打印对同一程序的分析结果，与我们
的教学结果对照；其二，运行优化管线（`-passes=default<O2>`）后比较
IR，观察分析驱动的变换实际改变了什么（死代码删除、循环简化）。
这要求我们生成的 IR 严格良构——这正是 verifyModule 存在的理由之一：
opt 对畸形模块会直接拒绝。也因此本章保持 IR 朴素：不手工折叠、不加
未经论证的标志，中端在其上做什么都能与源程序清楚对应。

### 17.13.9 翻译论证在全书论证体系中的位置

第 2 章引入了"可靠"的一般定义，本章论证的是一种特殊的可靠性——
"具体语义到具体语义"的保结构、保行为翻译。它与后续分析的可靠性
论证形式同构、难度递进：本章两侧都是具体世界（配置 ↔ 指令），第三篇
起一侧具体、一侧抽象（具体值 ↔ 类型/格元素），论证需要多一座
"抽象映射"桥。先在同构的简单情形上走通归纳，读者在第 24 章看到
"具体表达式 ↔ 类型变量"的对应时不会陌生。这也是本书把执行台放在
分析之前的原因：具体世界是检验一切抽象的基准。

### 17.13.10 除法与取整方向：一个尚未爆发但已埋下的分歧

TIP 的 `/` 继承数学记法，而我们选用的 sdiv 采用 C 语言家族的
"向零截断"：`-7 / 2` 在 sdiv 下为 -3，而某些数学教材的整除
定义（向下取整的地板除）给 -4。本章程序不含负数除法，分歧不爆发；
但必须在此写明，因为它不属于 8.13.4 的两个边界条件，而是一条
**两侧在良定义输入上就可能不同**的语义细节。处理办法有两种：
若主张 TIP 采用向零截断，则 sdiv 正确、语义条款须显式如此规定；
若主张地板除，则要在检测到负被除数时生成修正指令——那已经是
分析驱动的代码生成，留作习题。本书采用前者：在第 3 章的语言
定义里把 `/` 明确为机器整数的向零整除。这个例子说明，翻译论证
迫使我们把源语言规格中每一处含糊都钉死；规格含糊的地方，没有
任何翻译能"正确"，因为正确无定义。后续抽象解释中 widening 的
选择、指针分析的合并粒度，本质上是同类问题：先有精确规定，才有
可靠性可言。

### 17.13.11 组合性：为什么生成器与论证能共享同一种递归形状

回头看会发现一个优美的事实：irgen.cpp 里 expr 的代码结构与 8.13.2
归纳证明的结构完全重合——都是"按语法产生式分派、先处理子部分、
再组合"。这不是巧合，而是**组合语义**的一般性质：语言的语义按语法
组合地给出，则实现（翻译）与论证（对语法结构归纳）天然是同一种
递归。由此得到两个工程推论。其一，给 TIP 增加一个新表达式构造
（如第 53 章的取地址）时，工作量被严格局部化：写一个新节点、加
一条生成分支、补一条归纳情形，三处一一对应，不触碰已有分支。
其二，遗漏分支会同时在两处显现：代码里若没有对应分支则生成失败
（dynamic_cast 链末端抛错），论证里若缺该情形则归纳不完整——
这与第 12 章"输出对账防止静默漏分支"是同一思想在语义层的再现。
后续各篇的分析器虽然算法更复杂（迭代到不动点、沿图传播），其
可靠性证明仍是组合的：传递函数按程序点/语句局部定义，全局结论
由不动点框架组合出来。先在本章看清"同一种递归形状"，第三篇的
约束生成、第四篇的传递函数都不过是这一形状的变体。

## 17.14 真实输出解读

第 17.15 节给出的代码与 expected 文本逐字节一致，本节带读者把它读通。
建议先读 run 输出建立"程序做了什么"，再回到 IR 看清"机器怎样做"。

### 17.14.1 先看运行结果

ite.inputs 给了三行：5、0、3。main 有一个形参，每次执行读一个整数，
程序计算阶乘并 output：5! = 120；0 的阶乘约定为 1（循环一次不进，
f 保持 1）；3! = 6。输出三行 `run 1: 120`、`run 2: 1`、`run 3: 6`，
逐行可核。第二组 outputs.inputs 每行两个整数，main 无参、函数体自己
读两次 input：3 与 4 得到和 7、`3 * 2` 得到 6；10 与 20 得到 30、
20。注意输出顺序严格按程序里 output 的书写顺序，乘法输出总在加法之后，
这正是输出序列语义。

### 17.14.2 读 ite 的 IR 模块

模块开头是两个运行时声明，之后是 tip_main，最后是 tip_entry。沿块读
tip_main：

- entry 块为形参 n 开槽位并存入实参；为局部变量 f 开槽位，先零初始化、
  随即存入 1（对应 `f = 1`）；最后无条件进入 wh.cond。可以数到：源程序
  每次赋值都对应一次 store，没有额外动作。
- wh.cond 块是循环头：load n，`sgt ... 0` 得 i1，zext 成 i32——
  再 `icmp ne ... 0` 转回 i1 供分支使用。这里出现了第 17.5 节讲的两次
  类型转换的完整链条：TIP 的整数条件经过"比较产出 i32、条件处再还原
  成 i1"。文本上稍显迂回，但每一步都有语义来由。
- wh.body 块：load f、load n，mul 后 store 回 f；load n、减 1 后 store；
  跳回 wh.cond。循环体两条赋值的次序与源程序完全一致，回边显式可见。
- wh.exit 块：load f 调用 tip_output（对应 output 语句），再 load f 作为
  返回值。输出与返回用的是同一份槽位内容，故二者必然相等。

tip_entry 读一次 tip_input、把结果传给 tip_main。整个模块的块图与第 16 章为 ite.tip 构造的 CFG（条件节点 3、回边 5→3）结构相同，只是现在
每个 CFG 节点都落实成了具体指令。

### 17.14.3 读 outputs 的 IR 与完整对账

outputs.tip 的 tip_main 无参：entry 里为 x、y 两个 var 开两个槽位；
两次 call tip_input 的结果分别 store；然后 load 两个值做 add、交给
tip_output，load x 与常量 2 做 mul、再 output；最后返回常量 0。对照
源码六行函数体，生成的指令一对一提名。tip_entry 因为 main 无参而不读
任何输入、直接调用 tip_main——所以该程序的输入全部来自函数体内的
显式 input，这与 ite 由参数获得输入形成对照。理解这个区别，就读懂了
第 17.7 节入口包装存在的理由：参数的个数与位置由声明决定，入口统一
负责把输入流搬到参数上。

expected/output.txt 是对账脚本把两个程序的 --check 结果拼接而成：
`== ite.tip ==` 之后跟该程序完整模块，空行后是 `== outputs.tip ==`。
每次运行 check_example，tipa 重新生成模块与之逐字节比较——IR 里连
寄存器自动编号（%n1、%4 等）都因此被钉死，任何生成代码的漂移
都会立刻被捕获。这种"连编号都对账"的严格性，正是本章作为量具所
需要的：IR 稳定，后续用它讨论优化时才有共同的文本起点。

### 17.14.4 一张总览表：TIP 构造 ↔ IR 模式 ↔ 语义规则

把全章的对应关系收成一张表，可作为复习索引；每一行的完整论证都在
前文章节。

| TIP 构造 | 生成的 IR 模式 | 对应的语义规则 |
|---|---|---|
| 整数字面量 | i32 常量 | 字面量求自身 |
| 变量引用 | 查 locals 后 load | 内存中取当前值 |
| input | call @tip_input | 取输入首项并前移 |
| 算术二元运算 | add/sub/mul/sdiv | 先左后右按运算求值 |
| 比较 `>`/`==` | icmp sgt/eq + zext | 谓词真值得 1、假得 0 |
| 直接调用 | 实参按序 call | 局部内存中执行被调函数 |
| 赋值 | 算右值后 store | 更新内存中该变量 |
| output | call @tip_output | 追加输出序列 |
| if | icmp ne 0 + condBr + merge | 非零选 then，否则 else |
| while | header/body/exit + 回边 | 非零迭代，为零退出 |
| 块 | 顺序生成，无新块 | 顺序执行 |
| return | ret | 函数结果交给调用点 |

读表时关注最后两列的平行关系：IR 模式不过是语义规则在 LLVM 指令集上
的一种具体化，没有一条规则是翻译阶段新发明的。这正是 17.13 节归纳论证
能够一行一行走通的根本原因。

### 17.14.5 读 IR 时几个常见的误读

第一次读 IR 容易产生几个误解，在此预先澄清。`%n1`、`%4` 这样的名字
没有语义——它们只是打印器按定义顺序给的自动编号，改编号不改变程序；
真正的身份是"哪条指令定义了它"，def-use 关系才是结构。`ptr` 类型不
说明指向什么，不能从槽位类型推断变量内容；变量的语义内容只存在于
运行时。指令上的 `align 4` 是 ABI 对齐保证、不是值的一部分。块上的
`; preds = ...` 注释是打印器附加的前驱列表、不是指令。读懂这些，
IR 文本就回归为它本来的样子：带类型指令与块图的精确表示。

### 17.14.6 输出对账文件的结构再说明

expected/run/ite.txt 只有三行 run 记录，outputs.txt 两行；
expected/output.txt 则是两个完整模块。两类文件对账方式不同：前者比对
JIT 的可观察输出，后者比对生成器的可观察产物。对 --run，输入向量
来自 .inputs（.inputs 本身不嵌入文档——它不是文本产物），输出逐字节
固定；对 --check，输入只有源程序，输出因此在任何环境一致。分清
"哪个文件由哪个命令、以什么为输入产生"，run-all 的失败信息才
一目了然。

### 17.14.7 两个程序的 IR 并排看：哪些部分必然相同

把 ite 与 outputs 两个模块并排比较，能区分 IR 中"由框架决定"与
"由程序决定"的两部分，这是读任何编译器输出都有用的习惯。必然相同
的部分：两个运行时声明（tip_input/tip_output 的类型一字不差）、
tip_entry 的形状（无参、按形参数 call input、call tip_main、ret）、
入口块里参数与局部变量的槽位布局模式。随程序变化的部分：tip_main
的参数个数、槽位个数与名字、基本块的拓扑（ite 有 wh.cond/wh.body
回边，outputs 是直线代码）、指令数目。输出文本里 `ModuleID` 固定
为 "tip"——模块名由生成器构造时写死，与源文件名无关，这也是产物
跨机器、跨目录一致的条件之一。读输出时先扫框架部分确认协议，再
沿块图读程序部分，就不会在几十行槽位指令中迷路。

```cpp
// file: src/ast.hpp
// AST 定义：AST 是去掉了括号、分号等语法噪音的程序结构。
// 接口自本章起冻结，后续所有分析（名字、CFG、类型、格……）都在此之上工作。
#pragma once

#include <memory>
#include <string>
#include <utility>
#include <vector>

namespace tip {

enum class BOp { Add, Sub, Mul, Div, Gt, Eq };

struct Expr {
    virtual ~Expr() = default;
};
struct IntLit : Expr {
    int v;
    explicit IntLit(int value) : v(value) {}
};
struct VarRef : Expr {
    std::string name;
    explicit VarRef(std::string n) : name(std::move(n)) {}
};
struct InputE : Expr {};
struct Binop : Expr {
    BOp op;
    std::unique_ptr<Expr> l, r;
    Binop(BOp o, std::unique_ptr<Expr> lhs, std::unique_ptr<Expr> rhs)
        : op(o), l(std::move(lhs)), r(std::move(rhs)) {}
};
struct CallE : Expr {
    std::unique_ptr<Expr> callee;
    std::vector<std::unique_ptr<Expr>> args;
    CallE(std::unique_ptr<Expr> fn, std::vector<std::unique_ptr<Expr>> as)
        : callee(std::move(fn)), args(std::move(as)) {}
};
struct Deref : Expr {
    std::unique_ptr<Expr> e;
    explicit Deref(std::unique_ptr<Expr> p) : e(std::move(p)) {}
};
struct AddrOf : Expr {                       // spa: & Id
    std::string name;
    explicit AddrOf(std::string n) : name(std::move(n)) {}
};
struct AllocE : Expr {
    std::unique_ptr<Expr> e;
    explicit AllocE(std::unique_ptr<Expr> init) : e(std::move(init)) {}
};
struct NullE : Expr {};
struct RecLit : Expr {
    std::vector<std::pair<std::string, std::unique_ptr<Expr>>> fields;
    explicit RecLit(std::vector<std::pair<std::string, std::unique_ptr<Expr>>> fs)
        : fields(std::move(fs)) {}
};
struct FieldA : Expr {
    std::unique_ptr<Expr> e;
    std::string field;
    FieldA(std::unique_ptr<Expr> record, std::string f)
        : e(std::move(record)), field(std::move(f)) {}
};

struct Stmt {
    virtual ~Stmt() = default;
};
// target 只会是 VarRef / FieldA / Deref，文法 lvalue 已限定。
struct AssignS : Stmt {
    std::unique_ptr<Expr> target, value;
    AssignS(std::unique_ptr<Expr> t, std::unique_ptr<Expr> v)
        : target(std::move(t)), value(std::move(v)) {}
};
struct OutputS : Stmt {
    std::unique_ptr<Expr> e;
    explicit OutputS(std::unique_ptr<Expr> x) : e(std::move(x)) {}
};
struct IfS : Stmt {
    std::unique_ptr<Expr> cond;
    std::unique_ptr<Stmt> then, els;
    IfS(std::unique_ptr<Expr> c, std::unique_ptr<Stmt> t, std::unique_ptr<Stmt> e)
        : cond(std::move(c)), then(std::move(t)), els(std::move(e)) {}
};
struct WhileS : Stmt {
    std::unique_ptr<Expr> cond;
    std::unique_ptr<Stmt> body;
    WhileS(std::unique_ptr<Expr> c, std::unique_ptr<Stmt> b)
        : cond(std::move(c)), body(std::move(b)) {}
};
struct BlockS : Stmt {
    std::vector<std::unique_ptr<Stmt>> ss;
    explicit BlockS(std::vector<std::unique_ptr<Stmt>> v) : ss(std::move(v)) {}
};
struct ReturnS : Stmt {
    std::unique_ptr<Expr> e;
    explicit ReturnS(std::unique_ptr<Expr> x) : e(std::move(x)) {}
};

struct FunDecl {
    std::string name;
    std::vector<std::string> params;
    std::vector<std::string> vars;
    std::unique_ptr<Stmt> body;
    std::unique_ptr<ReturnS> ret;
};

struct ProgramA {
    std::vector<std::unique_ptr<FunDecl>> funs;
};

}  // namespace tip
```

```cpp
// file: src/ast_build.cpp
#include "ast_build.hpp"

#include <utility>
#include <vector>

namespace tip {

std::unique_ptr<ProgramA> AstBuilder::build(TIPParser::ProgramContext *tree) {
    auto program = std::make_unique<ProgramA>();
    for (auto *fc : tree->function()) program->funs.push_back(buildFun(fc));
    return program;
}

std::unique_ptr<FunDecl> AstBuilder::buildFun(TIPParser::FunctionContext *ctx) {
    auto f = std::make_unique<FunDecl>();
    f->name = ctx->IDENT()->getText();
    if (ctx->params()) {
        for (auto *p : ctx->params()->IDENT()) f->params.push_back(p->getText());
    }
    if (ctx->varDecls()) {
        for (auto *v : ctx->varDecls()->IDENT()) f->vars.push_back(v->getText());
    }

    std::vector<std::unique_ptr<Stmt>> body;
    for (auto *sc : ctx->stmt()) body.push_back(buildStmt(sc));
    f->body = std::make_unique<BlockS>(std::move(body));

    f->ret = std::make_unique<ReturnS>(buildExpr(ctx->expr()));
    return f;
}

std::unique_ptr<Expr> AstBuilder::buildLvalue(TIPParser::LvalueContext *lv) {
    std::unique_ptr<Expr> base;
    std::string field;
    if (auto *d = dynamic_cast<TIPParser::DirectLvalueContext *>(lv)) {
        base = std::make_unique<VarRef>(d->IDENT(0)->getText());
        if (d->IDENT().size() == 2) field = d->IDENT(1)->getText();
    } else {
        auto *p = dynamic_cast<TIPParser::PointerLvalueContext *>(lv);
        base = std::make_unique<Deref>(buildExpr(p->expr()));
        if (p->IDENT()) field = p->IDENT()->getText();
    }
    if (!field.empty())
        return std::make_unique<FieldA>(std::move(base), std::move(field));
    return base;
}

std::unique_ptr<Expr> AstBuilder::buildExpr(TIPParser::ExprContext *ctx) {
    if (auto *c = dynamic_cast<TIPParser::IntExprContext *>(ctx))
        return std::make_unique<IntLit>(std::stoi(c->INT()->getText()));
    if (auto *c = dynamic_cast<TIPParser::VarExprContext *>(ctx))
        return std::make_unique<VarRef>(c->IDENT()->getText());
    if (dynamic_cast<TIPParser::InputExprContext *>(ctx))
        return std::make_unique<InputE>();
    if (dynamic_cast<TIPParser::NullExprContext *>(ctx))
        return std::make_unique<NullE>();
    if (auto *c = dynamic_cast<TIPParser::ParenExprContext *>(ctx))
        return buildExpr(c->expr());

    if (auto *c = dynamic_cast<TIPParser::AddExprContext *>(ctx)) {
        const BOp op = c->PLUS() ? BOp::Add : BOp::Sub;
        return std::make_unique<Binop>(op, buildExpr(c->expr(0)), buildExpr(c->expr(1)));
    }
    if (auto *c = dynamic_cast<TIPParser::MulExprContext *>(ctx)) {
        const BOp op = c->STAR() ? BOp::Mul : BOp::Div;
        return std::make_unique<Binop>(op, buildExpr(c->expr(0)), buildExpr(c->expr(1)));
    }
    if (auto *c = dynamic_cast<TIPParser::CmpExprContext *>(ctx)) {
        const BOp op = c->GT() ? BOp::Gt : BOp::Eq;
        return std::make_unique<Binop>(op, buildExpr(c->expr(0)), buildExpr(c->expr(1)));
    }
    if (auto *c = dynamic_cast<TIPParser::NegExprContext *>(ctx)) {
        // TIP 没有负数字面量 token，-E 即 0-E。
        return std::make_unique<Binop>(BOp::Sub, std::make_unique<IntLit>(0),
                                       buildExpr(c->expr()));
    }
    if (auto *c = dynamic_cast<TIPParser::CallExprContext *>(ctx)) {
        std::vector<std::unique_ptr<Expr>> args;
        if (c->args())
            for (auto *a : c->args()->expr()) args.push_back(buildExpr(a));
        return std::make_unique<CallE>(buildExpr(c->expr()), std::move(args));
    }
    if (auto *c = dynamic_cast<TIPParser::FieldExprContext *>(ctx))
        return std::make_unique<FieldA>(buildExpr(c->expr()), c->IDENT()->getText());
    if (auto *c = dynamic_cast<TIPParser::DerefExprContext *>(ctx))
        return std::make_unique<Deref>(buildExpr(c->expr()));
    if (auto *c = dynamic_cast<TIPParser::AddrExprContext *>(ctx))
        return std::make_unique<AddrOf>(c->IDENT()->getText());
    if (auto *c = dynamic_cast<TIPParser::AllocExprContext *>(ctx))
        return std::make_unique<AllocE>(buildExpr(c->expr()));
    if (auto *c = dynamic_cast<TIPParser::RecExprContext *>(ctx)) {
        std::vector<std::pair<std::string, std::unique_ptr<Expr>>> fields;
        for (auto *fc : c->field())
            fields.emplace_back(fc->IDENT()->getText(), buildExpr(fc->expr()));
        return std::make_unique<RecLit>(std::move(fields));
    }
    return nullptr;  // 解析成功时不会到达
}

std::unique_ptr<Stmt> AstBuilder::buildStmt(TIPParser::StmtContext *ctx) {
    if (auto *c = dynamic_cast<TIPParser::AssignStmtContext *>(ctx))
        return std::make_unique<AssignS>(buildLvalue(c->lvalue()), buildExpr(c->expr()));
    if (auto *c = dynamic_cast<TIPParser::OutputStmtContext *>(ctx))
        return std::make_unique<OutputS>(buildExpr(c->expr()));
    if (auto *c = dynamic_cast<TIPParser::IfStmtContext *>(ctx)) {
        std::unique_ptr<Stmt> els;
        if (c->stmt().size() == 2) els = buildStmt(c->stmt(1));
        return std::make_unique<IfS>(buildExpr(c->expr()), buildStmt(c->stmt(0)),
                                     std::move(els));
    }
    if (auto *c = dynamic_cast<TIPParser::WhileStmtContext *>(ctx))
        return std::make_unique<WhileS>(buildExpr(c->expr()), buildStmt(c->stmt()));
    if (auto *c = dynamic_cast<TIPParser::BlockStmtContext *>(ctx)) {
        std::vector<std::unique_ptr<Stmt>> ss;
        for (auto *sc : c->stmt()) ss.push_back(buildStmt(sc));
        return std::make_unique<BlockS>(std::move(ss));
    }
    return nullptr;  // 解析成功时不会到达
}

std::unique_ptr<ProgramA> buildAst(TIPParser::ProgramContext *tree) {
    return AstBuilder{}.build(tree);
}
```

```cpp
IRGen::IRGen()
    : ctx(std::make_unique<LLVMContext>()),
      mod(std::make_unique<Module>("tip", *ctx)),
      b(std::make_unique<IRBuilder<>>(*ctx)) {
    // 运行时入口先声明：input 无参返回 i32，output 吃一个 i32。
    auto *i32 = Type::getInt32Ty(*ctx);
    rtInput_ = mod->getOrInsertFunction(
        "tip_input", FunctionType::get(i32, false));
    rtOutput_ = mod->getOrInsertFunction(
        "tip_output", FunctionType::get(Type::getVoidTy(*ctx), {i32}, false));
}

namespace {

// TIP 的 main 改名 tip_main：真正的 @main 是我们生成的 C 入口。
std::string emitName(const std::string &name) {
    return name == "main" ? "tip_main" : name;
}

}  // namespace

void IRGen::gen(const ProgramA &program, const Bindings &resolved) {
    bindings = &resolved;

    // 先创建全部函数（含类型），函数体互相前向调用时也能查到声明。
    auto *i32 = Type::getInt32Ty(*ctx);
    for (const auto &f : program.funs) {
        std::vector<Type *> args(f->params.size(), i32);
        auto *ft = FunctionType::get(i32, args, false);
        Function::Create(ft, Function::ExternalLinkage,
                         emitName(f->name), *mod);
    }

    for (size_t i = 0; i < program.funs.size(); ++i) {
        const auto &f = program.funs[i];
        cur = f.get();
        genFun(f.get(), resolved.scopes[i].get());
    }

    const FunDecl *mainFun = nullptr;
    for (const auto &f : program.funs)
        if (f->name == "main") mainFun = f.get();
    if (!mainFun) throw std::runtime_error("program has no main");
    genWrapper(mainFun);
}

void IRGen::genFun(const FunDecl *f, Scope *scope) {
    auto *fn = llvm::cast<Function>(mod->getFunction(emitName(f->name)));
    auto *entry = BasicBlock::Create(*ctx, "entry", fn);
    b->SetInsertPoint(entry);

    // 形参：alloca 槽位 + 存入实参；var 局部：alloca + 零初始化。
    for (size_t j = 0; j < f->params.size(); ++j) {
        const Symbol *s = &scope->table.at(f->params[j]);
        auto *slot = b->CreateAlloca(b->getInt32Ty(), nullptr, f->params[j]);
        b->CreateStore(fn->getArg(j), slot);
        locals[s] = slot;
    }
    for (const std::string &v : f->vars) {
        const Symbol *s = &scope->table.at(v);
        auto *slot = b->CreateAlloca(b->getInt32Ty(), nullptr, v);
        b->CreateStore(b->getInt32(0), slot);
        locals[s] = slot;
    }

    stmt(f->body.get());
    b->CreateRet(expr(f->ret->e.get()));
}

Value *IRGen::expr(const Expr *e) {
    if (const auto *x = dynamic_cast<const IntLit *>(e))
        return ConstantInt::get(b->getInt32Ty(), x->v, true);

    if (const auto *x = dynamic_cast<const VarRef *>(e)) {
        const Symbol *s = bindings->uses.at(x);
        return b->CreateLoad(b->getInt32Ty(), locals.at(s), x->name);
    }

    if (dynamic_cast<const InputE *>(e))
        return b->CreateCall(rtInput_);

    if (const auto *x = dynamic_cast<const Binop *>(e)) {
        Value *l = expr(x->l.get());
        Value *r = expr(x->r.get());
        switch (x->op) {
            case BOp::Add: return b->CreateAdd(l, r);
            case BOp::Sub: return b->CreateSub(l, r);
            case BOp::Mul: return b->CreateMul(l, r);
            case BOp::Div: return b->CreateSDiv(l, r);
            case BOp::Gt: {
                Value *p = b->CreateICmpSGT(l, r);
                return b->CreateZExt(p, b->getInt32Ty());
            }
            case BOp::Eq: {
                Value *p = b->CreateICmpEQ(l, r);
                return b->CreateZExt(p, b->getInt32Ty());
            }
        }
    }

    if (const auto *x = dynamic_cast<const CallE *>(e)) {
        const auto *nameUse = dynamic_cast<const VarRef *>(x->callee.get());
        if (!nameUse)
            throw std::runtime_error("ch17: 间接调用留待第 53 章");
        const Symbol *s = bindings->uses.at(nameUse);
        if (s->kind != Symbol::Fun)
            throw std::runtime_error("ch17: 间接调用留待第 53 章");
        auto *callee = mod->getFunction(emitName(s->name));
        std::vector<Value *> args;
        for (const auto &a : x->args) args.push_back(expr(a.get()));
        return b->CreateCall(callee, args);
    }

    throw std::runtime_error("ch17: 指针与记录构造留待第 53 章");
}

void IRGen::stmt(const Stmt *s) {
    if (const auto *x = dynamic_cast<const AssignS *>(s)) {
        const auto *target = dynamic_cast<const VarRef *>(x->target.get());
        if (!target)
            throw std::runtime_error("ch17: 经指针/字段写入留待第 53 章");
        const Symbol *sym = bindings->uses.at(target);
        b->CreateStore(expr(x->value.get()), locals.at(sym));
        return;
    }

    if (const auto *x = dynamic_cast<const OutputS *>(s)) {
        b->CreateCall(rtOutput_, {expr(x->e.get())});
        return;
    }

    if (const auto *x = dynamic_cast<const IfS *>(s)) {
        Function *fn = b->GetInsertBlock()->getParent();
        auto *thenBB = BasicBlock::Create(*ctx, "then", fn);
        auto *elseBB = BasicBlock::Create(*ctx, "else", fn);
        auto *mergeBB = BasicBlock::Create(*ctx, "merge", fn);

        Value *cc = b->CreateICmpNE(expr(x->cond.get()), b->getInt32(0));
        b->CreateCondBr(cc, thenBB, elseBB);

        b->SetInsertPoint(thenBB);
        stmt(x->then.get());
        if (!b->GetInsertBlock()->getTerminator()) b->CreateBr(mergeBB);

        b->SetInsertPoint(elseBB);
        if (x->els) {
            stmt(x->els.get());
            if (!b->GetInsertBlock()->getTerminator()) b->CreateBr(mergeBB);
        } else {
            b->CreateBr(mergeBB);
        }
        b->SetInsertPoint(mergeBB);
        return;
    }

    if (const auto *x = dynamic_cast<const WhileS *>(s)) {
        Function *fn = b->GetInsertBlock()->getParent();
        auto *header = BasicBlock::Create(*ctx, "wh.cond", fn);
        auto *bodyBB = BasicBlock::Create(*ctx, "wh.body", fn);
        auto *exitBB = BasicBlock::Create(*ctx, "wh.exit", fn);

        b->CreateBr(header);
        b->SetInsertPoint(header);
        Value *cc = b->CreateICmpNE(expr(x->cond.get()), b->getInt32(0));
        b->CreateCondBr(cc, bodyBB, exitBB);

        b->SetInsertPoint(bodyBB);
        stmt(x->body.get());
        if (!b->GetInsertBlock()->getTerminator()) b->CreateBr(header);

        b->SetInsertPoint(exitBB);
        return;
    }

    if (const auto *x = dynamic_cast<const BlockS *>(s)) {
        for (const auto &st : x->ss) stmt(st.get());
        return;
    }

    if (const auto *x = dynamic_cast<const ReturnS *>(s))
        b->CreateRet(expr(x->e.get()));
}

void IRGen::genWrapper(const FunDecl *mainFun) {
    // C 入口：按 TIP main 形参数目读 input，再调用 tip_main。
    // 不命名为 main——MinGW 目标会向 main 注入对 CRT 符号 __main 的调用。
    auto *fn = Function::Create(FunctionType::get(b->getInt32Ty(), false),
                                Function::ExternalLinkage, "tip_entry", *mod);
    auto *entry = BasicBlock::Create(*ctx, "entry", fn);
    b->SetInsertPoint(entry);

    std::vector<Value *> args;
    for (size_t j = 0; j < mainFun->params.size(); ++j)
        args.push_back(b->CreateCall(rtInput_));
    Value *r = b->CreateCall(mod->getFunction("tip_main"), args);
    b->CreateRet(r);
}

bool IRGen::verify() const {
    std::string err;
    llvm::raw_string_ostream os(err);
    bool bad = llvm::verifyModule(*mod, &os);
    os.str();
    return !bad;
}

std::string IRGen::dump() const {
    std::string out;
    llvm::raw_string_ostream os(out);
    mod->print(os, nullptr);
    return os.str();
}
```

```cpp
namespace tip {
namespace {

// JIT 模块通过这两个宿主函数与外界交换数据。
const std::vector<int> *inQueue = nullptr;
std::vector<int> *outQueue = nullptr;
size_t inPos = 0;

extern "C" int32_t tip_input() {
    if (inPos >= inQueue->size()) return 0;
    return (*inQueue)[inPos++];
}

extern "C" void tip_output(int32_t value) {
    outQueue->push_back(value);
}

void initNative() {
    // 进程内只初始化一次。
    static const bool ready = [] {
        llvm::InitializeNativeTarget();
        llvm::InitializeNativeTargetAsmPrinter();
        return true;
    }();
    (void)ready;
}

[[noreturn]] void fail(llvm::Error e) {
    std::string text = llvm::toString(std::move(e));
    throw std::runtime_error(text);
}

}  // namespace

std::vector<int> runJit(IRGen gen, const std::vector<int> &inputs) {
    initNative();
    std::vector<int> outputs;
    inQueue = &inputs;
    outQueue = &outputs;
    inPos = 0;

    auto jitOrErr = LLJITBuilder().create();
    if (!jitOrErr) fail(jitOrErr.takeError());
    auto jit = std::move(*jitOrErr);

    auto defineHost = [&](StringRef name, void *addr) {
        SymbolMap symbols;
        symbols[jit->mangleAndIntern(name)] = ExecutorSymbolDef(
            llvm::orc::ExecutorAddr::fromPtr(addr), JITSymbolFlags());
        if (llvm::Error e =
                jit->getMainJITDylib().define(absoluteSymbols(symbols)))
            fail(std::move(e));
    };
    defineHost("tip_input", reinterpret_cast<void *>(&tip_input));
    defineHost("tip_output", reinterpret_cast<void *>(&tip_output));

    ThreadSafeModule tsm(std::move(gen.mod), std::move(gen.ctx));
    if (llvm::Error e = jit->addIRModule(std::move(tsm)))
        fail(std::move(e));

    auto mainAddr = jit->lookup("tip_entry");
    if (!mainAddr) fail(mainAddr.takeError());
    auto *entry = jitTargetAddressToFunction<int (*)()>(mainAddr->getValue());
    entry();

    return outputs;
}
```

```cpp
// 第 17 章配套程序：解析 -> AST -> 名字解析 -> LLVM IR。
//   --check / --emit-ir FILE : 打印未优化的模块
//   --run FILE INPUTS        : 对 INPUTS 每行输入真实执行一次，打印输出序列
#include <fstream>
#include <iostream>
#include <memory>
#include <sstream>
#include <string>
#include <vector>

#include "TIPLexer.h"
#include "TIPParser.h"

#include "ast_build.hpp"
#include "irgen.hpp"
#include "jitrun.hpp"

class CollectErrorListener : public antlr4::BaseErrorListener {
public:
    std::vector<std::string> messages;

    void syntaxError(antlr4::Recognizer *, antlr4::Token *, size_t line,
                     size_t column, const std::string &msg,
                     std::exception_ptr) override {
        messages.push_back("syntax error line " + std::to_string(line) + ":" +
                           std::to_string(column) + " " + msg);
    }
};

namespace {

struct Parsed {
    std::unique_ptr<tip::ProgramA> ast;
    tip::Bindings bindings;
};

Parsed parseFile(const std::string &path) {
    std::ifstream src(path);
    if (!src) {
        std::cerr << "cannot open " << path << '\n';
        std::exit(1);
    }
    antlr4::ANTLRInputStream input(src);
    TIPLexer lexer(&input);
    antlr4::CommonTokenStream tokens(&lexer);
    TIPParser parser(&tokens);

    CollectErrorListener errors;
    lexer.removeErrorListeners();
    parser.removeErrorListeners();
    lexer.addErrorListener(&errors);
    parser.addErrorListener(&errors);

    TIPParser::ProgramContext *tree = parser.program();
    if (!errors.messages.empty()) {
        for (const std::string &m : errors.messages) std::cout << m << '\n';
        std::exit(2);
    }

    Parsed result;
    result.ast = tip::buildAst(tree);
    result.bindings = tip::resolveNames(*result.ast);
    if (!result.bindings.errors.empty()) {
        for (const tip::Diag &d : result.bindings.errors)
            std::cout << d.text << '\n';
        std::exit(3);
    }
    return result;
}

std::vector<int> parseRun(const std::string &line) {
    std::vector<int> values;
    std::istringstream ss(line);
    int v;
    while (ss >> v) values.push_back(v);
    return values;
}

}  // namespace

int main(int argc, char **argv) {
    if (argc >= 3 && (std::string(argv[1]) == "--check" ||
                      std::string(argv[1]) == "--emit-ir")) {
        Parsed p = parseFile(argv[2]);
        tip::IRGen gen;
        gen.gen(*p.ast, p.bindings);
        if (!gen.verify()) {
            std::cerr << "generated module failed verification\n";
            return 1;
        }
        std::cout << gen.dump();
        return 0;
    }

    if (argc == 4 && std::string(argv[1]) == "--run") {
        std::ifstream in(argv[3]);
        if (!in) {
            std::cerr << "cannot open " << argv[3] << '\n';
            return 1;
        }
        int run = 0;
        std::string line;
        while (std::getline(in, line)) {
            std::string trimmed = line;
            size_t a = trimmed.find_first_not_of(" \t\r\n");
            if (a == std::string::npos) continue;
            if (trimmed[a] == '#') continue;

            std::vector<int> inputs = parseRun(trimmed);
            // 每次执行重新生成：JIT 会消费模块。
            Parsed p = parseFile(argv[2]);
            tip::IRGen gen;
            gen.gen(*p.ast, p.bindings);
            if (!gen.verify()) {
                std::cerr << "generated module failed verification\n";
                return 1;
            }
            std::vector<int> outputs = tip::runJit(std::move(gen), inputs);

            std::cout << "run " << ++run << ":";
            for (size_t i = 0; i < outputs.size(); ++i)
                std::cout << (i ? ", " : " ") << outputs[i];
            std::cout << '\n';
        }
        return 0;
    }

    std::cerr << "usage: tipa {--check|--emit-ir} FILE | tipa --run FILE INPUTS\n";
    return 1;
}
```

```cpp
// file: src/pretty.cpp
#include "pretty.hpp"

#include <string>

namespace tip {

namespace {

// 表达式打印为前缀式：运算符与符号的对照表。
std::string exprText(const Expr *e) {
    if (const auto *x = dynamic_cast<const IntLit *>(e)) return std::to_string(x->v);
    if (const auto *x = dynamic_cast<const VarRef *>(e)) return x->name;
    if (dynamic_cast<const InputE *>(e)) return "input";
    if (dynamic_cast<const NullE *>(e)) return "null";

    if (const auto *x = dynamic_cast<const Binop *>(e)) {
        const char *sym = "+";
        switch (x->op) {
            case BOp::Add: sym = "+"; break;
            case BOp::Sub: sym = "-"; break;
            case BOp::Mul: sym = "*"; break;
            case BOp::Div: sym = "/"; break;
            case BOp::Gt: sym = ">"; break;
            case BOp::Eq: sym = "=="; break;
        }
        return "(" + std::string(sym) + " " + exprText(x->l.get()) + " " +
               exprText(x->r.get()) + ")";
    }
    if (const auto *x = dynamic_cast<const CallE *>(e)) {
        std::string s = "(call " + exprText(x->callee.get());
        for (const auto &a : x->args) s += " " + exprText(a.get());
        return s + ")";
    }
    if (const auto *x = dynamic_cast<const Deref *>(e))
        return "(* " + exprText(x->e.get()) + ")";
    if (const auto *x = dynamic_cast<const AddrOf *>(e)) return "(& " + x->name + ")";
    if (const auto *x = dynamic_cast<const AllocE *>(e))
        return "(alloc " + exprText(x->e.get()) + ")";
    if (const auto *x = dynamic_cast<const FieldA *>(e))
        return "(. " + exprText(x->e.get()) + " " + x->field + ")";
    if (const auto *x = dynamic_cast<const RecLit *>(e)) {
        std::string s = "{";
        for (size_t i = 0; i < x->fields.size(); ++i) {
            if (i) s += ", ";
            s += x->fields[i].first + ": " + exprText(x->fields[i].second.get());
        }
        return s + "}";
    }
    return "<unknown expr>";
}

std::string indent(int level) { return std::string(static_cast<size_t>(level) * 2, ' '); }

// 语句打印带缩进，一条语句一行（块内多行）。
void stmtText(const Stmt *s, int level, std::string &out) {
    if (const auto *x = dynamic_cast<const AssignS *>(s)) {
        out += indent(level) + exprText(x->target.get()) + " = " +
               exprText(x->value.get()) + " ;\n";
        return;
    }
    if (const auto *x = dynamic_cast<const OutputS *>(s)) {
        out += indent(level) + "output " + exprText(x->e.get()) + " ;\n";
        return;
    }
    if (const auto *x = dynamic_cast<const ReturnS *>(s)) {
        out += indent(level) + "return " + exprText(x->e.get()) + " ;\n";
        return;
    }
    if (const auto *x = dynamic_cast<const IfS *>(s)) {
        out += indent(level) + "if (" + exprText(x->cond.get()) + ")\n";
        stmtText(x->then.get(), level + 1, out);
        if (x->els) {
            out += indent(level) + "else\n";
            stmtText(x->els.get(), level + 1, out);
        }
        return;
    }
    if (const auto *x = dynamic_cast<const WhileS *>(s)) {
        out += indent(level) + "while (" + exprText(x->cond.get()) + ")\n";
        stmtText(x->body.get(), level + 1, out);
        return;
    }
    if (const auto *x = dynamic_cast<const BlockS *>(s)) {
        out += indent(level) + "{\n";
        for (const auto &st : x->ss) stmtText(st.get(), level + 1, out);
        out += indent(level) + "}\n";
        return;
    }
    out += indent(level) + "<unknown stmt>\n";
}

}  // namespace

std::string printProgram(const ProgramA &program) {
    std::string out;
    for (const auto &f : program.funs) {
        std::string paramList;
        for (size_t i = 0; i < f->params.size(); ++i) {
            if (i) paramList += ",";
            paramList += f->params[i];
        }
        out += f->name + "(" + paramList + ") {\n";
        if (!f->vars.empty()) {
            out += indent(1) + "var ";
            for (size_t i = 0; i < f->vars.size(); ++i) {
                if (i) out += ",";
                out += f->vars[i];
            }
            out += " ;\n";
        }
        // 函数体是 BlockS；打印其内部语句而不是再嵌一层花括号。
        const auto *body = dynamic_cast<const BlockS *>(f->body.get());
        for (const auto &st : body->ss) stmtText(st.get(), 1, out);
        stmtText(f->ret.get(), 1, out);
        out += "}\n";
    }
    return out;
}

}  // namespace tip
```

```cpp
// 解析器在遍历 AST 的同时完成绑定与诊断收集。
struct Resolver {
    Bindings bindings;
    Scope *current = nullptr;
    const FunDecl *owner = nullptr;

    void declare(const std::string &name, Symbol::Kind kind) {
        if (current->table.count(name)) {
            bindings.errors.push_back({"error: redeclared '" + name + "'"});
            return;  // 保留先声明者，后声明被忽略
        }
        current->table.emplace(name, Symbol{kind, name, owner});
    }

    void resolveExpr(const Expr *e) {
        if (const auto *x = dynamic_cast<const VarRef *>(e)) {
            const Symbol *s = current->lookup(x->name);
            if (!s) {
                bindings.errors.push_back({"error: undeclared '" + x->name + "'"});
            } else {
                bindings.uses[x] = s;
            }
            return;
        }
        if (const auto *x = dynamic_cast<const Binop *>(e)) {
            resolveExpr(x->l.get());
            resolveExpr(x->r.get());
            return;
        }
        if (const auto *x = dynamic_cast<const CallE *>(e)) {
            resolveExpr(x->callee.get());
            for (const auto &a : x->args) resolveExpr(a.get());
            return;
        }
        if (const auto *x = dynamic_cast<const Deref *>(e)) return resolveExpr(x->e.get());
        if (const auto *x = dynamic_cast<const AllocE *>(e)) return resolveExpr(x->e.get());
        if (const auto *x = dynamic_cast<const FieldA *>(e)) {
            resolveExpr(x->e.get());  // 字段名不是变量，无需解析
            return;
        }
        if (const auto *x = dynamic_cast<const RecLit *>(e)) {
            for (const auto &f : x->fields) resolveExpr(f.second.get());
            return;
        }
        // IntLit / InputE / AddrOf / NullE：无变量使用。
    }

    void resolveStmt(const Stmt *s) {
        if (const auto *x = dynamic_cast<const AssignS *>(s)) {
            resolveExpr(x->target.get());
            resolveExpr(x->value.get());
            return;
        }
        if (const auto *x = dynamic_cast<const OutputS *>(s)) return resolveExpr(x->e.get());
        if (const auto *x = dynamic_cast<const IfS *>(s)) {
            resolveExpr(x->cond.get());
            resolveStmt(x->then.get());
            if (x->els) resolveStmt(x->els.get());
            return;
        }
        if (const auto *x = dynamic_cast<const WhileS *>(s)) {
            resolveExpr(x->cond.get());
            resolveStmt(x->body.get());
            return;
        }
        if (const auto *x = dynamic_cast<const BlockS *>(s)) {
            for (const auto &st : x->ss) resolveStmt(st.get());
            return;
        }
        if (const auto *x = dynamic_cast<const ReturnS *>(s)) return resolveExpr(x->e.get());
    }
};

}  // namespace

const Symbol *Scope::lookup(const std::string &name) const {
    auto it = table.find(name);
    if (it != table.end()) return &it->second;
    return parent ? parent->lookup(name) : nullptr;
}

Bindings resolveNames(ProgramA &program) {
    Resolver resolver;
    resolver.bindings.global = Scope(nullptr);
    Scope *global = &resolver.bindings.global;

    // 第一遍：所有函数名进入全局作用域。
    for (const auto &f : program.funs) {
        if (global->table.count(f->name)) {
            resolver.bindings.errors.push_back({"error: redeclared '" + f->name + "'"});
            continue;
        }
        global->table.emplace(f->name, Symbol{Symbol::Fun, f->name, f.get()});
    }

    // 第二遍：每个函数开自己的作用域，父作用域是全局表；
    // 作用域所有权交给 Bindings，遍历结束后符号依然存活。
    for (const auto &f : program.funs) {
        auto functionScope = std::make_unique<Scope>(global);
        resolver.current = functionScope.get();
        resolver.owner = f.get();

        for (const std::string &p : f->params) resolver.declare(p, Symbol::Param);
        for (const std::string &v : f->vars) resolver.declare(v, Symbol::Local);

        resolver.resolveStmt(f->body.get());
        resolver.resolveStmt(f->ret.get());

        resolver.current = nullptr;
        resolver.bindings.scopes.push_back(std::move(functionScope));
    }
    return std::move(resolver.bindings);
}

}  // namespace tip
```

## 17.16 工程注意点

- **生成的模块立即校验、失败即中止**：verifyModule 在 --check/--run
  两条路径上都先于结果输出执行，结构错误不会流入执行阶段。
- **每次运行重新生成模块**：JIT 消费所有权，重新生成保证多次执行互不
  共享状态、代码无须实现模块复制。
- **I/O 只用定宽类型与 extern "C"**：宿主函数签名取 int32_t，符号名经
  mangleAndIntern 取得，避免宽度与修饰两类平台假设。
- **输入文件只承载数据、诊断只依赖源码**：.inputs 不进输出，错误文本
  不含路径，所有产物跨机器逐字节一致。
- **暂不支持的构造显式抛错**：指针、记录、间接调用在生成期被明确拒绝，
  不会静默产出语义错误的代码。

## 17.17 小结：执行台落成，第三篇开始

本章把 TIP 前端接到了 LLVM 上：AST 经 IRGen 翻译成结构良构的 LLVM 模块，
变量以 alloca 槽位承载、表达式以 SSA 值生成、if/while 以基本块与分支
编织，TIP 的 input/output 由 ORC 注入的宿主函数实现，tip_entry 负责
按 main 形参搬运输入；模块经 verifyModule 校验、经 LLJIT 本机执行。
翻译的保语义正确性以"配置语义 + 结构归纳"论证，两个示例程序的运行
结果与人工计算一致。

至此第二篇——分析的前置工作——全部完成。回顾这五章：第 4 章把字符
变成 parse tree，第 12 章把 parse tree 变成 AST，第 14 章把名字使用点
绑定到声明，第 16 章把树形语句展开成控制流图，本章把一切落实为可执行
的本机代码。五层表示各管一段、逐层收窄，每一层的产物都是下一层的输入，
且一经冻结不再修改。读者至此应当对"一个静态分析器操作的对象到底从何
而来"有了完整的、可动手复现的认识。

本章具体交付了什么，在此清点，便于读者自查：一个覆盖整数核心的
IRGen——字面量、变量、input、四种算术、两种比较、直接调用、五类
语句、多函数与入口包装；一个结构校验关口（每个生成模块必先通过
verifyModule）；一个 ORC 执行台（宿主函数注入、模块所有权交接、
入口查找与调用）；以及一套固定的命令行协议（--check/--emit-ir/
--run 与四级退出码）。两个示例程序的 IR 文本与五组具体执行结果
全部作为期望产物存档。建议读者合上本章后亲手做一次修改实验：把
ite.tip 的循环条件改成 `n > 1`，先手工推演输入 5 的新结果，再用
tipa --run 验证——改动一处源程序、不动一行 C++，就能观察整条
前端—生成—执行链条的响应，这是检验自己是否真正理解执行台的
最好方式。

下一章起进入第三篇：**类型分析**。问题从"程序是什么"转为"程序里的值
如何流动、各占什么形状"。我们将看到一种与前面完全不同的分析组织方式：
不为每个位置直接计算答案，而是让每个程序点持有一个**类型变量**，按程序
结构生成**约束**，最后通过**合一**求解。类型分析是 spa.pdf 理论体系的
第一个完整实例，也是后续格与数据流框架的先声。执行台在此暂退幕后，
直到第 32 章——届时它将以"可靠性检验者"的身份重新登场，把抽象预测
与本章建立的具体执行逐一对照。

最后用一句话收束本章，也是第二篇的终点：**我们先让程序"可执行"，
才有资格讨论对程序的"可断言"**。从下一章开始，断言登场。
