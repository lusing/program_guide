# 第 29 章　格的通用构造：从五个符号到任意抽象域

## 29.1 本章要解决的问题

第 28 章为一个具体的抽象域——五元符号格——手工写了序、join 与
抽象算术。一切从头写起的做法在示范原理时很好用，但无法扩展：
第 32 章要常量格，第 33 章要四个幂集格，第 37 章要区间格，第 54 章要指针集合格。如果每个域都像第 28 章那样从零开始，读者会淹没
在重复的样板里，更糟的是，"这些域之间的关系"这一层结构会完全
消失。而这一层结构恰恰是格理论送给静态分析的礼物：程序状态是
"变量集合到值格的映射"，映射格由值格**构造**出来；多变量状态
是若干单变量格的**积**；"此点尚未执行到"的初始信息由**提升**
补上；"哪些定值到达此处"由**幂集**承载。四种构造合起来，几乎
所有数据流分析的域都能从一两个基础域组装出来。

**构造的意义不只是省代码。** 一个手工写的映射格（第 28 章的
`SignEnv`）与一个用通用构造组装出的映射格，在数学上是同一个
对象，但后者的正确性论证可以继承：只要值格是格，映射格就
自动是格，单调性也自动成立。这种"性质随构造传播"的推理方式，
是从第 31 章起一切不动点论证的骨架——我们不再逐域验证格公理，
而是验证四个构造定理，然后放心地组装。

本章的形式化目标是：给出格的统一接口 `Lattice<A>`，证明四类
构造（提升、积、映射、幂集）都把格变成格，并在符号域上用固定
例子演示每个构造的行为。工程目标是：把第 28 章的五元格适配成
统一接口的形态，让通用构造可以直接消费它。

### 29.1.1 为什么"手写每个格"不可扩展

先体会一下不搞构造时的重复度。第 28 章的抽象环境是
`map<string,int>`，join 要逐变量取符号 join——十几行。第 32 章
的常量环境同样是 `map<string,Const>`，join 逐变量取常量 join——
结构一模一样，只是值域换了。第 33 章的到达定值是
`map<point, set<string>>`，还是逐键取并——又是同一个形状。
三份代码，三种 bug 的机会，三次正确性论证。

更关键的是**论证的重复**。第 28 章证明过"环境 join 逐变量取
符号 join 是单调的"，这个证明对常量环境、对集合环境逐字重复，
只有"符号 join 单调"这一处依赖具体域。构造的意义就是把证明
也模板化：证明一次"若 V 是格则 map 上的逐点格是格"，此后任何
值域拿来即用。数学上这叫把格封闭在某些运算下——格对提升、积、
映射、幂集封闭，正如整数对加法封闭。

还有第三重收益：**构造是可组合的。** "映射到积格"、"映射的
提升"、"幂集的积"，这些组合不需要新代码也不需要新证明——
构造定理可以嵌套应用。第 50 章的上下文敏感分析会把状态格再
与"调用串格"做积；没有本章的构造，那一章要一切重写。

### 29.1.3 与 spa 原书的对应

spa 第 4 章用一段话带过"格可以由简单格构造复合格"，给出了

真实的分析域，每条构造都值得看清边界条件。spa 的习题风格

### 29.1.4 本章不做的事

本章不引入任何新的程序语义或分析算法——没有方程、没有不动点、
没有传递函数的新内容；本章不改 TIP 文法与前端；不做泛型库的
完整工程化（错误处理、分配器定制、概念约束检查都不做，接口

concepts/虚函数接口"这类语言层比较只在 14.2 做一次定性讨论，

例子，不写自动化公理检查器——那是习题 14.3 的内容。

### 29.1.5 本章在全书验证体系中的位置

回顾全书已建立的验证体系，本章补上的是其中最关键的一块
承重板。第 3—7 章的验证（词法、语法、名字解析、CFG）
性质是"结构正确性"——程序长得对不对；第 9—12 章的
验证（类型）性质是"声明一致性"——用得对不对；从本章
开始的验证性质是**运行时行为界**——程序跑起来会发生
什么。三类性质分别由三种机制保证：结构性质由构造器
拒绝（解析失败），声明性质由推理规则拒绝（unify 失败），
行为性质由**格上的保守近似**给出（soundness 而非
decidability）。这解释了为什么第四篇的输出不再是非黑即
白的 pass/fail，而是一张"每个程序点的状态表"——行为的
近似不可能二值化，只能给出精确度可调的报告。

本章的构造器正是"行为界"体系的**类型系统**：第 28 章
手写的五元格相当于一个手搓类型，本章给出造类型的语法
（lift/product/maps/powerset），第 30 章给出约束方程，
第 31 章给出求解算法，第 33 章给出判定书写范式。读者
可以用"类型系统四件套"的框架去预期第四篇剩余章节的
节奏——框架稳定，域在换。

## 29.2 统一接口：Lattice&lt;A&gt; 的设计

### 29.2.1 数学对象先于代码

一个（有界）格是集合 A 连同其上的偏序 ⊑，满足两条结构要求：
任意两个元素有最小上界（join，记 ⊔）与最大下界（meet，记 ⊓），
并且存在全序两端的顶 ⊤ 与底 ⊥。数据流分析用到的格总是有界的，
顶对应"什么信息都可能"，底对应"还没有任何信息"。

对接口设计真正要紧的观察是：**join 与偏序互相决定。** 在格中，
a ⊑ b 当且仅当 a ⊔ b = b。这意味着接口里 leq 与 join 二者取其
一即可推出另一个，但同时提供两个有实际好处：算法（第 31 章的
worklist 判断"是否变化"、第 30 章的方程打印）两样都用；而且
显式的 leq 实现往往比"join 后比较相等"便宜得多——幂集格的
leq 是一次子集扫描，join 却要构造新集。

相等判定 eq 是第三个基本操作。数学上 eq(a,b) ⟺ a ⊑ b ∧ b ⊑ a，
但对大多数表示，直接相等比较远比两次 leq 便宜。接口于是定下
四件套：eq、leq、join，加上两个边界值 top 与 bot。

### 29.2.2 形式化接口

把上述讨论写成 C++：A 是抽象值的表示类型，格是五个成员的打包。

```cpp
template <class A> struct Lattice;
```

接口的完整定义在 29.12 节的 lattice.hpp 里，此处先给形状：
`topV`、`botV` 两个值字段加 `eqF`、`leqF`、`joinF` 三个
`std::function` 字段，成员函数 top()、bot()、eq()、leq()、
join() 转发到字段。三个函数字段恰好对应"格的三要素"，两个值
字段对应边界。这个形状是全章一切构造的交换媒介：lift 吃一个
`Lattice<A>` 吐一个 `Lattice<optional<A>>`，product 吃若干个吐
一个积格——构造函数的参数与返回值都是这个统一形状，嵌套组合
因此畅通无阻。

### 29.2.3 top 与 bot 为什么是值而不是函数

初见接口的读者可能疑惑：为什么 top/bot 是存储的值（`A topV`），
而 join 是函数？因为顶与底是格的**元素**，join 是格的**运算**。
元素是数据，运算是行为，接口如实地反映了这个本体论差别。

把 top/bot 做成函数（`A top() const`）看似更"懒"——大对象
可以按需构造。但对本章所有的格，顶与底都是小对象：符号域的
顶是整数 2，映射格的顶是"每个键都是值顶"的映射（构造时一次性
建好），幂集格的顶是全集（构造参数给出）。预构造的代价是构造
时一次拷贝，收益是每次取顶零开销、且顶元素在格的生命期内
稳定可共享。第 31 章的 worklist 每轮迭代都要取底值做初始比较，
值形态避免了反复构造。若某个未来域的顶真的巨大（比如全集
百万元素的幂集格），再换成惰性形态不迟——接口的使用方只
调 top()，形态变化不外泄。

### 29.2.4 std::function 字段 vs 虚函数 vs 概念约束

三种可选设计值得摆在一起比较，因为这是"抽象接口怎么选"的
一次示范。**方案甲（本书）**：`std::function` 字段。优点：
格是值——可以放进容器、按值传递、在运行时从配置组装（第 33 章的 DfaSpec 用同样的手法把四个分析参数化为数据）；构造函数
体就是全部注册逻辑，读者一屏看完。缺点：std::function 有
间接调用开销与闭包拷贝开销；类型不校验格公理。

**方案乙**：抽象基类 + 虚函数。每个域继承 `LatticeBase<A>`，
多态分发。缺点立现：lift/product 需要返回"构造出来的新格"，
虚函数方案下这些构造物得是堆上的动态对象，所有权管理立刻
复杂化（shared_ptr 泛滥）；且第 28 章以来的代码全部是值语义，
引入继承层级是风格断裂。

**方案丙**：C++20 概念约束的模板函数（requires 表达式要求
A 上有自由函数 join 等）。零开销、编译期校验，但构造不再是
"值"：你不能把"一个格"作为运行时数据传来传去，DfaSpec 那种
"分析规格即数据"的参数化做不成。而且本书构建脚本钉在 C++17。

本书选甲，并在 14.13 工程注意点里说明：若读者把这套代码用于
生产分析器，方案丙是升级方向，接口形状（五个操作）不必变——
这正是"接口与实现分离"的回报。

### 29.2.5 eq 的隐藏要求：表示相等与语义相等

`eqF` 默认按表示相等实现（各构造里都是 `a == b`），但值得
点破一个理论细节：格公理要求的是**语义相等**——两个元素
相等当且仅当互为下界。若某个域的表示不唯一（同一个抽象值有
两种写法），表示相等就过粗。本章四个构造的值域表示都唯一：
optional 的三种状态、tuple 逐分量、map 键集固定、set 无重复。
第 37 章的区间格会遇到表示问题（[2,+∞] 与 [2,INT_MAX] 是
同一个抽象值），那里的处理是**规范化**表示而非重写 eq——
第 28 章的 normalize（类型篇）与它遥相呼应：能规范化就不做
语义比较。这个原则到区间章会再讲一遍。

### 29.2.6 运算的消费协议：谁在什么时候调什么

接口的五个成员并不是同等活跃的。把后续章节的调用清单提前
列出来，有助于读者在实现每个域时分配注意力。**join** 是
最高频消费者：控制流每到一个汇合点（分支后合并、循环头）
都要合并状态（第 30 章方程、第 31 章 worklist、第 33 章
DFA 驱动全靠它）。**leq** 次之：worklist 的"是否变化"判断
（新旧状态 ⊑ 比较相等更快时用 eq，单调框架的一般表述用
leq）、must 分析的初始化判断都用它。**bot** 在初始化时
被批量消费：第 31 章把每个程序点初始化为全 ⊥，一次循环
N 个点调 N 次。**top** 的消费集中在 must 分析的初始化
（第 33 章：非入口点初始化为全集）与提升构造的顶传递。
**eq** 是最低频的：主要在 worklist 的变化检测与公理
自检里出场。

消费清单对实现者的指导意义在于**性能预算的分配**：join
要快（可能被调用数万次），bot/top 要便宜（构造时一次
预建），eq/leq 可以稍慢但绝不能错。反过来，清单也是
接口审查的依据——若某个域发现 top 没有买主（比如纯
may 分析的幂集格从不取全集），那不是接口冗余，而是
must 分析还没到来；接口为整个第四篇服务，不为某一章
裁剪。

还有一位隐形消费者：**调试打印**。格元素的可读形式
（signShow、mapShow）不进接口，却是每个域的必备配套
——第 31 章 --check 的每行输出都是"程序点 + 状态文本"。
配套打印函数的纪律与第 26 章相同：确定性、确定性、
还是确定性。

### 29.2.7 有界性与完备性：两个被省略的条件

严格的格定义（无限格语境）还要求任意子集（不只二元）有
上确界与下确界，即**完备格**（complete lattice）。本章
接口只保证二元 join 与有限格的有界性，为什么不追求完备？
两个原因。其一，**有限格自动完备**：有限偏序集若有全部
二元上确界，则任意子集的上确界就是对全体元素反复 join——
归纳可证。本章四个构造在有限输入下都产出有限格，完备性
免费获得。其二，**无限格的完备性在数据流语境里通常靠
构造保证而非验证**：区间格（第 37 章）用 ±∞ 补上边界、
链上补 supremum 后成为完备格，届时会显式检查。接口不
包含"任意子集 sup"不是偷懒，而是它无法用成员函数表示
（参数是一个集合而非两个元素），且有限语境下根本用不上。

Tarski 不动点定理（第 31 章的引理）陈述为：完备格上的
单调函数有不动点，且全体不动点构成完备格。到时读者会
看到：定理的前半句用完备性，算法的后半句（从底出发迭代）
用有限性——两个条件各司其职，本章接口为算法侧负责，
定理侧在第 31 章按需补齐。

### 29.2.8 std::function 的类型擦除：接口的代价从哪来

接口的六个 std::function 成员不是"更慢的虚函数"，值得
花一节讲清它们到底是什么，因为读者在后面的章节会反复
依赖它们的行为边界。std::function<R(Args…)> 是一个**类型
擦除容器**：任何可调用体（函数指针、lambda、带捕获的
闭包、仿函数）只要签名匹配，都能装进去；装入后只知道
"给它这些参数能返回 R"，原本的具体类型被抹掉了。本章
Lattice<A> 用它，等价于声明"我需要的只是一个满足这个
签名的运算，至于它是怎么算的，构造者自己决定"——类型
擦除把**接口与实现的分离**从编译期的模板约定降为运行
期的签名约定。

这个机制的三条边界必须记住。**其一，可拷贝是硬要求**：
装进去的可调用体必须能拷贝（不能捕获只移动的对象，比如
unique_ptr），因为 Lattice<A> 按值传递时会连闭包一起拷
（14.2.9）。**其二，调用有间接成本**：每次 join 一次
（可能的）堆访问加一次间接跳转，比直接函数调用慢几倍；
教学规模无感，工业规模是 14.2.4 方案丙的用武之地。
**其三，空态是运行期炸弹**：默认构造的 std::function 为
空，调用它抛 std::bad_function_call——本章用六参构造函数
一次性装齐全部成员，不给空态留出生机会，这是"让非法
状态不可表示"的老原则在接口设计上的又一次落地。

### 29.2.9 值语义的账：闭包拷贝与捕获清单

Lattice<A> 按值传递、按值返回、按值存进容器，每次拷贝
都会拷贝全部六个闭包。闭包拷贝的成本取决于**捕获清单**：
捕获一个 int、一个指针，是几十字节；捕获一个大容器，
拷贝就是 O(容器大小)。这给"写格运算的 lambda"立了一条
纪律：**捕获越小越好，能引用捕获外的大对象就不要值捕获**。
本章代码里 signLatticeDomain() 的闭包捕获的只有整型常量
与小函数，拷贝一个 Lattice<int> 是常数成本；powerset 的
闭包捕获全集字符串集合——这是一章里最大的一份捕获，拷贝
powerset 格的代价 O(|U|·平均串长)。值得吗？值得：全集
在构造期注入一次、拷贝发生在"把格传给求解器"的少数几
次调用里，而不是在热循环（join 每次迭代几百次）里——
**成本位置与频率错开**，是值语义设计里最常见的判断。
若读者将来发现闭包拷贝真的成为热点，标准的补救是把
Lattice<A> 的传递改成 const 引用（接口不变，调用约定
收紧），而不是改成 shared_ptr 共享——共享引入别名问题，
会让 14.2.8 刚立起来的"纯函数"纪律变得难以核查。

### 29.2.10 最小的格：两点链、三元素 V 形与布尔立方体

在动手组装大格之前，先看清楚格能小成什么样，后面一切复杂形状
都是这几个原型的组合。最小的有界格只有两个元素 {⊥, ⊤}，底与顶
直接相邻，高度为 1。它有好几个等价的现身方式：单元素全集幂集格
P({x}) = {∅, {x}}；布尔值域 {false, true} 配上逻辑运算；程序
分析里"某点可不可达"这一位信息。两点链上 join 就是逻辑或、
meet 就是逻辑与、leq 就是蕴含——数据流分析中 may/must 的直觉
全部可以先在这个最小格上建立，再搬到更大的格。

比两点链多一层的是三元素 V 形格：底 ⊥ 之上有两个互不可比的元素
a、b，它们的 join 是顶 ⊤，形状像字母 V。把符号格去掉 0 元素
（只保留 ⊥、−、+、⊤）得到的就是一个 V 形格：− 与 + 互不可比，
最小上界只能是 ⊤。V 形格是理解"信息为什么会在 join 时丢失"的
最小样本——在全序（链）上，两个元素总有一个小于另一个，join
直接取较大者，答案中总能保留其中一方的全部信息；而在 V 形的
分叉处，两条路径带来的承诺互不相容，分析只能上升到同时承认
二者的 ⊤，双方的具体信息都保不住。第 33 章四大 DFA 里所有
"合并后变保守"的瞬间，几何上都是在经过某个 V 的分叉。

反过来，元素两两可比的格叫**链**（chain）。平格 {⊥, c, ⊤}
（第 32 章常量格的形状）是一条三元素链：⊥ < c < ⊤。链上没有
分叉，join(a,b) 永远等于二者中较大的那个——这给常量传播带来
一个直接后果：join 不会"无中生有"，只会在"具体值"与"未知"
之间滑动，不会把两个不同的具体值折中成第三个具体值。这个性质
在后面第 35 章还要用来对照状态依赖传递函数：平格虽简单，状态
依赖一样可以发生，格的简单与传递函数的简单是两回事。

把 n 个两点链做积，得到的是 n 维布尔立方体 {0,1}ⁿ：2ⁿ 个元素、
高度 n，每个元素是一个 n 位向量，join 按位或、leq 按位蕴含。
这正是第 33 章 gen/kill 分析在工业实现里的真身——事实集合不
存成 std::set 而存成位向量，集合运算变成字宽级别的位运算。
14.6.5 节会回到这个表示；此处先记住几何对应：积构造把一维的链
拉成多维立方体，元素数随维数指数增长、高度只随维数线性增长。
"指数宽、线性高"这组数字解释了为什么不动点轮数可以不多
（高度线性），而每轮的表示却必须靠位向量或稀疏映射才能装下
（宽度指数）。第 31 章终止性证明用的是高度，复杂度分析用的
是宽度，两条线在这个最小立方体上就已经分开了。

## 29.3 提升构造：给域加一个新底

### 29.3.1 直觉与动机

许多分析需要表达"这个点还没执行到"或"这个变量还没被赋值"。
第 28 章的五元格自带 ⊥，可以直接用它表示"无信息"。但设想
一个只有 {−, 0, +, ⊤} 四个元素的域（没有底）：想把它用于
"初始全 ⊥"的 worklist（第 31 章），就得补一个最小元素。
**提升**（lift）构造就是干这个的：给它任何格 A，它返回
"A 加上一个新底"的格。新元素摆在所有人下面，原格的结构
原封不动。

用 C++ 的 `std::optional<A>` 表示提升域：`nullopt` 是新底，
`has_value()` 的元素就是原格元素。类型系统替我们保证了
"新底与旧元素可区分"——这比手工约定一个魔法值（比如用
−999 当底）可靠得多。

### 29.3.2 形式化定义

提升格 A⊥ 的载体是 A ∪ {⊥new}，序关系：

> x ⊑⊥ y 当且仅当 x = ⊥new，或 x、y ∈ A 且 x ⊑A y。

join 相应地：任何一方是新底，join 取另一方；双方都在 A 内，
join 就是 A 的 join。注意一个细蔓：原格的底 ⊥A 并没有被
移除，它现在是一个**普通元素**——比新底高、比其余低的
"次底"。两层底在语义上有分工：⊥new 表示"这个点没执行过"，
⊥A 表示"执行过但矛盾/不可行"。第 32 章的常量格会用到这个
区分：⊥new（未到）与 ⊥A（矛盾到达）是不同的信息。若读者
只想保留一层底，可以在提升后把原底折叠掉——那是一个变体
构造，本章不做。

### 29.3.3 代码导读

lift 的实现（29.12 节 lattice.hpp）是一个函数模板，吃
`const Lattice<A> &`，返回构造好的 `Lattice<std::optional<A>>`。
逐字段看：topV 是 `optional{l.top()}`——原顶包一层；botV 是
`optional{nullopt}`——新底。eqF 用 optional 的 `==`：optional
相等当且仅当"都空"或"都有且相等"，正是提升域的语义相等。

leqF 是四个分支的逻辑压缩：右元是空（新底）时，仅当左元也空
才成立（新底之下只有自己）；左空右非空恒成立（新底最小）；
双方都有值时委托原格的 leq。joinF 镜像：一方空取另一方，
双方有值委托原 join。两个 lambda 都按值捕获了原格 `l`——
原格是值语义的小对象（三个 std::function 加两个 int），按值
捕获让提升格自包含，不依赖外部生存期。

### 29.3.4 为什么提升格是格

验证格公理是构造定理的核心内容，以提升为例完整走一遍，其余
构造的验证在各自小节给出要点（完整展开会淹没在重复里）。

偏序公理：自反（x ⊑ x：若都有值用原格自反；若都空显然）；
反对称（x ⊑ y ⊑ x 蕴含相等：逐分支检查，唯一需要小心的是
"左空右非空"单向分支——它不能反向成立，因此不产生反对称
违反）；传递（三分支枚举：空参与任何组合都退化到原格传递性
或显然情形）。join 公理：幂等、交换、结合都能按"是否有值"
分支归约到原格的对应公理——**提升不改变 A 内部的代数结构，
只在边界加两种退化情形**，而两种退化情形（有 nullopt 参与）
逐条验证都平凡。这条"归约 + 边界平凡"的两段式论证是四个
构造共用的模板，值得记住。

join 与 leq 的相容性（a ⊑ b ⟺ a⊔b = b）同样按分支归约：
有值情形归约到原格的相容性，含空情形逐条验证。至此提升
构造定理成立：A 是有界格 ⟹ A⊥ 是有界格。单调性的继承
（若 f : A→A 单调则提升后的函数单调）留给习题 14.2。

### 29.3.5 与第 27 章 TyNull 的对照

类型篇的 TyNull 与提升的新底神似而不同，对照着看能加深对
两者的理解。相似处：都是"原域之外的一个特殊元素"，都表示
某种"缺失"。不同处有三。其一，TyNull 有自己的**相遇规则**
（null = ptr(T) 成功、null = int 失败），它在类型格里是
一个有独立行为的位置；提升的新底没有任何规则，只在 join/leq
里被动地被吸收。其二，TyNull 用 dynamic_cast 识别，是运行时
的类型标签；optional 用 has_value，是表示层的区分。其三，
null 参与的是**等式求解**（合一），新底参与的是**偏序运算**
（join/leq）——前者问"这两项能否同一"，后者问"这两点
谁覆盖谁"。域的扩展方式由它参与的运算决定，这是本章与
第 27 章合读时最有味道的一条经验。

### 29.3.6 平坦域：整体提升后的特例形状

有一个特例值得单独命名，因为它是后续章节的常客。取一个
**集合 S**（没有内部结构的"原子"集合，比如全体整数、
全体函数名），把每个元素提升成单元素格（x ⊑ x 仅此而已），
再整体提升加新底，得到域 S⊥ = {⊥} ∪ S——每个"真值"互
不可比，全部悬在底上。这个形状叫**平坦域**（flat domain）。

常量分析（第 32 章）的域就是平坦域的变体：{⊥矛盾} ∪ Z ∪
{⊤未知}——每个具体整数都是原子，5 与 7 不可比，join(5,7)=⊤
（"既是 5 又是 7，只能报未知"）。区间分析（第 37 章）则
相反：整数之间加了序（大小关系延伸成区间包含），域不平坦。
平坦与否决定了"两个值合并"的形状——平坦域一合并就糊化
（不同原子 join 必到顶），有序域合并还能保留部分信息
（[1,5]⊔[3,9]=[1,9]，比"未知"强得多）。这也是为什么
常量分析"稍有多路径就失效"而区间分析能兜住——第 32 章
的 SCCP 对照会把这一点讲成两栏并排，图形根子在今天的
平坦域概念。

平坦域还有一条工程性质：**eq 就是原子相等**，不需要任何
规范化讨论（14.2.5 的隐患在平坦域自动消失，原子只有一种
写法）。这也是常量格实现最简单的原因之一。

### 29.3.7 optional 之外的表示选择

std::optional 是提升域的现成载体，但不是唯一选择，比较
三种表示能看清表示与语义的距离。**optional<A>**：类型
安全、有 has_value 判别、与构造定理逐字对应——本书选择。
**哨兵值**：在 A 的表示里约定一个非法值当底（比如 int 域
用 INT_MIN）——省一层包装，但要求 A 有"确定没用到的
值"，且哨兵容易在别的代码路径被误当真值；类型系统不再
帮你把关。**独立判别结构**：`struct Lifted { bool present; A v; }`
——与 optional 等价，手写一遍而已，在 optional 语义
（比如拷贝行为、比较行为）不合适的场合使用。三条路里
optional 的比较行为（== 先比判别再比值）恰好等于提升域
的语义相等，这是"现成载体恰好语义对齐"的运气；若换
哨兵方案，leq/join/eq 三处都要手写判别，出错面扩大三倍。
表示选择的原则与第 27 章一致：**能让类型系统承担的判别
义务，就不要留给约定**。

### 29.3.8 bottom 的多重身份：不可达、矛盾、未定义

同一个 ⊥ 符号，在不同分析里承担不同的解释，初学者容易
把它们混成一个"坏值"。**符号分析（第 28 章）**里 ⊥ 是
不可达程序点的状态——控制流到不了的地方，信息集为空。
**常量分析（第 32 章）**里 ⊥ 叫"矛盾"（contradiction）——
一个点被推断成"x 恒等于 5"又被另一条路径推断成"x 恒等
于 7"，合并结果与"恒等于"的前提矛盾，报告不可达。
**条件常量传播（SCCP）**里 ⊥ 还兼"未定义"（undefined）——
CFG 还没走到这个点，暂时没有信息。三种解释共享同一个
代数性质：**⊥ 对 join 是单位元**（⊥⊔a=a，"多一条不可达
路径不改变任何结论"）、**对传递函数最安全**（⊥ 进什么
出什么都不影响其它点）。所以第 30 章的方程组把所有点
初始化为 ⊥ 时，用的是同一条"从最弱信息开始"的逻辑，
而不必关心每个域给 ⊥ 起的语义名字。反方向，⊤ 在各域
的解释倒是比较统一的："完全未知，任何结论都别基于我
得出"。⊥ 多义、⊤ 单义——这个不对称值得在遇到"为什么
我的 ⊥ 语义怪怪的"的困惑时拿出来对照。

### 29.3.9 lift 与第 24 章类型的对照：同形不同义

lift 的形状（加一个新底）在类型篇出现过近亲：第 24 章
引用类型 ptr(T) 加 null、第 29 章（数理逻辑读者跳过的
部分）的可空结构。但"形状相同"不等于"角色相同"，对照
一次可以防止概念串门。**提升域的 ⊥ 是格论角色**：它是
join 的单位元，参与不动点迭代，语义是"没有信息"。**可空
类型的 null 是类型论角色**：它是 ptr(T) 的一个正常 inhabitant，
语义是"没有对象"，参与的是解引用检查而非格运算。两者
偶尔会同框——常量分析里"指针为 null"作为一条**事实**，
生活在幂集格的事实全集里；而那个幂集格本身，可能建立
在某个提升域之上。层次分明地读：**格的元素是"关于程序的
事实"，类型是"程序的形状"；事实可以用格组合，形状用
类型组合，两套构造长得像是因为都在表达'有限信息下的
保守近似'，而不是因为它们是同一个东西。**第 32 章
把"空指针"做成数据流事实时，会再回头看这条界线。

### 29.3.10 连续提升、嵌套 optional 与"为什么只收四个构造器"

一个自然的问题是：lift 能不能连续用两次？lift(lift(A)) 得到
optional&lt;optional&lt;A&gt;&gt;，格中于是有两个底：外层 nullopt 与
内层 {nullopt}，二者在序上严格相邻，形状是在 A 下面垫了两级
台阶。数学上完全成立，但语义上必须想清楚两级底各自代表什么——
若只说得出"还没有值"一个意思，两级底就是冗余设计，join 时的
区分度永远用不到，却要为多一层 optional 付判空的代码复杂度。
两级底说得通的场景是两种"无值"成因需要分开追踪：比如外层底
表示"这个程序点不可达"，内层底表示"点可达但变量未赋值"，
此时连续提升是正当的。第 35 章可能未初始化分析其实选择了另一
条更直接的路——把"未初始化"放进幂集事实里显式追踪，而不是
叠两层 optional——两种建模在精度上可以等价，取舍在表示是否
顺手。这条对比值得记住：同一个数学事实，既可以用"给格加底"
表达，也可以用"在另一块格上加一个事实名"表达，格的选择首先
是表示工程问题，其次才是理论问题。

格论教材里还有几个标准构造本章刻意没有收入：**对偶格**（把序
整个倒过来，join 与 meet 互换——第 14.8.7 节专门讨论）、**商
格**（把若干元素按等价关系捏成一个）、**和/互斥和**（两块格
贴在一起）、**函数空间格**（14.5.7 节以"去掉固定键集的映射"
的形式露面）。不收的原因是教学上的 YAGNI：本书后续章节用到的
每一个状态格，都能用 lift、product、maps、powerset 四件套加
上手写基格拼出来；提前给出完整的构造器目录，读者反而要在没有
使用需求时记忆六个以上形状相同的模板签名。判断"构造器是否够
用"的客观标准是后面章节的实际消费——第 33 章用 powerset，
第 32 章用手写平格，第 37 章用手写区间格，第 49 章以后用 maps
组装过程间状态——四件套恰好覆盖，没有一章需要回头补构造器。

最后补一个实现层面的观察：lift 代码里判空分支的顺序不是随便
写的。leq 先问"上界 b 是不是底"，再问"下界 a 是不是底"，
两个问题的答案合起来覆盖"任一方为 ⊥"的全部四种组合；把顺序
写反结果相同，但与形式化定义（⊥ ⊑ 一切、除 ⊥ 外退回原格序）
的对应关系就不直接了。模板构造器是给读者读的，分支顺序应当
让人能逐行指回定义——这个自我要求在 product 的 fold 展开和
maps 的 getOrBot 上同样适用。

## 29.4 积构造：多分量并行

### 29.4.1 直觉与动机

一个程序常常同时携带多份独立的信息：分析需要为每个变量分别
追踪符号（第 31 章），或同时追踪"常量值"与"是否被取过地址"
（第 32 章的变体）。如果这些信息的抽象域互不干扰——一个变量
的符号不依赖另一个变量的符号——那么组合状态的自然方式是
**笛卡尔积**：状态是有序对 (a₁, a₂, …, aₙ)，每个分量取自
各自的格。

积格上"合并两条状态"的意思非常自然：逐分量合并。分支汇合处
一条路径带来 x=+，另一条带来 x=0，合并后 x 分量就是 +⊔0=⊤，
y 分量同理各自算各自的。序关系也是逐分量的：状态 s₁ ⊑ s₂
当且仅当每个分量都 ⊑。这种"一切逐分量"的原则有个名字——
**逐点定义**，它是把"单个格上的结构"搬运到"格的组集"上的
通用手法，14.5 的映射格会用完全一样的手法。

### 29.4.2 形式化定义

n 个格 A₁…Aₙ 的积是载体 A₁×…×Aₙ，序与运算逐分量：

> (a₁,…,aₙ) ⊑ (b₁,…,bₙ) ⟺ 对每个 i：aᵢ ⊑ᵢ bᵢ；
> join 逐分量取 ⊔ᵢ；顶=(⊤₁,…,⊤ₙ)；底=(⊥₁,…,⊥ₙ)。

积格的有界性直接继承：顶与底就是分量顶底打包。格公理的验证
全部归约到分量：自反、反对称、传递逐分量成立则整体成立；
join 的幂等交换结合逐分量归约。证明套路与提升一致——
"结构不相互作用时，复杂构造的性质就是分量的性质"。

一个值得停留的观察：**积格的高度（覆盖边计，与第 28 章
同一口径）是分量高度之和**，元素个数是分量元素个数之积。
这对第 31 章的终止性论证要紧——worklist 在有限格上每次
严格上升，总步数被"程序点数 × 格高"封顶。积格让"为 10
个变量建状态格"的高度从"符号格高度 2"涨到"2×10=20"
（若用一个大积格建模），而 14.5 的映射格给出的是
同一对象的另一种编码，高度语义相同。高度账目在第 31 章会
正式建立，本章先埋个伏笔。

### 29.4.3 代码导读：变参模板与 fold 表达式

product 的实现是本章唯一需要一点模板技巧的地方，因为分量的
**数目**在编译期才确定。函数模板签名
`product(const Lattice<As>&... ls)` 用变参包收集任意多个格；
返回 `Lattice<std::tuple<As...>>`，tuple 的元素类型恰好与
参数格的值域一一对应。C++17 的 fold 表达式把"逐分量"写成了
一行：tupleLeq 里 `(... && std::get<Is>(lats).leq(...))` 对
索引包做逻辑与折叠——每一分量都 ⊑ 才整体 ⊑，与形式化定义
逐字对应。tupleJoin 同理，用 `T{...}` 的列表初始化逐分量调
join 并打包。两个辅助函数都收一个
`std::index_sequence<Is...>`，这是把 tuple 的运行期索引展开
为编译期索引包的标准桥。

实现里有一个设计决定值得点破：**积格的 eq 用 tuple 的 `==`**。
tuple 相等逐分量调用元素类型的 `==`，对 int 分量就是数值相等。
若某分量的表示相等粗于语义相等（14.2.5 的隐患），tuple 的 ==
会跟着过粗——构造忠实继承分量的表示约定，这是值语义组合的
代价，也是把表示唯一化的另一个理由。

### 29.4.4 为什么积格是格

证明要点（完整枚举与 14.3.4 同构，此处只列归约目标）：偏序
三公理逐分量归约到各分量格；join 三公理逐分量归约；join 与
leq 的相容性逐分量归约。每个证明都是"对每个 i，用 Aᵢ 的对应
公理，再组装"。顶与底的有界性：顶的每个分量是分量顶，任何
元素逐分量 ⊑ 它——正是分量顶的定义；底同理。没有跨分量的
耦合，就没有超出分量公理的新义务——这句话是积构造定理的
一句话版本。

### 29.4.5 积的两种用途：多变量与多维度

积在后续章节里有两个不同面貌的用法，先分清以免混淆。第一个
面貌是**多变量状态**：把 n 个变量各自的单变量格做成积。
但注意第 31 章实际用的是 14.5 的映射格——当变量集合来自
程序文本、大小运行时才知道时，tuple（编译期定长）不够用，
映射格（运行时键集）才合身。tuple 版的积适合**数目固定且小**
的组合：第 39 章路径敏感分析里"分支条件 + 区间状态"两分量
的临时组合、第 52 章 IDE 里"事实格 + 边函数格"的配对。

第二个面貌是**多维度信息**：同一个变量的不同侧面（符号、
常量、活跃性）放在一个积里同步推进。这时各分量通常来自
不同的基础域——product(signLattice, constLattice, …)——
恰好演示了异构组合的能力。两个面貌的共同点：分量独立、
逐点运算。遇到"分量不独立"的情形（比如 knowing x 是常量
会改变 x 的符号推断），积就不是正确的组合，需要更精细的
域设计——那是第 32 章要面对的话题，此处点到为止。

### 29.4.6 手算一个三重积，并辨析"字典序积"

纸上做一次三重积能同时巩固两个概念。设三个分量格为
sign、sign、以及二元布尔格 B={⊥,⊤}（底底顶顶四元素，
join=或）。积 A = sign×sign×B 有 5×5×2=50 个元素，
高度 2+2+1=5（覆盖边计）。取两条状态 s₁=(0,−,⊥)、
s₂=(+,0,⊤)，逐分量合并：第一分量 0⊔+=⊤，第二分量
−⊔0=⊤，第三分量 ⊥⊔⊤=⊤，得 s₁⊔s₂=(⊤,⊤,⊤)——三路
信息全糊化。再取 s₃=(+,−,⊤)、s₄=(+,−,⊥)：第一二分量
相同直接保留，第三分量 ⊔⊤=⊤，得 (+,−,⊤)。两个例子
并排读出一个规律：**分量糊化是独立的**——前例全糊是
因为每个分量都"凑巧"不可比，后例保留了两维的完整精度。
多变量分析的精度故事就是"哪些维度凑巧可比"的故事，
第 31 章 sign1 的循环头合并恰好是"全部维度都可比"的
幸运情形（两个 +），结果出奇地精确。

再辨析一个容易混淆的姊妹构造：**字典序积**（lexicographic
product）。字典序积的序是"先比第一分量，仅当相等才比
第二分量"——像词典排序。它也是格，但 join 语义完全
不同：字典序积里 (0,−) 与 (+,−) 的 join 是 (+,?)（第一
分量 + 胜出，第二分量被无视或按规则取一）。数据流分析
几乎从不用字典序积——控制流汇合处两条路径的信息**没有
优先级**，逐点合并（笛卡尔积）才忠实于"两条路径都可能
发生"的语义。字典序积的用武之地在别处（优先级调度、
层级化配置合并），知道它存在、并且知道**为什么这里
不用它**，就足够了——构造的丰富性意味着选错构造是
真实的风险，辨认"语义要求的是哪一种合并"是设计能力
的一部分。

### 29.4.7 积的高度账目与终止预算

14.4.2 提到积格高度是分量高度之和，这里把账算细，因为
第 31 章的终止性证明将按这个口径引用。n 个分量格高度
h₁,…,hₙ（覆盖边计），积格高度 H=Σhᵢ。直觉：从全底到
全顶的最长上升路径上，每个分量各自从底爬到顶，分量之间
没有捷径也没有绕路——严格上升的每一步恰好抬高一个分量的
一级。这给了一个实用预算公式：worklist 最坏迭代次数 ≈
程序点数 × Σhᵢ。sign1.tip：7 点 × (2+2) = 28 次"可能
的新值计算"上界，实际运行十几次收敛——上界松但方向
正确，且**关键的是它是常数**。读者在第 31 章看到
"O(点数 × 格高)"的复杂度声明时，应当能立刻把"格高"
展开成今天这个 Σhᵢ 的形式，并知道它由构造参数（几个
变量、值域多高）直接决定。

### 29.4.8 复合状态的调试：逐分量打印的纪律

积格把多个维度的信息捆在一个 tuple 里，随之而来的是
一个调试期的现实问题：打印 (⊤,−,+) 给谁看？三个分量
分属三个域，各自的打印函数不同，混在一个括号里只是
勉强可读；等积格嵌套到三层（第 37 章的区间 × 符号 ×
常量性），括号串就会长到没法核对。本章从第一天起立的
规矩是：**每个域自带 mapShow 风格的打印，复合域的打印
逐分量委托**——printTuple 逐个调用分量的打印函数再拼
括号，嵌套几层就委托几层。这条纪律在第 31 章的输出表
里兑现：每行"程序点: 状态"，状态无论多深都是确定性的
单行文本，expected/output.txt 才能逐字节对账。

它还有一条不那么显然的收益：**逐分量打印 = 逐分量核对**。
人眼看 (⊤,−,+) 判断"对不对"时，实际是逐分量问"这一维
该是什么"——打印结构与核对结构一致，错误的定位从
"整个状态错了"缩小到"第 i 维错了"。第 27 章的记录字段
逐个打印、第 26 章的代换逐项打印，走的都是同一条路：
**调试输出的结构应当镜像数据的结构**。

### 29.4.9 积格上的代数账目：交换、结合与"为什么不是字典序"

积格既然是格，就自动继承格的全部代数定律，但把几条常用的
定律在分量层面核一遍，对写对代码有直接帮助。join 的交换律
（a ⊔ b = b ⊔ a）来自每个分量各自的交换律；结合律同理：三个
积元素先 join 前两个还是后两个，每个分量上的结果都是三个
分量值的 join。这条保证对求解器很重要——worklist 在有多个
前驱的节点上，按前驱队列的到达顺序逐个 join；顺序若影响
结果，算法的输出就依赖调度细节，变得无法复核。积格上结合
律与交换律成立，意味着"前驱按 CFG 邻接表的存储顺序合并"
是安全的：任何顺序收敛到同一个环境。第 31 章算法正确性论证
里"顺序无关性"那一步，依据的就是这两条定律。

更实质的一条是 join 对 meet 的分配律。积格在每个分量上分配
当且仅当每个分量格本身分配——符号格、幂集格、链都是分配格
（幂集格上并对交、交对并分配是集合代数的基本事实），所以
这些格的有限积依然分配。分配性是 IFDS 等框架（第 51 章）的
命根子：IFDS 要求传递函数可分配，即 F(a ⊔ b) = F(a) ⊔ F(b)，
才能把分析拆成"逐路径、逐事实"的图可达问题。此刻先记下这个
伏笔：gen/kill 函数天然可分配，因为它只做固定增删；而状态
依赖的传递函数（第 35 章）未必——可分配性与"是否看状态"
没有简单等价关系，必须逐函数验证。

还要再辨析一次字典序积。对两条链，除了逐分量积，还可以定义
字典序：先比第一分量，相等再比第二分量，像词典排单词。字典
序仍是偏序，但它的 join 不是逐分量 join——当第一分量不同时，
整个 join 就是第一分量较大的那个元素，第二分量原封不动。
字典序积因此是格（对链而言），却不是 product 构造给出的
那个格。为什么数据流分析一律用逐分量积而不用字典序积？因为
字典序给第一分量赋予了"否决权"：第二分量的信息在第一分量
不确定时被整体丢弃，这与"各维度信息独立合并"的分析意图
相悖；而且字典序积的高度是两链高度之**积**而非之和，终止
预算更差。逐分量积的高度相加、join 独立，恰是状态合并想要
的语义。几何上两种积的区别也能看出来：逐分量积把两条链拉成
矩形网格，字典序积把第二条链的一份拷贝挂在第一条链的每个
点上，是一长条串起来的梳齿结构。

## 29.5 映射构造：抽象环境的正式形态

### 29.5.1 直觉与动机

第 28 章的抽象环境是 `SignEnv = map<string,int>`，当时它是
手写的：joinEnv 逐变量 join，缺键按底。本章把这个手写形状
**升格为构造**：给定值格 V 与固定的键集 K，得到
"K 上的全函数、逐点运算"的格。这正是抽象解释里"环境"的
正式身份——**程序状态就是变量集到值格的映射格的元素**。
第 31 章的 worklist 求解的状态格、第 32 章的常量环境、
第 49 章的过程间环境，全部是这个构造的实例。

为什么值得升格？手写版本（ch28 的 joinEnv）与构造版本
（maps）在数学上等价，但构造版本带来三样东西：正确性论证
继承自构造定理，不再逐域重写；键集缺失行为统一为"按底"，
消除各处手写的分叉；并且映射格自己仍是格——它可以再被
提升、再进积、再进更大的映射，构造的封闭性在环境层面
继续生效。

### 29.5.2 形式化定义

固定键集 K、值格 V，映射格的载体是 K 到 V 的**全函数**，
用 std::map<K,V> 表示时允许"缺键"，缺键语义规定为取 ⊥：

> m₁ ⊑ m₂ ⟺ 对每个 k ∈ K：m₁(k) ⊑ m₂(k)（缺键按 ⊥）；
> join 逐键取 ⊔（缺键按 ⊥）；顶：每键为 ⊤；底：每键为 ⊥。

三条设计决定需要论证。**第一，键集为什么固定。** 若键集随
状态变化（一个状态有 x，另一个没有），两个状态的"合并"要
先对齐键集，序关系也要处理"键只在一方出现"的情形——可以
做，但每一步都多一种情况，构造定理的证明随之膨胀。TIP 的
变量集合是静态的：函数的形参与 var 声明在编译期确定全部
变量名，运行中不会新增。既然键集静态，就把它做成构造参数，
载体退化为"固定键集上的全函数"，一切逐点定义。第 54 章
的指针分析会遇到动态键（分配点集合随分析增长），那时用
"缺键即空集"的幂集式处理——两种键集策略各自匹配各自
的语义，14.6 会再比较。

**第二，缺键为什么按底。** 缺键的语义是"此状态没提这个
变量"。在数据流语义里，"没提"最安全且最一致的解释是
"信息为零"——即底。验证它与逐点序自洽：状态 {x=+}（y 缺）
⊑ {x=+, y=+} 吗？x 分量相等，y 分量 ⊥ ⊑ +，成立——缺键
按底让"知道得多"单调地高于"知道得少"，正是我们想要的。
若缺键按顶，则"知道 y 的信息"反而让状态**变小**，序方向
颠倒，worklist 的"只升不降"会失效。

**第三，顶与底为什么预构造。** 构造时把每键 ⊤ 的映射与
每键 ⊥ 的映射各建一份存进 topV/botV。代价 O(|K|) 一次，
换来 join/leq 里的 getOrBot 查询可以引用现成的底映射
（botM.at(k)）而不必每次临时构造。这个微型优化示范了
"顶底为值"（14.2.3）的实际回报。

### 29.5.3 元素个数与高度：有限性的来源

固定键集 + 有限值格 ⟹ 映射格有限：元素个数 |V|^|K|，高度
|K|·height(V)（覆盖边计，逐键独立上升）。符号域 |V|=5
（含顶底）、height(V)=2，两个变量 x、y 的状态格有 25 个
元素、高度 4。第 31 章 sign1.tip 的 worklist 终止步数的
上界由此而来——7 个程序点 × 4 级高度，再乘每次上升触发
的传播常数。**有限性是算法
终止的全部前提**，而它恰好由"键集固定 + 值格有限"两个
构造参数保证。第 37 章的区间格打破值格有限性，终止性
随之崩塌——那一章的加宽技术可以读作"用外科手术恢复
本章的有限性"。

### 29.5.4 代码导读

maps 的实现（29.12 节）逐字对应形式化定义，值得逐段读。
构造入口先建 topM 与 botM：对键集每个键放入值顶/值底。
getOrBot 是缺键语义的实现——查找失败返回 botM 里的对应项；
它按引用捕获 botM，避免拷贝。leqF 对键集逐键：任何一键
不满足 leq 立即短路返回 false，全过才 true——与"逐点序"
定义逐字对应，也使 leq 的期望复杂度是 O(|K|) 次值格 leq。
joinF 同样逐键，结果映射逐键 emplace。两个 lambda 都按值
捕获（[=]）——捕获了 l（值格）与 keys（键集），构造出的
映射格自包含。

一个值得注意的实现纪律：**join 与 leq 都不修改输入状态**。
joinF 构造新的结果映射，leqF 只读。第 31 章的 worklist
会在迭代中大量调用这两个运算，若任何一处悄悄改写输入，
"单调上升"的论证就有了漏洞。值语义 + 纯函数是格运算的
默认形态，除非性能证据足够强，不做原地优化。

### 29.5.5 为什么映射格是格

归约目标与积构造完全平行——事实上固定键集的映射格就是
"|K| 个 V 的积"的紧凑编码：序、join、顶、底逐键定义，
而键与键之间没有耦合，一切公理逐键归约到 V 的公理。
两者差别只在表示：tuple 编译期定长、类型异构友好；map
运行时键集、键为统一类型。教学实现里两者并存（14.4.5 的
两个面貌），理论视角里它们是同一个构造的两次呈现。

有一个技术细节属于映射格独有：std::map 的键全序与遍历
顺序。演示与第 31 章的输出都依赖 map 的字典序遍历——
输出确定性（第 26 章已立为规矩）在这里由标准容器的有序性
免费提供。若换 unordered_map，语义不变但输出顺序漂移，
expected 对账立刻失效——容器选择在此不只是性能问题，
还是可复现性问题。

### 29.5.6 maps 与第 28 章 SignEnv 的关系

值得诚实地说明：本章实现完成后，第 28 章的 joinEnv 并没有
被删掉重定向到 maps——两个版本并存于各自章节的快照里。
原因有二。其一，快照自包含：每章的代码是当时原理的直接
呈现，第 28 章呈现"逐点合并的最简手写"，本章呈现"同一
形状的构造化"，对照阅读本身就是教学材料。其二，第 28 章
的 SignEnv 缺键语义由"缺键即 ⊥"在读取端（evalExprSign）
处理，而 maps 在合并端统一处理——两种放置位置都正确，
但抽取公共构造的时机是"第三个使用者出现"（第 32 章的
常量环境），届时构造版的复用收益才真正兑现。这是重构
节奏的一条通用经验：抽象在第二个使用者出现时值得考虑，
在第三个使用者出现时必须完成。

### 29.5.7 从映射格到函数空间格：去掉固定键集

14.5.2 的第一设计决定是键集固定。若去掉这个前提——允许
键集任意、状态是"部分函数"——得到的构造在文献里叫**函数
空间格**（function space）或"映射到格的部分函数格"。
它的序与运算仍然是逐点定义，但缺键语义必须重新谈判：
本设计用"缺键=⊥"，则序要求"m₁ 有而 m₂ 没有的键，其值
必须 ⊑ ⊥，即恰为 ⊥"——部分函数格的元素实际上是
"非底值的有限支撑集"，序变成"支撑集包含 + 支撑上逐点"。

函数空间格数学上完全合法（仍是格），为什么本章不采用？
三个理由。其一，**实现复杂度跳档**：逐点序要处理三种
键情形（双方都有、仅一方有），join 要对齐支撑集，每个
运算的分支数翻倍。其二，**有限性论证变绕**：键集动态时
"格有限"需要键全宇宙有限 + 值格有限两个条件联合论证，
固定键集把前者变成构造参数、免掉论证。其三，**TIP 的
语义不需要**：变量集静态（14.5.2 已论），动态键的需求
第 54 章才出现，且那里的域是幂集形状、用"缺省空集"
的幂集处理更自然（14.6.3 的对照）。把函数空间格留作
概念储备而非实现，是"工具箱按需添置"的又一例——但
读者应在纸上推一遍它的 leq 三情形，确认自己有能力
在需要时把它造出来（练习 14.7）。

### 29.5.8 环境格上的逐点提升：把两章连起来

本章构造与第 28 章的传递函数有一个尚未言明的衔接点：
传递函数逐变量地更新环境，而"逐变量更新"在映射格视角下
是**逐点提升**——环境 m 更新变量 x 的意思是构造
m' = m[x ↦ v]，其中只有 x 键变化、其余键原样拷贝。
这个操作在函数式文献里叫"单点更新"，它的单调性可以
按映射格的构造定理归约：单点更新关于 x 键单调（值 v
代入后逐键比较，其余键恒等），关于其余键恒等。第 28 章
transferNode 的 `out[target->name] = evalExprSign(...)`——
先拷贝 out 再写一键——正是单点更新的命令式写法。当
读者在第 31 章看到 worklist 里"重算一个点的状态"时，
背后的代数事实是：**传递函数 = 若干单点更新与逐点
抽象运算的复合，全部按构造定理继承单调性**。链条到此
完整：格 → 构造 → 环境 → 单点更新 → 传递函数 →
单调 → 不动点存在且可达。每一环都在某章被建立，本节
把衔接处指明。

### 29.5.9 getOrBot 与"全函数"传统

getOrBot(m, k) 把部分映射查询变成全函数：缺键返回 ⊥。
这个小小的包装后面有一个值得点名的传统。文献里描述
数据流状态几乎总是用**完全函数** env : Var → AbsVal，
数学上干净；实现里却只有**部分映射**（map），因为程序
执行到某处之前，不是每个变量都被赋值过。getOrBot 就是
两个世界之间的桥：**存储保持部分性（省内存、符合执行
历史），查询呈现完全性（下游代码不用写缺键分支）**。
缺键的语义"没有信息"恰好是 ⊥ 的格论身份，于是这个桥
不需要任何特判——缺省值直接用格的底。

对照一个反例：若缺键返回 ⊤（"未知"），查询就撒了谎——
变量没被赋值不是"值太多说不出"，而是"根本没有值"，
两件事在格上分别对应 ⊥ 和 ⊤。第 32 章常量分析对"未
初始化变量"的处理（练习 14.9 会碰到）会把这个差别
升级成一道设计题：读一个没赋值的变量，该报什么？
今天先记住机制：**部分存储、全函数查询、缺键即底**。

### 29.5.10 环境上的两种"写"：强更新与弱更新预告

映射格回答的是"状态长什么样"，但分析器在传递函数里还要
回答一个操作性问题：对环境做一次写 x := v，结果是什么？
在单条确定路径上，写就是**强更新**（strong update）：键 x
的值被整个替换为 v，旧值与新值无关。这在映射格上根本不经过
join——直接对 map 做下标赋值即可。强更新的正确性前提是
"这个写必然发生且只有这一个状态"：程序点确实可达、流入
状态唯一、目标确定就是 x。这三个前提在路径内赋值全部成立，
所以本书前面每一章的传递函数都用强更新，读起来也最简单。

一旦分析合并了多条路径，前提就可能失效，此时必须使用**弱
更新**（weak update）：新值不替换旧值，而是与旧值 join。
弱更新对应这样的读解：这个点上的状态是多个可能世界的汇总，
x 在某些世界里还是旧值、在另一些世界里是新值，诚实的近似
只能是旧 ⊔ 新。弱更新是映射格的 join 运算的直接消费——这
也是为什么环境必须做成格而不是普通的字典：没有 join，弱
更新无从写起。什么时候可以安全地从弱升级为强？当且仅当
分析能证明"到达这个写的状态只有一个"。在流不敏感分析里
这个条件几乎永远不成立（所有赋值在概念上同时作用于同一份
状态），所以流不敏感的环境传播一律弱更新；在带路径条件
的分析里，单点分支内的赋值可以强更新。第 37 章以后的区间
分析会在同一个程序里同时用到两种写：合并点弱更新、顺序点
强更新，对照之下差别一目了然。

指针与别名会把这个问题再推尖锐一层：写的目标若不是变量名
x 而是 *p，分析在不知道 p 指向唯一对象时，必须对 p 的每个
可能指向都弱更新一次——可能包括分析者没意识到的对象。
第 54 章 Andersen 分析就是为回答"这次写究竟落到哪些键"
服务的；届时会看到，指针分析的精度直接决定环境上每次写能
不能强、弱更新的范围有多大。这条线索把"格的构造"与"指针
分析"两个看似无关的主题串了起来：它们共同服务于同一件事——
让传递函数对环境的每一次修改都有明确的点和明确的新旧关系。

这里还可以回头看清 getOrBot 的另一层用意：弱更新在键此前
从未出现过时，语义上是 ⊥ ⊔ v = v，即"旧世界里这个键取底"。
映射构造把缺失键解释为底，于是弱更新的代码不必区分"键不
存在"与"键存在且为底"两种情形，一条 join 规则覆盖全部。
表示上的简化最终来自底元素吸收性的设计，而不是来自特判
逻辑——好的格构造让传递函数少写分支，这是本章四个构造器
共同的工程价值。

## 29.6 幂集构造：集合域

### 29.6.1 直觉与动机

另一大类分析追踪的不是"每个变量的值"，而是"到达每个点的
事实集合"：哪些定值可能到达这里（到达定值）、哪些变量
可能未初始化（第 35 章）、哪些表达式此刻必然可用（可用
表达式）。事实用字符串或编号命名，状态就是**事实的集合**，
合并两条状态取并集（may 分析）。把"集合 + 并 + 包含序"
也做成构造，就得到**幂集构造**：给定全集 U，载体是 U 的
子集族 P(U)，序为 ⊆，join 为 ∪，顶为 U，底为 ∅。

### 29.6.2 形式化定义与一个方向的转换

幂集格（⊆ 序，∪ join）的有界性与公理是集合论的直给：∅ 与
U 是底顶，∪ 满足三条定律，⊆ 与 ∪ 相容。真正需要讨论的是
**must 分析的方向问题**。可用表达式（第 33 章）在汇合点取
**交**——"两条路径都可用才可用"。交不是 ⊆ 序幂集格的 join。
处理办法不是给接口加 meet，而是**翻转序**：把 must 分析的
格看成 ⊇ 序的幂集格——此序下 join 是 ∩，顶是 ∅，底是 U。
同一个载体、同一族运算，序方向一换，may 与 must 统一为
"取各自方向的 join"。第 33 章的 DfaSpec 用一个 bool may
参数实现这个翻转，本章先在理论上立好"序方向是视角选择"
这块基石。

为什么不在接口里加 meet？数学上格的对偶原理保证 meet 存在
且对偶公理成立，加了也不出错；但接口每多一个操作，四个
构造就要多实现并多论证一个成员，而后续章节的算法（worklist、
方程、DFA 驱动）只消费 join 与 leq。接口最小化的收益在
教学代码里尤其明显——每个成员都该有买主。

### 29.6.3 有限性：全集参数

P(U) 有限当且仅当 U 有限。TIP 的事实命名是有限的：变量名
有限、定值编号有限（每条赋值一个）、表达式文本有限。构造
参数 `universe` 显式给出全集，顶（=universe）与底（=∅）随之
确定。演示里用了默认参数——空全集，此时顶=底=∅，格退化
为单元素，join({a},{b})={a,b} 仍正确（并运算不查全集），
但"顶"失去了意义。这是**演示与实用的分界**：第 33 章会把
真实全集（如全部定值编号 d1…d5）传进来，顶元素开始承担
must 分析初始化的语义。全集为空时顶底重合的格是平凡的格，
用它做演示是安全的，用它做分析是空谈——区别就在宇宙参数。

### 29.6.4 代码导读

powerset 的实现是四个构造里最短的，因为 std::set 就是
幂集的现成载体。leqF 实现为子集判定：对 a 的每个元素查
b 是否包含，全含才 ⊑——O(|a|·log|b|) 的经典形状。joinF
是集合并：先拷贝 a，再 insert b 的全部元素。eqF 用 set 的
`==`（集合相等当且仅当互为子集，但直接比较更快）。构造
把 universe 存为 topV、空集存为 botV。与 maps 一样，全部
运算只读输入、构造新结果——格运算的纯函数纪律在此再次
生效。

与 maps 的键集参数对照：maps 的 keys 是"必须逐键处理的
骨架"，缺席的键有明确语义（⊥）；powerset 的 universe 只是
"顶的边界"，元素集合本身可大可小，缺席没有特殊语义——
一个子集要么包含事实要么不包含，没有"第三态"。两种参数
化对应两种域形状：函数式环境 vs 集合式事实。第 35 章
（未初始化分析）在两种形状之间做选择时会正式比较一次。

### 29.6.5 位向量：工业实现的影子

std::set<string> 是教学友好的集合表示，工业数据流引擎
（LLVM 的传统 Pass、各类编译器的 liveness 求解器）几乎
一律用**位向量**：每个事实一个编号，集合是 64 位字的
数组，join 是按位或、leq 是子集掩码测试、eq 是全字比较。
位向量把集合运算变成指令级的极廉运算，代价是要维护
"事实 ↔ 编号"的登记表（第 33 章的定值编号 d1…d5 就是
登记表的教学版）。本书不用位向量，因为教学程序的集合
只有几个元素，set 的清晰度远比常数因子重要；但读者应
知道教学表示与工业表示的对应关系——**表示变了，格没变**。
构造定理不关心载体是 set 还是 bitset，这又是"接口与
表示分离"的回报：第 33 章的四个分析若要工业强化，
只需换 powerset 构造的内部载体，驱动代码一行不改。

位向量还带来一个理论花絮：n 位向量连同按位运算恰是
2ⁿ 元素布尔代数的具体实现——幂集格、位向量格、布尔代数
三个名字，同一个数学对象。第 33 章讲 may/must 时会再次
遇到布尔代数的对偶律（补、De Morgan），届时位向量的
按位非就是格论里的补运算。

### 29.6.6 全集参数的运行时核对

powerset 把全集当构造参数，但 join/leq 的实现**并不检查**
元素是否真的属于全集——join({a},{b}) 在空全集下也返回
{a,b}（14.6.3）。这是有意的宽松还是疏漏？是有意的，
且值得说明边界在哪。全集的语义职责是**定义顶**：must
分析把非入口点初始化为全集，全集错了顶就错。而 join/leq
的正确性不依赖全集——并与包含在任何集合族上都成立。
于是全集参数只在一处被真正消费：topV 的构造。运行时
核对"每个元素 ∈ 全集"的成本是每次运算 O(|a|·log|U|)，
收益是更早抓到登记表 bug（事实没登记进全集）——第 33 章
选择在**登记处**（构建 DfaSpec 时）做一次性核对，而不是
在每次运算里反复核对。错误检查的成本放在成本最低、
离错误源头最近的位置，这是和 14.8.3 同源的设计判断。

### 29.6.7 meet 在幂集格里的身份：交

14.8.4 会论证"接口不设 meet"，但借幂集格把 meet 摸一遍
是有价值的，因为它简单到可以手算：若幂集格的 join 是并、
leq 是包含，则 meet 是**交**——两个子集的最大公共下界，
恰是同时包含于两者的最大集合。验证格论性质也顺手：
交与并满足吸收律 a∩(a∪b)=a，幂集格因此不仅是一般的格，
还是（有补的）**布尔代数**。有了 meet，"must 语义"可以
不通过对偶技巧、直接在幂集格上写：活跃变量的 must 版
（"所有路径都活跃"）就是各路径活跃集的交。那为什么第 33 章仍走对偶路线？工程账：对偶化后 may/must 共用同一
套 join 驱动代码、同一套 worklist、同一套终止性论证，
两套运算就要维护两条实现与两份证明——**表达能力等价时
选实现面小的那条**，与第 27 章"一个字段语义一个函数"
的节约精神同源。meet 留在本节纸上，不进接口。

### 29.6.8 四个构造器的复杂度与表示开销账目

四个构造器不仅形状不同，单次运算的代价也不同，这份账目在
分析器变大时会反过来决定哪些构造能实际使用。设底层格一次
leq/join 的代价为 O(c)、键集大小为 n、元素集合大小为 m。
lift 的每次运算只多一次 optional 判空，代价仍是 O(c)；
product 的代价是各分量之和 O(c₁ + c₂ + ⋯)，没有跨分量
交互；maps 对每个键逐点运算，代价 O(n·c)，且 join 要构造
一张全新的 n 键映射，分配与拷贝的常数开销在 n 大时很可观；
powerset 的 leq 是对较小集合的扫描 O(m)，join 是构造并集
O(m₁ + m₂)。这组数字解释了工业分析器的两个偏好：事实集合
用位向量表示时，powerset 的并、交、子集判定全部退化成长
度 m/字宽 的字运算（14.6.5 节）；环境用稀疏映射（只存非底
键）表示时，maps 的 join 只遍历双方实际出现过的键，而不
是声明全集——本书的 SignEnv 走的就是稀疏路线。

构造的嵌套使用让代价相乘，这是读复杂度时最容易漏掉的一点。
映射格 maps(K, product(L₁, L₂)) 上一次 join 的代价不是
O(n·(c₁+c₂)) 吗？确实如此；但如果顺序反过来，把环境做成
两个映射的积 product(maps(K,L₁), maps(K,L₂))，每次只动
一个维度的传递函数可以只更新其中一个映射，另一个整体共享
（copy-on-write 的机会）。两种构造数学同构，操作代价却因
"更新局部性"不同而拉开。教学代码一律按概念最直接的顺序
嵌套（环境即映射、值即积），正文在此指出：当性能成为问题，
先重新安排嵌套顺序，再考虑换数据结构，往往比换语言或换
算法见效更快。

内存占用同构地翻倍：maps 顶元素对每个键各存一份值顶，
powerset 顶存整个全集。第 31 章以后求解器同时保存每个程序
点的一份状态快照，总内存约为"点数 × 单点状态大小"。点少
（几十到几百）、状态稀疏时这完全可承受；点上万、值格积的
分量多时，必须靠稀疏表示与共享子对象压缩。终止性由格高度
保证、单轮时间由宽度和表示决定、内存由点数乘状态大小决定
——三笔账在本章第一次同时出现，后面每一章的工程权衡都不
过是在这三笔账之间挪动。

## 29.7 演示解读：五行输出逐行读

本章的 --check 不做分析，而是打印四个构造上**预先选定的
join 例子**——每个例子都挑在"结果不是显然的"的边界上，
五行输出就是四份小型实验报告。--check 仍然先让程序通过
完整前端（词法、语法、名字解析），这保持了"输入必须是
合法 TIP 程序"的接口纪律，也让本章可回归——未来任何一次
前端改动若弄坏了构造演示，对账会立刻报警。

输出第一行是标题，此后四行对应四个构造。

**第一行 `lift(sign): join(⊥,+) = +`。** 新底与任何元素
join 取该元素——底的单位元性质。挑这个例子是因为它是
提升格的"定义性"行为：若这行输出不是 +，说明新底没有被
正确识别为最小元。接着第二行 `lift(sign): join(0,−) = ⊤`
展示的是**原格内部**的 join 穿透提升层：0 与 − 不可比，
join 委托回符号格返回 ⊤。两行合读：提升层 transparent——
有值时仿佛提升不存在，无值时新底按单位元参与。区分这两行
很重要：第一行检验的是提升加的东西，第二行检验的是提升
没有破坏的东西。

**第三行 `product(sign,sign): join((0,+),(+,−)) = (⊤,⊤)`。**
两个分量各自独立地取 join：第一分量 0⊔+=⊤，第二分量
+⊔−=⊤。例子的挑选故意让两个分量"路径不同"——第一分量
是"底还是顶"的边界情形（0⊔+ 达到顶但经过的是不可比对），
第二分量是正负相遇。若实现错误地做了"分量间耦合"（比如
把两分量的结果再 join 一次），此例恰好不变（⊤⊔⊤=⊤），
所以单靠这一个例子不能排除全部耦合 bug——但配合 14.8 的
公理论证与 14.11 练习里的反例设计，覆盖是完备的。**演示
例子是论证的取样，不是论证的替代**，这句提醒适用于本章
乃至全书的一切 expected 文件。

**第四行 `maps{x,y}->sign: join({x=0,y=⊥},{x=+,y=+}) = {x=⊤,y=+}`。**
逐键合并：x 键 0⊔+=⊤；y 键 ⊥⊔+=+——缺键按底的语义
在这里得到了最直接的表达：第一个状态根本没提 y，合并后
y 取第二个状态的 +，仿佛第一个状态对 y 投了弃权票。
这是数据流"部分信息合并"的缩影：知道一半的状态与知道
另一半的状态合并，结果是两条知识的并。第 31 章 sign1.tip
循环头处两条路径的合并（一条带循环体信息、一条来自
循环外）在语义上正是这一行——maps 格把那件事提前演示了。

**第五行 `powerset: join({a},{b}) = {a,b}`。** 并集，
may 分析的合并语义。用字符串 {a},{b} 而不用更"语义化"的
名字（如 d1,d2），是因为本章的事实域还没有程序对应物——
第 33 章才会让集合元素是真实的定值与变量名。此处只展示
代数行为，命名留给有语义的一章。

### 29.7.1 为什么 0⊔− 是 ⊥ 还是 ⊤ 要分场合

演示里出现了两个易混的运算，值得专门分离。join(0,−)=⊤
是**格运算**：0 与 − 是格的两个不可比元素，它们的最小上界
是 ⊤。而 sAdd(0,−)=−（第 28 章的加法表）是**抽象算术**：
具体地，任何非负整数加负整数，结果符号随两数的绝对值而变，
但"加上 0"这一情形下符号保持——0+x=x 对具体值成立，抽象化
后 0 与 − 的抽象和是 −。同写一个"加"字的两件事，一个是
状态合并，一个是表达式求值，前者查 join 定义，后者查抽象
运算表。初学者最常见的概念事故就是把二者混为一谈——比如
以为赋值 `y = x + z` 在合并点会"join 两个操作数"。分清
之后再看第 31 章的 transferNode：合并（joinEnv）只发生在
控制流汇合处，算术（sAdd）只发生在赋值右值的求值里，
泾渭分明。

### 29.7.2 演示为什么不"遍历格元素穷举验证"

一个更雄心勃勃的演示是对每个构造穷举所有元素对、验证全部
join 结果。符号格 5 元素，积格 25，都可行；但幂集格随全集
2 次幂爆炸，穷举不可扩展；更重要的是，穷举验证的是**这个
实例**，而格公理是**对所有实例**的承诺——用 C++ 写一个
通用的"公理检查器"需要反射或概念技巧，超出本书工具钉
（C++17）与教学范围。本书的验证策略因此是三层：构造定理
的**纸上论证**（14.3.4/14.4.4/14.5.5/14.6.2）保证类别的
正确性；**固定示例**（本章演示）锚定每个构造的边界行为；
**端到端回归**（后续各章的 expected 对账）保证组装成的
分析器行为可复现。三层各覆盖一类错误，缺一不可——这也是
全书"三层验证"哲学在域构造层的落实。

### 29.7.4 为什么选这五个例子：演示即测试

latticeDemo 的五个 fixed join 不是随手挑的，每个例子
都在**钉一条语义边界**，合起来是一张最小覆盖表。例 1
join(⊥,+)=+ 钉的是提升构造的新底单位元——⊥ 不参与信息
合并，别把另一条路径拖糊。例 2 join(0,−)=⊤ 钉的是符号
域最反直觉的合并：0 与 − 都不是 +，合并却是 ⊤ 而非 −
或 0——格合并不做"多数投票"，两条互斥信息的并只能糊化。
例 3 的积格钉逐分量独立性：一个分量糊化不连坐其它分量。
例 4 的缺键合并钉 getOrBot 的单位元行为：缺键一边"让位"，
等价于 join 一个 ⊥。例 5 的集合并钉 may 语义：两条路径
的事实集合并起来，宁多勿漏。五条边界恰好覆盖四个构造
各自最容易写错的地方——**演示即测试，输出即断言**，
这正是 14.7.3 对账协议的内容侧：协议保证格式可对账，
例子选取保证语义可对账。

读者日后设计自己的域时，可以照这张表自查：新域的演示
是否覆盖了"单位元、最反直觉的合并、构造的独立性、缺省
行为、集合语义"五类边界？少一类，expected 文件就少一分
防错力。

### 29.7.6 脱离打印，在纸面上重推五行输出

读懂演示的检验标准是关掉程序、拿一张纸，只凭四个构造器的
形式化定义与符号格的 join 表，把五行输出逐行推出来。这一
小节给出推导的组织方式，读者应先自己推一遍再对照。

第一行 lift(sign): join(⊥,+)。提升格 join 的定义按两个参数
是否有值分三支；左参数是底（nullopt），命中"a 无底则返回 b"
一支，结果就是右参数 +。第二行 join(0,−)：两侧都有值，退回
原符号格的 join；查符号 join 表，0 与 − 互不可比，最小上界
为顶 ⊤。这两行示范了提升格推导的固定套路：先判空决定走哪
一支，只有"两侧都有值"时才需要查底层格——这个两步结构与
第 28 章手写符号格的单步查表相比，多出来的全部推理就是判空。

第三行积 join((0,+),(+,−))：逐分量处理，不允许跨分量组合。
第一分量 0 ⊔ + = ⊤（0 与 + 互不可比），第二分量 + ⊔ − = ⊤，
结果 (⊤,⊤)。推这一行时最常见的错误是"好心"跨分量配对，
以为第一分量的 + 能与第二分量的 − 发生关系；积的定义明确
禁止这种读法——分量之间在 join 时互不通信，任何交互只能
由更外层的传递函数引入。第四行映射 join，两变量 x、y 各自
独立：x 维 0 ⊔ + = ⊤；y 维上第一状态的 y 是底（s1 显式存了
y=⊥，与"键缺失"在映射格里等价），底 ⊔ + = +，结果
{x=⊤, y=+}。这一行同时验证了 getOrBot 约定：推导者不需要
区分 y 的底是显式存储还是缺失补出的，join 规则只有一条。

第五行幂集 join({a},{b})：并集运算，结果 {a,b}，没有任何
近似成分——幂集格上 join 是精确的集合合并，"变保守"只
发生在随后把 {a,b} 解释回程序事实时（比如 must 分析里看到
两个候选就无法断言具体哪一个）。五行推完，应当注意到一件
事：四行非平凡计算用到的全部"知识"只有符号 join 表一张，
四个构造器的贡献只是组织推导的骨架。这正是本章的核心主张——
构造器不增加新的数学内容，只提供把已知格组装成所需形状的
手段。若读者在推导某一行时不得不发明新规则（而不是查表加
套定义），那一行对应的代码就值得怀疑：要么构造器实现越出
了形式化定义，要么形式化定义本身漏掉了一支。演示与纸面推导
的互相核对，是比运行时断言更便宜、也更早发现问题的验证层。

## 29.8 格公理与验证策略

### 29.8.1 需要满足什么

把前几节散落的公理收拢成一张清单。对偏序 ⊑：自反、反对称、
传递。对 join ⊔：交换、结合、幂等（x⊔x=x）。序与运算相容：
x ⊑ y ⟺ x⊔y = y。有界性：x ⊑ ⊤，⊥ ⊑ x。数学上还可以
再少（leq 可由 join 定义），工程上四件套并列——每个成员都
有独立买主。

### 29.8.2 论证如何组织

四个构造的验证共用一条"归约"套路，值得显式总结，因为它是
读者将来构造新域时的操作指南。**第一步，识别结构不耦合的
边界**：提升的 nullopt 不与原元素交换信息、积的分量互不
读取、映射的键互不干扰、幂集的元素互不约束——这些"独立性"
是归约能够进行的前提。**第二步，把公理逐条归约**：含新底
的分支逐条验证（通常平凡：底是单位元），不含的分支直接
调用分量/原域的对应公理。**第三步，检查顶底**：构造后的
顶底是否恰是"逐分量/逐键/整体"的分量顶底——有界性在构造
下保持。三步走完，构造定理成立。以后每引入一个新域（常量
格、区间格、指针集合格），都按这三步走一遍，分析器的可靠性
链条才没有断环。

### 29.8.3 为什么不写运行时断言

读者可能期待代码里有 `assert(latticeLawsHold(l))` 一类的
运行时检查。本书选择不写，理由有四。其一，格公理是全称
命题，运行时只能抽样，抽样的通过给出虚假信心（见 14.7.2）。
其二，检查本身需要值域上的全等遍历，对幂集格不可行。其三，
assert 在 NDEBUG 构建下消失——被检查的保障随构建配置蒸发，
与"可靠性是论证出来的"这一立场相悖。其四，也是最实质的：
公理违反的典型来源是**join 表写错一两个格子**，端到端回归
（对账 expected）恰好对这类错误最敏感——join 表错，某个
程序点的分析结果就漂移，对账立刻红。所以我们的答案不是
"不验证"，而是**把验证放在对齐错误成本最低的层**：构造层
靠定理，实例层靠固定示例，分析层靠回归对账。

### 29.8.5 偏序、全序与格：sign 到底是什么序

三个概念容易搅在一起，用符号格理一遍。**偏序**（partial
order）只要求自反、反对称、传递——比较可以"失灵"（两个
元素互不可比，比如 0 与 +）。**全序**（total order）在此
之上要求任意两元素可比。**格**要求的是另一件事：任意两
元素有最小上界与最大下界——可比的元素当然有（较大者），
不可比的元素则靠"合并成第三个元素"补出上界。于是存在
既非全序又非格、全序但平凡成格、各种组合的偏序集，三个
维度正交。符号格属于"偏序但不是全序、是格"：0 与 + 不可
比（全序性失败），但 join 给出 ⊤（格性成立）。

这条辨析有实践出口。全序域（如第 37 章区间格的"宽度"
维度）上，join 可以退化成 max/min——实现能走捷径、论证
能省一半分支；偏序域（如积格、幂集格）上，join 必须老
老实实逐点/逐元素合并。写一个域的运算前先问一句"这个
序是全的吗"，能预判实现的分支形状与公理检查的覆盖面
（14.8.2 的论证组织方式也随答案变化：全序只需验证相邻
元素）。此外，"格不必全序"正是数据流分析表达力的来源
——若只能用全序域，多个变量的独立信息就装不进一个状态，
积构造将无从谈起。

### 29.8.7 对偶：把格倒过来看

格有一个免费得到新格的办法：把偏序整个反过来。格 (A, ⊑) 的
**对偶格** (A, ⪰) 以原 meet 为 join、原 join 为 meet、原顶
为底、原底为顶。公理体系自动保持：原格中"最小上界存在"翻
转后恰好陈述"最大下界存在"，而格同时保证二者。对偶的实际
用处首先是省一半理论：may 分析（join=并、求最小不动点）与
must 分析（meet=交、求最大不动点）是同一套理论在对偶格上
的两次实例，证明一个方向，另一个方向由对偶得出。第 33 章把
四类分析放进同一 DfaSpec 时，may/must 只是一个布尔位，背后
的统一性正源于此。

但对偶在工程实现上并不免费，值得小心两点。其一，本书求解器
只实现了"从底出发、join、最小不动点"这一个方向；跑 must
分析的标准技巧是**不实现对偶算法**，而是把 must 的 meet 与
"全域初始值"直接编码进同一个迭代器（18 章可用表达式分析的
initFull 就是这么做的）。这样代码只有一台引擎，正确性论证
却必须在心里同时握住对偶：初值从 ⊥ 改成 ⊤、收敛点从最小
不动点变成……对同一 join 迭代器而言仍是最小不动点，只是格
的起点和边界换了。"一台引擎 + 换五元组"之所以覆盖 may 与
must，前提是想清楚对偶发生在五元组的哪几栏（初值、边界、
合并运算），而不是误以为算法方向也变了。

其二，对偶保持格结构却不保持"信息直觉"的方向感。正向阅读
时 ⊑ 读作"更确定"（底最不确定、顶最……什么都可能），这个
读法本身容易自相矛盾——本书的约定是：底代表不可达/矛盾，
顶代表无信息的混沌，沿 join 上升是信息变**少**而承诺变宽。
对偶之后所有箭头反向，同一张图的讲述要整体改写。教学上的
建议是：永远只在一个固定方向上建立直觉（本书选 ⊥=矛盾、
⊤=无信息、join 合并可能性），需要 must 时改五元组而不改
直觉。对偶是证明工具和实现技巧，不必变成第二套需要日常
切换的语言。

## 29.9 同一个域的两种形态：从 SignLattice 到 Lattice&lt;int&gt;

### 29.9.1 适配器模式

第 28 章的五元格以 `SignLattice` 结构体形态存在：eq/leq/join
是成员函数，top/bot 是数据成员。本章的统一接口要求它以
`Lattice<int>` 形态出现。sign.cpp 里新增的
`signLatticeDomain()` 做的就是这个翻译：构造一个 SignLattice
实例，把它的三个成员函数包成三个 lambda，连同 STOP/SBOT
两个边界值一起填进 Lattice<int> 的字段。这是教科书式的
**适配器**：被适配者（SignLattice）与目标接口（Lattice<A>）
各自不变，翻译代码集中在一个函数里。

### 29.9.2 为什么不让 SignLattice 直接改造成 Lattice&lt;int&gt;

一个自然的反问：既然要统一，为什么不在第 28 章就把
SignLattice 写成 Lattice<int>？三个理由。第一，**两种形态
服务两种消费方式**：成员函数形态配合第 28 章的传递函数
（evalExprSign 直接调 sAdd 等自由函数，SignLattice 只在
joinEnv 里用），调用点少而固定；函数对象形态配合本章的
通用构造，格作为数据被捕获、传递、组合。第二，**教学时序**：
第 28 章的主角是抽象算术与单趟传播，引入函数对象只会分散
注意力；本章的主角才是"格作为可组合的值"。第三，**形态
差异本身是教材**：读者在第 28 章见过"域=一组运算"，在本章
见到"域=可以传递的数据"，两者合起来才是完整的现代观念——
运算与数据在本章的接口里合一了。

### 29.9.3 捕获方式的一个细节

signLatticeDomain 的两个 lambda 用 `[=]` 按值捕获了局部的
SignLattice 实例。SignLattice 是无状态的结构体（成员函数
不依赖实例数据，top/bot 是静态知道的常量），按值捕获安全
且零成本。这个细节值得多看一眼，因为它是"格的值语义"
能在构造间流动的基础：若 SignLattice 持有堆资源，按值捕获
会引入拷贝与生存期问题，届时应改用 shared_ptr 捕获或
无状态设计。本书所有域都是无状态/小对象——这不是巧合，
格的运算本来就该是纯函数；一旦发现某个域需要可变状态，
通常意味着把"分析的进度"误放进了"域的定义"。

### 29.9.5 适配器的抽查测试：等价性的便宜验证

signLatticeDomain 声称"与第 28 章的 SignLattice 语义等价"，
这句声称值得一个便宜的核对手段。完全等价验证需要枚举
两边的全部运算组合（5×5 的 join 表、25×25 的 leq 表），
手写一遍等于把两张表抄两次——不如回到第 28 章的表本身
当基准：**抽查测试**。在演示输出里固定几对"覆盖表上危险
格子"的运算（单位元格、对角线格、表角落的 ⊤ 行列），
让适配器跑一遍并与手写版本的理论值对账——latticeDemo
的五行输出里，例 1/例 2 实际就在做这件事。抽查设计的
原则与练习 14.3 的样本选取相同：**边界必查、随机可免**
——格运算的错误几乎总是发生在边界（底、顶、不可比对），
内部格子的实现与边界共享同一分支结构，抽中率低但
独立性差，抽查的边际价值小。

这节也顺手回答一个常见疑问：为什么不写一个"自动对表"
测试（枚举 5×5 全表）？可以写，而且值得写在 examples 的
自检里——但 expected/output.txt 走的是"确定性打印对账"
协议，全表 25 行会让演示输出膨胀而信息密度下降；全表
验证属于**开发期断言**，五行抽查属于**回归期基线**，
两种手段放各自的层，不混装。

第 30 章用 maps 构造的状态格写出 CFG 上的单调方程：每条
方程的右端是"前驱状态 join 后施加传递函数"，join 就是
maps 格的 join。第 31 章的 worklist 从全 ⊥ 出发迭代到

是第一个**无限**格——它将展示打破"值格有限"前提后的

也可以提前给出一张"消费对照表"：提升 → 第 32 章（常量
格的未到底）、第 52 章（IDE 事实格）；积 → 第 39 章

### 29.10.1 三个构造的三张使用合同

 Toolbox 有四个构造，但 lift 更像"预备步骤"（把域造出来），
product/maps/powerset 才是"组合步骤"（把域拼起来）。给
每个组合构造写一张使用合同——什么时候用、前提是什么、
产出什么——读者选型时对表即可。

**product 合同**：用于"多个独立维度的信息各记各账"的域。
前提：每个维度自身已是格，维度个数编译期已知。产出：
高度 = Σhᵢ 的积格，join/leq 逐分量。典型顾客：多变量符号
分析（14.4.3 的三变量）、 future 的"符号 × 常量性"复合
状态。反例信号：若两个维度**不独立**（一维约束另一维），
积格会把不可能的组合也当作合法状态——精度损失但不错，
需要更强的"关系域"时另行构造（第 37 章区间域是关系域
的特例：两界共享同一数值语义）。

**maps 合同**：用于"按名字索引的同质信息"。前提：键集
静态可枚举（变量名单在解析后固定），值域是格。产出：
高度 |K|·h(V) 的环境格，缺键 = ⊥。典型顾客：符号分析
环境（14.5.4）、第 32 章常量环境、第 33 章的
var→defset 映射的值侧。反例信号：若键集动态（方法表、
虚调用目标），maps 不适用——键本身要先进入分析对象。

**powerset 合同**：用于"事实集合"域。前提：事实的全集
可枚举且有限。产出：2^U 幂集格（may 序），join = 并。
典型顾客：第 33 章到达定值（事实 = 定值编号）、活跃变量
（事实 = 变量名）。must 用法：同一构造 + 反转初始化
（顶起跳），join 语义随之翻转（14.8.4 的对偶）。反例
信号：事实全集爆炸（路径全集、谓词全集）——幂集的
状态是全集的子集，全集大了状态跟着大，需要摘要技术
（第 37 章以后的话题）。

### 29.10.2 单调性预演：为第 15/16 章铺轨

第四篇的两大定理——方程组有最小不动点（15 章）、
worklist 收敛到它（16 章）——都押注在同一个前提上：
**传递函数单调**。本章虽不定义传递函数，却可以预演
单调性如何从格构造里"继承"下来，把链条先铺好。

定义：格 A 上的函数 f 单调，iff a ⊑ b ⟹ f(a) ⊑ f(b)。
直觉：输入信息更多，输出信息只会更多不会更少。第 28 章
的抽象运算已是单调的（读者可对 ADD_TABLE 抽查两行验证：
上行、右行都不会突然变"更精确"）。现在看构造如何放大
这条性质。**逐点提升**：若 f 单调，则"f 但对环境只动一个
键"（14.5.8 的单点更新）关于映射序单调——其余键恒等、
动的键走单调函数。**积格上的函数**：g(a₁,…,aₙ) 逐分量
使用单调函数再拼装 ⟹ 单调（每分量输入变大，各分量输出
不缩小，逐分量比较即得）。**幂集上的函数**：gen/kill 型
函数 F(S) = (S − kill) ∪ gen 显然单调（删得更多、并得更多
都只会让结果不缩小）。三条继承规则合起来覆盖了第 31 章
sign 分析的全部传递函数：transferNode = joinEnv（单调：
逐键 join 的单调性由构造定理给）+ 单点更新（单调）+
抽象运算（单调）。到第 31 章写不动点证明时，这三条规则
就是全部引理——今天预演，届时引用。

### 29.10.3 无限格的预告：从可枚举到摘要

本章四个构造的输入都隐含"有限"：键集有限、事实全集
有限、分量格有限。第 37 章起这个前提松绑——区间格把
全体整数（无限）压成"区间端点对"（仍无限多，但每个
元素有限表示），无穷域上的格构造成为常态。预告三条
在本章已埋好伏笔的变化。**其一，高度可能无穷**：整数
链 (−∞,+∞) 方向上区间可以无限上升，"有限格必收敛"的
免费午餐取消，需要** widening**（加宽算子强制爬升封顶）
——14.4.7 的高度账目届时要从"常数预算"改写成"带悬崖
护栏的预算"。**其二，完备性要显式论证**（14.2.7 的
伏笔）：区间格靠 ±∞ 补边界。**其三，精度与成本的
调节旋钮出现**：有限格里 join 是唯一合并算子，无限格
上"join 多久、加宽多狠"成为设计参数。读者可以把本章
的四个构造当作"有限世界的完整工具箱"，第 37 章之后
的内容当作"工具箱在无限世界的改造记录"——构造定理
本身不变，变的是格元素的可表示性与运算的终止性。

### 29.10.4 本章的边界：构造了什么、没构造什么

收尾前划一条清晰的线。本章**构造了**：把已有格变成新格
的四条通用路径，及每条路径上 join/leq/eq/顶/底的自动
继承——"正确性随构造继承"是全章的中心命题。本章**没有
构造**：传递函数（第 28 章手写、第 30 章方程化）、求解
算法（第 31 章 worklist）、精度改进算子（第 37 章
refinement）。这条线的意义在于**责任划分**：域的构造
错误（join 不单调、eq 不规范）与分析的驱动错误（方程
写错、worklist 漏传播）是两类 bug，出现在不同层、用不同
手段排查——前者查构造参数与运算实现，后者查方程表与
传播逻辑。第 31 章调不动点 bug 时，第一件事就是把状态
表与方程表分开核对，用的正是今天划的这条线。

### 29.10.5 格论小词典：本书反复使用的十个词

收束本章前，把散落在四章里的术语集中界定一次，后面章节再
出现这些词时不再重复定义。**偏序**：自反、反对称、传递的
二元关系。**上界/下界**：u 满足 a ⊑ u（上界）；界不唯一。
**最小上界**：所有上界中最小的那个，唯一性由反对称性保证，
所以可以命名为 join。**顶/底**：全格的上、下界，存在性由
"有界格"假设给出。**链**：任意两元素可比的子集；链的长度
（严格跳数）就是格的**高度**，它决定从底出发最坏要走多少
层 join。**可分配**：join 与 meet 互相分配，集合格与链都
满足。**单调函数**：x ⊑ y 推出 f(x) ⊑ f(y)；第 30 章起的
全部传递函数都必须满足，否则不动点与 MOP 的对应关系破产。
**不动点**：f(x) = x 的点；从底迭代单调 f 收敛到最小不动
点。**对偶**：序反转后 join/meet、顶/底互换。十个词就是
本章理论装备的全部，其余概念（完备性、连续格、伽里略连接
——后者留给第 70 章）都是在有具体需求时才引入。

使用这本小词典时值得提醒一个汉语教材常见的歧义："底"有时
被讲成"信息最少"，而本书中 ⊥ 的首要身份是"矛盾/不可达"，
不是"知道得少"——"知道得少、什么都可能"对应的是顶。
⊥ ⊑ a 的读法是"矛盾可以推出任何承诺"（爆炸原理），而不是
"⊥ 比 a 少知道一些事实然后逐渐学全"。迭代从 ⊥ 起步的操作
含义是"第一轮之前假设没有任何点可达"，随着信息加入，点
被提升到具体事实；若两条路径给出互相矛盾的具体承诺，join
不是回到 ⊥，而是升到 ⊤——矛盾在合并处被"宽承诺"消解，
这与逻辑中"两个矛盾命题推出一切"是两套机制。把 ⊥ 与 ⊤
这两端的语义一次钉死，后面读区间格的 lo&gt;hi、常量格的
kind=0、IFDS 的零边集合时才不会混淆：它们都是 ⊥，都只
表示"此路不通"，从不表示"一无所知"。

## 29.12 形状即直觉：四个构造的 Hasse 图

## 29.12 形状即直觉：四个构造的 Hasse 图

格的许多性质不用计算就能"看出来"——前提是会画 Hasse 图。
Hasse 图把格元素画成点、把覆盖关系（a ⊑ b 且中间没有第三者）
画成线，序方向约定为自下而上。本节为四个构造各画一张图，
并给出"从形状读分析"的三条读法。图是 ASCII 的，精度有限，
但足够建立直觉；正式的图形版本是练习 14.1 的任务。

### 29.12.1 符号格：菱形是一切的原型

```
        ⊤
      / | \
     −  0  +
      \ | /
        ⊥
```

五元格的形状是**菱形加一条中柱**：底在下方、顶在上方、三个
原子（−、0、+）横排中间。三条读法从这里开始建立。**读法一：
高度看最长链。** ⊥ → − → ⊤ 有两级覆盖边，格高为 2（按
覆盖边计，与第 28 章同一口径）。第 31 章的
终止步数上界直接用这个数。**读法二：宽度看同层元素。**
中间一层的三个原子两两不可比——每多一个不可比元素，
合并信息时"变模糊"的方向就多一种。**读法三：join 看最低
公共祖先。** − 与 + 的最低公共祖先是 ⊤，所以 −⊔+=⊤；
⊥ 与任何元素的最低公共祖先就是那个元素，所以底是单位元。
菱形结构下"join=向上走找分叉点"永远成立，这正是格比一般
偏序好用的地方：合并永远有唯一的答案。

### 29.12.2 提升格：在菱形下面再垫一层

```
           ⊤
         / | \
        −  0  +
         \ | /
          ⊥A
           |
          ⊥new
```

提升在菱形正下方垫了一个新底，原来的底 ⊥A 退居次底。
图的形状立刻讲出两个语义事实。其一，从 ⊥new 出发到任何
"有信息"的状态都恰需一步——"第一次执行到这个点"是一次
跳变，不是渐变。其二，⊥new 与 ⊥A 之间有覆盖边而 −、0、+
之间没有——"未执行"与"矛盾"是可比的（矛盾强于未执行），
而"正"与"负"不可比。把第 32 章的常量格提前在脑子里画一下：
它是把菱形的三个原子换成"每个具体整数"，在下面垫矛盾底、
再整体提升——同样的垫层手法，届时可以直接认出。

### 29.12.3 积格：把菱形拉成网格

```
      (⊤,⊤)
     /  |  \
(−,⊤) (0,⊤) (+,⊤)   … 第一分量方向
     \  |  /
   （第二分量方向同理，共 3×3=9 个内部节点）
      (⊥,⊥)
```

积格的 Hasse 图是两个菱形的**张量拉伸**：每个方向各自的
菱形结构叠加成 3×3 的网格，再整体上下各加一层（分量顶底
的组合）。九个"中间"元素排成矩阵，(0,−) 与 (+,−) 不可比，
(0,−) 与 (0,+) 也不可比——不可比对的数量随分量数乘性增长。
这正是"多变量分析的精度衰减"在形状上的根源：每条路径
带来的信息是一个格点，两条路径合并后是它们的最低公共
祖先，路径越多、信息越靠近顶层。读网格图的要领是**按坐标
读**：每个点的 x 坐标是第一分量的精度，y 坐标是第二分量的；
合并两条信息 = 各坐标分别向上取分叉点。

### 29.12.4 映射格与幂集格：维度爆炸与"看不见的图"

固定两个变量键、值为符号格的映射格，Hasse 图与 14.12.3 的
网格同构——14.5.5 已说明二者是同一构造的两次呈现，图形
证据在此：同样的 25 个元素、同样的网格。三个变量时网格
变成 5×5×5=125 个元素的三维阵列，纸面画不下；十个变量
时约千万级——**幂律爆炸让 Hasse 图从辅助直觉变成不可能
的奢侈品**。这不是理论的失败，恰恰是理论的成功：我们
用"逐键归约"的构造定理替代了"看着图验证"，图的不可画
正是构造方法必要性的证明。

幂集格同理且更甚：n 个事实的幂集有 2ⁿ 个元素。四五个事实
（第 35 章的小例子）还能画成超立方体；第 33 章的到达定值
（定值数十个）只能靠定理。对这两类"看不见的图"，正确的
直觉替代品是**坐标读法**：映射格的状态 = 每键一个坐标，
幂集格的状态 = 每事实一位布尔值；合并 = 逐坐标/逐位独立
合并。脑中不再放整张图，只放"一个状态有哪几个坐标"——
这就是本章构造方法给读者的认知升级。

### 29.12.5 从形状读精度：三条通用读法

把本节三次演示的读法收拢成通用手册，供后续章节反复取用。
**第一，高度决定终止速度**：worklist 的迭代步数被
"程序点数 × 格高"封顶（第 31 章正式证明），图越高收敛
越慢——区间格的"高"是无限的，这是第 37 章一切麻烦的
图形本源。**第二，宽度决定精度下限**：不可比元素越多，
"两条路径合并"越容易跳到高层；菱形格的三个原子已经是
"经济实惠"的设计——用最少的不可比元素覆盖最大值的
多样性。**第三，对称性决定 reasoning 负担**：菱形上下
对称、网格逐维对称，对称格的公理验证与调试都便宜；
不对称的格（第 50 章的调用串格）每处不对称都要单独
论证。三句话合起来：**画不出图就画坐标，算不出高度就
查构造定理，认不出精度就看不可比对**——这是本章送给
第四篇的读图工具包。

### 29.12.6 高度与宽度的几何读法

Hasse 图还有两个几何量值得念出声，口径与第 28 章一致：
**高度**是最长严格上升链的覆盖边数，**宽度**是同层最大
元素数。符号格高度 2（⊥ ≺ − ≺ ⊤ 两级）、宽度 3（三个
原子并排一层）；幂集格高度 |U|（∅ ⊂ {a} ⊂ … 逐元素
上升）、宽度在最中层可达 C(|U|,|U|/2)——两类形状对应
两类分析的性能画像：符号类分析"迭代多、状态小"，集合类
分析"迭代少、状态大"。高度控制不动点迭代的深度预算
（14.4.7），画图时"从底到顶要爬几级"就是预算的可视化；
宽度控制单次迭代的状态体积。第 33 章估算分析成本时，
可以直接在 Hasse 图上把两个数读出来，不需要跑程序。

## 29.13 预装第 31 章的状态格：一次完整的合成演练

本章的构造怎样在真实分析里拼装？最经济的答案是提前把
第 31 章要用的状态格现在就组装出来，走一遍完整流程——
构造 → 验证 → 与手写版本对照。这段演练不引入新代码
（需要的都是本章已有的部件），纯在纸面上完成。

### 29.13.1 组装

目标域：sign1.tip（第 28 章的示例程序，main 有变量 x、y）
的"每点抽象环境"格。分三步。

第一步，确定键集：main 的形参为空、var 声明为 x、y，
键集 K = {x, y}。键集从程序文本静态取得——14.5.2 的
"键集固定"前提在这里兑现：symtab（第 14 章）在名字解析时
已经收集了这两份名单，第 31 章的求解器直接复用。

第二步，确定值格：每个变量的取值抽象为符号，值格取
signLatticeDomain()——五元格的 Lattice<int> 形态。

第三步，应用构造：`maps(sign, {"x","y"})` 得到状态格。
完整的 C++ 表达式就一行：

```cpp
auto state = maps(signLatticeDomain(), std::set<std::string>{"x", "y"});
```

### 29.13.2 检查继承来的性质

按 14.8.2 的三步走检查。结构不耦合：x 与 y 两个键互不
干扰——成立，构造定理保证。归约：状态格的 join 逐键委托
符号 join——成立，由 maps 的 joinF 直接给出。顶底：顶是
{x=⊤, y=⊤}，底是 {x=⊥, y=⊥}——maps 构造时预建。高度：
|K|·height(sign) = 2×2 = 4（覆盖边计）；元素个数 5²=25。
四项全部"免费"获得，没有一行新代码需要论证——这就是
14.1.1 说的"性质随构造传播"。

### 29.13.3 与第 28 章手写版本的对照

把纸面状态格与第 28 章的 SignEnv 并排放：SignEnv 的缺键

不可变更新在 25 个元素的小格上没有性能顾虑，而且它让
"环境是格的元素、传递函数是格上的函数"这条主线保持
纯净——第 31 章的 solve.cpp 会用 `out[target->name] = ...`
的方式在拷贝出来的新环境上写键，语义就是不可变更新。

三步组装、四项免费、一处等价对照——整个过程没有出现

那一章真正的新内容只有两件：把 CFG 的边变成方程的形状

### 29.13.5 手算一遍第 31 章的状态

预装的状态格别只看着——把 sign1.tip 的前两轮迭代在纸上
走一遍，验证它与第 31 章输出一致。初始：七个程序点全
⊥ 状态（x=⊥ y=⊥）。第一轮：入口点 1 状态 {⊥,⊥}；点 2
（循环头）取前驱 join，入口贡献 {⊥,⊥}，回边暂无，得
{⊥,⊥}；点 3 算 y=1 得 {y=+,x=⊥}；点 4 算 x=y+1 得
{y=+,x=+}；回边把 {+,+} 送回点 2，重算 join({⊥,⊥},
{+,+}) = {+,+}——状态变了，新一轮开始。第二轮：点 2
join({⊥,⊥},{+,+}) 仍是 {+,+}，点 3、4 重算不产生新值，
收敛。对照第 31 章输出：点 2/3/4 全是 x=+ y=+——一致。
手算确认了两件事：**合并确实发生在循环头**（映射格的
join 消费点），**⊥ 前驱在合并中让位**（⊥⊔+=+，不可达
路径不拖累结论）。第 31 章的 worklist 做的正是这个手算
的机械化，带着这两轮手算去看 worklist 代码，每个函数
都有对照。

## 29.14 常见疑问与误区

本节以问答形式收拢本章成稿过程中预判的高频疑问。问答
不是补充材料，而是正文的另一种组织——每个答案都依赖
前面的论证，建议顺序读。

**问一：格一定要有限吗？无限格能不能用？**
能，但有代价。本章四个构造全部保持"有限性继承"（有限
值格 + 有限键集 ⟹ 有限映射格），第 31 章的终止性证明
正建在有限性上。无限格（区间格、第 54 章的指针集合在
无限分配点下的情形）理论上完全合法——Tarski 不动点定理
只需要完备格，不需要有限——但**算法**不再保证终止，
第 37 章将用加宽技术把无限格"重新变有限"。一句话：
理论要完备性，算法要有限性，两头都要就得会加宽。

**问二：为什么 join 单独给一个函数，而不从 leq 算？**
数学上可以（x⊔y 是"所有上界的族"的最小元，可由 leq
定义），工程上不划算：直接实现往往更便宜（14.2.2 的
幂集例子），而且"由 leq 搜索上确界"需要全枚举，有限小格
勉强可行、大格不可行。反过来"由 join 定义 leq"
（x⊑y ⟺ x⊔y=y）倒是可行的备用方案——但要付出一次
join 加一次全等比较的代价，且要求 eq 可靠。本书直接给
两件套，让每个域按最自然的形状实现。

**问三：eq、leq、join 之间会不会实现得不一致？**
会，这是真实风险。比如 join 写对而 leq 写反一个分支，
单独测 join 对、单独测 leq 也"大致对"，交叉使用才露馅。
对策有三层：构造定理只要求分量一致（分量内一致即可）；
固定示例覆盖典型交叉情形；第 31 章 worklist 用 leq 判
"没变化"、用 join 取新值，两函数不一致时表现为不收敛
或来回震荡——端到端回归会抓到。练习 14.3 的检查器是
更主动的第四层。

**问四：为什么不用现成的图库/浮点格/第三方库？**
教学目标决定的。第三方库把"格"封装在 API 后面，读者
失去观察 join 表、缺键语义、表示唯一化这些关键决策的
机会——而它们恰是本书要教的内容。此外本章代码约百行，
自包含、零依赖、构建脚本零改动，工程上也是最便宜的选择。
读者日后使用 Soufflé/Doop 等工业级框架（第 71 章延伸
阅读有地图）时，会认出它们的域语言正是本章构造的
工程化放大。

**问五：signLatticeDomain 每次调用都新建一份格，浪费吗？**
SignLattice 无状态，三个 lambda 捕获的也是无状态对象，
新建的只是五个小字段的打包——分配在栈上、随构造函数
返回即弃。若介意，可改成函数级静态单例；但注意静态
单例引入初始化顺序问题（static initialization order
fiasco），教学代码宁可做十次廉价构造也不引入那类
隐蔽坑。这与 14.9.3 的"无状态设计"一脉相承：格便宜
的前提是域纯。

**问六：四个构造里哪个最重要？**
映射格——抽象环境是它的元素，第 31 章起每章都在用。
但重要性排序不改变学习顺序建议：从 lift 读起（最短、
边界最少），经 product（模板技巧集中地），到 maps
（语义最重），最后 powerset（最短但序方向的讨论最巧）。
出题人视角再补一句：这四者的组合练习（映射到积、
幂集的积、提升的映射）是理解"封闭性"的最快途径。

**问七：本章的 Lattice 能表达第 27 章的类型格吗？**
能表达其骨架，不必表达其全部。类型的项代数（TyVar、
TyPtr、TyFun…）配上"同一化"就构成代数结构，但它的
求解机制是合一而非单调迭代——第 12.9.9 已预告两类
输出哲学的差别。硬把类型塞进 Lattice<A> 会得到一个
谁也不会调用的 join。识别"哪类问题用哪类代数结构"
本身就是分析器设计能力的一部分：等式问题找合一，
偏序问题找格，二者交界处（子类型 + 继承）才是真正
的研究前沿。

**问八：演示为什么复用 sign1.tip 这个文件名？**
sign1.tip 在本章只是"一个能通过前端的程序"，内容
不再被分析——但沿用同名有两点实际好处：回归脚本对
每个示例目录约定"至少一个 programs/*.tip"，复用文件
免去为演示另造程序；且读者从第 28 章认识这个名字，
读到 14.7 不会误以为输出里有分析结果。文件名与输出
的"名不副实"已在 14.7 开头显式声明——教育性的复用
要配套显式声明，否则就是误导。

**问九：四个构造能不能互相嵌套，有没有深度上限？**
能嵌套，没有原则上限——构造定理只要求"输入是格"，而
构造的输出仍是格，于是封闭性自动给出任意深度的组合
（映射到幂集、积的映射、提升的积……）。实践上有两条
软上限。其一是**可读性**：三层以上的复合状态，打印与
手算都开始吃力，调试成本按层数指数感觉增长；其二是
**高度的膨胀**（14.4.7 的 Σhᵢ 口径）：嵌套让各级高度
相加、元素个数相乘，两层映射格嵌套就可能把预算推到
不可行。遇到"想嵌第三层"的冲动时，先问 14.10.1 的
反例信号问题——多数时候是维度不独立，应该换关系域
而不是继续堆构造。

**问十：⊥ 和 ⊤ 都有了，"部分未知"的中间值怎么办？**
这正是格与布尔思维的分水岭。布尔思维里只有"知道/不知道"
两态；格思维里中间值是**一等公民**——−、0、+ 都比 ⊤
精确、比 ⊥ 特殊，(0,−) 比 (⊤,⊤) 精确。构造的职责之一
就是把这些中间值系统性地造出来：积格的中间值是各分量
各糊各的，幂集格的中间值是部分事实集。第 31 章输出的
价值恰恰在中间值：一个点报出 x=+ 而非 ⊤，才说明分析
真的推出了东西。若发现自设计的域"经常跳到 ⊤"，先检查
是不是把不该合并的维度捆在了一个分量里（14.4.3 的
独立性），再检查合并点是不是过多。

**问十一：单调性和连续性是一回事吗？**
不是，本章刻意只立了单调性。单调：a⊑b ⟹ f(a)⊑f(b)。
连续（格论意义）：对任意上升链 a₀⊑a₁⊑… 有
f(⊔aᵢ)=⊔f(aᵢ)——比单调强得多，它保证"极限处的函数值
等于函数值的极限"。有限格里二者重合（链长有限，sup
总是链上某个元素），所以本章不区分。第 37 章进入无限
格后，单调函数的不动点迭代不再保证到达**最小**不动点
（可能爬过头），那时连续性（或它的工程替身——加宽的
"重链检测"）才成为必需。现在记下术语的位置，届时
不必重新搭脚手架。

**问十二：能不能只写 leq，join 用"取最大"的搜索实现？**
问二讨论过可行性，这里补充一个更隐蔽的坑：搜索式实现
要求"上界族的最小元"唯一存在，而**实现里的相等判断若
不规范**（14.2.5 的隐患），搜索可能返回两个"相等"表示
中的任意一个，让 join 表面上确定、实际上漂移——同一
输入在不同调用路径返回不同写法，输出对账逐字节失败。
这再次指向同一原则：表示唯一化优先于语义比较。规范
表示做在前面，任何"按语义找答案"的实现才可靠。

```cpp
// file: src/lattice.hpp
// 格的统一接口与四类通用构造（spa 第 4 章）。
// 一个"格"只需提供：顶/底两个边界、相等判定、偏序、最小上界。
// 提升(lift)、积(product)、映射(maps)、幂集(powerset)能把简单格组装成
// 程序状态所需的复合格——抽象环境就是"变量集合 → 值格"的映射格。
#pragma once

#include <functional>
#include <map>
#include <optional>
#include <set>
#include <tuple>
#include <utility>

namespace tip {

template <class A>
struct Lattice {
    A topV;
    A botV;
    std::function<bool(const A &, const A &)> eqF;
    std::function<bool(const A &, const A &)> leqF;
    std::function<A(const A &, const A &)> joinF;

    const A &top() const { return topV; }
    const A &bot() const { return botV; }
    bool eq(const A &a, const A &b) const { return eqF(a, b); }
    bool leq(const A &a, const A &b) const { return leqF(a, b); }
    A join(const A &a, const A &b) const { return joinF(a, b); }
};

// ---- 提升：给 A 加一个新底 ⊥=nullopt（"还没有值"） ----
template <class A>
Lattice<std::optional<A>> lift(const Lattice<A> &l) {
    using O = std::optional<A>;
    return Lattice<O>{
        O{l.top()}, O{std::nullopt},
        [](const O &a, const O &b) { return a == b; },
        [l](const O &a, const O &b) {
            if (!b.has_value()) return a == b;        // ⊥ 最小
            if (!a.has_value()) return true;
            return l.leq(*a, *b);
        },
        [l](const O &a, const O &b) {
            if (!a.has_value()) return b;
            if (!b.has_value()) return a;
            return O{l.join(*a, *b)};
        }};
}

// ---- 积：分量各自取 join，序为逐分量序 ----
template <class T, std::size_t... Is, class LTuple>
T tupleJoin(std::index_sequence<Is...>, const LTuple &lats, const T &a, const T &b) {
    return T{std::get<Is>(lats).join(std::get<Is>(a), std::get<Is>(b))...};
}
template <class T, std::size_t... Is, class LTuple>
bool tupleLeq(std::index_sequence<Is...>, const LTuple &lats, const T &a, const T &b) {
    return (... && std::get<Is>(lats).leq(std::get<Is>(a), std::get<Is>(b)));
}

template <class... As>
Lattice<std::tuple<As...>> product(const Lattice<As> &... ls) {
    using T = std::tuple<As...>;
    auto lats = std::make_tuple(ls...);
    T topT{ls.top()...};
    T botT{ls.bot()...};
    return Lattice<T>{
        std::move(topT), std::move(botT),
        [](const T &a, const T &b) { return a == b; },
        [lats](const T &a, const T &b) {
            return tupleLeq<T>(std::make_index_sequence<sizeof...(As)>{}, lats, a, b);
        },
        [lats](const T &a, const T &b) {
            return tupleJoin<T>(std::make_index_sequence<sizeof...(As)>{}, lats, a, b);
        }};
}

// ---- 映射：固定键集上逐点 join；键缺失按底处理 ----
template <class K, class V>
Lattice<std::map<K, V>> maps(const Lattice<V> &l, const std::set<K> &keys) {
    using M = std::map<K, V>;
    M topM, botM;
    for (const K &k : keys) {
        topM.emplace(k, l.top());
        botM.emplace(k, l.bot());
    }
    auto getOrBot = [&botM](const M &m, const K &k) {
        auto it = m.find(k);
        if (it != m.end()) return it->second;
        return botM.at(k);
    };
    return Lattice<M>{
        topM, botM,
        [](const M &a, const M &b) { return a == b; },
        [=](const M &a, const M &b) {
            for (const K &k : keys)
                if (!l.leq(getOrBot(a, k), getOrBot(b, k))) return false;
            return true;
        },
        [=](const M &a, const M &b) {
            M r;
            for (const K &k : keys) r.emplace(k, l.join(getOrBot(a, k), getOrBot(b, k)));
            return r;
        }};
}

// ---- 幂集：join=并，meet=交，序=包含；顶=给定全集（默认为空集） ----
template <class K>
Lattice<std::set<K>> powerset(const std::set<K> &universe = {}) {
    using S = std::set<K>;
    return Lattice<S>{
        universe, S{},
        [](const S &a, const S &b) { return a == b; },
        [](const S &a, const S &b) {
            for (const K &k : a)
                if (!b.count(k)) return false;
            return true;
        },
        [](const S &a, const S &b) {
            S r = a;
            r.insert(b.begin(), b.end());
            return r;
        }};
}
```

```cpp
//   ⊥（不可达/无信息） < −、0、+（三者互不可比） < ⊤（三者皆可能）

// 同一符号域的 Lattice<int> 形态：供通用构造（lift/product/maps/…）组装使用。
Lattice<int> signLatticeDomain();

// 编码：⊥=-2, −=-1, 0=0, +=1, ⊤=2。
// 用整数编码只是存储便利；序关系不是整数大小，join 必须查 join 表。
constexpr int SBOT = -2;
constexpr int SMINUS = -1;
constexpr int SZERO = 0;
constexpr int SPLUS = 1;
constexpr int STOP = 2;

std::string signShow(int s);

// 符号格的三要素：判定相等、偏序、最小上界。
// 后面所有单调框架的算法只依赖这三个操作（及 top/bot 边界）。
struct SignLattice {
    int top = STOP;
    int bot = SBOT;

    bool eq(int a, int b) const { return a == b; }
    bool leq(int a, int b) const;
    int join(int a, int b) const;
};

// 抽象算术：每个操作都对应整数运算"按符号分类"后的最小上界。
// 例如 +:(+,−)→⊤，因为正整数加负整数可能是 −、0 或 +。
int sAdd(int a, int b);
int sSub(int a, int b);
int sMul(int a, int b);
int sDiv(int a, int b);  // 除数符号含 0 时按 ⊥ 处理（具体程序在此抛错/中止）

// 比较运算在 TIP 中产生 0/1：抽象结果恒为 {0,+}=⊤（⊥ 仍吸收）。
int sCompare(int a, int b);
```

```cpp
// file: src/sign.cpp
#include "sign.hpp"

#include <array>

namespace tip {

Lattice<int> signLatticeDomain() {
    SignLattice s;
    return Lattice<int>{
        STOP, SBOT,
        [](int a, int b) { return a == b; },
        [=](int a, int b) { return s.leq(a, b); },
        [=](int a, int b) { return s.join(a, b); }};
}

std::string signShow(int s) {
    switch (s) {
        case SBOT: return "⊥";
        case SMINUS: return "−";
        case SZERO: return "0";
        case SPLUS: return "+";
        case STOP: return "⊤";
    }
    return "?";
}

bool SignLattice::leq(int a, int b) const {
    if (a == SBOT || b == STOP) return true;   // 底最小、顶最大
    if (b == SBOT || a == STOP) return a == b; // 越过底/顶的唯一可能是相等
    return a == b;                             // −、0、+ 三者互不可比
}

int SignLattice::join(int a, int b) const {
    if (a == b) return a;
    if (a == SBOT) return b;                   // ⊥ ⊔ x = x
    if (b == SBOT) return a;
    return STOP;                               // 其余组合（含 −/0/+ 两两）= ⊤
}

namespace {

// 加法符号表（行=左操作数 [−,0,+,⊤]，列=右操作数）。
constexpr std::array<std::array<int, 4>, 4> ADD_TABLE = {{
    //  −      0      +      ⊤
    {{SMINUS, SMINUS, STOP,  STOP }},  // −
    {{SMINUS, SZERO,  SPLUS, STOP }},  // 0
    {{STOP,   SPLUS,  SPLUS, STOP }},  // +
    {{STOP,   STOP,   STOP,  STOP }},  // ⊤
}};

// 乘法符号表：同号得 +，异号得 −，任何一边是 0 得 0。
constexpr std::array<std::array<int, 4>, 4> MUL_TABLE = {{
    //  −      0      +      ⊤
    {{SPLUS,  SZERO,  SMINUS, STOP }},  // −
    {{SZERO,  SZERO,  SZERO,  SZERO}},  // 0
    {{SMINUS, SZERO,  SPLUS,  STOP }},  // +
    {{STOP,   SZERO,  STOP,   STOP }},  // ⊤
}};

int idx(int s) { return s + 1; }  // −(-1)→0, 0→1, +(1)→2, ⊤(2)→3

}  // namespace

int sAdd(int a, int b) {
    if (a == SBOT || b == SBOT) return SBOT;
    return ADD_TABLE[idx(a)][idx(b)];
}

int sSub(int a, int b) {
    if (a == SBOT || b == SBOT) return SBOT;
    // a − b = a + (−b)：−、+ 互换，0/⊤ 不变。
    const int negB = b == SMINUS ? SPLUS : b == SPLUS ? SMINUS : b;
    return ADD_TABLE[idx(a)][idx(negB)];
}

int sMul(int a, int b) {
    if (a == SBOT || b == SBOT) return SBOT;
    return MUL_TABLE[idx(a)][idx(b)];
}

int sDiv(int a, int b) {
    if (a == SBOT || b == SBOT) return SBOT;
    if (b == SZERO) return SBOT;  // 除以确定的 0：该路径具体不可行（抛错中止）
    // 排除"除数可能为 0"的情形后，商的符号规律与乘法相同。
    if (b == STOP) {
        // 除数 ∈ {−,0,+}：0 排除，剩下 {−,+}；结果符号对 −/+ 分别讨论后取 join。
        return sAdd(sMul(a, SMINUS), sMul(a, SPLUS));
    }
    return MUL_TABLE[idx(a)][idx(b)];
}

int sCompare(int a, int b) {
    if (a == SBOT || b == SBOT) return SBOT;
    return STOP;  // 比较结果只可能是 0 或 1：{0,+} 在本格中即 ⊤
}

}  // namespace tip
```

```cpp
#include <vector>

#include "pretty.hpp"

namespace tip {

int signOfLiteral(int v) {
    if (v < 0) return SMINUS;
    if (v == 0) return SZERO;
    return SPLUS;
}

int evalExprSign(const Expr *e, const SignEnv &env) {
    if (const auto *x = dynamic_cast<const IntLit *>(e)) return signOfLiteral(x->v);
    if (const auto *x = dynamic_cast<const VarRef *>(e)) {
        auto it = env.find(x->name);
        return it == env.end() ? SBOT : it->second;
    }
    if (dynamic_cast<const InputE *>(e)) return STOP;  // 输入流的下一个整数符号未知
    if (const auto *x = dynamic_cast<const Binop *>(e)) {
        const int l = evalExprSign(x->l.get(), env);
        const int r = evalExprSign(x->r.get(), env);
        switch (x->op) {
            case BOp::Add: return sAdd(l, r);
            case BOp::Sub: return sSub(l, r);
            case BOp::Mul: return sMul(l, r);
            case BOp::Div: return sDiv(l, r);
            case BOp::Gt:
            case BOp::Eq: return sCompare(l, r);
        }
    }
    // 函数调用的返回值、指针/记录相关表达式：本章按"任意整数"保守处理，
    // 精确分析在过程间（第 49 章起）与指针篇（第 54 章）给出。
    (void)e;
    return STOP;
}

SignEnv entryEnv(const FunDecl &f) {
    SignEnv env;
    for (const std::string &p : f.params) env[p] = STOP;  // 调用方实参符号未知
    return env;
}

SignEnv joinEnv(const SignEnv &a, const SignEnv &b) {
    SignEnv r = a;
    SignLattice lat;
    for (const auto &[k, v] : b) {
        auto it = r.find(k);
        r[k] = it == r.end() ? v : lat.join(it->second, v);
    }
    return r;
}

SignEnv transferNode(const CfgNode &node, const SignEnv &in) {
    if (node.kind != CfgNode::Kind::Assign || !node.stmt) return in;
    const auto *a = dynamic_cast<const AssignS *>(node.stmt);
    const auto *target = dynamic_cast<const VarRef *>(a->target.get());
    if (!target) return in;  // *p / r.f 目标：第 54 章指针分析之前保持环境不变
    SignEnv out = in;
    out[target->name] = evalExprSign(a->value.get(), in);
    return out;
}

namespace {

std::map<int, std::vector<int>> predecessorMap(const FunCfg &f) {
    std::map<int, std::vector<int>> preds;
    for (const auto &[from, to] : f.edges) preds[to].push_back(from);
    return preds;
}

const char *nodeLabel(CfgNode::Kind kind) {
    switch (kind) {
        case CfgNode::Kind::Entry: return "entry";
        case CfgNode::Kind::Exit: return "exit";
        case CfgNode::Kind::Assign: return "assign";
        case CfgNode::Kind::Output: return "output";
        case CfgNode::Kind::Branch: return "branch";
        case CfgNode::Kind::Return: return "return";
    }
    return "?";
}

}  // namespace

PointEnv singlePass(const Cfg &cfg, const ProgramA &program) {
    PointEnv states;
    for (const FunCfg &fc : cfg.funs) {
        const FunDecl *decl = nullptr;
        for (const auto &f : program.funs)
            if (f->name == fc.name) decl = f.get();

        const auto preds = predecessorMap(fc);
        for (const auto &[id, node] : fc.nodes) {
            if (node.kind == CfgNode::Kind::Entry) {
                states[id] = entryEnv(*decl);  // 边界条件：参数 ⊤
                continue;
            }
            // 前驱尚未计算（典型是循环回边）时其状态按全 ⊥（空环境）处理。
            SignEnv in;
            auto pit = preds.find(id);
            if (pit != preds.end()) {
                for (int q : pit->second) {
                    auto qit = states.find(q);
                    if (qit != states.end()) in = joinEnv(in, qit->second);
                }
            }
            states[id] = transferNode(node, in);
        }
    }
    return states;
}

std::string printPointEnv(const Cfg &cfg, const ProgramA &program,
                          const PointEnv &states) {
    std::ostringstream out;
    for (const FunCfg &fc : cfg.funs) {
        out << "-- " << fc.name << " --\n";

        const FunDecl *decl = nullptr;  // 变量打印顺序：参数在前，局部变量在后
        for (const auto &f : program.funs)
            if (f->name == fc.name) decl = f.get();
        std::vector<std::string> names = decl->params;
        for (const std::string &v : decl->vars) names.push_back(v);

        for (const auto &[id, node] : fc.nodes) {
            out << "  " << id << ' ' << nodeLabel(node.kind);
            if (node.kind == CfgNode::Kind::Branch && node.stmt) {
                // 分支点只标注条件，避免把整个 if/while 体压成一行又折行。
                if (const auto *w = dynamic_cast<const WhileS *>(node.stmt))
                    out << "  while " << printExpr(w->cond.get());
                else if (const auto *i = dynamic_cast<const IfS *>(node.stmt))
                    out << "  if " << printExpr(i->cond.get());
            } else if (node.stmt) {
                out << "  " << printStmtLine(*node.stmt);
            }
            out << ':';

            const SignEnv &env = states.at(id);
            for (const std::string &k : names) {
                auto it = env.find(k);
                out << ' ' << k << '='
                    << signShow(it == env.end() ? SBOT : it->second);
            }
            out << '\n';
        }
    }
    return out.str();
}
```

```cpp
// 两遍构造：第一遍按 AST 先序给所有程序点分配固定编号；第二遍连边。

            FunCfg fc;
            cur_ = &fc;
            cur_->name = fun->name;
            nextId_ = 1;
            stmtId_.clear();

            const int entry = addNode(CfgNode::Kind::Entry);
            cur_->entry = entry;
            numberStmt(fun->body.get());
            const int retId = addNode(CfgNode::Kind::Return, fun->ret.get());
            const int exitId = addNode(CfgNode::Kind::Exit);
            cur_->exitNode = exitId;

            // 连边：语句构造返回它自己的入口点集合；空块没有节点，直接透传后继。
            std::vector<int> bodyEntries = wireStmt(fun->body.get(), {retId});
            if (bodyEntries.empty()) bodyEntries = {retId};
            link(entry, bodyEntries);
            link(retId, {exitId});

            // set 去重并排序：CFG 边不允许重复，输出顺序固定。
            std::set<std::pair<int, int>> uniq(cur_->edges.begin(), cur_->edges.end());
            cur_->edges.assign(uniq.begin(), uniq.end());
            cfg.funs.push_back(std::move(*cur_));
        }
        return cfg;
    }

private:
    const ProgramA &program_;
    FunCfg *cur_ = nullptr;
    int nextId_ = 1;
    std::map<const Stmt *, int> stmtId_;

    int addNode(CfgNode::Kind kind, const Stmt *stmt = nullptr) {
        const int id = nextId_++;
        cur_->nodes.emplace(id, CfgNode{id, kind, stmt});
        return id;
    }

    // ---- 第一遍：编号 ----
    void numberStmt(const Stmt *s) {
        if (const auto *b = dynamic_cast<const BlockS *>(s)) {
            for (const auto &x : b->ss) numberStmt(x.get());
            return;
        }
        if (const auto *x = dynamic_cast<const IfS *>(s)) {
            stmtId_[x] = addNode(CfgNode::Kind::Branch, x);
            numberStmt(x->then.get());
            numberStmt(x->els.get());
            return;
        }
        if (const auto *x = dynamic_cast<const WhileS *>(s)) {
            stmtId_[x] = addNode(CfgNode::Kind::Branch, x);
            numberStmt(x->body.get());
            return;
        }
        if (dynamic_cast<const AssignS *>(s)) {
            stmtId_[s] = addNode(CfgNode::Kind::Assign, s);
            return;
        }
        if (dynamic_cast<const OutputS *>(s)) {
            stmtId_[s] = addNode(CfgNode::Kind::Output, s);
        }
    }

    // ---- 第二遍：连边。返回进入该语句时首先到达的程序点集合 ----
    std::vector<int> wireStmt(const Stmt *s, const std::vector<int> &succ) {
        if (const auto *b = dynamic_cast<const BlockS *>(s)) {
            std::vector<int> cur = succ;
            for (auto it = b->ss.rbegin(); it != b->ss.rend(); ++it)
                cur = wireStmt(it->get(), cur);
            return cur;
        }
        if (const auto *x = dynamic_cast<const IfS *>(s)) {
            const int n = stmtId_[x];
            std::vector<int> targets = wireStmt(x->then.get(), succ);
            if (targets.empty()) targets = succ;
            if (x->els) {
                std::vector<int> e = wireStmt(x->els.get(), succ);
                if (e.empty()) e = succ;
                targets.insert(targets.end(), e.begin(), e.end());
            } else {
                targets.insert(targets.end(), succ.begin(), succ.end());
            }
            link(n, targets);
            return {n};
        }
        if (const auto *x = dynamic_cast<const WhileS *>(s)) {
            const int n = stmtId_[x];
            // 循环体执行完回到条件点；空体时条件点连一条自边（等于死循环）。
            std::vector<int> bodyEntries = wireStmt(x->body.get(), {n});
            if (bodyEntries.empty()) bodyEntries = {n};
            link(n, bodyEntries);
            link(n, succ);
            return {n};
        }
        const int n = stmtId_[s];
        link(n, succ);
        return {n};
    }

    void link(int from, const std::vector<int> &to) {
        for (int t : to) cur_->edges.emplace_back(from, t);
    }
};

const char *kindName(CfgNode::Kind kind) {
    switch (kind) {
        case CfgNode::Kind::Entry: return "entry";
        case CfgNode::Kind::Exit: return "exit";
        case CfgNode::Kind::Assign: return "assign";
        case CfgNode::Kind::Output: return "output";
        case CfgNode::Kind::Branch: return "branch";
        case CfgNode::Kind::Return: return "return";
    }
    return "?";
}

}  // namespace

Cfg buildCfg(const ProgramA &program) { return CfgBuilder(program).run(); }

std::string printCfg(const Cfg &cfg) {
    std::ostringstream out;
    for (const FunCfg &f : cfg.funs) {
        out << "== " << f.name << " ==\n";
        out << "nodes:\n";
        for (const auto &[id, node] : f.nodes) {
            out << "  " << id << ": " << kindName(node.kind);
            if (node.stmt) out << "  " << printStmtLine(*node.stmt);
            out << "\n";
        }
        out << "edges:\n";
        for (const auto &[a, b] : f.edges) out << "  " << a << " -> " << b << "\n";
    }
    return out.str();
}
```

```cpp
// file: src/ast.hpp
// AST 定义：AST 是去掉了括号、分号等语法噪音的程序结构。
// 接口自本章起冻结，后续所有分析（名字、CFG、类型、格……）都在此之上工作。
#pragma once

#include <memory>
#include <string>
#include <utility>
#include <vector>

namespace tip {

enum class BOp { Add, Sub, Mul, Div, Gt, Eq };

struct Expr {
    virtual ~Expr() = default;
};
struct IntLit : Expr {
    int v;
    explicit IntLit(int value) : v(value) {}
};
struct VarRef : Expr {
    std::string name;
    explicit VarRef(std::string n) : name(std::move(n)) {}
};
struct InputE : Expr {};
struct Binop : Expr {
    BOp op;
    std::unique_ptr<Expr> l, r;
    Binop(BOp o, std::unique_ptr<Expr> lhs, std::unique_ptr<Expr> rhs)
        : op(o), l(std::move(lhs)), r(std::move(rhs)) {}
};
struct CallE : Expr {
    std::unique_ptr<Expr> callee;
    std::vector<std::unique_ptr<Expr>> args;
    CallE(std::unique_ptr<Expr> fn, std::vector<std::unique_ptr<Expr>> as)
        : callee(std::move(fn)), args(std::move(as)) {}
};
struct Deref : Expr {
    std::unique_ptr<Expr> e;
    explicit Deref(std::unique_ptr<Expr> p) : e(std::move(p)) {}
};
struct AddrOf : Expr {                       // spa: & Id
    std::string name;
    explicit AddrOf(std::string n) : name(std::move(n)) {}
};
struct AllocE : Expr {
    std::unique_ptr<Expr> e;
    explicit AllocE(std::unique_ptr<Expr> init) : e(std::move(init)) {}
};
struct NullE : Expr {};
struct RecLit : Expr {
    std::vector<std::pair<std::string, std::unique_ptr<Expr>>> fields;
    explicit RecLit(std::vector<std::pair<std::string, std::unique_ptr<Expr>>> fs)
        : fields(std::move(fs)) {}
};
struct FieldA : Expr {
    std::unique_ptr<Expr> e;
    std::string field;
    FieldA(std::unique_ptr<Expr> record, std::string f)
        : e(std::move(record)), field(std::move(f)) {}
};

struct Stmt {
    virtual ~Stmt() = default;
};
// target 只会是 VarRef / FieldA / Deref，文法 lvalue 已限定。
struct AssignS : Stmt {
    std::unique_ptr<Expr> target, value;
    AssignS(std::unique_ptr<Expr> t, std::unique_ptr<Expr> v)
        : target(std::move(t)), value(std::move(v)) {}
};
struct OutputS : Stmt {
    std::unique_ptr<Expr> e;
    explicit OutputS(std::unique_ptr<Expr> x) : e(std::move(x)) {}
};
struct IfS : Stmt {
    std::unique_ptr<Expr> cond;
    std::unique_ptr<Stmt> then, els;
    IfS(std::unique_ptr<Expr> c, std::unique_ptr<Stmt> t, std::unique_ptr<Stmt> e)
        : cond(std::move(c)), then(std::move(t)), els(std::move(e)) {}
};
struct WhileS : Stmt {
    std::unique_ptr<Expr> cond;
    std::unique_ptr<Stmt> body;
    WhileS(std::unique_ptr<Expr> c, std::unique_ptr<Stmt> b)
        : cond(std::move(c)), body(std::move(b)) {}
};
struct BlockS : Stmt {
    std::vector<std::unique_ptr<Stmt>> ss;
    explicit BlockS(std::vector<std::unique_ptr<Stmt>> v) : ss(std::move(v)) {}
};
struct ReturnS : Stmt {
    std::unique_ptr<Expr> e;
    explicit ReturnS(std::unique_ptr<Expr> x) : e(std::move(x)) {}
};

struct FunDecl {
    std::string name;
    std::vector<std::string> params;
    std::vector<std::string> vars;
    std::unique_ptr<Stmt> body;
    std::unique_ptr<ReturnS> ret;
};

struct ProgramA {
    std::vector<std::unique_ptr<FunDecl>> funs;
};

}  // namespace tip
```

```cpp
// file: src/ast_build.cpp
#include "ast_build.hpp"

#include <utility>
#include <vector>

namespace tip {

std::unique_ptr<ProgramA> AstBuilder::build(TIPParser::ProgramContext *tree) {
    auto program = std::make_unique<ProgramA>();
    for (auto *fc : tree->function()) program->funs.push_back(buildFun(fc));
    return program;
}

std::unique_ptr<FunDecl> AstBuilder::buildFun(TIPParser::FunctionContext *ctx) {
    auto f = std::make_unique<FunDecl>();
    f->name = ctx->IDENT()->getText();
    if (ctx->params()) {
        for (auto *p : ctx->params()->IDENT()) f->params.push_back(p->getText());
    }
    if (ctx->varDecls()) {
        for (auto *v : ctx->varDecls()->IDENT()) f->vars.push_back(v->getText());
    }

    std::vector<std::unique_ptr<Stmt>> body;
    for (auto *sc : ctx->stmt()) body.push_back(buildStmt(sc));
    f->body = std::make_unique<BlockS>(std::move(body));

    f->ret = std::make_unique<ReturnS>(buildExpr(ctx->expr()));
    return f;
}

std::unique_ptr<Expr> AstBuilder::buildLvalue(TIPParser::LvalueContext *lv) {
    std::unique_ptr<Expr> base;
    std::string field;
    if (auto *d = dynamic_cast<TIPParser::DirectLvalueContext *>(lv)) {
        base = std::make_unique<VarRef>(d->IDENT(0)->getText());
        if (d->IDENT().size() == 2) field = d->IDENT(1)->getText();
    } else {
        auto *p = dynamic_cast<TIPParser::PointerLvalueContext *>(lv);
        base = std::make_unique<Deref>(buildExpr(p->expr()));
        if (p->IDENT()) field = p->IDENT()->getText();
    }
    if (!field.empty())
        return std::make_unique<FieldA>(std::move(base), std::move(field));
    return base;
}

std::unique_ptr<Expr> AstBuilder::buildExpr(TIPParser::ExprContext *ctx) {
    if (auto *c = dynamic_cast<TIPParser::IntExprContext *>(ctx))
        return std::make_unique<IntLit>(std::stoi(c->INT()->getText()));
    if (auto *c = dynamic_cast<TIPParser::VarExprContext *>(ctx))
        return std::make_unique<VarRef>(c->IDENT()->getText());
    if (dynamic_cast<TIPParser::InputExprContext *>(ctx))
        return std::make_unique<InputE>();
    if (dynamic_cast<TIPParser::NullExprContext *>(ctx))
        return std::make_unique<NullE>();
    if (auto *c = dynamic_cast<TIPParser::ParenExprContext *>(ctx))
        return buildExpr(c->expr());

    if (auto *c = dynamic_cast<TIPParser::AddExprContext *>(ctx)) {
        const BOp op = c->PLUS() ? BOp::Add : BOp::Sub;
        return std::make_unique<Binop>(op, buildExpr(c->expr(0)), buildExpr(c->expr(1)));
    }
    if (auto *c = dynamic_cast<TIPParser::MulExprContext *>(ctx)) {
        const BOp op = c->STAR() ? BOp::Mul : BOp::Div;
        return std::make_unique<Binop>(op, buildExpr(c->expr(0)), buildExpr(c->expr(1)));
    }
    if (auto *c = dynamic_cast<TIPParser::CmpExprContext *>(ctx)) {
        const BOp op = c->GT() ? BOp::Gt : BOp::Eq;
        return std::make_unique<Binop>(op, buildExpr(c->expr(0)), buildExpr(c->expr(1)));
    }
    if (auto *c = dynamic_cast<TIPParser::NegExprContext *>(ctx)) {
        // TIP 没有负数字面量 token，-E 即 0-E。
        return std::make_unique<Binop>(BOp::Sub, std::make_unique<IntLit>(0),
                                       buildExpr(c->expr()));
    }
    if (auto *c = dynamic_cast<TIPParser::CallExprContext *>(ctx)) {
        std::vector<std::unique_ptr<Expr>> args;
        if (c->args())
            for (auto *a : c->args()->expr()) args.push_back(buildExpr(a));
        return std::make_unique<CallE>(buildExpr(c->expr()), std::move(args));
    }
    if (auto *c = dynamic_cast<TIPParser::FieldExprContext *>(ctx))
        return std::make_unique<FieldA>(buildExpr(c->expr()), c->IDENT()->getText());
    if (auto *c = dynamic_cast<TIPParser::DerefExprContext *>(ctx))
        return std::make_unique<Deref>(buildExpr(c->expr()));
    if (auto *c = dynamic_cast<TIPParser::AddrExprContext *>(ctx))
        return std::make_unique<AddrOf>(c->IDENT()->getText());
    if (auto *c = dynamic_cast<TIPParser::AllocExprContext *>(ctx))
        return std::make_unique<AllocE>(buildExpr(c->expr()));
    if (auto *c = dynamic_cast<TIPParser::RecExprContext *>(ctx)) {
        std::vector<std::pair<std::string, std::unique_ptr<Expr>>> fields;
        for (auto *fc : c->field())
            fields.emplace_back(fc->IDENT()->getText(), buildExpr(fc->expr()));
        return std::make_unique<RecLit>(std::move(fields));
    }
    return nullptr;  // 解析成功时不会到达
}

std::unique_ptr<Stmt> AstBuilder::buildStmt(TIPParser::StmtContext *ctx) {
    if (auto *c = dynamic_cast<TIPParser::AssignStmtContext *>(ctx))
        return std::make_unique<AssignS>(buildLvalue(c->lvalue()), buildExpr(c->expr()));
    if (auto *c = dynamic_cast<TIPParser::OutputStmtContext *>(ctx))
        return std::make_unique<OutputS>(buildExpr(c->expr()));
    if (auto *c = dynamic_cast<TIPParser::IfStmtContext *>(ctx)) {
        std::unique_ptr<Stmt> els;
        if (c->stmt().size() == 2) els = buildStmt(c->stmt(1));
        return std::make_unique<IfS>(buildExpr(c->expr()), buildStmt(c->stmt(0)),
                                     std::move(els));
    }
    if (auto *c = dynamic_cast<TIPParser::WhileStmtContext *>(ctx))
        return std::make_unique<WhileS>(buildExpr(c->expr()), buildStmt(c->stmt()));
    if (auto *c = dynamic_cast<TIPParser::BlockStmtContext *>(ctx)) {
        std::vector<std::unique_ptr<Stmt>> ss;
        for (auto *sc : c->stmt()) ss.push_back(buildStmt(sc));
        return std::make_unique<BlockS>(std::move(ss));
    }
    return nullptr;  // 解析成功时不会到达
}

std::unique_ptr<ProgramA> buildAst(TIPParser::ProgramContext *tree) {
    return AstBuilder{}.build(tree);
}
```

```cpp
// file: src/pretty.cpp
#include "pretty.hpp"

#include <string>

namespace tip {

namespace {

// 表达式打印为前缀式：运算符与符号的对照表。
std::string exprText(const Expr *e) {
    if (const auto *x = dynamic_cast<const IntLit *>(e)) return std::to_string(x->v);
    if (const auto *x = dynamic_cast<const VarRef *>(e)) return x->name;
    if (dynamic_cast<const InputE *>(e)) return "input";
    if (dynamic_cast<const NullE *>(e)) return "null";

    if (const auto *x = dynamic_cast<const Binop *>(e)) {
        const char *sym = "+";
        switch (x->op) {
            case BOp::Add: sym = "+"; break;
            case BOp::Sub: sym = "-"; break;
            case BOp::Mul: sym = "*"; break;
            case BOp::Div: sym = "/"; break;
            case BOp::Gt: sym = ">"; break;
            case BOp::Eq: sym = "=="; break;
        }
        return "(" + std::string(sym) + " " + exprText(x->l.get()) + " " +
               exprText(x->r.get()) + ")";
    }
    if (const auto *x = dynamic_cast<const CallE *>(e)) {
        std::string s = "(call " + exprText(x->callee.get());
        for (const auto &a : x->args) s += " " + exprText(a.get());
        return s + ")";
    }
    if (const auto *x = dynamic_cast<const Deref *>(e))
        return "(* " + exprText(x->e.get()) + ")";
    if (const auto *x = dynamic_cast<const AddrOf *>(e)) return "(& " + x->name + ")";
    if (const auto *x = dynamic_cast<const AllocE *>(e))
        return "(alloc " + exprText(x->e.get()) + ")";
    if (const auto *x = dynamic_cast<const FieldA *>(e))
        return "(. " + exprText(x->e.get()) + " " + x->field + ")";
    if (const auto *x = dynamic_cast<const RecLit *>(e)) {
        std::string s = "{";
        for (size_t i = 0; i < x->fields.size(); ++i) {
            if (i) s += ", ";
            s += x->fields[i].first + ": " + exprText(x->fields[i].second.get());
        }
        return s + "}";
    }
    return "<unknown expr>";
}

std::string indent(int level) { return std::string(static_cast<size_t>(level) * 2, ' '); }

// 语句打印带缩进，一条语句一行（块内多行）。
void stmtText(const Stmt *s, int level, std::string &out) {
    if (const auto *x = dynamic_cast<const AssignS *>(s)) {
        out += indent(level) + exprText(x->target.get()) + " = " +
               exprText(x->value.get()) + " ;\n";
        return;
    }
    if (const auto *x = dynamic_cast<const OutputS *>(s)) {
        out += indent(level) + "output " + exprText(x->e.get()) + " ;\n";
        return;
    }
    if (const auto *x = dynamic_cast<const ReturnS *>(s)) {
        out += indent(level) + "return " + exprText(x->e.get()) + " ;\n";
        return;
    }
    if (const auto *x = dynamic_cast<const IfS *>(s)) {
        out += indent(level) + "if (" + exprText(x->cond.get()) + ")\n";
        stmtText(x->then.get(), level + 1, out);
        if (x->els) {
            out += indent(level) + "else\n";
            stmtText(x->els.get(), level + 1, out);
        }
        return;
    }
    if (const auto *x = dynamic_cast<const WhileS *>(s)) {
        out += indent(level) + "while (" + exprText(x->cond.get()) + ")\n";
        stmtText(x->body.get(), level + 1, out);
        return;
    }
    if (const auto *x = dynamic_cast<const BlockS *>(s)) {
        out += indent(level) + "{\n";
        for (const auto &st : x->ss) stmtText(st.get(), level + 1, out);
        out += indent(level) + "}\n";
        return;
    }
    out += indent(level) + "<unknown stmt>\n";
}

}  // namespace

std::string printExpr(const Expr *e) { return exprText(e); }

std::string printProgram(const ProgramA &program) {
    std::string out;
    for (const auto &f : program.funs) {
        std::string paramList;
        for (size_t i = 0; i < f->params.size(); ++i) {
            if (i) paramList += ",";
            paramList += f->params[i];
        }
        out += f->name + "(" + paramList + ") {\n";
        if (!f->vars.empty()) {
            out += indent(1) + "var ";
            for (size_t i = 0; i < f->vars.size(); ++i) {
                if (i) out += ",";
                out += f->vars[i];
            }
            out += " ;\n";
        }
        // 函数体是 BlockS；打印其内部语句而不是再嵌一层花括号。
        const auto *body = dynamic_cast<const BlockS *>(f->body.get());
        for (const auto &st : body->ss) stmtText(st.get(), 1, out);
        stmtText(f->ret.get(), 1, out);
        out += "}\n";
    }
    return out;
}

// 单行形式：CFG 节点标签等"节点旁边写一句话"的场合使用。
std::string printStmtLine(const Stmt &stmt) {
    std::string out;
    stmtText(&stmt, 0, out);
    if (!out.empty() && out.back() == '\n') out.pop_back();
    return out;
}
```

```cpp
// file: src/symtab.cpp
#include "symtab.hpp"

#include <utility>

namespace tip {

namespace {

// 解析器在遍历 AST 的同时完成绑定与诊断收集。
struct Resolver {
    Bindings bindings;
    Scope *current = nullptr;
    const FunDecl *owner = nullptr;

    void declare(const std::string &name, Symbol::Kind kind) {
        if (current->table.count(name)) {
            bindings.errors.push_back({"error: redeclared '" + name + "'"});
            return;  // 保留先声明者，后声明被忽略
        }
        current->table.emplace(name, Symbol{kind, name, owner});
    }

    void resolveExpr(const Expr *e) {
        if (const auto *x = dynamic_cast<const VarRef *>(e)) {
            const Symbol *s = current->lookup(x->name);
            if (!s) {
                bindings.errors.push_back({"error: undeclared '" + x->name + "'"});
            } else {
                bindings.uses[x] = s;
            }
            return;
        }
        if (const auto *x = dynamic_cast<const Binop *>(e)) {
            resolveExpr(x->l.get());
            resolveExpr(x->r.get());
            return;
        }
        if (const auto *x = dynamic_cast<const CallE *>(e)) {
            resolveExpr(x->callee.get());
            for (const auto &a : x->args) resolveExpr(a.get());
            return;
        }
        if (const auto *x = dynamic_cast<const Deref *>(e)) return resolveExpr(x->e.get());
        if (const auto *x = dynamic_cast<const AllocE *>(e)) return resolveExpr(x->e.get());
        if (const auto *x = dynamic_cast<const FieldA *>(e)) {
            resolveExpr(x->e.get());  // 字段名不是变量，无需解析
            return;
        }
        if (const auto *x = dynamic_cast<const RecLit *>(e)) {
            for (const auto &f : x->fields) resolveExpr(f.second.get());
            return;
        }
        // IntLit / InputE / AddrOf / NullE：无变量使用。
    }

    void resolveStmt(const Stmt *s) {
        if (const auto *x = dynamic_cast<const AssignS *>(s)) {
            resolveExpr(x->target.get());
            resolveExpr(x->value.get());
            return;
        }
        if (const auto *x = dynamic_cast<const OutputS *>(s)) return resolveExpr(x->e.get());
        if (const auto *x = dynamic_cast<const IfS *>(s)) {
            resolveExpr(x->cond.get());
            resolveStmt(x->then.get());
            if (x->els) resolveStmt(x->els.get());
            return;
        }
        if (const auto *x = dynamic_cast<const WhileS *>(s)) {
            resolveExpr(x->cond.get());
            resolveStmt(x->body.get());
            return;
        }
        if (const auto *x = dynamic_cast<const BlockS *>(s)) {
            for (const auto &st : x->ss) resolveStmt(st.get());
            return;
        }
        if (const auto *x = dynamic_cast<const ReturnS *>(s)) return resolveExpr(x->e.get());
    }
};

}  // namespace

const Symbol *Scope::lookup(const std::string &name) const {
    auto it = table.find(name);
    if (it != table.end()) return &it->second;
    return parent ? parent->lookup(name) : nullptr;
}

Bindings resolveNames(ProgramA &program) {
    Resolver resolver;
    resolver.bindings.global = Scope(nullptr);
    Scope *global = &resolver.bindings.global;

    // 第一遍：所有函数名进入全局作用域。
    for (const auto &f : program.funs) {
        if (global->table.count(f->name)) {
            resolver.bindings.errors.push_back({"error: redeclared '" + f->name + "'"});
            continue;
        }
        global->table.emplace(f->name, Symbol{Symbol::Fun, f->name, f.get()});
    }

    // 第二遍：每个函数开自己的作用域，父作用域是全局表；
    // 作用域所有权交给 Bindings，遍历结束后符号依然存活。
    for (const auto &f : program.funs) {
        auto functionScope = std::make_unique<Scope>(global);
        resolver.current = functionScope.get();
        resolver.owner = f.get();

        for (const std::string &p : f->params) resolver.declare(p, Symbol::Param);
        for (const std::string &v : f->vars) resolver.declare(v, Symbol::Local);

        resolver.resolveStmt(f->body.get());
        resolver.resolveStmt(f->ret.get());

        resolver.current = nullptr;
        resolver.bindings.scopes.push_back(std::move(functionScope));
    }
    return std::move(resolver.bindings);
}

}  // namespace tip
```

```cpp
// file: src/irgen.hpp
// LLVM IR 生成：把 AST 翻译成 LLVM Module。
// 本章只覆盖整数核心：算术、比较、input/output、if/while、直接函数调用；
// 指针、记录、间接调用在第 53 章以后扩展，遇到时直接报错。
#pragma once

#include <map>
#include <memory>
#include <string>

#include "llvm/IR/IRBuilder.h"
#include "llvm/IR/LLVMContext.h"
#include "llvm/IR/Module.h"

#include "ast.hpp"
#include "symtab.hpp"

namespace tip {

struct IRGen {
    // 三者均以 unique_ptr 持有：JIT 需要接管 Module 与 Context 的所有权。
    std::unique_ptr<llvm::LLVMContext> ctx;
    std::unique_ptr<llvm::Module> mod;
    std::unique_ptr<llvm::IRBuilder<>> b;

    const Bindings *bindings = nullptr;
    const FunDecl *cur = nullptr;
    std::map<const Symbol *, llvm::AllocaInst *> locals;

    IRGen();

    // 生成全部 TIP 函数 + C main（main 改名 tip_main）。
    // 结束后模块必须通过 verify。
    void gen(const ProgramA &program, const Bindings &resolved);

    llvm::Value *expr(const Expr *e);
    void stmt(const Stmt *s);

    bool verify() const;
    std::string dump() const;

  private:
    llvm::FunctionCallee rtInput_, rtOutput_;

    void genFun(const FunDecl *f, Scope *scope);
    void genWrapper(const FunDecl *mainFun);
};

}  // namespace tip
```

```cpp
// file: src/irgen.cpp
#include "irgen.hpp"

#include <stdexcept>
#include <utility>
#include <vector>

#include "llvm/IR/BasicBlock.h"
#include "llvm/IR/Constants.h"
#include "llvm/IR/DerivedTypes.h"
#include "llvm/IR/Function.h"
#include "llvm/IR/Verifier.h"
#include "llvm/Support/raw_ostream.h"

using namespace llvm;

namespace tip {

IRGen::IRGen()
    : ctx(std::make_unique<LLVMContext>()),
      mod(std::make_unique<Module>("tip", *ctx)),
      b(std::make_unique<IRBuilder<>>(*ctx)) {
    // 运行时入口先声明：input 无参返回 i32，output 吃一个 i32。
    auto *i32 = Type::getInt32Ty(*ctx);
    rtInput_ = mod->getOrInsertFunction(
        "tip_input", FunctionType::get(i32, false));
    rtOutput_ = mod->getOrInsertFunction(
        "tip_output", FunctionType::get(Type::getVoidTy(*ctx), {i32}, false));
}

namespace {

// TIP 的 main 改名 tip_main：真正的 @main 是我们生成的 C 入口。
std::string emitName(const std::string &name) {
    return name == "main" ? "tip_main" : name;
}

}  // namespace

void IRGen::gen(const ProgramA &program, const Bindings &resolved) {
    bindings = &resolved;

    // 先创建全部函数（含类型），函数体互相前向调用时也能查到声明。
    auto *i32 = Type::getInt32Ty(*ctx);
    for (const auto &f : program.funs) {
        std::vector<Type *> args(f->params.size(), i32);
        auto *ft = FunctionType::get(i32, args, false);
        Function::Create(ft, Function::ExternalLinkage,
                         emitName(f->name), *mod);
    }

    for (size_t i = 0; i < program.funs.size(); ++i) {
        const auto &f = program.funs[i];
        cur = f.get();
        genFun(f.get(), resolved.scopes[i].get());
    }

    const FunDecl *mainFun = nullptr;
    for (const auto &f : program.funs)
        if (f->name == "main") mainFun = f.get();
    if (!mainFun) throw std::runtime_error("program has no main");
    genWrapper(mainFun);
}

void IRGen::genFun(const FunDecl *f, Scope *scope) {
    auto *fn = llvm::cast<Function>(mod->getFunction(emitName(f->name)));
    auto *entry = BasicBlock::Create(*ctx, "entry", fn);
    b->SetInsertPoint(entry);

    // 形参：alloca 槽位 + 存入实参；var 局部：alloca + 零初始化。
    for (size_t j = 0; j < f->params.size(); ++j) {
        const Symbol *s = &scope->table.at(f->params[j]);
        auto *slot = b->CreateAlloca(b->getInt32Ty(), nullptr, f->params[j]);
        b->CreateStore(fn->getArg(j), slot);
        locals[s] = slot;
    }
    for (const std::string &v : f->vars) {
        const Symbol *s = &scope->table.at(v);
        auto *slot = b->CreateAlloca(b->getInt32Ty(), nullptr, v);
        b->CreateStore(b->getInt32(0), slot);
        locals[s] = slot;
    }

    stmt(f->body.get());
    b->CreateRet(expr(f->ret->e.get()));
}

Value *IRGen::expr(const Expr *e) {
    if (const auto *x = dynamic_cast<const IntLit *>(e))
        return ConstantInt::get(b->getInt32Ty(), x->v, true);

    if (const auto *x = dynamic_cast<const VarRef *>(e)) {
        const Symbol *s = bindings->uses.at(x);
        return b->CreateLoad(b->getInt32Ty(), locals.at(s), x->name);
    }

    if (dynamic_cast<const InputE *>(e))
        return b->CreateCall(rtInput_);

    if (const auto *x = dynamic_cast<const Binop *>(e)) {
        Value *l = expr(x->l.get());
        Value *r = expr(x->r.get());
        switch (x->op) {
            case BOp::Add: return b->CreateAdd(l, r);
            case BOp::Sub: return b->CreateSub(l, r);
            case BOp::Mul: return b->CreateMul(l, r);
            case BOp::Div: return b->CreateSDiv(l, r);
            case BOp::Gt: {
                Value *p = b->CreateICmpSGT(l, r);
                return b->CreateZExt(p, b->getInt32Ty());
            }
            case BOp::Eq: {
                Value *p = b->CreateICmpEQ(l, r);
                return b->CreateZExt(p, b->getInt32Ty());
            }
        }
    }

    if (const auto *x = dynamic_cast<const CallE *>(e)) {
        const auto *nameUse = dynamic_cast<const VarRef *>(x->callee.get());
        if (!nameUse)
            throw std::runtime_error("ch17: 间接调用留待第 53 章");
        const Symbol *s = bindings->uses.at(nameUse);
        if (s->kind != Symbol::Fun)
            throw std::runtime_error("ch17: 间接调用留待第 53 章");
        auto *callee = mod->getFunction(emitName(s->name));
        std::vector<Value *> args;
        for (const auto &a : x->args) args.push_back(expr(a.get()));
        return b->CreateCall(callee, args);
    }

    throw std::runtime_error("ch17: 指针与记录构造留待第 53 章");
}

void IRGen::stmt(const Stmt *s) {
    if (const auto *x = dynamic_cast<const AssignS *>(s)) {
        const auto *target = dynamic_cast<const VarRef *>(x->target.get());
        if (!target)
            throw std::runtime_error("ch17: 经指针/字段写入留待第 53 章");
        const Symbol *sym = bindings->uses.at(target);
        b->CreateStore(expr(x->value.get()), locals.at(sym));
        return;
    }

    if (const auto *x = dynamic_cast<const OutputS *>(s)) {
        b->CreateCall(rtOutput_, {expr(x->e.get())});
        return;
    }

    if (const auto *x = dynamic_cast<const IfS *>(s)) {
        Function *fn = b->GetInsertBlock()->getParent();
        auto *thenBB = BasicBlock::Create(*ctx, "then", fn);
        auto *elseBB = BasicBlock::Create(*ctx, "else", fn);
        auto *mergeBB = BasicBlock::Create(*ctx, "merge", fn);

        Value *cc = b->CreateICmpNE(expr(x->cond.get()), b->getInt32(0));
        b->CreateCondBr(cc, thenBB, elseBB);

        b->SetInsertPoint(thenBB);
        stmt(x->then.get());
        if (!b->GetInsertBlock()->getTerminator()) b->CreateBr(mergeBB);

        b->SetInsertPoint(elseBB);
        if (x->els) {
            stmt(x->els.get());
            if (!b->GetInsertBlock()->getTerminator()) b->CreateBr(mergeBB);
        } else {
            b->CreateBr(mergeBB);
        }
        b->SetInsertPoint(mergeBB);
        return;
    }

    if (const auto *x = dynamic_cast<const WhileS *>(s)) {
        Function *fn = b->GetInsertBlock()->getParent();
        auto *header = BasicBlock::Create(*ctx, "wh.cond", fn);
        auto *bodyBB = BasicBlock::Create(*ctx, "wh.body", fn);
        auto *exitBB = BasicBlock::Create(*ctx, "wh.exit", fn);

        b->CreateBr(header);
        b->SetInsertPoint(header);
        Value *cc = b->CreateICmpNE(expr(x->cond.get()), b->getInt32(0));
        b->CreateCondBr(cc, bodyBB, exitBB);

        b->SetInsertPoint(bodyBB);
        stmt(x->body.get());
        if (!b->GetInsertBlock()->getTerminator()) b->CreateBr(header);

        b->SetInsertPoint(exitBB);
        return;
    }

    if (const auto *x = dynamic_cast<const BlockS *>(s)) {
        for (const auto &st : x->ss) stmt(st.get());
        return;
    }

    if (const auto *x = dynamic_cast<const ReturnS *>(s))
        b->CreateRet(expr(x->e.get()));
}

void IRGen::genWrapper(const FunDecl *mainFun) {
    // C 入口：按 TIP main 形参数目读 input，再调用 tip_main。
    // 不命名为 main——MinGW 目标会向 main 注入对 CRT 符号 __main 的调用。
    auto *fn = Function::Create(FunctionType::get(b->getInt32Ty(), false),
                                Function::ExternalLinkage, "tip_entry", *mod);
    auto *entry = BasicBlock::Create(*ctx, "entry", fn);
    b->SetInsertPoint(entry);

    std::vector<Value *> args;
    for (size_t j = 0; j < mainFun->params.size(); ++j)
        args.push_back(b->CreateCall(rtInput_));
    Value *r = b->CreateCall(mod->getFunction("tip_main"), args);
    b->CreateRet(r);
}

bool IRGen::verify() const {
    std::string err;
    llvm::raw_string_ostream os(err);
    bool bad = llvm::verifyModule(*mod, &os);
    os.str();
    return !bad;
}

std::string IRGen::dump() const {
    std::string out;
    llvm::raw_string_ostream os(out);
    mod->print(os, nullptr);
    return os.str();
}

}  // namespace tip
```

```cpp
// file: src/jitrun.cpp
#include "jitrun.hpp"

#include <cstdint>
#include <stdexcept>

#include "llvm/ExecutionEngine/JITSymbol.h"
#include "llvm/ExecutionEngine/Orc/Core.h"
#include "llvm/ExecutionEngine/Orc/LLJIT.h"
#include "llvm/ExecutionEngine/Orc/ThreadSafeModule.h"
#include "llvm/Support/TargetSelect.h"

using llvm::StringRef;
using llvm::JITSymbolFlags;
using llvm::orc::ExecutorSymbolDef;
using llvm::JITTargetAddress;
using llvm::jitTargetAddressToFunction;
using llvm::pointerToJITTargetAddress;
using llvm::orc::LLJITBuilder;
using llvm::orc::SymbolMap;
using llvm::orc::ThreadSafeModule;
using llvm::orc::absoluteSymbols;

namespace tip {
namespace {

// JIT 模块通过这两个宿主函数与外界交换数据。
const std::vector<int> *inQueue = nullptr;
std::vector<int> *outQueue = nullptr;
size_t inPos = 0;

extern "C" int32_t tip_input() {
    if (inPos >= inQueue->size()) return 0;
    return (*inQueue)[inPos++];
}

extern "C" void tip_output(int32_t value) {
    outQueue->push_back(value);
}

void initNative() {
    // 进程内只初始化一次。
    static const bool ready = [] {
        llvm::InitializeNativeTarget();
        llvm::InitializeNativeTargetAsmPrinter();
        return true;
    }();
    (void)ready;
}

[[noreturn]] void fail(llvm::Error e) {
    std::string text = llvm::toString(std::move(e));
    throw std::runtime_error(text);
}

}  // namespace

std::vector<int> runJit(IRGen gen, const std::vector<int> &inputs) {
    initNative();
    std::vector<int> outputs;
    inQueue = &inputs;
    outQueue = &outputs;
    inPos = 0;

    auto jitOrErr = LLJITBuilder().create();
    if (!jitOrErr) fail(jitOrErr.takeError());
    auto jit = std::move(*jitOrErr);

    auto defineHost = [&](StringRef name, void *addr) {
        SymbolMap symbols;
        symbols[jit->mangleAndIntern(name)] = ExecutorSymbolDef(
            llvm::orc::ExecutorAddr::fromPtr(addr), JITSymbolFlags());
        if (llvm::Error e =
                jit->getMainJITDylib().define(absoluteSymbols(symbols)))
            fail(std::move(e));
    };
    defineHost("tip_input", reinterpret_cast<void *>(&tip_input));
    defineHost("tip_output", reinterpret_cast<void *>(&tip_output));

    ThreadSafeModule tsm(std::move(gen.mod), std::move(gen.ctx));
    if (llvm::Error e = jit->addIRModule(std::move(tsm)))
        fail(std::move(e));

    auto mainAddr = jit->lookup("tip_entry");
    if (!mainAddr) fail(mainAddr.takeError());
    auto *entry = jitTargetAddressToFunction<int (*)()>(mainAddr->getValue());
    entry();

    return outputs;
}

}  // namespace tip
```

## 29.16 工程注意点

原理之外，记录五条实现层面的注意点。它们都是上述原理的
直接推论，不是并列的经验清单。

1. **格运算必须是纯函数。** join/leq 不改输入、不改捕获的
   状态（14.5.4、14.6.4 的纪律）。第 31 章的 worklist
   依赖"运算无副作用"来保证单调上升的论证与现实一致；
   任何为性能引入的原地修改都必须重走一遍论证。

2. **构造参数决定格的一切边界语义。** maps 的键集、
   powerset 的全集都是构造时注入的运行时数据；同样的
   代码、不同的参数，是不同的格。调试时先核对构造参数
   （键集对不对、全集全不全），再看运算实现——边界错误
   的症状与运算错误的症状常常无法从输出区分。

3. **std::function 的开销边界要心里有数。** 每次格运算
   一次间接调用、构造时若干次闭包拷贝。教学规模（元素
   数十、迭代数百）完全无感；若用于百万点位的工业分析，
   换概念约束模板（14.2.4 方案丙）而不是给 std::function
   打补丁。接口形状不变，迁移成本可控。

4. **表示唯一化优先于语义比较。** 14.2.5 的原则：eq 过粗
   或过细都会传导到整个构造家族；凡是发现"一个抽象值
   两种写法"，先做规范化（如第 26 章 normalize、第 37 章
   区间规范形），不要在 eqF 里写特殊分支。规范化是
   表示层的义务，比较层保持老实。

5. **演示输出是对账基线，任何一行都不得"顺手改进"。**
   fixed join 例子的文本进入 expected/output.txt，成为
   回归对账的字节基线；改动措辞、调整键序、增删例子都
   会导致对账漂移。若确需更新演示，走"先改程序、再生成、
   人工核对、后提交"的既定协议——第 3 章以来从未例外。

## 29.17 小结

本章把第 28 章"一个具体域"的经验升格为"域的组合学"。

- 接口上，格 = 顶、底两个值 + eq、leq、join 三个运算；
  Lattice<A> 用值语义打包，格从此可以像数据一样传递与组合；
- 构造上，提升（加新底）、积（逐分量）、映射（固定键集
  逐点）、幂集（子集族）四条构造定理把"格变成格"，正确性
  论证随构造继承，新域只需三步归约；
- 语义上，抽象环境正式成为映射格的元素，事实集合成为
  幂集格的元素，may/must 的差别被识别为序方向的视角选择；
- 演示上，五行固定输出分别锚定新底的单位元行为、穿透
  构造的内部 join、逐分量的独立性、缺键按底的合并语义、
  并集的 may 语义；
- 工程上，纯函数纪律、构造参数意识、表示唯一化、对账
  基线不可动四条规矩立起。

至此，数据流分析的全部代数材料备齐：域可以组装了。第 30 章把符号传递函数套到 CFG 上，写出第一组单调方程——格
世界与控制流图世界正式接轨。
