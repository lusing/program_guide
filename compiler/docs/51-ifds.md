# 第 51 章　IFDS：在超级图上为"有效路径"制表

## 51.1 问题：跨函数的可达性，朴素做法为什么两头不讨好

### 51.1.1 从第 35 章留下的那条边界出发

第 35 章我们做了一件让编译器前端立刻变得有用的事：在单个函数的 CFG 上
跑"可能未初始化"分析。一个局部变量在 `var` 声明之后、第一次赋值之前
是没有值的；若程序在这条"还没赋值"的路径边上读取了它，实际运行就会
读到一个不确定的占位值。分析把"变量 v 可能未初始化"当成一种可以沿
CFG 边传播的事实：语句不读不写 v，事实原样通过；语句给 v 赋了值，事
实被杀死；语句在 v 尚无保证时读取 v，并把读到的值交给另一个变量 w，
w 就被"污染"，也带上同样的事实。这套 kill/generate 的口径在单个函数
内工作得很好，因为单函数 CFG 上每一条边的语义都就地可见：边的源头语
句做什么、目的语句做什么，分析器一眼就能看清。

但第 35 章的分析视野被一条明确的边界框住：它只在一个函数内部看问题。
遇到函数调用语句，过程内分析的选择通常是把它当成一条普通语句处理
——承认"这里发生了点什么"，却不跨进被调函数的门。对于整数运算之类
的语句这没问题；可一旦分析关心的事实会**经调用的大门进出**，装看不
见就会两头漏信息。本章要处理的正是这种情形：变量 v 在调用方可能尚未
初始化，它被当作实参传进了 `f`；`f` 内部直接读取了对应的形参，再把
读到的值赋给局部变量 r，最后把 r 返回；调用方把返回值赋给 b。一条
"可能未初始化"的事实沿着 调用方 → 实参 → 形参 → 局部变量 → 返回值
→ 左值 这条链条一路流过去，每一步都跨在过程的边界上。只看门内、不
看门外的过程内分析，对这条链条只能沉默。

第 49 章把视野第一次推过了过程边界：我们先构造调用图，知道谁调用谁，
再以"上下文不敏感"的方式把所有调用点的信息合并到一份被调函数状态
里。第 50 章又用调用串 k-CFA 给同一个函数造了多个按调用历史区分的
"分身"。这两章让我们有了处理过程间问题的语言和直觉。但它们的求解
仍有一个共同的、值得在章首说清的特征：分析的信息被压进"每个程序点
一个环境（或一个集合）"这样的缓存里，调用边与返回边只是把环境整体
地搬运、合并。当分析关心的问题本质上是一个**可达性**问题——"某种有
限的事实能否沿着某类受约束的路径到达这个点"——时，把整个环境搬来
搬去既浪费，又容易在调用点之间串味。IFDS 就是为这一类问题量身定做
的框架：它直接在"事实沿路径流动"的层次上制表，既不复制函数体，也不
合并来历，并且给出多项式时间的精确答案。

### 51.1.2 朴素做法一：把调用当普通语句——链条断在门口

先看第一种朴素做法，也是过程内分析面对调用时的默认选择：把调用语句
`b = f(a);` 当成一条不透明的语句，不走进 `f`。在"可能未初始化"的眼
里，这条语句读了什么、写了什么？只看调用方的语法，它读了实参 a、写
了左值 b。于是最保守的口径是：a 可能未初始化的事实到此为止，不跟进
`f`；b 则一律按"它的值来自一次结果未知的调用"处理——要么保守地认为
b 一定可能未初始化，要么干脆认为调用总会返回一个有定义的值。两种口径
都不对：前者误报（明明 `f(5)` 返回的是有定义的值，却警告 b），后者
漏报（明明 `f(a)` 把 a 的未定义状态带进了返回值，却不警告）。

问题的根子在于：调用语句的语义不是一条边，而是**一整段**被调函数的
执行。a 的状态经实参映射成形参的初始状态；这段状态在函数体内几经
kill/generate，最后映射成返回值；返回值再映射成 b 的新状态。不跨过
大门，就无法回答"b 到底会不会未初始化"，只能在"一律报"和"一律不
报"之间二选一，而正确答案恰恰取决于 `f` 内部的结构。把调用当黑盒，
等于在最需要信息的地方主动放弃信息。

### 51.1.3 朴素做法二：把被调函数的 CFG 内联进来

第二种朴素做法看起来更"彻底"：既然调用的语义是执行被调函数的函数
体，那就把它的 CFG 复制进调用点，像宏展开一样拼成一张大的过程内
CFG，然后用第 35 章的老办法在这张大图上跑。直觉上这似乎能抓住完整
链条。但它同时踩中三颗雷，而且一颗比一颗根本。

第一颗雷是**调用与返回的配对**被破坏。一张朴素拼接的大图只表达"从
调用点可以走到被调函数入口、从被调函数出口可以走回某个调用点之后"，
却不表达"从站点 A 进去的那次执行，必须回到站点 A 之后，而不能回到
站点 B 之后"。当 `f` 被两个调用点共享时，朴素大图上存在一条拼出来
的路径：从站点 A 进入 `f`，却从 `f` 的出口走回站点 B 之后。这条路径
在真实执行里不可能发生——一次调用的返回地址在进入时就固定了——但
在拼接图上它畅通无阻。分析于是把只可能在"A 的上下文"里出现的事实，
错误地送到了 B 的左值，站点之间互相"串味"。内联得越完整，这种错配
路径反而越多。

第二颗雷是**代码与状态的膨胀**。一个被 n 个调用点共享的函数，物理上
要复制 n 份 CFG；一个在循环里被调用的函数，展开在概念上要复制无数
份。第 50 章讨论内联展开时已经算过这笔账：膨胀不是实现细节上的小
麻烦，它直接改变分析的规模，使"为每个调用点复制一份"在真实程序上
不可行。

第三颗雷最根本：**递归无法内联**。`f` 的函数体里调用 `f`，把函数体
抄进调用点之后，里面还是一个 `f` 调用，需要再抄一份，如此往复，
永远拼不完。第 49 章的三色 DFS 判环就是为了在动手前先认出这种情形；
认出来之后，朴素内联只能回退到保守答案，前两颗雷也并未因此消失。

### 51.1.4 正确的路径观：调用与返回必须配对

两种朴素做法的失败指向同一个认识：过程间分析真正要算的，不是"事实
能否在任意拼接路径上到达"，而是"事实能否在**调用与返回正确配对**的
路径上到达"。我们需要给路径分一分类，把真实执行中可能出现的那一类
单独挑出来。

一条穿过超级图（51.2 节会形式化地画出它）的路径，若每次从某个调用
点进入被调函数，最后都恰好返回到**同一个**调用点之后，就称它是一条
**有效路径**（valid path，文献中也称 realizable path，"可实现路径"）。
关键就在"同一个"：站点 A 的进入只能由站点 A 的返回闭合，站点 B 亦然，
像配对的括号一样层层对应。真实程序的任意一次具体执行所走过的路径
必然是有效路径——硬件在 `call` 指令时压入返回地址、在 `ret` 时弹回
该地址，配对由调用约定强制保证。反过来，像 25.1.3 中"从 A 进、从 B
出"那种拼接路径就不是有效路径，真实执行走不出来。

于是"b 是否可能未初始化"这个问题的精确含义是：**是否存在一条从程序
入口到调用点之后的有效路径，使'未初始化'的事实沿它到达 b。** 对所
有有效路径求事实的并，文献中称为 **MOVP**（Merge-Over-Valid-Paths，
对有效路径求合并）。朴素内联大图上求的是"对所有拼接路径求并"，因为
混入了非有效路径，结果可能比 MOVP 更"脏"，产生串味误报；把调用当
黑盒则干脆漏掉了经大门流动的路径。两条朴素路线一个过近似、一个欠
近似，而我们要的是恰好等于 MOVP 的那个答案。

### 51.1.5 本章要落地的事实：MOVP 可以在多项式时间精确求得

MOVP 的定义看起来昂贵：有效路径可以无限多条（循环、递归），要从中
求并，似乎得枚举路径，而路径数随长度指数增长。IFDS 框架的核心贡献
就是证明并实现了这样一个事实：

> 当数据事实域 D 有限、且每条超级图边上的流函数对事实集合**可分配**
> （distributive）时，整个程序的 MOVP 可以在**多项式时间**内精确求得，
> 无需枚举路径，也无需复制函数体。

这里有两个关键词，本章会各用一节讲透。"有限事实域"使得"某事实是否
到达"是一个纯粹的可达性问题，状态空间有界（51.3 节）。"可分配"使得
对一**集合**事实的分析，可以分解为对一个个**单点**事实的分析再求并，
分解不失真（25.3.3–25.3.4 节）；而单点事实在超级图上的传播，恰好可
以用一张不断增长的"路径边"表加一张工作表来完成（51.5 节）。多项式
的来源正是：不追踪路径本身，只追踪"从哪个入口事实、能到哪个点的哪
个事实"这样的边，边的总数是有界的。

需要诚实预告一条边界：并非所有过程间问题都可分配。我们在第 32 章做
过的常量传播，其朴素流函数就不是可分配的（两个"非常量"合在一起仍
是"非常量"，但单点看各自可能携带不同常量），因此不能直接套进 IFDS
而不损失精度；那一类携带"值"的问题属于下一章 IDE 框架的地盘。本章
用"可能未初始化"做实例，正是因为它的事实只有"在/不在"、流函数天然
可分配，能让 IFDS 的机制以最干净的形状呈现。

### 51.1.6 与 spa 原书、与前面章节的对应

spa 第 24 章在讲完 TIP 上的经典数据流应用之后，用相当篇幅处理过程间
分析：先指出上下文不敏感做法的精度损失，再介绍 IFDS 这一通用框架。
IFDS 本身出自 Reps、Horwitz、Sagiv 1995 年的论文 "Precise Interprocedural
Dataflow Analysis via Graph Reachability"，标题里的 "graph reachability"
一词已点明思想——把过程间数据流问题归约为一个图上的可达性问题。本章
的形式化（25.2、51.3 节）与求解器（25.5、51.6 节）按这条线走：先
构造显式的超级图，再把分析表达为"路径边"这一图结构上的可达性制表。

与第 50 章的关系值得专门说一句。第 50 章的调用串 k-CFA 回答的是
"按怎样的调用历史给函数分身"；IFDS 的路径边制表回答的是"单点事实能
否沿有效路径到达"。两者都尊重调用—返回配对，但着力点不同：k-CFA 的
精度旋钮是上下文（记住多少历史），IFDS 的威力来自可分配性与路径边。
有趣的是，本章实现的 IFDS 在配对返回时天然做到了"返回只送回对应的
调用点"——它在可达性这一层面，比第 50 章 k=0 的上下文不敏感常量
传播更"认人"。25.5.3 节会讲清这是怎么由 incoming 表实现的，51.8 节
再把两个框架并排比较。这是贯穿全书的母题：格、引擎、传递函数、上下
文、路径边都是可独立替换的部件，而 IFDS 给出了其中"可达性"这一格的
经典解法。

### 51.1.8 三个朴素方案的代价，放在一起看

把 25.1.2 到 25.1.4 的三个方案放在同一把尺子下：方案一（调用当普
通语句）的图最小、跑得最快，但对一切跨过程事实失明，callf.tip 上
会漏掉全部四条真警告里的三条；方案二（内联展开）精度满分，图的代
价随内联深度翻倍，两层调用就把 main 复制四份，遇到递归直接没有有
限的图可建；方案三（给每个函数手动写摘要）介于两者之间，摘要写对
了精度就是 MOVP，写错了没有任何机器检查——它把最难的部分推给了
人。IFDS 的位置是把方案三的"摘要"自动化：制表机在运行中动态地为
每个（调用点, 事实）组合生成精确摘要，存在 incoming 表里，用完即
弃。人写的摘要是先验的、一次性的；制表机的摘要是后验的、按需的、
且由算法保证正确——这正是"框架"相对于"手工技巧"的本质区别。

## 51.2 超级图：把过程间结构显式画出来

### 51.2.1 先有单函数 CFG，再有跨函数的超级图

IFDS 的工作台不是第 16 章那种单函数 CFG，而是把程序中所有函数的 CFG
拼在一起、再补上三类跨函数边之后得到的一张大图，称为**超级图**
（supergraph，也称 interprocedural control-flow graph，过程间控制流图）。
先回顾单函数 CFG 的形状：每个函数有一个入口点（entry）和一个出口点
（exit），中间是带编号的程序点，每点挂一条语句（赋值、输出、分支）
或一个返回点，点与点之间是过程内的控制流边。循环在图上是环，分支
在图上是分叉。这一层第 16 章已经实现，本章直接复用 `cfg.cpp` 构造出
全部函数的 CFG，再在其上叠加过程间结构。

把"全局程序点"简称为**标号点**。单函数内节点号只在该函数唯一，
`f` 的节点 4 与 `main` 的节点 4 互不相干；因此一个标号点必须由一对
信息指定：

> **标号点 = （函数名，该函数内 CFG 节点号）。**

代码里它就是 `ifds.hpp` 中的类型别名：

```cpp
using PP = std::pair<std::string, int>;
```

这一行给标号点起了简短的名字
`PP`（program point）。后文凡写 `n`、`m`，指的都是某个 `PP`。本章
打印输出里形如 `node 6` 的警告，其实际标号点是 `(main,6)`；打印时省
略函数名只是因为该警告列在对应函数的小节之下。

### 51.2.2 文法先决定了"调用长什么样"

在画三类跨函数边之前，先看它们的语法来源。本章快照的 TIP 文法在
第 16 章的整数核心之上已经包含了函数调用：一个表达式后接括号与实参
序列就是调用，调用可以出现在任意表达式位置。完整文法如下。

```cpp
// file: TIP.g4
grammar TIP;

program    : function+ EOF ;
singleExpr : expr EOF ;
function   : IDENT LPAREN params? RPAREN LBRACE varDecls? stmt* RETURN expr SEMI RBRACE ;
params     : IDENT (COMMA IDENT)* ;
varDecls   : VAR IDENT (COMMA IDENT)* SEMI ;

stmt       : lvalue ASSIGN expr SEMI                # assignStmt
           | OUTPUT expr SEMI                      # outputStmt
           | IF LPAREN expr RPAREN stmt (ELSE stmt)? # ifStmt
           | WHILE LPAREN expr RPAREN stmt         # whileStmt
           | LBRACE stmt* RBRACE                   # blockStmt
           ;
lvalue     : IDENT (DOT IDENT)?                    # directLvalue
           | STAR expr (DOT IDENT)?                # pointerLvalue
           ;

expr       : expr LPAREN args? RPAREN              # callExpr
           | expr DOT IDENT                        # fieldExpr
           | STAR expr                             # derefExpr
           | AND IDENT                             # addrExpr
           | ALLOC expr                            # allocExpr
           | MINUS expr                            # negExpr
           | expr (STAR|DIV) expr                   # mulExpr
           | expr (PLUS|MINUS) expr                # addExpr
           | expr (GT|EQ) expr                     # cmpExpr
           | INT                                   # intExpr
           | IDENT                                 # varExpr
           | INPUT                                 # inputExpr
           | NULL                                  # nullExpr
           | LPAREN expr RPAREN                    # parenExpr
           | LBRACE field (COMMA field)* RBRACE    # recExpr
           ;
field      : IDENT COLON expr ;
args       : expr (COMMA expr)* ;

WS         : [ \t\r\n]+ -> skip ;
BLOCK_CMT  : '/*' .*? '*/' -> skip ;
LINE_CMT   : '//' ~[\r\n]* -> skip ;
INPUT      : 'input' ;
OUTPUT     : 'output' ;
IF         : 'if' ;
ELSE       : 'else' ;
WHILE      : 'while' ;
VAR        : 'var' ;
RETURN     : 'return' ;
ALLOC      : 'alloc' ;
NULL       : 'null' ;
IDENT      : [a-zA-Z_][a-zA-Z0-9_]* ;
INT        : [0-9]+ ;
ASSIGN     : '=' ;
EQ         : '==' ;
GT         : '>' ;
PLUS       : '+' ;
MINUS      : '-' ;
STAR       : '*' ;
AND        : '&' ;
DIV        : '/' ;
LPAREN     : '(' ; RPAREN : ')' ;
LBRACE     : '{' ; RBRACE : '}' ;
SEMI       : ';' ; COMMA : ',' ; DOT : '.' ; COLON : ':' ;
```

我们只关注与超级图有关的几条规则。`expr : expr LPAREN args? RPAREN
# callExpr` 说明被调方本身是一个表达式——本章只处理被调方是一个
名字（直接函数调用）的情形，文法也允许形如 `g(x)(y)` 的高阶形状，
那种"函数值"的问题是第 53 章 0-CFA 的主题。`function` 规则给出函数
名、形参表、局部变量声明、语句体与末尾的 `return` 表达式。值得注意
的是 TIP 的函数**必须**以 `return expr` 收尾，返回值是一个完整表达
式——这为后文"返回边如何把返回表达式读取的事实送回左值"提供了明
确的挂钩点。

为了让教学求解器能干净地处理调用，本章的两个演示程序都写成每个调
用独占一条赋值语句，形如 `b = f(a);`。文法允许的其他形状（如
`output f(1)`、`x = g(0)+1`）求解器不按调用专门处理，而是把它们当
普通语句：其内部经大门流动的事实不会被制表。51.8 节会讨论放开这一
限制需要补哪些工作。明确"本章识别哪一类调用"的代码是 `ifds.cpp` 里
的 `callInfoOf`，51.6 节会逐行走读；这里先记住它的口径：**赋值右端
恰好是一个被调方为名字的调用，且左值是一个简单变量。**

### 51.2.3 三类过程间边

现在在所有函数的 CFG 之上补三类跨函数边。它们一一对应一次真实调用
在运行时的三个侧面，也是 IFDS 流函数要分别处理的三种跳转。

**第一类：调用边（call edge）。** 从调用点 `n`（调用方函数内挂着
`b = f(...)` 的那个点）连到被调函数 `f` 的入口点。它表达"控制在调用
点跳进被调函数"。调用边上发生的关键映射是**实参 → 形参**：第 i 个
实参表达式所携带的事实，映射成 `f` 的第 i 个形参的初始事实。此外
还有一个与具体变量无关的"零事实"（51.3 节定义）也经调用边进入，它
是可达性的载体。在我们的代码里这一边由 `callFlow` 实现，25.6.4 节
展开。

**第二类：调用-返回边（call-to-return edge）。** 从调用点 `n` 直接
连到它在调用方函数内的正常后继点 `m`（即 `f` 返回后控制真正落回的
那个点），完全不经过 `f` 的内部。它表达"与这次调用无关的局部信息，
在调用期间保持不变，绕过被调函数直接到达返回点"。为什么需要这样一
条看似"作弊"的边？因为调用方的局部变量中，除了左值 b 之外，其余变
量的值在调用前后不受 `f` 影响（TIP 没有按引用传参，形参是实参的绑
定副本）；这些事实必须有一条路径从 `n` 走到 `m`，而它们既不该进入
`f`（进去反而会与 `f` 的局部事实混淆），也不该被丢弃。于是让它们
沿这条短路"绕过"。唯独左值 b 不在此列：b 的新值要由 `f` 的返回给
出，所以调用-返回边上 b 的旧事实被**杀死**。代码中对应
`callToReturnFlow`。

**第三类：返回边（return edge）。** 从被调函数 `f` 的出口点连回调
用点的正常后继点 `m`。它表达"`f` 执行完毕、控制带着返回值回到调用
方"。返回边上的关键映射是**返回表达式 → 左值**：`f` 末尾 `return r`
中的 r 所携带的事实，映射成左值 b 的新事实。这一边与调用边必须配对
——25.2.4 小节马上强调——代码中由 `returnFlow` 配合一张 incoming
表实现，是本章最微妙的部分。

下图用文字勾勒一个调用点周围的三种跳转，箭头标签给出事实映射：

```text
        调用方局部事实(除 b 外)
   n ─────────call-to-return────────► m   (b 在 n 的旧事实被杀)
   │                                 ▲
   │ call: 实参 i → 形参 i            │ return: 返回表达式 → b
   ▼                                 │
 f 入口 ──► f 函数体 ──► f 出口 ──────┘
```

注意右边返回边的终点与调用-返回边的终点是**同一个**点 `m`：两条路
在 `m` 汇合，前者带来与调用无关的、绕过的局部事实，后者带来经被调
函数计算出的左值新事实。两者在 `m` 处求并，构成返回点完整的事实集。

### 51.2.4 配对是边的灵魂：返回只回对应调用点

超级图之所以不是"把函数 CFG 随便拼起来"，全在返回边与调用边的配对
纪律上。设想 `f` 被两个调用点共享：调用方函数里站点 `n_A` 是
`a = f(...)`，站点 `n_B` 是 `b = f(...)`，两者的正常后继分别是 `m_A`、
`m_B`。`f` 只有一份函数体、一个出口。若朴素地把 `f` 出口连到**所有**
后继点，图上就出现"从 `n_A` 进、走到 `m_B`"的路径——这正是 25.1.3
说的串味。超级图必须额外记住：经 `n_A` 进入 `f` 的那次（假想）执行，
其返回边只许落到 `m_A`；经 `n_B` 进入的，只许落到 `m_B`。

难点在于 `f` 的出口只有一个点，图的边上怎么记住"我是从哪个站点进来
的"？IFDS 不靠给函数造分身（那是第 50 章的路线），而是把配对信息
下放到**路径边**与一张 **incoming 表**里：每当一条事实经调用边从站点
`n` 进入 `f`，就在 incoming 表中记下"`f` 入口的这条事实，来自站点 `n`
处的某条路径边"。日后 `f` 出口处若有一条路径边带着相应事实，就按表
查回它来自哪些站点，只向那些站点的后继点发返回边。这样，从 `n_A`
进入的事实在出口处只会被送回 `m_A`，从 `n_B` 进入的只回 `m_B`，即便
它们流经的是同一个出口点。25.5.3 节会把这张表的结构和操作讲透，
25.6.5 节再对应到代码。先记住这个结论：**配对信息由 incoming 表承载，
返回边不是静态连死的，而是在制表过程中按表动态生成的。**

### 51.2.5 路径的三分类

有了超级图，可以严格地给路径分类。这里的"路径"指从某标号点出发、
沿超级图的边（含过程内边与三类过程间边）走到另一标号点的任意边序
列。我们区分三类：

- **路径（path）**：任意边序列，不管调用与返回如何配对。这是最宽的
  一类，包含"从 A 进、从 B 出"这种真实执行走不出来的拼法。若在这一
  类上求事实的并（MOP，Merge-Over-Paths），可能因混入伪路径而过度
  近似，产生串味误报。
- **有效路径（valid / realizable path）**：每个调用边都有一个与之同
  站点的返回边配对闭合，像括号一样正确嵌套。真实执行只走有效路径，
  所以 MOVP 才是我们想要的精确答案。
- **下行有效路径（same-level valid path，也常称 same-context path）**：
  一种更强的有效路径——调用边与返回边不仅配对，而且整体"进出平衡"，
  路径结束时调用栈深度与开始时相同（没有悬而未返的调用）。它对应
  "一次完整的、已经返回到调用方的执行"。

本章的路径边，其名字里的"路径"特指一种**下行有效**的片段：从某个
函数入口点出发、沿该函数的过程内边（其间可以调用别的函数并完整返回）
走到该函数内某个点，且调用—返回全程配对。25.5.1 节形式化路径边时
会给出它的精确形状。正是把"配对"这一约束内化到路径边的定义与传播
规则里，IFDS 才能在不显式枚举路径的情况下，只统计有效路径上的事
实——这是整个框架的枢纽。

## 51.3 形式化：事实域、流函数、可分配性

### 51.3.1 数据事实域 D 与零事实 0

IFDS 的第一层形式化是**事实**。本章分析回答的问题是"某个变量是否可
能未初始化"，因此一个最自然的事实就是一个变量名 v，含义为"到达当前
点时，v 可能尚未初始化"。把程序中全部变量名收集起来，得到一个有限
集合，记作 D。有限性在这里是结构性的、无需假设：TIP 程序的变量由
形参与 `var` 声明给出，个数在编译期固定。可达性问题的状态空间因此
有界——每个点上"哪些事实到达"至多有 2^|D| 种可能，虽随变量数指数，
但对单点事实的传播却是线性的，这正是可分配性要利用的地方。

光有变量名还缺一块拼图。考虑一条不携带任何"污点"、但程序确实会走
到的路径：我们仍需要某种东西表达"这个点是可达的"，并让它在调用、
生成等场合充当源头。为此引入一个特殊的**零事实**，记作 **0**（zero
fact，文献中有时记作 Λ 或 ⊥，但它不是格意义上的最小元，而是一个独立
的、恒真的事实）。0 的含义可以理解为"一条空事实"或"可达性本身"：
它在每个函数入口处被引入，沿每条边原样传播，任何真实可达的点上都有
0。它的两个用途会马上显现：一是作为调用边、返回边上始终通行的"载
体"，使"该调用确实发生"有事实为证；二是作为生成新事实的源头——
`x = 3` 这类语句不依赖任何污点，它生成"x 已初始化（即 x 的污点不存
在）"这一信息时，是在 0 之上生成，而不必要求某个变量事实到达。

代码中事实用 `ifds.hpp` 里的 `Fact` 表示：一个布尔位 `zero` 区分零事
实与变量事实，变量事实再带一个名字。25.6.2 节嵌入整份 `ifds.hpp` 时
会逐字段讲解；这里先记住两个构造：`fZero()` 给出 0，`fName(v)` 给出
变量 v 的事实。把 0 与变量名合起来，IFDS 流函数实际工作的定义域是
**D₀ = D ∪ {0}**。

### 51.3.2 流函数：一条边上的事实映射

超级图的每一类边都带一个**流函数**（flow function），它描述"沿这条
边，入口处的一个事实变成出口处的哪些事实"。注意是"一个事实 → 事实
的集合"，因为一条边可能同时杀死、保留、生成事实。形式化地，一条从
标号点 n 到 m 的边（按边的种类不同）配备

> f_(n,m) : D₀ → 2^{D₀}。

例如赋值 `x = e` 所在的过程内边，对输入事实 d 的行为是三件事的组合：
若 d 不是 x，d 存活（保留）；若 d 被 e 读取，则生成 x 的事实（因为 x
拿到了 e 的值，若 e 读的变量可能未初始化，x 也可能未初始化）；若 d
正是 x 的旧事实，则被杀死（赋值之后 x 有了新值）。若输入是 0，则
输出仍含 0，并在 e 不依赖污点时由 0 生成"x 已定义"——体现在事实集
上就是：不把 x 的污点事实放进去。本章把这套行为实现成函数
`normalFlow`。

为什么流函数以**单点**事实为输入，而不是直接吃"当前点的事实集合"？
这是 IFDS 最关键的设计选择，也是它能多项式求解的根由。对集合 S 的
行为 F(S) 不是另行定义的，而由单点行为逐点求并得到：

> **F(S) = ⨆_{d ∈ S} f(d) = ∪_{d ∈ S} f(d)。**

（当 S 含 0 时把 0 也计入，即 F(S)=∪_{d∈S∪{0}} f(d)。）也就是说，
框架从不直接处理"一捆事实"，它只在一个个单点事实上调用流函数，再把
结果并起来。这样，每条单点事实的传播轨迹彼此独立、可以分别制表。下
一小节给出这个分解不失真所需的条件。

### 51.3.3 可分配性：定义与直觉

把"对集合的行为"定义成"单点行为的并"，对任意 f 都能照写，但它未必
等于我们直觉上"把 f 直接作用于集合"的结果。两者相等所需的性质就是
**可分配性**（distributivity）：

> **f(A ∪ B) = f(A) ∪ f(B)**，对一切事实子集 A、B 成立。

满足可分配性时，先把集合并起来再过 f，与先分别过 f 再并结果，两种
做法完全等价。于是"在一个带着整捆事实的点上沿边传播"这件事，可以
被毫无损失地拆成"对捆中的每一个事实分别传播、再求并"。这正是 IFDS
需要的许可证：它允许框架把全部精力放在单点事实上，让每条事实独立地
沿超级图流动，而集合结论自动由并集恢复。

直觉上，可分配性说的是"**事实之间没有协同作用**"：一个事实能否通过
某条边、通过后变成什么，只取决于它自己，不因为"旁边恰好还有另一个
事实"而改变。对"可能未初始化"而言，这一点天然成立——v 是否可能未
初始化，只与 v 的定值历史有关，和 w 是否也未初始化毫无关系；赋值
`x = v` 读取 v 后生成 x 的事实，不会因为 w 也在边上就多生成或少生成
什么。kill/generate 这类"按变量名逐个处理"的流函数，本质上都是可分
配的。

### 51.3.4 证明思路：分解为什么不失真

这里给出可分配性使分解成立的论证骨架，它也是 IFDS 正确性证明的一
块基石，25.5.6 节会把它嵌进完整的归纳里。

设某标号点 n 上真正到达的事实集合是 S（我们要算的是 S 沿边到 m 后
的结果）。框架的做法是计算 ∪_{d∈S} f(d)。需要证明它等于"整体地把 n
到 m 的传递作用施加于 S"的结果 T。

**第一步：基例。** 若 S 为空集，两边都为空；若 S 为单点 {d}，由定义
两边都是 f(d)，相等。

**第二步：归纳。** 若 S = A ∪ B，按归纳假设对 A、B 分别有"整体作用
结果 = ∪_{d∈A} f(d)"与"= ∪_{d∈B} f(d)"。整体作用满足可分配性，故其
对 A∪B 的结果等于对 A 的结果 ∪ 对 B 的结果（这里正是使用 f(A∪B)=
f(A)∪f(B) 的地方），即 ∪_{d∈A} f(d) ∪ ∪_{d∈B} f(d) = ∪_{d∈S} f(d)。
于是分解不失真。

**第三步：有限性闭合。** S 是有限集（D 有限），所以这一归纳在有限
步内完成；不存在"无限个单点"导致分解发散的情形。

这三步的价值在于把"对集合的数据流"彻底归约为"对单点的图可达性"：
单点事实 d 能否沿有效路径到达某点，是一个纯粹的图上可达性问题，可
以用路径边表在多项式时间内回答；集合答案则由这些单点答案的并恢复。
若不可分配，第二步那个等式破裂，分解会失真——要么漏掉只有在"事实
协同出现"时才产生的信息（欠近似），要么框架的单点并集与真实整体作
用不符（结论不再等于 MOVP）。下一小节用一个大家熟悉的例子说明这种
破裂确实会发生。

### 51.3.5 反例：为什么常量传播不能直接套 IFDS

第 32 章做过常量传播：每个变量在每点被映射为"某常量 c"或"非常量
⊤"。它的朴素流函数就**不是**可分配的。考虑语句 `x = y + z`，并设想
两个独立到达的事实：单点地看 y=1、z=2（若框架能分别携带"y 是 1"和
"z 是 2"），合起来本应得到 x=3；但若把 y=1 与"z 非常量（⊤）"合并
携带，则 x=⊤。问题在于"x 是不是常量、是哪个常量"依赖于 y、z 两个值
的**协同**，而不能拆成"只看 y 的贡献 ∪ 只看 z 的贡献"——常量域上没
有与"并"相容的分解：1 ⊔ ⊤ = ⊤，信息在合并时不可逆地丢失。用 25.3.3
的话说，常量事实之间存在协同作用，违反了"一个事实的通过只取决于它
自己"。

这不是要否认可分配性，而是要划清 IFDS 的地界：它处理"事实的在/不
在"彼此独立的问题（未初始化、可达定义、指针别名的某些表述等），对
需要在事实上携带并组合**值**的问题，朴素的 IFDS 表达不了。下一章的
IDE 框架正是为此而生——它让每条路径边携带一个"边函数"，把值的映射
（而不仅是事实的有无）也纳入制表，代价是要处理函数的复合与规范化。
本章用"可能未初始化"，让自己稳稳压在可分配的一侧，IFDS 的机制因此
能以最纯粹的形状运行并给出精确的 MOVP。

### 51.3.6 本章四组流函数一览

最后把 25.2.3 的三类边与流函数对应起来，作为 51.6 节代码走读的索
引。本章实现四个流函数，全部以单点事实为输入、返回事实集合：

- `normalFlow`：普通过程内边。赋值非左值事实存活，读取的变量生成左
  值事实，旧左值事实被杀；0 恒等通过。
- `callFlow`：调用边。第 i 个实参读取的变量事实映射到第 i 个形参；0
  映射到 0。
- `callToReturnFlow`：调用-返回边。除左值外的事实原样绕过；左值在调
  用点的旧事实被杀；0 通过。
- `returnFlow`：返回边。返回表达式读取的变量事实映射到左值；0 映射
  到 0。

这四个函数都只在"单个变量名"的粒度上做 kill/generate，故按 25.3.3
节的判据它们都是可分配的。25.6.4–25.6.5 节会把每个函数的代码逐行嵌
入并讲解，先在这里建立它们各自承担的语义角色。

### 51.3.7 分配律的两个手工验证

定义读起来抽象，用两个小计算把它落到地上。第一个验证 kill/gen 型
流函数的分配性。设语句 s 为 `x = y`，事实集合 S = {y, z}。按集合语
义算：s 把 x 的事实杀掉、把 y 的事实复制给 x，F(S) = {z, x}。按分
解语义算：f(y) = {x}（y 被读取，生成 x；y 自身不是 x，存活——但
y 被复制后集合里是 x 不是 y，注意 `x = y` 之后谈论 y 的事实已经
无意义，输出只有 x），f(z) = {z}，f(0) = {0}。并起来 {x, z, 0}，
去掉零事实的冗余表示后与集合语义一致（零事实总在，通常不写出）。
两个方向得到的都是"z 存活、x 新生成"。

第二个验证反方向：把 S 拆小再合并，结果不变。S₁ = {y}，S₂ = {z}，
F(S₁) ∪ F(S₂) = {x} ∪ {z} = {x, z} = F(S₁ ∪ S₂)。这就是分配律的全
部内容——它对这类"杀与生成都不依赖集合整体"的函数自动成立。反例
同样算一遍就有感觉：常量传播的 F 把 S = {y↦1, y↦2}（两条路径各带
一个常量）映到 ⊤，但 F({y↦1}) ∪ F({y↦2}) = {y↦1, y↦2}，两个单
点结果的并是"两个常量都在"，而集合语义的答案是"不知道"——合并
发生在函数内部，分配律在门口就断了。

### 51.3.9 总回收：第 13 到 19 章的概念在本章各就各位

IFDS 是前半本教程概念的一次大检阅，值得把每个老朋友的新位置点名。
第 28 章的格在本章退居幕后：事实集合的并就是格的 join，但幂集格没
有高度问题，终止性不靠链有限。第 29 章的域构造在这里体现为"事实
域 D 加零事实"的自由完工——幂集格 2^(D∪{0})。第 30 章的不动点变
成了"表的增长不动点"：路径边集合在三个动作下单调递增，有限的宇
宙保证停。第 31 章的工作表换掉了流动的东西——从（结点, 格值）换
成路径边本身，但"新信息入队、重复信息丢弃"的纪律一模一样。第 32 章的强更新在 normalFlow 的杀操作里重现：赋值对单变量的事实是
精确的，因为事实按变量分裂。第 33 章的 gen/kill 对直接对应四张流
函数表。第 35 章的转移函数系统升级成了过程间版本——转移不再只
问"这条语句做什么"，还要问"这条边是哪一类过程间边"。

## 51.4 两个演示程序逐行读

### 51.4.1 init.tip：单函数内的 kill/generate

第一个程序 `init.tip` 不跨函数，作用是让我们在熟悉的地面上看清事实
如何被杀死、保留、生成，并作为与第 35 章交叉验证的基准。完整程序如
下。

```cpp
// file: programs/init.tip
main() {
  var a, b, c;
  a = input;
  if (a > 0) {
    b = 1;
  }
  output a;
  output b;
  c = b;
  output c;
  return 0;
}
```

逐行建立"事实"的直觉。进入 `main` 时三个局部变量 a、b、c 都只声明
未赋值，因此入口点上三者**都**带着"可能未初始化"的事实。点 2
`a = input;` 读取外部输入给 a 赋值，a 的旧污点被**杀死**——赋值之后 a
保证有值（TIP 中 `input` 总返回一个整数）。b、c 未被触及，事实保留。
点 3 是 `if (a > 0)` 分支，条件读取 a，但此时 a 已在点 2 被赋值，读 a
不会产生新的污点；分支内部 `b = 1` 给 b 赋常量，走这条路径时 b 的污
点被杀。然而分支并非必走：若 `a > 0` 为假，控制绕过 `b = 1`，b 仍然
没有任何赋值。两条路径在分支后合并，b 的事实在一条路径上被杀、在另
一条上保留，合并结果是 b **仍可能**未初始化。这是"事实沿有效路径求
并"的一个缩影：只要存在一条路径使污点保留，并集里就还有它。

于是点 5 `output a;` 干净（a 必被点 2 赋值）；点 6 `output b;` 危险
——存在不经 `b = 1` 的路径，b 可能未初始化就被输出；点 7 `c = b;` 读取
这个可能未初始化的 b，把污点**生成**到 c，于是 c 也可能未初始化；点 8
`output c;` 因而也危险。51.7 节的实测输出会显示警告恰好落在节点 6（b）、
7（b）、8（c），而节点 5 不警告。这与第 35 章过程内分析的结论逐字一
致——本章框架在不跨函数时应退化并吻合于过程内结果，这是我们有意设
计的一条自检。

### 51.4.2 callf.tip：污点经调用大门走一个来回

第二个程序 `callf.tip` 是本章的主角：它让"可能未初始化"的事实跨函数
传播，检验调用边、返回边与配对是否正确。完整程序如下。

```cpp
// file: programs/callf.tip
f(x) {
  var r;
  output x;
  r = x;
  return r;
}
main() {
  var a, b, c;
  if (input > 0) {
    a = 1;
  }
  b = f(a);
  c = f(5);
  output b;
  output c;
  return 0;
}
```

先看 `f`。它有一个形参 x、一个局部变量 r。点 2 `output x` 直接读取形
参；点 3 `r = x` 读取 x 赋给 r；末尾 `return r` 返回 r。`f` 本身不保证 x
到达时是否已初始化——这取决于调用方传入什么。因此从 `f` 内部孤立地
看，x 经调用边进入时是什么状态，output、r、返回值就是什么状态：若 x
可能未初始化，则点 2 的输出、点 3 的 r、以及返回值都可能未初始化。

再看 `main`。入口处 a、b、c 都未赋值。点 3 的 `if (input > 0)` 只在条件
成立时执行 `a = 1`；与 `init.tip` 同理，存在不进分支的路径，所以合并后
a 仍可能未初始化。关键是接下来的两次调用：

- 点 4 `b = f(a)`：实参是这个可能未初始化的 a。经调用边，a 的污点映
  射到 `f` 的形参 x；在 `f` 内它流过 output、r、返回值；再经返回边，
  返回值的污点映射回左值 b。因此 **b 可能未初始化**，点 6 `output b`
  危险。
- 点 5 `c = f(5)`：实参是常量 5，不读取任何变量，本身完全有定义。经
  调用边，x 的初始状态不含污点（5 恒有值）；`f` 内 output、r、返回值
  都干净；返回后 **c 有定义**，点 7 `output c` 不警告。

两个调用点共享同一份 `f` 函数体，但它们的结论必须各自独立：点 4 的污
染不能串到点 5，点 5 的干净也不能"洗白点 4。这正是 25.2.4 强调的配对
纪律——从点 4 进入的事实只回点 4 的后继，从点 5 进入的只回点 5 的后
继。51.7 节的输出会显示：`f` 内的警告（x、r、返回值）是因点 4 传入
可能未初始化的 a 而产生的；`main` 中点 4 本身还警告实参 a 可能未初始
化，点 6 警告 b，而点 5 与点 7 对 c 始终干净。**"`b=f(a)` 报警、`c=f(5)`
不报"这一组对照，是本章框架正确性最直观的试金石。**

### 51.4.3 两个程序合起来要说明的事

`init.tip` 把过程内的 kill/generate/合并钉死，并与第 35 章对齐；
`callf.tip` 在此之上加入调用大门，检验事实如何经实参→形参、返回值
→左值流动，以及多个调用点如何靠配对保持独立。前者保证"不跨函数时
框架不退步"，后者保证"跨函数时框架不串味、不漏报"。接下来 51.5 节
给出能同时满足这两点的算法——路径边制表。

## 51.5 路径边制表：算法核心

### 51.5.1 路径边：把"有效路径"压缩成一条边

IFDS 不枚举路径，它枚举**路径边**（path edge）。一条路径边是一个四元
组

> ⟨ s_p, d₁ ⟩ → ⟨ n, d₂ ⟩，

其中 s_p 是某个函数的入口标号点，n 是该函数内的一个标号点，d₁、d₂
是事实。它的含义是：**存在一条从函数入口 s_p 出发、到达 n 的下行有效
路径，使事实 d₁ 在入口处进入、沿路径传播后以事实 d₂ 出现在 n。** 这
条路径中间可以调用别的函数，但每次调用都已完整、同站点地返回（下行
有效，见 25.2.5），所以路径边把一整段可能很长、含嵌套调用的有效路
径**压缩**成"入口事实 → 当前事实"的一条边。代码中路径边就是
`ifds.hpp` 的 `PathEdge` 结构，25.6.2 节逐字段讲解。

为什么这个压缩能终止、又不丢信息？关键在路径边的两端都锚定在**函
数入口**与**函数内点**上，而不记录路径中间的历史。同一条 ⟨s_p,d₁⟩→
⟨n,d₂⟩ 即使由成千上万条不同的具体有效路径产生，在表里也只存一份—
—我们关心的是"这种入口事实能否到达当前事实"，而非"有多少条路径走
到"。由于函数数、入口点数、事实数、函数内点数都有限，可能的路径边
总数有界（量级随后给出），枚举必然终止。而 MOVP 要的正是存在性的
并：某事实 d₂ 出现在 n 的路径边末端，当且仅当存在有效路径使 d₂ 到
达。于是求全部路径边，就同时求得了 MOVP。

### 51.5.2 工作表与三个动作

算法维护一个路径边集合（即最终的表）和一个工作表。初始时放入种子
（25.5.4 节）；然后不断从工作表取出一条**新**路径边 e = ⟨s_p,d₁⟩→
⟨n,d₂⟩，按其末端 n 的种类做三种动作之一，可能产生若干新路径边加入表
与工作表。重复到工作表为空。三个动作与 25.2 的超级图结构一一对应：

**动作一：n 是普通点（过程内边）。** 查 n 所在函数 CFG 的正常后继
m。对每一个后继，把流函数 `normalFlow` 作用于 e 的末端事实 d₂，得到
事实集合；对集合中的每个 d₃，发一条新路径边

> ⟨ s_p, d₁ ⟩ → ⟨ m, d₃ ⟩。

注意新边的**源头**与 e 相同（同一函数入口、同一入口事实），只是末端
推进到 m、事实按流函数变化。这样，"从入口事实 d₁ 出发能到哪"的信息
沿着过程内边一步步延伸。

**动作二：n 是调用点。** 这里有两路并发的动作，对应调用边与调用-返
回边。

*（2a）调用边：* 把 `callFlow` 作用于 d₂，得到应进入被调函数入口的
事实集合；对其中每个 d₃，做两件事：一是发一条**被调函数内部的种子
路径边** ⟨ f_entry, d₃ ⟩ → ⟨ f_entry, d₃ ⟩（源头与末端都在被调函数入
口、事实相同，相当于"d₃ 到达了被调函数入口"）；二是在 incoming 表
中登记配对（25.5.3 节）。若这是第一次进入该被调函数，还要补上它自
己的局部变量种子。

*（2b）调用-返回边：* 把 `callToReturnFlow` 作用于 d₂，得到绕过调用
的事实集合；对每个 d₃，发路径边 ⟨s_p,d₁⟩→⟨retSite,d₃⟩，末端直接
到调用点的正常后继 retSite。局部事实由此不进被调函数、直接绕过。

**动作三：n 是某被调函数的出口点。** 这是配对返回的落点。先只考虑
"确实存在以此函数为被调方的调用点"，并把返回表达式对应的流函数
`returnFlow` 准备好。对每一个相关调用点，去 incoming 表查：e 的源头
事实 d₁，当初是从该调用点的哪些路径边进入的？对查到的每一个调用方
记录 ck（它记得调用方的入口 s_q 与入口事实 d₀），把 `returnFlow` 作
用于 e 的末端事实 d₂，得到 d₃，发一条把两端都接回**调用方**的路径边：

> ⟨ s_q, d₀ ⟩ → ⟨ retSite, d₃ ⟩。

这条新边的源头是调用方的函数入口与事实（由 ck 提供），末端是该调用
点的正常后继。如此，从某个调用点进入被调函数的事实，在出口处只会
沿记录回到那同一个调用点之后——配对由"查 incoming、只取该站点记录"
强制实现。

### 51.5.3 incoming 表：让出口找回调用方

incoming 表是 IFDS 配对机制的核心数据结构，值得单独讲清。它的键是
一对（**调用点 n，被调函数入口处的事实 d₃**），值是一个**调用方记录**
集合；每条记录里有两样东西：调用方路径边的源头标号点 s_p（调用方函
数入口）与源头事实 d₁。在动作 2a 中，每当一条事实经调用边从 n 进入
被调函数，就向键 (n,d₃) 插入记录 (s_p,d₁)，意思是：

> "被调函数入口处的事实 d₃，有一份是从调用点 n、由调用方入口事实
> (s_p,d₁) 那条路径边送来的。"

到了动作三，被调函数出口处有一条路径边 ⟨f_entry,d₁⟩→⟨exit,d₂⟩。要
把它送回调用方，就以**各调用点 n** 与 **d₁** 为键查表：键 (n,d₁) 下的
每条记录 (s_p,d₀) 都指出了一个当初的来路，于是沿该来路生成回到 n 之
后的边。这里键中包含**事实 d₁** 是关键中的关键：它保证只有"带着同一
个入口事实 d₁ 进入 f"的调用记录才会被配对。从点 4 带"a 的污点"进入
的事实，在出口处只会匹配点 4 登记的记录；点 5 传入常量 5 时登记的是
不含该污点的另一条事实，键不同，不会被点 4 的出口边误取。**站点与事
实双重定位，使共享同一函数体的多个调用点在返回时互不串味。**

### 51.5.4 种子：一切从函数入口开始

路径边从哪来？每个**被进入**的函数，其入口处都需要一组种子路径边，
形如 ⟨entry,d⟩→⟨entry,d⟩，源头与末端重合，表示"事实 d 在函数入口处
初始存在"。种子事实有两类：

- **零事实 0**：每个被进入的函数入口都有，表达"该函数确实被调用、入
  口可达"。0 是恒真的载体。
- **声明未赋值的局部变量**：`var` 声明的局部变量在入口时还没有值，其
  "可能未初始化"事实作为种子存在。

形参**不**列入种子：形参在进入时由调用边按实参赋予状态，它不是"天生
未初始化"，而是"随实参而定"。这一区分很重要——若错误地把形参也当
种子，那么即便所有调用点都传常量，形参仍会被永远标记为可能未初始
化，产生误报；若错误地不给局部变量种子，又会漏掉真正的未初始化路径。

程序从 `main` 起步：先放入 `main` 的零事实种子与其全部局部变量种子。
其余函数在动作 2a 中**首次被调用**时才补种子——这天然只分析真正可达
的函数，且因有"是否已进入"的标记，每个函数只补一次种子。

### 51.5.5 终止性：为什么边数有界

为什么工作表一定会空？核心是"新边"的定义：只有当一条路径边此前不在
表中时，它才入工作表，而可能的路径边总数有界。路径边的四个分量
——入口标号点、入口事实、末端标号点、末端事实——分别取自有限集合：
入口/末端标号点是有限的程序点，事实取自有限的 D₀。因此路径边总数至
多为 O(|P|·|D|·|P|·|D|)，其中 |P| 是程序点数、|D|=|D₀| 是事实数。每
轮循环至少加入一条此前没有的边（否则不产生工作表项），故循环轮数不
超过边总数，必然终止。

这一结论不依赖程序是否含循环或递归：循环在超级图上是环，但沿环传播
只会反复生成**已经在表中**的路径边（源头、事实、末端都不变），不再
产生新工作表项，于是环上的传播在有限步后自动平息。递归同理——`f` 调
`f` 会在 `f` 入口处登记 incoming 记录，但入口处的事实组合有限，能产生
的入口种子与路径边也有限。这正是"制表（tabulation）"相对"枚举路
径"的根本优势：它在有限的边空间里求不动点，而不是在无限的路径空间
里搜索。

### 51.5.6 正确性论证的结构

这里给出"算法求得的事实 = MOVP"的证明骨架，它与 25.3.4 的可分配性
论证拼接成完整证据。证明分两个方向，各自归纳。

**可靠性（soundness，表中有的，都有有效路径为证）：** 对路径边的生成
过程做归纳。种子边对应长度为零的平凡有效路径（就在函数入口）。动作
一沿单条过程内边延伸，路径仍下行有效；动作 2a 的种子边对应"经调用边
进入"这一有效前缀，动作 2b 的绕过边沿调用-返回边、不破坏配对；动作
三生成的边，其经过的路径是"调用方路径 + 进入被调函数 + 被调函数内
下行有效路径 + 同站点返回"，配对由 incoming 记录保证，故整条仍有效。
归纳可得每条表中边都对应某条有效路径，因此不会把伪路径上的事实误报
为可达。

**完备性（completeness，有效路径能到的，表里都有）：** 对有效路径的
长度归纳。任一到达 n 的有效路径，取其最后一次（最外层）动作：若是过
程内边，由归纳假设前一节点的路径边已在表中，动作一会生成它；若涉及
一次完整调用，调用前缀由 2a 登记、被调函数内的下行有效子路径由归纳
假设有路径边、动作三按 incoming 记录将其接回调用点。这里需要 25.3.4
的结论——集合结论可由单点事实的并无损恢复——以保证把路径上一捆事实
拆成单点制表时不漏掉协同本不该有的信息；对可分配问题，这种拆分恰好
完备。两方向合拢，表中末端事实集合即 MOVP。

需要提醒：这种"完备"是相对于 **MOVP**（只计有效路径）而言的，不是说
分析能精确预测每次具体执行——循环、递归、input 仍使多次执行的事实
被求并，分析给出的是全部可能有效路径的保守且（在可分配问题上）精确
的并。下一章 IDE 处理"值"时，我们还会遇到"可表达的边函数"带来的另一
层边界。

### 51.3.8 流函数的矩阵表示：为什么叫"爆炸图"

有限域上的任何函数都可以写成矩阵：行是输入事实、列是输出事实，
格点 (d₁, d₂) 为真当且仅当 d₂ ∈ f(d₁)。可分配函数的矩阵有个漂亮性
质——每一列的生成方式独立，复合对应矩阵乘法（布尔语义下乘法是
"存在一条中间事实"，加法是或）。把每个超级图边的流函数矩阵沿着
图"竖"起来，结点复制 |D|+1 层，就得到 spa 原书画的爆炸超图：分析
问题变成了爆炸图上的图可达性。制表机做的事等价于对爆炸图做 BFS，
但从不显式物化这份拷贝——路径边表就是 BFS 的 frontier 压缩。这个
视角解释了 25.9.1 的复杂度：爆炸图有 (|D|+1)·N 个结点，BFS 线性
于边数，边数至多每条超级图边贡献 (|D|+1)² 条。

矩阵视角还有一个红利：流函数的复合、并、传递闭包全部有矩阵运算
对应物，第 52 章把格点从布尔升级成三值常量、把矩阵元素从"有边"
升级成"边缘函数"时，整套代数几乎原封不动地搬过去。

### 51.5.8 工作表的顺序：为什么 FIFO 够用

主循环用的是普通双端队列、先进先出。第 31 章讨论过工作表顺序影
响的是收敛速度而不是结果；本章同理，但有一个过程间特有的现象值
得一提：调用边生成的被调函数路径边会立刻排到队尾，而调用方自己
的绕过边先被处理——于是"绕过"常常先于"穿行"到达返回点，表里先
有无调用的保守事实、再被带调用的精确事实补充。对可分配问题这只
影响中间状态的形状，终态与顺序无关（不动点唯一）。若换成 LIFO，
被调函数内部的边会先蔓延完再回到调用方，中间状态反过来。工程上
有人用优先队列按"图深度"排序来改善局部性，对本章规模毫无必要。

## 51.6 实现：从事实域到制表机

### 51.6.1 接口层：一个 Fact、一个 PathEdge、一张表

落地 IFDS 的第一步是把 51.3 节的数学对象翻译成三个 C++ 类型。事实域
D 在本章实例里是"程序里出现过的变量名"，再加上一个特殊的零事实；
`Fact` 用一个布尔成员区分两者。值得停下来想一下为什么零事实必须是
一等公民而不是普通集合元素：零事实承载的是**可达性本身**——只要某
个程序点存在一条以零事实结尾的路径边，就存在一条从函数入口出发的
有效路径真正走到这个点。分析器要回答"这个点可达吗"，靠的不是任何
变量事实，而恰恰是这个看似空洞的零事实。把它排进事实集合，制表机
就不需要为可达性单开一套机制。

`PathEdge` 是四元组（起点、起点事实、终点、终点事实），它压缩的是
"从函数入口的某条事实出发，存在一条过程内有效路径到达终点的某条事
实"这一整句话。51.5 节说过，tabulation 的全部状态就是路径边的集
合，所以 `IfdsResult` 里那张 `std::set<PathEdge>` 就是算法的不动点
表本体；`reach` 只是从表的末端提取出来的查询视图，`warnings` 则是
把查询结果对照语句的读取集合之后产生的诊断。

```cpp
// file: src/ifds.hpp
// 第 51 章配套：IFDS 框架（Reps–Horwitz–Sagiv）求解可能未初始化分析。
// IFDS 把分析问题表达成"有限事实集 D 上的可分配（distributive）流函数"，
// 再用 path-edge tabulation 在过程间超级图上求精确的 merge-over-valid-paths。
// 关键：流函数只在单点事实上定义，集合语义由逐点并集得到——
//   F(S) = ⨆_{d∈S∪{0}} f(d)
// 可分配性 f(a∪b)=f(a)∪f(b) 让这种分解不失真。
#pragma once

#include <map>
#include <set>
#include <string>
#include <utility>
#include <vector>

#include "ast.hpp"
#include "cfg.hpp"

namespace tip {

// 事实：零事实 0（恒真、可达性载体）或变量名（该变量可能未初始化）。
struct Fact {
    bool zero = false;
    std::string name;

    bool operator==(const Fact &o) const {
        return zero == o.zero && name == o.name;
    }
    bool operator<(const Fact &o) const {
        if (zero != o.zero) return zero > o.zero;  // 0 排在前（仅为稳定序）
        return name < o.name;
    }
};
Fact fZero();
Fact fName(std::string n);
std::string factShow(const Fact &f);

// 全局程序点：(函数名, 函数内 CFG 节点号)。
using PP = std::pair<std::string, int>;

// 路径边：(start 标号点) → (end 标号点)，表示存在一条过程内有效路径
// 从 entry 的事实 f1 走到 n 的事实 f2。
struct PathEdge {
    PP start;
    Fact f1;
    PP end;
    Fact f2;

    bool operator<(const PathEdge &o) const {
        if (start != o.start) return start < o.start;
        if (!(f1 == o.f1)) return f1 < o.f1;
        if (end != o.end) return end < o.end;
        return f2 < o.f2;
    }
};

struct IfdsResult {
    std::set<PathEdge> pathEdges;
    std::map<PP, std::set<Fact>> reach;  // 每个点到达的事实（path edge 末端）
    std::vector<std::string> warnings;
};

// 对整个程序跑 IFDS tabulation（实例固定为可能未初始化）。
IfdsResult solveIfds(const Cfg &cfg, const ProgramA &program);

std::string printIfds(const Cfg &cfg, const IfdsResult &r);

}  // namespace tip
```

头文件里有两处细节值得注释。其一，`Fact::operator<` 把零事实排在
所有变量事实之前——这只是让输出与内部遍历顺序稳定，与语义无关；集
合语义由 `operator==` 决定。其二，`PP` 直接复用 `std::pair<string,
int>`，函数名加节点号唯一确定一个超级图结点；第 49 章过程间分析里
我们已经用过同样的编码，这里沿用它，读者可以把两章的实现并排对照。

### 51.6.2 流函数层：四张小表撑起整个语义

`ifds.cpp` 的前一百行是四类流函数的实现，与 25.3.6 的表格逐行对
应。每个函数都遵守同一个契约：输入单点事实，输出事实集合。这个契
约正是可分配性的程序形态——集合层面的大流函数 F 完全由这些单点小
函数拼出来，`F(S) = ⨆ f(d)`。

`normalFlow` 处理普通赋值：目标变量自己的旧事实被杀掉；如果右端读
取了事实 d 对应的变量，目标变量就新生成一条同名事实（污点随赋值传
播）。注意"杀"与"生成"可以在同一次调用里同时发生——`b = b + 1` 会
杀掉 b 的旧事实、又立刻生成新的，净效果恰好是事实存活。零事实永远
映到零事实，这是所有流函数共享的第一行。

`callFlow` 把调用点上的事实翻译成形参事实：逐个实参检查其中的变量
引用，事实 d 命中第 i 个实参，就生成第 i 个形参的事实。`returnFlow`
对称地处理返回端：被调函数出口处的事实如果被返回表达式读取，就在
调用点的赋值左值上落地。`callToReturnFlow` 是最容易被忽略的一张
表：事实不进被调函数、直接绕过调用点到返回点存活，唯一的动作是杀
掉左值——因为左值在返回点的新值属于被调函数摘要的结果，调用方自
己不能再对它做任何假设。

```cpp
// file: src/ifds.cpp
#include "ifds.hpp"

#include <deque>
#include <sstream>

#include "pretty.hpp"

namespace tip {
namespace {

// ---- 表达式/语句读取的变量（与 ch35 init.cpp 同型，自带一份保持自包含） ----
std::set<std::string> usesOf(const Expr *e) {
    std::set<std::string> r;
    if (const auto *x = dynamic_cast<const VarRef *>(e)) {
        r.insert(x->name);
    } else if (const auto *x = dynamic_cast<const Binop *>(e)) {
        std::set<std::string> l = usesOf(x->l.get());
        r.insert(l.begin(), l.end());
        std::set<std::string> rr = usesOf(x->r.get());
        r.insert(rr.begin(), rr.end());
    } else if (const auto *x = dynamic_cast<const CallE *>(e)) {
        for (const auto &a : x->args) {
            std::set<std::string> s = usesOf(a.get());
            r.insert(s.begin(), s.end());
        }
    }
    return r;
}

std::set<std::string> stmtUses(const Stmt *s) {
    if (const auto *a = dynamic_cast<const AssignS *>(s))
        return usesOf(a->value.get());
    if (const auto *o = dynamic_cast<const OutputS *>(s)) return usesOf(o->e.get());
    if (const auto *r = dynamic_cast<const ReturnS *>(s)) return usesOf(r->e.get());
    if (const auto *w = dynamic_cast<const WhileS *>(s)) return usesOf(w->cond.get());
    if (const auto *i = dynamic_cast<const IfS *>(s)) return usesOf(i->cond.get());
    return {};
}

// ---- 调用点识别：赋值右端是单个具名函数调用（与 ch50 同口径） ----
struct CallInfo {
    std::string callee;
    const CallE *call = nullptr;
    std::string lhs;
};

CallInfo callInfoOf(const Stmt *s) {
    CallInfo ci;
    const auto *a = dynamic_cast<const AssignS *>(s);
    if (!a) return ci;
    const auto *t = dynamic_cast<const VarRef *>(a->target.get());
    const auto *c = dynamic_cast<const CallE *>(a->value.get());
    if (!t || !c) return ci;
    const auto *fn = dynamic_cast<const VarRef *>(c->callee.get());
    if (!fn) return ci;
    ci.callee = fn->name;
    ci.call = c;
    ci.lhs = t->name;
    return ci;
}

// ---- 四类可分配流函数：单点事实输入 → 事实集合 ----

// 普通过程内边（语句 s 之后）：
//   赋值 x=e（非调用）：d≠x 时 d 存活；d 被 e 读取时生成 x；
//   其余语句：恒等。零事实恒等通过。
std::set<Fact> normalFlow(const Stmt *s, Fact d) {
    std::set<Fact> out;
    if (d.zero) {
        out.insert(fZero());
        return out;
    }
    if (const auto *a = dynamic_cast<const AssignS *>(s)) {
        if (!callInfoOf(s).call) {
            const auto *t =
                dynamic_cast<const VarRef *>(a->target.get());
            if (t) {
                if (d.name != t->name) out.insert(d);
                std::set<std::string> rhs = usesOf(a->value.get());
                if (rhs.count(d.name)) out.insert(fName(t->name));
                return out;
            }
        }
    }
    out.insert(d);
    return out;
}

// 调用边（调用点 → 被调函数入口）：
//   d 出现在第 i 个实参里 → 形参 i；零事实→零事实。
std::set<Fact> callFlow(const CallInfo &ci,
                        const std::vector<std::string> &params, Fact d) {
    std::set<Fact> out;
    if (d.zero) {
        out.insert(fZero());
        return out;
    }
    for (size_t i = 0; i < ci.call->args.size() && i < params.size(); ++i) {
        std::set<std::string> argVars = usesOf(ci.call->args[i].get());
        if (argVars.count(d.name)) out.insert(fName(params[i]));
    }
    return out;
}

// 返回边（被调函数出口 → 返回点）：
//   d 被返回表达式读取 → 调用赋值的左值；零事实→零事实。
std::set<Fact> returnFlow(const CallInfo &ci, const Expr *retExpr, Fact d) {
    std::set<Fact> out;
    if (d.zero) {
        out.insert(fZero());
        return out;
    }
    std::set<std::string> retVars = usesOf(retExpr);
    if (retVars.count(d.name)) out.insert(fName(ci.lhs));
    return out;
}

// 调用-返回边（调用点 → 返回点，过程内"绕过"）：
//   局部事实存活，但左值被杀（左值的新值由被调函数摘要给出）；
//   零事实→零事实。
std::set<Fact> callToReturnFlow(const CallInfo &ci, Fact d) {
    std::set<Fact> out;
    if (d.zero) {
        out.insert(fZero());
        return out;
    }
    if (d.name != ci.lhs) out.insert(d);
    return out;
}

std::string showFactSet(const std::set<Fact> &fs) {
    std::set<std::string> names;
    for (const Fact &f : fs)
        if (!f.zero) names.insert(f.name);
    if (names.empty()) return "{}";
    std::ostringstream out;
    out << "{";
    bool first = true;
    for (const std::string &v : names) {
        if (!first) out << ",";
        out << v;
        first = false;
    }
    out << "}";
    return out.str();
}

}  // namespace

Fact fZero() { return Fact{true, ""}; }
Fact fName(std::string n) { return Fact{false, std::move(n)}; }

std::string factShow(const Fact &f) { return f.zero ? "0" : f.name; }

IfdsResult solveIfds(const Cfg &cfg, const ProgramA &program) {
    // 函数表与 FunCfg 表。
    std::map<std::string, const FunDecl *> decls;
    for (const auto &f : program.funs) decls[f->name] = f.get();
    std::map<std::string, const FunCfg *> fcfgs;
    for (const FunCfg &fc : cfg.funs) fcfgs[fc.name] = &fc;

    // 超级图：普通边集合（调用点的 CFG 出边另算 call-to-return）。
    // isCall[PP] → 调用信息；exitPP[fun]。
    std::map<PP, CallInfo> isCall;
    std::map<std::string, PP> exitPP;
    std::map<std::string, std::map<int, std::vector<int>>> normalSucc;
    for (const FunCfg &fc : cfg.funs) {
        exitPP[fc.name] = {fc.name, fc.exitNode};
        for (const auto &[id, node] : fc.nodes)
            if (node.stmt) {
                CallInfo ci = callInfoOf(node.stmt);
                if (ci.call && decls.count(ci.callee))
                    isCall[{fc.name, id}] = ci;
            }
        for (const auto &[a, b] : fc.edges)
            normalSucc[fc.name][a].push_back(b);
    }

    // incoming：调用点 PP × 被调入口事实 → 调用方 (start 标号, 站点事实)
    // 列表。被调函数出口路径边按此配对回送给调用方。
    struct CallerKey {
        PP start;
        Fact f1;
        bool operator<(const CallerKey &o) const {
            if (start != o.start) return start < o.start;
            return f1 < o.f1;
        }
    };
    std::map<std::pair<PP, Fact>, std::set<CallerKey>> incoming;

    IfdsResult res;
    std::deque<PathEdge> wl;
    auto addEdge = [&](const PathEdge &e) {
        if (res.pathEdges.insert(e).second) wl.push_back(e);
    };

    // 每个函数入口的种子事实：声明的局部变量（参数到达时已初始化）。
    auto seedsOf = [&](const std::string &fun) {
        std::set<Fact> seeds;
        const FunDecl *fd = decls.at(fun);
        for (const std::string &v : fd->vars) seeds.insert(fName(v));
        return seeds;
    };

    // main 起步：零事实路径边 + 种子；标记 main 已进入。
    std::set<std::string> entered;
    PP mainEntry{"main", fcfgs.at("main")->entry};
    addEdge({mainEntry, fZero(), mainEntry, fZero()});
    entered.insert("main");
    for (const Fact &s : seedsOf("main"))
        addEdge({mainEntry, s, mainEntry, s});

    while (!wl.empty()) {
        PathEdge e = wl.front();
        wl.pop_front();
        PP n = e.end;

        auto ciIt = isCall.find(n);
        if (ciIt != isCall.end()) {
            // ---- 调用点 ----
            const CallInfo &ci = ciIt->second;
            const FunCfg &calleeCfg = *fcfgs.at(ci.callee);
            PP calleeEntry{ci.callee, calleeCfg.entry};

            // 调用边：把入口事实送进被调函数，并登记 incoming 配对。
            for (const Fact &d3 : callFlow(ci, decls.at(ci.callee)->params, e.f2)) {
                incoming[{n, d3}].insert(CallerKey{e.start, e.f1});
                addEdge({calleeEntry, d3, calleeEntry, d3});
                // 首次进入被调函数：补它自己的种子路径边。
                if (!entered.count(ci.callee)) {
                    entered.insert(ci.callee);
                    for (const Fact &s : seedsOf(ci.callee))
                        addEdge({calleeEntry, s, calleeEntry, s});
                }
            }

            // 调用-返回边：局部事实绕过调用直接到返回点。
            for (int r : normalSucc[n.first][n.second]) {
                PP retSite{n.first, r};
                for (const Fact &d3 : callToReturnFlow(ci, e.f2))
                    addEdge({e.start, e.f1, retSite, d3});
            }
        } else if (exitPP.count(n.first) && n == exitPP[n.first]) {
            // ---- 被调函数出口：配对所有以此函数为被调方的调用点 ----
            for (const auto &[sitePP, ci] : isCall) {
                if (ci.callee != n.first) continue;
                const Expr *retExpr = decls.at(n.first)->ret->e.get();
                auto inIt = incoming.find({sitePP, e.f1});
                if (inIt == incoming.end()) continue;
                for (const CallerKey &ck : inIt->second) {
                    for (int r : normalSucc[sitePP.first][sitePP.second]) {
                        PP retSite{sitePP.first, r};
                        for (const Fact &d3 : returnFlow(ci, retExpr, e.f2))
                            addEdge({ck.start, ck.f1, retSite, d3});
                    }
                }
            }
        } else {
            // ---- 普通过程内边 ----
            const CfgNode &node = fcfgs.at(n.first)->nodes.at(n.second);
            for (int m : normalSucc[n.first][n.second]) {
                PP target{n.first, m};
                for (const Fact &d3 : normalFlow(node.stmt, e.f2))
                    addEdge({e.start, e.f1, target, d3});
            }
        }
    }

    // 提取每个点到达事实；警告：语句读取的变量 ∈ 到达事实。
    for (const PathEdge &e : res.pathEdges) res.reach[e.end].insert(e.f2);
    for (const FunCfg &fc : cfg.funs) {
        for (const auto &[id, node] : fc.nodes) {
            if (!node.stmt) continue;
            std::set<std::string> bad;
            auto rf = res.reach.find({fc.name, id});
            if (rf != res.reach.end()) {
                std::set<std::string> uses = stmtUses(node.stmt);
                for (const std::string &v : uses) {
                    Fact f = fName(v);
                    if (rf->second.count(f)) bad.insert(v);
                }
            }
            if (bad.empty()) continue;
            std::ostringstream w;
            w << "node " << id << ": " << printStmtLine(*node.stmt)
              << "  possibly uninitialized:";
            for (const std::string &v : bad) w << " " << v;
            res.warnings.push_back(w.str());
        }
    }
    return res;
}

std::string printIfds(const Cfg &cfg, const IfdsResult &r) {
    std::ostringstream out;
    out << "== IFDS path-edge tabulation, possibly-uninitialized ==\n";
    for (const FunCfg &fc : cfg.funs) {
        out << "-- " << fc.name << " --\n";
        for (const auto &[id, node] : fc.nodes) {
            out << "  " << id;
            if (node.stmt) out << " " << printStmtLine(*node.stmt);
            out << ": " << showFactSet(r.reach.count({fc.name, id})
                                            ? r.reach.at({fc.name, id})
                                            : std::set<Fact>{});
            if (node.stmt && callInfoOf(node.stmt).call) out << " (call site)";
            out << "\n";
        }
    }
    out << "-- warnings --\n";
    if (r.warnings.empty()) {
        out << "  (none)\n";
    } else {
        for (const std::string &w : r.warnings) out << "  " << w << "\n";
    }
    return out.str();
}

}  // namespace tip
```

### 51.6.3 制表机主循环：三个动作的现场

`solveIfds` 的主循环是 25.5.2 三个动作的直接翻译。工作表里流动的
是路径边；每弹出一条边，看它的末端落在哪类结点上，分三路处理。调
用点上做两件事：用 `callFlow` 把末端事实送进被调函数入口（动作二），
同时用 `callToReturnFlow` 给绕过边放行（动作一的调用版）。出口结点
上做配对回送（动作三）：在 `incoming` 表里查"谁以这条事实调过我"，
对每个登记过的调用方起点，用 `returnFlow` 把出口事实落到返回点。

`incoming` 表是整套机制里最精巧的一笔，值得单独看。它的键是（调
用点, 被调入口事实），值是所有以这条事实进入该函数的（调用方路径
边起点, 站点事实）对。为什么要记"起点"而不只记"调用点"？因为路径
边的起点标号携带的是"这条有效路径是从调用方哪个入口状态出发的"。
出口处配对回送时，新路径边的起点必须沿用调用方的原起点，而不是调
用点本身——只有这样，回到调用方之后的路径仍然是一条从函数入口出
发的连续有效路径，后续的制表才能继续以正确的标号延伸。丢掉这个起
点，路径就断在调用点，过程间分析退化成过程内拼接。

种子部分只给 main 播种：零事实一条、main 的每个局部变量一条。其
余函数的种子在**首次被调用时**补上（`entered` 集合防止重复）。这个
细节对应 25.5.4 的语义选择：只有真正从 main 可达的函数才值得分析；
不可达函数的入口没有零事实路径边，它们内部的事实永远不会出现在表
里——可达性再次由零事实默默承担。

主循环结束后，`reach` 与 `warnings` 的提取是纯查询：前者把路径边
按末端聚簇，后者对每条语句算读取集合、与到达事实求交。没有任何一
处再碰超级图的结构，分析结果的消费与算法本体干净地分离。

### 51.6.4 总装：main.cpp 的三行流水线

命令行外壳与前面各章相同：解析、建 CFG、跑分析、打印。IFDS 实例
固定为"可能未初始化"，所以 `--check` 后面没有任何参数化的域选择；
换一个问题（比如 25.13 练习里的零除检测）需要换四张流函数表与种子
函数，框架本身一行不动——这正是"框架"一词的含义。

```cpp
// file: src/main.cpp
// 第 51 章配套程序：IFDS 框架跑可能未初始化分析。
//   --check FILE : 超级图 path-edge tabulation，逐点打印到达事实与警告；
//                  结论与第 35 章单调框架（过程内）交叉一致，
//                  并展示过程间调用边/返回边如何携带污点
#include <fstream>
#include <iostream>
#include <memory>
#include <string>

#include "TIPLexer.h"
#include "TIPParser.h"
#include "antlr4-runtime.h"

#include "ast_build.hpp"
#include "cfg.hpp"
#include "ifds.hpp"
#include "symtab.hpp"

class CollectErrorListener : public antlr4::BaseErrorListener {
public:
    std::vector<std::string> messages;

    void syntaxError(antlr4::Recognizer *, antlr4::Token *, size_t line,
                     size_t column, const std::string &msg,
                     std::exception_ptr) override {
        messages.push_back("syntax error line " + std::to_string(line) + ":" +
                           std::to_string(column) + " " + msg);
    }
};

namespace {

struct Parsed {
    std::unique_ptr<tip::ProgramA> ast;
    tip::Bindings bindings;
};

Parsed parseFile(const std::string &path) {
    std::ifstream src(path);
    if (!src) {
        std::cerr << "cannot open " << path << '\n';
        std::exit(1);
    }
    antlr4::ANTLRInputStream input(src);
    TIPLexer lexer(&input);
    antlr4::CommonTokenStream tokens(&lexer);
    TIPParser parser(&tokens);

    CollectErrorListener errors;
    lexer.removeErrorListeners();
    parser.removeErrorListeners();
    lexer.addErrorListener(&errors);
    parser.addErrorListener(&errors);

    TIPParser::ProgramContext *tree = parser.program();
    if (!errors.messages.empty()) {
        for (const std::string &m : errors.messages) std::cout << m << '\n';
        std::exit(2);
    }

    Parsed result;
    result.ast = tip::buildAst(tree);
    result.bindings = tip::resolveNames(*result.ast);
    if (!result.bindings.errors.empty()) {
        for (const tip::Diag &d : result.bindings.errors)
            std::cout << d.text << '\n';
        std::exit(3);
    }
    return result;
}

}  // namespace

int main(int argc, char **argv) {
    if (argc != 3 || std::string(argv[1]) != "--check") {
        std::cerr << "usage: tipa --check FILE\n";
        return 1;
    }

    Parsed p = parseFile(argv[2]);
    tip::Cfg cfg = tip::buildCfg(*p.ast);
    tip::IfdsResult r = tip::solveIfds(cfg, *p.ast);
    std::cout << tip::printIfds(cfg, r);
    return 0;
}
```

### 51.6.5 打印层：把表压成人能读的形状

`printIfds` 的实现只有二十行，但它体现的分层值得单独指出。制表机
的完整状态是 `pathEdges` 集合——对 callf.tip 它有几十条，直接打印
既是噪声也难对账。打印层做的第一件事是聚合：按末端结点把路径边
聚簇、取末端事实的并，得到每点的"到达事实"——这正是用户心里的
问题形状："这个点上哪些变量可能未初始化"。第二件事是标注：调用
点后面加 `(call site)` 标记，让读者一眼看出哪行的语义里藏着边。
第三件事是诊断：warnings 单独成节，把"到达事实 ∩ 语句读取"的非
空结果按结点序输出。

对账脚本逐字节比较这份输出，意味着打印层的任何改动（哪怕只是调
整空格）都会被测试抓住。这不是负担而是契约：输出格式稳定，后续
章节引用本章结论时才有共同的锚点。第 52 章的 IDE 输出会沿用人分
析结果的习惯（先表后警告），第 53 章 0-CFA 换成"调用点 → callee
集合"的形状——聚合方式跟着问题走，但"完整状态留给自己、聚合视
图交给用户"的分层不变。

### 51.7.2 callf.tip：一次完整的"过门往返"

先看 f 的表。f 的入口到达集合是 {r,x}：r 是 f 自己的未初始化局部
变量，x 是形参——形参本身不播种，但 main 第 4 个结点以事实 a 调用
f 时，`callFlow` 把 a 的事实翻译成 x 的事实送了进来。于是 f 内部
`output x` 与 `r = x` 两条语句的警告就顺理成章：x 带着"可能未初始
化"进门，r 又从 x 染上。

回到 main 一侧，最有信息量的是结点 6 的警告 `output b ; possibly
uninitialized: b`。这条警告的完整传播链是：main 的 a 未初始化 →
`b = f(a)` 调用边把 a 的事实送成 x 的事 实 → f 内部 `r = x` 使 r
染上 → `return r` 的返回边把 r 的事实落回左值 b → `output b` 处警
报。事实一共跨了四道边界：实参到形参、函数内传播、返回表达式到左
值、继续传播。第 35 章的过程内版本连第一道都过不去；第 49 章的完
全内联版本能做到同样精度但要付出图膨胀的代价；IFDS 用一张表就精
确回答了。

再看结点 5 `c = f(5)`：没有产生任何警告。常量 5 不携带事实，c 的
事实在赋值处被杀、也没有新事实生成——同一个被调函数、同一个分析
框架，对两个调用点给出不同答案，因为进入函数的事实集合不同。这就
是"对每个调用点单独配对"买到的精度，第 50 章 call-string 做到的
事情在 IFDS 里是免费的：路径边天然以（起点, 事实）配对，不同调用
点送进来的事实在表里各行其道，互不污染。

### 51.7.3 init.tip：与第 35 章对表

init.tip 的输出与第 35 章过程内分析完全一致：`a = input` 之后 a
的警告消失；`b = 1` 沿 if 分支杀掉 b；`c = b` 让 c 继承 b 的事
实。这印证了框架的下界：对没有调用的程序，IFDS 退化为过程内可分
配数据流分析，结果不多不少。值得注意 node 3 之后的到达集合是
{b,c} 而入口是 {a,b,c}——a 的事实在 `a = input` 处被杀，而 if 结
点本身不杀 b、c，分支汇合后它们的存活状态不变。

还有一个安静的细节：f 在 init.tip 里根本不存在，表里也没有任何
关于"不可达函数"的行。整个输出里看不到 f，因为零事实从未到达过
一个不存在的函数入口——不可达代码在 IFDS 里不是被 special-case 掉
的，而是自然消失的。



### 51.5.7 三个动作的不变式

把 25.5.2 的工作表动作配上一条全局不变式，正确性论证就有了抓手。
不变式是：**表中任何时刻的任何路径边，都对应一条真实存在的有效
路径前缀**（可靠性方向）；工作表空时，**每条有效路径的每条边都已
在表中**（完备性方向）。第一条由归纳保证：种子的空路径合法；三个
动作只在"存在到达末端的有效路径前缀"之上延伸，延伸方式（流函数
映出的每个事实、配对回送的每个起点）都对应真实路径的拼接。第二
条由反证保证：若有一条有效路径的某条边缺席，取最短的这样的路径，
它的前一跳必然已在表中（更短），弹出那条边时动作必然生成这跳——
矛盾。

这个双方向论证就是 25.5.6 概述的展开，与第 30 章不动点归纳、第 31 章工作表可靠性的论证同构：差别只在"路径"的定义从图路径换成
了配对路径。读者至此应该能体会到本教程反复出现的一个模式——分
析算法的正确性从来不是靠测试保证的，而是靠一条不变式加上两个归
纳方向；测试只验证实现没有背离论证。

## 51.8 手工执行制表机：callf.tip 的完整 trace

### 51.8.1 为什么值得手工跑一遍

算法的正确性论证告诉我们制表机会停、停下来的表就是 MOVP，但没有告
诉我们表是怎么一步步长出来的。手工执行一遍 callf.tip——总共只有
两个函数、十来个程序点、三条变量事实——能把 25.5 的三个动作从抽
象描述变成手上的肌肉记忆。更重要的是，trace 里能亲眼看到两件在定
理陈述里看不见的事：incoming 表如何随调用慢慢长出配对，以及不同
调用点送进 f 的事实如何在表里互不干扰。下面按工作表的弹出顺序叙
述；每一步给出弹出的路径边、走的是哪一路、生成了哪些新边。读者可
以对照 25.7.1 的最终输出，逐条验证每张表项的来历。

### 51.8.2 初始状态与种子

程序点编号沿用第 16 章 CFG 构造的输出：main 的入口是 1 号结点，
`if` 条件是 2 号，`a = 1` 是 3 号，`b = f(a)` 是 4 号，`c = f(5)`
是 5 号，`output b` 是 6 号，`output c` 是 7 号，`return 0` 是 8 号，
出口是 9 号。f 的入口是 1 号，`output x` 是 2 号，`r = x` 是 3 号，
`return r` 是 4 号，出口是 5 号。

种子阶段往工作表里放四条路径边：main 入口的零事实自环（1,0）→
（1,0），以及 a、b、c 三条变量事实的自环（1,a）→（1,a）、
（1,b）→（1,b）、（1,c）→（1,c）。注意种子边的起点与终点都是函
数入口自己——路径边说的是"从入口的某事实到某点的事实存在过程内
有效路径"，入口到入口的空路径合法，所以自环是天然的起点。此时
`entered` 集合里只有 main；f 还没有入场券。

### 51.8.3 第一阶段：过程内蔓延

弹出零事实自环。末端是 main:1，普通结点，normalFlow 对零事实永远
返回零事实，于是生成（1,0）→（2,0）。弹出 a 的自环，同样延伸到
（1,a）→（2,a）；b、c 两条照抄。工作表里现在有四条指向 2 号的
边。

弹出（1,0）→（2,0）。2 号是 `if` 条件结点，不是调用点，两条出边
（then 分支去 3 号、else 分支汇合去 4 号——本例 else 为空，条件结
点直连 4 号）各自复制事实，生成（1,0）→（3,0）与（1,0）→（4,0）。
变量事实的边同样处理。这一阶段没有任何花哨的事情发生：可分配框架
里，普通语句的传播就是把每条单点事实各自搬过边。

到 3 号结点 `a = 1` 时第一次出现"杀"：a 的事实在赋值后被杀掉，
（1,a）→（3,a）不存在；但零事实与 b、c 的事实照常通过。到 4 号
`b = f(a)` 时，制表机第一次遇到调用点。

### 51.8.4 第二阶段：一次调用的完整生命周期

弹出（1,a）→（4,a）。末端是调用点，走调用分支。callFlow 检查实
参 a：事实 a 命中第 0 个实参，生成形参 x 的事实事。于是三件事同
时发生：incoming 表登记键（main:4, x）→ 值 {(main:1, a)}；路径边
（f:1, x）→（f:1, x）入表；f 首次入场，`entered` 插入 f，f 自己的
种子（f:1, r）自环一并生成。

同一时刻，callToReturnFlow 处理绕过边：事实 a 不等于左值 b，直接
放行，生成（1,a）→（5,a）——注意这条边的终点是 5 号 `c = f(5)`，
即调用点的 CFG 后继，而不是 4 号本身。左值 b 自己的事实在绕过边
上被杀：（1,b）→（4,b）弹出后，绕过生成的是空集，b 的事实在调用
点被"押"给了被调函数的返回摘要，调用方本地暂时无权谈论它。

f 内部的传播此时开始。弹出（f:1, x）→（f:1, x），延伸到 2 号
`output x`：零操作，生成（f:1,x）→（f:2,x）。r 的种子同样蔓延。
到 3 号 `r = x` 时，右端读取 x，事实 x 生成左值 r 的新事实——但 r
本来就有自己的未初始化事实，集合层面两者合并成 {r,x}，输出里 f:3
的到达集合正是这个形状。到 4 号 `return r`，语句读取 r，事实 r
通过。到 f:5 出口结点，配对动作登场。

### 51.8.5 第三阶段：出口配对与回送

弹出（f:1, x）→（f:5, x）。末端是 f 的出口，制表机扫描所有以 f
为被调方的调用点：main:4 与 main:5 都调 f。对 main:4，查 incoming
键（main:4, x）：有登记，值是 {(main:1, a)}。returnFlow 检查 f 的
返回表达式 r：事实 x 不被 r 读取（x 只是同名传染的中转，返回的是
r），没有新事实生成；于是对 main:4 的 CFG 后继 5 号……等一下——
回送的目标是调用点 main:4 的后继，即 main:5？不对，是 4 号自己的
后继 5 号结点。这里编号有个巧合：main 的 5 号结点既是 `c = f(5)`，
又是 `b = f(a)` 的返回点。回送边（1,a）→（5,a）……但这条边已经由
绕过边生成过了，集合去重让它安静地消失。真正有信息量的是 r 的事
实：弹出（f:1, r）→（f:5, r）时，returnFlow 发现返回表达式读取
r，对每个登记过的调用方起点生成左值事实——main:4 的 incoming 里
有 (main:1, a) 配对（因为 r 的事实在 f 里与 x 的事实地一起到达过
出口吗？没有——路径边是单事实的，r 的出口边是（f:1,r）→（f:5,r），
它的 incoming 查询键是（main:4, r）。而登记发生在调用边处理时：
当时只登记了 x 的事实事。于是查询落空，r 的事实无处可送？

这正是本章实现里最值得盯住的一处精细。回看 25.6.3：incoming 的键
是（调用点, 被调入口事实 d3），出口边（f:1,r）→（f:5,r）的起点事
实是 r，查（main:4, r）确实没有登记——r 不是从 main:4 进来的，
r 是 f 自己的种子。它在出口处能做的事只有一件：对每个调用点的
**零事实与入口事实族**做检查……不对，实现在这里对 isCall 的每个
调用点查 incoming[{sitePP, e.f1}]，e.f1 是 r，查不到就跳过。那
么输出里 main:6 的警告 `output b ; possibly uninitialized: b` 是
从哪来的？

答案藏在种子的播种时机里。当（1,a）→（4,a）触发 f 首次入场时，
f 的种子 r 同时生成（f:1,r）自环。这条自环蔓延到出口是（f:1,r）
→（f:5,r）。配对时它查（main:4, r）落空——但是！main:5 的调用
`c = f(5)` 处理（1,0）→（5,0）时，callFlow 对零事实生成零事实，
登记 incoming[（main:5, 0）]，而 r 的事实同样查不到。真正送出 r
的是**零事实路径**：零事实进入 f 后，f 的种子 r 已经在场（entered
机制保证了种子只补一次，但补出来的边起点是 f:1），出口的零事实边
（f:1,0）→（f:5,0）配对（main:5, 0）时，returnFlow 对零事实的处
理是返回零事实……左值 c 的新事实从哪里来？

读者若在这里停一下，就触到了 IFDS 教科书叙述里最含糊的一环。标
准答案：**左值在调用返回后的未初始化状态，不需要被"送回"——它
已经在调用点被杀掉又由被调函数的摘要重新决定**。本章实现的口径
是：callToReturnFlow 杀左值，returnFlow 只在"返回表达式读取了从
调用方进来的事实"时重新生成左值事实。于是 `b = f(a)` 的 b 警告来
自另一条链：a 的事实事进入 f 成为 x，f 里 `r = x` 生成 r（注意这
个 r 事实的**起点是 f:1**，是种子系），`return r` 读取 r——r 的
事实一路到出口（f:1,r）→（f:5,r）。配对查询（main:4, r）落空。

但输出里 main:6 明明报了 b。让我们数一数 main:4 的到达集合：
{a,b,c}——b 的事实还在！它没被杀？回看 callToReturnFlow：`if
(d.name != ci.lhs) out.insert(d);`——b 的事实确实被杀了。那
main:6 的 b 从哪来？答案：main:4 之后还有 main:5 `c = f(5)`，然后
main:6。b 的事实在 main:4 被杀，但它可以走**另一条路径**：main 的
种子（1,b）→（2,b）→（3,b）→ 4 号调用点，绕过边杀掉；可 2 号条
件结点还有一条直连 4 号的边（else 空），同样到 4 号，同样被杀。
到达集合 {a,b,c} 是**所有路径边末端的并**——包括从 4 号出发、经
f 内部回送重新长出来的 b。哪条回送边能长出 b？只有 returnFlow 在
（main:4 的某次配对）里生成左值 b。它需要出口事实是被返回表达式
读取的 d。d=r 的出口边查 incoming（main:4, r）——登记过吗？登记
的时机是调用边处理：`incoming[{n, d3}].insert(...)`，d3 是
callFlow 的输出。callFlow(ci, params, d) 对 d=a 输出 x，对 d=b、
d=c、d=0 输出……零事实！d=0 时 callFlow 返回 {0}，登记 incoming
[（main:4, 0）] 并生成（f:1,0）自环。零事实在 f 里蔓延到出口，
配对时 returnFlow(ci, retExpr, 0) 返回零事实——不生成 b。

我们似乎陷入了矛盾：输出确实报了 b，上面的推理却证明没有路径边
能把它送到 6 号。停在这里是值得的，因为解开它需要回到 25.3.4 的
分解引理。f 内部的 `r = x` 是一条普通赋值边：事实 x 进、事实 r
出。**这条边的路径边起点是 f:1**——于是（f:1,x）→（f:3,r）是一
条合法路径边！r 的事实在 3 号结点生成时，它的起点标号是 f:1、起
点事实是 x——也就是说，"从 f 入口的 x 出发，到 3 号的 r"被打成
了一条边。继续延伸到出口：（f:1,x）→（f:5,r）。配对时查的键是
（main:4, x）——这次查到了！值 {(main:1, a)}。returnFlow 用返回
表达式 r 检查末端事实 r：命中，生成左值 b 的事实事。回送边：
（main:1, a）→（main:5, b）。起点是 main:1、起点事实 a——路径从
main 入口的 a 事实出发，穿过调用大门、经 f 内部、回到调用方 5 号
结点的 b 事实。整条链在表里就是一条起点标号为（main:1, a）的路
径边的延伸序列。这就是 25.6.3 强调"回送沿用调用方原起点"的原因：
没有这个标号，（f:1,x）→（f:5,r）就接不回（main:1, a）。

b 的事实事从 5 号继续蔓延到 6 号 `output b`，警报响起。同一条机
制解释 c 的沉默：`c = f(5)` 的实参是常量，没有事实进门，f 出口处
配对（main:5, 0）只回送零事实，c 的新事实无从生成，而 c 自己的
种子事实在赋值处被杀——到达集合里 c 消失，`output c` 无警报。

### 51.8.6 trace 的收尾与核查

工作表排空后，路径边表共几十条，全部落在 25.5.5 的界内：每个函数
入口事实 × 每个结点至多一条末端。`reach` 视图把末端聚簇就得到
25.7.1 的每点集合；f 的 {r,x} 与 main 的 {a,b,c}→{a,b} 演化与输
出逐行吻合。warnings 的六条（f 内三条、main 三条）都能在上面的叙
述里找到出生地。

这个 trace 也暴露了手工推演的边界：三个变量、两个函数就已经需要
如此小心地区分"哪条事实从哪个起点来"；真实的分析器面对数百个事
实与数千个结点时，制表机的机械可靠性正是它的价值——人容易在配
对上出错，集合与映射不会。

### 51.8.7 incoming 表的增长方式

trace 里 incoming 表从空开始，每次调用边处理至多多登记一条（调用
点, 入口事实）键。观察它的增长极限：键空间是调用点数乘以事实数，
值空间是每个键下至多"起点 × 事实"对数——同样是多项式规模。更细
致地看，main:4 的键（main:4, x）只登记了一次，因为（1,a）→
（4,a）这条路径边只被弹出一次；表项的值集合 (main:1, a) 也只有一
个成员。真实程序里一个热点函数可能被上百个调用点、每个调用点带几
条不同事实进入，incoming 相应长出上百个键——这正是 25.9.1 复杂度
里 F·|D| 因子的来源之一。工程实现里有人把 incoming 按被调函数分
桶以改善缓存局部性；本章规模下线性扫描 isCall 的写法已经足够，且
代码与 25.5 的叙述一一对应，教学价值优先。

incoming 表还有个静默的正确性角色：它只在调用边处理时写入、出口
配对时读取，中间不被修改。假如允许在分析中途清空或改写它（比如某
种激进的内存回收），回送就会丢失配对，表里出现"进得去、出不来"
的路径边——分析不报错，但答案悄悄变小。把它当作只增的日志来理
解，正确性论证里的归纳才站得住。

## 51.9 复杂度与规模的账本

### 51.9.1 路径边的总数上界

路径边的形状是（起点, 起点事实, 终点, 终点事实）。起点只能是各函
数的入口——这是 tabulation 的关键约束：普通延伸、回送、绕过都不
改变起点标号，只有进入被调函数时才换到被调入口。设全程序有 F 个
函数、每函数入口至多 |D|+1 条事实（含零事实）、全程序共 N 个结
点、每个结点末端至多 |D|+1 条事实。路径边总数不超过
F·(|D|+1)·N·(|D|+1)，即 O(|D|²·F·N)。对固定的分析问题（|D| 是变
量数，与程序规模同阶），这是图尺寸的多项式——对照第 49 章内联
方案的指数膨胀，这就是制表机存在的理由。

每条路径边入表时工作一次，每次处理的代价是：流函数调用（O(1)，
本实例里就是几次集合查询）乘以出边数、加上出口配对时的 incoming
查询（键值查询 O(log) 乘以登记数）。总体仍是多项式。原始论文给
出的界是 O(|D|³·|E|) 级别，实践中支配项几乎总是表本身的规模。

### 51.9.2 精度的含义：MOVP 不是 MOP

merge-over-valid-paths 与更常见的 merge-over-all-paths 一字之差。
MOP 把所有图路径（包括调用返回不配对的"走捷径"路径）上的事实求
并，会引入假阳性——比如"进入 f 但从另一个调用点返回"这种现实中
不存在的路径。MOVP 只在配对路径上求并，本章 callf.tip 里 b 的警
报是真实路径的事实，c 的沉默是精确的。对可分配问题，制表机给出的
MOVP 恰好等于理想答案：没有假阳性，也没有假阴性。第 35 章的格世
界里我们讨论过 MOP 与 MFP 在分配格上的重合（f ⊔ g = distributive
时不动点逐点等于路径并），IFDS 把同一件事在过程间重新做了一遍，
而"可分配"从格运算的要求放松成了流函数的集合分配律——这正是
25.3.3 定义的形式。

### 51.9.3 与第 50 章代价的对照

call-string 上下文敏感要为每个 k 深度上下文复制一份状态，空间是
状态数乘以上下文数；IFDS 的空间是 |D|² 乘图尺寸，与调用深度无关。
反过来，IFDS 的事实必须可分配，常量、区间这类值域问题不满足；第 50 章的格没有这个限制。两个框架覆盖的问题集合几乎不相交，工程系
统里按问题选框架：布尔形状的传播（污点、未初始化、锁持有、空检
查路径）用 IFDS，数值性质的传播用 k-CFA 加格。

### 51.9.4 与位向量分析的血缘

把本章的事实域换成"变量的位向量"、流函数换成位向量的 gen/kill
掩码，IFDS 就退化成过程间的位向量数据流分析——活跃变量、可用表
达式这些第 33 章的经典问题全部覆盖。位掩码的按位或正是幂集格的
join，kill 掩码的补集正是"杀掉的事实"，可分配性在位世界里自动成
立（每个位独立）。历史上 Reps 等人的论文正是从"位向量问题的过程
间精确解"出发推广到任意有限事实域的，所以 IFDS 与 SHAPE 框架的
早期实现大量复用位向量机的骨架。理解了这层血缘，就不难明白为什
么工业级的空指针分析（如 Java 的 Symbolic Execution 系列）愿意把
问题编码成 IFDS：布尔形状的问题在事实域上自动获得精确解，而精确
解在诊断类分析里意味着零误报——用户信任的起点。

trace 里 incoming 表从空开始，每次调用边处理至多多登记一条（调用
点, 入口事实）键。观察它的增长极限：键空间是调用点数乘以事实数，

## 51.10 spa 第 24 章对照与术语约定

spa 原书第 24 章把这套方法称为 interprocedural dataflow analysis，
核心图表正是 exploded supergraph——把每个超级图结点复制 |D|+1 层、
每层一个事实，流函数变成层间的边。本章没有画爆炸图，而是直接以
路径边为第一公民实现，两种视角等价：爆炸图里的一条边就是表里的
一条路径边，爆炸图的可达性就是表的非空性。选择路径边视角是因为
它省掉了显式建层的内存开销，也让"起点标号"这个关键信息有了自然
的落点——爆炸图里它是隐式的（层的选择），表里它是显式的四元组
成员。

realizable path（可实现路径）在本教程里译作"有效路径"，强调"调
用返回配对"这一约束；有些文献译"可实现路径"。tabulation 译"制
表"，指算法的核心动作是把答案逐步填进路径边表。零事实 zero fact
有些文献写作 Λ 或 distinguished element，作用完全相同：承载可达
性、让所有流函数共享同一个单位元。

术语之外，原文还讨论了函数指针与虚调用对超级图构造的影响——调
用目标不唯一时，每个可能目标一组调用边与返回配对。本章的 TIP 程
序里调用目标是词法名，第 53 章的闭包程序会重新打开这个问题：届时
超级图的边集合要先经过一次控制流分析才能确定，那正是 0-CFA 的用
武之地。

 精度的账本：IFDS 与前几章的对比

把第 27、37、38 章与本章放在同一张账本上，可以看到三种过程间策略
的精确交换关系。第 35 章不跨过程：零成本、但对所有经调用传播的事
实失明。第 49 章内联展开：精度与本章相同（都是有效路径上的精确
并），代价是超级图尺寸随内联深度指数增长，且递归直接不可表达。第 50 章 call-string 上下文敏感：在非分配问题上用有限上下文换精度，
上下文长度 k 需要手工选择，超过深度的调用全部混在一起。IFDS 的位
置是：只要问题可分配，精度就是**精确的 MOVP**——不选 k、不近似、
不多不少；作为交换，能表达的问题必须能把集合语义分解成单点事实的
并。

最后这个交换正是下一章的入口。常量传播不可分配（两条路径各携带一
个不同常量，汇合后是"不知道"而不是两个常量的并），所以本章框架直
接套不上。但"让每个事实携带一个值、让路径边携带一个函数"的推广
——IDE——能把同一套制表机改造成值敏感的版本。读者带着 25.6 的实
现读第 52 章，会发现主循环三动作一个字都不用改，改的只是流函数的
返回类型从"事实集合"变成"环境格上的函数"。

### 51.11.1 从 call-string 到路径边：两种上下文的最终对照

第 50 章结束时留下的悬念可以在这里给出收束。call-string 的上下文
是"最近的 k 个调用点"，路径边的上下文是"从哪个函数入口、带着哪
条事实出发"——后者叫**功能上下文**（functional context）。两者的
差别在 callf.tip 上小到看不见，但程序稍一复杂就分野：两个调用点
传同样的实参时，功能上下文自动合并（起点事实相同），call-string
仍然分开（调用点不同）；反过来，一个调用点传不同实参时，功能上
下文分开（事实不同），call-string 却合并。哪种"分开"更有意义取
决于问题：对污点传播，实参内容决定一切，功能上下文更准；对缓存
行为，调用历史决定一切，call-string 更准。IFDS 选择功能上下文不
是它更强的证明，而是可分配性自然诱导的选择——集合语义里事实本
来就按单点分裂，起点跟着事实走是免费的。

### 51.11.2 三种精度损失的来源对照

把本章与前几章的"不精确"分类列在一起，能看清每种框架丢精度的位
置。第一种损失来自**路径合并**：第 13 到 17 章的格分析在汇合点把
多条路径的状态 join 成一个，符号分析在分支汇合处 x 从 + 变 ⊤ 就
是这一种。第二种来自**上下文合并**：第 50 章 k=0 时不同调用点的
形参混在一起，0-CFA（第 53 章）的 f 缓存累积所有调用方的实参也是
这一种。第三种来自**事实表达力**：常量传播无法用布尔事实表达"是
哪个常量"，IDE（第 52 章）用边缘函数补上这一层。IFDS 的特殊之处
是它把第一种损失彻底消除（MOVP 精确）、把第二种损失换成功能上下
文（对污点类问题恰好也不损失）、把第三种留给了 IDE。分析设计者
的日常工作，本质上就是诊断手头的问题丢在了哪一层、再挑一个能堵
住那一层的框架。

## 51.12 工程注意点

实现制表机时最容易失真的地方是配对的书刊号——不是算法，而是簿
记。第一，`incoming` 的键必须含被调入口事实 d3 而不只是调用点：同
一个调用点在不同事实下多次进入被调函数是常态，键少了这个分量，不
同事实的回送会串线。第二，回送路径边的起点要用 `CallerKey` 里的
原起点，而不是调用点；这是 25.6.3 反复强调的一点，写成调用点的话
程序仍然能跑，但结果悄悄变成"从调用点出发的路径"，精度损失不可
见。第三，工作表用路径边本身做去重（`pathEdges` 集合的 insert 返
回值决定是否入队），不要用（末端点, 事实）做键去重——那样会把不
同起点的路径边折叠掉，正是上一条错误的另一种形态。

第二个实践课题是种子的时机。本章把非 main 函数的种子推迟到首次被
调用，这既是效率考虑（不可达函数不分析），也是语义考虑（种子里隐
含"入口可达"的断言）。如果换成在启动时给所有函数播种，不可达函数
会带着满身假事实出现在表里，警告列表凭空多出一段——分析没有错，
但对"可能未初始化"这个实例来说，那些警告对应的代码永远不会执行。

第三个课题是输出的可读性。路径边表本身动辄数百行，直接打印既难读
也难对账；本章的打印只输出每个点的到达事实与警告，把表留在调试器
里。写这类框架时，把"算法的完整状态"与"用户的查询结果"分成两个
输出层次，后面每一章都在受益。

## 51.13 小结与练习

本章把"跨过程的数据流问题"从三个朴素方案的两难里拉出来，落在
Reps–Horwitz–Sagiv 的制表机上：事实域加零事实、可分配流函数、超
级图三类边、路径边工作表。机器在事实数乘图尺寸的多项式空间里精
确求解 merge-over-valid-paths，四个动作（延伸、送入、回送、绕过）
覆盖了所有情形。callf.tip 上四道边界一次走通，init.tip 上与过程
内版本分毫不差。

练习一：把事实域换成"可能为零的变量"（零除检测的传播版本），流
函数中只有赋值与返回两张表需要改；种子改为空。验证 `c = a / b` 在
b 可能来自返回值时报警。练习二：在 `callToReturnFlow` 里故意不杀
左值，观察 callf.tip 的输出如何变化，解释多出来的那条警告为什么
是假阳性。练习三：把 `incoming` 的回送起点改成调用点（25.12 第一
段的第二处），构造一个两层的调用链 `main → f → g`，说明输出在哪
个结点开始偏离正确答案、为什么制表仍然终止。

### 51.7.4 输出与 trace 的互查清单

把 25.8 的 trace 与 25.7.1 的输出对读，建议按这份清单走一遍。第
一，f 的入口集合 {r,x}：r 来自种子（25.8.2），x 来自 main:4 的调
用边（25.8.4）。第二，main 的 4 号结点集合 {a,b,c} 与 5 号相同：
b 的事实在 4 号被绕过边杀掉、又在同一点由回送边重新生成，到达集
合是所有路径边末端的并，杀与生相互抵消后外观不变——但 6 号的警
告证明 b 的事实的"重新生成"走的是 f 内部的真实路径，不是简单的
存活。第三，main:8 与 9 号的集合收缩到 {a,b}：c 的事实在 5 号被
杀（`c = f(5)` 的左值）且没有回送生成它。第四，warnings 的顺序
按（函数, 结点号）字典序，与打印循环的遍历序一致——对账时行序也
是契约的一部分。

### 练习再补两题

练习六：把 `callInfoOf` 的识别条件从"赋值右端是单个具名调用"放
宽到"赋值右端包含调用（如 `b = f(a) + 1`）"，本章实例的流函数哪
几张需要跟着改？提示：此时左值的旧事实不能简单杀掉——加法结果
的未初始化性只依赖 f 的返回值，而返回值在调用点之后才落地。

练习七：为本章实现加一个统计输出：路径边总数、工作表弹出的总次
数、incoming 表的条目数。在 callf.tip 上记录这三个数，然后把
main 里的调用从两次改成四次（复制粘贴两行），观察三个数的增长方
式。哪个数是线性于调用次数的？哪个不是？为什么路径边数的增长仍
然温和（提示：f 的入口事实集合没有变大）。

### 51.13.1 结束语：站在布尔与值的门槛上

回望这一章的旅程，起点是一个看似简单的抱怨：过程内分析对跨函数的
事实无能为力。我们试了三个朴素方案，看见它们分别在精度、规模、可
靠性上失手；然后超级图把"调用与返回必须配对"画进了图的定义，可分
配流函数把集合语义分解成单点事实的并，路径边制表把指数条有效路径
压缩进多项式空间的一张表。callf.tip 上那条贯穿四道边界的污点链，
最终只是表里一条起点标号为（main:1, a）的路径边的自然延伸——所
有抽象的机制，在结果里安静得像不存在一样。

但本章也反复碰到了同一堵墙：布尔事实表达不了"值"。常量传播的失
败反例、c = f(5) 的沉默与 b = f(a) 的警报之间的不对称、25.11.2
里第三种精度损失——它们都在说同一句话：有的问题需要每个事实带一
个值走完全程。下一章 IDE 将把这句话变成机制：路径边的末端事实之
外再挂一个环境格元素，流函数升级为格上的函数，四张表变成四族边
缘函数构造子。制表机本身——工作表、三动作、incoming 配对、起点
标号——原封不动。读者若把本章的 trace 亲手做过一遍，第 52 章的
trace 将只剩一个新看点：边缘函数如何沿路径复合、又如何在汇合处
保持有界的表示。

最后值得合上书想一想的是方法论的迁移。可分配性、超级图、制表
——这组工具的价值不限于编译器。任何"状态沿配对路径传播"的问题，
协议状态机的会话可达性、污点安全分析、数据库查询的谓词传播——
都能装进这个形状。教程选择在 TIP 这样的小语言上把机器造出来，正
是因为小到可以手 trace、又大到能容纳全部概念；把机器搬到工业语

终点不是会背复杂度，而是能在新问题里认出旧机器的形状——本章
的机器，形状是"配对路径上的精确可达"。

```cpp
// file: src/ast.hpp
// AST 定义：AST 是去掉了括号、分号等语法噪音的程序结构。
// 接口自本章起冻结，后续所有分析（名字、CFG、类型、格……）都在此之上工作。
#pragma once

#include <memory>
#include <string>
#include <utility>
#include <vector>

namespace tip {

enum class BOp { Add, Sub, Mul, Div, Gt, Eq };

struct Expr {
    virtual ~Expr() = default;
};
struct IntLit : Expr {
    int v;
    explicit IntLit(int value) : v(value) {}
};
struct VarRef : Expr {
    std::string name;
    explicit VarRef(std::string n) : name(std::move(n)) {}
};
struct InputE : Expr {};
struct Binop : Expr {
    BOp op;
    std::unique_ptr<Expr> l, r;
    Binop(BOp o, std::unique_ptr<Expr> lhs, std::unique_ptr<Expr> rhs)
        : op(o), l(std::move(lhs)), r(std::move(rhs)) {}
};
struct CallE : Expr {
    std::unique_ptr<Expr> callee;
    std::vector<std::unique_ptr<Expr>> args;
    CallE(std::unique_ptr<Expr> fn, std::vector<std::unique_ptr<Expr>> as)
        : callee(std::move(fn)), args(std::move(as)) {}
};
struct Deref : Expr {
    std::unique_ptr<Expr> e;
    explicit Deref(std::unique_ptr<Expr> p) : e(std::move(p)) {}
};
struct AddrOf : Expr {                       // spa: & Id
    std::string name;
    explicit AddrOf(std::string n) : name(std::move(n)) {}
};
struct AllocE : Expr {
    std::unique_ptr<Expr> e;
    explicit AllocE(std::unique_ptr<Expr> init) : e(std::move(init)) {}
};
struct NullE : Expr {};
struct RecLit : Expr {
    std::vector<std::pair<std::string, std::unique_ptr<Expr>>> fields;
    explicit RecLit(std::vector<std::pair<std::string, std::unique_ptr<Expr>>> fs)
        : fields(std::move(fs)) {}
};
struct FieldA : Expr {
    std::unique_ptr<Expr> e;
    std::string field;
    FieldA(std::unique_ptr<Expr> record, std::string f)
        : e(std::move(record)), field(std::move(f)) {}
};

struct Stmt {
    virtual ~Stmt() = default;
};
// target 只会是 VarRef / FieldA / Deref，文法 lvalue 已限定。
struct AssignS : Stmt {
    std::unique_ptr<Expr> target, value;
    AssignS(std::unique_ptr<Expr> t, std::unique_ptr<Expr> v)
        : target(std::move(t)), value(std::move(v)) {}
};
struct OutputS : Stmt {
    std::unique_ptr<Expr> e;
    explicit OutputS(std::unique_ptr<Expr> x) : e(std::move(x)) {}
};
struct IfS : Stmt {
    std::unique_ptr<Expr> cond;
    std::unique_ptr<Stmt> then, els;
    IfS(std::unique_ptr<Expr> c, std::unique_ptr<Stmt> t, std::unique_ptr<Stmt> e)
        : cond(std::move(c)), then(std::move(t)), els(std::move(e)) {}
};
struct WhileS : Stmt {
    std::unique_ptr<Expr> cond;
    std::unique_ptr<Stmt> body;
    WhileS(std::unique_ptr<Expr> c, std::unique_ptr<Stmt> b)
        : cond(std::move(c)), body(std::move(b)) {}
};
struct BlockS : Stmt {
    std::vector<std::unique_ptr<Stmt>> ss;
    explicit BlockS(std::vector<std::unique_ptr<Stmt>> v) : ss(std::move(v)) {}
};
struct ReturnS : Stmt {
    std::unique_ptr<Expr> e;
    explicit ReturnS(std::unique_ptr<Expr> x) : e(std::move(x)) {}
};

struct FunDecl {
    std::string name;
    std::vector<std::string> params;
    std::vector<std::string> vars;
    std::unique_ptr<Stmt> body;
    std::unique_ptr<ReturnS> ret;
};

struct ProgramA {
    std::vector<std::unique_ptr<FunDecl>> funs;
};

}  // namespace tip
```

AST 构造把 ANTLR 语法树搬到这套类层次上；本章没有改动任何一行。

```cpp
// file: src/ast_build.cpp
#include "ast_build.hpp"

#include <utility>
#include <vector>

namespace tip {

std::unique_ptr<ProgramA> AstBuilder::build(TIPParser::ProgramContext *tree) {
    auto program = std::make_unique<ProgramA>();
    for (auto *fc : tree->function()) program->funs.push_back(buildFun(fc));
    return program;
}

std::unique_ptr<FunDecl> AstBuilder::buildFun(TIPParser::FunctionContext *ctx) {
    auto f = std::make_unique<FunDecl>();
    f->name = ctx->IDENT()->getText();
    if (ctx->params()) {
        for (auto *p : ctx->params()->IDENT()) f->params.push_back(p->getText());
    }
    if (ctx->varDecls()) {
        for (auto *v : ctx->varDecls()->IDENT()) f->vars.push_back(v->getText());
    }

    std::vector<std::unique_ptr<Stmt>> body;
    for (auto *sc : ctx->stmt()) body.push_back(buildStmt(sc));
    f->body = std::make_unique<BlockS>(std::move(body));

    f->ret = std::make_unique<ReturnS>(buildExpr(ctx->expr()));
    return f;
}

std::unique_ptr<Expr> AstBuilder::buildLvalue(TIPParser::LvalueContext *lv) {
    std::unique_ptr<Expr> base;
    std::string field;
    if (auto *d = dynamic_cast<TIPParser::DirectLvalueContext *>(lv)) {
        base = std::make_unique<VarRef>(d->IDENT(0)->getText());
        if (d->IDENT().size() == 2) field = d->IDENT(1)->getText();
    } else {
        auto *p = dynamic_cast<TIPParser::PointerLvalueContext *>(lv);
        base = std::make_unique<Deref>(buildExpr(p->expr()));
        if (p->IDENT()) field = p->IDENT()->getText();
    }
    if (!field.empty())
        return std::make_unique<FieldA>(std::move(base), std::move(field));
    return base;
}

std::unique_ptr<Expr> AstBuilder::buildExpr(TIPParser::ExprContext *ctx) {
    if (auto *c = dynamic_cast<TIPParser::IntExprContext *>(ctx))
        return std::make_unique<IntLit>(std::stoi(c->INT()->getText()));
    if (auto *c = dynamic_cast<TIPParser::VarExprContext *>(ctx))
        return std::make_unique<VarRef>(c->IDENT()->getText());
    if (dynamic_cast<TIPParser::InputExprContext *>(ctx))
        return std::make_unique<InputE>();
    if (dynamic_cast<TIPParser::NullExprContext *>(ctx))
        return std::make_unique<NullE>();
    if (auto *c = dynamic_cast<TIPParser::ParenExprContext *>(ctx))
        return buildExpr(c->expr());

    if (auto *c = dynamic_cast<TIPParser::AddExprContext *>(ctx)) {
        const BOp op = c->PLUS() ? BOp::Add : BOp::Sub;
        return std::make_unique<Binop>(op, buildExpr(c->expr(0)), buildExpr(c->expr(1)));
    }
    if (auto *c = dynamic_cast<TIPParser::MulExprContext *>(ctx)) {
        const BOp op = c->STAR() ? BOp::Mul : BOp::Div;
        return std::make_unique<Binop>(op, buildExpr(c->expr(0)), buildExpr(c->expr(1)));
    }
    if (auto *c = dynamic_cast<TIPParser::CmpExprContext *>(ctx)) {
        const BOp op = c->GT() ? BOp::Gt : BOp::Eq;
        return std::make_unique<Binop>(op, buildExpr(c->expr(0)), buildExpr(c->expr(1)));
    }
    if (auto *c = dynamic_cast<TIPParser::NegExprContext *>(ctx)) {
        // TIP 没有负数字面量 token，-E 即 0-E。
        return std::make_unique<Binop>(BOp::Sub, std::make_unique<IntLit>(0),
                                       buildExpr(c->expr()));
    }
    if (auto *c = dynamic_cast<TIPParser::CallExprContext *>(ctx)) {
        std::vector<std::unique_ptr<Expr>> args;
        if (c->args())
            for (auto *a : c->args()->expr()) args.push_back(buildExpr(a));
        return std::make_unique<CallE>(buildExpr(c->expr()), std::move(args));
    }
    if (auto *c = dynamic_cast<TIPParser::FieldExprContext *>(ctx))
        return std::make_unique<FieldA>(buildExpr(c->expr()), c->IDENT()->getText());
    if (auto *c = dynamic_cast<TIPParser::DerefExprContext *>(ctx))
        return std::make_unique<Deref>(buildExpr(c->expr()));
    if (auto *c = dynamic_cast<TIPParser::AddrExprContext *>(ctx))
        return std::make_unique<AddrOf>(c->IDENT()->getText());
    if (auto *c = dynamic_cast<TIPParser::AllocExprContext *>(ctx))
        return std::make_unique<AllocE>(buildExpr(c->expr()));
    if (auto *c = dynamic_cast<TIPParser::RecExprContext *>(ctx)) {
        std::vector<std::pair<std::string, std::unique_ptr<Expr>>> fields;
        for (auto *fc : c->field())
            fields.emplace_back(fc->IDENT()->getText(), buildExpr(fc->expr()));
        return std::make_unique<RecLit>(std::move(fields));
    }
    return nullptr;  // 解析成功时不会到达
}

std::unique_ptr<Stmt> AstBuilder::buildStmt(TIPParser::StmtContext *ctx) {
    if (auto *c = dynamic_cast<TIPParser::AssignStmtContext *>(ctx))
        return std::make_unique<AssignS>(buildLvalue(c->lvalue()), buildExpr(c->expr()));
    if (auto *c = dynamic_cast<TIPParser::OutputStmtContext *>(ctx))
        return std::make_unique<OutputS>(buildExpr(c->expr()));
    if (auto *c = dynamic_cast<TIPParser::IfStmtContext *>(ctx)) {
        std::unique_ptr<Stmt> els;
        if (c->stmt().size() == 2) els = buildStmt(c->stmt(1));
        return std::make_unique<IfS>(buildExpr(c->expr()), buildStmt(c->stmt(0)),
                                     std::move(els));
    }
    if (auto *c = dynamic_cast<TIPParser::WhileStmtContext *>(ctx))
        return std::make_unique<WhileS>(buildExpr(c->expr()), buildStmt(c->stmt()));
    if (auto *c = dynamic_cast<TIPParser::BlockStmtContext *>(ctx)) {
        std::vector<std::unique_ptr<Stmt>> ss;
        for (auto *sc : c->stmt()) ss.push_back(buildStmt(sc));
        return std::make_unique<BlockS>(std::move(ss));
    }
    return nullptr;  // 解析成功时不会到达
}

std::unique_ptr<ProgramA> buildAst(TIPParser::ProgramContext *tree) {
    return AstBuilder{}.build(tree);
}

}  // namespace tip
```

名字解析填充符号表；`FunDecl` 里的 params 与 vars 向量正是种子的来
源。

```cpp
// file: src/symtab.cpp
#include "symtab.hpp"

#include <utility>

namespace tip {

namespace {

// 解析器在遍历 AST 的同时完成绑定与诊断收集。
struct Resolver {
    Bindings bindings;
    Scope *current = nullptr;
    const FunDecl *owner = nullptr;

    void declare(const std::string &name, Symbol::Kind kind) {
        if (current->table.count(name)) {
            bindings.errors.push_back({"error: redeclared '" + name + "'"});
            return;  // 保留先声明者，后声明被忽略
        }
        current->table.emplace(name, Symbol{kind, name, owner});
    }

    void resolveExpr(const Expr *e) {
        if (const auto *x = dynamic_cast<const VarRef *>(e)) {
            const Symbol *s = current->lookup(x->name);
            if (!s) {
                bindings.errors.push_back({"error: undeclared '" + x->name + "'"});
            } else {
                bindings.uses[x] = s;
            }
            return;
        }
        if (const auto *x = dynamic_cast<const Binop *>(e)) {
            resolveExpr(x->l.get());
            resolveExpr(x->r.get());
            return;
        }
        if (const auto *x = dynamic_cast<const CallE *>(e)) {
            resolveExpr(x->callee.get());
            for (const auto &a : x->args) resolveExpr(a.get());
            return;
        }
        if (const auto *x = dynamic_cast<const Deref *>(e)) return resolveExpr(x->e.get());
        if (const auto *x = dynamic_cast<const AllocE *>(e)) return resolveExpr(x->e.get());
        if (const auto *x = dynamic_cast<const FieldA *>(e)) {
            resolveExpr(x->e.get());  // 字段名不是变量，无需解析
            return;
        }
        if (const auto *x = dynamic_cast<const RecLit *>(e)) {
            for (const auto &f : x->fields) resolveExpr(f.second.get());
            return;
        }
        // IntLit / InputE / AddrOf / NullE：无变量使用。
    }

    void resolveStmt(const Stmt *s) {
        if (const auto *x = dynamic_cast<const AssignS *>(s)) {
            resolveExpr(x->target.get());
            resolveExpr(x->value.get());
            return;
        }
        if (const auto *x = dynamic_cast<const OutputS *>(s)) return resolveExpr(x->e.get());
        if (const auto *x = dynamic_cast<const IfS *>(s)) {
            resolveExpr(x->cond.get());
            resolveStmt(x->then.get());
            if (x->els) resolveStmt(x->els.get());
            return;
        }
        if (const auto *x = dynamic_cast<const WhileS *>(s)) {
            resolveExpr(x->cond.get());
            resolveStmt(x->body.get());
            return;
        }
        if (const auto *x = dynamic_cast<const BlockS *>(s)) {
            for (const auto &st : x->ss) resolveStmt(st.get());
            return;
        }
        if (const auto *x = dynamic_cast<const ReturnS *>(s)) return resolveExpr(x->e.get());
    }
};

}  // namespace

const Symbol *Scope::lookup(const std::string &name) const {
    auto it = table.find(name);
    if (it != table.end()) return &it->second;
    return parent ? parent->lookup(name) : nullptr;
}

Bindings resolveNames(ProgramA &program) {
    Resolver resolver;
    resolver.bindings.global = Scope(nullptr);
    Scope *global = &resolver.bindings.global;

    // 第一遍：所有函数名进入全局作用域。
    for (const auto &f : program.funs) {
        if (global->table.count(f->name)) {
            resolver.bindings.errors.push_back({"error: redeclared '" + f->name + "'"});
            continue;
        }
        global->table.emplace(f->name, Symbol{Symbol::Fun, f->name, f.get()});
    }

    // 第二遍：每个函数开自己的作用域，父作用域是全局表；
    // 作用域所有权交给 Bindings，遍历结束后符号依然存活。
    for (const auto &f : program.funs) {
        auto functionScope = std::make_unique<Scope>(global);
        resolver.current = functionScope.get();
        resolver.owner = f.get();

        for (const std::string &p : f->params) resolver.declare(p, Symbol::Param);
        for (const std::string &v : f->vars) resolver.declare(v, Symbol::Local);

        resolver.resolveStmt(f->body.get());
        resolver.resolveStmt(f->ret.get());

        resolver.current = nullptr;
        resolver.bindings.scopes.push_back(std::move(functionScope));
    }
    return std::move(resolver.bindings);
}

}  // namespace tip
```

CFG 构造的两遍算法（先编号后连边）在第 16 章讲过；本章的超级图直接
以它的输出为底图。

```cpp
// file: src/cfg.cpp
#include "cfg.hpp"

#include <map>
#include <set>
#include <sstream>
#include <vector>

#include "pretty.hpp"

namespace tip {
namespace {

// 两遍构造：第一遍按 AST 先序给所有程序点分配固定编号；第二遍连边。
// 先编号再连边，是为了让编号严格按源码顺序（连边时若先构造后继节点，
// 后继会抢在前面编号），从而输出与程序点编号都是确定的。
class CfgBuilder {
public:
    explicit CfgBuilder(const ProgramA &program) : program_(program) {}

    Cfg run() {
        Cfg cfg;
        for (const auto &fun : program_.funs) {
            FunCfg fc;
            cur_ = &fc;
            cur_->name = fun->name;
            nextId_ = 1;
            stmtId_.clear();

            const int entry = addNode(CfgNode::Kind::Entry);
            cur_->entry = entry;
            numberStmt(fun->body.get());
            const int retId = addNode(CfgNode::Kind::Return, fun->ret.get());
            const int exitId = addNode(CfgNode::Kind::Exit);
            cur_->exitNode = exitId;

            // 连边：语句构造返回它自己的入口点集合；空块没有节点，直接透传后继。
            std::vector<int> bodyEntries = wireStmt(fun->body.get(), {retId});
            if (bodyEntries.empty()) bodyEntries = {retId};
            link(entry, bodyEntries);
            link(retId, {exitId});

            // set 去重并排序：CFG 边不允许重复，输出顺序固定。
            std::set<std::pair<int, int>> uniq(cur_->edges.begin(), cur_->edges.end());
            cur_->edges.assign(uniq.begin(), uniq.end());
            cfg.funs.push_back(std::move(*cur_));
        }
        return cfg;
    }

private:
    const ProgramA &program_;
    FunCfg *cur_ = nullptr;
    int nextId_ = 1;
    std::map<const Stmt *, int> stmtId_;

    int addNode(CfgNode::Kind kind, const Stmt *stmt = nullptr) {
        const int id = nextId_++;
        cur_->nodes.emplace(id, CfgNode{id, kind, stmt});
        return id;
    }

    // ---- 第一遍：编号 ----
    void numberStmt(const Stmt *s) {
        if (const auto *b = dynamic_cast<const BlockS *>(s)) {
            for (const auto &x : b->ss) numberStmt(x.get());
            return;
        }
        if (const auto *x = dynamic_cast<const IfS *>(s)) {
            stmtId_[x] = addNode(CfgNode::Kind::Branch, x);
            numberStmt(x->then.get());
            numberStmt(x->els.get());
            return;
        }
        if (const auto *x = dynamic_cast<const WhileS *>(s)) {
            stmtId_[x] = addNode(CfgNode::Kind::Branch, x);
            numberStmt(x->body.get());
            return;
        }
        if (dynamic_cast<const AssignS *>(s)) {
            stmtId_[s] = addNode(CfgNode::Kind::Assign, s);
            return;
        }
        if (dynamic_cast<const OutputS *>(s)) {
            stmtId_[s] = addNode(CfgNode::Kind::Output, s);
        }
    }

    // ---- 第二遍：连边。返回进入该语句时首先到达的程序点集合 ----
    std::vector<int> wireStmt(const Stmt *s, const std::vector<int> &succ) {
        if (const auto *b = dynamic_cast<const BlockS *>(s)) {
            std::vector<int> cur = succ;
            for (auto it = b->ss.rbegin(); it != b->ss.rend(); ++it)
                cur = wireStmt(it->get(), cur);
            return cur;
        }
        if (const auto *x = dynamic_cast<const IfS *>(s)) {
            const int n = stmtId_[x];
            std::vector<int> targets = wireStmt(x->then.get(), succ);
            if (targets.empty()) targets = succ;
            if (x->els) {
                std::vector<int> e = wireStmt(x->els.get(), succ);
                if (e.empty()) e = succ;
                targets.insert(targets.end(), e.begin(), e.end());
            } else {
                targets.insert(targets.end(), succ.begin(), succ.end());
            }
            link(n, targets);
            return {n};
        }
        if (const auto *x = dynamic_cast<const WhileS *>(s)) {
            const int n = stmtId_[x];
            // 循环体执行完回到条件点；空体时条件点连一条自边（等于死循环）。
            std::vector<int> bodyEntries = wireStmt(x->body.get(), {n});
            if (bodyEntries.empty()) bodyEntries = {n};
            link(n, bodyEntries);
            link(n, succ);
            return {n};
        }
        const int n = stmtId_[s];
        link(n, succ);
        return {n};
    }

    void link(int from, const std::vector<int> &to) {
        for (int t : to) cur_->edges.emplace_back(from, t);
    }
};

const char *kindName(CfgNode::Kind kind) {
    switch (kind) {
        case CfgNode::Kind::Entry: return "entry";
        case CfgNode::Kind::Exit: return "exit";
        case CfgNode::Kind::Assign: return "assign";
        case CfgNode::Kind::Output: return "output";
        case CfgNode::Kind::Branch: return "branch";
        case CfgNode::Kind::Return: return "return";
    }
    return "?";
}

}  // namespace

Cfg buildCfg(const ProgramA &program) { return CfgBuilder(program).run(); }

std::string printCfg(const Cfg &cfg) {
    std::ostringstream out;
    for (const FunCfg &f : cfg.funs) {
        out << "== " << f.name << " ==\n";
        out << "nodes:\n";
        for (const auto &[id, node] : f.nodes) {
            out << "  " << id << ": " << kindName(node.kind);
            if (node.stmt) out << "  " << printStmtLine(*node.stmt);
            out << "\n";
        }
        out << "edges:\n";
        for (const auto &[a, b] : f.edges) out << "  " << a << " -> " << b << "\n";
    }
    return out.str();
}

}  // namespace tip
```

打印工具把语句压成单行文本，制表机用它生成警告行；多行 if/while
会原样换行打印，输出对账时以行为准。

```cpp
// file: src/pretty.cpp
#include "pretty.hpp"

#include <string>

namespace tip {

namespace {

// 表达式打印为前缀式：运算符与符号的对照表。
std::string exprText(const Expr *e) {
    if (const auto *x = dynamic_cast<const IntLit *>(e)) return std::to_string(x->v);
    if (const auto *x = dynamic_cast<const VarRef *>(e)) return x->name;
    if (dynamic_cast<const InputE *>(e)) return "input";
    if (dynamic_cast<const NullE *>(e)) return "null";

    if (const auto *x = dynamic_cast<const Binop *>(e)) {
        const char *sym = "+";
        switch (x->op) {
            case BOp::Add: sym = "+"; break;
            case BOp::Sub: sym = "-"; break;
            case BOp::Mul: sym = "*"; break;
            case BOp::Div: sym = "/"; break;
            case BOp::Gt: sym = ">"; break;
            case BOp::Eq: sym = "=="; break;
        }
        return "(" + std::string(sym) + " " + exprText(x->l.get()) + " " +
               exprText(x->r.get()) + ")";
    }
    if (const auto *x = dynamic_cast<const CallE *>(e)) {
        std::string s = "(call " + exprText(x->callee.get());
        for (const auto &a : x->args) s += " " + exprText(a.get());
        return s + ")";
    }
    if (const auto *x = dynamic_cast<const Deref *>(e))
        return "(* " + exprText(x->e.get()) + ")";
    if (const auto *x = dynamic_cast<const AddrOf *>(e)) return "(& " + x->name + ")";
    if (const auto *x = dynamic_cast<const AllocE *>(e))
        return "(alloc " + exprText(x->e.get()) + ")";
    if (const auto *x = dynamic_cast<const FieldA *>(e))
        return "(. " + exprText(x->e.get()) + " " + x->field + ")";
    if (const auto *x = dynamic_cast<const RecLit *>(e)) {
        std::string s = "{";
        for (size_t i = 0; i < x->fields.size(); ++i) {
            if (i) s += ", ";
            s += x->fields[i].first + ": " + exprText(x->fields[i].second.get());
        }
        return s + "}";
    }
    return "<unknown expr>";
}

std::string indent(int level) { return std::string(static_cast<size_t>(level) * 2, ' '); }

// 语句打印带缩进，一条语句一行（块内多行）。
void stmtText(const Stmt *s, int level, std::string &out) {
    if (const auto *x = dynamic_cast<const AssignS *>(s)) {
        out += indent(level) + exprText(x->target.get()) + " = " +
               exprText(x->value.get()) + " ;\n";
        return;
    }
    if (const auto *x = dynamic_cast<const OutputS *>(s)) {
        out += indent(level) + "output " + exprText(x->e.get()) + " ;\n";
        return;
    }
    if (const auto *x = dynamic_cast<const ReturnS *>(s)) {
        out += indent(level) + "return " + exprText(x->e.get()) + " ;\n";
        return;
    }
    if (const auto *x = dynamic_cast<const IfS *>(s)) {
        out += indent(level) + "if (" + exprText(x->cond.get()) + ")\n";
        stmtText(x->then.get(), level + 1, out);
        if (x->els) {
            out += indent(level) + "else\n";
            stmtText(x->els.get(), level + 1, out);
        }
        return;
    }
    if (const auto *x = dynamic_cast<const WhileS *>(s)) {
        out += indent(level) + "while (" + exprText(x->cond.get()) + ")\n";
        stmtText(x->body.get(), level + 1, out);
        return;
    }
    if (const auto *x = dynamic_cast<const BlockS *>(s)) {
        out += indent(level) + "{\n";
        for (const auto &st : x->ss) stmtText(st.get(), level + 1, out);
        out += indent(level) + "}\n";
        return;
    }
    out += indent(level) + "<unknown stmt>\n";
}

}  // namespace

std::string printExpr(const Expr *e) { return exprText(e); }

std::string printProgram(const ProgramA &program) {
    std::string out;
    for (const auto &f : program.funs) {
        std::string paramList;
        for (size_t i = 0; i < f->params.size(); ++i) {
            if (i) paramList += ",";
            paramList += f->params[i];
        }
        out += f->name + "(" + paramList + ") {\n";
        if (!f->vars.empty()) {
            out += indent(1) + "var ";
            for (size_t i = 0; i < f->vars.size(); ++i) {
                if (i) out += ",";
                out += f->vars[i];
            }
            out += " ;\n";
        }
        // 函数体是 BlockS；打印其内部语句而不是再嵌一层花括号。
        const auto *body = dynamic_cast<const BlockS *>(f->body.get());
        for (const auto &st : body->ss) stmtText(st.get(), 1, out);
        stmtText(f->ret.get(), 1, out);
        out += "}\n";
    }
    return out;
}

// 单行形式：CFG 节点标签等"节点旁边写一句话"的场合使用。
std::string printStmtLine(const Stmt &stmt) {
    std::string out;
    stmtText(&stmt, 0, out);
    if (!out.empty() && out.back() == '\n') out.pop_back();
    return out;
}

}  // namespace tip
```
