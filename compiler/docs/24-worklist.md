# 第 24 章　Worklist 不动点求解：把方程组真正解出来

## 24.1 本章目标

第 21 章建立了符号格——五个元素、一张 join 表、一套抽象算术；
第 22 章建立了格的通用构造——提升、积、映射、幂集，抽象环境被
正式确认为"变量集合上的映射格"；第 23 章把分析写成方程组——
每个程序点一条方程，右端是"传递函数作用于前驱的合并"。三章
合起来，单调框架的**规格**已经完整。但规格不是答案：第 21 章
的单趟执行在 sign1.tip 上给出 `output x` 处 `x=⊥`——一个明显
丢失了循环携带信息的错误结果；第 23 章的方程组停在"写下来"，
没有任何机制把它解出来。本章补上最后一件套：**worklist 不动点
求解**，让方程组从纸面走到收敛值。

用一句话概括本章与第 21 章的关系：单趟执行只把信息沿 CFG 的
**前向边**推了一遍，循环回边 `4 → 2` 上的信息没有回流；worklist
算法在回边携带新信息时把受影响的点**重新排队、重新计算**，
反复直到没有任何点再变化。这个"没有任何点再变化"的状态正是
方程组的不动点；而从全 ⊥ 出发、只做保守合并的迭代，到达的
恰好是**最小不动点**——精度最高的那个不动点。第 21 章的
`output x : x=⊥` 在本章被修正为 `x=+`：x 在循环体内被赋成
正数，循环出口沿回边把"+"带回循环头，再传到输出点。这不是
算法的运气，而是不动点理论保证的必然。

本章还要回答两个理论问题。**为什么一定会停？** 每次重算要么
让某点的状态严格上升、要么什么也不做，而格的高度有限，上升
次数因此有限——这与第 19 章合一的终止性论证（绑定表的单调
增长配 occurs 守卫）风味不同、结论同型：求解过程在一个有限
（或良基）结构上单调前进，不可能永远走下去。**为什么从 ⊥
出发得到的是最小不动点而不是随便哪个？** 因为 ⊥ 表示"尚未
证明任何事实"，迭代只做两件事——合并已证明的事实、施加
保守的传递函数——从不引入无根据的断言；因此收敛值只包含
方程组**可推导**的事实，而"可推导的最小封闭集"就是最小
不动点。这两个论证都将在本章完整给出。

### 24.1.1 与 spa 原书章节的对应

spa 第 4 章的 4.4 节以伪代码给出 worklist 算法，并指出两个
自由度：初始值的选择（全 ⊥ 或全 ⊤）与队列顺序的选择（任意）。
本书把两个自由度都落实为可运行的 C++：初始值固定为全 ⊥
（最小不动点语义），队列顺序固定为 FIFO（可复现的迭代轨迹），
并把"顺序不影响终态"作为一条定理陈述与论证（16.3.6）。spa
没有展开的终止性证明（它依赖 4.3 节的格高度概念），本书在
24.5 节补全到可以直接对账的程度。

对应关系逐行对账如下：spa 伪代码的 "worklist ← all
nodes" 对应 16.3.3 的"初始只放 entry"——spa 塞满全图
再逐个收敛，本书从 entry 出发只放受扰点，两者殊途同归
（16.4.3 的论证对两种初始化都成立），本书的选择让第一轮
就是 BFS 波前、轨迹更可读；"w ← extract"对应弹出，
"w ← insert successors"对应写回后的入队。spa 把
"transport 函数作用在合并结果上"内嵌在主循环里，本书
拆成 joinEnv + transferNode 两级——拆开是第 22 章
"映射格"与"传递函数"分层的代码投影，也让人工追踪
（16.6.2）能对每步单独验算。 spa 对边界条件一笔带过
（"给定 entry 的值"），本书用 entryEnv 与 entry 特判
把它做成结构（16.3.4）——将来第 40 章过程间分析要给
边界条件加维度，有结构才好扩展。

### 24.1.3 为什么求解值得独立成章

一个合理的疑问：迭代到不再变化，听起来不过十行代码的
循环，为什么配得上独立一章、还配上一整节正确性论证？
三个理由。

**理由一：这十行代码是全部分析的公共内核。** 类型分析
（17–20 章）每章有自己的求解器（合一），换一个分析就要
重写；从本章起，求解器与分析解耦——第 25 章的常量分析、
第 26 章的四大 DFA、第 28 章的未初始化分析，全部复用
同一个 solveFixpoint 的模式，只换域与传递函数。公共内核
的正确性论证做一次、处处引用，这正是把"求解"独立成章
的工程理由：**把最容易写错的十行代码钉死一次**。

**理由二：错误的表现形态极其隐蔽。** 求解器写错（比如
漏了去重、漏了某个后继、比较只查部分变量）几乎从不崩溃、
从不报错——它只是安静地给出一个**偏 ⊤ 的次品**或者偶发
的**偏 ⊥ 的错误答案**。回归测试若只对结果文本，次品
照样全绿。防御手段只有两个：把正确性论证写清楚（本章
16.4），把论证的核心不变量变成断言（练习三）。两者都
要求论证本身被完整陈述过——这就是本章篇幅的去向。

**理由三：理论在这里完成最后一次抽象跃迁。** 前三章的
主角还是"符号"这个具体域；从本章起，主角换成"域、方程、
求解器"三元组本身。16.2.4 的三步主旋律、16.4 的夹逼
论证、16.5 的高度度量，全部以任意有限格为对象陈述——
也就是说，读完本章，读者已经掌握了抽象解释的**迭代
内核**，后面每一章都只是给它喂不同的域。第 53 章回望
时会发现：类型、符号、常量、指针，全都在同一个骨架上
奔跑，骨架就是本章。

把前后章节的关系钉在一张小地图上。向前看：第 21–23 章

## 24.2 不动点迭代的直觉：从底向上

### 24.2.1 ⊥ 的语义："还没有任何事实"

先校准一个贯穿全章的读法。符号格里的 ⊥（编码 −2）在两个
场合出现，含义不同但同源：**在变量上**，它表示"这个变量
此刻还没有任何已证明的符号信息"；**在程序点上**，它表示
"这个点还没有被计算过，或者还没有任何执行流到达过它"。
两者的公共语义是"零信息"——不是"零值"（那是 0），也不是
"任意值"（那是 ⊤），而是**什么都还没说**。三者在格上的
位置一目了然：⊥ 在最底，0 与 −、+ 同居中层，⊤ 在最顶；
"零值"与"零信息"差一整层，混用它们是初学格语义的第一
个陷阱。

这个语义决定了迭代的初始姿态：所有程序点从 ⊥ 出发（实现
里更省事——空映射就是全 ⊥），像一张白纸。随后的每一次
计算只往纸上写"由方程与已写内容**强迫**接受的事实"：
合并前驱用的是 join，它只可能把信息变宽（更不确定）；
传递函数是抽象算术，它把输入事实保守地转换为输出事实。
没有任何一步引入"凭空猜测"。因此，迭代结束时纸上的全部
内容都是方程组**可推导**的——而方程组可推导事实的最大
封闭集，按定义就是最小不动点。这个论证的骨架已经完整，
24.4 节把它写成严格的三段归纳。

### 24.2.2 与解算术方程组的类比

把方程组想象成算术方程组会有帮助，但要小心一处差别。
算术方程 `x = x + 1` 无解；数据流方程 `v₂ = transfer(v₄ ⊔ v₁)`
却总有解——因为格是有限的、传递是单调的，Knaster–Tarski
不动点定理保证单调函数在完全格上必有不动点，且最小不动点
可以从 ⊥ 迭代逼近得到。差别来自合并算子：算术里的 `+` 把
差异放大，格里的 `⊔` 把差异收拢到公共上界。循环在 CFG 上
是环，在方程组里表现为"变量出现在自己的右端"（v₂ 依赖 v₄，
v₄ 经传递回到 v₂）——同一件事在类型世界里触发 occurs 检查
而报错，在格世界里却平稳地收敛，因为 join 提供了"自我
引用可以安放"的容器。这是两条求解路线最深刻的一个分野：
**合一靠结构无环保终止，不动点靠格有界保终止**；前者拒绝
循环引用，后者消化循环引用。第四篇之后的所有分析都活在
后一个世界里。

类比还有更细的一层可用。算术方程组的求解是"解压缩"：
解集可能是一根直线（无穷多解）、一个点（唯一解）或
空集；格上方程组的"解"是全体不动点，Knaster–Tarski
说它们构成完全格——往往比"一个点"宽得多，而算法
刻意挑那个最细的（lfp）。为什么挑最细？因为分析的
用途在下游：报警、优化、审查，每一步都消耗精度，
起点粗一寸，下游宽一尺。lfp 的"最小"不是数学洁癖，
是**精度经济学**：不动点格里离 ⊥ 最近的那一层，就是
这套框架能给出的最高精度——除非换更高的域（第 30 章），谁也够不到更下面。

### 24.2.3 一次手推：为什么循环出口是 +

在进入算法细节之前，先把本章的招牌结果手推一遍，后面读
代码和追踪时心里有底。程序 sign1.tip 的循环体是
`y = 1; x = y + 1`。第一轮：循环头 v₂ 只有 entry 一个前驱
有效，状态全 ⊥；体里 y 被 1 定值为 +，x 被 y+1 定值为
+ ⊔ + = +（sAdd(+,+) = +）。回边把 v₄ = {x=+, y=+} 送回
循环头。第二轮：v₂ 合并 entry 的全 ⊥ 与回边的 {x=+, y=+}，
得 {x=+, y=+}（⊥ ⊔ + = +，⊥ ⊔ + = +）。体里重算：y 仍被
定值为 +，x 仍为 + ⊔ + = +——**没有新事实**，第三轮与
第二轮完全相同，迭代收敛。循环头是 {x=+, y=+}，沿前向边
流到输出点，`output x` 处 x=+。

注意循环头 x 的推导：它合并了"还没进过循环体"（⊥）与
"至少跑过一轮"（+）。join(⊥, +) = + 而非 ⊤——这正是格设计
的回报：⊥ 是 join 的单位元，"不知道"与"知道是 +"合并后
仍然精确地是"知道是 +"。假如当初把初始值选成 ⊤（"任意
值"），同样的循环会停在 ⊤：⊤ ⊔ 任何值都是 ⊤，循环头永远
携带最大不确定。从底出发与从顶出发，一个收敛到最准、
一个收敛到最糊——这就是 spa 说的"初始值选择决定你得到
最小还是最大不动点"的全部含义。

顺带把"若函数有形参"的情形推演一遍，因为 sign1 的 main
无形参、边界条件的角色被隐藏了。假设换成 `main(a, b) {…}`：
entryEnv 会把 entry 的环境置为 {a=⊤, b=⊤}——形参的
符号对分析器完全未知，⊤ 是唯一诚实的表达。这个 ⊤
会沿前向边流遍全图：任何 `a + b` 得 ⊤，任何与 a 相关
的赋值得 ⊤。**形参是符号域里"精度税"最重的地方**——
除非调用方的实参符号能被传进来，那是第 40 章过程间
分析的工作。entry 边界在无参 main 时是空环境、在有参
函数时是"形参全 ⊤"，两种形态都是"把调用方的信息
如实编码"：没有调用方，就没有信息，⊤ 就是信息的
如实形态。第 25 章的常量分析在同一位置会遇到同样的
选择，届时"常量传播对形参无能为力"的现象在此时此地
已经埋下伏笔。

### 24.2.4 不动点迭代的通用形状

把上面的手推抽象掉具体域，得到一个对第四篇所有分析通用
的算法形状：

1. 给每个未知量赋初值 ⊥（边界条件处赋特值）；
2. 反复用方程右端重算每个未知量；
3. 某轮没有任何未知量变化时停止，当前赋值即最小不动点。

第 30 章的区间分析把这个形状照搬过去，会在第 3 步跌倒
——区间格高度无穷，上升可以永远继续——那时需要加宽算子
补救。第 42 章的 IFDS 把"未知量"换成"图上的路径边"，形状
不变。读者应当把这个三步形状当作第四篇的**主旋律**记住：
域可换、传递函数可换、合并可换，"从底向上迭代到不再变化"
这个骨架不变。

主旋律还有一条听不见的声部值得点名：第 3 步的"没有任何
未知量变化"是**全图谓词**——它要求每个点都安静，而
不是某个点安静。实现里把它落实成"队列空"，天然是全图
谓词；朴素实现里若用"某个点没变"当停止条件（初学者
常犯），迭代会在第一次安静处提前收工，交出半成品。
谓词的量词——"每个"还是"某个"——在自然语言里只差
两个字，在程序里就是收敛与次品的分界。三步主旋律的
每一步都值得这样抠一遍字眼：第 1 步"每个未知量"（不是
部分）、第 2 步"反复"（不是"一轮"）、第 3 步"没有任何"
（不是"没有某个"）——抠完之后，16.3 的代码为什么长成
那样，几乎全是必然。

### 24.2.5 Knaster–Tarski：定理本身

把 16.2.4 的直觉升格为定理。设 L 是完全格（任意子集都有
上确界与下确界；有限格自动完全），F: L → L 单调。则：

- F 的不动点集 Fix(F) = {x | F(x) = x} 在逐点序下本身构成
  完全格（特别地，存在最小不动点 lfp 与最大不动点 gfp）；
- lfp = ⊔ { Fⁱ(⊥) | i = 0,1,2,… }——从 ⊥ 反复施加 F 得到
  的链的上确界。

对本章，第二条中的"上确界"在有限格上就是"链在某处停住"。
"完全格"这个前提在有限格上自动成立：任意子集的上确界
至多是"全部元素的 join"，集合有限，join 有限次做完——
完全性在无限格里才需要单独操心。链 ⊥ ≤ F(⊥) ≤ F²(⊥)
≤ … 严格上升段有限（高度有限），停住处即 lfp。worklist
算法与这条定理的关系值得说清：
**定理保证停住的那个值是 lfp，算法保证我们在每一步都恰好
计算链上的下一项**——worklist 的"重算受扰点"不是这条链的
另一种走法吗？是的，但顺序不同：朴素迭代沿"全图一轮"为
单位走链，worklist 沿"扰动传播"为单位走链，两条路线的
中间项不同，停住的终点相同（合流性），总步数不同（16.8
的方向一、二都在优化这个数）。定理与算法的分工由此清晰：
**定理管终点，算法管路径**。

第一条（Fix 构成完全格）在本章的用处在 16.4.4：夹逼论证
需要"lfp 是最小的不动点"——若不动点集为空或无最小元，
夹逼失效。Knaster–Tarski 一次性把存在性与最小性都给出，
16.4 只需证明"算法停在不动点上"与"从不越界"两件事。

### 24.2.6 join 与 meet：一对对偶的读法

本章全程只用 join（⊔），但读者迟早会在文献里遇到 meet
（⊓，最大下界），提前把对偶关系铺好。在"事实"的读法下：

- **join 读作"或者"**：x=a ⊔ x=b 表示"a 或 b 都可能是 x
  的抽象值"——信息变宽，确定性下降，序上升。
- **meet 读作"并且"**：a ⊓ b 表示"同时满足 a 与 b 的最大
  信息"——信息收窄，确定性上升，序下降。

符号格上两个算子都好查：join 表本章已给（⊥ 是单位元、⊤
是吸收元）；meet 把两张表翻转——⊥ 吸收、⊤ 是单位元，
− ⊓ 0 = ⊥（没有整数既是正又是零）。对偶原理随之成立：
把一条关于 join 的真命题里的 ⊔ 换成 ⊓、≤ 换成 ≥、⊥ 换成
⊤，仍是真命题。lfp/gfp、从底迭代/从顶迭代、may 分析/
must 分析，全是这一对偶的具体化身——第 26 章的四大 DFA
里 may（活跃、到达）用 join、must（可用、非常忙）用 meet
（实现里记作交集），读者到时会看到对偶从修辞变成代码。

一个实用的辨认口诀：**问"这里可能是什么"用 join 从底走，
问"这里必然是什么"用 meet 从顶走**。两种问法都合法、都
可靠，精度与代价不同；分析设计者的第一个决定就是选一种
问法——选错的典型症状是"分析永远给出全集"（用 must 问了
一个 may 的问题）或"结果永远空集"（反之）。

对偶还提示了一个读代码的技巧：拿到任何一段分析代码，
先找它的合并算子在哪个函数、初值在哪一行——join 在
初值 ⊥ 旁、meet 在初值 ⊤ 旁，两个"指纹"一出现，这个
分析是 may 还是 must、它的不动点走哪一极，立刻定调。
第 26 章读者将用这个技巧在四组经典 DFA 的代码里秒判
阵营；现在先用它在 solve.cpp 上练手：joinEnv 与空映射
初值并排出现，may 分析无疑。

### 24.2.7 两变量环境格的形状：把积格画出来

16.2.1 说"程序点上的 ⊥"，16.5.1 说"环境格高度 2V"，两者
中间还缺一张具体的图：sign1 有两个局部变量 x、y，单变量
符号格 5 个元素，两变量的环境格就是它的笛卡尔积——25 个
元素、高度 4 的格。把它画出来不现实（25 个节点已经超出
哈斯图的可读范围），但它的骨架可以画：格的最底层是
(x=⊥, y=⊥)，最顶层是 (x=⊤, y=⊤)，从底到顶任何一条最长
链恰好走 4 步——x 从 ⊥ 升到 ⊤ 至多两步（⊥ → ±/0 → ⊤），
y 再走两步，积格的高度等于分量高度之和。

这张骨架图解释了 16.6 追踪里反复出现的现象。第一轮
沿前向边的写回，全是"从 (⊥,⊥) 向上走一格"的小步：
点 3 走到 (⊥,+)，点 4 走到 (+,+)。步 7 的回边合并把
点 2 从 (⊥,⊥) 直接推到 (+,+)——一次跳两格，因为两个
变量同时获得信息。第二轮的重算结果全部等于旧值：(+,+)
已经是这条链在循环头可达的上界，再无处可升。**每个点的
严格上升总量 ≤ 高度**这句话，在 25 个元素的格上就是
"每个点至多累计上升 4 格"。数一数 16.6 的追踪：七个点里
点 1 全程 ⊥（升 0），点 2 升 2 格（步 2 的 ⊥→⊥ 不算、
步 7 跳两格），点 3 升 2 格（步 3 一格、步 9 一格），点
4、5、6、7 各升 2 格——没有一个点超出预算 4。高度是
**每个点自己的链长预算**，不是全图写回次数的预算：一次
写回可以花掉多格预算（步 7 一步两格），而"预算 × 点数"
才是写回次数的上界（16.4.2 的 2PV 正由此而来）——这也
是回边合并比前向传播"更贵"的量化含义。

积格还有一个不显然的性质值得记下：它是**逐点格**——
序、join、meet 全部逐变量独立定义，两个环境可比较当且
仅当每个分量都可比较。这保证了"对某个变量的更新不影响
其他变量的序关系"，是 16.3.7 的 joinEnv 逐变量循环
合法性的理论根据；也是 16.4 论证里"环境格上的归纳"
能退化成"变量格上的归纳"的原因。

### 24.2.8 三行伪代码：主旋律的最小形式

收尾本节前，把 16.2.4 的三步形状压成三行伪代码，作为
全章的"记忆锚"。真实的 solve.cpp 是它的工程化展开，
每一处偏离都对应一个具体考虑：

- 把每个点置为 ⊥，把边界点置为特值；
- 只要还有点的右端可以重算，就重算它并与旧值比较；
- 全部相等时停止——当前赋值即最小不动点。

第一行的"边界点置为特值"在实现里不是初始化而是特判
（16.3.4）；第二行的"只要还有"在实现里是队列（16.3.4），
"重算并比较"在实现里是 join + transfer + 相等检查
（16.3.5）；第三行在实现里是"队列空"（16.3.6 的合流性
论证保证与"全部相等"等价）。**三行伪代码与工程代码之间
的每一个缺口，都是下一节要讲的一个设计决定**——读者
带着这张映射表进入 16.3，每段代码都知道自己在替哪行
伪代码站岗。

### 24.2.9 MOP 与 MFP：合并时机的两种哲学

spa 在第 4 章还埋了一个本章必须交代的概念对：**MOP**
（meet over all paths，沿所有路径合并）与 **MFP**
（maximal fixed point，最大不动点——术语历史的原因，
"maximal"在 may 分析语境下对应我们说的最小不动点，
读文献时按内容辨认，别按字面）。两者的差别只在**合并
发生的时机**：MOP 是理想主义——把程序每一条可能的执行
路径拿出来，沿路径逐点施加传递函数，最后把所有路径
在同一点的结果合并；MFP 是本章的算法——先在图上迭代
合并，路径的枚举被"不动点"这个代数对象替代了。

合并时机影响精度吗？影响，但方向微妙。若传递函数
**分配**（对任意 f：f(a ⊔ b) = f(a) ⊔ f(b)），先合并
后传递与先传递后合并结果相同，MFP = MOP——迭代法
一分不损地拿到理想值。若只**单调**不分配，一般的
不等式是 MFP ⊒ MOP 的抽象化读法：迭代结果可能比
路径理想值**更粗**。符号域的传递函数是哪一类？赋值
x = y + z 里 sAdd 不分配：sAdd(+, −) = ⊤，但取两个
具体环境分别算再加可能得到 + 与 −，join 起来是 ⊤ ⊔
⊤ = ⊤——碰巧一致；换个例子，sAdd(0, ⊤) = ⊤ 而分别
对 ⊤ 的两个成分 0 与 + 求 sAdd(0,·) 得 0 与 +，join
为 + ⊔ 0 = ⊤，仍一致……逐格验算可以确认：符号域的五张
表（join 与四则、比较）在两个参数上各自分配，所以本章的
MFP 就是 MOP，精度无折扣。但读者不要形成"迭代总是无损"
的错觉：第 30 章区间域的乘法分配性不成立，届时 MFP
与 MOP 的差距会以具体数字现身，第 32 章的路径敏感
分析则是从另一个方向逼近 MOP 的努力。

把 MOP/MFP 与 16.2.5 的 Knaster–Tarski 连起来：定理
保证迭代到达 MFP；分配性（或其缺失）决定 MFP 与 MOP
的距离；而"路径爆炸"决定了 MOP 本身不可计算（路径数
指数增长，这正是 MFP 存在的全部理由——**用代数把
组合爆炸折叠成有限迭代**）。三个概念各管一段，合起来
就是数据流分析精度的完整坐标系。

## 24.3 worklist 算法逐段讲解

朴素迭代（16.2.4 的第 2 步"重算每个未知量"按固定顺序扫全
图）的正确性毫无问题，代价却冤枉：绝大多数点在绝大多数
轮次里输入没变、重算是纯浪费。worklist 算法的全部改进
就在一句话：**只重算"输入可能变了"的点**。用一个队列维护
"待重算"集合，某点的值变化时把它的所有后继入队——后继的
输入（前驱状态）因此可能变化。队列空了，说明没有任何点
的输入还在变，迭代收敛。

本节按执行时间轴拆解 solve.cpp。先看接口，再看实现分段。

### 24.3.1 接口：solve.hpp

```cpp
// eqs 仅用于确认"求解的是第 23 章那组方程"；依赖关系取自 CFG。
PointEnv solveFixpoint(const Cfg &cfg, const ProgramA &program,
                       const std::vector<MonoEq> &eqs);
```

三个参数各司其职。`cfg` 提供图结构——谁是谁的前驱后继、
每个点上是什么语句；依赖关系完全从图上取，这是"方程组
就是 CFG 的另一种读法"的直接体现。`program` 提供入口
边界条件所需的函数形参表（entryEnv 要把形参置 ⊤）。
`eqs` 是第 23 章的方程组——细看实现会发现它被
`(void)eqs` 显式弃用：**方程组以 CFG 为唯一事实来源**，
第 23 章生成方程、本章求解，两者消费同一张图，天然
一致；保留参数是为了让接口把"解的是哪组方程"写在签名上，
读者与维护者不必翻实现就能确认规格对应。把规格写进接口
签名、哪怕实现暂时不消费，是规格与实现保持锁定的低成本
手段——一旦未来某个分析需要显式方程对象（第 43 章的 IDE
就是），接口不用动。

返回类型 `PointEnv`（程序点 → 抽象环境）沿用第 21 章。
值得强调映射的"缺键即 ⊥"约定在本章被赋予了正式身份：
它就是"初始值全 ⊥"的实现形态——空映射不必显式填满所有
程序点，缺键读取按 ⊥ 解释即可。这个约定在第 21 章只是
打印的便利，在本章成了算法的正确性组件（16.4 的归纳
基底用它）。

### 24.3.2 邻接表：neighborMap

```cpp
std::map<int, std::vector<int>> neighborMap(const FunCfg &f, bool successors) {
    std::map<int, std::vector<int>> r;
    for (const auto &[from, to] : f.edges) {
        if (successors) r[from].push_back(to);
        else r[to].push_back(from);
    }
    return r;
}
```

一个函数、一个布尔开关，同时服务前驱表与后继表：successors
为真时按 `from` 归档（出边），为假时按 `to` 归档（入边）。
CFG 的边表是 `vector<pair<int,int>>`，逐边扫描建表是 O(E)；
每个函数建一次、整个求解过程复用，摊销后可忽略。选
`std::map` 而非 `unordered_map` 是全书一贯的确定性纪律：
遍历顺序固定，迭代轨迹可复现，expected 文件才稳定。

注意第 11 章 CFG 构建已用 set 对边去重，本章的邻接表
继承的是一份无重复的边表；但求解器**没有**依赖这一
事实——即便边表真有重复，同一点出现在某前驱列表两次
也只是 join 两次同一个状态，结果不变，只是浪费一次
合并。正确性不依赖上游的去重，是比"上游保证过"更强
的安心。

### 24.3.3 初始化：一张白纸与一个入口

```cpp
PointEnv cur;
for (const FunCfg &fc : cfg.funs) {
    ...
    std::deque<int> wl{fc.entry};
    std::set<int> in{fc.entry};
```

`cur` 是当前解——全 ⊥ 的实现形态就是**空映射**：任何点
第一次被重算前都按 ⊥ 参与 join。`wl` 是 worklist 本体，
`std::deque` 提供两端口；初始只有 entry 一个点，因为
"输入可能变了"的点里，只有 entry 是无中生有（它的值从
⊥ 变为边界条件）。`in` 是队列成员集合：入队前查它防止
同一点占多个位（16.3.5 详述）。

每个函数独立跑一遍求解循环。函数之间没有数据流（调用
在 CFG 模型里是独立的函数子图，过程间分析是第 40 章的
主题），所以逐函数求解与一次性求解全程序等价，只是把
队列的生命期按函数切开，逻辑更清晰。

一个值得停半拍的设计问题：队列里放的是**点**，能不能
放**边**？可以——"边 worklist"（把 (from, to) 作为
工作单元，from 变了沿边 to 重算）是稀疏数据流的常见
形态，好处是重算可以直接跳过"点变了但这条边的合并
结果没变"的情形，坏处是工作单元翻倍（E vs P）、去重
集合跟着翻倍。点的 worklist 重算时重合并全部前驱，
边的 worklist 只重算一条边——前者实现简单、后者更省
重算。TIP 的程序小到二者无差，教科书与本书都选点；
第 32 章路径敏感分析按边分支状态，会自然过渡到边
视角，读者届时可以回看今天这个"本可二选一"的岔口。

### 24.3.4 弹出与重算：方程的右端

```cpp
int p = wl.front();
wl.pop_front();
in.erase(p);
const CfgNode &node = fc.nodes.at(p);

SignEnv nv;
if (node.kind == CfgNode::Kind::Entry) {
    nv = entryEnv(*decl);  // 边界条件不随前驱变化
} else {
    SignEnv before;
    auto pit2 = preds.find(p);
    if (pit2 != preds.end())
        for (int q : pit2->second)
            if (auto it = cur.find(q); it != cur.end())
                before = joinEnv(before, it->second);
    nv = transferNode(node, before);
}
```

弹出的点 p 要重算的正是第 23 章方程的右端。两个分支：

**entry 特判。** 边界条件是方程组里唯一不由前驱决定的点
（第 23 章打印为 `v1 = entry boundary (params = ⊤)`），
直接赋 `entryEnv(decl)`——形参逐个置 ⊤，局部变量不出现
（读取时按 ⊥）。把特判放进重算分支而不是初始化，保证
entry 被反复弹出时（理论上不会，见下）也稳定返回同一个
边界值，不依赖"入队恰好一次"的巧合。

**一般点：先合并、再传递。** `before` 从全 ⊥（空环境）
出发，逐个 join 前驱的当前状态；`cur.find(q)` 查不到的
前贡献 ⊥，而 joinEnv 与 ⊥ 合并等于没合并——所以代码里
"查不到就跳过"与方程里的"与 ⊥ join"严格等价。这是"缺键
即 ⊥"约定的第二处消费点（第一处是初始值），两处必须
保持同一解释，16.13 的注意点 2 会再敲一次。合并完成后
`transferNode` 施加语句的抽象语义：赋值点更新目标变量，
其余点（分支、输出、返回、出口）原样透传——这些透传
正是第 23 章方程 `v5 = v2`、`v6 = v5` 的代码形态。

### 24.3.5 比较与写回：变化的传导

```cpp
auto old = cur.find(p);
if (old == cur.end() || old->second != nv) {
    cur[p] = nv;  // 单调框架保证 nv ⊒ 旧值
    auto sit = succs.find(p);
    if (sit != succs.end())
        for (int s : sit->second)
            if (!in.count(s)) {
                wl.push_back(s);
                in.insert(s);
            }
}
```

`nv` 与旧值相等时什么都不做——这是 worklist 的灵魂：
**值没变的点不传播扰动**。不等时写回并入队全部后继。
两个细节值得放大。

第一，`old == cur.end()` 与 `old->second != nv` 合并成
一个条件：第一次计算（旧值为全 ⊥）视作"变了"。对 entry
这是事实（⊥ → 边界条件）；对一般点，若重算结果恰好是
全 ⊥（例如不可达分支里的赋值），也算"没变"而不入队后继
——正确，因为全 ⊥ 的后继合并里它本来就贡献 ⊥，跳过与
不跳过等价。

第三，写回的**原子性**读法：`cur[p] = nv` 之前，旧值
一直有效；之后，新值立即可被任何后继的重算读到。工作
队列单线程推进，"读到一半的值"不存在；将来若把弹出
并行化（16.3.11 提过的波前并行），写回就需要细粒度
同步或按 SCC 分片——现在的十行代码不含任何锁，恰恰
因为它的每一步都假设了单线程的原子读写。并行化不是
把锁加上去就完事，而是要重新审计这里的每个"读-比-写"
序列，这是第 53 章 AND 并行分析的一课，先在此立个
牌子。

第二，`in` 集合的防重语义。同一时刻队列里每个点至多一份
拷贝；弹出时 `in.erase(p)` 之后，p 仍可被再次入队（自己的
变化传导回来时）——sign1 的循环头 2 号点就被入队两次、
弹出两次（16.6 的追踪表可查）。防重避免的是"同一扰动
被排队多次"的爆炸，而不是"同一点多次重算"（后者是算法
需要的）。去掉 `in`，队列长度上界从点数恶化到"每次写回
的后继数之和"，最坏指数级的重复劳动；保留它，队列长度
恒 ≤ 点数，重算次数仍由格高度控制（16.5）。

### 24.3.5a 弹出序的一览：队列在 13 步里的涨落

（本节与 16.6.2 配合阅读。）把队列长度按步记下来，能
看到 worklist 的"呼吸"。每次弹出前的队列长度依次为
1, 1, 2, 2, 2, 2, 2, 3, 2, 2, 2, 1, 1——初始 1（只有
entry），前向传播期稳在 2（一点被弹出、一到两个后继
补位），步 8 前达到峰值 3（回边引爆后 3、5、7 同时
在队），此后单调回落，终值 0。长度曲线的形状由"入队
速率 vs 消费速率"决定：前向传播阶段两者相抵，回边
引爆后入队一度反超，收敛前夕（步 11 的"="不补位）
消费独走。工业求解器的性能调优日志里，队列长度曲线
是最便宜的诊断图——曲线早早归零而结果未出，说明有
点从未入队（前驱边漏建）；曲线只涨不消，说明扰动在
环上自激（单调性被破坏）。两条曲线病症分别对应
16.4.3 与 16.4.8 的两种错误，读图即知病灶在哪一层。

### 24.3.6 队列顺序不影响终态

FIFO（`push_back` + `front`）只是众多可行顺序之一。换成
LIFO（栈）、换成优先队列（按点号或按启发式），终态都
相同——因为终态是方程组的最小不动点，而不动点由方程组
唯一决定，与到达它的路径无关。这正是第 22 章合流性思想
的算法投影：格上的单调迭代"殊途同归"。顺序影响的只有
**迭代次数**：逆后序（reverse postorder，先算后继再算
前驱的拓扑倾向序）在实践中最少重算，随机顺序最多；FIFO
介于两者之间，且轨迹完全可预测——本章 16.6 的 13 步追踪
之所以能逐字写对，靠的就是 FIFO 的确定性。教学快照选
FIFO 的理由与第 22 章选朴素合一相同：透明换速度。

还有一条隐含的公平性保证值得写明：队列非空时循环必然
推进（弹出一个点），且每次写回至少让一个点严格上升；
由 16.5 的有界上升论证，写回总次数有限，故队列必然清空
——**算法不需要"防止死循环"的任何显式机制**，单调性
与有界性替我们守着。

"顺序不影响终态"还能给出一个两行的证明草图，比直观
更硬。设两种顺序分别收敛到 D₁ 与 D₂（各自都是不动点，
由 16.4.3）。关键在 16.4.1 的不变量对**任何**调度同时
成立：按顺序一执行时，D₂ 的值作为一组"假想解"同样
满足 cur ⊑ D₂（每个写回只消费单调操作与假想解的当前
值），故 D₁ ⊑ D₂；对称地 D₂ ⊑ D₁；故相等。这个论证
甚至不需要"调度公平"之外的前提——单调性把所有调度的
终点焊死在同一个 lfp 上。顺带一提，"公平"仍是必需的：
一个永不弹出某点的恶意调度会让算法挂在半空，FIFO、
LIFO、优先队列都自动公平，所以实践中从未碰过这个前提。

### 24.3.7 重算的两块基石：joinEnv 与 transferNode

求解器本身不含任何符号语义——语义全部住在第 21 章的
两个函数里。读它们的代码形态有助于确认"求解与语义解耦"
不是一句空话。

```cpp
SignEnv joinEnv(const SignEnv &a, const SignEnv &b) {
    SignEnv r = a;
    SignLattice lat;
    for (const auto &[k, v] : b) {
        auto it = r.find(k);
        r[k] = it == r.end() ? v : lat.join(it->second, v);
    }
    return r;
}
```

joinEnv 是映射格 join 的直接实现（第 22 章 maps 构造的
特化版）：以 a 为底拷贝，b 的每个键并进去——a 里没有的
键直接继承（与 ⊥ join 等价），有的键逐个查符号 join 表。
注意它**不删除**只在 a 里出现的键：缺键即 ⊥ 的约定下，
"a 有 k、b 没有 k"合并后 k 的值就是 a 的值，无需特殊
处理。三行代码承载了"映射格逐点合并"的全部语义，第 22 章的通用 maps 构造在这里以手写特化的形态服役——特化的
理由是性能（避免反复构造 map）与可读性，语义与通用版
逐点一致。

```cpp
SignEnv transferNode(const CfgNode &node, const SignEnv &in) {
    if (node.kind != CfgNode::Kind::Assign || !node.stmt) return in;
    const auto *a = dynamic_cast<const AssignS *>(node.stmt);
    const auto *target = dynamic_cast<const VarRef *>(a->target.get());
    if (!target) return in;  // *p / r.f 目标：第 45 章指针分析之前保持环境不变
    SignEnv out = in;
    out[target->name] = evalExprSign(a->value.get(), in);
    return out;
}
```

transferNode 的三个分支对应三类语句的抽象语义：非赋值
点透传（分支、输出、返回、出口——它们不改变变量绑定）；
赋值但目标不是普通变量（*p、r.f 这类左值）也透传——
第 21 章的保守决定，指针与记录目标的抽象需要指针分析
（第 45 章）做底座，此前"假装没看见"是 sound 的（不更新
抽象状态只会更保守，不会更错）；普通赋值更新目标变量，
右值的符号由 evalExprSign 递归计算——它沿表达式树下降，
字面量查 signOfLiteral、变量查表（缺键 ⊥）、input 置 ⊤、
二元运算查三张抽象算术表。求解器的每一步重算最终都
落到这两个函数上；16.4 的单调性前提由此兑现——joinEnv
逐点单调、evalExprSign 按表单调、组合单调。

顺带回答一个实现层的常见疑问：这里的语句与表达式分发
为什么用 dynamic_cast 而不是访问者模式（visitor）？
第 12 章的 irgen 用了 visitor（IRGen 类对每类语句一个
gen 重载），本章却是一串 dynamic_cast——两种风格在
同一本书里并存，是刻意的对照。visitor 适合"操作多、
类型稳定"的场景（irgen 的每一种 IR 节点都要装配），
dynamic_cast 适合"操作少、只关心几种类型"的场景
（transferNode 只对 Assign 感兴趣，其余全透传）。为
四种透传语句各写一个空的 visitor 重载，代码量翻倍而
信息为零——风格的选择标准从来不是"哪种更高级"，而是
**哪个消费者真正需要哪些分支**。

### 24.3.9 一次重算的全链路：步 5 的显微镜

16.6.2 的追踪表把每步压缩成三行；本节把其中信息量最大
的一步——步 5（弹出点 4，计算 x = y + 1）——放到显微镜
下，看清一次重算穿过的全部层次。此刻的 cur 是
`{1:{}, 2:{}, 3:{y=+}, 5:{}, 6:{}}`（队列内容以 16.6.2
追踪表的步序为准），我们只看点 4 这次重算本身：

1. **图查询**：`fc.nodes.at(4)` 取出结点——kind=Assign、
   stmt 指向 `x = y + 1` 的 AssignS。一次 map 查找。
2. **前驱查询**：`preds.find(4)` 得 `[3]`——4 号点只有
   3 号一个前驱（它不在任何循环头的汇流处）。
3. **状态读取**：`cur.find(3)` 命中 `{y=+}`；若此刻 3 号
   还没算完，缺席即 ⊥、跳过——代码里那句 `if (auto it =
   cur.find(q); it != cur.end())` 就是"缺键即 ⊥"的
   字面形态。
4. **合并**：joinEnv(⊥, {y=+})，b 侧只有一个键 y，a 侧
   空映射无此键，直接继承——before = {y=+}。单前驱点
   的"合并"全程只是拷贝。
5. **传递**：transferNode 识别 Assign 且目标是 VarRef
   x，进入更新分支，调 evalExprSign 展开 `y + 1`。
6. **表达式求值**：Binop(Add) 先递归左子树 VarRef y——
   查 before 得 +；再右子树 IntLit 1——signOfLiteral(1)
   = +；查 sAdd(+, +) = +。
7. **写回**：out 在 before 的基础上写入 out[x] = +，
   得 {x=+, y=+}。与 cur[4]（缺席）比较，`old ==
   cur.end()` 成立，写回、入队后继 2。

九个层次里，属于"求解器"的只有 1–4 与 7（图查询、
合并、写回），属于"语义"的是 5–6（传递与求值），属于
"数据结构"的是全部的 map 操作。**层次之间的边界就是
第 23 章方程组里"结构"与"右端"的边界**——方程 v₄ =
v₃[x := (+ y 1)] 的三个成分（左端、依赖、右端表达式）
在这九步里各归其位。读者以后调试任何 worklist 问题，
都建议做一次这样的显微镜练习：把出错的那次重算从头
走一遍，八成问题出在第 3 步（缺键约定不一致）或第 7 步
（比较漏了某个变量）。

### 24.3.10 TIP.g4 在链条中的位置

嵌入区的 TIP.g4 是前端五站点的源头，值得在求解器视角
下再看一眼。语法里与本章直接相关的三条产生式：表达式
产生式允许 `input`（InputE）、字面量（IntLit）、变量
引用（VarRef）与五种二元运算（Binop）——这四类恰好
一一对应 evalExprSign 的四个 dynamic_cast 分支；语句
产生式允许赋值、输出、条件与循环——对应 transferNode
的透传与更新两类行为；函数产生式规定形参表——对应
entryEnv 的边界条件。**语法的每一条在分析器里都有一个
消费者，没有剩余**；反过来，分析器的每个分支也都有一条
语法来源。这种双向覆盖不是巧合，而是"保守近似从具体
语义出发"的结构性保证：语法长出一棵树，树决定传递
函数要处理什么——多一条语法没被处理，要么显式透传
（sound，如函数调用返回 ⊤），要么就是漏洞。

一个有意思的观察收尾：`while (input > 0)` 的条件表达式
`(> input 0)` 在 expected 输出里被原样打印，但它**从未
被求值**——分支点透传，条件里的 `input > 0` 这个比较
不进入任何符号计算。初学者常在这里困惑："条件不是
决定了循环走不走吗，分析怎么不管它？"答案是：符号
分析不分路径，所有后继一视同仁（第 32 章的路径敏感
分析才会把"沿真边""沿假边"分开）；条件表达式的信息
在 16 章的框架里只体现在**控制流形状**上（分支点有
两个后继），不在数据流值上。这也是第 21 章把条件
打印出来、却不为它计算符号的原因——打印是给人看的
路标，计算是另一回事。

### 24.3.11 worklist 与图算法的血缘

把符号语义暂时忘掉，worklist 循环的骨架是任何一个
图算法课读者都见过的东西：从一个起点出发，反复"取一个
待处理结点、处理、把新触达的结点加入待处理集合"。
这与广度优先搜索（BFS）的队列循环同构——事实上，
当每个结点只需处理一次时（比如"从 entry 可达的结点
集合"这个平凡的分析），worklist 循环**就是** BFS；
FIFO 队列让它天然带着 BFS 的波前形状，16.6 的
"第一轮沿前向边铺满"正是 BFS 波前在 CFG 上的呈现。

更深刻的特例是拓扑序。若 CFG 无环（没有循环的程序），
每个结点的状态只依赖前驱、前驱不回头依赖它——按
拓扑序处理一遍，每个结点弹出时全部前驱已是终值，
一遍收敛，写回次数恰好 P。此时"不动点迭代"退化成
"拓扑遍历"，这也是方向二（SCC 分解）的原理：把一般
图拆成"无环部分 + 循环分量"，无环部分按拓扑一遍过，
只有循环分量内部需要真正的迭代。**迭代法的一切开销
都是环带来的**——这句话反过来给了"循环携带依赖"
一个定量的面孔：sign1 的 13 步里，去掉回边 4→2 后
一遍拓扑只需 7 步，多出的 6 步全部为环买单。

血缘关系还有工程上的回馈。图算法的成熟技巧可以
整体移植：邻接表预计算（本章的 neighborMap）、位图
标记（in 集合）、波前并行（多线程弹出无冲突点，第 53 章 AND 并行的雏形）。反过来，数据流求解器也回馈了
图算法社区一个经典问题形态：**单调约束系统上的不动点
求解**在约束传播、类型推导与形式验证的引擎里到处出现，
worklist 都是标准解。多个社区共享算法、各用各的词汇
——读文献时按结构认亲，别被术语带偏。

## 24.4 正确性论证

定理（worklist 求解的可靠与最优）：设方程组由 CFG、边界
条件与单调传递函数族构成（第 23 章已证每条传递单调、
join 单调、复合单调）。solveFixpoint 终止，且终止时的
`cur` 恰为该方程组在点序（逐点 ≤）下的最小不动点。

论证分四步：不变量、终止、终止时是不动点、且是最小的。

### 24.4.1 不变量：cur 永远不超过最小不动点

**断言：任意时刻，对每个已写入 `cur` 的点 p，
cur[p] ⊑ lfp[p]**（lfp 记最小不动点；未写入即 ⊥ ⊑ 任何值，
自动满足）。对写回次数归纳。

基底：初始 `cur` 为空，全 ⊥，平凡成立。

归纳步：某次写回把 cur[p] 更新为 nv。nv 由两部分构成：
前驱当前值的 join 与传递函数。由归纳假设，每个前驱的
当前值都 ⊑ lfp 的对应值；join 单调，故 before ⊑ join(lfp
前驱值)；传递单调，故 nv = transfer(before) ⊑ transfer(
lfp 前驱的 join)。而 lfp 是**不动点**——它在 p 点的值
恰好等于 transfer 作用于 lfp 前驱的 join（这正是第 23 章
方程在 lfp 处成立的意思）。所以 nv ⊑ lfp[p]，写回后
不变量保持。

这一步是全章最需要慢读的地方：它用了一次"lfp 是不动点"
（方程在 lfp 处取等）和两次单调性（join、transfer 各一）。
单调框架的三个组件各被用到恰好一次，谁的单调性缺失论证
就在哪里断——这也是第 23 章花整章证明单调性的回报所在。

抽象论证读完，用 16.6 的 13 步把不变量**逐次落实**一遍
——lfp 按追踪终态代入（点 1 为 ⊥，点 2–7 为 {x=+,y=+}），
检查每次写回是否满足 cur[p] ⊑ lfp[p]：

| 步 | 写回点 | 写回值 | lfp 值 | ⊑ 成立？ |
|---|---|---|---|---|
| 1 | 1 | {} | {}（⊥） | ✓ |
| 2 | 2 | {} | {x=+,y=+} | ⊥ ⊑ 任意 ✓ |
| 3 | 3 | {y=+} | {x=+,y=+} | y:+⊑+，x:缺即⊥ ✓ |
| 5 | 4 | {x=+,y=+} | {x=+,y=+} | 逐项相等 ✓ |
| 7 | 2 | {x=+,y=+} | {x=+,y=+} | ✓（这次是"顶到"） |
| 9 | 3 | {x=+,y=+} | {x=+,y=+} | ✓ |

（未列出的步 4、6、8、10、12、13 同型，留作自查。）
表的读法：前三步的写回值**严格低于** lfp——迭代从未
承诺一步到位，只承诺不越界；步 7 起，被回边"顶开"的
点逐个追平 lfp。所谓收敛，就是这张表的最右列从
"⊑"逐行变成"="的过程——**夹逼模板的下半段（16.4.3
的"终止时是不动点"）负责保证它最终全部变成 =**。

### 24.4.2 终止：写回次数有界

符号格高度为 2（最长链 ⊥ < − < ⊤，两条严格上升边）；
V 个变量上的环境格是积格，高度 2V；一次环境写回对应
积格上的一次严格上升（`old->second != nv` 且框架保证
nv ⊒ 旧值——每次写回要么第一次写入、要么严格上升）。
单点的环境至多严格上升 2V 次，P 个点共至多 2PV 次写回。
每次弹出至多引发一次写回，弹出次数有界，队列必然清空。

"框架保证 nv ⊒ 旧值"值得单独停一下：nv 是 transfer(join(
前驱当前值))，旧值是**上一次**的同型计算结果。两次计算
之间，只有某些前驱的值上升了（归纳于时间轴），join 单调
所以合并结果上升，transfer 单调所以 nv ⊇ 旧值。链条上的
每一环都是单调性，无一例外。

### 24.4.3 终止时是不动点

队列清空意味着：最后一次对每点的重算结果等于其存储值
（否则会写回并入队后继，队列就不会空）。对每条方程逐一
核对：方程右端 = transfer(join(前驱 cur 值)) = 最后一次
重算的 nv = cur[p] = 方程左端。全部方程满足，cur 是
方程组的不动点。

注意论证只用了"队列空 ⇒ 每点最近一次重算未被修改"。
队列空时可能有些点从未被重算过（不可达点）——它们的
方程右端合并出的也是全 ⊥（前驱们要么不存在、要么也全 ⊥），
与"未存储即 ⊥"一致，方程同样满足。不可达点停在 ⊥ 不是
缺陷而是特性：⊥ 正是"没有任何执行流到达"的抽象，第 25 章
的常量分析会把不可达点显式标为 BOT 并用于死代码判定。

### 24.4.4 最小性：三段收拢

三个事实拼起来：cur ⊑ lfp（16.4.1，全程保持）；cur 是
不动点（16.4.3）；lfp 是**最小的**不动点（Knaster–Tarski
保证存在，第 23 章在方程组语境下复述）。若 cur 严格小于
lfp 于某点，cur 是一个比最小者更小的不动点——矛盾。故
cur = lfp。可靠（是不动点）且最优（是最小的那个），定理
证毕。

把论证压成一句话带走：**从 ⊥ 出发、只用单调操作、收敛
即停——停下来的东西既不超过最小不动点（从未越界），又
是不动点（不再变化），所以就是它。**

### 24.4.5 与第 19 章正确性论证的对照

第 19 章证明合一"成功当且仅当有解"，本章证明 worklist
"收敛到最小不动点"。两个论证共享一个模式：**单向夹逼**。
合一侧：绑定表从空出发只增不改，任何时刻都不超出任何
解（绑定保持旧等式），终止时所有等式满足（每条都处理
过），故恰好是一般解。本章侧：cur 从 ⊥ 出发只升不降，
任何时刻不超出 lfp，终止时是不动点，故恰是 lfp。"不超过
上界 + 终止时达到下界要求"的两段式在两处一字不差地重演。
读者将来为任何新分析写正确性论证（第 24、27、39 章都要
写），照这个模板即可：先找"永不越界"的不变量，再证
"停止时已满足全部要求"。

### 24.4.6 论证的引理清单与复用地图

把 16.4 用到的全部前提清点一遍，做成一张"借据清单"——
将来任何复用本章求解器的分析（第 25 章起），只需核对自己
满足同样的借据：

1. **格是完全格且高度有限**（Knaster–Tarski 给不动点，
   高度给终止——16.5.1）；
2. **join 单调且交换结合**（joinEnv 逐点消费它）；
3. **每条传递函数单调**（transferNode/evalExprSign 按表
   单调，第 21 章的表可逐格核对）；
4. **边界条件是常量**（entryEnv 不依赖图状态）；
5. **相等判定可靠**（环境的 operator==，写回分支消费它）。

五条借据中，1、2 是域的义务，3、4 是分析的义务，5 是
实现的义务。第 25 章换常量域时，1 会出问题（常量格在
TIP 的整数上高度无穷）——届时借据清单的价值立刻显现：
哪一条断了、需要什么新机制（加宽）来补偿，一目了然。
正确性论证写成"借据清单 + 夹逼模板"的组合，正是为了让
"换域"成为一次可审计的操作而不是一场祈祷。

### 24.4.7 四步论证的义务矩阵

把四步各自的"消费"与"产出"列成矩阵，读者复查任何一步
时不必重读全文，直接定位它依赖什么、又给后续步骤留下
什么：

| 步骤 | 消费的前提 | 产出的结论 |
|---|---|---|
| 16.4.1 不变量 | join 单调、transfer 单调、lfp 是不动点 | 任何时刻 cur ⊑ lfp |
| 16.4.2 终止 | 高度有限、写回 = 严格上升 | 写回次数 ≤ 2PV |
| 16.4.3 不动点 | 队列空、缺键即 ⊥ 的一致读法 | 终态满足全部方程 |
| 16.4.4 最小性 | Knaster–Tarski 最小性、前两步结论 | 终态 = lfp |

矩阵读法有二。横看任意一行：前提全部来自第 23 章（单调
性、方程语义）或 16.2.5（Knaster–Tarski）——**本章没有

恰好是下一行的"消费的前提"的首项——链条首尾相接，没有

cur 映射里缺席的键、joinEnv 对缺席键的跳过、printPointEnv
对缺席键的打印，三处必须对"缺席 = ⊥"达成一致，否则
16.4.3 的"方程同样满足"就建立在流沙上。数学论证中夹着
一条实现约定，这提醒我们：**程序正确性论证的边界永远
延伸到实现约定的最深处**，第 24.12 节的注意点清单正是
为这些约定设立的登记处。

### 24.4.8 反面教材：单调性被破坏时会发生什么

论证的每一步都在消费单调性；把它抽走看算法如何塌方，
是检验理解深度的最快方式。构造一个故意反单调的传递
函数 f：f(⊥) = ⊤，f(⊤) = ⊥，中间三个值随意指定。
把它安在 sign1 的循环体上（比如让点 4 的传递取这个
f），worklist 会发生什么？

第一波：点 2 由 entry 得 ⊥，f(⊥) = ⊤ 写入点 4，扰动
沿回边把 ⊤ 送进循环头。第二波：循环头合并得含 ⊤ 的
环境，f(⊤) = ⊥ 写回点 4——**值下降**了。下降触发
新一轮扰动：循环头重算，又回到不含 ⊤ 的状态，f(⊥)
再次产出 ⊤……算法在 ⊤ 与 ⊥ 之间**振荡**，永不收敛
——16.4.2 的"写回 = 严格上升"前提被破坏，高度预算
耗尽的保险丝失效。更阴险的变体是"下降但绕回原值"：
f 让状态走 a → b → a 的循环，同样不收敛。还有一种
更坏的情形：f 不单调但碰巧收敛，终值却**不是任何
正确意义上的答案**——16.4.1 的"不越过 lfp"论证第一
步就失效了，收敛值可能包含无根据的断言（f(⊥) = ⊤
正是凭空断言的来源：⊥ 是"没有输入信息"，从"没有
信息"推出"任意值"在格上是上行、在逻辑上是僭越）。

这个反面教材给出一条工程军规：**自定义传递函数时，
单调性不是可选的审美，而是驱动循环的物理前提**。
第 23 章逐格验证五张表单调，就是在为本章的收敛性
出示证明；将来任何新域（区间、路径、指针点集）的
传递函数上岗前，都要过同一道单调性验收。验收方法
也顺手给出：对有限格可穷举全部 (a, b, a ⊑ b) 组合
断言 f(a) ⊑ f(b)——lattice_demo 的自测骨架稍加改造
就是一台单调性验收机，第 30 章会真的把它开起来。

## 24.5 终止性与复杂度

### 24.5.1 格高度：终止性的度量

16.4.2 的论证里藏着本章最重要的一个量：**格高度**——最长
严格上升链的边数。符号格高度 2；V 个变量的环境格高度 2V；
一般地，有限格的积格高度是各分量高度之和。高度把"迭代
会停"从祈祷变成定理：只要每步严格上升、上升空间只有
高度那么多格，就必然在有限步内无路可走。

不同域的高度天差地别，这直接预示了第四篇的分析难度谱。
符号格：2，常数——符号分析便宜。布尔格（第 26 章幂集的
基础域）：1。幂集格（全集 n 个元素）：n——四大 DFA 的
代价随事实数线性。常量格（int 上的扁平格）：所有整数加
⊤⊥——**无穷高**，朴素迭代不再保证终止，第 30 章区间格
同样无穷，第 31 章的加宽/收窄就是为它们准备的。读者可以
用"这个格多高"作为拿到任何新抽象域后的第一反应——它
同时回答"迭代贵不贵"与"会不会停"两个问题。

高度的计算有三条常用规则，把"拿到新域先问高度"变成
机械操作。规则一（链）：最长链的高度按"数跳数、不数
点"计——符号格的最长链 ⊥ < − < ⊤ 是三个元素两跳，
高度 2；若 n 个元素排成一条链，高度是 n − 1。规则二
（积）：积格高度
= 各分量高度之和——环境格 2V 直接由此而来。规则三
（映射）：定义域 D 上的映射格，若陪域高度 h 且 D 有限，
映射格高度 = |D| × h——它是规则二对"每个变量一个
分量"的重新表述。三条规则覆盖了本书前 28 章的全部域；
唯一要动手分析的只剩第 42 章 IFDS 的产品格与第 45 章
的点对格，届时再补。

### 24.5.2 复杂度：重算次数与单次代价

把 16.4.2 的界算细。设 P 个程序点、V 个变量、E 条边。

**重算（弹出）次数**：每次写回至多入队 out-degree 个后继，
写回总数 ≤ 2PV，故入队总数 ≤ 2PV·d̄（d̄ 平均出度，≤ 3 对
结构化 TIP），弹出同数。headline 结论：**重算次数
O(P·H)，H 为格高度**——即 spa 所说的 O(点数 × 格高) 量级。

**单次重算代价**：合并前驱 O(入度 × V) 次符号 join，每次
join O(1)（查表）；比较新旧 O(V)；合计 O(V)。邻接表查询
O(1)（map 已建好）。

**总代价**：O(P·H·V) = O(P·V²)（符号域 H=2V）。对第 26 章
的幂集域，"状态"是事实集合，单次合并 O(|全集|)，总量
O(P·|事实|²)——多项式，且实践中远达不到。

值得对照的是第 19 章的合一：近线性实现可达 O(n α(n))，
本书的朴素实现最坏立方但透明。两章的取舍再次同构——
**教学实现选可手推的朴素形态，把更聪明的实现留给 16.8
的变体综述**。

复杂度之外，两个实现级操作的代价也值得记账，它们在
理论上被大 O 吃掉、在工程里偶尔浮出。其一，in 集合的
count/insert/erase 是 O(log P)，若换成与点数等长的
位图（`std::vector<bool>` 或位运算的 uint64 组）可压
到 O(1)——工业求解器一律位图；本章用 set 是为了
让"集合成员"的语义一眼可读。其二，环境的拷贝：joinEnv
与 transferNode 都按值返回新 map，每次重算 O(V log V)
的结点构造——10 个变量、百次重算的规模下毫无感觉，
上千变量时这是第一个要改成原位更新加回滚的瓶颈。两处
都验证同一条经验：**先把算法写对，性能按 profile 指引
逐处兑现**——复杂度公式指出瓶颈的量级，profile 指出
常数藏在哪。

时间之外把内存也记一笔。`cur` 的规模是"已达点数 × V"
个键值对，最坏 P·V；队列与 in 集合各至多 P 个整数；
加上邻接表 O(E)——总内存 O(P·V + E)，对过程内的
任何分析都微不足道。真正吃内存的是第 41 章的上下文
敏感分析：同一函数的每个调用上下文都要一份独立的
"点 → 环境"表，内存随上下文数线性放大，届时"稀疏
求值、按需实例化"从优化手段变成生存必需——16.8 的
方向四在那里的地位也是这样升上来的。复杂度账本要
分章节记账：本节的每一行数字都只在"过程内、有限格"
的前提下成立，读者引用它们到新场景前，先检查前提
是否同行到达。

### 24.5.3 一个不能省的警告：高度必须有限

全部论证依赖"上升次数有限"。把符号格换成一个故意加高的
域（比如整数格，⊥ < 0 < 1 < 2 < … < ⊤），循环
`x = x + 1` 会让 x 的抽象值沿链一路爬升 1, 2, 3, …，永无
止境——算法不报错、不减速，只是安静地永不终止。这不是
实现的 bug，是域的选择问题：**无限高度格上的单调迭代
不保证停**。第 30 章将把这个现象在区间格上真实复现
（50 步后打印 DID NOT CONVERGE），第 31 章用加宽算子
把无穷链折成有限条上升路径后重新收敛。此处先立路标：
遇到"分析不吐结果"，先问格的高度，再查实现的 bug。

### 24.5.4 域高度一览：从本章到第 31 章

把第四篇将登场的抽象域与其高度（最长严格上升链的边数）
列成一张表，作为 16.5.1–16.5.3 的总结与后续章节的路标：

| 域 | 登场章节 | 高度 | 迭代命运 |
|---|---|---|---|
| 符号格 {⊥,−,0,+,⊤} | 21–24 | 2 | 必停，便宜 |
| 布尔格 {⊥,0,1,⊤}（概念） | 18 | 1 | 必停 |
| 幂集格（n 个事实） | 18 | n | 必停，O(P·n) 量级 |
| 常量格（int 扁平格） | 17 | ∞ | 不保证停——TIP 的循环可让常量沿 1,2,3,… 爬升 |
| 区间格（含 ±∞） | 20 | ∞ | 第 30 章实测不收敛 |
| 区间 + 加宽 ∇ | 21 | 有效 3–4 | 必停，精度换来 |

表的读法有两条。横向看，高度从 1 到 ∞ 连续谱系，"迭代
是否必停"在常量格处断裂——第 25 章的常量分析将采用
"每点至多重算固定轮数"的工程断路器（sound 的理由届时
给出），第 31 章的 ∇ 才是理论正解。纵向看，幂集格的
高度 = 事实数，这解释了第 26 章四大 DFA 的复杂度公式
为何都带 |事实| 因子：它们全在幂集格上迭代，高度即
基数。读者拿到任何新域，先问高度、再写代码——这张表
会随章节推进不断加长，第 41 章的上下文敏感格、第 45 章
的点对集合格都会入列。

### 24.5.5 一次完整的演算：sign1 的账本

把公式落到 sign1 的具体数字上，让抽象的 O 记号重新长出
血肉。sign1 的 CFG：P = 7 个程序点，E = 7 条边，V = 2 个
局部变量，符号域单变量高度 2、环境格高度 H = 2V = 4。

**写回次数上界**：2PV = 2 × 7 × 2 = 28。实测 12 次
（W 7 + U 5）——用掉上界的 43%。浪费来自哪里？四个
透传点（entry、output、return、exit）的第一次写入是
⊥ → ⊥（环境为空），没有消耗格高度却在 2PV 的计数里
各占一席；真正沿格攀爬的只有三个点（2、3、4 号）与
三个"后来被冲刷"的透传点。

**弹出次数上界**：每次写回入队至多出度个后继，sign1
的出度：点 1 出 1、点 2 出 2、点 3/4/5/6 各出 1、点 7
出 0。弹出次数 = 成功入队次数 = 1（entry 的初始入队）+
各次写回未被 in 集合挡下的入队之和。实测 13 次弹出：
12 次写回合计只成功入队 12 次——两次写回的后继被 in
集合挡下（步 7 入队 3、5 之后，步 9、10 又写回点 3、5
的后继 4 与 6，部分后继已在队中）。这道"挡板"正是
16.3.5 强调 in 集合语义的原因：没有它，同一后继会因
多次写回重复入队，队列里堆满过期副本。精确账目留给
读者按 16.6.2 逐步核对，此处示范的是"如何在几十步内
对一个算法做全量对账"的方法。

**理论复杂度对照**：O(P·H·V) = O(7 × 4 × 2) = O(56)
次符号运算；每次重算的实际工作量是"合并前驱（至多
2 个前驱 × 2 个变量）+ 传递 + 比较（2 个变量）"，约
8 次查表，13 次弹出合计约百次查表——同一量级。sign1
这个例子把"多项式且实践中远达不到"落成了"56 这个
具体的数"。

**朴素迭代的对照**：round-robin 每轮扫全部 P = 7 点，
sign1 收敛需要 3 轮（第三轮确认无变化）即 21 次重算
vs worklist 的 13 次弹出。小图上优势 modest；把图放大
到 N 个语句的直链加一个循环，朴素每轮 O(N)、轮数仍
2–3，worklist 的弹出只发生在"半径 > 0"的链上（16.6.6），
链长与循环体长度同阶——差距从常数级拉开到线性因子级。
这是方向一（逆后序）在真实求解器里被默认开启的量化
理由。

## 24.6 真实输出解读：13 步完整追踪

### 24.6.1 待解的对象

先看主角本人。programs/sign1.tip 全文九行：

> main() {
> &nbsp;&nbsp;var x, y;
> &nbsp;&nbsp;while (input > 0) {
> &nbsp;&nbsp;&nbsp;&nbsp;y = 1;
> &nbsp;&nbsp;&nbsp;&nbsp;x = y + 1;
> &nbsp;&nbsp;}
> &nbsp;&nbsp;output x;
> &nbsp;&nbsp;return 0;
> }

它是有意设计的最小循环样本：两个变量、一条回边、一个
输出。`while (input > 0)` 保证循环体至少跑一轮的路径
与一轮都不跑的路径并存（输入流下一个整数是否为正，
分析器一无所知）；循环体内 `y = 1` 直接给出 +，`x = y + 1`
经由一次抽象加法把 + 传给 x；`output x` 是观察点——
本章分析的全部价值浓缩在它的程序点状态里。变量 x 的
信息要到回边走通之后才在循环头可见，这正是不动点迭代
要解决的问题；若程序没有循环（读者可删掉 while 试试），
每个点至多被弹出一次，worklist 退化为一遍线性扫描。

sign1.tip 的 CFG（第 21 章编号）与方程（第 23 章打印）：

程序点 1=entry、2=while 分支、3=`y = 1`、4=`x = y + 1`、
5=`output x`、6=`return 0`、7=exit；边 1→2、2→3、2→5、
3→4、4→2（回边）、5→6、6→7。七条方程：

```text
v1 = entry boundary (params = ⊤)
v2 = join(v1,v4)
v3 = v2[y := 1]
v4 = v3[x := (+ y 1)]
v5 = v2
v6 = v5
v7 = v6
```

main 无形参，entry 边界是空环境；x、y 是局部变量，未赋值
前按 ⊥ 读取。

特殊工具：在 solve.cpp 的写回分支加两行打印（弹出点、
写回值），重跑 --check，机器自己会替你把表写出来——
这本身就是很好的调试基建练习。

步 1：弹出 1（entry）。走特判分支（Entry 结点不走合并
——边界条件与任何前驱无关，16.3.4 详解此决定），nv =
entryEnv = 空环境（main 无形参）。首次写入。入队后继 2。
cur: {1:{}}。注意这次写回是 ⊥ → ⊥（空环境写进空映射
等于没写）——但在实现里它仍走完整的写回分支并入队 2，
因为"空映射缺席键"与"显式写空环境"在数据上等价、在
控制流上不同：不写回就不会入队，entry 的后继将永远
无人计算。**第一次推动必须被允许，哪怕它没携带任何
信息**——这是初始化（16.3.3）把 entry 放进队列而非
依赖后续触发的理由。

步 2：弹出 2（branch）。合并前驱 1 的 {} 与 4 的（未算，
缺席即 ⊥，跳过）得 {}；分支透传（Branch 结点的 transfer
原样返回输入）。W cur[2]={}。入队 3、5——第一次一个点
扇出两个后继，队列开始分叉。

步 3：弹出 3（y:=1）。合并前驱 2 的 {} 得 {}；赋值传递
后 {y=+}——signOfLiteral(1) = + 写入 y。W cur[3]={y=+}。
入队 4。这是第一条真正的信息：格预算开始消耗。

步 4：弹出 5（output）。合并前驱 2 的 {} 得 {}；透传。
W cur[5]={}。入队 6。注意 FIFO 的次序效应：步 2 让 3、5
同时入队，3 先弹出；若队列是栈（LIFO），5 会先弹——
16.9 练习二验证的顺序无关性在此已有伏笔。

步 5：弹出 4（x:=y+1）。合并前驱 3 的 {y=+} 得 {y=+}；
sAdd(+,+)=+，结果 {y=+, x=+}。W cur[4]={x=+,y=+}。入队 2。

步 6：弹出 6（return）。合并前驱 5 的 {} 得 {}；透传。
W cur[6]={}。入队 7。

步 7：弹出 2（branch，第二次）。合并前驱 1 的 {} 与 4 的
{x=+,y=+}：逐变量 x: ⊥⊔+=+，y: ⊥⊔+=+，得 {x=+,y=+}；
透传。U cur[2]：{} → {x=+,y=+}——一次写回消耗两格高度。
入队 3、5。**回边携带的信息此刻进入循环头**——第 21 章
单趟执行没有的正是这一步。它同时是扰动半径最大的一次
写回（16.6.6）：点 2 的状态改变，意味着所有下游点的
重算前提都变了，3 与 5 两条传播链同时点火。

步 8：弹出 7（exit）。合并前驱 6 的 {} 得 {}；透传。
W cur[7]={}。无后继——它不知道自己即将在第二轮被
重算一次；FIFO 队列里 7 排在 3、5 的后面，第一轮的
"前向波前"至此走完全图。

**第一轮小结**：步 1–8 把全部 7 个点写了一遍，每个点
拿到的是"只看前向边"能看到的信息——循环体内部（3、4）
有了内容，循环下游（2、5、6、7）还是白纸。这轮与第 21 章的单趟执行几乎等价（唯一差别：单趟按结点编号扫，
这里按队列序扫），也就是说，**worklist 的第一轮就是
一次单趟执行**——它不为超越单趟而存在，它为"知道哪些
点值得再算一遍"而存在：本轮的全部价值是步 5 与步 7
之间那次回边写回，它把步 9–13 点燃了。

步 9：弹出 3（第二次）。合并前驱 2 的 {x=+,y=+} 得
{x=+,y=+}；赋值 y:=1 后 {x=+,y=+}（y 仍被 + 覆写，x
透传而来——**x 的信息第一次流过 3 号点**，它不是在
这里诞生的，是从循环头借道）。U cur[3]：{y=+} →
{x=+,y=+}。入队 4。这个细节值得咀嚼：3 号点自己的
传递函数对 x 毫无所知，x 的上升纯靠前驱变宽——数据流
分析里大量"知识"就是这样搭便车流过与自己无关的语句的。

步 10：弹出 5（第二次）。合并前驱 2 的 {x=+,y=+}；透传。
U cur[5]：{} → {x=+,y=+}。入队 6。output 语句不修改
环境——但它的程序点状态必须更新，因为下游 6、7 的
方程引用它；透传点在传播链里是"导线"，导线本身的
状态变化同样触发下游重算。

步 11：弹出 4（第二次）。合并前驱 3 的 {x=+,y=+}；重算
x := sAdd(+,+)=+，结果 {x=+,y=+}——**与旧值完全相同**，
无动作。这是全部 13 步里唯一的"="：收敛在数据上的瞬间
标志。

步 12：弹出 6（第二次）。合并前驱 5 的 {x=+,y=+}；透传。
U cur[6]。入队 7。return 语句同样透传——TIP 的 return
只结束控制流，不"销毁"任何变量的信息，故退出点的环境
与 return 点相同，这对第 40 章讨论"函数出口状态"是个
方便的起点。

步 13：弹出 7（第二次）。合并前驱 6 的 {x=+,y=+}；透传。
U cur[7]。无后继。队列空，停止。exit 点的 U 写回没有任何
观众——没有后继可入队，队列就此清空。**算法不知道自己
刚完成了一次数学意义上的收敛**；它只是再无活干。把
"再无活干"翻译成"到达最小不动点"的，是 16.4 的整段
论证——算法与定理在这个瞬间完成交接。

统计：13 次弹出、12 次写回（11 次 W + 5 次 U 中……精确地：
W 7 次——步 1、2、3、4、5、6、8；U 5 次——步 7、9、10、
12、13；"=" 1 次——步 11）。迭代轨迹呈现清晰的"两轮"
结构：第一轮（步 1–8）沿前向边把 ⊥ 状态铺满全图；第二轮
（步 7 引爆、9–13 收尾）把回边带来的 {x=+,y=+} 重新冲刷
一遍受影响子图。两个整数变量、高度 2V=4 的积格——实际
只用了两轮、13 步，远在 O(P·H) 上界之内。

### 24.6.3 终态与机器输出对照

追踪终态：点 1 为空环境（打印 x=⊥ y=⊥——entry 处两个
局部变量都未赋值），点 2–7 全部 {x=+, y=+}。expected
output.txt 的逐行内容与此一一对应：

```text
== sign1.tip ==
worklist fixpoint sign analysis (least fixpoint):
-- main --
  1 entry: x=⊥ y=⊥
  2 branch  while (> input 0): x=+ y=+
  3 assign  y = 1 ;: x=+ y=+
  4 assign  x = (+ y 1) ;: x=+ y=+
  5 output  output x ;: x=+ y=+
  6 return  return 0 ;: x=+ y=+
  7 exit: x=+ y=+
```

首行 `== sign1.tip ==` 是构建脚本回显的程序名（tipa
本身不打印它，expected 文件把它记在开头以便人工核对
"对的是哪个程序"），其余各行出自 tipa：第二行是
--check 分支打的标题，`-- main --` 之后每程序点一行。

打印器（第 21 章的 printPointEnv）对分支点只标条件文本
（`while (> input 0)`）而不压入整个循环体；变量按"形参
在前、局部变量在后"的固定顺序打印，缺键打印 ⊥——
点 1 的 `x=⊥ y=⊥` 就是缺键约定的打印形态。

这段 expected 文本在构建流水线里的消费方式值得交代，
因为它是"13 步追踪是否可信"的机器裁决。example_build.sh
构建 tipa 后跑 `tipa --check programs/sign1.tip`，把
stdout 与 expected/output.txt 逐字节比对——任何一个
字符（包括 `branch` 后的两个空格、行末的分号）不一致
都算失败。这份严格性的回报在迭代开发时才显现：改
solve.cpp 的任何一行，重跑构建，若 expected 未变，
说明外部行为未变；若变了，diff 直接指出哪个程序点的
哪个变量在哪个字符上偏离——**回归失败信息定位到格值
粒度**。第 26 章四大 DFA 会为同一套打印器生成四份
expected，届时这套对账机制的价值再翻四倍。

### 24.6.4 不动点修正了什么

把本章终态与第 21 章单趟结果并排，差异只在一处却意义重大：

| 程序点 | 第 21 章单趟 | 本章不动点 |
|---|---|---|
| 1 entry | x=⊥ y=⊥ | x=⊥ y=⊥ |
| 2 branch | x=⊥ y=⊥ | x=+ y=+ |
| 3 assign y=1 | x=⊥ y=+ | x=+ y=+ |
| 4 assign x=y+1 | x=+ y=+ | x=+ y=+ |
| 5 output | x=⊥ y=⊥ | x=+ y=+ |
| 6 return | x=⊥ y=⊥ | x=+ y=+ |
| 7 exit | x=⊥ y=⊥ | x=+ y=+ |

单趟在 2、5、6、7 四个点给 ⊥，语义是"没有信息"——但
这些点明明在循环至少跑一轮时必然执行且 x 必然为 +。⊥
在这里不是保守而是**错误**：它声称"什么都不知道"，而
事实是"知道是 +"。根因在 16.1 已点明：单趟走到回边目标
时回边信息还没算出来，按 ⊥ 参与合并后，正向信息无法
回流。不动点迭代让信息沿回边逆流而上（步 7），把"循环
至少跑一轮后 x 是 +"这个事实送回循环头，再漫过全图。

3 号点的差异同样值得解释，因为它展示的是另一类信息：
**循环携带值**（loop-carried value）。单趟在点 3 给
x=⊥ y=+，不动点给 x=+ y=+。点 3 在循环体内部、y 的
赋值之后——此刻 x 的"当前值"是什么？第一次进入循环
时 x 确实未赋值（⊥ 没说错），但第二次起，x 保留的是
上一轮循环体的赋值结果（+）。点 3 的不动点环境 x=+
说的正是这件事：**在任何一次到达点 3 的执行里，x 要么
是 ⊥（尚无赋值，仅首轮前）、要么是 +（上轮所赋），
两者 join 后为 +**……严格说 join(⊥, +) = +，⊥ 不改变
join 结果，所以"首轮 x 未赋值"这个可能性被 ⊥ 的单位元
身份悄然吸收了。读者要在这里停下来体会一次：不动点的
环境里没有"执行次数"的概念，它把"第一轮之前"与"之后
各轮"的所有可能堆在同一个格值里——⊥ 的存在使"尚无
信息"的那部分可能性透明地消失。第 28 章的未初始化分析
要区分"首次到达"与"再次到达"，届时将看到这个被吸收的
信息如何被专门的分析找回来。

从应用视角看这次修正的价值：假如第 28 章的未初始化分析
或第 32 章的除零检查以符号分析为底座，⊥ 与 + 的差别就是
"无法判断"与"可以放行"的差别——精度直接决定可用性。
这也是为什么第四篇把不动点求解放在一切具体分析之前：
它是所有后续精度的共同来源。

### 24.6.5 循环头的 join：一次精度的细读

值得把步 7 的合并再单独细读一次，因为它最能体现格设计的
意图。循环头 2 号点的两个前驱：1 号（entry，{}，即
x⊥y⊥）与 4 号（回边，{x=+,y=+}）。逐变量 join：
x: ⊥ ⊔ + = +；y: ⊥ ⊔ + = +。合并结果 {x=+,y=+}——
与回边一侧完全相同，entry 一侧没有"稀释"任何精度。

反过来看一个容易误判的对照：假如 entry 侧对 x 给的是
⊤（比如有人把"形参未知"的 ⊤ 语义错误地套到局部变量上），
join 变成 + ⊔ ⊤ = ⊤，循环头、循环体、出口全部被顶成 ⊤，
整个分析退化到全图一个精度。⊥ 与 ⊤ 在 join 表里的位置
差，就是"缺省值选对"与"缺省值选错"的代价差。第 21 章
entryEnv 只把形参置 ⊤、对局部变量不置任何值（读取按 ⊥），
正是这个道理：**局部变量在赋值前的"未知"应当是 ⊥
（还没有事实）而不是 ⊤（什么都有可能）**——TIP 读取
未赋值变量在第 28 章将被单独分析，此处按 ⊥ 处理与
"循环至少跑一轮"的可推导事实相容。

这一节还可以读出一条普遍的方法论。循环头的 join
是全图唯一一个"两条执行路径汇合"的合并点，它的
行为决定了整个循环区间的精度——**汇合点是分析的
咽喉**。设计抽象域时问"我的 join 在汇合点丢多少"，
设计传递函数时问"我给汇合点喂多少"，两者相乘就是
循环程序的最终精度。第 32 章路径敏感分析的动机、
第 41 章上下文敏感对"调用点汇合"的处理，全是围绕
这个咽喉做文章：要么减少汇合次数（分开路径）、要么
减少汇合损失（更精的 join）。咽喉的解剖图，就是
今天这一小节。

### 24.6.6 两轮结构的再读：扰动半径

16.6.2 末尾提到的"两轮结构"值得给它一个名字与定量。
定义某次写回的**扰动半径**为"从写回点到它引发的最后一次
写回的最长传播距离"。sign1 的 13 步里：第一轮的写回
（步 1–6）扰动半径都不超过 2（沿前向边一两跳就被 ⊥
吸收或透传）；步 7 的写回扰动半径最大——{x=+,y=+} 从
循环头出发，经 3、5 两路前向、再经 4 号回边返回，覆盖
全图（半径 5），引爆第二轮。第二轮各写回的半径逐次缩短：
步 9 触发步 11 的"="，链在 4 号点断掉；步 10 触发 12、13，
链在 7 号点（无后继）断掉。

扰动半径的直觉解释了 worklist 相对朴素迭代的收益来源：
朴素迭代每轮扫全图，相当于强行把半径 0 的点也走一遍；
worklist 只走半径 > 0 的链。对 sign1 这类小图收益有限
（13 步 vs 朴素两轮 14 次访问），对大图与稀疏扰动（典型
如优化管线里反复重算的增量分析）收益是数量级的。半径
这个概念还预告了第 42 章 IFDS 的复杂度论证——那里的
"扰动"是路径边，半径的分析对象是超级图，论证骨架与
此处同型。

半径也有反面教材：若传递函数设计得"过噪"——一次微小
变化引发大范围重算（比如一个把所有变量置 ⊤ 的粗心
传递），半径会处处满格，worklist 退化回朴素迭代。半径
的大小不是队列的属性，是**传递函数与格结构的属性**：
⊥ 作单位元吸收弱扰动、格宽度限制传播幅度，两者配合
才让"半径普遍小于全图"成为常态。设计新域时把"一个
变量变化平均能波及几个变量"列入设计审查项，是本章
方法论的延伸——第 30 章区间域的设计讨论会正式用到。

### 24.6.7 两轮快照：cur 的生长史

把 13 步按"扰动波前"重新组织成两张快照，cur 的生长史
一目了然。第一轮结束（步 8 之后，队列尚有 3、5）时：

```text
cur = { 1:{}, 2:{}, 3:{y=+}, 4:{x=+,y=+}, 5:{}, 6:{}, 7:{} }
```

第二轮结束（步 13 之后）时：

```text
cur = { 1:{}, 2:{x=+,y=+}, 3:{x=+,y=+}, 4:{x=+,y=+},
        5:{x=+,y=+}, 6:{x=+,y=+}, 7:{x=+,y=+} }
```

两张快照的差分恰好是 U 的五次写回：点 2、3、5、6、7。
注意第一轮快照的"残缺形状"——循环下游（2、5、6、7）
全是空环境，而循环体内部（3、4）已携带部分信息：信息
在回边处被卡住，第一轮快照就是那张"卡住"的定格。第二轮
快照则是"冲刷"完成后的畅通用形：除 entry 外全图一致。
**从残缺到畅通用，变化只发生在回边到达之后**——把两张
快照并排贴在任何讲数据流的黑板上，"为什么要不动点
迭代"这个问题就不用再答了。

快照还顺手验证了一个细节：点 1 在两轮之间纹丝不动
（{}），因为它的方程是边界条件、不引用任何前驱——它
不在任何扰动链上。不可扰动性是边界点的结构性质，16.4.3
的"不可达点停在 ⊥"讨论是它的反面（前驱全 ⊥ 的点也
不可扰动，但那是数据性质不是结构性质）。

## 24.7 与 JIT 执行台的对照预告

第 12 章建成的 ORC 执行台至今只承担过两种角色：跑通程序
（--run）与对照 IR（--emit-ir）。第 25 章将给它第三个
角色：**可靠性陪审团**。计划中的 --verify-soundness 流程
是：先跑本章的符号分析得到每个 output 点的符号预测，
再用 JIT 真实执行若干组输入，把每个具体输出值映射回符号
（正数 → +，零 → 0，负数 → −），断言其属于预测集合。

对本章的 sign1 结论，这个流程将是第一次"机器裁决"：
分析说 output x 处 x=+，JIT 用多组以正数开头的输入跑出
的输出值必须个个为正。若存在一组输入让输出为负或为零，
可靠性被经验推翻——16.4 的论证有漏洞或实现有 bug，
二者必居其一。预计它会全绿，但验证的价值不在"通过"
本身，而在建立**理论承诺 → 经验核查**的闭环：从此本书
每引入一个新域或新传递函数（常量、区间、路径精炼、
上下文敏感），都有一台自动陪审团随时待命。

一个诚实的预告同时立在这里：sign1 的可靠性核查将采用
"首输入为正"的输入集——因为若首个输入非正，循环体
一次都不执行，output 读到的是**未赋值**的 x，其具体值
连 TIP 语义自己都没有规定。符号分析假设"读到的变量都已
赋值"，这个假设本身对不对，是第 28 章"可能未初始化"
分析的专职课题。两层分析各管一段：符号管"赋了值之后
值的走向"，未初始化分析管"读的时候赋了没有"——第 25 章的实验设计会尊重这条分工。

把实验的形状再具体化一点。第 25 章的核查脚本将准备三组
输入，每组一行，喂给 `tipa --run`：

| 组 | 输入 | 预期输出值 | 映射回符号 | 断言 |
|---|---|---|---|---|
| 1 | 1 | 2 | + | ⊆ {+}，成立 |
| 2 | 5 | 6 | + | ⊆ {+}，成立 |
| 3 | 100 | 101 | + | ⊆ {+}，成立 |

"映射回符号"这一步是整个实验的概念枢纽：具体值 2 与
抽象值 + 分属两个世界，连接它们的是**具体化函数** γ
（gamma）——γ(+) = {1, 2, 3, …}，把抽象值膨胀成它所
覆盖的具体值集合。断言"输出 2 ∈ γ(+)"在字面上是
集合属于关系。第 53 章将把 γ 正式定义为 Galois 联结的
一半，并配一个反向的抽象化函数 α；此刻读者只需抓住
方向：**从具体到抽象用 α（多对一），从抽象到具体用 γ
（一对多）**，可靠性实验沿 γ 方向核查，抽象沿 α 方向
压缩。

三组输入全过，实验给出的是"三票通过"——它**不能**
证明 16.4 的定理（输入空间无穷，验证永远只覆盖有限
样本），但一次失败就能证伪。这是经验方法的不对称性，
也是它仍然值得做的理由：实现 bug 的形态千奇百怪（比较
写反、join 漏变量、入队漏后继），任何一种都大概率在三
票内暴露。理论证明管"算法对"，经验核查管"代码与算法
一致"——两条防线各司其职，第 25 章起并存于每个分析的
验证流程。

还差最后一块拼图：**预测的"过近似"身份**。16.4 保证
的是：真实输出值一定落在预测的格值所覆盖的集合里——
γ(+) 是全部正整数，机器跑出的 2 属于它。注意方向的
不对称：真实值可以是集合里任何一个元素（分析预测
x=+，真实输出恒为 2，精确说分析"过近似"了），但绝不
允许落在集合外（预测 x=+ 而真实输出为负，就是彻底的
不可靠，第 25 章的核查会把它当失败）。落到缺陷检测
的语言上：分析说"可能有问题"（例如除数的符号含 0），
真实程序可能根本不踩雷——这叫**假阳**，是过近似的
天然代价；分析说"不可能有问题"，真实程序就一定踩不
上——**假阴被可靠性封死**。假阳浪费人时、假阴害人
声誉，可靠性的全部意义就是保证后者永不发生；精度的
意义则是压缩前者。这条不对称是不动点分析可用于工程
的全部前提，第 28 章把它展开成一整章的报告策略。

## 24.8 工程变体：真实求解器的四个方向

本章的求解器是教科书形态；工业实现围绕两个目标进化——
更快收敛、更少重算。四个方向各举一例，均为综述不实现。

**方向一：更聪明的初始化顺序。** 逆后序（reverse
postorder，DFS 生成树的逆后遍历）让"信息源"先于"汇"被
计算，第一轮就基本到位；对循环密集的图，逆后序能把重算
次数压到接近理想。Kildall 1973 年的原始论文已给出这一
建议，至今仍是不动点求解器的默认配置。

**方向二：强连通分量分解。** 把 CFG 缩点成 DAG（分量间
无环），按拓扑序逐分量求解：无环部分一遍过，只有循环
分量内部需要真正迭代。这是把"回边"的限制性显式化——
迭代只发生在真正有环的地方。Tarjan 的 SCC 算法与 worklist
结合，是现代求解器的标准骨架。

**方向三：差异式重算。** 本章重算一个点时重新合并全部
前驱；差异式（differential）求解器记下"上次合并以来哪个
前驱的哪个变量变了"，只对受影响的变量做增量更新。代价
是要维护反向依赖表；收益在大图与高维状态上非常显著。
Rep 等人的需求驱动求解与近年数据流引擎普遍采用此路。

**方向四：按需（demand-driven）求解。** 反转提问方向：
不求全图不动点，只回答"点 p 处变量 x 的值是什么"——
沿依赖边反向追到必要为止。调试器里的"这个值哪来的"、
IDE 的悬停类型推断都是这个形态。它牺牲全局解的完备性，
换取单点查询的就近停止。

按需求解与全图求解的关系，像惰性求值与急切求值：
前者只算被问到的东西，但"问到什么程度才算够"需要
一套终止判据——反向追依赖可能顺着环转圈，按需求解器
同样要维护"已查询对"的缓存来切断循环，其正确性论证
仍是单调框架的（第 42 章的 IFDS 把这套判据写成定理）。
读者可以把方向四当作 16.6 追踪的镜像练习：正向追踪
回答"这个点的信息流到哪"，反向追踪回答"这个点的信息
从哪来"——sign1 的 `output x` 反向追两跳就到点 4 的
赋值，再一跳到点 3、再一跳到条件，四次查询即到底，
而正向的全图追踪要 13 步。查询的形状决定走的路。

四个方向放到 sign1 这张 7 点小图上，各自的轮廓会更清楚。
方向一改初始队列：entry 之后按逆后序先算 3、4 再算 2，
第一轮内部就完成一次"回边信息的提前到位"，两轮可压缩
成约 10 次弹出——方向对，图太小，收益个位数。方向二改
图视图：Tarjan 扫一遍发现整图是一个 SCC（循环把 2、3、4
缝在一起），分量内照常迭代、分量外的 5、6、7 拓扑序一遍
过——对 sign1 没省事，对"长直链 + 末尾小循环"的程序
省掉直链部分的全部重算。方向三改增量粒度：步 9 里 x 的
上升若按变量记账，步 11 的重算只需重算 x 一列、y 原样
复用——V=2 时节省一半，V=2000 时节省一半的绝对量就是
数量级。方向四最激进：只问"output x 处 x 的符号"，反向
追到 x 的唯一定值点 4、再追 y 的定值点 3、再追条件，
全程不过 10 步——它压根不构造其余三点的状态，代价是
换一个问题就要重追一次。

什么时候该上哪个方向，工程上的经验法则：编译器中端
（同一求解器被几千个函数反复调用）上方向一 + 二，几乎
白拿的收益；IDE 与 linter（查询稀疏、程序巨大）上方向
四；增量构建系统与持续分析（源码小改动频繁重跑）上
方向三。本书的示例规模全部落在"朴素够用"区，但读者
在第 42 章 IFDS 会与方向四的正经形态重逢，在第 41 章
上下文敏感分析里会看到方向二思想在调用图上的翻版。

四个方向正交，可任意组合。本书后续章节全部使用本章的
朴素 FIFO 形态：其一，示例程序规模不需要；其二，朴素
形态的每一步可手推（16.6 的追踪表就是证明），而可手推
是教程的第一生产力。顺带一提，读者天天在用的 LLVM
内部也是 worklist 思想的用户：它的分析 pass 多以
dense forward/backward propagation 的形态实现（本质
是按逆后序的 round-robin，方向一的亲缘），其简化
unreachable-block elimination、mem2reg 等则直接是
"变化才重算"的 worklist 循环。编译器基础设施的每一层
都藏着本章这十几行代码的放大版——学它不是学一道算法
题，是学编译器的基本心跳。

## 24.9 拓展练习

以下练习都在本章快照上可以直接动手，难度递增。共同
的纪律只有一条：先纸上、后机器——预测写下来再跑
--check，差异出现时先怀疑推演、再怀疑实现。直接跑
机器抄答案，等于把 16.6 亲手完成的追踪外包给了编译
器，训练效果归零。

**练习一（追踪验证）。** 把 sign1.tip 的循环体改成
`y = 0 - 1; x = y + 1`（先减后加一）。先在纸上预测每个
点的终态（提示：0 与 1 都是 +，sSub(+,+) 会给出什么？
x = sAdd(?, +) 的符号表项是什么？），再跑
`tipa --check` 对照。若预测不符，
用 16.6 的方法做 13 步追踪找出第一处分歧。

**练习二（顺序无关性的实验验证）。** 把 solve.cpp 的
`wl.front()/pop_front()` 改成 `wl.back()/pop_back()`（栈
式 LIFO），重新构建并对比 expected/output.txt。终态必须
逐字节相同（16.3.6 的定理），迭代步数可以不同——有兴趣
可以临时加一个弹出计数器，比较两种顺序的弹出次数。

**练习三（不变量的断言化）。** 在写回分支加入断言：nv
的每个变量的符号必须满足 leq(旧值, nv)（16.4.2 的"只升
不降"）。用 SignLattice::leq 逐变量检查，违反时打印程序
点与变量。全量回归应当全绿——这条断言把本章正确性论证
的核心不变量变成了常驻的回归防线。

**练习四（round-robin 对照实现）。** 不用队列，按点号
顺序反复全图扫描直到一轮无变化（16.2.4 的朴素形态）。
对比弹出（此处是访问）次数与 worklist 的差异，验证两者
终态一致。这个练习同时为第 26 章"四大 DFA 用统一求解器"
做手感准备。

**练习五（高度探测）。** 写一个三行程序让某个变量沿
`x = x + 1` 循环累积，抽象值每轮严格上升；用符号格跑
（会停，停在 +），再想象把域换成区间格（第 30 章），
解释为什么同样的驱动循环将不再终止。本题不需要写代码，
但需要把 16.5.3 的警告完整复述一遍——能讲清楚"为什么
符号停、区间不停"，才算真正掌握了高度这个概念。

### 24.9.1 解题要点（先自己动手，再读这里）

**练习一的关键**：`y = 0 - 1` 触发 sSub(+, +)——两个
操作数都是 +，正数减正数结果可 −、可 0、可 +，加法表
按 sSub 的换元规则给出 sAdd(+, −) = ⊤。于是 y=⊤ 进入
循环头第二轮合并：y 侧 ⊥ ⊔ ⊤ = ⊤，x = sAdd(⊤, +) =
⊤。终态是全图（除 entry）x=⊤ y=⊤。这道题的真意：
**一个减法就能把整个分析的精度打回原形**——具体上
0 − 1 恒为负，但符号域只见操作数的符号、不见数值，
它只能回答"正数减正数的一切可能"。符号域对减法的
敏感度极低，这不是缺陷而是域的能力边界，第 30 章
区间域正是为了补救它而生。

**练习二的关键**：LIFO 把 13 步变成几步不必预测——预测
没有意义，合流性保证终点唯一。值得观察的是步数差与
"哪类点被反复重算"：栈式顺序倾向深度优先，回边信息
可能更早到达，也可能更晚（取决于后继入队顺序），两种
都可能。若步数相同，检查是否巧合（sign1 太小）。

**练习三的关键**：断言写在哪一层很重要。写在写回分支
（旧值已取出、新值已算出）恰逢其时；写在 transfer 内部
则拿不到旧值。leq 需要逐变量比较——环境格的 leq 没有现成
函数（SignLattice::leq 是单变量的），练习的隐藏工作量
正是写出逐变量 leq 并处理"缺键即 ⊥"：比较方向是
leq(旧, 新)，一旦旧值里有而新值里没有的变量出现，立即
违约——新值把信息弄丢了。这个方向想清楚，断言就写对了。

**练习四的关键**：round-robin 的停止条件是"一整轮无任何
变化"，比 worklist 的"队列空"多扫一轮；实现时用
changed 标志而不是比较整张状态表（后者也是正确做法，
但标志法与第 26 章将看到的迭代器形态一致）。对照实验
的结论应当是：终态逐字节一致、访问次数 21 vs 13
（16.5.5 算过）。

**练习五的关键**：表述"为什么停/不停"时要用 16.4.2 的
框架回答——停 = 每点严格上升次数有界 = 高度有限。符号格
的 + 是吸收元：+ 再加任何东西还是 +，链被格的宽度"封顶"。
区间格没有吸收元：[1,1] + [1,1] = [2,2]，[2,2] + [1,1]
= [3,3]……每轮都造出**新的、此前从未出现过的**格元素，
链没有理由停。加宽算子做的事就是把无穷多个可能出现的
区间强行折叠到有限个（第 31 章 [0,∞) 这类"门槛区间"）。

**练习六（边界条件的实验）。** 给 sign1.tip 的 main 加一个
形参 `main(a)` 并把条件改成 `while (a > 0)`，重新跑
--check。先预测再跑机器：entry 点的环境应变为 `a=⊤`；
分支点透传，条件不参与求值（16.3.10）；循环体两次赋值
不经过 a，y、x 仍分别是 + 与 +。终态里 a 在各点应为何？
跑机器对照，并解释"形参 ⊤ 污染了哪些点、没污染哪些
点"——你会看到 ⊤ 并没有把 y、x 一起拖成 ⊤：污染
只沿**数据依赖**传播，a 与 y、x 无共享就无传染。
（16.2.3 末段已给出演示。）

**练习七（单调性验收机）。** 按 16.4.8 的处方写一个
三重循环，穷举 (a, b) 全部 25 个组合，对每个 a ⊑ b
断言五张表各自满足 f(a) ⊑ f(b)（把 join 也当作二元
函数验收，它应当对自己分配）。跑通后，故意把
MUL_TABLE 里的一个格子改错（比如把 sMul(−,−) 从
+ 改成 −——同号相乘得正，改成负显然荒谬），看验收机
能否抓到——抓到后再想想：这个改动同时破坏了 16.4 的
哪一步论证？（答案：单调性前提，且它还会让"结果 ⊑
lfp"在相应输入类上失真——先有体验，第 28 章可靠性
一节再 formal 化。）

**练习八（边 worklist）。** 按 16.3.3 的岔口把队列改成
存边：初始放 entry 的全部出边，写回后入"后继边"，去重
集合存边对。重跑 sign1 对比弹出次数与终态。这道练习
的收获不在性能（必然无差），而在实现第二个 worklist
时你会被迫重新回答一遍"工作单元是什么、去重去什么、
收敛判据是什么"——三个答案都换了一层皮而骨架纹丝不动，
框架的抽象层次感由此养成。

## 24.10 基础设施逐文件补讲：求解器的供货链

### 24.10.1 为什么要补讲基础设施

嵌入区的 27 个文件里，真正属于"worklist 求解"的只有
solve.hpp / solve.cpp 两个；其余 25 个文件分成三组：方程
生产侧（equations、sign、sign_transfer、lattice）、程序
表示侧（TIP.g4、ast、ast_build、cfg、pretty、symtab）与
执行台侧（irgen、jitrun、main）。前两组在 16.3 已经讲过
与求解直接相关的部分，第三组里的多数文件是第 12 章的老
朋友。但有一条纪律贯穿全书：**每章嵌入的每个文件都要在
本章得到讲解**——读者不翻源码也能读完嵌入区，这是写作
承诺。前几章讲过的不重复，本节只讲"第 24 章视角"下这
些文件呈现的新侧面：求解器向它们索取什么保证、它们哪里
的设计是专门为"被反复重算"服务的。

小节的顺序按"离求解器的距离"排：先图（cfg，求解器的
直接数据结构），再程序表示（ast、pretty、symtab），再
平行的执行台（irgen、jitrun），最后方程规格（equations）
与域（sign、lattice）、语法源头（TIP.g4）。离得近的
决定求解器怎么写，离得远的决定求解器算什么——两种
影响一样深刻，只是作用的层次不同。

### 24.10.2 cfg.hpp / cfg.cpp：被重算一千次的图

cfg 在第 21 章首次登场时，读者关注的是"树如何展开成
图"；本章它换了一副面孔——**被遍历次数最多的数据结构**。
13 步追踪里每弹出一点都要查前驱表、查后继表、查结点表，
这些查找的形态决定了 solve.cpp 的写法。三个值得站在求解
器立场重读的细节：

**结点表是 std::map 而不是 vector。** 编号从 1 连续
分配，本可以用 `vector<CfgNode>` 以 O(1) 下标访问；
选 map 是为了让"结点是否存在"可查询（Entry/Exit 之外
的点数由语句数决定，但空块、空循环体会让"编号 i 是否
对应实际语句"不确定）。solve.cpp 里 `fc.nodes.at(p)`
的代价是 O(log n)，对教学规模可忽略；工程求解器会换成
稠密数组加位图标记。这个取舍在 16.5.2 的复杂度表里
体现为对数因子——理论复杂度 O(P·H·V) 不含它，因为它
不随迭代次数增长。map 还带来了一个 vector 给不了的
便利：范围 for 遍历 `f.nodes` 按编号升序访问，printCfg
与 printPointEnv 的输出顺序因此免排序——容器选择
同时服务了算法与输出两个消费者。

**边表有序去重，邻接表顺序沿用。** run() 末尾用
`std::set` 把边表去重排序（保证 printCfg 输出确定）；
solve.cpp 的 neighborMap 按这份已去重的边表构建
pred/succ。构造器内部（wireStmt 的 targets 拼接）本
可能产生重复边——例如 if 无 else 时 `link(n, succ)`
与 then 分支透传会得到同一条边两次——去重挡在源头。
即便防线失守，求解器也天然容忍：重复前驱对 join 无害
（a ⊔ a = a），重复后继对入队无害（in 集合挡住重复
入队）。这是"双层防御"的例子：源头去重保整洁，消费
侧的语义点（join 与入队）对重复幂等——两层各就各位，
单层失效也不出正确性事故。16.13 的注意点 1 与此呼应。

**Branch 结点携带条件指针。** printPointEnv 打印分支
点时需要条件文本，CfgNode 里存了 `const Stmt *stmt`。
这个指针同时是 solve.cpp 判断结点种类的依据（Entry
特判、Assign 特判）。指针指向的语句由 AST 拥有，CFG
只借用——生命周期上，Cfg 与 AST 在 main 里同栈存活，
求解全程安全。若未来求解器异步化或跨线程，这里要换成
共享所有权；第 53 章 AND 并行分析会碰到这个问题。

### 24.10.3 ast.hpp / ast_build：表达式结构决定抽象精度

第 12 章讲 ast_build 时重点是"ANTLR 语法树如何压平成
自己的 AST"；本章读者要看到的是：**AST 的表达式分类
直接划定了符号分析的能力边界**。sign_transfer.cpp 的
evalExprSign 一路 dynamic_cast 下去：IntLit 走
signOfLiteral，VarRef 查环境，InputE 返 ⊤，Binop 查
双目符号表——AST 里没有的类别就是分析覆盖不到的类别。
TIP 没有一元负号语法（负数写成 `0 - x` 或字面量 -3），
所以传递函数不需要处理一元否定；TIP 有比较运算，而
比较结果是布尔量却住在一个整数域的分析里，于是
sCompare 把 {0, 1} 这个具体值集抽象成 {0, +}——它在
符号格里恰好并成 ⊤，所以比较恒返回 ⊤。这是抽象域与
具体域失配时"向上取整"的标准姿势：具体世界里的类型
差异（布尔 vs 整数）在抽象世界里不存在，多余的自由度
全数折进 ⊤。

ast_build 生成的 FunDecl 里有 vars（局部变量声明表）。
单看求解器，vars 完全用不上——环境是从赋值流里长出来
的，没赋过值的变量在 env 里缺席即 ⊥。vars 的用处全在
打印：printPointEnv 用"参数在前、局部在后"的顺序枚举
变量名，让每个程序点的环境行格式统一、可 diff。一个
字段只在展示层被消费，这正是"表示与解释分离"的清晰
案例：分析核心不依赖它，打印协议依赖它。

### 24.10.4 pretty.hpp / pretty.cpp：可 diff 的输出契约

printCfg 与 printStmtLine 在第 21 章已经为输出格式
立过规矩；本章 printPointEnv 把规矩延长了一条：**每个
程序点一行，冒号后逐变量列出 `名字=符号`，缺席变量
打 ⊥**。逐变量列出而不省略 ⊥ 项，是刻意的：expected
文件要做字节级比对，若 ⊥ 变量按"缺席"处理，那么
"变量从 ⊥ 升到 +" 的过渡在 diff 里表现为行增删而非
行内变化，机器与肉眼都更难核对。全量打印让每一步状态
变化都落在同一行的同一列。

另一个小设计：Branch 点只打 `while <cond>` / `if
<cond>`，不打印循环体。循环体的语句有自己的程序点行，
重复打印会把一行撑成多行还折行，expected 文件里
`2 branch while (> input 0): x=+ y=+` 这类的整齐感
由此而来。fmt 层的每个决定都该问一句"它让核对更容易
还是更难"——这行是教科书式的"更容易"。

打印器还有第三个常被忽略的职责：**它是变量的登记册**。
打印顺序"形参在前、局部变量在后"来自第 21 章，但"哪些
变量值得打印"这个问题在本章有了新的答案——全部声明
过的变量，一个不落。这与"缺键即 ⊥"配合，构成一条完整
的可观察性约定：任何变量在任何程序点都有确定的表达，
要么是它的格值、要么是 ⊥；不存在"没被打印所以不知道"
的盲区。调试分析器时，第一件事就是把状态打印器做满——
盲区里藏的 bug，比打印出来的多得多。

### 24.10.5 symtab.hpp / symtab.cpp：本章用它，但不用它的分析

名字解析在第 10 章是主角；本章 main.cpp 的 parseFile
仍然调用 resolveNames 并检查 errors——不是仪式，是
守门：**名字有错的程序进 CFG 之前就该被拦下**，否则
求解器会碰到悬空引用并产生无意义的状态。这是"前端
管线有序性"的一次重演：语法错（退出码 2）→ 名字错
（退出码 3）→ 分析输出。对数据流分析而言，名字解析
还有一个隐性贡献：resolveNames 之后的 AST 里，变量
引用与声明已建立对应，sign_transfer 直接用变量名字符串
作环境键之所以安全，是因为 TIP 无嵌套作用域、名字在
函数内唯一；若语言允许遮蔽，环境键必须换成声明指针
或去广义化的编号——那时 symtab 的绑定结构就会直接
成为环境的键类型。这个推演提前写在这里，第 45 章
基于流敏感指针分析的键设计正好接上。

值得注意的还有"检查了但结果没用"这个细节：main 拿到
bindings 后只看了 errors 空 不空，绑定本身没有传给
CFG 或求解器——在 TIP 这个"名字即键"的世界里，绑定
信息已经被名字字符串自身携带了。这不是浪费：错误
检查与信息供给是名字解析的两个独立职责，本章只消费
前者；第 41 章引入调用图时，函数名的绑定才成为必需
的输入。一个模块的产出被下游分期消费，是前端管线
"一次解析、处处使用"的常态。

### 24.10.6 irgen.hpp / irgen.cpp 与 jitrun：与求解平行的另一条流水线

main.cpp 里 --emit-ir 与 --run 两个分支和 --check
共享 parseFile 之后的分叉：一边 buildCfg→solveFixpoint，
一边 IRGen→runJit。本章不动这两条分支的代码，但值得
把"平行"说透：**符号分析与 LLVM IR 生成消费同一棵
AST，却互不依赖**——分析在树上的格值世界做保守推理，
IR 生成在树上的具体值世界做忠实翻译。第 25 章两者
合流：先用 --check 求出各程序点的符号，再挑符号为 +
的输入喂给 --run，机器执行的具体行为与分析预言的
保守上界当场对账。从这个视角看，本章的 irgen/jitrun
嵌入不是"为了凑齐文件"，而是为下一章的合流实验预置
了另一半装置。irgen 生成的模块在 --run 前过一遍
verify()，与分析侧"结果必须是方程组不动点"地位相同：
都是各自世界里的健全性底线，谁也不能跳过。

### 24.10.7 equations.hpp / equations.cpp：规格锚的完整理由

16.3.1 说过 eqs 参数在 solve.cpp 里被 `(void)eqs;`
搁置、仅作规格锚。本节把这句话背后的工程判断补完。
表面看这是浪费：方程组已经在 CFG 的拓扑里了，求解器
直接按图算就行。但三个理由支持保留形参：

其一，**接口自文档**。solveFixpoint 的签名写明"求解
的是这组方程"，读代码的人不必反查第 23 章就知道
输入语义；删掉它，函数退化成 `solveSign(cfg, ast)`，
依赖关系藏进函数名——名字会过时，类型不会。

其二，**防错位**。若未来有人改 cfg 的构造而忘了改
transfer 的语义，方程组与求解器就悄悄失配；单测里
拿 signEquations 的输出与 solveFixpoint 的结果互相
核对（方程组的逐点 join 应等于解），失配会当场暴露。
参数在，这种核对才有写处。

其三，**为第 30 章铺路**。那里引入变宽度域后，同一
个求解器要服务多个抽象域，方程表将变成真正的运行时
数据（每域一套方程生成器）。今天的 `(void)eqs;` 是
明天的 `eval(eqs[i])`——接口先于实现稳定下来，第 30 章的改造就只动工厂不动骨架。

### 24.10.8 sign.hpp / sign.cpp：表的艺术

第 21 章讲过抽象算术表的内容，本章补讲它们的
**实现形态在求解语境下的含义**。sign.cpp 的算术核心是
两张 constexpr 表——ADD_TABLE 与 MUL_TABLE，各 4×4
（行、列取 −、0、+、⊤ 四个非底值），外加一组特化包装：
sAdd 直查 ADD_TABLE；sSub 换元为 a + (−b)（只翻转右
操作数的 −/+）复用加法表；sMul 直查 MUL_TABLE；sDiv
先排除除数为确定的 0（返回 ⊥——具体程序在此抛错，
"除以确定的零"的路径不可行），再把"除数可能是 0"
的情形拆成对 −、+ 两支分别求商后 join；sCompare 最
简——TIP 比较结果只有 0/1 两个可能值，{0, +} 在符号格
中恰好并成 ⊤，直接返回。**四则运算被三张表加两行特判
全部覆盖**，每次符号运算的代价是常数且极小。这不是
品味问题而是复杂度问题：16.5.2 把总代价写成 O(P·H·V)
次符号运算，若单次运算自身不平凡（比如区间域的 join
要算端点合并），那个公式的常数因子就被放大；符号域
把常数压到 1，是它"便宜"标签的来处。

编码本身（SBOT=−2、SMINUS=−1、SZERO=0、SPLUS=1、
STOP=2）也有讲究，但讲究的方向与直觉相反：**整数
编码只是存储便利，序关系不是整数大小**——头注释特意
提醒这一点。− 与 + 编码上可比（−1 < 1），格上却互不
可比，leq 必须按"⊥ 最小、⊤ 最大、中间三者互不可比"
的三条分支实现，join 同样按逻辑查表而非取 max。把
格序当整数序是初学者最常见的实现错误，症状是 join
悄悄给出错误上界而一切照常运转。signShow 把五个编码
逐个映射为单字符的格值名，expected 输出里 `x=+`、
`y=⊥` 的紧凑格式直接来自这层映射。小整数编码加显式
序操作，是分析器工程的第一课：**域的表示越薄、序
越显式，驱动力越省、错误越难藏**；第 30 章的区间域
将用两个 int 端点表示一个格值，序与 join 依旧显式
成对出现，是同一思想的下一档。

### 24.10.9 lattice.hpp / lattice_demo：通用框架的服役记录

lattice.hpp 在第 22 章是主角（lift、product、maps、
powerset 四种格构造），在本章退居"理论依据"的位置：
joinEnv 是 maps 构造的手写特化，环境格的高度论证
（16.5.1）是 product 构造高度可加性的应用。嵌入区
保留 lattice.hpp 与 lattice_demo.cpp，不是要读者重读
第 22 章，而是让"理论框架"与"手写特化"同框：读者对照
joinEnv 三行代码与 maps 构造的通用实现，能看到特化
省掉了什么（中间 map 的构造与销毁、泛型分发的间接层）
、保留了什么（逐点合并的语义核心）。lattice_demo 的
自测在构建时验证通用构造的性质（join 交换、幂等、
单位元），等于为"手写特化与通用版语义一致"提供旁证
——旁证不是证明，真正的保证来自 16.4 对 joinEnv
的直接论证，但旁证便宜，值得常备。

第 30 章起，lattice.hpp 将重新走上前台：区间域用
product 构造（两个端点各自是一条链），加宽算子以
lattice 扩展的形式接入。本章是它在后台待命的快照。

### 24.10.10 TIP.g4：语法的最后一次出场

TIP.g4 自第 3 章以来逐章随代码嵌入，从未缺席；本章
是它作为"分析语法"的最后一次出场——第 25 章起语法

从"表达式类别 → 求值分支"的对应看它，这里补一个

（词法、语法、AST、名字解析）在第四篇里再也不会变，
所有后续章节的示例程序都用同一份语法书写、同一套

## 24.11 历史脉络、术语对照与常见疑问

### 24.11.1 历史脉络

worklist 算法的出生证书属于 Gary Kildall——1973 年他的
博士论文（后以"A Unified Approach to Global Program
Optimization"为题流传）把此前散落各处的数据流优化（到达
定值、活跃变量、可用表达式……）统一为"格 + 单调传递
函数 + 不动点求解"的框架，并给出两种驱动策略：round-robin
迭代与 worklist。本书记载的顺序——先方程后求解——正沿
Kildall 的统一路线；今日数据流教科书（Dragon Book、
Cooper & Torczon）的框架章几乎原样保留他的表述。

理论侧的基石更早：Knaster–Tarski 不动点定理（Tarski 1955
年发表，Knaster 1928 年已给出链版本）保证单调函数在完全
格上的不动点存在且构成完全格——16.2.5 的两条引述都出自
这里。将不动点语义推向程序语言全域的是 Cousot 夫妇
1977 年的抽象解释：他们证明所有"格上的保守近似"都是
具体语义经 Galois 联结的像——第 53 章的 Galois 框架
就是那篇论文的核心概念。工程侧，20 世纪 80 年代的
SCC 分解（Tarjan 1972 的算法被借入求解器）、90 年代的
需求驱动求解（Reps–Horwitz–Sagiv，也是第 42 章 IFDS 的
同一批作者）、21 世纪的差异式增量求解，把 Kildall 的
朴素循环进化成 16.8 描述的形态。

历史还有一页与算法无关但值得知道的人事：Kildall 后来
离开学术界创办了 Digital Research——CP/M 操作系统的
作者，个人计算机产业早期的关键人物。数据流分析统一
框架与微机操作系统出自同一人之手，这在计算机科学史
里是罕见的跨界；也提醒读者 1970 年代初"程序优化"与
"系统软件"在从业者眼里本是一体两面。本章给出的算法
在他的原始论文里叫"A Unified Approach"，统一正是那
一代研究者给自己立的题：把 Fortran 优化器里各自为政
的十几种分析收进一个数学框架——四篇之后的我们仍在
这个框架里添砖加瓦。

### 24.11.2 术语对照

本章术语在中文文献与原书间的对应整理如下，读者读其他
教材时可对照：

| 本书用语 | spa 原书 | 其他文献常见形态 |
|---|---|---|
| worklist 求解 | work-list algorithm | 工作表算法、待处理集算法 |
| 最小不动点 | least fixed point | lfp、最小解 |
| 格高度 | height of a lattice | 链长、height |
| 边界条件 | boundary condition | 边缘条件、初值条件 |
| 扰动传播 | (原书未命名) | 影响传播、脏点传播 |
| 逆后序 | reverse postorder | RPO、逆深度优先后序 |

"扰动传播"与"扰动半径"是本书自造的描述词——Kildall
论文里这个现象只有一句"only nodes whose inputs have
changed need be reprocessed"，没有一个响亮的名字。命名
的目的不是创新术语，而是让 16.6.6 的定量讨论有主语。

### 24.11.3 常见疑问

**问：为什么初始值全 ⊥ 而不是"只给 entry 赋边界值、其余
全 ⊥"——实现里 cur 是空映射，连 entry 也没有？**
答：二者等价。cur 为空映射时任何点按 ⊥ 读取，这正是
"其余全 ⊥"；entry 的边界值在第一次弹出时由特判分支写入。
"初始就显式填好 entry"是同义改写，只是多一次写。选择
空映射的额外收益是不可达点永远不占存储——它们的 ⊥
是隐式的。

**问：步 11 的"="之后为什么还要走步 12、13？队列里明明
只剩 6 和 7。** 答："="发生在 4 号点，说明循环内部的
链断了，但 5→6→7 的透传链还在冲刷（它们前一轮的状态
还停在第一轮的旧值）。数据流不会因为某处收敛就全局
收敛——只有队列空才是收敛的机器判据。这也是为什么
正确性论证（16.4.3）从"队列空"出发而不是从"某点没变"
出发。

**问：如果两个函数共用一个 worklist 会怎样？** 答：结果
仍正确（函数子图不相交，扰动不会跨函数），只是队列混合
后 FIFO 顺序的确定性描述变啰嗦。逐函数求解是确定性的
最简单形态。第 40 章过程间分析会把函数间调用边显式画进
图里，届时"逐函数"这个前提被废除，队列必须跨函数。

**问：为什么不把 joinEnv 的结果缓存，前驱只有一个时跳过
join？** 答：单前驱时 joinEnv(a, ⊥) = a，合并本就退化，
缓存收益为零；两前驱以上时缓存命中需要额外哈希与失效
逻辑，复杂度反而上升。16.8 的差异式方向是这件事的认真
版本——增量计算而非缓存，有兴趣的读者可作毕业练习。

**问：expected 文件里 entry 打印 x=⊥ y=⊥，能说"entry 处
x 是 ⊥"吗？** 答：能，但要读对含义：⊥ 在这里是"该变量
尚未被赋值，分析对它没有事实"，不是"值为负为零"。
16.2.1 的两条语义（变量上、程序点上）在此重合——entry
点上，两个变量都还没有任何已证明的符号信息。

**问：FIFO 队列为什么用 std::deque 而不用
std::queue？** 答：用了 deque 的接口（front/pop_front/
push_back），没裹 queue 适配器只是少一层包装——语义
等价。真正要避开的是 std::vector：pop_front 在 vector
上是 O(n)。std::set<int> in 的存在也常被问：为什么不用
`std::find(wl.begin(), wl.end(), s)` 查重？那是 O(n)
线性扫，set 是 O(log n)；队列长度只在常数几十，两者
都没差，但 set 表达"这是一个集合成员关系"的意图更
清楚。性能在这两处都不是决策因素，**意图表达才是**。

**问：solveFixpoint 逐函数循环里每次都线性搜 program.funs
找 decl，为什么不在 buildCfg 时就把 decl 指针存进
FunCfg？** 答：可以，而且更好——但 cfg.hpp 已经在第 21 章定稿，改动它的字段要牵动三个章节的文档与 expected；
教学快照的取舍是"接口稳定优先于局部优雅"。这个别扭
在 16.10.2 说过 CFG 借用 AST 指针时也出现过：凡跨模块
引用处，本书的实现宁可保守。工程代码应当在 buildCfg
里一并填好 decl——读者改到这里时，请顺手修正并同步
第 21 章对 FunCfg 字段的描述。

**问：环境用 std::map<string,int>，变量名做键；循环
里反复 join、比较，map 的对数开销累积起来可观吗？**
答：O(log V) 每次，V 是变量数，相对 join 本身的语义
开销可忽略。真正要换的场合是 V 上千的工业分析——键
换成稠密编号（变量 → 小整数），环境换 vector<int>，
join 与比较都变 O(V) 直接扫。第 41 章引入"变量编号"
视角时正好完成这次升级，此处先保持名字键的可读性。

**问：如果传递函数需要"看老值"怎么办？比如 `x = x + 1`
要用 x 的旧符号算新符号。** 答：transferNode 拿到的
in 就是"进入赋值点时"的环境，`evalExprSign(x->value,
in)` 查 VarRef 时读的正是 in——右侧永远用旧环境求值、
左端再用求值结果覆写，"看老值"天然支持。真正的麻烦
在覆写不彻底的场合（第 45 章的 `*p = v`，p 指向不唯一
时新值只能 join 进环境而非干净覆写），文献里称那对
概念为强更新/弱更新，此处按下不表。

**问：本章的分析结果能不能直接当优化依据删代码？**
答：不能。符号信息只回答"值的符号是什么"，不回答
"这条语句有没有副作用、可不可删"。把"分析结果"变成
"改写程序"之间隔着可靠性的第二层含义：分析对，不代表
基于它的改写对——改写的正确性还要另证（保持可观测
行为）。第 28 章的除零警告是"报告"不是"改写"，报告
类应用对分析精度的要求天然低于改写类，这也是为什么
先做警告后做优化。

**问：收敛判定能不能用"版本号"或"脏标记"替代整环境
比较？** 答：能，而且这是工业实现的常规优化——每个
环境维护一个代数（epoch），全局计数器每次任何写回时
自增，点 p 的代数记录它最后同步时的全局值；弹出 p 时
若全局代数未变则跳过重算。它与"重算后比较"的语义
等价的前提仍是单调性：两次同步之间若全局有变，p 的
输入只可能变宽。本章不做这个优化，理由是 16.6 的
13 步追踪依赖"每次弹出都重算"的朴素语义——省一次
重算，就少一行可讲的内容。

**问：分析为什么做在自建的 TIP CFG 上，而不做在
LLVM IR 上？IR 不是现成的 CFG 与方程载体吗？** 答：
LLVM IR 当然可以做数据流分析（LLVM 自己就在做），但
本书的分析教程选择 TIP 层有三个理由。其一，教学连续
性：第 4–11 章自建的前端让"语法树 → CFG → 方程"的
每一步都可见，IR 的构造细节（mem2reg、SSForm）会把
注意力拖进编译器工程。其二，源级语义：TIP 语句与
源代码一一对应，警告可以直接指回源码行；IR 层的
"变量"已是 SSA 值，回指源码需要调试信息。其三，规模
可控：TIP 的 CFG 小而确定，expected 对账才可能逐字节。
代价是分析结论不能直接给 LLVM 的优化器用——那本就
不是本书的目标，第 45 章指针分析仍将在 TIP 层完成。

**问：expected 里只有 main 一个函数——多函数程序的
输出格式是什么样？** 答：printPointEnv 按函数循环，
每个函数打 `-- 函数名 --` 一节；solveFixpoint 同样
逐函数求解。多函数程序（比如第 20 章用过的小例）的
输出就是多节拼接，节与节之间没有额外的分隔行——
拼接即格式。真正值得提前想的是"函数间有没有信息
流动"：本章的答案是"没有"，各函数各求各的，main 的
结果与 foo 的结果互不知晓；第 40 章过程间分析要做的
第一件事就是把"调用边"变成扰动边——被调函数的
出口状态成为调用点后继的前驱输入，worklist 的图
从 N 个孤岛变成一张全程序大图，而循环体（16.3 的
十行代码）一个字都不用改。这是"框架不变、换图即可"
的又一次兑现，也是本书把求解器放在方程与域之后讲的
最终理由：**它小到可以一字不改地放大**。

**问：机器输出的 10 行里，哪几行真正"证明"了最小
不动点？其余行的作用是什么？** 答：按证据价值分层
读。`2 branch while (> input 0): x=+ y=+` 是主证——
它只能由回边回流产生，是"迭代确实越过了一轮"的
书证；`1 entry: x=⊥ y=⊥` 是边界条件的书证——边界
没有形参、局部变量未赋值，两列 ⊥ 与 entryEnv 的
定义逐字吻合；`7 exit: x=+ y=+` 是透传链闭合的书证
——信息走完了全图最后一跳。其余行（3–6 号点）是
传播中间点的记录，它们与方程逐条对应，是"每一站
都按方程到达"的佐证。10 行里有 3 行主证、5 行佐证、
1 行标题、1 行脚本回显——**每一行都有被对账的义务，
但没有一行是装饰**。读者将来为自己的分析写 expected
时，同样值得按这个分层自问：哪几行是主证？缺了它
们中的任何一行，哪种错误会漏网？

**问：13 次弹出对应 12 次写回——剩下的那一次弹出干了
什么？写回次数为什么"差一点"就是弹出次数？** 答：多
出来的那次是步 11 的"="——重算了、结果与旧值相同、
什么都不做。白跑的弹出有个好性质：它不写回、也就不
入队任何后继，**扰动波在它这里到头了**；所以白跑只
会吸收队列的尾部，不会自我繁殖。弹出次数 = 写回次数 +
白跑次数，白跑的每一笔都追溯到某次写回的入队——总量
仍被 16.4.2 的界罩住，实践中是小头。优化器里那些
"跳过确认"的技巧（16.11.3 的版本号方案）省的正是
这部分小头。

**问：第 21 章的单趟执行能不能也解释成一次"不动点
求解"？** 答：能，而且解释完你会发现它错在哪里也一并
清楚了。单趟等价于"只扫一轮的 round-robin"：每个点
恰好重算一次，弹出序即编号序。一轮之后若恰好收敛
（无环程序必然如此，16.3.11 的拓扑论证），它就是
合法的求解器；有环时它停在半路——不是"少跑了几轮"
的性能问题，而是**停在了非不动点处**，输出不满足
方程组。把它放回 16.4 的四步论证里检查：终止性尚可
（一轮有限），"终止时是不动点"当场断裂——四步缺一，
结论全失。这个对照也顺便回答了"单趟有什么用"：它是
worklist 的第一轮（16.6 的第一轮小结），是收敛过程的
快照而非结果；把它当结果用，就是第 21 章 sign1 上
那批 ⊥ 的来历。

**问：假如把 `output x` 挪进循环体内，13 步追踪会变成
什么样？** 答：值得在纸上推一遍再读答案。output 成了
循环体的最后一个点，回边从它后面绕回循环头；第一轮
里 output 点在体内被算出 {y=+, x=+}——**它在第一轮
就拿到了 +，不再需要等回边回流**；循环头仍要等回边
（第二轮）才顶到 {x=+,y=+}，但此后 output 点的重算
只是透传，结果不变。追踪的步数会变（点的数量、边的
次序都变了），"循环头滞后一轮"的现象不变。这道推演
的收获是：**精度损失的位置由图形状决定**——单趟
吃亏的总是"回边目标及其下游"，而不是程序里位置靠后
的语句；把输出点挪进循环，等于把它从"下游"搬进了
"上游"。

```cpp
// file: src/solve.cpp
#include "solve.hpp"

#include <deque>
#include <map>
#include <set>
#include <vector>

namespace tip {

namespace {

std::map<int, std::vector<int>> neighborMap(const FunCfg &f, bool successors) {
    std::map<int, std::vector<int>> r;
    for (const auto &[from, to] : f.edges) {
        if (successors) r[from].push_back(to);
        else r[to].push_back(from);
    }
    return r;
}

}  // namespace

PointEnv solveFixpoint(const Cfg &cfg, const ProgramA &program,
                       const std::vector<MonoEq> &eqs) {
    (void)eqs;
    PointEnv cur;
    for (const FunCfg &fc : cfg.funs) {
        const FunDecl *decl = nullptr;
        for (const auto &f : program.funs)
            if (f->name == fc.name) decl = f.get();

        const auto succs = neighborMap(fc, true);
        const auto preds = neighborMap(fc, false);

        // 初始值：除入口边界外全部 ⊥（空环境）。
        std::deque<int> wl{fc.entry};
        std::set<int> in{fc.entry};
        while (!wl.empty()) {
            int p = wl.front();
            wl.pop_front();
            in.erase(p);
            const CfgNode &node = fc.nodes.at(p);

            SignEnv nv;
            if (node.kind == CfgNode::Kind::Entry) {
                nv = entryEnv(*decl);  // 边界条件不随前驱变化
            } else {
                SignEnv before;
                auto pit2 = preds.find(p);
                if (pit2 != preds.end())
                    for (int q : pit2->second)
                        if (auto it = cur.find(q); it != cur.end())
                            before = joinEnv(before, it->second);
                nv = transferNode(node, before);
            }

            auto old = cur.find(p);
            if (old == cur.end() || old->second != nv) {
                cur[p] = nv;  // 单调框架保证 nv ⊒ 旧值
                auto sit = succs.find(p);
                if (sit != succs.end())
                    for (int s : sit->second)
                        if (!in.count(s)) {
                            wl.push_back(s);
                            in.insert(s);
                        }
            }
        }
    }
    return cur;
}

}  // namespace tip
```

```cpp
#include <vector>

#include "ast.hpp"
#include "pretty.hpp"

namespace tip {
namespace {

std::map<int, std::vector<int>> predecessorMap(const FunCfg &f) {
    std::map<int, std::vector<int>> preds;
    for (const auto &[from, to] : f.edges) preds[to].push_back(from);
    return preds;
}

// join 项的文本：单前驱直接用该点，多前驱写 join(...)。
std::string joinText(const std::vector<int> &deps) {
    if (deps.size() == 1) return "v" + std::to_string(deps[0]);
    std::string r = "join(";
    for (size_t i = 0; i < deps.size(); ++i) {
        if (i) r += ",";
        r += "v" + std::to_string(deps[i]);
    }
    return r + ")";
}

}  // namespace

std::vector<MonoEq> signEquations(const Cfg &cfg) {
    std::vector<MonoEq> all;
    for (const FunCfg &fc : cfg.funs) {
        const auto preds = predecessorMap(fc);
        for (const auto &[id, node] : fc.nodes) {
            MonoEq e;
            e.point = id;
            auto pit = preds.find(id);
            if (pit != preds.end()) e.deps = pit->second;

            std::ostringstream out;
            if (node.kind == CfgNode::Kind::Entry) {
                out << "entry boundary (params = ⊤)";
            } else {
                out << joinText(e.deps);
                if (node.kind == CfgNode::Kind::Assign && node.stmt) {
                    const auto *a = dynamic_cast<const AssignS *>(node.stmt);
                    if (const auto *t = dynamic_cast<const VarRef *>(a->target.get()))
                        out << "[" << t->name << " := " << printExpr(a->value.get()) << "]";
                }
            }
            e.expr = out.str();
            all.push_back(std::move(e));
        }
    }
    return all;
}

std::string printEquations(const Cfg &cfg, const std::vector<MonoEq> &eqs) {
    std::ostringstream out;
    for (const FunCfg &fc : cfg.funs) {
        out << "-- " << fc.name << " --\n";
        for (const MonoEq &e : eqs) {
            bool inFun = false;
            if (const auto it = fc.nodes.find(e.point); it != fc.nodes.end()) inFun = true;
            if (!inFun) continue;
            out << "v" << e.point << " = " << e.expr << '\n';
        }
    }
    return out.str();
}

}  // namespace tip
```

```cpp
// 编码：⊥=-2, −=-1, 0=0, +=1, ⊤=2。

constexpr int SPLUS = 1;
constexpr int STOP = 2;

// 后面所有单调框架的算法只依赖这三个操作（及 top/bot 边界）。
struct SignLattice {
    int top = STOP;
    int bot = SBOT;

    bool eq(int a, int b) const { return a == b; }
    bool leq(int a, int b) const;
    int join(int a, int b) const;
};

// 抽象算术：每个操作都对应整数运算"按符号分类"后的最小上界。
// 例如 +:(+,−)→⊤，因为正整数加负整数可能是 −、0 或 +。

int sSub(int a, int b);
int sMul(int a, int b);

int sCompare(int a, int b);
```

```cpp
// file: src/sign.cpp
#include "sign.hpp"

#include <array>

namespace tip {

Lattice<int> signLatticeDomain() {
    SignLattice s;
    return Lattice<int>{
        STOP, SBOT,
        [](int a, int b) { return a == b; },
        [=](int a, int b) { return s.leq(a, b); },
        [=](int a, int b) { return s.join(a, b); }};
}

std::string signShow(int s) {
    switch (s) {
        case SBOT: return "⊥";
        case SMINUS: return "−";
        case SZERO: return "0";
        case SPLUS: return "+";
        case STOP: return "⊤";
    }
    return "?";
}

bool SignLattice::leq(int a, int b) const {
    if (a == SBOT || b == STOP) return true;   // 底最小、顶最大
    if (b == SBOT || a == STOP) return a == b; // 越过底/顶的唯一可能是相等
    return a == b;                             // −、0、+ 三者互不可比
}

int SignLattice::join(int a, int b) const {
    if (a == b) return a;
    if (a == SBOT) return b;                   // ⊥ ⊔ x = x
    if (b == SBOT) return a;
    return STOP;                               // 其余组合（含 −/0/+ 两两）= ⊤
}

namespace {

// 加法符号表（行=左操作数 [−,0,+,⊤]，列=右操作数）。
constexpr std::array<std::array<int, 4>, 4> ADD_TABLE = {{
    //  −      0      +      ⊤
    {{SMINUS, SMINUS, STOP,  STOP }},  // −
    {{SMINUS, SZERO,  SPLUS, STOP }},  // 0
    {{STOP,   SPLUS,  SPLUS, STOP }},  // +
    {{STOP,   STOP,   STOP,  STOP }},  // ⊤
}};

// 乘法符号表：同号得 +，异号得 −，任何一边是 0 得 0。
constexpr std::array<std::array<int, 4>, 4> MUL_TABLE = {{
    //  −      0      +      ⊤
    {{SPLUS,  SZERO,  SMINUS, STOP }},  // −
    {{SZERO,  SZERO,  SZERO,  SZERO}},  // 0
    {{SMINUS, SZERO,  SPLUS,  STOP }},  // +
    {{STOP,   SZERO,  STOP,   STOP }},  // ⊤
}};

int idx(int s) { return s + 1; }  // −(-1)→0, 0→1, +(1)→2, ⊤(2)→3

}  // namespace

int sAdd(int a, int b) {
    if (a == SBOT || b == SBOT) return SBOT;
    return ADD_TABLE[idx(a)][idx(b)];
}

int sSub(int a, int b) {
    if (a == SBOT || b == SBOT) return SBOT;
    // a − b = a + (−b)：−、+ 互换，0/⊤ 不变。
    const int negB = b == SMINUS ? SPLUS : b == SPLUS ? SMINUS : b;
    return ADD_TABLE[idx(a)][idx(negB)];
}

int sMul(int a, int b) {
    if (a == SBOT || b == SBOT) return SBOT;
    return MUL_TABLE[idx(a)][idx(b)];
}

int sDiv(int a, int b) {
    if (a == SBOT || b == SBOT) return SBOT;
    if (b == SZERO) return SBOT;  // 除以确定的 0：该路径具体不可行（抛错中止）
    // 排除"除数可能为 0"的情形后，商的符号规律与乘法相同。
    if (b == STOP) {
        // 除数 ∈ {−,0,+}：0 排除，剩下 {−,+}；结果符号对 −/+ 分别讨论后取 join。
        return sAdd(sMul(a, SMINUS), sMul(a, SPLUS));
    }
    return MUL_TABLE[idx(a)][idx(b)];
}

int sCompare(int a, int b) {
    if (a == SBOT || b == SBOT) return SBOT;
    return STOP;  // 比较结果只可能是 0 或 1：{0,+} 在本格中即 ⊤
}

}  // namespace tip
```

```cpp
#include <map>
```

```cpp
namespace tip {

int signOfLiteral(int v) {
    if (v < 0) return SMINUS;
    if (v == 0) return SZERO;
    return SPLUS;
}

int evalExprSign(const Expr *e, const SignEnv &env) {
    if (const auto *x = dynamic_cast<const IntLit *>(e)) return signOfLiteral(x->v);
    if (const auto *x = dynamic_cast<const VarRef *>(e)) {
        auto it = env.find(x->name);
        return it == env.end() ? SBOT : it->second;
    }
    if (dynamic_cast<const InputE *>(e)) return STOP;  // 输入流的下一个整数符号未知
    if (const auto *x = dynamic_cast<const Binop *>(e)) {
        const int l = evalExprSign(x->l.get(), env);
        const int r = evalExprSign(x->r.get(), env);
        switch (x->op) {
            case BOp::Add: return sAdd(l, r);
            case BOp::Sub: return sSub(l, r);
            case BOp::Mul: return sMul(l, r);
            case BOp::Div: return sDiv(l, r);
            case BOp::Gt:
            case BOp::Eq: return sCompare(l, r);
        }
    }
    // 函数调用的返回值、指针/记录相关表达式：本章按"任意整数"保守处理，
    // 精确分析在过程间（第 40 章起）与指针篇（第 45 章）给出。
    (void)e;
    return STOP;
}

SignEnv entryEnv(const FunDecl &f) {
    SignEnv env;
    for (const std::string &p : f.params) env[p] = STOP;  // 调用方实参符号未知
    return env;
}

SignEnv joinEnv(const SignEnv &a, const SignEnv &b) {
    SignEnv r = a;
    SignLattice lat;
    for (const auto &[k, v] : b) {
        auto it = r.find(k);
        r[k] = it == r.end() ? v : lat.join(it->second, v);
    }
    return r;
}

SignEnv transferNode(const CfgNode &node, const SignEnv &in) {
    if (node.kind != CfgNode::Kind::Assign || !node.stmt) return in;
    const auto *a = dynamic_cast<const AssignS *>(node.stmt);
    const auto *target = dynamic_cast<const VarRef *>(a->target.get());
    if (!target) return in;  // *p / r.f 目标：第 45 章指针分析之前保持环境不变
    SignEnv out = in;
    out[target->name] = evalExprSign(a->value.get(), in);
    return out;
}

namespace {

std::map<int, std::vector<int>> predecessorMap(const FunCfg &f) {
    std::map<int, std::vector<int>> preds;
    for (const auto &[from, to] : f.edges) preds[to].push_back(from);
    return preds;
}

const char *nodeLabel(CfgNode::Kind kind) {
    switch (kind) {
        case CfgNode::Kind::Entry: return "entry";
        case CfgNode::Kind::Exit: return "exit";
        case CfgNode::Kind::Assign: return "assign";
        case CfgNode::Kind::Output: return "output";
        case CfgNode::Kind::Branch: return "branch";
        case CfgNode::Kind::Return: return "return";
    }
    return "?";
}

}  // namespace

PointEnv singlePass(const Cfg &cfg, const ProgramA &program) {
    PointEnv states;
    for (const FunCfg &fc : cfg.funs) {
        const FunDecl *decl = nullptr;
        for (const auto &f : program.funs)
            if (f->name == fc.name) decl = f.get();

        const auto preds = predecessorMap(fc);
        for (const auto &[id, node] : fc.nodes) {
            if (node.kind == CfgNode::Kind::Entry) {
                states[id] = entryEnv(*decl);  // 边界条件：参数 ⊤
                continue;
            }
            // 前驱尚未计算（典型是循环回边）时其状态按全 ⊥（空环境）处理。
            SignEnv in;
            auto pit = preds.find(id);
            if (pit != preds.end()) {
                for (int q : pit->second) {
                    auto qit = states.find(q);
                    if (qit != states.end()) in = joinEnv(in, qit->second);
                }
            }
            states[id] = transferNode(node, in);
        }
    }
    return states;
}

std::string printPointEnv(const Cfg &cfg, const ProgramA &program,
                          const PointEnv &states) {
    std::ostringstream out;
    for (const FunCfg &fc : cfg.funs) {
        out << "-- " << fc.name << " --\n";

        const FunDecl *decl = nullptr;  // 变量打印顺序：参数在前，局部变量在后
        for (const auto &f : program.funs)
            if (f->name == fc.name) decl = f.get();
        std::vector<std::string> names = decl->params;
        for (const std::string &v : decl->vars) names.push_back(v);

        for (const auto &[id, node] : fc.nodes) {
            out << "  " << id << ' ' << nodeLabel(node.kind);
            if (node.kind == CfgNode::Kind::Branch && node.stmt) {
                // 分支点只标注条件，避免把整个 if/while 体压成一行又折行。
                if (const auto *w = dynamic_cast<const WhileS *>(node.stmt))
                    out << "  while " << printExpr(w->cond.get());
                else if (const auto *i = dynamic_cast<const IfS *>(node.stmt))
                    out << "  if " << printExpr(i->cond.get());
            } else if (node.stmt) {
                out << "  " << printStmtLine(*node.stmt);
            }
            out << ':';

            const SignEnv &env = states.at(id);
            for (const std::string &k : names) {
                auto it = env.find(k);
                out << ' ' << k << '='
                    << signShow(it == env.end() ? SBOT : it->second);
            }
            out << '\n';
        }
    }
    return out.str();
}
```

```cpp
// file: src/lattice.hpp
// 格的统一接口与四类通用构造（spa 第 4 章）。
// 一个"格"只需提供：顶/底两个边界、相等判定、偏序、最小上界。
// 提升(lift)、积(product)、映射(maps)、幂集(powerset)能把简单格组装成
// 程序状态所需的复合格——抽象环境就是"变量集合 → 值格"的映射格。
#pragma once

#include <functional>
#include <map>
#include <optional>
#include <set>
#include <tuple>
#include <utility>

namespace tip {

template <class A>
struct Lattice {
    A topV;
    A botV;
    std::function<bool(const A &, const A &)> eqF;
    std::function<bool(const A &, const A &)> leqF;
    std::function<A(const A &, const A &)> joinF;

    const A &top() const { return topV; }
    const A &bot() const { return botV; }
    bool eq(const A &a, const A &b) const { return eqF(a, b); }
    bool leq(const A &a, const A &b) const { return leqF(a, b); }
    A join(const A &a, const A &b) const { return joinF(a, b); }
};

// ---- 提升：给 A 加一个新底 ⊥=nullopt（"还没有值"） ----
template <class A>
Lattice<std::optional<A>> lift(const Lattice<A> &l) {
    using O = std::optional<A>;
    return Lattice<O>{
        O{l.top()}, O{std::nullopt},
        [](const O &a, const O &b) { return a == b; },
        [l](const O &a, const O &b) {
            if (!b.has_value()) return a == b;        // ⊥ 最小
            if (!a.has_value()) return true;
            return l.leq(*a, *b);
        },
        [l](const O &a, const O &b) {
            if (!a.has_value()) return b;
            if (!b.has_value()) return a;
            return O{l.join(*a, *b)};
        }};
}

// ---- 积：分量各自取 join，序为逐分量序 ----
template <class T, std::size_t... Is, class LTuple>
T tupleJoin(std::index_sequence<Is...>, const LTuple &lats, const T &a, const T &b) {
    return T{std::get<Is>(lats).join(std::get<Is>(a), std::get<Is>(b))...};
}
template <class T, std::size_t... Is, class LTuple>
bool tupleLeq(std::index_sequence<Is...>, const LTuple &lats, const T &a, const T &b) {
    return (... && std::get<Is>(lats).leq(std::get<Is>(a), std::get<Is>(b)));
}

template <class... As>
Lattice<std::tuple<As...>> product(const Lattice<As> &... ls) {
    using T = std::tuple<As...>;
    auto lats = std::make_tuple(ls...);
    T topT{ls.top()...};
    T botT{ls.bot()...};
    return Lattice<T>{
        std::move(topT), std::move(botT),
        [](const T &a, const T &b) { return a == b; },
        [lats](const T &a, const T &b) {
            return tupleLeq<T>(std::make_index_sequence<sizeof...(As)>{}, lats, a, b);
        },
        [lats](const T &a, const T &b) {
            return tupleJoin<T>(std::make_index_sequence<sizeof...(As)>{}, lats, a, b);
        }};
}

// ---- 映射：固定键集上逐点 join；键缺失按底处理 ----
template <class K, class V>
Lattice<std::map<K, V>> maps(const Lattice<V> &l, const std::set<K> &keys) {
    using M = std::map<K, V>;
    M topM, botM;
    for (const K &k : keys) {
        topM.emplace(k, l.top());
        botM.emplace(k, l.bot());
    }
    auto getOrBot = [&botM](const M &m, const K &k) {
        auto it = m.find(k);
        if (it != m.end()) return it->second;
        return botM.at(k);
    };
    return Lattice<M>{
        topM, botM,
        [](const M &a, const M &b) { return a == b; },
        [=](const M &a, const M &b) {
            for (const K &k : keys)
                if (!l.leq(getOrBot(a, k), getOrBot(b, k))) return false;
            return true;
        },
        [=](const M &a, const M &b) {
            M r;
            for (const K &k : keys) r.emplace(k, l.join(getOrBot(a, k), getOrBot(b, k)));
            return r;
        }};
}

// ---- 幂集：join=并，meet=交，序=包含；顶=给定全集（默认为空集） ----
template <class K>
Lattice<std::set<K>> powerset(const std::set<K> &universe = {}) {
    using S = std::set<K>;
    return Lattice<S>{
        universe, S{},
        [](const S &a, const S &b) { return a == b; },
        [](const S &a, const S &b) {
            for (const K &k : a)
                if (!b.count(k)) return false;
            return true;
        },
        [](const S &a, const S &b) {
            S r = a;
            r.insert(b.begin(), b.end());
            return r;
        }};
}

}  // namespace tip
```

```cpp
// file: src/cfg.cpp
#include "cfg.hpp"

#include <map>
#include <set>
#include <sstream>
#include <vector>

#include "pretty.hpp"

namespace tip {
namespace {

// 两遍构造：第一遍按 AST 先序给所有程序点分配固定编号；第二遍连边。
// 先编号再连边，是为了让编号严格按源码顺序（连边时若先构造后继节点，
// 后继会抢在前面编号），从而输出与程序点编号都是确定的。
class CfgBuilder {
public:
    explicit CfgBuilder(const ProgramA &program) : program_(program) {}

    Cfg run() {
        Cfg cfg;
        for (const auto &fun : program_.funs) {
            FunCfg fc;
            cur_ = &fc;
            cur_->name = fun->name;
            nextId_ = 1;
            stmtId_.clear();

            const int entry = addNode(CfgNode::Kind::Entry);
            cur_->entry = entry;
            numberStmt(fun->body.get());
            const int retId = addNode(CfgNode::Kind::Return, fun->ret.get());
            const int exitId = addNode(CfgNode::Kind::Exit);
            cur_->exitNode = exitId;

            // 连边：语句构造返回它自己的入口点集合；空块没有节点，直接透传后继。
            std::vector<int> bodyEntries = wireStmt(fun->body.get(), {retId});
            if (bodyEntries.empty()) bodyEntries = {retId};
            link(entry, bodyEntries);
            link(retId, {exitId});

            // set 去重并排序：CFG 边不允许重复，输出顺序固定。
            std::set<std::pair<int, int>> uniq(cur_->edges.begin(), cur_->edges.end());
            cur_->edges.assign(uniq.begin(), uniq.end());
            cfg.funs.push_back(std::move(*cur_));
        }
        return cfg;
    }

private:
    const ProgramA &program_;
    FunCfg *cur_ = nullptr;
    int nextId_ = 1;
    std::map<const Stmt *, int> stmtId_;

    int addNode(CfgNode::Kind kind, const Stmt *stmt = nullptr) {
        const int id = nextId_++;
        cur_->nodes.emplace(id, CfgNode{id, kind, stmt});
        return id;
    }

    // ---- 第一遍：编号 ----
    void numberStmt(const Stmt *s) {
        if (const auto *b = dynamic_cast<const BlockS *>(s)) {
            for (const auto &x : b->ss) numberStmt(x.get());
            return;
        }
        if (const auto *x = dynamic_cast<const IfS *>(s)) {
            stmtId_[x] = addNode(CfgNode::Kind::Branch, x);
            numberStmt(x->then.get());
            numberStmt(x->els.get());
            return;
        }
        if (const auto *x = dynamic_cast<const WhileS *>(s)) {
            stmtId_[x] = addNode(CfgNode::Kind::Branch, x);
            numberStmt(x->body.get());
            return;
        }
        if (dynamic_cast<const AssignS *>(s)) {
            stmtId_[s] = addNode(CfgNode::Kind::Assign, s);
            return;
        }
        if (dynamic_cast<const OutputS *>(s)) {
            stmtId_[s] = addNode(CfgNode::Kind::Output, s);
        }
    }

    // ---- 第二遍：连边。返回进入该语句时首先到达的程序点集合 ----
    std::vector<int> wireStmt(const Stmt *s, const std::vector<int> &succ) {
        if (const auto *b = dynamic_cast<const BlockS *>(s)) {
            std::vector<int> cur = succ;
            for (auto it = b->ss.rbegin(); it != b->ss.rend(); ++it)
                cur = wireStmt(it->get(), cur);
            return cur;
        }
        if (const auto *x = dynamic_cast<const IfS *>(s)) {
            const int n = stmtId_[x];
            std::vector<int> targets = wireStmt(x->then.get(), succ);
            if (targets.empty()) targets = succ;
            if (x->els) {
                std::vector<int> e = wireStmt(x->els.get(), succ);
                if (e.empty()) e = succ;
                targets.insert(targets.end(), e.begin(), e.end());
            } else {
                targets.insert(targets.end(), succ.begin(), succ.end());
            }
            link(n, targets);
            return {n};
        }
        if (const auto *x = dynamic_cast<const WhileS *>(s)) {
            const int n = stmtId_[x];
            // 循环体执行完回到条件点；空体时条件点连一条自边（等于死循环）。
            std::vector<int> bodyEntries = wireStmt(x->body.get(), {n});
            if (bodyEntries.empty()) bodyEntries = {n};
            link(n, bodyEntries);
            link(n, succ);
            return {n};
        }
        const int n = stmtId_[s];
        link(n, succ);
        return {n};
    }

    void link(int from, const std::vector<int> &to) {
        for (int t : to) cur_->edges.emplace_back(from, t);
    }
};

const char *kindName(CfgNode::Kind kind) {
    switch (kind) {
        case CfgNode::Kind::Entry: return "entry";
        case CfgNode::Kind::Exit: return "exit";
        case CfgNode::Kind::Assign: return "assign";
        case CfgNode::Kind::Output: return "output";
        case CfgNode::Kind::Branch: return "branch";
        case CfgNode::Kind::Return: return "return";
    }
    return "?";
}

}  // namespace

Cfg buildCfg(const ProgramA &program) { return CfgBuilder(program).run(); }

std::string printCfg(const Cfg &cfg) {
    std::ostringstream out;
    for (const FunCfg &f : cfg.funs) {
        out << "== " << f.name << " ==\n";
        out << "nodes:\n";
        for (const auto &[id, node] : f.nodes) {
            out << "  " << id << ": " << kindName(node.kind);
            if (node.stmt) out << "  " << printStmtLine(*node.stmt);
            out << "\n";
        }
        out << "edges:\n";
        for (const auto &[a, b] : f.edges) out << "  " << a << " -> " << b << "\n";
    }
    return out.str();
}

}  // namespace tip
```

```cpp
// file: src/ast.hpp
// AST 定义：AST 是去掉了括号、分号等语法噪音的程序结构。
// 接口自本章起冻结，后续所有分析（名字、CFG、类型、格……）都在此之上工作。
#pragma once

#include <memory>
#include <string>
#include <utility>
#include <vector>

namespace tip {

enum class BOp { Add, Sub, Mul, Div, Gt, Eq };

struct Expr {
    virtual ~Expr() = default;
};
struct IntLit : Expr {
    int v;
    explicit IntLit(int value) : v(value) {}
};
struct VarRef : Expr {
    std::string name;
    explicit VarRef(std::string n) : name(std::move(n)) {}
};
struct InputE : Expr {};
struct Binop : Expr {
    BOp op;
    std::unique_ptr<Expr> l, r;
    Binop(BOp o, std::unique_ptr<Expr> lhs, std::unique_ptr<Expr> rhs)
        : op(o), l(std::move(lhs)), r(std::move(rhs)) {}
};
struct CallE : Expr {
    std::unique_ptr<Expr> callee;
    std::vector<std::unique_ptr<Expr>> args;
    CallE(std::unique_ptr<Expr> fn, std::vector<std::unique_ptr<Expr>> as)
        : callee(std::move(fn)), args(std::move(as)) {}
};
struct Deref : Expr {
    std::unique_ptr<Expr> e;
    explicit Deref(std::unique_ptr<Expr> p) : e(std::move(p)) {}
};
struct AddrOf : Expr {                       // spa: & Id
    std::string name;
    explicit AddrOf(std::string n) : name(std::move(n)) {}
};
struct AllocE : Expr {
    std::unique_ptr<Expr> e;
    explicit AllocE(std::unique_ptr<Expr> init) : e(std::move(init)) {}
};
struct NullE : Expr {};
struct RecLit : Expr {
    std::vector<std::pair<std::string, std::unique_ptr<Expr>>> fields;
    explicit RecLit(std::vector<std::pair<std::string, std::unique_ptr<Expr>>> fs)
        : fields(std::move(fs)) {}
};
struct FieldA : Expr {
    std::unique_ptr<Expr> e;
    std::string field;
    FieldA(std::unique_ptr<Expr> record, std::string f)
        : e(std::move(record)), field(std::move(f)) {}
};

struct Stmt {
    virtual ~Stmt() = default;
};
// target 只会是 VarRef / FieldA / Deref，文法 lvalue 已限定。
struct AssignS : Stmt {
    std::unique_ptr<Expr> target, value;
    AssignS(std::unique_ptr<Expr> t, std::unique_ptr<Expr> v)
        : target(std::move(t)), value(std::move(v)) {}
};
struct OutputS : Stmt {
    std::unique_ptr<Expr> e;
    explicit OutputS(std::unique_ptr<Expr> x) : e(std::move(x)) {}
};
struct IfS : Stmt {
    std::unique_ptr<Expr> cond;
    std::unique_ptr<Stmt> then, els;
    IfS(std::unique_ptr<Expr> c, std::unique_ptr<Stmt> t, std::unique_ptr<Stmt> e)
        : cond(std::move(c)), then(std::move(t)), els(std::move(e)) {}
};
struct WhileS : Stmt {
    std::unique_ptr<Expr> cond;
    std::unique_ptr<Stmt> body;
    WhileS(std::unique_ptr<Expr> c, std::unique_ptr<Stmt> b)
        : cond(std::move(c)), body(std::move(b)) {}
};
struct BlockS : Stmt {
    std::vector<std::unique_ptr<Stmt>> ss;
    explicit BlockS(std::vector<std::unique_ptr<Stmt>> v) : ss(std::move(v)) {}
};
struct ReturnS : Stmt {
    std::unique_ptr<Expr> e;
    explicit ReturnS(std::unique_ptr<Expr> x) : e(std::move(x)) {}
};

struct FunDecl {
    std::string name;
    std::vector<std::string> params;
    std::vector<std::string> vars;
    std::unique_ptr<Stmt> body;
    std::unique_ptr<ReturnS> ret;
};

struct ProgramA {
    std::vector<std::unique_ptr<FunDecl>> funs;
};

}  // namespace tip
```

```cpp
// file: src/ast_build.cpp
#include "ast_build.hpp"

#include <utility>
#include <vector>

namespace tip {

std::unique_ptr<ProgramA> AstBuilder::build(TIPParser::ProgramContext *tree) {
    auto program = std::make_unique<ProgramA>();
    for (auto *fc : tree->function()) program->funs.push_back(buildFun(fc));
    return program;
}

std::unique_ptr<FunDecl> AstBuilder::buildFun(TIPParser::FunctionContext *ctx) {
    auto f = std::make_unique<FunDecl>();
    f->name = ctx->IDENT()->getText();
    if (ctx->params()) {
        for (auto *p : ctx->params()->IDENT()) f->params.push_back(p->getText());
    }
    if (ctx->varDecls()) {
        for (auto *v : ctx->varDecls()->IDENT()) f->vars.push_back(v->getText());
    }

    std::vector<std::unique_ptr<Stmt>> body;
    for (auto *sc : ctx->stmt()) body.push_back(buildStmt(sc));
    f->body = std::make_unique<BlockS>(std::move(body));

    f->ret = std::make_unique<ReturnS>(buildExpr(ctx->expr()));
    return f;
}

std::unique_ptr<Expr> AstBuilder::buildLvalue(TIPParser::LvalueContext *lv) {
    std::unique_ptr<Expr> base;
    std::string field;
    if (auto *d = dynamic_cast<TIPParser::DirectLvalueContext *>(lv)) {
        base = std::make_unique<VarRef>(d->IDENT(0)->getText());
        if (d->IDENT().size() == 2) field = d->IDENT(1)->getText();
    } else {
        auto *p = dynamic_cast<TIPParser::PointerLvalueContext *>(lv);
        base = std::make_unique<Deref>(buildExpr(p->expr()));
        if (p->IDENT()) field = p->IDENT()->getText();
    }
    if (!field.empty())
        return std::make_unique<FieldA>(std::move(base), std::move(field));
    return base;
}

std::unique_ptr<Expr> AstBuilder::buildExpr(TIPParser::ExprContext *ctx) {
    if (auto *c = dynamic_cast<TIPParser::IntExprContext *>(ctx))
        return std::make_unique<IntLit>(std::stoi(c->INT()->getText()));
    if (auto *c = dynamic_cast<TIPParser::VarExprContext *>(ctx))
        return std::make_unique<VarRef>(c->IDENT()->getText());
    if (dynamic_cast<TIPParser::InputExprContext *>(ctx))
        return std::make_unique<InputE>();
    if (dynamic_cast<TIPParser::NullExprContext *>(ctx))
        return std::make_unique<NullE>();
    if (auto *c = dynamic_cast<TIPParser::ParenExprContext *>(ctx))
        return buildExpr(c->expr());

    if (auto *c = dynamic_cast<TIPParser::AddExprContext *>(ctx)) {
        const BOp op = c->PLUS() ? BOp::Add : BOp::Sub;
        return std::make_unique<Binop>(op, buildExpr(c->expr(0)), buildExpr(c->expr(1)));
    }
    if (auto *c = dynamic_cast<TIPParser::MulExprContext *>(ctx)) {
        const BOp op = c->STAR() ? BOp::Mul : BOp::Div;
        return std::make_unique<Binop>(op, buildExpr(c->expr(0)), buildExpr(c->expr(1)));
    }
    if (auto *c = dynamic_cast<TIPParser::CmpExprContext *>(ctx)) {
        const BOp op = c->GT() ? BOp::Gt : BOp::Eq;
        return std::make_unique<Binop>(op, buildExpr(c->expr(0)), buildExpr(c->expr(1)));
    }
    if (auto *c = dynamic_cast<TIPParser::NegExprContext *>(ctx)) {
        // TIP 没有负数字面量 token，-E 即 0-E。
        return std::make_unique<Binop>(BOp::Sub, std::make_unique<IntLit>(0),
                                       buildExpr(c->expr()));
    }
    if (auto *c = dynamic_cast<TIPParser::CallExprContext *>(ctx)) {
        std::vector<std::unique_ptr<Expr>> args;
        if (c->args())
            for (auto *a : c->args()->expr()) args.push_back(buildExpr(a));
        return std::make_unique<CallE>(buildExpr(c->expr()), std::move(args));
    }
    if (auto *c = dynamic_cast<TIPParser::FieldExprContext *>(ctx))
        return std::make_unique<FieldA>(buildExpr(c->expr()), c->IDENT()->getText());
    if (auto *c = dynamic_cast<TIPParser::DerefExprContext *>(ctx))
        return std::make_unique<Deref>(buildExpr(c->expr()));
    if (auto *c = dynamic_cast<TIPParser::AddrExprContext *>(ctx))
        return std::make_unique<AddrOf>(c->IDENT()->getText());
    if (auto *c = dynamic_cast<TIPParser::AllocExprContext *>(ctx))
        return std::make_unique<AllocE>(buildExpr(c->expr()));
    if (auto *c = dynamic_cast<TIPParser::RecExprContext *>(ctx)) {
        std::vector<std::pair<std::string, std::unique_ptr<Expr>>> fields;
        for (auto *fc : c->field())
            fields.emplace_back(fc->IDENT()->getText(), buildExpr(fc->expr()));
        return std::make_unique<RecLit>(std::move(fields));
    }
    return nullptr;  // 解析成功时不会到达
}

std::unique_ptr<Stmt> AstBuilder::buildStmt(TIPParser::StmtContext *ctx) {
    if (auto *c = dynamic_cast<TIPParser::AssignStmtContext *>(ctx))
        return std::make_unique<AssignS>(buildLvalue(c->lvalue()), buildExpr(c->expr()));
    if (auto *c = dynamic_cast<TIPParser::OutputStmtContext *>(ctx))
        return std::make_unique<OutputS>(buildExpr(c->expr()));
    if (auto *c = dynamic_cast<TIPParser::IfStmtContext *>(ctx)) {
        std::unique_ptr<Stmt> els;
        if (c->stmt().size() == 2) els = buildStmt(c->stmt(1));
        return std::make_unique<IfS>(buildExpr(c->expr()), buildStmt(c->stmt(0)),
                                     std::move(els));
    }
    if (auto *c = dynamic_cast<TIPParser::WhileStmtContext *>(ctx))
        return std::make_unique<WhileS>(buildExpr(c->expr()), buildStmt(c->stmt()));
    if (auto *c = dynamic_cast<TIPParser::BlockStmtContext *>(ctx)) {
        std::vector<std::unique_ptr<Stmt>> ss;
        for (auto *sc : c->stmt()) ss.push_back(buildStmt(sc));
        return std::make_unique<BlockS>(std::move(ss));
    }
    return nullptr;  // 解析成功时不会到达
}

std::unique_ptr<ProgramA> buildAst(TIPParser::ProgramContext *tree) {
    return AstBuilder{}.build(tree);
}
```

```cpp
// file: src/pretty.cpp
#include "pretty.hpp"

#include <string>

namespace tip {

namespace {

// 表达式打印为前缀式：运算符与符号的对照表。
std::string exprText(const Expr *e) {
    if (const auto *x = dynamic_cast<const IntLit *>(e)) return std::to_string(x->v);
    if (const auto *x = dynamic_cast<const VarRef *>(e)) return x->name;
    if (dynamic_cast<const InputE *>(e)) return "input";
    if (dynamic_cast<const NullE *>(e)) return "null";

    if (const auto *x = dynamic_cast<const Binop *>(e)) {
        const char *sym = "+";
        switch (x->op) {
            case BOp::Add: sym = "+"; break;
            case BOp::Sub: sym = "-"; break;
            case BOp::Mul: sym = "*"; break;
            case BOp::Div: sym = "/"; break;
            case BOp::Gt: sym = ">"; break;
            case BOp::Eq: sym = "=="; break;
        }
        return "(" + std::string(sym) + " " + exprText(x->l.get()) + " " +
               exprText(x->r.get()) + ")";
    }
    if (const auto *x = dynamic_cast<const CallE *>(e)) {
        std::string s = "(call " + exprText(x->callee.get());
        for (const auto &a : x->args) s += " " + exprText(a.get());
        return s + ")";
    }
    if (const auto *x = dynamic_cast<const Deref *>(e))
        return "(* " + exprText(x->e.get()) + ")";
    if (const auto *x = dynamic_cast<const AddrOf *>(e)) return "(& " + x->name + ")";
    if (const auto *x = dynamic_cast<const AllocE *>(e))
        return "(alloc " + exprText(x->e.get()) + ")";
    if (const auto *x = dynamic_cast<const FieldA *>(e))
        return "(. " + exprText(x->e.get()) + " " + x->field + ")";
    if (const auto *x = dynamic_cast<const RecLit *>(e)) {
        std::string s = "{";
        for (size_t i = 0; i < x->fields.size(); ++i) {
            if (i) s += ", ";
            s += x->fields[i].first + ": " + exprText(x->fields[i].second.get());
        }
        return s + "}";
    }
    return "<unknown expr>";
}

std::string indent(int level) { return std::string(static_cast<size_t>(level) * 2, ' '); }

// 语句打印带缩进，一条语句一行（块内多行）。
void stmtText(const Stmt *s, int level, std::string &out) {
    if (const auto *x = dynamic_cast<const AssignS *>(s)) {
        out += indent(level) + exprText(x->target.get()) + " = " +
               exprText(x->value.get()) + " ;\n";
        return;
    }
    if (const auto *x = dynamic_cast<const OutputS *>(s)) {
        out += indent(level) + "output " + exprText(x->e.get()) + " ;\n";
        return;
    }
    if (const auto *x = dynamic_cast<const ReturnS *>(s)) {
        out += indent(level) + "return " + exprText(x->e.get()) + " ;\n";
        return;
    }
    if (const auto *x = dynamic_cast<const IfS *>(s)) {
        out += indent(level) + "if (" + exprText(x->cond.get()) + ")\n";
        stmtText(x->then.get(), level + 1, out);
        if (x->els) {
            out += indent(level) + "else\n";
            stmtText(x->els.get(), level + 1, out);
        }
        return;
    }
    if (const auto *x = dynamic_cast<const WhileS *>(s)) {
        out += indent(level) + "while (" + exprText(x->cond.get()) + ")\n";
        stmtText(x->body.get(), level + 1, out);
        return;
    }
    if (const auto *x = dynamic_cast<const BlockS *>(s)) {
        out += indent(level) + "{\n";
        for (const auto &st : x->ss) stmtText(st.get(), level + 1, out);
        out += indent(level) + "}\n";
        return;
    }
    out += indent(level) + "<unknown stmt>\n";
}

}  // namespace

std::string printExpr(const Expr *e) { return exprText(e); }

std::string printProgram(const ProgramA &program) {
    std::string out;
    for (const auto &f : program.funs) {
        std::string paramList;
        for (size_t i = 0; i < f->params.size(); ++i) {
            if (i) paramList += ",";
            paramList += f->params[i];
        }
        out += f->name + "(" + paramList + ") {\n";
        if (!f->vars.empty()) {
            out += indent(1) + "var ";
            for (size_t i = 0; i < f->vars.size(); ++i) {
                if (i) out += ",";
                out += f->vars[i];
            }
            out += " ;\n";
        }
        // 函数体是 BlockS；打印其内部语句而不是再嵌一层花括号。
        const auto *body = dynamic_cast<const BlockS *>(f->body.get());
        for (const auto &st : body->ss) stmtText(st.get(), 1, out);
        stmtText(f->ret.get(), 1, out);
        out += "}\n";
    }
    return out;
}

// 单行形式：CFG 节点标签等"节点旁边写一句话"的场合使用。
std::string printStmtLine(const Stmt &stmt) {
    std::string out;
    stmtText(&stmt, 0, out);
    if (!out.empty() && out.back() == '\n') out.pop_back();
    return out;
}

}  // namespace tip
```

```cpp
// file: src/symtab.hpp
// 符号表与名字解析：把 AST 上的每个 VarRef 绑定到它的声明
// （函数 / 参数 / 局部变量），同时产出未声明、重复声明诊断。
#pragma once

#include <map>
#include <string>
#include <vector>

#include "ast.hpp"

namespace tip {

    std::vector<std::unique_ptr<Scope>> scopes;
    std::vector<Diag> errors;
```

```cpp
// file: src/symtab.cpp
#include "symtab.hpp"

#include <utility>

namespace tip {

namespace {

// 解析器在遍历 AST 的同时完成绑定与诊断收集。
struct Resolver {
    Bindings bindings;
    Scope *current = nullptr;
    const FunDecl *owner = nullptr;

    void declare(const std::string &name, Symbol::Kind kind) {
        if (current->table.count(name)) {
            bindings.errors.push_back({"error: redeclared '" + name + "'"});
            return;  // 保留先声明者，后声明被忽略
        }
        current->table.emplace(name, Symbol{kind, name, owner});
    }

    void resolveExpr(const Expr *e) {
        if (const auto *x = dynamic_cast<const VarRef *>(e)) {
            const Symbol *s = current->lookup(x->name);
            if (!s) {
                bindings.errors.push_back({"error: undeclared '" + x->name + "'"});
            } else {
                bindings.uses[x] = s;
            }
            return;
        }
        if (const auto *x = dynamic_cast<const Binop *>(e)) {
            resolveExpr(x->l.get());
            resolveExpr(x->r.get());
            return;
        }
        if (const auto *x = dynamic_cast<const CallE *>(e)) {
            resolveExpr(x->callee.get());
            for (const auto &a : x->args) resolveExpr(a.get());
            return;
        }
        if (const auto *x = dynamic_cast<const Deref *>(e)) return resolveExpr(x->e.get());
        if (const auto *x = dynamic_cast<const AllocE *>(e)) return resolveExpr(x->e.get());
        if (const auto *x = dynamic_cast<const FieldA *>(e)) {
            resolveExpr(x->e.get());  // 字段名不是变量，无需解析
            return;
        }
        if (const auto *x = dynamic_cast<const RecLit *>(e)) {
            for (const auto &f : x->fields) resolveExpr(f.second.get());
            return;
        }
        // IntLit / InputE / AddrOf / NullE：无变量使用。
    }

    void resolveStmt(const Stmt *s) {
        if (const auto *x = dynamic_cast<const AssignS *>(s)) {
            resolveExpr(x->target.get());
            resolveExpr(x->value.get());
            return;
        }
        if (const auto *x = dynamic_cast<const OutputS *>(s)) return resolveExpr(x->e.get());
        if (const auto *x = dynamic_cast<const IfS *>(s)) {
            resolveExpr(x->cond.get());
            resolveStmt(x->then.get());
            if (x->els) resolveStmt(x->els.get());
            return;
        }
        if (const auto *x = dynamic_cast<const WhileS *>(s)) {
            resolveExpr(x->cond.get());
            resolveStmt(x->body.get());
            return;
        }
        if (const auto *x = dynamic_cast<const BlockS *>(s)) {
            for (const auto &st : x->ss) resolveStmt(st.get());
            return;
        }
        if (const auto *x = dynamic_cast<const ReturnS *>(s)) return resolveExpr(x->e.get());
    }
};

}  // namespace

const Symbol *Scope::lookup(const std::string &name) const {
    auto it = table.find(name);
    if (it != table.end()) return &it->second;
    return parent ? parent->lookup(name) : nullptr;
}

Bindings resolveNames(ProgramA &program) {
    Resolver resolver;
    resolver.bindings.global = Scope(nullptr);
    Scope *global = &resolver.bindings.global;

    // 第一遍：所有函数名进入全局作用域。
    for (const auto &f : program.funs) {
        if (global->table.count(f->name)) {
            resolver.bindings.errors.push_back({"error: redeclared '" + f->name + "'"});
            continue;
        }
        global->table.emplace(f->name, Symbol{Symbol::Fun, f->name, f.get()});
    }

    // 第二遍：每个函数开自己的作用域，父作用域是全局表；
    // 作用域所有权交给 Bindings，遍历结束后符号依然存活。
    for (const auto &f : program.funs) {
        auto functionScope = std::make_unique<Scope>(global);
        resolver.current = functionScope.get();
        resolver.owner = f.get();

        for (const std::string &p : f->params) resolver.declare(p, Symbol::Param);
        for (const std::string &v : f->vars) resolver.declare(v, Symbol::Local);

        resolver.resolveStmt(f->body.get());
        resolver.resolveStmt(f->ret.get());

        resolver.current = nullptr;
        resolver.bindings.scopes.push_back(std::move(functionScope));
    }
    return std::move(resolver.bindings);
}

}  // namespace tip
```

```cpp
// file: src/irgen.hpp
// LLVM IR 生成：把 AST 翻译成 LLVM Module。
// 本章只覆盖整数核心：算术、比较、input/output、if/while、直接函数调用；
// 指针、记录、间接调用在第 44 章以后扩展，遇到时直接报错。
#pragma once

#include <map>
#include <memory>
#include <string>

#include "llvm/IR/IRBuilder.h"
#include "llvm/IR/LLVMContext.h"
#include "llvm/IR/Module.h"

#include "ast.hpp"
#include "symtab.hpp"

struct IRGen {
    // 三者均以 unique_ptr 持有：JIT 需要接管 Module 与 Context 的所有权。

    std::unique_ptr<llvm::Module> mod;
    std::unique_ptr<llvm::IRBuilder<>> b;

    const Bindings *bindings = nullptr;
    const FunDecl *cur = nullptr;

    // 结束后模块必须通过 verify。
    void gen(const ProgramA &program, const Bindings &resolved);

    llvm::Value *expr(const Expr *e);
    void stmt(const Stmt *s);

    bool verify() const;
    std::string dump() const;

  private:
    llvm::FunctionCallee rtInput_, rtOutput_;

    void genFun(const FunDecl *f, Scope *scope);
    void genWrapper(const FunDecl *mainFun);
```

```cpp
// file: src/irgen.cpp
#include "irgen.hpp"

#include <stdexcept>
#include <utility>
#include <vector>

#include "llvm/IR/BasicBlock.h"
#include "llvm/IR/Constants.h"
#include "llvm/IR/DerivedTypes.h"
#include "llvm/IR/Function.h"
#include "llvm/IR/Verifier.h"
#include "llvm/Support/raw_ostream.h"

using namespace llvm;

namespace tip {

IRGen::IRGen()
    : ctx(std::make_unique<LLVMContext>()),
      mod(std::make_unique<Module>("tip", *ctx)),
      b(std::make_unique<IRBuilder<>>(*ctx)) {
    // 运行时入口先声明：input 无参返回 i32，output 吃一个 i32。
    auto *i32 = Type::getInt32Ty(*ctx);
    rtInput_ = mod->getOrInsertFunction(
        "tip_input", FunctionType::get(i32, false));
    rtOutput_ = mod->getOrInsertFunction(
        "tip_output", FunctionType::get(Type::getVoidTy(*ctx), {i32}, false));
}

namespace {

// TIP 的 main 改名 tip_main：真正的 @main 是我们生成的 C 入口。
std::string emitName(const std::string &name) {
    return name == "main" ? "tip_main" : name;
}

}  // namespace

void IRGen::gen(const ProgramA &program, const Bindings &resolved) {
    bindings = &resolved;

    // 先创建全部函数（含类型），函数体互相前向调用时也能查到声明。
    auto *i32 = Type::getInt32Ty(*ctx);
    for (const auto &f : program.funs) {
        std::vector<Type *> args(f->params.size(), i32);
        auto *ft = FunctionType::get(i32, args, false);
        Function::Create(ft, Function::ExternalLinkage,
                         emitName(f->name), *mod);
    }

    for (size_t i = 0; i < program.funs.size(); ++i) {
        const auto &f = program.funs[i];
        cur = f.get();
        genFun(f.get(), resolved.scopes[i].get());
    }

    const FunDecl *mainFun = nullptr;
    for (const auto &f : program.funs)
        if (f->name == "main") mainFun = f.get();
    if (!mainFun) throw std::runtime_error("program has no main");
    genWrapper(mainFun);
}

void IRGen::genFun(const FunDecl *f, Scope *scope) {
    auto *fn = llvm::cast<Function>(mod->getFunction(emitName(f->name)));
    auto *entry = BasicBlock::Create(*ctx, "entry", fn);
    b->SetInsertPoint(entry);

    // 形参：alloca 槽位 + 存入实参；var 局部：alloca + 零初始化。
    for (size_t j = 0; j < f->params.size(); ++j) {
        const Symbol *s = &scope->table.at(f->params[j]);
        auto *slot = b->CreateAlloca(b->getInt32Ty(), nullptr, f->params[j]);
        b->CreateStore(fn->getArg(j), slot);
        locals[s] = slot;
    }
    for (const std::string &v : f->vars) {
        const Symbol *s = &scope->table.at(v);
        auto *slot = b->CreateAlloca(b->getInt32Ty(), nullptr, v);
        b->CreateStore(b->getInt32(0), slot);
        locals[s] = slot;
    }

    stmt(f->body.get());
    b->CreateRet(expr(f->ret->e.get()));
}

Value *IRGen::expr(const Expr *e) {
    if (const auto *x = dynamic_cast<const IntLit *>(e))
        return ConstantInt::get(b->getInt32Ty(), x->v, true);

    if (const auto *x = dynamic_cast<const VarRef *>(e)) {
        const Symbol *s = bindings->uses.at(x);
        return b->CreateLoad(b->getInt32Ty(), locals.at(s), x->name);
    }

    if (dynamic_cast<const InputE *>(e))
        return b->CreateCall(rtInput_);

    if (const auto *x = dynamic_cast<const Binop *>(e)) {
        Value *l = expr(x->l.get());
        Value *r = expr(x->r.get());
        switch (x->op) {
            case BOp::Add: return b->CreateAdd(l, r);
            case BOp::Sub: return b->CreateSub(l, r);
            case BOp::Mul: return b->CreateMul(l, r);
            case BOp::Div: return b->CreateSDiv(l, r);
            case BOp::Gt: {
                Value *p = b->CreateICmpSGT(l, r);
                return b->CreateZExt(p, b->getInt32Ty());
            }
            case BOp::Eq: {
                Value *p = b->CreateICmpEQ(l, r);
                return b->CreateZExt(p, b->getInt32Ty());
            }
        }
    }

    if (const auto *x = dynamic_cast<const CallE *>(e)) {
        const auto *nameUse = dynamic_cast<const VarRef *>(x->callee.get());
        if (!nameUse)
            throw std::runtime_error("ch12: 间接调用留待第 44 章");
        const Symbol *s = bindings->uses.at(nameUse);
        if (s->kind != Symbol::Fun)
            throw std::runtime_error("ch12: 间接调用留待第 44 章");
        auto *callee = mod->getFunction(emitName(s->name));
        std::vector<Value *> args;
        for (const auto &a : x->args) args.push_back(expr(a.get()));
        return b->CreateCall(callee, args);
    }

    throw std::runtime_error("ch12: 指针与记录构造留待第 44 章");
}

void IRGen::stmt(const Stmt *s) {
    if (const auto *x = dynamic_cast<const AssignS *>(s)) {
        const auto *target = dynamic_cast<const VarRef *>(x->target.get());
        if (!target)
            throw std::runtime_error("ch12: 经指针/字段写入留待第 44 章");
        const Symbol *sym = bindings->uses.at(target);
        b->CreateStore(expr(x->value.get()), locals.at(sym));
        return;
    }

    if (const auto *x = dynamic_cast<const OutputS *>(s)) {
        b->CreateCall(rtOutput_, {expr(x->e.get())});
        return;
    }

    if (const auto *x = dynamic_cast<const IfS *>(s)) {
        Function *fn = b->GetInsertBlock()->getParent();
        auto *thenBB = BasicBlock::Create(*ctx, "then", fn);
        auto *elseBB = BasicBlock::Create(*ctx, "else", fn);
        auto *mergeBB = BasicBlock::Create(*ctx, "merge", fn);

        Value *cc = b->CreateICmpNE(expr(x->cond.get()), b->getInt32(0));
        b->CreateCondBr(cc, thenBB, elseBB);

        b->SetInsertPoint(thenBB);
        stmt(x->then.get());
        if (!b->GetInsertBlock()->getTerminator()) b->CreateBr(mergeBB);

        b->SetInsertPoint(elseBB);
        if (x->els) {
            stmt(x->els.get());
            if (!b->GetInsertBlock()->getTerminator()) b->CreateBr(mergeBB);
        } else {
            b->CreateBr(mergeBB);
        }
        b->SetInsertPoint(mergeBB);
        return;
    }

    if (const auto *x = dynamic_cast<const WhileS *>(s)) {
        Function *fn = b->GetInsertBlock()->getParent();
        auto *header = BasicBlock::Create(*ctx, "wh.cond", fn);
        auto *bodyBB = BasicBlock::Create(*ctx, "wh.body", fn);
        auto *exitBB = BasicBlock::Create(*ctx, "wh.exit", fn);

        b->CreateBr(header);
        b->SetInsertPoint(header);
        Value *cc = b->CreateICmpNE(expr(x->cond.get()), b->getInt32(0));
        b->CreateCondBr(cc, bodyBB, exitBB);

        b->SetInsertPoint(bodyBB);
        stmt(x->body.get());
        if (!b->GetInsertBlock()->getTerminator()) b->CreateBr(header);

        b->SetInsertPoint(exitBB);
        return;
    }

    if (const auto *x = dynamic_cast<const BlockS *>(s)) {
        for (const auto &st : x->ss) stmt(st.get());
        return;
    }

    if (const auto *x = dynamic_cast<const ReturnS *>(s))
        b->CreateRet(expr(x->e.get()));
}

void IRGen::genWrapper(const FunDecl *mainFun) {
    // C 入口：按 TIP main 形参数目读 input，再调用 tip_main。
    // 不命名为 main——MinGW 目标会向 main 注入对 CRT 符号 __main 的调用。
    auto *fn = Function::Create(FunctionType::get(b->getInt32Ty(), false),
                                Function::ExternalLinkage, "tip_entry", *mod);
    auto *entry = BasicBlock::Create(*ctx, "entry", fn);
    b->SetInsertPoint(entry);

    std::vector<Value *> args;
    for (size_t j = 0; j < mainFun->params.size(); ++j)
        args.push_back(b->CreateCall(rtInput_));
    Value *r = b->CreateCall(mod->getFunction("tip_main"), args);
    b->CreateRet(r);
}

bool IRGen::verify() const {
    std::string err;
    llvm::raw_string_ostream os(err);
    bool bad = llvm::verifyModule(*mod, &os);
    os.str();
    return !bad;
}

std::string IRGen::dump() const {
    std::string out;
    llvm::raw_string_ostream os(out);
    mod->print(os, nullptr);
    return os.str();
}

}  // namespace tip
```

```cpp
// file: src/jitrun.cpp
#include "jitrun.hpp"

#include <cstdint>
#include <stdexcept>

#include "llvm/ExecutionEngine/JITSymbol.h"
#include "llvm/ExecutionEngine/Orc/Core.h"
#include "llvm/ExecutionEngine/Orc/LLJIT.h"
#include "llvm/ExecutionEngine/Orc/ThreadSafeModule.h"
#include "llvm/Support/TargetSelect.h"

using llvm::StringRef;
using llvm::JITSymbolFlags;
using llvm::orc::ExecutorSymbolDef;
using llvm::JITTargetAddress;
using llvm::jitTargetAddressToFunction;
using llvm::pointerToJITTargetAddress;
using llvm::orc::LLJITBuilder;
using llvm::orc::SymbolMap;
using llvm::orc::ThreadSafeModule;
using llvm::orc::absoluteSymbols;

namespace tip {
namespace {

// JIT 模块通过这两个宿主函数与外界交换数据。
const std::vector<int> *inQueue = nullptr;
std::vector<int> *outQueue = nullptr;
size_t inPos = 0;

extern "C" int32_t tip_input() {
    if (inPos >= inQueue->size()) return 0;
    return (*inQueue)[inPos++];
}

extern "C" void tip_output(int32_t value) {
    outQueue->push_back(value);
}

void initNative() {
    // 进程内只初始化一次。
    static const bool ready = [] {
        llvm::InitializeNativeTarget();
        llvm::InitializeNativeTargetAsmPrinter();
        return true;
    }();
    (void)ready;
}

[[noreturn]] void fail(llvm::Error e) {
    std::string text = llvm::toString(std::move(e));
    throw std::runtime_error(text);
}

}  // namespace

std::vector<int> runJit(IRGen gen, const std::vector<int> &inputs) {
    initNative();
    std::vector<int> outputs;
    inQueue = &inputs;
    outQueue = &outputs;
    inPos = 0;

    auto jitOrErr = LLJITBuilder().create();
    if (!jitOrErr) fail(jitOrErr.takeError());
    auto jit = std::move(*jitOrErr);

    auto defineHost = [&](StringRef name, void *addr) {
        SymbolMap symbols;
        symbols[jit->mangleAndIntern(name)] = ExecutorSymbolDef(
            llvm::orc::ExecutorAddr::fromPtr(addr), JITSymbolFlags());
        if (llvm::Error e =
                jit->getMainJITDylib().define(absoluteSymbols(symbols)))
            fail(std::move(e));
    };
    defineHost("tip_input", reinterpret_cast<void *>(&tip_input));
    defineHost("tip_output", reinterpret_cast<void *>(&tip_output));

    ThreadSafeModule tsm(std::move(gen.mod), std::move(gen.ctx));
    if (llvm::Error e = jit->addIRModule(std::move(tsm)))
        fail(std::move(e));

    auto mainAddr = jit->lookup("tip_entry");
    if (!mainAddr) fail(mainAddr.takeError());
    auto *entry = jitTargetAddressToFunction<int (*)()>(mainAddr->getValue());
    entry();

    return outputs;
}

}  // namespace tip
```

## 24.13 工程注意点

原理之外，记录五条实现层面的注意点。它们是上述原理在
工程中的直接推论，而不是与原理并列的"经验清单"。

1. **in 集合与 erase-then-insert 纪律不能省。** 队列去重
   是复杂度上界的一部分（16.3.5）；弹出时先 erase、入队
   时再 insert，保证"同点至多一份、可再次入队"两个语义
   同时成立。任何"入队时不查重"的省略都会让最坏重算
   次数失控，而且回归测试发现不了（终态仍对，只是慢）。

2. **"缺键即 ⊥"的解释必须全工程一致。** 本章三处消费这
   一约定：初始空映射、前驱合并时跳过未算点、打印时补 ⊥。
   任何一处换成"缺键即 ⊤"或"缺键即 0"，16.4 的论证即刻
   失效且不报错。约定的解释集中写在头文件注释里（sign.hpp
   的 SignEnv 一行），修改前先读它。

3. **边界条件在重算分支特判，不靠初始化。** entry 的值
   与图无关；放进重算分支使每次弹出 entry 都稳定返回
   边界值，队列行为不再依赖"entry 恰好入队一次"。过程
   间分析（第 40 章）会给 entry 加上调用点上下文，届时
   这个特判分支是唯一需要扩展的地方——结构预留好了。

4. **新旧比较用整个环境的 ==，不做逐变量短路。** 漏比
   一个变量就漏一次传播，错误表现为精度丢失（结果偏 ⊤）
   而非崩溃，极难被发现。std::map 的 operator== 恰好是
   逐项全等，直接用；不要自作聪明改成"比较哈希"——
   哈希碰撞就是漏传播。

5. **规格参数（eqs）宁可闲置不可删除。** `(void)eqs` 是
   一份声明："本求解器解的是第 23 章那组方程"。删掉参数
   能让签名更"诚实"，却也切断了规格与实现之间最后一根
   可见连线——未来实现漂移（比如有人改了邻接表方向）时，
   接口上的规格锚点是审查的第一站。闲置参数携带文档
   职责，是接口设计里合法的冗余。

## 24.14 小结

本章把第四篇前三章的积累拧成了最后一个部件，"格—方程—
求解"三件套至此齐备。

- 直觉上，不动点迭代是"从白纸出发只写被强迫的事实"：
  ⊥ 是零信息，join 只收拢不放大，传递只保守转换；
  从底出发收敛到最小不动点，从顶出发收敛到最大——
  初始值的选择就是精度的选择；
- 算法上，worklist 用"变化才传播"把朴素迭代的全图重扫
  压缩为受扰子图重算：队列 + 去重集合 + 重算-比较-写回-
  入队四步循环，FIFO 顺序下轨迹完全确定；
- 正确性上，"cur 永不超出 lfp"的不变量配"终止时全部
  方程满足"的事实，从两端夹出 cur = lfp；论证只消费
  单调性与"lfp 是不动点"两个前提，与第 19 章合一的
  夹逼论证同构；
- 终止性上，格高度是全部答案：符号格高 2，环境格高
  2V，重算次数 O(P·H)；高度无穷的域（常量、区间）会
