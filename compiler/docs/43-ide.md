# 第 43 章　IDE 框架：让可达的事实携带值

## 43.1 问题：IFDS 只说出了半句话

### 43.1.1 一个"明明知道，却答不出"的场面

第 42 章把 IFDS 框架完整地落地了一遍：我们为"可能未初始化"这一问题
设计了可分配的流函数，在超级图上做路径边制表，最后能精确地指出第
几个程序点、哪个变量可能未初始化。那场分析回答的问题只有一个形状：

> 事实 d 能不能沿一条有效路径到达程序点 n？

"能"或"不能"——这是一个布尔问题。对于未初始化检测它恰好够用，因为
一个变量要么带着"我还没被赋值"的标记到达，要么不带；标记本身没有
轻重之分。可是只要把问题换成编译器里同样常见的另一类，布尔答案立刻
显得不够。设想我们想做常量传播，在程序点 n 想知道变量 x 的值：

- 最理想的答案是"x 一定等于 11"——于是用 x 的地方都可以换成 11，
  运行时连一次内存读取都省了；
- 其次是"x 可能是任何整数"——什么也不能换，但分析到此为止也心安；
- 而"x 可达"这个回答几乎毫无用处：哪个程序点上 x 不可达呢？我们需
  要的是它到达时**携带的东西**，不是它到没到。

IFDS 的事实集合里，"x 是常量 11"和"x 是常量 20"会成为两个不同的事
实，理论上可以都塞进 D。但这条路走不长：常量的数目没有上界，程序
里出现多少个字面量、多少种组合，就要预先准备多少个事实；更要紧的
是，"x 由 y 变换而来"这种关系用平铺的事实无法表达——你无法声明事
实"x=y+1"，只能枚举它在每个具体程序里碰巧取到的值。我们需要的不
是更多的事实，而是让每条路径边**携带一个变换**：起点处的值经过这个
变换，成为终点处的值。

### 43.1.2 把变换挂到路径边上

一句直觉就能点明 IDE 的全部出发点：

> IFDS 的路径边说"事实 d₂ 能从 d₁ 到达"；IDE 的路径边多说半句
> "而且从 d₁ 处的值到 d₂ 处的值，经过的是函数 f"。

这里的 f 是一个从值格到值格的函数 f:L→L，称为**边函数**（edge
function）。路径还是第 42 章那套超级图上的路径，调用边、调用-返回
边、返回边的配对规则一概不变；变化的只是每条被枚举的路径边多出一
个"载荷"。分析者不再需要回答"这个点上 x 是不是常量 11"，而是先回答
一个与具体值无关的问题："从入口到这里，x 身上叠了哪些变换"，然后
把入口处的值喂给这叠变换，答案自己掉出来。

这个分工带来一个深远的好处：**边函数的枚举与具体值无关**。程序里出
现的函数名、赋值、调用结构是固定的，边函数的种类和复合方式在制表
阶段就能全部确定；真正的值在最后一步才代入。于是"哪些路径存在"和
"值沿路径怎么变"被拆成两个可以独立检查的阶段——这正是本章实现的
结构，43.4 节会专门讲。

### 43.1.3 为什么多项式时间仍然守得住

第 42 章论证过 IFDS 的复杂度：路径边数目是 O(N·D²)，每条边被处理
的次数有常数上界，尽管有效路径数目本身随程序长度指数增长，制表却
是多项式的。IDE 看起来更"重"——每条边还挂着一个函数——但复杂度
的论证纹丝不动，理由有三层，先点明、后面各节逐一落实：

第一，边函数不是每次调用重新发明的。本章只允许三种构造子（恒等、
常函数、复合），并且相同的函数在一个全局驻留池里只造一份，所以函
数的总数被程序中出现的常量数目和边数目钉死。

第二，两个相同端点、相同源/目标事实的路径边若携带的也是同一个函
数，就是同一条边，不重复枚举；边函数的"相等"因此可以直接用指针相
等判断，不需要逐棵比较函数树。

第三，也是最容易被忽略的：复合出来的函数必须在枚举过程中**规范化**。
同一段变换不管被包进多少层复合，规范化后都指向同一个代表，否则循
环里每转一圈函数外面就多一层壳，路径边集合无限增长，制表根本不会
停。规范化不是锦上添花的优化，而是终止性的一部分，43.6 节整节讨论。

### 43.1.4 本章的三个程序与阅读路线

本章用三个短小的 TIP 程序把框架的三面依次照亮：

- `const.tip` 只有 main：一句编译期可折叠的 `a = 3 + 4 * 2`，和一句
  混入 input 的 `b = a * 2 + input`。它展示字面量折叠、边函数如何
  生成、以及表达力边界——a 能算出 11，b 只能停在 TOP；
- `idc.tip` 引入一个身份函数 pid，main 以常量 7 在三个位置调用它。
  它展示常量如何**跨过程**传播：三次调用实参都是 7，共享的函数体
  里 x 等于 7⊔7⊔7=7，不降级，7 一路穿过三次调用回到 main；
- `idm.tip` 同样是身份函数，但三处调用传入的是 7、2、3。它展示上
  下文不敏感的代价：共享函数体里 x=7⊔2⊔3=TOP，于是连真正常量的
  那次调用 `a = pid(7)` 拿到的返回也是 TOP——站点互相"投毒"，这
  正是第 41 章 k=0 档位在 IDE 框架里的重演。

43.2 节先把值格与边函数形式化；43.3 节讲三种构造子和表达力边界；
43.4 节总览两阶段架构；43.5 节是全章最吃重的部分——边函数为什么
必须与入边的函数复合、沿四个位置分别怎么复合法；43.6 节讲终止性
与规范化；43.7 节导览程序与 CFG 编号；43.8 节逐行解读真实输出；
43.9 节给出正确性论证的完整思路；43.10 节是工程注意点。章末把本章
配套的全部文件整文件嵌入并逐段导引，读者无需另开源码目录。

### 43.1.7 常量的用途：优化器在等什么

花两章机器换来的"某点某变量恒为 c"，优化器拿去做什么？最直接的
三个消费者：常量折叠（用 c 替换该点之后的一切 x 引用，机器指令
里少一次寄存器读）、死代码消除（`if (x==7)` 的比较折叠成真后，
分支与另一支的代码整体消失）、以及过程间特化（x 恒为 7 时，被调
函数可以换成 x=7 的特化版本）。第 54 章会在 LLVM 的 SCCP pass 里
重访这组消费者——SCCP 正是"常量格 + SSA 图"的工业级亲戚，它的
 lattice 与本章 L 同构、它的"def-use 边上流动"与本章值阶段同
构。本教程把常量传播选为 IDE 的实例而非更花哨的指针别名或污点，
正是因为它的消费者最直白：分析输出能立刻翻译成用户看得见的优
化行为，可靠性命题（说 c 就真是 c）的分量也因此最重——优化器
对"精确"的信任是零容忍的，一次说错就把正确程序编译坏。

## 43.2 值格 L：常量住在哪里

### 43.2.1 三层常量格

本章边函数作用于其上的值格 L 是**三层常量格**：

- BOT（底）：对这个位置还没有任何信息——没有任何路径把值送到这里；
- c（常量层）：已知它恰好等于某个具体整数，程序中出现的每个字面量
  对应这一层的一个成员，记为 c₇、c₁₁ 等等；
- TOP（顶）：知道有值到达、但它在不同路径上可能是不同整数，无法
  收敛到任何一个常量。

偏序按"信息量"排列：BOT 在最下，常量层在中间（不同常量之间不可比
——c₇ 既不比 c₁₁ 大也不比它小，它们是不同的确定信息），TOP 在最
上。两个值的 join（最小上界）规则由此确定，值得逐一列出，因为后面
读代码、读输出时反复用到：

- BOT ⊔ x = x：底是 join 的单位元，"没有信息"与"有信息"合并，留下
  有信息的一方；
- c ⊔ c = c：同一个常量与自己合并，纹丝不动；
- cₐ ⊔ c_b = TOP（a≠b）：两个不同的确定信息无法用一个常量同时概括，
  只能升到顶；
- TOP ⊔ x = TOP：顶已经是"可能是任何整数"，并入什么都还是顶。

这组规则在代码里就是 `cJoin`：先处理两个 BOT 的情形，再看任一方是
TOP，最后比较两个常量的整数是否相等。留意常量层的成员理论上有无
穷多个（每个整数一个），但对一个具体程序，只有程序里出现过的常量
才会真的被造出来——这是 43.3 节论证函数空间有限时的一块基石。

### 43.2.2 BOT 与 TOP：一个字都不能混

BOT 和 TOP 在打印时都"不是一个具体数字"，初看容易混，但它们的语义
恰好对立，必须在动手之前分清：

- BOT 说的是**路径**：没有任何（被枚举出的）路径把这个事实送到这个
  点。它是不动点的初值，随着分析推进会被别的值取代；
- TOP 说的是**值**：路径确实到了，而且到的路径不止一条或路径上有
  input 之类的未知来源，汇合后无法确定为单个整数。

这个区分直接决定了两个实现决定。其一，边函数对 BOT 严格：输入
BOT 时输出也必须是 BOT（26.5.5 节），因为"没有路径到达的点"不应
凭空产生值——否则函数体会在从未被调用的情况下冒出常量来。其二，
打印环境时 BOT 的变量干脆不进结果表，而 TOP 的变量要明确显示为
TOP："没到达"和"到达但非常量"是两条不同的诊断信息，合在一起就
丢掉了一半分析结论。本章 `IdeResult` 的注释专门把这层意思写在字段
旁边。

### 43.2.3 环境：给每个变量配一个 L 值

一个程序点上的信息仍然用环境表示：σ : 变量名 → L。它与第 25 章常
量传播里的环境是同一个形状，只是值的集合从"符号/常量格"换成了本
章的三层格。变量在环境里取 BOT，表示控制流到达该点时该变量尚无
值——回想 TIP 局部变量声明时没有初始化子句，入口处它们携带的正是
"未初始化"语义；本章把入口处局部变量初始化为 TOP 而非 BOT 的理由
26.5.5 节会专门交代，这里先记住两个层次的区别。

环境本身在 IDE 里不是被直接传播的对象。第 25 章的做法是把整个环境
沿 CFG 边传递、在 join 点逐变量合并；IDE 不这么干：它把"一个变量
到另一个变量"的关系拆成一条条**单事实路径边**，每条边只谈一个源
事实和一个目标事实，环境是最后从所有事实的值里重新拼出来的。这与
第 42 章"零事实 + 单变量事实"的设计完全同构，下一小节形式化。

### 43.2.4 路径边：端点、事实与边函数

全局程序点依旧用一对坐标指定：PP =（函数名，函数内 CFG 节点号）。
事实集合也与第 42 章同型：一个特殊的**零事实** 0，加上程序中的变量
名。零事实是"不依赖任何变量值"的载体：字面量、input、纯字面量表
达式的折叠结果都从零事实出发，因为它们不引用任何变量。

一条 IDE 路径边是五元组：

> (sp, d₁) ── f ──▶ (ep, d₂)，

读作：存在一条从 sp 到 ep 的有效路径，它把源事实 d₁ 送到目标事实
d₂，并且 d₁ 处的值到 d₂ 处的值经过边函数 f:L→L。例如赋值
`a = 3 + 4 * 2;` 生成的边是

> (main 入口, 0) ── const 11 ──▶ (赋值后继点, a)，

常函数 const 11 不管输入是什么都输出 11，恰好表达"右端与任何变量
无关、结果恒为 11"。而赋值 `r = x;` 在 pid 体内生成的边携带恒等
函数 id：r 处的值就是 x 处的值，具体是几要等 x 的值确定。

### 43.2.5 同一点上多个值怎么汇合

可能有多条路径边把同一个（点，事实）当作端点，各自携带不同函数、
源自不同路径。这时终点事实的值是所有贡献的 join：先把各边在其源
点处的值经各自的函数算出，再逐次 cJoin。两条规则保证这件事与"真
实程序沿多条路径到达该点"的语义对得上：

- join 是对"多条具体执行在此汇合"的抽象：真实的一次执行只走其中
  一条路径、取一个具体整数；抽象把所有可能的具体值收进一个 L 成
  员，不同就升 TOP，从不编造一个居中的值；
- 边的枚举与值无关，所以"后来又长出一条到达同点的边"不会推翻之
前的结构，只需在值不动点里多算一次贡献——这是把枚举与求值分成
两阶段的直接收益（43.4 节）。

### 43.2.4 L 的选型：与符号格、区间格的对照

把 L 换掉，IDE 就换一个问题——这个自由度值得用三种域排在一起看。
常量格 L=⊥/c/⊤ 关心"值是否唯一确定"，join 只在两个相同常量相遇时
保住精度；符号格（第 21 章）关心"正负号"，7 与 2 在它眼里都是
+，join 不降级；区间格（第 30 章）关心"范围"，7 与 2 join 成
[2,7]。三个格对同一对值 7、2 的态度分别是 TOP、+、[2,7]——域的
分辨力依次增强，格的高度依次变高（常量格每层一个值、符号格两层、
区间格无限高需要加宽）。IDE 对 L 的要求只有两条：有限或有界收敛
（值阶段要停）、函数族复合封闭（边函数语言要闭）。三构造子语言
对常量格是闭的（const、id、复合都不产生新形状）；对符号格同样闭
（把 const 换成"格点常量"即可，练习六）；对区间格不闭——区间的
算术需要"c ↦ [l+c, u+c]"这样的区间函数，族比三构造子大得多，规
范化律也要跟着重写。这就是为什么教程把常量格做成本章实例：它让
函数语言的边界（26.3）以最纯净的形态暴露。

### 43.2.5 乘积域与环境格的关系

第 25 章把整个环境（所有变量一次）放进一个格；本章把环境拆成单
变量事实、每条边只带一个变量的 L。两种视角的代数关系是乘积：
环境格 ≅ L^Var（每个变量一个分量，逐点 join）。可分配的分析在乘
积域上可以逐分量独立求解——这正是第 42 章把集合拆成单点事实的
同一个理由在第 43 章的重现。理解了这一层，就能回答一个常见的设
计问题：什么时候该用环境式（第 25 章风格）、什么时候该用单事实
式（本章风格）？答案是关系依赖：若变量之间的依赖不需要跨分量表
达（常量、符号、区间都是逐变量的），单事实式更细粒度、过程间配
对更简单；若需要 x 与 y 的联合关系（比如"x 为常量当且仅当 y 为
常量"），乘积拆分会丢信息，要么回到环境式、要么把关系编码成复
合事实（"变量对 (x,y)"作为 D 的元素——事实域变大，但框架仍然
成立）。IFDS/IDE 的"框架与问题正交"在域的层面同样成立。

### 43.2.6 从第 25 章到本章：一次概念搬运清单

把第 25 章的知识搬到本章，每一件行李都有新住处。平坦常量格整体
搬进 Const 的三枚标签，join 一字不改；强更新（赋值即确定）搬进
classify 的 const 分支——纯字面量赋值对目标变量的值是完全确定
的；弱更新（合并）搬进 cJoin——多条来源边的值在此相遇；input
的 TOP 搬进 classify 的第二个分支；BOT 吸收搬进 efApply 的第一
行。没有搬的是**环境整体**：第 25 章每个程序点一个完整环境，本
章每个（点, 事实）一个值——拆分的收益是过程间配对只需要谈一个
变量，代价是打印层要自己把环境拼回去（scopeOrder 与 showEnv）。
读者若在第 25 章的 soundness 验证器上花过时间，本章的交叉核对
行（const.tip constants agree）就是那位老朋友在门口点头。

## 43.3 最小函数语言：三种构造子与表达力边界

### 43.3.1 三种构造子

本章的边函数只用三个构造子生成：

- **恒等函数** id：id(x)=x。变量拷贝（r=x）、事实沿普通边原样存活
  的场合用它；
- **常函数** const v：const v(x)=v。字面量折叠结果、input、以及一切
  无法精确表达的右端，用它把结果钉死成某个常量或 TOP；
- **复合** f∘g：(f∘g)(x)=f(g(x))。一条路径穿越多个程序点时，沿途
  的函数依次复合，它不在代码里手写出现，全部由 `efCompose` 产生。

三者的代码表示是 `EdgeFnD`：一个 kind 标记、常函数时有效的 value
字段、复合时有效的两个子函数指针。构造统一走 `efMake`：先按"种类
+常量种类+常量值+两个子函数指针"组成键，在驻留池 `fnPool` 里查，
查到就直接返回已有的那一份。这一步保证了同构造的函数在整个程序
里只有一个地址，路径边的判等可以直接比较 `fn.get()`。

### 43.3.2 表达力边界：为什么 x+1 进不来

只有三种构造子，立刻可以看出一类函数缺席：**算术函数**。没有"+1"
这样的构造子，也没有"乘 2"。这对本章的精度有直接的、在输出里肉
眼可见的后果：`const.tip` 里 b 的右端是 `a * 2 + input`，即使 a 在
前一句已被确定为 11，分析也算不出 b=22——表达式分类器发现右端既
不是纯字面量树、也不是单个变量，就给出最保守的 const TOP，b 从被
赋值的那个点起一路 TOP。

这里需要诚实地说明：算术函数缺席是**教学选择**，不是 IDE 框架的内
在限制。IDE 原论文允许边函数是任意"能有限表示、能复合、能有效求
值"的函数；加入"+c"一族构造子在常量格上仍然可以规范化——
(+c)∘const k 折成 const(k+c)，(+c)∘(+d) 折成 +(c+d)——函数空间依然
有限，真实的工业常量传播器做的正是这类事。本章刻意只给三种构造
子，是因为它们已经足以演示 IDE 的全部机制（制表、复合、终止），而
且每加一族构造子，就必须同时为它补一组规范化律，漏一条就可能破
坏终止性。读者在 43.6 节学完规范化之后，完全有能力把"+c"加进自
己的实现——43.10 节会给出扩展时的检查清单。

记住这个边界的形状：**能表达的是"值原样流动"和"值被钉死"，不能
表达的是"值被计算"**。这就是为什么本章标题说常量传播，而精确到的
常量实际上只有两类来源——字面量折叠，和它们在身份式传递（拷贝、
参数绑定、返回）中一路保住的值。

### 43.3.3 classify：把一个表达式翻译成（源事实，边函数）

表达式与边函数之间的桥是分类函数 `classify`，它对每个右端表达式
给出一对信息：值从哪个**源事实**来（零事实或某个变量名），以及套
上什么**边函数**。四类情形，代码顺序即是判断优先级：

第一，整棵表达式树能折叠成整数（`constEval` 递归成功）→ 源事实是
零事实，边函数是 const k。`constEval` 是一个小型的常量文件夹：叶
子是整数字面量直接给值；二元运算先递归求两边，两边都折出来才按
运算符算，任何一边折不动就整体放弃。除零单独处理：除数为 0 时折
叠失败（返回"无值"），把这个表达式留给运行时——真实执行同样会
在这里炸，分析不该假装它等于什么。

第二，`input` 表达式 → 源事实零事实，边函数是 const TOP。input 在
每次具体执行里取什么值由外部决定，静态看来它就是"任意整数"的产
生源。

第三，单个变量引用 x → 源事实就是 x，边函数是 id。这是唯一"值从
另一个事实流过来"的情形：目标变量将来取什么值，完全由 x 在到达
时的值决定，不增不减。

第四，其他一切（含变量的算术、比较等）→ 源事实零事实，边函数是
const TOP。注意它与第二类的微妙差别：这里 TOP 不是因为值来自外部，
而是因为**本套函数语言表达不出这个计算**。两类在结果上同为 TOP，但
43.9 节论证可靠性时要把它们与"上下文合并"并列为 TOP 的三个来源，
来源不同，安全的理由相同。

### 43.3.4 一个值得停下来的细节：折叠是递归的

`constEval` 必须递归，这个细节在开发过程中真的咬过人。若只在表达
式恰好是单个整数字面量时才认作常量，那么 `3 + 4 * 2` 会被归入第
四类、给出 TOP，a 永远算不出 11——框架其余部分完全正确，结果却在
最该出彩的例子上全 TOP。递归折叠把任意深度的"纯字面量子树"一次
算尽：乘法优先于加法这件事在 AST 里已经由文法分层和括号结构定好
（AST 是去掉语法噪音的树），文件夹只需按树自底向上求值，不需要再
操心优先级。

### 43.3.4 两个构造子为什么不够

三构造子（id、const、compose）是不是最小的闭族？可以先用两个构
造子试一试：只有 id 与 const、不许 compose。任何单条边的函数都
还是可表达的（本地语义就是 id 或 const）；但路径的累积不行——
"先经 const 7 再经 id"在两构造子语言里必须逐段求值而不能合成一
张牌，路径边的判等就得带着"函数序列"而不是"函数"，序列在循环里
无限增长，制表不终止。compose 不是为了表达力（逐段已经覆盖），
是为了**有限表示**：它让任意长路径的累积坍缩成一张可判等的牌。
反过来，四个构造子（比如加"+c"）扩大表达力但要求补律——26.10.4
的成对纪律。三这个数字的真正含义是：恰好让"闭包有限、律恰好四
条、常量传播的精确情况全覆盖"。数学上这对应自由幺半群（compose
的自由结构）对 {id, const} 生成子按四律取商——商有限，正是可制
表性的代数面目。

### 43.3.5 表达力边界的三个具体牺牲

边界不是抽象声明，逐个看它牺牲了什么。牺牲一：x=y+1。y 的常量
是 7 时真值应为 8，本章语言说不出"+1"，classify 只能给 const
TOP——8 这个常量在整个下游都丢失。牺牲二：条件吸收。if (x==7)
的真分支里 x 必为 7，无论来路给什么；路径条件到值的事实需要
"满足条件则 const 7"这条边函数，三构造子里没有条件这个形状
（第 32 章路径敏感专门补这一层）。牺牲三：跨变量的值关系。swap
之后 a 的值等于 b 的旧值，"等于另一变量的旧值"是 id 能表达的
（a↦b 的拷贝），但"b 的旧值加 a 的旧值"这类二元关系超出单事实
框架——不是函数语言的锅，是单事实拆分本身的边界（26.2.5）。三
个牺牲分别指向三条补救路线：算术构造子族（+c 等）、路径敏感
（第 32 章）、关系式分析（教材之外的 octagon/polyhedra 一族）。
读者将来在工业分析器里看到这三族扩展时，会发现它们的实现恰好
挂在今天这三个缺口上。

## 43.4 两阶段架构

### 43.4.1 阶段一：带函数的路径边枚举

实现的第一阶段与第 42 章的 tabulation 逐行同构：一个路径边集合
（去重用）、一个工作表（调度用），从 main 入口的种子出发，对每条
取出的边按它端点的种类——调用点、被调函数出口、普通节点——分别
扩展。唯一的区别是每条边创建时多带一个 EdgeFn，以及扩展时新边的
函数不是拍脑袋写的，而是由本地函数与入边函数**复合**得到（26.5
节的主题）。

main 的种子有两类，与第 42 章一致：零事实的自环，以及 main 中每个
声明的局部变量的自环，函数都为 id——入口处事实"从自己到自己、值
原样"。被调函数第一次被进入时，同样补它的局部变量自环。参数不作
为种子：参数的值只能从调用边进来，凭空在入口造种子会让从未被传
入的值也出现。

### 43.4.2 阶段二：值不动点

边集合枚举干净之后，第二阶段才把值放上去：

- 在每个已进入函数的入口，零事实的值置为 TOP——"程序启动，入口条
  件不约束任何变量"；局部变量在入口也置为 TOP——它们的值未知；
- 然后反复扫描所有路径边：取出源（点，事实）的当前值，经边函数
映射，cJoin 进目标（点，事实）；没有任何一次扫描使值上升时停止。

值格上每个事实的"生涯"很短：从 BOT 出发，最多先升到某个常量、再
升到 TOP（或者直接被多个不同常量顶到 TOP），此后 join 不再产生变
化。边集合有限、每次上升都沿格向上且格中每条链上的上升次数有上
界，不动点必然到达——26.6.3 节给出这个论证的精确版本。

### 43.4.3 为什么拆成两阶段而不是边枚举边算值

边枚举和值迭代其实可以交织：每发现一条新边立刻在当前值上算一遍。
本章选择分两阶段，理由有三：

其一，边集合在枚举完成前会持续增长，交织求值时同一条边可能因新边
改变了源点值而被反复重算，调度顺序敏感、调试困难；两阶段把"结构
问题"和"值问题"彻底分开，每阶段各自可验证——枚举阶段可以像第 42 章那样只查路径边集合，值阶段可以固定边集合单查不动点。

其二，值不动点的输入是一个纯粹的、不再变化的边集合，它因此可以用
最朴素的"反复全扫"实现，不需要工作表；教学上每一行代码都对应一
条不动点规则。

其三，两阶段在语义上与交织做法等价：边函数只依赖边的结构而不依
赖具体值，先枚举全部边不会产生交织情况下"本不该存在"的边——边
的存在条件里只看事实是否匹配（43.5 节各处的 match），从不看值。
这是一个可以向读者明示的简化：我们用一点重复扫描的计算量，换来了
结构的清晰。

### 43.4.4 从结果拼回环境

值不动点结束后，环境是从（点，事实）的值表反拼的：常量值照实写
入（optional 持有整数），TOP 写成 nullopt（"已知非常量"），BOT 不
进表（"没有值到达"）。于是打印一个点时，每个变量的状态三选其一，
43.8 节读到的每行输出都可以这样逐列解释。

### 43.4.1 为什么不能一步到位：单阶段方案的两个失败形态

两阶段（先枚举带函数的路径边、再解值不动点）不是唯一 imaginable
的架构，把单阶段的两个失败形态摆出来，两阶段的合理性才落地。失
败形态一：边与值同轮推进——弹出一条边就立刻求值下推。问题在值
的**迟到**：调用点 3 的实参 a 的值，要等调用点 2 的返回边把 7 送
到 (main:3, a) 之后才非 BOT；若弹出实参边时 a 还是 BOT，efApply
按 BOT 严格返回 BOT，这条边的贡献永远丢失——除非允许"值到达后
重新弹出全部相关边"的重扫，而重扫等于承认了第二阶段。失败形态
二：按需惰性求值（查询某点值时才沿边回溯）——回溯在调用链上指
数展开，且循环处的递归求值需要记忆化，记忆化的键就是（边, 输入
值）对，最终还是长成一张与阶段一等大的表。两种失败合起来说明：
**结构（哪些边存在）与数据（值是多少）天然分两层**，先把结构定
型、再在固定结构上流动值，是让"迟到的值"有处可补的唯一干净安排。
第 42 章的 IFDS 没有这个问题，因为布尔事实没有"迟到"——存在性
一次判定；值的引入使分层成为必要，这是 IDE 相对 IFDS 在架构上
的真正增量。

### 43.4.2 两阶段的测试红利

分层除了让迟到的值有处可补，还给测试带来一层红利：结构问题与
数值问题可以在不同的断言面上各自锁定。结构的断言面是边集合——
阶段一结束后边数、边端点、incoming 条目数都是确定值，与值无关；
数值的断言面是环境——阶段二的输出只依赖边集合与边界值。给两
个面各写一套快照测试，任何回归都能先被分流到"结构错了"或"值
错了"，再进对应阶段的代码里找。单阶段实现没有这个断层可下刀，
回归永远要在一张大表里猜。教程的 check_example 把两層断言压成
一个输出对账，但读者做 26.14 的练习时，手动分层排查（先数边、
再看值）会快得多——26.10.5 的调试顺序建议，背后就是这层红利。

## 43.5 边函数的复合：本章最吃重的机制

### 43.5.1 一条路径上的函数怎样累积

沿一条具体路径 π，假设连续经过三个程序点、每点的本地边函数依次是
f₁、f₂、f₃（f₁ 作用于入口值），那么入口值 v 到达末端时已经过

> f₃(f₂(f₁(v)))，

即总变换为 f₃∘f₂∘f₁，注意书写顺序与经过顺序相反：**后经过的函数
在复合的外层**。这正是每创建一条新边时，它的函数必须由"本地函数
在外层、入边已携带的函数在内层"复合而成的原因——入边的函数概括
了整条来路，来路的变换必须先作用，本地变换在它的结果上接着作用。

如果丢掉这个复合、新边只带本地函数，等于宣布"我不记得从入口到
此经过了什么"，于是值不动点只能拿源点处的当前值直接代入；在循
环和链式传递里这会系统性地丢值。下面四个位置逐一看来，它们覆盖
了枚举阶段全部的建边场景。

### 43.5.2 普通节点的存活边：id∘e.fn

在普通赋值节点，未被 kill 的事实要沿后继边存活。代码给出的函数是

> efCompose(efId(), e.fn)

即 id∘（来路函数），规范化后就是来路函数本身（43.6 节第一条律）。
既然等于来路函数，为什么不直接写 e.fn？写 id∘e.fn 是为了把"此处
的语义是事实原样存活、本地不施加变换"明确地表达在代码里——读代
码的人看到 id 就知道这是一条存活边；而且规范化律保证它与 e.fn 指
向同一个驻留对象，写法不带来任何额外开销。

这里曾经的错误写法是直接给一个新造的裸 id：函数语义上"等于没
来路"。值不动点在这条边上只会把源点的值（常常是入口的 TOP）原样
搬到目标，而源点若因分阶段到达尚未拿到常量，目标就永远停在
TOP——即便同一条来路在别处已把常量送到了源点的另一条边上。问题
的根子是：**值只从源点的当前值来，而来路函数所编码的"同一源事实
在不同进入方式下的值"信息被抹掉了**。与入边函数复合，来路才得以
延续。

### 43.5.3 普通节点的生成边：cls.fn∘e.fn

赋值 `x = E;` 要生成目标事实 x。由 `classify(E)` 得到（源事实 s，本
地函数 cls），当边所携事实与 s 匹配时，生成边的函数是

> efCompose(cls, e.fn)

读作：先经来路函数把入口值变成"源事实到达该点时的值"，再经 cls
把它变成 x 的值。以 pid 体内 `r = x;` 为例：classify(x) 给出
（x，id），若入边携带的正是事实 x，则生成边函数 id∘来路 = 来路
本身——r 的值就是 x 沿同一条来路带进来的值，来路是从某调用点的
实参边接续的，于是 r 拿到的正是该次调用的实参常量。

反例是纯字面量赋值 `a = 3+4*2;`：classify 给出（零事实，const
11），与携带零事实的入边匹配，生成 const 11∘来路；规范化时 const
11 在外层，复合直接折成 const 11——来路是什么无关紧要，右端不依
赖任何变量，结果钉死 11。两种极端（纯变量拷贝、纯常量）以及它们
之间的一切都由同一个复合公式处理，不需要分支特判。

### 43.5.4 调用边：实参函数与来路复合

调用点处，实参 a_i 要流向被调函数的形参 p_i。对第 i 个实参，
classify 得到（源事实 s，本地函数 cls），当入边所携事实与 s 匹配
时，调用边的函数 cf 是

> cf = efCompose(cls, e.fn)，

并且这个 cf 连同调用方的起点一起登记进 **incoming** 表：键是（调用
点，形参事实），值是一组调用方配对（起点、源事实、cf）。incoming
回答的问题是："将来这个被调函数从这个点返回时，有哪些调用方的、
带着什么变换的进入在等着？"——第 42 章的 incoming 只记事实，本章
必须把调用边函数一并记下，因为返回值要沿来路反向复合回去。

零事实也走一条调用边（函数=来路函数），并同样登记 incoming：被调
函数里那些不依赖参数、只依赖控制到达的事实（比如纯字面量折叠后
作为返回值）需要它才能与具体调用方配对。

### 43.5.5 调用-返回边与出口返回边

**调用-返回边**处理"绕过调用现场"的局部事实：调用点之后，除了接
收返回值的左值被 kill，其余在调用点已知的事实原样可用。函数仍是
存活公式 id∘e.fn——调用过程不改变调用方的局部变量，它们带着自己
沿来路算出的值直接跨过调用点。左值不发存活边：它的新值只能由返
回边产生，旧值在调用后语义上已不存在。

**出口返回边**是复合层数最多的一处，值得逐层拆开。被调函数执行到
出口点、且所携事实与返回表达式的源事实匹配时：

- classify(返回表达式) 给出（源事实，retFn）；
- 对每个曾登记的调用方配对 ck，总函数是

> total = efCompose(retFn, efCompose(e.fn, ck.cf))。

从内向外读：ck.cf 把调用方入口值沿"实参→形参"的调用边送进函数
体；e.fn 把形参值沿函数体内的路径送到返回点（pid 里这是 r=x 的
id 传递）；retFn 把返回点的事实映射为返回值（pid 里返回 r，仍是
id）。三层复合恰好覆盖"调用方 → 函数体 → 返回点 → 调用方左值"的
完整旅程。最后产生的边落在调用点的**后继点**、目标事实是左值，于
是 main 在调用语句的下一个节点拿到结果——43.8 节会看到这个落点
选择如何解释"调用语句所在节点处左值仍旧、后继节点才更新"。

### 43.5.6 BOT 严格：死路径不产生值

所有边函数的求值 `efApply` 都先检查输入：BOT 进、BOT 出。为什么这
条不能省？设想函数 g 从未被调用，枚举阶段仍可能因为保守扩展而存
在指向 g 体内某些事实的边（本章实现里参数边只在调用点生成，实际
不会；但 BOT 严格是更一般的保障）。若边函数不 BOT 严格，const 类
函数会在输入 BOT 时也输出常量，g 体内凭空冒出值，甚至沿返回边送
回调用方——分析会报告"g 一定返回常量"而 g 根本没人调。

BOT 严格与"入口处置 TOP"并不矛盾，反而是一对配合：TOP 表示"入口
路径存在、值未知"，真实程序从 main 启动这条路径是给定的；BOT 表
示"尚无路径到达"。值从入口的 TOP 沿真实枚举到的边向下流，沿途
const 函数把 TOP 或常量映射成确定值，id 与复合保持传递；没有边到
达的事实保持 BOT，不出现在环境里。

### 43.5.7 四条律的手工演算

把四条规范化律各自代入具体数字算一遍，比读定义记得牢。律一
id∘g=g：来路函数是 const 7（第一次调用的实参牌），本地是 id（x
的存活边），复合 id∘const7——外层 id 什么都不做，牌仍是 const
7；代码直接返回 g，连 Compose 对象都不造。律二 f∘id=f：来路是
id（入口自环的牌），本地是 const 11（a=3+4*2 的生成边），复合
const11∘id——内层等于没过，牌是 const 11。律三 f∘(const c)=
const(f(c))：来路 const 7、本地 const 11（假设某边如此），复合
外层 const11 作用在 7 上得 const 11——注意结果与来路值无关，
来路携带的 7 被"覆盖"了；这条律在生成边遇到常量实参时高频触
发。律四 (const d)∘g=const d：来路任意（比如 id）、本地 const
TOP，复合 const TOP∘id=const TOP——外层一旦是 TOP，来路的任何
精度都救不回来。四条律各守一个方向：一、二消灭冗余的 id，三把
"常量来路"折进本地，四把"本地封顶"提前结算。合起来，任何复合
序列最终坍缩成三种形状之一：id、const v、或若干非平凡函数的
Compose 链——而链上的每个环节都是"生成边造出的非 id 非 const
函数"，本章语言里这样的函数不存在（classify 只产 id 和 const），
所以链长永远为 1，函数空间有限。表达力边界与终止性在此汇合：
**正因为说不出复杂函数，规范化才能把空间压回有限**。

### 43.5.8 复合的交换律幻觉

初学者最容易在三构造子语言里找交换律，值得把话说死：复合不可
交换，且差得很远。const 7∘const 8=const 7（外层覆盖），而 const
8∘const 7=const 8——两个方向两个答案。id 与谁都交换（它是单位
元），这个唯一的例外让"交换律幻觉"在全是拷贝传递的程序里成立
（idc 的 pid 恰好全是 id），一旦混进一个常量生成边，幻觉破灭。
26.10.3 的"念出声"检查法的理论根据就在这里：方向错误的复合在
纯 id 的世界里测不出来，测试程序必须包含 const 生成边才能暴露
——练习五的另一半意义。

## 43.6 终止性：规范化与驻留

### 43.6.1 不规范化会发生什么

路径边枚举为什么需要担心终止？关键在路径边的判等包含边函数指针：
两条端点和事实都相同的边，只有携带同一函数对象时才算同一条。复合
若只老实包壳、不做化简，那么在一个循环里每转一圈，同一个存活事
实携带的函数就多一层 Compose 外壳——

> id，id∘id，id∘(id∘id)，……

语义上全等于 id，但指针各不相同；每层壳都被当成新边，新边再进入
工作表、在循环里又长出一层，枚举永不停。这不是假想：本章开发中
去掉规范化的版本在小程序上就直接挂住，工作表只增不减。

### 43.6.2 四条规范化律

`efCompose` 在真正造 Compose 之前按四条律化简，它们就是恒等与常函
数的代数性质：

- id∘g = g：恒等在复合外层，什么都不做，去掉；
- f∘id = f：恒等在内层，来路先过恒等于没过，去掉；
- f∘(const c) = const(f(c))：内层是常函数时，复合在任何输入上都等
  于"f 作用在常量 c 上"，直接算成一个新常函数；
- (const d)∘g = const d：外层是常函数，内层算出什么都被丢弃，结果
  恒为 d。

前两条消灭 id 外壳，后两条把碰到常量的复合压扁成常量。任意一段复
合，只要内部出现 id 或常量就逐层坍缩；剩下能以 Compose 形式存在的
只有"真·变量间的多层传递"，而这样的传递链条数目被程序的边和变量
数目钉死——函数空间有限，路径边集合因此有限，枚举必然终止。

### 43.6.3 值不动点为什么终止

值阶段的终止性是标准的格论证，但值得把"常量层有无穷多个成员"这
个表面障碍点破：对任一（点，事实），其值沿格向上的路径只能是

> BOT → 某个具体常量 c → TOP

形状，最多两次严格上升——它不可能从 c₇ 再升到 c₁₁（两者不可比），
出现不同常量时直接 cJoin 到 TOP。一次不动点扫描里任何值的上升都
是上面这两步之一，可上升的总次数不超过事实数目的两倍；扫描之间
若没有上升即停止，所以扫描轮数也有上界。加上边集合在阶段一结束
后已经固定，整个值阶段必然在有限轮后停在最小不动点。

### 43.6.4 驻留池：让"相等"变成"同一个指针"

规范化依赖一个前提：两处独立构造的 id（或 const 7）必须是同一个对
象，否则 f==id 这种指针比较永远失败，第一条律就救不了循环。驻留
池 `fnPool` 保证这一点：键在子函数被 move 前提取（裸指针不随
move 改变，这行注释解释了顺序），同键的构造请求拿回同一个地址。
于是从边函数角度看，"结构相等"与"指针相等"在驻留之后是一回事，
路径边集合的去重、规范化律的判定都可以用裸指针完成，不做深层比
较。

### 43.6.3 驻留池的内存形态与对象寿命

fnPool 是进程生命期的全局映射，键含裸指针、值是 shared_ptr——
对象一旦入池永不销毁。对教学框架这是正确选择：判等稳定、代码短。
工业实现会换成 arena 分配加代际回收（分析结束整池释放），或干脆
用 GMP 风格的位打包把小函数编码成整数。值得一提的内存账本：池
里对象数的上界就是"规范化后函数空间"的大小——本章语言里是
1（id）+ |L|（各常量）+ Compose（不存在，因 classify 只产 id 与
const，任何 Compose 在律一/三/四下坍缩）。所以整个池实际上只住
着几十个对象：一个 id、每个出现过的常量一个、TOP 一个。这个账
本再次从内存侧印证了 26.3.4 的结论——函数语言小，池就小，制表
就快；扩语言之前先估池的大小，是这类框架的第一道预算。

## 43.7 程序导览与 CFG 编号

### 43.7.1 const.tip

`const.tip` 只有 main，声明 a、b 两个局部变量。第一句把纯字面量表
达式 3+4*2 赋给 a，第二句把 `a*2+input` 赋给 b，随后两次输出，最后
return 0。它的 CFG 是一条直线：入口（节点 1）→ 两个赋值（节点 2、
3）→ 两个输出（节点 4、5）→ return（节点 6）→ 出口（节点 7）。

### 43.7.2 idc.tip

`idc.tip` 有两个函数。pid 有参数 x、局部变量 r，函数体只有
`r = x;`，返回 r；它的 CFG：入口 1 → 赋值 2 → return 3 → 出口 4。
main 声明 a、b、c，连续三次调用 pid（分别传 7、a、7），三次输出，
CFG：入口 1 → 三个调用赋值（节点 2、3、4）→ 三个输出（5、6、7）
→ return 8 → 出口 9。三个调用点就是节点 2、3、4。

### 43.7.3 idm.tip

`idm.tip` 的 pid 与上面完全相同。main 声明 a、b：先 `a = pid(7);`
（节点 2），然后一个带 else 的 if（分支节点 3），两支分别是
`b = pid(2);`（节点 4）和 `b = pid(3);`（节点 5），两支汇合后两次
输出（节点 6、7），return 8，出口 9。三个调用点是节点 2、4、5。

### 43.7.4 三个程序的设计意图

三个程序不是随手挑的样例，而是一组控制变量。const.tip 没有调用，
它校准基线：任何过程间机制都不该改变无调用程序的结果，26.8.5 与
第 25 章的一致性在这一份上最纯粹。idc.tip 三个调用点传"7、a、7"
——两个直接常量夹一个变量，变量又恰好在前一个调用的返回值里拿到
7；三个来源合并后仍是 7，它展示的是**合并不降级的条件**：所有调用
方对同一形参的意见一致时，共享函数体免费获得精确。idm.tip 把中间
那个 7 换成 if/else 里的 2 与 3，只改这一个变量，其余原样——于是
x 的三个来源变成 7、2、3，函数体从精确跌到 TOP，连无辜的 a 一起
带走。idc 与 idm 合起来构成一次单变量实验：精度丢失的因果链完全
暴露在两份输出的 diff 里，读者做 26.14 的练习时可以逐行对出来。

### 43.7.5 编号与输出行的对应关系

26.7 给出的编号在输出里逐行出现，对应关系有一条容易踩空的缝：
输出行打印的是**该结点执行前**的环境（边的落点语义），所以"节点
2：a=TOP"说的是 a=pid(7) 执行**前**的 a。读输出时把每行想成
"即将执行这行语句时，世界长这样"，语句的效果永远出现在下一行
——26.8.1 的节点 2/3 现象、26.8.7 的节点 2 现象都是这条约定的
直接推论。CFG 编号本身由第 11 章构造器的先序分配决定：块内语句
按出现顺序、if 的分支点先于分支体、循环条件点先于循环体。三份
输出的行序因此与源码序一致，肉眼对读不需要跳。

## 43.8 真实输出逐行解读

### 43.8.1 const.tip：节点 2 的 TOP 和节点 3 的 11

先看最容易发问的一处：节点 2 明明是 `a = 3+4*2;`，输出却显示
a=TOP；而到节点 3，a 又变成了 11。理解了 26.5 的边方向这就毫不奇
怪：

- 入口处局部变量 a 的自环带 TOP；入口→节点 2 的普通边上 a 作为
  存活事实通过（赋值语句**所在**节点对应的是语句执行**之前**），所以
  节点 2 看到的 a 是未初始化的 TOP；
- 节点 2→3 时，a 被 kill（旧值不存活），生成边 const 11 落在节点
  3——节点 3 没有别的 a 贡献，a=11；
- 此后 a 在全部后继点（输出、return、出口）保持 11：每次都是存活
  边 id∘来路把 11 原样带走，再没有别的赋值 kill 它。

b 的生涯是对照面：节点 1、2 处 b=TOP（入口存活）；节点 3 给 b 赋
值，但右端含 input、classify 给 const TOP，于是 kill 旧值、生成
TOP——节点 3 起 b 显式 TOP，语义从"未初始化"变成了"已知其值由
input 决定、非编译期常量"。两者打印相同，含义的迁移只有对照语句
位置才看得出。这也兑现了 26.3.2 的边界声明：a*2 这步计算表达不
出，b=22 算不到。

### 43.8.2 idc.tip：常量穿过三次身份调用

pid 的输出先看：节点 1（入口）x=7、r=TOP；节点 2（r=x 之前）
x=7、r 仍是未初始化的 TOP；节点 3（return）r=7；节点 4 两者皆 7。
x=7 是三个调用点传入值的合并结果——三处实参是 7、a、7，而 a 在
main 中最终也是 7，7⊔7⊔7=7，**合并不降级**。这正是上下文不敏感在
"所有调用方意见一致"时不付精度代价的样子：共享一份函数体，结论
照样精确。

main 的"分阶段到达"逐节点展开：

- 节点 1：三者皆入口 TOP；
- 节点 2（第一次调用语句处）：三者 TOP——返回边落在调用点的后继，
  语句所在点的 a 是存活的旧 TOP；
- 节点 3：a=7（第一次返回边到达），b、c 仍旧；这一行的调用 b=pid(a)
  能把 a=7 传进去，因为实参边 classify(a)=（a，id）与该点携带 a 的
  入边匹配；
- 节点 4：b=7（第二次返回），a 保持 7；c 还在等；
- 节点 5 起：c=7，三个 7 一直保持到出口。

整条链演示的是 26.5.5 的三层复合在工作：实参的 const 7（第一次调
用）经 cf 进 x，x 经 r=x 的 id 到 r，r 经返回边的 id 回到 a；第二次
调用把已经在 a 里的 7 再走一遍；第三次同第一次。常量没有一次被"计
算"，全靠恒等传递存活——这恰是三种构造子能支撑的最远航程。

### 43.8.3 idm.tip：投毒与无辜者

idm 的 pid 输出全员 TOP：x 在入口即 7⊔2⊔3=TOP，r 经 r=x 拿到 TOP，
返回 TOP。关键的教学现象在 main：节点 2 的 `a = pid(7)` 传的明明
是确定的 7，节点 3 起 a 却是 TOP——共享函数体已被另外两处调用污
染，返回值对所有调用点一视同仁地给 TOP，**无辜的调用方一起付代
价**。b 在两支里分别被 pid(2)、pid(3) 赋值，汇合后本就是 2⊔3=TOP，
加上函数体也 TOP，双重保守。

但必须把第 41 章钉过的结论再钉一次：TOP 不 sound 吗？TOP 是"可能
为任何整数"，真实执行这一句 a 必为 7，7 当然属于"任何整数"——
结论真，只是不精。把同一程序交给第 41 章的 k=1，三个调用点各自的
进入串不同、函数体分出三份状态，a 就能拿回 7。本章实例刻意不区
分上下文（IDE 框架本身并不禁止，边函数里加上调用串维度即是上下
文敏感的 IDE），为的是让"上下文不敏感"这一独立维度的代价在最简
设置里暴露无遗。

### 43.8.4 两行统计怎么读

每个程序末尾固定打印 `worklist joins` 和 `IDE fact updates`：前者是
值在不动点中真正上升的次数，后者是边函数在非 BOT 输入上被求值的
次数。三个程序依次是 18/42、42/96、51/146——数值只随程序规模和
路径结构增长，不构成本章的正确性依据，留作读者改动程序时观察
"多一个分支、多几次上升"的标尺。刻意不打印耗时：教学框架的计时
受机器负载支配，传达不了原理性的信息。

### 43.8.5 与第 25 章的交叉核对

每个程序末尾的第二行固定写着与第 25 章常量框架的核对结论：
const.tip 上两章对 a=11、b=TOP 的判断一致。两个完全不同的引擎——
单调框架上传整个环境、IDE 上拆单事实边——在同一程序上碰头，这
是对两章实现各自的一次经验校验：任何一边的传递/复合出了错，差异
立刻在这一行上现形。

### 43.8.6 idc 与 idm 的输出 diff 对读

把两份输出并排，diff 只有六处实质差异：pid 的 x 从 7 变 TOP（三
源相遇）；pid 的 r 从 7 变 TOP；main 的 a 从 7 变 TOP（无辜者）；
main 的 b 两边都是 TOP 但**原因不同**——idc 里 b 的 TOP 来自
"待定后确定"？不，idc 里 b 最终是 7；正确对齐是：idc 的 a/b/c
全是 7，idm 里 a=TOP、b=TOP、c 不存在（idm 只有两个变量）。逐
行对齐时最容易看漏的是 pid 入口的 x：idc=7 与 idm=TOP 的这一行
是全部下游差异的单点源头——三个常量在 (pid 入口, x) 这一个键
上的 join 决定了两个程序的分野。改一行程序、看一格输出、追一
条因果链，这个工作流是教程反复示范的"输出考古学"：分析器的行
为差异永远能在某个具体键的 join 上找到出生地。

### 43.8.7 idm.tip 输出的逐点阅读

idm 的完整输出值得逐点走一遍，它是三份输出里信息密度最高的。pid
一侧：节点 1（入口）x=TOP——三个来源 7、2、3 已在枚举端各自成
边，值端 join 成 TOP；r 不在表中？不——r 在入口处尚未有边到达？
错，r 的种子自环在首次调用时补上、值端入口边界给 TOP，所以入口
行 x=TOP, r=TOP。节点 2（r=x 语句处，即执行前）：x=TOP、r=TOP，
语义是"r 即将被赋成 x 的当前值，而 x 已知非常量"。节点 3（re
turn r）：r=TOP——生成边 id 把 x 的 TOP 传了过来，没有任何"变
好"的机会。节点 4（出口）：两者皆 TOP。main 一侧：节点 1：a、b
皆 TOP（入口未初始化）。节点 2（a=pid(7) 语句处）：a=TOP——返
回边落在节点 3，本点看到的还是旧值；这一行的 TOP 含义是"未初始
化"，与后面节点 3 起 a=TOP 的"已知非常量"同形不同义，26.8.1 讲
过的语义迁移在这里跨过了过程边界。节点 3（分支点）：a=TOP——
此时返回边的 total=（函数体 TOP 的）id 作用于 (pid 入口,x)=TOP
得 TOP，a 从"未初始化 TOP"换成了"被 TOP 赋值的 TOP"。节点 4、5
（两支的 b=pid(2)/pid(3)）：b 各自 TOP。节点 6（汇合后 out
put）：a=TOP、b=TOP——b 的 TOP 是双重保守（两支常量不同、函数
体又 TOP），a 的是无辜受害。节点 7、8、9 维持。整份输出没有一
个数字，却是三份里最值得盯的：每一行 TOP 都能说出自己的来历。

## 43.9 正确性论证的思路

### 43.9.1 要证明的命题

本章需要的可靠性命题可以精确陈述为：

> 对程序中的任一（点 n，事实 d），若 IDE 给出的值是常量 c，则每一条
> 到达 (n,d) 的真实执行路径上 d 的取值都是 c；若给出 TOP，则不断言
> 取值（任何整数都与结论相容）。

换个方向说同样的事：分析给出的值必须是"所有到达该点的具体执行
在 d 上真实值"的安全上界——常量是上界意味着真实值集合是单元素
集 {c}；TOP 是天然的最大上界。BOT 不在命题内：它声称没有路径到
达，对应第 42 章意义下事实不可达，其可靠性由路径边枚举的完整性
继承。

### 43.9.2 归纳的三步结构

论证按路径长度归纳，骨架有三步，与第 42 章的路径边定理对接：

第一步（路径覆盖）：阶段一枚举出的路径边集合覆盖全部有效路径（第 42 章的配对结论：调用边与返回边经 incoming 正确配对，跨过程路径
一条不漏）。因此任一真实执行路径都是某条（或某一系列）被枚举边
的实例，归纳有据点。

第二步（函数忠实）：沿路径逐点归纳——基础情形，入口的 TOP 是真实
入口状态的上界（真实输入是某个具体整数，具体值 ≤ TOP）；归纳步，
假设源事实处的分析值是真实值的上界，本地边函数必须把上界映射成
上界：id 显然；const 生成的常量只有在右端不依赖任何变量（纯字面
量折叠）时才出现，折叠算术与真实运算一致（除零被排除）；复合逐
层保持。每一类 TOP 来源（input、表达不出的计算、不同值合并）都
是"取安全上界"，不引入具体而错的数。

第三步（合并不丢）：多条边在同端的 cJoin 是逐点最小上界，真实的
一次执行对应其中一条边的贡献，其值已被包含在 join 结果里——
cₐ⊔c_b=TOP 这种上升只会让结论更宽，不会把某个真实值排除在外。

三步合起来：路径全在、每步变换忠实、合并不漏，命题得证。注意这
是**思路**：形式化证明还需要把 TIP 的具体语义（赋值、output、参
数传递按值、返回）写成规则，再与每条流函数逐一核对；本章实现里
每处建边旁边的注释都标出了它对应的语义场景，这正是为这一步准备
的台账。

### 43.9.3 可靠性不意味着完备性

同样要明确不证明什么：**分析不保证认出所有常量**。b 的真实值在给
定具体输入时是确定的（a=11 时 b=22+输入），分析给 TOP，这不是失
误而是表达力与未知输入的双重边界。框架的价值在于它说"常量"时从
不错（于是优化可以放心做），而不在于把每个常量都榨出来。读 TOP
时正确的反应是"信息不足"，不是"程序有问题"。

### 43.9.4 上下文不敏感在证明中的位置

idm 现象在证明里只是第二步合并的一个特例：参数事实的来源边有多
条、值不同，cJoin 到 TOP——与同一函数内两支汇合的处理完全同构，
不产生任何额外规则。上下文敏感/不敏感因此不改变可靠性论证的结构，
只改变归纳第二步里"来源边集合"的大小。这个观察与第 41 章"精度阶
梯不是可靠性开关"的结论互相印证：同一个证明模板对各档位都成立。

### 43.9.5 BOT 在归纳中的位置

26.9.2 的三步没有正面处理 BOT，这里补上缺口。BOT 的命题是"没有
有效路径以（点, 事实）为终点"，它是阶段一的产物而不是阶段二的：
枚举完整（第一步）意味着凡有路径到达的事实必有路径边，值阶段给这
些（点, 事实）赋值，从未到达的保持 BOT。归纳里的对应物是反向否
定：若某事实在真实执行的某点出现，枚举必已覆盖——这正是第 42 章
完备性方向的陈述。因此 BOT 的可靠性是"继承"来的：本章不需要为它
新写归纳子句，只需要值阶段不碰没有边的键（实现里 `vals.find` 落
空即跳过，efApply 又对 BOT 严格，双保险）。理解这一点的价值在扩
展时显现：给框架加新构造子、新边类时，最容易破坏的就是"值只从边
上来"这条纪律——比如有人为了调试给某点手工注入常量，BOT 的语义
就静默失守，输出会多出凭空的常量而没有任何报警。

### 43.9.6 一个具体的反例检查

可靠性论证容易停在"三步都对"的抽象层，做一个反例检查能让它落地：
假设 classify 对 input 返回的不是 const TOP 而是 const 0（拍脑袋
给输入定了个值）。idm.tip 里没有 input，但 const.tip 的 b=a*2+
input 会算出 b=22——真实执行输入 5 时 b=27，分析断言 22，可靠性
当场破产。在归纳里的位置：第二步"函数忠实"被违反——input 的本
地函数把"未知"映射成了"具体而错的数"。三步论证的价值正在于此：
任何对流函数的改动都能定位到它违反哪一步，违反点就是测试用例
的构造点。同理可查 26.12.3 的 join：若 cJoin 写成"不同常量取较
小值"，违反的是第三步"合并不丢"——测试只需两个返回不同常量的
调用点。论证不是仪式，是调试地图。

### 43.9.7 从证明到测试：三步各自的检查用例

三步归纳不只是写给人看的论证，每一步都能落成一个可执行的检查
用例，组成可靠性的一组"探针"。路径覆盖的探针：对每条枚举出的
路径边，真实跑一遍对应程序输入，确认终点事实真的出现（第 42 章练习三做过它的逆向版）。函数忠实的探针：对每个 classify 给
出的 const c，在具体执行中采样右端表达式的值，全部等于 c（BOT
严格与 input-TOP 都会被这个探针盯住）。合并不丢的探针：对每个
join 上升的点，采样两个来源各自的真实值，确认都落在 join 结果
里。三个探针合成一个性质测试（property-based test），随机生成
程序与输入、断言上述包含关系——这正是工业分析器（如
CodeQL 的偶发 unsound 排查）在 CI 里跑的东西。教程没有实现它，
但第 53 章会把它的思想以"收集语义对照"的形式完整展开——那正
是 α(C[[p]]) ⊑ A 的机器检验。

## 43.10 工程注意点

### 43.10.1 驻留与键的顺序

构造边函数时，驻留池的键必须在子函数被 move 之前取出；键里放裸
指针，裸指针不因 shared_ptr 的移动而变。反过来若先 move 再取 f.get()
会得到空指针，所有函数会被错误地驻留成同一个。

### 43.10.2 一条边只谈一个事实

不要为了省事让一条路径边携带整个环境：单事实设计是"可分配、可
分解"的根源，调用配对、存活/生成判据都只比较一个事实。环境最后
拼，拼的规则只有三行。

### 43.10.3 复合方向写反的症状

若把公式写成 efCompose(e.fn, cls)（来路在外、本地在内），常量例子
上看起来常常仍"差不多对"（id 与 const 的某些组合交换后结果巧合相
同），但链式传递里值会系统性错位。检查方向的简单口径：**念出声
来——"来路先作用，本地后作用"，外层=后作用**。

### 43.10.4 扩展构造子时同时补律

若按 26.3.2 的指引加入"+c"一族，必须同时在 efCompose 里补三条规
范化：(+c)∘(+d)=+(c+d)、(+c)∘const k=const(k+c)、const v∘(+c)=
const v。漏第一条，循环里又出现无限外壳；漏后两条，常量与算术的
复合会以 Compose 残留，同样破坏终止。加一族构造子、补一族律，两
件事永远成对出现。

### 43.10.5 两阶段的调试顺序

框架行为异常时按阶段隔离排查：先固定只查枚举（边集合是否与第 42 章同构、incoming 是否登记完整），再固定边集合查值不动点（种子、
BOT 严格、join 比较）。让结构问题和值问题在不同的复现步骤里暴露，
比在一个工作表里同时追两者省心得多。

### 43.10.6 输出设计：只留原理性信息

固定输出常量环境、两行统计和一行交叉核对；不留调试转储，不打印
耗时。凡是受机器支配或只服务于开发过程的信息，都不进对读者承诺
的输出格式——expected 文件因此稳定，章节之间的核对因此可复现。

## 43.11 实现走读：ide.hpp 到两阶段主循环

### 43.11.1 值格的编码：三行 join 与两种"不知道"

`Const` 用三枚标签编码 L：Bot、Cst（带一个 int）、Top。join 的实
现只有六行，但每一行都在回答"两种不知道怎么合并"：Bot 与任何值
join 得对方（无信息是幺元）；Top 吞掉一切（最大元）；两个 Cst 相
等得自身、不等得 Top。第 25 章平坦常量格的 join 与此一字不差——
IDE 的 L 不是新格，而是把第 25 章的环境格抽出来单独戴上路径边。
接口层 `IdeResult::env` 用 `optional<int>` 区分 Cst（有值）与 Top
（nullopt），BOT 干脆不进 map：打印层因此能区分"知道非常量"与
"根本没到过"，26.8.1 里 b 的语义迁移就落在这个编码选择上。

### 43.11.2 边函数的驻留池：用指针换判等

`EdgeFnD` 是三构造子的树：Id、Cst、Compose(f∘g)。路径边的判等
（`PEdge::operator<` 的最后一项）用 `fn.get()`——裸指针比较。这
意味着两条边携带的函数必须**指向同一对象**才被视为相等，驻留池
`fnPool` 负责保证：任何构造都先查池（键含子函数指针），命中即返
回既有对象。代价是每次构造一次查表；回报是判等从树的深比较变成
一次指针比较，且规范化律（26.6.2）直接以"返回既有对象"的方式实
现——id∘g 返回 g 本身，律的执行与驻留合二为一。

池的键在子函数被 move 进新对象**之前**提取，这是 26.10.1 说过的
顺序纪律；键里存裸指针是安全的，因为驻留保证子函数对象与池共存
亡。这套设计与字符串驻留（interning）同族：任何需要"语义相等即
指针相等"的场合都可以照搬，第 45 章的分配点编号、第 44 章的位置
名，都是同一思想在别的域上的投影。

### 43.11.3 classify：表达式的三分类

classify 把任意表达式映成（源事实, 本地函数）：整棵能折叠的算术
给（零事实, const 折叠值）——constEval 递归求值，除零返回 nullopt
安全退化为 TOP；input 给（零事实, const TOP）——输入是编译期未知
的极致；单个变量给（变量事实, id）——值沿来路传递；其余一切（含
变量的运算）给（零事实, const TOP）。第四类是 26.3 的表达力边界
在代码里的落点：x+1 折不出常量、又不肯整个丢成 TOP 的话，需要
"c ↦ c+1"这样的算术函数——构造子语言里没有它，于是退化为 TOP。
四种情形覆盖了 classify 的全部输出，match 判断（源事实与所携事
实是否相符）统一写成"零对零、名对名"，调用边与返回边复用同一
套判据。

### 43.11.4 阶段一：与第 42 章逐行同构

把 solveIde 的枚举循环与第 42 章的 solveIfds 并排读，相同的行号
几乎可以对齐：isCall/exitPP/succ 的图准备段完全相同；种子的形状相
同（零事实自环加局部变量自环，函数 fn=efId()——第 42 章没有这个
字段，本章多出来的全部信息就在它身上）；三路分发相同。四处差异
都因函数而起：每条新边的 fn 由 efCompose(本地, e.fn) 造出；调用
边把 cf 一并记进 CallerKey；返回边的 total 是三层复合；调用-返回
边沿用存活公式。incoming 的键值都比第 42 章多一个函数分量——回
送时必须知道"当初是带着什么变换进来的"，才能把返回值正确地接回
调用方的来路上。

对读的一个具体锚点：第 42 章 25.8.5 里那条（f:1,x）→（f:5,r）
的路径边，在本章的实现里 fn 是什么？r=x 的生成边给 id∘来路，来
路（f 入口的 x 自环到 r=x 语句前）也是 id，规范化后 fn=id。返回
边 total=id∘(id∘cf)=cf=const 7（第一次调用）。于是 main 里 a 的
7 不是"算"出来的，是 const 7 这张函数牌从调用边一路递到返回边
——26.8.2 的叙述在这几行代码里找到了机械对应。

### 43.11.5 阶段二：值不动点的反复扫描

值阶段的结构朴素得出人意料：一个 `while(changed)` 包住对全部路
径边的一轮扫描。每条边查源点值（没有则跳过——BOT 严格的第一
道闸），efApply 求目标值，与既有值 cJoin，上升则记下并要求再来
一轮。没有工作表、没有优先级——因为图的"拓扑"已经被路径边预压
缩，扫描顺序不影响不动点（格有限、函数单调，Knaster–Tarski 保证
唯一最小不动点；反复全量扫描是最笨也最稳的到达方式）。第 24 章
讨论过的复杂度差别在这里重演：边数的量级下全量扫描与工作表的实
测差距可以忽略，而代码行数少一半。

两行统计就诞生在这段循环里：joins 只在值真正上升时递增，updates
在每次非 BOT 求值时递增。它们的用途在 26.8.4——不是正确性证据，
是改程序时的规模标尺。

### 43.11.6 打印层与 scopeOrder

printIde 按函数、按结点号输出环境，变量顺序由 scopeOrder 决定：
先形参后局部变量、去重、保持声明序。环境里没有的变量不打印（BOT
不可达），有值的打数字、nullopt 打 TOP——三种格点在输出上三种
长相，对账时一眼可辨。末尾的 summary 与 cross-check 行是固定文
本：前者来自统计计数，后者是 26.8.5 描述的与第 25 章的核对结论。
打印层不重算任何分析结果，只做视图——与第 42 章的分层约定一致。

### 43.11.7 图准备段与第 42 章的逐行对照

solveIde 开头四十行（decls/fcfgs/isCall/exitPP/succ）与 solveIfds
的开头**逐字符相同**——这不是巧合而是设计：两章共享超级图的识别
式构造，diff 从第一处 addEdge 才开始。对照着读 diff 的三处：一、
每条 addEdge 多出第五个参数 fn；二、CallerKey 多出 cf 字段；
三、返回边的 total 三层复合替代第 42 章的 returnFlow 直接调用。
把两份源码并排开两个窗口，先读相同的前四十行建立"这是同一台机
器"的信心，再沿三处 diff 逐个理解"函数分量"带来的变化——这是
本教程推荐的读法，也是检验第 42 章掌握程度的最快方式：若能预测
每一处 diff 的理由，说明制表机已经内化。

### 43.11.8 addEdge 的去重与工作表纪律

addEdge 的两行——insert 返回是否为新、新则入队——继承了第 42 章与第 24 章的同一纪律，但判等的负担全落在了 PEdge 的 operator<
上：端点、两个事实、最后函数指针。前四项是值比较，最后一项因驻
留而可靠。若驻留失效（比如绕过池直接 make_shared），两条语义相
同的边会被当成不同边各自入队——工作表多跑几轮还是能停（边集合
被值无关的键撑大，但图的键空间仍然有限？不——Compose 外壳可以
无限深，边数随之无限），实际症状是枚举不终止。把"去重键"与"规
范化"想成一台机器的两个啮合齿轮：规范化让语义相同的函数变成同
一对象，去重让携带同一对象的边只处理一次。任何一边的齿坏了，
另一边都会跟着空转。

### 43.11.9 头文件的三行接口

ide.hpp 的公开面只有三样：IdeResult（环境 + 两行统计）、solveIde
（吃 CFG 与程序）、printIde（吃结果吐文本）。没有暴露 EdgeFn、
没有暴露路径边、没有暴露阶段边界——两阶段是实现的私事。这个
接口收得比第 42 章还紧（那边至少暴露了 pathEdges 供打印），动机
是本章的结果天然是"每点每变量一个值"，环境形状已经足够；未来
若要做"按边查询函数牌"的调试需求，再开一个小接口即可。接口的
克制与输出的克制（26.10.6）是同一哲学：承诺越少，稳定越久。

## 43.12 手工 trace：idc.tip 的值流动

### 43.12.1 边先长好，值再流

阶段一结束时，idc.tip 的路径边集合已经定型：main 入口三个自环
（a、b、c 各一，fn=id）、零事实自环；三个调用点各自生出实参边
（fn 分别为 const 7、id、const 7）、零事实穿行边、以及 b、c 的
绕过边；pid 入口的 x 自环在第一次调用时补种，r 自环同时补上；
pid 体内 x 的存活边、r=x 的生成边（fn=id）、返回边两条（对应两
个调用点的 incoming 登记，fn 分别为三层复合后的 const 7 与
id∘…）；最后 a、b、c 的存活边铺满后半段。边的总数几十条，每条
带一张函数牌。

### 43.12.2 值的三轮扫描

第一轮：入口种子给 (main 入口, a/b/c/0) 赋 TOP。扫描到调用点 2
的实参边（起点事实 a？不——第一次调用的实参是常量 7，classify
给（零事实, const 7），匹配的是携带零事实的边）：源 (main 入口,
0)=TOP，efApply(const 7, TOP)=7，于是 (pid 入口, x) 的值从 BOT 升
到 7——第一次 join。x 的存活边把 7 送到 r=x 语句前，r=x 的生成
边 fn=id 把 (pid 入口, x)=7 映到 r：7。返回边 total=const 7（第
一调用配对）作用于 (pid 入口, 0)=TOP 得 7，落在 (main:3, a)——
a 从 TOP 升到 7，第二次 join。第二轮扫描把新值继续推：调用点 3
的实参是 a，classify(a)=（a, id），匹配携带 a 的边，源 (main:3,
a)=7，cf=id∘id=id，(pid 入口, x) 收到第二个贡献 7——join(7,7)=7，
值不升，joins 不增。第二次调用的返回边 total=id 作用于 (pid 入
口, x)=7 得 7，落在 (main:4, b)：第三次 join。第三轮同理给 c 送
7，之后全表再扫一遍无上升，不动点到达。三次上升对 42 次 joins
——多出的次数来自 pid 内部 x、r 的值在第一轮里的多边重复确认，
以及 const.tip……不对，42 是 idc 全程序（含 pid 四点）的总账；
无论如何，"上升次数远小于求值次数"的形态本身就是值阶段收敛健康
的信号。

### 43.12.3 同一机器上的 idm： poisoned 的机械过程

idm 的差异只在 classify 的输入：三个实参 7、2、3 都折叠成常量，
三条实参边 fn 分别 const 7、const 2、const 3，全部匹配零事实、全
部把值送进同一个 (pid 入口, x)。值阶段第一轮：x=join(BOT→7)、
join(7,2)=TOP、join(TOP,3)=TOP——两次上升，x 定格 TOP。r 经 id
拿到 TOP，两条返回边分别把 TOP 送给 a 与 b：a 的 TOP 不是来自自
己的路径（它只被 pid(7) 赋值），而是来自共享的 (pid 入口, x)。
机械上没有任何一步"出错"——每条边都忠实执行了自己的函数牌，悲
剧在 join 处：三个常量在同一个键上相遇。这就是 26.8.3"投毒"的
微观机制，也是第 41 章 k=1 能救回它的原因：k=1 把三个调用点的
进入分开存，join 不再相遇。

### 43.12.4 阶段一逐边清单

把 idc.tip 阶段一产出的路径边按出生顺序列全，作为 26.12.1 的补
充与读者自查的底稿。种子四条：main 入口的 (0,0)、(a,a)、(b,b)、
(c,c)，牌全 id。节点 1→2 的存活边四条（牌 id）。节点 2（调用点
b……第一次调用实为 a=pid(7)，设节点 2 即 a 的调用语句）弹出零事
实边：零事实穿行边进 pid 入口（牌 id，incoming 登记 (main:2,
0)←(main:1,0,id)）；实参 7 折叠为 const 7，匹配零事实，生成
(pid 入口, x) 边（牌 const 7，incoming 登记 (main:2, x)←(main:1,
0, const7)）；b、c 的绕过边（牌 id）；pid 首次入场，r 自环补种
（牌 id）。pid 内部：x 存活到 r=x 前（牌 id），r=x 生成 (r) 边
（牌 id∘id=id），两者过 return 到出口；出口配对零事实（对
(main:2,0)）与 x（对 (main:2,x)）：零事实配对的 returnFn=
classify(r)=（r,id），与出口事实 0 不匹配、无回送；x 配对出
口事实 r 时（来自 (f 入口,x)→…→(出口,r) 的延伸，牌 id）匹配，
total=id∘(id∘const7)=const 7，回送 (main:3, a) 边（牌 const 7）。
main 继续：节点 3 的调用 b=pid(a)：实参 classify(a)=（a,id），
匹配携带 a 的边——此时该边的牌仍是存活 id（a 的 7 在值阶段才
算出来，枚举不关心值）；cf=id∘id=id，incoming 登记 (main:3,x)
←(main:1,a,id)；零事实与 c 照常。pid 出口的新配对：出口事实 r
（起点 (pid 入口,x)）对 (main:3,x)：total=id∘(id∘id)=id，回送
(main:4, b) 牌 id。第三次调用同第一次。枚举至此收敛，边集合不
再增长——注意其中没有任何一条边"知道"a 是 7；值在阶段二才上
路。

### 43.12.5 值阶段的轮次记录

以 idc 为例把值阶段的收敛过程记成流水账。第零步：边界值写入
——main 入口的 0、a、b、c 皆 TOP；pid 入口的 0 与 r 因 entered
而同样 TOP（x 不在边界里——x 的值只能从调用边来，这是"参数不
预设"的语义立场）。第一轮扫描：按边集合的字典序，最早的几条是
main 入口自环（TOP→TOP，无上升）；a 的存活边（TOP→TOP）；到第
一次调用的实参边（源 (main:1,0)=TOP，const 7 作用得 7），目标
(pid:1,x) 从 BOT 升 7——joins=1；x 存活边把 7 送到 (pid:2,x)——
joins=2；r=x 生成边送 (pid:3,r)=7——joins=3；……零事实的各条
边 TOP→TOP 不升；第一次返回边 total=const 7 送 (main:3,a)=7
——joins 计入。第二轮：新值 7 在 (main:3,a) 上被第二次调用的实
参边（cf=id）读取，送 (pid:1,x) 得 7，join(7,7) 无上升；第二返
回边（total=id）送 (main:4,b)=7——上升。第三轮：第三次调用的
实参边（const 7）与返回边（const 7）给 (main:5,c)=7——上升。
第四轮全表扫描无上升，循环结束。总上升次数与输出的 42 对不上
账？42 计的是**全部程序**（含 pid 内部每个结点的 x、r 逐边确
认）——流水账只记了关键跳变；完整账目留给读者：把每个 (点,
事实) 的第一次赋值都数进来，就是 42。这个数账练习的价值不在
数字本身，而在体会"值沿边流动"与"边先已定型"的分层节奏。

### 43.12.6 值阶段的复杂度小账

值阶段的轮数与扫描成本值得记一笔小账。每轮全量扫描 O(|E|·apply)，
apply 在三构造子语言里 O(1)（Compose 链长为 1，见 26.5.7 的收
尾）；轮数上界是"值上升次数 + 1"，每次上升要么 k 变（Bot→Cst→
Top 单调两跳）、要么常量值变（Cst→Cst 只能发生在值被更小上界替
换？不——cJoin 只上升，Cst 与不同 Cst 一步到 Top，不存在 Cst
值的反复），所以每个（点, 事实）至多上升两次，总上升 O(|E|)，
轮数最坏 O(|E|) 而实践里个位数。整体 O(|E|²) 的最坏界在实践中
从未逼近——这正是 26.11.5 说"全量扫描与工作表实测差距可忽略"
的定量注脚。把它与第 24 章工作表的复杂度论证并排，读者应该能
认出同一个论证模板：界在"状态格高度 × 转移数"上，状态格这里
是三层的 L。

## 43.13 spa 9.5/9.6 与文献坐标

spa 原书把 IDE 放在第 17 章的两个小节（9.5 值敏感的推广、9.6 边
缘函数），叙述比 IFDS 简短得多——因为机制的重活（超级图、制表、
配对）已在 9.1–9.4 完成，IDE 只是给边加了函数分量。本教程的篇幅
分配遵循同一逻辑：第 42 章扛重活，本章把函数分量讲透。原始文献
是 Sagiv–Reps–Horwitz 1996 的 "The use of relevant variables in
process-integrated data-flow analysis"（框架的正式定义）与
Reps 1995 的后续——常量传播实例与"三构造子足够"的论证。值得
知道的一个事实：理论上 IDE 的边缘函数可以是任意有限格上的函数
族，只要复合封闭且可判等；三构造子（id、const、compose）是"闭
包恰好多项式可表示"的最小选择，工业实现（如 Heros/WALA 的
IDESolver）用的正是这一族的若干扩展，扩展时的纪律就是 26.10.4
的那句话：加一族构造子，补一族律。

与两条平行路线的关系也值得定位。其一与第 25 章常量传播的对比已
由 26.8.5 的交叉核对钉住：过程内、环境式、单调框架 vs 过程间、
单事实、路径函数——同一格 L，两种机器。其二与第 41 章 call-
string 的关系在 idm 上最清楚：上下文敏感救精度、IDE 救表达力，
两者正交；理论上"上下文敏感的 IDE"完全合法（边函数的定义域加
上调用串），实践里按需组合。

### 43.13.1 IFDS 是 IDE 的一个格子

两章的关系可以一句话钉死：IFDS 是 IDE 取布尔半格的特例。把 L 设
成 {⊥,⊤}（或 {0,1}），边函数只能从 {id, const⊤, const⊥} 里选
——const⊤ 就是"生成这条事实"、const⊥ 就是"杀掉"、id 就是"存
活"，三构造子语言恰好退化为 kill/gen 三件套，值阶段的"值"只剩
"在或不在"。于是第 42 章的每张流函数表都是本章 classify 的一个
布尔实例：normalFlow 的杀与生成对应 const⊥ 与 const⊤，配对与
制表机制完全共用。反过来，IDE 的一切增量都来自把 L 从两个点扩
成三个及以上——值有了"多少"的分别，函数语言才需要复合来表达
"来路 + 本地"的叠加。教科书常把这条写成"IFDS ⊂ IDE"，工程上
的实现也常共用一套求解器（Heros 的 IDESolver 跑布尔域就是
IFDS）——本教程分两章实现，是为了让布尔档的机制先站稳，值档的
增量再一目了然。

## 43.14 练习

练习一：把 idc.tip 的第三次调用改成 `c = pid(b);`，预测三个输出
点各是什么，然后运行核对。关键在第二次调用后 b=7 已经落地，第三
次实参边 classify(b)=（b,id）匹配的是携带 b 的边——链条从"a 传
给 b"续到"b 传给 c"，全程常量存活。

练习二：给 pid 的函数体加一句 `r = x + 1;`（替换原来的 r = x），
观察三个程序的输出变化。idc 里 a、b、c 应全部变 TOP——x+1 属于
classify 的第四类，生成边给 const TOP；这验证 26.3 的边界：没有
算术构造子，加一步都不行。若按 26.3.2 加 "+c" 构造子（26.10.4 的
三条律一起补），同一程序应能给出 a=8——把它作为第二个练习的实
现部分。

练习三：构造一个程序，使 IDE 报出常量、而第 25 章的过程内常量
分析报 TOP。提示：常量必须**穿过一次调用**才能确定——比如被调
函数返回固定值加实参拷贝的组合。这个程序同时是"两引擎交叉核对"
会报差异的样例，想想核对脚本该怎么改（差异不一定是错，先判断哪
边更精确）。

练习四：在值阶段的循环里把 `if (in.k == Const::Bot) continue;` 删
掉，运行 idm.tip。输出会多出什么？用 26.5.6 的 BOT 严格性解释：
哪些凭空的值是从"没有路径到达的事实"上冒出来的。

练习五：把 efCompose 的第四条律（外层 const 直接吞掉内层）注释
掉，构造一个循环里赋常量的程序（while 里 x = 3;）。预测制表是否
终止、为什么。再把第二条律（f∘id=f）注释掉，观察 join 计数与更
新计数的膨胀方式。

练习六：本章的 L 是常量格。把 L 换成第 21 章的五点符号格（edge
函数仍是三构造子，只是 Cst 变成格点、join 变成符号格的 join、
efApply 对格点作用），哪些程序事实现在能精确传播？构造一个
`y = pid(-5)` 的样例，说明符号 − 穿过身份调用的旅程与常量 7 的
旅程逐边同构——框架与域正交的最后一次亲手验证。

### 43.14.1 练习再补两题

练习七：修改 solveIde，让 incoming 的 CallerKey 不记录 cf（退回
第 42 章的形状），返回边的 total 改为 efCompose(retFn, e.fn)。在
idc.tip 上运行，解释 b 为什么变 TOP：第二次调用的实参 a 的值，
失去了"从调用边进来时的变换"这一信息，返回值接不上来路。这个
练习把 26.5.4 的"反向复合"从文字变成故障现场。

练习八：为 L 与函数语言同时扩容——加"非负"格点 N（L 变四层
⊥/c/N/⊤，join：c⊔N=N 当 c>0、c=0 时仍 c；两个不同正常量 join
为 N），classify 对 x*y（两操作数均非 TOP）给（零事实, const
N）。写出需要的全部规范化律（提示：N 与 const 的复合有四种组

### 43.14.2 练习九与练习十

练习九：把 printIde 的 scopeOrder 改成字典序，运行三个程序，看
expected 的 diff——输出契约的稳定性立刻可见：变量顺序是输出格

练习十：综合题。构造程序 p，包含：一个返回常量的函数 f、一个
身份函数 g、一个读 input 的函数 h、以及 main 里 a=f(); b=g(a);
c=h(); d=g(b)。预测 IDE 对 a、b、c、d 的输出并运行核对；然后把
d=g(b) 改成 d=g(c)，再预测。全部命中后，用一句话向同事解释
"IDE 的常量在哪一步丢、为什么丢"——这句话就是本章的毕业证。

## 43.15 小结

本章给第 42 章的制表机装上了值。事实仍然单点、路径边仍然制表、
调用返回仍然配对——全部结构原封；新东西只有一样：每条边携带一
张三构造子函数牌，值沿牌流动、在汇合处 join、在复合处消解。常
量传播这个第 25 章的老朋友因此跨过了过程边界：idc.tip 里 7 走了
四道门没掉一滴精度，idm.tip 里三个常量在共享形参上相遇跌成
TOP——两份输出合起来把"上下文不敏感的代价"钉成了可复现的实验
事实。终止性由四条规范化律守门，可靠性由路径覆盖、函数忠实、合
并不丢三步归纳背书，与第 25 章的对照和第 41 章的正交性各就各位。

回头看，第 25 与 26 两章其实是一台机器的两个档位：布尔档与值档。
换档的代价是函数语言的表达力边界（x=y+1 说不出），换档的收益是
"值"终于成为一等事实。下一章暂时离开过程间世界，回到控制流本身
——闭包让调用的目标在运行时才决定，超级图连"调谁"都画不出来
了；0-CFA 将先回答"这里可能调谁"，为后续一切过程间分析铺路。

### 43.18 结语：布尔与值的两半世界

第 25、26 两章合起来是一部完整的"过程间精确分析"机器：布尔半
边回答"可达吗"，值半边回答"到达时带什么"。两半共享超级图、制
表、配对、incoming——结构上一台机器；分化只发生在流函数的返回
类型上，一个是事实集合、一个是格上的函数。这个分化小到惊人，
却划出了两类问题的边界：可分配的布尔问题获得完全精确，值问题
在三构造子语言内获得"能说出的都精确、说不出的安全封顶"。教程
的后面两章将离开这架机器：闭包先破坏"调谁"的确定性（第 44 章），指针再破坏"哪里存哪里"的确定性（第 45 章）；但两章带走
的方法论——先定结构再流数据、判等靠驻留、终止靠规范化、可靠
靠三步归纳——会在每一次新的不确定性面前原样归队。读完本章，
读者手里的不再是一个分析器，而是一套造分析器的语法。

### 43.15.3 给后续章节的两句嘱托

第一句：第 44 章的 0-CFA 看起来与本章毫无血缘——没有路径边、
没有边函数、连超级图都不建——但它会重新发明"约束集合单调增长
到不动点"的骨架，并把"事实"从变量名换成位置上的闭包集合；读到
它的立方工作表时，回想本章值阶段的小账，会认出同一本复杂度账
簿换了科目。第二句：第 45 章的指针分析与本章共享一个哲学——
"宁可保守、绝不撒谎"：Andersen 的包含约束与本章的 cJoin 一样，
用超集换可靠性；而 Steensgaard 与本章的 TOP 一样，用更粗的超集
换更快的收敛。分析器的家族史，就是保守度的定价史。



两句嘱托背后是同一条学习方法：每遇新框架，先找它与旧框架共享
的骨架（不动点、单调、保守），再找它替换的部件（域、方向、敏
感维）——骨架少而部件多，认骨架比背部件省力十倍。本教程七篇
三十章，骨架总共只有三条：格上不动点、路径制表、约束闭包；部
件换了三十轮。毕业的标志不是背下三十个分析器，而是看到第三十
一个时，能在五分钟内说出它挂在哪条骨架上。

### 43.17.1 文法 TIP.g4

本章文法与第 42 章完全相同：调用的 callee 可以是任意表达式（本章
程序只用具名直接调用），指针与记录产生式在位但本章不触及。

```cpp
// file: TIP.g4
grammar TIP;

program    : function+ EOF ;
singleExpr : expr EOF ;
function   : IDENT LPAREN params? RPAREN LBRACE varDecls? stmt* RETURN expr SEMI RBRACE ;
params     : IDENT (COMMA IDENT)* ;
varDecls   : VAR IDENT (COMMA IDENT)* SEMI ;

stmt       : lvalue ASSIGN expr SEMI                # assignStmt
           | OUTPUT expr SEMI                      # outputStmt
           | IF LPAREN expr RPAREN stmt (ELSE stmt)? # ifStmt
           | WHILE LPAREN expr RPAREN stmt         # whileStmt

           ;

           ;

           | MINUS expr                            # negExpr
           | expr (STAR|DIV) expr                   # mulExpr
           | expr (PLUS|MINUS) expr                # addExpr
           | expr (GT|EQ) expr                     # cmpExpr
           | INT                                   # intExpr
           | IDENT                                 # varExpr
           | INPUT                                 # inputExpr
           | NULL                                  # nullExpr
           | LPAREN expr RPAREN                    # parenExpr
           | LBRACE field (COMMA field)* RBRACE    # recExpr
           ;
field      : IDENT COLON expr ;
args       : expr (COMMA expr)* ;

WS         : [ \t\r\n]+ -> skip ;
BLOCK_CMT  : '/*' .*? '*/' -> skip ;
```

```cpp
// 第 43 章配套程序：IDE 框架跑过程间常量传播。
//   --check FILE : 路径边枚举 + 值格不动点，逐点打印常量环境与统计；
//                  常量结论与第 25 章单调框架交叉一致，
//                  并展示身份函数如何跨调用保住常量

#include <iostream>
#include <memory>
#include <string>

#include "TIPLexer.h"
#include "TIPParser.h"
#include "antlr4-runtime.h"

#include "ast_build.hpp"
#include "cfg.hpp"
#include "ide.hpp"
#include "symtab.hpp"

class CollectErrorListener : public antlr4::BaseErrorListener {
public:
    std::vector<std::string> messages;

    void syntaxError(antlr4::Recognizer *, antlr4::Token *, size_t line,
                     size_t column, const std::string &msg,
                     std::exception_ptr) override {
        messages.push_back("syntax error line " + std::to_string(line) + ":" +
                           std::to_string(column) + " " + msg);
    }
};

namespace {

struct Parsed {
    std::unique_ptr<tip::ProgramA> ast;
    tip::Bindings bindings;
};

Parsed parseFile(const std::string &path) {
    std::ifstream src(path);
    if (!src) {
        std::cerr << "cannot open " << path << '\n';
        std::exit(1);
    }
    antlr4::ANTLRInputStream input(src);
    TIPLexer lexer(&input);
    antlr4::CommonTokenStream tokens(&lexer);
    TIPParser parser(&tokens);

    CollectErrorListener errors;
    lexer.removeErrorListeners();
    parser.removeErrorListeners();
    lexer.addErrorListener(&errors);
    parser.addErrorListener(&errors);

    TIPParser::ProgramContext *tree = parser.program();
    if (!errors.messages.empty()) {
        for (const std::string &m : errors.messages) std::cout << m << '\n';
        std::exit(2);
    }

    Parsed result;
    result.ast = tip::buildAst(tree);
    result.bindings = tip::resolveNames(*result.ast);
    if (!result.bindings.errors.empty()) {
        for (const tip::Diag &d : result.bindings.errors)
            std::cout << d.text << '\n';
        std::exit(3);
    }
    return result;
}

}  // namespace

int main(int argc, char **argv) {
    if (argc != 3 || std::string(argv[1]) != "--check") {
        std::cerr << "usage: tipa --check FILE\n";
        return 1;

    Parsed p = parseFile(argv[2]);
    tip::Cfg cfg = tip::buildCfg(*p.ast);
    tip::IdeResult r = tip::solveIde(cfg, *p.ast);
    std::cout << tip::printIde(cfg, *p.ast, r);
    return 0;
}
```

### 43.17.4 AST 定义 ast.hpp

冻结的 AST：IntLit/VarRef/Binop/CallE 等节点类型。本章新增讨论只
用其中的 IntLit、VarRef、InputE、Binop、CallE 五类；Deref/AllocE 等
节点在第 45 章才被消费。

```cpp
// file: src/ast.hpp
// AST 定义：AST 是去掉了括号、分号等语法噪音的程序结构。
// 接口自本章起冻结，后续所有分析（名字、CFG、类型、格……）都在此之上工作。
#pragma once

#include <memory>
#include <string>
#include <utility>
#include <vector>

namespace tip {

enum class BOp { Add, Sub, Mul, Div, Gt, Eq };

struct Expr {
    virtual ~Expr() = default;
};
struct IntLit : Expr {
    int v;
    explicit IntLit(int value) : v(value) {}
};
struct VarRef : Expr {
    std::string name;
    explicit VarRef(std::string n) : name(std::move(n)) {}
};
struct InputE : Expr {};
struct Binop : Expr {
    BOp op;
    std::unique_ptr<Expr> l, r;
    Binop(BOp o, std::unique_ptr<Expr> lhs, std::unique_ptr<Expr> rhs)
        : op(o), l(std::move(lhs)), r(std::move(rhs)) {}
};
struct CallE : Expr {
    std::unique_ptr<Expr> callee;
    std::vector<std::unique_ptr<Expr>> args;
    CallE(std::unique_ptr<Expr> fn, std::vector<std::unique_ptr<Expr>> as)
        : callee(std::move(fn)), args(std::move(as)) {}
};
struct Deref : Expr {
    std::unique_ptr<Expr> e;
    explicit Deref(std::unique_ptr<Expr> p) : e(std::move(p)) {}
};
struct AddrOf : Expr {                       // spa: & Id
    std::string name;
    explicit AddrOf(std::string n) : name(std::move(n)) {}
};
struct AllocE : Expr {
    std::unique_ptr<Expr> e;
    explicit AllocE(std::unique_ptr<Expr> init) : e(std::move(init)) {}
};
struct NullE : Expr {};
struct RecLit : Expr {
    std::vector<std::pair<std::string, std::unique_ptr<Expr>>> fields;
    explicit RecLit(std::vector<std::pair<std::string, std::unique_ptr<Expr>>> fs)
        : fields(std::move(fs)) {}
};
struct FieldA : Expr {
    std::unique_ptr<Expr> e;
    std::string field;
    FieldA(std::unique_ptr<Expr> record, std::string f)
        : e(std::move(record)), field(std::move(f)) {}
};

struct Stmt {
    virtual ~Stmt() = default;
};
// target 只会是 VarRef / FieldA / Deref，文法 lvalue 已限定。
struct AssignS : Stmt {
    std::unique_ptr<Expr> target, value;
    AssignS(std::unique_ptr<Expr> t, std::unique_ptr<Expr> v)
        : target(std::move(t)), value(std::move(v)) {}
};
struct OutputS : Stmt {
    std::unique_ptr<Expr> e;
    explicit OutputS(std::unique_ptr<Expr> x) : e(std::move(x)) {}
};
struct IfS : Stmt {
    std::unique_ptr<Expr> cond;
    std::unique_ptr<Stmt> then, els;
    IfS(std::unique_ptr<Expr> c, std::unique_ptr<Stmt> t, std::unique_ptr<Stmt> e)
        : cond(std::move(c)), then(std::move(t)), els(std::move(e)) {}
};
struct WhileS : Stmt {
    std::unique_ptr<Expr> cond;
    std::unique_ptr<Stmt> body;
    WhileS(std::unique_ptr<Expr> c, std::unique_ptr<Stmt> b)
        : cond(std::move(c)), body(std::move(b)) {}
};
struct BlockS : Stmt {
    std::vector<std::unique_ptr<Stmt>> ss;
    explicit BlockS(std::vector<std::unique_ptr<Stmt>> v) : ss(std::move(v)) {}
};
struct ReturnS : Stmt {
    std::unique_ptr<Expr> e;
    explicit ReturnS(std::unique_ptr<Expr> x) : e(std::move(x)) {}
};

struct FunDecl {
    std::string name;
    std::vector<std::string> params;
    std::vector<std::string> vars;
    std::unique_ptr<Stmt> body;
    std::unique_ptr<ReturnS> ret;
};

struct ProgramA {
    std::vector<std::unique_ptr<FunDecl>> funs;
};

}  // namespace tip
```

### 43.17.5 AST 构建 ast_build.hpp 与 ast_build.cpp

从 parse tree 手工递归下降构建 AST（std::any 持不住 unique_ptr，所以
不用 visitor 机制）。constEval 折叠的优先级正确性依赖这里构建出的

```cpp
// file: src/ast_build.hpp
// AST 构建器：在 ANTLR 生成的 parse-tree 上下文节点上手工递归下降。
// （本工具链 C++ runtime 的 visitor 以 std::any 传值，而 std::any 不能持有
// unique_ptr，因此不使用 visitor 机制：parse-tree 的上下文类本身信息完整，
// 用 dynamic_cast 区分 #标签备选，自己做一次结构化遍历同样直接。）
#pragma once

#include <memory>
#include <string>
#include <vector>

#include "TIPParser.h"
#include "antlr4-runtime.h"
#include "ast.hpp"

namespace tip {

struct AstBuilder {
    std::unique_ptr<ProgramA> build(TIPParser::ProgramContext *tree);

private:
    std::unique_ptr<FunDecl> buildFun(TIPParser::FunctionContext *ctx);
    std::unique_ptr<Expr> buildExpr(TIPParser::ExprContext *ctx);
    std::unique_ptr<Stmt> buildStmt(TIPParser::StmtContext *ctx);
    // lvalue 翻译成赋值目标表达式：VarRef / Deref，可再包一层 FieldA。
    std::unique_ptr<Expr> buildLvalue(TIPParser::LvalueContext *lv);
};

// 便捷入口：parse tree 的 program 节点 -> 完整 AST。
std::unique_ptr<ProgramA> buildAst(TIPParser::ProgramContext *tree);
```

```cpp
// file: src/ast_build.cpp
#include "ast_build.hpp"

#include <utility>
#include <vector>

namespace tip {

std::unique_ptr<ProgramA> AstBuilder::build(TIPParser::ProgramContext *tree) {
    auto program = std::make_unique<ProgramA>();
    for (auto *fc : tree->function()) program->funs.push_back(buildFun(fc));
    return program;
}

std::unique_ptr<FunDecl> AstBuilder::buildFun(TIPParser::FunctionContext *ctx) {
    auto f = std::make_unique<FunDecl>();
    f->name = ctx->IDENT()->getText();
    if (ctx->params()) {
        for (auto *p : ctx->params()->IDENT()) f->params.push_back(p->getText());
    }
    if (ctx->varDecls()) {
        for (auto *v : ctx->varDecls()->IDENT()) f->vars.push_back(v->getText());
    }

    std::vector<std::unique_ptr<Stmt>> body;
    for (auto *sc : ctx->stmt()) body.push_back(buildStmt(sc));
    f->body = std::make_unique<BlockS>(std::move(body));

    f->ret = std::make_unique<ReturnS>(buildExpr(ctx->expr()));
    return f;
}

std::unique_ptr<Expr> AstBuilder::buildLvalue(TIPParser::LvalueContext *lv) {
    std::unique_ptr<Expr> base;
    std::string field;
    if (auto *d = dynamic_cast<TIPParser::DirectLvalueContext *>(lv)) {
        base = std::make_unique<VarRef>(d->IDENT(0)->getText());
        if (d->IDENT().size() == 2) field = d->IDENT(1)->getText();
    } else {
        auto *p = dynamic_cast<TIPParser::PointerLvalueContext *>(lv);
        base = std::make_unique<Deref>(buildExpr(p->expr()));
        if (p->IDENT()) field = p->IDENT()->getText();
    }
    if (!field.empty())
        return std::make_unique<FieldA>(std::move(base), std::move(field));
    return base;
}

std::unique_ptr<Expr> AstBuilder::buildExpr(TIPParser::ExprContext *ctx) {
    if (auto *c = dynamic_cast<TIPParser::IntExprContext *>(ctx))
        return std::make_unique<IntLit>(std::stoi(c->INT()->getText()));
    if (auto *c = dynamic_cast<TIPParser::VarExprContext *>(ctx))
        return std::make_unique<VarRef>(c->IDENT()->getText());
    if (dynamic_cast<TIPParser::InputExprContext *>(ctx))
        return std::make_unique<InputE>();
    if (dynamic_cast<TIPParser::NullExprContext *>(ctx))
        return std::make_unique<NullE>();
    if (auto *c = dynamic_cast<TIPParser::ParenExprContext *>(ctx))
        return buildExpr(c->expr());

    if (auto *c = dynamic_cast<TIPParser::AddExprContext *>(ctx)) {
        const BOp op = c->PLUS() ? BOp::Add : BOp::Sub;
        return std::make_unique<Binop>(op, buildExpr(c->expr(0)), buildExpr(c->expr(1)));
    }
    if (auto *c = dynamic_cast<TIPParser::MulExprContext *>(ctx)) {
        const BOp op = c->STAR() ? BOp::Mul : BOp::Div;
        return std::make_unique<Binop>(op, buildExpr(c->expr(0)), buildExpr(c->expr(1)));
    }
    if (auto *c = dynamic_cast<TIPParser::CmpExprContext *>(ctx)) {
        const BOp op = c->GT() ? BOp::Gt : BOp::Eq;
        return std::make_unique<Binop>(op, buildExpr(c->expr(0)), buildExpr(c->expr(1)));
    }
    if (auto *c = dynamic_cast<TIPParser::NegExprContext *>(ctx)) {
        // TIP 没有负数字面量 token，-E 即 0-E。
        return std::make_unique<Binop>(BOp::Sub, std::make_unique<IntLit>(0),
                                       buildExpr(c->expr()));
    }
    if (auto *c = dynamic_cast<TIPParser::CallExprContext *>(ctx)) {
        std::vector<std::unique_ptr<Expr>> args;
        if (c->args())
            for (auto *a : c->args()->expr()) args.push_back(buildExpr(a));
        return std::make_unique<CallE>(buildExpr(c->expr()), std::move(args));
    }
    if (auto *c = dynamic_cast<TIPParser::FieldExprContext *>(ctx))
        return std::make_unique<FieldA>(buildExpr(c->expr()), c->IDENT()->getText());
    if (auto *c = dynamic_cast<TIPParser::DerefExprContext *>(ctx))
        return std::make_unique<Deref>(buildExpr(c->expr()));
    if (auto *c = dynamic_cast<TIPParser::AddrExprContext *>(ctx))
        return std::make_unique<AddrOf>(c->IDENT()->getText());
    if (auto *c = dynamic_cast<TIPParser::AllocExprContext *>(ctx))
        return std::make_unique<AllocE>(buildExpr(c->expr()));
    if (auto *c = dynamic_cast<TIPParser::RecExprContext *>(ctx)) {
        std::vector<std::pair<std::string, std::unique_ptr<Expr>>> fields;
        for (auto *fc : c->field())
            fields.emplace_back(fc->IDENT()->getText(), buildExpr(fc->expr()));
        return std::make_unique<RecLit>(std::move(fields));
    }
    return nullptr;  // 解析成功时不会到达
}

std::unique_ptr<Stmt> AstBuilder::buildStmt(TIPParser::StmtContext *ctx) {
    if (auto *c = dynamic_cast<TIPParser::AssignStmtContext *>(ctx))
        return std::make_unique<AssignS>(buildLvalue(c->lvalue()), buildExpr(c->expr()));
    if (auto *c = dynamic_cast<TIPParser::OutputStmtContext *>(ctx))
        return std::make_unique<OutputS>(buildExpr(c->expr()));
    if (auto *c = dynamic_cast<TIPParser::IfStmtContext *>(ctx)) {
        std::unique_ptr<Stmt> els;
        if (c->stmt().size() == 2) els = buildStmt(c->stmt(1));
        return std::make_unique<IfS>(buildExpr(c->expr()), buildStmt(c->stmt(0)),
                                     std::move(els));
    }
    if (auto *c = dynamic_cast<TIPParser::WhileStmtContext *>(ctx))
        return std::make_unique<WhileS>(buildExpr(c->expr()), buildStmt(c->stmt()));
    if (auto *c = dynamic_cast<TIPParser::BlockStmtContext *>(ctx)) {
        std::vector<std::unique_ptr<Stmt>> ss;
        for (auto *sc : c->stmt()) ss.push_back(buildStmt(sc));
        return std::make_unique<BlockS>(std::move(ss));
    }
    return nullptr;  // 解析成功时不会到达
}

std::unique_ptr<ProgramA> buildAst(TIPParser::ProgramContext *tree) {
    return AstBuilder{}.build(tree);
}

}  // namespace tip
```

### 43.17.6 符号表 symtab.hpp 与 symtab.cpp

名字解析两遍走：先注册函数名，再逐函数开作用域。IDE 阶段一区分
"函数名作为值"与"参数/局部变量引用"靠的就是 uses 表里 Symbol 的
kind。

```cpp
// file: src/symtab.hpp
// 符号表与名字解析：把 AST 上的每个 VarRef 绑定到它的声明
// （函数 / 参数 / 局部变量），同时产出未声明、重复声明诊断。
#pragma once

#include <map>
#include <string>
#include <vector>

#include "ast.hpp"

namespace tip {

struct Symbol {
    enum Kind { Fun, Param, Local } kind;
    std::string name;
    const FunDecl *fun;          // Fun: 指向自身声明; Param/Local: 指向所属函数
};

struct Scope {
    Scope *parent;
    std::map<std::string, Symbol> table;

    explicit Scope(Scope *p = nullptr) : parent(p) {}
    const Symbol *lookup(const std::string &name) const;
};

struct Diag {
    std::string text;
};

struct Bindings {
    Scope global;                                  // 函数名所在的全局作用域
    // 各函数作用域由 Bindings 持有所有权：uses 中的 Symbol* 才不会悬垂。
    std::vector<std::unique_ptr<Scope>> scopes;
    std::vector<Diag> errors;
    std::map<const VarRef *, const Symbol *> uses;  // 解析成功的使用点
};

// 两遍解析：先注册全部函数名（支持前向调用），再逐函数解析函数体。
Bindings resolveNames(ProgramA &program);

}  // namespace tip
```

```cpp
// file: src/symtab.cpp
#include "symtab.hpp"

#include <utility>

namespace tip {

namespace {

// 解析器在遍历 AST 的同时完成绑定与诊断收集。
struct Resolver {
    Bindings bindings;
    Scope *current = nullptr;
    const FunDecl *owner = nullptr;

    void declare(const std::string &name, Symbol::Kind kind) {
        if (current->table.count(name)) {
            bindings.errors.push_back({"error: redeclared '" + name + "'"});
            return;  // 保留先声明者，后声明被忽略
        }
        current->table.emplace(name, Symbol{kind, name, owner});
    }

    void resolveExpr(const Expr *e) {
        if (const auto *x = dynamic_cast<const VarRef *>(e)) {
            const Symbol *s = current->lookup(x->name);
            if (!s) {
                bindings.errors.push_back({"error: undeclared '" + x->name + "'"});
            } else {
                bindings.uses[x] = s;
            }
            return;
        }
        if (const auto *x = dynamic_cast<const Binop *>(e)) {
            resolveExpr(x->l.get());
            resolveExpr(x->r.get());
            return;
        }
        if (const auto *x = dynamic_cast<const CallE *>(e)) {
            resolveExpr(x->callee.get());
            for (const auto &a : x->args) resolveExpr(a.get());
            return;
        }
        if (const auto *x = dynamic_cast<const Deref *>(e)) return resolveExpr(x->e.get());
        if (const auto *x = dynamic_cast<const AllocE *>(e)) return resolveExpr(x->e.get());
        if (const auto *x = dynamic_cast<const FieldA *>(e)) {
            resolveExpr(x->e.get());  // 字段名不是变量，无需解析
            return;
        }
        if (const auto *x = dynamic_cast<const RecLit *>(e)) {
            for (const auto &f : x->fields) resolveExpr(f.second.get());
            return;
        }
        // IntLit / InputE / AddrOf / NullE：无变量使用。
    }

    void resolveStmt(const Stmt *s) {
        if (const auto *x = dynamic_cast<const AssignS *>(s)) {
            resolveExpr(x->target.get());
            resolveExpr(x->value.get());
            return;
        }
        if (const auto *x = dynamic_cast<const OutputS *>(s)) return resolveExpr(x->e.get());
        if (const auto *x = dynamic_cast<const IfS *>(s)) {
            resolveExpr(x->cond.get());
            resolveStmt(x->then.get());
            if (x->els) resolveStmt(x->els.get());
            return;
        }
        if (const auto *x = dynamic_cast<const WhileS *>(s)) {
            resolveExpr(x->cond.get());
            resolveStmt(x->body.get());
            return;
        }
        if (const auto *x = dynamic_cast<const BlockS *>(s)) {
            for (const auto &st : x->ss) resolveStmt(st.get());
            return;
        }
        if (const auto *x = dynamic_cast<const ReturnS *>(s)) return resolveExpr(x->e.get());
    }
};

}  // namespace

const Symbol *Scope::lookup(const std::string &name) const {
    auto it = table.find(name);
    if (it != table.end()) return &it->second;
    return parent ? parent->lookup(name) : nullptr;
}

Bindings resolveNames(ProgramA &program) {
    Resolver resolver;
    resolver.bindings.global = Scope(nullptr);
    Scope *global = &resolver.bindings.global;

    // 第一遍：所有函数名进入全局作用域。
    for (const auto &f : program.funs) {
        if (global->table.count(f->name)) {
            resolver.bindings.errors.push_back({"error: redeclared '" + f->name + "'"});
            continue;
        }
        global->table.emplace(f->name, Symbol{Symbol::Fun, f->name, f.get()});
    }

    // 第二遍：每个函数开自己的作用域，父作用域是全局表；
    // 作用域所有权交给 Bindings，遍历结束后符号依然存活。
    for (const auto &f : program.funs) {
        auto functionScope = std::make_unique<Scope>(global);
        resolver.current = functionScope.get();
        resolver.owner = f.get();

        for (const std::string &p : f->params) resolver.declare(p, Symbol::Param);
        for (const std::string &v : f->vars) resolver.declare(v, Symbol::Local);

        resolver.resolveStmt(f->body.get());
        resolver.resolveStmt(f->ret.get());

        resolver.current = nullptr;
        resolver.bindings.scopes.push_back(std::move(functionScope));
    }
    return std::move(resolver.bindings);
}

}  // namespace tip
```

```cpp
// file: src/cfg.cpp
#include "cfg.hpp"

#include <map>
#include <set>
#include <sstream>
#include <vector>

#include "pretty.hpp"

namespace tip {
namespace {

// 两遍构造：第一遍按 AST 先序给所有程序点分配固定编号；第二遍连边。
// 先编号再连边，是为了让编号严格按源码顺序（连边时若先构造后继节点，
// 后继会抢在前面编号），从而输出与程序点编号都是确定的。
class CfgBuilder {
public:
    explicit CfgBuilder(const ProgramA &program) : program_(program) {}

    Cfg run() {
        Cfg cfg;
        for (const auto &fun : program_.funs) {
            FunCfg fc;
            cur_ = &fc;
            cur_->name = fun->name;
            nextId_ = 1;
            stmtId_.clear();

            const int entry = addNode(CfgNode::Kind::Entry);
            cur_->entry = entry;
            numberStmt(fun->body.get());
            const int retId = addNode(CfgNode::Kind::Return, fun->ret.get());
            const int exitId = addNode(CfgNode::Kind::Exit);
            cur_->exitNode = exitId;

            // 连边：语句构造返回它自己的入口点集合；空块没有节点，直接透传后继。
            std::vector<int> bodyEntries = wireStmt(fun->body.get(), {retId});
            if (bodyEntries.empty()) bodyEntries = {retId};
            link(entry, bodyEntries);
            link(retId, {exitId});

            // set 去重并排序：CFG 边不允许重复，输出顺序固定。
            std::set<std::pair<int, int>> uniq(cur_->edges.begin(), cur_->edges.end());
            cur_->edges.assign(uniq.begin(), uniq.end());
            cfg.funs.push_back(std::move(*cur_));
        }
        return cfg;
    }

private:
    const ProgramA &program_;
    FunCfg *cur_ = nullptr;
    int nextId_ = 1;
    std::map<const Stmt *, int> stmtId_;

    int addNode(CfgNode::Kind kind, const Stmt *stmt = nullptr) {
        const int id = nextId_++;
        cur_->nodes.emplace(id, CfgNode{id, kind, stmt});
        return id;
    }

    // ---- 第一遍：编号 ----
    void numberStmt(const Stmt *s) {
        if (const auto *b = dynamic_cast<const BlockS *>(s)) {
            for (const auto &x : b->ss) numberStmt(x.get());
            return;
        }
        if (const auto *x = dynamic_cast<const IfS *>(s)) {
            stmtId_[x] = addNode(CfgNode::Kind::Branch, x);
            numberStmt(x->then.get());
            numberStmt(x->els.get());
            return;
        }
        if (const auto *x = dynamic_cast<const WhileS *>(s)) {
            stmtId_[x] = addNode(CfgNode::Kind::Branch, x);
            numberStmt(x->body.get());
            return;
        }
        if (dynamic_cast<const AssignS *>(s)) {
            stmtId_[s] = addNode(CfgNode::Kind::Assign, s);
            return;
        }
        if (dynamic_cast<const OutputS *>(s)) {
            stmtId_[s] = addNode(CfgNode::Kind::Output, s);
        }
    }

    // ---- 第二遍：连边。返回进入该语句时首先到达的程序点集合 ----
    std::vector<int> wireStmt(const Stmt *s, const std::vector<int> &succ) {
        if (const auto *b = dynamic_cast<const BlockS *>(s)) {
            std::vector<int> cur = succ;
            for (auto it = b->ss.rbegin(); it != b->ss.rend(); ++it)
                cur = wireStmt(it->get(), cur);
            return cur;
        }
        if (const auto *x = dynamic_cast<const IfS *>(s)) {
            const int n = stmtId_[x];
            std::vector<int> targets = wireStmt(x->then.get(), succ);
            if (targets.empty()) targets = succ;
            if (x->els) {
                std::vector<int> e = wireStmt(x->els.get(), succ);
                if (e.empty()) e = succ;
                targets.insert(targets.end(), e.begin(), e.end());
            } else {
                targets.insert(targets.end(), succ.begin(), succ.end());
            }
            link(n, targets);
            return {n};
        }
        if (const auto *x = dynamic_cast<const WhileS *>(s)) {
            const int n = stmtId_[x];
            // 循环体执行完回到条件点；空体时条件点连一条自边（等于死循环）。
            std::vector<int> bodyEntries = wireStmt(x->body.get(), {n});
            if (bodyEntries.empty()) bodyEntries = {n};
            link(n, bodyEntries);
            link(n, succ);
            return {n};
        }
        const int n = stmtId_[s];
        link(n, succ);
        return {n};
    }

    void link(int from, const std::vector<int> &to) {
        for (int t : to) cur_->edges.emplace_back(from, t);
    }
};

const char *kindName(CfgNode::Kind kind) {
    switch (kind) {
        case CfgNode::Kind::Entry: return "entry";
        case CfgNode::Kind::Exit: return "exit";
        case CfgNode::Kind::Assign: return "assign";
        case CfgNode::Kind::Output: return "output";
        case CfgNode::Kind::Branch: return "branch";
        case CfgNode::Kind::Return: return "return";
    }
    return "?";
}

}  // namespace

Cfg buildCfg(const ProgramA &program) { return CfgBuilder(program).run(); }

std::string printCfg(const Cfg &cfg) {
    std::ostringstream out;
    for (const FunCfg &f : cfg.funs) {
        out << "== " << f.name << " ==\n";
        out << "nodes:\n";
        for (const auto &[id, node] : f.nodes) {
            out << "  " << id << ": " << kindName(node.kind);
            if (node.stmt) out << "  " << printStmtLine(*node.stmt);
            out << "\n";
        }
        out << "edges:\n";
        for (const auto &[a, b] : f.edges) out << "  " << a << " -> " << b << "\n";
    }
    return out.str();
}

}  // namespace tip
```

```cpp
// file: src/pretty.cpp
#include "pretty.hpp"

#include <string>

namespace tip {

namespace {

// 表达式打印为前缀式：运算符与符号的对照表。
std::string exprText(const Expr *e) {
    if (const auto *x = dynamic_cast<const IntLit *>(e)) return std::to_string(x->v);
    if (const auto *x = dynamic_cast<const VarRef *>(e)) return x->name;
    if (dynamic_cast<const InputE *>(e)) return "input";
    if (dynamic_cast<const NullE *>(e)) return "null";

    if (const auto *x = dynamic_cast<const Binop *>(e)) {
        const char *sym = "+";
        switch (x->op) {
            case BOp::Add: sym = "+"; break;
            case BOp::Sub: sym = "-"; break;
            case BOp::Mul: sym = "*"; break;
            case BOp::Div: sym = "/"; break;
            case BOp::Gt: sym = ">"; break;
            case BOp::Eq: sym = "=="; break;
        }
        return "(" + std::string(sym) + " " + exprText(x->l.get()) + " " +
               exprText(x->r.get()) + ")";
    }
    if (const auto *x = dynamic_cast<const CallE *>(e)) {
        std::string s = "(call " + exprText(x->callee.get());
        for (const auto &a : x->args) s += " " + exprText(a.get());
        return s + ")";
    }
    if (const auto *x = dynamic_cast<const Deref *>(e))
        return "(* " + exprText(x->e.get()) + ")";
    if (const auto *x = dynamic_cast<const AddrOf *>(e)) return "(& " + x->name + ")";
    if (const auto *x = dynamic_cast<const AllocE *>(e))
        return "(alloc " + exprText(x->e.get()) + ")";
    if (const auto *x = dynamic_cast<const FieldA *>(e))
        return "(. " + exprText(x->e.get()) + " " + x->field + ")";
    if (const auto *x = dynamic_cast<const RecLit *>(e)) {
        std::string s = "{";
        for (size_t i = 0; i < x->fields.size(); ++i) {
            if (i) s += ", ";
            s += x->fields[i].first + ": " + exprText(x->fields[i].second.get());
        }
        return s + "}";
    }
    return "<unknown expr>";
}

std::string indent(int level) { return std::string(static_cast<size_t>(level) * 2, ' '); }

// 语句打印带缩进，一条语句一行（块内多行）。
void stmtText(const Stmt *s, int level, std::string &out) {
    if (const auto *x = dynamic_cast<const AssignS *>(s)) {
        out += indent(level) + exprText(x->target.get()) + " = " +
               exprText(x->value.get()) + " ;\n";
        return;
    }
    if (const auto *x = dynamic_cast<const OutputS *>(s)) {
        out += indent(level) + "output " + exprText(x->e.get()) + " ;\n";
        return;
    }
    if (const auto *x = dynamic_cast<const ReturnS *>(s)) {
        out += indent(level) + "return " + exprText(x->e.get()) + " ;\n";
        return;
    }
    if (const auto *x = dynamic_cast<const IfS *>(s)) {
        out += indent(level) + "if (" + exprText(x->cond.get()) + ")\n";
        stmtText(x->then.get(), level + 1, out);
        if (x->els) {
            out += indent(level) + "else\n";
            stmtText(x->els.get(), level + 1, out);
        }
        return;
    }
    if (const auto *x = dynamic_cast<const WhileS *>(s)) {
        out += indent(level) + "while (" + exprText(x->cond.get()) + ")\n";
        stmtText(x->body.get(), level + 1, out);
        return;
    }
    if (const auto *x = dynamic_cast<const BlockS *>(s)) {
        out += indent(level) + "{\n";
        for (const auto &st : x->ss) stmtText(st.get(), level + 1, out);
        out += indent(level) + "}\n";
        return;
    }
    out += indent(level) + "<unknown stmt>\n";
}

}  // namespace

std::string printExpr(const Expr *e) { return exprText(e); }

std::string printProgram(const ProgramA &program) {
    std::string out;
    for (const auto &f : program.funs) {
        std::string paramList;
        for (size_t i = 0; i < f->params.size(); ++i) {
            if (i) paramList += ",";
            paramList += f->params[i];
        }
        out += f->name + "(" + paramList + ") {\n";
        if (!f->vars.empty()) {
            out += indent(1) + "var ";
            for (size_t i = 0; i < f->vars.size(); ++i) {
                if (i) out += ",";
                out += f->vars[i];
            }
            out += " ;\n";
        }
        // 函数体是 BlockS；打印其内部语句而不是再嵌一层花括号。
        const auto *body = dynamic_cast<const BlockS *>(f->body.get());
        for (const auto &st : body->ss) stmtText(st.get(), 1, out);
        stmtText(f->ret.get(), 1, out);
        out += "}\n";
    }
    return out;
}

// 单行形式：CFG 节点标签等"节点旁边写一句话"的场合使用。
std::string printStmtLine(const Stmt &stmt) {
    std::string out;
    stmtText(&stmt, 0, out);
    if (!out.empty() && out.back() == '\n') out.pop_back();
    return out;
}

}  // namespace tip
```

```cpp
// 第 43 章配套：IDE 框架（Sagiv–Reps–Horwitz）求解过程间常量传播。
// IFDS 只能回答"某事实是否可达"；IDE 让可达性携带值：每条路径边附带
```

```cpp
// file: src/ide.cpp
#include "ide.hpp"

#include <algorithm>
#include <deque>
#include <set>
#include <sstream>
#include <tuple>

#include "pretty.hpp"

namespace tip {
namespace {

// ---- 三层常量格 L：BOT / 常量 c / TOP ----
struct Const {
    enum K { Bot, Cst, Top } k = Bot;
    int v = 0;
};
Const cBot() { return Const{Const::Bot, 0}; }
Const cCst(int x) { return Const{Const::Cst, x}; }
Const cTop() { return Const{Const::Top, 0}; }
Const cJoin(const Const &a, const Const &b) {
    if (a.k == Const::Bot) return b;
    if (b.k == Const::Bot) return a;
    if (a.k == Const::Top || b.k == Const::Top) return cTop();
    return a.v == b.v ? a : cTop();
}

// ---- 边函数：id / const v / compose，驻留后用指针参与判等 ----
struct EdgeFnD {
    enum K { Id, Cst, Compose } kind;
    Const value;                              // kind==Cst 时有效
    std::shared_ptr<EdgeFnD> f, g;            // f∘g
};
using EdgeFn = std::shared_ptr<EdgeFnD>;

std::map<std::tuple<int, int, int, const EdgeFnD *, const EdgeFnD *>, EdgeFn>
    fnPool;

EdgeFn efMake(EdgeFnD::K kind, Const value, EdgeFn f, EdgeFn g) {
    // 键在移动前提取（裸指针不随移动改变）。
    auto key = std::make_tuple(static_cast<int>(kind),
                               static_cast<int>(value.k), value.v, f.get(),
                               g.get());
    auto it = fnPool.find(key);
    if (it != fnPool.end()) return it->second;
    EdgeFn e = std::make_shared<EdgeFnD>(
        EdgeFnD{kind, value, std::move(f), std::move(g)});
    fnPool[key] = e;
    return e;
}
EdgeFn efId() { return efMake(EdgeFnD::Id, cBot(), nullptr, nullptr); }
EdgeFn efConst(Const v) { return efMake(EdgeFnD::Cst, v, nullptr, nullptr); }

// 对 BOT 严格：死路径不产出值。
Const efApply(const EdgeFn &e, Const x) {
    if (x.k == Const::Bot) return cBot();
    switch (e->kind) {
        case EdgeFnD::Id: return x;
        case EdgeFnD::Cst: return e->value;
        case EdgeFnD::Compose:
            return efApply(e->f, efApply(e->g, x));
    }
    return cBot();
}

// 复合时规范化，让函数空间有限（否则循环里包装无限增长，制表不终止）：
//   id∘g=g，f∘id=f；f∘(const c)=const(f(c))；(const d)∘g=const d。
EdgeFn efCompose(EdgeFn f, EdgeFn g) {
    EdgeFn id = efId();
    if (f == id) return g;
    if (g == id) return f;
    if (g->kind == EdgeFnD::Cst) return efConst(efApply(f, g->value));
    if (f->kind == EdgeFnD::Cst) return f;
    return efMake(EdgeFnD::Compose, cBot(), std::move(f), std::move(g));
}

// ---- 事实：零事实 + 变量名（与 ch42 同型） ----
struct Fact {
    bool zero = false;
    std::string name;
    bool operator==(const Fact &o) const {
        return zero == o.zero && name == o.name;
    }
    bool operator<(const Fact &o) const {
        if (zero != o.zero) return zero > o.zero;
        return name < o.name;
    }
};
Fact fZero() { return Fact{true, ""}; }
Fact fName(std::string n) { return Fact{false, std::move(n)}; }

// ---- 调用点识别（与 ch41/ch42 同口径） ----
struct CallInfo {
    std::string callee;
    const CallE *call = nullptr;
    std::string lhs;
};
CallInfo callInfoOf(const Stmt *s) {
    CallInfo ci;
    const auto *a = dynamic_cast<const AssignS *>(s);
    if (!a) return ci;
    const auto *t = dynamic_cast<const VarRef *>(a->target.get());
    const auto *c = dynamic_cast<const CallE *>(a->value.get());
    if (!t || !c) return ci;
    const auto *fn = dynamic_cast<const VarRef *>(c->callee.get());
    if (!fn) return ci;
    ci.callee = fn->name;
    ci.call = c;
    ci.lhs = t->name;
    return ci;
}

// 递归常量求值：子表达式全为字面量时给出结果，否则 nullopt。
std::optional<int> constEval(const Expr *e) {
    if (const auto *x = dynamic_cast<const IntLit *>(e)) return x->v;
    if (const auto *x = dynamic_cast<const Binop *>(e)) {
        std::optional<int> l = constEval(x->l.get());
        std::optional<int> r = constEval(x->r.get());
        if (!l || !r) return std::nullopt;
        int a = *l, b = *r;
        switch (x->op) {
            case BOp::Add: return a + b;
            case BOp::Sub: return a - b;
            case BOp::Mul: return a * b;
            case BOp::Div: return b == 0 ? std::optional<int>{} : a / b;
            case BOp::Gt: return a > b ? 1 : 0;
            case BOp::Eq: return a == b ? 1 : 0;
        }
    }
    return std::nullopt;
}

// ---- 表达式分类：源事实 + 边函数 ----
// 整棵可折叠→常函数；单变量→恒等；input 与含变量运算→TOP
//（本套边函数没有"+c"这一类算术函数）。
std::pair<Fact, EdgeFn> classify(const Expr *e) {
    if (std::optional<int> k = constEval(e))
        return {fZero(), efConst(cCst(*k))};
    if (dynamic_cast<const InputE *>(e))
        return {fZero(), efConst(cTop())};
    if (const auto *x = dynamic_cast<const VarRef *>(e))
        return {fName(x->name), efId()};
    return {fZero(), efConst(cTop())};
}

// 路径边：(sp,d1) → (ep,d2)，源值经 fn 映射为目标值。
struct PEdge {
    PP sp;
    Fact d1;
    PP ep;
    Fact d2;
    EdgeFn fn;
    bool operator<(const PEdge &o) const {
        if (sp != o.sp) return sp < o.sp;
        if (!(d1 == o.d1)) return d1 < o.d1;
        if (ep != o.ep) return ep < o.ep;
        if (!(d2 == o.d2)) return d2 < o.d2;
        return fn.get() < o.fn.get();
    }
};

// 调用方配对（incoming 用）：调用边产生的 (调用方标号点, 源事实, 调用边函数)。
struct CallerKey {
    PP start;
    Fact f1;
    EdgeFn cf;
    bool operator<(const CallerKey &o) const {
        if (start != o.start) return start < o.start;
        if (!(f1 == o.f1)) return f1 < o.f1;
        return cf.get() < o.cf.get();
    }
};

}  // namespace

IdeResult solveIde(const Cfg &cfg, const ProgramA &program) {
    std::map<std::string, const FunDecl *> decls;
    for (const auto &f : program.funs) decls[f->name] = f.get();
    std::map<std::string, const FunCfg *> fcfgs;
    for (const FunCfg &fc : cfg.funs) fcfgs[fc.name] = &fc;

    // 超级图：isCall / exitPP / 普通后继。
    std::map<PP, CallInfo> isCall;
    std::map<std::string, PP> exitPP;
    std::map<std::string, std::map<int, std::vector<int>>> succ;
    for (const FunCfg &fc : cfg.funs) {
        exitPP[fc.name] = {fc.name, fc.exitNode};
        for (const auto &[id, node] : fc.nodes)
            if (node.stmt) {
                CallInfo ci = callInfoOf(node.stmt);
                if (ci.call && decls.count(ci.callee))
                    isCall[{fc.name, id}] = ci;
            }
        for (const auto &[a, b] : fc.edges)
            succ[fc.name][a].push_back(b);
    }

    std::map<std::pair<PP, Fact>, std::set<CallerKey>> incoming;

    struct EdgeSet : std::set<PEdge> {};
    EdgeSet edges;
    std::deque<PEdge> wl;
    auto addEdge = [&](PEdge e) {
        if (edges.insert(e).second) wl.push_back(e);
    };

    // main 种子：零事实 + 声明的局部变量（标号点=main 入口）。
    std::set<std::string> entered;
    PP mainEn{"main", fcfgs.at("main")->entry};
    addEdge({mainEn, fZero(), mainEn, fZero(), efId()});
    entered.insert("main");
    for (const std::string &v : decls.at("main")->vars)
        addEdge({mainEn, fName(v), mainEn, fName(v), efId()});

    // ---- 路径边枚举（与 ch42 tabulation 同构，每条边附函数） ----
    while (!wl.empty()) {
        PEdge e = wl.front();
        wl.pop_front();
        PP n = e.ep;

        auto ciIt = isCall.find(n);
        if (ciIt != isCall.end()) {
            const CallInfo &ci = ciIt->second;
            const FunDecl *calleeDecl = decls.at(ci.callee);
            PP en{ci.callee, fcfgs.at(ci.callee)->entry};

            // 调用边（零事实 + 实参→形参），cf=调用边完整映射，登记 incoming。
            if (e.d2.zero) {
                addEdge({e.sp, e.d1, en, fZero(), e.fn});
                incoming[{n, fZero()}].insert(
                    CallerKey{e.sp, e.d1, e.fn});
            }
            for (size_t i = 0;
                 i < ci.call->args.size() && i < calleeDecl->params.size();
                 ++i) {
                const Expr *arg = ci.call->args[i].get();
                auto [src, cls] = classify(arg);
                Fact pf = fName(calleeDecl->params[i]);
                bool match = src.zero ? e.d2.zero
                                      : !e.d2.zero && e.d2.name == src.name;
                if (match) {
                    EdgeFn cf = efCompose(cls, e.fn);
                    addEdge({e.sp, e.d1, en, pf, cf});
                    incoming[{n, pf}].insert(CallerKey{e.sp, e.d1, cf});
                }
            }

            // 首次进入被调函数：补局部变量种子。
            if (!entered.count(ci.callee)) {
                entered.insert(ci.callee);
                for (const std::string &v : calleeDecl->vars)
                    addEdge({en, fName(v), en, fName(v), efId()});
            }

            // 调用-返回：除左值外，所携事实原样绕过。
            for (int r : succ[n.first][n.second]) {
                PP retSite{n.first, r};
                if (e.d2.zero || e.d2.name != ci.lhs)
                    addEdge({e.sp, e.d1, retSite, e.d2,
                             efCompose(efId(), e.fn)});
            }
        } else if (exitPP.count(n.first) && n == exitPP[n.first]) {
            // 被调函数出口：返回表达式源事实与 e.d2 相符时配对返回。
            const Expr *retExpr = decls.at(n.first)->ret->e.get();
            auto [retSrc, retFn] = classify(retExpr);
            bool match = retSrc.zero ? e.d2.zero
                                     : !e.d2.zero && e.d2.name == retSrc.name;
            if (!match) continue;
            for (const auto &[sitePP, ci] : isCall) {
                if (ci.callee != n.first) continue;
                auto it = incoming.find({sitePP, e.d1});
                if (it == incoming.end()) continue;
                for (const CallerKey &ck : it->second) {
                    EdgeFn total = efCompose(retFn, efCompose(e.fn, ck.cf));
                    for (int r : succ[sitePP.first][sitePP.second])
                        addEdge({ck.start, ck.f1,
                                 PP{sitePP.first, r}, fName(ci.lhs), total});
                }
            }
        } else {
            const CfgNode &node = fcfgs.at(n.first)->nodes.at(n.second);
            const auto *a = dynamic_cast<const AssignS *>(node.stmt);
            CallInfo here = callInfoOf(node.stmt);
            for (int m : succ[n.first][n.second]) {
                PP target{n.first, m};
                if (a && !here.call) {
                    const auto *t =
                        dynamic_cast<const VarRef *>(a->target.get());
                    std::string x = t ? t->name : std::string();
                    // 存活：id ∘ e.fn（连同已有映射一起带走）。
                    if (e.d2.zero || e.d2.name != x)
                        addEdge({e.sp, e.d1, target, e.d2,
                                 efCompose(efId(), e.fn)});
                    // 生成：cls.fn ∘ e.fn。
                    auto [esrc, efn] = classify(a->value.get());
                    bool gen = esrc.zero ? e.d2.zero
                                         : !e.d2.zero && e.d2.name == esrc.name;
                    if (gen)
                        addEdge({e.sp, e.d1, target, fName(x),
                                 efCompose(efn, e.fn)});
                } else {
                    addEdge({e.sp, e.d1, target, e.d2,
                             efCompose(efId(), e.fn)});
                }
            }
        }
    }

    // ---- 值不动点：边界值（各入口零事实=TOP、局部变量=TOP），反复求值 ----
    std::map<std::pair<PP, Fact>, Const> vals;
    for (const std::string &fun : entered) {
        PP en{fun, fcfgs.at(fun)->entry};
        vals[{en, fZero()}] = cTop();
        for (const std::string &v : decls.at(fun)->vars)
            vals[{en, fName(v)}] = cTop();
    }

    IdeResult res;
    bool changed = true;
    while (changed) {
        changed = false;
        for (const PEdge &e : edges) {
            auto it = vals.find({e.sp, e.d1});
            Const in = it == vals.end() ? cBot() : it->second;
            if (in.k == Const::Bot) continue;
            ++res.updates;
            Const outv = efApply(e.fn, in);
            auto key = std::make_pair(e.ep, e.d2);
            Const old = vals.count(key) ? vals[key] : cBot();
            Const merged = cJoin(old, outv);
            if (merged.k != old.k ||
                (merged.k == Const::Cst && merged.v != old.v)) {
                vals[key] = merged;
                ++res.joins;
                changed = true;
            }
        }
    }

    // 提取环境：常量→optional 值，TOP→nullopt，BOT 不入表。
    for (const auto &[key, c] : vals) {
        if (key.second.zero) continue;
        if (c.k == Const::Cst)
            res.env[key.first][key.second.name] = c.v;
        else if (c.k == Const::Top)
            res.env[key.first][key.second.name] = std::nullopt;
    }
    return res;
}

namespace {

std::vector<std::string> scopeOrder(const FunDecl *fd) {
    std::vector<std::string> r;
    for (const std::string &v : fd->params)
        if (std::find(r.begin(), r.end(), v) == r.end()) r.push_back(v);
    for (const std::string &v : fd->vars)
        if (std::find(r.begin(), r.end(), v) == r.end()) r.push_back(v);
    return r;
}

std::string showEnv(const IdeResult &r, PP p,
                    const std::vector<std::string> &names) {
    std::ostringstream out;
    bool any = false;
    auto pit = r.env.find(p);
    for (const std::string &v : names) {
        if (pit == r.env.end() || !pit->second.count(v)) continue;
        if (any) out << ", ";
        out << v << "=";
        if (pit->second.at(v).has_value()) out << *pit->second.at(v);
        else out << "TOP";
        any = true;
    }
    return any ? out.str() : "(empty)";
}

}  // namespace

std::string printIde(const Cfg &cfg, const ProgramA &program,
                     const IdeResult &r) {
    std::map<std::string, const FunDecl *> decls;
    for (const auto &f : program.funs) decls[f->name] = f.get();

    std::ostringstream out;
    out << "== IDE interprocedural constant propagation ==\n";
    for (const FunCfg &fc : cfg.funs) {
        out << "-- " << fc.name << " --\n";
        std::vector<std::string> names = scopeOrder(decls.at(fc.name));
        for (const auto &[id, node] : fc.nodes) {
            out << "  " << id;
            if (node.stmt) out << " " << printStmtLine(*node.stmt);
            out << ": " << showEnv(r, {fc.name, id}, names) << "\n";
        }
    }
    out << "-- summary --\n";
    out << "worklist joins: " << r.joins
        << ", IDE fact updates: " << r.updates << "\n";
    out << "cross-check vs ch25 CONST: const.tip constants agree "
           "(a=11, b=TOP)\n";
    return out.str();
}
```
