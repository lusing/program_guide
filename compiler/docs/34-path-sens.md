# 第 34 章　路径敏感：让分支条件沿着边走

## 34.1 本章要回答的问题

第 32 章把区间格造了出来，第 33 章用 widening 与 narrowing 治好了它
"迭代不终止"的病。到上一章结束时，我们手里已经有一个会终止、而且对
循环程序能给出紧区间的分析器。本章不急着换语言特性，而是回头检查
区间求解器在另一种程序形状上的表现——**条件分支**。循环关心的是
"同一点被反复到达时信息怎样累积"，分支关心的则是另一个问题：

> 一个汇合点有两条来路，从两条路分别带来的信息并不一样；分析器在
> 把它们 join 起来之后，还分得清"哪条路上知道哪件事"吗？

答案在前面的框架里是否定的。数据流方程的写法是"出口状态只由点上的
语句和入口状态决定"，而入口状态又是所有前驱出口的 join。join 是一次
**无视角的合并**：它把两包事实倒进同一个容器，容器里的每一件事实都
不再带来路标签。本章要演示这件事在两个具体程序上怎样造成精度损失，
然后给出补救：让 CFG 的边也参与传递——条件为真的边和条件为假的边
各自携带从条件推出的信息。这就是**路径敏感**（path sensitivity）最
朴素的含义。

第一个程序 `branch.tip` 只有一个 `if`：

```tip
// file: programs/branch.tip
main() {
  var x;
  x = input;
  if (x > 0) {
    output x;
  } else {
    output 0 - x;
  }
  return 0;
}
```

`x = input` 之后，x 的区间是全区间 `[-inf,+inf]`。条件 `x > 0` 把世界
劈成两半：走真边时 x 一定大于 0，走假边时 x 一定不大于 0。两个 output
语句分居两支：真支里 `output x`，假支里 `output 0 - x`。如果分析器在
分支边上什么也不做，两支看到的 x 都是全区间，预测的输出范围就会宽得
离谱；如果它能读懂条件，真支里的 x 应该收窄成 `[1,+inf]`，假支里的 x
应该压成 `[-inf,0]`，于是假支里 `0 - x` 的结果落在 `[0,+inf]`——负负
得正的保证，是从条件里"读"出来的，不是凭空猜的。

第二个程序 `div.tip` 更尖锐，它把路径敏感和一个真实的缺陷检查连在
一起：

```tip
// file: programs/div.tip
main() {
  var x;
  x = input;
  if (x > 5) {
    output 100 / x;
  }
  return 0;
}
```

除法 `100 / x` 只出现在真支里，而进入真支的条件是 `x > 5`。这意味着
两件事同时成立：x 严格大于 5，因而 x 不可能是 0；而且商被夹在一个
有限范围内。一个看不懂条件的分析器会怎样？它看到除数 x 的区间是
`[-inf,+inf]`——区间里含有 0——于是它必须发出"可能除零"的告警，
并把商保守地推成全区间。告警本身没有错：**在它掌握的信息下**，除零
确实没有被排除。但用户刚刚用条件 `x > 5` 亲手排除了除零，分析器却
没有领情，这就是一次典型的假阳性（false positive）。路径敏感的目标
不是让分析器"胆子大一点"，而是让它**看见用户已经写下的保证**。

本章的核心结论可以先讲在前面：路径敏感开关改变的是**精度**，不是
**可靠性**。关掉条件精炼时，所有预测仍然 sound，只是宽；打开之后，
预测变窄、假阳性消失，但窄下来的每一条边界都必须有条件作依据。这个
区分贯穿全章，也是静态分析工程里最常被混淆的一对概念，22.10 还会
回来专门讲。

## 34.2 直觉：条件是分支点上"免费"的信息

先离开代码，做一次思想实验。假设你在阅读一份别人写的程序，看到：

```
if (x > 0) {
    ...
}
```

你的眼睛刚扫过 `if`，还没进入花括号，就已经知道花括号里的 x 必然满足
x > 0——这不需要运行程序，也不需要任何人告诉你，它是**条件语句的语义
本身**：真支之所以被执行，正是因为条件求值为真。这个信息是免费的，
它就在程序文本里；但"免费"不等于"自动被利用"。一个只在程序点上做
join 的分析框架，结构上就没有地方安放它：点的入口状态是合并后的一团，
真支第一个点只有一个入口，框架无从知道这个入口"只从真边来"。

把这件事翻译成信息流的语言：普通的数据流分析里，信息只附着在
**程序点**上——"节点 n 的出口知道这些"。分支条件带来的信息却附着在
**边**上——"从分支节点沿真边离开时，额外知道这些；沿假边离开时，
额外知道另一些"。要利用它，不必推翻格、不必换不动点引擎，只需要让
边在 join 之前对经过它的状态做一次加工。这个加工必须满足一个朴素的
要求：**它只能删掉不可能性，不能增加可能性**。真边说 x > 0，于是
x ≤ 0 的部分被删掉；它绝不允许把 x 的范围扩大。满足这个要求的加工，
不会破坏分析的可靠性——22.9 会把这句话变成证明。

再看假支。条件为假给出的信息是 x ≤ 0（整数上 `x > 0` 的否定），它
同样删掉一半可能性。值得注意的是假支信息**不与真支对称地直观**：
真支是"下界抬起来"，假支是"上界压下去"，初学者容易只在真边做精炼
而漏掉假边，于是 `else` 分支的预测仍然宽。本章的实现对两条边一视同
仁，22.4 会看到三种条件形状下真假两边各自的规则。

第二个直觉关于合流之后。真支结束时 x ∈ [1,+inf]，假支结束时
x ∈ [-inf,0]，两支在 if 之后汇合，join 立刻又把它们并回全区间——
**路径敏感的信息在离开分支结构时被正常地"忘"掉了**。这不是缺陷：
汇合点确实可能从任一支到达，把两支的精确状态各自保留下来反而不 sound。
路径敏感只保证"身处某一支内部时看得见该支的条件"，它不试图在汇合后
记住历史。想在汇合后仍然区分来源，需要的是更重的机制（路径条件、
谓词抽象），那是 22.3.5 会划清的边界。

### 34.2.1 三句话直觉小结

把上面的长篇直觉压成三句，供后续章节回读。

第一句，条件信息在边上，不在点上。
- 点状态回答"到这里时知道什么"
- 边信息回答"沿这条边过来时，还额外知道什么"
- 分析要利用它，就得给边一个加工步骤

第二句，加工只能删除，不能新增。
- 删除不可能的状态：区间变窄
- 新增可能的状态：可靠性立刻出问题
- 收缩与单调，是这句话的形式化版本

第三句，信息在汇合点被有意忘掉。
- 身处分支内部：看得见本支条件
- 离开分支：两支并回，历史消失
- 想保留历史，要换更重的机制

### 34.2.2 一个反直觉的常识

最后澄清一个常见的直觉倒置：
路径敏感不是"记住走过哪些路径"，而是"在每条边上使用该边的条件"。
- 真正的全路径枚举会路径爆炸，不可行
- 本章从不枚举路径，状态数不随分支数增长
- 它做的是局部的、逐边的裁剪，再交给不动点求解
理解这个倒置，才能理解为什么本章的机制便宜，
也才能理解它为什么治不了相关性问题——
边只携带当前条件，不携带整条路径的条件合取。

## 34.3 形式化：从点上的传递函数到边上的精炼

### 34.3.1 复习：普通数据流方程

到目前为止，每个程序点 n 的数据流事实由一对方程描述。记 IN[n]、
OUT[n] 为点 n 的入口、出口事实，则：

```
IN[n]  = ⊔ { OUT[q] : q 是 n 的前驱 }
OUT[n] = f_n(IN[n])
```

其中 ⊔ 是格的 join（may 分析）或 meet（must 分析），f_n 是点 n 的
传递函数。注意方程的形状：IN[n] 只通过"前驱集合"与图发生关系，
前驱之间没有区别，每条边贡献的都是同一个 OUT[q]，边本身在方程里
**不出现**。这正是"流敏感但路径不敏感"的形式化写照：点的顺序被尊重
（流敏感），但点之间由哪条具体的边到达不被尊重（路径不敏感）。

### 34.3.2 边上的精炼函数

把边引进来。给每条边 (q,n) 配一个函数 ρ_{(q,n)}，它对从 q 流出、
沿这条边进入 n 的事实做加工：

```
IN[n] = ⊔ { ρ_{(q,n)}(OUT[q]) : q 是 n 的前驱 }
OUT[n] = f_n(IN[n])
```

绝大多数边上 ρ 是恒等函数——只有当 q 是分支节点（if/while 的条件点）
且边是它的真边或假边时，ρ 才从条件里提取信息。对区间格，ρ 作用在
环境上：它找到条件里的变量，按边的真假收紧该变量的区间，其余变量
原样保留。这个"只有一个变量被改动"的形状不是随便选的：TIP 的条件
语法只允许一个比较表达式，从中能稳定推出的也就只有一个变量的界；
复合布尔条件（`&&`、`||`）下可以同时精炼多个变量，但那需要语法与
规则的双重扩展，本章不涉及。

### 34.3.3 精炼必须是收缩与单调的

ρ 要配得上"只删不可能性"这句话，形式上至少要满足两条性质。其一是
**收缩**：对任何状态 S，ρ(S) ⊑ S——精炼后的事实在格序上更"高"
（信息更多），绝不比原来更宽。其二是**单调**：若 S ⊑ T，则
ρ(S) ⊑ ρ(T)——知道得更多时，精炼之后仍然知道得更多，不会出现
"信息多反而精炼不出"的反转。

为什么这两条性质是硬性的？收缩保证 ρ 不会无中生有：真边说 x > 0，
ρ 把 x 的区间从全区间收成 [1,+inf]，这是在删去 x ≤ 0 的值；如果 ρ
反而把区间扩大，被扩大出去的部分没有任何程序语义担保，可靠性立刻
破产。单调则是给不动点理论留的：第 25 章证明终止性与 MFP≤MOP 时
依赖整条方程链的单调性，边函数也是链上的一环；ρ 若不单调，worklist
照常能跑（代码甚至不会报错），但"不动点 over-近似具体执行"的论证
就出现了缺口。22.4 给出的三条精炼规则都可以直接验证这两条性质：
它们只是把某个端点换成一个更"靠内"的常数。

### 34.3.4 while 的真假边

分支节点有两种：if 和 while。if 的真边进真支、假边绕开（或进 else），
直觉直接。while 的两条边需要多说一句：真边从条件回到循环体，假边从
条件离开循环。在真边上条件成立——例如 `while (x > 0)` 的循环体里
x ≥ 1；在假边上条件被否定——退出循环时 x ≤ 0。循环体执行完还要回到
条件点重新判断，所以同一个条件点会从两条来路收到状态：循环外的初始
来路和循环体末尾的回边。两条来路在条件点 join，精炼只施加在条件点
**向外**的两条边上，不施加在回边本身——回边携带的是"执行完一轮后
的世界"，那里条件是否成立要重新判断，不能提前精炼。

本章的两个演示程序都没有循环，但求解器对 while 的处理与 if 完全一致，
因为它根本不区分二者：LocalWiring 恢复出的 BranchEdges 只记录"每个
分支节点的真边去哪、假边去哪"，不问节点是哪种语句。循环的终止仍由
widening 在条件点上保证，精炼与 widening 在同一点叠加，顺序是
**先 join、再 widening、出口后边精炼**——22.5.6 会对照代码确认这个
顺序。

### 34.3.5 局部精炼不是完全路径敏感

需要诚实地划一条边界。本章实现的路径敏感是**逐边局部的**：每条边只
看自己分支节点上的那一个条件，不记忆"此前经过的所有条件的合取"。
考虑嵌套分支：

```
if (x > 0) {
    if (y > 0) {
        output x / y;
    }
}
```

在内层分支的真支里，局部精炼同时看得到外层留下的 x（外层状态沿普通
边流进来，没有被遗忘——被遗忘的只在汇合点之后）和内层推出的 y，这
个例子它处理得对。但如果程序在两个分支之间插入一次汇合、再在更深处
追问 x，局部精炼就无能为力了：x 的信息在汇合点已被 join 稀释。完全的
路径敏感会为每条可行路径维护一个路径条件（path condition，即沿途布尔
条件的合取），路径数量在循环存在时无界，因而完全路径敏感与停机问题
一样不可判定。实际工具的选择是连续谱上的若干档：本章的单条件边精炼
是最轻一档；谓词抽象（predicate abstraction）用一组固定谓词的真假
向量给路径"归类"，是更重也更常见的一档；有界验证（bounded verification）
只展开前 k 条路径，放弃完备性换确定性。理解这个谱，比记住"路径敏感"
四个字重要得多。

### 34.3.6 γ 视角：精炼就是集合相交

形式化还可以再压缩一句：边精炼在具体化层面等于一次集合交。

逐步展开这句。
- 点 q 的环境 S 描述一个具体状态集合 γ(S)。
- 边 e = (q,r) 带着一个具体条件 c_e：穿过这条边的状态必满足它。
- 真实在这条边上流动的状态集合是 γ(S) ∩ {σ | c_e(σ)}。
- 若分析能在抽象域里表示这个交集，就令 OUT[r] 对应它。
- 区间域对比较条件恰好能表示，于是有了 22.4 的规则。

"能表示"三个字是全部前提：
- x>k 与区间相交，结果仍是区间 → 能表示
- x≠k 与区间相交，结果是两段 → 不能表示，放弃
- x<y 与笛卡尔环境相交，界落在两个变量上 → 不能表示，放弃
放弃时分析保留 γ(S) 全体：交集 ⊆ 原集，保留原集是可靠近似。

这个视角同时解释了正确性：
- 具体化的精炼集 = 原集 ∩ 条件集
- 它 ⊆ 原集：收缩性
- 条件集固定、相交关于集合包含单调：单调性
两条算子性质从集合交直接继承，无须额外论证。

### 34.3.7 历史信息存在哪里

一个自然的疑问：每条边只看当前条件，那之前分支的信息去哪了？
答案：存在环境里，由前驱逐点传递。

用嵌套分支看清：
- 外层真边把 x 裁窄，写入点状态
- 内层节点 join 时，前驱状态已带着窄区间
- 内层边精炼在窄区间上继续裁
历史不是被"记住"的，是不被擦除地传递的。

哪些操作会擦除历史：
- 对同一变量赋值：旧区间被新值整体替换
- 汇合：两支信息取包络，分支归属消失
- widening：界跳变，旧的有限界可能被放开
除这三类外，信息单调地保留并沿边收窄。

这也给出一条调试直觉：
- 某点该窄却宽，回溯找"最后一次擦除"
- 是赋值：检查新值为何宽
- 是汇合：检查两支是否都宽
- 是 widening：考虑 narrowing
定位擦除点，比反复审查条件规则更有效。

## 34.4 三种条件的精炼规则

本节把第 33 章 `refineOnBranch` 的规则系统地列一遍。三种被识别的条件
形状，每种都有真边、假边两套规则。记号：变量 x 当前区间 [lo,hi]，
哨兵 -inf/+inf 即 INT_MIN/INT_MAX。

### 34.4.1 `x > k`：抬下界与压上界

真边条件成立，x 严格大于 k，整数上等价于 x ≥ k+1：

```
lo' = max(lo, k+1)
```

假边条件被否定，x ≤ k：

```
hi' = min(hi, k)
```

另一端保持不动。若收紧后 lo' > hi'，区间变成 ⊥——这意味着在当前状态
下这条边不可达。这不是错误，恰恰是精炼在干活：典型场景是外层条件
已经把 x 钉成某个值，内层条件与之矛盾，那条边在任何执行中都不会被
走到，沿它传播的事实应当作为 ⊥ 被后续 join 吸收（⊥ 在 join 下被另一
边吸收，不影响结果）。

### 34.4.2 `k > x`：换个方向读

文法上比较可以朝两个方向写，`k > x` 在数学上就是 x < k，即 x ≤ k-1。
实现先把条件**归一化**：解析条件时统一辨认"变量在哪一侧、常数在哪一
侧、是什么比较符"，归一成"变量对常数"的内部形状，再套用同一组规则。
于是：

```
真边: hi' = min(hi, k-1)
假边: lo' = max(lo, k)
```

为什么要归一化而不是写六套规则？比较方向、交换两侧、`x < k` 与
`k > x` 的写法会产生 O(算子数 × 侧别) 的组合，每多写一套就多一处
出错面，而且不同套规则之间必须手工保持对偶一致。归一化把"读懂语法"
和"施加界规则"分成两个步骤：前者只处理形状，后者只有一种形状。这是
教科书里反复出现的实现纪律，22.5 还会在 LocalWiring 里看到同一种思想
的另一个例子。

### 34.4.3 `x == k`：钉死与排除

相等条件最强。真边 x 必须恰好等于 k，区间直接钉成点：

```
[lo',hi'] = [k,k]
```

假边 x 必须不等于 k，区间规则在这里出现一个表达力缺口：区间只能表示
"从 a 到 b 的所有整数"，而"[-inf,k-1] ∪ [k+1,+inf]"是两个区间的并，
单个区间装不下。保守的选择是**假边不精炼**——区间原样保留。这是 sound
的（没有删掉任何真实可能值），只是放弃了一次收紧；不 sound 的选择是
随便取其中半个区间，那会把另一半真实执行误判为不可达。当抽象域
"说不出"某条信息时，正确的反应永远是保留原样，而不是 approximer
得更激进。本章输出里看不到相等条件，但这条规则在求解器里就位，练习
题会请你验证它在具体程序上的行为。

### 34.4.4 规则的统一形状与可验证性

退后一步看，所有规则共享同一个形状：**挑一个端点，把它向区间内部
移动到由 k 算出的某个位置，另一个端点不动；移动后矛盾则得 ⊥**。在
这个形状下验证 22.3.3 的两条性质几乎是平凡的：端点只向内移，所以
结果区间被原区间包含（收缩）；输入区间越窄，向内移之后仍然越窄
（单调，端点移动量与原端点取 min/max，min/max 本身单调）。这正是把
精炼设计成"端点裁剪"而不是"重新计算区间"的回报——形式化性质不是
写完代码后补证的，而是被规则的形状直接保证的。

### 34.4.5 规则速查与形状边界

把三条规则的真假两向压成一张速查，再补上形状边界。

Cgt（x > k）：
- 真边：lo = max(lo, k+1)
- 假边：hi = min(hi, k)

Clt（x < k）：
- 真边：hi = min(hi, k−1)
- 假边：lo = max(lo, k)

Ceq（x == k）：
- 真边：k 在区间内则 [k,k]，否则 ⊥
- 假边：不精炼

统一形状：parseCond 只接受 (变量, 比较符, 常量)。
常量的来源是右端的常量折叠，不是字面量语法——右端可以是 `0-10`
这样的折叠式，只要能折成单点。

形状边界逐条列出：
- 两端都变量：拒绝
- 变量在右、常量在左：按比较符翻转归一（如 0>x 归为 Clt）
- 两端都常量：拒绝（职责属于常量条件处理）
- 含算术且折不成单点：拒绝
- 非比较运算（&&、!、单变量）：拒绝
拒绝一律退回"不精炼"，从不报错停机——形状不符不是程序错误。

### 34.4.6 规则与底的相互作用

精炼产出 ⊥ 后，下游传播遵循一条简单原则：
- ⊥ 环境到达赋值：变量重算，可能"复活"区间吗？

这里必须小心。
- 若 ⊥ 表示"该点不可达"，那么任何赋值都不应让路径复活
- 教学实现里 ⊥ 环境参与 evalIv：未绑定变量给全区间
- 单看数学，这似乎会"复活"

为什么实际不出问题：
- ⊥ 状态不会 enqueue 后继（CHG 判定中 ⊥ 仍是一个合法状态，
  会入队——这里要以具体实现为准核对）

对这一点，正确的阅读方式是回到形式化：
- ⊥ 的具体化集为空
- 空集经过任何传递函数仍是空集（单调函数保持底）
- 实现若让 ⊥ 复活成非底区间，是实现缺陷
本章代码的 ⊥ 来自 lo>hi 的单变量区间，环境中其他变量仍有值，
"点不可达"与"单变量底"在实现层面是两个粒度——
教学实现采用后者，所以不会出现整条路径复活的问题。
这一区分在写自己的分析时要尽早决定，不要混用两种底。

### 34.4.7 规则数量的克制

为什么只实现三条比较、六个方向，而不是把 >=、!=、链式比较
都写全：
- >= 只是 k−1 的平移，新增代码不新增概念
- != 等价于区间域表达不了的补条件，写了也只能放弃
- 链式比较本质是两个条件的合取，嵌套 if 已能表达
规则越少，性质核对（单调、收缩）的面越小；
教学实现宁可让前端形状受限，也要让每条规则都能被完整证明。

### 34.5.1 分支边的恢复

求解器做的第一件额外工作是恢复"每个分支节点的真边、假边分别指向
谁"：

```cpp
// file: src/path.cpp
#include "path.hpp"

#include <algorithm>
#include <set>
#include <sstream>

#include "pretty.hpp"
#include "widen.hpp"

namespace tip {
namespace {

// 分支节点携带的 cond 表达式（与第 33 章 widen.cpp 同一份局部重建）。
const Expr *condOf(const Stmt *s) {
    if (const auto *w = dynamic_cast<const WhileS *>(s)) return w->cond.get();
    if (const auto *i = dynamic_cast<const IfS *>(s)) return i->cond.get();
    return nullptr;
}

// CFG 构造器编号/连线规则的局部重建：拿到每个分支真/假边目标。
struct BranchEdges {
    std::map<int, int> trueOf, falseOf;
};

class LocalWiring {
public:
    BranchEdges run(const ProgramA &program) {
        for (const auto &fun : program.funs) {
            next_ = 2;
            id_.clear();
            number(fun->body.get());
            const int retId = next_++;
            (void)retId;
            wire(fun->body.get(), {retId});
        }
        return edges_;
    }

private:
    BranchEdges edges_;
    int next_ = 2;
    std::map<const Stmt *, int> id_;

    void number(const Stmt *s) {
        if (const auto *b = dynamic_cast<const BlockS *>(s)) {
            for (const auto &x : b->ss) number(x.get());
            return;
        }
        if (const auto *x = dynamic_cast<const IfS *>(s)) {
            id_[x] = next_++;
            number(x->then.get());
            if (x->els) number(x->els.get());
            return;
        }
        if (const auto *x = dynamic_cast<const WhileS *>(s)) {
            id_[x] = next_++;
            number(x->body.get());
            return;
        }
        if (dynamic_cast<const AssignS *>(s) || dynamic_cast<const OutputS *>(s))
            id_[s] = next_++;
    }

    std::vector<int> wire(const Stmt *s, std::vector<int> succ) {
        if (const auto *b = dynamic_cast<const BlockS *>(s)) {
            std::vector<int> cur = succ;
            for (auto it = b->ss.rbegin(); it != b->ss.rend(); ++it)
                cur = wire(it->get(), cur);
            return cur;
        }
        if (const auto *x = dynamic_cast<const IfS *>(s)) {
            const int n = id_.at(x);
            std::vector<int> targets = wireOrSelf(x->then.get(), succ);
            edges_.trueOf[n] = targets[0];
            std::vector<int> rest;
            if (x->els)
                rest = wireOrSelf(x->els.get(), succ);
            else
                rest = succ;
            edges_.falseOf[n] = rest[0];
            return {n};
        }
        if (const auto *x = dynamic_cast<const WhileS *>(s)) {
            const int n = id_.at(x);
            std::vector<int> bodyEntries = wireOrSelf(x->body.get(), {n});
            edges_.trueOf[n] = bodyEntries[0];
            edges_.falseOf[n] = succ[0];
            return {n};
        }
        return {id_.at(s)};
    }
    std::vector<int> wireOrSelf(const Stmt *s, std::vector<int> succ) {
        std::vector<int> r = wire(s, succ);
        if (r.empty()) r = succ;
        return r;
    }
};

// 收集表达式中的全部除法子式（含嵌套）。
void collectDivs(const Expr *e, std::vector<const Binop *> &out) {
    if (const auto *b = dynamic_cast<const Binop *>(e)) {
        collectDivs(b->l.get(), out);
        collectDivs(b->r.get(), out);
        if (b->op == BOp::Div) out.push_back(b);
    }
}

void collectDivsStmt(const Stmt *s, std::vector<const Binop *> &out) {
    if (const auto *a = dynamic_cast<const AssignS *>(s)) {
        collectDivs(a->value.get(), out);
    } else if (const auto *o = dynamic_cast<const OutputS *>(s)) {
        collectDivs(o->e.get(), out);
    } else if (const auto *r = dynamic_cast<const ReturnS *>(s)) {
        collectDivs(r->e.get(), out);
    } else if (const auto *w = dynamic_cast<const WhileS *>(s)) {
        collectDivs(w->cond.get(), out);
    } else if (const auto *i = dynamic_cast<const IfS *>(s)) {
        collectDivs(i->cond.get(), out);
    }
}

}  // namespace

PathResult solveInterval(const Cfg &cfg, const ProgramA &program,
                         int maxRounds, bool refineOnEdges) {
    Lattice<Iv> lat = ivLattice();
    PathResult res;

    std::set<int> widenPoints;
    for (const FunCfg &fc : cfg.funs)
        for (const auto &[id, node] : fc.nodes)
            if (dynamic_cast<const WhileS *>(node.stmt))
                widenPoints.insert(id);

    BranchEdges be = LocalWiring().run(program);
    const FunCfg &fc = cfg.funs[0];

    struct PredEdge {
        int node;
        bool refine;
        bool taken;
    };
    std::map<int, std::vector<PredEdge>> preds;
    for (const auto &[a, b] : fc.edges) {
        PredEdge pe{a, false, true};
        if (refineOnEdges) {
            if (be.trueOf.count(a) && be.trueOf[a] == b)
                pe = PredEdge{a, true, true};
            if (be.falseOf.count(a) && be.falseOf[a] == b)
                pe = PredEdge{a, true, false};
        }
        preds[b].push_back(pe);
    }

    auto computeIn = [&](int p, const std::map<int, IvEnv> &out) {
        IvEnv in;
        auto pit = preds.find(p);
        if (pit != preds.end()) {
            for (const PredEdge &pe : pit->second) {
                IvEnv piece;
                auto it = out.find(pe.node);
                if (it != out.end()) piece = it->second;
                if (pe.refine)
                    piece = refineOnBranch(condOf(fc.nodes.at(pe.node).stmt),
                                           piece, pe.taken);
                for (const auto &[k, v] : piece)
                    in[k] = lat.join(in.count(k) ? in[k] : lat.bot(), v);
            }
        }
        return in;
    };

    std::map<int, IvEnv> out;
    for (int round = 0; round < maxRounds; ++round) {
        bool changed = false;
        for (const auto &[id, node] : fc.nodes) {
            IvEnv in = computeIn(id, out);
            for (const std::string &p : program.funs[0]->params)
                in[p] = Iv{INT_MIN, INT_MAX};

            if (widenPoints.count(id)) {
                auto prev = out.find(id);
                if (prev != out.end())
                    for (auto &[k, v] : in) {
                        Iv pv =
                            prev->second.count(k) ? prev->second.at(k) : lat.bot();
                        v = widen(pv, v);
                    }
            }

            IvEnv o = in;
            if (const auto *a = dynamic_cast<const AssignS *>(node.stmt))
                if (const auto *t = dynamic_cast<const VarRef *>(a->target.get()))
                    o[t->name] = evalIv(a->value.get(), in);

            if (out.count(id) == 0 || !(out[id] == o)) {
                out[id] = o;
                changed = true;
            }
        }
        res.rounds = round + 1;
        if (!changed) {
            res.converged = true;
            break;
        }
    }
    res.out = out;
    return res;
}

std::vector<std::string> divZeroWarnings(const Cfg &cfg,
                                         const std::map<int, IvEnv> &out) {
    std::vector<std::string> warnings;
    for (const FunCfg &fc : cfg.funs)
        for (const auto &[id, node] : fc.nodes) {
            if (!node.stmt) continue;
            std::vector<const Binop *> divs;
            collectDivsStmt(node.stmt, divs);
            const IvEnv &env = out.at(id);
            for (const Binop *d : divs) {
                Iv den = evalIv(d->r.get(), env);
                bool containsZero = !(den.lo > den.hi) && den.lo <= 0 &&
                                    den.hi >= 0;
                if (containsZero) {
                    std::ostringstream line;
                    line << "node " << id << ": divisor "
                         << printExpr(d->r.get()) << " in " << ivText(den)
                         << " contains 0 — possible division by zero";
                    warnings.push_back(line.str());
                }
            }
        }
    return warnings;
}

std::vector<std::string> outputPredictions(const Cfg &cfg,
                                           const std::map<int, IvEnv> &out) {
    std::vector<std::string> lines;
    for (const FunCfg &fc : cfg.funs)
        for (const auto &[id, node] : fc.nodes) {
            const auto *o = dynamic_cast<const OutputS *>(node.stmt);
            if (!o) continue;
            Iv pred = evalIv(o->e.get(), out.at(id));
            std::ostringstream line;
            line << "output node " << id << ": " << printExpr(o->e.get())
                 << " in " << ivText(pred);
            lines.push_back(line.str());
        }
    return lines;
}

}  // namespace tip
```

为什么需要"恢复"？因为 CFG 的边表里没有 true/false 标签——
`fc.edges` 只是一组 `(from,to)` 整数对，从分支节点出发的两条边看起来
完全平等。而要在边上挂条件信息，必须知道哪条去真支、哪条去假支。
CFG 的头文件与实现早在第 12 章就已冻结、并被多章文档逐字节嵌入，
回头去给边表加标签要改动已经定稿的设施；更稳妥的办法是**在本章
局部复制 CFG 的编号规则**：既然节点编号完全由语法树的遍历顺序决定，
那么在同一份语法树上按同样的顺序再走一遍，必然得到同样的编号，
分支节点的两条边哪条先连、连向谁也就可以重新推出来。22.6 专门讲
这份 LocalWiring 的正确性依据。

### 34.5.2 PredEdge：给前驱表的边打标

恢复出 BranchEdges 后，求解器把 CFG 边表翻译成一张带标记的前驱表：

每条 (a,b) 边对 b 来说产生一个 PredEdge{node=a, refine=?, taken=?}。
精炼关闭时所有边 refine=false；精炼打开时，若这条边恰好是 a 的真边，
标记为 {refine=true, taken=true}，假边同理标 {taken=false}；分支节点
之外的普通边保持 refine=false。注意判定方式是"a 在真/假边表里，且
表中记录的目标恰为 b"——两步缺一不可，因为同一个节点 a 可能既作为
分支节点发出两条边，又作为普通节点出现在别的边中，仅凭 a 是否在表
里不足以确认当前这条边的身份。

### 34.5.3 computeIn：join 之前逐条精炼

有了带标记的前驱表，入口状态的计算就与第 33 章只差一步：

```
for (const PredEdge &pe : pit->second) {
    IvEnv piece = OUT[pe.node];
    if (pe.refine)
        piece = refineOnBranch(condOf(节点 pe.node 的语句), piece, pe.taken);
    in = join(in, piece);
}
```

三个细节值得停下来看。第一，精炼施加在**每一份前驱贡献上、join 之
前**：这个顺序是本质的。若先 join 再精炼，分支条件只能对着合并后的
全区间裁剪，真支的信息已经被假支污染，裁剪可能什么也裁不出来；先
精炼再 join，两条边各自收紧之后才汇合，这才是 22.3.2 方程的直接落地。
第二，精炼需要的是**前驱节点上分支语句的条件**，所以要用 condOf 从
节点语句里取出 WhileS/IfS 的 cond——边的起点 a 必是条件节点，取它的
条件天经地义。第三，join 的起点是空环境（∅ 在环境格上是 ⊥：所有
变量都缺信息），单份前驱经过 join 保持不变，这与前几章的处理一致。

### 34.5.4 主循环：与第 33 章逐行相同的骨架

节点的重算循环没有任何新东西：按节点号顺序，computeIn 取入口，
while 头对上一轮出口做 widening，赋值语句在入口环境上 evalIv 得出口，
变了就记账。`refineOnEdges` 在整个主循环里**只出现在建前驱表那一处**。
这正是设计要达到的效果：路径敏感性被完全隔离在"信息如何沿边进入"
这一个问题上，不动点迭代、widening、传递函数全都无须改动。若一个新
特性要求你改动求解器的每个角落，通常意味着它没有被放在正确的抽象层
上；本章的开关是一个正面例子。

### 34.5.5 两档结果都从同一份 CFG 产生

main 函数把同一份 CFG、同一轮 50 次封顶的迭代，分别用 false 和 true
跑两遍，顺序打印：

```cpp

//                  打印 output 点预测与除零告警的对比
#include <fstream>
#include <iostream>
#include <memory>
#include <string>

#include "TIPLexer.h"
#include "TIPParser.h"
#include "antlr4-runtime.h"

#include "ast_build.hpp"
#include "cfg.hpp"
#include "path.hpp"
#include "symtab.hpp"

class CollectErrorListener : public antlr4::BaseErrorListener {
public:
    std::vector<std::string> messages;

    void syntaxError(antlr4::Recognizer *, antlr4::Token *, size_t line,
                     size_t column, const std::string &msg,
                     std::exception_ptr) override {
        messages.push_back("syntax error line " + std::to_string(line) + ":" +
                           std::to_string(column) + " " + msg);
    }
};

namespace {

struct Parsed {
    std::unique_ptr<tip::ProgramA> ast;
    tip::Bindings bindings;
};

Parsed parseFile(const std::string &path) {
    std::ifstream src(path);
    if (!src) {
        std::cerr << "cannot open " << path << '\n';
        std::exit(1);
    }
    antlr4::ANTLRInputStream input(src);
    TIPLexer lexer(&input);
    antlr4::CommonTokenStream tokens(&lexer);
    TIPParser parser(&tokens);

    CollectErrorListener errors;
    lexer.removeErrorListeners();
    parser.removeErrorListeners();
    lexer.addErrorListener(&errors);
    parser.addErrorListener(&errors);

    TIPParser::ProgramContext *tree = parser.program();
    if (!errors.messages.empty()) {
        for (const std::string &m : errors.messages) std::cout << m << '\n';
        std::exit(2);
    }

    Parsed result;
    result.ast = tip::buildAst(tree);
    result.bindings = tip::resolveNames(*result.ast);
    if (!result.bindings.errors.empty()) {
        for (const tip::Diag &d : result.bindings.errors)
            std::cout << d.text << '\n';
        std::exit(3);
    }
    return result;
}

void reportMode(const char *name, const tip::Cfg &cfg,
                const tip::PathResult &r) {
    std::cout << name << "\n";
    for (const std::string &l : tip::outputPredictions(cfg, r.out))
        std::cout << "  " << l << "\n";
    std::vector<std::string> warns = tip::divZeroWarnings(cfg, r.out);
    if (warns.empty()) {
        std::cout << "  div-zero: (none)\n";
    } else {
        for (const std::string &w : warns) std::cout << "  div-zero: " << w << "\n";
    }
}

}  // namespace

int main(int argc, char **argv) {
    if (argc != 3 || std::string(argv[1]) != "--check") {
        std::cerr << "usage: tipa --check FILE\n";
        return 1;
    }

    Parsed p = parseFile(argv[2]);
    tip::Cfg cfg = tip::buildCfg(*p.ast);

    const int maxRounds = 50;
    tip::PathResult base = solveInterval(cfg, *p.ast, maxRounds, false);
    tip::PathResult refined = solveInterval(cfg, *p.ast, maxRounds, true);

    std::cout << "== interval analysis: flow-insensitive vs path-refined ==\n";
    reportMode("FLOW-INSENSITIVE (no edge refinement):", cfg, base);
    reportMode("PATH-REFINED (condition refinement on branch edges):", cfg,
               refined);
    return 0;
}
```

两档共用 `maxRounds=50` 与同一套 widening 点，因此输出差异可以干净地
归因于边上的精炼——对照实验里控制住其他变量，差异才有解释力。报告
分两块：outputPredictions 列出每个 output 点对输出表达式的区间预测，
divZeroWarnings 列出除零告警；无告警时显式打印 `(none)`，让"没有
告警"这件事在输出里同样可见，而不是靠沉默去暗示。

### 34.5.6 widening 与精炼的叠加顺序

在含循环的程序里，一个 while 条件点同时是 widening 点和精炼的出发边
起点，两个算子按如下顺序协作：入口处 join 前驱（含回边）→ 对 join
结果做 widening（对比上一轮该点出口）→ 出口 → 沿真/假边离开时精炼。
即 **widen 在点上、refine 在边上，widen 先于 refine**。这个顺序不能
反：精炼后的区间是"下一轮某一支看到的世界"，不应参与"本点是否还要
继续放宽"的判断，否则 widening 的阈值节奏会被分支局部信息打乱；而且
精炼发生在 widening 之后，意味着被精炼掉的部分本来就不在本点的出口
状态里做账，不会制造"状态变了又变"的假迭代。演示程序无循环，这一
顺序在本章输出中不可见，但它是求解器保持第 33 章终止性质的前提，
22.9.4 的论证会引用它。

## 34.6 LocalWiring：在冻结的设施上恢复语义

本节专门讲 path.cpp 里那份 LocalWiring 类，因为它体现了一条在真实
工程里反复出现的处境：**你需要的语义信息曾经存在于构造过程中，但
没有被最终的数据结构保留下来；而你又不能回头修改那个数据结构。**

### 34.6.1 信息是在哪一步丢失的

CFG 构造器（第 12 章的 cfg.cpp）在处理 IfS 时明确知道两条边的身份：
它先连一条边从条件节点到真支第一个点，再连一条到假支（或汇合后继）。
"第一条是真边、第二条是假边"这个信息在构造器的局部变量里存在过，
但写进 `std::vector<pair<int,int>> edges` 时被抹平了——边表里只有
整数对，没有第三列。这类"构造期可知、成品中丢失"的信息在软件里
极其常见：语法树展开成线性指令时丢失嵌套结构、遍历顺序丢失、临时
名与原名的对应丢失……它们共同的补救方式也一样：**如果构造过程是
确定性的，就重新执行一遍构造过程来恢复信息。**

### 34.6.2 确定性是复制成立的唯一前提

LocalWiring 敢断言"我编号的结果与 cfg.cpp 一致"，依据只有一条：
cfg.cpp 的编号是语法树的**确定性函数**。具体说，编号规则是：入口恒为
1；函数体按语法树先序遍历，从 2 开始递增；每个 if/while 条件点占一个
号，块内语句按出现顺序占号；函数体全部编号完，返回点占下一个号，
退出点（若有）再占一个。整个过程没有哈希遍历、没有按指针地址排序、
没有任何依赖运行时偶发状态的选择。因此在同一份语法树上：

```
cfg.cpp 的编号结果 == LocalWiring 的编号结果
```

不是"大概率一致"，而是由相同输入上的相同确定性过程必然相等。这也给
出了这条技巧的**适用检验**：只要原构造器里存在一个不确定性来源
（例如遍历 `std::unordered_map`、用对象地址当 tie-breaker），复制就
不再可靠，正确做法是回头固化原构造器（排序后再遍历），而不是连不
确定性一起复制。

### 34.6.3 连边规则同样要复制

编号只是一半，LocalWiring 的另一半 `wire` 复制 cfg.cpp 的连边规则：
块的出口语句连块的后继；if 的条件点分别连真、假支的第一个点；while
的条件点真边连循环体第一个点、假边连循环后继；空块/空支时直接连
后继（wireOrSelf 处理"支语句没有产生任何节点"的退化形状）。我们最终
需要的只是 BranchEdges——分支节点号到真假目标的两张表——所以
LocalWiring 没有重建整个 CFG，它只把编号和连线推导做到足以填出这两
张表为止。多重建任何东西都是浪费，也是在复制体里多留一处与本体
漂移的可能。

### 34.6.4 复制的代价与防护

任何代码复制都有一个不能回避的代价：**原规则一旦改变，复制体不会
自动跟着变**，二者会静默漂移。本章接受这份代价有两个理由：其一，
cfg.cpp 已在教程中定稿、不再修改，这是"快照式"教程的特殊便利；
其二，我们有一道便宜的一致性检验——LocalWiring 推出的边目标必须都
是 CFG 边表里真实存在的边：真边 (n, trueOf[n])、假边 (n, falseOf[n])
都要在 fc.edges 中查得到。22.5.2 的建表过程事实上执行了这道检验：
若编号漂移，真/假边要么匹配不上任何边（refine 永不点亮，输出退回
基线），要么错误地匹配（预测被错误收紧——这一种更危险）。工业代码
里对应的做法是给复制体写一个针对本体的差异测试：喂同一组输入，断言
二者推出的编号/边集合相同。把"复制正确"变成一条可重复执行的测试，
而不是一句注释里的承诺。

### 34.6.5 复制后的核对清单

复制设施是本章的工程现实，复制之后按清单逐条核对。

- 前端文件逐个比对版本：语法、AST 形状必须一致
- CFG 构造一致：节点编号规则差异会改变输出行序
- 仅允许新增文件，不允许改动复制来的文件语义
- 新增的接线点集中在一处，便于复查
- 两档输出共用同一条主路径，差别只由开关产生
- expected 文件由二进制真实生成，不手抄
- 手抄的期望即使"看着对"，也无法承担回归职责

清单的最后一条是态度：
- 复制不是设计目标，是在冻结设施约束下的手段
- 一旦上游设施允许扩展，复制件应被回收
- 长期共存的复制件，必然在某次升级中悄悄分叉

## 34.7 除零检查：从区间到告警

`divZeroWarnings` 把路径精炼的成果转成用户可见的缺陷判断。

### 34.7.1 判定规则

对每个程序点，先从该点语句里收集全部除法子式（collectDivsStmt 处理
赋值右端、输出表达式、return、if/while 条件，嵌套的除法通过
collectDivs 递归捞全），然后在该点的出口环境里抽象求值除数表达式：

```
den = evalIv(除数, env)
若 den 不是 ⊥ 且 den.lo ≤ 0 ≤ den.hi → 告警
```

含 0 即可能除零，这是标准的 may 告警：分析器不声称"除零一定发生"，
它只声称"除零没有被排除"。⊥ 不告警的理由也要说清：⊥ 表示该点不可达，
不可达的点上没有任何执行，自然无缺陷可报；若对 ⊥ 也告警，死代码会
稳定制造假阳性。

### 34.7.2 假阳性从哪里来

div.tip 把假阳性的完整解剖摆到了台面上。路径不敏感时：x 来自 input，
区间全范围；CFG 在分支点一分为二，但边不携带条件，真支第一个点看到
的 x 仍是全范围；除数区间含 0 → 告警。告警依据的每一步都正确，**错误
不在任何一条推理规则，而在缺失的信息**：`x > 5` 这个用户已经写下的
事实没有进入分析。理解这一点决定了团队面对静态分析告警时的正确反应
分类——有些告警指向真实缺陷，有些告警指向"分析器在这里看不到足够
信息"；后者既是在报缺陷，也是在请求你通过改写（显式条件、提前返回、
断言）把信息交给它。路径敏感分析器与这个程序配合时，假阳性消失：
真边上 x 被精炼成 [6,+inf]，除数区间不含 0，而且商被 evalIv 按端点
组合算成 [0,16]（100 除以 ≥6 的整数，截断商最大 16、最小趋于 0）。

### 34.7.3 为什么商是 [0,16]

第 32 章的区间除法分三档：除数区间含 0 → 全区间（商在数学上无界）；
两端都是常量 → 精确值；除数排除 0 且分子两端有限 → 取分子、除数端点
的四种组合 n/d，在 64 位整数上算截断商，再取包络。div.tip 落入第三档：
分子 [100,100]，除数 [6,+inf]。100/6 = 16 给出上界；100 除以趋于 +inf
的数截断为 0，给出下界——实现里 +inf 哨兵（INT_MAX）作为真实可表示
除数参与运算，100/INT_MAX 截断恰为 0，与"商趋于 0"的数学直觉一致，
无须为无穷单独写规则。这是把哨兵选成真实 C 整数值带来的便利：抽象
运算可以复用具体除法，只在越界处钳位。

### 34.7.4 may 告警的不对称责任

最后记一条工程伦理：may 告警宁可多报也不能漏报。漏报（false negative，
真实缺陷没有被报出）比多报严重得多——用户对"工具没说话"的信任是
无条件的，一次漏报就足以让整套工具失去价值；多报只消耗复审时间，
而且每一次多报都附带"信息不足"的解释。区间判定因此在所有边界上都
取保守侧：只要 0 没有被**严格排除**（lo>0 或 hi<0），就视为含 0。
注意 `[0,5]` 与 `[-3,0]` 都含端点 0，都必须告警——0 是真实可除零值，
端点不算"几乎排除"。这条"端点按真实值处理"的原则与 22.7.3 里哨兵
参与运算的做法一脉相承。

## 34.8 输出逐行解读

本章的 `expected/output.txt` 是 `--check` 对两个程序依次运行的完整
记录：

```text
; expected: expected/output.txt
== branch.tip ==
== interval analysis: flow-insensitive vs path-refined ==
FLOW-INSENSITIVE (no edge refinement):
  output node 4: x in [-inf,+inf]
  output node 5: (- 0 x) in [-2147483647,+inf]
  div-zero: (none)
PATH-REFINED (condition refinement on branch edges):
  output node 4: x in [1,+inf]
  output node 5: (- 0 x) in [0,+inf]
  div-zero: (none)
== div.tip ==
== interval analysis: flow-insensitive vs path-refined ==
FLOW-INSENSITIVE (no edge refinement):
  output node 4: (/ 100 x) in [-inf,+inf]
  div-zero: node 4: divisor x in [-inf,+inf] contains 0 — possible division by zero
PATH-REFINED (condition refinement on branch edges):
  output node 4: (/ 100 x) in [0,16]
  div-zero: (none)
```

### 34.8.1 branch.tip 的两档对照

第一段 `== branch.tip ==` 之后，路径不敏感基线给出三行预测。

`output node 4: x in [-inf,+inf]`：真支里直接输出 x，而该点看到的 x
与输入同范围——分析器不知道自己身处真支。`output node 5: (- 0 x) in
[-2147483647,+inf]`：假支输出 0−x。为什么不是全区间？因为区间减法是
端点运算：0 − [-inf,+inf] 的下界是 0 − (+inf)，而 INT_MIN 在 C 整数
里不是 0 的对称相反数——`0 - INT_MIN` 在数学上是 2147483648，超出
INT_MAX，饱和到 INT_MAX；上界 0 − (-inf) = +inf。所以即便没有路径
信息，表达式本身的形状也把下界从 -inf 抬到了 -2147483647（上界则
保持 +inf）。这是一个微妙但真实的精度：**格与抽象运算本身就在工作，
路径敏感只是在它们之上再加一层**。没有除零（表达式中无除法），打印
`div-zero: (none)`。

精炼档同样三行。`x in [1,+inf]`：真边把下界抬到 0+1。`(- 0 x) in
[0,+inf]`：假边把 x 压成 [-inf,0]，再做区间减法，下界 0−0=0，上界
0−(-inf)=+inf——"非正数取反是非负数"，与小学算术一致。两行预测
各自比基线窄，窄的部分全部能指回条件：这就是一次成功的精炼应有的
样子。

### 34.8.2 div.tip：告警消失的完整轨迹

第二段是本章的主角。基线三行：

`(/ 100 x) in [-inf,+inf]`：除数 x 全范围、含 0，区间除法落入最保守
的一档，商取全区间。`div-zero: node 4: divisor x in [-inf,+inf]
contains 0 — possible division by zero`：告警文本同时给出位置（节点
4）、除数表达式、除数区间与判定理由——好的告警文本让用户不必打开
工具源码就能复述分析器的推理。

精炼档两行：`(/ 100 x) in [0,16]`（22.7.3 的推导）与 `div-zero:
(none)`。同一个程序点、同一个除法表达式，两档之间只差边上的一条
规则，告警从有到无、商从全区间到 17 个整数值的窄范围。没有任何
魔法，也没有任何"放松检查"：放松检查得到的会是"不告警但也说不出
商的范围"，而这里分析器给出了**更强**的断言。用"断言的强弱"来检验
优化是否偷工减料，是可靠性工程里常用的反向核对。

### 34.8.3 哪些差异本章没有出现

读输出时也应注意缺席者。两档都没有出现 ⊥：两个程序的所有点在两档
下都可达，精炼没有在任何点上推出矛盾。若你的程序里条件互相矛盾
（如同一个嵌套分支要求 x>0 且 x<0），精炼会把不可达边变成 ⊥，join
吸收 ⊥ 后结果不变——那时输出里会短暂出现 ⊥，但它代表"此路不通"
而非"分析失败"。两档之间也没有 widening 轮数差异：无循环，轮数都是
1。这些缺席不是遗漏，是程序形状的如实反映；对照实验中，能解释"哪些
量为什么没变"和能解释"哪些量变了"同样重要。

### 34.8.4 阅读顺序建议

读输出文件时建议固定顺序，避免漏行。

- 先看 FLOW 段，建立无精炼基线
- 再看 REFINED 段，逐节点对比
- 节点相同的行，只比区间端点
- 区间变窄：记下是哪个端点动了
- 告警减少：回查对应除数区间
- 最后确认行数：两档节点集合应一致
行数不一致比区间变宽更值得警惕：
- 节点消失通常意味着接线漏掉了某个点
- 那是结构问题，不是精度问题

## 34.9 正确性论证思路

本节给出本章分析可靠性的论证骨架。沿用前几章的具体化映射 γ：区间
环境 S 的具体化是"把每个变量赋成其区间内某个整数（⊥ 环境对应空）"
的全部具体状态集合。可靠性目标不变：**每个程序点上，任何真实执行
到达该点时的具体状态，都属于该点分析出口事实的具体化。**

### 34.9.1 归纳结构

证明对程序点做结构化归纳（有循环时改为对迭代轮数归纳，取不动点）。
归纳假设：所有前驱点上真实执行的出口状态都被各自分析事实覆盖。考察
进入当前点的一次真实执行：它必沿某一条具体的边 e=(q,n) 从 q 来，
而 q 上的具体状态按归纳假设 ∈ γ(OUT[q])。边函数加工之后，需要证明
该具体状态 ∈ γ(ρ_e(OUT[q]))——即**精炼不会把真实状态删掉**。这一步
是本章相对前几章唯一的新增义务，下一小节单独处理。随后 join 保持
覆盖（γ 在 join 下封闭：具体状态属于某一份贡献，就属于贡献们的并），
点传递函数 f_n 保持覆盖（第 32 章已对区间算术的局部可靠性做过论证：
具体整数落在区间内，运算结果必落在结果区间内）。义务闭合。

### 34.9.2 精炼的局部可靠性

要证：若具体状态 σ ∈ γ(S)，且沿边 e 的条件在 σ 下按真实语义取值与
边的真假一致，则 σ ∈ γ(ρ_e(S))。以 `x > k` 真边为例：边为真意味着
σ(x) > 0 条件成立，即 σ(x) ≥ k+1；而 ρ 把 x 的区间下界抬到
max(lo,k+1)。σ 原本满足 σ(x) ≥ lo（因为 σ ∈ γ(S)），现在同时满足
σ(x) ≥ k+1，故 σ(x) ≥ max(lo,k+1)，σ 仍在精炼后的区间内；上界没动，
σ 在上界一侧的满足关系不变。其余变量区间没动，满足关系保持。假边
与另外两种条件是逐行同构的论证，唯一需要小心的是 22.4.3 的假边——
那里 ρ 选择恒等（放弃精炼），局部可靠性当然成立。若 ρ 错误地试图
用半个区间表示"≠k"，这一步就会失败：σ(x)=k+1 的真实状态会被漏掉。
可靠性证明在此充当了规则选择的裁判。

### 34.9.3 汇合与 ⊥ 的处理

22.2 说过"汇合后信息被正常忘掉"，形式上对应 join 的覆盖性质：真支
结束的具体状态 ∈ γ(真支事实)，假支同理；join 结果的具体化是两支
具体化的并（区间 join 的具体化恰为区间并——包络内所有整数，恰好
包含两支），所以无论执行从哪支到达汇合点，都被覆盖。代价是包络中
可能混入两支都不单独包含的值吗？不会：包络 [min lo, max hi] 里的
每个整数都属于"从某支可达"吗？严格地说，若两支区间是 [1,3] 与
[10,12]，包络 [1,12] 会把 4..9 也包含进来——这些值两支都不产生。
join 在此**过 approximate**：覆盖保持（sound），但混入了空隙（不精确）。
这就是路径不精确在汇合点的形式化来源；要消去空隙，需要非凸的域
（区间之并）或路径条件，代价是 22.3.5 说的不可判定边界。⊥ 一侧没有
对称问题：γ(⊥)=∅，⊥ 与任何事实 join 都被吸收，不可达边不贡献覆盖
义务，也不污染结果。

### 34.9.4 终止性不受影响

最后确认本章没有重新打开第 32 章的终止性缺口。边函数 ρ 只在每次
重算时被调用常数次（每条前驱边一次），它不改变状态被写回的格，
也不产生新的状态键——状态空间仍是"每点一个区间环境"，高度仍由
widening 压成有限。唯一可能的担心是 ρ 制造出 ⊥ 之后状态反复横跳：
检查 22.5 的写回条件，状态从非 ⊥ 变 ⊥ 是一次正常的单调移动（⊥ 在
环境格最低），而 ρ 的单调性保证后续轮次里它不会又被推回非 ⊥——
一旦某条边的所有前驱都只贡献 ⊥，精炼保持 ⊥。所以迭代序列仍然
单调、仍然在有限步稳定。widening 与 refine 的顺序（22.5.6）在这条
论证里被隐式使用：若反过来让精炼结果参与 widening 的状态比较，
"单调移动"的记账就不再成立。

### 34.9.5 归纳覆盖的三个细节

归纳证明在三个细节上容易被质疑，这里逐一补足。

细节一，多前驱点的归纳假设如何组合。
- 对每个前驱分别使用归纳假设：具体状态沿某条具体边来自某个前驱
- 该前驱的 OUT 覆盖它
- join 的具体化集合包含所有前驱具体化集合的并
  （γ 对 join 的这一性质，由区间包络定义直接成立）
- 所以 join 后的状态仍被覆盖
多条具体边一次只走一条，但证明要对"任意一条"成立，逐个前驱覆盖。

细节二，边精炼作用在 join 之后，条件信息怎样进入假设。
- 具体执行穿过边 (q,r) 时，条件的真假是确定的
- 真边：具体状态满足条件；规则把不满足条件的具体状态排除出具体化集
  （Cgt 真边后，具体化集里的每个状态 x≥k+1）
- 具体状态既满足条件，必在精炼后的具体化集中
- 假边同理（Clt/Cgt 假边条件取反后覆盖）
关键句式：ρ(γ) 的具体化集 = γ 的具体化集 ∩ 条件定义的状态集。
本章实现是这个集合交的区间形式。

细节三，不动点与逐轮近似的关系。
- 归纳严格说是对"第 n 轮近似"成立：任何执行长度不超过 n 的路径都被覆盖
- 真实程序的执行路径长度有限（TIP 程序每次执行是有限的）
- 取 n 为该路径长度，对应轮次的近似已覆盖它
- 不动点比每一轮近似都"宽"（单调序列的上界），也覆盖它
从"逐轮覆盖"过渡到"不动点覆盖"，靠的是有限执行与单调包含。

### 34.9.6 缺陷判定的推论链

有了状态覆盖，除零结论按下面的链条推出。
- 前提一：到达除法点的每个具体状态，都在入口环境的具体化集中。
- 前提二：除数表达式在该环境下的求值区间不含 0。
- 前提三：表达式求值本身是可靠的（具体除数属于区间）。
- 推论：每个具体除数 ≠ 0。
- 结论：该点不发生除零。

反过来，"可能除零"的含义：
- 除数区间含 0
- 分析只能说"具体化集里存在除数为 0 的状态"
- 该状态是否对应一条真实路径，区间分析不保证
- 这就是误报的逻辑位置：具体化集允许的状态超出真实可达集
注意"可能"不是"一定"：它是可靠性下的弱结论，工程师需要进一步证实。

### 34.9.7 论证的边界

这套论证明确不覆盖什么，必须说清：
- 不覆盖前端解析错误的程序（语法错误直接拒）
- 不覆盖整数溢出的具体后果（教学语义假设饱和；真实硬件回绕）
- 不覆盖 input 之外的外部世界
- 不证明终止性（while 可能具体地不终止，分析仍给出近似）

边界之外的问题不丢人：每个可靠的分析都带着假设清单。
危险的是假设没写出来，使用者按"全行为可靠"理解。

## 34.10 精度、可靠性与代价：三个独立的轴

本章最容易被压缩成一句"加了路径敏感，分析更准了"，但值得花一整节
把三个轴拆开，因为它们在工程决策里必须分别回答。

**可靠性（soundness）是二元的准入条件。** 一个分析要么 sound，要么不 sound；
"95% sound"不是可靠性指标，而是在描述缺陷率——漏掉的那 5% 会让用户
在无戒备时撞上真实缺陷。本章两档分析都 sound，开关不触碰这个轴。

**精度（precision）是连续的质量指标。** 同样 sound 的两个分析，可以一个
给出全区间、一个给出 [0,16]；精度衡量"具体化集合离真实可达集合有多远"，
即过 approximate 的程度。路径敏感只在这个轴上移动。判据永远是相对的：
在同一组程序、同一组查询点上比较具体化集合的包含关系——本章输出里，
精炼档每个预测区间都被基线区间包含，且至少一处严格更窄，所以"更精确"
有形式化依据，不是印象。

**代价（cost）是第三轴。** 局部边精炼的代价其实很小：每轮每条分支边
多一次端点裁剪，O(分支数 × 变量数)；本章没有新增状态键。但沿精度轴
继续走——谓词抽象、路径敏感的 k 限展开、流/上下文/路径三敏感叠加——
代价指数上升，而且上升的首先是**状态数**（谓词向量 2^p、上下文 × 路径
组合），其次才是 CPU。工程上的正确提问顺序因此是：这个分析 sound 吗？
在 sound 的候选里，哪一档精度足以压低用户实际看到的假阳性？这一档的
状态数与迭代轮数是否随程序规模可接受？跳过第二问直接堆精度，得到的
是没人等得起的工具；跳过第三问直接砍特性，得到的是天天喊狼来了的
工具。

工业界的静态分析产品线（从编译器警告到 Clang Static Analyzer、Infer、
CodeQL 一类）几乎都在这三个轴上做显式取舍：编译期默认通道选"sound
近似 + 轻精度 + 线性代价"，独立深度分析通道才开启路径/上下文敏感。
本章两档对照可以看作这条产品决策的最小模型——同一个可执行文件里
并排放着两档结果，读者可以直接数出"多花的那点计算买到了几行不再
误报的告警"。

### 34.10.1 三轴的独立性举例

三轴独立，意味着可以两两错位；下面三例把错位显式化。

高精度、高可靠、高代价的典型：
- 谓词抽象配大量谓词
- 状态数 2^n，SMT 调用昂贵
- 结论精确且可靠
- 代价是运行时间与维护成本

高精度、不可靠：理论上不该出现，但实践中有：
- 一条"聪明"的裁剪规则违反收缩
- 输出看着窄，实际排除了真实状态
- 这种"精度"必须拒绝：可靠性是准入门槛
- 三轴的顺序：先保可靠，再谈精度，最后谈代价

低精度、高可靠、低代价：
- 本章 FLOW 档
- 几乎不增加什么，结论宽但不出错
- 作为基线与兜底，永远有价值

### 34.10.2 工程上的取舍顺序

按什么顺序做取舍，建议如下：
1. 先确认可靠性（经验测试 + 算子性质）。
2. 再在目标缺陷类型上评估精度（反例库的误报率）。
3. 精度不达标，按 22.22.9 的分类选机制。
4. 机制选定后再压代价（队列策略、分模块开关）。
颠倒 3 和 4，会在错误的机制上做廉价优化。

### 34.10.3 代价的三个量

代价不只"跑得快不快"，至少量三个：
- 状态更新次数：与代码规模、环结构相关
- 内存峰值：最大同时存在的环境大小
- 工程维护成本：规则、谓词、例外清单的年增长量
第三个量在长期项目里往往决定生死：
- 一个分析首年快、准，第三年满是手写抑制
- 与一个稍慢但机制稳定的分析，后者通常胜出
把维护成本写进评估，才算量全了代价轴。

## 34.11 三个完整的纸上推导

读分析器的输出是一种能力，不看输出、自己在纸上把分析推一遍是另一种
更硬的能力。本节带读者把两个演示程序完整推一遍，再加一个本章代码
没有收录、但能暴露边界的小程序。建议读法：先自己拿一张纸推，再与
本节对账；对不上的地方，多半正是某个概念没有真正过关。

### 34.11.1 branch.tip 的逐点账本

先确定节点编号。按 LocalWiring 复制的先序规则：入口 = 1；函数体按
出现顺序，`x = input` 是节点 2；if 条件点是节点 3；真支 `output x`
是节点 4；假支 `output 0 - x` 是节点 5；函数体编号完，return 语句占
节点 6；若有退出节点再占 7。边：1→2，2→3，3→4（真），3→5（假），
4→6，5→6，6→（退出）。

从入口开始累积环境。节点 1（入口）无参数，环境空。节点 2 的入口
= 节点 1 的出口（空）；赋值 `x = input` 的传递把 x 写成
evalIv(input)=[-inf,+inf]；出口环境 {x:[-inf,+inf]}。节点 3 是条件点，
条件本身不修改环境（我们的条件只做判断、不赋值），出口与入口相同。

关键在节点 4 与 5 的入口。**精炼关闭**时：节点 4 的入口 = ρ=恒等
作用于节点 3 的出口 = {x:[-inf,+inf]}；output 不修改环境，输出表达式
x 在此环境求值 = [-inf,+inf]。节点 5 同理，输出表达式 `0-x` 走区间
减法 Iv{satAdd(l.lo, −r.hi), satAdd(l.hi, −r.l)}，左端 [0,0]、右端
[-inf,+inf]。

下界：satAdd(0, −INT_MAX) = −2147483647。上界这里有一个初学者十有
八九要滑的弯：−r.lo = −INT_MIN = 2147483648（在 long long 中），
satAdd(0,2147483648) 越过 INT_MAX，**饱和到 INT_MAX**——而 INT_MAX
正是 +inf 的哨兵，于是该端点显示为 +inf。饱和值与哨兵恰好重合，不是
巧合：哨兵选的就是具体域的真实端点，算术"爆出去"时落到的也正是
它。所以最终预测 [-2147483647,+inf] 与输出逐字一致。手推时若你在
这一步愣了一下（"上界到底是 2147483647 还是 +inf"），记住答案是
"二者是同一个 int 值的两个名字"——这正是把 ±∞ 编码成真实 C 整数
最容易绕进去、也最值得想透的一点。

**精炼打开**时：节点 4 的入口 = ρ_真边(节点 3 出口)，规则 `x>0` 真边
把下界抬成 max(-inf, 0+1)=1，环境 {x:[1,+inf]}；输出 x = [1,+inf]。
节点 5 的入口 = ρ_假边，上界压成 min(+inf, 0)=0，环境 {x:[-inf,0]}；
输出 `0-x`：下界 satAdd(0,−0)=0，上界 satAdd(0,−(−inf))=+inf，得
[0,+inf]。两支在节点 6 前汇合：节点 6 入口 = join(节点4出口, 节点5
出口)，x 回到包络 [-inf,+inf]——精炼的信息按 22.9.3 所说被正常遗忘。

### 34.11.2 div.tip 的逐点账本

节点编号：入口 1；`x = input` 节点 2；if 条件点 3；真支 output 节点 4；
return 节点 5。注意没有 else——假边从 3 直接连向汇合后继 5。边：
1→2，2→3，3→4（真），3→5（假），4→5。

**精炼关闭**：节点 4 入口 x 全区间。输出表达式 `100/x`，evalIv 走
Div：除数 [-inf,+inf] 含 0（lo≤0 且 hi≥0）→ 返回全区间；除零检查在
同一环境求值除数，含 0 → 告警。节点 5 的入口 = join(节点4出口,
ρ(节点3出口))：两条贡献都是 x 全范围，join 仍全范围。

**精炼打开**：节点 4 入口 = ρ_真边，条件 `x>5` 把下界抬到 6：
{x:[6,+inf]}。evalIv(100/x)：除数不含 0（lo=6>0），分子两端有限
（100），进入端点组合档：分子 {100,100}，除数 {6, INT_MAX}，组合
100/6=16、100/INT_MAX=0（截断），包络 [0,16]。除零检查：除数
[6,+inf]，不含 0 → 不告警。节点 5 入口 = join(节点4出口 {x:[6,+inf]},
ρ_假边(节点3))：假边规则把 x 压成 [-inf,5]；join([6,+inf],[-inf,5]) =
[-inf,+inf]——汇合点再次如实反映"执行可能从两支任一来"，而两支的
区间在这里恰无空隙地拼成全区间（5 与 6 相邻），与 22.9.3 担心的
"包络混入空隙"情形不同。这个细节值得记下：**join 是否过近似，要看
两支区间在数轴上是否相邻；路径精炼把边界推得越紧，拼回时空隙越小，
这是精度在汇合点的隐性收益。**

### 34.11.3 一个边界程序：精炼、汇合、再追问

考虑下面这份没有收录进示例目录的程序：

```
main() {
    var x, y;
    x = input;
    if (x > 0) {
        y = 1;
    } else {
        y = 0 - 1;
    }
    if (y > 0) {
        output x;
    }
    return 0;
}
```

第一个 if 精炼了 x 但赋值的是 y；两支在第一个 if 结束处汇合，y 的
入口 = join([1,1],[-1,-1]) = [-1,1]（注意这里包络混入了 0——两支都
不产生 y=0；这是 22.9.3 的空隙在真实程序里的样子：后续若问 y==0
就会假阳性）。第二个 if 问 y>0：真边精炼的是 y，与 x 无关；真支里
output x 时，x 的信息早在第一次汇合被 join 成全区间——尽管能走到
`y>0` 真支的路径必然来自第一个 if 的真支（只有那里 y=1），因而必然
x>0。局部边精炼推不出这一步：它需要记住"y=1 的来路同时带 x>0"，
即两个变量事实的**相关性**。单变量、逐边、无记忆的设计在此精确地
失效。要得到 x=[1,+inf]，需要么路径条件（合取），要么关系域
（跟踪 y 与 x 的关联），要么把环境提升成"环境之并"保留两支不相混。
这个程序值得抄下来反复看：它标出的不是"本章没做到"，而是**三类
更重机制各自要解决的具体问题**——学机制时带着这种最小反例，才不
会把谓词抽象、关系域、析取域混为一谈。

## 34.12 边精炼在其他格上的表现

本章的代码把边精炼挂在区间格上，但精炼思想与格无关：条件提供的是
"具体状态必须满足的约束"，任何抽象域只要能消费这个约束，就能在边
上收紧。本节把同一份条件信息分别放到常量格与符号格上考察——结论
是：**格的形状决定了它能从同一条件里挤出多少精度。**

### 34.12.1 常量格：只在相等条件上获益

扁平常量格的元素是 ⊥、具体值 c、⊤。考察 `if (x > 0)`：真边说
x>0——常量格能消费吗？x>0 是一个无穷值集，不能表达成某个 c，也
不是 ⊤ 能"收紧"的（⊤ 已经是最宽），规则只能是恒等。再看
`if (x == 5)`：真边说 x 恰为 5，这正是常量格最喜欢的形状——若入口
x=⊤，精炼后 x=5，一次从"未知"到"确定"的跳跃。假边 x≠5：⊤ 仍然无
法收紧（除了 5 以外什么都可能），恒等。可见常量传播加路径敏感，
精度收益集中在"条件恰好把变量钉死"的程序上：分派判别（dispatch on
tag）、边界特判、枚举分支。这也解释了一个常见现象：针对常量的路径
敏感优化（如条件常量传播，conditional constant propagation）把
"求值条件→沿可行边传播常量→不可达边剪 ⊥"做成协同过程，本质上就是
常量格 + 边精炼 + 不可达路径剪除的三合一。

### 34.12.2 符号格：真假两边各删一个符号

符号格（第 23 章的 {-,0,+} 之类）也能消费比较条件。`x > 0`：真边
删去 "-" 与 "0"，x 只剩 "+"；假边删去 "+"，x ∈ {"-","0"}。与区间格
相比，符号格的收益更粗（它本来就只分辨符号），但规则一一对应，
收缩与单调同样直接。注意 0 的处理：整数上 x>0 的真边严格排除 0，
漏掉这一点（把 0 留在真支）会让"用 x 做除数"的判断失准。**条件精
炼在任何格上都要逐条处理边界值**；格越简单，边界规则越容易因为
"差不多"被写错。

### 34.12.3 统一视角：条件作为域的重写算子

把两个例子与区间格并排放，可以提炼出一条一般接口：给抽象域 A 配
一个"条件消费"算子 filter : A × 布尔表达式 × 真假 → A，要求
filter(a,c,t) ⊑ a（收缩）、单调，且具体化满足
γ(filter(a,c,true)) = γ(a) ∩ {σ : c 在 σ 为真}（右式可能无法在 A 中
精确表示，此时取 A 中能覆盖它的最窄元素——即 f_a 在抽象域里的近
似）。本章区间格的三条规则、常量格只对等号生效、符号格删符号，都
是这个接口在各自域上的实现。这个接口还有一个对偶的读法：它就是
抽象解释里"假设语句（assume）"的传递函数——把分支条件翻译成
`assume(c)` / `assume(¬c)` 两个伪语句挂到边上，路径敏感便不再需要
求解器层面的任何特殊待遇，它只是两类额外语句的传递函数。许多实际
分析框架正是这样实现的：CFG 显式包含 assume 节点，边不再需要特殊
语义。本章选择边函数而非 assume 节点，是因为不想为教学分析改动
CFG 构造器；两种实现一一对应，练习题会请你把它们互相翻译。

### 34.12.4 相关条件与域的表达力极限

22.11.3 已经碰到：`if (x>0)` 之后 `y=1`，汇合后再问 y>0，需要 x 与 y
的相关性。单变量独立环境（无论挂区间、常量还是符号）结构上假设
"变量的抽象值彼此独立"——环境是各变量事实的**笛卡尔积**。笛卡尔
积域表达不了相关性：γ({x:Sx, y:Sy}) 是 Sx×Sy，包含"x 任意配 y
任意"的全部组合，包括具体执行中永不共同出现的组合。要表达相关，
必须打破笛卡尔形状：关系区间（tracking x−y 界的差界域/八边形）、
析取环境（环境之并，给每条路径一份）、或谓词抽象（任意关系谓词）。
边精炼本身不打破笛卡尔形状——它逐变量独立裁剪；因此它能解决
"同一点上单变量的界"问题，解决不了"变量间关系"问题。分清"条件消
费算子"与"域的笛卡尔性"这两个正交的设计点，是阅读更高级分析文献
的入场券。

## 34.13 从边精炼到谓词抽象

本节沿着精度轴向更重的一档走一小段，介绍谓词抽象的基本图景——不
要求读者掌握其全部算法，只要求理解它与本章做法的对应与分界，因为
工业级软件验证工具大多建立在这一图景上。

### 34.13.1 谓词集与抽象状态

选定一组关于程序状态的谓词，例如 {x>0, y==0, x<y, flag≠0}。谓词是
布尔的：在每个具体状态上非真即假。一个具体状态由此映射到一个
布尔向量（每个谓词的真假），向量就是该状态的**抽象状态**；向量空间
只有 2^n 个元素，无论具体状态空间多大。这与区间格的哲学一致（用
有限/可控的抽象集合 over-近似），差别在表达原料：区间只能说"单个
变量的界"，谓词可以说任意可表达的关系（只要有人把它写进谓词集）。

### 34.13.2 抽象后继与可行路径

分析沿 CFG 推进时，要回答"抽象状态 v 经过语句 s 能到达哪些抽象状态"：
取 v 的具体化（满足该真假组合的具体状态），施加 s 的具体后继，再
映射回布尔向量；实际计算不经过具体化（无穷），而是用定理证明器/
SMT 求解器判定"v ∧ s 的后继 ∧ v' 是否可满足"，可满足的 v' 都是后继。
不可满足的转换对应**不可行路径**，直接不产生后继——这是比本章更强
的能力：局部边精炼只能裁剪单个条件，谓词抽象可以判定"沿途条件合取
起来是否矛盾"，因而能剔除需要综合多个分支信息才看得出的死路径。
22.11.3 那种"y=1 必带 x>0"的关联，若谓词集中有相应谓词，就能被
利用。

### 34.13.3 代价与本章做法的定位

代价同样对应升级：抽象状态 2^n，理论上最坏指数；每次后继判定调用
SMT，单步代价远高于端点裁剪。工程上靠三招压住规模：笛卡尔抽象
（Cartesian abstraction，谓词独立更新、放弃跨谓词关联——它恰好退回
本章逐变量独立的精神）；懒精化（只对相关谓词求真假，未知先挂
*）；以及 CEGAR（counterexample-guided abstraction refinement，先跑
粗抽象，发现假反例时分析反例需要哪个新谓词、加进去重跑，直到假
反例消失或找到真反例）。本章的单条件边精炼在这个谱上的位置由此
清晰：它是"零个额外谓词、零次 SMT 调用、每边常数时间"的最轻档；
当一个项目的假阳性主要来自单变量边界（如除零、数组越界），这一档
能吃掉大头，而谓词抽象留给需要关系与路径推理的少量深度查询。
**用最轻的机制吃掉 80% 的误报，重机制按需触发**，是几乎所有可扩展
静态分析产品线的共同形状，22.10 的三轴取舍在这里再次出现。

### 34.13.4 谓词从哪来

最后一个实际问题：谓词集由谁选定？手工集（来自属性知识与已知缺陷
模式）可控但需要领域专家；自动精化（CEGAR 从反例中插值生成新谓词，
典型如 Craig 插值）省力但可能产生冗余、难读的谓词。混合做法最常见：
一组稳定的手工核心谓词 + 精化时的自动补充。与本章对照，区间阈值/
条件规则相当于把最常用的一批"谓词"（x>k 形态、边界比较）硬编码进
分析器，免去选择与求解——预加工常见问题，是轻量分析器的立身之本。

## 34.14 告警治理：从读懂警报到改写程序

路径敏感的最终用户价值在告警质量上，而告警质量只有一半由分析器
决定；另一半是**程序员如何与告警共处**。本节讲实践侧。

### 34.14.1 三类告警的分类处置

收到一条静态分析告警，先分三类。第一类，具体路径可复述、条件无
矛盾：按真实缺陷处理——修代码或补测试。第二类，分析器明确显示
"信息在此处断裂"（如除数区间全范围、目标可能来自多个函数）：它在
请求信息；处置不是抑制，而是把程序改写成信息可流动的形状。第三类，
沿已知不可达路径报出（矛盾条件、调试桩）：先确认真不可达，再用
**局部、可检索、带理由**的方式抑制（22.14.3）。把三类混为一谈（要么
全信、要么全关）是团队引入静态分析后最常见的失败模式。

### 34.14.2 让信息流动的改写模式

针对第二类，几种经典改写。guard clause（卫语句/提前返回）：把
`if (x != null) { 整个函数体 }` 反过来写成 `if (x == null) return;
函数体`——分支结构被压扁，函数体里所有点都稳定地在 x≠null 的边
内，路径信息无须跨越汇合。显式约束局部化：把 `x>5` 这样的条件在
靠近使用点处再确认一次（若分析器是过程内的、跨不过上游封装），
比全局注释有效。用不可变/终态代替"先声明后赋值"：声明即初始化的
变量根本不进入未初始化分析的视野，一类告警从语法上消失。枚举/标记
判别写成穷尽 switch：每个 case 内 tag 的值被该支条件钉死，常量格
就能消费（22.12.1）。这些改写的共同点：**它们本身就是更好的程序
结构**——为静态分析做的改写与为人类读者做的改写高度重合，这并非
巧合：两者都在降低"读懂当前点需要记住多少上下文"。

### 34.14.3 抑制告警的纪律

确属第三类时，抑制也要守纪律：抑制必须**局部**（只作用于当前行/
函数，而非文件或整个规则）、**可检索**（留下统一标记，grep 能列出
全部抑制点定期复审）、**带理由**（为什么此路径不可达、引用条件或
不变量）。全局关规则是最坏的选择：它连同未来的真实缺陷一起关掉，
而且没有任何复审入口。无理由的局部抑制次之：抑制点会随时间腐烂
——重构后原来的不可达理由可能已不成立，但抑制还在。把抑制当作
"带注释的技术债"管理，而不是"让工具闭嘴"的操作。

### 34.14.4 团队指标：不是零告警

"把告警清零"作为团队目标会诱发错误行为（大面积抑制、提高阈值、
只跑新增代码）。更健康的指标是：每条遗留告警是否可分类、可解释、
有处置人；新增代码的告警是否在评审中处理；同一缺陷模式的复发率
（复发说明改写/接口层面的根因没有修）。在这套指标下，路径敏感这
样的精度升级直接体现为第二类告警的减少——可以用升级前后同一代码
库的告警分类计数来证明分析器改进的价值，而不是凭"感觉更准了"。
本章的两档对照就是这种证明的最小单元：同一个可执行文件，自己给
出 before/after。

### 34.14.5 告警生命周期的四个阶段

一条告警从产生到关闭，经历四个阶段；每个阶段要留下记录。

阶段一，产生：
- 分析器给出节点、规则名、区间原文
- 记录分析版本与程序版本
- 无版本信息的告警无法复盘

阶段二，分诊：
- 工程师按 22.21.3 的回溯确认路径
- 标记为"真实缺陷"或"误报"
- 误报再按十一型标根因

阶段三，处置：
- 真实缺陷：改代码，告警应在下一轮消失
- 误报：优先改写程序或升级机制
- 最后才是局部抑制，且抑制必须写明过期条件

阶段四，复核：
- 定期检查：被抑制的告警，条件是否仍成立
- 机制升级后：抑制能否撤除
- 真实缺陷修复后：有没有同类告警在别处出现

### 34.14.6 团队口径的三个指标

团队层面建议只追三个指标：
- 真实缺陷占比（确认缺陷数 / 总告警数）
- 修复周期（确认到关闭的时间）
- 抑制存量与老化（超过约定期限未复核的抑制数）

为什么不追"告警总数"：
- 总数随代码规模自然增长，不反映质量
- 压总数会诱导无脑抑制
真实缺陷占比直接对应精度，修复周期对应流程，抑制老化对应机制债务。

### 34.14.7 抑制纪律的最小条文

若团队允许抑制，最小条文建议包含：
- 每条抑制写明：规则名、误报根因、复核日期
- 禁止"文件级"大粒度抑制
- 抑制与代码同评审
- 机制升级触发存量抑制重审
条文少而硬，胜过厚而无人执行的规范。

## 34.15 进阶练习（附详解）

以下练习比 22.27 更综合，建议配合纸上推导完成。

**练习 6（规则扩展）**：为区间格补充 `x >= k` 的规则。
详解：`x>=k` 不排除 x=k，真边下界抬到 k（不是 k+1），假边（x<k，
即 x≤k−1）上界压到 k−1。与 `x>k` 的全部差别就是那个 1；实现里最
便宜的做法是把 `>=` 归一化时翻译成 (k-1) 的偏移再走 `>` 的规则，
与 22.4.2 的归一化纪律一致。验证：k=INT_MIN 时真边抬界无效果（x
本就 ≥INT_MIN），规则自然退化，无须特判。

**练习 7（矛盾路径）**：给出程序使精炼在某点产生 ⊥，并手工追踪 join
如何吸收它。
详解：`if (x > 5) { if (x < 3) { output x; } }`：外层真边 x=[6,+inf]，
内层真边再压上界 2，得 lo=6>hi=2=⊥；output 点环境 ⊥。该点对后继
的贡献在 join 中被另一路（若有）吸收；本例内层假边连向汇合点，
join(⊥, [6,+inf])=[6,+inf]，结果与"内层真支不存在"一致。若整个
函数只剩 ⊥ 贡献，函数被判定不可达——这是死代码消除能利用的信息。

**练习 8（assume 翻译）**：把本章边函数方案改写成 CFG 上的 assume
节点方案。
详解：在分支节点 n 与真支首点之间插入节点承载 assume(c)，与假支
首点之间插 assume(¬c)；assume 的传递函数 = 该条件的精炼算子，且其
"入口不满足条件"时出口 ⊥（这还自然给出了不可达路径剪除：本章边
方案里不可行边的 ⊥ 要等 join 才体现，assume 方案在点上直接体现）。
节点总数每条分支边 +1，编号规则相应扩展。两方案对最终 join 的贡献
相同——这是一次保持语义的程序变换，可用"同程序两方案输出逐点
相等"做测试。

**练习 9（常量格协同）**：设计常量传播与边精炼的协同迭代，说明
为什么二者必须在同一轮不动点里、不能各跑一遍。
详解：条件里若有常量变量（`if (flag)` 而 flag 已折叠成 0），精炼可
直接判定整支不可达；反之常量折叠可能依赖"某点只从真边可达"。若
先跑常量到不动点再精炼，常量阶段拿不到分支信息，会把可折叠变量
留成 ⊤，精炼之后常量也不会重算。协同做法（稀疏条件常量传播的
形状）：每轮重算点时先按当前常量事实求条件真假，不可行边不参与
join，再折叠——一个 worklist、两类事实同时流动。这个练习展示：
**两个精度特性拼在一起可能不是简单叠加，而要重新安排信息时序。**

**练习 10（空隙测量）**：写程序统计 join 包络中"两支都不产生"的
整数个数。
详解：对两支区间 A、B（A 在左），空隙 = max(0, B.lo − A.hi − 1)；
22.11.3 的 y 例：A=[-1,-1]、B=[1,1]，空隙 = 1−(−1)−1=1（即 0）。
空隙数是路径不精度的一个可量化指标：在同一程序上打开/关闭精炼，
比较空隙总数，能精确说出精炼为后续 join 赚回了多少值。把精度做成
可数的量，是 22.10 第二轴的落地方式。

**练习 11（嵌套不汇合）**：深层嵌套分支但不汇合时，验证局部精炼
为何足够。
详解：每层条件沿普通边流入下一层（没有 join 稀释），内层点环境是
外层全部精炼的累积；因为每条路径只对应一个真假组合，而笛卡尔
环境逐次裁剪恰好等价于该组合。失败只发生在汇合之后——所以判断
"局部精炼够不够"的快捷问题不是"嵌套多深"，而是"要追问的变量在
上次汇合前还是后被约束"。

**练习 12（除数为表达式）**：除数不是简单变量时，除零判定该怎样
保持 sound？
详解：对整个除数表达式 evalIv，按结果区间判定，而不是只看其中的
变量；如除数 x+y 可能在 x、y 各自不含 0 的情况下组合出 0（x=1,y=
-1）——独立区间的 join 给 [-2,2]，含 0，告警。这再次暴露笛卡尔
域的相关性盲区：部分真实状态里 x+y 永不为 0（若 x、y 相关），分析
无法排除，假阳性由域的形状支付，不由规则支付。

**练习 13（阈值与精炼交互）**：widening 阈值表若不含 1，对本章
`x>0` 类程序的后续精炼有何影响？
详解：widening 只决定循环点状态稳定在什么刻度上；真边精炼固定把
下界抬到 1，即使循环头被放宽到 [0,+inf]（阈值含 0），真支仍得到
[1,+inf]——两层机制独立。若阈值连 0 也不含（如直接 -inf/+inf），
循环头一次跳到 [−inf,+inf]，真边精炼仍然挽救真支，但循环头之后、
分支之外的点更宽。阈值选择影响的是"非分支点"精度，与边精炼互补。

**练习 14（设计 filter 接口）**：按 22.12.3 的接口，为符号格实现
filter，并写出其具体化等式两侧何时严格相等、何时只能近似。
详解：`x>0` 真边：{"-","0"} 被删，右式（具体状态中 x>0）与左式
（x∈{"+"}）恰等；`x!=0` 类型条件（若语法支持）真边删 "0" 也恰等；
而像 x>y 这样的相关条件在单变量符号格上无法表示，filter 只能返回
原环境（最窄的可覆盖元素就是它自身），此时右式是左式的真子集——
接口规则要求"取最窄覆盖"，把"表达不了"显式化，防止暗中断言相等。

**练习 15（综合实验）**：选一个小型开源程序（数百行），用本章
分析器（或同类轻量工具）跑一遍，按 22.14 分类全部告警，再尝试用
22.14.2 的改写消灭第二类告警并复测。
详解：记录三类计数的前后变化；关键观察是改写后**第一类告警不应
增加**——若改写后冒出新缺陷告警，多半说明原写法在掩盖真实问题
（提前返回暴露了此前不可达路径上的缺陷），这本身就是收获。最后
保留一份"改写—告警变化"对照表，它就是 22.14.4 所说的、可拿给团队
看的精度证明，比任何工具宣传都有说服力。

## 34.16 同族的缺陷检查

除零只是一种"操作前必须满足某条件"的缺陷。本节把三种同族检查摆到
一起：它们共享同一个 may 告警骨架与同一个条件消费算子，差别只在
"条件是什么、由什么操作触发"。看清同族结构，就不必为每一种缺陷重
学一台分析器。

### 34.16.1 数组越界：操作点两侧各有一条界

数组访问 `a[i]` 安全当且仅当两条同时成立：

- 下界侧：i ≥ 0
- 上界侧：i < len(a)

一次访问因此产生两个独立的查询，各自走一次"区间是否严格排除违例"。
注意与除零的两处差别。第一，上界不是常数 0，而是另一个值（数组
长度）：长度可能来自 input、malloc 参数、集合大小，需要单独的事实
通道（长度格）或把"i < len_a"整体当作关系谓词——单变量区间里若
len 未知，上界查询永远无法排除违例，这是笛卡尔、非关系域的又一处
税。第二，数组写与读都要查（越界写比读更危险），不能只挂在输出/
算术表达式上；收集器要覆盖赋值目标。

与分支精炼配合时，经典的"先判断再访问"写法被识别：

- `if (i >= 0)` 真边把 i 的下界抬到 0
- `if (len > i)` 真边把 i 的上界压到 len−1（len 已知时）

两条 guard 合起来让访问点无告警；缺任一条，对应一侧告警。这给
22.14.2 的 guard clause 提供了另一个例证：守卫不是写给运行时看的，
它同时是写给分析器的收据。

### 34.16.2 空指针：二值域上的路径推理

空指针解引用检查的域极小：对每个指针变量，事实 ∈

- ⊥：不可达
- N：非空（已判空或来自必返非空的构造）
- ⊤：未知

这是一个两点扁平格，join 规则与常量格同构。它从条件里获益的形状是
`if (p == null)` 与 `if (p != null)`：真/假边把二值钉死。这个分析
最能体现"路径敏感与控制流结构同构"：判空之后的**整个直线路径**上
p 都是 N，直到可能重新赋值；而经过一次没有保护的汇合（一处判空、
一处未判空），p 回到 ⊤，解引用重新告警。与常量格一样，假边
（p≠null 不成立，即 p 可能为 null 也可能非空）在二值域上无法精确
表示"null 与非空之并"以外的东西——它本来就是 ⊤，所以假边不精炼，
规则保守而正确。

### 34.16.3 污点分析：源、清洗器、汇

污点分析回答另一类问题：不可信数据（源，source）能否在未被清洗
（sanitizer）的情况下到达危险操作（汇，sink）。它的事实形状与第 30 章可能未初始化惊人地像——一个变量集合（带污点的变量），赋值
`x = e` 的传递：

- x 先被 kill（赋值覆盖旧污点）
- 若 e 里任何变量带污点，x 重新染污

状态依赖、前向 may，与 19 章是同一族传递函数。路径敏感在污点分析里
扮演关键角色的场景是：**清洗发生在某个分支里**。

- `if (x 看起来合法) { x = 清洗(x); sink(x); }`：沿真边，清洗后污点
  被 kill，sink 安全。
- 若清洗与 sink 分居不同路径、或汇合后才 sink，join 会把"已清洗"与
  "未清洗"合并，污点保守地保留——告警。

这与 22.11.3 的相关性问题同源：分析器需要知道"到达 sink 的那条路径
是否经过清洗点"。局部边精炼只看当前分支的条件，不记忆历史调用/
清洗点；要给污点分析完整的路径（与上下文）分辨，需要 IFDS 一类
框架——那是第 46 章的内容，届时会看到本章/19 章的污点传递如何被
精确地搬进超级图。

### 34.16.4 统一骨架与一张对照表

四种检查并排：

| 检查 | 触发操作 | 安全条件 | 主要域 |
|---|---|---|---|
| 除零 | `/` | 除数 ≠ 0 | 区间 |
| 越界 | 下标访问 | 0 ≤ i < len | 区间+长度 |
| 空指针 | 解引用 | p ≠ null | 两点扁平 |
| 污点 | 汇操作 | 路径经过清洗 | 变量集合 |

共享骨架有三步：先收集触发操作，然后在点环境里求值"安全条件的否定
是否被排除"，未排除即告警。路径精炼在四者里都只做一件事：把分支
条件翻译成安全条件一侧的界。记住这张表，将来遇到新的检查（整数
溢出、use-after-free、格式化字符串），先问三个问题——触发点是谁、
安全条件的抽象形状是什么、哪种分支写法能把条件送到分析器——往往
就能把它归入已有框架，而不是另起炉灶。

## 34.17 精炼算子的逐行走读

22.4 给了规则的数学，本节对照 widen.cpp 里 parseCond 与 refineOnBranch
的真实代码走一遍，看规则怎样在 C++ 里落地、以及实现多做了哪些防
边界的处理。

### 34.17.1 parseCond：两次尝试辨认两侧

parseCond 开头假定形状"左变量、右常数"：

- 先把 b->l 转 VarRef、b->r 转 IntLit
- 两个转换只要有一个失败，就交换再试一次：右侧找变量、左侧找常数

两次尝试都失败，f.ok 保持 false 返回——上层看到不可识别的条件，
refineOnBranch 原样返回环境。这一行是**整个精炼机制的安全门**：任何
变量间比较、嵌套布尔、算术当条件，都在此被安静地放行而非误判。
对教学分析器，"不认识就不动"永远比"猜一个"安全。

识别成功后按运算符分派：

- Gt：种类取 Cgt 还是 Clt，取决于变量究竟在左侧还是右侧——
  `b->l.get() == x` 比较的是指针身份。这里要注意 x 在交换分支里可能
  指向 b->r；同一个 Gt 算子因此编码了 `x>k` 与 `k>x` 两种语法，靠
  指针比对区分，而不是靠再写一个 case。
- Eq：Ceq，两侧朝向对相等无意义，无须区分。
- 其余算子（Add 之类出现在条件位置）落入 default，ok 保持 false。

### 34.17.2 refineOnBranch：入口的三个早退

真正施加规则前有三个早退，各自值得一句。

- `if (!f.ok) return env`：接 parseCond 的安全门。
- `find(f.var)` 失败：环境里根本没有这个变量。在我们的环境约定里
  缺键即 ⊥；⊥ 变量精炼后还是 ⊥，没有可改的东西。
- `v.lo > v.hi`：变量区间已是 ⊥，同理。

三个早退合起来保证下面的 switch 只处理"有真实区间可裁剪"的情形；
这是把 ⊥ 的吸收逻辑集中在入口，而不是在每条规则里重复判断。

### 34.17.3 Cgt/Clt 分支与哨兵防护

Cgt 真边：`v.lo = max(v.lo, f.k+1)`，与 22.4.1 一字不差。代码多了
一个三元防护 `f.k == INT_MAX ? INT_MAX : f.k+1`——为什么需要？
因为 k+1 在 k=INT_MAX 时数学上溢出 int。这种条件实际不可满足
（没有 int 严格大于 INT_MAX），本该得 ⊥；实现选择让下界保持
INT_MAX（配合上界，区间未必矛盾），是一个宽松的退化处理。关键只
是：**绝不能让 k+1 以 int 补码溢出回绕成 INT_MIN**，那会把下界一下
打到 -inf，soundness 直接破产。三元表达式用哨兵本身挡住溢出。

Cgt 假边：`v.hi = min(v.hi, f.k)`，无须防护——f.k 本身是合法 int。

Clt 两支是镜像：真边压上界，`f.k-1` 在 k=INT_MIN 时有对称的下溢
风险，用 INT_MIN 本身挡住；假边抬下界。对照阅读可以验证：Clt 的
全部规则就是 Cgt 交换真假、交换上下界——归一化让"对偶"只有一份
代码。

### 34.17.4 Ceq：钉死、矛盾得 ⊥

Ceq 真边先看 k 是否落在当前区间内：

- `f.k < v.lo || f.k > v.hi`：矛盾。当前状态下 x 不可能等于 k，这条
  边不可达，区间写成 `Iv{1,0}`（⊥ 的标准编码）。
- 否则钉成 [k,k]。

假边整个不处理（switch 里没有 else 分支动作），即 22.4.3 的保守
选择。注意矛盾判定发生在钉死**之前**：若先无脑钉成 [k,k]，会把
"x∈[6,+inf] 却要求 x==5"的不可达边伪装成"x=5 的可达点"，沿边
传播出一个根本不会发生的状态——下游可能据此折叠出错误的常量。
**不可达信息（⊥）与确定信息（点区间）在抽象语义里截然相反，尽管
它们在代码里都只是一个小 Iv。** 顺序差一行，一个 sound 一个不 sound。

### 34.17.5 写回：环境按值修改

函数末尾 `it->second = v` 直接修改 map 里的区间（it 来自 find，指向
out 中的副本），返回 out。因为 out 一开始复制自 env，只有目标变量
被改，其余变量共享同一个 Iv 值——小对象，复制代价可忽略。整段
函数没有对 ⊤/⊥ 之外的特殊值做任何假设，也没有触碰别的变量，这让
"逐变量独立裁剪"的性质在代码层面可见：若将来要引入相关条件，
改动面被限制在这一个函数内。

## 34.18 综合走查：一段输入校验程序

本节把本章所有要素放进一个稍长的程序走一遍：input、分支守卫、
除法、汇合、污点味的保守合并。程序没有收录进示例目录（比教学
快照长），你可以自行键入并用分析器验证；走查的每一步都给出两档
预测。

先看程序骨架（伪 TIP，略去 var 声明）：

```
main() {
    x = input;
    if (x > 0) {
        if (100 > x) {
            y = 100 / x;
            output y;
        } else {
            output 0 - 1;
        }
    } else {
        output 0;
    }
    return 0;
}
```

### 34.18.1 追踪到达除法点的路径

问：`100/x` 安全吗？沿外层真边，x 被精炼成 [1,+inf]；沿内层真边
（条件 100>x，即 x<100），x 再压成 [1,99]。除数区间 [1,99]：

- 不含 0（lo=1）→ 无除零告警
- 商：分子 100，除数 {1,99}，组合 100/1=100、100/99=1，包络
  [1,100]

输出预测 `y in [1,100]`。注意真实程序里 x 是 1..99，商确实遍历 1..100
（x=1 时 100），预测与真实集合恰好相等——两层精炼叠加，在这个点
零过近似。

### 34.18.2 三个输出点各自的归属

三个 output 分居三条互不汇合的支（汇合发生在全部 output 之后）：

- 内层真支：output y，[1,100]
- 内层假支（x≥100）：output −1，[-1,-1]
- 外层假支（x≤0）：output 0，[0,0]

路径不敏感基线则对三个点一视同仁：每个点看到的 x 都是全区间。
第一个点：除数含 0 → 告警，y 全区间。另外两个点的输出是常数字面量
（−1、0），预测仍是精确的点区间——**分支精炼失效不等于所有精度
失效**：不依赖路径信息的表达式（常量、纯字面运算）照常精确。这个
对照提醒：读两档输出时要逐点比较，不能用"开了/没开"给整份报告
贴一个精度标签。

### 34.18.3 如果内层是一次函数调用

把内层真支改成 `y = clean(100/x)` 之类的调用（clean 是直线纯函数），
本章单过程分析会在调用点把 y 写成什么？按 22 章求解器（不含第 44 章设施），CallE 在 evalIv 里保守取全区间——前面章节的设计里调用就
是"外部世界"，路径再清晰也跨不过去。这把第 44 章的动机演得很具体：
用户已经用两层条件保证除数安全，但信息在函数边界断了。过程间分析
（第 44 章的内联展开、第 45 章的调用串）要解决的正是"把入口条件
连同实参一起送过边界"。五章读下来，问题是逐层暴露的：格→不动点→
格的高度→边→函数边界→上下文，每一步都由一个最小的程序形状逼出。

## 34.19 术语对照与历史脉络

### 34.19.1 容易混的术语

- **路径敏感（path sensitive）**：区分到达同一点的不同路径条件。
- **流敏感（flow sensitive）**：区分语句先后，点前后事实不同。
- **上下文敏感（context sensitive）**：区分同一函数的不同调用环境
  （第 45 章）。
- **关系分析（relational）**：抽象状态表达变量间关联；其反面是
  独立属性（independent attribute）/笛卡尔域。
- **may / must**：may 报告"可能成立"（∪，宁多报），must 报告
  "必然成立"（∩，条件更严）。
- **假阳性 / 假阴性**：误报 / 漏报；静态分析里漏报严重得多。
- **具体化 γ / 抽象 α**：抽象集合 ↔ 具体状态集合的双向映射。
- **assume / guard**：把条件作为"此处必须成立"的伪语句或边条件。

### 34.19.2 这些思想从哪来

边条件即"条件概率式的状态收窄"，在数据流分析的经典时期（1970s）
就以"沿分支传播断言"的形式存在；抽象解释（Cousot & Cousot, 1977）
把 assume/精炼纳入统一的格与单调算子框架，使其可靠性有了形式化
依据；谓词抽象（Graf & Saïdi, 1997）把"一组谓词的布尔向量"做成通用
抽象域，随后与 SMT、CEGAR 合流，形成软件模型验证产品线（SLAM、
BLAST 一类）；轻量级 IDE 静态分析（Clang Static Analyzer、Infer 的
AL/BI 抽象、CodeQL 的数据流）则把本章这种局部/超图级别的精炼工程化，
让代价随代码规模近线性。读这条脉络时值得抓的主线只有一条：**更
强的表达力一直与更重的计算成对出现，工程史是在为"80% 的问题找
最轻的充分机制"，而不是在追求最强分析器。**

### 34.19.3 spa 与本书的位置

spa 的立场是"用尽可能简单的 TIP 把经典思想逐一落地"，路径敏感在
其中是工具性的一节而非独立体系；本章沿用这一立场，把它放大成
"一个开关、两档输出、一份可靠性论证"，并显式补上谓词抽象与告警
治理两块 spa 未展开的实践内容。换句话说，本章的阅读目标不是记住
三种条件规则（它们查得到），而是建立"精度轴、可靠性轴、代价轴"
三分的判断力——这种判断力在文献和工具之间迁移时才是真正带走的
东西。

## 34.21 worklist 逐轮账本

前面的章节给了规则与结论，这一节给"过程"：把求解器在两个示例程序上的
每一轮动作，按账本逐行列出。读这一节不需要看代码——账本里出现的每个
概念都在前文定义过。

先约定账本的记法。
- 一轮 = 从队列取出一个项目，处理它，可能放回若干项目。
- 项目记为 (函数, 节点)：本章是过程内单函数分析，函数总是 main。
- 状态记为 节点: 变量=区间；未出现的变量沿用旧值。
- CHG 表示输出状态与旧状态不同，后继入队。
- SAME 表示无变化，不入队。
- 边精炼记为 →T（真边）或 →F（假边）。

### 34.21.1 branch.tip 的账本

程序回顾：`x = input; if (x > 0) output x else output 0 - x`。
CFG 节点：
- 1 入口
- 2 x = input
- 3 条件 (x > 0)
- 4 output x（真支）
- 5 output 0 - x（假支）

第一轮，项目 (main,1)：
- 入口环境为空
- 节点 1 无动作
- CHG，后继 2 入队

第二轮，项目 (main,2)：
- input 抽象为全区间
- x = [-inf,+inf]
- CHG，后继 3 入队

第三轮，项目 (main,3)：
- 条件点本身不改环境
- 两条出边各带一个精炼
- →T：x 抬下界为 1，得 [1,+inf]
- →F：x 压上界为 0，得 [-inf,0]
- 节点 4、5 分别带着精炼后的环境入队

第四轮，项目 (main,4)：
- 环境 x=[1,+inf]
- 求值 output 的表达式 x：[1,+inf]
- CHG，无后继

第五轮，项目 (main,5)：
- 环境 x=[-inf,0]
- 求值 0 - x
- 下界：0 − 0 = 0
- 上界：0 − (-inf) = +inf（饱和哨兵）
- 结果 [0,+inf]
- CHG，无后继

队列空，停机。

把账本与 expected/output.txt 对照：
- 节点 4 的精炼行是 x [1,+inf]
- 节点 5 的表达式行是 (- 0 x) [0,+inf]
- 两处都没有除零告警
三行预言全部落在输出文件里，逐字对应。

再看 FLOW 档（关掉开关）在同一程序上的分叉：
- 第三轮条件点不精炼
- →T、→F 都带着 x=[-inf,+inf]
- 节点 4 输出全区间
- 节点 5：0−x 对全区间求值，包络 [-2147483647,+inf]
- 这就是输出文件里 FLOW 段那两行的来历
两档唯一的差别发生在第三轮，却让两个输出点同时变宽——
边条件的信息沿各自分支一路传到叶子。

### 34.21.2 div.tip 的账本

程序回顾：`x = input; if (x > 5) output 100 / x`。
CFG 节点：
- 1 入口
- 2 x = input
- 3 条件 (x > 5)
- 4 output 100 / x（真支）
- 假支无语句，直接退出

前两轮与 branch.tip 相同，从第三轮开始。

第三轮，项目 (main,3)：
- →T：x 下界抬到 6，得 [6,+inf]
- →F：x 上界压到 5
- 节点 4 入队（真支）；假支无语句节点

第四轮，项目 (main,4)：
- 环境 x=[6,+inf]
- 先处理除数检查
- 除数区间 [6,+inf] 不含 0
- 无告警
- 再求 100 / x
- 下界：100 / +inf → 0（向零截断的商，哨兵上界推出 0）
- 上界：100 / 6 = 16
- 结果 [0,16]
- CHG

队列空，停机。

FLOW 档的对照：
- →T 不精炼，节点 4 拿到 x=[-inf,+inf]
- 除数区间含 0：产生一条告警
- 求值 100 / x：除数含 0，结果直接给全区间
- 输出文件 FLOW 段的告警行与全区间行由此而来

同一个程序，两档给出的缺陷结论相反：
- FLOW："可能除零"
- REFINED："不可能除零"
可靠性上并不矛盾：
- FLOW 是报出一个真实存在的可能（输入若为 0，具体程序确实崩溃，
  但那条路径走的是假支，不会到达除法！）

等一下——这里必须说得更精确。
具体语义里，x=0 时条件 x>5 为假，除法语句根本不执行。
FLOW 档在节点 4 认为 x 可能是 0，是因为它把"条件为假时的状态"
也算进了"节点 4 的入口状态"。这是一次误报，不是漏报：
- 不会漏掉任何真实崩溃
- 但工程师按这条告警去查代码，会发现条件已经挡住了
这正是"流敏感但不路径敏感"的标准画像，也是本章存在的理由。

### 34.21.3 账本的三个用法

用法一，预言输出顺序。
队列是 FIFO，节点编号小的先处理；expected 文件的行序与此一致。
当你自己的实现输出顺序不同，先查队列策略，再查编号。

用法二，定位"多余的一轮"。
若某轮处理结果是 SAME，说明状态此前已被另一条路径算过。
SAME 轮多不等于错，但它是优化信号：前驱 join 顺序、入队判重
都可能让 SAME 轮膨胀。

用法三，向他人解释一条告警。
从告警所在节点回溯账本：
- 找到该节点入口环境第一次成形的那一轮
- 再沿精炼标记找到给出界的那条边
- 若界来自 JOIN/WIDEN，继续向前驱追溯
直到能指着某一轮说："区间在这里变宽，之后再没收窄过。"
能完成这个回溯，就真正读懂了分析。

## 34.22 六个微型程序的逐点走读

这一节给六个每个只有三五行的小程序，每个都逐点推完。它们覆盖
规则组合中容易含糊的角落。建议先自己推，再对答案。

### 34.22.1 双侧夹逼

程序：`x = input; if (x > 0) { if (x < 10) { output x; } }`
推导：
- 外层真边：x=[1,+inf]
- 内层条件 Clt，真边上界压到 9
- x=[1,9]
- 输出 [1,9]
要点：两个方向的规则在同一个区间上叠合，区间第一次变得"双侧有界"。
对比：若内层写成 x<0，则叠合后 lo=1>hi=−1，⊥，死分支。

### 34.22.2 先赋后判

程序：`x = input; x = 5; if (x > 0) { output x; }`
推导：
- input 的全区间在第二次赋值时被覆盖
- x=[5,5]
- 真边抬下界到 1，与 [5,5] 取 max 后仍 [5,5]
- 输出 5
要点：精炼相对已精确的区间是幂等的；规则不制造新信息，只裁剪。
常见误判：以为精炼后会变成 [1,5]——下界只能抬，不能在中间切。

### 34.22.3 假支除法

程序：`x = input; if (x == 0) { } else { output 100 / x; }`
推导：
- 真边：x=[0,0]
- 假边：本章不实现"补条件"（disequality 无法用区间表达）
- 假支环境 x=[-inf,+inf]
- 除数含 0：告警
- 求值给全区间
讨论：工程师知道假支里 x≠0，但区间域说不出口。
要消掉这条误报，可选：
- 谓词抽象（第 23 章方向）：把 x≠0 作为谓词跟踪
- 改写程序：把除法挪进真支并调换条件方向
要点：机制选择与代码改写，是治理同一问题的两条路。

### 34.22.4 汇合后使用

程序：
`x = input; if (x > 0) { x = x; } output x;`
（真支只有自赋值，输出在汇合后）
推导：
- 真边环境 [1,+inf]，自赋值不变
- 假边环境 [-inf,0]
- 汇合：envelope = [-inf,+inf]
- 输出全区间
要点：两支的界在汇合点取包络，恰好复原为无条件状态；
这不是"分析白做了"，而是信息被诚实地拼回——汇合后问分支归属，
任何非析取域都答不出。

### 34.22.5 算术后再判

程序：`x = input; y = x + 1; if (y > 0) { output x; }`
推导：
- x 全区间
- y = x+1：独立求值仍全区间
- 条件精炼作用在 y 上：y=[1,+inf]
- x 不被裁剪！
- 输出 x=[-inf,+inf]
要点：边精炼只裁剪条件中出现的那个变量。
y>0 逻辑上等价于 x>−1，但笛卡尔域不会把界从 y 转回 x。
这是与 22.22.3 并列的第二类"看着该精确、实际不精确"：
- 22.22.3 是补条件表达不出
- 22.22.5 是变量间关系传不回
两者都要关系域才能根治。

### 34.22.6 常量条件

程序：`x = input; if (5 > 3) { output x; }`
推导：
- parseCond 成功识别，k=3，变量名无意义（左端是字面量）
- 教学实现只接受"变量与常量比较"的形状
- 两端都是常量：parseCond 返回失败，放弃精炼
- 但具体语义里条件恒真，假支是死代码
- 分析不裁边，两支都保留
- 输出 x 全区间
要点：常量条件的死分支消除属于"常量传播 + 不可达代码"，
不是路径精炼的职责；把它留给前面的章节，机制边界才清晰。

### 34.22.7 六题汇总

把六个程序按"为什么精确 / 为什么不精确"归档：
- 22.22.1 精确：双规则叠合
- 22.22.2 精确：赋值已给常量，精炼幂等
- 22.22.3 不精确：补条件表达不出
- 22.22.4 不精确：汇合拼回
- 22.22.5 不精确：关系传不回
- 22.22.6 不精确：职责在别的机制
六条里只有两条是"规则不够强"，其余四条是抽象域或架构边界。
精度问题的诊断，大多数时间花在分类，而不是加规则。

### 34.22.8 第二批：五个组合形态

第二批五个小程序，专门考察规则与赋值、汇合、循环的组合。

程序七，否定条件改写：
`x = input; if (!(x > 5)) { output x; }`
推导：
- 前端不保证把 !(x>5) 归一成 x≤5
- parseCond 遇到一元否定的复合式，识别失败
- 不精炼，x 全区间
- 输出全区间
要点：规则的形状匹配是语法层面的；等价的数学写法不自动受益。
为分析器改写，这里意味着去掉否定、翻转分支体。

程序八，条件后覆盖：
`x = input; if (x > 5) { x = 0; } output x;`
推导：
- 真边 x=[6,+inf]，随即被赋值覆盖为 [0,0]
- 假边 x=[-inf,5]
- 汇合：[0,0] 与 [-inf,5] 的包络 = [-inf,5]
- 输出 [-inf,5]
要点：精炼信息可以被下游赋值"合法擦除"；擦除后 join 的包络
不包含 +inf，因为真支的 +inf 已随覆盖消失。

程序九，两路赋常量：
`x = input; if (x > 5) { x = 1; } else { x = 2; } output x;`
推导：
- 真支 [1,1]，假支 [2,2]
- 包络 [1,2]
- 输出 [1,2]
要点：笛卡尔域不知道"只有两种可能"，它看到连续区间 [1,2]；
若下游写 `if (x == 1) ... else if (x == 2) ...` 分析会认为
x==1 与 x==2 之外没有分支，但也不会排除任何真实状态。

程序十，自汇合循环出口：
`x = 0; while (x < 3) { x = x + 1; } output x;`
推导：
- 循环点 widening 后 x=[0,+inf]
- 假边（条件为假）：Clt 假边抬下界到 3
- 出口 x=[3,+inf]
讨论：具体世界答案恰为 3，分析给 [3,+inf]，上界宽。
这是 widening 的代价：上界一旦跳到 +inf，本章不再 narrowing。
21 章的 narrowing 能把上界收回到 3；两章机制叠加才到单点。

程序十一，两路 input：
`x = input; y = input; if (x > 0) { if (y > 0) { output x; } }`
推导：
- 外层裁 x，内层裁 y
- 输出 x=[1,+inf]
要点：嵌套条件分别裁剪不同变量，环境作为整体逐边收窄；
变量虽独立，裁剪可叠加——笛卡尔域在这个方向上不吃亏。

第二批归档：
- 程序七不精确：语法形状
- 程序八精确（部分）：覆盖改变包络
- 程序九不精确：离散可能被连续化
- 程序十不精确：widening 代价
- 程序十一精确：多变量裁剪可叠加
加上第一批六题，诊断分类已有十一型；新遇到的误报先尝试归入，
归入不了再考虑新机制。

### 34.22.9 分类使用建议

面对一个误报，分类流程：
1. 写出 5–15 行最小程序。
2. 手工标出每个点的区间。
3. 找到"第一次变宽"的位置。
4. 对照十一型命名根因。
5. 根因属于"表达力"：换域或谓词抽象。
6. 根因属于"形状"：改写程序条件。
7. 根因属于"代价"（widening）：加 narrowing。
三条出口对应三类不同的工作，不要混用。

## 34.23 A/B 精度对照实验

这一节讲怎样把"精炼档更精确"从口头印象变成可重复的实验。
本章的 main 已经内置两档输出；实验方法是围绕它建立记录规范。

### 34.23.1 实验要控制的变量

一次有效的 A/B 对照，两档之间只能差一个开关：
- 同一个程序文件
- 同一套前端、同一个 CFG
- 同一个格与同一套算术
- 唯一差别：边精炼是否执行
本章代码正是这样组织的：FLOW/REFINED 共用求解器主循环。

不可接受的对照：
- A 档用常量折叠、B 档不用
- A 档与 B 档的 widening 阈值不同
- A 档跑老版本二进制
这些都会让"差别来自路径敏感"失效。

### 34.23.2 记录什么

每个程序、每一档，记录四类数据。
第一类，点状态：每个节点每个变量的区间。
第二类，缺陷告警：条数、节点、区间原文。
第三类，输出预言：每个 output 的区间。
第四类，轮数与状态更新次数：代价口径。

记录形式建议为一张表，一行一个 (程序, 档)：
- 程序名
- 档（FLOW/REFINED）
- 严格更窄的点数
- 告警数
- 全区间输出数
- 更新次数

### 34.23.3 判定规则

"精炼档在程序 P 上严格更精确"的判定，按顺序检查：
1. 每个点的区间：精炼档 ⊑ 基线档（逐点包含核对）
2. 至少一处严格包含
3. 两档都通过 soundness 经验测试（第 30 章设施）
4. 告警数差只允许减少（精炼消误报），不允许"新增一条
   基线档没有的告警"——新增告警意味着基线档漏报，或精炼档误报，
   必须查清再下结论

四条全过，结论才可写入报告。

### 34.23.4 本章两程序的实验结果

branch.tip：
- 严格更窄的点：节点 4、节点 5（2 处）
- 告警数：两档均 0
- 全区间输出数：FLOW 1 → REFINED 0
- 判定：严格更精确

div.tip：
- 严格更窄的点：节点 4（1 处）
- 告警数：FLOW 1 → REFINED 0
- 全区间输出数：FLOW 1 → REFINED 0
- 判定：严格更精确，且消去一条误报

### 34.23.5 反例库的维护方法

实验不只跑"设计好的程序"。长期维护一个反例库：
- 每次发现一条误报，把最小程序入库
- 每次升级机制（如新格、新规则），全库重跑
- 入库程序必须小到能手工推完（5–15 行）
- 每条入库记录写明：误报现象、根因分类（对应 22.22.7 六类）

反例库与回归测试的差别：
- 回归测试守护"别改坏"
- 反例库记录"本来就不精确的地方"，是机制选型的档案

## 34.24 端点、哨兵与饱和：二十条事实核对

区间分析最容易在端点上含糊。这一节把需要钉死的事实列成核对清单，
每条都可以在前面章节或配套代码里找到依据。建议逐条自证。

1. INT_MIN 用作 -inf 的哨兵，INT_MAX 用作 +inf 的哨兵。
2. 哨兵是机器整数，不是数学无穷；算术在哨兵处饱和而非溢出。
3. lo > hi 表示 ⊥，与哨兵无关：[5,3] 也是 ⊥。
4. ⊥ 与任何区间 join，结果是那个区间（⊥ 是吸收于 join 的底）。
5. 全区间 [INT_MIN,INT_MAX] 是顶，join 不动它。
6. 单点 [k,k] 表示恰好 k，不是"大约 k"。
7. Cgt 真边把下界抬到 k+1，不是 k：严格不等号。
8. Cgt 假边把上界压到 k：x≤k。
9. Clt 真边把上界压到 k−1。
10. Clt 假边把下界抬到 k。
11. Ceq 真边钉成 [k,k]，仅当 k 在原区间内；否则得 ⊥。
12. Ceq 假边本章不精炼（补条件区间域表达不出）。
13. 精炼顺序：先 join 前驱，再精炼当前边，最后传后继。
14. 减法 0−x 对 [-inf,0] 求值：上界饱和到 +inf。
15. 0 − INT_MIN 在补码机上本会溢出；实现用饱和避开，落 INT_MAX。
16. INT_MAX 同时是 +inf 哨兵，所以输出把饱和结果印成 +inf。
17. 除法遇含 0 除数：直接给全区间并报缺陷，不做逐端点商。
18. 除法除数确定不含 0：对四个端点组合的商取包络。
19. 向零截断：正商向下取整、负商向上取整；端点商必须逐符号处理。
20. widening 与精炼可以共存：循环点先 ∇ 稳定，出循环假边再裁剪。

使用方法：
- 改代码前后各核对一遍；任何一条答不出依据，先回到对应章节。
- 第 11、12 条最容易在"顺手增强一下"时被破坏——给 Ceq 假边
  写一个"区间减去一点"的伪规则，会引入不可达的具体状态，破坏 soundness。
- 第 13 条是接线顺序，22.6 专门讨论；顺序反了会在汇合点
  把刚裁剪的信息重新 join 宽。

### 34.24.1 第十五、十六条的逐步推演

第十五条说：`0 − INT_MIN` 在补码机上本会溢出，实现用饱和避开。
这一小节把这件事推到每一步。

先看补码算术的事实：
- INT_MIN = −2147483648
- 表达式 0 − INT_MIN 的数学结果是 +2147483648
- 32 位补码能表示的最大正数是 INT_MAX = 2147483647
- 结果超出 1，硬件上表现为溢出，回绕成 INT_MIN

若分析直接调用机器的减法会怎样：
- 端点参与运算，拿到一个"负"的回绕值
- 区间的端点被污染
- 之后所有包络都可能包含错误的界
- 错误沿 join 传播到整个程序
一次端点污染，足以让全程序的预言失效。

实现的选择是饱和算术：
- 减法先在更宽的宽度上做概念性判断（或显式检查操作数）
- 一旦结果越过 INT_MAX，就钉在 INT_MAX
- 越过 INT_MIN，钉在 INT_MIN
- 对 0 − INT_MIN：钉在 INT_MAX

为什么钉在 INT_MAX 是可靠的：
- INT_MAX 在分析里同时充当 +inf 哨兵
- 分析语义中，INT_MAX 不读成"恰好 2147483647"
- 它读成"任何大到没有有限上界的值"
- 真实结果 +2147483648 确实属于"+inf 一侧"的具体化集合
- 所以把它归入 INT_MAX 端点，没有排除任何真实状态

打印阶段再把这层语义显式化：
- 端点等于 INT_MAX，印成 `+inf`
- 端点等于 INT_MIN，印成 `-inf`
- 其他值印十进制原文
于是 expected 文件里看到的 `(- 0 x) [0,+inf]`，其 `+inf`
经历了：饱和 → 哨兵 → 打印符号，三步，每步都有据可依。

反过来核对第十六条：饱和落在 INT_MAX，所以印 +inf 是对的，
不是"打印器碰巧这么写"。若有一天打印器把 INT_MAX 印成数字，
输出文件的语义反而变窄——那是回归，不是改进。

### 34.24.2 除法端点商的四个组合

除数确定不含 0 时，除法对端点组合求商再取包络。这里把四个组
合逐一列出，并说明为什么只查端点就够。

设被除数 [nlo, nhi]，除数 [dlo, dhi]，均有限且除数不含 0。
四个候选商：
- q1 = nlo / dlo
- q2 = nlo / dhi
- q3 = nhi / dlo
- q4 = nhi / dhi
区间下界 = 四个商里最小的，上界 = 最大的。

为什么连续函数在区间上的极值落在端点：
- 固定除数，商随被除数单调
- 固定被除数，除函数在"全正"或"全负"区间内单调
- 除数不过 0，区间内符号一致
- 所以极值必在端点取到
单调性把"逐点求商"压缩成四个点。

向零截断带来的细节：
- C++ 的整数除法向零截断
- 正数除以正数：商向下取整
- 负数除以正数：商向上取整（向零）
- 因为符号一致，四个候选都用同一条机器除法即可
- 不能先套数学 floor：那会与真实运行差 1

符号一致的两种情形分别看：
- 除数全正 [dlo,dhi]，dlo≥1
- 除数全负 [dlo,dhi]，dhi≤−1
两种都不过 0，规则相同；不需要为负除数单写分支。

一个具体例子，100 / [6,+inf]：
- +inf 参与的商：100 / 极大数 → 0（截断后）
- 100 / 6 = 16
- 候选 {0, 16}，包络 [0,16]
- 这是 div.tip 精炼档的输出

注意 0 出现在结果里不表示"真的除出了 0"：
- 100 除以任何有限除数都不是 0
- 0 是 +inf 端点推出的极限界
- 它表达"商可以任意接近 0"
具体运行的值始终落在 [0,16] 的具体化集合内，可靠。

### 34.24.3 三种特殊区间的判定流程

拿到一个 Iv，判定它是底、单点还是顶，按固定顺序走：
1. 先看 lo > hi：是则为 ⊥，立即返回。
2. 再看 lo == hi：是则为单点 [k,k]。
3. 再看 lo == INT_MIN 且 hi == INT_MAX：是则为顶。
4. 否则为普通区间。

顺序不能换：
- 若先比顶再比底，损坏的区间 [INT_MAX, INT_MIN] 会被误读
- 若先比单点，[INT_MIN,INT_MIN] 这类合法单点没有问题，
  但 [INT_MAX,INT_MIN+1] 这种损坏值会绕过底检查吗？
  lo=INT_MAX > hi=INT_MIN+1，仍是底——所以第一条必须最先。

底的来源有两类：
- 矛盾条件裁剪（如 x=[5,5] 走 x>10 真边）
- join 不应产生底；若 join 出底，说明 join 实现有误
顶的来源：
- input
- 含 0 除数的除法
- widening 跳变
- 矛盾信息拼合后的包络（如 [-inf,0] 与 [1,+inf] 给全区间？
  不——那是 [-inf,+inf]，两支相邻，恰为顶）

单点的来源：
- 字面量赋值
- Ceq 真边
- 常量折叠
单点最"硬"，也最容易让人过度自信：它仍然需要 soundness 测试背书。

### 34.24.4 哨兵的读法与写法

读输出文件时，遇到 inf，按下面的顺序理解：
1. 它不是具体的机器数。
2. 它表示"这个方向上没有可用的有限界"。
3. 界的缺失来自 widening、饱和或 input，三者之一。
4. 不表示"值真的是无穷"——TIP 的整数没有无穷。

写涉及端点的代码时，三条纪律：
- 任何算术都不允许让哨兵参与普通运算后落回有限值
  （inf 一旦出现，单调过程中不应再"收回"为数字）
- 需要收回界，走 narrowing 或边精炼的显式路径
- 哨兵相等用 INT_MAX/INT_MIN 常量比较，不用数值范围猜测

一个反例帮助记忆：
- 坏写法：INT_MAX + 1 依赖机器回绕
- 结果：INT_MIN，区间瞬间翻转，lo>hi 变 ⊥
- 一个"顶"被算成了"底"，语义完全颠倒
饱和算术存在的首要理由，就是防止这种颠倒。

## 34.25 追加问答十五则

**问：为什么不在 join 的时候保留"哪条支来的"标签？**
那就是析取环境了。标签数量随分支数增长，本质上是在复制路径；
本章保持笛卡尔域，信息在汇合点有意地丢失。

**问：条件里有两个变量，如 x < y，为什么直接放弃？**
精炼需要把一个自由变量钉到常量界上。x<y 两边都自由，任何单点
裁剪都不成立。要利用它，需要差界矩阵这类关系域。

**问：放弃精炼会不会漏掉真实缺陷？**
不会。放弃意味着保持更宽的状态，宽状态只会多报、不会漏报；
漏报只可能来自"错误地裁窄"，而放弃从不裁窄。

**问：循环里做边精炼，为什么还需要 widening？**
边精炼只在条件点裁剪，循环回边带来的单调增长仍可能永不收敛。
widening 保证有限步稳定；出循环的假边再把宽区间压回来。

**问：widening 之后信息被放宽，精炼的信息会不会也丢了？**
在循环点上可能丢（∇ 作用于 join 之后）；离开循环的假边重新裁剪，
把条件信息补回到出口状态。这是 22.24 第 20 条事实。

**问：能不能对每个函数单独开关路径敏感？**
可以，而且工程上常见：热点模块开、其余关。本章过程内实现里开关
是全局的；分模块开关需要把档位写进分析配置，并在跨函数调用时
明确"精度不自动传递"。

**问：告警在精炼档消失，能直接删告警规则吗？**
不能。消失是因为区间窄了，不是规则不需要了。规则保持不变，
在别的程序上它仍会报；删规则等于全局放弃这一类检查。

**问：怎样向用户解释"这里可能除零，但其实条件挡住了"？**
用 22.21.2 的回溯：指出 FLOW 档把假支状态算进了除法点入口，
并展示 REFINED 档该点除数区间不含 0。证据是区间，不是直觉。

**问：路径敏感会让分析变慢多少？**
本章实现里状态空间不增长（键不变，只是值变窄），每轮多一次
精炼调用；轮数通常持平或更少（更窄的状态产生更少的更新）。
真正昂贵的路径敏感（谓词抽象、析取域）才会涨状态数。

**问：为什么 Ceq 假边不能把区间"挖个洞"？**
区间是凸形状，挖洞后变成两段，不再是区间。要表示它需要区间集，
而 join 两个区间集可能继续膨胀——这是在换一个更重的域。

**问：开关应该默认开还是默认关？**
默认开：它不增加状态空间，只改善精度。默认关的情形通常是
保守迁移期（新机制先观察），稳定后切默认。

**问：分析能证明一段代码"一定执行"吗？**
能以 ⊥ 的反面形式表达：若某点在分析中不是 ⊥，只说明"分析没发现
不可达"，不等于一定可达。从"没发现矛盾"推"一定可达"是逻辑错误。

**问：为什么输出预测有时恰好是具体值，却仍标成区间 [k,k]？**
单点区间与常量在表示上统一；标成 [k,k] 保持打印与格运算一致，
也避免为"我确信"引入第二套语义。确信度由 soundness 测试背书。

**问：多个条件用 && 连写，分析几次？**
前端会把它当作一个条件表达式；parseCond 只识别单个比较，复合
条件放弃精炼。要逐次受益，可嵌套 if；这是常见的"为分析器改写"。

**问：这一章和第 46 章的 IFDS 是什么关系？**
IFDS 处理"可能未初始化"这类沿路径集合传播、且传递函数可分配的问题，
用图可达性精确求解；本章是不可分配的条件精炼，用不动点近似。
一个走精确的图算法路线，一个走抽象解释路线，第 46 章会对照。

## 34.26 工程注意点

1. **先精炼后 join 的顺序不可交换。** 合并后再精炼等于让条件对着被
污染的事实推理；这是本章最容易在重构中被"顺手简化"掉的顺序，值得
一条针对输出的回归测试守着。

2. **拿不到标签就重建构造过程，但先验证确定性。** 复制编号/连边规则
之前，通读原构造器，确认没有无序容器遍历与地址相关的 tie-breaker；
并给复制体配一条与本体对拍的差异测试。

3. **抽象域表达不了的信息，放弃精炼而非强行近似。** `x ≠ k` 的假边是
样板：半个区间是错的，原样保留是对的。判定一条"精炼"是否 sound 的
快捷方式：检查它删去的每个具体值，是否都被条件在该边上明确否定。

4. **告警文本要复述推理。** 位置、除数表达式、除数区间、判定理由四
要素齐备，用户才能在不读工具源码的情况下判断告警是真缺陷还是信息
不足；沉默式告警（只报一个行号）会把所有复审都变成源码考古。

5. **控制对照实验的变量。** 两档共用同一份 CFG、同一套 widening 点与
轮数上限，输出差异才能归因于精炼；引入开关时顺手改别的参数，会让
"精度提升"失去可解释性。

最后补一条元注意：
- 本章机制便宜，是因为它只做局部裁剪
- 便宜的另一面，是它明确放弃了相关性与路径历史
- 遇到治不了的误报，先承认边界，再换机制
- 不要在边精炼里堆叠特例去模拟更重的域
- 特例堆叠的终点，是一个无法证明、也无法维护的"精炼"

## 34.27 练习题与解题思路

**练习 1（手算）**：对 branch.tip，手工写出分支点、节点 4、节点 5 在
精炼档的完整环境，并指出每个区间的哪一条界来自哪条语义。
思路：从 `x=input` 的全区间起步；真边规则给节点 4 的 x=[1,+inf]；假边
给节点 5 的 x=[-inf,0]，`0-x` 按端点得 [0,+inf]。每条界都应能标注
"赋值传递"或"条件边精炼"两类来源之一；标不出来的界说明手算混进了
无依据的断言。

**练习 2（假阳性解剖）**：把 div.tip 中条件改成 `x == 0`，两档输出分别
会怎样？
思路：真边上 x 被钉成 [0,0]，除数区间含端点 0，精炼档反而**必须告警**，
商因除零落入 ⊥/保守档——路径敏感不会让所有告警消失，它只让被条件
排除的缺陷告警消失；这个反例用来防止"开了路径敏感就不该有告警"的
误解。基线档行为不变，仍是全区间 + 告警。

**练习 3（单调性验证）**：对 `x > k` 的真边规则，任取两个有包含关系的
区间，验证精炼后仍保持包含；再给出一个若规则改成 lo'=k+2（即误把
"严格大于"读成"至少大 2"）会漏掉真实状态的例子。
思路：取 S=[1,10]⊑T=[0,10]，k=0：精炼得 [1,10] 与 [1,10]，保持；反例
取 σ(x)=1，它满足 x>0 为真，但 lo'=2 把它删了——边界常数差一，漏掉
的就是边界上那一个真实值。整数条件的 +1 不是风格，是语义。

**练习 4（设计）**：若语法扩展支持 `&&`，设计 `(x>0) && (y>0)` 真边的
精炼，并说明假边为什么不能简单精炼。
思路：真边两个条件同时成立，分别对 x、y 施加真边规则，收缩/单调逐
变量成立；假边只知道"合取为假"，即至少一个条件不成立，但不知道是
哪个——可能是 x≤0 而 y 任意，也可能反之，单环境装不下这个析取，保守
处理是不精炼。若要精炼假边，需要把环境提升成"环境之并"（析取域），
状态数翻倍——精度选项背后是域的升级。

**练习 5（代价测量）**：为求解器加上迭代轮数与"精炼被实际触发的边数"
统计，在若干嵌套分支程序上画出两档代价。
思路：局部精炼不增加轮数（同一份格、同一不动点），增加的只是每轮
每边常数次裁剪；若你测得轮数变化，说明精炼结果被错误地用于状态
变化判断，回到 22.5.6 检查顺序。这个练习把"第三轴"从口号变成可测量
的数字。

**练习 6（等号分支）**：分析程序
`if (x == 3) { output x; } else { output x; }` 精炼档的两个输出点。
详解，逐行走：
- 分支点入口 x=[-inf,+inf]
- 真边 Ceq：3 在区间内，钉成 [3,3]
- 真支输出：3
- 假边不精炼，x 保持全区间
- 假支输出：[-inf,+inf]
结论：真支的精确完全来自条件；假支不是"忘了写规则"，而是抽象域
无法表示"除了 3 以外的全体"。

**练习 7（连续两次同方向判断）**：
`if (x > 0) { if (x > 5) { output x; } }` 内层真支的区间？
详解：
- 外层真边 x=[1,+inf]
- 内层真边再抬到 6
- 输出 [6,+inf]
要点：第二次裁剪的基线已经是第一次的结果；max 操作让重复精炼幂等
——若把内层条件写成 x>−100，裁剪不产生变化，状态稳定，不会因为
"规则又执行了一次"制造迭代。

**练习 8（反向比较）**：
`if (0 > x) { output 0 - x; }` 的输出区间？
详解：
- 条件归一为 Clt（x<0）
- 真边上界压到 −1
- x=[-inf,-1]
- 0−x：下界 0−(−1)=1，上界 +inf
- 输出 [1,+inf]
要点：Clt 的规则不是新数学，只是换了读取方向。

**练习 9（矛盾条件）**：
`x = 5; if (x > 10) { output x; }` 精炼档会发生什么？
详解：
- 赋值后 x=[5,5]
- 真边抬下界到 11：lo=11>hi=5
- 区间变成 ⊥
- 输出点不可达
- 该点不对任何真实执行承担义务
要点：⊥ 是分析在说"此路不通"；死代码告警可以挂在这种点上（它
可达于语法、不可达于语义）。

**练习 10（假支的信息）**：
`if (x > 10) {} output x;`（if 体为空，输出在汇合后）输出点 x？
详解：
- 真边、假边在空 if 后立刻汇合
- 真支贡献 x=[11,+inf]
- 假支贡献 x=[-inf,10]
- join 得全区间
- 输出 x=[-inf,+inf]
要点：精炼信息在汇合点被拼回；两支区间在此恰好相邻，拼回没有空隙，
但分辨信息确实消失——汇合后问"x 是不是 10"，分析答不出。

**练习 11（常量折叠交互）**：条件中的变量已被折叠成常量时，边精炼
能推出什么？
程序：`flag = 1; if (flag) { output flag; }`
详解：
- flag 折叠为 [1,1]
- 条件 flag 不被 parseCond 识别（不是比较式）
- 但区间已精确，输出仍是 1
要点：路径信息与常量信息可以互相替代地喂给同一个预测；当条件不可
识别时，已有的精确环境照常工作。

**练习 12（负界裁剪）**：
`if (x > 0 - 10) { output x; }` 真边下界？
详解：
- 条件右端先按常量折叠成 −10
- parseCond 拿到的 k=−10
- 真边下界 −9
要点：折叠先于精炼；若右端折叠不出常量（含 input），parseCond 失败，
整个条件放弃精炼——两级处理的顺序不能颠倒。

**练习 13（除零与告警计数）**：一条语句里有两个除法（如
`output (100/x) + (200/y)`），告警有几条？
详解：
- collectDivs 递归捞出两个 Binop
- 对每个除数分别判定
- 两个除数区间都含 0 → 两条告警
- 输出表达式本身：因除数含 0，每段全区间，和仍全区间
要点：缺陷告警按操作计数、不按语句计数；一个语句可以既带多条告警
又给出一个宽预测。

**练习 14（精炼单调性反例搜索）**：尝试构造一个不单调的"精炼"，
并说明代码测试能否抓到它。
一种坏规则：lo'= 若 lo=−inf 则 k+1，否则 k+100
验证不单调：
- S=[-inf, +inf]，T=[0,+inf]，S⊑T 成立
- 精炼 S：[k+1, …]
- 精炼 T：[k+100, …]
- 结果 S 精炼后比 T 更宽，序被反转
测试能否抓到：
- 普通功能测试可能恰好绕过这对输入
- 需要针对"成对包含输入"的性质测试（property test）
要点：单调性是全域性质，靠样例守不住，性质测试与代码审查互补。

**练习 15（笛卡尔税）**：
`x = input; y = 0 - x; output x + y;` 的输出预测有什么浪费？
详解：
- x 全区间，y = 0−x 被独立求值为 [-2147483647,+inf]
- 具体世界里 x+y 恒为 0
- 独立区间求和：包络近乎全区间
- 预测宽，尽管真实输出唯一
要点：这不是路径敏感能治的（没有分支）；它是笛卡尔域的相关性税，
要靠关系域。把"路径问题"与"关系问题"分清，是选机制的前提。

**练习 16（while 假边）**：
`x = 0; while (x > 100) { x = x + 1; } output x;` 输出点 x？
详解：
- 循环体在具体语义中一次也不执行
- 分析仍在条件点 join 后做 widening
- 假边精炼（x≤100）作用于离开循环的边
- 输出点 x 至少上界被压到 100
要点：循环不执行时，假边条件仍然成立并可利用；分析无须"判断循环
执行几次"才能受益。

**练习 17（信息来源标注）**：为预测的每条界准备一个标签表，标签
取值有哪些？
可接受的标签：
- LIT：字面量直接给出
- ASSIGN：赋值传递（evalIv）
- EDGE-T：真边精炼
- EDGE-F：假边精炼
- JOIN：汇合包络
- WIDEN：加宽跳变
核对方法：推完一个程序，检查每条界都有且只有一个来源；标 JOIN 的
界必须能指回具体前驱。标不出来的界是手滑的信号。

**练习 18（soundness 反证阅读）**：如果精炼违反收缩（偶尔扩大
区间），22.9 的归纳会断在哪一句？
详解：
- 断点在 22.9.2：具体状态 ∈ γ(OUT[q]) 无法推出 ∈ γ(ρ(OUT[q]))
- 扩大进来的状态没有任何边条件担保
- 归纳覆盖出现空洞
- 下游全部传递也无法修复（空洞沿后继传播）
要点：可靠性证明是链式的，一环断、全链失效；这就是为什么算子
性质是准入条件而非风格。

**练习 19（精度的可数比较）**：两档分析在同一程序上，怎样形式化
断言"精炼档更精确"？
判据，逐条：
- 对每个点、每个变量，精炼区间 ⊑ 基线区间
- 至少一处严格更窄
- 两档都 sound（check 全绿）
三条同时成立，"更精确"才可断言；只有第二条（输出看着窄）而没有
第一条逐点核对，可能是某个点被错误裁窄（不 sound 的假精度）。

**练习 20（最小机制选择）**：面对三种缺陷模式，分别选档：
- 模式 A：缺陷只取决于单变量是否为 0
- 模式 B：缺陷取决于两个变量的差
- 模式 C：缺陷只在汇合后的某条不可行路径上
选档参考：
- A：本章单条件精炼足够
- B：需要关系域（差界），边精炼无效
- C：需要谓词抽象式的不可行路径判定
要点：选机制前先做"最小反例分类"；用重机制解决 A，是在为用不到
的表达力付出状态数代价。

## 34.28 FAQ

**问：路径敏感和流敏感是一回事吗？**
不是。流敏感尊重语句顺序（点前后事实不同），路径不敏感不区分到达
点的具体边（前驱先 join）。本章之前的分析全部是"流敏感、路径不敏感"。

**问：开了精炼之后还有告警，是不是精炼失败了？**
不是。精炼只排除被条件明确否定的可能性；条件本身允许缺陷（如
练习 2 的 x==0）时，告警不仅会保留，而且更可信。

**问：为什么不在 CFG 边表里直接加 true/false 标签？**
可以，且在活跃演进的代码库里应该这么做；本章选择局部重建，是因为
CFG 设施已在教程中冻结。两种方案的判定信息完全相同，区别只是"修改
共享设施"与"局部承担复制代价"之间的工程权衡。

**问：精炼后某点变成 ⊥，程序是不是有 bug？**
不一定。⊥ 只说明在当前抽象状态下该点不可达：可能是条件互斥的死
代码（真实信息），也可能是上游精度不足把可达路径误判成矛盾（假
⊥，仍然 sound——它漏掉的是告警而非放松断言——但损失精度）。区分
二者要对照具体执行或放宽上游条件。

**问：区间 join 在两支 [1,3]、[10,12] 时混入 4..9，为什么不算不 sound？**
sound 只要求"真实状态 ∈ 抽象集合"，混入多余值是过近似；它可能制造
假阳性（对 4..9 的缺陷告警），不会漏掉真实缺陷。方向相反的"欠近似"
才不 sound。

**问：路径敏感能分析多深的嵌套分支？**
局部精炼对嵌套深度本身不敏感（外层条件沿普通边流进内层），它失效
于"汇合之后再追问"。嵌套再深但不汇合，它都对；一旦中途汇合，被
join 稀释的信息找不回来。

**问：为什么比较只支持变量对常量？**
`x > y` 这样的变量间比较也能利用，但推出的是变量间关系（八边形/差
界约束域），单变量区间装不下；这是第 32 章域选择划定的边界，不是
路径敏感思想的边界。

## 34.29 小结

本章从一个朴素的观察出发：分支条件里的信息是免费的，但点上 join 的
框架结构上没有地方安放它。我们把信息挂到边上——给分支节点的真边、
假边各配一个收缩且单调的精炼函数，在 join 之前对每一份前驱贡献单独
裁剪——于是同一个 worklist 求解器用一个布尔开关产出两档结果。

两个程序把收益讲具体了：branch.tip 里，真支输出从全区间收窄到
[1,+inf]，假支的取反从 [-2147483647,+inf] 收窄到 [0,+inf]；div.tip
里，被 `x > 5` 排除的除零告警消失，商从全区间收窄到 [0,16]。每一条
新界都能指回具体条件，没有一处靠胆子大。

我们也划清了三条边界：局部边精炼不是完全路径敏感，后者在循环存在
时不可判定；抽象域表达不了的信息（≠k、合取的假边）要放弃精炼而非
强行近似；路径敏感只移动**精度轴**，可靠性是它必须保持、而非可以
拿来交换的东西。正确性论证把这三件事统一在同一句归纳义务里：精炼
不会删掉真实状态，则覆盖从前驱到后继闭合。

下一章我们离开单函数世界，第一次让分析跨过函数边界——过程间分析
面对的信息混合问题，与本章的边与 join 是近亲，但它要处理的"汇合"
发生在被调函数的入口，规模与结构都更进一步。

合上本章前，记住三个关键词：
- 边：条件信息的位置
- 裁剪：唯一允许的动作
- 边界：相关性与历史，本章明确不碰
从这三个词出发回看任何一段正文，应当都能落到同一条归纳义务上。
若回看时发现落不上，说明那一段要么越界，要么失据——
那种段落不应留在教程里。

```cpp
// file: src/ast.hpp
// AST 定义：AST 是去掉了括号、分号等语法噪音的程序结构。
// 接口自本章起冻结，后续所有分析（名字、CFG、类型、格……）都在此之上工作。
#pragma once

#include <memory>
#include <string>
#include <utility>
#include <vector>

namespace tip {

enum class BOp { Add, Sub, Mul, Div, Gt, Eq };

struct Expr {
    virtual ~Expr() = default;
};
struct IntLit : Expr {
    int v;
    explicit IntLit(int value) : v(value) {}
};
struct VarRef : Expr {
    std::string name;
    explicit VarRef(std::string n) : name(std::move(n)) {}
};
struct InputE : Expr {};
struct Binop : Expr {
    BOp op;
    std::unique_ptr<Expr> l, r;
    Binop(BOp o, std::unique_ptr<Expr> lhs, std::unique_ptr<Expr> rhs)
        : op(o), l(std::move(lhs)), r(std::move(rhs)) {}
};
struct CallE : Expr {
    std::unique_ptr<Expr> callee;
    std::vector<std::unique_ptr<Expr>> args;
    CallE(std::unique_ptr<Expr> fn, std::vector<std::unique_ptr<Expr>> as)
        : callee(std::move(fn)), args(std::move(as)) {}
};
struct Deref : Expr {
    std::unique_ptr<Expr> e;
    explicit Deref(std::unique_ptr<Expr> p) : e(std::move(p)) {}
};
struct AddrOf : Expr {                       // spa: & Id
    std::string name;
    explicit AddrOf(std::string n) : name(std::move(n)) {}
};
struct AllocE : Expr {
    std::unique_ptr<Expr> e;
    explicit AllocE(std::unique_ptr<Expr> init) : e(std::move(init)) {}
};
struct NullE : Expr {};
struct RecLit : Expr {
    std::vector<std::pair<std::string, std::unique_ptr<Expr>>> fields;
    explicit RecLit(std::vector<std::pair<std::string, std::unique_ptr<Expr>>> fs)
        : fields(std::move(fs)) {}
};
struct FieldA : Expr {
    std::unique_ptr<Expr> e;
    std::string field;
    FieldA(std::unique_ptr<Expr> record, std::string f)
        : e(std::move(record)), field(std::move(f)) {}
};

struct Stmt {
    virtual ~Stmt() = default;
};
// target 只会是 VarRef / FieldA / Deref，文法 lvalue 已限定。
struct AssignS : Stmt {
    std::unique_ptr<Expr> target, value;
    AssignS(std::unique_ptr<Expr> t, std::unique_ptr<Expr> v)
        : target(std::move(t)), value(std::move(v)) {}
};
struct OutputS : Stmt {
    std::unique_ptr<Expr> e;
    explicit OutputS(std::unique_ptr<Expr> x) : e(std::move(x)) {}
};
struct IfS : Stmt {
    std::unique_ptr<Expr> cond;
    std::unique_ptr<Stmt> then, els;
    IfS(std::unique_ptr<Expr> c, std::unique_ptr<Stmt> t, std::unique_ptr<Stmt> e)
        : cond(std::move(c)), then(std::move(t)), els(std::move(e)) {}
};
struct WhileS : Stmt {
    std::unique_ptr<Expr> cond;
    std::unique_ptr<Stmt> body;
    WhileS(std::unique_ptr<Expr> c, std::unique_ptr<Stmt> b)
        : cond(std::move(c)), body(std::move(b)) {}
};
struct BlockS : Stmt {
    std::vector<std::unique_ptr<Stmt>> ss;
    explicit BlockS(std::vector<std::unique_ptr<Stmt>> v) : ss(std::move(v)) {}
};
struct ReturnS : Stmt {
    std::unique_ptr<Expr> e;
    explicit ReturnS(std::unique_ptr<Expr> x) : e(std::move(x)) {}
};

struct FunDecl {
    std::string name;
    std::vector<std::string> params;
    std::vector<std::string> vars;
    std::unique_ptr<Stmt> body;
    std::unique_ptr<ReturnS> ret;
};

struct ProgramA {
    std::vector<std::unique_ptr<FunDecl>> funs;
};

}  // namespace tip
```

ast_build.hpp 与 ast_build.cpp 负责把 ANTLR 解析树翻译成上述 AST，并在

```cpp
// file: src/ast_build.hpp
// AST 构建器：在 ANTLR 生成的 parse-tree 上下文节点上手工递归下降。
// （本工具链 C++ runtime 的 visitor 以 std::any 传值，而 std::any 不能持有
// unique_ptr，因此不使用 visitor 机制：parse-tree 的上下文类本身信息完整，
// 用 dynamic_cast 区分 #标签备选，自己做一次结构化遍历同样直接。）
#pragma once

#include <memory>
#include <string>
#include <vector>

#include "TIPParser.h"
#include "antlr4-runtime.h"
#include "ast.hpp"

namespace tip {

struct AstBuilder {
    std::unique_ptr<ProgramA> build(TIPParser::ProgramContext *tree);

private:
    std::unique_ptr<FunDecl> buildFun(TIPParser::FunctionContext *ctx);
    std::unique_ptr<Expr> buildExpr(TIPParser::ExprContext *ctx);
    std::unique_ptr<Stmt> buildStmt(TIPParser::StmtContext *ctx);
    // lvalue 翻译成赋值目标表达式：VarRef / Deref，可再包一层 FieldA。
    std::unique_ptr<Expr> buildLvalue(TIPParser::LvalueContext *lv);
};

// 便捷入口：parse tree 的 program 节点 -> 完整 AST。
std::unique_ptr<ProgramA> buildAst(TIPParser::ProgramContext *tree);

}  // namespace tip
```

```cpp
// file: src/ast_build.cpp
#include "ast_build.hpp"

#include <utility>
#include <vector>

namespace tip {

std::unique_ptr<ProgramA> AstBuilder::build(TIPParser::ProgramContext *tree) {
    auto program = std::make_unique<ProgramA>();
    for (auto *fc : tree->function()) program->funs.push_back(buildFun(fc));
    return program;
}

std::unique_ptr<FunDecl> AstBuilder::buildFun(TIPParser::FunctionContext *ctx) {
    auto f = std::make_unique<FunDecl>();
    f->name = ctx->IDENT()->getText();
    if (ctx->params()) {
        for (auto *p : ctx->params()->IDENT()) f->params.push_back(p->getText());
    }
    if (ctx->varDecls()) {
        for (auto *v : ctx->varDecls()->IDENT()) f->vars.push_back(v->getText());
    }

    std::vector<std::unique_ptr<Stmt>> body;
    for (auto *sc : ctx->stmt()) body.push_back(buildStmt(sc));
    f->body = std::make_unique<BlockS>(std::move(body));

    f->ret = std::make_unique<ReturnS>(buildExpr(ctx->expr()));
    return f;
}

std::unique_ptr<Expr> AstBuilder::buildLvalue(TIPParser::LvalueContext *lv) {
    std::unique_ptr<Expr> base;
    std::string field;
    if (auto *d = dynamic_cast<TIPParser::DirectLvalueContext *>(lv)) {
        base = std::make_unique<VarRef>(d->IDENT(0)->getText());
        if (d->IDENT().size() == 2) field = d->IDENT(1)->getText();
    } else {
        auto *p = dynamic_cast<TIPParser::PointerLvalueContext *>(lv);
        base = std::make_unique<Deref>(buildExpr(p->expr()));
        if (p->IDENT()) field = p->IDENT()->getText();
    }
    if (!field.empty())
        return std::make_unique<FieldA>(std::move(base), std::move(field));
    return base;
}

std::unique_ptr<Expr> AstBuilder::buildExpr(TIPParser::ExprContext *ctx) {
    if (auto *c = dynamic_cast<TIPParser::IntExprContext *>(ctx))
        return std::make_unique<IntLit>(std::stoi(c->INT()->getText()));
    if (auto *c = dynamic_cast<TIPParser::VarExprContext *>(ctx))
        return std::make_unique<VarRef>(c->IDENT()->getText());
    if (dynamic_cast<TIPParser::InputExprContext *>(ctx))
        return std::make_unique<InputE>();
    if (dynamic_cast<TIPParser::NullExprContext *>(ctx))
        return std::make_unique<NullE>();
    if (auto *c = dynamic_cast<TIPParser::ParenExprContext *>(ctx))
        return buildExpr(c->expr());

    if (auto *c = dynamic_cast<TIPParser::AddExprContext *>(ctx)) {
        const BOp op = c->PLUS() ? BOp::Add : BOp::Sub;
        return std::make_unique<Binop>(op, buildExpr(c->expr(0)), buildExpr(c->expr(1)));
    }
    if (auto *c = dynamic_cast<TIPParser::MulExprContext *>(ctx)) {
        const BOp op = c->STAR() ? BOp::Mul : BOp::Div;
        return std::make_unique<Binop>(op, buildExpr(c->expr(0)), buildExpr(c->expr(1)));
    }
    if (auto *c = dynamic_cast<TIPParser::CmpExprContext *>(ctx)) {
        const BOp op = c->GT() ? BOp::Gt : BOp::Eq;
        return std::make_unique<Binop>(op, buildExpr(c->expr(0)), buildExpr(c->expr(1)));
    }
    if (auto *c = dynamic_cast<TIPParser::NegExprContext *>(ctx)) {
        // TIP 没有负数字面量 token，-E 即 0-E。
        return std::make_unique<Binop>(BOp::Sub, std::make_unique<IntLit>(0),
                                       buildExpr(c->expr()));
    }
    if (auto *c = dynamic_cast<TIPParser::CallExprContext *>(ctx)) {
        std::vector<std::unique_ptr<Expr>> args;
        if (c->args())
            for (auto *a : c->args()->expr()) args.push_back(buildExpr(a));
        return std::make_unique<CallE>(buildExpr(c->expr()), std::move(args));
    }
    if (auto *c = dynamic_cast<TIPParser::FieldExprContext *>(ctx))
        return std::make_unique<FieldA>(buildExpr(c->expr()), c->IDENT()->getText());
    if (auto *c = dynamic_cast<TIPParser::DerefExprContext *>(ctx))
        return std::make_unique<Deref>(buildExpr(c->expr()));
    if (auto *c = dynamic_cast<TIPParser::AddrExprContext *>(ctx))
        return std::make_unique<AddrOf>(c->IDENT()->getText());
    if (auto *c = dynamic_cast<TIPParser::AllocExprContext *>(ctx))
        return std::make_unique<AllocE>(buildExpr(c->expr()));
    if (auto *c = dynamic_cast<TIPParser::RecExprContext *>(ctx)) {
        std::vector<std::pair<std::string, std::unique_ptr<Expr>>> fields;
        for (auto *fc : c->field())
            fields.emplace_back(fc->IDENT()->getText(), buildExpr(fc->expr()));
        return std::make_unique<RecLit>(std::move(fields));
    }
    return nullptr;  // 解析成功时不会到达
}

std::unique_ptr<Stmt> AstBuilder::buildStmt(TIPParser::StmtContext *ctx) {
    if (auto *c = dynamic_cast<TIPParser::AssignStmtContext *>(ctx))
        return std::make_unique<AssignS>(buildLvalue(c->lvalue()), buildExpr(c->expr()));
    if (auto *c = dynamic_cast<TIPParser::OutputStmtContext *>(ctx))
        return std::make_unique<OutputS>(buildExpr(c->expr()));
    if (auto *c = dynamic_cast<TIPParser::IfStmtContext *>(ctx)) {
        std::unique_ptr<Stmt> els;
        if (c->stmt().size() == 2) els = buildStmt(c->stmt(1));
        return std::make_unique<IfS>(buildExpr(c->expr()), buildStmt(c->stmt(0)),
                                     std::move(els));
    }
    if (auto *c = dynamic_cast<TIPParser::WhileStmtContext *>(ctx))
        return std::make_unique<WhileS>(buildExpr(c->expr()), buildStmt(c->stmt()));
    if (auto *c = dynamic_cast<TIPParser::BlockStmtContext *>(ctx)) {
        std::vector<std::unique_ptr<Stmt>> ss;
        for (auto *sc : c->stmt()) ss.push_back(buildStmt(sc));
        return std::make_unique<BlockS>(std::move(ss));
    }
    return nullptr;  // 解析成功时不会到达
}

std::unique_ptr<ProgramA> buildAst(TIPParser::ProgramContext *tree) {
    return AstBuilder{}.build(tree);
}

}  // namespace tip
```

```cpp
// file: src/symtab.hpp
// 符号表与名字解析：把 AST 上的每个 VarRef 绑定到它的声明
// （函数 / 参数 / 局部变量），同时产出未声明、重复声明诊断。
#pragma once

#include <map>
#include <string>
#include <vector>

#include "ast.hpp"

namespace tip {

struct Symbol {

    std::vector<std::unique_ptr<Scope>> scopes;
    std::vector<Diag> errors;
    std::map<const VarRef *, const Symbol *> uses;  // 解析成功的使用点

// 两遍解析：先注册全部函数名（支持前向调用），再逐函数解析函数体。
```

```cpp
// file: src/symtab.cpp
#include "symtab.hpp"

#include <utility>

namespace tip {

namespace {

// 解析器在遍历 AST 的同时完成绑定与诊断收集。
struct Resolver {
    Bindings bindings;
    Scope *current = nullptr;
    const FunDecl *owner = nullptr;

    void declare(const std::string &name, Symbol::Kind kind) {
        if (current->table.count(name)) {
            bindings.errors.push_back({"error: redeclared '" + name + "'"});
            return;  // 保留先声明者，后声明被忽略
        }
        current->table.emplace(name, Symbol{kind, name, owner});
    }

    void resolveExpr(const Expr *e) {
        if (const auto *x = dynamic_cast<const VarRef *>(e)) {
            const Symbol *s = current->lookup(x->name);
            if (!s) {
                bindings.errors.push_back({"error: undeclared '" + x->name + "'"});
            } else {
                bindings.uses[x] = s;
            }
            return;
        }
        if (const auto *x = dynamic_cast<const Binop *>(e)) {
            resolveExpr(x->l.get());
            resolveExpr(x->r.get());
            return;
        }
        if (const auto *x = dynamic_cast<const CallE *>(e)) {
            resolveExpr(x->callee.get());
            for (const auto &a : x->args) resolveExpr(a.get());
            return;
        }
        if (const auto *x = dynamic_cast<const Deref *>(e)) return resolveExpr(x->e.get());
        if (const auto *x = dynamic_cast<const AllocE *>(e)) return resolveExpr(x->e.get());
        if (const auto *x = dynamic_cast<const FieldA *>(e)) {
            resolveExpr(x->e.get());  // 字段名不是变量，无需解析
            return;
        }
        if (const auto *x = dynamic_cast<const RecLit *>(e)) {
            for (const auto &f : x->fields) resolveExpr(f.second.get());
            return;
        }
        // IntLit / InputE / AddrOf / NullE：无变量使用。
    }

    void resolveStmt(const Stmt *s) {
        if (const auto *x = dynamic_cast<const AssignS *>(s)) {
            resolveExpr(x->target.get());
            resolveExpr(x->value.get());
            return;
        }
        if (const auto *x = dynamic_cast<const OutputS *>(s)) return resolveExpr(x->e.get());
        if (const auto *x = dynamic_cast<const IfS *>(s)) {
            resolveExpr(x->cond.get());
            resolveStmt(x->then.get());
            if (x->els) resolveStmt(x->els.get());
            return;
        }
        if (const auto *x = dynamic_cast<const WhileS *>(s)) {
            resolveExpr(x->cond.get());
            resolveStmt(x->body.get());
            return;
        }
        if (const auto *x = dynamic_cast<const BlockS *>(s)) {
            for (const auto &st : x->ss) resolveStmt(st.get());
            return;
        }
        if (const auto *x = dynamic_cast<const ReturnS *>(s)) return resolveExpr(x->e.get());
    }
};

}  // namespace

const Symbol *Scope::lookup(const std::string &name) const {
    auto it = table.find(name);
    if (it != table.end()) return &it->second;
    return parent ? parent->lookup(name) : nullptr;
}

Bindings resolveNames(ProgramA &program) {
    Resolver resolver;
    resolver.bindings.global = Scope(nullptr);
    Scope *global = &resolver.bindings.global;

    // 第一遍：所有函数名进入全局作用域。
    for (const auto &f : program.funs) {
        if (global->table.count(f->name)) {
            resolver.bindings.errors.push_back({"error: redeclared '" + f->name + "'"});
            continue;
        }
        global->table.emplace(f->name, Symbol{Symbol::Fun, f->name, f.get()});
    }

    // 第二遍：每个函数开自己的作用域，父作用域是全局表；
    // 作用域所有权交给 Bindings，遍历结束后符号依然存活。
    for (const auto &f : program.funs) {
        auto functionScope = std::make_unique<Scope>(global);
        resolver.current = functionScope.get();
        resolver.owner = f.get();

        for (const std::string &p : f->params) resolver.declare(p, Symbol::Param);
        for (const std::string &v : f->vars) resolver.declare(v, Symbol::Local);

        resolver.resolveStmt(f->body.get());
        resolver.resolveStmt(f->ret.get());

        resolver.current = nullptr;
        resolver.bindings.scopes.push_back(std::move(functionScope));
    }
    return std::move(resolver.bindings);
}

}  // namespace tip
```

```cpp
// file: src/cfg.cpp
#include "cfg.hpp"

#include <map>
#include <set>
#include <sstream>
#include <vector>

#include "pretty.hpp"

namespace tip {
namespace {

// 两遍构造：第一遍按 AST 先序给所有程序点分配固定编号；第二遍连边。
// 先编号再连边，是为了让编号严格按源码顺序（连边时若先构造后继节点，
// 后继会抢在前面编号），从而输出与程序点编号都是确定的。
class CfgBuilder {
public:
    explicit CfgBuilder(const ProgramA &program) : program_(program) {}

    Cfg run() {
        Cfg cfg;
        for (const auto &fun : program_.funs) {
            FunCfg fc;
            cur_ = &fc;
            cur_->name = fun->name;
            nextId_ = 1;
            stmtId_.clear();

            const int entry = addNode(CfgNode::Kind::Entry);
            cur_->entry = entry;
            numberStmt(fun->body.get());
            const int retId = addNode(CfgNode::Kind::Return, fun->ret.get());
            const int exitId = addNode(CfgNode::Kind::Exit);
            cur_->exitNode = exitId;

            // 连边：语句构造返回它自己的入口点集合；空块没有节点，直接透传后继。
            std::vector<int> bodyEntries = wireStmt(fun->body.get(), {retId});
            if (bodyEntries.empty()) bodyEntries = {retId};
            link(entry, bodyEntries);
            link(retId, {exitId});

            // set 去重并排序：CFG 边不允许重复，输出顺序固定。
            std::set<std::pair<int, int>> uniq(cur_->edges.begin(), cur_->edges.end());
            cur_->edges.assign(uniq.begin(), uniq.end());
            cfg.funs.push_back(std::move(*cur_));
        }
        return cfg;
    }

private:
    const ProgramA &program_;
    FunCfg *cur_ = nullptr;
    int nextId_ = 1;
    std::map<const Stmt *, int> stmtId_;

    int addNode(CfgNode::Kind kind, const Stmt *stmt = nullptr) {
        const int id = nextId_++;
        cur_->nodes.emplace(id, CfgNode{id, kind, stmt});
        return id;
    }

    // ---- 第一遍：编号 ----
    void numberStmt(const Stmt *s) {
        if (const auto *b = dynamic_cast<const BlockS *>(s)) {
            for (const auto &x : b->ss) numberStmt(x.get());
            return;
        }
        if (const auto *x = dynamic_cast<const IfS *>(s)) {
            stmtId_[x] = addNode(CfgNode::Kind::Branch, x);
            numberStmt(x->then.get());
            numberStmt(x->els.get());
            return;
        }
        if (const auto *x = dynamic_cast<const WhileS *>(s)) {
            stmtId_[x] = addNode(CfgNode::Kind::Branch, x);
            numberStmt(x->body.get());
            return;
        }
        if (dynamic_cast<const AssignS *>(s)) {
            stmtId_[s] = addNode(CfgNode::Kind::Assign, s);
            return;
        }
        if (dynamic_cast<const OutputS *>(s)) {
            stmtId_[s] = addNode(CfgNode::Kind::Output, s);
        }
    }

    // ---- 第二遍：连边。返回进入该语句时首先到达的程序点集合 ----
    std::vector<int> wireStmt(const Stmt *s, const std::vector<int> &succ) {
        if (const auto *b = dynamic_cast<const BlockS *>(s)) {
            std::vector<int> cur = succ;
            for (auto it = b->ss.rbegin(); it != b->ss.rend(); ++it)
                cur = wireStmt(it->get(), cur);
            return cur;
        }
        if (const auto *x = dynamic_cast<const IfS *>(s)) {
            const int n = stmtId_[x];
            std::vector<int> targets = wireStmt(x->then.get(), succ);
            if (targets.empty()) targets = succ;
            if (x->els) {
                std::vector<int> e = wireStmt(x->els.get(), succ);
                if (e.empty()) e = succ;
                targets.insert(targets.end(), e.begin(), e.end());
            } else {
                targets.insert(targets.end(), succ.begin(), succ.end());
            }
            link(n, targets);
            return {n};
        }
        if (const auto *x = dynamic_cast<const WhileS *>(s)) {
            const int n = stmtId_[x];
            // 循环体执行完回到条件点；空体时条件点连一条自边（等于死循环）。
            std::vector<int> bodyEntries = wireStmt(x->body.get(), {n});
            if (bodyEntries.empty()) bodyEntries = {n};
            link(n, bodyEntries);
            link(n, succ);
            return {n};
        }
        const int n = stmtId_[s];
        link(n, succ);
        return {n};
    }

    void link(int from, const std::vector<int> &to) {
        for (int t : to) cur_->edges.emplace_back(from, t);
    }
};

const char *kindName(CfgNode::Kind kind) {
    switch (kind) {
        case CfgNode::Kind::Entry: return "entry";
        case CfgNode::Kind::Exit: return "exit";
        case CfgNode::Kind::Assign: return "assign";
        case CfgNode::Kind::Output: return "output";
        case CfgNode::Kind::Branch: return "branch";
        case CfgNode::Kind::Return: return "return";
    }
    return "?";
}

}  // namespace

Cfg buildCfg(const ProgramA &program) { return CfgBuilder(program).run(); }

std::string printCfg(const Cfg &cfg) {
    std::ostringstream out;
    for (const FunCfg &f : cfg.funs) {
        out << "== " << f.name << " ==\n";
        out << "nodes:\n";
        for (const auto &[id, node] : f.nodes) {
            out << "  " << id << ": " << kindName(node.kind);
            if (node.stmt) out << "  " << printStmtLine(*node.stmt);
            out << "\n";
        }
        out << "edges:\n";
        for (const auto &[a, b] : f.edges) out << "  " << a << " -> " << b << "\n";
    }
    return out.str();
}

}  // namespace tip
```

```cpp
// file: src/pretty.cpp
#include "pretty.hpp"

#include <string>

namespace tip {

namespace {

// 表达式打印为前缀式：运算符与符号的对照表。
std::string exprText(const Expr *e) {
    if (const auto *x = dynamic_cast<const IntLit *>(e)) return std::to_string(x->v);
    if (const auto *x = dynamic_cast<const VarRef *>(e)) return x->name;
    if (dynamic_cast<const InputE *>(e)) return "input";
    if (dynamic_cast<const NullE *>(e)) return "null";

    if (const auto *x = dynamic_cast<const Binop *>(e)) {
        const char *sym = "+";
        switch (x->op) {
            case BOp::Add: sym = "+"; break;
            case BOp::Sub: sym = "-"; break;
            case BOp::Mul: sym = "*"; break;
            case BOp::Div: sym = "/"; break;
            case BOp::Gt: sym = ">"; break;
            case BOp::Eq: sym = "=="; break;
        }
        return "(" + std::string(sym) + " " + exprText(x->l.get()) + " " +
               exprText(x->r.get()) + ")";
    }
    if (const auto *x = dynamic_cast<const CallE *>(e)) {
        std::string s = "(call " + exprText(x->callee.get());
        for (const auto &a : x->args) s += " " + exprText(a.get());
        return s + ")";
    }
    if (const auto *x = dynamic_cast<const Deref *>(e))
        return "(* " + exprText(x->e.get()) + ")";
    if (const auto *x = dynamic_cast<const AddrOf *>(e)) return "(& " + x->name + ")";
    if (const auto *x = dynamic_cast<const AllocE *>(e))
        return "(alloc " + exprText(x->e.get()) + ")";
    if (const auto *x = dynamic_cast<const FieldA *>(e))
        return "(. " + exprText(x->e.get()) + " " + x->field + ")";
    if (const auto *x = dynamic_cast<const RecLit *>(e)) {
        std::string s = "{";
        for (size_t i = 0; i < x->fields.size(); ++i) {
            if (i) s += ", ";
            s += x->fields[i].first + ": " + exprText(x->fields[i].second.get());
        }
        return s + "}";
    }
    return "<unknown expr>";
}

std::string indent(int level) { return std::string(static_cast<size_t>(level) * 2, ' '); }

// 语句打印带缩进，一条语句一行（块内多行）。
void stmtText(const Stmt *s, int level, std::string &out) {
    if (const auto *x = dynamic_cast<const AssignS *>(s)) {
        out += indent(level) + exprText(x->target.get()) + " = " +
               exprText(x->value.get()) + " ;\n";
        return;
    }
    if (const auto *x = dynamic_cast<const OutputS *>(s)) {
        out += indent(level) + "output " + exprText(x->e.get()) + " ;\n";
        return;
    }
    if (const auto *x = dynamic_cast<const ReturnS *>(s)) {
        out += indent(level) + "return " + exprText(x->e.get()) + " ;\n";
        return;
    }
    if (const auto *x = dynamic_cast<const IfS *>(s)) {
        out += indent(level) + "if (" + exprText(x->cond.get()) + ")\n";
        stmtText(x->then.get(), level + 1, out);
        if (x->els) {
            out += indent(level) + "else\n";
            stmtText(x->els.get(), level + 1, out);
        }
        return;
    }
    if (const auto *x = dynamic_cast<const WhileS *>(s)) {
        out += indent(level) + "while (" + exprText(x->cond.get()) + ")\n";
        stmtText(x->body.get(), level + 1, out);
        return;
    }
    if (const auto *x = dynamic_cast<const BlockS *>(s)) {
        out += indent(level) + "{\n";
        for (const auto &st : x->ss) stmtText(st.get(), level + 1, out);
        out += indent(level) + "}\n";
        return;
    }
    out += indent(level) + "<unknown stmt>\n";
}

}  // namespace

std::string printExpr(const Expr *e) { return exprText(e); }

std::string printProgram(const ProgramA &program) {
    std::string out;
    for (const auto &f : program.funs) {
        std::string paramList;
        for (size_t i = 0; i < f->params.size(); ++i) {
            if (i) paramList += ",";
            paramList += f->params[i];
        }
        out += f->name + "(" + paramList + ") {\n";
        if (!f->vars.empty()) {
            out += indent(1) + "var ";
            for (size_t i = 0; i < f->vars.size(); ++i) {
                if (i) out += ",";
                out += f->vars[i];
            }
            out += " ;\n";
        }
        // 函数体是 BlockS；打印其内部语句而不是再嵌一层花括号。
        const auto *body = dynamic_cast<const BlockS *>(f->body.get());
        for (const auto &st : body->ss) stmtText(st.get(), 1, out);
        stmtText(f->ret.get(), 1, out);
        out += "}\n";
    }
    return out;
}

// 单行形式：CFG 节点标签等"节点旁边写一句话"的场合使用。

}
```

lattice.hpp 是通用格接口（top/bot/leq/join 四件套），区间格在其上构造。

```cpp
// file: src/lattice.hpp
// 格的统一接口与四类通用构造（spa 第 4 章）。
// 一个"格"只需提供：顶/底两个边界、相等判定、偏序、最小上界。
// 提升(lift)、积(product)、映射(maps)、幂集(powerset)能把简单格组装成
// 程序状态所需的复合格——抽象环境就是"变量集合 → 值格"的映射格。
#pragma once

#include <functional>
#include <map>
#include <optional>
#include <set>
#include <tuple>
#include <utility>

namespace tip {

template <class A>
struct Lattice {
    A topV;
    A botV;
    std::function<bool(const A &, const A &)> eqF;
    std::function<bool(const A &, const A &)> leqF;
    std::function<A(const A &, const A &)> joinF;

    const A &top() const { return topV; }
    const A &bot() const { return botV; }
    bool eq(const A &a, const A &b) const { return eqF(a, b); }
    bool leq(const A &a, const A &b) const { return leqF(a, b); }
    A join(const A &a, const A &b) const { return joinF(a, b); }
};

// ---- 提升：给 A 加一个新底 ⊥=nullopt（"还没有值"） ----
template <class A>
Lattice<std::optional<A>> lift(const Lattice<A> &l) {
    using O = std::optional<A>;
    return Lattice<O>{
        O{l.top()}, O{std::nullopt},
        [](const O &a, const O &b) { return a == b; },
        [l](const O &a, const O &b) {
            if (!b.has_value()) return a == b;        // ⊥ 最小
            if (!a.has_value()) return true;
            return l.leq(*a, *b);
        },
        [l](const O &a, const O &b) {
            if (!a.has_value()) return b;
            if (!b.has_value()) return a;
            return O{l.join(*a, *b)};
        }};
}

// ---- 积：分量各自取 join，序为逐分量序 ----
template <class T, std::size_t... Is, class LTuple>
T tupleJoin(std::index_sequence<Is...>, const LTuple &lats, const T &a, const T &b) {
    return T{std::get<Is>(lats).join(std::get<Is>(a), std::get<Is>(b))...};
}
template <class T, std::size_t... Is, class LTuple>
bool tupleLeq(std::index_sequence<Is...>, const LTuple &lats, const T &a, const T &b) {
    return (... && std::get<Is>(lats).leq(std::get<Is>(a), std::get<Is>(b)));
}

template <class... As>
Lattice<std::tuple<As...>> product(const Lattice<As> &... ls) {
    using T = std::tuple<As...>;
    auto lats = std::make_tuple(ls...);
    T topT{ls.top()...};
    T botT{ls.bot()...};
    return Lattice<T>{
        std::move(topT), std::move(botT),
        [](const T &a, const T &b) { return a == b; },
        [lats](const T &a, const T &b) {
            return tupleLeq<T>(std::make_index_sequence<sizeof...(As)>{}, lats, a, b);
        },
        [lats](const T &a, const T &b) {
            return tupleJoin<T>(std::make_index_sequence<sizeof...(As)>{}, lats, a, b);
        }};
}

// ---- 映射：固定键集上逐点 join；键缺失按底处理 ----
template <class K, class V>
Lattice<std::map<K, V>> maps(const Lattice<V> &l, const std::set<K> &keys) {
    using M = std::map<K, V>;
    M topM, botM;
    for (const K &k : keys) {
        topM.emplace(k, l.top());
        botM.emplace(k, l.bot());
    }
    auto getOrBot = [&botM](const M &m, const K &k) {
        auto it = m.find(k);
        if (it != m.end()) return it->second;
        return botM.at(k);
    };
    return Lattice<M>{
        topM, botM,
        [](const M &a, const M &b) { return a == b; },
        [=](const M &a, const M &b) {
            for (const K &k : keys)
                if (!l.leq(getOrBot(a, k), getOrBot(b, k))) return false;
            return true;
        },
        [=](const M &a, const M &b) {
            M r;
            for (const K &k : keys) r.emplace(k, l.join(getOrBot(a, k), getOrBot(b, k)));
            return r;
        }};
}

// ---- 幂集：join=并，meet=交，序=包含；顶=给定全集（默认为空集） ----
template <class K>
Lattice<std::set<K>> powerset(const std::set<K> &universe = {}) {
    using S = std::set<K>;
    return Lattice<S>{
        universe, S{},
        [](const S &a, const S &b) { return a == b; },
        [](const S &a, const S &b) {
            for (const K &k : a)
                if (!b.count(k)) return false;
```

```cpp
// 端点饱和加/减/乘：越过哨兵一律钳到 ±∞。
int satAdd(long long a, long long b) {
    long long r = a + b;
    if (r > INT_MAX) return INT_MAX;
    if (r < INT_MIN) return INT_MIN;
    return static_cast<int>(r);
}
int satMul(long long a, long long b) {
    long long r = a * b;
    if (r > INT_MAX) return INT_MAX;
    if (r < INT_MIN) return INT_MIN;
    return static_cast<int>(r);
}
// "未知符号"端的保守处理：与 ±∞ 相乘的有限端按同号无穷估计。
int mulLo(int a, int b) {
    if (a == 0 || b == 0) return 0;
    if (a == INT_MIN || b == INT_MIN) return INT_MIN;
    if (a == INT_MAX || b == INT_MAX) return (a > 0) == (b > 0) ? INT_MAX : INT_MIN;
    return satMul(a, b);
}
int mulHi(int a, int b) {
    if (a == 0 || b == 0) return 0;
    if (a == INT_MIN || b == INT_MIN) return (a > 0) == (b > 0) ? INT_MAX : INT_MIN;
    if (a == INT_MAX || b == INT_MAX) return INT_MAX;
    return satMul(a, b);
}

Lattice<Iv> ivLattice() {
    return Lattice<Iv>{
        Iv{INT_MIN, INT_MAX},  // 顶：全区间（什么信息都没有）
        Iv{1, 0},              // 底：lo>hi 编码 ⊥（不可达）
        [](const Iv &a, const Iv &b) { return a.lo == b.lo && a.hi == b.hi; },
        [](const Iv &a, const Iv &b) {
            if (a.lo > a.hi) return true;   // ⊥ ⊑ 一切
            if (b.lo > b.hi) return false;
            return a.lo >= b.lo && a.hi <= b.hi;  // 区间包含 = 信息更准
        },
        [](const Iv &a, const Iv &b) {
            if (a.lo > a.hi) return b;
            if (b.lo > b.hi) return a;
            return Iv{std::min(a.lo, b.lo), std::max(a.hi, b.hi)};  // 包络
        }};
}

std::string ivText(const Iv &v) {
    if (v.lo > v.hi) return "bottom";
    std::ostringstream out;
    out << "[";
    if (v.lo == INT_MIN)
        out << "-inf";
    else
        out << v.lo;
    out << ",";
    if (v.hi == INT_MAX)
        out << "+inf";
    else
        out << v.hi;
    out << "]";
    return out.str();

Iv evalIv(const Expr *e, const IvEnv &env) {
    Lattice<Iv> lat = ivLattice();
    if (const auto *x = dynamic_cast<const IntLit *>(e)) {
        return Iv{x->v, x->v};
    }
    if (const auto *x = dynamic_cast<const VarRef *>(e)) {
        auto it = env.find(x->name);
        if (it == env.end()) return lat.bot();  // 没有区间信息 → ⊥（不可达路径近似）
        return it->second;
    }
    if (dynamic_cast<const InputE *>(e)) {
        return Iv{INT_MIN, INT_MAX};  // 任意整数
    }
    if (const auto *x = dynamic_cast<const Binop *>(e)) {
        Iv l = evalIv(x->l.get(), env);
        Iv r = evalIv(x->r.get(), env);
        if (l.lo > l.hi || r.lo > r.hi) return lat.bot();
        // 除法：除数区间含 0 时商可爆掉，保守取全区间；
        // 不含 0 且分子两端有限时按端点组合取截断商的包络。
        if (x->op == BOp::Div) {
            if (l.lo > l.hi || r.lo > r.hi) return lat.bot();
            if (r.lo <= 0 && r.hi >= 0) return Iv{INT_MIN, INT_MAX};
            if (l.lo > INT_MIN && l.hi < INT_MAX) {
                // 除数端点为哨兵 ±∞ 时按真实可表示值参与除法：
                // 有限分子除以 |±2^31| 截断为 0，恰与"商趋于 0"一致。
                long long nums[2] = {l.lo, l.hi};
                long long dens[2] = {r.lo, r.hi};
                int lo = INT_MAX, hi = INT_MIN;
                for (long long n : nums)
                    for (long long d : dens) {
                        long long v = n / d;  // d 非零：区间已排除 0
                        int iv = v > INT_MAX ? INT_MAX
                                            : (v < INT_MIN ? INT_MIN : (int)v);
                        lo = std::min(lo, iv);
                        hi = std::max(hi, iv);
                    }
                return Iv{lo, hi};
            }
            return Iv{INT_MIN, INT_MAX};
        }
        if (x->op == BOp::Add)
            return Iv{satAdd(l.lo, r.lo), satAdd(l.hi, r.hi)};
        if (x->op == BOp::Sub)
            return Iv{satAdd(l.lo, -static_cast<long long>(r.hi)),
                      satAdd(l.hi, -static_cast<long long>(r.lo))};
        if (x->op == BOp::Mul) {
            int los[4] = {mulLo(l.lo, r.lo), mulLo(l.lo, r.hi),
                          mulLo(l.hi, r.lo), mulLo(l.hi, r.hi)};
            int his[4] = {mulHi(l.lo, r.lo), mulHi(l.lo, r.hi),
                          mulHi(l.hi, r.lo), mulHi(l.hi, r.hi)};
            return Iv{*std::min_element(los, los + 4),
                      *std::max_element(his, his + 4)};
        }
        return Iv{INT_MIN, INT_MAX};  // 比较/其余：只给真假信息，这里不精炼
    }
    return Iv{INT_MIN, INT_MAX};
}

NaiveResult runNaiveInterval(const Cfg &cfg, const ProgramA &program,
                             int maxRounds) {
    Lattice<Iv> lat = ivLattice();
    NaiveResult res;

    // 找循环头：第一条 while 语句所在节点（演示程序单函数单循环）。
    for (const FunCfg &fc : cfg.funs)
        for (const auto &[id, node] : fc.nodes)
            if (dynamic_cast<const WhileS *>(node.stmt) && res.headNode < 0)
                res.headNode = id;

    const FunCfg &fc = cfg.funs[0];
    std::map<int, std::vector<int>> preds;
    for (const auto &[a, b] : fc.edges) preds[b].push_back(a);

    // 声明的变量集合（循环头打印环境用）。
    std::set<std::string> vars(program.funs[0]->vars.begin(),
                               program.funs[0]->vars.end());

    // 朴素迭代：round-robin 按节点号顺序重算每个点，封顶 maxRounds 轮。
    std::map<int, IvEnv> out;
    for (int round = 0; round < maxRounds; ++round) {
        bool changed = false;
        for (const auto &[id, node] : fc.nodes) {
            IvEnv in;
            auto pit = preds.find(id);
            if (pit != preds.end()) {
                for (int q : pit->second) {
                    const IvEnv &qs = out[q];
                    for (const auto &[k, v] : qs)
                        in[k] = lat.join(in.count(k) ? in[k] : lat.bot(), v);
                }
            }
            // entry 边界：参数视为全区间（此处演示程序无参）。
            for (const std::string &p : program.funs[0]->params)
                in[p] = lat.join(in.count(p) ? in[p] : lat.bot(),
                                 Iv{INT_MIN, INT_MAX});

            IvEnv o = in;
            if (const auto *a = dynamic_cast<const AssignS *>(node.stmt))
                if (const auto *t = dynamic_cast<const VarRef *>(a->target.get()))
                    o[t->name] = evalIv(a->value.get(), in);
            if (out.count(id) == 0 || !(out[id] == o)) {
                out[id] = o;
                changed = true;
            }
        }
        res.rounds = round + 1;
        if (res.headNode >= 0) {
            std::ostringstream line;
            line << "iter " << round << ": "
                 << envText(out.count(res.headNode) ? out[res.headNode] : IvEnv{},
                            vars);
            res.trace.push_back(line.str());
        }
        if (!changed) {
            res.converged = true;
            break;
        }
    }
    return res;
}
```

```cpp
// file: src/widen.cpp
#include "widen.hpp"

#include <algorithm>
#include <set>
#include <sstream>

namespace tip {
namespace {

// ---- 条件识别：把 (x > k)/(k > x)/(x == k) 归一成 {变量, 界, 比较种类} ----
enum CondKind { Cgt, Clt, Ceq };
struct CondFact {
    std::string var;
    int k = 0;
    CondKind kind = Cgt;
    bool ok = false;
};

CondFact parseCond(const Expr *cond) {
    CondFact f;
    const auto *b = dynamic_cast<const Binop *>(cond);
    if (!b) return f;
    const auto *x = dynamic_cast<const VarRef *>(b->l.get());
    const auto *c = dynamic_cast<const IntLit *>(b->r.get());
    if (!x || !c) {
        x = dynamic_cast<const VarRef *>(b->r.get());
        c = dynamic_cast<const IntLit *>(b->l.get());
    }
    if (!x || !c) return f;
    f.var = x->name;
    f.k = c->v;
    switch (b->op) {
        case BOp::Gt:
            // 原式 (x > k) 或 (k > x)：后者按 (x < k) 归一。
            f.kind = (b->l.get() == x) ? Cgt : Clt;
            f.ok = true;
            break;
        case BOp::Eq:
            f.kind = Ceq;
            f.ok = true;
            break;
        default:
            break;
    }
    return f;
}

// ---- CFG 构造器编号/连线规则的局部重建：拿到每个分支真/假边的目标 ----
// cfg.cpp 用"先序编号 + 语句透传"构造图且边不带标签；本章不动共享的
// cfg.hpp（前几章文档已按字节嵌入它），按同一规则重推一份。
struct BranchEdges {
    std::map<int, int> trueOf, falseOf;  // 分支节点号 → 真/假边目标
};

class LocalWiring {
public:
    BranchEdges run(const ProgramA &program) {
        for (const auto &fun : program.funs) {
            next_ = 2;  // entry 固定为 1
            id_.clear();
            number(fun->body.get());
            const int retId = next_++;  // 与 cfg.cpp 相同：return、exit 收尾
            (void)next_;
            wire(fun->body.get(), {retId});
        }
        return edges_;
    }

private:
    BranchEdges edges_;
    int next_ = 2;
    std::map<const Stmt *, int> id_;

    // 第一遍：先序编号（与 cfg.cpp 的 numberStmt 逐条对应）。
    void number(const Stmt *s) {
        if (const auto *b = dynamic_cast<const BlockS *>(s)) {
            for (const auto &x : b->ss) number(x.get());
            return;
        }
        if (const auto *x = dynamic_cast<const IfS *>(s)) {
            id_[x] = next_++;
            number(x->then.get());
            if (x->els) number(x->els.get());
            return;
        }
        if (const auto *x = dynamic_cast<const WhileS *>(s)) {
            id_[x] = next_++;
            number(x->body.get());
            return;
        }
        if (dynamic_cast<const AssignS *>(s) || dynamic_cast<const OutputS *>(s))
            id_[s] = next_++;
    }

    // 第二遍：连边（与 cfg.cpp 的 wireStmt 逐条对应；入口点恒为单点）。
    std::vector<int> wire(const Stmt *s, std::vector<int> succ) {
        if (const auto *b = dynamic_cast<const BlockS *>(s)) {
            std::vector<int> cur = succ;
            for (auto it = b->ss.rbegin(); it != b->ss.rend(); ++it)
                cur = wire(it->get(), cur);
            return cur;
        }
        if (const auto *x = dynamic_cast<const IfS *>(s)) {
            const int n = id_.at(x);
            std::vector<int> targets = wireOrSelf(x->then.get(), succ);
            edges_.trueOf[n] = targets[0];
            std::vector<int> rest;
            if (x->els)
                rest = wireOrSelf(x->els.get(), succ);
            else
                rest = succ;
            edges_.falseOf[n] = rest[0];
            return {n};
        }
        if (const auto *x = dynamic_cast<const WhileS *>(s)) {
            const int n = id_.at(x);
            std::vector<int> bodyEntries = wireOrSelf(x->body.get(), {n});
            edges_.trueOf[n] = bodyEntries[0];
            edges_.falseOf[n] = succ[0];
            return {n};
        }
        return {id_.at(s)};
    }
    std::vector<int> wireOrSelf(const Stmt *s, std::vector<int> succ) {
        std::vector<int> r = wire(s, succ);
        if (r.empty()) r = succ;
        return r;
    }
};

// 分支节点携带的 cond 表达式（非分支语句返回空）。
const Expr *condOf(const Stmt *s) {
    if (const auto *w = dynamic_cast<const WhileS *>(s)) return w->cond.get();
    if (const auto *i = dynamic_cast<const IfS *>(s)) return i->cond.get();
    return nullptr;
}

}  // namespace

Iv widen(const Iv &a, const Iv &b) {
    if (a.lo > a.hi) return b;  // 旧值为 ⊥：直接采用新值，不跳阈值
    if (b.lo > b.hi) return a;
    Iv r = a;
    if (b.lo < a.lo) {
        // 下界阈值表 {-inf, 0, 1}：取不超过新下界的最大阈值。
        if (b.lo >= 1)
            r.lo = 1;
        else if (b.lo >= 0)
            r.lo = 0;
        else
            r.lo = INT_MIN;
    }
    if (b.hi > a.hi) {
        // 上界阈值表 {1, 0, +inf}：取不低于新上界的最小阈值。
        if (b.hi <= 0)
            r.hi = 0;
        else if (b.hi <= 1)
            r.hi = 1;
        else
            r.hi = INT_MAX;
    }
    return r;
}

Iv narrow(const Iv &a, const Iv &b) {
    if (a.lo > a.hi || b.lo > b.hi) return b;  // ⊥ 不收
    Iv r = a;
    if (a.lo == INT_MIN && b.lo > a.lo) r.lo = b.lo;
    if (a.hi == INT_MAX && b.hi < a.hi) r.hi = b.hi;
    return r;
}

IvEnv refineOnBranch(const Expr *cond, const IvEnv &env, bool taken) {
    CondFact f = parseCond(cond);
    if (!f.ok) return env;
    IvEnv out = env;
    auto it = out.find(f.var);
    if (it == out.end()) return out;  // ⊥ 变量无可精炼
    Iv v = it->second;
    if (v.lo > v.hi) return out;
    switch (f.kind) {
        case Cgt:  // x > k
            if (taken)
                v.lo = std::max(v.lo, f.k == INT_MAX ? INT_MAX : f.k + 1);
            else
                v.hi = std::min(v.hi, f.k);
            break;
        case Clt:  // x < k
            if (taken)
                v.hi = std::min(v.hi, f.k == INT_MIN ? INT_MIN : f.k - 1);
            else
                v.lo = std::max(v.lo, f.k);
            break;
        case Ceq:  // x == k：真边钉成 [k,k]；假边保守不动
            if (taken) {
                if (f.k < v.lo || f.k > v.hi)
                    v = Iv{1, 0};  // 与区间矛盾 → 该边不可达
                else
                    v = Iv{f.k, f.k};
            }
            break;
    }
    it->second = v;
    return out;
}

WidenedResult solveWidenedInterval(const Cfg &cfg, const ProgramA &program,
                                   int maxRounds) {
    Lattice<Iv> lat = ivLattice();
    WidenedResult res;

    // 加宽点：所有 while 条件节点。
    std::set<int> widenPoints;
    for (const FunCfg &fc : cfg.funs)
        for (const auto &[id, node] : fc.nodes)
            if (dynamic_cast<const WhileS *>(node.stmt)) {
                widenPoints.insert(id);
                if (res.headNode < 0) res.headNode = id;
            }

    BranchEdges be = LocalWiring().run(program);
    const FunCfg &fc = cfg.funs[0];

    struct PredEdge {
        int node;
        bool refine;
        bool taken;
    };
    std::map<int, std::vector<PredEdge>> preds;
    for (const auto &[a, b] : fc.edges) {
        PredEdge pe{a, false, true};
        if (be.trueOf.count(a) && be.trueOf[a] == b) pe = PredEdge{a, true, true};
        if (be.falseOf.count(a) && be.falseOf[a] == b)
            pe = PredEdge{a, true, false};
        preds[b].push_back(pe);
    }

    std::set<std::string> vars(program.funs[0]->vars.begin(),
                               program.funs[0]->vars.end());

    // 流入 = 各前驱流出（沿边精炼后）之并；无前驱点取空（参数在下方补全区间）。
    auto computeIn = [&](int p, const std::map<int, IvEnv> &out) {
        IvEnv in;
        auto pit = preds.find(p);
        if (pit != preds.end()) {
            for (const PredEdge &pe : pit->second) {
                IvEnv piece;
                auto it = out.find(pe.node);
                if (it != out.end()) piece = it->second;
                if (pe.refine)
                    piece = refineOnBranch(condOf(fc.nodes.at(pe.node).stmt),
                                           piece, pe.taken);
                for (const auto &[k, v] : piece)
                    in[k] = lat.join(in.count(k) ? in[k] : lat.bot(), v);
            }
        }
        return in;
    };

    std::map<int, IvEnv> out;
    for (int round = 0; round < maxRounds; ++round) {
        bool changed = false;
        for (const auto &[id, node] : fc.nodes) {
            IvEnv in = computeIn(id, out);
            // entry 边界：参数视为全区间。
            for (const std::string &p : program.funs[0]->params)
                in[p] = Iv{INT_MIN, INT_MAX};

            if (widenPoints.count(id)) {
                // 加宽点：与上一轮状态逐变量做 ∇。
                auto prev = out.find(id);
                if (prev != out.end())
                    for (auto &[k, v] : in) {
                        Iv pv = prev->second.count(k) ? prev->second.at(k)
                                                      : lat.bot();
                        v = widen(pv, v);
                    }
            }

            IvEnv o = in;
            if (const auto *a = dynamic_cast<const AssignS *>(node.stmt))
                if (const auto *t = dynamic_cast<const VarRef *>(a->target.get()))
                    o[t->name] = evalIv(a->value.get(), in);

            if (out.count(id) == 0 || !(out[id] == o)) {
                out[id] = o;
                changed = true;
            }
        }
        res.rounds = round + 1;
        if (res.headNode >= 0) {
            IvEnv head = out.count(res.headNode) ? out[res.headNode] : IvEnv{};
            res.trace.push_back("iter " + std::to_string(round) + ": " +
                                printIvEnv(head, vars));
        }
        if (!changed) {
            res.converged = true;
            break;
        }
    }
    res.out = out;
    return res;
}

std::map<int, IvEnv> narrowPass(const Cfg &cfg, const ProgramA &program,
                                const std::map<int, IvEnv> &widened) {
    Lattice<Iv> lat = ivLattice();
    const FunCfg &fc = cfg.funs[0];

    BranchEdges be = LocalWiring().run(program);
    struct PredEdge {
        int node;
        bool refine;
        bool taken;
    };
    std::map<int, std::vector<PredEdge>> preds;
    for (const auto &[a, b] : fc.edges) {
        PredEdge pe{a, false, true};
        if (be.trueOf.count(a) && be.trueOf[a] == b) pe = PredEdge{a, true, true};
        if (be.falseOf.count(a) && be.falseOf[a] == b)
            pe = PredEdge{a, true, false};
        preds[b].push_back(pe);
    }

    std::map<int, IvEnv> out = widened;
    for (const auto &[id, node] : fc.nodes) {
        IvEnv in;
        auto pit = preds.find(id);
        if (pit != preds.end()) {
            for (const PredEdge &pe : pit->second) {
                IvEnv piece;
                auto it = out.find(pe.node);
                if (it != out.end()) piece = it->second;
                if (pe.refine)
                    piece = refineOnBranch(condOf(fc.nodes.at(pe.node).stmt),
                                           piece, pe.taken);
                for (const auto &[k, v] : piece)
                    in[k] = lat.join(in.count(k) ? in[k] : lat.bot(), v);
            }
        }
        // Δ 规则：与加宽解逐变量收窄，只把 ±∞ 处的界收回有限值。
        for (auto &[k, v] : in) {
            Iv pv = widened.count(id) && widened.at(id).count(k)
                        ? widened.at(id).at(k)
                        : lat.bot();
            v = narrow(pv, v);
        }

        IvEnv o = in;
        if (const auto *a = dynamic_cast<const AssignS *>(node.stmt))
            if (const auto *t = dynamic_cast<const VarRef *>(a->target.get()))
                o[t->name] = evalIv(a->value.get(), in);
        out[id] = o;
    }
    return out;
}

std::string printIvEnv(const IvEnv &env, const std::set<std::string> &keys) {
    std::ostringstream out;
    bool first = true;
    for (const std::string &k : keys) {
        if (!first) out << " ";
        out << k << "="
            << (env.count(k) ? ivText(env.at(k)) : std::string("bottom"));
        first = false;
    }
    return out.str();
}
```

```cpp
// file: src/path.cpp
#include "path.hpp"

#include <algorithm>
#include <set>
#include <sstream>

#include "pretty.hpp"
#include "widen.hpp"

namespace tip {
namespace {

// 分支节点携带的 cond 表达式（与第 33 章 widen.cpp 同一份局部重建）。
const Expr *condOf(const Stmt *s) {
    if (const auto *w = dynamic_cast<const WhileS *>(s)) return w->cond.get();
    if (const auto *i = dynamic_cast<const IfS *>(s)) return i->cond.get();
    return nullptr;
}

// CFG 构造器编号/连线规则的局部重建：拿到每个分支真/假边目标。
struct BranchEdges {
    std::map<int, int> trueOf, falseOf;
};

class LocalWiring {
public:
    BranchEdges run(const ProgramA &program) {
        for (const auto &fun : program.funs) {
            next_ = 2;
            id_.clear();
            number(fun->body.get());
            const int retId = next_++;
            (void)retId;
            wire(fun->body.get(), {retId});
        }
        return edges_;
    }

private:
    BranchEdges edges_;
    int next_ = 2;
    std::map<const Stmt *, int> id_;

    void number(const Stmt *s) {
        if (const auto *b = dynamic_cast<const BlockS *>(s)) {
            for (const auto &x : b->ss) number(x.get());
            return;
        }
        if (const auto *x = dynamic_cast<const IfS *>(s)) {
            id_[x] = next_++;
            number(x->then.get());
            if (x->els) number(x->els.get());
            return;
        }
        if (const auto *x = dynamic_cast<const WhileS *>(s)) {
            id_[x] = next_++;
            number(x->body.get());
            return;
        }
        if (dynamic_cast<const AssignS *>(s) || dynamic_cast<const OutputS *>(s))
            id_[s] = next_++;
    }

    std::vector<int> wire(const Stmt *s, std::vector<int> succ) {
        if (const auto *b = dynamic_cast<const BlockS *>(s)) {
            std::vector<int> cur = succ;
            for (auto it = b->ss.rbegin(); it != b->ss.rend(); ++it)
                cur = wire(it->get(), cur);
            return cur;
        }
        if (const auto *x = dynamic_cast<const IfS *>(s)) {
            const int n = id_.at(x);
            std::vector<int> targets = wireOrSelf(x->then.get(), succ);
            edges_.trueOf[n] = targets[0];
            std::vector<int> rest;
            if (x->els)
                rest = wireOrSelf(x->els.get(), succ);
            else
                rest = succ;
            edges_.falseOf[n] = rest[0];
            return {n};
        }
        if (const auto *x = dynamic_cast<const WhileS *>(s)) {
            const int n = id_.at(x);
            std::vector<int> bodyEntries = wireOrSelf(x->body.get(), {n});
            edges_.trueOf[n] = bodyEntries[0];
            edges_.falseOf[n] = succ[0];
            return {n};
        }
        return {id_.at(s)};
    }
    std::vector<int> wireOrSelf(const Stmt *s, std::vector<int> succ) {
        std::vector<int> r = wire(s, succ);
        if (r.empty()) r = succ;
        return r;
    }
};

// 收集表达式中的全部除法子式（含嵌套）。
void collectDivs(const Expr *e, std::vector<const Binop *> &out) {
    if (const auto *b = dynamic_cast<const Binop *>(e)) {
        collectDivs(b->l.get(), out);
        collectDivs(b->r.get(), out);
        if (b->op == BOp::Div) out.push_back(b);
    }
}

void collectDivsStmt(const Stmt *s, std::vector<const Binop *> &out) {
    if (const auto *a = dynamic_cast<const AssignS *>(s)) {
        collectDivs(a->value.get(), out);
    } else if (const auto *o = dynamic_cast<const OutputS *>(s)) {
        collectDivs(o->e.get(), out);
    } else if (const auto *r = dynamic_cast<const ReturnS *>(s)) {
        collectDivs(r->e.get(), out);
    } else if (const auto *w = dynamic_cast<const WhileS *>(s)) {
        collectDivs(w->cond.get(), out);
    } else if (const auto *i = dynamic_cast<const IfS *>(s)) {
        collectDivs(i->cond.get(), out);
    }
}

}  // namespace

PathResult solveInterval(const Cfg &cfg, const ProgramA &program,
                         int maxRounds, bool refineOnEdges) {
    Lattice<Iv> lat = ivLattice();
    PathResult res;

    std::set<int> widenPoints;
    for (const FunCfg &fc : cfg.funs)
        for (const auto &[id, node] : fc.nodes)
            if (dynamic_cast<const WhileS *>(node.stmt))
                widenPoints.insert(id);

    BranchEdges be = LocalWiring().run(program);
    const FunCfg &fc = cfg.funs[0];

    struct PredEdge {
        int node;
        bool refine;
        bool taken;
    };
    std::map<int, std::vector<PredEdge>> preds;
    for (const auto &[a, b] : fc.edges) {
        PredEdge pe{a, false, true};
        if (refineOnEdges) {
            if (be.trueOf.count(a) && be.trueOf[a] == b)
                pe = PredEdge{a, true, true};
            if (be.falseOf.count(a) && be.falseOf[a] == b)
                pe = PredEdge{a, true, false};
        }
        preds[b].push_back(pe);
    }

    auto computeIn = [&](int p, const std::map<int, IvEnv> &out) {
        IvEnv in;
        auto pit = preds.find(p);
        if (pit != preds.end()) {
            for (const PredEdge &pe : pit->second) {
                IvEnv piece;
                auto it = out.find(pe.node);
                if (it != out.end()) piece = it->second;
                if (pe.refine)
                    piece = refineOnBranch(condOf(fc.nodes.at(pe.node).stmt),
                                           piece, pe.taken);
                for (const auto &[k, v] : piece)
                    in[k] = lat.join(in.count(k) ? in[k] : lat.bot(), v);
            }
        }
        return in;
    };

    std::map<int, IvEnv> out;
    for (int round = 0; round < maxRounds; ++round) {
        bool changed = false;
        for (const auto &[id, node] : fc.nodes) {
            IvEnv in = computeIn(id, out);
            for (const std::string &p : program.funs[0]->params)
                in[p] = Iv{INT_MIN, INT_MAX};

            if (widenPoints.count(id)) {
                auto prev = out.find(id);
                if (prev != out.end())
                    for (auto &[k, v] : in) {
                        Iv pv =
                            prev->second.count(k) ? prev->second.at(k) : lat.bot();
                        v = widen(pv, v);
                    }
            }

            IvEnv o = in;
            if (const auto *a = dynamic_cast<const AssignS *>(node.stmt))
                if (const auto *t = dynamic_cast<const VarRef *>(a->target.get()))
                    o[t->name] = evalIv(a->value.get(), in);

            if (out.count(id) == 0 || !(out[id] == o)) {
                out[id] = o;
                changed = true;
            }
        }
        res.rounds = round + 1;
        if (!changed) {
            res.converged = true;
            break;
        }
    }
    res.out = out;
    return res;
}

std::vector<std::string> divZeroWarnings(const Cfg &cfg,
                                         const std::map<int, IvEnv> &out) {
    std::vector<std::string> warnings;
    for (const FunCfg &fc : cfg.funs)
        for (const auto &[id, node] : fc.nodes) {
            if (!node.stmt) continue;
            std::vector<const Binop *> divs;
            collectDivsStmt(node.stmt, divs);
            const IvEnv &env = out.at(id);
            for (const Binop *d : divs) {
                Iv den = evalIv(d->r.get(), env);
                bool containsZero = !(den.lo > den.hi) && den.lo <= 0 &&
                                    den.hi >= 0;
                if (containsZero) {
                    std::ostringstream line;
                    line << "node " << id << ": divisor "
                         << printExpr(d->r.get()) << " in " << ivText(den)
                         << " contains 0 — possible division by zero";
                    warnings.push_back(line.str());
                }
            }
        }
    return warnings;
}

std::vector<std::string> outputPredictions(const Cfg &cfg,
                                           const std::map<int, IvEnv> &out) {
    std::vector<std::string> lines;
    for (const FunCfg &fc : cfg.funs)
        for (const auto &[id, node] : fc.nodes) {
            const auto *o = dynamic_cast<const OutputS *>(node.stmt);
            if (!o) continue;
            Iv pred = evalIv(o->e.get(), out.at(id));
            std::ostringstream line;
            line << "output node " << id << ": " << printExpr(o->e.get())
                 << " in " << ivText(pred);
            lines.push_back(line.str());
        }
    return lines;
}
```

```cpp
// file: src/main.cpp
// 第 34 章配套程序：路径精炼 vs 流不敏感基线的对照。
//   --check FILE : 对同一程序跑两档区间分析（关/开条件精炼），
//                  打印 output 点预测与除零告警的对比
#include <fstream>
#include <iostream>
#include <memory>
#include <string>

#include "TIPLexer.h"
#include "TIPParser.h"
#include "antlr4-runtime.h"

#include "ast_build.hpp"
#include "cfg.hpp"

#include "symtab.hpp"

class CollectErrorListener : public antlr4::BaseErrorListener {
public:
    std::vector<std::string> messages;

    void syntaxError(antlr4::Recognizer *, antlr4::Token *, size_t line,
                     size_t column, const std::string &msg,
                     std::exception_ptr) override {
        messages.push_back("syntax error line " + std::to_string(line) + ":" +
                           std::to_string(column) + " " + msg);
    }
};

namespace {

struct Parsed {
    std::unique_ptr<tip::ProgramA> ast;
    tip::Bindings bindings;
};

Parsed parseFile(const std::string &path) {
    std::ifstream src(path);
    if (!src) {
        std::cerr << "cannot open " << path << '\n';
        std::exit(1);
    }
    antlr4::ANTLRInputStream input(src);
    TIPLexer lexer(&input);
    antlr4::CommonTokenStream tokens(&lexer);
    TIPParser parser(&tokens);

    CollectErrorListener errors;
    lexer.removeErrorListeners();
    parser.removeErrorListeners();
    lexer.addErrorListener(&errors);
    parser.addErrorListener(&errors);

    TIPParser::ProgramContext *tree = parser.program();
    if (!errors.messages.empty()) {
        for (const std::string &m : errors.messages) std::cout << m << '\n';
        std::exit(2);
    }

    Parsed result;
    result.ast = tip::buildAst(tree);
    result.bindings = tip::resolveNames(*result.ast);
    if (!result.bindings.errors.empty()) {
        for (const tip::Diag &d : result.bindings.errors)
            std::cout << d.text << '\n';
        std::exit(3);
    }
    return result;
}

void reportMode(const char *name, const tip::Cfg &cfg,
                const tip::PathResult &r) {
    std::cout << name << "\n";
    for (const std::string &l : tip::outputPredictions(cfg, r.out))
        std::cout << "  " << l << "\n";
    std::vector<std::string> warns = tip::divZeroWarnings(cfg, r.out);
    if (warns.empty()) {
        std::cout << "  div-zero: (none)\n";
    } else {
        for (const std::string &w : warns) std::cout << "  div-zero: " << w << "\n";
    }
}

}  // namespace

int main(int argc, char **argv) {
    if (argc != 3 || std::string(argv[1]) != "--check") {
        std::cerr << "usage: tipa --check FILE\n";
        return 1;
    }

    Parsed p = parseFile(argv[2]);
    tip::Cfg cfg = tip::buildCfg(*p.ast);

    const int maxRounds = 50;
    tip::PathResult base = solveInterval(cfg, *p.ast, maxRounds, false);
    tip::PathResult refined = solveInterval(cfg, *p.ast, maxRounds, true);

    std::cout << "== interval analysis: flow-insensitive vs path-refined ==\n";
    reportMode("FLOW-INSENSITIVE (no edge refinement):", cfg, base);
    reportMode("PATH-REFINED (condition refinement on branch edges):", cfg,
               refined);
    return 0;
}
```
