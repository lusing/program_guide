# 第 02 章　不可判定性：为什么静态分析注定是近似

## 2.1 理想分析器的画像

第 01 章描绘了静态分析器的工作：不运行程序，就对所有可能运行下结论。
顺着这个目标，很自然会设想一个**理想分析器**：对任意程序，它既能指出所有真实的错误，
又从不误报，还能在有限时间内算完。这样的工具存在吗？

本章给出的答案是理论计算机科学最经典的否定结论之一：**不存在**。
这不是因为现有的工程水平不够，而是可计算性的数学限制——
任何算法都不可能精确地回答关于程序运行行为的非平凡问题。
正因如此，"可靠的近似"不是静态分析的妥协方案，而是它唯一可能的形态。

本章配套程序把三条结论以固定文本打印出来：停机问题的自指论证、Rice 定理、
可靠（sound）与完备（complete）的取舍。正文将逐一给出它们的严格含义。

## 2.2 停机问题：对角化的直觉

### 2.2.1 问题陈述

**停机问题**问：是否存在一个算法 $D$，它读入任意程序 $P$ 的文本和任意输入 $x$，
总能判定 $P$ 在 $x$ 上是会正常停止，还是会永远运行下去？

$$D(\langle P\rangle, x) = \begin{cases} \text{“停止”} & \text{若 } P(x) \text{ 最终停止} \\ \text{“循环”} & \text{若 } P(x) \text{ 永远运行} \end{cases}$$

1936 年，图灵证明了这样的 $D$ 不存在。论证的核心手法叫**对角化（diagonalization）**：
假设 $D$ 存在，就用它构造一个"专门让 $D$ 说错"的程序。

### 2.2.2 自指程序的构造

假设 $D$ 存在，构造程序 $H$：

```
H(y):
    if D(y, y) = “循环” then 立即停止
    if D(y, y) = “停止” then 永远循环
```

$H$ 读入一个程序文本 $y$，先让 $D$ 判断“程序 $y$ 在输入它自己的文本 $y$ 时会怎样”，
然后做出**与预测相反**的行为。现在把 $H$ 自己的文本 $\langle H\rangle$ 喂给它本身，考察 $H(\langle H\rangle)$：

- 若 $D(\langle H\rangle, \langle H\rangle)$ 说“停止”，$H$ 按定义必须永远循环——$D$ 说错了；
- 若 $D$ 说“循环”，$H$ 按定义立即停止——$D$ 又说错了。

两种情况下 $D$ 都错误，与“$D$ 总能判定”的假设矛盾，故 $D$ 不存在。
这里最关键的机关是**自指**：让一个程序的输入恰是它自己的文本，
于是对假设中的判定器形成了一条无法满足的对角线。

### 2.2.3 从停机问题到“是否可能除零”

本书关心的不是停机本身，而是“程序会不会出错”。同样的对角化可以直接搬过来。
假设存在分析器 $A$，对任意程序都能判定“它是否**可能**除零”。
利用可计算性理论中的**递归定理（recursion theorem）**，可以构造一个程序 $Q$，
$Q$ 在运行时能获得自己的文本 $\langle Q\rangle$，然后：

- 让 $A$ 分析 $\langle Q\rangle$；
- 若 $A$ 说“安全”，$Q$ 立刻执行一次除零；
- 若 $A$ 说“可能除零”，$Q$ 正常返回。

再考察 $Q$ 自身：$A$ 说安全时 $Q$ 真的除零，说可能出错时 $Q$ 偏偏安全——$A$ 必错，矛盾。
因此“对任意程序判定其是否可能除零”和停机问题一样，**不可判定**。
本章输出里的第一段话，就是这个构造的文字版。

也可以换一个更工程化的视角理解两者的关系：假如能判定“程序是否可能除零”，
我们就能在任意程序的每一个停止点上把“正常停止”改写成触发错误、把“永不停止”改写成不触发，
从而用这个分析器判定停机问题。停机问题不可判定，故前者也不可能——
这在可计算性理论中称为**归约（reduction）**：把一个已知不可判定的问题化归为新问题。

## 2.3 Rice 定理：所有非平凡语义性质都不可判定

停机问题只是否定结论的开端。1953 年，Rice 给出了一个范围广得多的定理：

> **Rice 定理：** 程序所计算的（部分递归）函数的任何**非平凡语义性质**，都是不可判定的。

这句话有两个关键词。

- **语义性质**：关于程序“做什么”的性质，而不是“怎么写”的性质。
  “变量名是否以 `_` 开头”是语法性质，可以判定；“程序是否总会输出正数”是语义性质。
- **非平凡**：该性质既不是所有程序都满足、也不是所有程序都不满足——
  存在满足它的程序，也存在不满足它的程序。“会停止”“不存在内存泄漏”“计算结果恒为非负”，
  都是非平凡语义性质。

Rice 定理的实用推论非常干脆：我们在工程上想问的绝大多数运行时问题——
“总能输出正数吗”“有没有内存泄漏”“会不会把整数溢出到缓冲区外”——
**都没有精确的算法答案**。本书第 03–12 章实现的类型分析、第 17 章之后的各种数据流分析，
没有一个、也不可能有一个是“对所有程序既不漏报也不误报”的。

## 2.4 可靠与完备：用集合包含关系说清楚

既然精确不可能，分析器只能在两个方向的错误之间选择立场。先把两类错误命名清楚。

- **漏报（false negative）**：错误在某条运行中真的发生，分析器却没有告警。
- **误报（false positive）**：分析器发出告警，但对应的运行其实不存在或错误不可能发生。

对任意程序 $P$，记：

- $\mathrm{Err}(P)$：错误**真正会发生**的位置（或运行）的集合；
- $\mathrm{Warn}(P)$：分析器**发出告警**的位置的集合。

那么分析质量可以用这两个集合的包含关系精确刻画。

### 2.4.1 可靠（sound）：$\mathrm{Err}(P) \subseteq \mathrm{Warn}(P)$

可靠的分析保证：错误真发生时，分析器一定提前告警——**没有漏报**。
包含关系允许 $\mathrm{Warn}$ 比 $\mathrm{Err}$ 大，所以可靠分析**可能误报**。
“宁可误报，不可漏报”是验证工具与缺陷发现工具的默认立场：
漏掉一个真实的空指针解引用，代价远高于让程序员多核查几条可疑告警。

### 2.4.2 完备（complete）：$\mathrm{Warn}(P) \subseteq \mathrm{Err}(P)$

完备的分析保证：每条告警都对应真实错误——**没有误报**。
它不保证真实错误全部被指出，所以完备分析**可能漏报**。
“不告警时一定没问题”，但沉默不代表程序安全。

### 2.4.3 四格总览

| 立场 | 集合关系 | 漏报 | 误报 | 可行性 |
|---|---|---|---|---|
| 既可靠又完备 | $\mathrm{Warn}=\mathrm{Err}$ | 无 | 无 | 不可能（等于精确判定） |
| 可靠（sound） | $\mathrm{Err}\subseteq\mathrm{Warn}$ | 无 | 可能 | 可实现，本书的主线 |
| 完备（complete） | $\mathrm{Warn}\subseteq\mathrm{Err}$ | 可能 | 无 | 可实现，部分优化采用 |
| 两者都不保证 | 无包含关系 | 可能 | 可能 | 只能作启发式提示 |

需要特别说明的是“既可靠又完备”那一格：若分析器对任意程序都满足
$\mathrm{Warn}=\mathrm{Err}$，它就是 Rice 定理所说的“对非平凡语义性质的精确判定器”，
而这类判定器已被证明不存在。所以这一格不是“很难做到”，而是“在数学上不可能”。

### 2.4.4 优化场景里的方向反转

本书后面会遇到一个微妙之处：在**编译优化**中，可靠性的方向是反过来表述的。
优化器若声称“这两处表达式等价、可以合并”，它必须保证在**所有运行**下等价——
一次误判就会改变程序语义。因此优化采用的是“安全的下近似”：
只有确有把握时才动手，宁可放弃优化机会（漏掉可优化点），不可错误优化。
第 17、19 章实现常量分析并与 LLVM 对照时，会再次回到这个方向问题。

## 2.5 精度—成本谱系

放弃精确之后，剩下的问题不是“做不做近似”，而是“近似得多粗”。

要区分的程序状态越多，分析就越精确：跟踪每个变量的具体整数值比只跟踪正负号精确，
区分调用路径（第 24 章上下文敏感）比不区分精确。但每多区分一类状态，
迭代中需要维护和传播的信息就成倍增长——计算时间与存储空间的成本随之上升。

于是所有静态分析都落在一条**精度—成本谱系**上：一端是粗糙但极快的分析
（如本书第 17 章的符号分析，每个变量只有五种可能），
另一端是逼近精确状态枚举、成本高昂的分析。静态分析的工程艺术性，
本质上就是在这条谱系上为眼前的问题选择一个落点：保证可靠的前提下，
用尽量小的成本换取够用的精度。后续每一章都会同时给出分析结果与它能处理的程序规模，
让这条谱系可以被实际观察，而不只是口头断言。

## 2.6 不可判定不等于无能为力

读到这里可能产生一个疑问：既然一切非平凡问题都不可判定，静态分析为何仍然有用？
关键在于不可判定性结论的**适用范围**——它断言的是不存在对**所有程序**都正确的算法，
并不意味着对**具体程序**无法获得可靠结论。

- 对一个给定的具体程序，如果它的状态空间有限，原则上可以枚举全部状态精确回答；
  只是状态数随变量数指数膨胀（第 07 章的控制流图会让这一点可见），
  不可扩展，才需要对无穷多的程序都能统一工作的近似技术。
- 单调数据流框架（第 14–16 章）保证：无论程序多大，迭代都在有限步停止，
  且停止时得到的不动点在可靠性意义下覆盖所有真实运行。
  我们放弃了“精确”，换来了“必然终止且结论可靠”——这是一笔数学上可证明划算的交换。
- LLVM 实验台提供另一重经验保障：从第 08 章起，每个被分析的程序都能真实执行，
  我们可以用成批的具体输入检验“每个具体值确实落在预测集合中”。
  经验检验不能代替可靠性证明，但能抓住证明与实现之间的落差。

## 2.7 工程注意点

- **先声明可靠性方向，再设计分析**：动手写传播规则之前，先明确这是“可能出错”的上近似
  （$\mathrm{Err}\subseteq\mathrm{Warn}$）还是“确有把握”的下近似。方向错了，
  后续每一条规则的正确性讨论都会失焦。
- **误报是要管理的成本，而不是要消灭的错误**：在可靠分析中追求零误报等于追求精确判定，
  注定失败；实际目标是把误报控制在使用者能接受的比例。
- **本章程序只陈述结论，不做证明**：真正的证明工具（格、Galois 连接）要到第 12–16 章才建立；
  这里让直觉先行，理论随后补上，是本书一贯的推进顺序。

## 2.10 小结

停机问题与 Rice 定理为全书划定了边界：任何算法都不可能对所有程序精确回答
非平凡的运行时问题。静态分析因此只能是近似，而近似有且只有两种纯粹立场——
可靠（不漏报，可能误报）与完备（不误报，可能漏报），两者兼得在数学上不可能。
本书此后全部采用可靠立场：宁可多报，也要覆盖每一条真实运行。
