# 第 1 章　静态分析：在程序运行之前知道它会做什么

## 1.1 一个朴素的问题

拿到一个程序，最直接的理解方式是**运行它**：给它输入，观察输出。但运行只能一次回答一种情况。
而真正令程序员不安的问题几乎都带有"所有"或"可能"这样的量词：

- 这个函数对**所有**输入都不会除零吗？
- 这块内存在**任何一条**执行路径上都不会泄漏吗？
- 用户提交的数据**有没有可能**流到一条危险的 SQL 语句里？

测试用有限次运行去逼近这些问题，它永远无法覆盖输入空间里的全部情况。
**静态分析**研究的是另一条路：不运行程序，只通过检查程序文本，
对程序在**所有可能运行**下的行为给出有根据的结论。

本书以 Anders Møller 与 Michael I. Schwartzbach 的《Static Program Analysis》为理论骨架，
在一门专为教学设计的小型语言 TIP 上，把类型分析、数据流分析、指针分析、抽象解释逐一实现出来。
前端用 ANTLR4 把程序文本翻译成可推理的结构；理论用格与不动点把"近似"变成可计算的对象；
另外借助 LLVM 的 ORC JIT 让程序真实运行，用具体执行反过来检验分析结论是否站得住脚。

## 1.2 贯穿全书的两句话

先看一个极简的程序片段，它会在本章被三种工具分别审视：

```tip
x = input;        // 从输入流读一个整数
output x / x;     // 输出 x 除以 x
```

`input` 是 TIP 的特殊表达式：程序每次运行到它，就从输入流取得一个任意整数。
于是这段程序有一个无穷大的输入空间——所有整数。问一个具体问题：**第二行可能除零吗？**

- 若这次运行读到的是 5，则 `5 / 5 = 1`，平安无事；
- 若读到的是 0，则 `0 / 0` 在 TIP 的整数语义下是一个运行时错误。

对任何一次**具体**运行，答案非此即彼；但程序本身不固定输入，
"可能除零吗"问的是：**输入空间中是否存在一条导致错误的运行**。

## 1.3 三种工具，三条知识边界

同一个程序交给三种工具，它们各自知道的东西差别很大。本章的配套程序把这三段话原样打印出来。

### 编译器的视角

编译器知道程序**是否合语法**，知道每个表达式的**类型**（除法两侧都是 `int`），
然后忠实地生成可执行代码。它的职责是把"这次运行"正确地执行出来，
而不是回答"在所有运行下会怎样"。标准编译器不会因为 `x` 可能为 0 就拒绝这段程序——
是否除零取决于运行时读到什么，这超出了编译器被要求回答的问题范围。

### lint 风格规则检查器的视角

lint 一类工具的工作方式是**模式匹配**：维护一个可疑写法的规则库，
逐条在程序文本上寻找匹配。它擅长发现硬编码的危险常量、已知的易错 API 用法。
但模式匹配的覆盖面取决于规则库是否恰好收录了眼前这种形状：
本例除法两侧是**同一个变量**，是否危险取决于这个变量能取到什么值，
纯文本规则没有"取值集合"的概念，很可能悄悄漏报。

### 静态分析器的视角

静态分析器回答问题的依据是对运行空间的**可靠近似**：
`input` 可能产生任意整数，于是它把 `x` 的可能取值近似为"所有整数"——这个集合包含 0，
因此除法的分母可能为 0，应当告警。注意它为"可靠"付出了代价：
它也会把那些**事实上**不会读到 0 的部署情形报成可能。这种"宁可多报"的取向不是缺陷，
而是下一章将要形式化的、在不可判定性面前唯一可守的立场。

三者的根本差别可以概括为一句话：**编译器让单次运行成为可能，
测试覆盖少量运行，静态分析试图对全部运行同时下结论。**

## 1.4 把问题说精确：执行、输入空间与性质

为了让"对全部运行下结论"不再只是一句口号，先引入三个贯穿全书的记号。

- 把程序记作 $P$，它的合法输入构成一个集合 $I$（在本例中是整数集 $\mathbb{Z}$）。
- 程序在一个具体输入 $i \in I$ 上的执行，记作 $\llbracket P \rrbracket(i)$：
  它要么正常结束并给出结果，要么因为除零等错误而中断。
- 我们关心的性质记作一个谓词 $\varphi$，例如
  $\varphi(i) =$ "在输入 $i$ 下，$P$ 不发生除零"。

于是：

- **动态测试**做的是：挑一个有限子集 $\{i_1,\dots,i_k\} \subseteq I$，
  逐一检查 $\varphi(i_1),\dots,\varphi(i_k)$ 是否成立；
- **静态分析**做的是：不实际计算任何 $\llbracket P \rrbracket(i)$，
  仅凭 $P$ 的文本，回答 "$\forall i \in I,\ \varphi(i)$ 成立吗"
  （验证型问题）或 "$\exists i \in I,\ \neg\varphi(i)$ 成立吗"（缺陷型问题）。

这组记号也解释了为什么静态分析必然是**近似**：
$I$ 往往无穷大，而 $\llbracket P \rrbracket$ 的精确信息（第 2 章将证明）根本无法在有限时间内取得。
分析器用一个可以有限计算的对象去代替无穷的运行集合，
这个代替对象称为**抽象**，构造它并保证结论可靠的一般理论就是第 22 章的抽象解释。

## 1.5 第一次抽象：把 input 看成"所有整数"

本例已经隐含了全书最重要的思想萌芽。`input` 在单次运行中是一个确定的整数，
但分析器不跟踪单次运行，它需要一个能**同时代表所有可能运行**的说法：

> 不把 `x` 看成"某个还不知道的整数"，而把它看成一个**集合** $\mathbb{Z}$。

从此，程序里每个变量在每个程序点上都不再绑定一个值，而是绑定一个**值的集合**。
赋值、运算都被改写成集合层面的操作。当除法的分母集合包含 0，
我们就知道"存在一条运行会除零"。这个朴素的想法在第 24、29 章会发展成
符号分析与区间分析，在第 23–26 章会得到严格的代数基础——格与不动点。

## 1.6 静态分析的四类应用

静态分析不是单一工具，而是一类技术在四种问题上的落地。本章程序把四类应用原样列出。

1. **程序验证**：目标是证明性质在所有运行下成立，例如"指针永远不为空""数组下标永远不越界"。
   验证型分析采用可靠近似：只要分析器声称性质成立，它就必须在任何运行中都成立。
2. **缺陷发现**：目标是在部署前主动定位除零、资源泄漏、缓冲区越界。
   这类工具宁可容忍一些误报，也要保证真实缺陷不被漏掉。
3. **编译优化**：常量传播、死代码消除、寄存器分配，本质上都依赖"这个表达式在所有运行下值不变吗"
   一类信息。LLVM 等工业编译器的中端就是一套庞大的静态分析流水线，
   本书第 24、27、39 章会把我们的玩具分析与 LLVM 的相应 pass 并排对照。
4. **安全分析**：信息流（污点）分析追踪不可信数据能否流到敏感操作，
   也用于筛查程序是否具有某种恶意行为模式。

## 1.7 本书的三件工具如何分工

在进入理论之前，先说明 ANTLR4、格与不动点理论、LLVM 在实验台中各自扮演的角色。

- **ANTLR4 负责"读懂程序"**：它根据文法把 TIP 源文本变成一棵抽象语法树（第 4–9 章），
  再由我们在树上完成作用域解析（第 11 章）与控制流图构造（第 12 章）。
  没有结构化的程序表示，任何推理都无从谈起。
- **格与不动点负责"算出近似"**：循环让程序的信息依赖形成环，
  无法用一遍直接计算。第 23–26 章将证明，在一个称为"格"的代数结构上反复迭代，
  必然在有限步达到稳定的不动点，而这个不动点就是分析结果。
- **LLVM 负责"让程序真跑起来"**：我们把 TIP 翻译成 LLVM IR 并用 ORC JIT 执行（第 13 章起）。
  之后每实现一个分析，都可以挑选大量具体输入真实运行，
  检查每个具体值确实落在分析器预测的抽象集合之内——
  用经验证据检验可靠性，而不是只相信自己的证明。

## 1.8 工程注意点

- **输出必须确定**：本章及之后每一章的程序输出都不允许出现地址、时间、线程编号等随机器变化的内容，
  因为教程用逐字节对账来保证"书上看到的输出就是你会得到的输出"。
- **分析结论与告警分开措辞**："x 的可能取值集合包含 0"是分析事实，"可能除零"是由它推出的告警。
  全书保持这两个层次的区分，因为可靠性证明针对的是前者。
- **宁可让示例小**：两句话的程序足以暴露"单次运行"与"所有运行"的差别；
  示例越小，原理与代码之间的距离越短。

## 1.11 小结

静态分析的独特之处在于量词：测试和编译器围绕单次运行工作，
而分析器要在不运行程序的前提下，对所有可能运行下结论。
实现这一点的基本手法是**抽象**——用值的集合代替具体的值；
而代价是**近似**，分析器必须在"误报"与"漏报"之间选择立场。
下一章将证明，这种代价不是工程能力问题，而是可计算性的根本限制：
精确回答非平凡的运行时问题，在数学上不可能。
