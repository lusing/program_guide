# 第 13 章　符号格：第一个数据流抽象域

从本章起，本书进入第四篇——格与数据流分析。类型篇回答的
问题是"程序的结构是否自洽"，答案是二值的：约束系统要么有解
要么无解。接下来的四章建立另一类分析：对每个程序点报告"运行
时值可能是什么"，答案是近似的、分级的、且永远可靠的。本章以
最小的抽象域——符号格——完整走通"抽象域、传递函数、单趟
执行"三件事，并刻意暴露它们在循环面前的失效，为第 14 章的
格构造、第 15 章的方程组、第 16 章的不动点算法铺路。

## 13.1 为什么需要抽象

考虑一个最朴素的问题：程序点 p 处变量 x 的值是多少？类型篇
的机器会回答"x 是整数"——这是结构层面的全部知识，对取值
一无所知。而许多实际关切恰恰关于值：`100 / x` 会不会除以零？
`output x` 会不会打出负数？`while (x > 0)` 能不能终止？回答
它们需要另一类分析，其对象是**值域**而不是类型域。

值域本身是无穷的：一个 int 变量可以取 2³² 个具体值（按 TIP
的语义模型甚至更多）。对每个具体值逐一追踪显然不可行，也
没有必要——"除以零吗"这样的问题不关心 x 是 5 还是 7，只
关心它是否可能为 0。于是做第一层压缩：**把整数按符号分成
三类**——负数、零、正数。三类之外再加两个特殊元素，构成
一个五个元素的有限域：

- −：某个确定的负数（不知道是哪个）；
- 0：恰好是零；
- +：某个确定的正数；
- ⊤（顶）：三者皆可能，即"任意整数"；
- ⊥（底）：不可达，"没有信息"，通常是路径不可行或尚未
  分析到的占位。

这个压缩用一个具体化函数（concretization）γ 严格表述：
γ(−) = {n ∈ ℤ | n < 0}，γ(0) = {0}，γ(+) = {n ∈ ℤ | n > 0}，
γ(⊤) = ℤ，γ(⊥) = ∅。每个抽象元素**代表一组具体值**，抽象
分析的每一条结论都是关于这组值的全称陈述：说"x 是 +"，
意思是"x 的运行时值属于 {1, 2, 3, …}，绝不可能是 0 或负数"。
"绝不"二字是可靠性的承诺来源——第 13.10 节会把承诺变成
论证。

五类元素对"除以零"这样的问题已经够用（0 与 −/+ 分开了），
对"是奇数吗"则完全无能为力——符号抽象根本看不到奇偶。
这不是缺陷，是**抽象域的设计选择**：每个域只保留它打算
回答的那类问题的信息。第 20 章的区间域保留大小关系，第 17
章的常量域保留精确值，各回答各自的问题族。学会"按问题选
域"，比记住任何具体域都重要。

还有一个贯穿全书的视角转换值得现在点明。类型篇的推理
对象是**程序文本**：一个表达式有一个类型，事实挂在语法
节点上。数据流分析的推理对象是**执行**：一个程序点有一组
可能的运行时状态，事实挂在控制流图的节点上。同一份 AST、
同一张 CFG（第 7 章构建的），承载了两种截然不同的知识。
从本章起，"程序点"（program point，第 7 章 CFG 节点编号）
成为一切结论的坐标。

### 13.1.1 三类典型问题的形状

把"值的问题"具体化，本章读者应能对下列每一条立刻说出
它需要的最小信息量——这是选择抽象域的第一项训练：

**"100 / x 会不会除以零？"** 需要知道 x 是否可能为 0。
符号域恰好把 0 立为独立元素，回答它是零成本的：x 的
抽象值是 0，则必然除零；是 − 或 +，则绝无可能；是 ⊤，
则"可能，分析无法排除"。注意三种回答对应三种工程动作：
第一种的下游是报错或插入防御（第 21 章的验证器会做），
第二种的下游是优化（除法可以放心保留），第三种的下游
是"报告存疑"——抽象域天生三值（确定安全/确定危险/
无法判定），把二元问题升级为三值回答，是静态分析的
基本礼仪，也是它与"断言式"检查工具的分野。

**"output x 会不会打出负数？"** 需要沿控制流追踪 x 的
符号到 output 点。这正是本章分析的主菜——同时它立刻
暴露了追踪的两个技术前提：要有"到哪一点"的坐标（CFG
程序点，第 7 章），要有"沿边合并"的规则（join，13.2
节）。问题本身一句话，答案的机器是一整章。

**"while (x > 0) 能不能终止？"** 这是最诱人也最危险
的问题。符号域只答"符号"，答不了"大小趋势"：x 从正数
出发每圈加一，永远为正——符号域可以断言循环条件始终
可能成立（x ∈ γ(+)），但"终止"需要"x 严格递减"这类
序关系知识，超出符号域的表达力。**知道一个域不能回答
什么，与知道它能回答什么同样重要**：本条是第 20 章
区间域、第 25 章终止性专题的伏笔，现在记下"符号域答
不了"这个边界即可。

三条问题共享同一个回答框架：程序点坐标 + 值的抽象域 +
沿 CFG 的传播规则。框架是本章真正的产品，符号域只是
插进框架的第一块样板。

### 13.1.2 为什么不用"跑一遍"代替分析

一个诚实的疑问：想知 output 处 x 的符号，直接用几个输入
跑几遍程序不就行了？模拟执行（测试、fuzzing、concolic）
与静态分析的差异，本章值得说透，因为符号格恰好是差异
最清晰的标本。

跑一遍给出的是**一个**具体值：输入 5，得 y=+、x=+——
正确，但只对这一个输入。换输入 0 呢？循环一次不进，
output 处 x 未赋值（未定义行为）。换输入 −3？同样零圈。
测试发现不了"未初始化"这个坑，除非测试者**想到**要喂
非正数——而"想到所有输入类"正是人类测力的天花板。
静态分析则把全部输入类一次性纳入：input 被抽象为 ⊤
（13.6.2），从第一天起就代表"任何整数"，任何输入都逃
不出 γ(⊤) = ℤ 的覆盖。

差别可以压缩成一句话：**测试在具体值空间采样，分析在
抽象空间证明**。采样的结论是"喂过的输入没出事"，证明
的结论是"所有输入下，出事的情形都被覆盖"。代价同样
悬殊：分析对循环程序给出 ⊥ 白卷（本章）——它宁可说
"不知道"也不说"没事"，而白卷恰恰是它诚实的标志；
第 16 章修好之后，它对每一条结论都附带"对所有执行"
的担保，这是任何有限次测试都无法给出的担保强度。

二者的正确关系是互补而非替代：静态分析圈定"值得测试
的输入类"（抽象值为 ⊤ 的变量就是 fuzzing 的靶子），
测试回收分析无法到达的角落（库函数内部、真实硬件行为）。
本书教分析，但读者应带着"分析是测试的放大器"这个
工程观离开本章。

## 13.2 符号格：域、序与最小上界

五个抽象元素还只是"域"（domain）；要在这里面做推理，需要
**序**。符号域上的偏序 ⊑ 直觉是"信息更多"：⊥ 表示什么都
不知道，− 表示确定的负号——后者信息更多，故 ⊥ ⊑ −。
−、0、+ 三者互不包含信息，互不可比；⊤ 包含全部三种可能，
是最大元。画成 Hasse 图：

```
        ⊤
      / | \
     −  0  +
      \ | /
        ⊥
```

自下而上读：底在最低处，顶在最高处，三个具体符号悬在中间
彼此平级。偏序的三条公理在此逐一可验：自反（x ⊑ x，任何
元素与自己信息一样多）；反对称（x ⊑ y 且 y ⊑ x 则 x = y）；
传递（⊥ ⊑ − 且 − ⊑ ⊤）。五元格是格论的教科书第一例，规模
虽小，公理俱全。

序刻画"信息多少"，而分析中最频繁的动作是**合并**：两条
控制流路径在汇合点相遇，两条路径各自携带的信息要合起来。
合并的数学形态是最小上界（least upper bound，join，记 ⊔）：
x ⊔ y 是"既包含 x 的信息、又包含 y 的信息"的最小元素。
符号域上的 join 表逐格枚举：

| ⊔ | − | 0 | + | ⊤ | ⊥ |
|---|---|---|---|---|---|
| **−** | − | ⊤ | ⊤ | ⊤ | − |
| **0** | ⊤ | 0 | ⊤ | ⊤ | 0 |
| **+** | ⊤ | ⊤ | + | ⊤ | + |
| **⊤** | ⊤ | ⊤ | ⊤ | ⊤ | ⊤ |
| **⊥** | − | 0 | + | ⊤ | ⊥ |

读三行就够：− ⊔ 0 = ⊤（一路说负、一路说零，只能取"任意"）；
x ⊔ x = x（同一路径重复合并不损失）；⊥ ⊔ x = x（⊥ 是合并
的单位元——一条"没有信息"的路径不拖累另一条）。最后一行
正是第 13.7 节单趟执行能够"看似工作"的原因，也是它出错
的方式，见下。

与 join 对偶的是最大下界（meet，⊓）：x ⊓ y 是"同时满足
x 与 y 的信息"的最大元素。符号域上 − ⊓ 0 = ⊥（一个数不能
既负又零）。meet 在本章不参与算法，但格的定义要求二者俱在，
且第 18 章 must 类分析（可用表达式、非常忙）会以 meet 为主角。
现在先把 meet 的表留给读者按对偶性自证。

格还有一个纯代数的视角：join 满足幂等（x ⊔ x = x）、交换
（x ⊔ y = y ⊔ x）、结合（(x ⊔ y) ⊔ z = x ⊔ (y ⊔ z)）三条
定律。幂等保证重复合并无害；交换与结合保证**合并的次序与
分组无关**——这是第 16 章 worklist 算法"以任何顺序处理
程序点都收敛到同一答案"的代数根源。三条定律在五元格上
可以逐格验算（25 个有序对，工作量正好够一次习题），它们的
一般证明来自格的公理化定义。

### 13.2.1 为什么恰好是这五个元素

域的设计值得倒过来问一遍：为什么不是三个（−、0、+）？
为什么不是六个、七个？

三个元素的版本（丢掉 ⊥ 与 ⊤）看似更简，实则两头都缺。
缺 ⊤：入口处参数的符号是什么？input 的返回值是什么？没有
"任意"元素，边界条件无处安放——要么谎称参数是 +（不可靠），
要么把分析拒之门外。缺 ⊥：汇合点若有一条路径还没算完
（本章单趟正是如此）、或一条路径根本不可行（除数为零的
分支），拿什么占位？⊥ 是"无信息"与"不可达"的公共名字，
去掉它，分析的每条边界都会漏。

七个元素的版本（把 {0,+}"非负"与 {−,0}"非正"也收进来）
则立刻更精确：sCompare 可以返回 {0,+} 而不是 ⊤，`x > 0`
的测试结果有了用武之地。那为什么本章不直接上七元格？
答案是**教学次序**：五元格是"域—序—join—γ—传递函数"
全流程的最小实例，每一格都能在纸上验算；七元格的 join
表有四十九格，论证密度翻倍而新思想为零。更重要的是，
"加一个元素就多一分精度"的升级路径本身就是教材——
13.12 节的拓展练习让你亲手做这次升级，做过的手比看过的
眼记得牢。抽象域永远可以更细，设计的品味在于"为要回答
的问题恰好够细"：本章要回答的是"除以零吗""是正吗"，
五元格恰好够；要回答"比较结果如何"，就加 {0,+}；要回答
"差多少"，就换区间域（第 20 章）。

还要防一个对称的误解：⊥ 与 ⊤ 不是"第六、第七种符号"，
而是域的**结构元素**——它们的存在让 join 有单位元、让
偏序有端点、让"尚未分析"与"不可达"有合法的载体。
三个具体符号（−、0、+）回答问题，两个结构元素（⊥、⊤）
让问答这件事本身成为可能。

### 13.2.2 把 Hasse 图读成计算

Hasse 图不只是示意图，它编码了格的全部运算，值得练出
"看图算 join"的条件反射。规则有两条：**join 看最低公共
祖先**（图上从两个元素各向上走，第一个共同到达的点），
**meet 看最高公共后代**（对称地向下走）。用图验算本章
用到的每个事实：− ⊔ 0：从 − 向上只能到 ⊤，从 0 向上只能
到 ⊤，公共祖先唯有 ⊤——正是表里的值；⊥ ⊔ −：⊥ 向上一步
即可到 −，− 的最低公共祖先是自己——单位元身份一目了然；
x ⊔ x：同一元素向上走零步，公共祖先是自己——幂等律
在图上是平凡的。同样地，meet：− ⊓ 0 向下走，公共后代
唯有 ⊥——"既负又零"不存在，恰是图的读法。

高度（height）也从图上直接读出：最长严格上升链
⊥ ≺ − ≺ ⊤ 有两级，故高度为 2。这个数在 13.11 节会变成
迭代次数上界的原料：**格的高度 × 每点的可能上升次数**
决定不动点迭代的收敛速度。小格的工程红利在此兑现——
高度 2 的域，迭代几乎瞬间收敛；第 17 章常量域高度为 3
（⊥ ≺ c ≺ ⊤），第 20 章区间域高度与整数范围成正比
（那时才需要 widening 这种重炮）。

最后记一个读图纪律：Hasse 图**只画覆盖关系**（x ≺ y 且
中间无第三元素时才连边），非覆盖的序关系要靠传递性补全。
初读者有时把"− 与 + 之间没有边"误读为"不可比"，其实是
"不可比"——两条路径无论如何走都不会在中间元素相遇；
而对 ⊥ 与 −，边存在意味着 ⊥ ≺ − 严格成立。图上"没有
边"与"不可比"是两回事，传递闭包先于一切判断。



逐字面把五元格的序检查一遍：⊥ ⊑ −（无信息 → 确定负，
信息增加）；− ⋢ 0（"确定负"与"确定为零"谁也不包含谁）；
− ⊑ ⊤（确定负 ⊆ 任意整数）。三条判例分别展示了序的
三种判断结果：成立、不成立、成立——而任何"数值直觉"
（− 比 0 小，所以 − ⊑ 0？）都会在第二条判例上翻车。
符号域上没有天然的数值序，只有信息序：**⊑ 读作
"至多是"而不是"小于等于"**。x ⊑ y 的规范读法是
"x 的信息是 y 的信息的一部分"，或等价地，γ(x) ⊆ γ(y)。
此后全书凡见 ⊑，一律默念这个读法。

### 13.2.3 ⊥ 在本章出现过的四副面孔

⊥ 是全章最忙碌的元素，也是最容易被误读的元素。它在
本章先后以四种身份出场，把它们并排放一次，误解就无处
藏身。

**面孔一：路径不可达**（13.4 的除法表）。除数为零时
执行中止，中止后没有状态需要描述，抽象结果取 ⊥——
γ(⊥) = ∅ 与"没有任何到达此处的结果"精确对应。

**面孔二：事实未建立**（13.6.1 的缺键约定）。entry
环境里没有 y 的键，读取 y 得 ⊥——这不是说 y 不可达，
而是说分析还没有走到建立 y 的赋值。单趟语境下"未
建立"与"不可达"的后果相同（γ 是空集，没有具体状态
被覆盖），但在第 16 章的不动点语境里，"未建立"会
被迭代修正，"不可达"永远保持空集——两个面孔届时
分道扬镳。

**面孔三：合并的单位元**（13.2 的 join 表）。⊥ ⊔ x
= x——一条没有信息的路径不拖累另一条。这条代数性质
让"缺席的前驱"与"缺席的键"可以安全地参与合并。

**面孔四：分析的诚实白卷**（13.8 的 output 行）。分析
能力不足时，输出 ⊥ 而不是硬猜——⊥ 是"我不知道"的
正式写法，是分析器对自己边界的如实陈述。

四副面孔共享同一个数学身份（γ(⊥) = ∅）却服务四种
不同的语境；识别"眼前的 ⊥ 是哪一副面孔"因此成为
读分析输出的基本技能——13.8.3 的第三层读法（读缺陷）
本质上就是面孔鉴别。

## 13.3 从具体到抽象：γ 的两条纪律

第 13.1 节给出了 γ 的定义。要让它成为分析的基石，还需两条
纪律，它们合起来刻画"抽象域是具体域的合法压缩"。

**纪律一：γ 对 join 恰好是并。** γ(x ⊔ y) = γ(x) ∪ γ(y)。
在符号域上这条逐格可验：γ(−) ∪ γ(0) = 负整数 ∪ {0}，恰好
是"既可能负也可能零"的全部具体值，而它没有更小的抽象
代表（− 与 0 都覆盖不全），故 join 必须给 ⊤。并结构完整
无漏。这一点并非所有抽象域都做得到——某些域的 join 只能
保证 γ(x ⊔ y) ⊇ γ(x) ∪ γ(y)（合并结果覆盖两个输入，但可能
多覆盖一些）。符号域恰好精确，这使它的分析结论在"域内"
无可挑剔；精确与否只取决于传递函数。

**纪律二：γ 单调。** x ⊑ y 蕴含 γ(x) ⊆ γ(y)。信息越多，
代表的具体值集合越小。这条让"以抽象序比较"成为"以集合
包含比较"的安全替身：分析器内部的每次"上升"（从 − 升到
⊤）对应外部结论的放宽（从"必负"放宽到"任意"），绝不
反向收紧——**分析从不撤回已经给出的宽容**，只可能变得更
保守。单向性是后面一切迭代算法敢从 ⊥ 出发逐步上升的前提。

两条纪律合起来还有一个推论：γ(⊥) = ∅ 与 γ(⊤) = ℤ 自动
成立（⊥ 是最小元、⊤ 是最大元，经单调性与"γ 全体并集
= ℤ"夹出）。底与顶在语义上从来不是两个"新值"，而是
"无"与"全部"的占位。初学格论最常见的误解是把 ⊥ 当成
某种特殊整数——它什么整数都不代表，它代表"此路不通"或
"此问未答"。

### 13.3.1 γ 之外还有一个方向：α 的预告

细心的读者会注意到，13.3 只讲了从抽象到具体的 γ，没有讲
反向——给定一组具体值，"最佳"的抽象元素是什么？这个方向
的函数叫抽象化函数（abstraction function）α：℘(ℤ) → D，
定义为 α(S) = 包含 S 的最小抽象元素（对序 ⊑ 而言）。α 与
γ 是一对伴随：α(S) ⊑ x 当且仅当 S ⊆ γ(x)。这条性质叫
**Galois 连接**（Galois connection），是抽象解释理论的
中心构件——它保证"抽象侧的推理"与"具体侧的事实"互相
翻译时不产生歧义。

本章的实现里找不到 α，这是有意的省略还是偷懒？两者都不是。
符号域的五个元素在定义时就是**按意图命名的**：− 的意思
就是"负数全体"，0 的意思就是"零"，α 对它们恒等（对单点
集合 {−5} 而言 α = −，对 {−3, 2} 而言 α = ⊤，与直觉全同）。
只有当抽象元素的意义不能从名字直接读出时——比如第 20 章
区间域的 [0, +∞) 代表哪个整数集合、第 17 章常量域的 ⊤
与 ⊥ 各覆盖什么——α 才需要显式定义并参与论证。本教程
的处理是：**能读出名字的域免写 α，读不出的域必须写**，
第 14 章的泛型构造将第一次严格执行这条纪律。

Galois 连接还有一个工程上重要的推论：α ∘ γ 是恒等
（抽象元素各自代表不同的值集合，不多不少），而 γ ∘ α
把任意值集合"圆整"到最近的可达抽象——信息只能在这个
圆整处丢失，且丢失的方向由 α 的"最小上界"定义锁死：
**永远丢向更粗**。这就是可靠性不靠小心、而靠构造的
含义——域造对了，粗心也粗不出错误结论。

## 13.4 抽象算术：传递规则的正确性论证

有了域和序，还需要**运算**：程序做整数加法，抽象层必须
回答"− 加 + 是什么"。这一层叫抽象算术（abstract
interpretation 的第一块实物），它的每一张表都是一条
可靠性主张，本章把它们全部摊开论证。

正确的目标格式是：若 a ∈ γ(l) 且 b ∈ γ(r)，则 a + b ∈
γ(sAdd(l, r))。换句话说，sAdd(l, r) 必须是集合
{a + b | a ∈ γ(l), b ∈ γ(r)} 的**上界**；若恰好是最小上界，
则称表项精确（optimal）。逐项验证：

**负加负得 −。** 两个负整数之和是负整数（a < 0, b < 0 ⇒
a + b < 0），且结果可以取到任意负数（取 a = n, b = −1）。
故 {a+b} ⊆ γ(−) 且上确界正是 −，表项 − + − = − 精确。

**负加零得 −，正加零得 +，零加零得零。** 加零不改变值，
三类各自封闭，表项精确且显然。

**负加正得 ⊤。** a = −1, b = 2 给正；a = −2, b = 1 给负；
a = −1, b = 1 给零。三种结果都取得到，而域内没有
"−/0/+ 皆可能"的单一元素，最小上界是 ⊤。这一格是**必然
的精度损失**：不是表写错了，是五元格表达力到此为止。

**含 ⊤ 的行。** ⊤ 代表"任意整数"，任意整数加任何东西的
符号不可判定，只能 ⊤。 ⊥ 吸收：若一边不可达，加法在
该路径根本不发生，结果仍是 ⊥（⊥ 是 ⊔ 的单位元，也是
抽象运算的吸收元——"不可达 + 任何 = 不可达"）。

乘法表同理，而且更整齐：同号相乘得正、异号相乘得负、
零乘任何为零；⊤ 传播，⊥ 吸收。每格论证与加法同构，
留作例题走一遍（例如 + × −：正数乘负数必为负，且任意
负数可达，故精确）。值得指出乘法表的两个"免费精确"：
0 × ⊤ = 0——一侧确定是零，无论另一侧多未知，积必为零；
这是抽象算术里少见的"信息越多越准"的反例（一侧未知
完全不影响结论）。初学者常把"未知"与"危险"混同，
0 × ⊤ = 0 是最好的澄清。

**减法**不需要新表：a − b = a + (−b)，减法经取负归约为
加法。取负在符号域上是 − 与 + 互换（0、⊤、⊥ 自反），
恰好是域的自对偶映射。工程上这意味着减法的表永远不必
维护——维护半张表（加法）就够了，错表的风险随之减半。

**除法**是四则中唯一需要语义决策的。分三种情形：

其一，除数确定非零（− 或 +）：商的符号规律与乘法相同
（a/b 的符号 = a 的符号 × b 的符号），直接复用乘法表，
表项精确。

其二，除数确定为零：TIP 的具体语义中除以零使执行中止，
中止点之后没有"执行状态"需要被覆盖，抽象结果取 ⊥
（不可达）。注意这与"抛出异常后继续"的语言不同——
那种语言里除零产生一个特殊值，需要为它立一个新域元素。
**抽象域的形状跟随具体语义**，又一次印证"语义先行"。

其三，除数为 ⊤（可能是零也可能不是）：需要被 0 ⊔ − ⊔ +
覆盖的商集合。除以零的那些执行中止了，它们对后续程序点
不贡献状态，因此只需对除数 ∈ {−, +} 的情形取 join——
实现里写成 sAdd(sMul(a, −), sMul(a, +))，即"a 乘以
商的符号规律"在两种除号下各算一遍再合并。这条规则
精确吗？对 a = ⊤ 给 ⊤；对 a = +、b ∈ {−,+} 给 {−,+} =
⊤。除法天然比乘法粗糙一档，因为"除数符号已知"比
"乘数符号已知"信息弱（除法对零敏感）。

**比较运算**是最后一张"表"，也是最简：无论操作数符号
如何，x > y 与 x == y 的结果是 0 或 1，二者都是正数或零
……准确地说 0 与 1 都属于 γ(⊤)（1 > 0），但都不属于
γ(−)，也不是 0 或单独的 +。域里没有 {0, +} 这个元素，
最紧的上界是 ⊤。于是 sCompare 恒返回 ⊤（⊥ 吸收照旧）。
这里暴露了符号域的一个真实短板：**比较结果的信息被
完全丢弃**。第 22 章的路径敏感分析会让分支条件反过来
精化变量区间——那是对今天这个损失的第一次偿还。也可以
现在就还：给格加一个 {0,+} 元素（六元格），比较即可
精确——这是本章拓展练习的第一题，做完它比读十页格论
更能体会"域的形状由问题决定"。

### 13.4.1 见证值：每格表项都要经得起反例追问

逐格论证的正确性形态是"∀a ∈ γ(l), ∀b ∈ γ(r)：a op b ∈
γ(表项)"。全称命题的检验方式是**找反例**——为每个表项
主动构造最刁钻的见证值，构造不出来才算过关。把加法表
最可疑的几格过一遍：

− + + = ⊤ 的证据链：a = −1, b = 2 得正；a = −2, b = 1 得
负；a = −1, b = 1 得零。三枚见证值分别落在 γ(+)、γ(−)、
γ(0)，而域内没有元素同时覆盖三者，join 只能 ⊤。注意
见证值的作用是**双向**的：它们既证明 ⊤ 是对的（结果
确实横跨三类），又证明更细的元素是错的（若表里写 +，
a = −2, b = 1 = −1 这一单例即构成反例）。一张表的对错
由最刁钻的一对输入决定，与"多数情况"无关——这是抽象
算术与概率估计的本质区别：分析承诺的是"所有执行"，
一对反例就足以击穿。

+ × − = − 的证据链：正数乘负数必为负（a > 0, b < 0 ⇒
ab < 0，有理不等式的符号规则），且任意负数可达
（b = −1 时 ab = a 取遍 γ(+)；a 固定后 b 扫过 γ(−)，
积扫过全部负数——严格地说乘法的像可能不满，比如
a = 2, b ∈ γ(−) 的积是偶负数，但 γ(−) 覆盖所有负数，
覆盖性依然成立）。这一格精确。

0 × ⊤ = 0 的证据链：a = 0 时无论 b 取什么积都是 0，
单点集合 {0} 的最小覆盖是 0。见证值这里反向发力——
**找不到任何反例**，因为一侧的确定性完全封锁了结果的
可能范围。这是全表最漂亮的一格：最未知的输入遇上最
确定的输入，结论反而最精确。

把这套追问固化成习惯：写下一格表项时，先自问"什么样的
一对输入会让它错？"——能构造出反例就改表，构造不出就
在注释里记下 witnessing 论证（本章源码的注释正是这个
风格）。表驱动实现的隐藏福利在此：正确性论证的粒度与
代码的粒度严格对齐，一格一证，互不牵连；分支语句实现
的论证粒度则是整个控制流，证一处要读全部。

### 13.4.2 最优性：表还能再紧吗

可靠性只要求表项是"某个上界"；工程上自然想问：它是最小
上界吗？若每一格都是最小上界，称传递函数**最优**
（optimal）——在给定域上不可能更精确。逐格检视本章四张
运算：加、减、乘的每一格都精确（见证值论证同时证明了
下确界不可再小：结果集合横跨的每个具体符号类都有成员，
任何更细的元素都盖不全）。除法与比较是仅有的两个疑点，
分开裁决。

除数为 ⊤ 的实现（对除号 ∈ {−, +} 取 join）是最优的吗？
对 a = +：除以负数商为负、除以正数商为正，结果集合是
{−, +}，其最小覆盖恰是 ⊤——实现给 ⊤，精确。对 a = 0：
零除以任何非零数都是零，结果集合 {0}，最小覆盖 0——
实现给的是 sAdd(sMul(0, −), sMul(0, +)) = 0 ⊔ 0 = 0，
恰好精确。对 a = ⊤ 给 ⊤，显然。**除法表逐格最优**，
归功于"除号按符号枚举再 join"这个实现形态天然贴合
最小上界的定义。

比较恒 ⊤ 则**不是**最优——最优应当是 {0,+}，但域里没有
这个元素。这里的措辞要精确：不是表写粗了，是**域不够细**；
最优性永远是"相对给定域"的最优。想精确，改域（加 {0,+}），
而不是在原域上想办法——原域里 {0,+} 的最小覆盖就是 ⊤，
⊤ 已经是极限。区分"域的表达力上限"与"实现的粗心浪费"
是性能与精度调优的第一课：前者的解法是换域，后者的解法
是改代码，对症才能下药。

### 13.4.3 为新运算推导一张表的工作流程

将来语言扩展、抽象域扩展，总要为新运算推导新表。把本章
四张表背后的**推导流程**提炼成固定五步，以后照单施工：

**第一步，写出具体语义。** 被抽象的运算在具体世界里是
什么函数？加减乘除是整数四则（除法的"除零中止执行"是
语义决定，必须在此步锁定）；将来新增的任何运算同理。
语义没写清就动笔推表，是抽象算术错误的头号来源——
除法表的"除零取 ⊥"若不是第一步明确"除零使执行中止"，
很容易顺手写成"除零得 0"：一个貌似合理、实则不可靠的
表项（具体程序除零后没有后续状态，取 0 会凭空覆盖一个
不存在的值）。

**第二步，枚举输入类的笛卡尔积。** 对二元运算即 4×4 = 16
格（⊥ 吸收在外）。每格问一句："a ∈ γ(l)，b ∈ γ(r) 时，
a op b 的全体可能结果是什么集合？"结果集合的形状决定
下一步。

**第三步，求结果集合的最小覆盖。** 集合整体落在某个
γ(x) 内时取最细的 x；横跨多类时取各候选的 join。这一步
是 13.4.1 见证值技术的主战场——每格至少构造一对让结果
"最散"的见证值，才能确信覆盖没有取得过细。

**第四步，回填表格并写注释。** 表项旁注明论证要点（如
"0×⊤=0：一侧确定封锁结果"）。注释是 13.10 节正确性
论证的索引：将来读代码的人（包括三个月后的作者本人）
沿注释能直达每格的成立理由。

**第五步，穷举测试。** 表是主张，测试是主张的机械化
复核（13.12 练习 4 与 7 的模板）；五步走完，新表与本章
四张表具有同等的论证地位。

用一元取负（假想的语言扩展）演习一遍：语义是 −a；输入
四类；结果集合 {−a | a ∈ γ(l)}——γ(−) 的像取遍 γ(+)，
覆盖 +；γ(0) 像 {0}，覆盖 0；γ(+) 像 γ(−)，覆盖 −；
γ(⊤) 像 γ(⊤)。表：−↦+、0↦0、+↦−、⊤↦⊤，每格精确。
再演习 min（假想扩展）：min(−, +) = −（负的更小，确定）；
min(+, −) = −；min(−, −) = −；min(0, +) = 0；min(+, +)
= +；而 min(⊤, +) 的结果可能是 + 也可能更小，覆盖
{≤ +} = {−, 0, +}，只能 ⊤。推到一半就会发现 min 的表
**不对称**（min(−,+) = − 而 max(−,+) = +，两格都精确但
方向相反），真正成立的是经取负的对偶律 min(a, b) =
−max(−a, −b)。这个演习的教益：不是所有运算的表都像
加乘那样规整，"应该镜像""应该对称"的直觉必须经过
纸面检验——五步流程的价值正在于强迫直觉落地。

## 13.5 sign.hpp 与 sign.cpp 逐段导读

理论就位，看实现。符号域的全部知识压缩在一个头文件加一个
实现文件里，加起来不到一百三十行；值得逐段读的是三处
设计决定。

### 13.5.1 用整数编码五个元素

sign.hpp 把五个抽象元素编码为 constexpr 整数：⊥ = −2、
− = −1、0 = 0、+ = 1、⊤ = 2。用 int 而不是枚举或类层次，
是刻意的：

第一，**抽象元素的值要进入容器**。环境是"变量名 → 符号"
的映射，std::map 的值类型越平凡，复制、比较、打印越直接；
类型篇的 Type 树需要 shared_ptr 是因为类型有结构，符号
没有——它是纯原子。

第二，**编码不是语义**。注释里专门警告"序关系不是整数
大小"：按 int 大小，⊥ < − < 0 < + < ⊤ 恰好排成一条链，
但真实的序里 −、0、+ 互不可比！若有人图省事直接写
`a <= b`，会得到一个"更精巧"的假序，所有单调性论证
悄悄失效。防止这类错误的机制不是类型系统（int 挡不住），
而是把 leq/join 做成唯一的访问入口——本章代码里没有任何
位置直接比较两个符号整数。这是"用小接口包住危险原语"的
教科书做法。

第三，表驱动运算（13.5.3）用 int 下标访问 constexpr 数组，
零开销且可静态初始化——若符号是对象，得为每张表写构造
逻辑，教课书代码的清晰度反而下降。

### 13.5.2 leq 与 join：五元格的完整实现

SignLattice 结构体把格的三要素（eq、leq、join）连同 top/bot
边界收在一起。leq 的实现三行：

底最小（任何 x 满足 ⊥ ⊑ x）、顶最大（任何 x 满足 x ⊑ ⊤）
是两个特判；剩下的核心恰是"−、0、+ 互不可比"——相等才
成立。三条分支合起来覆盖 25 个有序对，与 13.2 节的 Hasse
图完全一致。join 的实现四行：相等直返；⊥ 作单位元；
**其余一切组合返回 ⊤**——包括 (−,0)、(−,+)、(0,+) 三个
"真合并"与 (x,⊤) 两个"吸收"。把六种情形压成一行不是
偷懒：在五元格里，"两个不同且都非底的非顶元素"的 join
**必然**是 ⊤（它们互不可比，任何具体符号都不够覆盖，
只剩顶）。一行代码背后是一条域结构定理，这正是小格的
红利。

### 13.5.3 表驱动的抽象算术

加法与乘法各是一张 4×4 的 constexpr 二维表，行列为
{−, 0, +, ⊤}（⊥ 在进入运算前已被吸收分支拦截，无需入表）。
表的好处有三：一，**可视**——整张正确性主张一览无余，
评审表比评审分支语句容易得多；二，**可查**——13.4 节的
逐格论证可以直接在表上定位，哪一格有疑问就看哪一格；
三，**可测**——为表写穷举断言（对每格检查 γ 语义）是
三十行的测试，第 13.10 节的论证可以机械化。减法经由
取负归约到加法表；除法按 13.4 节的三情形分支实现，
除数为 ⊤ 时以 sAdd(sMul(a, −), sMul(a, +)) 表达"对非零
除号取 join"；比较恒 ⊤，无需表。

idx 辅助函数把符号编码平移成数组下标（−1 → 0 … 2 → 3），
它是"编码不是语义"的又一次现身：下标连续只是实现便利，
不承载任何序信息。

### 13.5.4 signShow：输出的字形也是语义的一部分

sign.cpp 的 signShow 把五个编码翻译成打印字形：⊥、−、0、
+、⊤。直接用数学字形而非 ASCII 代号（比如 "BOT"、
"NEG"）是个值得说明的选择。本章的输出要与 13.8 节的手工
推演逐行对照，字形与 Hasse 图、与 join 表、与正文记号
**完全一致**时，对照是零翻译成本的；任何代号系统都要求
读者随身携带一张映射表，对照时多一次心内翻译，出错面
随之扩大。终端对 Unicode 的支持如今是默认假设，教程
代码理直气壮地受益。

signShow 的实现是一个五分支 switch，缺省分支抛
std::logic_error——五个编码之外出现第六个值意味着内存
越界或逻辑错误，是**崩溃优于沉默**的情形：带毒的符号
流入 join 表会悄悄产出错误结论，比当场崩溃恶劣得多。
这条防御在类型篇出现过同款（TyKind 的 default 分支），
数据流篇沿用：凡以整数编码枚举语义的地方，switch 必带
default-throw，让不变量的破坏在最近的现场爆炸。

还有一处小而关键：signShow 接受的是 int 而不是自定义
枚举类型，因为环境容器（std::map 的值）与表驱动运算的
下标都需要平凡的 int；类型安全由此从"类型系统"转移到
"约定 + 单点翻译"——**全部符号只在 signShow 一处变成
人可读文本**，其余代码只面对整数编码与两个入口
（leq/join）。一进一出的收口让编码约定集中到两个文件，
出错面被压到最小。



### 13.5.5 头文件与实现文件的分工

sign.hpp 只放三样东西：五个编码常量（constexpr int），
SignLattice 结构体（top/bot 字段加 eq/leq/join 三个成员
函数——体量小到直接内联在头文件里），五个抽象运算的
**声明**（sAdd/sSub/sMul/sDiv/sCompare）。sign.cpp 放
实现：signShow、leq/join 的完整逻辑、两张运算表、除法的
三情形分支。这个"常量 + 微型格类在头、运算在实现"的
切法遵循一条对所有抽象域都适用的分工原则：**域的形状
是接口，运算的论证是实现**。sign.hpp 的读者（比如第 14
章的泛型构造）只需要知道"这是个五元素格、边界是谁、
join 的入口叫什么"，不需要被 4×4 的表干扰；而表的正确性
论证（13.4 节）集中在 sign.cpp，与它的实现物理同址。

sign_transfer.hpp / sign_transfer.cpp 沿用同一原则：
SignEnv、PointEnv 两个类型别名与五个函数签名是接口，
entryEnv/joinEnv/transferNode/singlePass/printPointEnv
的实现是论证的现场。两对文件合起来构成一条清晰的依赖
单向道：sign_transfer 依赖 sign（传递函数用抽象算术），
main 依赖 sign_transfer（驱动用传递函数），sign 不依赖
任何本章文件（域是自足的）。依赖图无环是 13.6.2 所说
"抽象求值与具体求值同构"得以维持的结构前提——一旦
有人图方便让 sign 反过来 include 前端文件，域的复用
（第 14 章要在完全不同的前端上复用它）就断了。

还有一行容易忽略的接口设计：printPointEnv 放在
sign_transfer 里而不是单独的输出模块，是个小妥协——
它本质是"结果的渲染"，与传递无关。放这里是因为它消费
PointEnv 这个 sign_transfer 私有的类型别名，而本章示例
不设独立的 reporting 层。第 16 章复用 printPointEnv 打印
不动点结果时，这个决定的收益会显形：**同一渲染器、两种
求解器**，输出格式的逐字节一致性（工程注意点 5）由此
免费获得。


## 13.6 抽象环境与传递函数

域与运算解决"单个值怎么抽象"；分析的真正对象是**状态**
——一个程序点上全部变量的抽象取值。本节建立三个层次：
环境、表达式求值、语句传递。

### 13.6.1 SignEnv：缺键即底

SignEnv 是 std::map<std::string, int>：变量名到符号的映射。
关键约定是**缺键视为 ⊥**：一个变量若不在映射里，读它得到
⊥（无信息）。这个约定让"还没被赋值过的局部变量"无需显式
初始化——entry 环境只登记参数，var 声明的变量在第 19 章
"可能未初始化"分析之前一直以缺键形态存在，读取即 ⊥。
⊥ 作为"无信息"的双重身份（路径不可达 / 事实未建立）在此
短暂重合，到第 16 章不动点语境下两者会严格区分（前者的
γ 是空集，后者只是"尚未上升"）；本章的单趟语境里这个
重合无害。

### 13.6.2 evalExprSign：表达式层的抽象求值

evalExprSign 对 AST 表达式做一次"符号语义"的求值：字面量
按正负分类（signOfLiteral 三分支）；变量查环境、缺键 ⊥；
input 恒 ⊤——输入流的下一个整数对外部世界全然未知，⊤
是它唯一诚实的抽象；二元运算按操作符分发到 13.4 节的
抽象算术，其中比较（Gt、Eq）走 sCompare。

递归结构值得驻足：抽象求值与具体求值**同构**——同样的
递归下降、同样的操作符分发，只是"值"换成了"符号"、
"运算"换成了"符号表"。这个同构不是巧合：抽象解释的
核心主张就是"用抽象域上的运算镜像具体语义"，结构上的
镜像使正确性论证可以逐构造对应（13.10 节）。也正因为
同构，具体求值器将来怎么扩展（比如新的表达式构造），
抽象求值器就该同步扩展，二者永远成对演化。

三个"降级"处也要如实指出：函数调用的返回值、指针与
记录相关表达式，本章一律返回 ⊤。调用返回 ⊤ 是因为
过程间的信息流动要到第 23 章才打通；指针/记录 ⊤ 是
因为符号域只谈整数、地址的"符号"没有意义（地址参与
的只有解引用与字段访问，其值最终仍是整数，精确处理
需要形状信息——第 28 章指针分析的领地）。降级不是
遗忘，是**显式声明的分析边界**：本章承诺的可靠性范围
是"标量整数程序"，超出的部分以 ⊤ 兜底且永不违反承诺。

递归同构的三个推论值得单独记下，它们在后续章节反复
兑现。

**推论一：正确性论证按构造进行。** 因为抽象求值与具体
求值结构相同，归纳证明可以沿同一棵表达式树走（13.10.1
节）——每加一种表达式构造，两边同步加一个 case，证明
同步加一步归纳。结构与证明同构意味着"忘了证明某个
构造"几乎不可能：AST 里看得见没被覆盖的节点类型。

**推论二：测试可以互相对照。** 对同一程序分别跑具体
求值（--run）与抽象求值（--check），具体值应永远落在
对应点抽象值的 γ 里——这是比单元测试强得多的**差分
断言**，第 17 章会把它做成 --verify-soundness 开关，
对一批程序自动执行"具体执行 ⊆ 抽象结论"的核对。本章
的 sign1.tip 手工完成同一件事：input 取 3 时，--run
打出的 x=4（具体），--check 的点 5 虽然是 ⊥（未覆盖），
但第 16 章修复后 --check 给 +，γ(+) ∋ 4 ✓。差分断言
是"可靠性"从纸面走到工程的桥。

**推论三：性能特征可预期。** 具体求值 O(表达式大小)，
抽象求值同阶——表的 O(1) 查找取代 ALU 的一拍运算，
常数略贵、量级相同。数据流分析的总体开销因此是
"程序大小 × 迭代轮数"的多项式，与第 11 章合一的
近线性、第 21 章验证器的多项式同属"静态分析不比
编译慢多少"的家族承诺——这一承诺让分析器敢常驻
在每次构建里，而非只住在论文里。

### 13.6.3 缺键即底的边界情形

"缺键视为 ⊥"的约定有两个边界情形，正面想清楚它们，
约定才算真正掌握。

**情形一：读后写。** sign1.tip 的点 4 计算时读 y（有键，
+），写 x（原缺键，写入后键出现）。环境从 {y:+} 变为
{y:+, x:+}——**键集随执行增长**。这不是例外而是常态：
映射格的元素不必共享同一键集（第 14 章的 maps 构造会
把"键集可以不同"形式化为格的定义），joinEnv 的键集取并
正是为此设计。要点是：缺键读作 ⊥（无信息）与缺键在
join 中作 ⊥（中性元）是同一条约定的两个侧面，工程上
只要守住"所有读取与合并都经由带缺省的统一入口"，键集
的增长就自动正确。

**情形二：死变量的键。** 变量离开作用域后，它的键仍在
环境里（本章不删键）。TIP 的 var 作用域是函数级（第 3
章文法），循环体里声明的变量在退出循环后仍占一个键——
它的值是最后一次赋值的抽象，对后续分析无害但也无用。
真正的编译器会做活性分析（第 18 章 liveness 的领地）
把死变量的键剪掉，本章保留它们：剪键是优化不是正确性
需求，教学示例里多一个键换来的是"环境键集单调不减"
这条容易检查的不变量。**正确性与整洁冲突时先保正确**，
这是贯穿全书的小决定模式。

### 13.6.4 entryEnv 与 joinEnv：环境的边界与合并

entryEnv 为函数入口建立环境：每个参数置 ⊤。理由与 input
相同——调用方可能传任何整数（本章没有过程间分析，甚至
不知道调用方是谁），⊤ 是唯一可靠起点。局部变量不入表
（缺键 ⊥，见 13.6.1）。这个函数定义了分析的**边界条件**：
迭代也好、单趟也好，一切推演都从这里出发，边界条件错了
全盘皆错。

joinEnv 把两个环境按变量逐个 join，键集取并：a 有 b 没有
的变量取 a 的值（b 那边缺键 = ⊥，⊥ ⊔ x = x）；两边都有
的取符号 join。它与 13.2 节的映射格（第 14 章的 maps
构造）在语义上完全一致——本章手写它，第 14 章把它
泛型化。逐变量独立合并是"环境格 = 变量集上的映射格"
的直感实现；它的一个推论是变量之间不相关（x 的符号
与 y 的符号各自独立），表达能力更强的域（比如区间对
(x, y) 的联合约束）会打破这种独立性——那是后面章节
的升级路线。

### 13.6.5 transferNode：语句层的传递函数

transferNode 是传递函数（transfer function）的语句级实现：
输入一个程序点入口的抽象环境，输出该点执行后的环境。
它的分发极简：只有 Assign 节点改变环境——把赋值目标
（仅当目标是 VarRef，即标量变量）在环境里更新为右表达式
的抽象值；Output、Branch、Return、Entry、Exit 一律恒等
返回（它们不改变变量的符号，只消费或测试值）。

恒等分支里藏着本章最重要的语义决定之一：**if 与 while
的条件测试不产生任何信息**。直觉上 `if (x > 0)` 明明
告诉我们 x 是正的！但把这条信息写进 then 分支的状态，
意味着 merge 回来时要做更细的处理——那正是第 22 章
路径敏感分析的全部内容。本章的分析是**流不敏感于分支
语义**的：条件两侧的环境相同。这不是"忘了做"，而是
"分析精度的又一根刻度尺"，它的刻度名目（流敏感/路径
敏感）在第 22 章逐一标定。

指针/记录赋值目标（*p = …、r.f = …）同样恒等返回：
在没有别名信息（第 28 章）的情况下，我们不知道 *p
指向哪个变量、r.f 占哪个存储位，贸然更新任何变量
都可能不可靠，保持环境不变是最保守的正确选择（漏更新
使信息偏少=偏 ⊤ 方向=安全，错误更新则可能毁掉可靠性）。
"宁缺勿错"在数据流分析里的形式就是**一切不确定都朝
⊤ 方向退化**。

### 13.6.6 从 SignEnv 到映射格：手搓与泛型的分工

SignEnv 用 std::map 实现"变量到符号"的映射，joinEnv 手写
逐键合并——这个结构在第 14 章会被泛型构造 maps 重写。
手搓一遍再泛型化，是本教程格论部分的固定教法，值得在
此说明分工的原理。

映射格的数学定义是：两个映射的序 = 逐键的序（⟨D⟩^V，
第 14 章 maps 构造），join = 逐键 join，缺键视为键上的
底。SignEnv 的三个实现决定与之一一对应：缺键即 ⊥（13.6.1）
对应"缺键视为底"；joinEnv 的键集取并、共有键取符号 join
对应"逐键 join"；打印时缺键印 ⊥ 对应"映射格的元素在
渲染时展开为全变量视图"。手写版把定义的每一句都落成了
一行代码，泛型版再把每一行抽象成类型参数——读过手写版
的人看泛型版，每一处 `joinF` 的调用都能对上昨天手写的
那一行。

这种"先具体后泛型"的路径还有一层可靠性红利：映射格的
可靠性论证（环境覆盖性的 join 保持，13.10 节）在手写版
里是逐键的三行代码，肉眼可验；泛型版复用同一论证但
读者已经知道要验什么。直接读泛型库的人容易犯的错误是
**不知道缺键语义**——泛型 maps 的缺键是底还是顶，直接
决定分析是"乐观"还是"悲观"，用错方向则可靠性整个
翻转。手搓经历让这个开关的位置永远留在肌肉记忆里。

## 13.7 单趟执行：沿 CFG 走一遍

域、环境、传递函数俱备，只差"驱动"：以什么顺序、对哪些
程序点施加传递函数。本章采用最简单的驱动——**单趟**
（single pass）：按程序点编号顺序（CFG 构造时保证编号
即源码顺序，见第 7 章）对每个点计算一次：

- Entry 点：状态 = entryEnv（边界条件，不依赖前驱）；
- 其余点：状态 = transferNode(node, join(前驱已有状态))。

前驱状态从已算好的 states 表里取；**取不到的前驱按 ⊥
处理**——这正是单趟的软肋所在：CFG 边里，循环回边从
后面的点指回前面的点（while 体尾指回条件点），按编号
顺序走到条件点时，回边的源点还没算，于是这条输入被
当成 ⊥。⊥ 是 join 的单位元，所以"回边缺席"等价于
"回边不存在"——循环携带的全部信息被丢掉了。

要强调单趟**没有违反可靠性**：丢信息只会让结果偏向 ⊤
（更保守），绝不会无中生有地断言精确值。它错在**精度**
而非**正确性**——但第 13.8 节的真实输出会显示，对循环
程序，这种精度损失足以让分析在最需要的地方（循环出口）
输出毫无信息量的 ⊥。分析器存在感的下限，就是别在用户
最关心的点上交白卷。

另一个实现层选择：程序点状态存进 std::map<int, SignEnv>
（PointEnv），编号有序，遍历与打印天然确定。多函数程序
逐函数处理，函数间无信息流动（同 13.6.2 的调用 ⊤ 一致）。

### 13.7.1 遍历顺序的选择余地

编号升序是最省事的顺序，但不是唯一的顺序，也不是最优的
顺序。数据流文献里常见的驱动顺序有三种，各自的性格值得
认清，因为第 16 章的 worklist 要在其中做正式选择。

**编号序（本章）**：实现一行循环，与源码顺序一致，输出
天然可读。缺点如 13.7 所述——回边目标先于回边源点被
计算，循环信息全丢。

**逆后序（RPO，reverse postorder）**：对 CFG 做深度优先
搜索，按"离开节点的时刻"倒序排列，得到的顺序保证每个
节点在其所有**来自入口方向**的前驱之后（回边除外——
回边在 DFS 里正是那个"指向已访问祖先"的例外）。正向
分析用 RPO 可以让绝大多数点一次就算对，只有环上的点
需要重算。第 16 章的 worklist 初值就用 RPO 装载，这是
"遍历方向跟随信息流向"的工程化表达。

**任意序（朴素迭代）**：顺序完全无所谓，反复全量扫描
直到不再变化。正确性由 join 的交换律结合律保证（13.2
节），代价是扫描次数可能多几轮。它的存在价值是理论
参照：任何顺序的迭代都收敛到同一个不动点——这条性质
让"顺序"从正确性问题降级为效率问题。

三种顺序在 sign1.tip 上的差异可以亲手试出：RPO 下点 2
仍然先于点 4（环的存在无法绕开），第一次仍吃 ⊥，但
**只要允许重算**（第 16 章），RPO 的重算轮数就明显少于
编号序。顺序不影响答案（合流性），只影响到达答案的
路费——这与类型篇 11.23 节的合流性讨论形成漂亮的
呼应：合一的重写系统合流，格上的迭代也合流，两篇
分享同一条数学根。

### 13.7.2 传递函数的单调性：可靠性的第四块地基

γ 的两条纪律之外，还有一个隐含前提必须摆上台面：传递
函数本身要**单调**——σ̂1 ⊑ σ̂2（逐变量）蕴含
transfer(n, σ̂1) ⊑ transfer(n, σ̂2)。直觉说法：给传递函数
更多输入信息，它至多给出更多输出信息，绝不倒退。

本章的 transferNode 单调吗？逐层核对。evalExprSign 对
VarRef 的查表是单调的（输入环境的每键更多信息 → 查得
的符号按 ⊑ 更多）；对 Binop 的表查询是单调的——验证
抽象算术表的一个非显然性质：**表中任意两行（列）按 ⊑
逐格比较，右端的格子也按 ⊑ 逐格比较**。以加法表为例：
行 − 的格子是 (−, ⊤, ⊤)，行 0 的是 (⊤, 0, ⊤)……严格地说
需要的是"输入格上升 ⇒ 输出格不下降"，逐对检查 4×4 表
即可确认（0 × ⊤ = 0 与 0 × − = 0 相等，⊥ 相关分支吸收，
其余 ⊤ 传播——表没有一处"输入变好、输出变坏"）。
joinEnv 逐键 join 单调（join 对两个参数都单调，格论
通例）；entryEnv 是常函数，平凡单调。

单调性为什么是必需的？两个消费者。其一是第 16 章的
迭代收敛论证：不动点迭代反复以 join 攒信息再传给传递
函数，只有单调才能保证"信息只增不减、迭代不震荡"——
非单调的传递函数会让迭代在两个状态间荡秋千，永不
收敛。其二是可靠性论证本身：13.10 定理的证明暗用了
"输入覆盖加强时输出覆盖不减弱"，非单调函数可以在
输入更精确时给出更粗（甚至错误）的输出，逐点可靠性
无法拼成全局可靠性。

顺带区分一对容易混淆的性质：单调（monotone）与分配
（distributive，f(x ⊔ y) = f(x) ⊔ f(y)）。本章的传递
函数恰好分配（单变量赋值 + 表驱动运算的对称性），但
分配性不是必需的——第 17 章常量域遇到 join 依赖时
（x = 1 或 x = 2 两条路径汇合后 x 的常量性丢失），
传递函数仍单调但不再分配。**单调是收敛的底线，分配
只是精度的奢侈品**，记住这句话，第 17 章不会慌。

### 13.7.3 单趟状态表的三个不变量

singlePass 维护的 states 表（PointEnv）在整个执行期间
满足三条不变量，把它们写下来，既是对单趟代码的规格
说明，也是第 16 章 worklist 表的对照原型。

**不变量一：表中键的编号 ≤ 当前遍历位置。** 单趟严格
按编号推进，任何时刻只有"已计算"的点在表里——这条
让"查不到 = 还没算 = 按 ⊥"成为合法解读。

**不变量二：表中每个值是 transferNode 的一次输出。**
状态要么来自 entryEnv（点 1），要么来自某个前驱的
joinEnv 再过 transfer——没有第三个来源，表里不会出现
凭空的状态。

**不变量三：一旦写入，永不改写。** 单趟每点只算一次，
states[id] = ... 只对同一个 id 执行一次。第 16 章的
worklist 恰恰废除这条（允许反复改写），且以"改写时
新值必 ⊒ 旧值"（严格上升）取而代之——**两章之间
真正变化的只有这一条不变量**，其余全部继承。

### 13.7.4 singlePass 的代码形态与不变量的对应

把 13.7.3 的三条不变量对到 singlePass 的代码骨架上，
能看清"规格如何长成代码"。整个函数是一个二重循环：
外层按函数迭代（多函数程序逐个分析，函数间无信息流动），
内层按该函数 CFG 的节点序迭代。内层体只有三种动作，
恰好对应三个来源的划分：Entry 节点取 entryEnv（不变量
二的第一个来源）；其余节点收集前驱的已计算状态做
joinEnv，再过 transferNode（不变量二的第二个来源）；
结果写入 states（不变量三的一次性写入）。前驱状态
查表用 find——查不到就跳过该前驱（等价于按 ⊥ 参与
join），这正是"回边缺席"在代码里的真实形状：不是一行
注释，也不是一个标记，而是**一次 find 失败**。

打印环节（printPointEnv）与计算环节（singlePass）在
sign_transfer.cpp 里同文件不同职责：前者只读 states、
后者只写，读写分离让"输出的形状"（13.14 注意点 5）
可以在不触碰分析逻辑的前提下独立演化。第 16 章会把
singlePass 整体替换为 worklist 求解器，而 printPointEnv
一行不动——接口设计对演化的支撑，届时自见分晓。

函数签名也值得一读：singlePass 接受 Program 的 AST 与
已建好的 CFG，返回 PointEnv。它不自己建 CFG、不自己
parse——单一职责使每个环节都可以单独测试（给固定 CFG
喂固定 AST，断言输出环境），13.8.1 的手演因此可以
转化为单元测试：七个点的期望环境逐点写死，机器替你
重演草稿纸。

## 13.8 真实输出解读：循环在哪里丢的信息

运行 `tipa --check examples/13_sign_lattice/programs/sign1.tip`，
得到本章嵌入的 expected/output.txt。程序是 spa 4.1 的
动机例（x = x + 1 循环的教学变体）：

```
main() {
  var x, y;
  while (input > 0) {
    y = 1;
    x = y + 1;
  }
  output x;
  return 0;
}
```

七个程序点（第 7 章 CFG 编号）：1 entry、2 while 条件、
3 y=1、4 x=y+1、5 output x、6 return、7 exit。逐点读输出：

**点 1（entry）**：x=⊥ y=⊥。无参数，环境为空，两个变量都
是"未建立"——这不是说它们不存在，而是说此刻对它们一无所
知。这是全程序唯一"合法的 ⊥"：其余点的 ⊥ 全是单趟缺陷
的产物。

**点 2（while 条件）**：x=⊥ y=⊥。它的前驱有两个——entry
（点 1）与循环回边（点 4）。按编号顺序，算到点 2 时点 4
尚未计算，回边按 ⊥ 缺席，于是状态 = 点 1 的状态原样透传
（transferNode 对 Branch 恒等）。**循环携带的全部信息在
这一刻被判了死刑**：稍后点 4 会算出 y=+ x=+，但没有任何
机制把这份信息送回点 2——单趟没有第二次机会。

**点 3（y = 1）**：y=+。字面量 1 是正数，表项直接精确。
x 仍 ⊥（缺键，尚未被赋值）。

**点 4（x = y + 1）**：x=+ y=+。y 是 +，+ 加 + 得 +（加法
表，精确）；x 被更新为 +。此刻循环体内的一切其实已经
算清：**再执行一轮，点 2 就该知道 y=+**。机器离正确答案
只差一次重算，而单趟的设计让它止步于此。

**点 5（output x）**：x=⊥ y=⊥。output 的唯一前驱是点 2，
状态原样透传。**这是全章的痛点**：程序在循环体至少执行
一次后必然走到 output，那时 y=+、x=+ 是铁的事实（y=1
随后 x=y+1，两行在循环内 unconditional）；正确的分析结论
应是 x=+。而单趟交出的答卷是 ⊥——"无信息"。一个只要
翻一遍循环体就能回答的问题，分析器交了白卷。

**点 6、7（return、exit）**：透传点 5 的 ⊥/⊥。return 0
的右值是常量零，但 Return 节点不改变环境、也不被本输出
格式反映（环境里没有"返回值"槽位），于是出口状态仍带着
下游看来的 ⊥。对本章的输出格式无碍——结论以每点环境
为准——但它提示：**分析的输出形状（环境里放什么）本身
也是设计决定**，第 17 章把返回值纳入状态时，输出会多一列。

把丢信息的链条完整复述一遍：回边 4→2 在点 2 计算时缺席
⇒ 点 2 的状态 ⊥/⊥ ⇒ 沿边传播，点 5、6、7 全部继承 ⊥
⇒ 循环外一切归零。修复它只需要一件事：**算完点 4 后回头
重算点 2**，直到不再变化。这一句话就是第 16 章 worklist
算法的全部直觉；把它说成定理（最小不动点）需要第 15 章
的方程组语言；而"重算会不会无穷进行下去"的担忧，由
格的高度有限回答（13.11 节）。三章的分工在本章已经显形。

### 13.8.1 逐点手演：草稿纸上的单趟

单趟算法只有七行代码的复杂度，值得在草稿纸上完整手演一遍
——这一节推演的每一步都对应 expected/output.txt 的一行，
读代码之前先推代码，是本章反复出现的练习形态。

先定边界：main 无参数，entryEnv 返回空映射；变量 x、y
在 var 声明处不入表。CFG 七个点，编号即源码顺序，边集为
1→2、2→3、2→5、3→4、4→2（回边）、5→6、6→7。遍历从
点 1 开始，编号升序：

**点 1（entry）**：无前驱需要 join（按定义直接取
entryEnv），状态 = {}。打印时 x、y 都缺键，各印 ⊥——
注意**打印**与**存储**的差别：环境里根本没有 x、y 两个键，
⊥ 是打印层对缺键的呈现。存 ⊥ 进去与不存，在 join 语义下
等价，但"不存"让环境保持最小，变量多时省去无谓的表项。

**点 2（branch while (> input 0)）**：前驱两个。点 1 的
状态在表里（{}）；点 4 的还没算——states 查不到，按 ⊥
缺席。joinEnv({} , ⊥) = {}（缺键即 ⊥，⊥ ⊔ 缺 = 缺）。
transferNode 对 branch 恒等，状态不变。输出 x=⊥ y=⊥，
两个 ⊥ 都是缺键的打印像。

**点 3（assign y = 1）**：唯一前驱点 2，状态 {} 进来。
transferNode 计算 evalExprSign(1, env) = +（字面量正数），
目标 y 是 VarRef，环境更新为 {y: +}。x 仍缺键。输出
x=⊥ y=+——x 的 ⊥ 与 y 的 + 并排出现，正是"缺键即 ⊥"
约定最直观的展示：同一行里，一个变量是"还没轮到它"，
另一个是"刚刚建立的事实"。

**点 4（assign x = (+ y 1)）**：前驱点 3，状态 {y: +}。
evalExprSign 递归：IntLit 1 → +；VarRef y → 查表得 +；
Binop(+) → sAdd(+, +) = +。目标 x 更新：{y: +, x: +}。
**到这里，循环体的全部事实已经算清**——y=+、x=+，
而且它们对循环的任意圈数都成立（每圈都先 y=1 再
x=y+1，两个赋值不受循环次数影响）。可惜没有任何机制
把这份信息送回点 2。

**点 5（output x）**：前驱只有点 2（branch 的 false 出边
直通 output——while 条件不成立时跳出循环）。点 2 的状态
是 {}，透传。**输出 x=⊥ y=⊥，全章痛点在此定格**：程序
能执行到 output 的前提是 while 至少完整跑过一圈
（若条件首次即假，跳到 output 时 x、y 确实未赋值——
等等，这个细节值得停下来）。

停下是对的：条件首次即假的情形真的存在（input 第一个
值是负数或零），那时 output 处 x、y 确实没有值——TIP
语义下读未赋值变量是未定义行为（第 19 章的"可能未
初始化"分析正是为它而生）。所以"x=+ y=+"对 output 点
**不是无条件成立的**：它成立当且仅当循环至少执行一圈。
正确的分析结论（第 16 章 worklist 给出的）是 x=+ y=+，
其依据是不动点定义下点 2 的状态 = entry 状态 ⊔ 回边
状态 = {} ⊔ {x:+, y:+} = {x:+, y:+}——**不动点语义把
"至少一圈"的路径与非零圈路径合在一起**，而 {} 这份
"零圈"信息在 {x:+,y:+} 面前被 join 吸收为零贡献（缺键
⊥ ⊔ {x:+} = {x:+}）。换句话说，修正后的分析对"零圈
时读未初始化变量"这个语义坑做了乐观合并——这是数据流
分析的经典立场（逃逸路径不拖垮整体精度），它与第 19 章
的悲观立场（专门揪出未初始化）形成有趣的张力，留到
那一章正面交锋。

**点 6（return 0）**、**点 7（exit）**：各只有一个前驱，
透传 {}，输出 x=⊥ y=⊥。Return 不改环境，`0` 这个常量
没有进入输出——环境里没有"返回值"槽位（13.8 节末尾
已提），输出格式以变量环境为全部内容。

七步推演到此。回头看，整条"信息丢失链"只有一环：点 2
计算时点 4 缺席。**单趟的全部精度损失都可以追溯到这一句**：
序不对、机制缺。序的修正（谁先算）不解决本质——点 4 依赖
点 3 依赖点 2，点 2 又依赖点 4，这个环注定没有一次性
的拓扑序；机制修正（允许重算）才是出路，那就是第 16 章。

### 13.8.2 与 spa 4.1 的对照

本例与 spa（Møller & Schwartzbach《Static Program
Analysis》）4.1 节的动机例同源：原书用 `x = input; y =
x; while (…) { x = x + 1; }` 一类的小循环引出"数据流
分析需要不动点"的动机，结论同样是"循环携带的信息在
一次性遍历中丢失"。本章把例子压缩为两行赋值加一个
output，压缩的理由是让**每一个抽象元素在输出里都有
出镜机会**：字面量分类（y=1 得 +）、抽象算术（y+1 得
+）、缺键即 ⊥（entry 行）、回边缺席（output 行的 ⊥）、
恒等传递（return/exit 行）——五行输出各演一个角色，
没有一行是陪跑。

原书在这一节之后立刻转向格与不动点的理论建设，本书
把同样的理论摊开为三章：第 14 章把"变量环境"这个
具体结构泛型化为格构造子（lift/product/maps/powerset），
第 15 章把"单趟每次一步"改写成方程组（每个程序点一个
变量、每条边一个方程），第 16 章给出 worklist 求解器。
三章读完回看 sign1.tip 的 output 行，⊥ 变成 +——那一行
的翻转就是三章理论的总验收。

### 13.8.3 输出的三层读法

expected/output.txt 的 11 行可以按三层来读，每层回答
一个不同的问题——这个分层读法适用于全书后续所有分析
输出的解读。

**第一层：读"结论"**（变量 = 符号）。每行末尾的
x=… y=… 是分析的直接产品：该程序点入口处每个变量的
抽象值。第 3 行的 x=⊥ y=+、第 4 行的 x=+ y=+ 是其中
唯一两条"非平凡"信息，其余行的 ⊥ 大多是缺键或缺前驱
的呈现。快速扫读时只看非 ⊥ 的项。

**第二层：读"机制"**（每行为什么如此）。把 13.8.1 的
手演对到每一行：点 3 的 y=+ 来自字面量分类，点 4 的
x=+ 来自 sAdd(+, +)，点 5 的 ⊥ 来自回边缺席。这一层
读法的目标是能**复述因果链**——合上书后能对任何一个
行说出"它的状态从哪条边来、过了哪个传递"。

**第三层：读"缺陷"**（哪里本可以更好）。点 5 的 ⊥
是缺陷而非结论——正确的值应是 +（第 16 章）。分清
"分析的诚实输出"与"分析的最终潜力"是读任何分析器
输出的修养：⊥ 既可能是"确实不可达"（点 1 的合法 ⊥），
也可能是"分析器能力不足"（点 5 的白卷）。区分二者
没有输出格式上的捷径，只能靠对机制的第三层理解——
这正是本书坚持"手演 + 机制讲解"而不满足于贴输出的
原因。

三层读法也是一种调试纪律。分析器的输出错了（比如
某点的符号明显不对）时，沿"哪一行 → 哪条边 → 哪个
传递函数"回溯，通常三步之内定位到出错的表项或缺失
的键；对整个输出做三层解读的习惯，就是为将来调试
第 17–28 章更复杂的分析器练手。

### 13.8.4 变一变程序：看输出对源码的敏感度

输出的价值在对照中显形。把 sign1.tip 做三个最小变体
（不必真的改示例，纸上推演即可），预测每行的变化，是
检验 13.8.1 手演是否内化的试金石。

**变体一：把循环体改成 `y = 0; x = y + 1;`。** 点 3 变为
y=0（字面量零），点 4 变为 x=+（sAdd(0, +) = +，加法表
第三行）。点 5 仍是 ⊥——变体只动了循环体内部的常量，
单趟的机制缺陷原封不动。**机制的缺陷与程序的内容正交**：
无论循环体算什么，回边缺席的惩罚一视同仁。

**变体二：把 `while` 改成 `if`。** CFG 里回边消失，
编号序与信息流向完全一致——单趟胜任有余。推演一遍：
点 2（branch）状态 {}；点 3 得 {y:+}；点 4 得
{y:+, x:+}；点 5（output）有两个前驱——branch 的
false 出边（状态 {}，对应条件首次即假的零圈路径）与
点 4（{y:+, x:+}，对应执行过 if 体的路径）。此刻两个
前驱都已在 states 表里，joinEnv 正常工作：缺键 ⊥ 与
+ 合并得 +，输出 x=+ y=+。对照原程序点 5 的 ⊥ 白卷，
变体二的输出点干干净净——**单趟的缺陷专属循环**，
无环程序（哪怕满地分叉汇合）它都处理得很好。这个
对照精确划定了病灶：不是"合并"不会做（joinEnv 一直在
做），而是"回边的源点晚于目标点被计算"这一编号序
冲突。凡是无环的依赖，一次有序遍历都能搞定；有环
才需要迭代。

**变体三：给 main 加参数 `main(int x)`。** entryEnv
多出 x=⊤（参数任意），点 1 输出 x=⊤ y=⊥；此后 x 的
⊤ 一路传到点 5。有趣的是点 4：赋值 x = y + 1 会把
entry 带来的 ⊤ **覆盖**为 +——分析器对"变量被重新
赋值"的处理是直接替换而不是 join，因为赋值是确定性的
（旧值随语句执行消失）。何时 join、何时替换，是数据流
分析最容易写错的分岔口：**沿边到达用 join，语句执行
用替换**。这句话第 15 章的方程组会给它一个正式的名字
（方程的右端在入口处是 join，在赋值出口处是传递函数）。

三个变体指向同一个结论：输出的每一格都是"程序内容 ×
分析机制"的乘积，读输出就是同时读这两位作者。

## 13.9 与类型分析的对照：两种静态知识的分工

本章是类型篇与数据流篇的分水岭，把两种分析并排摆一次，
它们各自的形状会更清楚。

**信息挂在哪。** 类型事实挂在语法结构上：表达式 τ(E)、
声明 τ(x)、函数 TyFun——同一表达式无论执行到多少次，
类型唯一。数据流事实挂在程序点上：同一条 `output x`，
从循环里到达与从循环外到达，x 的符号可以不同——事实上
本章的 CFG 里每条语句恰好一个点，而第 22 章路径敏感
会进一步按**到达路径**细分。坐标系的差异决定了两类
分析回答的问题族：类型答"这个表达式是什么形状"，数据流
答"执行到这里，值可能是什么"。

**信息怎么合。** 类型篇的"合"是合一：把两处对同一变量的
描述**对齐成同一个**（10.16.7 的主解）。数据流篇的"合"
是 join：把两处描述**并成更大的一团**。合一拒绝不一致
（int 与 ptr 相遇即报错）；join 容忍一切不一致（− 与 +
相遇即 ⊤，没有错误只有变粗）。前者是"规格检查"，后者
是"行为预测"，容错哲学完全相反。

**要不要迭代。** 合一靠代换定向传播，一次绑定、处处替换，
天然无环（occurs 检查守门）。数据流方程天然有环（循环
回边），必须靠迭代逼近，而迭代的收敛由格的有限高度保证。
所以类型篇一次求解、数据流篇反复重算——不是实现取舍，
是问题结构的必然。

**输出什么。** 类型分析的输出是二值判定（有解/无解）加
精确解表；数据流分析输出逐点报告，且报告本身有"粗细"
之分（+ 比 ⊤ 精）。误差第一次成为输出的一等公民——
相应地，"误差朝哪个方向偏"成为必须论证的性质（可靠性），
这是 13.10 节的任务。

### 13.9.1 两种分析在同一个程序上的合作

对照不是为了分高下，是为了分**工**。把 sign1.tip 交给
两套机器：类型篇的约束机器答"程序能否通过类型检查"
——能，而且 x、y 都是 int；数据流机器答"output 处 x
的符号"——本章给 ⊥，第 16 章给 +。两个答案互不冲突、
互不冗余：类型检查挡不住"除以零"（`100 / x` 类型完好，
x 仍可为 0），符号分析挡不住"把字符串当整数"（那是
类型错误，数据流根本不在这个平面上看问题）。

实际工具链里二者是**串联**的：先类型后数据流，类型
不过的程序不必进入数据流阶段（它的"运行时值"问题
建立在错误前提上）；类型通过的数据流程序，其所有
表达式都有确定类型，抽象求值可以放心假设操作数是
整数——本章 evalExprSign 敢于对 Binop 直接查抽象
算术表，前提正是类型篇已经把"操作数是整数"证完了。
**抽象域的合法性依赖上游的类型保证**：若语言无类型，
"值的符号"这个抽象要为"操作数可能是字符串"之类的
情形另立元素。类型分析与数据流分析的接口就在这里：
前者交付"表达式都是良类型 int"，后者在这个前提下
开工。

第三种视角也值得一提：两类分析共享同一份 CFG 基础
设施（第 7 章）与同一套 AST（第 3 章），但读取方式
不同——类型篇读 AST 的声明结构（收集器遍历语法树，
10.2 节），几乎不碰 CFG；数据流篇读 CFG 的点与边，
只在求值叶子处回看 AST。同一程序的两张"地图"，
比例尺不同、标注不同、用途不同。

### 13.9.2 五维对照表

把 13.9 与 13.9.1 的讨论压成一张对照表，作为类型篇与
数据流篇的"界碑"。表不是结论的替代，是记忆的挂钩：

| 维度 | 类型分析（9–12 章） | 数据流分析（13 章起） |
|------|--------------------|----------------------|
| 事实坐标 | 语法结构（表达式、声明） | 程序点（CFG 节点） |
| 合并规则 | 合一（对齐成同一描述） | join（并成更粗的描述） |
| 不一致的处理 | 报错（TypeError） | 变粗（−⊔+=⊤） |
| 迭代需求 | 无（代换定向传播） | 有（回边天然成环） |
| 收敛保证 | occurs check + 结构递减 | 格有限高度 + 单调上升 |
| 输出形态 | 二值判定 + 精确解表 | 逐点报告，粗细分级 |
| 误差方向 | 无误差（有解即精确） | 永远朝 ⊤（保守）方向 |
| 典型问题 | "这个表达式是什么形状" | "执行到这里值可能是什么" |

两栏不是竞争关系而是接力关系（13.9.1 的串联流水线），
表的最后一行给出最实用的记忆：**类型答形状问题，
数据流答值问题**。遇到一个新需求时先问它落在哪一栏，
选错了体系，后面全部力气都会花在"用错误的坐标系
回答正确的问题"上——例如想用类型系统表达"x 非零"
（流类型/精化类型可以勉强做，但那是第 22 章路径敏感
思想的类型化重演），或想用数据流表达"函数返回值形状"
（得先把形状编码成抽象域，绕远路）。

数据流分析的可靠性陈述有一个标准形态，先陈述再论证。
之所以叫**局部**，是因为陈述与证明都只看"一个程序点的
一步"——不涉及执行历史、不涉及循环圈数、不涉及调用
栈。局部的命题小到可以逐语句验证，而整条执行轨迹的
可靠性由局部的命题沿边拼装而成（13.10.3）——**把大
定理拆成小命题、再把小命题钉在代码的每个分支上**，
是本章处理"分析器是否可靠"这个天然宏大问题的全部
策略。下述定理沿 13.6 节的四类语句分派证明，每类
几行；读完它们应能体会：可靠性不是一遍总检，而是
写在每个 transfer 分支里的局部义务。



数据流分析的可靠性陈述有一个标准形态，先陈述再论证。

**定理（局部可靠性）。** 设 σ 是程序点 n 入口处的一个
具体环境（变量到整数的映射），且 σ ∈ γ(in(n))（σ 被 n
入口的抽象环境覆盖）；设 σ′ 是 σ 执行 n 对应语句一步后
的具体环境。则 σ′ ∈ γ(out(n))，其中 out(n) =
transferNode(node, in(n))。

论证按语句类型分派，每条都短：

**Entry。** 入口环境对参数置 ⊤：任何实参组合都在 γ(⊤) = ℤ
内。局部变量缺键 ⊥——程序首执行时它们尚无值，"无值"
与 γ(⊥) = ∅ 相容（没有具体状态宣称对应它们）。边界条件
可靠。

**Assign（标量目标）。** out = in[x ↦ v̂]，其中
v̂ = evalExprSign(rhs, in)。需证两点。其一，表达式求值的
可靠性：对任意 σ ∈ γ(in)，σ⟦rhs⟧ ∈ γ(v̂)。这是 13.4 节
各表项论证的归纳组合：字面量精确分类；变量查表按 in 的
覆盖性传递；复合运算按操作符表逐层保覆盖（每层的
"结果 ∈ γ(表项)"正是 13.4 节逐格验过的主张）。归纳沿
表达式结构走，基例三条、归纳步一种（Binop），InputE 的
⊤ 由"输入任意"直接成立。其二，更新后的环境覆盖 σ′：
被更新的 x，σ′⟦x⟧ = σ⟦rhs⟧ ∈ γ(v̂)；其余变量未被触动，
in 对它们的覆盖原样继承。合起来 σ′ ∈ γ(out)。

**Output / Branch / Return。** 语句不写变量，σ′ = σ，
恒等传递可靠。注意 Branch 的条件测试虽然"发生"了，但它
不改变变量值——改变的是**哪些路径可行**，而路径可行性
的精化不在本章承诺范围内（13.6.5 的声明）。

**指针/记录目标。** transferNode 恒等返回，需证 σ′ ∈
γ(in)：σ′ 与 σ 的差异只发生在某个存储位置上，而该位置
在本章的抽象里没有名字；所有变量的值……严格地说，*p = 5
可能改变某个标量变量的值！此时 γ(in) 不再覆盖 σ′——
可靠性破了吗？没有，因为**承诺的范围**（13.6.2 显式声明）
是标量程序：对含指针写入的程序，本章分析不提供结论。
工程上仍以 ⊤ 兜底（任何读指针目标得来的值都是 ⊤），
且本教程后续在第 28 章补全别名信息后重开此承诺。诚实地
划界比假装全能可靠——这是类型篇 10.17 节"约束表达力
边界"的数据流版。

**Join 的可靠性**是另一半：汇合点的抽象状态须覆盖来自
任一前驱的具体状态。joinEnv 逐变量取符号 join，而符号
join 恰是 γ 下的集合并（13.3 纪律一），故覆盖性保持。
单趟的"缺前驱按 ⊥"也在此获得可靠解释：γ(⊥) = ∅，缺席
的前驱不覆盖任何具体状态，等于放弃那部分输入——丢的
是精度，不是承诺。

局部可靠性定理是逐点的；把"每点可靠"升级为"整条执行
轨迹处处被覆盖"只需沿 CFG 边归纳（归纳基础是 entry
边界，归纳步是本定理），这个整体版本在第 16 章以
不动点语言重新陈述。本章记住局部版即可——它是每一行
transfer 代码的契约。

### 13.10.1 表达式求值可靠性的归纳细节

13.10 的 Assign 情形把"表达式求值可靠性"作为一个引理引用
了，这里把引理的归纳展开补齐，它是后续各章（14、15、17、
20）共用的模板。

**引理（抽象求值可靠性）。** 对任意表达式 E、任意具体
环境 σ 与抽象环境 σ̂，若 σ ∈ γ(σ̂)（即对每个变量
x：σ⟦x⟧ ∈ γ(σ̂⟦x⟧)，缺键两侧同步按 ⊥/∅ 处理），则
σ⟦E⟧ ∈ γ(evalExprSign(E, σ̂))。

**基例三条。** IntLit：n 与 signOfLiteral(n) 同类（负/
零/正按定义），n ∈ γ(对应符号)，精确。VarRef：σ⟦x⟧ ∈
γ(σ̂⟦x⟧) 正是覆盖性假设的展开。InputE：任何整数 ∈
γ(⊤)，"任意输入"是可靠性论证里最便宜也最诚实的
一步——它对真实世界不做任何假设。

**归纳步一种。** E = E1 op E2：由归纳假设，
v1 ∈ γ(ê1)、v2 ∈ γ(ê2)，其中 ê1、ê2 是子表达式的抽象值；
按操作符分派到 sAdd/sSub/sMul/sDiv/sCompare，13.4 节的
逐格论证恰好陈述的就是"v1 ∈ γ(ê1) ∧ v2 ∈ γ(ê2) ⇒
v1 op v2 ∈ γ(op(ê1, ê2))"——**逐格表项的精确措辞与
归纳步的需求逐字匹配**，这就是 13.4 节当初把目标格式
写成那样一课的回报。归纳沿表达式结构下降，叶子是
三类基例，内部节点只有 Binop 一种，引理得证。

这个"表项措辞 = 归纳步需求"的对齐不是巧合，是 13.4 节
目标格式的设计意图。往后每一章扩展抽象域（加运算、
换域），只要保持这个措辞纪律，正确性证明就能机械地
跟着代码生长——**让证明的形状与代码的形状同构**，
是本教程对"分析正确性"的一贯工程解法：不靠事后补证，
靠事前把证明的骨架浇筑进代码的结构里。

### 13.10.2 joinEnv 覆盖性的逐步证明

13.10 的归纳步在汇合点引用了 join 的覆盖性，这里是完整
的逐步证明——它短到两行，但每一步都对应 joinEnv 实现的
一行代码，"证明与代码同构"的最小标本。

**命题。** 设 σ1 ∈ γ(σ̂1)、σ2 ∈ γ(σ̂2)，则
σ ∈ γ(joinEnv(σ̂1, σ̂2)) 对 σ ∈ {σ1, σ2} 均成立
（以 σ = σ1 为例）。

**证。** 对任意变量 x 分三情形。情形一：x 同时在 σ̂1、
σ̂2 中——joinEnv 给 σ̂1⟦x⟧ ⊔ σ̂2⟦x⟧，而 γ 对符号 join
恰好是并（13.3 纪律一），故 σ1⟦x⟧ ∈ γ(σ̂1⟦x⟧) ⊆
γ(σ̂1⟦x⟧ ⊔ σ̂2⟦x⟧) ✓。情形二：x 只在 σ̂1 中——joinEnv
键集取并，x 的值原样是 σ̂1⟦x⟧，覆盖性原样继承 ✓。
情形三：x 只在 σ̂2 中——σ1 中 x 缺键，按约定 σ1 中
x 的值对应 ⊥（γ(⊥) = ∅），γ(σ̂2⟦x⟧) 无论如何都覆盖
"没有具体值要覆盖"的空集……严格地说这里要小心：σ1
缺 x 意味着"σ1 语境下 x 无值"，把它看作 ∅ 即可，覆盖性
平凡成立 ✓。三情形穷尽，命题得证。∎

证明里的三情形与 joinEnv 的三段逻辑（共有键 join、
单侧键保留、键集取并）一一对应；纪律一（γ 对 join 是并）
是唯一引用的格性质。往后第 14 章把 SignEnv 泛型化成
maps 构造时，这条命题会原样升级为"映射格 join 的覆盖性
引理"，情形划分一个不变，变的只是"符号 join"被换成
"任意格的 joinF"——**引理的形状比引理的内容更长寿**，
这是把证明写清楚的第二重回报。

### 13.10.3 从局部到全局：沿边归纳

局部可靠性定理管"一步"；整条执行轨迹处处被覆盖还需要
一次归纳，把"每步可靠"串成"全程可靠"。

**定理（轨迹可靠性）。** 设某次具体执行依次经过程序点
n0, n1, …, nk（n0 为 entry），每步的状态为 σ0, …, σk。
则对每个 i：σi ∈ γ(in(ni))——只要每个 ni 的入口抽象
状态 in(ni) 满足 13.10 定理的前提。

归纳基础：i = 0，n0 = entry，in(n0) = entryEnv，
13.10 的 Entry 情形已证任何"真实初始状态"被覆盖。
归纳步：σi ∈ γ(in(ni)) 成立时，执行 ni 一步得 σi+1
∈ γ(transferNode(node_i, in(ni)))，而执行轨迹上 ni 的
后继是 ni+1，故 out(ni) 正是 in(ni+1)（单点前驱时直接
相等；汇合点时由 join 的覆盖性——任一前驱的 out 都被
join 结果覆盖，13.3 纪律一）传递过去。

证明里"汇合点"一句值得放大：join 覆盖性的全部意义
就是让**多条执行轨迹在同一点共享一个抽象状态**——
分析把轨迹束起来，每条都被同一个抽象状态覆盖。这是
数据流分析"以一敌万"的机制：抽象状态是无数具体状态的
公共伞，可靠性保证伞下没有漏网之鱼，精度决定伞有多小。
本章的伞有几处破洞（回边缺席让部分轨迹的"伞"提前
收走了——那些轨迹在点 2 的 in 不再被覆盖，轨迹可靠性
对**循环执行两圈以上**的程序失效！），这是单趟真正的
代价：不仅精度差，连可靠性承诺的范围都缩水到"最多
一圈"。第 16 章的不动点把这最后一块短板补齐——
**不动点不是锦上添花的精度工程，是可靠性本身的必需品**，
这是本章与第 16 章之间最深刻的一条线。

### 13.10.4 单趟的可靠性边界：一个诚实的断言

把 13.10 各结果合起来，本章能给用户的最终承诺是：

**对不含指针写入、不含循环回边被截断情形的程序点
（即所有前驱都按编号序先于该点被计算的点），单趟输出
的每个抽象环境覆盖该点全部可达的具体状态。**

这个断言的措辞值得逐词推敲："不含指针写入"是 13.10
Assign 情形的承诺边界；"前驱先于该点"是单趟机制的
固有限制——它把 while 循环体出口与出口后的所有点
（点 5、6、7）排除在担保之外，恰是 expected/output.txt
里那三行 ⊥ 的位置。**担保失效的位置与白卷出现的位置
精确重合**：这不是巧合，而是"⊥ = 无信息 = 无担保"的
同一枚硬币——分析知道自己在哪里失明，并把失明如实
写在输出里。第 16 章的不动点把断言中的限制条款删掉
（除指针边界外），担保范围扩展到全程序每一点——
届时重读本节，会看到"机制的缺陷"如何整个转化为
"担保的扩展"。

### 13.10.5 两条纪律如何变成自动化测试

13.3 的两条 γ 纪律目前只活在纸面上；它们有精确的
逐格形态，因此可以被机械化。把纪律翻译成测试，是
"可靠性由构造保证"的最后一步——构造有疏漏时，
测试兜底。

**纪律一的测试（γ-join 律）。** 对符号域的全部 5×5
有序对断言：γ(签名 a ⊔ 签名 b) == γ(a) ∪ γ(b)。测试
需要 γ 的机器表示——把五个符号映射为整数集合
（γ(−) = {n | n < 0} 在测试里采样为 {-3, -1} 等代表
元素即可，穷举整数不可行，但符号分类只需每类一个
见证）：对每格取若干对见证具体值，断言"具体结果 ∈
γ(表项)"（与 13.12 练习 4 同型）。注意这个测试比
join 律测试（练习 7）强：练习 7 验证代数结构，本
测试验证代数结构**相对于 γ 的语义正确性**——一个
精心构造的假 join 可以满足全部格定律却违背 γ。

**纪律二的测试（单调传递函数）。** 对环境的采样
字典序断言：σ̂1 ⊑ σ̂2 蕴含 transfer(n, σ̂1) ⊑
transfer(n, σ̂2)。环境采样取"变量全排列 × 符号全组合"
的代表性子集（教学程序变量少，全组合可行），13.7.2
的表格论证由此机械化。

两个测试的共同点是**量词的规模**：五元素域让"全称
量化"退化为"穷举列举"——这是小域的第二重工程红利
（第一重是 13.11 的高度论证）。第 14 章把域泛型化
之后，这两个测试升级为对任意 Lattice 实例的属性测试
模板；第 17 章的 --verify-soundness 则是它们的集成
版（对整程序、真实执行核对 γ 覆盖）。测试金字塔的
底层在这里就打好了。

## 13.11 终止性与局限

单趟的终止性不足挂齿：每点计算一次，n 个点 n 次传递，
线性时间。值得记录的是**它为什么 terminating**：没有
迭代、没有回访，任何点的状态只算一次、写一次。这也正是
它不精确的根源——循环要求回访，而单趟拒绝回访。

数据流分析的真正终止性议题在第 16 章：worklist 反复重算，
会不会无穷？答案的骨架本章已备齐——格有限（五元素），
环境是有限变量集上的映射格（第 14 章给出构造），状态空间
有限；若每次重算要么不变要么沿序**严格上升**（单调性），
则每点至多上升"格高度"次，总数有限。五元格的高度是 2
（⊥ 到 ⊤ 最长链两步），变量 k 个的状态格高度 2k——
上界粗糙但够用。第 16 章把这些骨架装配成定理。

本章遗留的局限清单，按修复章节排好：循环信息丢失 →
第 16 章不动点；join 太粗（− ⊔ + 直接 ⊤）→ 区间域
（第 20 章）等更细的域；比较信息丢弃 → 路径敏感
（第 22 章）；调用返回 ⊤ → 过程间分析（第 23 章）；
指针/记录目标不更新 → 指针分析（第 28 章）。一张清单
看得到全书后半的路线图——每个局限都是后续某章的存在
理由。

把骨架装配成数字。设程序有 n 个程序点、k 个变量，五元格
高度 2，则状态格（k 变量的映射格）高度 2k，每次重算某点
至多令该点状态沿链上升 2k 格。朴素全量迭代至多
O(n·k) 轮、每轮 O(n·k) 的工作量；worklist（第 16 章）
只重算受影响的点，实际轮数远低于上界。这些上界对教学
程序是天文数字般的宽裕——重要它们的是**形状**而非数值：
有限域 ⇒ 有限状态空间 ⇒ 严格上升 ⇒ 必然终止，四步
推理链在每一章的新域上重复使用，只有"高度"这个参数
在变。第 20 章区间域之所以兴师动众，正是因为它的
高度不再有限，推理链在第一步就断。

### 13.11.1 widening 的预告

"格有限 ⇒ 迭代终止"依赖格的**有限高度**，而这个前提
在第 20 章区间域上崩塌：区间 [0, 2147483647] 与
[0, 2147483648] 严格递增，链可以长得与整数范围一样——
循环 `while (…) { x = x + 1; }` 的迭代会一圈一圈抬升
上界，永不收敛。届时的对策是 widening（加宽）：迭代若
在同一处连续上升超过阈值，强行把区间扩到 ±∞。加宽
牺牲精度换取终止性，再靠 narrowing（收窄）补回一部分。
本章不实现这些，但 13.11 的骨架——"终止性 = 高度有限
× 单调上升"——是理解 widening 为何必要、又为何有效
的全部前置。看到域时先问高度，是格分析的肌肉记忆。

### 13.11.2 局限清单的三种读法

13.11 列出的五条局限（循环、join 粗、比较丢弃、调用、
指针）不是一张"待办事项"，它的读法决定了学习者从
本章带走什么。三种读法对应三种用途。

**作为路线图读**：每条局限的箭头指向修复它的章节，
合起来就是第四篇到第六篇的目录——循环→16、精度→20、
分支→22、过程间→23、指针→28。知道"每一章解决哪个
局限"，后面的章节就有了坐标系：读到第 20 章时应当
自问"它是不是在还 13.11 欠的那笔'join 太粗'的债"。

**作为设计方法论读**：五条局限没有一条是"分析器写错
了"——它们全部是**表达力的边界**，且每条边界都以
⊤（或恒等传递）的形式显式声明。这是抽象解释的工程
哲学：缺陷要设计进去、文档出来、注释钉住（工程注意
点 4），而不是藏着掖着等用户发现。五条局限的每一处
在代码里都有对应的注释，局限清单因此也是**代码导读
的索引**。

**作为需求清单读**：把清单倒过来问"如果我只关心其中
一条怎么办"，就得到"按需裁剪的分析器"思路——只要
循环精度不要指针分析，16 章之后即可止步；只要除零
检查，13 章本身已够（sDiv 的 0 检测不依赖任何后续
章节）。教学序列是线性的，工程取舍是多维的，清单是
两套坐标系的换算表。

// file: src/sign.hpp
// 符号格（Sign lattice, spa 第 4 章）：把整数的具体值按"正负号"分五类。
//   ⊥（不可达/无信息） < −、0、+（三者互不可比） < ⊤（三者皆可能）
// 本章只给"域 + 序 + join"和抽象算术；多趟不动点在第 16 章补上。
#pragma once

#include <string>

namespace tip {

// 编码：⊥=-2, −=-1, 0=0, +=1, ⊤=2。
// 用整数编码只是存储便利；序关系不是整数大小，join 必须查 join 表。
constexpr int SBOT = -2;
constexpr int SMINUS = -1;
constexpr int SZERO = 0;
constexpr int SPLUS = 1;
constexpr int STOP = 2;

std::string signShow(int s);

// 符号格的三要素：判定相等、偏序、最小上界。
// 后面所有单调框架的算法只依赖这三个操作（及 top/bot 边界）。
struct SignLattice {
    int top = STOP;
    int bot = SBOT;

    bool eq(int a, int b) const { return a == b; }
    bool leq(int a, int b) const;
    int join(int a, int b) const;
};

// 抽象算术：每个操作都对应整数运算"按符号分类"后的最小上界。
// 例如 +:(+,−)→⊤，因为正整数加负整数可能是 −、0 或 +。
int sAdd(int a, int b);
int sSub(int a, int b);
int sMul(int a, int b);
int sDiv(int a, int b);  // 除数符号含 0 时按 ⊥ 处理（具体程序在此抛错/中止）

// 比较运算在 TIP 中产生 0/1：抽象结果恒为 {0,+}=⊤（⊥ 仍吸收）。
int sCompare(int a, int b);

}  // namespace tip

// file: src/sign.cpp
#include "sign.hpp"

#include <array>

namespace tip {

std::string signShow(int s) {
    switch (s) {
        case SBOT: return "⊥";
        case SMINUS: return "−";
        case SZERO: return "0";
        case SPLUS: return "+";
        case STOP: return "⊤";
    }
    return "?";
}

bool SignLattice::leq(int a, int b) const {
    if (a == SBOT || b == STOP) return true;   // 底最小、顶最大
    if (b == SBOT || a == STOP) return a == b; // 越过底/顶的唯一可能是相等
    return a == b;                             // −、0、+ 三者互不可比
}

int SignLattice::join(int a, int b) const {
    if (a == b) return a;
    if (a == SBOT) return b;                   // ⊥ ⊔ x = x
    if (b == SBOT) return a;
    return STOP;                               // 其余组合（含 −/0/+ 两两）= ⊤
}

namespace {

// 加法符号表（行=左操作数 [−,0,+,⊤]，列=右操作数）。
constexpr std::array<std::array<int, 4>, 4> ADD_TABLE = {{
    //  −      0      +      ⊤
    {{SMINUS, SMINUS, STOP,  STOP }},  // −
    {{SMINUS, SZERO,  SPLUS, STOP }},  // 0
    {{STOP,   SPLUS,  SPLUS, STOP }},  // +
    {{STOP,   STOP,   STOP,  STOP }},  // ⊤
}};

// 乘法符号表：同号得 +，异号得 −，任何一边是 0 得 0。
constexpr std::array<std::array<int, 4>, 4> MUL_TABLE = {{
    //  −      0      +      ⊤
    {{SPLUS,  SZERO,  SMINUS, STOP }},  // −
    {{SZERO,  SZERO,  SZERO,  SZERO}},  // 0
    {{SMINUS, SZERO,  SPLUS,  STOP }},  // +
    {{STOP,   SZERO,  STOP,   STOP }},  // ⊤
}};

int idx(int s) { return s + 1; }  // −(-1)→0, 0→1, +(1)→2, ⊤(2)→3

}  // namespace

int sAdd(int a, int b) {
    if (a == SBOT || b == SBOT) return SBOT;
    return ADD_TABLE[idx(a)][idx(b)];
}

int sSub(int a, int b) {
    if (a == SBOT || b == SBOT) return SBOT;
    // a − b = a + (−b)：−、+ 互换，0/⊤ 不变。
    const int negB = b == SMINUS ? SPLUS : b == SPLUS ? SMINUS : b;
    return ADD_TABLE[idx(a)][idx(negB)];
}

int sMul(int a, int b) {
    if (a == SBOT || b == SBOT) return SBOT;
    return MUL_TABLE[idx(a)][idx(b)];
}

int sDiv(int a, int b) {
    if (a == SBOT || b == SBOT) return SBOT;
    if (b == SZERO) return SBOT;  // 除以确定的 0：该路径具体不可行（抛错中止）
    // 排除"除数可能为 0"的情形后，商的符号规律与乘法相同。
    if (b == STOP) {
        // 除数 ∈ {−,0,+}：0 排除，剩下 {−,+}；结果符号对 −/+ 分别讨论后取 join。
        return sAdd(sMul(a, SMINUS), sMul(a, SPLUS));
    }
    return MUL_TABLE[idx(a)][idx(b)];
}

int sCompare(int a, int b) {
    if (a == SBOT || b == SBOT) return SBOT;
    return STOP;  // 比较结果只可能是 0 或 1：{0,+} 在本格中即 ⊤
}

}  // namespace tip

// file: src/sign_transfer.cpp
#include "sign_transfer.hpp"

#include <map>
#include <set>
#include <sstream>
#include <vector>

#include "pretty.hpp"
#include "sign.hpp"

namespace tip {

int signOfLiteral(int v) {
    if (v < 0) return SMINUS;
    if (v == 0) return SZERO;
    return SPLUS;
}

int evalExprSign(const Expr *e, const SignEnv &env) {
    if (const auto *x = dynamic_cast<const IntLit *>(e)) return signOfLiteral(x->v);
    if (const auto *x = dynamic_cast<const VarRef *>(e)) {
        auto it = env.find(x->name);
        return it == env.end() ? SBOT : it->second;
    }
    if (dynamic_cast<const InputE *>(e)) return STOP;  // 输入流的下一个整数符号未知
    if (const auto *x = dynamic_cast<const Binop *>(e)) {
        const int l = evalExprSign(x->l.get(), env);
        const int r = evalExprSign(x->r.get(), env);
        switch (x->op) {
            case BOp::Add: return sAdd(l, r);
            case BOp::Sub: return sSub(l, r);
            case BOp::Mul: return sMul(l, r);
            case BOp::Div: return sDiv(l, r);
            case BOp::Gt:
            case BOp::Eq: return sCompare(l, r);
        }
    }
    // 函数调用的返回值、指针/记录相关表达式：本章按"任意整数"保守处理，
    // 精确分析在过程间（第 23 章起）与指针篇（第 28 章）给出。
    (void)e;
    return STOP;
}

SignEnv entryEnv(const FunDecl &f) {
    SignEnv env;
    for (const std::string &p : f.params) env[p] = STOP;  // 调用方实参符号未知
    return env;
}

SignEnv joinEnv(const SignEnv &a, const SignEnv &b) {
    SignEnv r = a;
    SignLattice lat;
    for (const auto &[k, v] : b) {
        auto it = r.find(k);
        r[k] = it == r.end() ? v : lat.join(it->second, v);
    }
    return r;
}

SignEnv transferNode(const CfgNode &node, const SignEnv &in) {
    if (node.kind != CfgNode::Kind::Assign || !node.stmt) return in;
    const auto *a = dynamic_cast<const AssignS *>(node.stmt);
    const auto *target = dynamic_cast<const VarRef *>(a->target.get());
    if (!target) return in;  // *p / r.f 目标：第 28 章指针分析之前保持环境不变
    SignEnv out = in;
    out[target->name] = evalExprSign(a->value.get(), in);
    return out;
}

namespace {

std::map<int, std::vector<int>> predecessorMap(const FunCfg &f) {
    std::map<int, std::vector<int>> preds;
    for (const auto &[from, to] : f.edges) preds[to].push_back(from);
    return preds;
}

const char *nodeLabel(CfgNode::Kind kind) {
    switch (kind) {
        case CfgNode::Kind::Entry: return "entry";
        case CfgNode::Kind::Exit: return "exit";
        case CfgNode::Kind::Assign: return "assign";
        case CfgNode::Kind::Output: return "output";
        case CfgNode::Kind::Branch: return "branch";
        case CfgNode::Kind::Return: return "return";
    }
    return "?";
}

}  // namespace

PointEnv singlePass(const Cfg &cfg, const ProgramA &program) {
    PointEnv states;
    for (const FunCfg &fc : cfg.funs) {
        const FunDecl *decl = nullptr;
        for (const auto &f : program.funs)
            if (f->name == fc.name) decl = f.get();

        const auto preds = predecessorMap(fc);
        for (const auto &[id, node] : fc.nodes) {
            if (node.kind == CfgNode::Kind::Entry) {
                states[id] = entryEnv(*decl);  // 边界条件：参数 ⊤
                continue;
            }
            // 前驱尚未计算（典型是循环回边）时其状态按全 ⊥（空环境）处理。
            SignEnv in;
            auto pit = preds.find(id);
            if (pit != preds.end()) {
                for (int q : pit->second) {
                    auto qit = states.find(q);
                    if (qit != states.end()) in = joinEnv(in, qit->second);
                }
            }
            states[id] = transferNode(node, in);
        }
    }
    return states;
}

std::string printPointEnv(const Cfg &cfg, const ProgramA &program,
                          const PointEnv &states) {
    std::ostringstream out;
    for (const FunCfg &fc : cfg.funs) {
        out << "-- " << fc.name << " --\n";

        const FunDecl *decl = nullptr;  // 变量打印顺序：参数在前，局部变量在后
        for (const auto &f : program.funs)
            if (f->name == fc.name) decl = f.get();
        std::vector<std::string> names = decl->params;
        for (const std::string &v : decl->vars) names.push_back(v);

        for (const auto &[id, node] : fc.nodes) {
            out << "  " << id << ' ' << nodeLabel(node.kind);
            if (node.kind == CfgNode::Kind::Branch && node.stmt) {
                // 分支点只标注条件，避免把整个 if/while 体压成一行又折行。
                if (const auto *w = dynamic_cast<const WhileS *>(node.stmt))
                    out << "  while " << printExpr(w->cond.get());
                else if (const auto *i = dynamic_cast<const IfS *>(node.stmt))
                    out << "  if " << printExpr(i->cond.get());
            } else if (node.stmt) {
                out << "  " << printStmtLine(*node.stmt);
            }
            out << ':';

            const SignEnv &env = states.at(id);
            for (const std::string &k : names) {
                auto it = env.find(k);
                out << ' ' << k << '='
                    << signShow(it == env.end() ? SBOT : it->second);
            }
            out << '\n';
        }
    }
    return out.str();
}

class CollectErrorListener : public antlr4::BaseErrorListener {
public:
    std::vector<std::string> messages;

    void syntaxError(antlr4::Recognizer *, antlr4::Token *, size_t line,
                     size_t column, const std::string &msg,
                     std::exception_ptr) override {
        messages.push_back("syntax error line " + std::to_string(line) + ":" +
                           std::to_string(column) + " " + msg);
    }

struct Parsed {
    std::unique_ptr<tip::ProgramA> ast;
    tip::Bindings bindings;

Parsed parseFile(const std::string &path) {
    std::ifstream src(path);
    if (!src) {
        std::cerr << "cannot open " << path << '\n';
        std::exit(1);
    }
    antlr4::ANTLRInputStream input(src);
    TIPLexer lexer(&input);
    antlr4::CommonTokenStream tokens(&lexer);
    TIPParser parser(&tokens);

    CollectErrorListener errors;
    lexer.removeErrorListeners();
    parser.removeErrorListeners();
    lexer.addErrorListener(&errors);
    parser.addErrorListener(&errors);

    TIPParser::ProgramContext *tree = parser.program();
    if (!errors.messages.empty()) {
        for (const std::string &m : errors.messages) std::cout << m << '\n';
        std::exit(2);
    }

    Parsed result;
    result.ast = tip::buildAst(tree);
    result.bindings = tip::resolveNames(*result.ast);
    if (!result.bindings.errors.empty()) {
        for (const tip::Diag &d : result.bindings.errors)
            std::cout << d.text << '\n';
        std::exit(3);
    }
    return result;
}

    std::vector<int> values;

    while (ss >> v) values.push_back(v);

        Parsed p = parseFile(argv[2]);
        tip::Cfg cfg = tip::buildCfg(*p.ast);
        tip::PointEnv states = tip::singlePass(cfg, *p.ast);

        std::cout << "single-pass sign analysis (back edges ignored, no fixpoint):\n";
        std::cout << tip::printPointEnv(cfg, *p.ast, states);
        return 0;
    }

    if (argc >= 3 && std::string(argv[1]) == "--emit-ir") {
        Parsed p = parseFile(argv[2]);
        tip::IRGen gen;
        gen.gen(*p.ast, p.bindings);
        if (!gen.verify()) {
            std::cerr << "generated module failed verification\n";
            return 1;
        }
        std::cout << gen.dump();
        return 0;
    }

    if (argc == 4 && std::string(argv[1]) == "--run") {
        std::ifstream in(argv[3]);
        if (!in) {
            std::cerr << "cannot open " << argv[3] << '\n';
            return 1;
        }
        int run = 0;
        std::string line;
        while (std::getline(in, line)) {
            std::string trimmed = line;
            size_t a = trimmed.find_first_not_of(" \t\r\n");
            if (a == std::string::npos) continue;
            if (trimmed[a] == '#') continue;

            std::vector<int> inputs = parseRun(trimmed);
            Parsed p = parseFile(argv[2]);
            tip::IRGen gen;
            gen.gen(*p.ast, p.bindings);
            if (!gen.verify()) {
                std::cerr << "generated module failed verification\n";
                return 1;
            }
            std::vector<int> outputs = tip::runJit(std::move(gen), inputs);

            std::cout << "run " << ++run << ":";
            for (size_t i = 0; i < outputs.size(); ++i)
                std::cout << (i ? ", " : " ") << outputs[i];
            std::cout << '\n';
        }
        return 0;
    }

    std::cerr << "usage: tipa --check FILE | tipa --emit-ir FILE | tipa --run FILE INPUTS\n";
    return 1;
}

// file: src/cfg.cpp
#include "cfg.hpp"

#include <map>
#include <set>
#include <sstream>
#include <vector>

#include "pretty.hpp"

namespace tip {
namespace {

// 两遍构造：第一遍按 AST 先序给所有程序点分配固定编号；第二遍连边。
// 先编号再连边，是为了让编号严格按源码顺序（连边时若先构造后继节点，
// 后继会抢在前面编号），从而输出与程序点编号都是确定的。
class CfgBuilder {
public:
    explicit CfgBuilder(const ProgramA &program) : program_(program) {}

    Cfg run() {
        Cfg cfg;
        for (const auto &fun : program_.funs) {
            FunCfg fc;
            cur_ = &fc;
            cur_->name = fun->name;
            nextId_ = 1;
            stmtId_.clear();

            const int entry = addNode(CfgNode::Kind::Entry);
            cur_->entry = entry;
            numberStmt(fun->body.get());
            const int retId = addNode(CfgNode::Kind::Return, fun->ret.get());
            const int exitId = addNode(CfgNode::Kind::Exit);
            cur_->exitNode = exitId;

            // 连边：语句构造返回它自己的入口点集合；空块没有节点，直接透传后继。
            std::vector<int> bodyEntries = wireStmt(fun->body.get(), {retId});
            if (bodyEntries.empty()) bodyEntries = {retId};
            link(entry, bodyEntries);
            link(retId, {exitId});

            // set 去重并排序：CFG 边不允许重复，输出顺序固定。
            std::set<std::pair<int, int>> uniq(cur_->edges.begin(), cur_->edges.end());
            cur_->edges.assign(uniq.begin(), uniq.end());
            cfg.funs.push_back(std::move(*cur_));
        }
        return cfg;
    }

private:
    const ProgramA &program_;
    FunCfg *cur_ = nullptr;
    int nextId_ = 1;
    std::map<const Stmt *, int> stmtId_;

    int addNode(CfgNode::Kind kind, const Stmt *stmt = nullptr) {
        const int id = nextId_++;
        cur_->nodes.emplace(id, CfgNode{id, kind, stmt});
        return id;
    }

    // ---- 第一遍：编号 ----
    void numberStmt(const Stmt *s) {
        if (const auto *b = dynamic_cast<const BlockS *>(s)) {
            for (const auto &x : b->ss) numberStmt(x.get());
            return;
        }
        if (const auto *x = dynamic_cast<const IfS *>(s)) {
            stmtId_[x] = addNode(CfgNode::Kind::Branch, x);
            numberStmt(x->then.get());
            numberStmt(x->els.get());
            return;
        }
        if (const auto *x = dynamic_cast<const WhileS *>(s)) {
            stmtId_[x] = addNode(CfgNode::Kind::Branch, x);
            numberStmt(x->body.get());
            return;
        }
        if (dynamic_cast<const AssignS *>(s)) {
            stmtId_[s] = addNode(CfgNode::Kind::Assign, s);
            return;
        }
        if (dynamic_cast<const OutputS *>(s)) {
            stmtId_[s] = addNode(CfgNode::Kind::Output, s);
        }
    }

    // ---- 第二遍：连边。返回进入该语句时首先到达的程序点集合 ----
    std::vector<int> wireStmt(const Stmt *s, const std::vector<int> &succ) {
        if (const auto *b = dynamic_cast<const BlockS *>(s)) {
            std::vector<int> cur = succ;
            for (auto it = b->ss.rbegin(); it != b->ss.rend(); ++it)
                cur = wireStmt(it->get(), cur);
            return cur;
        }
        if (const auto *x = dynamic_cast<const IfS *>(s)) {
            const int n = stmtId_[x];
            std::vector<int> targets = wireStmt(x->then.get(), succ);
            if (targets.empty()) targets = succ;
            if (x->els) {
                std::vector<int> e = wireStmt(x->els.get(), succ);
                if (e.empty()) e = succ;
                targets.insert(targets.end(), e.begin(), e.end());
            } else {
                targets.insert(targets.end(), succ.begin(), succ.end());
            }
            link(n, targets);
            return {n};
        }
        if (const auto *x = dynamic_cast<const WhileS *>(s)) {
            const int n = stmtId_[x];
            // 循环体执行完回到条件点；空体时条件点连一条自边（等于死循环）。
            std::vector<int> bodyEntries = wireStmt(x->body.get(), {n});
            if (bodyEntries.empty()) bodyEntries = {n};
            link(n, bodyEntries);
            link(n, succ);
            return {n};
        }
        const int n = stmtId_[s];
        link(n, succ);
        return {n};
    }

    void link(int from, const std::vector<int> &to) {
        for (int t : to) cur_->edges.emplace_back(from, t);
    }
};

const char *kindName(CfgNode::Kind kind) {
    switch (kind) {
        case CfgNode::Kind::Entry: return "entry";
        case CfgNode::Kind::Exit: return "exit";
        case CfgNode::Kind::Assign: return "assign";
        case CfgNode::Kind::Output: return "output";
        case CfgNode::Kind::Branch: return "branch";
        case CfgNode::Kind::Return: return "return";
    }
    return "?";
}

}  // namespace

Cfg buildCfg(const ProgramA &program) { return CfgBuilder(program).run(); }

std::string printCfg(const Cfg &cfg) {
    std::ostringstream out;
    for (const FunCfg &f : cfg.funs) {
        out << "== " << f.name << " ==\n";
        out << "nodes:\n";
        for (const auto &[id, node] : f.nodes) {
            out << "  " << id << ": " << kindName(node.kind);
            if (node.stmt) out << "  " << printStmtLine(*node.stmt);
            out << "\n";
        }
        out << "edges:\n";
        for (const auto &[a, b] : f.edges) out << "  " << a << " -> " << b << "\n";
    }
    return out.str();
}

enum class BOp { Add, Sub, Mul, Div, Gt, Eq };

struct Expr {
    virtual ~Expr() = default;
};
struct IntLit : Expr {
    int v;
    explicit IntLit(int value) : v(value) {}
};
struct VarRef : Expr {
    std::string name;
    explicit VarRef(std::string n) : name(std::move(n)) {}

    BOp op;
    std::unique_ptr<Expr> l, r;

    std::unique_ptr<Stmt> body;

// file: src/ast_build.cpp
#include "ast_build.hpp"

#include <utility>
#include <vector>

namespace tip {

std::unique_ptr<ProgramA> AstBuilder::build(TIPParser::ProgramContext *tree) {
    auto program = std::make_unique<ProgramA>();
    for (auto *fc : tree->function()) program->funs.push_back(buildFun(fc));
    return program;
}

std::unique_ptr<FunDecl> AstBuilder::buildFun(TIPParser::FunctionContext *ctx) {
    auto f = std::make_unique<FunDecl>();
    f->name = ctx->IDENT()->getText();
    if (ctx->params()) {
        for (auto *p : ctx->params()->IDENT()) f->params.push_back(p->getText());
    }
    if (ctx->varDecls()) {
        for (auto *v : ctx->varDecls()->IDENT()) f->vars.push_back(v->getText());
    }

    std::vector<std::unique_ptr<Stmt>> body;
    for (auto *sc : ctx->stmt()) body.push_back(buildStmt(sc));
    f->body = std::make_unique<BlockS>(std::move(body));

    f->ret = std::make_unique<ReturnS>(buildExpr(ctx->expr()));
    return f;
}

std::unique_ptr<Expr> AstBuilder::buildLvalue(TIPParser::LvalueContext *lv) {
    std::unique_ptr<Expr> base;
    std::string field;
    if (auto *d = dynamic_cast<TIPParser::DirectLvalueContext *>(lv)) {
        base = std::make_unique<VarRef>(d->IDENT(0)->getText());
        if (d->IDENT().size() == 2) field = d->IDENT(1)->getText();
    } else {
        auto *p = dynamic_cast<TIPParser::PointerLvalueContext *>(lv);
        base = std::make_unique<Deref>(buildExpr(p->expr()));
        if (p->IDENT()) field = p->IDENT()->getText();
    }
    if (!field.empty())
        return std::make_unique<FieldA>(std::move(base), std::move(field));
    return base;
}

std::unique_ptr<Expr> AstBuilder::buildExpr(TIPParser::ExprContext *ctx) {
    if (auto *c = dynamic_cast<TIPParser::IntExprContext *>(ctx))
        return std::make_unique<IntLit>(std::stoi(c->INT()->getText()));
    if (auto *c = dynamic_cast<TIPParser::VarExprContext *>(ctx))
        return std::make_unique<VarRef>(c->IDENT()->getText());
    if (dynamic_cast<TIPParser::InputExprContext *>(ctx))
        return std::make_unique<InputE>();
    if (dynamic_cast<TIPParser::NullExprContext *>(ctx))
        return std::make_unique<NullE>();
    if (auto *c = dynamic_cast<TIPParser::ParenExprContext *>(ctx))
        return buildExpr(c->expr());

    if (auto *c = dynamic_cast<TIPParser::AddExprContext *>(ctx)) {
        const BOp op = c->PLUS() ? BOp::Add : BOp::Sub;
        return std::make_unique<Binop>(op, buildExpr(c->expr(0)), buildExpr(c->expr(1)));
    }
    if (auto *c = dynamic_cast<TIPParser::MulExprContext *>(ctx)) {
        const BOp op = c->STAR() ? BOp::Mul : BOp::Div;
        return std::make_unique<Binop>(op, buildExpr(c->expr(0)), buildExpr(c->expr(1)));
    }
    if (auto *c = dynamic_cast<TIPParser::CmpExprContext *>(ctx)) {
        const BOp op = c->GT() ? BOp::Gt : BOp::Eq;
        return std::make_unique<Binop>(op, buildExpr(c->expr(0)), buildExpr(c->expr(1)));
    }
    if (auto *c = dynamic_cast<TIPParser::NegExprContext *>(ctx)) {
        // TIP 没有负数字面量 token，-E 即 0-E。
        return std::make_unique<Binop>(BOp::Sub, std::make_unique<IntLit>(0),
                                       buildExpr(c->expr()));
    }
    if (auto *c = dynamic_cast<TIPParser::CallExprContext *>(ctx)) {
        std::vector<std::unique_ptr<Expr>> args;
        if (c->args())
            for (auto *a : c->args()->expr()) args.push_back(buildExpr(a));
        return std::make_unique<CallE>(buildExpr(c->expr()), std::move(args));
    }
    if (auto *c = dynamic_cast<TIPParser::FieldExprContext *>(ctx))
        return std::make_unique<FieldA>(buildExpr(c->expr()), c->IDENT()->getText());
    if (auto *c = dynamic_cast<TIPParser::DerefExprContext *>(ctx))
        return std::make_unique<Deref>(buildExpr(c->expr()));
    if (auto *c = dynamic_cast<TIPParser::AddrExprContext *>(ctx))
        return std::make_unique<AddrOf>(c->IDENT()->getText());
    if (auto *c = dynamic_cast<TIPParser::AllocExprContext *>(ctx))
        return std::make_unique<AllocE>(buildExpr(c->expr()));
    if (auto *c = dynamic_cast<TIPParser::RecExprContext *>(ctx)) {
        std::vector<std::pair<std::string, std::unique_ptr<Expr>>> fields;
        for (auto *fc : c->field())
            fields.emplace_back(fc->IDENT()->getText(), buildExpr(fc->expr()));
        return std::make_unique<RecLit>(std::move(fields));
    }
    return nullptr;  // 解析成功时不会到达
}

std::unique_ptr<Stmt> AstBuilder::buildStmt(TIPParser::StmtContext *ctx) {
    if (auto *c = dynamic_cast<TIPParser::AssignStmtContext *>(ctx))
        return std::make_unique<AssignS>(buildLvalue(c->lvalue()), buildExpr(c->expr()));
    if (auto *c = dynamic_cast<TIPParser::OutputStmtContext *>(ctx))
        return std::make_unique<OutputS>(buildExpr(c->expr()));
    if (auto *c = dynamic_cast<TIPParser::IfStmtContext *>(ctx)) {
        std::unique_ptr<Stmt> els;
        if (c->stmt().size() == 2) els = buildStmt(c->stmt(1));
        return std::make_unique<IfS>(buildExpr(c->expr()), buildStmt(c->stmt(0)),
                                     std::move(els));
    }
    if (auto *c = dynamic_cast<TIPParser::WhileStmtContext *>(ctx))
        return std::make_unique<WhileS>(buildExpr(c->expr()), buildStmt(c->stmt()));
    if (auto *c = dynamic_cast<TIPParser::BlockStmtContext *>(ctx)) {
        std::vector<std::unique_ptr<Stmt>> ss;
        for (auto *sc : c->stmt()) ss.push_back(buildStmt(sc));
        return std::make_unique<BlockS>(std::move(ss));
    }
    return nullptr;  // 解析成功时不会到达
}

std::unique_ptr<ProgramA> buildAst(TIPParser::ProgramContext *tree) {
    return AstBuilder{}.build(tree);
}

}  // namespace tip

// file: src/pretty.cpp
#include "pretty.hpp"

#include <string>

namespace tip {

namespace {

// 表达式打印为前缀式：运算符与符号的对照表。
std::string exprText(const Expr *e) {
    if (const auto *x = dynamic_cast<const IntLit *>(e)) return std::to_string(x->v);
    if (const auto *x = dynamic_cast<const VarRef *>(e)) return x->name;
    if (dynamic_cast<const InputE *>(e)) return "input";
    if (dynamic_cast<const NullE *>(e)) return "null";

    if (const auto *x = dynamic_cast<const Binop *>(e)) {
        const char *sym = "+";
        switch (x->op) {
            case BOp::Add: sym = "+"; break;
            case BOp::Sub: sym = "-"; break;
            case BOp::Mul: sym = "*"; break;
            case BOp::Div: sym = "/"; break;
            case BOp::Gt: sym = ">"; break;
            case BOp::Eq: sym = "=="; break;
        }
        return "(" + std::string(sym) + " " + exprText(x->l.get()) + " " +
               exprText(x->r.get()) + ")";
    }
    if (const auto *x = dynamic_cast<const CallE *>(e)) {
        std::string s = "(call " + exprText(x->callee.get());
        for (const auto &a : x->args) s += " " + exprText(a.get());
        return s + ")";
    }
    if (const auto *x = dynamic_cast<const Deref *>(e))
        return "(* " + exprText(x->e.get()) + ")";
    if (const auto *x = dynamic_cast<const AddrOf *>(e)) return "(& " + x->name + ")";
    if (const auto *x = dynamic_cast<const AllocE *>(e))
        return "(alloc " + exprText(x->e.get()) + ")";
    if (const auto *x = dynamic_cast<const FieldA *>(e))
        return "(. " + exprText(x->e.get()) + " " + x->field + ")";
    if (const auto *x = dynamic_cast<const RecLit *>(e)) {
        std::string s = "{";
        for (size_t i = 0; i < x->fields.size(); ++i) {
            if (i) s += ", ";
            s += x->fields[i].first + ": " + exprText(x->fields[i].second.get());
        }
        return s + "}";
    }
    return "<unknown expr>";
}

std::string indent(int level) { return std::string(static_cast<size_t>(level) * 2, ' '); }

// 语句打印带缩进，一条语句一行（块内多行）。
void stmtText(const Stmt *s, int level, std::string &out) {
    if (const auto *x = dynamic_cast<const AssignS *>(s)) {
        out += indent(level) + exprText(x->target.get()) + " = " +
               exprText(x->value.get()) + " ;\n";
        return;
    }
    if (const auto *x = dynamic_cast<const OutputS *>(s)) {
        out += indent(level) + "output " + exprText(x->e.get()) + " ;\n";
        return;
    }
    if (const auto *x = dynamic_cast<const ReturnS *>(s)) {
        out += indent(level) + "return " + exprText(x->e.get()) + " ;\n";
        return;
    }
    if (const auto *x = dynamic_cast<const IfS *>(s)) {
        out += indent(level) + "if (" + exprText(x->cond.get()) + ")\n";
        stmtText(x->then.get(), level + 1, out);
        if (x->els) {
            out += indent(level) + "else\n";
            stmtText(x->els.get(), level + 1, out);
        }
        return;
    }
    if (const auto *x = dynamic_cast<const WhileS *>(s)) {
        out += indent(level) + "while (" + exprText(x->cond.get()) + ")\n";
        stmtText(x->body.get(), level + 1, out);
        return;
    }
    if (const auto *x = dynamic_cast<const BlockS *>(s)) {
        out += indent(level) + "{\n";
        for (const auto &st : x->ss) stmtText(st.get(), level + 1, out);
        out += indent(level) + "}\n";
        return;
    }
    out += indent(level) + "<unknown stmt>\n";
}

}  // namespace

std::string printExpr(const Expr *e) { return exprText(e); }

std::string printProgram(const ProgramA &program) {
    std::string out;
    for (const auto &f : program.funs) {
        std::string paramList;
        for (size_t i = 0; i < f->params.size(); ++i) {
            if (i) paramList += ",";
            paramList += f->params[i];
        }
        out += f->name + "(" + paramList + ") {\n";
        if (!f->vars.empty()) {
            out += indent(1) + "var ";
            for (size_t i = 0; i < f->vars.size(); ++i) {
                if (i) out += ",";
                out += f->vars[i];
            }
            out += " ;\n";
        }
        // 函数体是 BlockS；打印其内部语句而不是再嵌一层花括号。
        const auto *body = dynamic_cast<const BlockS *>(f->body.get());
        for (const auto &st : body->ss) stmtText(st.get(), 1, out);
        stmtText(f->ret.get(), 1, out);
        out += "}\n";
    }
    return out;
}

// 单行形式：CFG 节点标签等"节点旁边写一句话"的场合使用。
std::string printStmtLine(const Stmt &stmt) {
    std::string out;
    stmtText(&stmt, 0, out);
    if (!out.empty() && out.back() == '\n') out.pop_back();
    return out;
}

}  // namespace tip

// file: src/symtab.cpp
#include "symtab.hpp"

#include <utility>

namespace tip {

namespace {

// 解析器在遍历 AST 的同时完成绑定与诊断收集。
struct Resolver {
    Bindings bindings;
    Scope *current = nullptr;
    const FunDecl *owner = nullptr;

    void declare(const std::string &name, Symbol::Kind kind) {
        if (current->table.count(name)) {
            bindings.errors.push_back({"error: redeclared '" + name + "'"});
            return;  // 保留先声明者，后声明被忽略
        }
        current->table.emplace(name, Symbol{kind, name, owner});
    }

    void resolveExpr(const Expr *e) {
        if (const auto *x = dynamic_cast<const VarRef *>(e)) {
            const Symbol *s = current->lookup(x->name);
            if (!s) {
                bindings.errors.push_back({"error: undeclared '" + x->name + "'"});
            } else {
                bindings.uses[x] = s;
            }
            return;
        }
        if (const auto *x = dynamic_cast<const Binop *>(e)) {
            resolveExpr(x->l.get());
            resolveExpr(x->r.get());
            return;
        }
        if (const auto *x = dynamic_cast<const CallE *>(e)) {
            resolveExpr(x->callee.get());
            for (const auto &a : x->args) resolveExpr(a.get());
            return;
        }
        if (const auto *x = dynamic_cast<const Deref *>(e)) return resolveExpr(x->e.get());
        if (const auto *x = dynamic_cast<const AllocE *>(e)) return resolveExpr(x->e.get());
        if (const auto *x = dynamic_cast<const FieldA *>(e)) {
            resolveExpr(x->e.get());  // 字段名不是变量，无需解析
            return;
        }
        if (const auto *x = dynamic_cast<const RecLit *>(e)) {
            for (const auto &f : x->fields) resolveExpr(f.second.get());
            return;
        }
        // IntLit / InputE / AddrOf / NullE：无变量使用。
    }

    void resolveStmt(const Stmt *s) {
        if (const auto *x = dynamic_cast<const AssignS *>(s)) {
            resolveExpr(x->target.get());
            resolveExpr(x->value.get());
            return;
        }
        if (const auto *x = dynamic_cast<const OutputS *>(s)) return resolveExpr(x->e.get());
        if (const auto *x = dynamic_cast<const IfS *>(s)) {
            resolveExpr(x->cond.get());
            resolveStmt(x->then.get());
            if (x->els) resolveStmt(x->els.get());
            return;
        }
        if (const auto *x = dynamic_cast<const WhileS *>(s)) {
            resolveExpr(x->cond.get());
            resolveStmt(x->body.get());
            return;
        }
        if (const auto *x = dynamic_cast<const BlockS *>(s)) {
            for (const auto &st : x->ss) resolveStmt(st.get());
            return;
        }
        if (const auto *x = dynamic_cast<const ReturnS *>(s)) return resolveExpr(x->e.get());
    }
};

}  // namespace

const Symbol *Scope::lookup(const std::string &name) const {
    auto it = table.find(name);
    if (it != table.end()) return &it->second;
    return parent ? parent->lookup(name) : nullptr;
}

Bindings resolveNames(ProgramA &program) {
    Resolver resolver;
    resolver.bindings.global = Scope(nullptr);
    Scope *global = &resolver.bindings.global;

    // 第一遍：所有函数名进入全局作用域。
    for (const auto &f : program.funs) {
        if (global->table.count(f->name)) {
            resolver.bindings.errors.push_back({"error: redeclared '" + f->name + "'"});
            continue;
        }
        global->table.emplace(f->name, Symbol{Symbol::Fun, f->name, f.get()});
    }

    // 第二遍：每个函数开自己的作用域，父作用域是全局表；
    // 作用域所有权交给 Bindings，遍历结束后符号依然存活。
    for (const auto &f : program.funs) {
        auto functionScope = std::make_unique<Scope>(global);
        resolver.current = functionScope.get();
        resolver.owner = f.get();

        for (const std::string &p : f->params) resolver.declare(p, Symbol::Param);
        for (const std::string &v : f->vars) resolver.declare(v, Symbol::Local);

        resolver.resolveStmt(f->body.get());
        resolver.resolveStmt(f->ret.get());

        resolver.current = nullptr;
        resolver.bindings.scopes.push_back(std::move(functionScope));
    }
    return std::move(resolver.bindings);
}

}  // namespace tip

// LLVM IR 生成：把 AST 翻译成 LLVM Module。
// 本章只覆盖整数核心：算术、比较、input/output、if/while、直接函数调用；

// file: src/irgen.cpp
#include "irgen.hpp"

#include <stdexcept>
#include <utility>
#include <vector>

#include "llvm/IR/BasicBlock.h"
#include "llvm/IR/Constants.h"
#include "llvm/IR/DerivedTypes.h"
#include "llvm/IR/Function.h"
#include "llvm/IR/Verifier.h"
#include "llvm/Support/raw_ostream.h"

using namespace llvm;

namespace tip {

IRGen::IRGen()
    : ctx(std::make_unique<LLVMContext>()),
      mod(std::make_unique<Module>("tip", *ctx)),
      b(std::make_unique<IRBuilder<>>(*ctx)) {
    // 运行时入口先声明：input 无参返回 i32，output 吃一个 i32。
    auto *i32 = Type::getInt32Ty(*ctx);
    rtInput_ = mod->getOrInsertFunction(
        "tip_input", FunctionType::get(i32, false));
    rtOutput_ = mod->getOrInsertFunction(
        "tip_output", FunctionType::get(Type::getVoidTy(*ctx), {i32}, false));
}

namespace {

// TIP 的 main 改名 tip_main：真正的 @main 是我们生成的 C 入口。
std::string emitName(const std::string &name) {
    return name == "main" ? "tip_main" : name;
}

}  // namespace

void IRGen::gen(const ProgramA &program, const Bindings &resolved) {
    bindings = &resolved;

    // 先创建全部函数（含类型），函数体互相前向调用时也能查到声明。
    auto *i32 = Type::getInt32Ty(*ctx);
    for (const auto &f : program.funs) {
        std::vector<Type *> args(f->params.size(), i32);
        auto *ft = FunctionType::get(i32, args, false);
        Function::Create(ft, Function::ExternalLinkage,
                         emitName(f->name), *mod);
    }

    for (size_t i = 0; i < program.funs.size(); ++i) {
        const auto &f = program.funs[i];
        cur = f.get();
        genFun(f.get(), resolved.scopes[i].get());
    }

    const FunDecl *mainFun = nullptr;
    for (const auto &f : program.funs)
        if (f->name == "main") mainFun = f.get();
    if (!mainFun) throw std::runtime_error("program has no main");
    genWrapper(mainFun);
}

void IRGen::genFun(const FunDecl *f, Scope *scope) {
    auto *fn = llvm::cast<Function>(mod->getFunction(emitName(f->name)));
    auto *entry = BasicBlock::Create(*ctx, "entry", fn);
    b->SetInsertPoint(entry);

    // 形参：alloca 槽位 + 存入实参；var 局部：alloca + 零初始化。
    for (size_t j = 0; j < f->params.size(); ++j) {
        const Symbol *s = &scope->table.at(f->params[j]);
        auto *slot = b->CreateAlloca(b->getInt32Ty(), nullptr, f->params[j]);
        b->CreateStore(fn->getArg(j), slot);
        locals[s] = slot;
    }
    for (const std::string &v : f->vars) {
        const Symbol *s = &scope->table.at(v);
        auto *slot = b->CreateAlloca(b->getInt32Ty(), nullptr, v);
        b->CreateStore(b->getInt32(0), slot);
        locals[s] = slot;
    }

    stmt(f->body.get());
    b->CreateRet(expr(f->ret->e.get()));
}

Value *IRGen::expr(const Expr *e) {
    if (const auto *x = dynamic_cast<const IntLit *>(e))
        return ConstantInt::get(b->getInt32Ty(), x->v, true);

    if (const auto *x = dynamic_cast<const VarRef *>(e)) {
        const Symbol *s = bindings->uses.at(x);
        return b->CreateLoad(b->getInt32Ty(), locals.at(s), x->name);
    }

    if (dynamic_cast<const InputE *>(e))
        return b->CreateCall(rtInput_);

    if (const auto *x = dynamic_cast<const Binop *>(e)) {
        Value *l = expr(x->l.get());
        Value *r = expr(x->r.get());
        switch (x->op) {
            case BOp::Add: return b->CreateAdd(l, r);
            case BOp::Sub: return b->CreateSub(l, r);
            case BOp::Mul: return b->CreateMul(l, r);
            case BOp::Div: return b->CreateSDiv(l, r);
            case BOp::Gt: {
                Value *p = b->CreateICmpSGT(l, r);
                return b->CreateZExt(p, b->getInt32Ty());
            }
            case BOp::Eq: {
                Value *p = b->CreateICmpEQ(l, r);
                return b->CreateZExt(p, b->getInt32Ty());
            }
        }
    }

    if (const auto *x = dynamic_cast<const CallE *>(e)) {
        const auto *nameUse = dynamic_cast<const VarRef *>(x->callee.get());
        if (!nameUse)
            throw std::runtime_error("ch08: 间接调用留待第 27 章");
        const Symbol *s = bindings->uses.at(nameUse);
        if (s->kind != Symbol::Fun)
            throw std::runtime_error("ch08: 间接调用留待第 27 章");
        auto *callee = mod->getFunction(emitName(s->name));
        std::vector<Value *> args;
        for (const auto &a : x->args) args.push_back(expr(a.get()));
        return b->CreateCall(callee, args);
    }

    throw std::runtime_error("ch08: 指针与记录构造留待第 27 章");
}

void IRGen::stmt(const Stmt *s) {
    if (const auto *x = dynamic_cast<const AssignS *>(s)) {
        const auto *target = dynamic_cast<const VarRef *>(x->target.get());
        if (!target)
            throw std::runtime_error("ch08: 经指针/字段写入留待第 27 章");
        const Symbol *sym = bindings->uses.at(target);
        b->CreateStore(expr(x->value.get()), locals.at(sym));
        return;
    }

    if (const auto *x = dynamic_cast<const OutputS *>(s)) {
        b->CreateCall(rtOutput_, {expr(x->e.get())});
        return;
    }

    if (const auto *x = dynamic_cast<const IfS *>(s)) {
        Function *fn = b->GetInsertBlock()->getParent();
        auto *thenBB = BasicBlock::Create(*ctx, "then", fn);
        auto *elseBB = BasicBlock::Create(*ctx, "else", fn);
        auto *mergeBB = BasicBlock::Create(*ctx, "merge", fn);

        Value *cc = b->CreateICmpNE(expr(x->cond.get()), b->getInt32(0));
        b->CreateCondBr(cc, thenBB, elseBB);

        b->SetInsertPoint(thenBB);
        stmt(x->then.get());
        if (!b->GetInsertBlock()->getTerminator()) b->CreateBr(mergeBB);

        b->SetInsertPoint(elseBB);
        if (x->els) {
            stmt(x->els.get());
            if (!b->GetInsertBlock()->getTerminator()) b->CreateBr(mergeBB);
        } else {
            b->CreateBr(mergeBB);
        }
        b->SetInsertPoint(mergeBB);
        return;
    }

    if (const auto *x = dynamic_cast<const WhileS *>(s)) {
        Function *fn = b->GetInsertBlock()->getParent();
        auto *header = BasicBlock::Create(*ctx, "wh.cond", fn);
        auto *bodyBB = BasicBlock::Create(*ctx, "wh.body", fn);
        auto *exitBB = BasicBlock::Create(*ctx, "wh.exit", fn);

        b->CreateBr(header);
        b->SetInsertPoint(header);
        Value *cc = b->CreateICmpNE(expr(x->cond.get()), b->getInt32(0));
        b->CreateCondBr(cc, bodyBB, exitBB);

        b->SetInsertPoint(bodyBB);
        stmt(x->body.get());
        if (!b->GetInsertBlock()->getTerminator()) b->CreateBr(header);

        b->SetInsertPoint(exitBB);
        return;
    }

    if (const auto *x = dynamic_cast<const BlockS *>(s)) {
        for (const auto &st : x->ss) stmt(st.get());
        return;
    }

    if (const auto *x = dynamic_cast<const ReturnS *>(s))
        b->CreateRet(expr(x->e.get()));
}

void IRGen::genWrapper(const FunDecl *mainFun) {
    // C 入口：按 TIP main 形参数目读 input，再调用 tip_main。
    // 不命名为 main——MinGW 目标会向 main 注入对 CRT 符号 __main 的调用。
    auto *fn = Function::Create(FunctionType::get(b->getInt32Ty(), false),
                                Function::ExternalLinkage, "tip_entry", *mod);
    auto *entry = BasicBlock::Create(*ctx, "entry", fn);
    b->SetInsertPoint(entry);

    std::vector<Value *> args;
    for (size_t j = 0; j < mainFun->params.size(); ++j)
        args.push_back(b->CreateCall(rtInput_));
    Value *r = b->CreateCall(mod->getFunction("tip_main"), args);
    b->CreateRet(r);
}

bool IRGen::verify() const {
    std::string err;
    llvm::raw_string_ostream os(err);
    bool bad = llvm::verifyModule(*mod, &os);
    os.str();
    return !bad;
}

std::string IRGen::dump() const {
    std::string out;
    llvm::raw_string_ostream os(out);
    mod->print(os, nullptr);
    return os.str();
}

#include "llvm/ExecutionEngine/JITSymbol.h"
#include "llvm/ExecutionEngine/Orc/Core.h"
#include "llvm/ExecutionEngine/Orc/LLJIT.h"
#include "llvm/ExecutionEngine/Orc/ThreadSafeModule.h"
#include "llvm/Support/TargetSelect.h"

using llvm::StringRef;
using llvm::JITSymbolFlags;
using llvm::orc::ExecutorSymbolDef;
using llvm::JITTargetAddress;
using llvm::jitTargetAddressToFunction;
using llvm::pointerToJITTargetAddress;
using llvm::orc::LLJITBuilder;
using llvm::orc::SymbolMap;
using llvm::orc::ThreadSafeModule;
using llvm::orc::absoluteSymbols;

namespace tip {
namespace {

// JIT 模块通过这两个宿主函数与外界交换数据。
const std::vector<int> *inQueue = nullptr;
std::vector<int> *outQueue = nullptr;
size_t inPos = 0;

extern "C" int32_t tip_input() {
    if (inPos >= inQueue->size()) return 0;
    return (*inQueue)[inPos++];
}

extern "C" void tip_output(int32_t value) {
    outQueue->push_back(value);
}

void initNative() {
    // 进程内只初始化一次。
    static const bool ready = [] {
        llvm::InitializeNativeTarget();
        llvm::InitializeNativeTargetAsmPrinter();
        return true;
    }();
    (void)ready;
}

[[noreturn]] void fail(llvm::Error e) {
    std::string text = llvm::toString(std::move(e));
    throw std::runtime_error(text);
}

}  // namespace

std::vector<int> runJit(IRGen gen, const std::vector<int> &inputs) {
    initNative();
    std::vector<int> outputs;
    inQueue = &inputs;
    outQueue = &outputs;
    inPos = 0;

    auto jitOrErr = LLJITBuilder().create();
    if (!jitOrErr) fail(jitOrErr.takeError());
    auto jit = std::move(*jitOrErr);

    auto defineHost = [&](StringRef name, void *addr) {
        SymbolMap symbols;
        symbols[jit->mangleAndIntern(name)] = ExecutorSymbolDef(
            llvm::orc::ExecutorAddr::fromPtr(addr), JITSymbolFlags());
        if (llvm::Error e =
                jit->getMainJITDylib().define(absoluteSymbols(symbols)))
            fail(std::move(e));
    };
    defineHost("tip_input", reinterpret_cast<void *>(&tip_input));
    defineHost("tip_output", reinterpret_cast<void *>(&tip_output));

    ThreadSafeModule tsm(std::move(gen.mod), std::move(gen.ctx));
    if (llvm::Error e = jit->addIRModule(std::move(tsm)))
        fail(std::move(e));

    auto mainAddr = jit->lookup("tip_entry");
    if (!mainAddr) fail(mainAddr.takeError());
    auto *entry = jitTargetAddressToFunction<int (*)()>(mainAddr->getValue());
    entry();

    return outputs;
}

}  // namespace tip

## 13.14 工程注意点

原理之外，五条实现层面的注意点。它们都是上述原理在工程
中的直接推论，而非与原理并列的经验清单。

1. **抽象元素的编码与语义必须隔离。** int 编码便利存储，
   但序与 join 只能经 SignLattice 的 leq/join 访问；直接
   比较编码整数会得到"恰好是链"的假序（13.5.1）。任何
   新增抽象域都应复制这一纪律：编码私有化或文档警告 +
   单一入口，二选一。

2. **抽象算术用表而不用分支。** 表是完整的正确性主张，
   可评审、可穷举测试（13.5.3）；等价的 if/else 链无法
   一眼验证完备性。新域的运算优先写成 constexpr 表，
   写不成的（如除法的三情形）把表外逻辑压缩到最少。

3. **缺键即 ⊥ 的约定必须全链一致。** evalExprSign 读缺键
   得 ⊥、joinEnv 以缺键为 ⊥ 参与合并、printPointEnv 把
   缺键印成 ⊥——三处若有一处把缺键当 0 或当 −，可靠性
   与确定性同时崩塌。约定写进类型别名旁的注释，消费方
   全部经由统一入口（env.find + 缺省）。特别警惕的一个
   反模式是 `env[x]` 直接下标访问：std::map 的 operator[]
   对缺键**插入默认值 0**——0 在符号域里是"确定为零"，
   与"无信息"差了整整两个格级；一行图省事的下标访问
   能把"不确定"伪装成"确定的零"，下游的除法检查会因此
   给出"绝不除零"的错误担保。全章代码坚持 find + 缺省
   正是封死这扇门。

4. **分析边界的每一处降级都要显式注释。** 调用返回 ⊤、
   指针目标不更新、条件不精化——三处降级各有注释指向
   修复章节。降级若无注释，三个月后会被当成 bug"修复"，
   而没有别名信息支撑的"修复"正是可靠性事故的来源。

5. **输出格式服务于逐字节回归。** printPointEnv 固定
   "参数在前、局部在后"的变量序、分支点只印条件不印
   整个语句体——每个决定都为了让同一程序的同一次分析
   产出逐字节相同的文本。本章的 expected/output.txt
   因此成为第 16 章（同程序的不动点结果）的天然对照组。
   值得复述的设计动机：变量序若跟随 std::map 的字典序，
   输出会随变量命名漂移（加一个 z 变量不影响 x 的位置，
   但改名为 a 就挪动全部行）；固定为"声明序"让输出
   只随语义变化，回归对账的噪音降到零。分析器的输出
   是给别人看的，但首先是给 diff 看的。

## 13.15 小结

本章建立了数据流分析的第一块完整实物：

- **域**：五个符号 {⊥, −, 0, +, ⊤}，经具体化函数 γ 与
  整数世界相接；偏序表"信息多少"，join 表"合并"，二者
  逐格可验，五元格是格论公理的最小标本；
- **抽象算术**：加、减、乘、除、比较五张表，每格都是
  "具体结果落在 γ(表项) 内"的可靠性主张，除法的除零
  语义与比较的精度损失展示了"域的形状由语义与问题
  共同决定"；
- **传递**：环境（缺键即 ⊥）、表达式抽象求值（与具体
  求值同构）、语句传递（只有标量赋值改变状态）三层，
  边界条件 entryEnv 定起点，一切不确定朝 ⊤ 退化；
- **驱动**：单趟沿 CFG 依编号顺序逐点传递，可靠但不精
  确——回边缺席使循环携带信息尽失，sign1.tip 的
  output 点交了 ⊥ 白卷；
- **论证**：局部可靠性定理逐语句成立，join 的覆盖性
  由"γ 对 join 是并"担保；丢精度与丢可靠性被严格
  分开。

三个贯穿全书的主题在本章首次露面，值得点名：**语义
先行**（除法表的第一步是锁定"除零中止"的语义）；**构造
优于小心**（Galois 连接让可靠性由域的形状而非程序员的
警觉保证）；**证明与代码同构**（表项措辞 = 归纳步需求，
joinEnv 三情形 = 覆盖性证明三情形）。往后每一章的
新域、新传递函数、新求解器，都是这三条主题的再演绎——
读到后面觉得"这一章怎么又是这三句话"时，恰好说明
你已经在用本书的方式思考了。

单趟的答卷值得最后定格一眼：可靠（在声明边界内）、
不精确（循环全盲）、诚实（白卷写在 ⊥ 里）。它是一个
故意保留的半成品——它的每一处缺陷都是下一章的引言。
第 14 章先把"环境"这个手搓结构泛型化为格构造子，让
任意域都能组装出任意变量集上的状态格；第 15 章把
"单趟每次一步"改写成显式方程组，让"循环要重算"从
直觉变成方程；第 16 章的 worklist 解方程到不动点，
sign1 的 output 将交出迟到两章的正确答案 x=+。
