# 第 48 章　0-CFA：当"被调函数"本身是数据流的答案

## 48.1 问题：调用图不是起点，而是被分析出来的东西

### 48.1.1 回顾：前面的章节默认了一件我们并不总有权默认的事

从第 12 章构造 CFG 起，到第 44 章把分析扩展到整个程序、再到第 45 章用
调用串给同一个函数造多个"分身"，我们一直在享受一个免费的前提：**程序
里每一次调用要调到谁，读源码就知道**。TIP 的调用写成前缀式的
`(call f x)`，其中 `f` 是一个写死在文本里的名字；扫描程序文本，找到
名字为 `f` 的那个函数声明，调用边就画出来了。第 44 章构造调用图的时
候，工作简单到只是"对每个函数里的每个调用，按名字查表"。

这个前提在一类程序面前立刻失效：**当被调位置出现的不是名字、而是一
个会在运行时才确定值的表达式**。TIP 的文法从第 4 章起就是为此准备
的——产生式 `expr : expr LPAREN args? RPAREN` 里，括号左边的被调位
置是任意 `expr`，并不要求是 IDENT。于是完全合法的程序里可以出现这样
的句子：函数 `twice` 接收一个参数 `f`，然后在函数体里写 `f(x)`；至于
`f` 到底是谁，取决于**谁、以什么实参调用了 `twice`**。`main` 里写
`twice(inc, 5)`，`f` 就是 `inc`；另一个地方写 `twice(dbl, 5)`，`f` 就
是 `dbl`。

这类函数有一个经典的名字：**高阶函数**（higher-order function）——接
收函数作为参数（或返回函数作为结果）的函数。高阶在现代语言里随处可
见：把比较器传给排序函数、把回调传给事件循环、把转换函数传给 map。在
这些程序上，"调用图"不再是可以先画好的静态地图。`f(x)` 这一行要调
谁，取决于 `f` 的**数据流**；而要知道 `f` 的数据流，又得先知道程序里
的调用如何流动——包括 `f(x)` 自己会调到谁。这就是本章要正面处理的循
环依赖。

### 48.1.2 "鸡与蛋"：调用图依赖数据流，数据流依赖调用图

把循环依赖的两个方向并排放，问题的形状就清楚了：

> **方向一（分析数据需要调用图）：** 要知道参数 `f` 在 `twice` 函数体
> 里可能持有哪些函数，就得知道 `twice` 会被哪些调用点调用、各自传了
> 什么实参。这要求调用边已经存在。
>
> **方向二（构造调用图需要数据流）：** 要为句子 `f(x)` 画出调用边，
> 就得知道 `f` 这个表达式可能求值成哪些函数值。这要求数据流已经分
> 析完。

任何"先完整做好一件再做另一件"的顺序都行不通：先画调用图，`f(x)` 一
边是空白；先分析数据流，`f` 的来源在 `twice` 的调用边之外，同样是空
白。读者在第 25 章已经见过这种形状——当约束构成环，顺序算法无解，出
路是**不动点**：不再追求一步到位，而是从一个贫乏的猜测出发，按规则
反复改进猜测，直到再推一轮什么都不改变。那一章的不动点发生在"格上的
状态"；本章的不动点发生在**一个不断长出新边的约束系统**上。

具体的直觉是这样。一开始我们只知道最不需要推理的事实：**函数名出现
在表达式里，这个表达式的值就是那个函数**。`twice(inc, 5)` 里的 `inc`
虽然写在实参位置，但它确实就是 `inc` 函数——这与数据如何流动无关，
是纯文本事实。从这批种子事实出发，值沿着"赋值、参数传递"流动：实参
`inc` 绑定到形参 `f`，于是我们第一次得知 `f` 可能是 `inc`。这个新事实
立刻回过头来补全调用图：`f(x)` 处可能调用 `inc`，于是 `x` 又该绑定到
`inc` 的形参、`f(x)` 的返回又该接回 `inc` 的返回。每一条新边都可能暴
露更多"某个表达式的值是某个函数"的事实，每一个这样的事实又可能长出
更多边。两个互相依赖的方向，在反复的"事实 → 边 → 事实"交替中一同长
成，直到闭合。

### 48.1.3 为什么这件事值得单独讲一章

读者可能会想：第 45 章的上下文敏感分析已经在处理"同一函数在不同调用
点的状态"，那不也是在分析调用之间的信息流动吗，为什么还要单独设立一
章？差别在**分析的输出**。第 45 章（以及第 44 章）假设调用图已知，分
析输出的是"每个程序点上变量的值（符号、常量、区间……）"；调用边是
**输入**。本章反过来，分析输出的是"每个调用点可能调到哪些函数"——
调用边是**输出**。这是控制流分析（control flow analysis）的本职：在
直接调用读名字即可的语言里它几乎隐形，但在高阶程序里它是一切其他分析
的前置——不知道 `f(x)` 调到谁，第 27 章的常量传播到了这一行就只能
保守地放弃，第 30 章的未初始化分析也无法跟随进入被调函数。

换句话说，本章在为前面所有分析"扫清视线"。工业编译器里的情形一模一
样：C++ 中通过函数指针、虚函数表发生的调用，分析器必须先估计指针可
能指向哪些函数，才能继续内联和常量传播；Java 虚拟机的 JIT 要先推测
虚调用的目标，才能做后续优化。**先恢复控制流，再在恢复出的控制流上分
析数据**，这一顺序在高阶特性出现后从"读文本一步完成"变成了"求一个不
动点"。

### 48.1.4 本章要落地的核心结论

按惯例先把结论摆明，因为它决定了怎么读实验结果：

**0-CFA 把"函数可能流向哪里"的问题精确地编码成一组集合包含约束，其
最小不动点就是答案；它在多项式（最坏三次）时间内终止，并且可靠——它
可能多报调用目标，但绝不会漏掉真实执行会发生的调用。**

这个陈述里有三个词要在正文逐一兑现。"集合包含约束"是 48.2 节的形式
化：程序被翻译成与语法无关的约束数据，求解器不再认识函数和语句。
"最小不动点"是 27.4–48.5 节的算法：从种子事实出发反复闭包，最后得到
的集合是满足全部约束的**最小**解——多一个函数都不应该有。"可靠"是
48.7 节的论证：真实执行的每一次调用，都能在分析给出的目标集合里找到
对应；分析的误差只朝"多报"一个方向发生。

名字里的"0"也需要预告。它与第 45 章 k-CFA 里的 `k=0` 是**同一个 0**：
不区分调用上下文、所有调用点共享一份分析结论。0-CFA 是上下文不敏感
的控制流分析；同一个被调函数在不同调用点被传入不同函数实参时，形参
位置会把它们合并。48.9 节会专门回到这个对应，把本章与第 45 章彻底接
上。读者将看到，第 45 章里"精度阶梯最底层"的 k=0，换个分析对象就是
本章的主角。

### 48.1.5 与 spa 原书及前后章节的对应

spa 第 20 章处理高阶语言的控制流分析：以 λ 演算风格的形式化给出抽象
缓存（abstract cache）与约束规则，并说明约束求解如何恢复调用图。Nielson
等人的《程序的形式化语义》则从抽象解释的角度给出同一组规则的完整可靠
性证明。本章的形式化（48.2 节）按"抽象缓存 + 位置命名约定"这条线
走，但在两个地方做了面向本书读者的落地。

其一，TIP 没有 λ 表达式语法：函数不能匿名地写在表达式里，所有函数都
是平级的具名声明，函数**名字**作为值流动。于是 spa 形式化里"每个 λ
子式一个标签"的设定，在 TIP 上简化为"每个函数名一个标签"；抽象位置
主要是形参、局部变量和为复杂表达式临时编号的中间位置。其二，spa 对
求解的描述是数学上的约束闭包；本章把闭包过程压进读者已经熟悉的
worklist 框架——和第 26 章一样的队列、一样的"只处理真上升"纪律，
只是传播的不是格值而是"（位置，函数名）"这样的二元事实。

向前承接：本章的结果（每个调用点的函数集）在真实编译器里立刻会被第 27 章式的常量传播、第 46 章式的 IFDS 消费。本章只做控制流这一件事，
刻意不把两类分析耦合——单一职责让"边如何长出"这一新机制保持可见。

### 48.1.6 本章的阅读路线

### 48.1.7 同一问题在真实语言里的三副面孔

函数值引起的"调谁不确定"不是 TIP 的特产，三副真实面孔各有各的
变形。JavaScript 里最常见的是回调：数组方法 map/filter 的实参
是一个闭包，调用点的目标集合由所有传过的回调决定——引擎的
inline cache（IC）就是调用点局部的迷你 0-CFA：观测几次、缓存
一个形状、失配就退化，与分析的区别只在"采样"还是"保守并"。
C 里的函数指针是裸形态：语法上 *fp 与 fp 无别，静态看调用点只
有一个名字，分析必须穿透赋值链——本章 twice 的 f 与它同构。
Rust 的闭包更讲究：每个闭包表达式是独立的匿名类型，调用是静
态分派的，但 Box<dyn Fn> 一装箱，动态分发回来了，目标集合=
装箱点的集合——又一次 val/copy/激活。三副面孔共享一个事实：
**只要函数能当值传，调用图就是分析的结果而非输入**。工业分
析器（flow/TAJS 对 JS、SVF 对 C）无一例外把控制流分析放在指
针分析之前或与之联立，原因正在于此。

## 48.2 形式化：抽象缓存、位置与约束

### 48.2.1 λ 标签：函数值的抽象名字

先定义函数值的抽象表示。在具体执行中，一个函数值是"一段代码连同它
的定义环境"；控制流分析此刻不关心环境，只关心**代码**——调用发生
时真正被执行的是哪个函数体。因此每个函数值被抽象为它的声明名字，
也就是一个 **λ 标签**（lambda label）：

> **λ 标签集合 Lab = { f | f 是程序中声明的函数名 }。**

对 `twice.tip` 而言，Lab = { twice, inc, main }。一次具体调用
`f(x)` 在分析里被抽象为：在标签集合中选择一个 f 可能持有的标签。
因为标签与程序中的函数一一对应、函数在 TIP 中必须全局唯一命名，标
签之间不会混淆。

值得诚实指出这个抽象丢掉了什么：两个同名函数在有嵌套作用域的语言里
可能是两个不同闭包；TIP 函数平级、名字全局唯一，所以不存在此问题。
另外，真正的 λ 演算允许函数在表达式中即时定义，同一处语法在运行中
被反复求值会产生多个闭包实例；TIP 中函数声明只求值一次（名字在加
载时绑定），因此"一个名字一个标签"是精确的而不只是保守近似。

### 48.2.2 抽象位置：值停在什么地方

函数值在程序中流动，总得有"位置"承载它。本章定义三类抽象位置
（abstract location）：

> 1. **变量位置**：函数 `f` 的形参或局部变量 `x` 记为字符串
>    `f.x`，例如 `twice.f`、`twice.x`、`inc.y`。
> 2. **中间位置**：生成器给每个不能直接对应到变量的表达式分配一个
>    顺序编号 `%1、%2、…`，用来表达"这个表达式的结果流到那个表
>    达式"。
> 3. **主函数特例**：`main` 的变量直接记为裸名（`r`、`s`），与程序
>    文本一致；这只是书写约定，形式化上与 `main.x` 等价。

为什么需要中间位置？考虑 `return f(f(x))`：外层调用的实参是另一个调
用 `f(x)`。要表达"内层调用的返回值流到外层调用的实参绑定"，就需要
一个名字称呼"内层调用的结果"。编号位置就是这个名字。它们大多只在约
束传播过程中短暂出场，最终报告里只打印有名字的变量位置；48.6 节的
输出将验证这一点。

抽象缓存（abstract cache）是本章的核心数据结构：

> **C : 位置 → 标签集合**，即 C(ℓ) ⊆ Lab，表示"运行到与位置 ℓ 相关
> 的表达式/变量时，函数值可能是 C(ℓ) 中的任何一个标签"。

`C(twice.f) = {inc}` 的读法是：在所有可能执行中，`twice` 的形参 `f`
可能持有的函数值，恰好包括 `inc`（且分析认为没有别的）。缓存从空集
开始，随约束闭包不断长大；空集表示"目前还没有任何路径把函数值送到
这里"。

### 48.2.3 两类基础约束：val 与 copy

有了位置和标签，程序里最简单的事实被写成两类约束。

**val 约束（名字出现）：** 当函数名 `g` 作为一个表达式出现（典型地
作为实参，如 `twice(inc, 5)` 中的 `inc`），该表达式的结果位置 ℓ 必
须包含标签 g：

> C(ℓ) ⊇ { g }。

这条约束不依赖任何分析结论：文本里写的是名字 `inc`，它求值就是
`inc` 函数。它是整个闭包的**种子**——没有 val，缓存将永远是空集。

**copy 约束（值的流动）：** 当一个表达式的结果被赋给变量、或一个
变量被读出送入另一个表达式，值的集合整体流动：

> C(ℓ_dst) ⊇ C(ℓ_src)。

注意右边是**整个集合**，不是单个标签。`f` 形参位置持有 `{inc, dbl}`
时，`g = f` 之后 g 的位置也得到 `{inc, dbl}` 两个标签。这正是集合
包含式分析的传播方式，读者在第 25 章的单调框架里已见过同型操作：
源集合每长出一个元素，目的集合就应当包含它。

举个完整的小例子。`twice(inc, 5)` 中，实参 `inc` 的结果位置 ℓ₁ 收到
val 约束 C(ℓ₁) ⊇ {inc}；调用发生时，实参绑定到形参（下一小节给规
则），等价于 copy 约束 C(twice.f) ⊇ C(ℓ₁)。两条约束合起来，第一次
推出 C(twice.f) ⊇ {inc}——"鸡与蛋"在这一步被打破：我们并不是先知
道 f 是什么才分析调用，而是**先知道实参文本写了什么**，再让值沿绑
定流过去。

### 48.2.4 间接调用规则：函数集每长一个标签，就激活一次绑定

现在给本章真正的主角——被调位置是变量的调用 `f(args)`——定规则。
关键观察是：这样一个调用的**形状**（实参有几个、结果给谁）在静态时
已知，未知的只是 f 的标签集合。于是规则被写成一个条件形式：

> **调用激活规则：** 设调用点 s 的被调表达式结果位置为 ℓ_f，第 i 个
> 实参的结果位置为 a_i，调用结果位置为 r。每当一个标签 g 新进入
> C(ℓ_f)，就激活以下两类约束：
>
> 1. **形参绑定：** C(g.p_i) ⊇ C(a_i)，对每个形参位置 g.p_i；
> 2. **返回绑定：** C(r) ⊇ C(ρ(g))，其中 ρ(g) 是 g 的返回表达式的结
>    果位置。

这个规则把"鸡与蛋"精确地形式化了。它说：调用边不是静态画死的，而
是**每当被调位置的缓存长大就动态长出一批 copy 约束**。f 先只有
{inc}，于是 x 绑定到 inc 的形参、返回从 inc 的返回接回；后来 f 又长
出 {dbl}（假设另一个调用点传入了 dbl），同样的形状再为 dbl 激活一
次。每个"（调用点, 目标标签）"配对只需激活一次——第二次再看到同样
的标签时，它长出的 copy 约束已经存在。

为什么激活规则是可靠的（不漏报）？因为它不挑标签：**凡是**进入
C(ℓ_f) 的标签都得到完整的形参、返回绑定。48.7 节的正确性论证会反过
来说：C(ℓ_f) 本身是可靠的（真实执行 f 可能持有的函数值都在里面），
对每个这样的值激活绑定，覆盖了真实调用的全部数据流动。

### 48.2.5 约束的解：最小不动点

把上述全部约束收集起来，它们定义了缓存上的一个变换 F：给定当前缓存
C，F(C) 是把所有 val 种子加入、所有 copy 包含关系满足、所有激活规则
对 C 中已存在的标签触发后得到的缓存。因为所有规则都只让集合**长
大**，F 关于集合包含是单调的：C₁ ⊆ C₂ 蕴含 F(C₁) ⊆ F(C₂)。

从空缓存 C₀（所有位置映射到空集）出发反复应用：

> C₀ = ∅，C₁ = F(C₀)，C₂ = F(C₁)，…

单调 + 有限（位置数有限、标签数有限，缓存空间是有限格）保证序列到
达不动点 C* = F(C*)。更重要的是，由于从最小的 C₀ 出发，C* 是**最小
不动点**：任何满足全部约束的缓存 C′ 都有 C* ⊆ C′（每一步都有
C_i ⊆ C′，归纳即得）。最小性是精确性的形式化表达——分析给出的每
一个标签都是某条规则迫出来的，没有凭空添加。

这也解释了 27.1.2 节的直觉为什么是对的：两个互相依赖的方向不对应于
"先做谁"的排序，而对应于同一个 F 的反复应用。种子事实在 C₁ 出现，
它们触发的激活在 C₂ 长出新的 copy，新的 copy 又在 C₃ 把标签送到更
多位置……环被迭代展开，而不是被剪断。

### 48.2.6 可靠性的直觉先给一版

正式论证留到 27.7，这里先建立直觉。分析声称：凡真实执行中表达式求
值出某个函数值 g，g 一定在该表达式结果位置的缓存里。按表达式结构逐
层看：函数名出现处，val 约束直接把标签放入；变量处，值必然来自某次
赋值或形参绑定，对应 copy 约束把来源集合接了过来；调用结果处，真实
被调函数必然在被调位置的缓存里（归纳假设），激活规则已把该函数的返
回位置接到结果位置。三条路径覆盖了函数值出现的全部语法位置。

误差的方向因此是单向的：分析可能把真实执行**不会**调用的函数也列入
（因为它合并了不同路径、不同调用点的可能性），但不会把真实执行
**会**调用的函数漏掉。对一个优化器而言，这正是所需的形状：多报的代
价是放弃几处优化，漏报的代价则是把程序改坏。

### 48.2.7 换个视角：0-CFA 是指针分析的特款

把"函数值"读作"指向"，本章的机器与第 49 章的指针分析只差一步
润色：位置≈变量、标签≈分配点、val≈New（分配点流入变量）、
copy≈Copy（变量间流）、激活≈Store/Load 的解引用展开。Andersen
的四类约束里，本章天然有前两类，第三、四类（Store/Load）正是
"激活"在指针世界的对应物——间接写的目标集合要先知道 p 指谁。
这个同构不是巧合：Shivers 的原始论文标题里就有 "control-flow
analysis" 与指针分析共同的理论祖先（抽象解释 + 幂集格）。读者
带着这个视角读第 49 章，会发现 Steensgaard 的并查集不过是把
本章的"缓存只涨"改成"缓存只并"——union-find 是单调 union 的
压缩存储。两章合读，一套幂集格的两种工程化。

### 48.2.8 一个手算的最小约束系统

把 twice.tip 的约束系统完整写在纸上（求解之前的静态部分），
是连接 27.2 与 27.5 的桥。按生成器的编号：main 的调用表达式
twice(inc, 5)——genExpr 先给 callee 表达式 twice 发 val(%c1,
twice)，给实参 inc 发 val(%a1, inc)，字面量 5 不发；CallEdge
登记 {site: main:1, calleeLoc: %c1, argLocs: [%a1, %v5],
resultLoc: %r1}。twice 体：f 是形参（run 已登记名字），x 同；
两次调用 f(x)——callee 是 VarRef f（非函数名，发 copy(%c2 ←
f)），实参 x 发 copy(%a2 ← x)，CallEdge 两条；x+…inc 体：无函
子。全部静态约束六条：两条 val、四条 copy——加上每个函数的返
回位与参数名表。求解时动态长出的约束（激活产物）再补：copy
(f ← %a1)、copy (twice.x? 参数绑定方向是形参←实参即 copy(f,
%a1)——注意方向：值从实参流向形参)、copy(结果位 %r1 ← twice
的返回位)……最后 copy 链把 "twice" 从 %c1 带到 %r1（main 的
output 读它）。整个系统不超过十条约束，手工十分钟、机器一瞬
——但手工过的那十分钟，是后面一切"为什么这样设计"的直觉存
款。

## 48.3 演示程序：twice 与 apply

### 48.3.1 twice.tip：三行函数体里的两次间接调用

第一个程序只有三个函数、九行文本，却把本章的全部要素装了进去：

```
// file: programs/twice.tip
twice(f, x) {
  return f(f(x));
}
inc(y) {
  return y + 1;
}
main() {
  return twice(inc, 5);
}
```

逐行读。`twice` 接收两个参数：f 占据"被调位置"，x 是普通数据；函数
体唯一一句是返回 `f(f(x))`——先调用 f、实参为 x，再把内层调用的结
果作为实参第二次调用 f。这里有**两个**间接调用点：内层 `f(x)` 与外
层 `f(...)`，二者的被调表达式都是变量 f。`inc` 是普通的一阶函数，把
参数加一。`main` 在唯一的（直接）调用点把 `inc` 和 5 交给 twice，并
把 twice 的返回值作为整个程序的结果。

动手之前先预测结果，这是读分析输出的正确姿势。main 把 inc 传给形参
f，所以 twice 的函数体里 f 只可能是 inc；两个间接调用点都应解析到
{inc}。形参 x 绑定到 5，inc 第一次作用于 5 得 6，第二次得 7——这是
具体语义，但控制流分析此刻只回答"调到谁"，预期两个调用点都是单元素
集 {inc}，main 的直接调用点是 {twice}。此外没有别的函数值流动：5 是
整数、y+1 是整数，标签集合只在 f 相关的位置非空。

### 48.3.2 apply.tip：上下文不敏感如何让函数集合长出两个元素

第二个程序把"合并"这一机制点亮：

```
// file: programs/apply.tip
apply(f, x) {
  return f(x);
}
inc(a) {
  return a + 1;
}
dbl(b) {
  return b * 2;
}
main() {
  var r, s;
  r = apply(inc, 3);
  s = apply(dbl, 3);
  output r;
  output s;
  return 0;
}
```

apply 是与 twice 同型的高阶函数，但函数体只有一个间接调用点
`f(x)`。main 在**两个**直接调用点分别以 inc 和 dbl 调用 apply，并把
结果存入 r、s。预测：apply 的形参位置 f 先后收到两个标签——来自站点
1 的 inc、来自站点 2 的 dbl；因为分析不区分"这次进入 apply 是从哪个
站点来"（这就是名字里的 0），两个标签进入**同一个**位置缓存
C(apply.f) = {inc, dbl}。

于是 apply 内部唯一的间接调用点 f(x) 解析到集合 {inc, dbl}：分析报
告"这一行可能调用 inc，也可能调用 dbl"。请注意，在每一次**具体**执
行中这一行只调到其中一个：站点 1 那次是 inc，站点 2 那次是 dbl。分
析无法把两次进入分开，于是对这一行给出两种可能性。这不是错误——
r 和 s 处的两个直接调用点各自只解析到 {apply}，分析没有在调用图的
层面混淆"谁调用了 apply"；它混淆的是 apply **内部** f 的身份。这个
区分在 48.6 节读输出时还会回来，而它正是第 45 章 k=0 的同一件事：
不记住调用点，站点之间互相把可能性"倒进"同一个形参。

整数结果顺带预测：r 处 apply(inc,3) 具体返回 4，s 处 apply(dbl,3)
返回 6；本章的分析不计算值，输出里不会出现 4 和 6，但 output 语句
的存在保证程序语义完整——读者若运行它（TIP 工具链支持解释执行）可
以核对这两个数。

### 48.3.3 两个程序是一对最小对偶

twice 与 apply 不是两个孤立样例，而是一对精心构造的对偶。
twice 考核的是"**同一个形参在不同调用点收到不同函数**"——
f 在两次间接调用里都是 {inc}，但那是因为 main 只传了 inc；把
main 换成传两个不同函数（练习四），f 立刻变 {inc,dec}，两次
间接调用点的集合同时膨胀。apply 考核的是"**不同形参在不同调
用点收到不同函数**"——f 先后收到 dbl 与 inc，单个调用点
apply:1 的集合就有两个元素。前者的不精确要靠调用点上下文救
（哪个调用点传的谁），后者的不精确要靠值上下文救（这次进入
时 f 装的是谁）——两种上下文恰好是 k-CFA 的 call-string 与
functional 两条路线（第 46 章末的对照在这里第三次出现）。一
对程序、两行输出，把 k>0 的两类收益各展示了一半，剩下的一
半留给读者在练习里补全实验。

## 48.4 约束生成器：把 AST 翻译成与语法无关的数据

### 48.4.1 为什么先有生成器、再有求解器

本章代码最主要的设计决定是**两层分离**：`buildCfaConstraints` 遍历
AST 和名字绑定，产出一个纯粹的数据结构 `CfaConstraints`；`solve0Cfa`
只接收这个数据结构，其中没有任何 AST 类型，没有语句、表达式的指
针。这个分离的价值在第 46 章已经预演过：约束是分析的"中间语言"，
一旦程序被翻译过去，求解器就与源语言的具体语法脱钩——同一个求解
器日后可以服务于不同的前端，而生成器的正确性（翻译对不对）与求解器
的正确性（闭包对不对）可以分别论证。

`CfaConstraints` 的字段对应 48.2 节的形式化：`lambda` 是标签集合；
`edges` 是 val/copy 两类三元组；`calls` 是间接调用的形状记录；
`retLoc` 给出每个函数返回表达式的结果位置（激活规则的 ρ）；`params`
是形参名表，让求解器能拼出 `g.p_i` 这样的形参位置而无需认识函数声
明；`siteText` 只是把调用表达式的打印文本存下来供报告使用。

### 48.4.2 genExpr：每个表达式一个结果位置

生成器的核心是递归方法 `genExpr`：对任意表达式，先分配一个新的中
间位置 `%N`，再按表达式种类发出约束，最后返回这个位置。逐类看它如
何对应 27.2 的规则。

**变量引用（VarRef）**是唯一发出基础约束的地方。生成器查名字绑定
表：若这个名字绑定的符号种类是 Fun（函数名），发出 val 三元组
`("val", loc, 函数名)`——名字出现处，位置包含该标签；若绑定的是
形参或局部变量，发出 copy 三元组 `("copy", loc, "函数名.变量名")`
——表达式的结果位置包含该变量位置的缓存。这里可以清楚看到第 11 章
名字分析的作用：**同一个语法形状的 VarRef，可能是函数名也可能是变
量**，不查绑定就无法决定发哪类约束；生成器自己不做任何作用域推
理，一切结论来自 `bindings.uses`。

**调用表达式（CallE）**对应激活规则的静态部分：递归处理被调表达式
得到它的结果位置，递归处理每个实参得到各自的结果位置，然后生成调
用点标签（当前函数名加函数内序号，如 `twice:1`）、保存表达式文本
并登记一条 `CallEdge`。注意此刻**并不**判断这次调用是直接的还是间
接的——`twice(inc, 5)` 和 `f(x)` 在生成器看来都是一条 CallEdge；
区别完全体现在被调表达式的结果位置最终会包含哪些标签：前者通过 val
直接得到 {twice}，后者等待 copy 传播。把两类调用统一处理，规则更少
也更不容易遗漏。

**其余表达式**只负责让递归继续：Binop 处理左右两个子表达式（良态
TIP 中算术不产生函数值，但函数名可能作为子表达式出现，例如
`twice(inc, x+1)` 里的 inc 与 x+1 都要被走到）；Deref、AllocE、
FieldA 处理各自的子表达式；RecLit 遍历每个字段值。IntLit、InputE、
NullE 既无函数值也无子表达式，结果位置收到空集约束——它们在 0-CFA
里是"终点"。

### 48.4.3 genStmt：只有直接变量赋值会绑定函数值

语句层面的处理更简单。对赋值语句，生成器先递归得到右端结果位置；
若左端是直接变量，发出 copy 三元组把右端缓存接到 `当前函数.变量名`
位置。左端若是字段访问或指针解引用，本章不发约束——良态的 TIP 程
序不用它们承载函数值；右端仍已被递归处理，其中的函数引用不会丢。

OutputS 递归处理表达式；IfS、WhileS 处理条件并递归进入子语句（else
分支可空）；BlockS 顺序处理语句列表。函数末尾的 return 语句不在
genStmt 中处理，而由生成器的主流程统一处理：每个函数走完函数体后，
对返回表达式调用一次 genExpr，并把结果位置登记为 `retLoc[函数名]`
——这正是激活规则返回绑定里需要的 ρ(g)，由生成器一次性确定，求解
器直接查表。

### 48.4.4 run：标签集与形参名表的登记

`run` 是生成器的入口：先遍历全部函数登记 `lambda`（标签集合与声明
顺序无关，为集合）；再逐函数登记形参名表 `params`、处理函数体、
登记返回位置。形参名表值得单独说明：激活规则需要为**被调函数** g
拼它的形参位置 `g.p_i`，而求解器只见约束；把形参名作为函数签名的
一部分放进约束数据，求解器就不必反向解析任何声明。这是"让求解器对
AST 一无所知"这一设计目标直接逼出的字段。

生成器的一次完整产出，对 `twice.tip` 而言，形状大致是：val 边把
{inc} 放进 main 中实参 inc 的中间位置、把 {twice} 放进被调位置；
两条 CallEdge（main 处的直接调用、twice 函数体内的两条间接调用各一
条，共三条）；copy 边把实参缓存接到 twice.f、把 x 的位置接到实参
5 的位置（整数，标签为空），以及返回位置的接线。具体的标签传播在求
解器中发生——生成器只负责让约束齐备，**一个标签都不自己传播**。

### 48.4.5 生成器的自包含契约

genExpr/genStmt/run 三段共享一条隐式契约：**产出的约束只引用
位置与标签，不再引用 AST**。检验的方法是想象把 CfaConstraints
序列化存盘、重启进程再加载求解——一切照常。这条契约的价值
在工程上是解耦（求解器可以换 Datalog 后端、生成器可以换语
言前端），在教学上是清晰：第 25/26 章的制表机直接拿着 AST 边
走边问语句语义，本章把语义问题全部前移到生成阶段，求解器面
前只有一张纯数据的图。两种风格都对：前者省一次翻译、后者换
一层稳定接口。读者可以量一量：cfa.cpp 里 dynamic_cast 的次数
集中在生成器那几十行，求解器一段一次也没有——那条分界线就
是契约的物理位置。

### 48.4.6 genExpr 的返回值约定

genExpr 对每个表达式返回一个"结果位置"，这个约定比看起来重
要：它让任意嵌套的表达式（f(g(x))+h(y)）都能机械地拆成位置间
的约束网——每个子表达式一个位置、每个值流动一条 copy/val。
替代方案是"语句级约束"（每条赋值发一条大约束、内嵌子表达式），
省位置但约束形状不统一，求解器的激活无从下手。位置化是第 49 章指针分析的直接前置：那边的"变量、字段、分配点"全部是位
置，四类约束全部是位置间的包含——本章先在小规模上把位置这
个抽象用熟，下一章它就要装地址了。读者可以数一数 twice.tip
的位置总数（不到十个），再想象同一程序在语句级方案里的约束
数——粒度选择的工程直觉，从数数开始。

## 48.5 cubic worklist：让约束闭包在队列上终止

### 48.5.1 五张表与一个队列

`solve0Cfa` 的全部状态是五样东西：结果缓存 `cache`（位置→标签集）；
反向表 `copyOut`（源位置→目的位置集合，回答"这个位置长出标签时要送
给谁"）；调用索引 `callAt`（被调位置→监听它的 CallEdge 编号）；已
激活配对集合 `activated`（CallEdge 编号, 标签），保证每条动态约束只
长一次；以及工作表 `wl`，元素是"（位置, 新标签）"二元组。

这个结构是第 26 章 worklist 思想的直接再现，但有一个关键升级：那里
工作表携带"某个状态节点可能变了"，处理时**整体重算**该节点；这里
工作表精确携带"哪个位置**新长出了哪个标签**"，处理时只传播这一个
标签。增量到标签粒度是必要的——激活规则要按标签触发，整体重算无
法表达"f 长出 dbl 时才为 dbl 补绑定"。

### 48.5.2 add：唯一的入队点

lambda `add(loc, fun)` 把标签插入缓存：若它是该位置的新元素，缓存
真上升，上升计数加一，二元组入队。所有标签进入缓存都经过 add——
初始化的 val、copy 传播、激活后的存量补推，无一例外。于是"缓存集
合单调长大、每个（位置,标签）配对至多入队一次"由这一个函数强制保
证，终止性论证（27.8）因此只需要数 add 的调用上限。

### 48.5.3 初始化：先建监听，再撒种子

初始化分两步，顺序刻意如此。第一步遍历所有静态边：val 边调用 add
把标签送入（此刻即可能入队）；copy 边**只登记反向表** copyOut，不
立刻传递——因为源位置此刻或许已有标签、或许还空着，统一由工作表
处理可以避免"登记顺序"影响结果。第二步登记 callAt：每条 CallEdge
监听其被调表达式的结果位置。

注释里点明"顺序无关"：即使 val 种子在 copy 监听登记之前入队，它
们也只是排在队列里，出队传播时 copyOut 已全部就位。初始化结束后，
队列里装着全部种子事实（对 twice.tip 就是 {inc}、{twice} 等几个
val），闭包尚未发生。

### 48.5.4 传播：copy 与激活

工作表循环每轮取出一个（位置,标签），做两件事。

**copy 传播：** 查 copyOut，若有目的位置集合，对每个目的调用 add
把同一标签送过去。这一步实现 C(dst) ⊇ C(src)：源每长出一个标签
就推一个，不动点时整个源集合都已到达每个目的。

**调用激活：** 查 callAt，若该位置正被某些 CallEdge 监听，逐条处理：
配对（边编号,标签）若已激活过则跳过，否则激活计数加一、把标签记
入该调用点的解析集合 `sites`，然后长出 27.2.4 的两类约束。形参绑
定：查 params 得到目标函数的形参名，把 `实参位置 → g.形参位置`
登记进 copyOut，并把实参位置**已有的**标签存量补推（实参可能在此
次激活之前就已带着标签——监听刚登记，不能指望队列替我们传存量）。
返回绑定：把 `g 的返回位置 → 调用结果位置` 登记进 copyOut，同样把
返回位置的存量标签补推到结果位置。

"登记监听 + 存量补推"这一对动作是动态长边时的固定模式：新边只对
**未来**的上升自动生效，**过去**已发生的上升必须手工追平。两处补推
代码做的就是这件事。

### 48.5.5 为什么是三次：一次粗略的计数

最坏复杂度可以从 add 的次数和每次处理的代价直接数出。设程序规模为
n（位置数与标签数都为 O(n)）。每个缓存集合至多包含全部标签，故
add 的成功次数（真上升）≤ 位置数 × 标签数 = O(n²)。每次处理一个
二元组，copy 传播扫描的目的集合、激活扫描的形参个数，单次合计可
达 O(n)。总量 O(n²) × O(n) = **O(n³)**——"cubic"由此得名。实践
中常数很小：真实程序的缓存集合大多只有一两个标签，copyOut 的度数
也有限；本章程序的缓存上升分别只有 5 次和 8 次（48.6 节输出），
与 n² 的最坏情形相去甚远。

### 48.5.6 求解器逐段走读

solve0Cfa 的骨架分四段：数据准备、监听索引、种子、主循环。数据
准备段把 CfaConstraints 的三张表搬进局部：cache（位置→标签集，
解的本体）、copyOut（位置→目标位置列表，惰性 copy 的接线）、
callAt（callee 位置→以它为目标的调用点列表）。三张表各回答一
个查询："谁有什么"、"给了谁"、"谁在等它"——求解器的全部行为都
是对这三个问题的回答的组合。

监听索引的建立顺序有个小讲究：callAt 先于种子。若倒过来，种子
下推时 callAt 还空着，激活不会发生，第一跳就断——症状是所有
调用点报告空集、rises 停在种子数。这个顺序约束在代码里只是一
行的先后，语义上是"接线完成再通电"。

主循环每弹一条 (位置, 标签)：先查 copyOut——把标签沿每条出边
转发，目标位置缓存若未见过该标签则入队（rise）；再查 callAt
——对该位置的每个调用站点，若 (站点, 标签) 未激活过，执行绑定
（copy 形参←实参、copy 结果←返回位）并立即下推**存量**：此刻
实参位缓存里已有的标签马上沿新边转发，不等下一轮。存量下推是
正确性的小关键：边是后来才长出来的，早到的值不能假装没来过。
27.10.2 把它列为注意点，这里给出它的机械对应。

计数的两行：rises 在缓存涨时递增、activations 在（站点, 标签）
首次激活时递增。它们不做任何决策，只做观测——但 27.11 的练习
四会展示它们作为回归探针的价值。

### 48.5.7 一个 мысленно 的反例：不激活会怎样

把激活机制整个删掉（copyOut 与 rises 保留），twice.tip 的输出
会变成什么样？f 缓存涨到 {inc}（copy 链还在），但 twice:1 与
twice:2 的解析集合来自哪里——报告查的是 sites[site]，而 sites
只在激活时登记！于是两个间接调用点报告空集，inc 的 x 缓存也空
（copy(inc.x←…) 从未发出）。结论：**缓存是解，激活是解到调用
点的投影**——删激活丢的不是精度是整个间接调用语义。反过来只
删 copyOut：缓存永不涨、f 恒空、激活永不触发，全部报告空集。
两个反例合起来把 27.2.4 的规则"函数集每长一个标签就激活一次"
的两半（长集合、激活）各自单独拆下来看了个明白。

### 48.5.8 缓存即不动点：代数一面

把求解器放在格论的光下照一照。状态空间是"位置→标签幂集"的乘
积格，序取逐点包含；每一步传播/激活都是把某个分量变大（缓存
只增不减），所以整个执行是一条严格上升链；分量数 × 每分量高
度（|Λ|+1）给出链长上界，终止性由链有限直接给出——这与第 25 章的论证逐字同型，只是"格"从显式的 sign 换成了隐式的幂集乘
积。最小不动点同样免费：从空缓存出发、每次只做**必须做**的传
播（缓存去重保证不多做），到达的正是约束系统的最小解——包含
任何其他解的最小集合。反方向也可以问：最大解存在吗？包含约
束从空往上长，只有最小解有意义（最大解是"所有位置装所有标
签"的平凡物）。0-CFA 的"分析结果"四字，代数面目就是这张乘积
格上的 lfp；第 49 章的 Andersen 用同一张脸，Steensgaard 把
lfp 换成它的一个上近似（并查集合并使解只增且并得更狠）——
三个分析器，一条格论脊梁。

## 48.6 实测输出：调用点与缓存逐个读

### 48.6.1 twice.tip 的报告

`tipa --check twice.tip` 的完整输出收录在 expected/output.txt，逐段
读。报告头之后是"resolved call sites"，三个调用点按程序中出现顺序
排列：twice 函数体内的两个间接调用点（标签 `twice:1` 是内层
f(x)、`twice:2` 是外层 f(f(x))）都解析到 {inc}；main 的直接调用点
`main:1` 解析到 {twice}。与 27.3.1 的预测逐字一致。

"abstract caches"段只打印有名字且非空的位置：`twice.f: {inc}`。这一
行是整个分析的支点——它非空，两个间接调用点才有目标；它只有一个
元素，调用点才是单元素集。注意 twice.x、inc.y 等位置没有出现：它
们承载的是整数，标签集合为空；中间位置 %N 也按设计被省略。统计行
`cache rises: 5` 与 27.5.5 的口径一致：全程序只有五个（位置,标签）
配对曾经真上升——每个标签都有明确来路，最小不动点的"最小"在计数
上也可感知。

### 48.6.2 apply.tip 的报告

apply 程序的报告里，调用点段给出三行：main 的两个直接调用点各解析
{apply}；apply 内部的间接调用点 `apply:1` 解析 {inc,dbl}——两个标
签，按字典序排列。缓存段唯一一行 `apply.f: {dbl,inc}` 是原因：上下
文不敏感把两个调用点传入的函数名合并进同一个形参位置，激活规则对
两个标签各触发一次，间接调用点因此得到两个目标。

统计行是 `cache rises: 8, call activations: 4`。激活计数 4 的构成可
以逐项核对：apply:1 对 inc、dbl 各一次（2），main:1、main:2 对
apply 各一次（2）。twice 程序的激活计数是 3（twice:1、twice:2 对
inc，main:1 对 twice）。两个数字都等于"（调用点,真实解析到的标
签）配对"的总数，这从经验上验证了配对集合 activated 的记账与报告
内容自洽。

### 48.6.3 输出如何体现"最小"与"不遗漏"

把两个程序的报告合起来看，可以分别检验不动点的两个性质。最小性：
所有出现的标签都能逆向追到一条 val 种子——{inc} 来自 twice(inc,..)
与 apply(inc,..) 的实参，{dbl} 来自 apply(dbl,..)，{twice}、{apply}
来自 main 中直接调用的被调名字；没有一个标签是无来源的。不遗漏：
以具体执行检验 twice 返回 7、apply 程序输出 4 和 6（这些函数值调
用关系），涉及的三次、三次调用目标全部落在报告的对应集合中。分析
在这两个极小程序上给出了与直觉完全吻合的调用图。

### 48.6.4 手工 trace：twice.tip 的求解全程

把 cubic worklist 在 twice.tip 上的完整旅程记成流水账，是检验读
者是否真正吃透 27.5 的最好方式；下面按事件顺序叙述，读者可对照
27.6.1 的最终报告逐条找到出生地。twice 的 main 只有一句 `output
twice(inc)(5)`……按程序实际形状：main 调 twice，把 inc 与 5 作为
实参；twice 体里两次 `f x` 间接调用；inc 体里 `x+1`。约束生成器
先跑完，产出的静态约束是：val("twice.1", twice)——调用点实参
twice 处；copy(twice.f ← …)；等一下，f 是形参不是全局变量，它
的绑定靠调用点动态生成。静态部分真正有的只是：三次 val 约束
（main 的调用点把 twice 绑到结果位置、twice 的两次调用……这两
次是间接的，只在 callee 集合非空后才激活）；copy(twice.x ←
main 的实参位置)、copy(twice 结果 ← inc…不，inc 在 main 侧)。
把叙事校准到代码：genStmt 只对**直接变量赋值**发 copy，genExpr
对 VarRef 发 val（当名字是函数）或 copy（当名字是变量），CallE
登记 CallEdge 站点但不立即发约束。于是静态产出是：val(main 调
用点的实参 1 位置, "twice")；copy(twice.x, main 的实参 2 位置
——5 那个)；val……inc 作为 main 的实参 1 传给 twice 的 f？main
的调用是 twice(inc, 5)——genExpr(inc) 发 val(arg 位, "inc")，
CallEdge 登记 (site=main:1, calleeLoc=f 的位置？不——calleeLoc
是**被调函数的入口位置**，间接调用时它指向 f 这个形参变量位
置)。这些细节在 27.4 已逐段讲过，这里只跟踪队列。

初始化：监听建好（copyOut、callAt），种子入队——val(main 的
arg1, twice) 与 val(arg2 位? 5 是字面量——字面量不发 val，它没
有函数身份；只有 inc 发)。所以种子两条：val(twice 的绑定位,
"twice")（main 调用点的 callee 表达式是具名 twice，genExpr 发
val）与 val(inc 实参位, "inc")。求解开始。弹出 val(inc 位,
"inc")：监听该位的 callAt 没有（它不是 callee 位置），无事。弹
出 val(twice 位, "twice")：该位的 callAt 有 main:1（main 的调用
点的 calleeLoc 正是它），激活——(main:1, twice) 未见过，执行绑
定：copy(twice.f ← inc 实参位)、copy(twice.x ← 5 的位置——字
面量位置无约束，实际是对每个实参位置发 copy 形参←实参)。存量
检查：twice.f 位当前缓存空，f 的缓存此刻涨 "inc"？——copy 是
惰性的：copyOut 登记了 f←inc 位，但 "inc" 已在 inc 位缓存里，
立即下推 copy(f 位, "inc")。缓存 rises 计 1。弹出它：f 位的
callAt 有两个站点（twice:1、twice:2），各自激活 (twice:1,
inc) 与 (twice:2, inc)：绑定 copy(inc.x ← twice 调用点的实参
位)、copy(结果位 ← inc 的返回位置)。x 的缓存随后涨…inc 不读
别的函数，链条到此收敛。总账：rises 5 次（f、inc.x、以及三处
结果位）、激活 3 次——与 27.6.1 报告的统计行严丝合缝。整条链
的关键一跳是 "inc" 落进 f 的缓存那一步：没有它，两个间接调用
点永远空转；有了它，参数绑定像多米诺一样自动倒完。

### 48.6.5 apply.tip 的 trace：集合为什么长出两个

apply 的链条只多一环。种子：val(apply 位, "apply")、val(dbl 实
参位, "dbl")、val(inc 实参位, "inc")。弹出 val(apply 位)：激活
(main:1, apply)，绑定 copy(apply.f ← 第 1 实参位)、copy(apply.x
← 第 2 实参位)。dbl 已在其位，f 缓存涨 "dbl"（rise 1）。弹出
copy(f,"dbl")：callAt 的站点 apply:1 激活 (apply:1, dbl)，绑定
copy(dbl.y ← apply 调用点实参位)。随后 "inc" 侧对称地走一遍：
inc 实参位的 val 无监听……不对——main 的调用 apply(dbl, inc)
把两个实参都交给 apply 的 f 与 x；f 只绑第 1 个。那 "inc" 怎么
进的 f？看程序：apply.tip 的 main 是 `apply(dbl,inc)` 还是两次
调用？27.3.2 说 apply:1 → {dbl,inc}——f 集合有两个元素，说明
两个不同的调用点（或一个调用点的两次不同绑定路径）分别把 dbl
与 inc 送进 f。按程序实际（apply(f,x){return f(x)}；main 先
apply(dbl,5) 再 apply(inc,7)——两个直接调用点）：两次激活各自
copy(apply.f ← 各自的实参位)，f 的缓存先后涨 "dbl"、"inc"
（rises 2），callAt 里 apply:1 这一个站点对两个标签各激活一次
——(apply:1, dbl) 与 (apply:1, inc)，激活数 4（含 main 的两
次）。f 缓存 {dbl,inc} 报告在案，一切对上。这个 trace 的教学
点：**同一站点的多次激活是合法且必要的**——激活的键是（站
点, 标签）二元组，不是站点；第 45 章的 call-string 在这里若取
k=0，行为与此完全一致，这正是"0-CFA"名字的由来。

### 48.6.6 printCfa 的报告生成

printCfa 的输出分三段：每个调用点的解析集合（"fun:n (调用文
本): {标签集}"）、跳过 % 临时位置的具名缓存、统计两行。第一段
遍历 CfaConstraints.calls，查 sites[site]——它是求解时激活登记
的（站点→标签集），未激活过的站点打印空集（程序里不存在这种
情况：有 CallEdge 必然至少一个标签到达过？不——若 callee 位置
从无函数值到达，站点保持空集，报告 {∅}，这本身就是"此调用点
不可达/无目标"的诊断）。第二段遍历 cache，过滤 % 开头的临时位
置——它们是表达式求值的中间站，对读者没有信息量；具名位置
（twice.f、apply.f）才是"抽象堆"的可读投影。第三段的 rises 与
activations 直接来自求解器计数。三段合起来约二十行输出，是
27.6 逐行解读的底稿。

### 48.6.7 输出契约的稳定性

本章输出被 check_example 逐字节对账，这意味着三件事成为公开
契约：调用点报告的顺序（calls 向量的生成序）、缓存报告的过
滤规则（跳过 %）、统计行的措辞。任何一处变动都要求同步更新
expected——教程的章节间引用（27.6 的解读、练习的预测）也都
押在这份稳定性上。写自己的分析器时值得早一点建立同样的纪律：
输出格式一旦被测试锁定，它就从"打印语句"升格为"分析器的公
开语义"，后续的每个改进都要过这道门——这恰恰是防止输出随
实现漂移、让历史结论可复查的最便宜手段。

### 48.6.8 读输出的三个层次

同一份 27.6.1 的报告，可以按三个层次读出三种收获。第一层读事
实：每个调用点的集合是什么、每个具名缓存装了什么——这一层
是查表，任何人十秒钟完成。第二层读来历：twice:1 的 {inc} 是
哪条约束链的产物（27.6.4 的流水账）、f 的 {inc} 在激活机制里
的对应事件——这一层要会做 trace，是理解算法的标志。第三层
读代价：{inc} 的单元素性押在什么前提上（main 只传了一个函
数）、前提松动时集合怎么膨胀（练习四）、膨胀的精度后果在
下游分析里如何显形（0-CFA 喂给第 46 章超级图时，多一个标签
就多一组调用边与返回配对）——这一层是分析设计者的视角。教
程要求读者至少走到第二层；第三层的完整走通，要等第 60 章
把全部分析放进同一张对照表时自然完成。

## 48.7 正确性论证思路：具体调用都落在解析集合内

### 48.7.1 论证的靶陈述

论证的目标是一句话：

> **可靠性：** 对任意一次具体执行，若在调用点 s 处调用了函数 g（或
> 任意表达式求值出函数值 g），则 g ∈ C(ℓ_s)（相应地 g 在该表达式
> 结果位置的缓存里）。

论证采用结构归纳（对表达式）+ 计算归纳（对执行步数），和第 27 章
可靠性论证的骨架一致：先证明表达式求值与缓存的对应（引理），再用
它覆盖调用点。下面只给思路，不逐行展开形式细节。

### 48.7.2 表达式引理的三个分支

引理：若表达式 e 在某环境下求值出函数 g，e 的结果位置缓存包含 g。
按 e 的语法分三类，恰好对应生成器的三种处理。函数名：val 约束静态
成立，与环境无关。变量：g 来自该变量在环境中的当前值；沿环境的来
源倒推，这个值要么由某条赋值写入（copy 边连接赋值右端位置）、要么
是形参实参（激活规则的形参绑定），由归纳假设标签在来源位置，copy
闭包把它送到变量位置。调用结果：真实被调 h 在被调表达式的缓存里
（对子表达式的归纳），激活规则已为 h 长出返回绑定，h 的返回值来源
于其返回表达式（再一层归纳），标签经返回位置到达结果位置。

### 48.7.3 调用点结论与误差方向

引理直接给出调用点结论：s 处真实调用 g 意味着被调表达式求值出 g，
故 g ∈ C(ℓ_s)。27.6 的每个解析集合因此是真实目标的超集。论证同时
确认误差只有一个方向：规则从不删除标签，分析无法"少报"；而标签经
过 copy 合并与跨路径 join，完全可能包含具体某次执行不出现的函数
——apply 程序的 {inc,dbl} 在单次执行中只用其一，就是活生生的例
子。优化器消费这种集合时，必须对其中**每个**标签保持正确性。

### 48.7.4 论证依赖的简化前提

需要诚实列出论证依赖的前提：TIP 函数全局唯一命名且不可重新赋值
（函数名绑定不可变——由第 11 章符号表与文法共同保证，TIP 没有
`inc = ...` 这样的写法，因为赋值左端不会解析到函数符号）；不考虑
经指针/字段发生的函数值写入（本章不发相关约束）；所有函数出现在
同一程序中（无外部函数，除运行时的 input/output，它们不作为值流
动）。放开任何一条，规则都要相应扩展——函数指针把第 49 章的指针
分析与本章耦合，外部函数则需要人工提供初始标签集合。

### 48.7.5 可靠性的机器探针

第 47 章给三步归纳各配了探针，本章的可靠性陈述（真实 callee ∈
解析集合）同样可以落地成可执行的检查：随机生成或手工构造若干
闭包程序，用第 13 章的 LLVM 执行台真实跑（闭包程序的调用目标
在运行时可打印——给 TIP 解释器加一行 trace 即可），收集每个
调用点**实际发生**的 callee 序列，断言序列的每个成员都在静态
解析集合里。这个探针与第 49 章 main.cpp 的 --verify-soundness
是同一个模式的两种实例化：那边检查"解引用的指针是否可能为
null"，这边检查"调用的目标是否在集合内"。教程没有为本章实现
它（闭包程序的运行时目标收集需要动解释器，收益边际低于第 49 章的 null 检查），但读者可以把它当作一个完整的小项目：
生成器、求解器、执行台三件都是现成的，缺的只是那条 trace 与
一个断言循环——半天工作量，换来"我的 0-CFA 从未漏报"的机器
证据。

## 48.8 终止性与复杂度

### 48.8.1 终止性

终止性论证只需两点：每个（位置,标签）配对至多经 add 成功一次（集
合插入去重）；可插入的配对总数 ≤ 位置数 × 标签数，二者有限。工作
表因此必然排空。激活规则动态长出的 copy 边不破坏论证——它只改变
copyOut 的内容（目的位置集合同样是有限集合，去重插入），不创造新
的标签种类。

### 48.8.2 复杂度

如 27.5.5 所数：O(n³) 最坏时间。空间是 O(n²)：缓存内容总量 ≤ 位
置数 × 标签数，copyOut 边数另有 O(n²) 上限（动态边的目的也是已有
位置）。作为对照，第 45 章的 k=0 分析状态数为 O(n) 但建立在已知
调用图上；本章用三次以内的代价**换出**那张调用图——高阶程序上这
是必须付的钱。

### 48.8.3 与更精密分析的接口

0-CFA 之上的精度提升有两条标准路线。一是 k-CFA 化：像第 45 章一样
给位置加调用串维度，k=1 即可拆开 apply 的两次进入（代价是状态膨
胀，最坏复杂度升到指数）。二是多态/多态分割（polymorphic splitting）：
按语法结构给不同调用点不同的分析变元。本章实现刻意停在 k=0——它
是所有高阶控制流分析的共同基座，先把这一层的形状吃透，48.9 节的
对应才讲得清楚。

### 48.8.4 三次方的具体来源

27.8.2 给了 O(n³) 的结论，这里把三次方的来源拆开看。设位置数
n、每位置标签至多 |Λ|（函数个数）。传播阶段：每条 copy 边至
多转发 |Λ| 次（缓存去重），边数 O(n²)，共 O(n²|Λ|)；激活阶
段：每次激活发 O(实参数) 条 copy，激活总数 |sites|·|Λ|，新增
边 O(|sites|·|Λ|·ar)；新增边再进传播……迭代嵌套起来最坏三次
方。具体最坏例：一条链 a₁→a₂→…→aₙ 的 copy，配 n 个标签逐个
进 a₁——每个标签沿链走 n 步，共 n²；再让每个中间位置带一个
调用点，每标签每到一处激活一次、每次激活的新边又携带标签走一
遍——n³ 到手。实践里 n³ 从未逼近：标签数通常是个位数、调用
点的实参少、图稀疏；27.6 两份报告的 rises/activations 计数就
是"实践远离最坏界"的直接证据。

### 48.8.5 计数与复杂度的互相印证

把 27.6 两份报告的计数放回 27.8.4 的账本，做一次"理论-实测"
对账。twice：rises=5——f 一次、inc.x 一次、三处结果位共三次；
activations=3——main:1 对 twice 一次、twice:1 与 twice:2 对
inc 各一次。位置约十个、标签两个、激活三次，n³ 的理论界在天
上，实测计数是——每一次激活都能在程序文本上指出对应的调用
点与实参。apply：rises=8、activations=4，多出的三次 rise 对
应第二个函数值进 f 后的三条新传播。两份计数都是"程序形状的
线性函数"而非"图尺寸的多项式"——这就是稀疏程序上 0-CFA 的
常态，也是它能在千万行代码上跑通的物质基础。读者做练习九
的规模实验时，把每一条计数的增量归因到具体的约束事件，这
份对账能力就是复杂度分析的实战版。

## 48.9 与 k-CFA 的关系：同一个"0"

### 48.9.1 从两个方向看同一件事

第 45 章的 k=0 与本章的 0-CFA 在定义上是**同一个分析决策**：不区分
调用历史，所有进入同一函数的信息汇入同一份结论。只是两章消费这个决
策的方式不同。第 45 章：调用图已知，k=0 决定"值"如何合并——
apply(inc,3) 与 apply(dbl,3) 若分析的是返回值，两次的结果会在被调
函数的单一状态里互相干扰。本章：调用图未知，同一个合并决定"被调函
数集合"如何长成——两次调用把 inc、dbl 倒进同一个 f 位置。

### 48.9.2 输出互补：边与值

两章的输出恰好互补。本章输出调用边（每个调用点的函数集），第 45 章
输出边上流动的值（每个调用串下变量的格值）。在一个完整的高阶编译器
里二者串联：先跑本章得到调用图（可能每个调用点是多元素集），再在
这张图上跑数据流；若想要 k>1 的精度，两个阶段通常合并成一个算法
（k-CFA 的经典定义本来就同时恢复控制流与环境）。本章与第 45 章把它
们拆开教，是为了让两个维度各自可见。

### 48.9.3 为什么 0 是合理的工程默认

最后一点解释了为什么 0 档最常见：在大量程序里，函数参数流向单一
（twice.tip 就是——f 全程只有 inc），k>0 拆出的分箱大多内容相
同，白白付出状态代价；真正多态的少数位置，可以像第 45 章那样局部
加深。**先拿 0-CFA 的可靠底图，再按需加深**，与全书反复出现的
"先可靠、后精确"节奏完全一致。

## 48.9.4 Shivers 的 k：一段家谱

k-CFA 的名字来自 Olin Shivers 1991 年的博士论文。他把控制流分
析表述为"抽象非确定性机器"：具体机器每步知道下一步调谁，抽象
机器在每个调用点带一**集合**的可能目标；为了给这个集合记忆上
下文，他给抽象状态加上最近 k 个调用点的序列——k=0 就是丢弃全
部历史，只剩集合本身。家谱的下一辈：Shivers 自己的 k=1 实现证
明了精度收益，也证明了指数代价；再往后，实用化的路线分了两
支——一支往"环境式的 0-CFA"走（把形参绑定改成环境查找，得到
等价但更快的表述，代表是 Might 的 协变分析族），一支往"Datalog
化"走（把约束写进逻辑程序，靠半朴素求值跑闭包，代表是
Whaley–Lam，第 49 章的 Doop 是它的指针分析后裔）。本教程的实
现是教科书式的集合式 0-CFA：没有环境、没有 Datalog，只有幂集
格上的单调增长——正因为它最朴素，k 的含义才最裸露：k 每加
一，状态空间乘上 |sites|；k=0 时那因子是 1，历史不存在，精度
与代价同时见底。

### 48.9.5 从 0-CFA 到本章代码的三个简写

本章实现对理论做了三个值得点名的简写。其一，函数值只有名字
（λ 标签），没有闭包环境——TIP 没有自由变量，标签即全貌；真
语言里闭包 = 标签 + 环境，0-CFA 要配一个地址抽象（本章位置集
合的推广）才完整。其二，返回值用"函数返回位置"这个粗粒度汇
点，没有调用点敏感的返回边——这是流不敏感的必然，返回位置属
于函数不属于调用。其三，字面量不发任何约束——它们不是函数
值，进不了缓存；若语言把整数也当值放进同一套位置（如
JavaScript），需要给每个位置一个"值域"维度，分析会长出第 49 章指针分析的模样。三个简写合起来划定了本章的适用边界：
TIP 这样的一等函数纯函数语言、只关心"调谁"、不关心值流。边
界之内，0-CFA 是精确的最小充分机器。

## 48.10 工程注意点

### 48.10.1 生成器与求解器之间的契约要最小

两层结构真正的纪律是约束数据的字段要**刚好够用**。本章为形参名表
纠结过一轮：求解器需要形参位置名，最省事的做法是把 AST 指针塞过
去——但那会立刻让"求解器与语言无关"名存实亡，日后换前端就得改
求解器。最终放进约束的是字符串形式的签名信息（params），代价只是
生成器多登记一个字段。契约里每多一个与具体语法相关的字段，都是未
来的维护点；能靠命名约定解决的（f.p_i），不要靠暴露结构解决。

### 48.10.2 动态长边时别忘了存量

新长出的 copy 边通过反向表对未来的上升自动生效，但边诞生**之前**位
置已有的标签不会自动流过来。本章在形参、返回两处各做了一次"查缓
存、补推存量"。这类问题在静态代码里没有任何异常提示——漏了补推，
症状只是某些标签在不动点里神秘缺席，且通常只在特定的激活顺序下出
现。对策是把"登记监听 + 追平存量"写成固定的成对动作，而不是分别
记起。

### 48.10.3 让计数成为自检的一部分

报告里的 rises 与 activations 不只是给读者看的统计，它们也是开发时
的廉价自检：在极小程序上这两个数字是可以手工核对的（27.6.2 就核对
过激活计数）。计数对不上，问题一定出在去重或配对逻辑，且症状会比
"集合里少个标签"更早暴露。给分析器留几个固定小程序、固定计数，
相当于给不动点算法准备一组确定性的回归用例。

### 48.10.4 报告范围要服务于阅读

打印全部 %N 位置会让输出被中间编号淹没；本章只报告有名字的变量位
置与调用点集合，调试细节留在开发期。呈现分析结果时，"读者想验证
什么"决定打印什么：本章要让人验证的是调用图，于是位置按调用相关
性筛选。这与第 13 章以来的做法一脉相承——工具的文本输出本身就是
教程界面的一部分，噪音即误导。

### 48.10.5 报告之外：给调试留的门

求解器把 cache 与 sites 两张表整个留在 CfaResult 里返回，而
printCfa 只挑了三段打印。这不是浪费：完整的表是调试与扩展的
接口——27.11 的练习七要打印 % 临时位，直接在 printCfa 里去掉
过滤即可；将来要接第 49 章式的 soundness 验证，也要从 cache
里查每个调用点的集合。分析器与报告器之间留这扇门，等于把
"分析的结果"与"结果的呈现"分开承诺——呈现可以随读者需要增
删，结果一旦稳定就不再动。教程里每一章的 printX 都遵守这条
分层，读者写自己的分析器时，这扇门的成本是一行 struct 拷
贝，收益是整个后续章节。

## 48.11 练习题与思路

1. 在 `twice.tip` 的 main 中增加一句 `twice(dbl, 5)`，预测并核对两
   个间接调用点的解析集合与 twice.f 的内容。思路：f 位置合并
   {inc,dbl}，twice:1、twice:2 都解析到两个标签；对照 apply 的报
   告理解"同一函数体被多态使用"。
2. 若 TIP 允许函数返回函数（如 `mk() { return inc; }`），约束生成
   需要在何处增加什么信息？思路：返回表达式若是变量（绑定为函
   数），现有返回绑定已能传播标签；说明激活规则的返回绑定为何天
   然覆盖这一情形，并用一个程序验证。
3. 手工对 twice.tip 模拟 F 的前三次迭代，列出每轮新出现的标签与
   新激活的配对，核对 27.6 的统计。思路：val 在首轮出现，形参绑定
   在次轮把标签送到 twice.f，激活在第三轮闭合调用点。
4. 讨论：为什么"经指针写入函数值"不能简单忽略？给出把第 49 章
   Andersen 与本章耦合的规则草案。思路：若 v∈pts(p)，`*p = g` 应
   让 v 的缓存包含 g 的标签——指针位置需要能携带标签集合。
5. 把 `apply.tip` 的两个调用点改成三次调用（再传入一个新函数），
   预测 rises/activations 增量并实测。思路：新标签带来一个 val、
   形参位置一次上升、调用点一次激活；体会计数如何随使用线性增长。

### 48.11.1 练习补充（三题）

练习四：给 twice.tip 加一个函数 dec（x-1），main 里再调一次
twice(dec)(3)。预测 rises 与 activations 各涨多少（提示：新
调用点激活 1 次、dec 绑定引发 f 缓存 rise 1 次、随后 twice:1
与 twice:2 对 "dec" 各激活一次——共 3 次激活、f 缓存涨到
{inc,dec}）。运行核对，解释 f 集合变大后 twice:1 的报告如
何从 {inc} 变 {inc,dec}。

练习五：把 apply.tip 改成嵌套两次：apply(apply(f, g), x) 的形
状（需要适配 apply 的两个参数类型一致）。预测哪些缓存会涨到
两个元素、哪些调用点的解析集合是 {apply} 而哪些是 {dbl,inc,
…}。这道题检验"位置"概念：外层 apply 的实参 1 位置装的是"应
用后的函数"，它的集合必须先由内层调用的结果位置 copy 过来。

练习六：给 CfaConstraints 加第四种约束——"return 位 → 调用
结果位"现在是激活时才发的 copy；把它改成静态约束（生成器直接
发 copy(结果位 ← 返回位)），求解器与输出会变化吗？先推理再实
验：copy 是惰性传播，静态发意味着"返回位有啥结果位就有啥"，
与激活时发等价——除非返回位在激活前就涨了缓存（本题的 TIP
程序里不会）。这个练习演示同一语义的两种约束布局，以及"惰性
copy + 动态激活"为什么是更通用的形状。

## 48.12 本章小结

本章处理了"调用图不再能从文本直接读出"的情形：高阶函数让被调位
置成为数据流的答案，而数据流又依赖调用图，循环依赖由最小不动点
解开。形式化上，程序被翻译为抽象缓存上的集合包含约束——val 提供
种子，copy 传递标签集合，调用激活规则在被调位置每长出一个函数时
动态补全形参与返回绑定。算法上，全部闭包压进一个标签粒度的
worklist：每个（位置,标签）配对至多处理一次，最坏 O(n³) 时间、
O(n²) 空间终止。经验上，twice 的两个间接调用点精确解析到 inc，
apply 的共享函数体把两次调用的 inc、dbl 如实合并——误差只朝多报
方向发生，真实调用从不缺席。最后，本章的"0"与第 45 章 k-CFA 的
k=0 是同一个决策：不记调用历史、共享一份结论；两章输出互补——
本章给出调用边，第 45 章在边上分析值。至此，第六篇已经把"可达性
框架（IFDS）、带值的可达性（IDE）、高阶控制流（0-CFA）"三块基
石铺好，下一章将面对 TIP 中最后一种需要专门分析的值：**指针**。

### 48.12.1 动手验证本章

验证入口与前两章一致：`bash tools/example_build.sh
examples/48_closure_0cfa` 构建，`python tools/check_example.py
examples/48_closure_0cfa` 对账两份报告与统计行（纯 LF、逐字
节）。docs 对账由 tools/check_docs.py 覆盖全部 14 个配套文件。
本章的输出里有三处理想的实验观测点：twice:1 的集合内容（加
新函数立刻变）、rises/activations 的计数（每加一次调用按练
习四的账本涨）、apply.f 的双元素集合（k=0 的代价展示）。改程
序、跑对账、读 diff——0-CFA 的全部行为都写在这三处。

### 48.13 与下一章的桥：从"调谁"到"指哪"

本章回答的问题（这个调用点可能调谁）是"间接跳转目标解析"的
函数版；下一章把同一句式换成内存版：这个变量可能指向哪个分配
点。两章的机器只差一个量词的用法——0-CFA 把不确定性收在**值
的集合**里（缓存），指针分析把它收在**约束的包含**里（pts 集
合）。但工程形态分道扬镳：集合版可以并查集化（Steensgaard 的
选择）、可以 Datalog 化（Doop 的选择）、可以在两条路之间按精
度预算插值（本章习题之外的广阔天地）。带上 27.5 的求解器读第 49 章，认骨架、换部件——这正是 26 章结尾那句方法论的第一
次实战。

### 48.11.2 练习再补两题

练习七：修改 printCfa，让它也报告 % 临时位置的缓存（去掉过滤）。

练习八：把 genExpr 对 VarRef 的处理改成"永远发 val"（不区分函

是 λ 标签，val(位置, "x") 里的 "x" 不是任何函数——缓存里出现

### 48.9.6 与第 45 章的实验性对照

第 45 章的 k=0 与本章 0-CFA 在理论上等价（都是上下文不敏感的
最小解），但两台机器的输出形状完全不同：前者打印每个函数入
口的环境（变量→值域），后者打印调用点集合与缓存（位置→函
数集）。同一程序喂两台机器，能直接对读的是"精度的形态"：
24 章里 main 的 a 在两次不同调用后合并成 ⊤ 的现象，在本章对
应 f 缓存涨到两个标签；24 章靠加 k 拆环境，本章靠加 k 拆缓
存——两种"拆"在实现上分别是 call-string 复制与（站点, 标
签）配对的细化。读者若做过 24 章的练习，把同样的程序改造成
闭包形状跑本章，两张输出的并排就是"k 的两种花法"的完整
对照表。

### 48.12.2 一页纸回顾

位置装标签，缓存即堆；val 撒种子，copy 接线忙；标签到 callee
位，激活补绑定；形参←实参、结果←返回位，存量立即下推忙；
rises 记缓存涨，activations 记配对；twice 单点集、apply 双点
集，k=0 的代价两行看光。三次方是理论价，实测计数个位躺；
下一章把函数值换成地址，同一骨架再上岗。

### 48.12.3 与附录文件的对读建议

附录十个支撑文件里，与本章语义真正相关的只有三处浅接口：
ast.hpp 的 CallE 形状（callee 是表达式而非名字——生成器据此

### 48.11.3 练习最后两题

练习九：性能题。把 twice 嵌套三层——thrice(g,x) = g(g(g(x)))
的形状（TIP 里写成组合两次的 twice 加一层）。预测 rises 与
activations 的增长曲线，实测三个规模（一层/两层/三层），画出
计数随规模的变化。它是接近线性还是接近平方？用 27.8.4 的账

练习十：毕业题。给本章分析加"返回值位置"的调用点敏感版：结
果位不再统一用 fun 的返回位，而是每个（调用点, 标签）激活时

一小步——并且亲身体会到精度每前进一小步、位置空间付出多大
的膨胀。

### 48.13.1 结语：把"调谁"变成数据

本章最深的转变不在算法而在**问题的地位**：调用图从编译器的既
定输入，降格为分析器的一阶产出。一旦"调谁"变成数据，后面一切
过程间分析（第 25/26 章的超级图、第 49 章的指针图）对闭包语言
就重新可用——先跑 0-CFA、按解析集合展开调用边，超级图就画出
来了。工业编译器对虚函数/接口调用的 devirtualization 正是这
条流水线：控制流分析给出候选目标集合，集合 singleton 时把间
接调用改写成直接调用，剩下的交给内联与常量传播。读者在本章
拿到的不只是一个 twice/apply 的求解器，而是"不确定性的一等
公民化"这个思想本身：集合出现在值的位置上，格律就接管了它
的一切行为——增长有界、合并安全、查询可靠。下一章把同样的
思想浇灌到内存地址上，收成叫指向分析。

## 附.1 文法 TIP.g4

## 附.4 核心分析：cfa.hpp 与 cfa.cpp

### 附.4.1 src/cfa.hpp

cfa.hpp 是本章形式化与代码的接合部，建议对照 48.2 节阅读：
CfaConstraints 的 lambda、edges、calls 分别对应标签集、val/copy 约
束、调用形状；retLoc 与 params 是激活规则所需的函数信息；CfaResult
的 cache、sites 是两个方向的答案（缓存与调用点集合），rises、
activations 是 27.10.3 所说的自检计数。文件头注释完整说明了两层
设计。全文如下：

```cpp
// file: src/cfa.hpp
// 第 48 章配套：0-CFA（零阶控制流分析）——为高阶调用回答
// "这个调用点可能调到哪些函数"。
//
// 设计分两层，正文会完整讲解：
//   1. 约束生成：把程序翻译成"与语法无关"的约束数据 CfaConstraints；
//   2. 不动点求解：solve0Cfa 只见约束，在"位置 → 函数集"的缓存上
//      做 cubic worklist；每当调用点的函数集长出新函数，
//      动态长出形参绑定与返回绑定（"鸡与蛋"由不动点解开）。
#pragma once

#include <map>
#include <set>
#include <string>
#include <tuple>
#include <vector>

#include "ast.hpp"
#include "symtab.hpp"

namespace tip {

struct CfaConstraints {
    // 程序中全部函数名（抽象 λ 标签集合）。
    std::set<std::string> lambda;

    // 抽象位置（abstract location）的命名约定：
    //   形参/局部变量 → "fun.x"（生成器与求解器共同遵守）；
    //   表达式结果位置 → "%N"（生成器顺序编号，仅用于串联约束）。
    //
    // 两类基础边（三元组 (kind, a, b)）：
    //   ("val",  loc, fun) : 位置 loc 的缓存 ⊇ {fun}（函数名出现处）；
    //   ("copy", dst, src) : 位置 dst 的缓存 ⊇ 位置 src 的缓存（变量间流动）。
    std::vector<std::tuple<std::string, std::string, std::string>> edges;

    // 间接调用：函数值位置 calleeLoc 每"长出"一个函数 fun，
    // 就按命名约定激活一次绑定：
    //   fun 的第 i 个形参位置 ⊇ 第 i 个实参位置；
    //   调用结果位置        ⊇ fun 的返回表达式位置。
    struct CallEdge {
        std::string site;                  // 调用点标签 "fun:n"
        std::string calleeLoc;
        std::vector<std::string> argLocs;
        std::string resultLoc;
    };
    std::vector<CallEdge> calls;

    std::map<std::string, std::string> retLoc;    // 函数名 → 返回表达式结果位置
    std::map<std::string, std::string> siteText;  // 调用点标签 → 表达式文本
    // 形参名表（函数签名的一部分）：求解器据此拼形参位置 "fun.param"，
    // 无需接触 AST。
    std::map<std::string, std::vector<std::string>> params;
};

// 遍历 AST + 名字绑定，生成 0-CFA 约束。
CfaConstraints buildCfaConstraints(const ProgramA &program,
                                   const Bindings &bindings);

struct CfaResult {
    std::map<std::string, std::set<std::string>> cache;  // 位置 → 函数集
    std::map<std::string, std::set<std::string>> sites;  // 调用点 → 函数集
    long activations = 0;   // 新（调用点, 目标函数）配对数
    long rises = 0;         // 缓存集合并使集合真上升的次数
};

CfaResult solve0Cfa(const CfaConstraints &c);

std::string printCfa(const CfaConstraints &c, const CfaResult &r);

}  // namespace tip
```

### 附.4.2 src/cfa.cpp

cfa.cpp 包含三个部分：匿名命名空间内的 ConstraintGen（48.4 节逐方法
讲过）、solve0Cfa（48.5 节逐表讲过）、printCfa（报告格式化，按调用
点→命名缓存→统计三段输出，决定了附.3 的文本形状）。阅读时建议把
genExpr 的分支与 27.2.3–27.2.4 的规则并置，把激活段两处"存量补推"
与 27.10.2 并置。全文如下：

```cpp
// file: src/cfa.cpp
#include "cfa.hpp"

#include <deque>
#include <set>
#include <sstream>
#include <utility>

#include "pretty.hpp"

namespace tip {
namespace {

// 约束生成器：给每个表达式分配一个结果位置，并递归收集约束。
struct ConstraintGen {
    const Bindings &bindings;
    CfaConstraints c;
    int locCounter = 0;
    std::map<std::string, int> siteCounter;
    std::string current;   // 当前所在函数名

    explicit ConstraintGen(const Bindings &b) : bindings(b) {}

    std::string freshLoc() { return "%" + std::to_string(++locCounter); }
    std::string varLoc(const std::string &fun, const std::string &name) {
        return fun + "." + name;
    }

    // 表达式 → 结果位置；沿途发出约束。
    std::string genExpr(const Expr *e) {
        std::string loc = freshLoc();

        if (const auto *x = dynamic_cast<const VarRef *>(e)) {
            auto it = bindings.uses.find(x);
            if (it != bindings.uses.end()) {
                const Symbol *sym = it->second;
                if (sym->kind == Symbol::Fun) {
                    // 函数名作为值出现：loc ⊇ {name}。
                    c.edges.emplace_back("val", loc, sym->name);
                } else {
                    // 参数/局部变量：loc ⊇ "fun.name" 的缓存。
                    c.edges.emplace_back(
                        "copy", loc, varLoc(sym->fun->name, sym->name));
                }
            }
        } else if (const auto *x = dynamic_cast<const CallE *>(e)) {
            std::string fn = genExpr(x->callee.get());
            std::vector<std::string> args;
            for (const auto &a : x->args) args.push_back(genExpr(a.get()));

            int n = ++siteCounter[current];
            std::string site = current + ":" + std::to_string(n);
            c.siteText[site] = printExpr(e);
            c.calls.push_back(
                CfaConstraints::CallEdge{site, fn, std::move(args), loc});
        } else if (const auto *x = dynamic_cast<const Binop *>(e)) {
            // 良态 TIP 中算术/比较不产生函数值；子表达式仍须走一遍，
            // 因为其中可能出现函数引用（如作为实参的一部分）。
            genExpr(x->l.get());
            genExpr(x->r.get());
        } else if (const auto *x = dynamic_cast<const Deref *>(e)) {
            genExpr(x->e.get());
        } else if (const auto *x = dynamic_cast<const AllocE *>(e)) {
            genExpr(x->e.get());
        } else if (const auto *x = dynamic_cast<const FieldA *>(e)) {
            genExpr(x->e.get());
        } else if (const auto *x = dynamic_cast<const RecLit *>(e)) {
            for (const auto &[f, v] : x->fields) genExpr(v.get());
        }
        // IntLit / InputE / NullE：无函数值，也无子表达式。
        return loc;
    }

    void genStmt(const Stmt *s) {
        if (const auto *x = dynamic_cast<const AssignS *>(s)) {
            std::string rhs = genExpr(x->value.get());
            // 只有"直接变量赋值"会绑定函数值；字段/指针左值在良态
            // TIP 中不承载函数，忽略（其 RHS 已走过）。
            if (const auto *t = dynamic_cast<const VarRef *>(x->target.get()))
                c.edges.emplace_back("copy", varLoc(current, t->name), rhs);
        } else if (const auto *x = dynamic_cast<const OutputS *>(s)) {
            genExpr(x->e.get());
        } else if (const auto *x = dynamic_cast<const IfS *>(s)) {
            genExpr(x->cond.get());
            genStmt(x->then.get());
            if (x->els) genStmt(x->els.get());
        } else if (const auto *x = dynamic_cast<const WhileS *>(s)) {
            genExpr(x->cond.get());
            genStmt(x->body.get());
        } else if (const auto *x = dynamic_cast<const BlockS *>(s)) {
            for (const auto &st : x->ss) genStmt(st.get());
        }
        // 函数的 return 语句由 FunDecl 层统一处理（它要登记 retLoc）。
    }

    CfaConstraints run(const ProgramA &program) {
        for (const auto &f : program.funs) c.lambda.insert(f->name);

        for (const auto &f : program.funs) {
            current = f->name;
            c.params[f->name] = f->params;
            genStmt(f->body.get());
            c.retLoc[f->name] = genExpr(f->ret->e.get());
        }
        return std::move(c);
    }
};

}  // namespace

CfaConstraints buildCfaConstraints(const ProgramA &program,
                                   const Bindings &bindings) {
    ConstraintGen gen(bindings);
    return gen.run(program);
}

CfaResult solve0Cfa(const CfaConstraints &c) {
    CfaResult r;

    // copyOut[src]：src 每长出一个函数，都要复制到这些目的位置。
    std::map<std::string, std::set<std::string>> copyOut;
    // callAt[loc]：监听该位置的调用边索引；位置长出函数即尝试激活。
    std::map<std::string, std::vector<size_t>> callAt;
    // 已激活的（调用边, 函数）配对——同一路径只绑定一次。
    std::set<std::pair<size_t, std::string>> activated;

    std::deque<std::pair<std::string, std::string>> wl;  // (位置, 新函数)

    auto add = [&](const std::string &loc, const std::string &fun) {
        if (r.cache[loc].insert(fun).second) {
            ++r.rises;
            wl.emplace_back(loc, fun);
        }
    };

    // 先登记所有静态边：copy 边建监听关系；val 边直接入队。
    // 顺序无关——copy 监听先就位，val 引发的传播在出队时统一处理。
    for (const auto &[kind, a, b] : c.edges) {
        if (kind == "val") {
            add(a, b);
        } else {  // "copy": a ⊇ b
            copyOut[b].insert(a);
        }
    }
    for (size_t i = 0; i < c.calls.size(); ++i)
        callAt[c.calls[i].calleeLoc].push_back(i);

    while (!wl.empty()) {
        auto [loc, fun] = wl.front();
        wl.pop_front();

        // copy 传播：src 长出 fun → 所有 dst 长出 fun。
        auto cit = copyOut.find(loc);
        if (cit != copyOut.end())
            for (const std::string &dst : cit->second) add(dst, fun);

        // 调用激活：loc 长出 fun → 按命名约定长出参数/返回 copy 边。
        auto kit = callAt.find(loc);
        if (kit == callAt.end()) continue;
        for (size_t ci : kit->second) {
            if (!activated.emplace(ci, fun).second) continue;
            ++r.activations;
            const CfaConstraints::CallEdge &call = c.calls[ci];
            r.sites[call.site].insert(fun);

            // 参数绑定（仅在形参个数范围内）：形参位置 "fun.p" ⊇ 实参位置。
            // 实参可能在激活前就已带着函数值，登记监听后把存量补推一遍。
            auto pit = c.params.find(fun);
            if (pit != c.params.end())
                for (size_t i = 0;
                     i < call.argLocs.size() && i < pit->second.size(); ++i) {
                    const std::string &arg = call.argLocs[i];
                    std::string param = fun + "." + pit->second[i];
                    copyOut[arg].insert(param);
                auto ait = r.cache.find(arg);
                if (ait != r.cache.end())
                    for (const std::string &g : ait->second) add(param, g);
            }

            auto rit = c.retLoc.find(fun);
            if (rit != c.retLoc.end()) {
                copyOut[rit->second].insert(call.resultLoc);
                auto eit = r.cache.find(rit->second);
                if (eit != r.cache.end())
                    for (const std::string &g : eit->second)
                        add(call.resultLoc, g);
            }
        }
    }
    return r;
}

std::string printCfa(const CfaConstraints &c, const CfaResult &r) {
    std::ostringstream out;
    out << "== 0-CFA control-flow analysis ==\n";
    out << "-- resolved call sites --\n";
    for (const auto &call : c.calls) {
        out << "  " << call.site << " " << c.siteText.at(call.site) << ": {";
        auto it = r.sites.find(call.site);
        bool first = true;
        if (it != r.sites.end())
            for (const std::string &f : it->second) {
                if (!first) out << ",";
                out << f;
                first = false;
            }
        out << "}\n";
    }

    out << "-- abstract caches (named locations) --\n";
    for (const auto &[loc, funs] : r.cache) {
        if (loc.rfind("%", 0) == 0 || funs.empty()) continue;
        out << "  " << loc << ": {";
        bool first = true;
        for (const std::string &f : funs) {
            if (!first) out << ",";
            out << f;
            first = false;
        }
        out << "}\n";
    }

    out << "-- stats --\n";
    out << "cache rises: " << r.rises
        << ", call activations: " << r.activations << "\n";
    return out.str();
}

}  // namespace tip
```

```cpp
    parser.removeErrorListeners();
```

## 附.6 AST 与前端基础设施

### 附.6.1 src/ast.hpp

ast.hpp 定义全书冻结的 AST 接口。与本章相关的是两类节点：VarRef
（同一个类承载函数名与变量引用，种类由符号表判定）和 CallE
（callee 是任意 Expr，这是高阶调用在数据结构上的根）。其余节点
（Binop、Deref、AllocE 等）决定了 genExpr 需要递归经过的分支。
全文如下：

```cpp
// file: src/ast.hpp
// AST 定义：AST 是去掉了括号、分号等语法噪音的程序结构。
// 接口自本章起冻结，后续所有分析（名字、CFG、类型、格……）都在此之上工作。
#pragma once

#include <memory>
#include <string>
#include <utility>
#include <vector>

namespace tip {

enum class BOp { Add, Sub, Mul, Div, Gt, Eq };

struct Expr {
    virtual ~Expr() = default;
};
struct IntLit : Expr {
    int v;
    explicit IntLit(int value) : v(value) {}
};
struct VarRef : Expr {
    std::string name;
    explicit VarRef(std::string n) : name(std::move(n)) {}
};
struct InputE : Expr {};
struct Binop : Expr {
    BOp op;
    std::unique_ptr<Expr> l, r;
    Binop(BOp o, std::unique_ptr<Expr> lhs, std::unique_ptr<Expr> rhs)
        : op(o), l(std::move(lhs)), r(std::move(rhs)) {}
};
struct CallE : Expr {
    std::unique_ptr<Expr> callee;
    std::vector<std::unique_ptr<Expr>> args;
    CallE(std::unique_ptr<Expr> fn, std::vector<std::unique_ptr<Expr>> as)
        : callee(std::move(fn)), args(std::move(as)) {}
};
struct Deref : Expr {
    std::unique_ptr<Expr> e;
    explicit Deref(std::unique_ptr<Expr> p) : e(std::move(p)) {}
};
struct AddrOf : Expr {                       // spa: & Id
    std::string name;
    explicit AddrOf(std::string n) : name(std::move(n)) {}
};
struct AllocE : Expr {
    std::unique_ptr<Expr> e;
    explicit AllocE(std::unique_ptr<Expr> init) : e(std::move(init)) {}
};
struct NullE : Expr {};
struct RecLit : Expr {
    std::vector<std::pair<std::string, std::unique_ptr<Expr>>> fields;
    explicit RecLit(std::vector<std::pair<std::string, std::unique_ptr<Expr>>> fs)
        : fields(std::move(fs)) {}
};
struct FieldA : Expr {
    std::unique_ptr<Expr> e;
    std::string field;
    FieldA(std::unique_ptr<Expr> record, std::string f)
        : e(std::move(record)), field(std::move(f)) {}
};

struct Stmt {
    virtual ~Stmt() = default;
};
// target 只会是 VarRef / FieldA / Deref，文法 lvalue 已限定。
struct AssignS : Stmt {
    std::unique_ptr<Expr> target, value;
    AssignS(std::unique_ptr<Expr> t, std::unique_ptr<Expr> v)
        : target(std::move(t)), value(std::move(v)) {}
};
struct OutputS : Stmt {
    std::unique_ptr<Expr> e;
    explicit OutputS(std::unique_ptr<Expr> x) : e(std::move(x)) {}
};
struct IfS : Stmt {
    std::unique_ptr<Expr> cond;
    std::unique_ptr<Stmt> then, els;
    IfS(std::unique_ptr<Expr> c, std::unique_ptr<Stmt> t, std::unique_ptr<Stmt> e)
        : cond(std::move(c)), then(std::move(t)), els(std::move(e)) {}
};
struct WhileS : Stmt {
    std::unique_ptr<Expr> cond;
    std::unique_ptr<Stmt> body;
    WhileS(std::unique_ptr<Expr> c, std::unique_ptr<Stmt> b)
        : cond(std::move(c)), body(std::move(b)) {}
};
struct BlockS : Stmt {
    std::vector<std::unique_ptr<Stmt>> ss;
    explicit BlockS(std::vector<std::unique_ptr<Stmt>> v) : ss(std::move(v)) {}
};
struct ReturnS : Stmt {
    std::unique_ptr<Expr> e;
    explicit ReturnS(std::unique_ptr<Expr> x) : e(std::move(x)) {}
};

struct FunDecl {
    std::string name;
    std::vector<std::string> params;
    std::vector<std::string> vars;
    std::unique_ptr<Stmt> body;
    std::unique_ptr<ReturnS> ret;
};

struct ProgramA {
    std::vector<std::unique_ptr<FunDecl>> funs;
};

}  // namespace tip
```

### 附.6.2 src/ast_build.hpp 与 src/ast_build.cpp

AST 构建器负责把 ANTLR 的 parse tree 翻译为 ast.hpp 中的对象。本章
不新增任何构建规则，但生成器依赖它的两点既有行为：函数名与变量

```cpp
// file: src/ast_build.hpp
// AST 构建器：在 ANTLR 生成的 parse-tree 上下文节点上手工递归下降。
// （本工具链 C++ runtime 的 visitor 以 std::any 传值，而 std::any 不能持有
// unique_ptr，因此不使用 visitor 机制：parse-tree 的上下文类本身信息完整，
```

```cpp
// file: src/ast_build.cpp
#include "ast_build.hpp"

#include <utility>
#include <vector>

namespace tip {

std::unique_ptr<ProgramA> AstBuilder::build(TIPParser::ProgramContext *tree) {
    auto program = std::make_unique<ProgramA>();
    for (auto *fc : tree->function()) program->funs.push_back(buildFun(fc));
    return program;
}

std::unique_ptr<FunDecl> AstBuilder::buildFun(TIPParser::FunctionContext *ctx) {
    auto f = std::make_unique<FunDecl>();
    f->name = ctx->IDENT()->getText();
    if (ctx->params()) {
        for (auto *p : ctx->params()->IDENT()) f->params.push_back(p->getText());
    }
    if (ctx->varDecls()) {
        for (auto *v : ctx->varDecls()->IDENT()) f->vars.push_back(v->getText());
    }

    std::vector<std::unique_ptr<Stmt>> body;
    for (auto *sc : ctx->stmt()) body.push_back(buildStmt(sc));
    f->body = std::make_unique<BlockS>(std::move(body));

    f->ret = std::make_unique<ReturnS>(buildExpr(ctx->expr()));
    return f;
}

std::unique_ptr<Expr> AstBuilder::buildLvalue(TIPParser::LvalueContext *lv) {
    std::unique_ptr<Expr> base;
    std::string field;
    if (auto *d = dynamic_cast<TIPParser::DirectLvalueContext *>(lv)) {
        base = std::make_unique<VarRef>(d->IDENT(0)->getText());
        if (d->IDENT().size() == 2) field = d->IDENT(1)->getText();
    } else {
        auto *p = dynamic_cast<TIPParser::PointerLvalueContext *>(lv);
        base = std::make_unique<Deref>(buildExpr(p->expr()));
        if (p->IDENT()) field = p->IDENT()->getText();
    }
    if (!field.empty())
        return std::make_unique<FieldA>(std::move(base), std::move(field));
    return base;
}

std::unique_ptr<Expr> AstBuilder::buildExpr(TIPParser::ExprContext *ctx) {
    if (auto *c = dynamic_cast<TIPParser::IntExprContext *>(ctx))
        return std::make_unique<IntLit>(std::stoi(c->INT()->getText()));
    if (auto *c = dynamic_cast<TIPParser::VarExprContext *>(ctx))
        return std::make_unique<VarRef>(c->IDENT()->getText());
    if (dynamic_cast<TIPParser::InputExprContext *>(ctx))
        return std::make_unique<InputE>();
    if (dynamic_cast<TIPParser::NullExprContext *>(ctx))
        return std::make_unique<NullE>();
    if (auto *c = dynamic_cast<TIPParser::ParenExprContext *>(ctx))
        return buildExpr(c->expr());

    if (auto *c = dynamic_cast<TIPParser::AddExprContext *>(ctx)) {
        const BOp op = c->PLUS() ? BOp::Add : BOp::Sub;
        return std::make_unique<Binop>(op, buildExpr(c->expr(0)), buildExpr(c->expr(1)));
    }
    if (auto *c = dynamic_cast<TIPParser::MulExprContext *>(ctx)) {
        const BOp op = c->STAR() ? BOp::Mul : BOp::Div;
        return std::make_unique<Binop>(op, buildExpr(c->expr(0)), buildExpr(c->expr(1)));
    }
    if (auto *c = dynamic_cast<TIPParser::CmpExprContext *>(ctx)) {
        const BOp op = c->GT() ? BOp::Gt : BOp::Eq;
        return std::make_unique<Binop>(op, buildExpr(c->expr(0)), buildExpr(c->expr(1)));
    }
    if (auto *c = dynamic_cast<TIPParser::NegExprContext *>(ctx)) {
        // TIP 没有负数字面量 token，-E 即 0-E。
        return std::make_unique<Binop>(BOp::Sub, std::make_unique<IntLit>(0),
                                       buildExpr(c->expr()));
    }
    if (auto *c = dynamic_cast<TIPParser::CallExprContext *>(ctx)) {
        std::vector<std::unique_ptr<Expr>> args;
        if (c->args())
            for (auto *a : c->args()->expr()) args.push_back(buildExpr(a));
        return std::make_unique<CallE>(buildExpr(c->expr()), std::move(args));
    }
    if (auto *c = dynamic_cast<TIPParser::FieldExprContext *>(ctx))
        return std::make_unique<FieldA>(buildExpr(c->expr()), c->IDENT()->getText());
    if (auto *c = dynamic_cast<TIPParser::DerefExprContext *>(ctx))
        return std::make_unique<Deref>(buildExpr(c->expr()));
    if (auto *c = dynamic_cast<TIPParser::AddrExprContext *>(ctx))
        return std::make_unique<AddrOf>(c->IDENT()->getText());
    if (auto *c = dynamic_cast<TIPParser::AllocExprContext *>(ctx))
        return std::make_unique<AllocE>(buildExpr(c->expr()));
    if (auto *c = dynamic_cast<TIPParser::RecExprContext *>(ctx)) {
        std::vector<std::pair<std::string, std::unique_ptr<Expr>>> fields;
        for (auto *fc : c->field())
            fields.emplace_back(fc->IDENT()->getText(), buildExpr(fc->expr()));
        return std::make_unique<RecLit>(std::move(fields));
    }
    return nullptr;  // 解析成功时不会到达
}

std::unique_ptr<Stmt> AstBuilder::buildStmt(TIPParser::StmtContext *ctx) {
    if (auto *c = dynamic_cast<TIPParser::AssignStmtContext *>(ctx))
        return std::make_unique<AssignS>(buildLvalue(c->lvalue()), buildExpr(c->expr()));
    if (auto *c = dynamic_cast<TIPParser::OutputStmtContext *>(ctx))
        return std::make_unique<OutputS>(buildExpr(c->expr()));
    if (auto *c = dynamic_cast<TIPParser::IfStmtContext *>(ctx)) {
        std::unique_ptr<Stmt> els;
        if (c->stmt().size() == 2) els = buildStmt(c->stmt(1));
        return std::make_unique<IfS>(buildExpr(c->expr()), buildStmt(c->stmt(0)),
                                     std::move(els));
    }
    if (auto *c = dynamic_cast<TIPParser::WhileStmtContext *>(ctx))
        return std::make_unique<WhileS>(buildExpr(c->expr()), buildStmt(c->stmt()));
    if (auto *c = dynamic_cast<TIPParser::BlockStmtContext *>(ctx)) {
        std::vector<std::unique_ptr<Stmt>> ss;
        for (auto *sc : c->stmt()) ss.push_back(buildStmt(sc));
        return std::make_unique<BlockS>(std::move(ss));
    }
    return nullptr;  // 解析成功时不会到达
}

std::unique_ptr<ProgramA> buildAst(TIPParser::ProgramContext *tree) {
    return AstBuilder{}.build(tree);
}

}  // namespace tip
```

### 附.6.3 src/symtab.hpp 与 src/symtab.cpp

符号表是本章约束生成的判定依据：resolveNames 先注册全部函数名再
逐函数解析，使每个 VarRef 的符号（Fun/Param/Local）可查；生成器
据符号种类发 val 或 copy，并使用 Fun 指针拼变量位置。需要强调的
是函数名与变量名在符号表中分层（全局作用域挂函数，函数作用域挂
形参与局部变量），这保证 f 形参位置不会与某个叫 f 的函数混淆。
头文件与实现全文如下：

```cpp
// file: src/symtab.hpp
// 符号表与名字解析：把 AST 上的每个 VarRef 绑定到它的声明
// （函数 / 参数 / 局部变量），同时产出未声明、重复声明诊断。
#pragma once

#include <map>
#include <string>
#include <vector>

#include "ast.hpp"

namespace tip {

struct Symbol {
    enum Kind { Fun, Param, Local } kind;
    std::string name;
    const FunDecl *fun;          // Fun: 指向自身声明; Param/Local: 指向所属函数
};

struct Scope {
    Scope *parent;
    std::map<std::string, Symbol> table;

    explicit Scope(Scope *p = nullptr) : parent(p) {}
    const Symbol *lookup(const std::string &name) const;
};

struct Diag {
    std::string text;
};

struct Bindings {
    Scope global;                                  // 函数名所在的全局作用域
    // 各函数作用域由 Bindings 持有所有权：uses 中的 Symbol* 才不会悬垂。
    std::vector<std::unique_ptr<Scope>> scopes;
    std::vector<Diag> errors;
    std::map<const VarRef *, const Symbol *> uses;  // 解析成功的使用点
};

// 两遍解析：先注册全部函数名（支持前向调用），再逐函数解析函数体。
Bindings resolveNames(ProgramA &program);

}  // namespace tip
```

```cpp
// file: src/symtab.cpp
#include "symtab.hpp"

#include <utility>

namespace tip {

namespace {

// 解析器在遍历 AST 的同时完成绑定与诊断收集。
struct Resolver {
    Bindings bindings;
    Scope *current = nullptr;
    const FunDecl *owner = nullptr;

    void declare(const std::string &name, Symbol::Kind kind) {
        if (current->table.count(name)) {
            bindings.errors.push_back({"error: redeclared '" + name + "'"});
            return;  // 保留先声明者，后声明被忽略
        }
        current->table.emplace(name, Symbol{kind, name, owner});
    }

    void resolveExpr(const Expr *e) {
        if (const auto *x = dynamic_cast<const VarRef *>(e)) {
            const Symbol *s = current->lookup(x->name);
            if (!s) {
                bindings.errors.push_back({"error: undeclared '" + x->name + "'"});
            } else {
                bindings.uses[x] = s;
            }
            return;
        }
        if (const auto *x = dynamic_cast<const Binop *>(e)) {
            resolveExpr(x->l.get());
            resolveExpr(x->r.get());
            return;
        }
        if (const auto *x = dynamic_cast<const CallE *>(e)) {
            resolveExpr(x->callee.get());
            for (const auto &a : x->args) resolveExpr(a.get());
            return;
        }
        if (const auto *x = dynamic_cast<const Deref *>(e)) return resolveExpr(x->e.get());
        if (const auto *x = dynamic_cast<const AllocE *>(e)) return resolveExpr(x->e.get());
        if (const auto *x = dynamic_cast<const FieldA *>(e)) {
            resolveExpr(x->e.get());  // 字段名不是变量，无需解析
            return;
        }
        if (const auto *x = dynamic_cast<const RecLit *>(e)) {
            for (const auto &f : x->fields) resolveExpr(f.second.get());
            return;
        }
        // IntLit / InputE / AddrOf / NullE：无变量使用。
    }

    void resolveStmt(const Stmt *s) {
        if (const auto *x = dynamic_cast<const AssignS *>(s)) {
            resolveExpr(x->target.get());
            resolveExpr(x->value.get());
            return;
        }
        if (const auto *x = dynamic_cast<const OutputS *>(s)) return resolveExpr(x->e.get());
        if (const auto *x = dynamic_cast<const IfS *>(s)) {
            resolveExpr(x->cond.get());
            resolveStmt(x->then.get());
            if (x->els) resolveStmt(x->els.get());
            return;
        }
        if (const auto *x = dynamic_cast<const WhileS *>(s)) {
            resolveExpr(x->cond.get());
            resolveStmt(x->body.get());
            return;
        }
        if (const auto *x = dynamic_cast<const BlockS *>(s)) {
            for (const auto &st : x->ss) resolveStmt(st.get());
            return;
        }
        if (const auto *x = dynamic_cast<const ReturnS *>(s)) return resolveExpr(x->e.get());
    }
};

}  // namespace

const Symbol *Scope::lookup(const std::string &name) const {
    auto it = table.find(name);
    if (it != table.end()) return &it->second;
    return parent ? parent->lookup(name) : nullptr;
}

Bindings resolveNames(ProgramA &program) {
    Resolver resolver;
    resolver.bindings.global = Scope(nullptr);
    Scope *global = &resolver.bindings.global;

    // 第一遍：所有函数名进入全局作用域。
    for (const auto &f : program.funs) {
        if (global->table.count(f->name)) {
            resolver.bindings.errors.push_back({"error: redeclared '" + f->name + "'"});
            continue;
        }
        global->table.emplace(f->name, Symbol{Symbol::Fun, f->name, f.get()});
    }

    // 第二遍：每个函数开自己的作用域，父作用域是全局表；
    // 作用域所有权交给 Bindings，遍历结束后符号依然存活。
    for (const auto &f : program.funs) {
        auto functionScope = std::make_unique<Scope>(global);
        resolver.current = functionScope.get();
        resolver.owner = f.get();

        for (const std::string &p : f->params) resolver.declare(p, Symbol::Param);
        for (const std::string &v : f->vars) resolver.declare(v, Symbol::Local);

        resolver.resolveStmt(f->body.get());
        resolver.resolveStmt(f->ret.get());

        resolver.current = nullptr;
        resolver.bindings.scopes.push_back(std::move(functionScope));
    }
    return std::move(resolver.bindings);
}

}  // namespace tip
```

### 附.7.2 src/cfg.cpp

cfg.cpp 的实现把语句展开为节点与边（第 12 章建立，本章原样快照）。
本章的约束生成器选择不经过 CFG 而直接遍历 AST，因为它需要为每个
表达式编号、且不关心语句顺序之外的图结构；两种走法等价，读者可
对照第 45 章经过 CFG 的实现理解这一取舍。全文如下：

```cpp
// file: src/cfg.cpp
#include "cfg.hpp"

#include <map>
#include <set>
#include <sstream>
#include <vector>

#include "pretty.hpp"

namespace tip {
namespace {

// 两遍构造：第一遍按 AST 先序给所有程序点分配固定编号；第二遍连边。
// 先编号再连边，是为了让编号严格按源码顺序（连边时若先构造后继节点，
// 后继会抢在前面编号），从而输出与程序点编号都是确定的。
class CfgBuilder {
public:
    explicit CfgBuilder(const ProgramA &program) : program_(program) {}

    Cfg run() {
        Cfg cfg;
        for (const auto &fun : program_.funs) {
            FunCfg fc;
            cur_ = &fc;
            cur_->name = fun->name;
            nextId_ = 1;
            stmtId_.clear();

            const int entry = addNode(CfgNode::Kind::Entry);
            cur_->entry = entry;
            numberStmt(fun->body.get());
            const int retId = addNode(CfgNode::Kind::Return, fun->ret.get());
            const int exitId = addNode(CfgNode::Kind::Exit);
            cur_->exitNode = exitId;

            // 连边：语句构造返回它自己的入口点集合；空块没有节点，直接透传后继。
            std::vector<int> bodyEntries = wireStmt(fun->body.get(), {retId});
            if (bodyEntries.empty()) bodyEntries = {retId};
            link(entry, bodyEntries);
            link(retId, {exitId});

            // set 去重并排序：CFG 边不允许重复，输出顺序固定。
            std::set<std::pair<int, int>> uniq(cur_->edges.begin(), cur_->edges.end());
            cur_->edges.assign(uniq.begin(), uniq.end());
            cfg.funs.push_back(std::move(*cur_));
        }
        return cfg;
    }

private:
    const ProgramA &program_;
    FunCfg *cur_ = nullptr;
    int nextId_ = 1;
    std::map<const Stmt *, int> stmtId_;

    int addNode(CfgNode::Kind kind, const Stmt *stmt = nullptr) {
        const int id = nextId_++;
        cur_->nodes.emplace(id, CfgNode{id, kind, stmt});
        return id;
    }

    // ---- 第一遍：编号 ----
    void numberStmt(const Stmt *s) {
        if (const auto *b = dynamic_cast<const BlockS *>(s)) {
            for (const auto &x : b->ss) numberStmt(x.get());
            return;
        }
        if (const auto *x = dynamic_cast<const IfS *>(s)) {
            stmtId_[x] = addNode(CfgNode::Kind::Branch, x);
            numberStmt(x->then.get());
            numberStmt(x->els.get());
            return;
        }
        if (const auto *x = dynamic_cast<const WhileS *>(s)) {
            stmtId_[x] = addNode(CfgNode::Kind::Branch, x);
            numberStmt(x->body.get());
            return;
        }
        if (dynamic_cast<const AssignS *>(s)) {
            stmtId_[s] = addNode(CfgNode::Kind::Assign, s);
            return;
        }
        if (dynamic_cast<const OutputS *>(s)) {
            stmtId_[s] = addNode(CfgNode::Kind::Output, s);
        }
    }

    // ---- 第二遍：连边。返回进入该语句时首先到达的程序点集合 ----
    std::vector<int> wireStmt(const Stmt *s, const std::vector<int> &succ) {
        if (const auto *b = dynamic_cast<const BlockS *>(s)) {
            std::vector<int> cur = succ;
            for (auto it = b->ss.rbegin(); it != b->ss.rend(); ++it)
                cur = wireStmt(it->get(), cur);
            return cur;
        }
        if (const auto *x = dynamic_cast<const IfS *>(s)) {
            const int n = stmtId_[x];
            std::vector<int> targets = wireStmt(x->then.get(), succ);
            if (targets.empty()) targets = succ;
            if (x->els) {
                std::vector<int> e = wireStmt(x->els.get(), succ);
                if (e.empty()) e = succ;
                targets.insert(targets.end(), e.begin(), e.end());
            } else {
                targets.insert(targets.end(), succ.begin(), succ.end());
            }
            link(n, targets);
            return {n};
        }
        if (const auto *x = dynamic_cast<const WhileS *>(s)) {
            const int n = stmtId_[x];
            // 循环体执行完回到条件点；空体时条件点连一条自边（等于死循环）。
            std::vector<int> bodyEntries = wireStmt(x->body.get(), {n});
            if (bodyEntries.empty()) bodyEntries = {n};
            link(n, bodyEntries);
            link(n, succ);
            return {n};
        }
        const int n = stmtId_[s];
        link(n, succ);
        return {n};
    }

    void link(int from, const std::vector<int> &to) {
        for (int t : to) cur_->edges.emplace_back(from, t);
    }
};

const char *kindName(CfgNode::Kind kind) {
    switch (kind) {
        case CfgNode::Kind::Entry: return "entry";
        case CfgNode::Kind::Exit: return "exit";
        case CfgNode::Kind::Assign: return "assign";
        case CfgNode::Kind::Output: return "output";
        case CfgNode::Kind::Branch: return "branch";
        case CfgNode::Kind::Return: return "return";
    }
    return "?";
}

}  // namespace

Cfg buildCfg(const ProgramA &program) { return CfgBuilder(program).run(); }

std::string printCfg(const Cfg &cfg) {
    std::ostringstream out;
    for (const FunCfg &f : cfg.funs) {
        out << "== " << f.name << " ==\n";
        out << "nodes:\n";
        for (const auto &[id, node] : f.nodes) {
            out << "  " << id << ": " << kindName(node.kind);
            if (node.stmt) out << "  " << printStmtLine(*node.stmt);
            out << "\n";
        }
        out << "edges:\n";
        for (const auto &[a, b] : f.edges) out << "  " << a << " -> " << b << "\n";
    }
    return out.str();
}

}  // namespace tip
```

```cpp
// file: src/pretty.cpp
#include "pretty.hpp"

#include <string>

namespace tip {

namespace {

// 表达式打印为前缀式：运算符与符号的对照表。
std::string exprText(const Expr *e) {
    if (const auto *x = dynamic_cast<const IntLit *>(e)) return std::to_string(x->v);
    if (const auto *x = dynamic_cast<const VarRef *>(e)) return x->name;
    if (dynamic_cast<const InputE *>(e)) return "input";
    if (dynamic_cast<const NullE *>(e)) return "null";

    if (const auto *x = dynamic_cast<const Binop *>(e)) {
        const char *sym = "+";
        switch (x->op) {
            case BOp::Add: sym = "+"; break;
            case BOp::Sub: sym = "-"; break;
            case BOp::Mul: sym = "*"; break;
            case BOp::Div: sym = "/"; break;
            case BOp::Gt: sym = ">"; break;
            case BOp::Eq: sym = "=="; break;
        }
        return "(" + std::string(sym) + " " + exprText(x->l.get()) + " " +
               exprText(x->r.get()) + ")";
    }
    if (const auto *x = dynamic_cast<const CallE *>(e)) {
        std::string s = "(call " + exprText(x->callee.get());
        for (const auto &a : x->args) s += " " + exprText(a.get());
        return s + ")";
    }
    if (const auto *x = dynamic_cast<const Deref *>(e))
        return "(* " + exprText(x->e.get()) + ")";
    if (const auto *x = dynamic_cast<const AddrOf *>(e)) return "(& " + x->name + ")";
    if (const auto *x = dynamic_cast<const AllocE *>(e))
        return "(alloc " + exprText(x->e.get()) + ")";
    if (const auto *x = dynamic_cast<const FieldA *>(e))
        return "(. " + exprText(x->e.get()) + " " + x->field + ")";
    if (const auto *x = dynamic_cast<const RecLit *>(e)) {
        std::string s = "{";
        for (size_t i = 0; i < x->fields.size(); ++i) {
            if (i) s += ", ";
            s += x->fields[i].first + ": " + exprText(x->fields[i].second.get());
        }
        return s + "}";
    }
    return "<unknown expr>";
}

std::string indent(int level) { return std::string(static_cast<size_t>(level) * 2, ' '); }

// 语句打印带缩进，一条语句一行（块内多行）。
void stmtText(const Stmt *s, int level, std::string &out) {
    if (const auto *x = dynamic_cast<const AssignS *>(s)) {
        out += indent(level) + exprText(x->target.get()) + " = " +
               exprText(x->value.get()) + " ;\n";
        return;
    }
    if (const auto *x = dynamic_cast<const OutputS *>(s)) {
        out += indent(level) + "output " + exprText(x->e.get()) + " ;\n";
        return;
    }
    if (const auto *x = dynamic_cast<const ReturnS *>(s)) {
        out += indent(level) + "return " + exprText(x->e.get()) + " ;\n";
        return;
    }
    if (const auto *x = dynamic_cast<const IfS *>(s)) {
        out += indent(level) + "if (" + exprText(x->cond.get()) + ")\n";
        stmtText(x->then.get(), level + 1, out);
        if (x->els) {
            out += indent(level) + "else\n";
            stmtText(x->els.get(), level + 1, out);
        }
        return;
    }
    if (const auto *x = dynamic_cast<const WhileS *>(s)) {
        out += indent(level) + "while (" + exprText(x->cond.get()) + ")\n";
        stmtText(x->body.get(), level + 1, out);
        return;
    }
    if (const auto *x = dynamic_cast<const BlockS *>(s)) {
        out += indent(level) + "{\n";
        for (const auto &st : x->ss) stmtText(st.get(), level + 1, out);
        out += indent(level) + "}\n";
        return;
    }
    out += indent(level) + "<unknown stmt>\n";
}

}  // namespace

std::string printExpr(const Expr *e) { return exprText(e); }

std::string printProgram(const ProgramA &program) {
    std::string out;
    for (const auto &f : program.funs) {
        std::string paramList;
        for (size_t i = 0; i < f->params.size(); ++i) {
            if (i) paramList += ",";
            paramList += f->params[i];
        }
        out += f->name + "(" + paramList + ") {\n";
        if (!f->vars.empty()) {
            out += indent(1) + "var ";
            for (size_t i = 0; i < f->vars.size(); ++i) {
                if (i) out += ",";
                out += f->vars[i];
            }
            out += " ;\n";
        }
        // 函数体是 BlockS；打印其内部语句而不是再嵌一层花括号。
        const auto *body = dynamic_cast<const BlockS *>(f->body.get());
        for (const auto &st : body->ss) stmtText(st.get(), 1, out);
        stmtText(f->ret.get(), 1, out);
        out += "}\n";
    }
    return out;
}

// 单行形式：CFG 节点标签等"节点旁边写一句话"的场合使用。
std::string printStmtLine(const Stmt &stmt) {
    std::string out;
    stmtText(&stmt, 0, out);
    if (!out.empty() && out.back() == '\n') out.pop_back();
    return out;
}

}  // namespace tip
```
