# 第 19 章　记录、null 与类型分析的边界：类型系统总装

## 19.1 本章要解决的三个问题

第 16 章建立了类型的语言——具体构造子与新鲜变量；第 17 章建立了约束
生成——按程序结构把"谁该等于谁"逐一写下；第 18 章建立了 Robinson
合一——用代换求解这些等式，并证明了求解过程的终止性与（合一成功时的）
可靠性。三章合起来，类型分析的主体已经完整。但还有三个问题没有回答，
本章逐一处理，然后对整个类型分析做一次总装与审视。

**第一，null 怎么处理。** TIP 的 `null` 是一个没有形状的值：它不携带
任何整数，也不携带字段表，可它显然与指针有关——把 null 用在算术里
是错误，把它赋给一个指针变量却是再正常不过的用法。第 17 章收集约束
时刻意跳过了 null，因为它不适合任何普通等式；第 18 章的合一规则也没
有它的位置。本章必须补上这条规则，并论证补上之后可靠性仍然成立。

**第二，怎样把三段接成一个完整的分析器。** 前面三章分别演示了类型
构造、约束表、解。使用者真正想要的是：对一份 TIP 程序，直接看到
"每个表达式是什么类型、每个函数是什么类型"。这要求 collect、unify
与一个最后的整理步骤协同工作，并把输出固定成稳定、可读、可对账的
协议。这个整理步骤就是 normalize——深度展开所有嵌套别名。

**第三，这个类型分析做不到什么。** 类型分析是 spa 类型篇章的第一个
完整分析器，但它有两条明确的局限：它是**流不敏感**的——对变量的
全部使用点一视同仁，不区分"在赋值之前还是之后"；它是**无多态**的
——一个函数只有一个类型，多次调用不能各自获得不同的实例。这两条
不是实现疏忽，而是当前分析框架的原理性后果。理解局限的根源，比记住
局限的现象更重要：它精确地指出了后续篇章要引入什么机制。

本章末尾有一个"错误矩阵"：五个精心构造的错误程序，每个触发合一的
一条不同拒绝规则。它不是踩坑记录，而是类型系统**能力边界的形式化
展示**——正如物理学家用一组边界实验标定仪器的量程，我们用五个反例
标定类型系统"能接受什么、必须拒绝什么"。读者应当把注意力放在每条
诊断与合一规则的对应上，而不是背诵错误信息文本。

spa 的类型篇章（第 3 章）把类型分析组织为"类型语言 → 约束生成 →

### 19.1.3 本章不做的事

划清边界同样重要。本章不引入新的程序值或运行机制——全部价值在
分析侧；不实现多态或流敏感（这是后续篇章的任务，此处只追根源、
不给半成品）；不讨论类型系统的高级特性（参数化模块、子类型化的
完整理论、依赖类型）；不做漏洞查找式的工程分析。null 的讨论也限
在"形状相容性"内：空指针解引用的动态检测不在类型分析范围。

把"不做"写明有两个理由：防止读者误以为这些主题被本章覆盖、防止
本章代码在"顺便支持一下"的诱惑下膨胀。一个教学章节的质量，一半
取决于它克制住了什么。

## 19.2 null 的问题：一个没有形状的值

### 19.2.1 先看直觉：null 在程序里怎样出现

在 TIP 程序里，null 几乎只出现在指针上下文。考虑这样的用法：指针
变量 p 在程序开头没有指向任何对象，先赋 null，之后在某个分支里才
真正指向一个分配单元。这是一种常见的编程模式——用 null 表示"此刻
尚无值"。要让它通过类型检查，分析必须接受 `p = null;` 与
`p = alloc 1;` 同时合法，即 null 与 `ptr(int)` 相容。

反过来，null 不能被算术接受：`null + 1` 毫无意义；不能被 output
当作整数输出；不能充当函数；不能充当记录。也就是说，null 的类型
行为是**非对称**的：它宽宏地与一切指针相容，却严格地拒绝非指针。
这种非对称正是难点所在——它不是一个普通的类型构造子，不能简单地
写成 `null = ptr(int)`，因为指针指向的类型可以是任意的。

### 19.2.2 为什么不能给 null 一个"任意指针"的魔法类型

初学者最容易想到的方案是：给 null 一个特殊的内部类型，含义是
"任意指针"，在合一遇到它时总是成功。这个方案看起来简单，实则会
破坏可靠性。问题在于"总是成功"覆盖了太多情形：null 与 int 之间
也会成功（如果检查写得不够仔细），null 与函数类型之间也会成功，
类型系统等于开了一个不受约束的后门。

更隐蔽的问题是**信息丢失的方向**。若先合一 `null = ptr(α)` 成功、
把 α 原样保留，之后 α 可被别的约束确定为 int，一切正常；但若合一
顺序反过来，先有 `ptr(α) = null`，"总是成功"的魔法规则若把 α
也一并消解，后续对 α 的约束就失去了落点。可靠性论证要求每一条
合一条文在两种方向上给出完全相同的结果（合一必须是对称的），
魔法规则很难满足。

本书的处理是**把 null 做成一个真正的类型构造子 `TyNull`**，让它
参与普通的合一过程，并为它写三条明确的规则。规则少而精确，每条
都可论证；不搞特殊通道。

### 19.2.3 三条规则的形式化

约束收集时，每个 null 表达式 E 得到一条普通等式
`τ(E) = null`（null 是新构造子）。于是全部工作都落在合一阶段，
规则共三条，外加一条冲突：

> **规则 N1**：`null = null` 成功，不产生绑定。
>
> **规则 N2**：`null = ptr(T)` 成功，不绑定 T。
>
> **规则 N3**：`null = α`（α 是未绑定变量）成功，并把 α 绑定为
> null。
>
> **冲突 N4**：`null = int`、`null = (…)->…`、`null = {…}`
> 抛出类型不匹配。

逐条解释。N1 是恒等情形，两个 null 当然相容。N2 是核心：null 与
任意指针相容，且**指针指向什么完全不受影响**——T 被保留，之后可由
其他约束确定。注意 N2 不要求 T 也是某个特定形状，`ptr(α)` 与 null
同样成功。N3 处理 null 与变量的情形：为什么要把变量绑定为 null、
而不是绑定为指针？因为此刻没有任何指针结构可以绑定——等式只告诉
我们该变量"至少是 null 这一侧的东西"，把它绑成 null 是最保守、
信息量最大的选择；若之后另有约束 `α = ptr(int)`，则用 N2 的精神
处理 null 与指针（届时 `α` 已展开为 null，null 与 ptr 成功）。

N4 的必要性来自 12.2.1 的非对称性：null 只属于指针世界。诊断文本
给出 null 与冲突类型的对照，便于使用者定位。

### 19.2.4 规则在代码中的位置

这三条规则实现在 unify.cpp 的 doUnify 前部、变量分支之前。阅读代码
时注意三个细节：先把两侧经 applySubst 展开（变量别名必须先走穿，
否则 `α = null` 之后再来 `α = ptr(int)` 时看不到 null）；null 的
判定与"另一侧是什么"分开写——other 可能是 null、ptr、变量或其他
构造子，四种去向正好对应 N1–N4；N3 的绑定写进同一个替换表，因此
null 的信息与普通变量绑定走完全相同的路径，不需要额外存储。

为什么 null 分支放在变量分支之前？因为展开后若一侧是 null、另一侧
恰好也是未绑定变量，两条规则都适用；语义要求此时采用 N3（绑成
null），而不是普通变量绑定（那会把 null 绑给变量，方向相反——
虽然本例中等价，但在链式情形下信息量不同）。规则的书写次序是
经过推演的，不是排版随意。

### 19.2.5 用定型断言重新陈述

前面的规则以"等式"叙述，这是因为整个分析以合一实现。但类型论的
标准语言是**定型断言**（typing judgment），此处对照陈述一次，帮助
读过其他类型教材的读者建立桥梁。定型断言形如

    Γ ⊢ E : T

读作"在环境 Γ 下，表达式 E 具有类型 T"，Γ 记录名字到类型的映射。
null 的定型规则写成：

    ─────────────            Γ ⊢ E : ptr(T)
    Γ ⊢ null : null          ─────────────────
                           Γ ⊢ null ≈ E   （相容）

左规则说 null 字面值的类型就是 null 构造子；右规则不是定型规则
而是**相容关系**：null 与任何指针类型相容。注意这里出现了两个层次
——"表达式的类型是什么"与"两个类型是否相容"。本章实现把二者统一进
合一：相容即"合一会成功"。在不支持子类型的语言里，相容退化为
相等；null 是 TIP 中唯一使"相容"宽于"相等"的构造，因此它也可以被
理解为一种极其有限的、null <: ptr(T) 的**子类型关系**。本章不展开
子类型理论（那需要格上的偏序，第四篇的主题），只请读者记住：
N2 在数学结构上就是一条子类型规则，它将在第四篇以一般形式重现。

### 19.2.6 null 能抓住什么、抓不住什么

必须诚实地说明 null 规则的能力边界。它能抓住的是**静态形状错误**：
把 null（或指针）放进算术、把整数当指针，这些在收集或合一阶段
立刻失败。它抓不住的是**空指针解引用**：

    p = null;
    output *p;

这份程序能通过类型检查——p 的类型是 ptr(int)（null 与 ptr 相容，
N2），解引用约束完全成立；但具体运行时对空指针取内容，毫无意义，
TIP 的具体执行会以运行错误报告。为什么类型系统不拒绝它？因为拒绝
需要回答"p 在解引用处是否可能为 null"，而这依赖于**沿控制流追踪
p 的取值历史**——又是流敏感性。类型分析刻意不做这件事。

这一区分对实践至关重要：静态类型系统保证"形状正确"，不保证
"引用非空"。工业语言为此发明了多种补救：Java 的注解类型
（@Nullable）、Kotlin 的可空类型把 null 性提升进类型系统、Rust
干脆要求用 Option 显式标记。这些设计的共同精神是：**让"可能为空"
成为类型上可见的信息**。本章的简单 null 不携带这种信息，N3 中
"只能是 null 无法表达"的精度缺口（见 12.6.2）与此处同源。读者
日后学习这些机制时，会看到它们正是为了堵住本章指出的缺口。

### 19.2.7 与 C/Java 中 null 的比较

C 语言的空指针常量 0（及 NULL 宏）具有特殊的松散类型行为：它可以
出现在任何指针上下文，编译器隐式转换；历史上 C 还允许指针与整数
互相转换，留下大量隐患。TIP 吸取的教训是**严格分离**：null 只与
指针相容（N2），指针绝不与整数相容（12.9.1）。比较可以发现，
TIP 用很少的规则得到了明显更强的安全保证，代价是程序员失去了
"把地址当整数算"的自由——对教学语言这是划算的交换。

Java 的 null 类型更接近本章的形式化：null 是一个有自己类型（null
类型）的字面量，它与所有引用类型相容，与基本类型（int 等）不相容。
Java 虚拟机规范明确写出 null 类型没有名字、不能声明变量、其唯一
值就是 null——这与 TyNull 不对应任何运行时数据形状完全一致。
读者可把本节的三条规则与 JVM 规范的 null 类型条款互相印证，体会
"一个没有值的形状的类型"在不同系统中怎样被严格处理。

### 19.2.8 小步合一的一个完整轨迹

用最短的片段演示规则联动。对 `p = alloc 5; q = null;`（假设随后
`q = p`），约束与合一的次序为：

1. alloc 节点 t3：等式 t3 = ptr(t4)，绑定；
2. 赋值 p = alloc：t_p = ptr(t4)；
3. null 节点 t5：t5 = null，命中构造子规则（null 与 null）；
4. 赋值 q = null：t_q = null，命中 N3 的对称处理，t_q 绑为 null；
5. 赋值 q = p：t_q = t_p，展开 t_q 得 null、t_p 得 ptr(t4)，
   命中 N2，成功，**t4 不被绑定**；
6. 归一报告：p 为 ptr(int)（t4 经字面量约束为 int），q 为
   ptr(int)——注意 q 的内部解 null 在最后一条约束后经 N2 "提升"
   回指针，报告使用的最终结构来自 t_p。

这个轨迹暴露了一个实现细节：替换表中 t_q → null 的映射**并不会被
改写**为指针；归一得到 ptr(int) 是因为沿着 t_q = t_p 的别名链
（t_q 实际先被第 4 步绑成 null……此处要小心）。工程实现中的真实
次序是：第 4 步的赋值约束若 t_q 已绑定则直接对 null 做合一，
N2 成功且不产生新绑定；第 5 步若两变量都已绑定则是 null 与 ptr
的合一。代码能正确处理各种次序，恰恰因为 N1–N3 都**不依赖类型
变量的身份**、只依赖展开后的构造。建议读者在调试器中单步一次，
亲手看到 applySubst 如何把链条走穿——这比任何文字都更能说明
"代换"究竟是什么。

### 19.2.9 null 在函数与记录位置

补全两个边角位置的讨论。其一，函数可以返回 null：
`f() { return null; }`。返回类型变量与 null 经 N1 精神合一成功，
f 的最终类型是 `() -> null`。这看起来古怪（一个"只能返回 null"
的函数），但完全正确——若 f 只有这一条 return，其返回值确实恒为
null；若另有 return 一个 alloc，则两返回约束把返回变量同时连到
null 与 ptr(…)，N2 使二者相容，最终类型提升为指针。归一报告
函数类型时取指针结构（信息更宽的一侧），与 12.2.8 的轨迹同理。

其二，记录字段可以是 null：`{p: null}` 与 `{p: alloc 1}` 若经同一
变量合并，字段类型按 N2 提升为 ptr(int)；若该字段始终只有 null，
字段类型就是 null。记录合一只按字段名配对、不特殊处理 null——
N 规则在逐分量合一时自然生效，无需在 TyRec 里开洞。这体现了规则
的**正交性**：null 规则与复合结构规则互不感知，任意嵌套（记录里放
函数、函数返回记录、指针指向记录）都由规则组合处理，而组合数量
不爆炸——这是好的规则系统与补丁堆的区别所在。

还需指出一个 TIP 明确禁止、由规则自动拒绝的形状：null 不能被 alloc
——`alloc null` 本身合法（alloc 对子表达式无类型要求，产生
ptr(null)），但 `null.f` 会在记录形状检查处失败；把 null 当函数
调用（`null()`）在函数构造检查处失败。因此即使语法上写出这些
表达式，类型网没有它们的容身之处，拒绝规则与诊断无需特判——
全部走通用冲突分支。

## 19.3 分析总装：从程序到最终类型

### 19.3.1 三段流水线

本章把分析组织成严格的三段：

1. **collect（收集）**：遍历 AST，每个表达式首次出现时分配一个新鲜
   类型变量，按产生式生成等式；同时为每个声明（形参、var、函数名）
   建立类型。输出是 Collected：约束表、节点→变量映射、节点出现顺序、
   声明→类型映射。
2. **unify（求解）**：按约束表顺序逐条合一，信息累积进同一个替换表；
   任何一条失败，立即以 TypeError 抛出，分析报告类型错误。
3. **normalize（归一）**：对每个要报告的类型变量，沿替换展开，并
   递归重建结构内部，得到不含别名的最终类型。

三段的接口在前几章已经冻结，本章只做接线。一个值得强调的工程判断
是：约束的生成与求解**严格分离**。收集阶段不做任何代换、不判断
相容与否；求解阶段不回到 AST。这种分离让两部分可以各自论证
（生成的完备性、求解的可靠性），也让错误定位精确——失败一定发生
在某一条具体约束上。

### 19.3.2 为什么需要 normalize：解与解的表达

第 18 章的替换表已经是一个数学意义上的解。为什么打印时还要
normalize？考虑一个简单片段：`p = alloc 5;` 之后 p 的类型变量
被绑成 `ptr(τ₅)`，而 τ₅ 又被字面量约束绑成 int。替换表里存的是
两条映射：τ₂ → ptr(τ₅)、τ₅ → int。只做顶层 apply 得到 `ptr(t5)`，
这在数学上没有错，但对读报告的人不友好——他还要自己再展开一层
才看得到 `ptr(int)`。

normalize 做的事是**递归重建**：进入 ptr 内部，把分量也展开、重建。
它不改变解的信息，只改变解的表达。代码里 rebuild 函数逐构造处理：
int、未绑定变量原样返回；ptr 重建其指向类型；函数重建每个形参与
返回类型；记录重建每个字段。重建总是终止的——每次递归进入严格
更小的结构，且替换表的无环性（occurs 检查保证）排除了无限展开。

区分"解"与"解的表达"是一种重要的工程自觉：内部表示服务于算法
（替换表最便于合一写入），外部呈现服务于人（完全展开最便于阅读）；
二者之间用一个小而明确的转换连接。

### 19.3.3 --check 的输出协议

本章 --check 的输出分三块，格式固定，expected 文件逐字节对账：

- `types:` 之后，按表达式**首次出现的源码顺序**，每行
  `τ: <表达式前缀形式> : <最终类型>`。表达式用第 8 章的打印器
  （printExpr），类型用归一后的 show。
- `functions:` 之后，每个函数一行 `名字 : <函数类型>`，按程序中
  的声明顺序。
- 类型错误时不打印上述两块，只输出
  `type error: <诊断>` 一行，退出码 3。

为什么按首次出现顺序而不是约束顺序？因为读者拿着源程序核对时，
视线移动的顺序就是表达式被遍历的顺序；编号 τ 的大小恰好反映这一
顺序（新鲜变量在首次访问时分配）。这也解释了输出中编号可能不
连续（如 rec 程序里 t8 之后是 t10）——某些编号被函数类型或字段
占位的内部变量占用，它们不对应可报告的顶层表达式。

### 19.3.4 Collected 的四个字段各自承担什么

Collected 结构只有四个字段，但每个都承担明确职责，值得逐一讲清，
因为它们对应静态分析器的四类标准信息。

**cons（约束表）** 是求解器的唯一输入。它是一个有序表而非集合——
合一虽在数学上与顺序无关（主解唯一），但错误诊断的编号、信息
依赖约束处理次序，保持源码顺序让诊断可复现。每条约束携带 why
字符串：它不参与算法，却在教学与调试时回答"这条等式从哪条语法
规则来"。工业分析器中这类溯源信息（provenance）往往占代码量的
很大比例，因为诊断质量直接取决于它。

**node（节点→变量）** 让分析在第二次访问同一表达式时取回同一个
变量。为什么会第二次访问？约束生成在父节点处需要引用子节点的
类型（如加法需要两个子节点的 τ），而子节点在遍历时已分配过。
没有这张映射，要么重复分配（同一表达式出现两个类型，约束丢失），
要么把变量塞进 AST 节点（污染前端数据结构）。用独立映射保持
AST 与分析状态分离，是贯穿本书的设计原则。

**order（节点首次出现顺序）** 只为报告服务（12.3.3 已述）。它与
node 分离而不是在报告时遍历 AST，是因为遍历逻辑分散在 genExpr
的递归中，重走一遍 AST 得到的顺序虽相同却重复了遍历代码；在分配
时顺手记录一次，简单可靠。

**decl（声明→类型）** 服务于所有"使用名字"的表达式：变量引用、
取地址、调用。声明包括三类——函数形参、var 声明的局部变量、
函数名本身；它们的类型在收集开始前（两遍收集的第一阶段）就已
建立并登记，因此前向引用、函数间互相调用都能找到落点。

### 19.3.5 为什么类型对象用共享指针

Tp 是 shared_ptr&lt;Type&gt;。这是一个经过权衡的选择，原因有三：

其一，**同一个变量对象必须在多处共享身份**。τ(x) 这个类型变量在
声明处创建、在每个引用点被取出、在约束中反复出现；各处持有的
必须是同一个对象，否则"把 α 绑成 int"只有一处可见。值语义会
复制对象，绑定无法传播。

其二，类型表是**异构容器**：vector&lt;Con&gt;、map&lt;…, Tp&gt; 里要同时
放 int、ptr、函数、变量，基类指针是 C++ 里最直接的异构手段。

其三，生命周期由这些容器共同管理，shared_ptr 的引用计数省去手工
所有权分析。代价是少量开销与类型比较时必须走虚函数/typeid——
对教学规模可忽略。一个更微妙的点是：合一绑定信息**不存放在
TyVar 对象内部**（没有 mutable 字段），而存放在外部替换表。这样
同一个变量对象即便出现在十处，解也只有一份、在一张表里，
applySubst 单点查询；这与"对象可变"的方案相比，推理简单得多，
也避免了别名对象间状态不同步的经典错误。

### 19.3.6 新鲜变量计数器：为什么是进程全局的

TyVar 的编号来自一个进程全局静态计数器，从 1 递增。为什么不用
每个函数一个计数器、或每次分析一个计数器？因为编号的唯一性
范围必须覆盖**一份分析中同时存在的所有变量**——约束跨越函数
边界（调用把调用点变量与函数定义变量相连），编号一旦在不同
函数间重复，诊断文本就会混淆，人工对账不可能。

为什么不每次分析重置？进程内若连续分析多份程序（如测试循环），
重置会让程序 A 的约束与程序 B 的变量编号重合，调试信息互相污染。
全局单调递增保证任何两个现存变量编号不同，输出可追溯到具体
分析。这个选择的代价只是编号会"显得很大"——好处是简单且永不出错。
注意计数器是进程状态而非分析状态：它不影响分析结果（换个起始
编号，解不变），只影响呈现，因此不破坏纯度。

### 19.3.7 两遍收集：为什么顺序不能颠倒

collect 内部是两遍结构：第一阶段建立全部函数类型并登记形参、var、
函数符号；第二阶段才遍历函数体、生成表达式约束并连接 return。
为什么必须这样？

TIP 允许前向调用与函数互相调用：main 可以调用在它后面声明的 f，
f 又可以回调 main。若按"遇到一个函数就完整处理它"的单遍方式，
处理 main 的调用点时，f 的符号尚无类型，map 查找直接抛越界。
第一阶段先把所有函数的"骨架类型"（形参类型变量序列 → 返回变量）
建好并登记，函数体再怎么向前向后引用，名字都能解析到类型。

这是静态分析中常见的**先建声明、后填用法**模式，本质上是处理
（潜在的）循环依赖：函数间的调用图可能有环，不能按拓扑序逐个
完成。先让所有节点"存在"，再连边，环就不再是障碍。记录字段
名也做了类似处理——第一遍先遍历全程序收集所有字段名，第二遍
生成字段访问约束时才能给出"含全程序字段集"的占位记录。两处
处理同构，读者抓住"先让结构存在，再建立连接"这一条即可。

### 19.3.8 收集器的输入输出契约

用契约式语言把 collect 重述一次，便于测试：

前置条件：AST 非空；symtab 已完成（每个 VarRef 的绑定非空）。
后置条件之一：node 恰好覆盖程序中全部表达式节点，每个节点关联
恰好一个类型变量；order 含且仅含这些节点，无重复，顺序等于
深度优先遍历的首次访问序。后置条件之二：decl 覆盖全部形参、var、
函数名。后置条件之三：每条约束两侧均为可达类型对象，why 非空。
不变量：collect 不修改 AST、不修改符号表、不做合一。

把契约定到这个粒度，收集器就可以**脱离合一独立测试**：检查结构
性质（节点数、顺序、覆盖）即可发现大量错误，而不必构造"什么
程序该报什么类型"的行为测试。这是静态分析测试的一般经验：
算法各阶段的结构性质（每个输入有对应输出、无重复无遗漏）比端到端
行为便宜得多，且定位精确——order 错了查遍历，约束少了查规则分支。

### 19.3.9 为什么不在 AST 节点里缓存类型

一个自然的替代方案是在 Expr 基类加一个 mutable Tp typeCache 字段。
本书拒绝，理由有三：AST 属于前端，多个分析（类型、后面的数据流）
会各自需要不同的节点信息，缓存字段会使前端结构随分析数目膨胀；
可变缓存引入失效问题（重新分析时谁清空？）；独立映射使分析状态
随 Collected 一起生灭，无残留。**前端数据对分析只读，分析状态
独立存放**——这条边界在第八篇多分析并存时价值尤为明显。

## 19.4 主流程代码逐段讲解

main.cpp 是总装的全部实现，共百余行，下面按段落讲解。阅读时对照
第 19.13 节的完整文件。

**前端部分**与前几章相同：parseFile 完成词法、语法、AST 构建与名字
解析，语法错误退出码 2、语义错误退出码 3。类型分析严格建立在名字
绑定之上——VarRef 到 Symbol 的映射在收集时被直接消费。

**--check 分支**的逻辑是流水线的直译：先 collect；然后用一个空替换
表，try 块内逐条 unify。为什么把合一包在 try 里？因为 TypeError 是
异常，我们希望在**第一条不可满足的约束**处停止，并把该约束的诊断
直接作为报告——异常携带的信息（哪两个类型、以何种方式冲突）比一个
笼统的"类型错误"精确得多。捕获后输出一行、返回退出码 3。

**报告表达式类型**：遍历 collected.order（只有它保留了源码顺序；
node 映射不保证顺序）。每个节点的类型变量在 node 表中，归一后与
表达式文本一起打印。注意这里重新从变量构造出发做 normalize，而不
是缓存结果——报告逻辑只跑一次，简单直接，且 normalize 是纯函数，
无副作用。

**报告函数类型**：函数名到 Symbol 的映射在全局表里，decl 表给出其
类型；归一后打印。main 函数若无形参，其类型显示为 `() -> int`——
这正确反映了 TIP main 无参时的形状（它的输入来自动态的 input，
不是静态参数）。

退出码在类型错误时为 3，与第 10 章语义错误的层级一致：类型错误
是"程序虽有良构 AST 但不满足静态约束"，晚于语法、早于任何执行。

### 19.4.1 逐步跟踪一次 --check

把一次完整的 --check 运行拆成时间轴，便于对照代码阅读：

t0：读入源文件文本。t1：ANTLR 词法分析，非法字符在此报语法错误
（退出码 2）。t2：ANTLR 语法分析，按 TIP.g4 产生式建树，结构错误
（如缺少分号）同样退出码 2。t3：ast_build 把 ANTLR 的具体语法树
转成本书 AST（ast.hpp 的节点层次），并完成初步语义检查。t4：
symtab 构建作用域与符号表，VarRef 绑定到 Symbol；未声明名字、
重复声明等名字错误报退出码 3。

t5：collect 遍历 AST 产出 Collected（12.3 已详述内部）。t6：空
替换表上的合一循环；失败则打印诊断、退出码 3。t7：normalize
对 order 中每个节点及每个函数类型做深度展开。t8：按协议打印并以
0 退出。

把这条时间轴记住，后续章节的所有分析（第五篇起）都挂在 t5/t6
这两个槽位上——前端（t1–t4）与呈现（t7–t8）几乎不变，变化的是
"生成什么约束/方程、怎样求解"。这正是把前端做成"分析工作台"的
意义：一次投入，反复复用。

### 19.4.2 为什么收集阶段不抛类型错误

一个设计细节值得讲明：collect 永远不会因为"两个类型看起来矛盾"
而失败。哪怕程序第一行写 `x = 1`、第二行写 `x = alloc 2`，收集
都平静地把两条等式都写进约束表；冲突要到合一阶段才暴露。为什么
坚持这种分离？

因为"矛盾"在收集时刻往往还不是矛盾——彼时类型变量尚未求解，
`ptr(t4)` 与 int 是否冲突取决于 t4 与整个替换表的后续演化，提前
判断需要在收集器内部维护部分代换，等于把合一算法复制一份。把
"约束是什么"（语法问题）与"约束是否可满足"（求解问题）分开，
每个阶段只回答一个问题，是约束式分析的标准架构。第四篇的数据流
方程、第五篇的 IFDS 都遵循同一原则：先声明约束，再用通用机制
求解。

### 19.4.3 诊断信息是怎样构造出来的

TypeError 的 what() 文本在 unify.cpp 各冲突点构造，包含三种信息：
冲突的两个类型（show 结果）、冲突的类别（type mismatch / arity /
record shape / occurs check）、以及必要时的嵌套编号。这些信息在
抛出点都是现成的——doUnify 的参数就是两侧类型，规则本身知道
冲突类别，因此构造诊断不需要额外查询。

main.cpp 捕获后只加 `type error: ` 前缀。这一层次划分使诊断文本
的"内容正确性"可以随合一规则一起论证：每条冲突规则产生的文本
必然引用了真正冲突的双方。编号为何有时未展开（如 ptr(t4) 而非
ptr(int)）？因为抛出发生在求解中途，t4 尚未被后续约束确定；
这不是缺陷，而是诚实地反映了"分析在此刻知道什么"。要求诊断
总是完全展开，需要在错误时额外跑一次部分归一，得不偿失。

### 19.4.4 --emit-ir 与 --run 为何在本章保留

本章示例仍保留前几章的 --emit-ir 与 --run 两个分支，即使它们与类型
分析无关。这是有意的：每个 examples/NN 快照是一个**可独立使用的
完整工具**，读者在任意一章停下，都能同时拥有前端、执行台与截至该章
的分析能力。删去执行分支会让第 19 章快照无法亲手验证"类型良好的
程序确实能运行"——而这正是可靠性直觉的来源。

代价是快照间存在重复代码。本书接受这种重复：快照架构用磁盘空间
换取"每章自包含、章间演进可逐行 diff"。读 diff 是本书的重要学习
路径——打开 examples/11 与 examples/12 的 constraints.cpp 对照，
本章新增的 null/记录规则一目了然，比在单份不断变动的代码中翻阅
历史仁慈。工程上，共享库式组织（一份代码、特性开关）在真实产品中
更合适；教学上，演进快照的可观察性无可替代。

### 19.4.5 一个最小的手工分析流程

不使用工具，仅凭纸笔分析 TIP 程序的推荐流程固化如下，建议读者对
本章三个程序各做一次：

一、圈出所有表达式并编号（遍历顺序）。二、为每个形参/var/函数名
分配类型变量。三、对照 12.11.1/12.11.2 的规则逐条写等式。四、从
int 字面量开始消元：把 int 传播到所有相连变量，再把 ptr/函数/记录
结构按分量拆开。五、遇到矛盾立即记录（哪两个构造、经哪条规则）——
你已预测出诊断。六、无矛盾则把所有变量消元到底，写出每个函数的
类型。

熟练后这个流程对几十行的程序只需几分钟。它的价值不在结果（工具
瞬间给出），而在让你**内化规则的方向性**——手写过一遍约束的人，读
诊断时看到的是规则冲突，没写过的人看到的只是英文句子。

## 19.5 三个正常程序的报告解读

### 19.5.1 arith：函数类型怎样被推导出来

arith 程序的核心是 main 对 add1 的调用。对照输出逐段看：

表达式 `3 + 4 * 2` 被拆成三个报告：整个加法 t5 为 int，其右子树
乘法 t7 为 int，叶子 t6/t8/t9 各自 int。这是约束生成"先递归子树、
再写等式"的直接结果——子节点的变量编号小于父节点。

条件 `x > 10`（t11）报告 int：比较的操作数被约束为 int、结果也是
int（0/1）。两分支里 output 的值 t14、t15 都报告 int，output 语句
不产生值，因此不单独占行。

最值得看的是调用 `add1(x)`（t16）：调用约束把被调位置 t17 与
函数类型 `(t18) -> t16` 相连，而 t17 又是变量 add1 的使用——它
等于 add1 的声明类型。于是 add1 的类型 `(int) -> int` 与调用点
期望的形状合一：形参 t18 与实参 x（int）相容，返回 t16 与 add1
的返回表达式 t19 相容。输出末尾 functions 块给出最终结果：
`add1 : (int) -> int`。注意这一推导中**调用点与函数定义双向约束**
——这正是 12.8 要讨论的无多态局限的根源，先在此记住这个形状。

### 19.5.2 ptr：多层指针

ptr 程序包含三层结构：`alloc 5` 给出 `ptr(int)`（t4）；取地址
`&p` 给出 `ptr(ptr(int))`（t7）——p 自己的声明类型此时已被
alloc 一侧确定为 ptr(int)；于是 q 的类型 t8 是 ptr(ptr(int))。

经指针写入 `*p = 1` 的报告：目标 `*p`（t10）为 int——约束
`τ(p) = ptr(τ(*p))` 与 p 的 ptr(int) 合一时，内层 t10 被确定为
int；右值 t9 也是 int，赋值约束成立。

`return **q`（t14）展示连续解引用：q 是 ptr(ptr(int))，`*q`
（t15）得到 ptr(int)，`**q`（t14）得到 int。两层约束
`τ(q)=ptr(τ(*q))` 与 `τ(*q)=ptr(τ(**q))` 依次生效。读这段输出
可以验证一个一般事实：每多一层解引用，类型上就少一层 ptr——
类型结构精确跟踪了指针的层数，这正是强类型指针分析的价值。

### 19.5.3 rec：记录形状

rec 程序构造记录 `{x: 1, y: 2}`：t3 的类型是
`{x: int, y: int}`，两个字段分量 t4、t5 分别为 int。字段访问
r.x（t7）与 r.y（t10）都报告 int。

字段访问的约束生成值得回顾（第 17 章）：记录位置被要求等于一个
"含有该字段"的形状，其余字段以新鲜变量占位。对 r.x，约束中的
记录形如 `{x: t7, y: α}`；与 r 的真实类型 `{x: int, y: int}`
合一时，α 被确定为 int、t7 被确定为 int。r.y 的约束方向相反、
同理成立。两个字段访问因此都能成功，且共享同一个 r 的类型——
字段顺序在合一中不敏感（按名字查找），但字段数目必须一致：
若约束占位的字段集与实际记录字段集不同，立刻报 record shape，
12.9 的 bad-field 程序正是此情形。

### 19.5.4 arith 报告逐行对账

output.txt 第 3–19 行覆盖 arith 的每个表达式，下面给出每一行的
"约束来历"，读者据此可独立重建整张表。

t5（整个加法）：赋值右值约束把它与 x 相连；加法规则同时要求
t5=int 及两子节点 t6、t7 为 int。t6 为字面量 3，int。t7 为乘法，
其规则要求 t7=int 及 t8、t9 为 int。t8、t9 为字面量 4、2。
注意行序 5→6→7→8→9 是深度优先遍历：父先报告、再依次报告子树，
这是 genExpr"先 varOf 登记自身、再递归"的直接后果。

t10（赋值左值 x）：VarRef，等于 x 的声明类型。t11（比较）：
比较规则要求结果 int 且两侧 t12、t13 为 int。t12 是 x 的又一次
出现（条件里），编号与 t10 不同——**每次引用表达式是独立的 AST
节点、有独立 τ**，但它们都等于同一个声明类型，这是"共享变量"
机制生效的地方。t14、t15 是两分支 output 的操作数。

t16（调用）：调用规则的三相连——被调 t17 须为 `(t18) -> t16`；
t17 是 add1 的 VarRef，其声明类型在第一阶段已建；t18 是实参 x；
t19 起进入 add1 函数体（order 是全程序拼接的，main 之后紧接着
add1）：t19 是返回表达式加法、t20 是形参 n 的引用、t21 是字面量。
return 的连接约束把 add1 的返回变量与 t19 相连。最终 t17 这一行
直接报告 `(int) -> int`：函数名在调用点作为表达式出现时，其 τ
就是函数类型本身，归一后已完全展开——这一行常被误读为"add1
被当成了普通变量"，恰恰相反，它展示了**函数在 TIP 中是一等实体**，
函数名可以出现在表达式位置（第 3 章的一等函数语法正以此为基础，
届时函数类型还能经变量流动）。

### 19.5.5 ptr 报告逐行对账

第 25–37 行为 ptr 程序。t4 为 alloc：alloc 规则 t4 = ptr(t5)，
t5 是字面量 int。t6 是 p 的引用，t_p = ptr(int)。t7 是取地址：
AddrOf 规则 t7 = ptr(t_p)，故 ptr(ptr(int))。t8 是 q 的引用，
q 的声明类型经赋值约束等于 t7。

t9 是 `*p = 1` 的右值。t10 是解引用目标：Deref 规则
t_p = ptr(t10)，与 ptr(int) 合一得 t10=int。t11 是同语句里 p
的引用节点。t12/t13 对应 output 语句：`output *p` 的解引用 t12
与其中 p 的引用 t13。

t21–23 是 return `**q` 的三个节点：t15 是 `*q`（规则
t_q=ptr(t15)，得 ptr(int)），t14 是再解引用（规则
t15=ptr(t14)，得 int），t16 是 q 的引用。注意编号次序 t14 &lt;
t15 &lt; t16：外层表达式先登记、递归时子节点才登记。读多层指针
报告的诀窍就是"看 ptr 的层数"：t16 二层、t15 一层、t14 零层，
每进一层减一，与源码的解引用层数严格对应。若某行层数对不上，
几乎一定是约束规则写错——这种**层数不变量**是人工核对指针类型
最省力的工具。

### 19.5.6 rec 报告与"消失的 t9"

第 42–49 行为 rec。t3 记录字面量：RecLit 规则按字段逐对构造，
t3 = {x: t4, y: t5}，两个分量为 int。t6 是赋值处 r 的引用。
t7 是 r.x 字段访问，t8 是其中 r 的引用。t10 是 r.y——注意
**t9 消失了**。t9 没有消失，它是 r.x 约束生成的占位记录
`{x: t7, y: t9}` 中的内部变量：这个占位记录整体只出现在约束里、
不是 AST 节点，因此它的字段分量 t9 不进 order、不单独报告；它
经与 r 的真实类型合一被绑成 int。同理 r.y 的占位记录使用 t10
与 t12（也不报告）。

"消失的编号"因此有了精确解释：每个未出现在 types 块的编号都被
一个**不对应任何 AST 节点的内部结构**占用——函数类型的参数/返回
骨架（arith 的 t1–t4）、占位记录的字段（rec 的 t9、t12）。能从
输出编号的缺口反推出内部结构，说明对收集器的理解已经到位。第
47/49 行 r 的两次引用都报告完整记录类型，与 t6 相同：同一声明
类型在三个位置被共享、被报告，完全一致。

### 19.5.7 三个程序共同暴露的四个不变量

跨三个程序总结，以下不变量在每份报告中都成立，它们既可用于人工
核对，也可写进自动化检查：

**引用一致**：同一名字的所有引用行类型相同（x 的 t10/t12/t14、
p 的 t6/t11/t13、r 的 t6/t8/t11）。这是声明共享变量的直接后果，
任何一处不同即收集或合一有缺陷。

**层数守恒**（指针程序）：每经一层 deref 少一层 ptr，每经一层
alloc/& 多一层；报告中所有节点的层数可仅由源码位置预算。

**字段闭合**（记录程序）：记录类型的字段集合恰好等于其字面量
字段集合，全程序中字段名集合是有限已知的；占位变量不会泄漏进
最终报告。

**函数闭合**：functions 块恰好列出程序中全部函数；每个函数的类型
与其 return 表达式类型、与所有调用点的期望类型同时相容——双向
闭合，无单向残留。

这四个不变量合起来几乎穷尽了"类型报告应当满足的结构性质"。实践
中，把它们写成独立于 expected 对账的断言是值得的：expected 只能
抓整体漂移，不变量能在新增程序时持续守护，且失败信息直接指出
违反的是哪一条。这也是本书反复使用的手法——**对账文件守护具体
产物，不变量守护一类产物**。

## 19.6 正确性论证：含 null 的主解可靠

### 19.6.1 可靠性命题（加入 null 之后）

第 18 章论证了：合一成功时，替换表是约束集的一个解；并且在一个
简单的具体语义对应下，解出的类型不与实际值矛盾。加入 TyNull 后
命题形式不变，但必须补 null 一侧的论证：

> 对每条含 null 的合一规则，规则成功后（N1–N3），等式两侧在指针
> 世界的具体解释不矛盾；规则失败（N4）时，两侧在任何解释下都
> 不可能相容。

这是"可靠性"对新构造的标准扩展方式：不必重证全部结论，只需证明
新规则不破坏既有不变量。

### 19.6.2 三条规则为何不破坏可靠性

逐条核对。N1（null=null）：两个无形状值相等，任何解释下成立。
N2（null=ptr(T)）：具体语义中 null 是一个合法的指针值（"空指针"），
它属于指针值的集合；等式不约束 T，因此 T 承载的值信息毫无损失。
关键在于 N2 **只声称相容性、不声称等价**——它不表示 null 与某个
具体地址相同，只表示 null 可以出现在 ptr 类型的位置。这与具体
运行不矛盾：运行时一个 ptr(int) 变量确实可以持有空指针。

N3（null=α，绑 α 为 null）：绑定后 α 的解是 null，比"某个待定
指针"更精确（信息更少但确定）。可靠性要求 α 实际可能承载的值
都在其类型预测内——α 处若具体运行得到非空指针，会与 null 类型
矛盾吗？这里要诚实指出一个边界：本章的简单类型语言**无法区分
"只能是 null"与"可能是 null 也可能指向对象"**。N3 把 α 绑成
null 是在"无其他约束"时的保守选择；一旦另有 α = ptr(int) 约束，
按 N2 的展开处理，最终类型回到指针。因此实际程序中 N3 只在该
变量确实没有其他指针约束时生效，预测与运行不矛盾。这一讨论也
暴露了类型系统精度的边界——要表达"可空指针"这种更精细的
概念，需要格上的近似（第四篇）或带标签的联合类型。

N4 的可靠性即其反面：int、函数、记录的值空间与 null 没有交集，
拒绝是唯一正确的选择。

### 19.6.3 主解与规范形式

normalize 不改变可靠性，因为它只沿替换展开、按结构重建：重建出
的类型与原类型在"变量最终解到什么"上完全相同（可用结构归纳
逐构造证明，ptr/函数/记录各分量的等价由归纳假设给出）。因此
打印出的规范形式与内部替换表是同一个解，可靠性传递到读者看到
的文本。把内部解与呈现解的等价论证清楚，"输出正确"才有依据，
而不是凭印象认为打印器不会错。

### 19.6.4 完备性：程序类型良好时分析必定找到解

可靠性只保证"找到的解不错"，还需要另一半——**完备性**：若程序
在类型规则下确实有解，分析不会因为算法缺陷而找不到。对约束式
分析，完备性分解为两步：

生成的完备性（约束没有漏掉任何语法规则要求的关系）：可对表达式
结构归纳——每个产生式在 genExpr 中都有对应分支，分支生成的等式
与定型规则一一对应；语句同理。这要求 genExpr 与 TIP.g4 的产生式
保持同步，新增语法构造时两处必须同改（这也是第 16 章起文法快照
逐章演进的原因）。

求解的完备性（约束集有解时合一成功）：Robinson 定理的经典部分。
直觉是——变量绑定规则总能把一个变量"消去"（用右侧替换它，变量
数目严格减少）；其余规则把复合项分解为更小的子等式（ptr 进内层、
函数逐参数、记录逐字段）；两条路径都使某种良基度量下降，故若
所有分支都不冲突，算法在度量耗尽时给出完整代换。冲突被抛出，
当且仅当两个顶层构造（或参数数目、字段形状）不可调和——任何解
都无法同时满足两侧，失败是必然的而非策略选择。

把两半合起来：程序类型良好 ⇒ 约束集有解（定型推导给出一个解）
⇒ 合一成功并返回一个解；合一成功 ⇒ 返回的代换满足全部约束
⇒ 程序类型良好。**"有解"与"分析接受"恰好吻合**，这是一个分析器
能追求的最强理论保证。

### 19.6.5 主类型：为什么不需要"猜类型"

合一返回的解有一个更强的性质：它是**主解**（principal solution）
——任何其他解都能由它再实例化得到（直观上，主解最一般、信息
恰如其分，不多不少）。为什么这条性质重要？因为它意味着算法
**不需要搜索与猜测**：不存在"先假设 x 是 int 试试、不行再假设是
ptr"的回溯。主解唯一，任何求解次序都到达它。

对比一下：若类型系统允许多种相互排斥的局部假设且没有主解
（如带重载和隐式转换的语言），类型推断就必须回溯或做约束
优先级裁决，复杂度与可预测性都恶化。TIP 的类型规则之所以
适合教学，正在于其约束天然有主解。第 16 章"把答案推迟为
变量"的决定在此收获全部回报——变量不预设答案，主解自然浮现。

主解性质对多态讨论（12.8）也是关键铺垫：多态语言把主解的概念
从"一个类型"推广为"一个类型方案"，方案的各实例共享同一个
主方案。理解了单态主解，推广到 ∀α 只是量词化的一步。

### 19.6.6 与数值方程求解的类比

合一与中学的方程求解有深刻的结构相似，值得点出：等式 `x+1 =
y+2` 中，消去同类结构（两侧 +1/+2 对应项）、对分量分别建立
关系；变量被表达式替换类似代入消元法；occurs 检查对应"禁止
x = x+1 这种自指方程"（它在有限数中无解）。差别在于类型项是
符号构造而非数值量，没有减法或移项——只能"消去相同构造子"。

这个类比对学习后面的抽象解释有意外帮助：数据流方程的求解同样
是"从初值出发反复代入直到稳定"，只是代入的对象从有限项变成
格元素、等式变成单调函数。Robinson 合一可视为在**有限项的平凡
格**上的不动点计算——绑定序列在"所有变量都被确定"时稳定。
第 20 章会把"反复代入直到稳定"提炼为一般的不动点定理；读者
届时若觉得似曾相识，正是因为合一早已示范过这个形状。

### 19.6.7 把可靠性证明写成可核对的结构

证明在工程中常被略过，但本书主张把它写成**他人可逐行核对**的
结构，因为静态分析器的全部价值就建立在"不错报"上。下面给出一个
可直接照用的组织模板：

第一步，陈述**具体世界**：定义程序值的集合（TIP：整数、空指针、
由 alloc 产生的单元地址、函数闭包）以及"值 v 属于类型 T"的关系
——整数属于 int；地址 a 属于 ptr(T) 当且仅当 a 所指单元的内容
属于 T；函数闭包属于 (Ts)->T 当且仅当参数与返回按此对应；空指针
属于一切 ptr(T)（N2 的语义根据，也仅此而已——它不属于 int 等）。

第二步，陈述**归纳命题**：若 Γ 把每个名字映射到其实际值所属类型，
且 Γ ⊢ E : T，则 E 的求值结果属于 T。对语句陈述相应命题（赋值后
环境仍满足类型关系）。

第三步，**按语法规则逐案例归纳**：每个产生式对应一个案例，案例的
结论恰好使用该产生式生成的约束。算术案例依赖"子结果属于 int 且
整数运算结果是整数"；deref 案例依赖 ptr 类型关系的定义；null 案例
直接成立（空指针属于 ptr，由定义）。案例之间互不重叠，覆盖全部
语法——这要求案例表与 genExpr 的分支表相同，12.11.4 已强调。

第四步，处理**语句与循环**：while 不需要对循环次数归纳——命题只声称
"若条件求值为整数（它总是），则每次迭代后环境仍满足类型"，由
内嵌语句案例与顺序复合直接推出；无限循环不产生结果，命题 vacuously
成立。这展示了类型可靠性证明为何不需要处理具体数值——类型关系对
所有整数一视同仁。

第五步，**合一代入的可靠性**：证明每次写入 α := t 后，"α 的实际值
属于 t"成立（由等式约束，α 与 t 处在同一语法位置）；occurs 检查
保证 t 不含 α，命题不循环。所有写入的合取即最终命题。

这个模板最有价值的一点是：**每个案例都很短**，长的是案例表本身。
写完后核对的方法也简单——数 genExpr 分支数与案例数是否相等、
每条约束是否在某案例中被引用。若读者从未写过机器可核以外的证明，
这是最好的第一次练习：它不依赖灵感，只依赖纪律。

### 19.6.8 可靠性 vs 精确性的术语澄清

文献中 sound / precise / complete 三个词常被混用，此处钉清。
**可靠**（sound）：分析说"成立"的性质一定成立（不允许假阳性式的
错误断言；方向随问题表述）。**完备**（complete）：所有实际成立的
性质分析都能发现。**精确**（precise）：在可靠的分析中，结论尽可能
强——两个可靠分析，结论更具体者更精确（ptr(int) 比 ptr(?) 精确，
"x=3"比"x 是 int"精确）。

类型分析在"程序能否通过"这个问题上既可靠又完备（12.6.4）。但在
更细的问题上（"x 在第 7 行是什么"）它不精确——它给出整个作用域
一个答案，哪怕各点本可不同。精确性的损失换取成本下降，这正是
12.7 的主题。术语清楚之后，"让分析更敏感"的精确含义是：**在保持
可靠性的前提下，把结论从粗粒度提升到细粒度**——不是增加新性质，
而是让同一性质在更多程序点/上下文中被区分。

### 19.6.9 类型分析作为抽象解释的雏形

本节为第四篇埋下最后一根伏线。抽象解释（abstract interpretation）
的核心主张是：静态分析是对具体执行的**抽象**——具体值映射到抽象
元素，具体操作映射到抽象操作，可靠性由二者之间的映射保持。类型
分析恰好是这个主张最简单的实例：

具体一侧是运行值的集合；抽象一侧是类型项；映射关系就是 12.6.7
定义的"值属于类型"。具体操作（整数加法、取地址、函数调用）在
抽象一侧被提升为约束生成规则；执行路径在抽象一侧消失（流不敏感）
——这本身就是一种自觉的抽象选择。

用这个视角回看，合一求解相当于在抽象域上直接解方程；主解相当于
抽象域中"恰如其分"的不动点；null 规则相当于抽象映射中"空指针
映射到 ptr 家族"的条款。所有概念都对得上号，只是类型域太简单
（有限构造、无无限上升链），不需要格论的全套工具。

第四篇的工作因此可以理解为：**保留抽象解释的全部主张，把简单的
类型域换成一般的格**——格允许不精确但有用的元素（顶、并、区间），
允许不动点迭代，允许在精度与终止间显式权衡。届时读者会不断遇到
本章已经见过的结构（映射、提升、可靠性传递），差别只在抽象域的
丰富程度。能把类型分析读成抽象解释雏形的人，学习格论时将不会
觉得是在学新东西，而是给老朋友添置更大的工作台。

## 19.7 边界一：流不敏感

### 19.7.1 现象：合并点的矛盾

考虑这样的程序（spa 3.5 的典型例子）：

```
if (b) x = 1; else x = &y;
output x;
```

x 在一个分支得 int、另一分支得 ptr(int)。本章的类型分析会怎么
判？它没有"合并两个类型"的机制——x 的声明只有一个类型变量，
两次赋值各写一条等式：int = τ(x) 与 ptr(int) = τ(x)，合一在
第二条处直接失败，程序被判类型错误。

注意这在 TIP 的原始设计中确实被视为错误：TIP 要求每个变量类型
一致且流不敏感。但站在"分析精度"的角度，真正有意思的不是
"报错"本身，而是：**分析器无法回答"在 output 处，x 到底可能
是什么"**——它只能在"矛盾"与"拒绝程序"之间选择，不能给出
"x ∈ {int, ptr(int)}"这样一个有用的近似。

### 19.7.2 根源：类型语言里没有"近似"这一操作

为什么给不出近似？回看类型分析的机制：答案全部由**等式与合一**
产生，等式的语义是"两边严格相等"。类型语言中有 int、ptr、函数、
记录这些构造，却没有一个构造表示"若干类型之并"。要表达
{int, ptr(int)}，必须先在类型世界里引入新元素（联合、顶元素）、
并为它定义合一行为——那已经不再是类型系统，而是**格上的抽象
解释**。

更本质地说，流不敏感的根源是分析**不使用控制流信息**：τ(x) 在
整个函数里只有一个，读它的位置与赋值位置在约束中毫无区别。
第 11 章辛苦建立的 CFG，在类型分析里完全没被消费。这不是疏忽
——类型分析有意只在 AST 上工作以保持简单，但代价就是分不清
"此刻"与"彼时"。

### 19.7.4 三个精度等级的对照

把"流"这一维度的可能精度展开，有助于看清本章所处的位置：

**流不敏感**（本章）：忽略语句顺序与控制流，把全部约束一锅煮。
优点是代价最小——约束数与程序大小成正比、一次遍历、解全局唯一；
缺点是上面的矛盾程序无法分析，以及大量"先初始化后使用"的信息
被浪费。

**流敏感**（第六篇的经典数据流分析）：每个程序点为每个变量保存
一份信息，沿 CFG 传播，汇合点合并。它能精确回答"x 在此刻可能
是什么"；`x=1` 与 `x=&y` 在汇合点合并为 {int, ptr(int)}，继续
传播而非报错。代价是信息按点复制、需要不动点迭代。

**路径敏感**（第七篇）：更进一步，区分到达同一汇合点的不同路径
条件——它能表达"在 b 为真的分支后 x 必为 int"。这需要在信息中
携带路径条件（通常是谓词），代价显著上升。spa 用专门一章讨论
路径敏感性的收益与成本，本书第七篇跟进。

三级精度回答的是同一个问题（"此刻 x 是什么"），区别只在合并与
区分信息的粒度。一个成熟的工程判断是：**精度按需要选取**——类型
检查这种"形状"问题，流不敏感恰好够用且主解优美；常量传播、
指针分析等问题则必须升级。本书后续篇章就是按这一精度阶梯逐级
攀登，每一级都讲清"上一级在哪里失效、本级引入什么新机制"。

### 19.7.5 为什么类型分析"因祸得福"

值得玩味的是，流不敏感在类型分析上不只是妥协，也带来了流敏感
分析难以获得的好处：全局唯一主解（12.6.5）、无需迭代、约束可
任意重排（便于并行收集）、以及极强的可预测性。类型信息的特点
是——**形状在整个作用域内本就应当一致**：让 x 此刻是 int、彼时
是 ptr，即使能表达，通常也是程序坏味道而非有用信息。

因此"流不敏感"对类型分析是恰当的粒度，而非被迫的降级；同样的
粒度对符号执行或指针分析则不可接受。方法论上的教训是：不要抽象
地追求"越敏感越好"，而要先问**目标性质本身随不随控制点变化**。
spa 全书反复展示这种"性质决定框架"的思维方式，本章的两条边界
是最初的两个范例。

### 19.7.6 用一个真实程序感受误报

下面的程序在运行时毫无问题，却会被本章分析拒绝，它具体展示了
"流不敏感造成误报"意味着什么：

    main() {
      var x;
      x = 1;
      output x;
      x = alloc 2;
      output *x;
      return 0;
    }

两个 output 在运行时分别处理整数与指针，x 的两次使用各得其所。
分析只看到 τ(x) 同时被约束为 int 与 ptr(int)，拒绝。注意这个程序
与 12.7.1 的分支程序不同：那里类型在同一点汇合、语义上确实需要
近似才能描述；这里类型在**不同时间**各自独立、连汇合都没有，分析
仍然拒绝。这说明流不敏感的代价不仅是"合并不了"，还包括"无法
顺序地复用变量"——它把时间轴整个抹掉了。

第六篇的流敏感框架处理这个程序不费吹灰之力：每个程序点一份 τ，
x 的类型沿语句推进、被覆盖而非合并，两个 output 点各看到精确
类型。对照这同一程序在两种框架下的命运，比任何定义都更能说明
框架升级带来了什么。本书刻意在此给出这个"运行正确却被拒绝"的
程序：可靠性（reject 的必是冲突）与精确性（该接受的被拒绝）是
两件事，本章分析可靠但在此程序上不精确——术语澄清（12.6.8）由此
落地为可见的例子。

### 19.7.3 出路预告：格、并与 widening

第四篇将引入三个机制解决这个问题：**格**把"信息的多少"组织成
偏序（int 与 ptr 之并有一个确定的位置——更不精确但包含二者）；
**单调数据流框架**让信息沿 CFG 逐点传播、在汇合点做并；
**widening（加宽）** 保证迭代在无限上升的格上仍终止。届时同样
的程序，分析器不再报错，而会在 output 点给出一个（也许是顶
元素的）近似。本章的"被迫矛盾"正是引出这套机制的动机：先看清
等式世界的边界，才理解格世界的必要。

## 19.8 边界二：无多态

### 19.8.1 现象：一次调用约束所有调用

考虑一个想被复用的函数：

```
id(x) { return x; }
main() {
  var a, b;
  a = id(1);
  b = id(alloc 2);
  return a;
}
```

id 的类型只有一个类型变量给 x。第一次调用 id(1) 经调用约束把
x 定为 int；第二次 id(alloc 2) 又要求 x = ptr(int)。两条约束
在同一个变量上冲突，合一失败。一个在概念上无比自然——
"id 原样返回它收到的东西，对任何类型都成立"——的函数，
本章的分析无法接受。

### 19.8.2 根源：函数符号只有一个类型

根源与 12.7 平行但不同：函数名作为 Symbol 在全局作用域只绑定
一个类型（12.5.1 已看到调用点与定义共享变量）。分析里没有
"同一函数的每次调用各有一份类型"的概念——调用点虽然生成了
各自的实参变量，但这些变量全部连到**同一个**函数类型的形参上，
互相约束。

为什么不让函数在每次调用时"复制"一份类型？因为"何时复制、
复制哪些变量、复制后不同调用的结果如何区分"本身需要一套
机制：需要识别函数类型中哪些是可泛化的部分（不依赖调用点
环境的变量），把它们提升为**类型方案**（带量词的类型，如
∀α. α → α），并在每个调用点把方案**实例化**（用量词变量的
新副本替换）。这正是 ML 家族语言 let-多态的核心。本章框架
没有类型方案、没有量词、没有实例化步骤，因此无从谈起。

### 19.8.3 多态需要什么：方案与实例化

具体地，多态需要三处增补：其一，类型语言增加量词
（`∀α₁…αₙ. τ`），类型方案与普通类型分层；其二，在函数（或
let 绑定）处理点做**泛化**——把该点环境中未被约束的自由
变量收集为量词；其三，每个使用/调用点做实例化——新鲜变量
替换量词。泛化与实例化的次序、哪些变量可泛化（仅依赖环境
分析）有严格规则，错误的泛化会破坏可靠性（著名的 let/polymorphic
recursion 问题）。

本书不实现多态：TIP 的设计哲学是简单的单态类型，且 spa 的
分析主线在格与数据流，不在参数化类型。但读者应当认得这个
形状——日后读 Haskell/OCaml/Rust 的类型系统，类型方案与
实例化是第一课。此处点到为止。

### 19.8.4 一等函数使无多态问题更尖锐

回顾 TIP 把函数作为一等值：函数可以经参数传递、被变量持有。
在单态框架下，这使多态缺口比普通调用更显眼：

    apply(f, x) { return f(x); }

apply 的类型是 `( (t1) -> t2, t1 ) -> t2`——注意其内部结构
*看起来*已经像多态：t1、t2 是变量。若只调用一次，`apply(add1,
3)` 把 t1/t2 实例化为 int，结果完美；但第二次以不同类型调用，
同一对变量再次被约束，冲突照旧。换言之，**函数内部的类型变量
提供了多态的"形状"，唯独缺少"每次调用刷新一份"的实例化动作**。

这精确展示了多态机制的最小增量：类型语言不变，只需在调用点
把被调函数类型中的自由变量替换为新鲜副本。ML 的 value
restriction、Rust 的单态化（编译期为每个具体类型生成一份代码）
是同一思想的不同工程实现。本书在第 03 篇实现一等函数的具体
执行时会再次遇到 apply——它的运行毫无障碍（运行时类型被擦除、
值自由流动），障碍纯粹是静态分析精度的。对照"运行能过、检查
不过"的程序，最能体会静态分析的精度是一个独立于语言语义的
设计维度：同一份语言，可有各种精度的分析。

### 19.8.5 两条局限的共同结构

12.7 与 12.8 表面上是两个缺点，抽象一层看是**同一个缺陷的两次
出现**：分析对"同一个程序实体（变量、函数）在不同动态情形
（控制点、调用点）下的不同行为"只准备了**一份静态信息**。

流敏感给变量按控制点准备多份；上下文敏感（第七篇）给函数按
调用上下文准备多份。两条出路的机制也平行——都需要决定"分多少
份、份与份何时合并、如何保证终止"。spa 的精妙之处在于把这些
看似分散的问题统一进"近似 + 不动点"的框架：每份信息是格元素，
合并是并，终止由有限高度或加宽保证。读者从本章带走的最重要的
概念，或许就是这个"一份对多份"的视角——它是后面几乎所有进阶
分析（上下文、路径、对象敏感性）的总纲。

### 19.8.6 无多态误报的一个真实例子

与 12.7.6 平行，给出"运行正确、检查拒绝"的多态版本，使局限
可观察：

    main() { return twice(inc, 3); }
    twice(g, x) { return g(g(x)); }
    inc(n) { return n + 1; }

程序运行必然得到整数 5。分析中 twice 的类型是
`( (t1) -> t2, t1 ) -> t2`；两次调用 g 经同一个函数骨架相连，
本例内部类型恰好自洽（t1=t2=int 由 inc 与 x 推出），能通过。
但若同一 twice 还被 `twice(inc, alloc 1)` 调用，t1 立刻同时
被要求为 int 与 ptr——不是 twice 内部矛盾，而是**两份不同的使用
压在同一份骨架上**。

多态系统的解法前面已讲（方案 ∀αβ. (α→β, α) → β……严格说 twice
的类型是 ∀α. (α→α, α) → α，因为 g 的入参与 x、g 的返回共享 α），
每个调用点实例化一份，两调用互不相见。对照可见，多态不是给函数
"更聪明的类型"，而是给每次使用"独立的一份类型"——精度问题依旧
是 12.8.5 的"一份对多份"。本例也顺便演示了怎样从代码结构读出
∀ 约束：凡是函数类型中自由出现、且各出现之间由函数体内部连接的
变量（t1 出现在参数与返回），就是要量化的对象；量化分析（哪些
变量该绑在一起）本质上是一次小规模的依赖追踪。

## 19.9 错误矩阵：能力边界的形式化展示

五个错误程序各触发合一的一条规则。下面逐一对照：程序做了什么、
哪条约束失败、诊断文本怎样读出冲突双方。这组矩阵的价值在于
**完备地分隔了五类失败**：五个程序两两不触发同一条规则，因此
可用来检验一个类型系统的拒绝行为是否与设计一致——换一个实现，
五个诊断应一一对应。

### 19.9.1 binop-ptr：构造子冲突

程序把指针 p 直接加 1：`output p + 1`。约束生成要求加法两侧
均为 int，p 的类型（来自 alloc）是 ptr(int)。合一时两侧顶层
构造子不同——ptr 与 int——命中"构造子必须相同"的检查，
诊断为 `type mismatch: ptr(t4) vs int`。诊断里 t4 是 alloc
内层变量在求解那一刻尚未完全展开的编号（错误在约束顺序中
较早爆发），它准确指出了冲突的具体位置。这条矩阵标定：**类型
系统严格区分指针与整数**，不做 C 语言那种隐式指针运算。

### 19.9.2 deref-int：同一个检查的反方向

程序对整数 x 解引用：`output *x`。deref 的约束是
`τ(x) = ptr(τ(*x))`，而 x 是 int——冲突仍是构造子不同，
诊断方向反过来：`type mismatch: int vs ptr(t5)`。

把 12.9.1 与本则并排，验证了合一检查的**对称性**：无论等式
写成 ptr=int 还是 int=ptr，拒绝与诊断的对照关系一致（只是
左右次序随约束方向）。对称性是 12.6 可靠性的一部分，用两个
程序把它显式标定。

### 19.9.3 arity：函数类型的结构检查

程序以两个实参调用只收一个参数的 f。调用约束生成期望类型
`(t6, t7) -> t4`，f 的声明类型是 `(t2) -> t3`；两个函数
构造子相同，但**参数数目不同**，命中 arity 检查，诊断
`arity mismatch: (t2) -> t3 vs (t6, t7) -> t4`。

这条矩阵把"函数形状"的两层检查分开：构造子不同（拿 int
当函数调）走 type mismatch，构造子同但参数数目异走 arity。
TIP 不支持可变参数或默认参数，参数数目是函数身份的一部分。
诊断同时打印两侧完整函数形状，使用者可直接核对是多了还是
少了实参。

### 19.9.4 bad-field：记录形状检查

程序构造 `{x: 1}` 却访问 r.z。字段访问约束要求 r 等于含字段
z 的记录 `{x: t8, z: t6}`（字段名占位来自全程序收集的字段集）；
与实际 `{x: t4}` 合一时字段数目不同，命中 record shape 检查，
诊断 `record shape: {x: t4} vs {x: t8, z: t6}`。

若字段数目相同但名字不同（如 `{x:1}` 对 `{y:1}`），则走到
更深一层的 no field 检查。本矩阵标定的是**外层形状**：记录
类型严格按字段集合确定，访问不存在的字段绝不静默容忍。字段
是 TIP 唯一按名字而非位置匹配的结构，这条检查保证名字笔误
被静态捕获。

### 19.9.5 occurs：无环性检查

程序 `x = &x`：赋值约束把 τ(x) 与 `ptr(τ(x))` 相连。变量
分支在绑定前做 occurs 检查，发现 x 出现在 ptr(x) 内部，
命中检查，诊断
`occurs check: t2 occurs in ptr(t2)`。

这是五条规则中最"数学"的一条：程序未必立刻产生明显的语义
灾难，但接受它意味着类型需要一个无限类型 ptr(ptr(ptr(...)))，
且替换表将出现环、apply 永不终止。类型系统以 occurs 检查
守住"类型是有限项、替换无环"的底线。第 18 章的终止性证明
直接依赖它；本矩阵用最小程序把这条底线标定出来。

### 19.9.6 约束顺序的完整追踪

把五个程序在合一爆炸前经历的约束序列完整列出（编号为各程序
独立分析的真实编号，诊断已给出对应锚点）：

**binop-ptr**：alloc 先建立 t3=ptr(t4)；p 的声明类型经赋值等于
ptr(t4)；output 的操作数是加法，加法规则先写左子节点约束
t_left=int；左子节点是 p 的引用，其 τ = t_p = ptr(t4)；等式
int = ptr(t4) 在这一秒爆炸，t4 因尚未被任何 int 约束碰到而保持
变量形态——诊断正是 ptr(t4) vs int。这个轨迹说明诊断中编号的
"生"与"熟"由约束顺序决定，而约束顺序由 AST 遍历决定，全部可
预测。

**deref-int**：x 先经 `x=1` 得 int；解引用规则写
t_x = ptr(t_result)，即 int = ptr(t5)，爆炸。与上一程序的轨迹
对照可见，同一对构造子（int、ptr）只是交换左右，文本随之交换，
规则行为完全对称——对称性不是巧合，而是 doUnify 在变量情形用
"交换参数递归调用"统一了两个方向。

**arity**：f 的骨架类型在第一阶段建立为 `(t2) -> t3`；调用点
生成 t4 为调用结果、t6/t7 为两个实参、期望类型
`(t6,t7)->t4`；被调位置 t5（f 的引用）的 τ 等于 f 的骨架；
等式 `(t2)->t3 = (t6,t7)->t4` 先过构造子检查（同为函数），
随即在参数数目处爆炸。注意返回类型尚未比较就失败了——规则按
"先数目、后逐对"的次序工作，因为数目不同时逐对比较没有意义。

**bad-field**：字面量 `{x:1}` 建立 t3={x:t4}；r 的类型随之确定；
字段访问 z 时，占位记录按全程序字段集 {x,z} 构造为
`{x:t8, z:t6}`（分量编号取自该处新变量）；等式两侧记录构造子
相同，但字段数目 1≠2，在外层形状检查处爆炸，内部字段无需逐对。
若程序写成两个字段但名字不同，才会进入逐字段名查找、报"字段
缺失"——两层检查覆盖两种错误，互不混淆。

**occurs**：x 的声明变量 t2 在第一阶段建立；自指赋值约束直接
写 t2 = ptr(t2)；变量分支在准备绑定前先做 containsVar(t2,
ptr(t2))，递归进入 ptr 内层发现 t2 本身，爆炸。整个过程不产生
任何绑定——替换表保持空、无环，这是 occurs 先于绑定的意义：
宁可拒绝，也不让替换表被污染成需要回滚的状态。合一不做回滚，
因为它从不需要——所有破坏性写入都在确认安全之后。

### 19.9.7 矩阵总览

五类失败对应合一的五道防线，可用一张表归纳阅读：构造子冲突
（ptr vs int，含两个方向）、参数数目、记录形状、occurs。加上
12.2 的 null 冲突，合一所拒绝的全部情形在此被程序集穷举——
这正是"矩阵"一词的含义：不是错误信息的罗列，而是分析器判定
边界的系统采样。读这张矩阵的正确姿势，是合上文本、自己预测
每个程序的诊断，再与期望对照；预测全部正确，才算真正掌握了
合一规则。

还可以从矩阵反推一件事：**类型分析没有"可能对也可能错"的灰色
输出**——每个程序要么导出完整主解、要么在第一条矛盾约束处
确定地拒绝。这与第四篇"输出一个也许不精确的近似"形成鲜明对照：
类型世界里信息只有"完全确定"与"自相矛盾"两态，格世界里才有
中间地带。记住两种输出哲学的差异，是进入第四篇的思想准备。

### 19.9.8 诊断措辞的设计理由

五个诊断的措辞经过选择，理由值得讲明，因为读者将来要为自己的
分析写诊断。`type mismatch: A vs B` 用于构造子冲突——"mismatch"
是类型文献标准词，"A vs B"保持约束方向（左来自等式左侧），读者
可据方向回到具体规则分支。

`arity mismatch` 单独命名而非归入 type mismatch：参数数目错误的
修法（增减实参）与形状错误（改表达式）完全不同，独立类别使诊断
可被工具（及人）快速分流。`record shape` 同理——"shape"精确指示
是字段集合层面的冲突，区别于字段内层类型冲突（后者仍是 type
mismatch）。`occurs check` 保留算法术语：这类错误罕见且特殊，
看到它的程序员应当知道去查自指构造，术语本身就是线索。

一句话总结设计原则：**诊断类别对应修法类别，诊断内容引用冲突
双方，诊断方向反映约束方向**。本章只有五条诊断，正适合把原则
演练精熟；工业编译器的数百条诊断是同一原则的规模放大。

### 19.9.9 类型错误与动态错误的分界

矩阵里的五个程序有一个共同点：即使放行编译，它们也未必立刻
出事。`p + 1` 在具体执行里做的是指针所指向字节的整数运算；
`*x` 对整数解引用读到的是栈槽上的任意位型；`x = &x` 自指在
TIP 的语义表里根本没有对应动作。类型系统拒绝它们，拒绝的
依据不是"运行会崩溃"，而是**程序在类型层面自相矛盾**——
它要求的形状对不上它自己给出的形状。

这提醒我们分清两类静态保证。第一类是"拒绝矛盾"：类型分析
的工作方式。约束系统无解即报错，有解即对一切输入一致成立，
中间没有概率、没有"通常安全"。第二类是"近似追踪"：第四篇
开始的数据流分析的工作方式。它对每个程序点给出一个可能值
的抽象集合，值域越宽结论越弱，但只要抽象正确，结论对每一条
真实执行路径都成立。两类保证的哲学不同——一类求"结构自洽"，
一类求"路径覆盖"——工具形态也不同：前者输出二元判定，后者
输出逐点报告。

为什么本章选择在类型篇的末尾强调这一点？因为错误矩阵把
"拒绝"的机械性展示得最彻底：五个诊断全部由五条合一规则
确定地触发，没有任何一条依赖启发式或经验参数。读者由此
看到静态分析光谱的一端——完全精确、完全机械、但只覆盖
"类型可表达"的事实。第四篇将走到光谱另一端：领域可以
随意设计（符号、常量、区间、指针集合），精度可以用格与
加宽来调节，代价是每一步都要重新论证可靠。两端合起来，
才是"静态分析"一词的完整外延。

## 19.10 真实输出总览

本节把 expected/output.txt 的读法做最后交代，第 19.13 节嵌入的
文件即真实产物。每个程序以 `== 名字 ==` 开头，随后 types 与
functions 两块；三个程序共五十余行报告，全部可由源程序手工推导。
建议的核对路径：先在源程序上圈出每个表达式、按遍历顺序编号，
再逐行对照报告中的类型；遇到 ptr/rec 报告，回到 12.5 的讲解。
错误程序不进入 output.txt——它们的诊断分别存于
expected/errors/<名字>.txt，每个文件只有一行，与退出码 3 一起
对账。

产物跨机器一致的条件在此重申：诊断中的编号由遍历顺序决定、
不含路径或时间；表达式与类型的打印样式随版本固定。因此任何
环境下 run-all 的对账结果相同；版本升级导致的输出漂移会被
逐字节比较捕获，迫使我们重新核对。

### 19.10.1 输出协议为什么值得专门设计

初学者常觉得"打印点东西看看"不值一提，本节论证输出协议是分析器
的一等组成。首先，协议是**分析的可观察语义**：使用者（及测试）只能
通过输出知道分析说了什么，内部替换表再漂亮，输出含糊则分析等于
含糊。其次，协议决定诊断的**可行动性**——`ptr(t4) vs int` 让使用者
立刻知道"指针与整数冲突"，而"type error"毫无用处。

本章协议的三个设计原则可作为一般参考：**位置可定位**（表达式文本
与类型同行，读者不必在源文件与报告间跳转）、**信息可推理**（类型
完全归一，不留读者作业）、**文本可复现**（无环境信息，逐字节对账）。
工业分析器（诊断、LSP 的 hover/diagnostic、SARIF 报告）在更复杂的
尺度上追求同样三件事。学会在百行规模上严肃对待协议，日后面对
IDE 集成才不会把"能打印"误当成"设计完成"。

### 19.10.2 三层验证中本章的位置

本书对每个示例施行三层验证。第一层（产物逐字节对账）：本章 --check
对正常程序的输出与 output.txt 对账，错误程序的诊断与 errors/*.txt
对账，并核对退出码；这验证了实现与协议一致。第二层（可靠性的实证）：
第 24 章起，用 ORC 具体执行大量程序，检验静态预测与真实运行不矛盾；
类型分析本身虽可直接做实证（类型良好的程序应当能运行），本书把
实证统一安排在理论完备之后。第三层（与工业分析对照）：用 opt 调用
LLVM 中端，比较结论。

值得讲明三层各能抓什么错：对账层抓"实现漂移"（改代码无意改了
行为），实证层抓"模型错误"（规则本身不健全——单靠看代码极难发现，
因为错误程序往往能自圆其说），对照层抓"精度误判"（我的分析声称
比工业分析更精确时，是不是哪里弄错了）。任何单一一层都不足够：
全绿的对账可能建立在错误的模型上，完美的理论也可能被实现背叛。
三通道冗余是本书从大量实践中提炼的安全网。

### 19.10.3 错误程序的测试协议

正常程序的对账直观简单，错误程序的测试协议反而值得专门写明，因为
它有三个必须同时满足的条件，缺一不可：

其一，**进程退出码必须为 3**。仅检查输出文本不够——若实现错误地
把诊断打印到 stdout 却以 0 退出，调用方（构建系统、编辑器）会认为
程序合法；退出码是机器消费的信号，文本是人消费的解释。

其二，**stdout（或约定的诊断流）必须与 errors/&lt;name&gt;.txt 逐字节
相同**，包括单行无尾差异的规范（文件以一行文本存储，程序输出允许
结尾换行，比对时按 rstrip 后的协议行比较——这与 check_docs 的
rstrip 口径一致）。

其三，**该程序不得产生任何其他副作用**：不写文件、不进入执行阶段。
这通过构造保证——类型错误在前端分析路径上拦截，--run 同样先经过
检查（运行路径内部复用类型/语义检查），因此错误程序永远触不到
ORC。协议上的这一顺序（先检查、后执行）值得明确：它意味着
`tipa --run bad.tip` 也只会报类型错误、不会带病执行，杜绝了"检查
是检查、运行是运行"的双轨隐患。

三个条件可由一个参数化测试循环统一执行：对 programs/errors/*.tip
逐一套用。新增错误程序时只需添加 .tip 与 .txt 两个文件、无需改测试
代码——**新增案例零成本**是测试协议设计的目标，它直接决定矩阵将来
扩充的意愿。

## 19.11 类型规则全景：把四章压成一张演绎网

本节把第 16–19 章的全部规则集中重述一遍，但不是简单摘抄——目的
是让读者看到这些规则怎样构成一张**演绎网**：每个节点（一个类型
结论）都由确定的前提推出，整张网的边界就是类型系统的能力。

### 19.11.1 表达式规则（按语法构造）

字面量 int：τ(E) = int。没有前提，是网的源点。input：τ(E) =
int——输入流的形状被语言固定为整数，因此无需看输入本身，分析在
不知道具体输入的情况下给出类型；这是静态分析的第一个范例：
**结论不依赖具体输入，只依赖语言对输入的承诺**。

二元算术：两个子节点均 int，结果 int。三条等式（左=int、右=int、
父=int）由一次访问生成。比较：子节点 int，结果 int——TIP 没有
布尔类型，比较值就是 0/1 整数，这解释了为什么比较可以直接喂给
if 而算术结果也能做条件（语言层面二者不分）。

变量引用：τ(E) = 声明类型。声明类型是**共享变量**——这是全网唯一
"边连到别处既有节点"的规则，所有引用经它汇到同一个 τ。

调用：τ(被调) = (τ(实参₁),…) -> τ(E)。一条等式把四个角色（被调、
各实参、结果）缝在一起；它是网中信息密度最高的规则。

alloc：τ(E) = ptr(τ(子))。取地址：τ(E) = ptr(声明类型)。解引用：
τ(子) = ptr(τ(E))。注意解引用规则与 alloc 规则方向相反——alloc
由内向外造 ptr，deref 要求被解引用项已经"是"ptr。null：τ(E)=null。

记录字面量：τ(E) = {f₁: τ(E₁),…}，字段对一一对应。字段访问：
τ(记录) = {…, f: τ(E), …}，其余字段以变量占位——占位正是规则
"只约束该约束的、对其余保持沉默"的体现，与 N2 不绑定 T 同构。

### 19.11.2 语句规则

赋值：τ(目标) = τ(值)。output：τ(E) = int。if/while：τ(条件) =
int；子语句内部规则照常生效，语句本身不产生类型。return：
τ(E) = 所在函数的返回类型变量；连接约束在第二遍生成，因为函数
返回变量在第一阶段才存在。

语句规则的共同特征：它们不引入新值，只**检查**或**连接**。因此语句
"类型良好"的含义就是其各检查成立——这与表达式"产生一个类型"
形成层次区分，形式化时通常分别用 ⊢ E : T 与 ⊢ S ok 两种断言。

### 19.11.3 声明与共享规则

形参：每个形参一个共享变量，记入函数类型与 decl。var：每个变量
一个共享变量。函数名：其类型 = (形参类型…) -> 返回变量。三类
声明在第一阶段全部建成——声明规则的要点不是等式形状，而是
**共享范围**：形参变量的共享范围覆盖函数体与调用约束，var 变量
覆盖整个函数（流不敏感），函数类型覆盖全程序。把"谁与谁共享"
想清楚，规则就记住了一大半，不必背诵每条等式。

### 19.11.4 合一条文（求解规则）

变量-变量相同：成功。变量 α-项：occurs 检查通过后 α := 项。
构造-同构造：检查形状（ptr 无额外条件；函数查参数数目；记录查
字段数目），递归逐分量。null：N1–N4。冲突：类型不匹配/参数
数目/记录形状/occurs。这七条构成求解器全部行为，可直接与代码
的分支结构一一对照——这也是本章嵌入 unify.cpp 全部源码的原因：
规则与代码分支应当能逐行互证，任何一条"代码里有但上面没列"
的分支都值得警惕。

### 19.11.5 网的读法：从程序到解的两条路径

给定程序，在这张网上有两条等价的推理路径。**自底向上**（按 AST）：
从源点（字面量、声明）出发，沿规则向父节点推进，信息逐层累积，
直到所有节点被确定——这对应约束收集加上代入。**方程视角**（按
约束表）：把全部等式摊开，用消元（合一）求解——变量被逐个消去，
最后每个变量都有规范项。两条路径到达同一个主解，因为规则本就是
同一套约束的两种遍历次序。

教学上建议两种路径都亲手走一次：自底向上培养"类型感"（不需要
纸笔就能心算小程序的类型），方程视角培养"调试感"（当分析结果
意外时，知道去哪条约束上找原因）。第 20 章起，程序将大到无法
心算，方程视角与自动化求解成为主线——但此刻在小网上建立的直觉，
是理解大网的基础。

### 19.11.6 完整工作例：一张网上的 11 个变量

用 ptr 程序把"演绎网"具体化，列出其全部变量（含不报告的内部
变量）与连线，读者可在纸上复现：

- t1：main 的返回类型变量（骨架）；
- t2：add1？——ptr 程序无 add1，t2 实际是……按真实编号，函数
  main 的骨架为 `() -> t1`，占用 t1；t2、t3 为 main 的 var 变量
  （p、q 各一个）；t4 起为函数体节点。
- t4=ptr(t5)（alloc 规则）；t5=int（字面量）；t6=t2（p 引用连到
  声明）；赋值连 t2=t4；t7=ptr(t2)（取地址）；t8=t3（q 引用）；
  赋值连 t3=t7；t9=int；t10 经 deref 规则 t2=ptr(t10) 确定；
  t11=t2；t12 经 t2=ptr(t12)；t13=t2；t15 经 t3=ptr(t15)；
  t14 经 t15=ptr(t14)；t16=t3。

现在做消元：t5:=int；t4:=ptr(int)；t2:=ptr(int)；t6:=ptr(int)；
t7:=ptr(ptr(int))；t3:=ptr(ptr(int))；t8、t16 同；t10:=int；
t12:=int；t15:=ptr(int)；t14:=int；t1:=int（return 经具体执行
返回 int；return 语句连接 t1=t14）。对照第 12.5.5 的报告逐行
相同——这就是主解：不消元到底则看到 tN，消元到底则看到全 int/
ptr 结构，两种呈现一个解。

亲手消元一次，会发现三个算法性质无处可藏：每次消元严格减少一个
未决变量（终止）；消元顺序可换（t5 先于 t2 或反过来，终局相同）；
一旦某变量被绑成复合项（t4=ptr(t5)），后续对 t5 的消元自动借
t4 传播（信息共享）。这三条就是 Robinson 合一的全部秘密，纸笔
半小时胜过阅读万字描述。

### 19.11.7 规则出错时的现象学

反过来记录"规则若写错会怎样"，供调试时对号入座（这是原理性的
故障模式表，不是实现坑清单）：

漏写子约束（如加法忘记约束操作数 int）→ 漏报，错误程序被接受，
实证层（运行）会抓到：程序运行得到无意义结果或崩溃。
方向写反（deref 写成 τ(E)=ptr(τ(子))）→ 误报或漏报，正常程序
报 occurs/类型冲突，错误程序被放行；纸笔消元立刻暴露方向不一致。
共享变复制（声明类型每次新建变量）→ 所有引用脱钩，报告中同一
变量的多次出现类型各异，输出协议的"同声明一致"不变量被破坏。
occurs 缺失 → 无限循环或栈溢出，终止性失效，这是唯一会让分析器
挂死的规则错误。
null 规则过宽（N4 缺失）→ 漏报一切 null 误用；过窄（N2 缺失）→
正常指针程序大面积误报。五个错误程序加上三个正常程序构成双向
测试网：过宽与过窄分别被两侧捕获，这正是矩阵设计的方法论——
**反例标定拒绝边界，正例标定接受边界，缺一侧都可能把规则调反**。

## 19.12 与工业实践的对照

### 19.12.1 clang 怎样报同类错误

用 C/C++ 编译器对照本章的五个错误，是检验规则普适性的好方法。
`int x; *x;` 在 clang 下报 "indirection requires pointer operand
('int' invalid)"——与 deref-int 触发同一条构造子检查，差别只是
措辞与 clang 附带的源码片段、修复建议（fix-it）。`f(1,2)` 参数
过多报 "too many arguments to function call, expected 1, have 2"
——对应 arity，clang 的诊断直接给出数目差，这正是本章诊断文本
同时打印两侧函数形状所追求的信息。

结构体字段笔误在 C 中报 "no member named 'z'"——对应 bad-field
的内层字段名检查（本章程序在外层数目处就已失败）。对照可见
工业诊断与教学诊断的核心信息完全一致，工业优势在源码定位精度
（行列、下划线、跨模板实例化的实例化栈）与修复建议——这些是
工程量而非新原理。学完本章，读者应能读懂任何一门类 C 语言的
类型诊断，因为拒绝它们的规则就是上面这几条。

### 19.12.2 类型擦除：运行时为什么"感觉不到"类型

本章解出的类型在 LLVM IR 里几乎不留痕迹：整数与指针都是 SSA 值，
ptr 是不透明类型，函数调用按静态签名生成 call——**类型用于在生成
IR 前拒绝程序，而不随程序运行**。这叫类型擦除。它的后果值得
体会：`tipa --run` 与 `--check` 是两条独立路径，运行不重新检查，
检查不产生运行所需信息（除了签名）。

工业上的对照是 Java 的擦除泛型：`List<Integer>` 与 `List<String>`
运行时同为 List，多态信息只服务编译期。反过来，保留运行时类型
信息的系统（动态类型语言、带有 RTTI 的 C++）要为类型标签付空间
与间接代价。TIP 选择完全擦除，分析器是程序之外的观察者而非
程序的一部分——这一立场贯穿全书：静态分析是"在运行前用程序文本
（及对运行空间的数学模型）回答问题"的独立活动。

### 19.12.3 与 LLVM 中端分析的第一次接头

LLVM 自己的中端也做静态分析：SCCP（稀疏条件常量传播）在 IR 上
求常量与可达性的格上不动点；基本别名分析回答两个指针是否可能
指向同一对象。第 24 章起，本书将用自己的分析结果与这些工业分析
互相印证——例如对同一程序，本书的符号分析若判定某点符号为 +，
则 SCCP/常量传播的结果不应与之矛盾；若矛盾，必有一方建模错误。

接头此刻只需记住一个事实：LLVM 分析的输入（IR）比本书分析的输入
（TIP 源）层次更低，但求解的数学框架（格 + 单调函数 + 不动点）
完全相同。本书先在简单语言上把框架做透，再向下对照工业系统——
这比直接在百万行 IR 上学习理论仁慈得多，也符合"工作台"的整体
设计：ANTLR 端简化语言，LLVM 端提供真实尺度的参照物。

### 19.12.4 为什么生产分析器往往"宁漏不误"

本章类型检查采取"有疑必拒"——类型不明的程序不能运行。但很多
生产场景的静态分析（bug 查找、漏洞扫描）采取相反策略：**宁可
漏报（soundness 放松）也不误报**，因为误报淹没真实问题、使
工具被弃用。spa 开篇就讨论这一权衡，本书第 24 章以实验展示
"不健全的分析在什么程序上出错"。

类型检查之所以能"硬"，是因为它伴随语言设计：程序员接受规则、
类型错误有确定修法。独立分析工具没有这种契约地位，必须在精确
与噪音间走钢丝。读者日后设计分析时，第一个要决定的不是用什么
算法，而是**分析是否必须可靠（sound）、漏报与误报的代价各是
什么**——本章的主解世界给了"完全可靠"一端的范本，后面会见到
光谱的另一端。

### 19.12.5 精度—成本的一张总账

把本章涉及的各分析按成本排序，可得到一张随本书展开的总账：

类型分析（本章）：一次 AST 遍历收集 + 近线性代价的合一（实际
工程中几乎瞬时），全局单份信息；精度限于形状。
流敏感数据流（第六篇）：按程序点保存信息 + 不动点迭代，成本
约为点数 × 格操作；精度覆盖常量、符号、可达性等。
上下文/路径敏感（第七篇）：信息按上下文/路径复制，最坏情况
指数成本，工程上靠摘要与剪枝控制。
IFDS/指针分析（第八篇）：用图算法或约束求解处理跨过程与别名，
成本在多项式到不可判定之间分级。

这张账的方法论要点是：**每种精度的成本都有理论下界，不是工程
优化能抹平的**。例如上下文敏感的指数性来自路径组合，任何实现
都逃不过最坏情形；指针别名分析在一般情形下不可判定，所有工业
算法都是自觉的近似。因此选择分析框架时，正确的问题是"目标性质
需要哪一级精度、预算能承担到哪一级"，而非"哪个算法最快"。spa
的教学艺术在于先证明下界的存在，再给出实践中表现良好的近似——
本书后续各篇将逐栏填写这张账。

### 19.12.6 本章在全书中的枢纽地位

本章在 30 章中处于一个枢纽位置：向前，它收束前 12 章建立的全部
设施（ANTLR 前端、CFG、LLVM 执行台）；向后，它以两条局限启动
后续 18 章——第四篇的格与不动点、第五篇的经典数据流、第六、七篇
的精度升级、第八篇的跨过程与指针分析，每一篇都可视为在回应本章
指出的某个缺口。

因此建议读者在进入第四篇前重读一次 12.7–12.9：第一次读是学类型
系统，重读时带着"后续机制如何填这些缺口"的问题，体验会完全不同。
好的教程结构使同一段文字在不同阶段承载不同的信息密度，本章刻意
被设计成这样一个可回访的枢纽章。

// file: src/ast.hpp
// AST 定义：AST 是去掉了括号、分号等语法噪音的程序结构。
// 接口自本章起冻结，后续所有分析（名字、CFG、类型、格……）都在此之上工作。
#pragma once

#include <memory>
#include <string>
#include <utility>
#include <vector>

namespace tip {

enum class BOp { Add, Sub, Mul, Div, Gt, Eq };

struct Expr {
    virtual ~Expr() = default;
};
struct IntLit : Expr {
    int v;
    explicit IntLit(int value) : v(value) {}
};
struct VarRef : Expr {
    std::string name;
    explicit VarRef(std::string n) : name(std::move(n)) {}
};
struct InputE : Expr {};
struct Binop : Expr {
    BOp op;
    std::unique_ptr<Expr> l, r;
    Binop(BOp o, std::unique_ptr<Expr> lhs, std::unique_ptr<Expr> rhs)
        : op(o), l(std::move(lhs)), r(std::move(rhs)) {}
};
struct CallE : Expr {
    std::unique_ptr<Expr> callee;
    std::vector<std::unique_ptr<Expr>> args;
    CallE(std::unique_ptr<Expr> fn, std::vector<std::unique_ptr<Expr>> as)
        : callee(std::move(fn)), args(std::move(as)) {}
};
struct Deref : Expr {
    std::unique_ptr<Expr> e;
    explicit Deref(std::unique_ptr<Expr> p) : e(std::move(p)) {}
};
struct AddrOf : Expr {                       // spa: & Id
    std::string name;
    explicit AddrOf(std::string n) : name(std::move(n)) {}
};
struct AllocE : Expr {
    std::unique_ptr<Expr> e;
    explicit AllocE(std::unique_ptr<Expr> init) : e(std::move(init)) {}
};
struct NullE : Expr {};
struct RecLit : Expr {
    std::vector<std::pair<std::string, std::unique_ptr<Expr>>> fields;
    explicit RecLit(std::vector<std::pair<std::string, std::unique_ptr<Expr>>> fs)
        : fields(std::move(fs)) {}
};
struct FieldA : Expr {
    std::unique_ptr<Expr> e;
    std::string field;
    FieldA(std::unique_ptr<Expr> record, std::string f)
        : e(std::move(record)), field(std::move(f)) {}
};

struct Stmt {
    virtual ~Stmt() = default;
};
// target 只会是 VarRef / FieldA / Deref，文法 lvalue 已限定。
struct AssignS : Stmt {
    std::unique_ptr<Expr> target, value;
    AssignS(std::unique_ptr<Expr> t, std::unique_ptr<Expr> v)
        : target(std::move(t)), value(std::move(v)) {}
};
struct OutputS : Stmt {
    std::unique_ptr<Expr> e;
    explicit OutputS(std::unique_ptr<Expr> x) : e(std::move(x)) {}
};
struct IfS : Stmt {
    std::unique_ptr<Expr> cond;
    std::unique_ptr<Stmt> then, els;
    IfS(std::unique_ptr<Expr> c, std::unique_ptr<Stmt> t, std::unique_ptr<Stmt> e)
        : cond(std::move(c)), then(std::move(t)), els(std::move(e)) {}
};
struct WhileS : Stmt {
    std::unique_ptr<Expr> cond;
    std::unique_ptr<Stmt> body;
    WhileS(std::unique_ptr<Expr> c, std::unique_ptr<Stmt> b)
        : cond(std::move(c)), body(std::move(b)) {}
};
struct BlockS : Stmt {
    std::vector<std::unique_ptr<Stmt>> ss;
    explicit BlockS(std::vector<std::unique_ptr<Stmt>> v) : ss(std::move(v)) {}
};
struct ReturnS : Stmt {
    std::unique_ptr<Expr> e;
    explicit ReturnS(std::unique_ptr<Expr> x) : e(std::move(x)) {}
};

struct FunDecl {
    std::string name;
    std::vector<std::string> params;
    std::vector<std::string> vars;
    std::unique_ptr<Stmt> body;
    std::unique_ptr<ReturnS> ret;
};

struct ProgramA {
    std::vector<std::unique_ptr<FunDecl>> funs;
};

}  // namespace tip

// file: src/type.hpp
// 类型的表示：具体类型构造子 + 可合一的类型变量。
// 从本章起，分析不再直接"算出"答案，而是先搭类型结构、生成约束、
// 再由第 18 章的合一求解。类型对象以 shared_ptr 共享：同一个类型变量
// 会被约束的两侧、嵌套结构多处引用，不能用 unique_ptr。
#pragma once

#include <memory>
#include <string>
#include <vector>

namespace tip {

struct Type;
using Tp = std::shared_ptr<Type>;

struct Type {
    virtual std::string show() const = 0;
    virtual ~Type() = default;
};

struct TyInt : Type {
    std::string show() const override { return "int"; }
};

struct TyPtr : Type {
    Tp to;
    explicit TyPtr(Tp t) : to(std::move(t)) {}
    std::string show() const override { return "ptr(" + to->show() + ")"; }
};

struct TyFun : Type {
    std::vector<Tp> params;
    Tp ret;
    TyFun(std::vector<Tp> ps, Tp r) : params(std::move(ps)), ret(std::move(r)) {}
    std::string show() const override {
        std::string s = "(";
        for (size_t i = 0; i < params.size(); ++i) {
            if (i) s += ", ";
            s += params[i]->show();
        }
        s += ") -> " + ret->show();
        return s;
    }
};

struct TyRec : Type {
    std::vector<std::pair<std::string, Tp>> fields;
    explicit TyRec(std::vector<std::pair<std::string, Tp>> fs)
        : fields(std::move(fs)) {}
    std::string show() const override {
        std::string s = "{";
        for (size_t i = 0; i < fields.size(); ++i) {
            if (i) s += ", ";
            s += fields[i].first + ": " + fields[i].second->show();
        }
        return s + "}";
    }
};

struct TyNull : Type {
    std::string show() const override { return "null"; }
};

struct TyVar : Type {
    int id;
    explicit TyVar(int i) : id(i) {}
    std::string show() const override { return "t" + std::to_string(id); }
    // 新鲜变量编号：进程内单调递增，从 1 开始。
    static int fresh() {
        static int counter = 0;
        return ++counter;
    }
};

// 便利构造。
inline Tp tint() { return std::make_shared<TyInt>(); }
inline Tp tvar() { return std::make_shared<TyVar>(TyVar::fresh()); }

}  // namespace tip

#include "ast_build.hpp"

#include <utility>
#include <vector>

namespace tip {

std::unique_ptr<ProgramA> AstBuilder::build(TIPParser::ProgramContext *tree) {
    auto program = std::make_unique<ProgramA>();
    for (auto *fc : tree->function()) program->funs.push_back(buildFun(fc));
    return program;
}

std::unique_ptr<FunDecl> AstBuilder::buildFun(TIPParser::FunctionContext *ctx) {
    auto f = std::make_unique<FunDecl>();
    f->name = ctx->IDENT()->getText();
    if (ctx->params()) {
        for (auto *p : ctx->params()->IDENT()) f->params.push_back(p->getText());
    }
    if (ctx->varDecls()) {
        for (auto *v : ctx->varDecls()->IDENT()) f->vars.push_back(v->getText());
    }

    std::vector<std::unique_ptr<Stmt>> body;
    for (auto *sc : ctx->stmt()) body.push_back(buildStmt(sc));
    f->body = std::make_unique<BlockS>(std::move(body));

    f->ret = std::make_unique<ReturnS>(buildExpr(ctx->expr()));
    return f;
}

std::unique_ptr<Expr> AstBuilder::buildLvalue(TIPParser::LvalueContext *lv) {
    std::unique_ptr<Expr> base;
    std::string field;
    if (auto *d = dynamic_cast<TIPParser::DirectLvalueContext *>(lv)) {
        base = std::make_unique<VarRef>(d->IDENT(0)->getText());
        if (d->IDENT().size() == 2) field = d->IDENT(1)->getText();
    } else {
        auto *p = dynamic_cast<TIPParser::PointerLvalueContext *>(lv);
        base = std::make_unique<Deref>(buildExpr(p->expr()));
        if (p->IDENT()) field = p->IDENT()->getText();
    }
    if (!field.empty())
        return std::make_unique<FieldA>(std::move(base), std::move(field));
    return base;
}

std::unique_ptr<Expr> AstBuilder::buildExpr(TIPParser::ExprContext *ctx) {
    if (auto *c = dynamic_cast<TIPParser::IntExprContext *>(ctx))
        return std::make_unique<IntLit>(std::stoi(c->INT()->getText()));
    if (auto *c = dynamic_cast<TIPParser::VarExprContext *>(ctx))
        return std::make_unique<VarRef>(c->IDENT()->getText());
    if (dynamic_cast<TIPParser::InputExprContext *>(ctx))
        return std::make_unique<InputE>();
    if (dynamic_cast<TIPParser::NullExprContext *>(ctx))
        return std::make_unique<NullE>();
    if (auto *c = dynamic_cast<TIPParser::ParenExprContext *>(ctx))
        return buildExpr(c->expr());

    if (auto *c = dynamic_cast<TIPParser::AddExprContext *>(ctx)) {
        const BOp op = c->PLUS() ? BOp::Add : BOp::Sub;
        return std::make_unique<Binop>(op, buildExpr(c->expr(0)), buildExpr(c->expr(1)));
    }
    if (auto *c = dynamic_cast<TIPParser::MulExprContext *>(ctx)) {
        const BOp op = c->STAR() ? BOp::Mul : BOp::Div;
        return std::make_unique<Binop>(op, buildExpr(c->expr(0)), buildExpr(c->expr(1)));
    }
    if (auto *c = dynamic_cast<TIPParser::CmpExprContext *>(ctx)) {
        const BOp op = c->GT() ? BOp::Gt : BOp::Eq;
        return std::make_unique<Binop>(op, buildExpr(c->expr(0)), buildExpr(c->expr(1)));
    }
    if (auto *c = dynamic_cast<TIPParser::NegExprContext *>(ctx)) {
        // TIP 没有负数字面量 token，-E 即 0-E。
        return std::make_unique<Binop>(BOp::Sub, std::make_unique<IntLit>(0),
                                       buildExpr(c->expr()));
    }
    if (auto *c = dynamic_cast<TIPParser::CallExprContext *>(ctx)) {
        std::vector<std::unique_ptr<Expr>> args;
        if (c->args())
            for (auto *a : c->args()->expr()) args.push_back(buildExpr(a));
        return std::make_unique<CallE>(buildExpr(c->expr()), std::move(args));
    }
    if (auto *c = dynamic_cast<TIPParser::FieldExprContext *>(ctx))
        return std::make_unique<FieldA>(buildExpr(c->expr()), c->IDENT()->getText());
    if (auto *c = dynamic_cast<TIPParser::DerefExprContext *>(ctx))
        return std::make_unique<Deref>(buildExpr(c->expr()));
    if (auto *c = dynamic_cast<TIPParser::AddrExprContext *>(ctx))
        return std::make_unique<AddrOf>(c->IDENT()->getText());
    if (auto *c = dynamic_cast<TIPParser::AllocExprContext *>(ctx))
        return std::make_unique<AllocE>(buildExpr(c->expr()));
    if (auto *c = dynamic_cast<TIPParser::RecExprContext *>(ctx)) {
        std::vector<std::pair<std::string, std::unique_ptr<Expr>>> fields;
        for (auto *fc : c->field())
            fields.emplace_back(fc->IDENT()->getText(), buildExpr(fc->expr()));
        return std::make_unique<RecLit>(std::move(fields));
    }
    return nullptr;  // 解析成功时不会到达
}

std::unique_ptr<Stmt> AstBuilder::buildStmt(TIPParser::StmtContext *ctx) {
    if (auto *c = dynamic_cast<TIPParser::AssignStmtContext *>(ctx))
        return std::make_unique<AssignS>(buildLvalue(c->lvalue()), buildExpr(c->expr()));
    if (auto *c = dynamic_cast<TIPParser::OutputStmtContext *>(ctx))
        return std::make_unique<OutputS>(buildExpr(c->expr()));
    if (auto *c = dynamic_cast<TIPParser::IfStmtContext *>(ctx)) {
        std::unique_ptr<Stmt> els;
        if (c->stmt().size() == 2) els = buildStmt(c->stmt(1));
        return std::make_unique<IfS>(buildExpr(c->expr()), buildStmt(c->stmt(0)),
                                     std::move(els));
    }
    if (auto *c = dynamic_cast<TIPParser::WhileStmtContext *>(ctx))
        return std::make_unique<WhileS>(buildExpr(c->expr()), buildStmt(c->stmt()));
    if (auto *c = dynamic_cast<TIPParser::BlockStmtContext *>(ctx)) {
        std::vector<std::unique_ptr<Stmt>> ss;
        for (auto *sc : c->stmt()) ss.push_back(buildStmt(sc));
        return std::make_unique<BlockS>(std::move(ss));
    }
    return nullptr;  // 解析成功时不会到达
}

std::unique_ptr<ProgramA> buildAst(TIPParser::ProgramContext *tree) {
    return AstBuilder{}.build(tree);
}

}  // namespace tip

// file: src/constraints.cpp
#include "constraints.hpp"

#include <algorithm>
#include <utility>

namespace tip {
namespace {

struct Collector {
    const Bindings *bindings;
    Collected out;
    std::vector<std::string> allFields;

    Tp varOf(const Expr *e) {
        auto it = out.node.find(e);
        if (it != out.node.end()) return it->second;
        Tp t = tvar();
        out.node.emplace(e, t);
        out.order.push_back(e);
        return t;
    }

    void eq(Tp a, Tp b, std::string why) {
        out.cons.push_back(Con{std::move(a), std::move(b), std::move(why)});
    }

    void genExpr(const Expr *e) {
        Tp t = varOf(e);

        if (const auto *x = dynamic_cast<const IntLit *>(e)) {
            (void)x;
            eq(t, tint(), "整数字面量");
            return;
        }
        if (const auto *x = dynamic_cast<const VarRef *>(e)) {
            eq(t, out.decl.at(bindings->uses.at(x)), "变量使用");
            return;
        }
        if (dynamic_cast<const InputE *>(e)) {
            eq(t, tint(), "input 是整数");
            return;
        }
        if (dynamic_cast<const NullE *>(e)) {
            // null：合一时与任意 ptr 相容（包括 ptr 链上的变量）。
            eq(t, std::make_shared<TyNull>(), "null 与任意 ptr 相容");
            return;
        }

        if (const auto *x = dynamic_cast<const Binop *>(e)) {
            genExpr(x->l.get());
            genExpr(x->r.get());
            eq(varOf(x->l.get()), tint(), "二元运算左操作数为 int");
            eq(varOf(x->r.get()), tint(), "二元运算右操作数为 int");
            eq(t, tint(),
               x->op == BOp::Gt || x->op == BOp::Eq ? "比较结果为 int(0/1)" : "算术结果为 int");
            return;
        }

        if (const auto *x = dynamic_cast<const CallE *>(e)) {
            // 被调位置可以是任意表达式；参数按序生成。
            genExpr(x->callee.get());
            for (const auto &a : x->args) genExpr(a.get());
            std::vector<Tp> ps;
            for (const auto &a : x->args) ps.push_back(varOf(a.get()));
            Tp ft = std::make_shared<TyFun>(std::move(ps), t);
            eq(varOf(x->callee.get()), ft, "被调表达式须为接受这些实参、返回 τ 的函数");
            return;
        }

        if (const auto *x = dynamic_cast<const AllocE *>(e)) {
            genExpr(x->e.get());
            eq(t, std::make_shared<TyPtr>(varOf(x->e.get())), "alloc E 的类型是 ptr(τ(E))");
            return;
        }
        if (const auto *x = dynamic_cast<const Deref *>(e)) {
            genExpr(x->e.get());
            eq(varOf(x->e.get()), std::make_shared<TyPtr>(t), "对 *E：τ(E)=ptr(τ)");
            return;
        }
        if (const auto *x = dynamic_cast<const AddrOf *>(e)) {
            // &Id：在当前函数作用域（含全局父作用域）里找到该声明。
            const Symbol *s = nullptr;
            for (const auto &scope : bindings->scopes) {
                auto it = scope->table.find(x->name);
                if (it != scope->table.end()) { s = &it->second; break; }
            }
            if (!s) {
                auto it = bindings->global.table.find(x->name);
                if (it != bindings->global.table.end()) s = &it->second;
            }
            eq(t, std::make_shared<TyPtr>(out.decl.at(s)), "&Id 的类型是 ptr(声明类型)");
            return;
        }

        if (const auto *x = dynamic_cast<const RecLit *>(e)) {
            std::vector<std::pair<std::string, Tp>> fs;
            for (const auto &kv : x->fields) {
                genExpr(kv.second.get());
                fs.emplace_back(kv.first, varOf(kv.second.get()));
            }
            eq(t, std::make_shared<TyRec>(std::move(fs)), "记录构造的字段逐个对应");
            return;
        }
        if (const auto *x = dynamic_cast<const FieldA *>(e)) {
            genExpr(x->e.get());
            // spa：记录须含字段 f: τ；其余字段名以新鲜变量占位。
            std::vector<std::pair<std::string, Tp>> fs;
            for (const std::string &name : allFields) {
                if (name == x->field)
                    fs.emplace_back(name, t);
                else
                    fs.emplace_back(name, tvar());
            }
            eq(varOf(x->e.get()), std::make_shared<TyRec>(std::move(fs)),
               "字段访问：记录须含 " + x->field);
            return;
        }
    }

    void genStmt(const Stmt *s) {
        if (const auto *x = dynamic_cast<const AssignS *>(s)) {
            genExpr(x->value.get());
            genExpr(x->target.get());
            eq(varOf(x->target.get()), varOf(x->value.get()), "赋值左右类型相同");
            return;
        }
        if (const auto *x = dynamic_cast<const OutputS *>(s)) {
            genExpr(x->e.get());
            eq(varOf(x->e.get()), tint(), "output 的值是 int");
            return;
        }
        if (const auto *x = dynamic_cast<const IfS *>(s)) {
            genExpr(x->cond.get());
            eq(varOf(x->cond.get()), tint(), "if 条件是 int");
            genStmt(x->then.get());
            if (x->els) genStmt(x->els.get());
            return;
        }
        if (const auto *x = dynamic_cast<const WhileS *>(s)) {
            genExpr(x->cond.get());
            eq(varOf(x->cond.get()), tint(), "while 条件是 int");
            genStmt(x->body.get());
            return;
        }
        if (const auto *x = dynamic_cast<const BlockS *>(s)) {
            for (const auto &st : x->ss) genStmt(st.get());
            return;
        }
        if (const auto *x = dynamic_cast<const ReturnS *>(s)) {
            genExpr(x->e.get());  // return 表达式在函数级约束中连接
        }
    }
};

void gatherFields(const Expr *e, std::vector<std::string> &names) {
    if (const auto *x = dynamic_cast<const RecLit *>(e))
        for (const auto &kv : x->fields) {
            if (std::find(names.begin(), names.end(), kv.first) == names.end())
                names.push_back(kv.first);
            gatherFields(kv.second.get(), names);
        }
    if (const auto *x = dynamic_cast<const FieldA *>(e)) {
        if (std::find(names.begin(), names.end(), x->field) == names.end())
            names.push_back(x->field);
        gatherFields(x->e.get(), names);
    }
    if (const auto *x = dynamic_cast<const Binop *>(e)) {
        gatherFields(x->l.get(), names);
        gatherFields(x->r.get(), names);
    }
    if (const auto *x = dynamic_cast<const CallE *>(e)) {
        gatherFields(x->callee.get(), names);
        for (const auto &a : x->args) gatherFields(a.get(), names);
    }
    if (const auto *x = dynamic_cast<const AllocE *>(e)) gatherFields(x->e.get(), names);
    if (const auto *x = dynamic_cast<const Deref *>(e)) gatherFields(x->e.get(), names);
}

}  // namespace

Collected collect(const ProgramA &program, const Bindings &bindings) {
    Collector c;
    c.bindings = &bindings;

    // 第一遍：收集程序中出现过的全部字段名（字段访问的记录形状需要）。
    for (const auto &f : program.funs) {
        gatherFields(f->ret->e.get(), c.allFields);
        for (const auto &st : dynamic_cast<const BlockS *>(f->body.get())->ss) {
            // 语句内的字段收集
            const Stmt *s = st.get();
            if (const auto *a = dynamic_cast<const AssignS *>(s)) {
                gatherFields(a->target.get(), c.allFields);
                gatherFields(a->value.get(), c.allFields);
            } else if (const auto *a = dynamic_cast<const OutputS *>(s)) {
                gatherFields(a->e.get(), c.allFields);
            } else if (const auto *a = dynamic_cast<const IfS *>(s)) {
                gatherFields(a->cond.get(), c.allFields);
            } else if (const auto *a = dynamic_cast<const WhileS *>(s)) {
                gatherFields(a->cond.get(), c.allFields);
            }
        }
    }

    // 第二遍 A：为全部函数建类型（形参/var 新鲜变量）并登记函数名，
    // 这样函数体互相前向调用时被调函数的类型已在 decl 中。
    std::vector<Tp> funTypes;
    for (size_t i = 0; i < program.funs.size(); ++i) {
        const FunDecl *f = program.funs[i].get();
        std::vector<Tp> ps;
        for (size_t j = 0; j < f->params.size(); ++j) ps.push_back(tvar());
        Tp retVar = tvar();
        Tp ft = std::make_shared<TyFun>(ps, retVar);

        for (size_t j = 0; j < f->params.size(); ++j) {
            const Symbol *s = &bindings.scopes[i]->table.at(f->params[j]);
            c.out.decl[s] = ps[j];
        }
        for (const std::string &v : f->vars) {
            const Symbol *s = &bindings.scopes[i]->table.at(v);
            c.out.decl[s] = tvar();
        }
        for (const auto &kv : bindings.global.table)
            if (kv.second.kind == Symbol::Fun && kv.second.name == f->name)
                c.out.decl[&kv.second] = ft;
        funTypes.push_back(ft);
    }

    // 第二遍 B：按函数顺序走函数体与 return。
    for (size_t i = 0; i < program.funs.size(); ++i) {
        const FunDecl *f = program.funs[i].get();
        for (const auto &st : dynamic_cast<const BlockS *>(f->body.get())->ss)
            c.genStmt(st.get());

        c.genExpr(f->ret->e.get());
        const auto *ft = dynamic_cast<const TyFun *>(funTypes[i].get());
        c.eq(ft->ret, c.varOf(f->ret->e.get()), "return 表达式确定返回类型");
    }
    return c.out;
}

}  // namespace tip

// TIP 的 main 改名 tip_main：真正的 @main 是我们生成的 C 入口。
std::string emitName(const std::string &name) {
    return name == "main" ? "tip_main" : name;
}

void IRGen::gen(const ProgramA &program, const Bindings &resolved) {
    bindings = &resolved;

    // 先创建全部函数（含类型），函数体互相前向调用时也能查到声明。
    auto *i32 = Type::getInt32Ty(*ctx);
    for (const auto &f : program.funs) {
        std::vector<Type *> args(f->params.size(), i32);
        auto *ft = FunctionType::get(i32, args, false);
        Function::Create(ft, Function::ExternalLinkage,
                         emitName(f->name), *mod);
    }

    for (size_t i = 0; i < program.funs.size(); ++i) {
        const auto &f = program.funs[i];
        cur = f.get();
        genFun(f.get(), resolved.scopes[i].get());
    }

    const FunDecl *mainFun = nullptr;
    for (const auto &f : program.funs)
        if (f->name == "main") mainFun = f.get();
    if (!mainFun) throw std::runtime_error("program has no main");
    genWrapper(mainFun);
}

void IRGen::genFun(const FunDecl *f, Scope *scope) {
    auto *fn = llvm::cast<Function>(mod->getFunction(emitName(f->name)));
    auto *entry = BasicBlock::Create(*ctx, "entry", fn);
    b->SetInsertPoint(entry);

    // 形参：alloca 槽位 + 存入实参；var 局部：alloca + 零初始化。
    for (size_t j = 0; j < f->params.size(); ++j) {
        const Symbol *s = &scope->table.at(f->params[j]);
        auto *slot = b->CreateAlloca(b->getInt32Ty(), nullptr, f->params[j]);
        b->CreateStore(fn->getArg(j), slot);
        locals[s] = slot;
    }
    for (const std::string &v : f->vars) {
        const Symbol *s = &scope->table.at(v);
        auto *slot = b->CreateAlloca(b->getInt32Ty(), nullptr, v);
        b->CreateStore(b->getInt32(0), slot);
        locals[s] = slot;
    }

    stmt(f->body.get());
    b->CreateRet(expr(f->ret->e.get()));
}

Value *IRGen::expr(const Expr *e) {
    if (const auto *x = dynamic_cast<const IntLit *>(e))
        return ConstantInt::get(b->getInt32Ty(), x->v, true);

    if (const auto *x = dynamic_cast<const VarRef *>(e)) {
        const Symbol *s = bindings->uses.at(x);
        return b->CreateLoad(b->getInt32Ty(), locals.at(s), x->name);
    }

    if (dynamic_cast<const InputE *>(e))
        return b->CreateCall(rtInput_);

    if (const auto *x = dynamic_cast<const Binop *>(e)) {
        Value *l = expr(x->l.get());
        Value *r = expr(x->r.get());
        switch (x->op) {
            case BOp::Add: return b->CreateAdd(l, r);
            case BOp::Sub: return b->CreateSub(l, r);
            case BOp::Mul: return b->CreateMul(l, r);
            case BOp::Div: return b->CreateSDiv(l, r);
            case BOp::Gt: {
                Value *p = b->CreateICmpSGT(l, r);
                return b->CreateZExt(p, b->getInt32Ty());
            }
            case BOp::Eq: {
                Value *p = b->CreateICmpEQ(l, r);
                return b->CreateZExt(p, b->getInt32Ty());
            }
        }
    }

    if (const auto *x = dynamic_cast<const CallE *>(e)) {
        const auto *nameUse = dynamic_cast<const VarRef *>(x->callee.get());
        if (!nameUse)
            throw std::runtime_error("ch12: 间接调用留待第 41 章");
        const Symbol *s = bindings->uses.at(nameUse);
        if (s->kind != Symbol::Fun)
            throw std::runtime_error("ch12: 间接调用留待第 41 章");
        auto *callee = mod->getFunction(emitName(s->name));
        std::vector<Value *> args;
        for (const auto &a : x->args) args.push_back(expr(a.get()));
        return b->CreateCall(callee, args);
    }

    throw std::runtime_error("ch12: 指针与记录构造留待第 41 章");
}

void IRGen::stmt(const Stmt *s) {
    if (const auto *x = dynamic_cast<const AssignS *>(s)) {
        const auto *target = dynamic_cast<const VarRef *>(x->target.get());
        if (!target)
            throw std::runtime_error("ch12: 经指针/字段写入留待第 41 章");
        const Symbol *sym = bindings->uses.at(target);
        b->CreateStore(expr(x->value.get()), locals.at(sym));
        return;
    }

    if (const auto *x = dynamic_cast<const OutputS *>(s)) {
        b->CreateCall(rtOutput_, {expr(x->e.get())});
        return;
    }

    if (const auto *x = dynamic_cast<const IfS *>(s)) {
        Function *fn = b->GetInsertBlock()->getParent();
        auto *thenBB = BasicBlock::Create(*ctx, "then", fn);
        auto *elseBB = BasicBlock::Create(*ctx, "else", fn);
        auto *mergeBB = BasicBlock::Create(*ctx, "merge", fn);

        Value *cc = b->CreateICmpNE(expr(x->cond.get()), b->getInt32(0));
        b->CreateCondBr(cc, thenBB, elseBB);

        b->SetInsertPoint(thenBB);
        stmt(x->then.get());
        if (!b->GetInsertBlock()->getTerminator()) b->CreateBr(mergeBB);

        b->SetInsertPoint(elseBB);
        if (x->els) {
            stmt(x->els.get());
            if (!b->GetInsertBlock()->getTerminator()) b->CreateBr(mergeBB);
        } else {
            b->CreateBr(mergeBB);
        }
        b->SetInsertPoint(mergeBB);
        return;
    }

    if (const auto *x = dynamic_cast<const WhileS *>(s)) {
        Function *fn = b->GetInsertBlock()->getParent();
        auto *header = BasicBlock::Create(*ctx, "wh.cond", fn);
        auto *bodyBB = BasicBlock::Create(*ctx, "wh.body", fn);
        auto *exitBB = BasicBlock::Create(*ctx, "wh.exit", fn);

        b->CreateBr(header);
        b->SetInsertPoint(header);
        Value *cc = b->CreateICmpNE(expr(x->cond.get()), b->getInt32(0));
        b->CreateCondBr(cc, bodyBB, exitBB);

        b->SetInsertPoint(bodyBB);
        stmt(x->body.get());
        if (!b->GetInsertBlock()->getTerminator()) b->CreateBr(header);

        b->SetInsertPoint(exitBB);
        return;
    }

    if (const auto *x = dynamic_cast<const BlockS *>(s)) {
        for (const auto &st : x->ss) stmt(st.get());
        return;
    }

    if (const auto *x = dynamic_cast<const ReturnS *>(s))
        b->CreateRet(expr(x->e.get()));
}

void IRGen::genWrapper(const FunDecl *mainFun) {
    // C 入口：按 TIP main 形参数目读 input，再调用 tip_main。
    // 不命名为 main——MinGW 目标会向 main 注入对 CRT 符号 __main 的调用。
    auto *fn = Function::Create(FunctionType::get(b->getInt32Ty(), false),
                                Function::ExternalLinkage, "tip_entry", *mod);
    auto *entry = BasicBlock::Create(*ctx, "entry", fn);
    b->SetInsertPoint(entry);

    std::vector<Value *> args;
    for (size_t j = 0; j < mainFun->params.size(); ++j)
        args.push_back(b->CreateCall(rtInput_));
    Value *r = b->CreateCall(mod->getFunction("tip_main"), args);
    b->CreateRet(r);
}

bool IRGen::verify() const {
    std::string err;
    llvm::raw_string_ostream os(err);
    bool bad = llvm::verifyModule(*mod, &os);
    os.str();
    return !bad;
}

std::string IRGen::dump() const {
    std::string out;
    llvm::raw_string_ostream os(out);
    mod->print(os, nullptr);
    return os.str();
}

// JIT 模块通过这两个宿主函数与外界交换数据。
const std::vector<int> *inQueue = nullptr;
std::vector<int> *outQueue = nullptr;
size_t inPos = 0;

extern "C" int32_t tip_input() {
    if (inPos >= inQueue->size()) return 0;
    return (*inQueue)[inPos++];
}

extern "C" void tip_output(int32_t value) {
    outQueue->push_back(value);
}

void initNative() {
    // 进程内只初始化一次。
    static const bool ready = [] {
        llvm::InitializeNativeTarget();
        llvm::InitializeNativeTargetAsmPrinter();
        return true;
    }();
    (void)ready;
}

[[noreturn]] void fail(llvm::Error e) {
    std::string text = llvm::toString(std::move(e));
    throw std::runtime_error(text);
}

}  // namespace

std::vector<int> runJit(IRGen gen, const std::vector<int> &inputs) {
    initNative();
    std::vector<int> outputs;
    inQueue = &inputs;
    outQueue = &outputs;
    inPos = 0;

    auto jitOrErr = LLJITBuilder().create();
    if (!jitOrErr) fail(jitOrErr.takeError());
    auto jit = std::move(*jitOrErr);

    auto defineHost = [&](StringRef name, void *addr) {
        SymbolMap symbols;
        symbols[jit->mangleAndIntern(name)] = ExecutorSymbolDef(
            llvm::orc::ExecutorAddr::fromPtr(addr), JITSymbolFlags());
        if (llvm::Error e =
                jit->getMainJITDylib().define(absoluteSymbols(symbols)))
            fail(std::move(e));
    };
    defineHost("tip_input", reinterpret_cast<void *>(&tip_input));
    defineHost("tip_output", reinterpret_cast<void *>(&tip_output));

    ThreadSafeModule tsm(std::move(gen.mod), std::move(gen.ctx));
    if (llvm::Error e = jit->addIRModule(std::move(tsm)))
        fail(std::move(e));

    auto mainAddr = jit->lookup("tip_entry");
    if (!mainAddr) fail(mainAddr.takeError());
    auto *entry = jitTargetAddressToFunction<int (*)()>(mainAddr->getValue());
    entry();

    return outputs;
}

// 表达式打印为前缀式：运算符与符号的对照表。
std::string exprText(const Expr *e) {
    if (const auto *x = dynamic_cast<const IntLit *>(e)) return std::to_string(x->v);
    if (const auto *x = dynamic_cast<const VarRef *>(e)) return x->name;
    if (dynamic_cast<const InputE *>(e)) return "input";
    if (dynamic_cast<const NullE *>(e)) return "null";

    if (const auto *x = dynamic_cast<const Binop *>(e)) {
        const char *sym = "+";
        switch (x->op) {
            case BOp::Add: sym = "+"; break;
            case BOp::Sub: sym = "-"; break;
            case BOp::Mul: sym = "*"; break;
            case BOp::Div: sym = "/"; break;
            case BOp::Gt: sym = ">"; break;
            case BOp::Eq: sym = "=="; break;
        }
        return "(" + std::string(sym) + " " + exprText(x->l.get()) + " " +
               exprText(x->r.get()) + ")";
    }
    if (const auto *x = dynamic_cast<const CallE *>(e)) {
        std::string s = "(call " + exprText(x->callee.get());
        for (const auto &a : x->args) s += " " + exprText(a.get());
        return s + ")";
    }
    if (const auto *x = dynamic_cast<const Deref *>(e))
        return "(* " + exprText(x->e.get()) + ")";
    if (const auto *x = dynamic_cast<const AddrOf *>(e)) return "(& " + x->name + ")";
    if (const auto *x = dynamic_cast<const AllocE *>(e))
        return "(alloc " + exprText(x->e.get()) + ")";
    if (const auto *x = dynamic_cast<const FieldA *>(e))
        return "(. " + exprText(x->e.get()) + " " + x->field + ")";
    if (const auto *x = dynamic_cast<const RecLit *>(e)) {
        std::string s = "{";
        for (size_t i = 0; i < x->fields.size(); ++i) {
            if (i) s += ", ";
            s += x->fields[i].first + ": " + exprText(x->fields[i].second.get());
        }
        return s + "}";
    }
    return "<unknown expr>";
}

std::string indent(int level) { return std::string(static_cast<size_t>(level) * 2, ' '); }

// 语句打印带缩进，一条语句一行（块内多行）。
void stmtText(const Stmt *s, int level, std::string &out) {
    if (const auto *x = dynamic_cast<const AssignS *>(s)) {
        out += indent(level) + exprText(x->target.get()) + " = " +
               exprText(x->value.get()) + " ;\n";
        return;
    }
    if (const auto *x = dynamic_cast<const OutputS *>(s)) {
        out += indent(level) + "output " + exprText(x->e.get()) + " ;\n";
        return;
    }
    if (const auto *x = dynamic_cast<const ReturnS *>(s)) {
        out += indent(level) + "return " + exprText(x->e.get()) + " ;\n";
        return;
    }
    if (const auto *x = dynamic_cast<const IfS *>(s)) {
        out += indent(level) + "if (" + exprText(x->cond.get()) + ")\n";
        stmtText(x->then.get(), level + 1, out);
        if (x->els) {
            out += indent(level) + "else\n";
            stmtText(x->els.get(), level + 1, out);
        }
        return;
    }
    if (const auto *x = dynamic_cast<const WhileS *>(s)) {
        out += indent(level) + "while (" + exprText(x->cond.get()) + ")\n";
        stmtText(x->body.get(), level + 1, out);
        return;
    }
    if (const auto *x = dynamic_cast<const BlockS *>(s)) {
        out += indent(level) + "{\n";
        for (const auto &st : x->ss) stmtText(st.get(), level + 1, out);
        out += indent(level) + "}\n";
        return;
    }
    out += indent(level) + "<unknown stmt>\n";
}

}  // namespace

std::string printExpr(const Expr *e) { return exprText(e); }

std::string printProgram(const ProgramA &program) {
    std::string out;
    for (const auto &f : program.funs) {
        std::string paramList;
        for (size_t i = 0; i < f->params.size(); ++i) {
            if (i) paramList += ",";
            paramList += f->params[i];
        }
        out += f->name + "(" + paramList + ") {\n";
        if (!f->vars.empty()) {
            out += indent(1) + "var ";
            for (size_t i = 0; i < f->vars.size(); ++i) {
                if (i) out += ",";
                out += f->vars[i];
            }
            out += " ;\n";
        }
        // 函数体是 BlockS；打印其内部语句而不是再嵌一层花括号。
        const auto *body = dynamic_cast<const BlockS *>(f->body.get());
        for (const auto &st : body->ss) stmtText(st.get(), 1, out);
        stmtText(f->ret.get(), 1, out);
        out += "}\n";
    }
    return out;
}

// file: src/symtab.cpp
#include "symtab.hpp"

#include <utility>

namespace tip {

namespace {

// 解析器在遍历 AST 的同时完成绑定与诊断收集。
struct Resolver {
    Bindings bindings;
    Scope *current = nullptr;
    const FunDecl *owner = nullptr;

    void declare(const std::string &name, Symbol::Kind kind) {
        if (current->table.count(name)) {
            bindings.errors.push_back({"error: redeclared '" + name + "'"});
            return;  // 保留先声明者，后声明被忽略
        }
        current->table.emplace(name, Symbol{kind, name, owner});
    }

    void resolveExpr(const Expr *e) {
        if (const auto *x = dynamic_cast<const VarRef *>(e)) {
            const Symbol *s = current->lookup(x->name);
            if (!s) {
                bindings.errors.push_back({"error: undeclared '" + x->name + "'"});
            } else {
                bindings.uses[x] = s;
            }
            return;
        }
        if (const auto *x = dynamic_cast<const Binop *>(e)) {
            resolveExpr(x->l.get());
            resolveExpr(x->r.get());
            return;
        }
        if (const auto *x = dynamic_cast<const CallE *>(e)) {
            resolveExpr(x->callee.get());
            for (const auto &a : x->args) resolveExpr(a.get());
            return;
        }
        if (const auto *x = dynamic_cast<const Deref *>(e)) return resolveExpr(x->e.get());
        if (const auto *x = dynamic_cast<const AllocE *>(e)) return resolveExpr(x->e.get());
        if (const auto *x = dynamic_cast<const FieldA *>(e)) {
            resolveExpr(x->e.get());  // 字段名不是变量，无需解析
            return;
        }
        if (const auto *x = dynamic_cast<const RecLit *>(e)) {
            for (const auto &f : x->fields) resolveExpr(f.second.get());
            return;
        }
        // IntLit / InputE / AddrOf / NullE：无变量使用。
    }

    void resolveStmt(const Stmt *s) {
        if (const auto *x = dynamic_cast<const AssignS *>(s)) {
            resolveExpr(x->target.get());
            resolveExpr(x->value.get());
            return;
        }
        if (const auto *x = dynamic_cast<const OutputS *>(s)) return resolveExpr(x->e.get());
        if (const auto *x = dynamic_cast<const IfS *>(s)) {
            resolveExpr(x->cond.get());
            resolveStmt(x->then.get());
            if (x->els) resolveStmt(x->els.get());
            return;
        }
        if (const auto *x = dynamic_cast<const WhileS *>(s)) {
            resolveExpr(x->cond.get());
            resolveStmt(x->body.get());
            return;
        }
        if (const auto *x = dynamic_cast<const BlockS *>(s)) {
            for (const auto &st : x->ss) resolveStmt(st.get());
            return;
        }
        if (const auto *x = dynamic_cast<const ReturnS *>(s)) return resolveExpr(x->e.get());
    }
};

}  // namespace

const Symbol *Scope::lookup(const std::string &name) const {
    auto it = table.find(name);
    if (it != table.end()) return &it->second;
    return parent ? parent->lookup(name) : nullptr;
}

Bindings resolveNames(ProgramA &program) {
    Resolver resolver;
    resolver.bindings.global = Scope(nullptr);
    Scope *global = &resolver.bindings.global;

    // 第一遍：所有函数名进入全局作用域。
    for (const auto &f : program.funs) {
        if (global->table.count(f->name)) {
            resolver.bindings.errors.push_back({"error: redeclared '" + f->name + "'"});
            continue;
        }
        global->table.emplace(f->name, Symbol{Symbol::Fun, f->name, f.get()});
    }

    // 第二遍：每个函数开自己的作用域，父作用域是全局表；
    // 作用域所有权交给 Bindings，遍历结束后符号依然存活。
    for (const auto &f : program.funs) {
        auto functionScope = std::make_unique<Scope>(global);
        resolver.current = functionScope.get();
        resolver.owner = f.get();

        for (const std::string &p : f->params) resolver.declare(p, Symbol::Param);
        for (const std::string &v : f->vars) resolver.declare(v, Symbol::Local);

        resolver.resolveStmt(f->body.get());
        resolver.resolveStmt(f->ret.get());

        resolver.current = nullptr;
        resolver.bindings.scopes.push_back(std::move(functionScope));
    }
    return std::move(resolver.bindings);
}

}  // namespace tip

// file: src/unify.cpp
#include "unify.hpp"

#include <algorithm>

namespace tip {
namespace {

// 沿替换反复走到非变量。文件内统一用这个名字，避免与 std::apply 冲突。
Tp applySubst(const Subst &s, Tp t) {
    while (const auto *v = dynamic_cast<const TyVar *>(t.get())) {
        auto it = s.find(v->id);
        if (it == s.end()) break;
        t = it->second;
    }
    return t;
}

// occurs 检查：结构 t（先展开别名）中是否出现编号 id 的变量。
bool containsVar(const Subst &s, int id, Tp t) {
    t = applySubst(s, t);
    if (const auto *v = dynamic_cast<TyVar *>(t.get())) return v->id == id;
    if (const auto *p = dynamic_cast<TyPtr *>(t.get()))
        return containsVar(s, id, p->to);
    if (const auto *f = dynamic_cast<TyFun *>(t.get())) {
        for (const Tp &a : f->params)
            if (containsVar(s, id, a)) return true;
        return containsVar(s, id, f->ret);
    }
    if (const auto *r = dynamic_cast<TyRec *>(t.get()))
        for (const auto &kv : r->fields)
            if (containsVar(s, id, kv.second)) return true;
    return false;
}

void doUnify(Tp aa, Tp bb, Subst &s) {
    Tp a = applySubst(s, aa), b = applySubst(s, bb);
    auto *va = dynamic_cast<TyVar *>(a.get());
    auto *vb = dynamic_cast<TyVar *>(b.get());

    // 同一变量：恒等，成功。
    if (va && vb && va->id == vb->id) return;

    // null 的三条规则：null~null 成功；null~ptr 成功；null~变量绑定为 null；
    // null 与 int/fun/rec 冲突。
    const bool nullA = dynamic_cast<TyNull *>(a.get()) != nullptr;
    const bool nullB = dynamic_cast<TyNull *>(b.get()) != nullptr;
    if (nullA || nullB) {
        Tp other = nullA ? b : a;
        if (dynamic_cast<TyNull *>(other.get())) return;
        if (dynamic_cast<TyPtr *>(other.get())) return;
        if (auto *ov = dynamic_cast<TyVar *>(other.get())) {
            s[ov->id] = std::make_shared<TyNull>();
            return;
        }
        throw TypeError("type mismatch: null vs " + other->show());
    }

    if (va) {
        if (containsVar(s, va->id, b))
            throw TypeError("occurs check: t" + std::to_string(va->id) +
                            " occurs in " + b->show());
        s[va->id] = b;
        return;
    }
    if (vb) {
        // 交换参数，复用上面的变量绑定分支。
        doUnify(b, a, s);
        return;
    }

    // 两侧都是构造类型：构造子必须相同。
    if (typeid(*a) != typeid(*b))
        throw TypeError("type mismatch: " + a->show() + " vs " + b->show());

    if (const auto *p = dynamic_cast<TyPtr *>(a.get())) {
        doUnify(p->to, dynamic_cast<TyPtr *>(b.get())->to, s);
    } else if (const auto *f = dynamic_cast<TyFun *>(a.get())) {
        auto *g = dynamic_cast<TyFun *>(b.get());
        if (f->params.size() != g->params.size())
            throw TypeError("arity mismatch: " + a->show() + " vs " + b->show());
        for (size_t i = 0; i < f->params.size(); ++i)
            doUnify(f->params[i], g->params[i], s);
        doUnify(f->ret, g->ret, s);
    } else if (const auto *r = dynamic_cast<TyRec *>(a.get())) {
        auto *q = dynamic_cast<TyRec *>(b.get());
        if (r->fields.size() != q->fields.size())
            throw TypeError("record shape: " + a->show() + " vs " + b->show());
        for (const auto &kv : r->fields) {
            auto it = std::find_if(q->fields.begin(), q->fields.end(),
                                   [&](const auto &x) { return x.first == kv.first; });
            if (it == q->fields.end())
                throw TypeError("no field '" + kv.first + "' in " + q->show());
            doUnify(kv.second, it->second, s);
        }
    }
}

// 递归重建：结构内部每个分量先展开别名再重建。
Tp rebuild(const Subst &s, Tp t) {
    t = applySubst(s, t);
    if (dynamic_cast<TyInt *>(t.get()) || dynamic_cast<TyVar *>(t.get()))
        return t;
    if (const auto *p = dynamic_cast<TyPtr *>(t.get()))
        return std::make_shared<TyPtr>(rebuild(s, p->to));
    if (const auto *f = dynamic_cast<TyFun *>(t.get())) {
        std::vector<Tp> ps;
        for (const Tp &a : f->params) ps.push_back(rebuild(s, a));
        return std::make_shared<TyFun>(std::move(ps), rebuild(s, f->ret));
    }
    if (const auto *r = dynamic_cast<TyRec *>(t.get())) {
        std::vector<std::pair<std::string, Tp>> fs;
        for (const auto &kv : r->fields) fs.emplace_back(kv.first, rebuild(s, kv.second));
        return std::make_shared<TyRec>(std::move(fs));
    }
    return t;
}

}  // namespace

Tp apply(const Subst &s, Tp t) { return applySubst(s, t); }

Tp normalize(const Subst &s, Tp t) { return rebuild(s, t); }

void unify(Tp a, Tp b, Subst &s) { doUnify(a, b, s); }

}  // namespace tip

## 19.15 小结：类型分析收官，格的世界在望

本章为类型分析补上最后一块拼图：null 以三条规则与指针世界相容、

--check 按表达式与函数报告最终类型；含 null 的可靠性以"逐条

矩阵，标定了合一的五道防线。

回顾第三篇四章：类型变量把"答案"推迟为未知，约束生成按程序
结构写下等式，合一以代换求解、以 occurs 守终止，总装把解呈现
为人可读的形式。读者至此应当能回答三个层次的问题：类型分析
**怎样**工作（变量—约束—合一）、**为什么**其结果可信（解的存在
与可靠性论证）、**做不到什么、根源何在**（流不敏感因无近似、
无多态因无方案）。

同时，类型分析的两条边界精确指向了后续内容：要在控制流汇合处
合并矛盾信息，需要格与单调框架；要让分析沿 CFG 逐点传播，需要

——就从一个看似简单的问题开始：当答案不能一次性算出，怎样从

变化"的状态叫不动点；类型分析中合一隐式到达的终点，将被
提升为一套显式的、适用范围远更广的理论。

### 19.15.1 第三篇的概念地图

合上代码，第三篇只留下五个概念，它们按依赖次序排列：**类型项**
（第 16 章，描述答案的语言，构造子与变量并存）→ **类型变量**
（把未知答案合法化，使推断无需猜测）→ **约束**（第 17 章，按程序
结构写下的等式，生成与求解分离）→ **合一与代换**（第 18 章，消元
式求解，occurs 守终止、主解保证唯一）→ **总装与边界**（本章，
null 补全形状世界、归一呈现解、流不敏感与无多态标定局限）。

五个概念之上悬着一条总原理——**静态分析是在运行前、以程序文本为
输入、对程序行为的可靠近似**。类型分析的近似方式是"要么完全确定
形状、要么拒绝程序"；后面各篇逐步放宽近似的形式。若读者只能从
第三篇记住一句话，应是：**把答案变成变量、把规则变成等式、把求解
交给通用机制，并始终论证可靠性**。这个范式从类型到数据流、从单过
程到跨过程反复出现，是 spa 全书的骨架。

### 19.15.3 一段历史旁注

类型推断走向自动化的历史值得一句话回顾：Hindley–Milner 类型系统
在 1970 年代把"主类型 + 合一推断"定型，使程序员无需手写类型注解
而编译器仍能给出可靠结论；Robinson 早在 1965 年提出的合一本为
定理证明而发明，却在类型推断中找到最成功的应用之一。本书实现的
虽只是单态子集，但每一条规则（消元、occurs、主解）都来自这条
主线。理解工具的谱系，有助于判断哪些设计是本质、哪些是偶然——
本章规则的长久生命力，来自它们同时服务于逻辑与计算两个传统。

### 19.15.4 写给将动手实现的读者

最后给即将从零实现类型分析的读者三条操作建议，它们不是规则而是
次序安排：

先实现类型项与 show，用几个手写类型验证打印（第 16 章的做法）——
不要在还不能看见类型时就写合一。再实现收集器并**打印约束表**，
对照程序逐条人工核对，约束正确之前不要碰合一——大多数"合一 bug"
实为约束错误。最后实现合一，每加一条规则就用正常与错误两侧程序
检验（12.11.7 的双向原则）。

每一步都有可观察的中间产物（类型文本、约束文本、最终报告），每步
只引入一个新机制。按此次序，整个类型分析可在很少的调试痛苦下
完成；颠倒次序（先写合一、再猜约束）则会在"类型不对"的迷雾中
反复打转，因为三个机制的错误现象高度相似。分阶段让错误可定位，
这一工程纪律与全书的论证纪律一脉相承：**一次只处理一个问题，并
让处理结果可核对**。
