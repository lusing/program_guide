# 第 09 章　类型变量：把"未知"放进数据结构

## 9.1 第三篇要回答什么问题

前两篇完成了全部前置工作。第一篇回答了一个方法论问题：静态分析是
什么、为什么它对"全部可能运行"下结论的承诺既有意义又有不可逾越
的边界；第二篇把分析要操作的对象一步一步造了出来——字符流经
ANTLR 变成语法树，语法树经提炼变成抽象语法树，树上的名字使用点
经符号表绑定到声明，语句经控制流分析展开成图，最后整个程序经
LLVM 获得了一条可控制、可重复的具体执行通道。到上一章结束，
"程序是什么"这个问题已经被彻底回答：我们有它的五种表示，每一种
都精确、可复现、且彼此对账。

从本章开始，问题换了。我们不再追问程序的表示，而是追问程序里
**值的形状**。"形状"这个词需要先说清楚。考虑下面两个表达式在
运行时的差别：

```
3 + 4
alloc 5
```

第一个表达式的值是整数 7——一个数；第二个表达式的值是一个地址，
它指向另一个值 5。这两个值在运行时都是 32 位的比特串，在我们
第 08 章生成的 LLVM IR 里甚至都住在某种机器表示中；但它们能参与
的后续运算完全不同：对 7 可以做加法，对地址做加法在 TIP 的设计
里没有意义；反过来，只有地址能被解引用，对 7 写 `*7` 是荒谬的。
**类型**就是对值按"能做什么"所做的分类：整数是一类，指向某类值
的指针是另一类，函数、记录各自成类。类型分析的任务，是在不运行
程序的前提下，确定每个表达式的值属于哪一类。

读者或许会觉得这件事平凡：`3` 当然是整数，`alloc 5` 当然是指针，
逐个表达式看一遍不就知道了？本章的全部篇幅都在解释为什么这件事
**不平凡**，以及一种处理"不平凡"的标准数据结构。先把困难亮出来，
再介绍工具，工具就不再是需要背诵的清单，而是为解决一个具体问题
而生的自然选择。

### 9.1.1 一个具体的困惑：input 到底是什么

看第 03 章就熟悉的最小程序：

```
main() {
  output input;
  return 0;
}
```

`input` 的值在程序写就时根本不存在——它来自运行时的输入流，这次
运行是 5，下次运行是 -100，再下次可能是任何 32 位整数。那么
`input` 的类型是什么？奇怪之处在于：它的**值**千变万化，它的
**类型**却异常稳定——无论喂进来什么，都是整数。这里出现了第一个
重要的区分：**类型不依赖具体的值**。我们不需要知道 input 等于几
就能知道它是整数；类型信息是比值信息粗糙、但在值未知时仍然可得
的那一层知识。这正是静态分析的一般母题在类型问题上的具体表现：
放弃精确（具体是几），换取在运行前、对全部运行成立的结论（总是
整数）。

参数带来同样的困惑。

```
f(x) {
  return x + 1;
}
```

写 f 的时候，x 只是一个名字，没有值；我们甚至不知道调用者会传
整数还是指针进来——在没有类型规则的语言里，两种调用在语法上都
合法。要判断 `x + 1` 是否合理，必须先确定 x 的形状，而 x 的形状
要等到看见调用点才知道；可一个函数可能有几十个调用点，调用点
传入的东西本身又可能依赖别的参数……未知在程序里**传播**，无法靠
"盯着一个表达式看"来消除。

### 9.1.2 "形状"与"值"的分层

把上面两个例子一般化，可以得到类型分析赖以成立的分层世界观。
一个程序在运行时发生的事情是：每个表达式在每次到达它时产生一个
具体值，值的空间是无穷的（数学整数、各种地址组合）。类型分析在
值的空间之上铺一层有限的"形状空间"：所有具体整数被归为同一形状
`int`；所有指向某形状值的地址被归为形状 `ptr(τ)`；函数按参数与
返回值的形状归类；记录按字段的形状归类。无穷多个具体值坍缩为
有限（本书中就是五个构造子组合出的）形状。

这一分层与第 02 章对"可靠分析"的定义严丝合缝：分析给每个表达
式一个形状断言，断言声称的是"无论程序怎么运行，到达该表达式时
产生的具体值，其形状都属于被断言的类"。判定具体值属于什么形状
是运行时的、确定的；由程序文本在运行前推断形状，则是分析要做
的事。类型分析是本书第一个完整的"具体—抽象"对应实例：下一层是
具体值，上一层是类型项，中间靠"值到形状的归类"连接。第 13 章
讲格（lattice）时会看到，这种分层可以被进一步抽象和形式化；
本章先把类型这一具体的抽象层亲手建起来。

还要先点明类型分析与第 08 章执行台的关系。执行台在第三篇暂时退
居幕后，但它保证了一件事：我们的语言有确定的具体语义，每个程序
在给定输入下的具体值是唯一确定、可被观察的。因此类型断言原则上
**可以被反例证伪**——若某次真实运行中一个声称是整数的表达式竟
产生了地址（在我们的实现里这不会发生，因为 IR 的类型系统也在把
关），断言就是错的。类型分析不是凭空的符号游戏，它的每一个结论
都对应着第 08 章可执行程序的具体行为。

### 9.1.3 哪些运行时灾难对应哪一层防御

把 TIP 程序可能出现的运行时异常与防御层次列出，读者就能定位类型
分析在整个质量体系中的职责边界。算术类异常（除零、整数溢出）属于
值层面，类型层不防，需常量传播或区间分析（第 20 章之后）；形状类
异常（解引用非指针、对非函数发起调用、实参个数不符、访问缺失字段）
正是类型层的目标；资源与 I/O 类问题（读空输入流）由运行时库约定。
这一分工不是偶然：**分析能排除的错误，恰好是它的抽象粒度能区分的
错误**。类型只分形状，故只排除形状错误。这个判断准则在后面每一章
都适用——选择一个抽象域时，先问它把值空间切成了哪些类，就知道它
能防什么、必漏什么。

还要强调"输入值千变万化但类型恒定"背后更深的一层：我们之所以能对
`input` 这种完全未知的值下断言，是因为 TIP 的值空间被语言设计严格
限定——输入流里只有整数，不存在"输入一个指针"的可能。语言的边界
即分析可靠性的边界。若语言允许把任意字节解释为指针（如 C），分析
就要为这些额外可能性付出保守性代价。类型分析与其语言是共生关系：
规则写在语言定义里，分析只是在运行前重新发现这些规则。

### 9.1.4 本章在全书路线图中的位置

最后用一小段固定坐标。第三篇（09–12 章）是全书"约束驱动分析"的
完整标本：本章造词汇，第 10 章造生成器，第 11 章造求解器，第 12
章补规则、展局限。第四篇（13–16 章）把"先占位、列方程"的思想
推广到格与不动点；第五、六篇让抽象域从符号一路细化到区间；第七篇
处理函数与指针带来的组合爆炸。读者在任何一章迷路时，都可以回到
9.17.2 的对照表问自己："这里的未知是什么、方程是什么、解怎么求"
——三个问题能定位绝大多数分析的骨架。本章的特殊性在于它是这套
提问法第一次完整落地的地方，慢一点是值得的。

## 9.2 为什么不能直接"算出"类型

设想我们用前八章最熟悉的方式实现类型分析：写一个递归函数，输入
一个表达式节点，直接返回它的类型。字面量好办（返回 int），二元
运算好办（先递归求两侧、检查都是 int、返回 int），指针与记录也
可以照此组合。这个函数能写多长？会在哪个节点上卡住？本节把这条
看似自然的路走到它的失败点，失败的位置正好指明了需要的新数据
结构。

### 9.2.1 未知量的传播：变量引用这一关

直接递归算法在 VarRef 节点上第一次受阻。变量引用 `x` 的类型等于
x 的**声明**所具有的类型，而声明本身不携带任何表达式——形参 x 的
类型取决于调用者，var 声明的 x 的类型取决于程序里所有对它赋值的
右值。要在访问 `x` 时回答类型，就必须先知道别处（可能是尚未遍历
到的调用点、赋值点）的信息。一个直接的修法是给每个声明挂一个
"先算出来填进去"的槽位，先扫一遍程序算声明、再扫表达式——这
在简单情形下能工作，但它依赖一个危险的假设：**声明的类型可以在
不看使用点的情况下独立确定**。

看一个让假设破裂的程序：

```
main() {
  var p;
  p = alloc 5;
  output *p;
  return 0;
}
```

p 的类型完全由赋值 `p = alloc 5` 确定为"指向整数的指针"，这个信息
在赋值点上，要流向 p 的声明，再从声明流向 `*p` 处的使用。信息的
方向不是单一的树状递归方向（自底向上），而是在赋值点、声明、使用
点之间**横向流动**。更棘手的是递归函数：

```
loop(n) {
  if (n == 0) return 0;
  return loop(n - 1);
}
```

要确定 loop 的类型，需要知道它函数体里那次调用的类型，而那次调用
的被调者就是 loop 自己——不先知道 loop 的类型，函数体无法分析；
不先分析函数体，loop 的类型无从得知。信息的依赖形成了**环**。

### 9.2.2 一个失败的直接算法，以及失败教会的事

把直接递归算法认真实现出来，会观察到三类失败，分别对应三种缺失
的机制。其一，遇到形参/var 时没有可返回的东西——我们需要一个表示
"此处类型未知、待定"的对象；其二，为了确定未知对象，需要把程序
结构施加的要求记录下来（"p 必须等于 alloc 5 的类型"、"二元运算
两侧必须都是 int"），这些要求在直接算法里散落在控制流里，没有被
显式保存，一旦换个遍历顺序结论就可能不同——我们需要一种与遍历
顺序无关的、可积累的**要求的表示**；其三，环依赖意味着"按顺序算
完一个再算下一个"的模型根本不闭合——我们需要一个能处理"互相
引用、最终一起解出"的求解过程。

这正是数学里处理未知量时早已成熟的套路，形式如下。不要直接追问
每个未知量等于什么，而是：给每个未知量起一个名字（变量）；把题目
给出的全部条件写成以这些变量表达的**方程**；最后用统一的解方程
过程一次性求出所有变量。方程可以在不知道答案时写出（"x 的平方加
1 等于 5"不需要先知道 x），可以互相引用（方程组），甚至可以暂时
无解或多解——解方程阶段会给出判定。把这套思想搬到类型问题上，
得到本章引入的两个部件：**类型变量**（给未知类型起的名字，本章
实现）与**类型约束**（类型之间的等式，第 10 章实现），以及第 11
章的求解过程（合一）。

本章只做第一件事：把"未知的类型"变成一个可以放进数据结构、可以
被传递、可以被打印的普通对象。它单独不能分析任何程序——这一点
必须诚实，本章的 tipa --check 只打印类型构造的演示，不分析程序的
类型；但它是后两章一切工作的地基。先有可以表达"未知"的词，才能
写出以未知表达的方程。

### 9.2.3 一个历史视角：类型曾经住在哪里

值得顺带一提，"先占位、后求解"并非一开始就是类型问题的默认形态。
早期强类型语言的编译器里，类型信息通常直接登记在符号表条目中：
声明语法强制写出每个名字的类型（C 的 `int *p`），编译器在一次
线性扫描中把类型填进符号表，使用点查表即可。这条路之所以走得通，
是因为程序员用**类型标注**替编译器完成了信息汇集——未知被语言
语法提前消灭了。它不需要类型变量，也不需要合一。

当语言允许省略标注（ML 传统的类型推断），"谁提供信息"的责任从
程序员转给分析器，9.2 的三个困难才真正浮现：使用点可能先于信息
源、约束散落、依赖成环。类型变量与合一正是为接住这份责任而发展
出的机制。理解这段历史能帮助读者建立恰当的预期：类型推断不是
"更聪明的查表"，而是用一整套约束求解技术换取省略标注的自由；
代价（算法复杂度、单态/多态的细微限制）都源于此。TIP 处在光谱
中间——无标注、规则简单、但接受第 12 章将展示的表达力局限。

## 9.3 核心思想：先占位，后求解

### 9.3.1 类型变量就是"占位的未知"

一个**类型变量**代表一个"类型目前未知、以后确定"的位置。它与整数
`int`、指针 `ptr(...)` 等具体类型构造处在同一层：它也是一个类型
项，可以出现在任何类型能出现的地方——函数的参数位置、指针指向
的位置、记录字段的位置。区别只在于：具体构造子的形状已经确定，
变量的形状待定。给每个未知位置一个不同的变量（用唯一编号区分），
我们就能在完全不知道答案的情况下，把程序的类型结构**搭出来**。

以 9.2.1 的程序为例，搭结构的过程（细节是第 10 章的内容，这里只
看直觉）大致是：给 p 的声明一个变量 α；`alloc 5` 的类型是
`ptr(int)`——5 是 int 已知；于是程序给出条件"α 必须等于
ptr(int)"；`*p` 的类型则记为另一个变量 β，条件是"α 必须等于
ptr(β)"。注意这两个条件在写出时不需要知道 α、β 是什么：它们只是
记录要求。α、β 像代数方程里的未知数一样占位，结构先行，答案后至。

### 9.3.2 两阶段架构：生成与求解分离

于是整个类型分析被切成两个阶段，这一分离是本篇最重要的架构决定。

- **生成阶段**（第 10 章）：遍历一次 AST，为每个表达式、每个声明
  准备类型变量，按语法产生式把"此处必须成立的类型等式"一条条记录
  下来。此阶段不做任何求解：不判断两个类型是否相容，不试图确定
  变量，只负责**完整、忠实地**把程序施加的全部条件收集成一个数据。
- **求解阶段**（第 11 章）：取出生成阶段收集的全部等式，用统一的
  算法（合一）一起求解，确定每个变量；若条件互相矛盾（如要求同一
  变量既是 int 又是指针），在此阶段报出类型错误。

分离的好处值得逐一说明。生成阶段因此极其简单：它只需要懂局部的
语法规则（每个产生式对应哪些等式），不需要全局知识，天然可以按
AST 的递归结构组织。求解阶段因此与程序源文本脱钩：它面对的只是
一堆等式，同一求解器可以服务于任何程序、甚至任何能生成这类等式
的前端。正确性论证也因此分层：可以分别论证"生成的等式完整且忠实
于源程序"与"求解器对等式的解正确"，两个小论证替代一个纠缠的大
论证。最后，错误报告集中在求解阶段、信息精确（哪两个形状冲突），
而不是在遍历程序的某个不确定位置冒出。

### 9.3.3 与代数解方程的一张对照表

| 代数 | 类型分析 |
|---|---|
| 未知量 x, y | 类型变量 α, β（TyVar） |
| 数、四则运算构造的表达式 | int、ptr、fun、rec 构造的类型项 |
| 题目条件 | 程序的语法规则施加的等式（Con） |
| 方程组 | 约束集合 |
| 代入消元 | 合一（unify） |
| 方程无解（矛盾） | 类型错误 |
| 解：变量到值的映射 | 置换：变量编号到类型的映射（Subst） |

这张表会贯穿后续三章。本章实现的是表的第二行与第一行的右半：
类型项的表示（五个构造子）与变量的表示（编号）。读代码时随时
对照此表，就不会在类族、计数器、智能指针这些工程细节中忘记它们
各自对应着解方程图景里的哪一块。

### 9.3.4 为什么约束是等式而不是"子类型"关系

本书的类型约束一律取**等式** τ₁ = τ₂：两侧形状最终必须严格吻合。
另一种设计是允许**子类型** τ₁ ≤ τ₂（一侧可当作另一侧使用，如
null ≤ ptr(τ)），那样约束是不等式、求解需要更复杂的定型与合并。
等式设计的好处是求解器极简（第 11 章合一，一页核心代码），且解
唯一（主解）；代价是表达力受限——null 不能自然地作为"所有指针的
子类型"，只能在合一中开特例（第 12 章），记录宽度多态也无法表达。

这是静态分析设计中反复出现的权衡：**约束语言越弱，求解器越简单、
结论越确定；约束语言越强，表达力越高但求解可能变复杂甚至不可判定**。
spa 的教学选择是先把最弱、最优雅的等式约束讲透，再在需要处（null）
局部开口子。读者读第 12 章的特殊规则时应当意识到：那不是随意的补丁，
而是"等式框架内模拟一个子类型事实"的最小代价。后面 IFDS、指针分析
等章节还会遇到同样的决策模式——先确定约束/事实语言的表达力，再
设计求解器。

### 9.3.5 一个术语澄清："类型变量"不是"可变的类型"

初学者容易把"类型变量"误解为一个"可以在不同时刻变成不同类型"的
对象。恰恰相反：一个类型变量在一次完整分析中代表**唯一**待定的
类型项，一经求解便固定，不随程序点、不随执行时刻改变。它"变
量"的含义是代数意义上的"未知量占位"，而非命令式编程意义上的"可
变存储"。这个误解若不排除，后面读到多态（同一个 id 似乎在不同
调用处"变成"不同类型）时会格外困惑——多态的正确解释是"类型方案
在各使用点产生**不同的新鲜变量副本**"（9.14.1），而非一个变量
反复变脸。术语的精确在这里直接决定了对机制的理解是否走样；本书
凡称"变量"，都指这种外部映射待确定的占位符。

## 9.4 形式化：类型项的语法

在看 C++ 表示之前，先用一小节给出类型项的形式化语法。理由和
第 04–05 章一样：先有精确的记号，讨论数据结构的每个设计选择时
才有客观依据，也才说得清两个类型"相等"到底是什么意思。

令 α 取自一个无穷的类型变量集合，则类型项 τ 由下列产生式给出：

```
τ ::= int
    | ptr(τ)
    | (τ, ..., τ) -> τ
    | { f1: τ, ..., fn: τ }
    | α
```

逐行解释。`int` 是唯一的基础类型，TIP 只有整数，没有单独的布尔
类型（第 03 章设计：比较产生整数 0/1），因此不需要 bool。
`ptr(τ)` 是指向 τ 类型值的指针；注意指针类型携带它指向什么的
信息——知道一个值是"指向整数的指针"，就同时知道了解引用它会
得到整数。`(τ₁,…,τₙ) -> τ` 是函数类型：n 个参数的形状与一个
返回值的形状；参数个数为零时写作 `() -> τ`。`{ f₁: τ₁, … }` 是
记录类型：字段名到类型的有限映射。α 是类型变量，代表待定的类型
项。

### 9.4.1 关于这个语法的三个约定

第一，类型项是**有限**的语法树：每个构造子的分量个数有限，且嵌套
深度有限。变量 α 单独是一棵完整的（虽然未定的）树。第二，两个
类型项的相等按结构定义：构造子相同且每个对应分量相等；两个不同
编号的变量不相等（它们是两个不同的未知量），编号相同才是同一个
变量。第三，变量可以**代表任意**类型项，包括另一个变量、包括含
变量的复合项；"α 等于什么"通过一个从变量编号到类型项的映射
（第 11 章的置换 Subst）表达，而不是通过修改类型项本身——类型
项一经构造不被改动，这与第 05 章 AST 节点一经冻结不再修改是同一
原则。

### 9.4.2 指针为什么让"类型的结构"成为图

一个需要预先建立的心像：虽然 9.4 的语法把类型项写成树，但一旦
引入"变量被绑定到含自身的项"的可能性，类型的**依赖关系**就不再
是树。例如程序 `x = &x`（TIP 允许取变量自身的地址）会产生条件
α = ptr(α)：α 的类型指向 α 自己。条件图上出现一个环。这个条件
有意义吗？第 12 章会看到，合一算法的 occurs 检查正是用在这里——
在"类型必须是有限树"的约定下，α = ptr(α) 没有有限解，被判定为
错误。但"依赖可以成环、同一变量可在一个项里出现多次"这一事实，
直接决定了本章一个关键的工程选择：类型对象必须允许被**共享**
（多处引用同一个 α），而不能采用独占式的树形表示。9.6 节展开。

即使在合法程序里，共享也无处不在：同一个形参变量 α 既出现在
函数类型的参数位置，又出现在函数体里每次引用该形参的位置；若用
树（每次出现复制一份），则"这是同一个未知量"的身份就丢失了，
求解时无法把各处条件汇到同一个变量上。**身份（identity）必须被
保留**——这是类型变量与第 08 章 LLVM 值共享的同一个思想：对象的
同一性携带语义，复制即改变含义。

### 9.4.3 类型项的集合论语义：一个类型代表一组值

形式化语法回答"类型项长什么样"，还应回答"类型项**意味着什么**"。
标准回答是把每个类型项解释为一个运行时值的集合：`int` 解释为全部
可能整数构成的集合；`ptr(τ)` 解释为所有"指向某个 τ 类值"的地址
（外加 null，按第 12 章规则）；`(τ₁,…,τₙ) -> τ` 解释为把 τ₁,…,τₙ
类输入映射为 τ 类输出的函数集合；记录类型解释为字段取值分别属于
对应集合的记录值集合；类型变量 α 解释为某个待定集合的占位。

这一解释把"类型相等"与"值集合相等"、把"类型错误"与"值集合不相交"
联系起来：说 `3 + alloc 5` 类型错误，等价于说两侧要求的值集合（int
与地址集）没有公共元素——没有任何运行时值能同时满足两边。它也是
通往第 13 章及抽象解释（第 20 章）的桥梁：**类型项就是粗糙的抽象
域元素，它所命名的值集合就是它的具体化**。区别在于类型的集合由语法
构造刚性决定（int 与 ptr 的解释要么相等要么不交），而后面的格允许
更灵活的近似与合并。先理解"类型即值集"，后面"抽象状态即值状态集"
就是顺水推舟。

## 9.5 数据结构：Type 类族

从本节开始看真实代码。本章新增的文件只有一个：`type.hpp`，定义
类型项的全部表示。它在第 9.8 节逐行给出并讲解；下面先解释五个
设计选择，每个选择都对应 9.4 形式化语法或前面各节的一条需求。

在逐个选择之前，先给出阅读这份代码的总纲，以免见木不见林。数据
结构的全部职责是**忠实承载 9.4 的语法**：每个语法产生式对应一个
结构体，产生式的每个语法位置对应结构体的一个成员，打印规则对应
show。除此之外的一切——遍历、判定、求解——都不属于这里。因此
检验自己是否读懂 type.hpp 的方式不是"能否默写成员"，而是：任给
一个手写的类型项（如 ptr((int) -> {x: α})），能否立刻说出由哪些
类、以什么共享关系构造；任给一段构造代码，能否纸上画出其类型树
并标出哪些 Tp 指向同一对象。数据结构服务于结构思维，结构思维则
通过手算（9.12）内化。带着这一总纲读下面的五个选择，每一条都
会显出其必然性，而不是作者的个人口味。

### 9.5.1 基类 Type 与虚函数 show

所有类型构造共享一个抽象基类 `Type`，它规定两件事：一个纯虚函数
`show()`，返回类型项的字符串表示（这是本章及后两章打印类型、打印
约束、打印解的统一出口）；一个虚析构函数。为什么需要共同基类？
因为不同的构造子要被**统一地存放和传递**：指针的分量、函数的参数
序列、约束的两侧，这些位置既可能放 int 这样的具体构造，也可能放
类型变量，需要一种"任意类型项"的句柄。基类指针（确切说是基类的
shared_ptr，见 9.6）提供这个统一类型。

虚析构函数不是装饰：通过基类指针销毁派生对象时，没有虚析构就
不会调用派生类的析构，分量（如 TyPtr 持有的子类型 shared_ptr）
不会被正确释放。这是任何多态类层级的第一条机械要求。

### 9.5.2 TyInt：无分量的构造子

`TyInt` 对应产生式 `int`，没有任何分量，因此它的类体几乎为空，
只实现 show 返回字符串 "int"。它是类型项这棵树的叶子。一个值得
注意的设计选择：TyInt 不携带任何值——它不区分整数 3 和整数 7，
这正是 9.1.2 "形状不依赖具体值"的落地：所有整数值共享同一个形状
表示。后两章里所有"此处必须是整数"的条件，都通过指向 TyInt 的
指针表达，且不同位置的 int 形状在结构上完全等价（虽然我们的实现
每次新建一个 TyInt 对象，但相等性按结构判定而非对象身份）。

### 9.5.3 TyPtr、TyFun、TyRec：携带分量的复合构造

三个复合构造子各自持有"再拼出自己"所需的全部分量，与 9.4 语法
括号里的部分一一对应。`TyPtr` 持有一个类型项（指向的形状）。
`TyFun` 持有一个类型项序列（参数形状）加一个类型项（返回形状）。
`TyRec` 持有字段名与类型项的配对序列。每个构造子的 show 实现都
是：固定的构造子记号（ptr(...)、() -> ...、{...}）包裹各分量的
show——打印规则与语法产生式同构，因此读输出文本就能重建语法树。

这里字段与参数选用**有序序列**（vector）而非映射（map），有两个
理由。其一，类型项的形式化定义里，函数参数本就有次序（第 1 个
参数与第 2 个不可交换），序列天然表达；其二，记录按 TIP 与 spa
的约定，字段相等按"字段名集合相同"判定、与书写次序无关，用序列
存储时，合一（第 11 章）按字段名在另一侧查找对应项，不依赖位置
——第 12 章的错误矩阵会验证这一点（颠倒字段顺序的两个记录仍能
合一）。用最简单的存储、把次序相关性放进求解规则，是类型表示与
求解分离（9.3.2）的又一体现。

### 9.5.4 TyVar：携带编号的变量

`TyVar` 对应产生式 α，只携带一个整数编号。两个 TyVar 当且仅当
编号相等时代表同一个未知量（9.4.1），因此编号的唯一性是整个
机制正确的前提：每"要一个新变量"，编号必须与此前所有变量不同。
这由 TyVar 的静态成员函数 `fresh()` 保证（9.7 节）。TyVar 的
show 打印字母 t 加编号（t1、t2……），与具体构造子的打印形式
（int、ptr(...)）一眼可分，读输出时立刻能区分"已确定的形状"与
"待定的变量"。

### 9.5.5 为什么用继承分派而不是 std::variant

C++17 提供了另一种表示"若干构造子选一"的标准设施：
`std::variant<TyIntData, TyPtrData, ..., TyVarData>` 配合
std::visit 分派。本书前八章没有采用它，本章也沿用继承方案，理由
有三。其一，所有构造子都需要 show 等共同操作且操作集合会随章节
增加（后两章需要 occurs 检查、归一重建），虚函数让"加一个操作"
保持局部，variant 下加操作要修改所有 visit 处；其二，递归类型用
variant 表达需要前向声明与指针包装的额外样板，而继承方案里"基类
指针能指向任何派生类"天然支持递归；其三，也是最实际的：我们需要
在生成、求解代码里大量做"这个类型项是不是变量/指针"的判断与
分量提取，`dynamic_cast<TyVar*>` 同时完成判定与取分量，写法与
第 05 章 AST 消费者、第 08 章 IR 生成的分派风格一致，全代码库
共享同一种阅读习惯。variant 方案在纯函数式风格、希望穷尽性检查
由编译器强制时有优势；本项目的取舍是一致性优先。

### 9.5.6 show 的三条性质

show 虽只是打印函数，它的设计仍有可论证的性质，且这些性质被后三
章的输出对账依赖。其一，**完全性**：任何类型项都能打印，包括含
未绑定变量的项——变量打印编号，不会出现"无法显示"的分支。其二，
**单射性的直觉**：不同形状的类型项打印文本不同（构造记号互不
冲突：int 不带括号、ptr( 带 ptr、-> 带箭头、花括号带花括号），
因此读文本可以无歧义地重建形状；这也是错误信息里直接用 show 给出
冲突双方而不会误导读者的原因。其三，**对结构递归**：复合构造的
打印由其分量的打印组合而成，于是嵌套项的打印长度有限、深度可见。
三条性质合起来让打印文本成为类型项合格的"外部表示"，可以存档为
expected、可以被读者直接当作推理依据。

## 9.6 所有权：为什么是 shared_ptr

本节解释 type.hpp 第一眼最显眼的决定：所有类型项通过
`std::shared_ptr<Type>`（别名 Tp）持有和传递，而不是第 05 章 AST
使用的 unique_ptr，也不是裸指针。三种选择各自的含义必须说清楚，
因为这是本章唯一一个与已有代码习惯不同的所有权决定。

### 9.6.1 同一个变量被多处引用

9.4.2 已经论证：类型变量的身份必须在多处出现之间被保留——形参 α
同时出现在函数类型与函数体的多个使用点，这些位置必须引用**同一个
对象**，这样求解时对 α 的一次确定才能被所有位置同时观察到。
unique_ptr 的语义是独占：一个对象只有一个所有者，要在多处出现
只能移动（移动后原处为空）或复制（复制得到另一个对象，身份丢失）。
两种语义都不符合"同一未知量、多处共享"的需求。shared_ptr 的语义
正是共享所有权：多个 Tp 可以指向同一个对象，最后一个引用消失时
对象才销毁。复制一个 Tp 复制的是"引用"，对象身份保持——这正是
我们需要的：到处传递 α 而 α 始终是 α。

### 9.6.2 环：α = ptr(α) 排除了 unique_ptr，也考验 shared_ptr

指针构造使**循环引用**成为可能：条件 α = ptr(α) 对应的对象结构是
一个 TyPtr，其分量 Tp 指回同一个 TyVar。unique_ptr 在语言层面
就无法构造这样的环（TyPtr 独占其分量，TyVar 无法反过来被 TyPtr
"拥有"又同时在外存活）；裸指针可以构造但所有权无归属、销毁责任
不清。shared_ptr 让环可以被构造：TyPtr 的分量与外部变量各自持有
对 TyVar 的引用。

必须诚实地指出 shared_ptr 在环上的一个真实代价：引用计数在环上
不归零（TyVar 与 TyPtr 经环互相计数），对象不会被自动释放——这
是循环引用的经典泄漏。对本教程影响为零：类型对象在单次 tipa
运行中构造、程序退出时由操作系统统一回收，我们不追求类型对象的
提前析构。若要在长期运行的服务里消除它，标准手段是把"拥有"与
"观察"分开（环上一处改用不增计数的 weak_ptr）；本章没有这个
需求，引入 weak_ptr 只会让表示复杂化。记住取舍的形式：**用理论上
的循环泄漏，换取共享与成环的表达力**，泄漏在程序生命周期内不
爆发。

### 9.6.3 与裸指针方案的对比

也可以让类型对象归一个集中的"类型池"所有（如第 05 章讨论过的
arena），各处传递裸指针，最后整池销毁。这在很多编译器里是实际
做法，且没有计数开销。本章没有采用，原因有二：类型项会在生成与
求解过程中被**新建**（求解时会构造新的复合项，如归一重建），它们
的生命周期不完全等于一次遍历，集中池要为此设计分代管理；而
shared_ptr 让对象的生命周期自动正确，无须额外的池代码，对教学
程序这更小、更不易错。计数的运行时开销在类型项这种数百量级的
对象上完全可忽略。一句话：unique_ptr 表达独占树，裸指针+池表达
集中永生，shared_ptr 表达**分布式共享**——类型变量的世界正是
分布式共享的。

### 9.6.4 一笔成本账

shared_ptr 相对 unique_ptr 确有成本：每个 Tp 携带一个控制块指针，
复制/销毁要原子地增减强引用计数（原子操作比普通加减贵一个量级），
对象本体与控制块分两处分配（make_shared 已合并分配，缓解但未消除
间接）。把规模代入：本章程序的类型项总数在数十量级，第 10 章全
程序收集后也仅数百，计数操作的总耗时远小于一次 LLVM 构建的零头，
成本不可观察。反过来，若在热路径（如每节点、每指令执行一次）上
共享百万级对象，引用计数才会成为瓶颈，那时应考虑 arena+裸指针。
工程决策的一般形式：**先按语义需要选所有权，再用量级数据检验成本
是否真实**；本节的取舍经得起这一检验。

## 9.7 新鲜变量生成

### 9.7.1 单调计数器

TyVar::fresh 的实现是一个函数内静态计数器，每调用一次加一，返回
新编号；编号从 1 起。它满足 9.5.4 的唯一性要求：计数器只增不减，
返回值两两不同。把计数器做成 TyVar 的静态成员而非全局变量，把
"编号从哪里来"的知识收在 TyVar 一处：构造类型变量的唯一正当方式
就是 tvar() 便利函数（内部调 fresh），不存在绕过计数器手工编号的
合法路径——手工编号与计数器冲突只是时间问题。

### 9.7.2 确定性为什么是硬要求

fresh 的一个隐含性质与本书全部自动化机制相关：**给定同一份源程序，
每次运行 tipa 产生的编号序列必须完全相同**。计数器从零起、按
AST 的固定遍历顺序调用 fresh，不接触任何环境信息（时间、内存
地址、输入），因此编号是程序文本的确定函数。这不是洁癖：第 9.10
节的输出对账逐字节比较 --check 的结果，若编号一次运行是 t1/t2、
另一次因遍历顺序或并发变成 t2/t1，expected 文件立刻失配，且失败
信息无法反映任何真实错误，只是噪音。确定性把"编号"变成源程序的
稳定投影，输出才可复现、可存档、可 diff。第 08 章 JIT 的输入
脚本化、诊断文本不含路径，服务的是同一个原则：**一切产物只由
源程序文本决定**。

### 9.7.3 编号不是名字

最后澄清编号的语义地位。t1 里的 1 只是计数器的次序，**不反映类型
变量在源程序中的位置、也不携带类型信息**：t1 不因为编号小就更
"基础"，它与 t99 在被求解前地位完全平等。读输出时不要试图从编号
推断"这是哪个变量"——变量与源程序位置的对应由第 10 章的收集器
维护（每个表达式与自己的 TyVar 关联），编号只保证互不相同。编号
是变量的**身份证号**，不是变量的**含义**；含义由约束施加、由求解
确定。这与第 08 章 IR 文本中 `%5` 只是自动编号、真正身份是
def-use 关系，是同一种设计：人读的编号与机器用的身份分离。

### 9.7.4 编号在调试输出中的读法

读第 11、12 章输出时，读者会看到大量 tN。这里给一份阅读纪律：
同一输出中编号相同必为同一未知量（由收集器的 memoization 保证）；
编号不同未必代表形状不同——求解后两个变量可能被绑定到同一项；
编号大小不反映依赖方向或嵌套深度，只反映"第一次被需要"的遍历
次序。排查类型错误时，正确的动作是从冲突信息中的两个 tN 出发，
在 --check（第 12 章）输出里找到它们各自对应的源表达式（输出按
表达式顺序列出），而不是盯着编号猜含义。编号是索引，表达式位置
才是内容——9.7.3 的区分在调试方法上同样适用。

## 9.8 type.hpp 逐行导读

下面给出 type.hpp 的完整内容（第 9.20 节再次以可对账的形式给出，
本节先逐段导读关键行，阅读时两份是同一个文件）。文件开头的注释
交代了三件事：类型对象为何用 shared_ptr（9.6）、分析的两阶段
（9.3.2）、本文件在其中的位置（表示层）。

包含的标准头各有职责：`<memory>` 提供 shared_ptr 与 make_shared；
`<string>` 是 show 的返回类型与字段名的类型；`<vector>` 承载函数
参数与记录字段序列。注意没有包含 `<map>`——类型项本身不用映射
（9.5.3），映射是第 11 章置换层的事，头文件只包含自己真正需要的
设施，这与第 05 章 ast.hpp 的克制一致。

别名 `using Tp = std::shared_ptr<Type>;` 之后，五个结构体逐一落地
前面各节的讨论。阅读 TyFun 的 show 时注意一个小细节：参数序列为
空时正确打印 `() -> int` 而不是多出分隔符——分隔符加在"每个非首
项之前"的写法统一处理了零项、单项、多项三种情形。TyRec 的 show
用同样的模式。这类打印细节虽小，却直接决定 expected 输出能否逐
字节稳定；规则只有一条：**分隔符的放置由位置条件（是否第一项）
决定，不依赖项数**，于是任意项数同一写法。

文件末尾的两个 inline 便利函数 `tint()` 与 `tvar()` 是创建类型项
的推荐入口。为什么提供它们？因为裸写
`std::make_shared<TyInt>()` 长且重复，而"要一个 int 形状"、"要
一个新变量"是后两章最高频的两个动作；便利函数让收集器（第 10
章）的代码只表达语义意图。tvar 把"申请编号 + 包成 TyVar + 包成
shared_ptr"三步合一，因此调用处不可能忘记走 fresh——这是把
9.7.1 的唯一性要求封装进 API，而不是靠调用者遵守纪律。

还应说明几个被有意排除在文件之外的东西，以正视听。没有任何遍历
代码（AST 访问属于第 10 章）；没有错误类型（TypeError 属于第 11
章，且它是求解层设施，不污染表示层）；没有 TyNull（第 12 章加入，
避免本章在尚无合一时引入无法消化的特例）；没有任何 C++ 运算符
重载（如 ==）——结构相等是第 11 章合一的职责，表示层提供原始
材料而不预设判定方式。一个表示文件应当像一份语法的附录：构造子、
分量、打印，仅此而已；每多一个函数都要回答"它是否属于表示层"。
这种克制与 ast.hpp 第 1–2 行声明的"接口冻结"纪律一致：先把最小
接口冻结，再让后续章节在其上生长。

## 9.9 main.cpp：--check 为什么换了语义

本章对 tipa 的命令行只做一处改动：`--check` 不再打印 LLVM IR
（那是第 08 章的语义），改为先完整跑一遍前端（解析、AST、名字
解析），再打印一份**类型构造演示**。需要解释两件事：演示在展示
什么，以及前端为什么仍然全程运行。

### 9.9.1 演示部分逐行看

printTypeDemo 顺序打印七行（见 9.10），分两组。前三行加记录行
展示四个具体构造子的打印形状：int、ptr(int)、(int) -> int、
{x: int}。构造它们的代码值得对照阅读：ptr 与 fun 都复用同一个
`i`（指向 TyInt 的 Tp）——这正是 9.6.1 的共享，多个复合项引用
同一子对象，无须为每处新建 int。函数类型只演示一个参数的情形；
记录只演示一个字段。

后三行连续调用 tvar() 三次，打印 t1、t2、t3——这是新鲜计数器
（9.7）唯一可见的输出：三个编号两两不同、严格递增。注意一个
顺序细节：演示里构造 ptr/fun/rec 时**没有**消耗变量编号（那些
都是具体构造子），所以三个 tvar 恰好得到 t1/t2/t3 而不是更大的
号；编号的起点和次序都可手工预测，输出因此可逐字节核对。

### 9.9.2 前端为什么仍然全程运行

既然本章不分析程序类型，--check 为什么还要解析、建 AST、做名字
解析，而不直接打印演示？因为本章的 tipa 必须保持一个承诺：**它
仍然是第 08 章那个能处理 TIP 的工具**，前端链条在类型层加入后
继续工作、不被破坏。具体说，跑 --check 仍然对语法错误以退出码 2
中止、对名字错误以退出码 3 中止——错误程序根本到不了演示；只有
前端全部通过的程序才看到类型演示。这样第 10 章把演示换成真正的
约束收集时，parseFile 及其退出码约定原样可用，本章只是在它之后
挂了一个临时的展示函数。前端是冻结的地基（第二篇的承诺），每一
章的新分析都建立在它之上、不削弱它。

### 9.9.3 --emit-ir 与 --run 原样保留

--emit-ir 与 --run 的代码与第 08 章完全相同、行为不变：前者打印
未优化 IR，后者按输入脚本逐行 JIT 执行。保留它们有两个意义。技术
上，它让执行台在类型篇随时可用——读者可以对任何程序同时观察
类型演示（--check）与具体行为（--run），为第 12 章之后"抽象预测
对照具体执行"埋下通道。心理上，它强化了工具的连续性：章节增加的
是能力，新章节不收回旧能力。命令行协议的总原则从第 08 章起没有
变过：子命令只增不改，退出码分层固定。

### 9.9.4 退出码协议在本章的状态

把退出码在本章的实际行为固定下来，供自动化脚本依赖：0 表示一切
正常（--check 看到演示、--emit-ir 打印完毕、--run 全部用例执行
完毕）；2 仅用于语法错误，由 parseFile 内部在 ANTLR 报告语法问题
时返回；3 用于语义类错误，本章包括未声明名字、重复声明等名字层
错误，从第 11 章起加入类型错误。关键约定是**退出码在章节演进中
语义不变、只扩充成员**：脚本可以永远用 `$? == 2` 判定语法问题而
不必关心章节号。--check 的演示只在退出码 0 的路径上出现，因此
expected/output.txt 与 errors 目录下的期望文件互不干扰——错误
程序的输出存档在 errors 子目录，成功程序的输出存档在 output.txt。

## 9.10 真实输出解读

本章 expected/output.txt 是对两个程序分别跑 --check 的拼接，格式
与第 06 章以来一致：每个程序一段，段首 `== 文件名 ==`。

### 9.10.1 先读单个程序的七行

```
-- type structures --
int
ptr(int)
(int) -> int
{x: int}
t1
t2
t3
```

第一行是演示自己的标题，表明以下与被检查的源程序无关——同样的
七行对任何前端能通过的程序都一样。接下来四行是 9.4 语法里四个
构造子的具体例子：从无分量的 int，到包一层的 ptr(int)，到携带
参数与返回的函数类型，到携带命名字段的记录。读这四行应当能反向
说出 C++ 里各用了哪个类：int↔TyInt、ptr↔TyPtr、->↔TyFun、
花括号↔TyRec。最后三行是三个不同的类型变量，编号递增、形状
待定。

### 9.10.2 七行之外什么都没有——这本身是信息

值得专门指出输出里**不出现**的东西。没有对源程序的任何分析：ite
是阶乘循环、outputs 是双输入加法，这个差别在输出里完全不可见，
因为本章还没有写出约束（9.2.2：类型变量单独不分析程序）。没有
错误检查除前端之外的内容：一个类型完全错误的程序只要语法和名字
通过，本章一样给它看七行演示。没有未绑定的变量打印成奇怪的
"unknown"——t1/t2/t3 的形状未定，打印的就是它们的编号，而非
占位文本。输出的朴素性诚实地反映了本章的能力边界：**我们只造出
了表达类型与未知的词汇，还没用它陈述任何关于具体程序的事情**。
第 10 章的输出将第一次因程序不同而不同。

### 9.10.3 两个程序输出逐字节相同

ite.tip 与 outputs.tip 的两段输出一字不差。这件事初看像缺陷，
实则精确地表明了本章的依赖关系：--check 的输出只依赖"前端是否
通过"这一个比特，通过之后只依赖 type.hpp 的演示代码，不依赖
AST 内容。把这一点与 9.7.2 的确定性合起来看：输出是（程序能否
通过前端，类型表示代码）的确定函数；两个程序在第一分量上同为
"通过"，输出必然相同。读者到第 10 章可以用同样的视角检验：
那时输出开始依赖程序，因为收集器读取了 AST 与绑定，而类型表示
本身仍不变。学会区分"输出的哪部分由框架决定、哪部分由程序决定"
（第 08 章 8.14.7 的读法），是读任何分析器输出的通用方法。

### 9.10.4 期望输出如何重新生成

本章 expected/output.txt 的生成方式与全系列一致：构建快照后，对
programs 下每个程序依次运行 tipa --check，段首打印文件名标记，
拼接为 output.txt；--run 的产物来自 inputs 脚本。整个过程由
tools/ 下的通用脚本驱动，不为本章特化——这保证"重新生成"在任何
机器、任何时候得到同样的字节流（前提是固定的编译器与 LLVM 版本）。
理解这一点有实际用途：若读者修改了 printTypeDemo（如多加一行），
重生成脚本会让对账失败，失败 diff 精确指出哪一行变了，从而强迫
作者同时更新讲解文字与期望产物——**机器对账把"文档与代码一致"
从愿望变成机制**。第 09 章的特殊之处仅在于演示与源程序无关，
因此 output.txt 中两段必然相同；若某天它们不同了，说明前端行为
意外地渗进了演示，那是 bug 的信号。

### 9.10.5 输出规模与源程序规模的关系

读输出还有一个可用于自检的数量关系：本章输出行数与源程序规模
**完全无关**（两个程序同为九行一段）。这是一个极端但诚实的端点，
正好校准读者对后续章节输出规模的预期。第 10 章起，约束条数随
表达式与声明数近似线性增长（每个产生式贡献固定条数的约束），
因此输出规模成为源程序规模的线性投影；第 13 章的数据流输出随
程序点数增长；更精细分析的输出则可能因上下文展开而超线性膨胀。
**输出规模本身泄露了分析的复杂度结构**——读一个分析器先看它输出
多大、随什么增长，往往比读它的功能说明更快理解其成本。本章的
"零增长"不是缺陷而是立场：表示层不消费程序，规模与程序无关恰恰
证明这一点。

## 9.11 其余源文件：冻结组件的快速对照

第 9.20 节嵌入的文件里，除 type.hpp 与 main.cpp 外都是第二篇已
逐章讲解、此后冻结的组件。本节给出它们与本章的关系，避免读者以
为类型层需要改动它们——答案是不需要，这正是分层的回报。

"冻结"一词的含义值得说准：不是这些文件永远不变，而是它们的**接口**
（结构体成员、函数签名、文法符号）从此稳定，变化只允许发生在内部
实现且不得改变既有行为。类型层因此可以放心地在这些接口上构建，
无须担心下一章地基移动。这种"接口冻结、消费者叠加"的纪律从第 05
章 ast.hpp 开头两行就被宣布，贯穿全书：每个分析都是新添的消费者，
而非对地基的改造。读者在自己的项目里也可以采用同样的节奏——先
冻结一层、充分验证，再在其上叠加，比起边改地基边盖楼，返工成本
低得多。

- `TIP.g4`：第 04 章的文法。它早已包含指针（alloc、&、*、null）
  与记录（花括号、点号）的全部产生式——第二篇文法先行，类型层
  因此无须为新构造修改一个语法符号。
- `ast.hpp` / `ast_build.{hpp,cpp}`：第 05 章的 AST 与构建器。
  AllocE、AddrOf、Deref、NullE、RecLit、FieldA 节点当时就已齐备；
  第 10 章的收集器只是又一个 AST 消费者，与 pretty、CFG 并列。
- `pretty.{hpp,cpp}`：第 05 章的打印器。本章 main.cpp 在报告每个
  表达式类型时会复用它（printExpr 在第 12 章登场；本章 main 未用，
  但文件保持完整），把"表达式长什么样"与"表达式是什么类型"两件
  事的表示分开。
- `symtab.{hpp,cpp}`：第 06 章的名字解析。第 10 章收集器直接消费
  它的输出：变量使用点经 bindings.uses 找到声明，同一声明的所有
  使用共享为该声明准备的同一个 TyVar——类型层建立在名字层之上。
- `irgen.{hpp,cpp}` / `jitrun.{hpp,cpp}`：第 08 章的执行台。本章
  原样保留以支撑 --emit-ir/--run；第 17 章可靠性检验时它会重新
  成为主角。

把这份清单与 9.1.2 的分层对照：每一层只依赖紧邻的下一层产物，
类型层（第三篇）架在名字层与 AST 层上，不触及其余。新增一整个
分析篇而不修改任何旧文件（除 main.cpp 的命令分支），是分层架构
可演化性的直接证据。

对读者阅读第 9.20 节嵌入代码再给两点建议。其一，冻结文件不必逐行
精读：只需在 ast.hpp 中确认十个表达式类、六个 BOp 枚举与
FunDecl 的字段，在 symtab.hpp 中确认 Symbol/Symbol::Kind 与
Bindings 的四个成员，其余实现文件（ast_build、symtab 的 cpp）在
类型篇只作为"保证产出正确"的黑箱存在——第二篇已经为它们交过账。
其二，阅读时区分两类信息：哪些字段会被第 10 章读取（如 VarRef.name
不再需要，因为 uses 已把 VarRef 映射到 Symbol；AddrOf.name 仍需要，
因文法限定取地址只对名字），哪些只是 IR 与打印层的设施。带着
"消费者视角"读，代码的每一行就有了轻重。

## 9.12 手算三例：在纸上搭类型结构

在进入更多概念之前，先用三个程序把"类型变量占位、结构先行"的过程
亲手走一遍。读这一节时建议拿纸笔，先盖住我的推导自己搭，再对照。
本节出现的全部条件在第 10 章会由收集器机械生成，手算的目的是让
读者相信：那不是魔法，只是把本节的动作按固定规则做出来而已。

手算时统一采用下面的记号约定，后文五个例子一致：希腊字母 α、β、γ
等为类型变量（对应实现中的 TyVar 与打印输出中的 tN）；"形状 A =
形状 B"表示一条等式约束（对应第 10 章的 Con）；箭头右侧给出条件
的来源理由（哪个语法构造施加的）。请特别注意区分两类动作：**搭**
（新建变量、按语法把分量拼起来）与**连**（在两个已搭好的位置之间
加等式）。收集器的实现里这两类动作也是分开的函数（varOf 负责搭、
eq 负责连），手算与代码由此一一对应。读例子时若感到某处"突然
知道了答案"，多半是把第 11 章的求解动作提前做了——正确的手算
纪律是：9.12 各例中先把条件全部列完，再做最后一步代入。

### 9.12.1 例一：纯算术，变量几乎用不上

程序：

```
main() {
  return 3 + 4 * 2;
}
```

从叶子开始。字面量 3、4、2 的形状直接是 int，不需要变量。`4 * 2`
要求两侧都是 int（已满足），自身是 int；`3 + (...)` 同理。return
要求返回表达式的形状等于 main 的返回类型，而 main 的返回类型在
TIP 约定中由返回语句确定——这里是 int。整个推导里没有出现未知，
一个类型变量都不需要分配。这说明类型变量不是处处必需：**封闭的、
无参数依赖的片段可以直接定型**。变量是为"信息缺失"付出的记号成本，
缺失消失处成本也消失。第 10 章的收集器仍会机械地为每个表达式挂
变量（规则统一、代码简单），但那些变量会被立刻约束成 int；统一
规则比"能省则省"的优化规则更易论证正确。

### 9.12.2 例二：恒等函数与它的调用点

程序片段：

```
id(x) {
  return x;
}
main() {
  return id(5);
}
```

分析 id 时，x 的形状未知，发一个变量 α；函数体唯一的信息是
"return x"，于是返回类型等于 α。id 的类型因此搭成 (α) -> α——
注意参数位置和返回位置出现的是**同一个 α**，这正是 9.6 共享身份
的用武之地：两处引用同一变量，"进去什么就出来什么"这个信息被
结构本身携带，无须文字说明。

再看调用点 id(5)。给整个调用表达式一个变量 β（它的值形状待
定）。调用的结构施加两个条件：被调位置的类型必须是"接受实参
序列的函数"，且该函数的返回类型等于调用结果。实参 5 是 int，
因此条件写作：id 的类型 = (int) -> β。把此前搭好的 id 类型代入
同一位置，得到 (α) -> α = (int) -> β。此时未知仍可并存；第 11
章的合一将按结构拆开这个等式：α = int、α = β，于是 β = int，
调用结果为 int，id 在本程序中按 (int) -> int 使用。

这个例子埋下两条后话。其一，id 的类型 (α) -> α 读作"对任意形状
α 都成立的恒等"——这是**多态**的雏形；但本书实现的简单机制里
α 在全局只有一个解，若程序里还写了 id(alloc 0)，求解器会被要求
同时令 α = int 与 α = ptr(...)，报错。第 12 章把这一"单态"局限
讲透。其二，函数调用条件的形式化正是第 10 章的规则 CallE：
τcallee = (τarg1,…,τargn) -> τresult。

### 9.12.3 例三：指针链

程序：

```
main() {
  var p;
  var q;
  p = alloc 5;
  q = &p;
  output **q;
  return 0;
}
```

先为两个声明各发变量：p 为 α，q 为 γ。`alloc 5` 的形状由规则
直接搭出：5 是 int，故为 ptr(int)。赋值 `p = alloc 5` 要求两侧
形状相同：α = ptr(int)。`&p` 的形状是"指向 p 声明类型"的指针，
即 ptr(α)；赋值 `q = &p` 给出 γ = ptr(α)。

最后看 `**q`。第一层解引用：q 的形状必须是"指向某形状 β₁"的
指针，即 γ = ptr(β₁)，而 `*q` 的形状是 β₁。第二层：β₁ 必须是
ptr(β₂)，`**q` 的形状是 β₂。所有条件摆在一处：

```
α  = ptr(int)
γ  = ptr(α)
γ  = ptr(β₁)
β₁ = ptr(β₂)
```

第 11 章逐对合一：α 落地为 ptr(int)；γ 落地为 ptr(ptr(int))；
对照 γ 的两种展开得 β₁ = α = ptr(int)；再由 β₁ = ptr(β₂) 得
β₂ = int。`**q` 输出整数，与运行时实际情况（5）的形状一致。
手算至此，读者应当体会到三件事：条件可以在完全不知道答案时
全部写出；条件之间横向引用、成链；最后的求解是机械的代入与
结构对照——没有一处需要"灵感"。

### 9.12.4 例四：记录与字段访问

程序：

```
main() {
  var p;
  p = {x: 1, y: 2};
  output p.x;
  return 0;
}
```

p 的声明发变量 α。记录字面量有两个字段，分量表达式都是 int 字面量，
形状直接搭成 {x: int, y: int}；赋值给出 α = {x: int, y: int}。
访问 `p.x` 时，规则要求 p 的形状是"含有字段 x 的记录"：给整个字段
访问一个新变量 β，条件写作 α 必须等于某个 {…, x: β, …}。求解时
对照已有的记录形状，找到 x 字段的分量，β = int，输出整数。

这里有一个第 10 章实现上的微妙点，值得先想清楚：生成 `p.x` 的条件
时，收集器需要知道"p 的记录还应该有哪些字段"。若只写 {x: β}，而
赋值点说 α = {x: int, y: int}，两式字段集合不同，按宽度一致的
约定本应相容（一侧只"提及"了 x，另一侧字段更全），naive 的记录
相等却会报错。spa 的处理预告：第 10 章收集器在生成任何记录条件前，
先在整个程序范围**汇总所有出现过的字段名**（gatherFields），于是
`p.x` 处搭出的待定型记录也包含 y 的位置（挂一个新变量），等式两侧
宽度一致。换言之，记录的"字段集合"是一个**程序级事实**，不能只靠
局部可见信息；这与类型变量"信息跨处流动"的总主题一脉相承。

### 9.12.5 例五：循环里的 input

最后看一个含循环与输入的程序骨架：

```
sum(n) {
  var s;
  s = 0;
  while (n > 0) {
    s = s + input;
    n = n - 1;
  }
  return s;
}
```

这里每个声明各有变量：n 为 α（参数），s 为 γ（局部）。循环条件
要求 α 与 0 同属 int，故 α = int；循环体里 `s + input` 要求 γ 是
int（input 自身是 int），`n - 1` 与 α = int 一致；返回语句令函数
返回类型等于 γ = int。有趣的是 `s = s + input`：同一语句两侧引用
同一个 γ，而 input 的**值**每次循环都可能不同——类型分析对此毫无
困难，因为它从不追踪值，只确认 γ 在所有赋值下形状恒为 int。这把
9.1.2 的分层推到了最直白的形式：输入流的全部随机性在类型层坍缩为
同一个 int，循环的重复执行坍缩为同一组条件。

## 9.13 结构类型：相等性由形状而非名字决定

9.4.1 已按结构定义了类型项的相等，这里展开它的后果，因为它影响
第 10–12 章的每一条规则。我们的类型世界里**没有类型定义、没有
类型名**：不存在"type PtrToInt = ptr(int)"这样的声明让两个类型
因同名而相等。两个类型相等，当且仅当它们从最外层构造子到每一个
嵌套分量都一一吻合。这称为**结构类型系统**（structural typing），
与按声明身份判定的**名义类型系统**（nominal typing，C、Java 的
类/结构体即属此类）相对。

结构观有三个直接好处。其一，类型项自给自足：看到 ptr(int) 就知道
它的全部含义，不需要再去查某个名字的定义，分析器无须维护"类型名
环境"。其二，兼容关系可递归判定：第 11 章的合一就是结构相等在
含变量情形下的推广——对照构造子、递归分量，规则一页纸能写完。
其三，记录天然受益：两个分别书写的记录字面量 `{x:1, y:2}` 与
`{y:2, x:1}` 字段集合相同，按 spa 的约定形状相同；字段书写顺序
是源程序的偶然，不是形状的一部分。

代价也应说明。名义系统里"不同定义即不同类型"可以防止偶然混用
（如用 int 表示厘米和英寸），结构系统对此不设防——形状相同即
相容。TIP 是教学语言，不追求这类区分。记住分歧的本质：名义系统
把"程序员宣布的身份"纳入类型，结构系统只承认"实际的形状"。本书
的分析一律在结构观下进行，因此第 11 章判定 TyRec 相等时只看
字段名与各字段的分量。

结构观还有一个常被忽视的副产品：类型项因此可以在不同程序片段、
甚至不同程序之间直接比较与复用——两个文件里独立写出的 ptr(int)
是同一个形状，不依赖任何跨文件的声明登记。对分析工程这意味着
类型表示无须全局命名管理，组件之间的接口只需共享结构定义。在
多模块语言中，这种"无名字即可相容"的特性简化了分模块分析的
合并；反过来，想要强制模块边界的抽象保护，则需要名义机制。

### 9.13.1 记录宽度：一个程序级的形状事实

9.12.4 已预告 gatherFields，这里把"宽度"的形式化地位讲清楚。记录
类型 {f₁:τ₁,…,fₙ:τₙ} 的形状包含两个维度：字段名集合（宽度）与
每个字段的形状。在 spa 的 TIP 类型规则中，两个记录类型相容要求
字段名集合**相同**——不多不少；多出字段与缺少字段一样不被简单的
合一规则接受（本书不实现记录宽度多态）。困难仅在于：生成条件时，
某个被访问记录的完整宽度无法从单个使用点看见，它分散在该变量的
赋值点与所有字段访问点上。

因此第 10 章收集器在遍历前先做一次全程序扫描，收集所有记录字面量
与所有 FieldA 中出现过的字段名，形成一个全局字段名表；此后任何
"待定型记录"都按此表搭出全部字段位置，未在局部提及的字段挂新鲜
变量。这样做的正确性依据是：若程序最终良类型，则某个记录变量在
所有赋值点与访问点上的字段集合必然一致（否则求值时必出现访问缺失
字段，即 9.16 意义上的走错）；提前把这些字段位置搭好，只是把这一
语义前提显式化。要注意它的代价：字段名表是全程序汇总的，不同的、
互不相关的记录也共享字段名集合的构造——这对正确性无害（变量各有
归属），只是生成的变量编号更多；第 10 章输出里可以观察到这一点。

## 9.14 一等函数：函数类型为什么是普通类型项

TIP 的函数是**一等公民**：函数名是一个普通名字，可以出现在表达式
里、作为参数传递、作为结果返回（spa 的函数式语言一章专门讨论）。
这一设计决定了为什么 TyFun 必须与 TyInt、TyPtr 处在同一层、可以
出现在任意类型位置——包括另一个 TyFun 的参数位置与返回位置。
看程序：

```
apply(g, x) {
  return g(x);
}
```

g 是一个普通形参，形状未知，发变量 α；x 发 β。函数体 `g(x)` 施加
条件：α 必须是"接受一个 β 形状实参的函数"，即 α = (β) -> γ，γ
为调用结果的新变量；返回语句给出 apply 的返回类型等于 γ。于是
apply 的类型搭成 (α, β) -> γ 并附带 α = (β) -> γ，归一后写作
((β) -> γ, β) -> γ。这个类型项里 TyFun 嵌套出现——函数类型本身
又是另一个函数类型的分量。若 TyFun 不是普通类型项，"参数是函数"
就无法表达，一等函数在类型层直接消失。

这一结构也预告了第 25 章之后的控制流分析难题。`g(x)` 的被调者
不是一个直接名字，而是类型为函数的变量；运行时 g 可能指向程序里
任何形状相容的函数。类型分析回答"g 是某种函数"，但回答不了"g
具体可能指向哪几个函数"——后者需要 0-CFA 之类的流分析，其答案
是一个函数集合而非单个类型项。同一个调用点因此被两层分析从不同
方向刻画：类型层保证调用**形状合法**（被调者确为函数、实参形状
匹配），流分析层给出被调者的**可能身份**。本章只搭第一层，但
TyFun 的表示已经为两层准备好了共同的词汇。

### 9.14.1 高阶给推断带来的复杂性

函数作为参数与结果一旦被允许，类型项的嵌套深度在原则上没有上限：
可以写出"接受一个函数、返回另一个函数"的程序，其类型含两层
TyFun；手写语法里看不出层数，只有搭出类型结构才知道。这正是
"结构先行"比"直接算答案"更适合此类语言的另一理由：收集器无须
预判嵌套层数，它只在每次见到调用或被调位置时机械地要求"此处为
函数类型"，层数由约束自身长出来。

也要提前指出简单合一机制在高阶情形下的一个表达力缺口：前面 9.12.2
说过 (α) -> α 的多态雏形在"α 全局唯一解"的约定下是单态的。这个
缺口在高阶时更显眼——把 id 传给两次以不同形状使用它的 map 类函数，
本应是合法的多态使用，本书实现会报错。完整的 Hindley–Milner 机制
用"泛化/实例化"让每个类型方案在使用点获得新鲜副本，可以解决；
spa 与本书的选择是讲清单态机制及其局限（第 12 章），把多态留作
概念性的注脚。读者只需记住：**TyFun 嵌套的表达力我们有，类型方案
泛化的表达力我们没有**，两者是不同维度的能力。

## 9.15 LLVM 自己的类型系统：为什么它不能替代类型分析

第 08 章生成的 IR 里每个值都有一个 LLVM 类型，读者自然会问：既然
LLVM 已经有类型系统，为什么还要自己造一层？本节给出原理性回答：
两个类型系统作用在不同的抽象层，回答不同的问题，且现代 LLVM 在
关键位置**主动放弃**了源级信息。

### 9.15.1 不透明指针抹掉了指向类型

从 LLVM 15 起，指针类型统一为不透明的 `ptr`：IR 里不再写出
"指向什么"，`i32*` 这样的带参指针类型成为历史。这对中间层是
合理简化（指针变换优化不必再维护指向类型），但对源级类型分析
意味着：**alloc E 产生的 ptr 在 LLVM 看来只是 ptr，它指向 int 还是
指向另一个指针，LLVM 不记录**。load/store 指令各自携带操作数类型
（`load i32, ptr %p`），指向类型只能从使用处逐条恢复、且不再是
指针值本身的属性。我们的 TyPtr 之所以必须携带分量 τ，正是要在
源级把这条被中间层抹掉的信息作为一等事实保留：分析"p 两次解引用
后是什么"时，需要 ptr(ptr(int)) 这样的嵌套形状，而在不透明指针
的 IR 里它只是两个 ptr。

### 9.15.2 LLVM 类型回答"表示是否良构"，不回答源程序问题

LLVM 的类型检查（verifyModule）关心的是 IR 是否良构：指令操作数
种类是否正确（如 br 的条件必须是 i1）、phi 的类型是否一致、函数
签名与调用是否匹配。它不回答、也无从回答源语言层面的问题：这个
TIP 函数被调用时实参个数对不对（IR 生成时 TIP 实参已被我们翻译成
固定个数的 i32，形状错误的程序在第 08 章的前端里根本不被阻止）、
这个指针解引用在源语言里是否合法、记录是否有被访问的字段。换言
之，LLVM 类型系统是**低层 IR 的良构性裁判**，我们的类型分析是
**源程序语义性质的推断器**；前者在编译管线的下游，后者在前端。

更一般地说，这是一切"借助工业编译器后端做分析"的项目必须认清的
分工：后端的类型、校验为后端自己的转换与代码生成服务，源级分析
的结论（变量形状、可能被调函数、可能别名）要由前端自己的数据结构
承载。第 08 章我们让 LLVM 当"执行与对照"的底座；本章起，类型知识
归我们自己管。两套类型形状上相似（都有 int、ptr、函数类型）、
精神上也都属结构观，但层次不同、互不替代。

### 9.15.3 函数签名的跨层翻译

TyFun 与 LLVM 函数类型还有一处微妙的语义错位。TIP 函数可接收
指针参数（形状 ptr(τ)），而第 08 章生成 IR 时所有 TIP 值统一翻译
为 i32（指针也以机器整数宽度传递）或 ptr；LLVM 看到的签名是固定
机器类型的序列，它无法据此判断两次调用传入的**源级形状**是否一致。
也就是说，源函数类型 `(ptr(int), int) -> int` 在跨进 IR 的那一刻
被"压平"为低层签名，形状信息只存在于我们的 TyFun 中。若源程序
里两次调用同一函数、一次传指针一次传整数，IR 层面可能照样生成
成功——这个错误只有我们自己的类型层拦得住。

一般化这条教训：**每次跨抽象层的翻译都可能丢失信息，分析必须把
它关心的信息在丢失之前固定在自己的表示里**。TyPtr 的分量、TyFun
的参数形状，都是为抵抗翻译压平而存在的。第 25 章之后做指针别名
分析时，同样的原则会以另一种形式出现：LLVM 不主动告诉你两个
ptr 是否别名，那是分析者自己要重建的源级事实。

## 9.16 可靠性的含义：良类型程序不走错

类型分析最终要对第 02 章的总框架交账：它的断言可靠意味着什么？
本节给出直觉性的回答，为第 17 章的经验检验和后续形式化论证铺路，
不展开完整证明。

### 9.16.1 Milner 的格言

R. Milner 有一句被反复引用的表述：**良类型的程序不会"走错"**
（well-typed programs cannot go wrong）。"走错"特指一类运行时
灾难：把一个值当作它不是的形状来用——解引用一个整数、按两个
参数调用只接受一个的函数、访问记录里不存在的字段、对 null 之外
的非指针取值。良类型意味着这些操作在程序的**任何**运行中都不会
发生：类型断言覆盖全部路径、全部输入，而不仅是测试到的情形。
注意它不承诺程序不产生错误结果（`1/0` 在 TIP 运行时另有语义）、
不承诺终止；它只排除"形状层面的非法操作"。这与第 02 章可靠性
的定义精确对齐：断言（每个使用点的操作数形状合法）对全部具体
执行成立，反例只能是一次真实的走错。

### 9.16.2 保持与进展：论证可靠性的两块积木

对这类结论的标准证明策略由两部分组成，这里给出思路而非证明。
**保持**（preservation，又称主题消减）：一次良类型的具体求值步骤
之后，结果仍具有相容类型——类型在执行中不被颠覆。**进展**
（progress）：良类型的表达式要么已算完，要么总能迈出下一步——
"卡住"（无可适用的求值规则，即走错）的情形只可能出现在形状
非法的操作上，而那些操作被类型规则排除。两者合起来：良类型程序
从合法状态出发（保持保证持续合法），永远不会卡住（进展排除
走错）。对 TIP，各语法构造的求值规则与第 10 章约束规则一一对应，
保持性的证明就是逐构造核对"约束施加的条件正是求值规则的前提"。
本书不要求读者写出这些证明，但要求读者能指出：**每条约束存在的
理由，都是某个求值规则的前提**——如 Deref 约束 τ(e)=ptr(τ) 对应
"只有指向某值的地址才能解引用"。约束不是人为规定，是具体语义
前提的形式化。

### 9.16.3 与第 17 章经验检验的关系

证明与经验检验在这里分工而非互相替代。原理上的可靠性论证覆盖
全部程序、全部运行，是终极依据；但它依赖"收集器忠实、求解器
正确"等人工实现环节，而实现可能有 bug。第 17 章将用第 08 章的
JIT 做经验性的补充：让分析对一批程序给出形状预测，再真实运行
这些程序、检查所有解引用/调用/字段访问处的具体值确为预测的形状。
经验检验不能证明可靠性（有限样本不覆盖全部运行），却能抓住实现
与规则之间的偏差。本章先把"预测"的数据结构造准。

### 9.16.4 类型擦除：类型知识只活在编译期

良类型程序运行时不再需要类型信息：整数就是机器整数，地址跳转时
被调函数的代码已经确定，记录字段在低层布局中按固定偏移访问。这
称为**类型擦除**（type erasure）——类型是编译期（这里是 tipa
运行期、目标程序运行之前）的知识，它指导检查（排除走错）与翻译
（决定布局与调用约定），然后消失。第 08 章的 JIT 对此是现成的
例证：tipa 先完成自己的前端工作、再让 ORC 执行不含任何 TIP 类型
痕迹的 IR。

擦除观回答了一个常见疑问："类型既然可靠，为什么运行时还会有
null 解引用之类的错误？"在我们的实现里，第 12 章的规则保证
**良类型**程序不发生这些错误；若程序员跳过类型检查、或类型系统
本就不精确（它对 null 只证明"是某个指针或空"，不证明"非空"），
错误仍可达。可靠性的范围严格等于类型规则能排除的范围，不多不少。

### 9.16.5 比较产生整数：一个设计决定的连锁后果

第 03 章把 `>`、`==` 的结果规定为整数 0/1 而非单独的布尔类型，
此处可以看清这个设计决定如何一路传导。类型层因此不需要 bool
构造子（9.4 的五个构造子已足），Binop 的六条规则统一为"两侧
int、结果 int"；条件位置（if/while）不要求专门的布尔形状，普通
int 即可——这与 C 的传统一致。在 IR 层（第 08 章），比较先产生
i1，再经 zext 变成 i32 以与 TIP 的 int 统一，条件分支前又把 i32
截断回 i1。一个源语言层面"不要 bool"的小决定，在表示层省了一个
构造子、在翻译层多了一对扩展/截断指令。

它对可靠性论证也有后果：类型层无法区分一个 int 是"算术结果"还是
"比较结果"，因此不能阻止把布尔当数值参与奇怪运算（TIP 认为这
本就合法）。**类型构造子的粒度决定了分析能区分什么**；想要区分，
就加构造子、承担更复杂的规则——这是后面所有抽象设计的基本权衡，
第 17 章选择符号域时会再次遇到。

### 9.16.6 错误发现时机：早与晚的质量经济学

可靠性讨论还隐含一个工程经济学命题：**错误被发现的位置离错误的
根源越近，修复成本越低**。类型分析在运行前、对全程序操作，因此
它把形状错误从"用户运行到某条偏僻路径才崩溃"提前到"构建一刻、
且精确定位到冲突的两个形状"。测试只能覆盖被执行路径，而类型规则
覆盖全部路径——一个从未被测试调用的函数里实参个数错了，类型检查
一样报得出。这不是类型分析特有的魔法，而是"在更早的阶段用更粗
粒度但全路径的知识换覆盖率"的一般原理；后面每一类静态分析都在
重复这一时间轴上的收益。

也应诚实指出早发现的边界：类型只能早发现**形状类**错误，对逻辑类
错误（算法写错、条件取反）它沉默。把类型检查当作质量的一部分而非
全部，是正确的使用姿态；过度期待"类型通过即程序正确"会失望，而
否定类型检查则是放弃了一笔几乎免费的全路径保险。第 17 章之后
读者会看到分析与测试如何互补共存：分析给全覆盖的粗结论，测试与
JIT 实验给精确但有限的验证。

### 9.16.7 经验检验为什么不能取代可靠性论证

第 17 章将用大量 JIT 运行给类型分析"验身"，有必要提前摆正它与
可靠性论证的关系，避免读者误以为测试够多即可免谈证明。经验检验
有两个不可逾越的限制：样本有限（只跑了被选程序与被选输入，无穷
的程序空间与输入空间未被覆盖）；观察点有限（只检查了显式插桩的
操作位置，一个未被想到的走错模式可能根本没被观测）。任何有限的
实验集都可能被精心（或偶然）绕过，因此它给的是"实现与规则暂未
发现偏差"的信心，不是"无偏差"的结论。

可靠性论证反过来：它对所有程序与所有运行一劳永逸，但只在"规则与
实现均正确"的假设下成立——而假设可能因一行代码错误落空。两者
因此构成双保险：论证定边界、实验查实现。本书在工程能力允许处
两者都做，且让它们的产物互相牵制——实验脚本本身也被纳入全绿
协议，一旦分析代码变更使预测与执行脱节，流水线立即报警。理解
这种关系后，读者既不会因"反正有测试"而轻视形式化，也不会因
"已证明可靠"而认为测试多余；静态分析的可信度正是建立在这两种
知识的叠加之上。

## 9.17 类型变量在分析谱系中的位置

把视野从 TIP 拉开：类型变量不是孤立的发明，它位于一条更长的
谱系中，认清这条谱系有助于后面十几章的学习。

### 9.17.1 逻辑变量与合一的由来

以变量表示未知、以规则生成等式、以合一求解，这一范式来自 J. A.
Robinson 1965 年的归结原理：其中的"逻辑变量"代表尚未确定的项，
合一算法在两式相容时求出最一般的变量绑定。它后来成为 Prolog 的
运算核心，也是 ML 类型推断（Hindley–Milner）的求解机制。我们在
第 11 章实现的就是该算法的教学版。理解这段渊源有一个实际收益：
合一所求的"解"有特殊性——当等式有解时，合一给出**最一般解**
（主解），所有其他解都是它的精化；因此类型推断不会在多个解之间
任意挑选，推断结果具有唯一性。这是类型等式与普通方程的一个深刻
差别，第 11 章会用"绑定只从变量指向项、且变量不被反复改向"的
机制保证这一性质。

### 9.17.2 与数据流方程的对照：两种未知，两种解法

第 13 章起将遇到另一种未知：程序点上"此刻可能有哪些值/哪些事实"
的集合。那里同样先占位（每个程序点一个未知量）、再按程序结构
列方程。但求解方式不同：数据流未知量取值于一个**格**（如集合，
可大可小、可在迭代中反复增长），靠单调迭代到达不动点；类型
未知量取值于类型项，靠一次性的合一绑定确定、不回头。两种范式的
分野本章先埋下对照：**结构等式有主解→合一；格上方程只有不动点→
迭代**。spa 全书正是先讲类型（约束+合一），再讲格与数据流
（方程+不动点），第 13 章开始我们进入后者，读者会看到"先占位"
的思想复现、而求解器完全换了一副面孔。

### 9.17.3 记号预告：定型环境与断言

后面章节（及 spa 原著）会用一种标准记号表达"在什么前提下，什么
有什么类型"：

```
Γ ⊢ E : τ
```

读作"在环境 Γ 下，表达式 E 的类型为 τ"。环境 Γ 是名字到类型的
有限映射，记录当前可见的形参、局部变量、函数名各是什么形状；
它就是符号表（第 06 章的产物）在类型层的对应物——作用域结构
相同，表里装的从"声明身份"换成"声明的类型"。语句的断言形式类似
（Γ ⊢ S ⊢ Γ′，表示执行语句后环境被更新），第 10 章收集器实际
采用的"约束列表"是同一规则体系的另一种簿记形式：每写一条
τ₁ = τ₂ 的约束，等价于在推导树上记录一次必须成立的定型步骤。

为什么本书代码不直接实现成"带 Γ 的递归定型函数"？因为那种写法把
"规则应用"与"求解"混在一起（回到 9.2 的顺序依赖问题），对含未知
的程序必须在 Γ 中允许类型变量、并延后判定——一旦允许延后，显式
记录约束反而更干净。记号 Γ ⊢ E : τ 主要用于**论证**：第 10 章讲
每条生成规则时可以对照它在断言体系里的原型，读者由此看到收集器
不是启发式的经验代码，而是形式规则的机械实现。

### 9.17.4 主解性质的工程意义

合一在有解时给出最一般解，这条性质不只是理论上的优美，对工具行为
有两个直接后果。其一，推断结果对求解顺序不敏感（在正确实现下）：
无论先处理哪条约束，最终的主解相同——这把 9.2 "换个遍历顺序结论
就可能不同"的病根彻底拔除，也使输出可复现。其二，主解保留了全部
合法使用的可能：对 `id(x){return x;}`，主解 (α)->α 不擅自把 α
定为某个具体形状，因此"哪里迫使 α 落地、哪里没有"在解中清晰可见；
排查类型错误时，可以沿着"变量是被哪一条约束绑定的"追溯到具体源
程序位置。若求解器在信息不足时任意挑选（如默认 α=int），错误会
延迟爆发、诊断失去定位。主解因此既是逻辑性质，也是诊断可用性的
基础。

## 9.18 冻结文件逐个看：第 10 章将消费什么

第 9.20 节嵌入的文件较多，本节给出一份精确的"消费清单"，说明第
10 章的收集器具体读取哪些已有定义。这样读者在阅读嵌入代码时可以
带着问题看，而不是平均用力。

`ast.hpp` 提供表达式类族，十个派生类覆盖 TIP 全部值产生形式：
IntLit（字面整数，形状直接为 int）、InputE（输入，形状为 int
但值未知）、VarRef（经名字层找到声明形状）、Binop（六个算子
Add/Sub/Mul/Div/Gt/Eq，两侧 int、结果 int）、CallE（callee 可为
任意表达式——因一等函数，被调者未必是名字）、Deref、AddrOf
（注意 AddrOf 直接携带字段名 name，因为文法限定 &Id）、AllocE、
NullE、RecLit（字段名到表达式的配对序列）、FieldA（记录表达式
加字段名）。语句侧与类型相关的只有 AssignS（两侧形状必须相同）
与 ReturnS（返回表达式确定函数返回类型）；IfS/WhileS 的条件在
TIP 中也是 int，第 10 章对它们同样施加"条件为 int"。FunDecl
携带 params、vars 两组名字与 body、ret，是函数类型构造的依据；
ProgramA 是函数声明序列。

`symtab.hpp` 提供收集器所需的全部名字信息：Symbol 的三种 Kind
（Fun/Param/Local）区分声明种类——函数名的声明形状是 TyFun，
参数与局部变量的声明形状待定；Bindings.uses 把每个 VarRef 指到
Symbol，使"使用点形状 = 声明形状"的条件可以机械建立；
Bindings.scopes 持有各函数作用域的所有权（因此其中指针有效），
供 AddrOf 等需要跨作用域查名字的规则使用；global 是函数名所在
的全局作用域。第 06 章"两遍解析、先注册全部函数名"的设计，使
得收集器在处理任何函数体时，调用到的前向函数也已在 global 中
可查——9.2.1 的前向调用困惑在名字层已被解开，类型层坐享其成。

`TIP.g4` 提供的保证是：AST 里出现的构造与类型规则一一对应，不
会有文法允许、类型层没有准备的节点。`main.cpp` 中的 parseFile
封装"解析+AST+名字解析"及 2/3 退出码，是 --check、--emit-ir、
--run 三个分支共同的入口；第 10 章只替换 printTypeDemo 的位置。
其余 pretty、CFG 相关组件不被类型层消费，列出以求完整。

## 9.19 本章概念问答

**问：类型变量和第 08 章 IR 里的 SSA 虚拟寄存器是一回事吗？**
不是，但角色相似。SSA 寄存器代表一次具体计算的结果，其 LLVM
类型在 IR 生成时已写定；类型变量代表一个**形状未知**的源级位置，
待第 11 章求解。前者是值的身份，后者是形状的占位。

**问：既然每个 int 都新建 TyInt 对象，两个 int 会不会被判为
不等？** 不会。相等性按结构判定（9.13），TyInt 无分量，任意两个
TyInt 结构恒等；对象地址的不同不进入判定。合一比较的是构造子
种类（typeid）而非对象身份。

**问：计数器在程序中途"归零重开"行不行？** 不行，且无需如此。
编号只需唯一、不需从 1 连续才有意义；归零必然重号，重号使两个
不同未知量坍缩为一个，分析立即出错。编号是全局资源。

**问：为什么记录字段用序列存，不怕顺序写反？** 因为相等规则
（合一）按字段名在另一侧查找对应项、不按位置（9.5.3）。顺序
只影响存储与打印，不影响判定；expected 中记录的打印顺序由收集器
遍历字段名的固定方式决定，仍然逐字节稳定。

**问：null 的类型是什么？本章为什么不给规则？** 直觉上 null 是
"空指针"，应与所有指针形状相容，又不等于任何具体的 ptr(τ)。
它需要 TyNull 构造与合一中的特殊规则（null 与 ptr 相容、与 int
冲突），第 12 章专门处理；本章只预告这一不规则性的存在。

**问：类型分析能查出除零吗？** 不能。`1/0` 两侧形状都是 int，
类型层完全合法；除零是值层面的性质，而类型层主动放弃了值信息
（9.1.2）。要查除零需用更精细的常量/区间分析，第 20 章之后的
内容。

**问：为什么不直接在 AST 节点里塞一个类型字段、遍历中填好？**
那正是 9.2 失败的直接算法变体：填入顺序影响结果，环依赖无法处理，
且条件（约束）没有被显式保存、无法集中报告错误。两阶段架构
（9.3.2）用"约束数据 + 独立求解"换顺序无关性与可论证性。

**问：本章 tipa 对类型错误程序毫无反应，不算退步吗？** 本章
**尚未实现类型分析**，只有它的表示层；反应能力在第 11 章一次性
到位，并在第 12 章覆盖五类错误。分章是教学拆解，不是能力倒退：
前端的语法/名字检查（退出码 2/3）在本章全程有效。

**问：TyVar 直接带一个指向绑定结果的指针，不是比编号+映射更
省事？** 这会把"变量"与"变量的解"合并成一个可变对象，求解前各处
持有的同一对象将在绑定时被全体观察到改动——看似方便，实则破坏
9.4.1 "项一经构造不被改动"的约定：绑定顺序、回溯（occur 失败后
撤销）都会污染共享对象，且无法同时表示"尝试性绑定"。编号+置换
映射让绑定是外部的、可丢弃的数据，求解过程因此可以简单且不产生
副作用。

**问：函数参数为什么不用 TyRec（命名参数）统一表示？** 参数有
固定次序、按位置匹配；记录字段无序、按名字匹配（9.5.3）。用一种
结构表示两种匹配语义，合一规则就要处处特判；两种构造各司其职，
规则反而最短。形式化表示的选择应让**规则简单**，而非让构造子
数量最少。

**问：多个函数都有形参 x，它们的类型变量会混吗？** 不会。变量
是按声明实体（Symbol）发的，不是按名字发的；第 10 章的收集器
逐个函数处理、为每个 Param/Local Symbol 单独发变量，同名不同属
的 x 各有编号。第 06 章名字解析已把"同一个名字"细分为"不同的
声明实体"，类型层在这个更细的身份上工作。

**问：为什么要能表示参数个数为零的函数？main 就总是零参。**
文法允许 `f(){...}`，TyFun 的参数序列自然可以为空；打印规则对空
序列的处理（9.8）保证 `() -> int` 正确显示。零参不是特殊构造，
只是序列长度为零这一普通情形，规则无须为此分支。

**问：类型项需要可比较大小（排序）吗？** 表示本身不需要——相等
按结构、求解靠合一，没有"谁大谁小"的问题。大小关系是第 13 章
格的概念（近似的精粗），类型项世界里只有"相同/矛盾/待定"三种
关系。把这两种关系分清，读后面的格章节时才不会误用类型直觉。

**问：本章的代码能直接被第 13 章之后的分析复用吗？** 部分能。
Tp/TyVar 是通用的"结构化未知项"设施，但格分析的元素（集合、
区间）有自己的表示与并/交运算，不套用 TyInt/TyPtr。复用的是
思想（先占位、形式化、可打印），不是类定义；本书每一类分析都为
自己的抽象域给出最小表示。

**问：把所有类型项都做成不可变对象，求解时岂不是要大量新建？**
是的，但量级很小：合一只在变量绑定处写入映射，不重建项；只有
打印"归一后形状"时（第 11 章 normalize）才递归重建一次，每个项
至多遍历一遍。不可变 + 外部映射的组合，总工作量仍是类型项规模的
线性量级。

**问：记录和指针谁更"难分析"？** 难点性质不同。记录的难在宽度
事实分散（9.13.1）与按名匹配，但形状规则封闭；指针的难在别名——
指针分析要回答"两个指针是否可能指向同一处"，那是流敏感、可能
近二次复杂度的问题（第 27 章）。类型层只回答形状，两者在此难度
相当；一旦进入流分析，指针深得多。

**问：本章学完，读者应当能独立做出什么？** 三件事：对任何小规模
TIP 函数，手画其类型结构、标出共享的变量（如 9.12）；解释类型

```cpp
// file: src/ast.hpp
// AST 定义：AST 是去掉了括号、分号等语法噪音的程序结构。
// 接口自本章起冻结，后续所有分析（名字、CFG、类型、格……）都在此之上工作。
#pragma once

#include <memory>
#include <string>
#include <utility>
#include <vector>

namespace tip {

enum class BOp { Add, Sub, Mul, Div, Gt, Eq };

struct Expr {
    virtual ~Expr() = default;
};
struct IntLit : Expr {
    int v;
    explicit IntLit(int value) : v(value) {}
};
struct VarRef : Expr {
    std::string name;
    explicit VarRef(std::string n) : name(std::move(n)) {}
};
struct InputE : Expr {};
struct Binop : Expr {
    BOp op;
    std::unique_ptr<Expr> l, r;
    Binop(BOp o, std::unique_ptr<Expr> lhs, std::unique_ptr<Expr> rhs)
        : op(o), l(std::move(lhs)), r(std::move(rhs)) {}
};
struct CallE : Expr {
    std::unique_ptr<Expr> callee;
    std::vector<std::unique_ptr<Expr>> args;
    CallE(std::unique_ptr<Expr> fn, std::vector<std::unique_ptr<Expr>> as)
        : callee(std::move(fn)), args(std::move(as)) {}
};
struct Deref : Expr {
    std::unique_ptr<Expr> e;
    explicit Deref(std::unique_ptr<Expr> p) : e(std::move(p)) {}
};
struct AddrOf : Expr {                       // spa: & Id
    std::string name;
    explicit AddrOf(std::string n) : name(std::move(n)) {}
};
struct AllocE : Expr {
    std::unique_ptr<Expr> e;
    explicit AllocE(std::unique_ptr<Expr> init) : e(std::move(init)) {}
};
struct NullE : Expr {};
struct RecLit : Expr {
    std::vector<std::pair<std::string, std::unique_ptr<Expr>>> fields;
    explicit RecLit(std::vector<std::pair<std::string, std::unique_ptr<Expr>>> fs)
        : fields(std::move(fs)) {}
};
struct FieldA : Expr {
    std::unique_ptr<Expr> e;
    std::string field;
    FieldA(std::unique_ptr<Expr> record, std::string f)
        : e(std::move(record)), field(std::move(f)) {}
};

struct Stmt {
    virtual ~Stmt() = default;
};
// target 只会是 VarRef / FieldA / Deref，文法 lvalue 已限定。
struct AssignS : Stmt {
    std::unique_ptr<Expr> target, value;
    AssignS(std::unique_ptr<Expr> t, std::unique_ptr<Expr> v)
        : target(std::move(t)), value(std::move(v)) {}
};
struct OutputS : Stmt {
    std::unique_ptr<Expr> e;
    explicit OutputS(std::unique_ptr<Expr> x) : e(std::move(x)) {}
};
struct IfS : Stmt {
    std::unique_ptr<Expr> cond;
    std::unique_ptr<Stmt> then, els;
    IfS(std::unique_ptr<Expr> c, std::unique_ptr<Stmt> t, std::unique_ptr<Stmt> e)
        : cond(std::move(c)), then(std::move(t)), els(std::move(e)) {}
};
struct WhileS : Stmt {
    std::unique_ptr<Expr> cond;
    std::unique_ptr<Stmt> body;
    WhileS(std::unique_ptr<Expr> c, std::unique_ptr<Stmt> b)
        : cond(std::move(c)), body(std::move(b)) {}
};
struct BlockS : Stmt {
    std::vector<std::unique_ptr<Stmt>> ss;
    explicit BlockS(std::vector<std::unique_ptr<Stmt>> v) : ss(std::move(v)) {}
};
struct ReturnS : Stmt {
    std::unique_ptr<Expr> e;
    explicit ReturnS(std::unique_ptr<Expr> x) : e(std::move(x)) {}
};

struct FunDecl {
    std::string name;
    std::vector<std::string> params;
    std::vector<std::string> vars;
    std::unique_ptr<Stmt> body;
    std::unique_ptr<ReturnS> ret;
};

struct ProgramA {
    std::vector<std::unique_ptr<FunDecl>> funs;
};

}  // namespace tip
```

```cpp
// （本工具链 C++ runtime 的 visitor 以 std::any 传值，而 std::any 不能持有
```

```cpp
// file: src/ast_build.cpp
#include "ast_build.hpp"

#include <utility>
#include <vector>

namespace tip {

std::unique_ptr<ProgramA> AstBuilder::build(TIPParser::ProgramContext *tree) {
    auto program = std::make_unique<ProgramA>();
    for (auto *fc : tree->function()) program->funs.push_back(buildFun(fc));
    return program;
}

std::unique_ptr<FunDecl> AstBuilder::buildFun(TIPParser::FunctionContext *ctx) {
    auto f = std::make_unique<FunDecl>();
    f->name = ctx->IDENT()->getText();
    if (ctx->params()) {
        for (auto *p : ctx->params()->IDENT()) f->params.push_back(p->getText());
    }
    if (ctx->varDecls()) {
        for (auto *v : ctx->varDecls()->IDENT()) f->vars.push_back(v->getText());
    }

    std::vector<std::unique_ptr<Stmt>> body;
    for (auto *sc : ctx->stmt()) body.push_back(buildStmt(sc));
    f->body = std::make_unique<BlockS>(std::move(body));

    f->ret = std::make_unique<ReturnS>(buildExpr(ctx->expr()));
    return f;
}

std::unique_ptr<Expr> AstBuilder::buildLvalue(TIPParser::LvalueContext *lv) {
    std::unique_ptr<Expr> base;
    std::string field;
    if (auto *d = dynamic_cast<TIPParser::DirectLvalueContext *>(lv)) {
        base = std::make_unique<VarRef>(d->IDENT(0)->getText());
        if (d->IDENT().size() == 2) field = d->IDENT(1)->getText();
    } else {
        auto *p = dynamic_cast<TIPParser::PointerLvalueContext *>(lv);
        base = std::make_unique<Deref>(buildExpr(p->expr()));
        if (p->IDENT()) field = p->IDENT()->getText();
    }
    if (!field.empty())
        return std::make_unique<FieldA>(std::move(base), std::move(field));
    return base;
}

std::unique_ptr<Expr> AstBuilder::buildExpr(TIPParser::ExprContext *ctx) {
    if (auto *c = dynamic_cast<TIPParser::IntExprContext *>(ctx))
        return std::make_unique<IntLit>(std::stoi(c->INT()->getText()));
    if (auto *c = dynamic_cast<TIPParser::VarExprContext *>(ctx))
        return std::make_unique<VarRef>(c->IDENT()->getText());
    if (dynamic_cast<TIPParser::InputExprContext *>(ctx))
        return std::make_unique<InputE>();
    if (dynamic_cast<TIPParser::NullExprContext *>(ctx))
        return std::make_unique<NullE>();
    if (auto *c = dynamic_cast<TIPParser::ParenExprContext *>(ctx))
        return buildExpr(c->expr());

    if (auto *c = dynamic_cast<TIPParser::AddExprContext *>(ctx)) {
        const BOp op = c->PLUS() ? BOp::Add : BOp::Sub;
        return std::make_unique<Binop>(op, buildExpr(c->expr(0)), buildExpr(c->expr(1)));
    }
    if (auto *c = dynamic_cast<TIPParser::MulExprContext *>(ctx)) {
        const BOp op = c->STAR() ? BOp::Mul : BOp::Div;
        return std::make_unique<Binop>(op, buildExpr(c->expr(0)), buildExpr(c->expr(1)));
    }
    if (auto *c = dynamic_cast<TIPParser::CmpExprContext *>(ctx)) {
        const BOp op = c->GT() ? BOp::Gt : BOp::Eq;
        return std::make_unique<Binop>(op, buildExpr(c->expr(0)), buildExpr(c->expr(1)));
    }
    if (auto *c = dynamic_cast<TIPParser::NegExprContext *>(ctx)) {
        // TIP 没有负数字面量 token，-E 即 0-E。
        return std::make_unique<Binop>(BOp::Sub, std::make_unique<IntLit>(0),
                                       buildExpr(c->expr()));
    }
    if (auto *c = dynamic_cast<TIPParser::CallExprContext *>(ctx)) {
        std::vector<std::unique_ptr<Expr>> args;
        if (c->args())
            for (auto *a : c->args()->expr()) args.push_back(buildExpr(a));
        return std::make_unique<CallE>(buildExpr(c->expr()), std::move(args));
    }
    if (auto *c = dynamic_cast<TIPParser::FieldExprContext *>(ctx))
        return std::make_unique<FieldA>(buildExpr(c->expr()), c->IDENT()->getText());
    if (auto *c = dynamic_cast<TIPParser::DerefExprContext *>(ctx))
        return std::make_unique<Deref>(buildExpr(c->expr()));
    if (auto *c = dynamic_cast<TIPParser::AddrExprContext *>(ctx))
        return std::make_unique<AddrOf>(c->IDENT()->getText());
    if (auto *c = dynamic_cast<TIPParser::AllocExprContext *>(ctx))
        return std::make_unique<AllocE>(buildExpr(c->expr()));
    if (auto *c = dynamic_cast<TIPParser::RecExprContext *>(ctx)) {
        std::vector<std::pair<std::string, std::unique_ptr<Expr>>> fields;
        for (auto *fc : c->field())
            fields.emplace_back(fc->IDENT()->getText(), buildExpr(fc->expr()));
        return std::make_unique<RecLit>(std::move(fields));
    }
    return nullptr;  // 解析成功时不会到达
}

std::unique_ptr<Stmt> AstBuilder::buildStmt(TIPParser::StmtContext *ctx) {
    if (auto *c = dynamic_cast<TIPParser::AssignStmtContext *>(ctx))
        return std::make_unique<AssignS>(buildLvalue(c->lvalue()), buildExpr(c->expr()));
    if (auto *c = dynamic_cast<TIPParser::OutputStmtContext *>(ctx))
        return std::make_unique<OutputS>(buildExpr(c->expr()));
    if (auto *c = dynamic_cast<TIPParser::IfStmtContext *>(ctx)) {
        std::unique_ptr<Stmt> els;
        if (c->stmt().size() == 2) els = buildStmt(c->stmt(1));
        return std::make_unique<IfS>(buildExpr(c->expr()), buildStmt(c->stmt(0)),
                                     std::move(els));
    }
    if (auto *c = dynamic_cast<TIPParser::WhileStmtContext *>(ctx))
        return std::make_unique<WhileS>(buildExpr(c->expr()), buildStmt(c->stmt()));
    if (auto *c = dynamic_cast<TIPParser::BlockStmtContext *>(ctx)) {
        std::vector<std::unique_ptr<Stmt>> ss;
        for (auto *sc : c->stmt()) ss.push_back(buildStmt(sc));
        return std::make_unique<BlockS>(std::move(ss));
    }
    return nullptr;  // 解析成功时不会到达
}

std::unique_ptr<ProgramA> buildAst(TIPParser::ProgramContext *tree) {
    return AstBuilder{}.build(tree);
}

}  // namespace tip
```

```cpp
// file: src/pretty.cpp
#include "pretty.hpp"

#include <string>

namespace tip {

namespace {

// 表达式打印为前缀式：运算符与符号的对照表。
std::string exprText(const Expr *e) {
    if (const auto *x = dynamic_cast<const IntLit *>(e)) return std::to_string(x->v);
    if (const auto *x = dynamic_cast<const VarRef *>(e)) return x->name;
    if (dynamic_cast<const InputE *>(e)) return "input";
    if (dynamic_cast<const NullE *>(e)) return "null";

    if (const auto *x = dynamic_cast<const Binop *>(e)) {
        const char *sym = "+";
        switch (x->op) {
            case BOp::Add: sym = "+"; break;
            case BOp::Sub: sym = "-"; break;
            case BOp::Mul: sym = "*"; break;
            case BOp::Div: sym = "/"; break;
            case BOp::Gt: sym = ">"; break;
            case BOp::Eq: sym = "=="; break;
        }
        return "(" + std::string(sym) + " " + exprText(x->l.get()) + " " +
               exprText(x->r.get()) + ")";
    }
    if (const auto *x = dynamic_cast<const CallE *>(e)) {
        std::string s = "(call " + exprText(x->callee.get());
        for (const auto &a : x->args) s += " " + exprText(a.get());
        return s + ")";
    }
    if (const auto *x = dynamic_cast<const Deref *>(e))
        return "(* " + exprText(x->e.get()) + ")";
    if (const auto *x = dynamic_cast<const AddrOf *>(e)) return "(& " + x->name + ")";
    if (const auto *x = dynamic_cast<const AllocE *>(e))
        return "(alloc " + exprText(x->e.get()) + ")";
    if (const auto *x = dynamic_cast<const FieldA *>(e))
        return "(. " + exprText(x->e.get()) + " " + x->field + ")";
    if (const auto *x = dynamic_cast<const RecLit *>(e)) {
        std::string s = "{";
        for (size_t i = 0; i < x->fields.size(); ++i) {
            if (i) s += ", ";
            s += x->fields[i].first + ": " + exprText(x->fields[i].second.get());
        }
        return s + "}";
    }
    return "<unknown expr>";
}

std::string indent(int level) { return std::string(static_cast<size_t>(level) * 2, ' '); }

// 语句打印带缩进，一条语句一行（块内多行）。
void stmtText(const Stmt *s, int level, std::string &out) {
    if (const auto *x = dynamic_cast<const AssignS *>(s)) {
        out += indent(level) + exprText(x->target.get()) + " = " +
               exprText(x->value.get()) + " ;\n";
        return;
    }
    if (const auto *x = dynamic_cast<const OutputS *>(s)) {
        out += indent(level) + "output " + exprText(x->e.get()) + " ;\n";
        return;
    }
    if (const auto *x = dynamic_cast<const ReturnS *>(s)) {
        out += indent(level) + "return " + exprText(x->e.get()) + " ;\n";
        return;
    }
    if (const auto *x = dynamic_cast<const IfS *>(s)) {
        out += indent(level) + "if (" + exprText(x->cond.get()) + ")\n";
        stmtText(x->then.get(), level + 1, out);
        if (x->els) {
            out += indent(level) + "else\n";
            stmtText(x->els.get(), level + 1, out);
        }
        return;
    }
    if (const auto *x = dynamic_cast<const WhileS *>(s)) {
        out += indent(level) + "while (" + exprText(x->cond.get()) + ")\n";
        stmtText(x->body.get(), level + 1, out);
        return;
    }
    if (const auto *x = dynamic_cast<const BlockS *>(s)) {
        out += indent(level) + "{\n";
        for (const auto &st : x->ss) stmtText(st.get(), level + 1, out);
        out += indent(level) + "}\n";
        return;
    }
    out += indent(level) + "<unknown stmt>\n";
}

}  // namespace

std::string printProgram(const ProgramA &program) {
    std::string out;
    for (const auto &f : program.funs) {
        std::string paramList;
        for (size_t i = 0; i < f->params.size(); ++i) {
            if (i) paramList += ",";
            paramList += f->params[i];
        }
        out += f->name + "(" + paramList + ") {\n";
        if (!f->vars.empty()) {
            out += indent(1) + "var ";
            for (size_t i = 0; i < f->vars.size(); ++i) {
                if (i) out += ",";
                out += f->vars[i];
            }
            out += " ;\n";
        }
        // 函数体是 BlockS；打印其内部语句而不是再嵌一层花括号。
        const auto *body = dynamic_cast<const BlockS *>(f->body.get());
        for (const auto &st : body->ss) stmtText(st.get(), 1, out);
        stmtText(f->ret.get(), 1, out);
        out += "}\n";
    }
    return out;
}

}  // namespace tip
```

```cpp
// 符号表与名字解析：把 AST 上的每个 VarRef 绑定到它的声明

namespace tip {

struct Symbol {

    std::string name;
    const FunDecl *fun;          // Fun: 指向自身声明; Param/Local: 指向所属函数
};

struct Scope {

    std::vector<std::unique_ptr<Scope>> scopes;

    std::map<const VarRef *, const Symbol *> uses;  // 解析成功的使用点
};
```

```cpp
// file: src/symtab.cpp
#include "symtab.hpp"

#include <utility>

namespace tip {

namespace {

// 解析器在遍历 AST 的同时完成绑定与诊断收集。
struct Resolver {
    Bindings bindings;
    Scope *current = nullptr;
    const FunDecl *owner = nullptr;

    void declare(const std::string &name, Symbol::Kind kind) {
        if (current->table.count(name)) {
            bindings.errors.push_back({"error: redeclared '" + name + "'"});
            return;  // 保留先声明者，后声明被忽略
        }
        current->table.emplace(name, Symbol{kind, name, owner});
    }

    void resolveExpr(const Expr *e) {
        if (const auto *x = dynamic_cast<const VarRef *>(e)) {
            const Symbol *s = current->lookup(x->name);
            if (!s) {
                bindings.errors.push_back({"error: undeclared '" + x->name + "'"});
            } else {
                bindings.uses[x] = s;
            }
            return;
        }
        if (const auto *x = dynamic_cast<const Binop *>(e)) {
            resolveExpr(x->l.get());
            resolveExpr(x->r.get());
            return;
        }
        if (const auto *x = dynamic_cast<const CallE *>(e)) {
            resolveExpr(x->callee.get());
            for (const auto &a : x->args) resolveExpr(a.get());
            return;
        }
        if (const auto *x = dynamic_cast<const Deref *>(e)) return resolveExpr(x->e.get());
        if (const auto *x = dynamic_cast<const AllocE *>(e)) return resolveExpr(x->e.get());
        if (const auto *x = dynamic_cast<const FieldA *>(e)) {
            resolveExpr(x->e.get());  // 字段名不是变量，无需解析
            return;
        }
        if (const auto *x = dynamic_cast<const RecLit *>(e)) {
            for (const auto &f : x->fields) resolveExpr(f.second.get());
            return;
        }
        // IntLit / InputE / AddrOf / NullE：无变量使用。
    }

    void resolveStmt(const Stmt *s) {
        if (const auto *x = dynamic_cast<const AssignS *>(s)) {
            resolveExpr(x->target.get());
            resolveExpr(x->value.get());
            return;
        }
        if (const auto *x = dynamic_cast<const OutputS *>(s)) return resolveExpr(x->e.get());
        if (const auto *x = dynamic_cast<const IfS *>(s)) {
            resolveExpr(x->cond.get());
            resolveStmt(x->then.get());
            if (x->els) resolveStmt(x->els.get());
            return;
        }
        if (const auto *x = dynamic_cast<const WhileS *>(s)) {
            resolveExpr(x->cond.get());
            resolveStmt(x->body.get());
            return;
        }
        if (const auto *x = dynamic_cast<const BlockS *>(s)) {
            for (const auto &st : x->ss) resolveStmt(st.get());
            return;
        }
        if (const auto *x = dynamic_cast<const ReturnS *>(s)) return resolveExpr(x->e.get());
    }
};

}  // namespace

const Symbol *Scope::lookup(const std::string &name) const {
    auto it = table.find(name);
    if (it != table.end()) return &it->second;
    return parent ? parent->lookup(name) : nullptr;
}

Bindings resolveNames(ProgramA &program) {
    Resolver resolver;
    resolver.bindings.global = Scope(nullptr);
    Scope *global = &resolver.bindings.global;

    // 第一遍：所有函数名进入全局作用域。
    for (const auto &f : program.funs) {
        if (global->table.count(f->name)) {
            resolver.bindings.errors.push_back({"error: redeclared '" + f->name + "'"});
            continue;
        }
        global->table.emplace(f->name, Symbol{Symbol::Fun, f->name, f.get()});
    }

    // 第二遍：每个函数开自己的作用域，父作用域是全局表；
    // 作用域所有权交给 Bindings，遍历结束后符号依然存活。
    for (const auto &f : program.funs) {
        auto functionScope = std::make_unique<Scope>(global);
        resolver.current = functionScope.get();
        resolver.owner = f.get();

        for (const std::string &p : f->params) resolver.declare(p, Symbol::Param);
        for (const std::string &v : f->vars) resolver.declare(v, Symbol::Local);

        resolver.resolveStmt(f->body.get());
        resolver.resolveStmt(f->ret.get());

        resolver.current = nullptr;
        resolver.bindings.scopes.push_back(std::move(functionScope));
    }
    return std::move(resolver.bindings);
}

}  // namespace tip
```

```cpp
// LLVM IR 生成：把 AST 翻译成 LLVM Module。
// 本章只覆盖整数核心：算术、比较、input/output、if/while、直接函数调用；
```

```cpp
IRGen::IRGen()
    : ctx(std::make_unique<LLVMContext>()),
      mod(std::make_unique<Module>("tip", *ctx)),
      b(std::make_unique<IRBuilder<>>(*ctx)) {
    // 运行时入口先声明：input 无参返回 i32，output 吃一个 i32。
    auto *i32 = Type::getInt32Ty(*ctx);
    rtInput_ = mod->getOrInsertFunction(
        "tip_input", FunctionType::get(i32, false));
    rtOutput_ = mod->getOrInsertFunction(
        "tip_output", FunctionType::get(Type::getVoidTy(*ctx), {i32}, false));
}

namespace {

// TIP 的 main 改名 tip_main：真正的 @main 是我们生成的 C 入口。
std::string emitName(const std::string &name) {
    return name == "main" ? "tip_main" : name;
}

}  // namespace

void IRGen::gen(const ProgramA &program, const Bindings &resolved) {
    bindings = &resolved;

    // 先创建全部函数（含类型），函数体互相前向调用时也能查到声明。
    auto *i32 = Type::getInt32Ty(*ctx);
    for (const auto &f : program.funs) {
        std::vector<Type *> args(f->params.size(), i32);
        auto *ft = FunctionType::get(i32, args, false);
        Function::Create(ft, Function::ExternalLinkage,
                         emitName(f->name), *mod);
    }

    for (size_t i = 0; i < program.funs.size(); ++i) {
        const auto &f = program.funs[i];
        cur = f.get();
        genFun(f.get(), resolved.scopes[i].get());
    }

    const FunDecl *mainFun = nullptr;
    for (const auto &f : program.funs)
        if (f->name == "main") mainFun = f.get();
    if (!mainFun) throw std::runtime_error("program has no main");
    genWrapper(mainFun);
}

void IRGen::genFun(const FunDecl *f, Scope *scope) {
    auto *fn = llvm::cast<Function>(mod->getFunction(emitName(f->name)));
    auto *entry = BasicBlock::Create(*ctx, "entry", fn);
    b->SetInsertPoint(entry);

    // 形参：alloca 槽位 + 存入实参；var 局部：alloca + 零初始化。
    for (size_t j = 0; j < f->params.size(); ++j) {
        const Symbol *s = &scope->table.at(f->params[j]);
        auto *slot = b->CreateAlloca(b->getInt32Ty(), nullptr, f->params[j]);
        b->CreateStore(fn->getArg(j), slot);
        locals[s] = slot;
    }
    for (const std::string &v : f->vars) {
        const Symbol *s = &scope->table.at(v);
        auto *slot = b->CreateAlloca(b->getInt32Ty(), nullptr, v);
        b->CreateStore(b->getInt32(0), slot);
        locals[s] = slot;
    }

    stmt(f->body.get());
    b->CreateRet(expr(f->ret->e.get()));
}

Value *IRGen::expr(const Expr *e) {
    if (const auto *x = dynamic_cast<const IntLit *>(e))
        return ConstantInt::get(b->getInt32Ty(), x->v, true);

    if (const auto *x = dynamic_cast<const VarRef *>(e)) {
        const Symbol *s = bindings->uses.at(x);
        return b->CreateLoad(b->getInt32Ty(), locals.at(s), x->name);
    }

    if (dynamic_cast<const InputE *>(e))
        return b->CreateCall(rtInput_);

    if (const auto *x = dynamic_cast<const Binop *>(e)) {
        Value *l = expr(x->l.get());
        Value *r = expr(x->r.get());
        switch (x->op) {
            case BOp::Add: return b->CreateAdd(l, r);
            case BOp::Sub: return b->CreateSub(l, r);
            case BOp::Mul: return b->CreateMul(l, r);
            case BOp::Div: return b->CreateSDiv(l, r);
            case BOp::Gt: {
                Value *p = b->CreateICmpSGT(l, r);
                return b->CreateZExt(p, b->getInt32Ty());
            }
            case BOp::Eq: {
                Value *p = b->CreateICmpEQ(l, r);
                return b->CreateZExt(p, b->getInt32Ty());
            }
        }
    }

    if (const auto *x = dynamic_cast<const CallE *>(e)) {
        const auto *nameUse = dynamic_cast<const VarRef *>(x->callee.get());
        if (!nameUse)
            throw std::runtime_error("ch08: 间接调用留待第 27 章");
        const Symbol *s = bindings->uses.at(nameUse);
        if (s->kind != Symbol::Fun)
            throw std::runtime_error("ch08: 间接调用留待第 27 章");
        auto *callee = mod->getFunction(emitName(s->name));
        std::vector<Value *> args;
        for (const auto &a : x->args) args.push_back(expr(a.get()));
        return b->CreateCall(callee, args);
    }

    throw std::runtime_error("ch08: 指针与记录构造留待第 27 章");
}

void IRGen::stmt(const Stmt *s) {
    if (const auto *x = dynamic_cast<const AssignS *>(s)) {
        const auto *target = dynamic_cast<const VarRef *>(x->target.get());
        if (!target)
            throw std::runtime_error("ch08: 经指针/字段写入留待第 27 章");
        const Symbol *sym = bindings->uses.at(target);
        b->CreateStore(expr(x->value.get()), locals.at(sym));
        return;
    }

    if (const auto *x = dynamic_cast<const OutputS *>(s)) {
        b->CreateCall(rtOutput_, {expr(x->e.get())});
        return;
    }

    if (const auto *x = dynamic_cast<const IfS *>(s)) {
        Function *fn = b->GetInsertBlock()->getParent();
        auto *thenBB = BasicBlock::Create(*ctx, "then", fn);
        auto *elseBB = BasicBlock::Create(*ctx, "else", fn);
        auto *mergeBB = BasicBlock::Create(*ctx, "merge", fn);

        Value *cc = b->CreateICmpNE(expr(x->cond.get()), b->getInt32(0));
        b->CreateCondBr(cc, thenBB, elseBB);

        b->SetInsertPoint(thenBB);
        stmt(x->then.get());
        if (!b->GetInsertBlock()->getTerminator()) b->CreateBr(mergeBB);

        b->SetInsertPoint(elseBB);
        if (x->els) {
            stmt(x->els.get());
            if (!b->GetInsertBlock()->getTerminator()) b->CreateBr(mergeBB);
        } else {
            b->CreateBr(mergeBB);
        }
        b->SetInsertPoint(mergeBB);
        return;
    }

    if (const auto *x = dynamic_cast<const WhileS *>(s)) {
        Function *fn = b->GetInsertBlock()->getParent();
        auto *header = BasicBlock::Create(*ctx, "wh.cond", fn);
        auto *bodyBB = BasicBlock::Create(*ctx, "wh.body", fn);
        auto *exitBB = BasicBlock::Create(*ctx, "wh.exit", fn);

        b->CreateBr(header);
        b->SetInsertPoint(header);
        Value *cc = b->CreateICmpNE(expr(x->cond.get()), b->getInt32(0));
        b->CreateCondBr(cc, bodyBB, exitBB);

        b->SetInsertPoint(bodyBB);
        stmt(x->body.get());
        if (!b->GetInsertBlock()->getTerminator()) b->CreateBr(header);

        b->SetInsertPoint(exitBB);
        return;
    }

    if (const auto *x = dynamic_cast<const BlockS *>(s)) {
        for (const auto &st : x->ss) stmt(st.get());
        return;
    }

    if (const auto *x = dynamic_cast<const ReturnS *>(s))
        b->CreateRet(expr(x->e.get()));
}

void IRGen::genWrapper(const FunDecl *mainFun) {
    // C 入口：按 TIP main 形参数目读 input，再调用 tip_main。
    // 不命名为 main——MinGW 目标会向 main 注入对 CRT 符号 __main 的调用。
    auto *fn = Function::Create(FunctionType::get(b->getInt32Ty(), false),
                                Function::ExternalLinkage, "tip_entry", *mod);
    auto *entry = BasicBlock::Create(*ctx, "entry", fn);
    b->SetInsertPoint(entry);

    std::vector<Value *> args;
    for (size_t j = 0; j < mainFun->params.size(); ++j)
        args.push_back(b->CreateCall(rtInput_));
    Value *r = b->CreateCall(mod->getFunction("tip_main"), args);
    b->CreateRet(r);
}

bool IRGen::verify() const {
    std::string err;
    llvm::raw_string_ostream os(err);
    bool bad = llvm::verifyModule(*mod, &os);
    os.str();
    return !bad;
}

std::string IRGen::dump() const {
    std::string out;
    llvm::raw_string_ostream os(out);
    mod->print(os, nullptr);
    return os.str();
}
```

```cpp
#include "jitrun.hpp"

#include <cstdint>
#include <stdexcept>

#include "llvm/ExecutionEngine/JITSymbol.h"
#include "llvm/ExecutionEngine/Orc/Core.h"
#include "llvm/ExecutionEngine/Orc/LLJIT.h"
#include "llvm/ExecutionEngine/Orc/ThreadSafeModule.h"
#include "llvm/Support/TargetSelect.h"

using llvm::StringRef;
using llvm::JITSymbolFlags;
using llvm::orc::ExecutorSymbolDef;
using llvm::JITTargetAddress;
using llvm::jitTargetAddressToFunction;
using llvm::pointerToJITTargetAddress;
using llvm::orc::LLJITBuilder;
using llvm::orc::SymbolMap;
using llvm::orc::ThreadSafeModule;
using llvm::orc::absoluteSymbols;

namespace tip {
namespace {

// JIT 模块通过这两个宿主函数与外界交换数据。
const std::vector<int> *inQueue = nullptr;
std::vector<int> *outQueue = nullptr;
size_t inPos = 0;

extern "C" int32_t tip_input() {
    if (inPos >= inQueue->size()) return 0;
    return (*inQueue)[inPos++];
}

extern "C" void tip_output(int32_t value) {
    outQueue->push_back(value);
}

void initNative() {
    // 进程内只初始化一次。
    static const bool ready = [] {
        llvm::InitializeNativeTarget();
        llvm::InitializeNativeTargetAsmPrinter();
        return true;
    }();
    (void)ready;
}

[[noreturn]] void fail(llvm::Error e) {
    std::string text = llvm::toString(std::move(e));
    throw std::runtime_error(text);
}

}  // namespace

std::vector<int> runJit(IRGen gen, const std::vector<int> &inputs) {
    initNative();
    std::vector<int> outputs;
    inQueue = &inputs;
    outQueue = &outputs;
    inPos = 0;

    auto jitOrErr = LLJITBuilder().create();
    if (!jitOrErr) fail(jitOrErr.takeError());
    auto jit = std::move(*jitOrErr);

    auto defineHost = [&](StringRef name, void *addr) {
        SymbolMap symbols;
        symbols[jit->mangleAndIntern(name)] = ExecutorSymbolDef(
            llvm::orc::ExecutorAddr::fromPtr(addr), JITSymbolFlags());
        if (llvm::Error e =
                jit->getMainJITDylib().define(absoluteSymbols(symbols)))
            fail(std::move(e));
    };
    defineHost("tip_input", reinterpret_cast<void *>(&tip_input));
    defineHost("tip_output", reinterpret_cast<void *>(&tip_output));

    ThreadSafeModule tsm(std::move(gen.mod), std::move(gen.ctx));
    if (llvm::Error e = jit->addIRModule(std::move(tsm)))
        fail(std::move(e));

    auto mainAddr = jit->lookup("tip_entry");
    if (!mainAddr) fail(mainAddr.takeError());
    auto *entry = jitTargetAddressToFunction<int (*)()>(mainAddr->getValue());
    entry();

    return outputs;
}
```

```cpp
// 类型的表示：具体类型构造子 + 可合一的类型变量。

namespace tip {

struct Type;
using Tp = std::shared_ptr<Type>;

struct Type {
    virtual std::string show() const = 0;
    virtual ~Type() = default;
};

struct TyInt : Type {
    std::string show() const override { return "int"; }
};

struct TyPtr : Type {
    Tp to;
    explicit TyPtr(Tp t) : to(std::move(t)) {}
    std::string show() const override { return "ptr(" + to->show() + ")"; }
};

struct TyFun : Type {
    std::vector<Tp> params;
    Tp ret;
    TyFun(std::vector<Tp> ps, Tp r) : params(std::move(ps)), ret(std::move(r)) {}
    std::string show() const override {
        std::string s = "(";
        for (size_t i = 0; i < params.size(); ++i) {
            if (i) s += ", ";
            s += params[i]->show();
        }
        s += ") -> " + ret->show();
        return s;
    }
};

struct TyRec : Type {
    std::vector<std::pair<std::string, Tp>> fields;
    explicit TyRec(std::vector<std::pair<std::string, Tp>> fs)
        : fields(std::move(fs)) {}
    std::string show() const override {
        std::string s = "{";
        for (size_t i = 0; i < fields.size(); ++i) {
            if (i) s += ", ";
            s += fields[i].first + ": " + fields[i].second->show();
        }
        return s + "}";
    }
};

struct TyVar : Type {
    int id;
    explicit TyVar(int i) : id(i) {}
    std::string show() const override { return "t" + std::to_string(id); }
    // 新鲜变量编号：进程内单调递增，从 1 开始。
    static int fresh() {
        static int counter = 0;
        return ++counter;
    }
};
```

```cpp
// file: src/main.cpp
// 第 09 章配套程序：类型表示登场。
//   --check FILE    : 解析 -> AST -> 名字解析，随后打印类型构造演示
//   --emit-ir FILE  : 打印未优化的 LLVM 模块
//   --run FILE INPUTS: 对 INPUTS 每行输入真实执行一次，打印输出序列
#include <fstream>
#include <iostream>
#include <memory>
#include <sstream>
#include <string>
#include <utility>
#include <vector>

#include "TIPLexer.h"
#include "TIPParser.h"
#include "antlr4-runtime.h"

#include "ast_build.hpp"
#include "irgen.hpp"
#include "jitrun.hpp"
#include "symtab.hpp"
#include "type.hpp"

class CollectErrorListener : public antlr4::BaseErrorListener {
public:
    std::vector<std::string> messages;

    void syntaxError(antlr4::Recognizer *, antlr4::Token *, size_t line,
                     size_t column, const std::string &msg,
                     std::exception_ptr) override {
        messages.push_back("syntax error line " + std::to_string(line) + ":" +
                           std::to_string(column) + " " + msg);
    }
};

namespace {

struct Parsed {
    std::unique_ptr<tip::ProgramA> ast;
    tip::Bindings bindings;
};

Parsed parseFile(const std::string &path) {
    std::ifstream src(path);
    if (!src) {
        std::cerr << "cannot open " << path << '\n';
        std::exit(1);
    }
    antlr4::ANTLRInputStream input(src);
    TIPLexer lexer(&input);
    antlr4::CommonTokenStream tokens(&lexer);
    TIPParser parser(&tokens);

    CollectErrorListener errors;
    lexer.removeErrorListeners();
    parser.removeErrorListeners();
    lexer.addErrorListener(&errors);
    parser.addErrorListener(&errors);

    TIPParser::ProgramContext *tree = parser.program();
    if (!errors.messages.empty()) {
        for (const std::string &m : errors.messages) std::cout << m << '\n';
        std::exit(2);
    }

    Parsed result;
    result.ast = tip::buildAst(tree);
    result.bindings = tip::resolveNames(*result.ast);
    if (!result.bindings.errors.empty()) {
        for (const tip::Diag &d : result.bindings.errors)
            std::cout << d.text << '\n';
        std::exit(3);
    }
    return result;
}

// 第 09 章演示：具体类型构造子与新鲜类型变量如何打印。
void printTypeDemo() {
    std::cout << "-- type structures --\n";
    tip::Tp i = tip::tint();
    std::cout << i->show() << '\n';
    std::cout << tip::Tp(std::make_shared<tip::TyPtr>(i))->show() << '\n';
    std::cout << tip::Tp(std::make_shared<tip::TyFun>(
                     std::vector<tip::Tp>{i}, i))->show()
              << '\n';
    std::cout << tip::Tp(std::make_shared<tip::TyRec>(
                     std::vector<std::pair<std::string, tip::Tp>>{{"x", i}}))->show()
              << '\n';
    for (int k = 0; k < 3; ++k) std::cout << tip::tvar()->show() << '\n';
}

std::vector<int> parseRun(const std::string &line) {
    std::vector<int> values;
    std::istringstream ss(line);
    int v;
    while (ss >> v) values.push_back(v);
    return values;
}

int main(int argc, char **argv) {
    if (argc >= 3 && std::string(argv[1]) == "--check") {
        Parsed p = parseFile(argv[2]);  // 前端仍然全程工作
        (void)p;
        printTypeDemo();
        return 0;
    }

    if (argc >= 3 && std::string(argv[1]) == "--emit-ir") {
        Parsed p = parseFile(argv[2]);
        tip::IRGen gen;
        gen.gen(*p.ast, p.bindings);
        if (!gen.verify()) {
            std::cerr << "generated module failed verification\n";
            return 1;
        }
        std::cout << gen.dump();
        return 0;
    }

    if (argc == 4 && std::string(argv[1]) == "--run") {
        std::ifstream in(argv[3]);
        if (!in) {
            std::cerr << "cannot open " << argv[3] << '\n';
            return 1;
        }
        int run = 0;
        std::string line;
        while (std::getline(in, line)) {
            std::string trimmed = line;
            size_t a = trimmed.find_first_not_of(" \t\r\n");
            if (a == std::string::npos) continue;
            if (trimmed[a] == '#') continue;

            std::vector<int> inputs = parseRun(trimmed);
            // 每次执行重新生成：JIT 会消费模块。
            Parsed p = parseFile(argv[2]);
            tip::IRGen gen;
            gen.gen(*p.ast, p.bindings);
            if (!gen.verify()) {
                std::cerr << "generated module failed verification\n";
                return 1;
            }
            std::vector<int> outputs = tip::runJit(std::move(gen), inputs);

            std::cout << "run " << ++run << ":";
            for (size_t i = 0; i < outputs.size(); ++i)
                std::cout << (i ? ", " : " ") << outputs[i];
            std::cout << '\n';
        }
        return 0;
    }

    std::cerr << "usage: tipa --check FILE | tipa --emit-ir FILE | tipa --run FILE INPUTS\n";
    return 1;
}
```

## 9.21 工程注意点

- **类型变量只经 tvar()/fresh() 创建**：单调计数器保证编号两两
  不同，手工编号必然与计数器冲突。
- **类型项一律用 Tp（shared_ptr）传递**：变量身份需要跨多处共享，
  且 α=ptr(α) 的环只有共享所有权能表达；环上的理论泄漏在单次
  运行内不爆发。
- **类型对象构造后不被修改**："变量等于什么"由第 11 章的置换映射
  表达，不回写类型项，保证共享的各处不会观察到互相干扰的改动。
- **演示与分析分离**：--check 先完整跑前端（错误仍以 2/3 退出），
  前端通过后才打印演示；新分析不削弱旧约定。
- **产物只依赖源程序与固定版本**：编号顺序、打印样式均确定，
  expected 跨机器逐字节一致。

这五条不是可以背诵了事的"坑"，而是前面各节原理在工程动作上的
投影：第一条来自 9.7 的计数器论证，第二条来自 9.6 的身份共享需求，
第三条来自 9.4.1 的不可变约定与 9.17.4 的主解性质，第四条来自
9.9 的命令协议，第五条来自 9.7.2 与 9.10.4 的机器对账机制。读者
若能从每一条工程注意点反查到对应原理，就掌握了本章而不只是记住
了操作。后续章节的工程注意点也都按同一方式组织：少量条目、每条
有原理出处；它服务于实践，不取代理解。

## 9.22 小结：未知已可表达，方程即将写出

本章为类型分析建立了词汇层。形式化地，类型项由五个构造子组成：
int、ptr(τ)、函数类型、记录类型，以及代表待定类型的类型变量；
工程上，Type 类族以继承分派实现这些构造，以 shared_ptr 保证同一
变量在多处出现之间的身份共享、并允许成环，以单调计数器保证新鲜
编号两两不同且对源程序确定。tipa 的 --check 改为"前端 + 类型构造
演示"，两个程序的七行输出逐字节相同，诚实地表明本章只造出了
表达未知的词、尚未用它分析具体程序。

为什么要绕这一圈？9.2 节的直接递归算法在三个点上失败：形参/var
处无类型可返、程序施加的条件散落而无法积累、递归与环依赖使
"按序算完"的模型不闭合。类型变量把"未知"变成一等数据，恰好
对症：它让程序的**类型结构可以在答案未知时先行搭出**。这是静态
分析反复出现的母题——先设计能表达"不精确/待定"的表示，再在
表示上求解；第 13 章的格元素、第 17 章的抽象状态都是这一母题的
后继。

本章还预先建立了几条贯穿全书的认识。结构观（9.13）让相等性只
依赖形状、使合一规则短而可判定；记录宽度（9.13.1）展示了一类
"分散在程序各处、必须汇总的形状事实"；与 LLVM 类型系统的对照
（9.15）说明低层翻译会压平源级信息，分析必须在丢失前把它固定
下来；可靠性（9.16）把每条约束的存在依据追溯到具体求值规则的
前提，并预告第 17 章用 JIT 做经验性对账。五个手算例子（9.12）
则表明全部过程是机械的：条件在答案未知时写出、横向引用、最终
一起解出，无须灵感。

下一章做 9.3.2 两阶段架构的前半：遍历 AST，用本章的类型变量
为每个表达式和声明占位，按语法产生式把全部条件收集成**类型等式**
——"二元运算两侧必须是 int"、"被调者必须是接受这些实参的函数"、
"alloc E 的类型是 ptr(τ(E))"；9.17.3 的定型记号 Γ ⊢ E : τ 将
作为每条收集规则的论证原型。读者将第一次看到 --check 的输出
因程序不同而不同：约束表就是程序类型结构的完整投影。第 11 章再
实现以代入消元为原型的合一，让 t1、t2 这些占位符一个个落地为
int、ptr(int)；第 12 章补全记录与 null 的规则，并直面这套分析的
两个真实局限——流不敏感与无多态。从第 13 章起，"先占位"的母题
将换上格与不动点的新面孔反复出现。

合卷之前，给读者留一个可以自测的总问题：如果让你在不看第 10 章
的情况下，向另一个人解释"为什么给程序做类型检查，第一步不是检查
而是造一批带编号的空壳"，你会怎么讲？若你的解释里包含了信息缺失
（9.1）、横向流动与环（9.2）、两阶段分离（9.3）与身份共享（9.6）
这四点，本章就算真正读完了；若讲不出，回到对应小节再读一遍相应
的手算例子。教程的目标从来不是让读者记住 type.hpp 的行数，而是
让这套"先把未知变成一等数据"的思维方式成为读者自己的工具。
