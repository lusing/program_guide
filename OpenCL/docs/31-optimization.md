# 31 · 优化方法论：autotune 实验台与优化循环

> 对应示例 `examples/31_autotune/main.c`。参照 OiA 10.4 节（Ten tips for high-performance kernels）、OPE 第 8 章（General tips）、HCL 第 12 章（用剖析数据找瓶颈）。

## 31.1 优化循环（先度量，再动手）

```
① 用事件剖析定位瓶颈（传输 or 计算 or 等待）
   ↓ 传输瓶颈 → 减次数/非阻塞重叠/留在设备多算几步（14 章）
② 计算瓶颈 → 访存模式（30 章）→ 分支/占用率 → 算术强度
③ 每改一处：同一基准 + 预热 + 多轮取最优（31 章实验台）
④ 数值对拍保证没改错（所有算法章的铁律）
```

OiA 的十条军规浓缩版：了解硬件；数据对齐合并；向量化装载；少分支；local 慎用但用对；组大小扫一遍；原子少用（或私有化，22 章）；传输与计算重叠；内核别太肥（占用率）；最后才抠算术。

## 31.2 autotune 实验台：扫 local size

最优组大小依赖"内核 × 数据 × 设备"三元组，**推理不如实验**。示例 31 的套路：

```c
const size_t cands[] = {32, 64, 96, 128, 192, 256, 384, 512, 768, 1024};
/* 每个 candidate：
   ① 过滤：l > CL_KERNEL_WORK_GROUP_SIZE 跳过；global % l != 0 跳过
   ② 预热一轮（首轮含加载开销，实测不预热数据不可信）
   ③ 5 轮剖析取最优
*/
```

实测（RTX 3060，8M 元素 fma 内核）：

```
preferred multiple = 32, max work-group = 256
   local      best ms       GB/s
      32        0.437      153.6
      64        0.304      220.7
      96            - (not divisible)
     128        0.303      221.4
     192            - (not divisible)
     256        0.306      219.2
     384..1024      - (exceeds max)
winner: local=128 (0.303 ms)
y[0] = 74.0 after 24 launches (expect 74.0)
31 autotune PASS
```

读数：

- 32（一个 warp）最差——每组只占一个 warp 槽，调度开销摊不薄；
- 64–256 是平台期（带宽墙：221 GB/s 双向读写，内存受限内核的标志）；
- **结论与 `CL_KERNEL_PREFERRED_WORK_GROUP_SIZE_MULTIPLE = 32` 一致但更精**：倍数只是"对齐粒度"，最优值要扫。

> 预热实测的教训：第一轮比后续慢数倍（程序加载 + 页表 + 时钟爬升），不预热的 autotune 会选错。

## 31.4 基准测试纪律

1. **对拍先行**：每个 variant 都验正确性（示例每个 candidate 后校验累积值）；
2. 预热 + 多轮取最优/中位数；
3. 事件剖析（设备时间）而非墙钟（含主机噪声）；
4. 固定数据与形状；换设备重扫（本机 GPU 与 CPU 的最优 local 相差甚远）；
5. 谨防基准撒谎：编译器可能优化掉"没被消费"的计算——让结果参与校验断言（示例的 `y[0]==expect` 就是防"死代码消除"）。

## 31.5 什么时候停止优化

- 带宽达到设备水位的 60%+（内存受限内核基本到顶，30 章实测参考值）；
- 剖析显示时间大头在传输——去优化传输（14 章）而不是内核；
- 收益/工时比低于直接换库（clBlast 一行调用，32 章）。
