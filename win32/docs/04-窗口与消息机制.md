## 4.1 句柄：Win32 的资源通行证

第 1 章说过，句柄是"不透明的资源标识"。这里把它讲透。

Windows 内核为每种系统对象（窗口、文件、进程、线程、事件……）维护对象结构，但**绝不把结构体的地址直接给应用程序**。你拿到的是一个索引/令牌——句柄，凭它去找系统办事。进程里有一张**句柄表**，句柄值本质上是这张表的槽位号：

```text
进程句柄表（内核维护）           你的代码
┌──────┬────────────────────┐
│ 槽 0 │ → 文件对象(只读权限) │ ◄── HANDLE h = 0x1234
│ 槽 1 │ → 事件对象           │ ◄── HANDLE ev = 0x1238
│  …   │  …                  │
└──────┴────────────────────┘
你只能拿槽位号办事，看不到也改不了对象本身
```

这样做的好处：

- **隔离**：程序不能篡改内核对象的内部数据；
- **安全**：每个句柄带访问权限，打开文件时申请只读，拿到的句柄就写不了（第 17 章展开）；
- **稳定**：系统内部可以随意移动、重组对象，句柄值不变。

常见句柄类型（它们本质都是指针宽度的整数）：

| 类型 | 代表的资源 | 归还方式 |
|------|-----------|---------|
| `HWND` | 窗口 | `DestroyWindow` |
| `HANDLE` | 进程/线程/事件/文件等内核对象 | `CloseHandle` |
| `HDC` | 绘图上下文 | `ReleaseDC` / `EndPaint`（成对） |
| `HMENU` | 菜单 | `DestroyMenu` |
| `HPEN` / `HBRUSH` / `HFONT` | GDI 绘图对象 | `DeleteObject` |
| `HINSTANCE` / `HMODULE` | 已加载的模块 | 进程退出自动释放 |

**核心纪律：谁创建，谁归还；每种句柄都有对应的 Close/Destroy/Delete。** 句柄泄漏不像内存泄漏那么出名，但一个长时间运行的 GUI 程序若在 `WM_PAINT` 里反复创建 GDI 对象而不删，系统 GDI 配额（默认每进程 10000 个）耗尽后界面就会诡异失灵——第 9 章会再强调。

## 4.2 窗口类与窗口：模板与实例

`RegisterClassExW` 注册的是**窗口类（window class）**——一种窗口的"模板"，描述这类窗口共用的事件处理函数、光标、背景刷、图标；`CreateWindowExW` 按模板创建具体**实例**。这和面向对象里"类/对象"的关系一样，甚至更好记：**窗口类是 C 语言时代的虚表**——`lpfnWndProc` 字段就是这个类的"虚函数入口"。

类名在全进程内唯一（跨进程则由"全局类/局部类"规则区分，初学不必深究）。模板字段中初学必须理解的是：

```cpp
WNDCLASSEXW wc = {};
wc.cbSize        = sizeof(wc);      // 结构体自报大小：API 靠它做版本兼容
wc.lpfnWndProc   = WndProc;         // ★ 这类窗口的事件都送到这个函数
wc.hInstance     = hInstance;       // ★ 类属于哪个模块
wc.lpszClassName = L"HelloWindowClass"; // ★ 类名
wc.hCursor       = LoadCursor(nullptr, IDC_ARROW); // 鼠标进入窗口的形状
wc.hbrBackground = (HBRUSH)(COLOR_WINDOW + 1);     // 背景刷；nullptr 则需自己画背景
wc.style         = CS_HREDRAW | CS_VREDRAW;        // 可选：尺寸变化时强制整窗重绘
wc.hIcon         = LoadIconW(nullptr, IDI_APPLICATION); // 标题栏/任务栏图标
```

`(HBRUSH)(COLOR_WINDOW + 1)` 这行很费解，值得单独解释：`COLOR_WINDOW` 是系统颜色编号（0～30 的整数），加 1 是历史约定——"值比颜色编号大 1 的 HBRUSH 表示系统颜色"。它不是真正的刷子句柄，只是让系统代为填充背景的暗号。

窗口实例创建时决定的是：类名（用哪个模板）、标题、尺寸、样式、父窗口、控件 ID。同一个类可以创建任意多个窗口实例。

## 4.3 一条消息的旅程

这是全书最核心的一张图。当你按下鼠标左键，事件这样流动：

```text
你点击窗口
   ▼
硬件中断 → 内核输入驱动 → win32k 判断光标在哪个窗口上
   ▼
把 WM_LBUTTONDOWN 投递到【创建该窗口的线程】的消息队列
   ▼
                    ┌──────────────────────────────┐
   线程消息队列 ───► │ WM_PAINT │ WM_LBUTTONDOWN │ … │   （队列：先进先出）
                    └──────────────────────────────┘
   ▼
该线程正在 GetMessage 里睡觉，被唤醒，取到消息
   ▼
TranslateMessage（键盘消息的翻译步骤，鼠标消息直接跳过）
   ▼
DispatchMessage → 系统根据窗口句柄找到它注册的 WndProc
   ▼
调用 WndProc(hwnd, WM_LBUTTONDOWN, wParam, lParam)
   ▼
你的代码处理，return 0
   ▼
回到 GetMessage 继续睡觉……
```

注意一个关键点：**消息队列属于线程，不属于窗口**。窗口只是消息的"收件地址"（`msg.hwnd`）。这条设计决定了后面很多行为——比如工作线程没窗口也能收消息（`PostThreadMessage`）、UI 线程忙则它创建的所有窗口都无响应。

由此推出 GUI 程序最重要的工程铁律：

> **`WndProc` 是在消息循环线程（UI 线程）里执行的。如果你的 `WndProc` 里干活超过几百毫秒，整个程序就会"卡死"——因为下一件事、下一个窗口拖动都在排队等你。** 耗时工作必须丢给工作线程（第 14 章）。

这也解释了消息循环的本质：它不是"空转"，`GetMessage` 在队列空时把线程挂起（不占 CPU），队列来了消息才唤醒——和"忙等"的 `while(true)` 有本质区别。

## 4.4 消息循环三行代码逐个讲

```cpp
MSG msg = {};
while (GetMessageW(&msg, nullptr, 0, 0) > 0) {
    TranslateMessage(&msg);
    DispatchMessageW(&msg);
}
```

**`GetMessageW`**：从当前线程队列取一条消息填进 `msg`。队列空则线程挂起。返回值有三种，这是初学者最容易忽略的细节：

- `> 0`：正常消息，继续循环；
- `0`：取到了 **`WM_QUIT`**——退出循环，程序结束。`WM_QUIT` 不会进 `WndProc`，它只被 `GetMessage` 看到；
- `-1`：出错（比如参数非法），所以严格写法是 `> 0` 而不是 `!= 0`。

**`TranslateMessage`**：只干一件事——把按键消息（`WM_KEYDOWN`）翻译成字符消息（`WM_CHAR`）。没有它，你收不到"用户按了字母 a"这种文本级消息，只能自己处理扫描码。照写即可，对非键盘消息没有副作用。

**`DispatchMessageW`**：查 `msg.hwnd` 对应窗口的注册信息，调用它的 `WndProc`，并**等待 `WndProc` 返回**再回到 `GetMessage`——是同步的调用。注意消息的四个字段在 `WndProc` 里如何对应：

```cpp
MSG msg = {
    hwnd,     // → WndProc 第 1 参：消息属于哪个窗口
    message,  // → 第 2 参：消息编号（WM_...）
    wParam,   // → 第 3 参：附加信息 1
    lParam    // → 第 4 参：附加信息 2
};
```

`MSG` 还有一个 `time` 和 `pt`（消息产生时间与光标位置），平时用得少。

## 4.5 `wParam` 与 `lParam`：位布局图解

每条消息的附加信息都塞在 `wParam`/`lParam` 两个整数里，**不同消息的解读方式不同**——必须查文档，不能想当然。常见的三种"打包"方式：

```text
① 鼠标类消息（WM_LBUTTONDOWN 等）——lParam 打包坐标：
   lParam:  ┌────────────────┬────────────────┐
            │  高 16 位: y    │  低 16 位: x    │
            └────────────────┴────────────────┘
   int x = GET_X_LPARAM(lParam);   // 宏：有符号截取，推荐
   int y = GET_Y_LPARAM(lParam);
   // LOWORD/HIWORD 是无符号截取，负坐标（多屏场景）会出错

② 控件/菜单通知（WM_COMMAND）——wParam 打包"来源"：
   wParam:  ┌────────────────┬────────────────┐
           │ 高16位: 通知码   │ 低16位: 控件 ID │
           └────────────────┴────────────────┘
   lParam: 控件的 HWND
   int id = LOWORD(wParam);           // 谁发的
   int code = HIWORD(wParam);         // 发生了什么（BN_CLICKED 等）

③ 简单传值：wParam 或 lParam 直接就是一个整数/指针
   WM_CHAR:  wParam 是字符编码
   WM_SIZE:  wParam 是缩放类型，LOWORD(lParam)=新宽，HIWORD(lParam)=新高
```

打包/解包的配套宏：

| 宏 | 作用 |
|----|------|
| `LOWORD(x)` / `HIWORD(x)` | 取低/高 16 位（无符号） |
| `GET_X_LPARAM` / `GET_Y_LPARAM` | 取坐标（有符号，处理多屏负坐标，需 `<windowsx.h>`） |
| `MAKELPARAM(lo, hi)` | 打包两个 16 位成 lParam |

## 4.6 `WndProc` 的解剖与常用消息

```cpp
LRESULT CALLBACK WndProc(HWND hwnd, UINT msg, WPARAM wParam, LPARAM lParam) {
    switch (msg) {
    case WM_CREATE:  ... return 0;   // 窗口创建完成、显示之前：初始化控件、布局
    case WM_SIZE:    ... return 0;   // 尺寸变化：重新布局子控件
    case WM_PAINT:   ... return 0;   // 需要重绘（第 9 章专讲）
    case WM_COMMAND: ... return 0;   // 菜单/控件通知（第 5、10 章）
    case WM_CLOSE:   ... return 0;   // 用户点了 ✕（可以先弹"确定退出吗"，
                                     //  不想关闭就 return 0 不传给 DefWindowProc）
    case WM_DESTROY: PostQuitMessage(0); return 0;  // 窗口已销毁：结束消息循环
    }
    return DefWindowProcW(hwnd, msg, wParam, lParam);  // 兜底交给系统
}
```

要点：

- `WM_CLOSE` 与 `WM_DESTROY` 是两回事：点 ✕ 先来 `WM_CLOSE`（"用户想关"），默认处理是调 `DestroyWindow`；`DestroyWindow` 执行后窗口没了，来 `WM_DESTROY`（"窗口已没"），这里调 `PostQuitMessage(0)` 投递 `WM_QUIT` 让消息循环结束。两个环节都可以拦截：`WM_CLOSE` 里 `return 0` 可阻止关闭（询问确认就写在这），`WM_DESTROY` 不调 `PostQuitMessage` 则窗口没了进程还在。
- `LRESULT` 是返回值类型（`LONG_PTR`），`CALLBACK` 同 `WINAPI`，是给系统的回调约定。
- 返回值有讲究：多数消息 `return 0` 表示"我处理了"，个别消息（如 `WM_ERASEBKGND`）的返回值参与系统决策，查文档。

常用消息速查：

| 消息 | 时机 | wParam / lParam |
|------|------|-----------------|
| `WM_CREATE` | 窗口创建中 | lParam 指向 `LPCREATESTRUCT`（可取出 hInstance） |
| `WM_SIZE` | 尺寸变化 | wParam=原因；lParam 打包新客户区宽高 |
| `WM_PAINT` | 需要重绘 | 无附加信息 |
| `WM_COMMAND` | 菜单/控件通知 | 见 4.5 节 ② |
| `WM_NOTIFY` | 通用控件的复杂通知 | lParam 指向 `NMHDR`（第 6 章） |
| `WM_LBUTTONDOWN/UP`、`WM_RBUTTONDOWN/UP` | 鼠标按键 | wParam=按键状态（MK_SHIFT 等）；lParam=坐标 |
| `WM_MOUSEMOVE` | 鼠标移动 | 同上 |
| `WM_MOUSEWHEEL` | 滚轮 | wParam 高 16 位=滚动增量（120 的倍数） |
| `WM_CHAR` | 字符输入 | wParam=宽字符编码 |
| `WM_KEYDOWN/UP` | 物理按键 | wParam=虚拟键码 |
| `WM_TIMER` | 定时器到期 | wParam=定时器 ID |
| `WM_CLOSE` / `WM_DESTROY` | 关闭 / 已销毁 | —— |

## 4.7 发消息的三种方式：`SendMessage` / `PostMessage` / `PostThreadMessage`

系统提供了三个方向不同的投递原语，区别在于**同步还是异步、发给窗口还是线程**：

| API | 行为 | 返回时机 | 典型用途 |
|-----|------|---------|---------|
| `SendMessageW` | 直达 `WndProc`，**等它执行完** | `WndProc` 返回后 | 需要立刻拿到结果的查询，如 `WM_GETTEXT` 读控件内容 |
| `PostMessageW` | 放入目标线程队列就返回，**不等** | 立即 | 通知性质：后台线程让 UI 线程更新状态（第 14 章） |
| `PostThreadMessageW` | 投给线程队列本身（不关联窗口） | 立即 | 给没有窗口的工作线程发指令 |

两条重要纪律：

1. **跨线程时 `SendMessage` 有死锁风险**：A 线程 `SendMessage` 给 B 线程的窗口会阻塞到 B 处理完；若此时 B 又在等 A 手里的锁，就死锁了。跨线程通知首选 `PostMessage`。
2. **`PostMessage` 传指针要小心生命周期**：投递的是一个 `LPARAM`，若指向栈变量，接收方读到时栈帧早没了。传堆指针（如 `_wcsdup` 的结果），由接收方负责 `free`——`examples/11_thread_sync_demo` 就是这个模式。

另外，`SendMessageW(hEdit, WM_GETTEXT, ...)` 这种"给自己进程的控件发消息"是最常用的控件操作方式——控件就是窗口（第 5 章），消息就是它的方法调用接口。

## 4.8 定时器：没有多线程也能"定时"

初学者常以为定时就要开线程。GUI 程序里更地道的做法是 `WM_TIMER`：

```cpp
case WM_CREATE:
    SetTimer(hwnd, 1, 500, nullptr);   // 每 500ms 给 hwnd 发一条 WM_TIMER
    return 0;

case WM_TIMER:
    if (wParam == 1) {
        // 周期性更新界面，例如刷新时钟、轮询状态
    }
    return 0;

case WM_DESTROY:
    KillTimer(hwnd, 1);                // 用完必须销毁
    return 0;
```

`WM_TIMER` 优先级低（队列里攒着不会连发）、精度约 15ms，但零线程成本、天然线程安全（在 UI 线程执行）。对"每秒刷新一次状态栏"这类需求正合适。它属于"三种定时器"中最低门槛的一种——需要精确定时或跨线程等待时，还有可等待定时器与 QPC 计时，第 18 章给完整对比表。

## 4.9 实战：消息观测器

`examples/02_message_loop/main.cpp` 把本章内容串成一个可玩的小程序：点击弹窗显示坐标、按住左键拖动改标题、按 ESC 关闭。核心就是这些消息各就各位：

```cpp
case WM_LBUTTONDOWN: {                      // lParam 打包坐标（见 4.5 ①）
    wchar_t text[64];
    wsprintfW(text, L"Click at (%d, %d)",
              GET_X_LPARAM(lParam), GET_Y_LPARAM(lParam));
    MessageBoxW(hwnd, text, L"Mouse Message", MB_OK);
    return 0;
}
case WM_MOUSEMOVE:                          // wParam 里能查到按键状态
    if (wParam & MK_LBUTTON) {
        SetWindowTextW(hwnd, L"Dragging...");
    }
    return 0;
```

建议动手实验：把 `DefWindowProcW` 注释掉重新编译，验证窗口立刻"残废"；把 `TranslateMessage` 删掉，验证收不到 `WM_CHAR`——对机制的最好理解来自破坏它。

## 4.10 易错清单

| 症状 | 原因 | 解法 |
|------|------|------|
| 程序"未响应"，过了一会儿又恢复 | `WndProc` 里干了耗时活，队列堵车 | 耗时活丢工作线程 + `PostMessage` 回传（第 14 章） |
| 收不到 `WM_CHAR` | 消息循环漏了 `TranslateMessage` | 补上（4.4） |
| 鼠标坐标在副屏（负坐标）上算错 | 用 `LOWORD` 无符号截取 | 用 `GET_X_LPARAM`（4.5） |
| 关闭确认弹了两次 | 在 `WM_DESTROY` 而不是 `WM_CLOSE` 里问 | 拦 `WM_CLOSE`（4.6） |
| 窗口关了进程还在 | `WM_DESTROY` 忘了 `PostQuitMessage` | 补上 |
| 跨线程 `SendMessage` 偶发卡死 | 同步跨线程 + 锁顺序 | 改 `PostMessage`（4.7） |
| 定时器越积越多 | 多个 `SetTimer` 用了同一个 ID 或忘 `KillTimer` | ID 区分 + 配对销毁 |

## 4.11 小结

1. 句柄 = 进程句柄表的槽位号：隔离、带权限、稳定；每种句柄有配对归还函数。
2. 窗口类是模板（C 时代的虚表），`CreateWindowExW` 造实例；队列属于线程，窗口只是收件地址。
3. 消息循环三行：`GetMessage`（可睡/三态返回）、`TranslateMessage`（键盘翻译）、`DispatchMessage`（同步送达 WndProc）。
4. `wParam/lParam` 的解读因消息而异，查文档 + 用对解包宏。
5. UI 线程的铁律：`WndProc` 不干重活；跨线程通知用 `PostMessage`。

## 4.12 动手练习

1. 给消息观测器加：右键双击（提示：记录上次 `WM_RBUTTONUP` 的时间，`GetDoubleClickTime()` 是系统阈值）弹出"你双击了右键"。
2. 加一个每秒走字的标题栏时钟（`WM_TIMER` + `GetLocalTime` + `SetWindowTextW`——第 18 章前先用起来）。
3. 实验：在 `WndProc` 里 `Sleep(5000)` 再处理消息，编译后拖动窗口，观察标题栏变"未响应"——体验 4.3 的铁律，然后改成 `WM_TIMER` 方案验证恢复。
