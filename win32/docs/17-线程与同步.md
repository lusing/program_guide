## 17.1 创建线程：`CreateThread`

```cpp
DWORD WINAPI Worker(LPVOID param) {        // 线程函数签名固定
    int* counter = (int*)param;            // 参数是指针，想传什么包个结构体传地址
    for (int i = 0; i < 5; ++i) {
        // 干活……
        Sleep(100);                        // 挂起 100ms，让出 CPU
    }
    return 0;                              // 返回值即线程退出码
}

int main() {
    int counter = 0;
    HANDLE h = CreateThread(nullptr, 0, Worker, &counter, 0, nullptr);
    //                    安全属性, 栈大小(0=默认1MB), 函数, 参数, 创建标志, 收返回的线程ID
    if (h) {
        WaitForSingleObject(h, INFINITE);  // 等线程结束（"join"）
        CloseHandle(h);                    // 句柄纪律不变
    }
    return 0;
}
```

理解要点：

- **每个线程一个栈**（默认 1MB，虚拟内存，实际用到才提交——第 18 章的概念在这里出现）；
- **线程函数返回即线程结束**。不要用 `ExitThread`（跳过 C++ 析构！），永远不要 `TerminateThread`（线程在任意指令处被腰斩，锁不释放、堆可能损坏——文档原话"尽量别用"）；
- **C++ 程序里用 `_beginthreadex` 或 `std::thread`**：`CreateThread` 不知道 C 运行时（CRT）的线程局部初始化，混用 CRT（`printf`、`strtok` 等）时官方推荐 `_beginthreadex`；而现代 C++ 代码直接 `std::thread`——它内部就是 `CreateThread` 的正确封装。本章为了看清机制用 `CreateThread`，工程代码请用 `std::thread` + `std::mutex`，两者学到的概念完全互通。

线程的其他常规操作：`SuspendThread`/`ResumeThread`（挂起恢复，慎用——见下节"暂停计数"）、`SetThreadDescription(h, L"worker-io")`（💡 Win10 1607+，调试器里终于能认出线程）、`GetExitCodeThread` 取返回值。

## 17.2 调度：抢占、时间片与优先级

线程创建出来，**什么时候运行、跑多久，决定权在调度程序**。《Windows 核心编程》第 7 章把这层机制讲得很透，本节取其主干。

**抢占式调度的基本图景**。每个线程的内核对象里保存着一份**上下文（CONTEXT）**——CPU 寄存器的快照。系统每隔约 20ms（一个**时间片**）检查所有线程：只有"可调度"的线程才候选，选中谁就把谁的上下文装回 CPU（**上下文切换**），被换下的寄存器存回它的内核对象。系统从开机到关机都在重复这个循环。三个直接推论：

1. **线程随时可能被抢占**——哪怕正跑到某条指令的一半（下一条还没执行）。这就是竞态（17.4 节）的物理根源；
2. **Windows 不是实时操作系统**。任何"保证线程在 X 毫秒内开始运行"的承诺都做不到——想都不用想；
3. **大多数线程大多数时间不可调度**：在等消息、等锁、等 I/O、等超时。等待中的线程不占 CPU——这正是等待函数（17.5 节）存在的意义。

**暂停计数**。线程内核对象里有一个"暂停计数"，`CreateThread` 默认在线程初始化完成后把它减为 0（线程开始跑）；传 `CREATE_SUSPENDED` 则保持为 1，线程创建完但不跑——经典用法是"先建后调"：

```cpp
HANDLE h = CreateThread(nullptr, 0, Worker, &data, CREATE_SUSPENDED, nullptr);
SetThreadPriority(h, THREAD_PRIORITY_IDLE);   // 趁还没跑，先设置属性
ResumeThread(h);                              // 返回值是"前一个暂停计数"
```

`SuspendThread`/`ResumeThread` 配对（计数可叠加，最多 127 次）。**慎用 `SuspendThread`**：你不知道目标线程暂停瞬间正拿着什么锁——它可能正持着堆的锁，别的线程再碰堆就全体卡死。没有"暂停整个进程"的正规 API（那是调试器的特权，`WaitForDebugEvent`）。

**优先级：0 到 31**。系统总是先调度高优先级的可调度线程：

- **0 级**：全系统只有"零页线程"（空闲时把空闲 RAM 清零的内核线程），应用拿不到；
- **1~15**：动态区——系统会在这个范围内**临时提升**线程优先级（见下）；
- **16~31**：实时区——能抢占大多数操作系统组件，用错会让鼠标键盘都失去响应。需要 `SeIncreaseBasePriorityPrivilege` 权限。

只要 31 级线程一直可调度，低优先级线程就永远得不到 CPU——这叫**饥饿（starvation）**。多核能缓解（高优先级线程占不住所有核），但设计上要避免"高优先级线程长时间忙转"。

**你设置的不是 0~31**。微软故意在调度程序外面加了抽象层：你只组合两个旋钮，映射成 0~31 的事系统包办（且随版本变化，别依赖具体数字）：

- **进程的优先级类**（6 档）：`IDLE / BELOW_NORMAL / NORMAL / ABOVE_NORMAL / HIGH / REALTIME`。99% 的程序用 `NORMAL`；屏幕保护、后台统计用 `IDLE`；任务管理器用 `HIGH`（这样系统再卡你也能呼出它杀进程）；`REALTIME` 基本不要碰；
- **线程的相对优先级**（7 档）：`THREAD_PRIORITY_IDLE / LOWEST / BELOW_NORMAL / NORMAL / ABOVE_NORMAL / HIGHEST / TIME_CRITICAL`。

| 相对优先级 \ 类 | 空闲 | 低于正常 | 正常 | 高于正常 | 高 | 实时 |
|---|---|---|---|---|---|---|
| 关键时间 | 15 | 15 | 15 | 15 | 15 | 31 |
| 最高 | 6 | 8 | 10 | 12 | 15 | 26 |
| **正常** | 4 | 6 | **8** | 10 | 13 | 24 |
| 最低 | 2 | 4 | 6 | 8 | 11 | 22 |
| 空闲 | 1 | 1 | 1 | 1 | 1 | 16 |

（正常类+正常线程 = 8，这就是"大多数线程都是 8"的由来。）

```cpp
SetPriorityClass(GetCurrentProcess(), BELOW_NORMAL_PRIORITY_CLASS);  // 进程级
SetThreadPriority(h, THREAD_PRIORITY_ABOVE_NORMAL);                  // 线程级
```

**动态提升**——系统会"自作主张"地临时加优先级：键盘/磁盘等设备驱动唤醒线程时，常给 +2 一类的临时提升，随后每个时间片递减，回落到基本优先级；**饥饿保护**：低优先级线程约 3~4 秒得不到 CPU 时，系统把它提到 15 并给双倍时间片。所以"低优先级线程会饿死"在实践中有兜底。不想要提升可以 `SetThreadPriorityBoost(h, FALSE)` 关掉。使用原则一句话：**高优先级线程应该"快速响应然后马上睡回去"**，把 CPU 留给批处理。

**主动让出**：

```cpp
Sleep(0);          // 放弃剩余时间片。但只让给"同优先级"线程——没有同级候选时自己立刻又被调度
SwitchToThread();  // 放弃时间片，且允许比它低的线程运行（低优先级线程持锁时的礼貌让法）
```

**测量线程的 CPU 时间**：`GetThreadTimes(h, &create, &exit, &kernel, &user)`（内核时间+用户时间，单位 100ns），进程级是 `GetProcessTimes`。测量"墙上时间"仍用第 21 章的 QPC——两者回答不同问题。

**亲缘性（affinity）**：默认"软亲缘性"——调度程序尽量让线程留在上次的 CPU（缓存还热）。需要钉死时用"硬亲缘性"：

```cpp
SetProcessAffinityMask(hProc, 0x00000005);   // 该进程的线程只许跑 CPU0 和 CPU2（位掩码）
SetThreadAffinityMask(hThread, 0x00000002);  // 单个线程钉在 CPU1（必须是进程掩码的子集）
SetThreadIdealProcessor(hThread, 1);         // 软钉：首选 CPU1，忙时可迁移
```

真实动机是 NUMA 机器（跨内存板访问慢几个数量级）与测量噪声消除。**随意钉核常常变慢**：把三个线程都钉在 CPU0，其余核闲着，调度程序干着急——掩码是约束不是加速器。

## 17.3 竞态条件：为什么需要同步

两个线程同时对同一个 `int` 做 `++`，结果经常不是期望值：

```cpp
++counter;                 // 一行 = 读 → 加 → 写 三步
// 线程 A 读到 5，线程 B 也读到 5，各自加成 6 写回 —— 两次加法只加了一次
```

这叫**竞态条件（race condition）**。不是"可能出错"，是**一定**会出错，只是频率取决于时序——于是成为最阴险的 bug。此外还有**内存可见性**问题：编译器/CPU 有权把变量缓存在寄存器/缓存里，另一个线程可能长时间看不到写入。

解决思路三种，按代价从低到高：

1. **原子操作**：单变量的加减、交换、比较——`InterlockedIncrement(&counter)` 或 C++ `std::atomic<int>`；
2. **锁**：一段代码同一时间只许一个线程进——本章主角；
3. **不共享**：每线程独立数据，最后合并——最优雅，设计时优先考虑。

### 互锁函数家族：不只是 ++

互锁家族（Interlocked）全部保证原子性，且**不进内核**（几十个 CPU 周节，比一次内核切换约 1000 周期快两个数量级）。四个最有用的成员：

| 函数 | 语义（伪代码） | 典型用途 |
|------|--------------|---------|
| `InterlockedIncrement/Decrement` | `*p += 1` | 引用计数 |
| `InterlockedExchangeAdd` | `*p += n`（n 可负） | 任意步长的原子加减 |
| `InterlockedExchange(Pointer)` | `old = *p; *p = v; return old` | 原子换值（发布指针） |
| `InterlockedCompareExchange(Pointer)` | `if (*p == expected) *p = new;` | **CAS**——无锁算法的地基 |

用 `InterlockedExchange` 能手搓一个最原始的**循环锁（spinlock）**：

```cpp
while (InterlockedExchange(&g_inUse, TRUE))   // 原子地"举起占用旗"，返回旧值
    Sleep(0);                                  // 别人占着就稍让（纯自旋会更糟）
// ... 临界区 ...
InterlockedExchange(&g_inUse, FALSE);
```

两条纪律（《核心编程》第 8 章的告诫）：**单 CPU 机器上不要用循环锁**——唯一能释放锁的线程被你转圈的线程堵在外面，纯属死锁；多核上也要"短持快放"。实际工程里循环锁几乎只活在 CS/SRWLock 的内部实现里，你直接用的机会不多——但 CAS 是 `std::atomic` compare_exchange 的底座，认识它就理解了一半无锁编程。

### 高速缓存行与伪共享

CPU 取内存不取"一个变量"，而是取整条**缓存行**（32/64 字节）。两个线程各自频繁写**逻辑上无关**的两个变量，若它们恰好挤在同一条缓存行里，核间缓存一致性协议会让这条行在两个核之间来回失效——性能掉一大截，而代码看起来毫无问题。这叫**伪共享（false sharing）**，多线程热点数据的经典暗坑：

```cpp
struct Counters {                       // 坏：两个计数器大概率同处一行
    LONG countA; LONG countB;
};
struct alignas(64) PaddedCounter { LONG v; };   // 好：各占一行（C++11 alignas）
struct CountersFixed { PaddedCounter a; PaddedCounter b; };
```

口诀：**按访问者分组数据**——单线程独占的放一起，多线程各写各的用对齐隔开；只读数据与读写数据分开。

## 17.4 同步原语全家福

Win32 的同步对象有明确分工，选型看两个问题：**保护的是什么**、**同步双方在不在同一进程**。

### `CRITICAL_SECTION`：同进程内的轻量锁

```cpp
CRITICAL_SECTION cs;
InitializeCriticalSection(&cs);          // 用完 DeleteCriticalSection

EnterCriticalSection(&cs);               // 拿锁（别人拿着就睡）
// ... 临界区：摸共享数据 ...
LeaveCriticalSection(&cs);               // 放锁
```

特点：进程内有效、极快、**非内核对象**（没有句柄、不能 `WaitForSingleObject`）。纪律：Enter/Leave 之间不得提前 return（会永久死锁），结构上尽量把临界区缩到只包数据访问。

看穿它的内部（《核心编程》8.4 节的解剖）：CS 其实是"**先自旋、后入睡**"的两段式——争用时先用循环锁空转几次（**SpinCount**），赌持有者很快放锁；赌输了才转入内核等待（此时才需要真正的事件内核对象，系统**等到第一次争用才创建它**——多数从不争用的 CS 因此零内核开销）：

```cpp
InitializeCriticalSectionAndSpinCount(&cs, 4000);   // 多核才有意义；单核自动忽略
TryEnterCriticalSection(&cs);                        // 拿不到立刻返回 FALSE（0 等待版）
```

使用技巧三条：**每份资源一把锁**（两份不相干的数据共用一把锁 = 白白串行化）；**同持多锁必须全局同序**（防死锁，17.8 节）；**锁内干活越短越好**（拷个快照出来慢慢用，别在锁里调回调/发消息）。

### SRWLock 与条件变量：现代首选

> 💡 **现代视角（Vista+）**：`CRITICAL_SECTION` 是"读写不分"的独占锁。**SRWLock**（Slim Reader/Writer Lock）区分读者与写者——读多写少的场景（配置查询、缓存）吞吐量成倍提升；配套的**条件变量** `CONDITION_VARIABLE` 干净地解决"等待某个条件成立"。

```cpp
SRWLOCK lock = SRWLOCK_INIT;                 // 静态初始化，不需要 Initialize/Destroy
CONDITION_VARIABLE cv = CONDITION_VARIABLE_INIT;

// 写线程
AcquireSRWLockExclusive(&lock);
queue.push_back(item);
ReleaseSRWLockExclusive(&lock);
WakeConditionVariable(&cv);                  // 叫醒一个等待者

// 读线程
AcquireSRWLockShared(&lock);                 // 多个读者可同时持有共享锁
// ... 只读 ...
ReleaseSRWLockShared(&lock);

// 条件等待（规范四步，SleepConditionVariableSRW 内部原子放锁+睡）
AcquireSRWLockExclusive(&lock);
while (queue.empty())                        // ★ 必须 while：防虚假唤醒
    SleepConditionVariableSRW(&lock, &cv, INFINITE, 0);
item = queue.front(); queue.pop_front();
ReleaseSRWLockExclusive(&lock);
```

对应 C++ 标准件：`std::shared_mutex`（C++17）、`std::condition_variable`——概念一一对应。`examples/14_srwlock_demo` 是完整的生产者/消费者实现（控制台，可直接运行观察三个线程的交错输出）。

### `Mutex`：跨进程的锁

```cpp
HANDLE m = CreateMutexW(nullptr, FALSE, L"Local\\MyAppSingleton");
if (GetLastError() == ERROR_ALREADY_EXISTS) {
    // 已有实例在跑 → 单实例检测的经典用法
    return 0;
}
WaitForSingleObject(m, INFINITE);
// ... 跨进程共享的资源 ...
ReleaseMutex(m);
CloseHandle(m);
```

与 `CRITICAL_SECTION` 的本质区别：**内核对象、有名字、可跨进程、可设超时、可被安全策略控制**。代价是每次加锁都进内核，比临界区慢一个量级。命名规则 `Local\`（本会话）/`Global\`（全系统所有会话）。

Mutex 还有两个专属语义（内核对象里的"特例"）：

1. **线程所有权与递归**：Mutex 记住"谁拥有我"。同一个线程反复 `WaitForSingleObject` 同一个 mutex 会成功（递归计数 +1），`ReleaseMutex` 要配对同样次数；**别的线程调 `ReleaseMutex` 直接失败**（`ERROR_NOT_OWNER`）——CS 同样支持同线程递归，但没有"所有权"的强校验；
2. **遗弃（abandonment）**：拥有 mutex 的线程没放锁就死了（又一个别用 `TerminateThread` 的理由），系统会把 mutex 强制归还，等待者醒来但拿到的是 `WAIT_ABANDONED` 而非 `WAIT_OBJECT_0`——含义是"锁到手了，但**受保护的数据可能处于半损坏状态**"，严谨的程序要把它当错误处理（重新初始化共享数据），而不是当成功。

### `Event`：通知信号

```cpp
HANDLE done = CreateEventW(nullptr,     // 安全属性
                           TRUE,        // 手动复位(TRUE)/自动复位(FALSE)
                           FALSE,       // 初始状态：未触发
                           nullptr);    // 不命名（进程内用）

// 工作线程：完工后 SetEvent(done);
// 主线程：WaitForSingleObject(done, INFINITE); → "等到完工为止"
```

两种复位语义：**手动复位**像广播开关（Set 一次，所有等待者都醒，直到你 Reset）；**自动复位**像发号机（Set 一次只放行一个等待者）。典型用途：后台任务完成通知、线程优雅退出（退出标志 + 事件二合一）、生产者-消费者唤醒。选法口诀：**"一件事所有相关者都要知道"用手动；"一个工作项一个认领者"用自动**。

### `Semaphore`：并发数量闸门

```cpp
HANDLE sem = CreateSemaphoreW(nullptr, 3, 3, nullptr);   // 初始 3 / 上限 3
WaitForSingleObject(sem, INFINITE);   // 计数 -1，为 0 则睡
// ... 最多 3 个线程同时进入 ...
ReleaseSemaphore(sem, 1, nullptr);    // 计数 +1（可一次放行多个）
```

用途：限制同时打开的文件数、并发下载连接数、线程池的任务槽。互斥量其实就是"上限 1 的信号量"。规则四条：计数 > 0 即触发；计数不为负；不超上限；**等待成功即减一**（这个"副作用"是它工作的方式，见下节）。

### 选型速查表

| 原语 | 进程内/跨进程 | 独占/共享 | 典型用途 |
|------|-------------|----------|---------|
| `CRITICAL_SECTION` | 进程内 | 独占 | 通用共享数据保护（默认选择） |
| SRWLock | 进程内 | 独占+共享 | 读多写少 |
| 条件变量 | 进程内（配上面两种锁） | —— | "等条件成立" |
| `Mutex` | 跨进程 | 独占（有所有权） | 单实例检测、跨进程资源 |
| `Event` | 进程内或跨进程 | —— | 完成通知、退出信号 |
| `Semaphore` | 进程内或跨进程 | 计数 | 并发数量限制 |

## 17.5 等待函数与"成功等待的副作用"

```cpp
WaitForSingleObject(h, INFINITE);            // 等一个；可给超时毫秒数
WaitForMultipleObjects(3, handles, TRUE, INFINITE);
//                            ↑ TRUE=等全部，FALSE=任一即可
//  返回 WAIT_OBJECT_0 + i 表示第 i 个就绪；WAIT_TIMEOUT 超时；WAIT_FAILED 出错
//  ★ 句柄数组上限 64 个（MAXIMUM_WAIT_OBJECTS），更多要分组等
```

能被等待的统一叫**可等待对象**：进程、线程、Job、文件、控制台输入、文件修改通知、事件、可等待定时器、信号量、互斥体——"等待"是内核对象模型统一的威力（第 1 章说的"句柄 + 等待"两个正交概念）。

《核心编程》第 9 章点破的一个常被忽略的机制——**成功等待的副作用**：对某些对象，"等到它"这个动作本身会**改变它的状态**（只有返回 `WAIT_OBJECT_0` 才算成功；`WAIT_TIMEOUT`/`WAIT_FAILED` 不改状态）：

| 对象 | 未触发 | 触发 | 成功等待的副作用 |
|------|--------|------|----------------|
| 进程 / 线程 | 还活着 | 已终止 | 无 |
| 自动复位事件 | `ResetEvent` 后 | `SetEvent` 后 | **自动复位**（这就是名字的由来） |
| 手动复位事件 | `ResetEvent` 后 | `SetEvent` 后 | 无 |
| 信号量 | 计数 = 0 | 计数 > 0 | **计数 -1** |
| 互斥体 | 被某线程拥有 | 无主 | **所有权交给等待者**；遗弃时返回 `WAIT_ABANDONED` |

这张表解释了很多"灵异现象"：多个线程等同一个自动复位事件，`SetEvent` 一次只醒一个（醒的动作把事件复位了）；信号量"等待即扣款"；`WaitForMultipleObjects(FALSE)` 任一模式下**返回的下标总是最小的已触发者**——循环再等时若不把已处理的句柄从数组里摘掉，会立刻又返回同一个下标。

另两条等待函数的性质：**整体原子**——`WaitForMultipleObjects(TRUE)` 检查全部对象、执行全部副作用是一步到位的（两个自动事件不会各被一个线程"各扣一半"而双双冻死）；**唤醒大致 FIFO**——微软官方口径只说"算法是公平的"，实践近似先来先服务（调试器断点会全体暂停线程，打乱次序）。

UI 线程专用的等待：`MsgWaitForMultipleObjectsEx`——在等内核对象的同时**让窗口消息照样进来**（普通等待会让界面失去响应）。工作线程等退出事件 + 主线程等结果时，它是"两边都不卡"的正解（第 17.9 节的 GUI 架构里它是进阶选项）。

## 17.6 `WaitOnAddress`：无对象的等待

> 💡 **现代视角（Win8+）**：`WaitOnAddress(&value, &compare, sizeof(value), timeout)` 提供轻量级"等某个内存值变化"，无需创建任何内核对象——高性能无锁结构的积木。配对的唤醒是 `WakeByAddressSingle/All`。初学知道即可，看到现码能认出它不属于"内核对象等待"家族。

## 17.7 线程池与纤程：别亲手管理线程的生命

> 💡 **现代视角（Vista+）**：频繁短任务不该每次 `CreateThread`（创建开销 ~微秒级 + 1MB 栈提交）。系统线程池 API 按《核心编程》第 11 章归纳的**四种方案**各有一个入口，线程数量自动按 CPU 核数与负载调节：

```cpp
VOID CALLBACK Work(PTP_CALLBACK_INSTANCE, PVOID ctx) { /* 干活 */ }

// 方案 1：异步调用一个函数（有活就丢给池）
SubmitThreadpoolWork(CreateThreadpoolWork(Work, ctx, nullptr));

// 方案 2：按规定时间间隔调用（定时任务）
CreateThreadpoolTimer(...);   // SetThreadpoolTimer 设 due time 与周期

// 方案 3：当某个内核对象变为已触发时调用（等待代理）
CreateThreadpoolWait(...);    // SetThreadpoolWait 挂上事件/进程句柄

// 方案 4：异步 I/O 完成时调用（ overlapped I/O 配套）
CreateThreadpoolIo(...);
```

工程上等价物是 C++ 层的各种线程池/`std::async`；理解系统池的意义在于：调试时看到 `ntdll!TppWorkerThread` 线程知道它们是谁，以及**别在池回调里做阻塞等待**（池线程是稀缺资源）。

顺带一提《核心编程》第 12 章的**纤程（fiber）**：用户态调度的"协作式线程"（`ConvertThreadToFiber`/`SwitchToFiber`），为移植 Unix 协作式代码而生。现代代码几乎不需要它——`std::coroutine`（第 29 章）才是正路，认识名字即可。

## 17.8 死锁：四条件与预防

两个线程各持一把锁、互相等对方的那把——永久卡死。死锁发生的四个必要条件：**互斥**（资源独占）、**持有并等待**、**不可剥夺**、**循环等待**。工程预防按性价比排序：

1. **锁排序**：全程序规定锁的获取顺序（如"先 A 后 B"），循环等待即不可能——最有效；
2. **缩小临界区**：锁内不调未知代码（回调可能反过来拿锁）；
3. **`TryEnterCriticalSection`/带超时的 `WaitForSingleObject`**：拿不到就退避重试，破坏"持有等待"；
4. 少造锁：一把大锁的吞吐损失通常好过五把小锁的死锁风险（先对再快）。

## 17.9 GUI 铁律：后台干活，UI 线程收结果

现在把线程放进 GUI 程序。第 4 章的铁律（`WndProc` 卡住 = 全程序卡死）决定了标准架构：

```text
UI 线程                          工作线程
   │ 按钮"开始扫描"                  │
   │ CreateThread(...) ────────────→ 扫描文件 / 算数据 / 读网络
   │ 继续响应消息（界面不卡）          │ 每N步：
   │ ←──────── PostMessageW(WM_APP+1, 数据) ── 报告进度
   │ WM_APP+1: SetWindowText 更新界面 │
   │ ←──────── 完成时 SetEvent / PostMessage "done" ──
```

完整可运行示例见 `examples/11_thread_sync_demo`，其要点浓缩如下：

```cpp
constexpr UINT WM_APP_PROGRESS = WM_APP + 1;   // WM_APP 起是应用自定义消息的保留区

// 工作线程：只做计算与通知，绝不碰控件
DWORD WINAPI Worker(LPVOID param) {
    auto* st = (DemoState*)param;
    for (int i = 1; i <= 5; ++i) {
        Sleep(250);
        EnterCriticalSection(&st->cs);
        LONG v = ++st->counter;                 // 共享数据用锁保护
        LeaveCriticalSection(&st->cs);

        wchar_t* msg = _wcsdup(L"tick");        // ★ 跨线程传数据：堆分配
        PostMessageW(st->hwnd, WM_APP_PROGRESS, (WPARAM)v, (LPARAM)msg);
    }
    SetEvent(st->done);                          // 完成信号
    return 0;
}

// UI 线程：收到进度消息，更新界面，并负责释放 _wcsdup 的内存
case WM_APP_PROGRESS: {
    wchar_t* text = (wchar_t*)lParam;
    if (text) { SetWindowTextW(hStatus, text); free(text); }
    return 0;
}
```

三条纪律再强调一遍：**工作线程不碰任何窗口/控件**（窗口属于创建它的线程）；**跨线程通知用 `PostMessage` 不用 `SendMessage`**（4.7 节的死锁风险）；**`LPARAM` 传指针注意生命周期**（堆分配、接收方释放）。

为什么要锁 `counter`？虽然单变量可以用 `InterlockedIncrement` 免锁，示例里用临界区是为了演示"多步更新"的标准姿势——真实业务里共享的很少是单个整数，而是一整个数据结构。

## 17.10 易错清单

| 症状 | 原因 | 解法 |
|------|------|------|
| 计数偶尔少加 | `++` 非原子，竞态 | `InterlockedIncrement` 或锁（17.3） |
| 多核下多线程反而变慢 | 热点变量挤在同一缓存行（伪共享） | 按访问者分组 + `alignas(64)`（17.3） |
| 后台线程抢得 UI 卡顿 | 高优先级线程长时间忙转 | 高优先级只做"快响应就睡"（17.2） |
| 临界区拿了不放 | 中间提前 `return`/异常 | 缩小临界区 + C++ 侧用 RAII（`std::lock_guard`） |
| 想拿 CS 但不能等 | —— | `TryEnterCriticalSection`（17.4） |
| 条件等待偶发拿空数据 | 醒来没用 `while` 复查 | `SleepConditionVariable*` 必配 `while`（17.4） |
| 等 mutex 拿到锁后数据是坏的 | 前持有者暴毙，`WAIT_ABANDONED` 被当成功 | 判返回值，重新初始化共享数据（17.4） |
| `WaitForMultipleObjects(FALSE)` 循环总返回同一个下标 | 已处理句柄没摘出数组 | 摘除或压缩句柄数组（17.5） |
| UI 线程等待内核对象时界面冻住 | 普通等待不吃消息 | `MsgWaitForMultipleObjectsEx`（17.5） |
| 线程函数里 `ExitThread` | 跳过 C++ 析构 | `return` 自然退出 |
| 界面偶发卡死 | 跨线程 `SendMessage` 撞锁 | 改 `PostMessage`（17.9） |
| 进度消息里读野指针 | 栈地址当 `LPARAM` 投递 | 堆分配 + 接收方释放 |
| `WaitForMultipleObjects` 传 70 个句柄 | 上限 64 | 分组等待 |
| 换成 `std::thread` 后 CRT 状态怪 | 老代码用 `CreateThread` 混 CRT | 统一 `_beginthreadex`/`std::thread` |
| `SuspendThread` 后全家卡死 | 目标线程持着堆锁被冻结 | 别挂起"不明"线程（17.2） |
| 亲缘性钉核后吞吐下降 | 掩码是约束不是加速 | 默认软亲缘性，确有需要再钉（17.2） |

## 17.11 小结

1. 线程 = 栈 + 寄存器的执行流；`CreateThread` 四参核心，返回即结束，句柄要关。
2. 调度是抢占式的：时间片轮转 + 优先级（0~31）；你只组合"进程优先级类 × 线程相对优先级"，系统映射并动态提升；`Sleep(0)` 让同级、`SwitchToThread` 连低级也让；亲缘性默认软、硬钉要谨慎。
3. 竞态是必然不是偶然：原子操作（互锁家族，CAS 是无锁地基）、锁、不共享三档解法；多核热点当心伪共享。
4. 选型表：进程内默认 `CRITICAL_SECTION`（先自旋后入睡，SpinCount 可调），读多写少 SRWLock，跨进程 Mutex（有所有权与遗弃语义），通知 Event（手动广播/自动发号），限流 Semaphore；条件等待必配 `while`。
5. 等待统一走 `WaitForSingleObject`/`WaitForMultipleObjects`（上限 64）；**成功等待有副作用**（事件复位/信号量减一/所有权转移），`WAIT_ABANDONED` 要当错误。
6. GUI 铁律：后台干活 + `PostMessage` 回传 + 接收方释放；锁排序防死锁；系统线程池四入口接住"短任务高频"场景。

## 17.12 动手练习

1. 把 `14_srwlock_demo` 改造：生产者放"哨兵值 0"表示关门，消费者收到哨兵即退出——完整的优雅关闭协议。
2. 用 `WaitForMultipleObjects` 同时等 3 个工作线程，全部完成后打印汇总（注意 TRUE/FALSE 语义差异各试一遍，FALSE 模式体会"摘句柄"的必要性）。
3. 复现死锁：两个线程按相反顺序拿两把锁，观察卡死；再用"锁排序"修复。用调试器的"冻结线程"功能帮助观察。
4. 优先级实验：起一个 `THREAD_PRIORITY_IDLE` 的忙循环线程和一个正常优先级的忙循环线程，观察任务管理器 CPU 占用比；再把进程类改为 `HIGH`，看动态提升如何兜底低优先级线程（饥饿保护）。
5. 伪共享实验：写两个程序各起 4 线程对各自的计数器累加 10 亿次——一版普通 `long` 数组、一版 `alignas(64)` 对齐数组，对比耗时（多核机器效果明显）。
