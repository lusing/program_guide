# 第 15 章 内存管理

> 本章回答的问题：`new`/`malloc` 底下是什么？虚拟内存、保留、提交、页保护分别是什么？什么时候需要 `VirtualAlloc`、`HeapAlloc`、文件映射？内存映射文件为什么能当共享内存用？

> 💡 **本章定位**：内存管理是 Win32 系统服务层的地基。C++ 的 `new`、各语言的运行时、各种分配器，最终全部落到本章的 API 上——第 1 章"无替代品"名单的又一员。

本章示例：`examples/09_memory_monitor`、`examples/12_memory_deep_dive`。

## 9.1 三个层次：先建地图

Windows 程序的内存分三个层次，从上到下越来越"系统"：

```text
┌─────────────────────────────────────────────┐
│ ① C/C++ 层：new / malloc / std::vector      │  ← 99% 的日常代码在这层
│    底下是 C 运行时堆，堆底下又是 ③           │
├─────────────────────────────────────────────┤
│ ② 进程堆：HeapAlloc / HeapFree              │  ← CRT 堆通常就是它的一层包装
│    面向"频繁分配小块"的通用分配器             │
├─────────────────────────────────────────────┤
│ ③ 虚拟内存：VirtualAlloc / VirtualFree      │  ← 直接跟内核对话
│    以页为单位，控制地址空间与物理内存的映射    │
└─────────────────────────────────────────────┘
```

选择哪一层的判据：日常对象用 `new`；需要自定义分配器/对象池时用 ②；需要"一次性要一大块、控制权限、跨进程共享"时用 ③。

## 9.2 虚拟内存：进程眼中的世界

每个进程拥有自己独立的一整段**虚拟地址空间**（64 位程序是 128TB 的理论空间）。关键事实：

- **地址是假的**。进程里看到的 `0x7FF6ABC12340` 不是物理内存地址，CPU 通过页表把它翻译成物理页帧。所以进程 A 的某地址和进程 B 的同数值地址毫无关系——这是进程隔离的地基。
- **地址空间 ≠ 已用内存**。虚拟地址可以先"登记"不"兑现"。这就是保留/提交两个动作：
  - **`MEM_RESERVE`（保留）**：登记一段虚拟地址范围，说"这段我要了"，但不分配任何物理资源。免费、快速。
  - **`MEM_COMMIT`（提交）**：对保留的区间说"这部分现在要用"，系统记账承诺物理内存/页面文件支持。**真正产生内存压力的是提交**。
- **分配单位是页（page）**：x64 标准页 4KB。任何分配都被向上取整到页边界——`VirtualAlloc` 要 1 字节，实际提交 4KB。
- **缺页（page fault）**：第一次写某提交页时才真正绑定物理页帧（demand-zero paging）。这就是"提交了 1GB 但实际只用了 100MB"时物理内存占用不高的原因。

`GetSystemInfo` 可查页大小与处理器信息：

```cpp
SYSTEM_INFO si = {};
GetSystemInfo(&si);
// si.dwPageSize（一般 4096）、si.dwNumberOfProcessors、si.dwAllocationGranularity（64KB）
```

注意 `dwAllocationGranularity` 是 64KB：`VirtualAlloc` 的起始地址按 64KB 对齐——保留大块再内部切分时这个粒度很重要。

## 9.3 `VirtualAlloc` / `VirtualFree`

```cpp
// 保留并提交 1MB 可读写内存
void* p = VirtualAlloc(
    nullptr,                          // 让系统挑地址（通常如此）
    1024 * 1024,
    MEM_RESERVE | MEM_COMMIT,         // 一步到位；也可先 RESERVE 后逐段 COMMIT
    PAGE_READWRITE);                  // 页保护属性

if (p) {
    // p 指向的内存初始内容为 0（新提交页保证零页）
    memset(p, 0xAA, 1024 * 1024);
    VirtualFree(p, 0, MEM_RELEASE);   // ★ 大小参数必须为 0，整个区间释放
}
```

规则：

- `MEM_RELEASE` 时大小必须传 0（按保留时登记的整块释放）；想只退掉一半用 `MEM_DECOMMIT`；
- 分配失败返回 `nullptr`（不是异常），查 `GetLastError()`；
- 页保护属性见 9.5。

> 💡 **现代视角（Win10 1803+）**：`VirtualAlloc2`/`MapViewOfFile3` 是新一代接口，新增：**占位符分配**（预留地址槽位防竞态）、**内存分区**（NUMA/容器场景指定物理节点）、支持已保留区间的"替换式映射"。普通应用仍用旧 API 即可，但读现代系统代码（Chrome、WSL）会频繁遇到它们。

大页（2MB 页，减少 TLB miss）：`VirtualAlloc(..., MEM_LARGE_PAGES)`，需要 `SeLockMemoryPrivilege` 特权且要先启用，属于服务器级优化，知道存在即可。

## 9.4 堆：`HeapAlloc` 与老朋友们

进程默认有一个堆（"进程堆"），C 运行时的 `malloc`/`new` 通常基于它（或自建堆）再包一层小对象优化：

```cpp
HANDLE heap = GetProcessHeap();                    // 进程默认堆的句柄
void* p = HeapAlloc(heap, HEAP_ZERO_MEMORY, 4096); // 分配 4KB 并清零
if (p) {
    strcpy_s((char*)p, 4096, "hello");
    HeapFree(heap, 0, p);
}
```

需要独立堆（比如"整堆销毁释放全部对象""堆级加锁策略"）时用 `HeapCreate` 创建私有堆。DLL 相关的堆选择问题（分配与释放跨 DLL 边界要用同一堆）第 19 章会讲。

**`GlobalAlloc` / `LocalAlloc`：博物馆展品**。它们是 16 位时代的"全局/局部堆"API，32 位以后两者完全等价（都是进程堆的包装）。今天存在的唯一理由：**部分 API 的签名还要求它们**——最典型的是剪贴板（`SetClipboardData` 要 `HGLOBAL`）。新代码一律不用；哪天被剪贴板 API 逼着用一次，照下面写：

```cpp
HGLOBAL h = GlobalAlloc(GMEM_MOVEABLE, size);   // GMEM_MOVEABLE 的"可移动"早已无意义
void* p = GlobalLock(h);                        // 拿到真实指针
memcpy(p, data, size);
GlobalUnlock(h);
// ... 交给剪贴板后由系统释放；否则 GlobalFree(h)
```

## 9.5 页保护：`VirtualProtect`

每页都有保护属性，决定读写执行权限：

| 属性 | 含义 |
|------|------|
| `PAGE_READWRITE` | 常规可读写 |
| `PAGE_READONLY` | 只读（写就崩，适合防篡改/写时复制基础） |
| `PAGE_NOACCESS` | 全禁（探雷器/哨兵页） |
| `PAGE_EXECUTE_READ` | 可执行+读（现代系统要求代码页显式可执行，DEP 的基础） |
| `PAGE_GUARD` | 修饰符：访问一次触发异常再自动清除（栈自动增长的实现原理！） |

```cpp
void* p = VirtualAlloc(nullptr, 4096, MEM_RESERVE | MEM_COMMIT, PAGE_READWRITE);
DWORD old = 0;
VirtualProtect(p, 4096, PAGE_READONLY, &old);   // 收走写权限；old 带回旧属性
// ...此后写入这里会触发访问违例（0xC0000005）...
VirtualProtect(p, 4096, PAGE_READWRITE, &old);  // 恢复
```

用途：JIT（先 RW 写入机器码，再改 RX 执行）、内存越界哨兵、防篡改。`VirtualQuery` 则可反查任意地址的所属区域/保护属性/状态——写内存检查工具的积木。

## 9.6 查询内存状态

**系统层面**（`examples/09_memory_monitor`）：

```cpp
MEMORYSTATUSEX mem = { sizeof(mem) };          // ★ 老规矩：先自报结构体大小
GlobalMemoryStatusEx(&mem);
// mem.ullTotalPhys / ullAvailPhys     物理内存
// mem.ullTotalVirtual / ullAvailVirtual  本进程可用的虚拟地址空间
// mem.dwMemoryLoad                    内存负载百分比
```

**进程层面**（`psapi.h`）：

```cpp
PROCESS_MEMORY_COUNTERS pmc = {};
GetProcessMemoryInfo(GetCurrentProcess(), &pmc, sizeof(pmc));
// pmc.WorkingSetSize       工作集：实际驻留物理内存的字节数（任务管理器"内存"列的主口径）
// pmc.PeakWorkingSetSize   峰值
// pmc.PagefileUsage        已提交量
```

区分两个概念：**提交**（virtual size，欠账）与**工作集**（working set，实际占着物理内存）。"我的程序任务管理器显示 200MB"通常指工作集，不等于你 `VirtualAlloc` 的量。

## 9.7 文件映射：文件当内存用，内存当共享用

`CreateFileMapping` + `MapViewOfFile` 是 Win32 里最"一鱼两吃"的机制——同一套调用，两个经典用途：

```cpp
// 用途 A：大文件随机访问（免 read/write 系统调用，让缺页机制替你搬运）
HANDLE hFile = CreateFileW(L"data.bin", GENERIC_READ | GENERIC_WRITE,
                           0, nullptr, OPEN_EXISTING, FILE_ATTRIBUTE_NORMAL, nullptr);

// 用途 B：无后端文件的共享内存（INVALID_HANDLE_VALUE = 页文件支持的映射）
HANDLE hFile = INVALID_HANDLE_VALUE;

HANDLE hMap = CreateFileMappingW(hFile, nullptr, PAGE_READWRITE,
                                 0,                  // 高 32 位大小
                                 4096,               // 低 32 位大小（两参拼 64 位）
                                 L"Local\\MyDemo");  // ★ 命名 → 可跨进程打开（OpenFileMappingW）

void* p = MapViewOfFile(hMap, FILE_MAP_ALL_ACCESS, 0, 0, 4096);  // 映射进本进程地址空间
strcpy_s((char*)p, 4096, "hello, shared memory");

// 清理四件套，缺一不可
UnmapViewOfFile(p);
CloseHandle(hMap);
CloseHandle(hFile);      // 注意：映射建立后即可关文件句柄，映射仍然有效
```

两个进程用同样的名字 `CreateFileMappingW`/`OpenFileMappingW`，各自 `MapViewOfFile` 后，写的一方 `strcpy`、读的一方直接 `memcpy`——这就是 Windows 上**共享内存 IPC** 的标准做法（同名前缀 `Local\`/`Global\` 规则见第 14 章）。真实用户：Chrome 各进程间的共享段、日志缓冲、数据库页缓存。

使用纪律：**映射大小 ≤ 文件大小**（对真实文件）；多进程同时写要自己加锁（互斥体，见第 14 章）；写不等于落盘（要强刷用 `FlushViewOfFile`）。

> 💡 **现代视角（Win10 1803+）**：`MapViewOfFile3` 配合 `VirtualAlloc2` 的占位符可在指定地址做映射，是容器/沙箱场景管理地址空间的新基件。

## 9.8 内存错误与诊断

Win32 不像托管语言有护栏，典型死法与对策：

| 症状 | 常见原因 |
|------|---------|
| 崩溃码 `0xC0000005` 访问违例 | 空指针/悬垂指针/越界/写只读页 |
| `VirtualAlloc` 返回 nullptr | 参数错（大小、保护属性冲突）或地址空间耗尽（32 位程序常见） |
| 句柄/映射泄漏累积 | `MapViewOfFile` 忘 `Unmap`、`CloseHandle` 缺失——工具：任务管理器"句柄"列 |
| 堆损坏崩溃在"毫不相干"的地方 | 越界写把堆元数据写坏了，崩溃点≠肇事点；用 Application Verifier / 调试堆（`_CRTDBG`）定位 |
| 栈溢出 `0xC00000FD` | 深递归；超大栈上数组（改堆分配） |

内存相关的检查习惯：分配/释放成对书写（同 4.1 节句柄纪律）；谁分配谁释放（跨模块传内存先约定由谁释放）；`HEAP_ZERO_MEMORY` 消灭未初始化读取。
