## 34.1 发布前检查清单

Debug 版编出来的 exe 不是"程序"，是"实验品"。交付前的标准动作：

1. **Release 编译**（`/O2`、断言关闭），pdb 文件**留在自己手里**——崩溃栈符号化全靠它（3.7 的 minidump 没有 pdb 就是一串地址）；给每个发布版本建档：exe + pdb + 源码 tag 一一对应；
2. **依赖核对**：`dumpbin /dependents build\你的.exe` 列出全部 DLL 依赖，逐个回答"目标机器上有吗？"——答案只有三种：系统自带（`kernel32.dll` 等）、随包分发（第三方 DLL）、CRT（见下节）；
3. **别依赖开发机环境**：目标机器没有你的 SDK、没有 `PATH` 里的临时目录。最狠的自测法：把 exe 拷进一台干净虚拟机（或新建 Windows 沙盒）双击运行。

## 34.2 CRT 部署：`/MT` 还是 `/MD`

C/C++ 运行时库（CRT）是部署问题的第一大来源。MSVC 给两个开关：

| 开关 | 链接方式 | exe 体积 | 依赖 |
|------|---------|---------|------|
| `/MD`（默认，Debug 版是 `/MDd`） | 动态：用 `vcruntime140.dll`、`msvcp140.dll`（x64 还多一个 `vcruntime140_1.dll`） | 小 | 目标机器要有这三个 DLL |
| `/MT` | 静态：CRT 全部编进 exe | 大几 MB | **零 CRT 依赖** |

一个关键的现代事实（很多老资料讲错了）：**VS2015 起 CRT 拆成了两半**——`ucrtbase.dll`（UCRT，C 标准函数）与 `vcruntime140.dll`（编译器支撑）。**UCRT 从 Windows 10 起是操作系统组件**，随 Windows Update 更新，Win10/11 机器上永远有；还要操心的只剩 `vcruntime140` 系三个小 DLL（几百 KB）。所以现代口径是：

- **小工具/绿色软件**：`/MT` 一把梭，单文件 exe 拷走就跑（本教程示例即是——不依赖任何 CRT DLL）；
- **正式产品/多 exe 家族**：`/MD` + **app-local 部署**（把 `vcruntime140*.dll` 复制到 exe 旁边一起发）。第 22 章的 DLL 搜索顺序在这里兑现：**exe 目录优先级最高，官方也推荐这种"放旁边"的部署法**（不要往系统目录塞，不要指望用户装 VC Redist）。

> 💡 老黄历辨析："目标机器要装 vcredist"的说法过时了——那是 VS2013 及以前（`msvcr120.dll` 时代）的规矩。如今要么 `/MT`，要么 DLL 放 exe 旁。

## 34.3 版本资源：VERSIONINFO

右键 exe → 属性 → "详细信息"那一页，就来自 `.rc` 资源脚本里的 `VERSIONINFO`：

```rc
// version.rc —— 用 rc.exe 编译成 .res 链进 exe
#include <windows.h>
#define VER_FILEVERSION 1,2,0,7
#define VER_FILEVERSION_STR "1.2.0.7\0"

VS_VERSION_INFO VERSIONINFO
 FILEVERSION    VER_FILEVERSION
 PRODUCTVERSION VER_FILEVERSION
 FILEFLAGSMASK  0x3fL
 FILEOS         VOS_NT_WINDOWS32
 FILETYPE       VFT_APP
BEGIN
    BLOCK "StringFileInfo"
    BEGIN
        BLOCK "080404b0"              // 中文(0x0804) + Unicode(0x04b0)
        BEGIN
            VALUE "CompanyName",      "示例公司"
            VALUE "FileDescription",  "我的第一个 Win32 程序"
            VALUE "FileVersion",      VER_FILEVERSION_STR
            VALUE "ProductName",      "MyApp"
        END
    END
    BLOCK "VarFileInfo"
    BEGIN
        VALUE "Translation", 0x804, 1200
    END
END
```

程序内外都消费它：资源管理器显示它、安装器比对它决定升级/降级（34.5）、你的自更新逻辑读它判断新旧（34.6）。**程序内读取**走 version.dll 三件套（`GetFileVersionInfoSizeExW` → `GetFileVersionInfoW` → `VerQueryValueW`），就是 `examples/42_version_info` 的全部内容——它能读任何 exe/dll 的版本页，包括**用来探测操作系统版本**（读 `kernel32.dll` 的产品版本，比 `GetVersionExW` 那套受兼容垫片干扰的 API 诚实得多，21 章的 `RtlGetVersion` 之外的民间正解）。

注意 `Translation` 块与字符串块的 langID 必须配对：查询字符串要走 `"\\StringFileInfo\\<langID><charset>\\<键名>"` 路径，先查 `"\\VarFileInfo\\Translation"` 拿到实际 langID 再拼——42 示例演示了这个两段式（又是 19 章的"问尺寸"模式家族）。

## 34.4 应用清单：一个文件声明四件事

**manifest**（清单）是随 exe 的 XML 声明，把以前要靠 API 调用或系统猜的行为变成**声明式**。教程里三处"运行时写法"在这里合流成对照：

| 声明 | 替代的运行时写法 | 已讲章节 |
|------|----------------|---------|
| `<dpiAwareness>PerMonitorV2</dpiAwareness>` | `SetProcessDpiAwarenessContext` | 12 章 |
| 依赖 `Microsoft.Windows.Common-Controls` 6.0 | `InitCommonControlsEx` 之外的主题启用前提 | 6 章 |
| `<requestedExecutionLevel level="requireAdministrator">` | 右键"以管理员运行"/`ShellExecuteW` 提权 | 20 章 |
| `<longPathAware>true</longPathAware>` | `\\?\` 前缀长路径的清单开关 | 19 章 |

DPI 一项的示例：

```xml
<?xml version="1.0" encoding="UTF-8" standalone="yes"?>
<assembly xmlns="urn:schemas-microsoft-com:asm.v1" manifestVersion="1.0">
  <application xmlns="urn:schemas-microsoft-com:asm.v3">
    <windowsSettings>
      <dpiAwareness xmlns="http://schemas.microsoft.com/SMI/2016/WindowsSettings">PerMonitorV2</dpiAwareness>
      <longPathAware xmlns="http://schemas.microsoft.com/SMI/2016/WindowsSettings">true</longPathAware>
    </windowsSettings>
  </application>
  <!-- UAC：默认 asInvoker；要管理员就改 requireAdministrator（20 章） -->
  <trustInfo xmlns="urn:schemas-microsoft-com:asm.v3">
    <security>
      <requestedPrivileges>
        <requestedExecutionLevel level="asInvoker" uiAccess="false"/>
      </requestedPrivileges>
    </security>
  </trustInfo>
  <!-- 兼容性：声明"我支持 Win10/11"，换回真实版本号（21 章的另一种解法） -->
  <compatibility xmlns="urn:schemas-microsoft-com:compatibility.v1">
    <application>
      <supportedOS Id="{8e0f7a12-bfb3-4fe8-b9a5-48fd50a15a9a}"/>  <!-- Win10/11 -->
    </application>
  </compatibility>
</assembly>
```

两条工程规则：**声明优先于调用**（进程启动早期就生效，没有竞态窗口——DPI 声明尤其如此）；**一个 exe 一份清单**。嵌入方式二选一：`.rc` 里 `1 RT_MANIFEST "app.manifest"`，或链接器开关 `/MANIFEST:EMBED`（MSVC 默认会自动生成并嵌入一份最小清单，自定义就是替换它）。

## 34.5 安装器：MSI、脚本 EXE 与 MSIX

| 格式 | 工具 | 形态 | 特点 |
|------|------|------|------|
| **MSI** | WiX Toolset（写 XML 编译成 .msi） | Windows Installer 数据库 | 系统标准：事务性（装一半失败自动回滚）、组策略批量部署、`UpgradeCode` 升级链；语法繁琐 |
| **脚本 EXE** | NSIS / Inno Setup | 自解压安装向导 | 轻量灵活、脚本即全部逻辑；装写注册表、释文件、创快捷方式都是几行的事 |
| **MSIX** | MakeAppx / 打包工具 | 现代应用包 | 干净安装/卸载（不留注册表尸体）、增量更新、可上 Store；Win10 1607+ |

三者不互斥——同一个产品常常"官网发 EXE 安装器、企业客户给 MSI、上架 Store 用 MSIX"。感受一下三种脚本的真实长相（各取最内核的几行）：

```text
NSIS：                                     Inno Setup：
OutFile "MyAppSetup.exe"                   [Files]
InstallDir "$PROGRAMFILES64\MyApp"          Source: "MyApp.exe"; DestDir: "{app}"
Section                                    [Icons]
  SetOutPath "$INSTDIR"                     Name: "{autoprograms}\MyApp"; Filename: "{app}\MyApp.exe"
  File "MyApp.exe"                         [Run]
  WriteUninstaller "$INSTDIR\uninst.exe"    Filename: "{app}\MyApp.exe"; Flags: postinstall
SectionEnd
```

MSIX 值得多说两句：**Win32 程序可以直接打包成 MSIX**（MSIX Packaging Tool 或手动写清单），不用改一行代码——打包后获得容器化的干净卸载与自动更新，代价是文件写入被重定向到私有位置（virtualization），某些"往安装目录写配置"的老习惯会踩到。29 章说过的结论在这里落地：**工具类程序直接发 exe；要认真分发、要自动更新，MSIX 是现代答案**。

WiX/NSIS/Inno 的完整教程各自成书，本章给你的是选型判断力 + 认得出这三种脚本——真要做安装器时按表选工具查文档。

## 34.6 分发渠道、签名与更新

**渠道**：官网直链（便携 zip 或安装器）、Microsoft Store（MSIX）、包管理器（**winget**——微软官方仓库，提交一个 YAML 清单即可上架，用户 `winget install 你的应用`；Chocolatey 同理）。winget 清单核心几行（完整 schema 在 `microsoft/winget-pkgs` 仓库）：

```yaml
PackageIdentifier: Example.MyApp
PackageVersion: 1.2.0.7
Installers:
  - Architecture: x64
    InstallerUrl: https://example.com/MyAppSetup.exe
    InstallerType: nullsoft            # NSIS；Inno 是 inno，MSI 是 wix/msi
    InstallerSha256: <哈希>
```

**代码签名**：用代码签名证书 + `signtool sign /fd SHA256 /tr <时间戳服务器>` 给 exe/安装器签名。无签名的程序会被 **SmartScreen** 拦（"Windows 已保护你的电脑"），声誉攒起来之前下载量越少越难受——正式分发签名不是可选项。个人开发者的现实路径：先无签名直发攒口碑，或用 Azure Code Signing 等按量付费方案。

**版本号与更新**：

- 版本号用语义化版本（`主.次.修订.编译号`），与 VERSIONINFO、安装器升级逻辑、winget 清单**四处一致**——升级判断、回滚判定全靠它；
- **自更新的经典难题是"exe 不能覆盖正在运行的自己"**。标准舞步：新版本下载为 `MyApp_new.exe` → 把旧 `MyApp.exe` 改名 `MyApp_old.exe`（**运行中的 exe 允许改名**，只是不能写/删）→ 新版就位 → 下次启动删除旧文件（或用 `MoveFileEx(MOVEFILE_DELAY_UNTIL_REBOOT)` 托付给系统）。MSIX 则完全免舞步——更新是平台行为；
- 更新检查本身就是一个 HTTP 请求（拉一个版本 JSON 对比本地版本）——33 章的 Winsock 或更省事的 `WinHttpCrackUrl` 系就能做。

## 34.7 完整示例：版本信息读取器

`examples/42_version_info`（控制台，`version.lib` 同样源内链接）演示 34.3 的三件套：

```cpp
// 两段式：先问尺寸，再取数据（19 章的模式第 N 次出现）
DWORD handle = 0;
DWORD size = GetFileVersionInfoSizeExW(FILE_VER_GET_LOCAL_ONLY, path, &handle);
if (size == 0) { /* 没有版本资源——自己 build 的 exe 正是如此 */ }

std::vector<BYTE> data(size);
GetFileVersionInfoW(path, 0, size, data.data());

VS_FIXEDFILEINFO* ffi = nullptr; UINT ffiLen = 0;
VerQueryValueW(data.data(), L"\\", (void**)&ffi, &ffiLen);
// ffi->dwFileVersionMS / LS → 文件版本（高位/低位各打包两段）

struct Lang { WORD lang, codepage; }* langs = nullptr; UINT langLen = 0;
VerQueryValueW(data.data(), L"\\VarFileInfo\\Translation", (void**)&langs, &langLen);
wchar_t subblock[64];
swprintf_s(subblock, L"\\StringFileInfo\\%04x%04x\\ProductName",
           langs[0].lang, langs[0].codepage);       // 拼出 langID+charset 路径
wchar_t* product = nullptr; UINT productLen = 0;
VerQueryValueW(data.data(), subblock, (void**)&product, &productLen);
```

实测输出（无参数运行）：第一段读自己——`GetFileVersionInfoSizeExW` 返回 0、`GetLastError` 为 1813（`ERROR_RESOURCE_TYPE_NOT_FOUND`），"没有版本资源"（教学点：没做 34.3 的程序就是这个样子）；第二段读 `C:\Windows\System32\kernel32.dll`——完整打印二进制段与字符串段，其中产品版本就是操作系统的版本号（本机 Win11 实测打印 `10.0.26100.9549`，即 24H2 基线；文件版本却显示 6.2 开头——kernel32 二进制层面钉在兼容基线上，21 章"版本号骗人"的又一实证）。

## 34.8 易错清单

| 症状 | 原因 | 解法 |
|------|------|------|
| 程序在别人机器上起不来 | `/MD` 但没带 `vcruntime140.dll` | `/MT` 或 app-local 部署（34.2） |
| 往系统目录塞 vcruntime 被拒/留隐患 | 系统目录是 OS 的地盘 | DLL 放 exe 旁（22 章搜索顺序） |
| 右键属性没有"详细信息"页 | 没编入 VERSIONINFO | version.rc（34.3） |
| 装了新版旧版还在 / 升级降级混乱 | 版本号四处不一致 | VERSIONINFO/安装器/清单统一版本源（34.6） |
| 目标机器 DPI 模糊、UAC 弹错级别、版本号是 6.1 | manifest 没声明 dpiAwareness / requestedExecutionLevel / supportedOS | 34.4 的清单模板 |
| 无签名下载被 SmartScreen 拦 | 未签名 | signtool + 证书（34.6） |
| 自更新"拒绝访问" | 运行中的 exe 不能被写 | 改名腾位舞步（34.6） |
| MSIX 打包后配置"丢了" | 写入被虚拟化重定向 | 改写到 `ApplicationData`（34.5） |
| winget 上架被拒 | 清单哈希/版本不匹配 | InstallerSha256 与实际文件核对（34.6） |
| exe 在干净虚拟机缺 DLL | 第三方依赖没随包 | `dumpbin /dependents` 核对（34.1） |

## 34.9 小结

1. 交付三步：Release + pdb 留档、`dumpbin /dependents` 依赖核对、干净虚拟机验证。
2. CRT 现状：UCRT 是 Win10+ 系统组件；`/MT` 单文件自包含，`/MD` 配 app-local（DLL 放 exe 旁）——别再念"装 vcredist"的旧经。
3. VERSIONINFO 写版本、manifest 声明 DPI/提权级别/comctl32 6.0/长路径四大行为——声明优先于运行时调用。
4. 打包选型：企业标准化 MSI（WiX）、轻量向导 NSIS/Inno、现代分发与自动更新 MSIX（Win32 可直接打包）。
5. 分发：官网/Store/winget（YAML 清单）；签名过 SmartScreen；自更新用"改名腾位"舞步，MSIX 免舞步。

## 34.10 动手练习

1. 给任意一个本教程示例加 `version.rc`（34.3 模板）：`rc /fo build\ver.res version.rc` 后与 obj 一起链接，用 42 示例读回验证闭环。
2. 写一份 `app.manifest`（34.4 模板）嵌进去，对照效果：DPI 声明前后在高分屏上截屏对比、`requireAdministrator` 后看 UAC 盾牌图标（20 章的实验重做一遍声明版）。
3. 用 Inno Setup 或 NSIS 给"示例 14 的绘图板 + 示例 35 的 DLL"打一个安装器（装到 Program Files、创开始菜单快捷方式、带卸载），在干净目录验证安装/卸载不留垃圾。
4. 给 42 示例加命令行参数：批量读一个目录下所有 exe 的版本、按版本排序输出——一个简易的"依赖版本审计"工具。
