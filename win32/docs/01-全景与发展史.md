# 第 1 章 Win32 API 全景与发展史

> 本章回答的问题：Win32 API 到底是什么？它和 Windows 的关系是什么？三十多年来它经历了什么？哪些部分已经过时，哪些部分至今没有任何替代品？为什么 2026 年学习它仍然有价值？

## 1.1 重新定位：Win32 是操作系统的服务接口，不只是"窗口库"

很多教程把 Win32 讲成"用 C 写 Windows 窗口程序的方法"。这个理解只对了一小半。

更准确的定位是：**Win32 API 是 Windows 操作系统暴露给应用程序的官方 C 语言服务接口**。你的程序想要操作系统做任何事——申请内存、读写文件、启动进程、等待事件、显示窗口、绘制像素、枚举设备——都必须通过它。它是应用程序与操作系统内核之间那道唯一的官方大门。

从这个角度看，Win32 API 天然分成两大块：

| 板块 | 覆盖能力 | 现状 |
|------|---------|------|
| **系统服务层** | 进程、线程、同步、内存、文件、注册表、DLL 加载、安全、网络、设备 | **至今没有替代品**。无论上层用什么语言、什么框架，最终都落到这里 |
| **界面与图形层** | 窗口、消息、控件、对话框、GDI、菜单 | 不断被新的 UI 技术封装和更替，但底层的窗口与消息模型从未被替换 |

理解这张表，就理解了学习 Win32 的真正价值：

- **系统服务层是永久的**。.NET 运行时的 `FileStream` 底层是 `CreateFileW`；Java 的 `Thread` 底层是 `CreateThread`；Chrome 的进程模型用 `CreateProcessW` 和 Job 对象搭建；WSL、Docker Desktop、VS Code 的文件监视用 `ReadDirectoryChangesW`。任何认真做 Windows 系统级软件的人，绕不开这层。
- **界面层是演化的地基**。MFC、WPF、WinForms、UWP、WinUI 3 都建在同一个窗口/消息模型之上。学了 Win32，这些框架对你不再是黑盒。

所以本教程的章节安排是均衡的：窗口与消息部分约占一半，进程、线程、内存、文件这些系统服务部分占另一半。这不是"附加内容"，而是 Win32 的本体。

## 1.2 分层视图：一个 API 调用到底经过了什么

当你的程序调用 `CreateFileW` 时，请求会穿过下面这条链：

```text
你的程序 (test.exe)
    │  调用 CreateFileW —— 这个函数在哪里？
    ▼
Windows SDK 头文件 + 导入库 (kernel32.lib)
    │  链接时解析到 kernel32.dll 的导出
    ▼
子系统 DLL：kernel32.dll / user32.dll / gdi32.dll ...
    │  很多函数在这里只是"转发站"
    ▼
API Set（api-ms-win-core-file-l1-1-0.dll 之类的逻辑名字）
    │  按名字路由到真正的实现
    ▼
ntdll.dll —— 系统调用的统一入口
    │  syscall 指令陷入内核
    ▼
Windows 内核 (ntoskrnl.exe：对象管理器、I/O 管理器、内存管理器)
    │        +
    │  win32k.sys（窗口管理器与 GDI 的内核部分）
    ▼
硬件
```

初学阶段你不需要背这条链，但要知道三个事实：

1. **你 import 的 DLL 不一定是实现者**。`kernel32.dll` 中大量的文件、进程函数实际通过 API Set 转发到别的模块。API Set 是 Windows 8 引入的"逻辑 DLL 名"机制，目的是让系统组件解耦重构而不破坏应用兼容性。第 19 章讲 DLL 时会回到这里。
2. **GUI 相关调用要跨两个世界**。窗口和 GDI 的实现横跨用户态（`user32.dll`）和内核态（`win32k.sys`），这是它比纯文件操作复杂得多的原因之一。
3. **所有系统调用最终汇聚在 `ntdll.dll`**。微软不承诺 `ntdll` 的接口稳定，官方契约只到 Win32 API 这一层——这就是"Win32 是官方边界"的含义。

常用的子系统 DLL 及其分工：

| DLL | 职责 | 典型 API |
|-----|------|---------|
| `kernel32.dll` | 进程、线程、内存、文件、同步、堆、控制台 | `CreateProcessW` `VirtualAlloc` `CreateFileW` `WaitForSingleObject` |
| `user32.dll` | 窗口、消息、菜单、输入、对话框 | `CreateWindowExW` `GetMessage` `SendMessageW` |
| `gdi32.dll` | 二维绘图、字体、位图 | `BeginPaint` `TextOutW` `CreatePen` |
| `shell32.dll` | 桌面集成、资源管理器、文件对话框 | `ShellExecuteW` |
| `comctl32.dll` | 通用控件（工具栏、列表视图等） | 工具栏、状态栏 |
| `advapi32.dll` | 注册表、安全、服务 | `RegOpenKeyExW` |
| `psapi.dll` | 进程/内存信息查询 | `GetProcessMemoryInfo` |
| `dwmapi.dll` | 桌面窗口管理器（Vista+） | `DwmSetWindowAttribute` |
| `ntdll.dll` | 系统调用入口（非官方契约） | —— |

## 1.3 发展史：从 1985 年到 Windows 11

Win32 不是一天设计出来的，也不是一个版本发布的。把历史切成几个时代，每个时代留下来的"遗产"至今都写在 API 的形状里。

### 1）前史：Win16 时代（1985–1993）

Windows 1.0 到 3.1 跑在 16 位 DOS 之上，API 称为 Win16。这个时代的遗产是**包袱最重的地方**：

- `WPARAM`（word parameter）名字里的 "W" 是 16 位的 word——如今它已经是 64 位了，但名字改不了；
- `LONG` 指针类型、`NEAR`/`FAR` 的痕迹、`GlobalAlloc`/`LocalAlloc` 这种"全局/局部堆"的区分，都是 16 位分段内存模型的遗物，Win32 之后就只是历史兼容物；
- 消息驱动的编程模型在 Win16 就已定型，沿用至今。

### 2）Win32 的诞生：NT 3.1 与 Windows 95（1993–1995）

两条路线同时推出 32 位 API，合流为 Win32：

- **Windows NT 3.1（1993）**：全新的 32 位内核，天生支持抢占式多任务、每个进程独立地址空间、Unicode。今天所有 Windows 都是 NT 家族的后代。
- **Windows 95（1995）**：面向消费市场的 32 位系统，为了在 4MB 内存的机器上跑起来和兼容 16 位程序，内部做了大量妥协。

这个时代定型的东西构成了今天 Win32 的主体：`CreateProcess`、`CreateThread`、`VirtualAlloc`、`CreateFile`、窗口类、消息循环——本教程第 4 章到第 16 章的内容，骨架都在这里。

### 3）NT 统一与 64 位化（1996–2005）

- **Windows 2000 / XP**：消费市场全面转到 NT 内核。NT 4.0 把 GDI 从用户态搬进内核，图形性能大幅提升。
- **Windows XP Professional x64（2003/2005）**：指针从 32 位变 64 位。Win32 API 的应对方式不是推倒重来，而是引入 `DWORD_PTR`、`UINT_PTR`、`LONG_PTR` 这些"指针宽度"类型，以及 `WPARAM`/`LPARAM` 升为 64 位。**旧程序几乎不用改就能重编译**——这种向后兼容的执念是 Win32 最重要的设计哲学。

### 4）现代化改造：Vista 与 Windows 7（2006–2012）

Vista 是一次大规模的安全与图形现代化，对开发者影响深远：

- **UAC（用户账户控制）**：程序默认没有管理员权限，"写进程序目录"这类习惯从此失效，manifest 与权限提升成为必修课；
- **DWM（桌面窗口管理器）**：所有窗口改由系统合成渲染，GDI 窗口也如此，从此有了毛玻璃、缩略图动画；
- **Session 0 隔离**：服务不再能显示窗口，后台服务与 UI 正式分离；
- **大量新同步原语**：`SRWLock`、条件变量、线程池 API 都在这个时代加入（第 14 章会讲），它们的性能远超 `CRITICAL_SECTION`，但很多教材至今还在只教老的东西。

### 5）动荡期：Windows 8 / 8.1（2012–2015）

微软试图用 WinRT（全新的面向对象 API 层）和 UWP 取代 Win32。结果证明 UI 层可以另起炉灶，**系统服务层无法替代**——开发者仍然需要文件、进程、内存这些底层能力。这个时代最重要的遗产是 API Set 机制和"UWP 沙箱"概念。

### 6）复兴期：Windows 10（2015–2021）

Win32 在 Windows 10 时代强势回归，微软自己也承认桌面主力应用（Office、Photoshop、Chrome、游戏）全是 Win32。这一时期对 Win32 的重要新增：

- **Per-Monitor V2 DPI 感知（1703，2017）**：混合高 DPI 屏幕的时代必需品，窗口级 DPI 感知（第 9 章）；
- **ConPTY（1809，2018）**：伪控制台 API，Windows Terminal、VS Code 集成终端的基础；
- **`VirtualAlloc2` / `MapViewOfFile3`（1803）**：支持内存分区与占位符分配的新一代内存 API（第 15 章）；
- **`SetThreadDescription`（1607）**：终于可以给线程起名字了，调试器直接可见（第 14 章）；
- **Job 对象、进程缓解策略持续增强**：Chrome 等浏览器用它做沙箱（第 13 章）；
- **MSIX 与桌面桥**：Win32 程序可以打包进现代分发体系。

### 7）当下：Windows 11（2021–）

Win11 的界面焕然一新，但对 Win32 开发者而言，变化是"加法"而非"替换"：

- **圆角窗口**：`DwmSetWindowAttribute` + `DWMWA_WINDOW_CORNER_PREFERENCE`，一行代码获得系统圆角（第 9 章）；
- **Mica / Acrylic 材质**：`DWMWA_SYSTEMBACKDROP_TYPE`，让窗口背景融入桌面壁纸；
- **WinUI 3**：新一代 UI 框架，但它运行在 Win32 窗口模型之上——证据就是 WinUI 3 程序的进程里照样有消息循环和 HWND。

## 1.4 哪些被更替了，哪些永远没有

这张表是本章最重要的结论：

| 能力 | 老写法 | 后来的封装/替代 | 底层还有替代品吗 |
|------|--------|----------------|----------------|
| 窗口与消息 | user32 | MFC / WinForms / WPF / WinUI | **没有**——所有框架都落在同一套 HWND 与消息上 |
| 二维绘图 | GDI | Direct2D、DirectWrite（GDI 仍在维护） | 有替代，但 GDI 因简单仍是入门首选 |
| 进程 | `CreateProcessW` | 无 | **没有** |
| 线程与同步 | `CreateThread`、`CRITICAL_SECTION` | C++ `std::thread`、OpenMP | **没有**——`std::thread` 在 Windows 上就是 `CreateThread` 的封装 |
| 内存 | `VirtualAlloc` / 堆 API | C++ `new`、各种分配器 | **没有**——所有分配器最终问内核要内存 |
| 文件 | `CreateFileW` | C 标准库、`std::filesystem` | **没有**——`std::filesystem` 在 Windows 上包着这些 API |
| DLL | `LoadLibraryW` | 无 | **没有** |

一句话：**UI 会过时，系统服务不会**。这也是本教程把进程/线程/内存/文件作为一级公民来写的原因。

## 1.5 初学者最容易误解的四个概念

现在预先澄清四个贯穿全书的概念，后面各章会展开：

**1）句柄（Handle）**：Win32 里几乎所有系统资源都用一个不透明的 32/64 位值代表，叫句柄。`HWND` 是窗口句柄、`HANDLE` 是通用内核对象句柄、`HDC` 是绘图上下文句柄。你从不直接访问句柄指向的东西，只能把它交还给 API。句柄是需要归还的资源——`CloseHandle`、`DestroyWindow`、`DeleteObject` 都是"归还"动作（第 4 章展开）。

**2）A/W 双轨与 `TCHAR`**：绝大多数有字符串参数的 API 都有 `CreateWindowA`（ANSI）和 `CreateWindowW`（宽字符）两个版本。**现代代码一律直接用 `W` 版本 + `wchar_t` + `L"..."` 字面量**，不要碰 `TCHAR`/`TEXT` 宏——它们是 90 年代为了能在 ANSI/Unicode 之间切换发明的，今天只制造混乱（第 2 章展开）。

**3）消息驱动**：Windows GUI 程序不是"你写主流程然后调用界面"，而是"你注册一个窗口过程函数，系统在事件发生时调用你"。程序主体是一个不断取消息、分发消息的循环（第 4 章展开）。

**4）版本宏**：`WINVER` 和 `_WIN32_WINNT` 宏决定你的程序声明支持的最老 Windows 版本，从而决定能看到哪些新 API。想用 `SetThreadDescription` 就必须把宏设到 `_WIN32_WINNT_WIN10` 以上（第 2 章讲怎么设）。
