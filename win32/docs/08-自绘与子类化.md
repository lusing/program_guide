# 第 8 章 自绘与子类化

> **本章回答的问题**：系统控件的样子能不能改？Owner Draw 和 Custom Draw 差在哪？想改控件的行为（而不只是长相）怎么办？`SetWindowSubclass` 比老的子类化方法好在哪？
>
> **前置章节**：第 6 章（`WM_NOTIFY`/结构体通知）、第 7 章（comctl32 家族）。
>
> **你将做出什么**：三个"与众不同"的控件（`examples/19_custom_draw`）：按下变色的自绘按钮、隔行变色的列表、输入自动转大写的编辑框。

本章示例：`examples/19_custom_draw/main.cpp`。

## 8.1 外观定制的四条路：按代价选

"这控件长得不行"——按改造深度从浅到深，有四条路：

| 路 | 做法 | 代价 | 适用 |
|----|------|------|------|
| ① 样式/消息参数 | 换样式位、发设置消息（第 5~7 章一直在做） | 零 | 系统设计内的外观选项 |
| ② Custom Draw | 接管**部分**绘制阶段（改颜色最划算） | 低 | 列表行颜色、字体微调 |
| ③ Owner Draw | 系统**只给画布**，全画自己来 | 中 | 完全自定义的按钮/菜单项 |
| ④ 完全自绘 | 不要系统控件，整窗自己画 | 高 | 特殊交互、游戏化界面（第 25 章 Direct2D 是正路） |

原则：**能用浅的绝不用深的**。本章讲②③和"改行为"的子类化，④留给 Direct2D 章。

## 8.2 Owner Draw：系统给画布，你落笔

三步走：

**第一步**，创建控件时声明"我要自己画"（按钮加 `BS_OWNERDRAW`）：

```cpp
CreateWindowExW(0, L"BUTTON", L"",
    WS_CHILD | WS_VISIBLE | BS_OWNERDRAW,       // ★ 声明自绘
    10, 10, 160, 40, hwnd, (HMENU)(INT_PTR)IDC_ODBTN, hInst, nullptr);
```

**第二步**，绘制的不是你，而是**父窗口**在 `WM_DRAWITEM` 里干（控件把"该画了"连同画布交给父窗口）：

```cpp
case WM_DRAWITEM: {
    DRAWITEMSTRUCT* dis = (DRAWITEMSTRUCT*)lParam;
    if (dis->CtlID != IDC_ODBTN) break;

    // 按下状态换色：系统在 itemState 里告诉你
    COLORREF bg = (dis->itemState & ODS_SELECTED) ? RGB(0x7A, 0x1F, 0xC8)
                                                  : RGB(0x2B, 0x7B, 0xD5);
    HBRUSH brush = CreateSolidBrush(bg);
    FillRect(dis->hDC, &dis->rcItem, brush);
    DeleteObject(brush);
    SetBkMode(dis->hDC, TRANSPARENT);
    SetTextColor(dis->hDC, RGB(255, 255, 255));
    DrawTextW(dis->hDC, L"自绘按钮（按下变色）", -1, &dis->rcItem,
              DT_CENTER | DT_VCENTER | DT_SINGLELINE);
    return TRUE;    // ★ 告诉系统"画完了"（不返回 TRUE 会被默认处理再涂一遍）
}
```

**第三步**，记住 `DRAWITEMSTRUCT` 的关键字段：

| 字段 | 含义 |
|------|------|
| `hDC` | 画布（已裁剪到控件区域） |
| `rcItem` | 画多大 |
| `CtlID` / `CtlType` | 谁在求画（多控件共用处理时先分流） |
| `itemState` | 状态位：`ODS_SELECTED`（按下）、`ODS_FOCUS`（焦点）、`ODS_DISABLED`（禁用） |
| `itemData` | Owner Draw 列表/组合框时挂的每项自定义数据 |

Owner Draw 适用面比按钮宽：菜单项（`MF_OWNERDRAW`）、列表框/组合框条目（`LBS_OWNERDRAWFIXED`）都能这么干——套路统一为"声明 + 父窗口 WM_DRAWITEM"。**代价**：焦点框、禁用态、悬停效果……系统全不管了，都得自己画。

## 8.3 Custom Draw：只接管你要的阶段

ListView 的隔行变色若用 Owner Draw，整行绘制全接管（选中高亮、图标、文本对齐全自己来）——杀鸡用牛刀。**Custom Draw** 提供"两阶段握手"，允许只改颜色、其余仍由系统画：

```text
阶段一：CDDS_PREPAINT（整个控件画之前）
   └─ 返回 CDRF_NOTIFYITEMDRAW ──"申请逐项通知"
阶段二：CDDS_ITEMPREPAINT（每一项画之前）
   └─ 改 NMLVCUSTOMDRAW 的 clrTextBk / clrText
   └─ 返回 CDRF_NEWFONT ──"颜色改了，按新色继续画"
（不申请就收不到阶段二——这是"改了没反应"的第一嫌疑人）
```

代码骨架（在 `WM_NOTIFY` 里，第 6 章的通道）：

```cpp
case WM_NOTIFY: {
    LPNMHDR nm = (LPNMHDR)lParam;
    if (nm->idFrom == IDC_LIST && nm->code == NM_CUSTOMDRAW) {
        LPNMLVCUSTOMDRAW cd = (LPNMLVCUSTOMDRAW)lParam;
        switch (cd->nmcd.dwDrawStage) {
        case CDDS_PREPAINT:
            return CDRF_NOTIFYITEMDRAW;          // ① 申请逐项
        case CDDS_ITEMPREPAINT: {                 // ② 每项画前改色
            int row = (int)cd->nmcd.dwItemSpec;
            cd->clrTextBk = (row % 2) ? RGB(0xE4, 0xEF, 0xFB) : RGB(255, 255, 255);
            return CDRF_NEWFONT;
        }
        }
    }
    break;
}
```

注意返回值走 `WndProc` 的返回值（`WM_NOTIFY` 的协议），不是写到结构体里。Custom Draw 还能继续下钻（`CDRF_NOTIFYPOSTPAINT`、子项级 `CDDS_SUBITEM | CDDS_ITEMPREPAINT`——每格单独上色），机制相同：**你要什么阶段，就在上一阶段申请什么**。

与 Owner Draw 的分工一句话：**改颜色用 Custom Draw，改内容布局用 Owner Draw**。

## 8.4 子类化：改行为，不是改外观

以上都在改"长相"。想改**行为**——比如"编辑框输入自动转大写"——需要拦截发给控件的消息，在它到达控件自己的窗口过程之前加工。这就是**子类化（subclassing）**：给窗口换一个"代理过程"。

**老方法**（了解即可，读旧代码必备）：

```cpp
WNDPROC oldProc = (WNDPROC)SetWindowLongPtrW(hEdit, GWLP_WNDPROC, (LONG_PTR)MyProc);
// MyProc 里：处理完自己的逻辑后 CallWindowProcW(oldProc, ...) 转发
```

两个坑：64 位下早期代码用 `SetWindowLong`（32 位截断）会崩；多个模块同时子类化同一窗口时，拆除顺序不当会跳过别人的过程。

**现代方法**（comctl32 提供，本教程采用）：

```cpp
// 安装：带 id，可叠层，过程签名固定六参
SetWindowSubclass(hEdit, SubEditProc, 1, 0);

LRESULT CALLBACK SubEditProc(HWND hwnd, UINT msg, WPARAM wParam, LPARAM lParam,
                             UINT_PTR uIdSubclass, DWORD_PTR dwRefData) {
    if (msg == WM_CHAR && wParam >= L'a' && wParam <= L'z') {
        wParam -= L'a' - L'A';                   // ★ 加工参数：小写转大写
    }
    return DefSubclassProc(hwnd, msg, wParam, lParam);   // 其余交给原过程
}

// 拆除（WM_DESTROY）：
RemoveWindowSubclass(hEdit, SubEditProc, 1);
```

三个要点：

- `DefSubclassProc` 是"继续原链"的正规出口（内部自动找原过程），**别在子类过程里直接 `CallWindowProc`**；
- 每条消息都会先过你手：这是"拦截、加工、放行"的通用模式（统计、热键、校验都能做）；
- 安装/拆除配对，id 区分不同安装——叠两层子类互不干扰。

子类化 + Custom Draw/Owner Draw 组合，就得到了"外观行为都自定义"的完整自由度。

## 8.5 完整示例解剖

`examples/19_custom_draw/main.cpp` 三段对应三条技术：

1. **自绘按钮**：`BS_OWNERDRAW` + `WM_DRAWITEM`，按 `ODS_SELECTED` 切换底色，`return TRUE`；
2. **隔行变色列表**：`NM_CUSTOMDRAW` 两阶段握手，`clrTextBk` 交替两色；
3. **大写编辑框**：`SetWindowSubclass` 拦 `WM_CHAR` 改参数，`DefSubclassProc` 放行。

运行体验点：按住按钮看变色；看列表奇偶行底色；在编辑框敲小写看自动大写——三条技术一次看全。

## 8.6 去处：再往上是什么

本章的三条路都还"住在系统控件里"。当需求走到系统控件给不了的交互（异形面板、动画密集、游戏 HUD），就该抛弃控件、整窗自绘——那正是 **Direct2D** 的领地（第 25 章：工厂/渲染目标/画刷三件套，渲染进 HWND）。到时候回头看，GDI 绘图（第 9 章）的一切概念都还管用。

## 8.7 易错清单

| 症状 | 原因 | 解法 |
|------|------|------|
| `WM_DRAWITEM` 画了还被涂掉 | 没返回 `TRUE` | 8.2 |
| 自绘按钮没有焦点框 | Owner Draw 后系统不管了 | 查 `ODS_FOCUS` 自己画 `DrawFocusRect` |
| Custom Draw 改色没反应 | 阶段一没返回 `CDRF_NOTIFYITEMDRAW` | 8.3（两阶段握手） |
| Custom Draw 返回值没生效 | 往结构体里写而不是 return | 8.3（走 WndProc 返回值） |
| 子类过程后控件行为全乱 | 忘走 `DefSubclassProc` | 8.4 |
| 退出后偶发崩溃 | `RemoveWindowSubclass` 没配对 | `WM_DESTROY` 拆除 |
| 老代码 64 位崩 | `SetWindowLong` 32 位截断 | 读到就改 `SetWindowLongPtr`/`SetWindowSubclass` |

## 8.8 小结

1. 外观定制按代价排序：样式参数 → Custom Draw（改色）→ Owner Draw（全画）→ 完全自绘（第 25 章）。
2. Owner Draw = 声明样式 + 父窗口 `WM_DRAWITEM`；状态在 `itemState`，处理完 `return TRUE`。
3. Custom Draw = 两阶段握手：`PREPAINT` 申请逐项，`ITEMPREPAINT` 改色返回 `CDRF_NEWFONT`。
4. 改行为用子类化：`SetWindowSubclass` + `DefSubclassProc` + `RemoveWindowSubclass` 三件套。
5. 想要完全自由 = 走 Direct2D，系统控件的世界到此为止。

## 8.9 动手练习

1. 给自绘按钮补"悬停变色"：处理 `WM_MOUSEMOVE` 追踪光标是否在按钮区（或查 `ODS_HOTLIGHT` 状态与 `WM_DRAWITEM` 的触发条件——需要让系统重画，`InvalidateRect`）。
2. 把隔行变色改成"三色循环"，并给偶数行同时改文字颜色（`clrText`）。
3. 子类化挑战：拦 `WM_PASTE`，把粘贴进编辑框的文本里的空格全部删除（提示：拦下后自己取剪贴板内容加工——第 29 章的剪贴板 API 可以提前用）。
