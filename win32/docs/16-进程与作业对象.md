# 第 16 章 进程与作业对象

> **本章回答的问题**：进程和线程到底是什么关系？怎么启动一个程序并等它结束？怎么列出系统里所有进程？`TerminateProcess` 为什么是"最后手段"？Job 对象解决什么问题？
>
> **前置章节**：第 3 章（错误处理）、第 15 章（命令行里的编码）；线程与同步是下一章的主角，本章只在概念上分清两者。
>
> **你将做出什么**：一个进程管理器（`examples/08_process_manager`）：枚举、启动、结束进程的完整 GUI 工具。

本章示例：`examples/08_process_manager/main.cpp`。

> 本章进程属性、终止语义与作业部分参考《Windows 核心编程》（Jeffrey Richter）第 4~5 章整理。

## 16.1 概念：进程是容器，线程是执行流

- **进程**：一个正在运行的程序实例 = 独立的虚拟地址空间 + 资源句柄表 + 安全上下文 + **至少一个线程**。进程不执行任何代码，它只是容器。
- **线程**：进程内被调度执行代码的实体，拥有自己的栈和寄存器状态。同一进程内的多个线程**共享全部地址空间**——这是效率的来源，也是灾难的来源（怎么管住它，见第 17 章）。
- **PID**：进程的唯一编号；**句柄**：进程对象的访问凭证（`OpenProcess` 拿到，用完 `CloseHandle`）。

```text
┌── 进程（容器）────────────────────────────┐
│  虚拟地址空间：代码/数据/堆/加载的 DLL        │
│  句柄表  │  安全令牌  │  至少 1 个线程 ──→ ┌─ 线程：栈 + 寄存器 = 执行流
│                                        └─ 线程：可以有很多个（第 17 章）
└────────────────────────────────────────┘
```

所有进程 API 在 `kernel32.dll`，信息查询类在 `psapi.dll`/`tlhelp32.h`。

## 16.2 启动进程：`CreateProcessW`

```cpp
wchar_t cmd[] = L"notepad.exe";        // ★ 必须是可写缓冲区（见下）
STARTUPINFOW si = { sizeof(si) };      // 子进程的启动外观（窗口大小、句柄继承等）
PROCESS_INFORMATION pi = {};           // 返回：进程句柄、主线程句柄、两个 ID

BOOL ok = CreateProcessW(
    nullptr,            // 应用程序路径；nullptr 表示从命令行解析
    cmd,                // 命令行（可写！）
    nullptr, nullptr,   // 安全属性，默认
    FALSE,              // 不继承句柄
    0,                  // 创建标志（CREATE_SUSPENDED 可让进程先挂起）
    nullptr, nullptr,   // 环境变量、工作目录
    &si, &pi);

if (ok) {
    // pi.hProcess / pi.hThread 是你的两个句柄，pi.dwProcessId 是 PID
    CloseHandle(pi.hThread);    // 不等主线程就先还掉它的句柄
    CloseHandle(pi.hProcess);   // 不需要等待/取退出码就一起还掉
}
```

三个易错点：

1. **命令行参数必须可写**：文档写明"本函数可能修改该缓冲区"（它要在原地补引号、补路径）。`CreateProcessW(nullptr, (LPWSTR)L"notepad.exe", ...)` 把只读字面量强转传入是未定义行为——照上面先拷进局部数组。
2. **两个句柄都要还**。不 `CloseHandle` 不只是泄漏——只要你还持有 `hProcess`，**即使子进程退出，它也不会真正结束**（进程对象保持到所有句柄关闭），做"启动后等待退出"逻辑时尤其致命。
3. **失败判断**：返回 `FALSE` 后查 `GetLastError()`；找不到 exe 是 `ERROR_FILE_NOT_FOUND`。

等待子进程结束并取退出码：

```cpp
WaitForSingleObject(pi.hProcess, INFINITE);     // 线程句柄、进程句柄、事件……都能等
DWORD code = 0;
GetExitCodeProcess(pi.hProcess, &code);         // 即子进程 main/wWinMain 的返回值
```

"启动外部工具并等待"（编译器包装器、安装器、构建脚本）就是这两行。

### 参数深读：应用名、搜索顺序与创建标志

《核心编程》4.2 节对 `CreateProcess` 参数的考据值得知道三层：

1. **`pszApplicationName` 几乎永远传 `nullptr`**——此时系统把命令行**第一个 token**当 exe 名，并按固定顺序搜索：调用进程的 exe 目录 → 当前目录 → 系统目录（System32）→ Windows 目录 → `PATH`。这解释了"为什么 `notepad` 不用写全路径"，也解释了"当前目录排在 PATH 前面"这个被多数人记反的顺序（安全上要警惕：攻击者在你当前目录放的假 exe 会赢过 PATH 里的真货）。反过来显式给 `pszApplicationName` 时命令行第一 token 不再用于定位 exe——`argv[0]` 由命令行原样决定，可以与真实 exe 无关；
2. **`fdwCreate` 常用标志**：`CREATE_SUSPENDED`（先建后跑，17.2 节"先设置属性再 Resume"）、`CREATE_NEW_CONSOLE`/`CREATE_NO_WINDOW`（控制台子进程的窗口策略）、`DETACHED_PROCESS`（脱离控制台）、`CREATE_NEW_PROCESS_GROUP`（Ctrl+C 分组，让子进程不受父进程 ^C 影响）、`CREATE_UNICODE_ENVIRONMENT`（自造环境块时必须给，指明块是宽字符）、`CREATE_BREAKAWAY_FROM_JOB`（脱离父作业，见 16.5）、`DEBUG_PROCESS`（把自己变成子进程的调试器）；
3. **环境块（`lpEnvironment`）**：传 `nullptr` = 子进程**拷贝**一份父进程的环境（注意是拷贝不是共享——子进程改了不影响父进程，反之亦然）。自己构造环境块时格式是 `名字=值\0名字=值\0\0`（按名字排序、双 \0 结尾、宽字符时要加 `CREATE_UNICODE_ENVIRONMENT`）。

### 命令行与环境变量：进程自带的两个"配置面"

进程自己视角的两个入口（不只是父进程的事）：

```cpp
// 完整命令行（含 exe 全路径）——wWinMain 的 pszCmdParam 只是它的一段
LPWSTR cmdline = GetCommandLineW();
int argc = 0;
LPWSTR* argv = CommandLineToArgvW(cmdline, &argc);   // 拆成 argc/argv（shell32）
LocalFree(argv);                                      // 它分配在堆上，要还

// 环境变量三件套
wchar_t buf[256];
GetEnvironmentVariableW(L"PATH", buf, 256);          // 读（返回所需长度，0=不存在）
SetEnvironmentVariableW(L"MYAPP_LEVEL", L"debug");   // 写/删（值传 nullptr 删除）
ExpandEnvironmentStringsW(L"%USERPROFILE%\\cfg.ini", buf, 256);   // 展开 %var%
```

环境块由**登录会话**从注册表（`HKLM\...\Environment` + `HKCU\Environment`）初始化，子进程逐级拷贝继承。改了注册表想让已运行的 Explorer 等程序刷新，广播 `WM_SETTINGCHANGE`（lParam 指向字符串 `"Environment"`）——安装器的标准动作。

## 16.3 枚举进程：工具帮助快照

任务管理器式的进程列表用 ToolHelp 快照 API（`tlhelp32.h`）：

```cpp
#include <tlhelp32.h>

HANDLE snap = CreateToolhelp32Snapshot(TH32CS_SNAPPROCESS, 0);  // 拍下全系统进程快照
if (snap != INVALID_HANDLE_VALUE) {
    PROCESSENTRY32W pe = { sizeof(pe) };          // ★ dwSize 必须先填！
    if (Process32FirstW(snap, &pe)) {
        do {
            wprintf(L"%lu\t%ls\n", pe.th32ProcessID, pe.szExeFile);
        } while (Process32NextW(snap, &pe));      // 循环遍历到返回 FALSE
    }
    CloseHandle(snap);                            // 快照也是句柄
}
```

注意这个 API 的复古风格：`dwSize` 先赋值（版本协商，同 `WNDCLASSEX.cbSize`）、`First/Next` 循环范式（同 `FindFirstFile`）。`PROCESSENTRY32W` 里还有父进程 PID、线程数、内存占用等字段。

现代替代：`EnumProcesses`（psapi）只给 PID 数组，再逐个 `OpenProcess` 查名字；更完整的查询走 `NtQuerySystemInformation`（非官方契约，别用）。初学用 ToolHelp 即可，它 1998 年至今没变过。

## 16.4 打开、终止进程

```cpp
// 按 PID 打开：权限按需申请，给多了会被安全策略拒绝
HANDLE h = OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION | SYNCHRONIZE, FALSE, pid);
// 常用权限：PROCESS_QUERY_LIMITED_INFORMATION 查状态
//          SYNCHRONIZE 等待退出
//          PROCESS_TERMINATE 强杀
//          PROCESS_VM_READ 读内存（第 18 章用）
```

**终止进程的两种姿势**，语义天差地别：

```cpp
// 优雅：请求 GUI 程序自己关（向它的顶层窗口发 WM_CLOSE）
PostMessageW(hWndOfTarget, WM_CLOSE, 0, 0);   // 程序可弹"保存吗"，可拒绝

// 强制：TerminateProcess——立即杀死，无任何清理机会
HANDLE h = OpenProcess(PROCESS_TERMINATE, FALSE, pid);
if (h) {
    TerminateProcess(h, 1);       // 目标进程的 DLL 不收卸载通知、缓冲数据全丢
    CloseHandle(h);
}
```

`TerminateProcess` 是文档明言的"最后手段"：目标没有机会运行任何清理代码。正常业务用 `WM_CLOSE` 或让子进程响应约定的退出信号；只有任务管理器式的"强杀"工具才用它。

### 进程终止时发生了什么

终止进程其实有四条路（按体面程度排序）：**主线程入口函数返回**（唯一"自然"的路，CRT 会调用已析构的全局对象、刷新 stdio 缓冲）、`ExitProcess`（跳过其他线程与 C++ 析构）、`TerminateProcess`（外部强杀，零清理）、以及"最后一个线程自己结束"。无论哪条路，内核做的收尾是同一套（《核心编程》4.3.4 的清单）：

1. 剩余所有线程终止（它们没有机会说再见——这就是"多线程程序别用 `ExitProcess`"的原因）；
2. 该进程的所有**用户对象/GDI 对象**被释放；**内核对象**被关闭——但若别的进程还持有句柄，对象本体继续活着；
3. 退出码从 `STILL_ACTIVE`（`0x103`）改为最终值；
4. **进程内核对象变为已触发状态**——所以 `WaitForSingleObject(hProcess, ...)` 能等到它（第 17 章的"可等待对象"）；
5. 使用计数减一。

第 2/5 条合起来是个关键认知：**"进程死了"≠"进程对象没了"**。只要父进程还捏着 `hProcess`，内核就保留着退出码与统计（CPU 时间等）供你 `GetExitCodeProcess` 查询；句柄一关，对象才真正销毁。轮询 `STILL_ACTIVE` 判死是不优雅且不可靠的（退出码恰好是 `0x103` 就误判），正解是等待函数。

## 16.5 现代：Job 对象 —— 管理一组进程

> 💡 **现代视角（Windows 2000 引入，Vista 后大幅增强）**：真实软件很少只管一个子进程。Chrome 的每个标签页进程、编译器的进程池、构建系统的子进程树，都挂在一个 **Job 对象**下统一管理：子进程崩了全组回收、限制整组内存/CPU、整组终止。

```cpp
HANDLE hJob = CreateJobObjectW(nullptr, nullptr);

JOBOBJECT_EXTENDED_LIMIT_INFORMATION limit = {};
limit.ProcessMemoryLimit = 512 * 1024 * 1024;              // 整组内存上限 512MB
limit.BasicLimitInformation.LimitFlags = JOB_OBJECT_LIMIT_PROCESS_MEMORY;
SetInformationJobObject(hJob, JobObjectExtendedLimitInformation, &limit, sizeof(limit));

AssignProcessToJobObject(hJob, childProcess);   // 把子进程收编（可收多个）

// 想整组终结：TerminateJobObject(hJob, 1);
// 想感知"整组全退了"：Job 对象可配事件通知（JobObjectAssociateCompletionPortInformation）
```

一个标志性的实用点：默认情况下子进程"继承"父进程的 Job。做"我的程序要被别人的 Job 管理"（比如在 CI 里运行）时，用 `CREATE_BREAKAWAY_FROM_JOB` 标志让子进程脱离。

### Job 的三类限制与两类通知

限制分三个信息类，按需组合（`SetInformationJobObject` 的第二参）：

| 信息类 | 能限制什么 | 代表标志 |
|--------|-----------|---------|
| `JobObjectBasicLimitInformation` | CPU 时间（单进程/整组）、活跃进程数上限、优先级类、亲缘性、UI 桌面限制（禁剪贴板/禁读屏等 `JOB_OBJECT_UILIMIT_*`） | `JOB_OBJECT_LIMIT_PROCESS_TIME`、`JOB_OBJECT_LIMIT_ACTIVE_PROCESS` |
| `JobObjectExtendedLimitInformation`（超集） | **内存**：单进程 / 整组提交上限、保留峰值（`PeakJobMemoryUsed` 回读） | `JOB_OBJECT_LIMIT_PROCESS_MEMORY`、`JOB_OBJECT_LIMIT_JOB_MEMORY` |
| `JobObjectIoRateControlInformation`（💡 Win10+） | 整组 **I/O 速率**（MB/s 上限）——现代容器/沙箱的配额手段 | `JOB_OBJECT_IO_RATE_CONTROL_ENABLE` |

两类通知：

1. **作业对象本身就是可等待的**——整组的 CPU 时间配额耗尽时它被触发（系统此时已强杀组内所有进程）。等它就是 `WaitForSingleObject(hJob, ...)`；
2. **细粒度事件走 I/O 完成端口**：`JobObjectAssociateCompletionPortInformation` 把 Job 挂到完成端口上，之后 `GetQueuedCompletionStatus` 会收到 `JOB_OBJECT_MSG_ACTIVE_PROCESS_ZERO`（组内清空）、`JOB_OBJECT_MSG_EXIT_PROCESS`（某进程退出，伴 PID）、`JOB_OBJECT_MSG_END_OF_JOB_TIME` 等消息——构建系统"最后一个子进程退出后汇总"的正规做法。

统计回读用 `QueryInformationJobObject(hJob, JobObjectBasicAndIoAccountingInformation, ...)`：整组用户/内核 CPU 时间、缺页数、曾经/当前的进程数、被限额杀掉的进程数、I/O 读写计数——给"任务面板"填数据的现成来源。

## 16.6 属性列表一句话：`STARTUPINFOEXW`

`CreateProcessW` 还有现代化的扩展：`STARTUPINFOEXW` 携带**属性列表**（attribute list），能声明"只继承这两个句柄"（`PROC_THREAD_ATTRIBUTE_HANDLE_LIST`——第 20 章安全话题会用到）、"父进程是谁"等。机制了解即可，需要时查 `UpdateProcThreadAttribute`。

`examples/08_process_manager` 把本章串成一个 GUI 工具：快照枚举填进列表（第 6 章 ListView 的真实用武之地）→ 选中进程查 PID → "启动记事本"按钮走 `CreateProcessW` 全流程（含双句柄关闭）→ "结束进程"按钮先试 `WM_CLOSE`、强杀入口用 `TerminateProcess` 并二次确认。

## 16.8 易错清单

| 症状 | 原因 | 解法 |
|------|------|------|
| `CreateProcessW` 偶发崩/行为怪 | 命令行传了只读字面量 | 可写缓冲（16.2） |
| "等子进程退出"永远等不到 | `hProcess` 没关，进程对象吊着 | 用完两个句柄都 `CloseHandle` |
| `Process32FirstW` 直接失败 | `dwSize` 忘了赋 `sizeof` | 16.3 |
| 枚举拿不到某些进程名 | 权限不足（系统进程） | `OpenProcess` 失败按错误处理，别硬读 |
| 杀不掉进程 | 没权限（`OpenProcess` 返回 null） | 需要管理员/提权（第 20 章） |
| 子进程控制台窗口一闪而过 | 期望行为如此 | `CREATE_NO_WINDOW` 等标志查文档 |
| 自造环境块子进程乱码/崩 | 宽字符块没加 `CREATE_UNICODE_ENVIRONMENT`，或少了结尾双 `\0` | 16.2 |
| 当前目录的假 exe 抢跑 | exe 搜索顺序里"当前目录"在 PATH 前 | 全路径或清当前目录（16.2） |
| 轮询 `STILL_ACTIVE` 偶发误判 | 退出码恰为 `0x103` | 等 `hProcess` 触发（16.4） |
| 子进程"逃不出"父 Job | 作业没开 `JOB_OBJECT_LIMIT_BREAKAWAY_OK` | 允许后配 `CREATE_BREAKAWAY_FROM_JOB`（16.5） |

## 16.9 小结

1. 进程是容器（地址空间+句柄表+令牌），线程是执行流；本章管容器，第 17 章管执行流。
2. `CreateProcessW` 三纪律：命令行可写、双句柄必关、失败查 `GetLastError`；exe 搜索顺序里当前目录在 PATH 之前；命令行与环境块是进程自带的两个配置面（`GetCommandLineW`/`CommandLineToArgvW`、环境三件套）。
3. 枚举三范式：`dwSize` 先填、First/Next 循环、快照句柄要关。
4. 终止分两档：`WM_CLOSE` 优雅、`TerminateProcess` 最后手段；**进程死了对象还在**——退出码与统计活到句柄关闭，等待触发才是判死正解。
5. 多进程管理用 Job 对象：三类限制（基本/扩展/IO 速率）、收编、整组终结、完成端口收细粒度事件、`JobObjectBasicAndIoAccountingInformation` 回读统计。

## 16.10 动手练习
