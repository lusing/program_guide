# 第 14 章 线程与同步

> **本章回答的问题**：怎么创建线程？两个线程改一个变量为什么会丢更新？`CRITICAL_SECTION`、SRWLock、Mutex、Event、Semaphore 各管什么？条件变量为什么必须配 `while`？GUI 程序怎么把耗时工作放到后台还不卡界面？
>
> **前置章节**：第 13 章（进程是容器、线程是执行流；"句柄+等待"两个正交概念）。
>
> **你将做出什么**：两个程序——GUI 的后台任务演示（`examples/11_thread_sync_demo`）与控制台的生产者/消费者（`examples/14_srwlock_demo`）。

本章示例：`examples/11_thread_sync_demo`、`examples/14_srwlock_demo`。

## 14.1 创建线程：`CreateThread`

```cpp
DWORD WINAPI Worker(LPVOID param) {        // 线程函数签名固定
    int* counter = (int*)param;            // 参数是指针，想传什么包个结构体传地址
    for (int i = 0; i < 5; ++i) {
        // 干活……
        Sleep(100);                        // 挂起 100ms，让出 CPU
    }
    return 0;                              // 返回值即线程退出码
}

int main() {
    int counter = 0;
    HANDLE h = CreateThread(nullptr, 0, Worker, &counter, 0, nullptr);
    //                    安全属性, 栈大小(0=默认1MB), 函数, 参数, 创建标志, 收返回的线程ID
    if (h) {
        WaitForSingleObject(h, INFINITE);  // 等线程结束（"join"）
        CloseHandle(h);                    // 句柄纪律不变
    }
    return 0;
}
```

理解要点：

- **每个线程一个栈**（默认 1MB，虚拟内存，实际用到才提交——第 15 章的概念在这里出现）；
- **线程函数返回即线程结束**。不要用 `ExitThread`（跳过 C++ 析构！），永远不要 `TerminateThread`（线程在任意指令处被腰斩，锁不释放、堆可能损坏——文档原话"尽量别用"）；
- **C++ 程序里用 `_beginthreadex` 或 `std::thread`**：`CreateThread` 不知道 C 运行时（CRT）的线程局部初始化，混用 CRT（`printf`、`strtok` 等）时官方推荐 `_beginthreadex`；而现代 C++ 代码直接 `std::thread`——它内部就是 `CreateThread` 的正确封装。本章为了看清机制用 `CreateThread`，工程代码请用 `std::thread` + `std::mutex`，两者学到的概念完全互通。

线程的其他常规操作：`SuspendThread`/`ResumeThread`（挂起恢复，慎用）、`SetThreadDescription(h, L"worker-io")`（💡 Win10 1607+，调试器里终于能认出线程）、`GetExitCodeThread` 取返回值。

## 14.2 竞态条件：为什么需要同步

两个线程同时对同一个 `int` 做 `++`，结果经常不是期望值：

```cpp
++counter;                 // 一行 = 读 → 加 → 写 三步
// 线程 A 读到 5，线程 B 也读到 5，各自加成 6 写回 —— 两次加法只加了一次
```

这叫**竞态条件（race condition）**。不是"可能出错"，是**一定**会出错，只是频率取决于时序——于是成为最阴险的 bug。此外还有**内存可见性**问题：编译器/CPU 有权把变量缓存在寄存器/缓存里，另一个线程可能长时间看不到写入。

解决思路三种，按代价从低到高：

1. **原子操作**：单变量的加减、交换、比较——`InterlockedIncrement(&counter)` 或 C++ `std::atomic<int>`；
2. **锁**：一段代码同一时间只许一个线程进——本章主角；
3. **不共享**：每线程独立数据，最后合并——最优雅，设计时优先考虑。

## 14.3 同步原语全家福

Win32 的同步对象有明确分工，选型看两个问题：**保护的是什么**、**同步双方在不在同一进程**。

### `CRITICAL_SECTION`：同进程内的轻量锁

```cpp
CRITICAL_SECTION cs;
InitializeCriticalSection(&cs);          // 用完 DeleteCriticalSection

EnterCriticalSection(&cs);               // 拿锁（别人拿着就睡）
// ... 临界区：摸共享数据 ...
LeaveCriticalSection(&cs);               // 放锁
```

特点：进程内有效、极快（先自旋再挂起）、**非内核对象**（没有句柄、不能 `WaitForSingleObject`）。纪律：Enter/Leave 之间不得提前 return（会永久死锁），结构上尽量把临界区缩到只包数据访问。

### SRWLock 与条件变量：现代首选

> 💡 **现代视角（Vista+）**：`CRITICAL_SECTION` 是"读写不分"的独占锁。**SRWLock**（Slim Reader/Writer Lock）区分读者与写者——读多写少的场景（配置查询、缓存）吞吐量成倍提升；配套的**条件变量** `CONDITION_VARIABLE` 干净地解决"等待某个条件成立"。

```cpp
SRWLOCK lock = SRWLOCK_INIT;                 // 静态初始化，不需要 Initialize/Destroy
CONDITION_VARIABLE cv = CONDITION_VARIABLE_INIT;

// 写线程
AcquireSRWLockExclusive(&lock);
queue.push_back(item);
ReleaseSRWLockExclusive(&lock);
WakeConditionVariable(&cv);                  // 叫醒一个等待者

// 读线程
AcquireSRWLockShared(&lock);                 // 多个读者可同时持有共享锁
// ... 只读 ...
ReleaseSRWLockShared(&lock);

// 条件等待（规范四步，SleepConditionVariableSRW 内部原子放锁+睡）
AcquireSRWLockExclusive(&lock);
while (queue.empty())                        // ★ 必须 while：防虚假唤醒
    SleepConditionVariableSRW(&lock, &cv, INFINITE, 0);
item = queue.front(); queue.pop_front();
ReleaseSRWLockExclusive(&lock);
```

对应 C++ 标准件：`std::shared_mutex`（C++17）、`std::condition_variable`——概念一一对应。`examples/14_srwlock_demo` 是完整的生产者/消费者实现（控制台，可直接运行观察三个线程的交错输出）。

### `Mutex`：跨进程的锁

```cpp
HANDLE m = CreateMutexW(nullptr, FALSE, L"Local\\MyAppSingleton");
if (GetLastError() == ERROR_ALREADY_EXISTS) {
    // 已有实例在跑 → 单实例检测的经典用法
    return 0;
}
WaitForSingleObject(m, INFINITE);
// ... 跨进程共享的资源 ...
ReleaseMutex(m);
CloseHandle(m);
```

与 `CRITICAL_SECTION` 的本质区别：**内核对象、有名字、可跨进程、可设超时、可被安全策略控制**。代价是每次加锁都进内核，比临界区慢一个量级。命名规则 `Local\`（本会话）/`Global\`（全系统所有会话）。

### `Event`：通知信号

```cpp
HANDLE done = CreateEventW(nullptr,     // 安全属性
                           TRUE,        // 手动复位(TRUE)/自动复位(FALSE)
                           FALSE,       // 初始状态：未触发
                           nullptr);    // 不命名（进程内用）

// 工作线程：完工后 SetEvent(done);
// 主线程：WaitForSingleObject(done, INFINITE); → "等到完工为止"
```

两种复位语义：**手动复位**像广播开关（Set 一次，所有等待者都醒，直到你 Reset）；**自动复位**像发号机（Set 一次只放行一个等待者）。典型用途：后台任务完成通知、线程优雅退出（退出标志 + 事件二合一）、生产者-消费者唤醒。

### `Semaphore`：并发数量闸门

```cpp
HANDLE sem = CreateSemaphoreW(nullptr, 3, 3, nullptr);   // 初始 3 / 上限 3
WaitForSingleObject(sem, INFINITE);   // 计数 -1，为 0 则睡
// ... 最多 3 个线程同时进入 ...
ReleaseSemaphore(sem, 1, nullptr);    // 计数 +1
```

用途：限制同时打开的文件数、并发下载连接数、线程池的任务槽。互斥量其实就是"上限 1 的信号量"。

### 选型速查表

| 原语 | 进程内/跨进程 | 独占/共享 | 典型用途 |
|------|-------------|----------|---------|
| `CRITICAL_SECTION` | 进程内 | 独占 | 通用共享数据保护（默认选择） |
| SRWLock | 进程内 | 独占+共享 | 读多写少 |
| 条件变量 | 进程内（配上面两种锁） | —— | "等条件成立" |
| `Mutex` | 跨进程 | 独占 | 单实例检测、跨进程资源 |
| `Event` | 进程内或跨进程 | —— | 完成通知、退出信号 |
| `Semaphore` | 进程内或跨进程 | 计数 | 并发数量限制 |

### 等待全家桶

```cpp
WaitForSingleObject(h, INFINITE);            // 等一个；可给超时毫秒数
WaitForMultipleObjects(3, handles, TRUE, INFINITE);
//                            ↑ TRUE=等全部，FALSE=任一即可
//  返回 WAIT_OBJECT_0 + i 表示第 i 个就绪；WAIT_TIMEOUT 超时；WAIT_FAILED 出错
//  ★ 句柄数组上限 64 个，更多要分组等
```

能被等待的统一叫**可等待对象**：线程、进程、事件、互斥体、信号量、Job……"等待"是内核对象模型统一的威力（第 1 章说的"句柄 + 等待"两个正交概念）。

## 14.4 `WaitOnAddress`：无对象的等待

> 💡 **现代视角（Win8+）**：`WaitOnAddress(&value, &compare, sizeof(value), timeout)` 提供轻量级"等某个内存值变化"，无需创建任何内核对象——高性能无锁结构的积木。配对的唤醒是 `WakeByAddressSingle/All`。初学知道即可，看到现码能认出它不属于"内核对象等待"家族。

## 14.5 线程池：不要亲手创建成百上千个线程

> 💡 **现代视角（Vista+）**：频繁短任务不该每次 `CreateThread`（创建开销 ~微秒级 + 1MB 栈提交）。系统线程池 API 一行提交任务，线程数量自动按 CPU 核数与负载调节：

```cpp
VOID CALLBACK Task(PTP_CALLBACK_INSTANCE, PVOID context) { /* 干活 */ };

SubmitThreadpoolWork(CreateThreadpoolWork(Task, context, nullptr));
// 还有定时器（CreateThreadpoolTimer）、等待（CreateThreadpoolWait）、I/O 完成等变体
```

工程上等价物是 C++ 层的各种线程池/`std::async`；理解系统池的意义在于：调试时看到 `ntdll!TppWorkerThread` 线程知道它们是谁。

## 14.6 死锁：四条件与预防

两个线程各持一把锁、互相等对方的那把——永久卡死。死锁发生的四个必要条件：**互斥**（资源独占）、**持有并等待**、**不可剥夺**、**循环等待**。工程预防按性价比排序：

1. **锁排序**：全程序规定锁的获取顺序（如"先 A 后 B"），循环等待即不可能——最有效；
2. **缩小临界区**：锁内不调未知代码（回调可能反过来拿锁）；
3. **`TryEnterCriticalSection`/带超时的 `WaitForSingleObject`**：拿不到就退避重试，破坏"持有等待"；
4. 少造锁：一把大锁的吞吐损失通常好过五把小锁的死锁风险（先对再快）。

## 14.7 GUI 铁律：后台干活，UI 线程收结果

现在把线程放进 GUI 程序。第 4 章的铁律（`WndProc` 卡住 = 全程序卡死）决定了标准架构：

```text
UI 线程                          工作线程
   │ 按钮"开始扫描"                  │
   │ CreateThread(...) ────────────→ 扫描文件 / 算数据 / 读网络
   │ 继续响应消息（界面不卡）          │ 每N步：
   │ ←──────── PostMessageW(WM_APP+1, 数据) ── 报告进度
   │ WM_APP+1: SetWindowText 更新界面 │
   │ ←──────── 完成时 SetEvent / PostMessage "done" ──
```

完整可运行示例见 `examples/11_thread_sync_demo`，其要点浓缩如下：

```cpp
constexpr UINT WM_APP_PROGRESS = WM_APP + 1;   // WM_APP 起是应用自定义消息的保留区

// 工作线程：只做计算与通知，绝不碰控件
DWORD WINAPI Worker(LPVOID param) {
    auto* st = (DemoState*)param;
    for (int i = 1; i <= 5; ++i) {
        Sleep(250);
        EnterCriticalSection(&st->cs);
        LONG v = ++st->counter;                 // 共享数据用锁保护
        LeaveCriticalSection(&st->cs);

        wchar_t* msg = _wcsdup(L"tick");        // ★ 跨线程传数据：堆分配
        PostMessageW(st->hwnd, WM_APP_PROGRESS, (WPARAM)v, (LPARAM)msg);
    }
    SetEvent(st->done);                          // 完成信号
    return 0;
}

// UI 线程：收到进度消息，更新界面，并负责释放 _wcsdup 的内存
case WM_APP_PROGRESS: {
    wchar_t* text = (wchar_t*)lParam;
    if (text) { SetWindowTextW(hStatus, text); free(text); }
    return 0;
}
```

三条纪律再强调一遍：**工作线程不碰任何窗口/控件**（窗口属于创建它的线程）；**跨线程通知用 `PostMessage` 不用 `SendMessage`**（4.7 节的死锁风险）；**`LPARAM` 传指针注意生命周期**（堆分配、接收方释放）。

为什么要锁 `counter`？虽然单变量可以用 `InterlockedIncrement` 免锁，示例里用临界区是为了演示"多步更新"的标准姿势——真实业务里共享的很少是单个整数，而是一整个数据结构。

## 14.8 易错清单

| 症状 | 原因 | 解法 |
|------|------|------|
| 计数偶尔少加 | `++` 非原子，竞态 | `InterlockedIncrement` 或锁（14.2） |
| 临界区拿了不放 | 中间提前 `return`/异常 | 缩小临界区 + C++ 侧用 RAII（`std::lock_guard`） |
| 条件等待偶发拿空数据 | 醒来没用 `while` 复查 | `SleepConditionVariable*` 必配 `while`（14.3） |
| 线程函数里 `ExitThread` | 跳过 C++ 析构 | `return` 自然退出 |
| 界面偶发卡死 | 跨线程 `SendMessage` 撞锁 | 改 `PostMessage`（14.7） |
| 进度消息里读野指针 | 栈地址当 `LPARAM` 投递 | 堆分配 + 接收方释放 |
| `WaitForMultipleObjects` 传 70 个句柄 | 上限 64 | 分组等待 |
| 换成 `std::thread` 后 CRT 状态怪 | 老代码用 `CreateThread` 混 CRT | 统一 `_beginthreadex`/`std::thread` |

## 14.9 小结

1. 线程 = 栈 + 寄存器的执行流；`CreateThread` 四参核心，返回即结束，句柄要关。
2. 竞态是必然不是偶然：原子操作、锁、不共享三档解法。
3. 选型表：进程内默认 `CRITICAL_SECTION`，读多写少 SRWLock，跨进程 Mutex，通知 Event，限流 Semaphore；条件等待必配 `while`。
4. 等待统一走 `WaitForSingleObject`/`WaitForMultipleObjects`（上限 64）。
5. GUI 铁律：后台干活 + `PostMessage` 回传 + 接收方释放；锁排序防死锁。
