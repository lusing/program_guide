# 第 21 章 注册表

> **本章回答的问题**：注册表到底是什么、为什么存在？键/值/类型怎么组织？增删改查的 API 套路？HKLM 和 HKCU 该写哪个？32 位程序为什么"查不到"64 位键？
>
> **前置章节**：第 17 章（HKLM 需要管理员——权限模型在那一章）；本章的路径知识是第 24 章 COM 注册的直接前置。
>
> **你将做出什么**：一个注册表全流程工具（`examples/25_registry_tool`）：建键、写三种类型、读回、枚举、整树删除——自建自清，环境零污染。

本章示例：`examples/25_registry_tool/main.cpp`。

## 21.1 注册表是什么：配置的中央仓库

程序需要记住配置：上次窗口位置、最近文件列表、序列号。Win3.x 时代各用各的 `.ini` 文件，三个不够：**没有并发保护**（两个程序同时写坏文件）、**没有权限模型**（谁都读谁的秘密）、**查询低效**（全文扫描）。注册表（Registry）就是系统级答案：一棵由系统统一管理、带安全描述符、可高效查询的**配置数据库**。

参观路线：`Win+R` → `regedit` → 只看不动。左侧是树，右侧是数据——这个界面本身就是下一节的数据模型。

## 21.2 五大根键与数据模型

| 根键 | 内容 | 你该不该写 |
|------|------|-----------|
| `HKEY_CLASSES_ROOT`（HKCR） | 文件关联、COM 类注册 | 间接写（见下） |
| `HKEY_CURRENT_USER`（HKCU） | 当前用户的配置 | **应用配置的家** |
| `HKEY_LOCAL_MACHINE`（HKLM） | 全机器配置（软件/硬件/系统） | 安装器才写，需管理员 |
| `HKEY_USERS`（HKU） | 所有用户的装载点 | 少直接碰 |
| `HKEY_CURRENT_CONFIG`（HKCC） | 当前硬件配置档案 | 几乎只读 |

两个必须知道的结构事实：

1. **HKCR 是合成视图** = `HKLM\Software\Classes` 与 `HKCU\Software\Classes` 的合并（HKCU 优先）。这解释了两件事：per-user 安装的文件关联为什么生效；以及第 24 章的 COM 组件为什么注册进 `HKCU\Software\Classes` 就能免管理员工作；
2. **HKCU 是 HKU 里当前用户分支的映射**——同一用户不同登录会话看到各自的。

数据模型三要素：

```text
键（key）── 树的节点，路径如 HKCU\Software\MyApp
   │
   ├── 值（value）── 键下挂着"名值对"，一个键可有很多值
   │      每个值有：名称 + 类型 + 数据
   │      名称为空的值叫"默认值"（@(Default)）
   └── 子键（subkey）── 树继续往下
```

类型表（`TypeName` 函数处理不完的都在这）：

| 类型 | 装什么 | 备注 |
|------|--------|------|
| `REG_SZ` | 字符串 | 最常用；**数据字节数含结尾 NUL** |
| `REG_EXPAND_SZ` | 带 `%VAR%` 的字符串 | 读取时要不要展开是调用方的选择 |
| `REG_DWORD` | 32 位整数 | 开关/计数 |
| `REG_QWORD` | 64 位整数 | 时间戳等 |
| `REG_BINARY` | 原始字节 | 任意数据 |
| `REG_MULTI_SZ` | 多字符串 | NUL 分隔、双 NUL 收尾 |

## 21.3 增：`RegCreateKeyExW` 与 `RegOpenKeyExW`

`RegCreateKeyExW` 是"创建或打开"合一（已存在就打开，不存在就建）——应用初始化配置键的标准写法：

```cpp
HKEY key;
LSTATUS st = RegCreateKeyExW(HKEY_CURRENT_USER, L"Software\\MyApp\\Main",
                             0, nullptr, REG_OPTION_NON_VOLATILE,
                             KEY_ALL_ACCESS, nullptr, &key, nullptr);
if (st != ERROR_SUCCESS) { /* LSTATUS 就是 Win32 错误码，第 3 章翻译它 */ }
```

参数要点：第四参（class）与最后两参（安全描述符模板、是否新建标记）初学传默认；**访问权限**按需收窄（只读用 `KEY_READ`）。确定键已存在时可用纯打开的 `RegOpenKeyExW`（不存在返回错误）。

注意返回值类型是 `LSTATUS`——就是 `GetLastError()` 那套错误码，`ERROR_SUCCESS` 为 0；要人话就用第 3 章的 `FormatMessageW` 套路或 `reg.exe` 侧对照。

## 21.4 写：`RegSetValueExW` 与 NUL 字节数

```cpp
// DWORD
DWORD count = 42;
RegSetValueExW(key, L"计数", 0, REG_DWORD, (const BYTE*)&count, sizeof(count));

// 字符串：★ 字节数 = (字符数 + 1) * sizeof(wchar_t)，结尾 NUL 必须计入
const wchar_t* hello = L"你好";
RegSetValueExW(key, L"问候", 0, REG_SZ, (const BYTE*)hello,
               (DWORD)((wcslen(hello) + 1) * sizeof(wchar_t)));
```

漏掉结尾 NUL 是注册表头号坑：`regedit` 能显示，程序读回时 `RegQueryValueExW` 给的 size 不含 NUL，字符串越界读。读方防御法：缓冲清零 + 手动补 NUL。

## 21.5 读：两段式与一步式

定长类型直接读：

```cpp
DWORD num = 0, type = 0, size = sizeof(num);
RegQueryValueExW(key, L"计数", nullptr, &type, (BYTE*)&num, &size);
```

变长类型（字符串）的标准姿势同样是**两段式**（第 12 章的老朋友）：先传 `nullptr` 问 size，再分配再读。嫌麻烦有现代一步式：

```cpp
wchar_t buf[256]; DWORD cb = sizeof(buf);
RegGetValueW(HKEY_CURRENT_USER, L"Software\\MyApp", L"问候",
             RRF_RT_REG_SZ, nullptr, buf, &cb);
// RegGetValueW 的三连好处：自动展开 EXPAND_SZ、自动截断保证 NUL、能直接按根键+路径调用
```

## 21.6 枚举：`ERROR_NO_MORE_ITEMS` 循环范式

枚举值与子键是同一套"索引循环"（第 13 章快照枚举、第 16 章目录枚举的表亲）：

```cpp
for (DWORD i = 0; ; ++i) {
    wchar_t name[64]; DWORD nameLen = 64;
    LSTATUS st = RegEnumValueW(key, i, name, &nameLen, nullptr,
                               &type, nullptr, nullptr);
    if (st == ERROR_NO_MORE_ITEMS) break;    // 正常结束信号，不是错误
    if (st != ERROR_SUCCESS) break;
    // ...
}
```

细节：`nameLen` 每轮都要重置为缓冲容量（它是入参/出参两用）；子键枚举换 `RegEnumKeyExW`（少 type/data 两参）。

## 21.7 删除：`RegDeleteKeyW` vs `RegDeleteTreeW`

`RegDeleteKeyW` 只删**空键**（有子键会失败）；要"整棵砍"用 `RegDeleteTreeW`（Vista+）。删值用 `RegDeleteValueW`。示例的清场就是一句 `RegDeleteTreeW(HKCU, L"Software\\GuideWin32")`——**教程代码的纪律：自己建的树自己拆干净**。

## 21.8 64 位重定向：WOW64 的平行世界

32 位进程跑在 64 位系统上时，注册表访问被**自动重定向**：

| 32 位进程访问 | 实际落到 |
|--------------|---------|
| `HKLM\Software` | `HKLM\Software\Wow6432Node` |
| `HKLM\Software\Classes\CLSID` | `...\Classes\Wow6432Node\CLSID` |

设计动机：让 32/64 位组件同名注册互不踩踏。带来的经典 bug：32 位工具写入后，64 位程序（或 `regedit` 默认的 64 位视图）"看不见"。两个出口：访问时带 `KEY_WOW64_64KEY` 权限位看对面世界；`regedit` 里也能切（对 Hive 加载 32 位视图）。HKCU 的重定向项少得多，用户级配置基本无感。

## 21.9 权限与工程惯例

- **HKLM 写需要管理员**（第 17 章）——所以应用运行期配置写 `HKCU\Software\<公司>\<产品>`，安装器才碰 HKLM；
- 路径惯例：`Software\MyCompany\MyApp`（版本可作子键，`MyApp\1.0`）；
- COM 注册是特殊存在：写 `HKCU\Software\Classes\...`（per-user，免管理员）或 `HKLM\Software\Classes\...`（全机，要管理员）——**第 24 章手写 COM 服务器时用前者**，21.2 的合成视图知识将在那里兑现；
- 命令行对照：`reg query`、`reg add`、`reg delete`、`reg export`——脚本时代的老朋友，也是本教程验证示例清场效果的工具。

## 21.11 易错清单

| 症状 | 原因 | 解法 |
|------|------|------|
| 写出的字符串读回越界/乱码 | 字节数漏了结尾 NUL | 21.4 公式 |
| `RegEnumValueW` 第二轮名字怪 | `nameLen` 没重置回容量 | 每轮复位（21.6） |
| `RegDeleteKeyW` 报错 | 键非空 | `RegDeleteTreeW` |
| HKLM 写入失败 `ERROR_ACCESS_DENIED` | 标准用户令牌 | 写 HKCU 或提权（17 章） |
| 32 位程序注册的 COM 类 64 位看不见 | Wow6432Node 重定向 | `KEY_WOW64_64KEY` 或统一位数（21.8） |
| `regedit` 里删了键程序又重建 | 程序退出时写回配置 | 正常行为，改程序逻辑 |
| 把大数据（几 MB）塞注册表 | 注册表不是数据库 | 配置存文件，注册表只放指针 |

## 21.12 小结

1. 注册表 = 带权限与并发保护的配置数据库；HKCR 是 Classes 合成视图，HKCU 是应用的家。
2. 模型三要素：键/值/类型；字符串字节数含 NUL 是头号坑。
3. API 套路：Create/Open 合一建键、两段式读、`ERROR_NO_MORE_ITEMS` 枚举循环、Tree 整删。
4. `RegGetValueW` 一步式带展开与 NUL 保证，新代码优先。
5. WOW64 重定向让 32 位程序活在平行世界；HKCU 基本无感，CLSID 谨慎。
