# 第 8 章 进程与线程

> 本章回答的问题：进程和线程到底是什么关系？怎么启动、枚举、等待、结束一个进程？怎么创建线程？多个线程抢一个变量怎么办——从 `CRITICAL_SECTION` 到 SRWLock，各种同步原语各管什么？GUI 程序怎么把耗时工作放到后台还不卡界面？

> 💡 **本章定位**：这是系统服务层的开篇——第 1 章说过，进程/线程/同步是 Win32 至今**没有任何替代品**的能力。.NET 的 `Thread`、`std::thread`、各种语言运行时，在 Windows 上最终都是本章这些调用。

本章示例：`examples/08_process_manager`、`examples/11_thread_sync_demo`、`examples/14_srwlock_demo`（现代同步原语）。

## 8.1 概念：进程是容器，线程是执行流

- **进程**：一个正在运行的程序实例 = 独立的虚拟地址空间 + 资源句柄表 + 安全上下文 + **至少一个线程**。进程不执行任何代码，它只是容器。
- **线程**：进程内被调度执行代码的实体，拥有自己的栈和寄存器状态。同一进程内的多个线程**共享全部地址空间**——这是效率的来源，也是灾难的来源。
- **PID**：进程的唯一编号；**句柄**：进程对象的访问凭证（`OpenProcess` 拿到，用完 `CloseHandle`）。

所有进程/线程 API 在 `kernel32.dll`，信息查询类在 `psapi.dll`/`tlhelp32.h`。

## 8.2 启动进程：`CreateProcessW`

```cpp
wchar_t cmd[] = L"notepad.exe";        // ★ 必须是可写缓冲区（见下）
STARTUPINFOW si = { sizeof(si) };      // 子进程的启动外观（窗口大小、句柄继承等）
PROCESS_INFORMATION pi = {};           // 返回：进程句柄、主线程句柄、两个 ID

BOOL ok = CreateProcessW(
    nullptr,            // 应用程序路径；nullptr 表示从命令行解析
    cmd,                // 命令行（可写！）
    nullptr, nullptr,   // 安全属性，默认
    FALSE,              // 不继承句柄
    0,                  // 创建标志（CREATE_SUSPENDED 可让进程先挂起）
    nullptr, nullptr,   // 环境变量、工作目录
    &si, &pi);

if (ok) {
    // pi.hProcess / pi.hThread 是你的两个句柄，pi.dwProcessId 是 PID
    CloseHandle(pi.hThread);    // 不等主线程就先还掉它的句柄
    CloseHandle(pi.hProcess);   // 不需要等待/取退出码就一起还掉
}
```

三个易错点：

1. **命令行参数必须可写**：文档写明"本函数可能修改该缓冲区"（它要在原地补引号、补路径）。`CreateProcessW(nullptr, (LPWSTR)L"notepad.exe", ...)` 把只读字面量强转传入是未定义行为——照上面先拷进局部数组。
2. **两个句柄都要还**。不 `CloseHandle` 不只是泄漏——只要你还持有 `hProcess`，**即使子进程退出，它也不会真正结束**（进程对象保持到所有句柄关闭），做"启动后等待退出"逻辑时尤其致命。
3. **失败判断**：返回 `FALSE` 后查 `GetLastError()`；找不到 exe 是 `ERROR_FILE_NOT_FOUND`。

等待子进程结束并取退出码：

```cpp
WaitForSingleObject(pi.hProcess, INFINITE);     // 线程句柄、进程句柄、事件……都能等
DWORD code = 0;
GetExitCodeProcess(pi.hProcess, &code);         // 即子进程 main/wWinMain 的返回值
```

"启动外部工具并等待"（编译器包装器、安装器、构建脚本）就是这两行。

## 8.3 枚举进程：工具帮助快照

任务管理器式的进程列表用 ToolHelp 快照 API（`tlhelp32.h`）：

```cpp
#include <tlhelp32.h>

HANDLE snap = CreateToolhelp32Snapshot(TH32CS_SNAPPROCESS, 0);  // 拍下全系统进程快照
if (snap != INVALID_HANDLE_VALUE) {
    PROCESSENTRY32W pe = { sizeof(pe) };          // ★ dwSize 必须先填！
    if (Process32FirstW(snap, &pe)) {
        do {
            wprintf(L"%lu\t%ls\n", pe.th32ProcessID, pe.szExeFile);
        } while (Process32NextW(snap, &pe));      // 循环遍历到返回 FALSE
    }
    CloseHandle(snap);                            // 快照也是句柄
}
```

注意这个 API 的复古风格：`dwSize` 先赋值（版本协商，同 `WNDCLASSEX.cbSize`）、`First/Next` 循环范式（同 `FindFirstFile`）。`PROCESSENTRY32W` 里还有父进程 PID、线程数、内存占用等字段。

现代替代：`EnumProcesses`（psapi）只给 PID 数组，再逐个 `OpenProcess` 查名字；更完整的查询走 `NtQuerySystemInformation`（非官方契约，别用）。初学用 ToolHelp 即可，它 1998 年至今没变过。

## 8.4 打开、终止进程

```cpp
// 按 PID 打开：权限按需申请，给多了会被安全策略拒绝
HANDLE h = OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION | SYNCHRONIZE, FALSE, pid);
// 常用权限：PROCESS_QUERY_LIMITED_INFORMATION 查状态
//          SYNCHRONIZE 等待退出
//          PROCESS_TERMINATE 强杀
//          PROCESS_VM_READ 读内存（第 9 章用）
```

**终止进程的两种姿势**，语义天差地别：

```cpp
// 优雅：请求 GUI 程序自己关（向它的顶层窗口发 WM_CLOSE）
PostMessageW(hWndOfTarget, WM_CLOSE, 0, 0);   // 程序可弹"保存吗"，可拒绝

// 强制：TerminateProcess——立即杀死，无任何清理机会
HANDLE h = OpenProcess(PROCESS_TERMINATE, FALSE, pid);
if (h) {
    TerminateProcess(h, 1);       // 目标进程的 DLL 不收卸载通知、缓冲数据全丢
    CloseHandle(h);
}
```

`TerminateProcess` 是文档明言的"最后手段"：目标没有机会运行任何清理代码。正常业务用 `WM_CLOSE` 或让子进程响应约定的退出信号；只有任务管理器式的"强杀"工具才用它。

## 8.5 现代：Job 对象 —— 管理一组进程

> 💡 **现代视角（Windows 2000 引入，Vista 后大幅增强）**：真实软件很少只管一个子进程。Chrome 的每个标签页进程、编译器的进程池、构建系统的子进程树，都挂在一个 **Job 对象**下统一管理：子进程崩了全组回收、限制整组内存/CPU、整组终止。

```cpp
HANDLE hJob = CreateJobObjectW(nullptr, nullptr);

JOBOBJECT_EXTENDED_LIMIT_INFORMATION limit = {};
limit.ProcessMemoryLimit = 512 * 1024 * 1024;              // 整组内存上限 512MB
limit.BasicLimitInformation.LimitFlags = JOB_OBJECT_LIMIT_PROCESS_MEMORY;
SetInformationJobObject(hJob, JobObjectExtendedLimitInformation, &limit, sizeof(limit));

AssignProcessToJobObject(hJob, childProcess);   // 把子进程收编（可收多个）

// 想整组终结：TerminateJobObject(hJob, 1);
// 想感知"整组全退了"：Job 对象可配事件通知（JobObjectAssociateCompletionPortInformation）
```

一个标志性的实用点：默认情况下子进程"继承"父进程的 Job。做"我的程序要被别人的 Job 管理"（比如在 CI 里运行）时，用 `CREATE_BREAKAWAY_FROM_JOB` 标志让子进程脱离。

## 8.6 创建线程：`CreateThread`

```cpp
#include <windows.h>

DWORD WINAPI Worker(LPVOID param) {        // 线程函数签名固定
    int* counter = (int*)param;            // 参数是指针，想传什么包个结构体传地址
    for (int i = 0; i < 5; ++i) {
        // 干活……
        Sleep(100);                        // 挂起 100ms，让出 CPU
    }
    return 0;                              // 返回值即线程退出码
}

int main() {
    int counter = 0;
    HANDLE h = CreateThread(nullptr, 0, Worker, &counter, 0, nullptr);
    //                    安全属性, 栈大小(0=默认1MB), 函数, 参数, 创建标志, 收返回的线程ID
    if (h) {
        WaitForSingleObject(h, INFINITE);  // 等线程结束（"join"）
        CloseHandle(h);                    // 句柄纪律不变
    }
    return 0;
}
```

理解要点：

- **每个线程一个栈**（默认 1MB，虚拟内存，实际用到才提交——第 9 章的概念在这里出现）；
- **线程函数返回即线程结束**。不要用 `ExitThread`（跳过 C++ 析构！），永远不要 `TerminateThread`（线程在任意指令处被腰斩，锁不释放、堆可能损坏——文档原话"尽量别用"）；
- **C++ 程序里用 `_beginthreadex` 或 `std::thread`**：`CreateThread` 不知道 C 运行时（CRT）的线程局部初始化，混用 CRT（`printf`、`strtok` 等）时官方推荐 `_beginthreadex`；而现代 C++ 代码直接 `std::thread`——它内部就是 `CreateThread` 的正确封装。本章为了看清机制用 `CreateThread`，工程代码请用 `std::thread` + `std::mutex`，两者学到的概念完全互通。

线程的其他常规操作：`SuspendThread`/`ResumeThread`（挂起恢复，慎用）、`SetThreadDescription(h, L"worker-io")`（💡 Win10 1607+，调试器里终于能认出线程）、`GetExitCodeThread` 取返回值。

## 8.7 竞态条件：为什么需要同步

两个线程同时对同一个 `int` 做 `++`，结果经常不是期望值：

```cpp
++counter;                 // 一行 = 读 → 加 → 写 三步
// 线程 A 读到 5，线程 B 也读到 5，各自加成 6 写回 —— 两次加法只加了一次
```

这叫**竞态条件（race condition）**。不是"可能出错"，是**一定**会出错，只是频率取决于时序——于是成为最阴险的 bug。此外还有**内存可见性**问题：编译器/CPU 有权把变量缓存在寄存器/缓存里，另一个线程可能长时间看不到写入。

解决思路三种，按代价从低到高：

1. **原子操作**：单变量的加减、交换、比较——`InterlockedIncrement(&counter)` 或 C++ `std::atomic<int>`；
2. **锁**：一段代码同一时间只许一个线程进——本章主角；
3. **不共享**：每线程独立数据，最后合并——最优雅，设计时优先考虑。

## 8.8 同步原语全家福

Win32 的同步对象有明确分工，选型看两个问题：**保护的是什么**、**同步双方在不在同一进程**。

### `CRITICAL_SECTION`：同进程内的轻量锁

```cpp
CRITICAL_SECTION cs;
InitializeCriticalSection(&cs);          // 用完 DeleteCriticalSection

EnterCriticalSection(&cs);               // 拿锁（别人拿着就睡）
// ... 临界区：摸共享数据 ...
LeaveCriticalSection(&cs);               // 放锁
```

特点：进程内有效、极快（先自旋再挂起）、**非内核对象**（没有句柄、不能 `WaitForSingleObject`）。纪律：Enter/Leave 之间不得提前 return（会永久死锁），结构上尽量把临界区缩到只包数据访问。

### SRWLock 与条件变量：现代首选

> 💡 **现代视角（Vista+）**：`CRITICAL_SECTION` 是"读写不分"的独占锁。**SRWLock**（Slim Reader/Writer Lock）区分读者与写者——读多写少的场景（配置查询、缓存）吞吐量成倍提升；配套的**条件变量** `CONDITION_VARIABLE` 干净地解决"等待某个条件成立"。

```cpp
SRWLOCK lock = SRWLOCK_INIT;                 // 静态初始化，不需要 Initialize/Destroy
CONDITION_VARIABLE cv = CONDITION_VARIABLE_INIT;

// 写线程
AcquireSRWLockExclusive(&lock);
queue.push_back(item);
ReleaseSRWLockExclusive(&lock);
WakeConditionVariable(&cv);                  // 叫醒一个等待者

// 读线程
AcquireSRWLockShared(&lock);                 // 多个读者可同时持有共享锁
// ... 只读 ...
ReleaseSRWLockShared(&lock);

// 条件等待（规范四步，SleepConditionVariableCS/SRWW 内部原子放锁+睡）
AcquireSRWLockExclusive(&lock);
while (queue.empty())                        // ★ 必须 while：防止虚假唤醒
    SleepConditionVariableSRW(&lock, &cv, INFINITE, 0);
item = queue.front(); queue.pop_front();
ReleaseSRWLockExclusive(&lock);
```

对应 C++ 标准件：`std::shared_mutex`（C++17）、`std::condition_variable`——概念一一对应。

### `Mutex`：跨进程的锁

```cpp
HANDLE m = CreateMutexW(nullptr, FALSE, L"Local\\MyAppSingleton");
if (GetLastError() == ERROR_ALREADY_EXISTS) {
    // 已有实例在跑 → 单实例检测的经典用法
    return 0;
}
WaitForSingleObject(m, INFINITE);
// ... 跨进程共享的资源 ...
ReleaseMutex(m);
CloseHandle(m);
```

与 `CRITICAL_SECTION` 的本质区别：**内核对象、有名字、可跨进程、可设超时、可被安全策略控制**。代价是每次加锁都进内核，比临界区慢一个量级。命名规则 `Local\`（本会话）/`Global\`（全系统所有会话）。

### `Event`：通知信号

```cpp
HANDLE done = CreateEventW(nullptr,     // 安全属性
                           TRUE,        // 手动复位(TRUE)/自动复位(FALSE)
                           FALSE,       // 初始状态：未触发
                           nullptr);    // 不命名（进程内用）

// 工作线程：完工后 SetEvent(done);
// 主线程：WaitForSingleObject(done, INFINITE); → "等到完工为止"
```

两种复位语义：**手动复位**像广播开关（Set 一次，所有等待者都醒，直到你 Reset）；**自动复位**像发号机（Set 一次只放行一个等待者）。典型用途：后台任务完成通知、线程优雅退出（退出标志 + 事件二合一）、生产者-消费者唤醒。

### `Semaphore`：并发数量闸门

```cpp
HANDLE sem = CreateSemaphoreW(nullptr, 3, 3, nullptr);   // 初始 3 / 上限 3
WaitForSingleObject(sem, INFINITE);   // 计数 -1，为 0 则睡
// ... 最多 3 个线程同时进入 ...
ReleaseSemaphore(sem, 1, nullptr);    // 计数 +1
```

用途：限制同时打开的文件数、并发下载连接数、线程池的任务槽。互斥量其实就是"上限 1 的信号量"。

### 等待全家桶

```cpp
WaitForSingleObject(h, INFINITE);            // 等一个；可给超时毫秒数
WaitForMultipleObjects(3, handles, TRUE, INFINITE);
//                            ↑ TRUE=等全部，FALSE=任一即可
// 返回 WAIT_OBJECT_0 + i 表示第 i 个就绪；WAIT_TIMEOUT 超时；WAIT_FAILED 出错
```

能被等待的统一叫**可等待对象**：线程、进程、事件、互斥体、信号量、Job……"等待"是内核对象模型统一的威力（第 1 章说的"句柄 + 等待"两个正交概念）。

> 💡 **现代视角（Win8+）**：`WaitOnAddress(&value, &compare, sizeof(value), timeout)` 提供轻量级"等某个内存值变化"，无需创建任何内核对象——高性能无锁结构的积木。初学知道即可。

### 线程池：不要亲手创建成百上千个线程

> 💡 **现代视角（Vista+）**：频繁短任务不该每次 `CreateThread`（创建开销 ~微秒级 + 1MB 栈提交）。系统线程池 API 一行提交任务，线程数量自动按 CPU 核数与负载调节：

```cpp
VOID CALLBACK Task(PTP_CALLBACK_INSTANCE, PVOID context) { /* 干活 */ };

SubmitThreadpoolWork(CreateThreadpoolWork(Task, context, nullptr));
// 还有定时器（CreateThreadpoolTimer）、等待（CreateThreadpoolWait）、I/O 完成等变体
```

工程上等价物是 C++ 层的各种线程池/`std::async`；理解系统池的意义在于：调试时看到 `ntdll!TppWorkerThread` 线程知道它们是谁。

## 8.9 GUI 铁律：后台干活，UI 线程收结果

现在把线程放进 GUI 程序。第 3 章的铁律（`WndProc` 卡住 = 全程序卡死）决定了标准架构：

```text
UI 线程                          工作线程
   │ 按钮"开始扫描"                  │
   │ CreateThread(...) ────────────→ 扫描文件 / 算数据 / 读网络
   │ 继续响应消息（界面不卡）          │ 每###步：
   │ ←──────── PostMessageW(WM_APP+1, 数据) ── 报告进度
   │ WM_APP+1: SetWindowText 更新界面 │
   │ ←──────── 完成时 SetEvent / PostMessage "done" ──
```

完整可运行示例见 `examples/11_thread_sync_demo`，其要点浓缩如下：

```cpp
constexpr UINT WM_APP_PROGRESS = WM_APP + 1;   // WM_APP 起是应用自定义消息的保留区

// 工作线程：只做计算与通知，绝不碰控件
DWORD WINAPI Worker(LPVOID param) {
    auto* st = (DemoState*)param;
    for (int i = 1; i <= 5; ++i) {
        Sleep(250);
        EnterCriticalSection(&st->cs);
        LONG v = ++st->counter;                 // 共享数据用锁保护
        LeaveCriticalSection(&st->cs);

        wchar_t* msg = _wcsdup(L"tick");        // ★ 跨线程传数据：堆分配
        PostMessageW(st->hwnd, WM_APP_PROGRESS, (WPARAM)v, (LPARAM)msg);
    }
    SetEvent(st->done);                          // 完成信号
    return 0;
}

// UI 线程：收到进度消息，更新界面，并负责释放 _wcsdup 的内存
case WM_APP_PROGRESS: {
    wchar_t* text = (wchar_t*)lParam;
    if (text) { SetWindowTextW(hStatus, text); free(text); }
    return 0;
}
```

三条纪律再强调一遍：**工作线程不碰任何窗口/控件**（窗口属于创建它的线程）；**跨线程通知用 `PostMessage` 不用 `SendMessage`**（3.7 节的死锁风险）；**`LPARAM` 传指针注意生命周期**（堆分配、接收方释放）。

为什么要锁 `counter`？虽然单变量可以用 `InterlockedIncrement` 免锁，示例里用临界区是为了演示"多步更新"的标准姿势——真实业务里共享的很少是单个整数，而是一整个数据结构。

## 8.11 易错清单

- `CreateProcessW` 命令行传了只读字面量（未定义行为）；
- 子进程句柄没 `CloseHandle`，导致"等退出"逻辑永远等不到；
- `PROCESSENTRY32W` 忘了 `dwSize = sizeof(pe)`，`Process32FirstW` 直接失败；
- 线程函数里用 `ExitThread` 提前返回，跳过 C++ 析构；
- 临界区中间 `return`，锁永远不还；
- `SleepConditionVariable` 后用 `if` 不用 `while`，虚假唤醒时拿到空数据；
- 工作线程直接 `SetWindowTextW` 摸控件——大多数时候"碰巧能用"，迟早诡异地死。
