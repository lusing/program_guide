## 36.1 边界之下：一次 CreateFileW 的完整旅程

第 1 章给过调用链的目录（你的程序 → 子系统 DLL → API Set → ntdll → 内核），现在下潜到机器层。你在记事本里按 Ctrl+O，最终走到 `CreateFileW`：

```text
notepad.exe
    │ CreateFileW —— kernel32.dll（官方文档的边界到此为止）
    ▼
ntdll.dll!NtCreateFile     ★ 整个系统里"最后的用户态代码"
    │ ① 把系统服务号（一个整数）放进 EAX 寄存器
    │ ② 执行 syscall 指令 —— CPU 从此切换到内核模式（ring 3 → ring 0）
    ▼
系统服务分发器（内核）
    │ 按 EAX 里的号码查 SSDT（系统服务分发表）
    ▼
ntoskrnl.exe!NtCreateFile   ← 与 ntdll 里的函数同名同参——真身在这里
    │ 内核 I/O 管理器干活
    ▼
syscall 之后的下一条指令 —— 线程回到用户态继续跑
```

三个值得记住的事实：

1. **ntdll 的三重身份**：它是 Native API 的用户态实现（`Nt*` 函数族），也是用户态最低层——它还内嵌堆管理器、PE 加载器（22 章"DLL 怎么进进程"的实际执行者）和一部分线程池；
2. **kernel32 里的 `CreateFileW` 大体是"参数翻译 + 转发"**——真正的语义在内核的同名函数里。这也是第 1 章"你 import 的 DLL 不一定是实现者"的微观解释；
3. **`syscall` 指令是唯一正门**。Win32 时代的教材还讲 `int 2Eh`/`sysenter`，x64 上一律 `syscall`——服务号与指令都随系统版本变化，这正是"不要自己拼系统调用"的原因。

## 36.2 Native API 与 NTSTATUS：官方契约之下的方言

ntdll 导出的 `Nt*`/`Zw*` 函数族叫 **Native API**。第 16 章枚举进程时说过它"非官方契约，别用"——现在看清这位"别用"的长辈长什么样（看得懂是素养，依赖它是冒险：微软不承诺它跨版本稳定）。

两条语言规则：

- **NTSTATUS 不是 HRESULT**。0 表成功；**负值（最高位=1）才是错误**；低 16 位是具体码。还有一批**成功级非零状态**——44 示例实测撞上的 `0x00000105`（`STATUS_MORE_ENTRIES`，"还有更多条目"）就是典型，按 `!= 0` 判失败会把成功当错误；
- **没有完整的导入库承诺**。SDK 的 `ntdll.lib` 只有部分函数，稳妥姿势是 21 章 `RtlGetVersion` 用过的 `GetProcAddress` 动态解析。

旗舰函数 `NtQuerySystemInformation`：一次系统调用返回全系统进程/线程信息（psapi 的 `EnumProcesses`、任务管理器看到的都是这份内核数据的衍生品）。用法骨架（44 示例实测 281 进程 / 4090 线程）：

```cpp
// 条目链表：靠 NextEntryOffset 前进，0 表示到头（ImageName 是不带 \0 的 UNICODE_STRING）
typedef NTSTATUS(NTAPI* NtQSI_t)(ULONG, PVOID, ULONG, PULONG);
NtQSI_t NtQSI = (NtQSI_t)GetProcAddress(GetModuleHandleW(L"ntdll.dll"),
                                        "NtQuerySystemInformation");
ULONG size = 1 << 20; NTSTATUS st;
for (;;) {                                   // 标准形态：INFO_LENGTH_MISMATCH 就翻倍重来
    buf = malloc(size);
    st = NtQSI(5 /*SystemProcessInformation*/, buf, size, nullptr);
    if (st != STATUS_INFO_LENGTH_MISMATCH) break;
    free(buf); size *= 2;
}
```

它的条目结构（`SYSTEM_PROCESS_INFORMATION`）SDK 不给全定义，需要照 WDK/Process Hacker 抄一份——这也是 Native API 生态的日常。

## 36.3 TEB 与 PEB：线程与进程的"自我档案"

syscall 那条链之外，用户态还有两块高价值内存：**TEB（线程环境块，每线程一份）**和 **PEB（进程环境块，每进程一份）**。x64 上 `gs` 段寄存器直指 TEB，`NtCurrentTeb()` 一行就拿到：

```cpp
PTEB teb = NtCurrentTeb();
PPEB peb = teb->ProcessEnvironmentBlock;      // TEB 里最常用的指针
peb->BeingDebugged;                           // ← IsDebuggerPresent() 读的就是这一个字节
peb->ProcessParameters->CommandLine;          // ← GetCommandLineW() 返回的就是这块内存
peb->Ldr;                                     // ← 已加载模块链表（22 章的档案库）
```

44 示例的实测输出（对照列证明所言非虚）：

```text
TEB @ 000000E25E6A9000，PEB @ 000000E25E6A8000
PEB.BeingDebugged = 0   ← 反调试第一课：调试器接管进程时置 1
PEB 映像基址     = 00007FF74B0A0000   ← 对照 GetModuleHandle(nullptr) = 00007FF74B0A0000
命令行真身       = "G:\...\44_nt_native.exe"   ← CRT 的 argv 就是解析它来的
```

为什么值得看：`BeingDebugged` 是反调试与"检测自己被分析"的第一课（3.7 说过调试器怎么改这里）；`ProcessParameters` 是进程启动参数的原始档案（命令行、环境块、标准句柄的真身）；`Ldr` 链表就是"这个进程加载了哪些 DLL"的权威清单——23.6 讲 PE 时提过的加载器，数据就挂在这。SDK 头文件 `winternl.h` 给了 PEB 的部分字段（其余以 `Reserved` 面目出现，偏移照 WDK 对号入座）。

## 36.4 对象命名空间：Local\ 与 Global\ 的谜底

第 17/20 章用命名互斥体时欠了一个解释：`Local\` 与 `Global\` 前缀到底改了什么？答案是**对象管理器的目录树**——内核给所有"可命名对象"（互斥体/事件/信号量/节/ALPC 端口……）维护了一棵像文件系统一样的命名树：

```text
\                                ← 对象管理器命名空间根
├── ??                           ← "DOS 设备"目录：盘符与 \\.\ 设备名的落点（36.5）
│     C: → \Device\HarddiskVolume5
│     CONIN$、CONOUT$ → \Device\ConDrvServer …
├── BaseNamedObjects             ← 全局命名对象（Global\ 的家）
├── Sessions
│     └── 4（会话号）
│           └── BaseNamedObjects ← 本会话命名对象（Local\ 的家；服务在会话 0）
├── Device                       ← 所有设备对象；用户态不可直接按名访问
└── KernelObjects …
```

规则（Pavel 书第 1 章的原文结论）：用户态 `CreateMutexW(L"名字")` 实际创建在 `\Sessions\<本会话>\BaseNamedObjects`；`Global\` 前缀才落进全局 `\BaseNamedObjects`；AppContainer（UWP 沙箱）还有更深的私有目录。**服务（30 章，会话 0）想和用户会话的进程互斥，必须用 `Global\`**——第 20 章的结论在这里拿到实证。

44 示例第三节亲手验证（先种两个互斥体再枚举两个目录）：

```text
已创建命名互斥体 Local\Win32TutorialDemo 与 Global\Win32TutorialDemo
打开 \BaseNamedObjects：成功
  MSDTC Bridge 3.0.0.0_Perf_Library_Lock_PID_15c4   Mutant
  SM0:7800:120:WilError_03_p0                       Semaphore
  [CoreUI]-PID(12464)-TID(8872) …                   ALPC Port
  Win32TutorialDemo                                 Mutant   ← 我们种的
  （共 1127 个命名对象，其中 Win32TutorialDemo 命中 1 个）
打开 \Sessions\4\BaseNamedObjects：成功
  …
  Win32TutorialDemo                                 Mutant   ← 我们种的
  （共 1467 个命名对象，其中 Win32TutorialDemo 命中 1 个）
```

`Local\` 那个只出现在会话目录、`Global\` 那个只出现在全局目录，各自恰好命中一次——谜底揭晓。枚举用的 `NtOpenDirectoryObject` + `NtQueryDirectoryObject` 又是 Native API 家族成员（注意 36.2 的教训：`STATUS_MORE_ENTRIES` 是成功级状态，按负值判错才对）。想肉眼看这棵树：Sysinternals 的 **WinObj**（管理员运行）就是它的资源管理器。

顺带一提对象"名字"的语义细节（容易想当然）：进程/线程对象**没有名字只有 ID**（所以 `OpenProcess` 收数字不收字符串）；文件对象的"名字"是路径不是对象名。命名空间里住的是互斥体/事件/信号量/节/端口这些"生来为了跨进程"的类型。

## 36.5 与驱动对话：设备也是文件

内核驱动的服务对象是**设备对象**，它们住在 `\Device` 目录下——用户态**不能**直接按名访问。官方给的窗户是**符号链接**：驱动（或系统）在 `\??` 目录里放一个链接指向设备，用户态用 `CreateFile` 打开 `\\.\链接名`。名字翻译链：

```text
CreateFileW(L"\\\\.\\Booster")        ← 两个反斜杠开头的 NT 设备路径语法
    ↓  \\.\  被翻译为  \??\
\??\Booster  --符号链接-->  \Device\Booster
    ↓  打开成功 = 向该设备的驱动投递 IRP_MJ_CREATE
拿到句柄：WriteFile/ReadFile/DeviceIoControl 全部可用
```

驱动没加载（没有设备对象、没有符号链接）时，`CreateFile` 报错误 2（`ERROR_FILE_NOT_FOUND`）——Pavel 书第 4 章特意点出这个"最常见的第一脚踩空"。四类用户态调用与驱动的对应（张铮书表 11.1 的现代版）：

| 用户态调用 | 驱动收到的 IRP | 典型用途 |
|-----------|---------------|---------|
| `CreateFile` / `CloseHandle` | `IRP_MJ_CREATE` / `IRP_MJ_CLOSE` | 建立会话（驱动可在此做权限检查） |
| `WriteFile` / `ReadFile` | `IRP_MJ_WRITE` / `IRP_MJ_READ` | 收发数据 |
| `DeviceIoControl` | `IRP_MJ_DEVICE_CONTROL` | **带类型的命令通道**（问规格、下命令） |

`DeviceIoControl` 的核心是 **IOCTL 控制码**——一个 32 位整数，由 `CTL_CODE` 宏打包四元组：

```cpp
#define CTL_CODE(DeviceType, Function, Method, Access) \
    ((DeviceType) << 16) | ((Access) << 14) | ((Function) << 2) | (Method)
// 自定义控制码：DeviceType ≥ 0x8000，Function ≥ 0x800（微软保留低位段）
```

其中 **Method 决定两个缓冲区怎么过边界**——这是"用户态指针为什么不能直接给驱动"的答案。驱动代码可能在中断上下文、随机线程上下文里跑，用户缓冲随时可能被换出或释放，于是 I/O 管理器提供三种代劳：

| Method | 机制 | 代价 | 适用 |
|--------|------|------|------|
| `METHOD_BUFFERED` | I/O 管理器在非分页池建系统缓冲区，进内核拷一次、出内核拷一次 | 两次拷贝 | 小缓冲（≤1 页）的默认选择 |
| `METHOD_IN/OUT_DIRECT` | 建 mdl 把用户页**锁进物理内存**并映射出一份系统地址 | 零拷贝 | 大缓冲（磁盘 I/O 都是它） |
| `METHOD_NEITHER` | 原样传指针，驱动自己负责安全访问 | 最快最险 | 特定高性能场景 |

现在回看 `DeviceIoControl` 的参数表就懂了：`lpInBuffer`/`lpOutBuffer` 双缓冲、`lpdwBytesReturned` 报告"拷回来多少"——全是这套机制的镜像。44 示例第四节的两手实测：

```text
WriteFile(\\.\CONOUT$) 成功 —— 控制台本身就是设备驱动（condrv），printf 的终点站是它
\\.\PhysicalDrive0：产品 KBG5AZNV512G LA KIOXIA 总线类型 17（NVMe）
    ↑ 0 权限打开 + IOCTL_STORAGE_QUERY_PROPERTY，两段问尺寸（19 章模式再现）
打开不存在的 \\.\NoSuchDriverDemo0：2（ERROR_FILE_NOT_FOUND）
```

注意第二手**不需要管理员**：用 0 权限（`dwDesiredAccess = 0`）打开 + 只读 IOCTL，问的是"你是谁"而不是"让我读写你"——最小权限原则在设备接口上同样成立。

## 36.6 IRP 之旅：一次 I/O 请求的一生

把 36.5 的对应表串成时间线，就是 Windows I/O 的核心抽象 **IRP（I/O Request Packet）**：

```text
线程调 DeviceIoControl
    ↓ I/O 管理器：打包 IRP（头 + 每层设备一个 I/O 堆栈位置）
    ↓ 按设备栈逐层下传：每层驱动用 IoGetCurrentIrpStackLocation 取自己的参数
    ↓ 驱动处理：按 Method 拿缓冲（36.5 三选一）
    ↓ IoCompleteRequest：完成请求
    ↓ （Buffered 读）I/O 管理器排队内核 APC，等原线程被调度时把结果拷回用户缓冲
线程从 DeviceIoControl 返回，lpdwBytesReturned 有值
```

三个设计美感值得品：**包驱动**（请求自带全部上下文，谁在都行，异步天然成立）；**栈分层**（过滤驱动插在设备栈中间就能观摩/修改别人的 I/O——杀软与加密盘的架构基础）；**完成即拷回**（拷回用 APC，因为必须在请求线程自己的地址空间里做）。同步/异步的官方入口就是第 19 章的 `OVERLAPPED`：`DeviceIoControl` 传了它就立即返回、完成时通知——慢设备（磁盘/网络）必须这么伺候。

## 36.7 驱动生态与学习路线

本章始终站在用户态往下看。真要迈过边界写驱动，先认清地图（两本书恰好互补）：

| 生态 | 是什么 | 对应书 |
|------|--------|--------|
| **WDM** | 裸内核 API（`DriverEntry`、派遣例程、IRP 手工处理）——本章 36.5/36.6 讲的全是它的世界 | 张铮第 11 章的 DDK 时代样本 |

工程现实四条：① 开发要 **WDK**（本教程的 MSVC 工具链之外再装一层）；② 驱动要**签名**才能装（测试签名模式 `bcdedit /testsigning` 或虚拟机里过，Pavel 第 15 章）；③ 调试要 **WinDbg**（本机内核调试已禁，正规姿势是双机：虚拟机 + 网络/串口，Pavel 第 5 章有完整教程）；④ 驱动的加载者正是 30 章的 **SCM**——`CreateService SERVICE_KERNEL_DRIVER` + `StartService`，服务一章的知识直接复用。张铮书第 11 章把这条路走了一遍（用 SCM 加载自写驱动、`DeviceIoControl` 交互、做防火墙）；Pavel 书是这门手艺目前的最佳系统教材——学完本教程 35 章再读它，门槛只剩"内核纪律"本身（IRQL、分页、崩溃即蓝屏）。

## 36.9 易错清单

| 症状 | 原因 | 解法 |
|------|------|------|
| 把 NTSTATUS 当 HRESULT 判 `FAILED()` | 两者位布局不同 | 零/负值语义：`st < 0` 才是错（36.2） |
| 成功调用被当失败 | `STATUS_MORE_ENTRIES`(0x105) 等成功级非零状态 | 按负值判错，不用 `!= 0` |
| 动态解析 ntdll 函数返回空 | 函数名拼写/版本差异 | 21 章 `GetProcAddress` 模式 + 空指针检查 |
| `NtQuerySystemInformation` 总返回 0xC0000004 | 缓冲不够 | 翻倍重试循环（36.2 的标准形态） |
| 枚举对象目录死循环 | `STATUS_MORE_ENTRIES` 当失败、`RestartScan` 每轮传 TRUE | 首轮 TRUE 之后 FALSE，靠 `Context` 续读 |
| 打开 `\Device\XXX` 直接失败 | 用户态不可见 `\Device` | 走 `\??` 符号链接，即 `\\.\名字`（36.5） |
| `CreateFile(L"\\\\.\\...")` 错误 2 | 驱动没加载/名字拼错 | 错误 2 = 没有这个设备，先查驱动状态 |
| 对 PhysicalDrive 用 GENERIC_READ 被拒 | 读写设备要管理员 | 0 权限 + 只读 IOCTL 够用就绝不多要（36.5） |
| 抄的 `SYSTEM_PROCESS_INFORMATION` 字段错位 | SDK 无定义，各版本结构有差异 | 对照 WDK/Process Hacker，先跑通再信任 |
| `winternl.h` 与 `ntstatus.h` 宏冲突 | include 顺序 | `WIN32_NO_STATUS` 三明治写法（36.8） |

## 36.10 小结

1. Win32 之下：kernel32 转发 → ntdll（最后的用户态）→ 服务号 + `syscall` → SSDT → 内核同名函数——ntdll 还兼职堆管理器与 PE 加载器。
2. Native API 是官方契约之下的方言：NTSTATUS 零/负值语义、成功级非零状态、动态解析、SDK 不给全的结构自己抄——看得懂是素养，依赖它是冒险。
3. TEB/PEB 是自我档案：`BeingDebugged`、`ProcessParameters`（命令行真身）、`Ldr`（模块清单）——`NtCurrentTeb()` 一行直达。
4. 对象命名空间解谜：`Local\` → `\Sessions\N\BaseNamedObjects`，`Global\` → 全局 `\BaseNamedObjects`；设备住 `\Device`，用户态经 `\??` 符号链接访问（`\\.\`）。
5. 设备也是文件：`CreateFile`/`WriteFile`/`DeviceIoControl` 分别变成 IRP_MJ_CREATE/WRITE/DEVICE_CONTROL；IOCTL 控制码四元组里的 Method 决定缓冲过界方式（Buffered 双拷贝 / Direct 零拷贝 / Neither 自理）。
6. 学驱动先认地图：WDM（地基）→ KMDF（现代框架）→ Minifilter/WFP（专项）——门槛是 WDK、签名、双机调试；SCM 加载驱动的知识 30 章已经给过。

## 36.11 动手练习

1. 用 44 示例的 ① 段改一个"线程数 Top 10"排行（按 `NumberOfThreads` 排序）——体会一次调用拿全量数据的甜头。
2. 在调试器（3 章）里跑 44 示例，观察 `BeingDebugged` 从 0 变 1——再看 `IsDebuggerPresent` 的反汇编，就一条 `movzx`。
3. 用 `NtQueryDirectoryObject` 枚举 `\??` 目录，找出 `C:` 和 `CONOUT$` 各自链接到哪个 `\Device\...`——36.5 的翻译链亲眼验证（WinObj 交叉对照）。
