## 35.1 进程边界的另一面：隔离到底挡住了谁

第 16 章说过：每个进程有独立的虚拟地址空间，谁也踩不着谁。这句话的准确版本是——**挡不住有足够权限句柄的人**。Win32 给了三个"门"：

| 函数 | 作用 | 需要的权限（OpenProcess 时申请） |
|------|------|------|
| `ReadProcessMemory` | 读别的进程的内存 | `PROCESS_VM_READ` + `PROCESS_QUERY_INFORMATION` |
| `WriteProcessMemory` | 写别的进程的内存 | `PROCESS_VM_WRITE` + `PROCESS_VM_OPERATION` |
| `VirtualQueryEx` | 查别的进程的地址空间布局 | `PROCESS_QUERY_INFORMATION` |

权限不是申请就给：**目标进程的安全描述符（20 章）与调用者的令牌对得上才给**。亲手试试边界在哪：

- 打开同用户的普通进程：全权限到手（这就是修改器的工作条件）；
- 打开 `winlogon.exe` 等系统进程：`OpenProcess` 失败，错误 5（`ERROR_ACCESS_DENIED`）——除非进程令牌里有 `SeDebugPrivilege`（调试特权，管理员可启用，张铮书中 `EnableDebugPrivilege` 四步：`OpenProcessToken` → `LookupPrivilegeValue` → `AdjustTokenPrivileges` → `CloseHandle`）；
- 打开受保护进程（PPL，如杀软、DRM 服务）：即使管理员 + 调试特权也被拒——这是 Vista 以后给"必须无人能碰"的进程开的特权通道。

一句话：**隔离挡的是"无句柄的野访问"；有权限句柄，地址空间就是透明的**。本章所有演示只针对自己启动的子进程——工程伦理与法律边界同技术边界一样真实（游戏修改违反多数在线服务条款；同样的手法读别人进程里的密码框，就是犯罪工具）。

## 35.2 扫描器骨架：三件套怎么配合

"游戏修改器"的核心是**按值搜索**：知道屏幕上显示金钱 1003，就把目标进程整个地址空间扫一遍，记下所有内容等于 1003 的地址。张铮 2005 年的原版从 64KB 盲读到 2GB、每页 4KB 硬读（读不动就跳过）；x64 时代的正确写法是先问布局再读：

```cpp
MEMORY_BASIC_INFORMATION mbi;
ULONGLONG addr = 0x10000;                    // 前 64KB 永不可提交
while (VirtualQueryEx(hProc, (LPCVOID)addr, &mbi, sizeof(mbi)) == sizeof(mbi)) {
    BOOL readable = mbi.State == MEM_COMMIT                 // 只要已提交的
        && !(mbi.Protect & PAGE_GUARD)                      // 跳过 guard 页（栈伸展页）
        && (mbi.Protect & (PAGE_READONLY | PAGE_READWRITE | PAGE_WRITECOPY |
                           PAGE_EXECUTE_READ | PAGE_EXECUTE_READWRITE));
    if (readable) { /* ReadProcessMemory 整块读入，逐 8 字节比对哨兵值 */ }
    addr = (ULONGLONG)mbi.BaseAddress + mbi.RegionSize;     // 跳到下一区域
    if (addr >= 0x00007FFFFFFEFFFF) break;                  // x64 用户空间上限
}
```

三个实战要点：

1. **`VirtualQueryEx` 是第 18 章 `VirtualQuery` 的跨进程版**——同一区域信息结构（State/Protect/Type），只是问的是别人家的布局。一次调用把"哪里能读"问清楚，比盲读高效且文明；
2. **哨兵值选 8 字节**（`ULONGLONG`）：扫 4 字节 DWORD 时，堆元数据、句柄值、时间戳都常撞车；8 字节的魔数碰撞概率约等于零；
3. **映像页里的常量是假命中**：如果你扫的值恰好是目标程序里写死的字面量（`movabs rax, 0x00C0FFEE...` 的立即数就躺在 `.text` 里），它会**永远命中、永远不变**，任何"等值变化"的收窄都排不掉它。43 示例第一版就栽在这——靶子的哨兵是编译期常量，首扫永远多出 2 处。解法有二：真实工具默认跳过 `MEM_IMAGE` 页；43 示例的解法更彻底——**哨兵值由靶子运行时随机生成**，映像里根本没有。

## 35.3 收窄的语义：重扫新值 ∩ 旧地址列表

首扫通常命中多处（多个变量恰好同值 + 偶然巧合）。张铮书的 `FindNext` 给出了经典语义，值得原样记住：

```text
第一次：扫旧值 V0 → 地址集合 A
游戏里数值变化：V0 → V1（花钱了/掉血了）
第二次：扫新值 V1 → 地址集合 B
答案 = A ∩ B   ← 既装过旧值、现在又装着新值的地址
```

只装旧值的（没变的诱饵、映像常量）被 A∩B 排除；只装新值的（中途恰好多出来的副本）也被排除。迭代几轮后集合收缩到 1，那就是目标变量——`WriteProcessMemory` 直接写入。

43 示例把这套流程全自动演给你看（它同时是 16 章 `CreateProcess` + 管道重定向的复习课）：

```text
[靶子] 屏幕上显示：金钱 V=0x0010000000009846        ← 修改器从靶子输出解析（=玩家看屏幕）
[修改器] 第一次扫描：6 处命中（5 个变量 + 零星巧合）
[靶子] 屏幕上显示：金钱 V=0x0010000000009746（花掉了一点）
[修改器] 新值 2 处命中 ∩ 旧列表 6 处 = 1 处——收窄到唯一，这就是金库
[修改器] 对 00007FF65808BAF0 写入 0x00deadbeefcafe00 ...
[靶子] 检测到金库被改写：0x0010000000009746 -> 0x00deadbeefcafe00（跨进程写入成功！）
```

靶子打印的 `g_gold` 地址与修改器扫出的唯一命中**逐位一致**——两份独立证据指向同一块内存，这是跨进程读写最直观的闭环验证。

## 35.4 Windows 钩子：消息流的监视点

进程隔离有一条官方开的窗户：**钩子（Hook）**。Windows 是消息驱动的（第 4 章），系统允许你在"消息到达目标窗口过程之前"插一个监视点：

```cpp
HHOOK h = SetWindowsHookExW(WH_KEYBOARD, HookProc, hInstDll, dwThreadId);
// ...
LRESULT CALLBACK HookProc(int nCode, WPARAM wParam, LPARAM lParam) {
    if (nCode >= 0) { /* 看/改这条消息 */ }
    return CallNextHookEx(hHook, nCode, wParam, lParam);   // ★ 钩子链纪律：永远传下去
}
UnhookWindowsHookEx(h);
```

三条纪律：`nCode < 0` 时必须直接放行；处理完必须 `CallNextHookEx`（同一位置可能挂了一串钩子）；**用完立刻卸载**（每个钩子都在给全系统每条消息加税）。

关键分野在 `dwThreadId` 参数，它决定了钩子的形态：

| 形态 | 条件 | 后果 |
|------|------|------|
| **局部钩子** | `dwThreadId` 是自己进程的线程 | 回调函数在本进程内即可，怎么写都行 |
| **远程钩子**（全局） | `dwThreadId` = 0 或别的进程的线程 | 回调将在**目标进程**被调用——代码必须住在 DLL 里，系统把你的 DLL **映射进**每个用到相关消息的进程 |

远程钩子 + DLL 就是 23.8 说的"钩子注入"的机制本体：不是你把 DLL 塞进去，是**系统替你塞**。张铮书的键盘钩子实例（`WH_KEYBOARD` 全局钩子）是这套手艺的经典样本，其中有个必学的细节——**共享数据段**：

```cpp
#pragma data_seg("Shared")          // 这个段在所有映射了本 DLL 的进程间共享一块物理内存
HHOOK g_hHook = NULL;               // ★ 未初始化的变量不进共享段！必须显式初始化
HWND  g_hWndCaller = NULL;
#pragma data_seg()
// 还要 .def 里声明：SECTIONS Shared READ WRITE SHARED
```

为什么需要它：钩子句柄和"通知谁"只在安装进程里设置过，但回调跑在**别的进程**里——没有共享段，别的进程看到的全是零。

## 35.5 现代写法：WH_KEYBOARD_LL，免 DLL 的低级钩子

老式 `WH_KEYBOARD` 全局钩子要把 DLL 注入所有进程，动静大、也被安全软件盯得最紧。XP 之后有了低层替代：

```cpp
g_hook = SetWindowsHookExW(WH_KEYBOARD_LL, LowLevelKbProc, GetModuleHandleW(nullptr), 0);
```

三点本质区别：

1. **回调永远在安装它的线程/进程里执行**（系统把键盘事件投递给你），不需要 DLL，也不注入任何进程——43 示例 `-hook` 模式 30 行就是全部；
2. **装钩的线程必须泵消息**：事件经由你的消息队列送达，没有 `GetMessage`/`PeekMessage` 循环回调就永远不触发——这是低级钩子的第一坑（43 示例的泵循环就是为它写的）；
3. **看得更低**：老式钩子看到的是"消息队列里的 `WM_KEYDOWN`"，低级钩子看到的是扫描码级的原始事件（还能识别 `LLKHF_INJECTED`——注入的按键，屏幕键盘/输入法就是这么被识别的）。系统给回调约 300ms 预算（`LowLevelHooksTimeout`），超时直接摘钩——回调里干重活会"神秘失效"。

## 35.6 注入与侦测全景：一张攻防表

把 23.8 的"一瞥"展开成全景（依然只讲机制、演示只针对自家进程）：

| 手法 | 机制 | 现状/防御 |
|------|------|----------|
| `AppInit_DLLs` | user32 初始化时替每个 GUI 进程 `LoadLibrary` 清单里的 DLL | 现代默认禁用，历史名词 |
| 钩子注入 | 35.4 的远程钩子，系统替你映射 DLL | 安全软件重点监控对象 |
| 远程线程注入 | `CreateRemoteThread` 起线程，入口 = `LoadLibraryA`，参数 = `VirtualAllocEx`+`WriteProcessMemory` 预先写进目标的 DLL 路径 | 能用的前提仍是权限句柄；`LoadLibrary` 与线程函数签名一致（都收一个指针）纯属 ABI 巧合 |
| API 挂接 | 改目标模块导入表（IAT）或函数开头字节 | CFG 让间接调用只走白名单；改代码触发代码完整性校验 |

其中"远程线程注入"有一个值得品的设计巧合：`CreateRemoteThread` 的入口函数签名 `DWORD (*)(LPVOID)` 与 `LoadLibraryA` 的 `HMODULE (*)(LPCSTR)` **二进制兼容**（同为 WINAPI 约定、同收一个指针宽度参数）——而且 kernel32 在每个进程映射在同地址，所以"本进程里查到的 LoadLibrary 地址"在目标进程同样有效。防的是同一套：**UIPI/完整性级别拦低权限碰高权限**（20 章）、**CFG** 拦异常跳转、**PPL** 让关键进程连句柄都拿不到、EDR 从行为侧盯"谁在别人进程里起线程"。

张铮书里还有个漂亮的攻防对照（2.4.4 节）：游戏定时枚举进程杀掉外挂（Toolhelp 枚举 + `TerminateProcess`），外挂反过来钩掉系统的 `TerminateProcess` 让任务管理器都杀不动它——攻与防用同一门手艺，这正是"理解原理才能做防御"的最好注脚。

## 35.7 完整示例：43_cross_process

三模式单 exe（`wmain` 分流，41 例的网络演示同款）：

```text
43_cross_process            修改器主模式：起靶子 → 扫描 → 收窄 → 改写 → 靶子确认
43_cross_process -target    靶子模式：五个哨兵变量、定时漂移、被改写时自报退出
43_cross_process -hook      WH_KEYBOARD_LL 自观测 6 秒（安装 → 泵消息 → 卸载）
```

工程细节三则：① 靶子经管道由修改器转发输出（16 章重定向手法），修改器顺带从输出里**解析数值**——对应"玩家看屏幕"这个真实工作流；② 哨兵值运行时随机生成（35.2 的常量陷阱）；③ 全家 `setvbuf` 无缓冲，强杀不丢日志（37/41 例的老规矩）。

## 35.8 易错清单

| 症状 | 原因 | 解法 |
|------|------|------|
| `OpenProcess` 返回 NULL，错误 5 | 目标是系统/高完整性/PPL 进程 | 权限边界即设计（35.1）；自家演示用 `CreateProcess` 的返回句柄 |
| 扫描命中数永远不变、收窄不动 | 哨兵是目标映像里的编译期常量 | 值运行时生成，或跳过 `MEM_IMAGE` 页（35.2） |
| `ReadProcessMemory` 间歇失败 | 区域刚被释放/保护变更 | 以区域为单位读，失败整块跳过（布局随时在变） |
| 收窄后写错地址、靶子崩 | 没做 A∩B，写进了巧合命中 | 重扫新值再求交（35.3） |
| 全局 `WH_KEYBOARD` 钩子不生效 | 回调不在 DLL 里 / DLL 没进目标进程 | 远程钩子必须 DLL + 共享数据段（35.4） |
| 共享段"不共享" | `#pragma data_seg` 里的变量没初始化 | 未初始化变量落在默认数据段——必须显式赋初值 |
| `WH_KEYBOARD_LL` 装上却无回调 | 装钩线程没有消息循环 | 泵消息（35.5），回调跑在你的线程里 |
| 低级钩子装一会儿就"失效" | 回调超时（默认约 300ms）被系统摘除 | 回调只做轻活 |
| `#pragma data_seg` 后链接报段属性错 | 没声明段可共享 | `.def` 里 `SECTIONS ... SHARED` 或 `/SECTION:Shared,RWS` |

## 35.9 小结

1. 进程隔离挡的是野访问；有权限句柄（`OpenProcess` 申请 `PROCESS_VM_*`），`ReadProcessMemory`/`WriteProcessMemory`/`VirtualQueryEx` 三件套让地址空间透明——系统/PPL 进程是边界。
2. 修改器工作流 = 首扫旧值 → 等值变化 → 重扫新值 ∩ 旧地址列表 → 唯一即目标 → 写入。映像常量是排不掉的假命中，值要运行时生成。
3. 钩子是消息流的官方监视点：局部钩子随便写；远程（全局）钩子必须 DLL + 共享数据段，它同时就是"钩子注入"的机制本体。
4. 现代低层用 `WH_KEYBOARD_LL`：免 DLL、回调在本进程，代价是装钩线程必须泵消息、回调限时。
5. 注入三招（AppInit/钩子/远程线程）全部依赖权限句柄，防它的四件套是 UIPI/CFG/PPL/行为检测——攻防同源。

## 35.10 动手练习

1. 给 43 示例的扫描器加 `MEM_PRIVATE` 过滤开关（只扫堆/栈等私有内存），观察首扫命中数变化——再想想为什么全局变量（住在映像 `.data` 页）会从结果里消失。
2. 把靶子的哨兵改回编译期常量，重跑验证 35.2 的"假命中"陷阱——教科书知识亲手复现一遍。
3. 给 `-hook` 模式加 `GetAsyncKeyState` 对照：钩子回调与异步状态查询看到的事件顺序一致吗？
4. 用 16 章知识写一个小工具：`OpenProcess` 打开记事本（同用户），`ReadProcessMemory` 读它标题栏进程的 PEB（36 章的预热）——失败的话想想为什么（提示：完整性级别）。
