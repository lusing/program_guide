# 23 · 贪婪算法：每步取最优，全局就最优吗

## 23.1 动机与直觉：凭直觉生活的人都在用贪婪

从本章起，我们离开数据结构的世界，进入算法设计方法的世界（与 Sahni 教材第 13–17 章对应）。前 22 章反复出现一个问题："这个操作要花多少时间？"接下来五章换一个问题："这个问题该怎么解？"——用什么样的策略，把输入变成最优解。

第一个策略是所有人每天都在用的：**贪婪算法（greedy method）**。找零钱时先给最大面额；装行李时先塞最轻的箱子；赶工期时先干最赚钱的活。它的流程是"逐步构造解"：问题分 n 个阶段，每个阶段作出一个**在当前信息下看起来最好**的决策，决策一旦作出**永不反悔**，n 步之后解就构造完毕。作出决策所依据的标准叫**贪婪准则（greedy criterion）**。

这个策略最迷人的地方在于它的两面性：

- 找零钱（面额 25/10/5/1 美分）先给大票，找出的硬币数**恰好最少**——贪婪给出全局最优；
- 同样的"先给大票"策略，在面额 14/5/2/1 分的国家找 18 分：14+2+1+1 用了 4 枚，最优解是 14+2+2 用 3 枚——贪婪**不是最优**。

其实你已经写过不少贪婪算法而不自知，本教程前文至少出现过三次：

- **第 15 章哈夫曼编码**：每次从堆里取两个权重最小的树合并——"最小者先配对"就是贪婪准则，WPL 的最优性靠证明撑腰；
- **第 20 章 Prim 与 Kruskal**：每次挑"不会成环的最小权边"（Kruskal）或"离生成树最近的顶点"（Prim），贪婪构造成本最小的生成树；
- **第 20 章 Dijkstra**：每次锁定"当前距离估计最小的未定型顶点"，靠非负权保证这个决策不可反悔。

当时的重点在数据结构（堆、并查集如何支撑这些"每步取最小"），本章把镜头反过来：**准则本身怎么设计、怎么证明、什么时候会翻车**。读这三处旧代码时会发现，它们的正确性论证与本章 23.3 节是同一套语言。

为什么同一个策略时灵时不灵？这正是本章要建立的核心判断力：**贪婪算法证明最优靠两条性质——贪婪选择性质与最优子结构**。

- **贪婪选择性质**：存在一个最优解，包含当前贪婪决策所选的那个元素。也就是说"第一步走贪心这步"不会把最优解排除在外。
- **最优子结构**：作出第一步决策后，剩下的问题与原问题同型，其最优解与第一步拼起来仍是原问题的最优解。

两条都成立，贪婪就严格最优；任何一条断裂，贪婪退化为启发式——可能很近，也可能差很远。第 25 章的动态规划正是"贪婪断裂"问题的解药，到时可以对照。

本章实现三个贪婪的经典应用：装载问题（个数最优，贪婪严格最优）、部分背包（价值最优，贪婪严格最优）、任务调度（利润最优，贪婪严格最优），并在 23.3.4 节亲手拆掉一个反例——0/1 背包上贪婪如何失灵。

## 23.2 ADT 合同

三个函数都遵循同一份总合同：输入是一组"候选元素 + 一条约束（容量或时间槽）"，输出是一个最优的**数值指标**（不返回选取方案——把方案也返回的版本在 25/26 章会做，这里刻意只算指标，让贪婪准则本身看得更清楚）。

**装载问题合同：**

- `container_loading(weights, cap)`：前提 `weights` 全为正、`cap ≥ 0`；返回最多能装入的箱数。事后不改变输入。
- 关键口径：最优目标**是箱数、不是载重利用率**。"装满"与"装多"是两个不同的优化函数，选错口径就选错算法。

**部分背包合同：**

- `fractional_knapsack(values, weights, cap)`：前提两 span 等长、`weights` 全为正、`cap ≥ 0`；物品**可拆分**（装 0.3 个也算合法）；返回最大总价值，`double` 计算。
- 与 0/1 背包的分界线只有一条：允不允许拆。可拆 → 贪婪最优；不可拆 → 贪婪失灵（见 23.3.4）。

**任务调度合同：**

- `job_sequencing(jobs)`：前提每项 `deadline ≥ 1`；每项任务恰好耗 1 个时间槽，在 `deadline` 前完成才得 `profit`；返回可得的最大总利润。
- 时间槽数量由输入决定：`1..max(deadline)`，不是固定值。这是实现里最容易算错维度的前提，23.7 坑 2 专门讲。

三份合同共同的隐性约定：**平局必须有确定规则**（本实现：利润相等按截止日早者先；装载按重量升序稳定排序语义），否则跨编译器的输出无法逐字节一致——这是全教程的确定性纪律在算法章的延续。

## 23.3 设计与不变量：三个贪婪准则与它们的证明

### 23.3.1 装载问题：轻者优先，交换论证定最优

贪婪准则：**每次选最轻的未装箱子**。为什么轻的优先箱数最多？用交换论证（exchange argument）——这是证明贪婪最优的标准武器，值得完整看一次：

设贪婪选出箱子集合 G，任取一个最优解 OPT。若 G ≠ OPT，因为 G 是"逐个取当前最轻"构造的，必有某个重量：G 中第 k 轻的箱子 g 比 OPT 中某个箱子 o 更轻，而 o 不在 G 里。把 OPT 里的 o 换成 g：箱数不变、总重不增（g 更轻），可行性与最优性都保住。反复交换，OPT 被逐步改造成 G 而最优值不变——所以 G 也是最优解。

实现上，交换论证等于一句话："**更轻的箱子放进解里永远不吃亏**"。于是排序后从头装到超载为止：

```cpp
std::sort(sorted.begin(), sorted.end());   // 轻者在前
for (const int w : sorted) {
    if (used + w > cap) break;             // 当前装不下，后面更重的全装不下
    used += w;
    ++count;
}
```

为什么遇到第一个装不下的就可以 `break` 而不是 `continue`？不变量是"数组已升序"：后面所有箱子的重量 ≥ 当前这个，当前都放不下，后面必然放不下。这个不变量把扫描从"试探每个箱子"（O(n) 次失败判断）砍成"装到第一处失败为止"。

测试夹具 [10,20,30]、cap=50：装 10、20（合计 30），30 装不下 → 2 箱。注意**总重 30 远未用满 50**——最优是箱数口径，这正说明"优化函数是什么"本身就是设计决策。

### 23.3.2 部分背包：单位价值定序，可拆性是关键

贪婪准则：**单位价值 `values[i]/weights[i]` 最高者先装；装不下整个就装一部分**。

为什么可拆时贪婪严格最优？直觉版：把容量想成一种"货币"，每件物品按单位价值把容量换成价值。容量花在单价最高的物品上，总价值当然最大。严格版仍是交换论证：若最优解先装了单价低的 a 而容量给了单价高的 b 不足，把 a 的一部分容量挪给 b，总价值严格增加（或不变）——与"最优"矛盾。

```cpp
std::sort(idx.begin(), idx.end(), [&](auto a, auto b) {
    return values[a] / weights[a] > values[b] / weights[b];  // 单位价值降序
});
// 先整件装；某件装不下时装其一部分并停止
```

为什么最后一件只装一部分就 `break`？因为背包此刻**满了**（`weights[i] > remain` 时装 `remain/weights[i]` 恰好用光容量），后面单价更低的物品再无容量可分。

夹具验证：单位价值 6 > 5 > 4，装 60+100（重 30），剩余容量 20 装 1/3 的 120 → 60+100+80 = 240.0。

有一个实现细节值得点名：比较器里做**除法**（`values/weights` 的商排序）。数学上等价于交叉相乘（`values[a]*weights[b] > values[b]*weights[a]`），后者只用乘法、无除零风险（前提已保证 weights 为正，所以本实现保留除法以贴合"单位价值"的直觉），但若把前提放宽到允许零重量的物品，必须改用交叉相乘——这是"前提即实现"的直接例子。

### 23.3.3 任务调度：利润降序 + 最晚空位

问题：单台机器、时间槽 1..T，任务 i 耗 1 槽、必须在 `deadline[i]`（含）前完成才得 `profit[i]`，最大化总利润。

贪婪准则分两半：**利润降序考虑任务**；每项任务**安排在其截止日之前最晚的空闲槽**。"最晚空位"这半句是精髓——把早的槽位留给截止日更紧的任务，是典型的"保留灵活性"策略。

```cpp
for (const Job& j : sorted) {
    for (int slot = j.deadline; slot >= 1; --slot) {   // 从截止日往前找
        if (!used[slot]) { used[slot] = true; total += j.profit; break; }
    }                                                   // 一路到 1 都满：放弃此项
}
```

夹具五任务 {（d2,100),(1,19),(2,27),(1,25),(3,15)}：利润降序 100、27、25、19、15。100 占槽 2；27 找最晚空位 ≤2 → 槽 2 已满、占槽 1；25 的槽 1 已满、放弃；19 同；15 占槽 3。总利润 100+27+15 = **142**，恰好是全局最优（穷举全部排程可验证 142 是上界：三个时间槽最多选三项，140 的组合 d1=25+100 不存在合法排法——25 与 100 都挤不进与 15 并存的三槽结构）。

把五步全部列成表，"最晚空位"如何给低利润任务留出余地一目了然：

| 步 | 任务（利润，截止日） | 槽占用 | 决策 |
|---|---|---|---|
| 1 | (100, 2) | 槽 2 空 | 占槽 2（最晚空位即槽 2） |
| 2 | (27, 2) | 槽 2 满 | 占槽 1（往前找到的第一个空位） |
| 3 | (25, 1) | 槽 1 满 | 放弃——不可反悔，决策即终局 |
| 4 | (19, 1) | 槽 1 满 | 放弃 |
| 5 | (15, 3) | 槽 3 空 | 占槽 3 |

读表可见两个关键：其一，步 2 若把 27 随手放在"从早到晚第一个空位"（也是槽 1）结果相同，但一般情形不成立——若再来一个 (30,1) 的任务，"最晚空位"策略已在步 2 把槽 1 用掉，30 只能放弃；正确的实现永远是"尽量靠后"。其二，步 3 的 25 被放弃不是实现瑕疵，而是贪婪的定义：已作出的决策（100、27 占槽）永不回退。

交换论证版本：若最优解的某槽给了低利润任务而高利润任务在飞，两者截止日覆盖面允许互换时交换只增不减利润；"最晚空位"保证高利润任务永远有槽可占。

### 23.3.4 贪婪何时失灵：0/1 背包的现场翻车

同一个背包，只把"可拆"改成"不可拆"，贪婪立刻失灵。反例（2 件物品、容量 30）：

- 物品 A：重 30、价值 120（单位价值 4）
- 物品 B：重 20、价值 100（单位价值 5）

贪婪按单位价值先装 B（重 20），剩 10 装不下 A，总价值 **100**；最优解是装 A，价值 **120**。差额 20 不是数值噪声，是策略本身的盲区：贪婪无法"预见"装下 A 后多余容量被浪费。

0/1 背包为什么"一步走错满盘皆输"？因为它**没有贪婪选择性质**——不存在"某个最优解一定包含单位价值最高的物品"的保证（上例即反证）。这类问题的正解是第 25 章的动态规划（它同时评估"装/不装"两个分支）与第 26 章的回溯。看懂这节，就明白了为什么需要那两章。

## 23.4 复杂度推导

三个函数同构：**排序主导 + 一遍线性扫描**。

- 装载：排序 O(n log n) + 扫描 O(n) = **O(n log n)**；额外空间 O(n)（排序副本）。
- 部分背包：建索引 O(n) + 排序 O(n log n) + 扫描 O(n) = **O(n log n)**；空间 O(n)。
- 任务调度：排序 O(m log m)（m 为任务数）+ 双层循环最坏 Σ deadline 层，但每槽至多被占一次、每次成功即 break，总槽位 ≤ max deadline，失败扫描至多 m 次 → 均摊 **O(m log m + m + T)**，T = max deadline；空间 O(T)。

扫描部分是 O(n)，排序是 O(n log n)，所以**总复杂度被排序钉死**——这也是贪婪算法工程上的招牌：先排个序，然后线性走一遍，通常快得惊人。对比第 25 章动态规划的 O(n·cap) 表格法，贪婪在"适用场景内"永远更快；它贵在适用面窄。

把已学与将学的四种策略放在同一张表上，选择空间立刻清晰：

| 策略 | 一句话流程 | 是否保证最优 | 典型代价 | 本章例子 |
|---|---|---|---|---|
| 贪婪 | 每步取局部最优、不反悔 | 有证明时严格最优，否则启发式 | O(n log n) 常见 | 装载/部分背包/任务调度 |
| 穷举 | 枚举全部候选解取最好 | 一定最优 | O(2ⁿ) 或更差，只能小规模 | 23.3.4 的上界验证 |
| 动态规划（25 章） | 自底向上填表，子问题只解一次 | 最优 | O(n·cap) 等 | 0/1 背包的正解 |
| 回溯（26 章） | 系统试错 + 剪枝回退 | 最优 | 指数最坏、剪枝后可用 | 0/1 背包的另一正解 |

贪婪与穷举的关系值得单独一提：**贪婪跑得快，所以"用穷举验证贪婪"是可行的开发习惯**——小规模数据上两者对拍，一致则有信心，不一致则立刻得到反例。本章的任务调度 142 就可这样验证；工程上这是算法代码最好的单元测试形态。

## 23.5 完整示例输出

程序真实输出（build/23_greedy.msvc.out，MSVC 与 clang 逐字节一致）：

```text
装载问题（cap=50）：箱重 [10,20,30] 最多装 2 箱（10+20=30，再装 30 超载）
装载问题边界：空输入得 0；cap=90 装 [50,40] 恰好 2 箱；cap=0 一箱不装
部分背包（cap=50）：最优价值 240.0（单位价值 6>5>4 依次装）
部分背包边界：空输入与 cap=0 均得 0.0
任务调度：最大利润 142（day1=27、day2=100、day3=15；利润 25/19 被挤出）
任务调度边界：空输入得 0；三个任务挤 day1 只能完成利润最高的 50
自检通过
```

逐行解释：

- 第 1 行：升序装入 10、20 后合计 30，30 已超 50−30=20 的余量，`break` 停止——与 23.3.1 的手推一致，断言 `== 2`。
- 第 2 行：三组边界。空输入返回 0；[50,40] 与 cap=90 **恰好装满**（边界值 `used + w > cap` 用严格大于，等于时合法）；cap=0 时第一件就失败。
- 第 3 行：断言 `best == 240.0`（精确相等）。60+100 整件装入后剩余 20，120×(20/30) 的浮点结果恰为 80.0（IEEE 754 正确舍入），总价值 240.0 无累积误差。
- 第 4 行：空 span 与 cap=0 都走"循环体不执行"路径，返回 0.0。
- 第 5 行：五任务例，142 与 23.3.3 的逐步推演一致；括号里点出被贪婪挤掉的利润 25 与 19——"决策不可反悔"的直观体现。
- 第 6 行：三件任务 deadline 全是 1，只有一个时间槽，贪婪留下利润最高的 50——问题退化成"取最大"，也是"最晚空位"策略的极限情形。

## 23.6 与标准库的对照

- 标准库**没有贪婪算法框架**——贪婪是设计策略而非数据结构，C++ 标准库提供的是它的零件：排序与优先队列。
- 排序用 `std::sort` 配自定义比较器即可表达贪婪准则（单位价值降序、利润降序都是一行比较器）。注意比较器必须满足**严格弱序**（等值时返回 false），"利润相等按截止日"正是为此而写。
- 若候选流是动态产生的，贪婪选择可用 `std::priority_queue` 代替排序——每步取堆顶，等价于"边输入边排序"。
- `std::partial_sort` / `std::nth_element`：若贪婪准则只需"取出前 k 个最轻/最贵"，可免全排序，O(n log k)。
- 三道题都没有对应的标准设施。工程上"装箱装载"这类 NP 难问题的工业解法是启发式组合（如首次适应递减 FFD），贪婪是它们的零件。
- 第 25 章预告：0/1 背包的 DP 解法在同样接口上返回最优方案（不只指标）；两章对照即可体会"贪婪 vs 动态规划"的能力边界。

## 23.7 本章坑位

- **坑 1：在 0/1 背包上用贪婪。** 现象：单位价值降序装入，结果 100 而最优 120（23.3.4 反例），且测试数据温和时完全发现不了。原因：0/1 背包无贪婪选择性质，"先拿单价高的"可能堵死更好的组合。后果：得到看似合理的次优解，线上长期悄悄亏 10%–20%。防法：先问"物品可不可拆/排序后是否满足交换论证"，不可拆就换 DP（25 章）或回溯（26 章）。
- **坑 2：任务调度的截止日维度 off-by-one。** 现象：时间槽开 `vector<bool>(max_deadline)`，槽 1 访问 `used[1]` 没问题，但循环写 `slot >= 0` 或把"第 deadline 天"映射到下标 deadline 时越界/漏判。原因：槽编号 1..T 与 0 基数组错位一格。后果：要么崩溃，要么多占一个不存在的槽静默算错利润。防法：数组开 `max_deadline + 1`，下标直接用槽号，下界固定 `slot >= 1`。
- **坑 3：浮点单位价值比较的精度。** 现象：两件物品单位价值理论相等（如 100/20 与 150/30），浮点除法结果一高一低，排序次序随编译器舍入漂移。后果：两通道输出不一致，或选出的"最优"在等价解间跳变。防法：等值情形改用交叉相乘（整数时精确）或给比较器加平局决胜键（如按编号），保证全序确定。
- **坑 4：贪婪准则选错优化函数。** 现象：装载问题按"价值/重量比"或"先装重的凑满容量"实现，箱数反而不最多。原因：优化函数是**箱数**，准则必须服务它（轻者优先）；"装得满"和"装得多"是两个问题。后果：算法没错、题答错了。防法：动手前用一句话写出优化函数和贪婪准则，再问一遍"交换论证通不通过"。
- **坑 5：排序不设平局规则导致输出漂移。** 现象：利润相等的任务在 MSVC 与 clang 下进入不同次序（不同实现的标准 sort 不保证稳定），最晚空位分配结果随之不同。后果：逐字节一致性校验失败，或同一份数据两次运行结果不同。防法：比较器补上确定性的平局键（本实现按截止日），或改用 `std::stable_sort` 并固定输入次序。
- **坑 6：空输入与零容量没走查。** 现象：`max(deadline)` 对空输入得 0 后仍开数组没问题，但若有代码取 `sorted.front()` 就崩；cap=0 时部分背包比较器照样执行、却无物品可装。原因：贪婪主体是"循环 + 前提"，空输入让前提失效。后果：边界崩溃或断言误报。防法：循环天然处理空输入，禁止在任何地方对候选集取 front/top；把空输入、零容量写进固定断言。
- **坑 7：把"局部最优"当"全局最优"的口头禅滥用。** 现象：面试或评审时听到"这是贪心的"就放行正确性。原因：贪婪的名字给了它不该有的可信度——找零钱最优、找 18 分（面额 14/5/2/1）就不优。后果：以直觉代替证明，错的算法配上对的输出格式。防法：每个贪婪算法配一条交换论证或反例，说不出来就先当启发式对待。

本章小结：贪婪算法 = **排序（定序的准则）+ 扫描（不反悔的选择）**，工程实现几乎总是一行比较器加一个循环。它的可信度不来自名字，而来自两条可检验的性质：贪婪选择性质与最优子结构；证明武器是交换论证——"把最优解里的某个元素换成贪婪选的，不亏"反复进行即可。三个例子里装载问题展示了"优化函数口径决定准则方向"，部分背包展示了"可拆性"这一前提的价值，任务调度展示了"保留灵活性"（最晚空位）这类反直觉的好准则。而 0/1 背包的翻车是本章最重要的产出：它划出了贪婪的边界，也是第 25、26 章登场的理由。
