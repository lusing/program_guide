# 12 · 树与森林：多叉树的表示与转换

## 12.1 动机与直觉：家谱为什么"塞不进二叉树"

第 11 章的二叉树规定每个节点最多两个孩子。但现实中大量层级关系没有这个限制：一个家庭有三个孩子，一位经理带五个小组，一个目录下有十几个文件。硬把这些关系塞进二叉树也不是不行（理论上任何树都能编码成二叉树），但直接按"多叉树"思考更自然。

再想一步：很多问题面对的甚至不是一棵树，而是**若干棵树并排站着**——一个文件系统有 C 盘、D 盘、U 盘，各自是一棵树；一个系里有若干位教授，各自带着自己的学生树；离散数学里的一个偏序集可能分解成若干条链。这种"树的集合"叫**森林（forest）**。

本章解决三个问题：① 多叉树在内存里怎么存；② 森林怎样与二叉树互相转换（这是把第 11 章的全部武器"借过来用"的桥梁）；③ 顺带把第 06 章的并查集加强到工业级——按秩合并加路径压缩。

先建立直觉。想象一张家谱画在纸上：每个人名下面拉出一条横线，横线连着所有孩子的名字。要把它搬进只有"左指针、右指针"的节点结构，只需约定两件事：**左指针连我的第一个孩子，右指针连我右边的兄弟。** 一位父亲的三个孩子，本来共用一条横线，现在变成"老大左挂在父亲下、老二右挂在老大桥、老三右挂在老二旁"的链子。这就是本章全部技术的胚芽——把"一排孩子"编码成"一条兄弟链"。

## 12.2 ADT 合同

### 12.2.1 树/森林 `Tree<T>`

`Tree<T>` 用长子-兄弟表示统一表达一棵树和一片森林，提供：

- `add_root(v)`：向森林添一棵只含根的新树；先添的树排在前面；
- `add_child(parent, child)`：按值找到 parent，把 child 挂为其孩子；孩子按调用次序排列；**找不到 parent 是编程错误，抛 `std::runtime_error`**；
- `preorder()`：返回先序序列——先访问根，再依次先序遍历每棵子树；森林逐棵进行。

为什么查找失败选择抛异常而不是返回错误码？因为"给一个不存在的人挂孩子"说明调用方的逻辑已经错了，这不是可预期的业务失败，继续执行只会制造更乱的结构。这与全教程"编程错误抛异常"的约定一致。

### 12.2.2 转换的二叉树表示 `BinTreeRep<T>`

转换不能跨示例依赖第 11 章的 `BinaryTree`，因此本章自带最小二叉树类型 `BinTreeRep<T>`：每个节点有 `left`、`right`，提供 `preorder()` 与全套 RAII。它只承担"转换目标"这一个角色。

- `to_binary_tree(forest)`：森林 → 二叉树；
- `from_binary_tree(bin)`：二叉树 → 森林。

### 12.2.3 加强版并查集 `UnionFind2`

第 06 章的 `UnionFind` 按大小合并且不压缩；本章 `UnionFind2` 的合同：

- `find(i)`：返回根，**并做路径压缩**；
- `unite(a, b)`：按秩合并，矮树挂高树；同秩时 b 侧挂到 a 侧、a 根秩加一；本就同集返回 false；
- `rank_of(i)`：根的秩（树高上界）；`depth_of(i)`：沿父指针到根的实际步数；
- `rank_sanity()`：全体秩不超过理论界；`count()`：等价类数。

## 12.3 设计与不变量

### 12.3.1 多叉树的三种经典表示

先看选择空间，理解为什么本章选第三种。

**（1）双亲表示法。** 每个节点只存"我爸爸是谁"（一个下标）。找父亲、判根都极快，数组即可；但"列出某人的全部孩子"必须扫遍全表，为孩子挂节点也不自然。适合"只往上溯源"的场景（如第 20 章 AOE 事件的某些计算）。

**（2）孩子表示法。** 每个节点挂一条自己的孩子链表，或开二维结构。列孩子直接、挂孩子方便；但找父亲要到处搜，且每个节点的链表头要额外管理。

**（3）长子-兄弟表示法。** 每个节点固定两条线索，把多叉树变成一棵"转了 45 度"的二叉树。孩子和兄弟都能顺链访问，节点结构统一、空间不随孩子数变化。代价是找父亲仍需搜索，且"第 k 个孩子"要沿兄弟链走 k 步。

孩子数不可预测、又要频繁处理子树时，第三种最均衡，也是本章的选择。

### 12.3.2 节点结构与核心不变量

节点只有三条内容：

```cpp
struct Node {
    T data;
    Node* first_child = nullptr;    // 第一个孩子，没有则空
    Node* next_sibling = nullptr;  // 右边的兄弟，没有则空
};
```

这个表示必须时刻维持两条不变量：

1. **孩子链不变量：** 任一节点的 `first_child` 出发，沿 `next_sibling` 走，恰好经过它的全部孩子一次，链尾为空——不多（不能混进别人的孩子）、不少、不打结（链上不能出现环）；
2. **兄弟平级不变量：** 同一条兄弟链上的节点互为兄弟、拥有同一个父亲；`next_sibling` 绝不跨越层级。

`add_child` 为什么把新孩子接到链**末端**而不是头部？两者都维持不变量，但"末端追加"使孩子次序严格等于调用次序——先添加的是"长子"，读先序、读转换结果时任何机器、任何运行次序下都得到同一序列。若采用头插，次序会依赖调用顺序的镜像，虽也确定，但与日常"长幼有序"的直觉相反，容易把断言写错。

### 12.3.3 一棵树与一片森林的统一

关键设计：**根节点也允许有 `next_sibling`，指向森林里下一棵树的根。**

```text
A ──→ F              根链：两棵树
│      │
B─→C─→D G─→...
    │
    E
```

`add_root` 就是在根链末端接一个新根；`preorder` 对根链逐棵树进行。于是类名虽叫 `Tree`，一个对象表达的实际是森林——单根是森林的特例。这避免了再维护一个"森林容器"类型，也让转换函数只有一种情形要处理。

### 12.3.4 森林 ↔ 二叉树：两条规则与正确性

转换规则只有两条，请记牢：

```text
节点 x 的左孩子  = x 的第一个孩子
节点 x 的右孩子  = x 右边的兄弟
```

实现是对这两条规则的逐节点直译：

```cpp
BNode* b = new BNode{n->data};
b->left  = convert(n->first_child);    // 左：长子
b->right = convert(n->next_sibling);  // 右：兄弟（含下一棵树的根）
```

第一行新建同值节点；第二、三行递归处理两条线索。注意根链上的第二棵树根 F 是从 A 的 `next_sibling` 进入、最终落在二叉树根 A 的**右子树**里——标准教材中"森林里第 i 棵树成为第 i−1 棵树根的右子树"正是这个机制，不需要额外规则。

为什么转换后**先序序列不变**？森林先序是"根 → 依次各子树"；二叉树先序是"根 → 左子树 → 右子树"。左子树恰好装着长子带队的全部孩子（对应"依次各子树"的展开），右子树装兄弟，而兄弟在森林先序中本就排在"自己的子树全部走完之后"——两种访问次序逐节点对应，故序列必然相同。这不是巧合，而是规则设计的目的。

### 12.3.5 逆转换与往返一致

逆转换把同一组映射反过来：

```cpp
n->first_child  = invert(b->left);    // 左还原成长子
n->next_sibling = invert(b->right);  // 右还原成兄弟
```

因为两种节点结构经这两条映射**一一对应**（每个二叉节点的左/右都唯一决定原节点的两条线索），先去再回必得到同构的森林。示例用断言验证往返后的先序与原森林完全一致——这同时是对"转换不丢信息"的机器核查。

实现层面的一个小安排：`from_binary_tree` 递归直接构造好整棵节点链，由 `Tree::adopt_root` 一次接管所有权，避免再调一遍 `add_root` 造成二次插入。

### 12.3.6 并查集：秩、按秩合并、路径压缩

**秩（rank）**是节点所在树高的**上界**，初始为 0。合并规则：

```cpp
if (rank_a < rank_b) std::swap(ra, rb);  // 永远让矮树挂高树
else if (rank_a == rank_b) ++rank_a;      // 同秩才长高
parent[rb] = ra;
```

逐块看：第一行保证被挂的是较矮一侧，于是接完之后树高不增加；只有第二行的同秩情形，根下多了一层等高子树，秩才需要加一。这维持了秩的不变量：**任何节点的秩永远不小于它真实子树的高度，且秩只在同秩合并时增长。**

路径压缩在 `find` 中完成：递归找到根后，回程把沿途节点的父指针**直接改成根**：

```cpp
if (parent[i] != i) parent[i] = find(parent[i]);
```

递归式的写法让"找根"和"改挂"在一次回程里同时发生。压缩会让真实高度变小，但**秩不回改**——秩从此只是一个宽松上界，这正是它叫 rank 而不叫 height 的原因。

## 12.4 复杂度推导

### 12.4.1 Tree 各操作

- `preorder`：每个节点访问一次，O(n)；
- `add_child`：要先按值查找 parent。查找最坏遍历全部节点（父亲在最后一个被检查处），O(n)；链上追加 O(孩子数) 最坏 O(n)，合计 O(n)；
- `add_root`：根链追加 O(树的棵数)，最坏 O(n)。

若把"找到 parent 之后的节点位置"直接交给调用方（例如返回节点句柄），挂孩子可降到 O(1)；本章选择按值查找是为了接口简单、教学聚焦。

### 12.4.2 转换

去与回都恰好每个节点处理一次、建一个新节点，时间与空间均 O(n)。

### 12.4.3 并查集

- 只按秩、不压缩：每棵树高 O(log n)（秩为 r 的根至少挂 2ʳ 个节点——秩每加一必是同秩合并、节点数至少翻倍），故单次 O(log n)；
- 再叠加路径压缩：m 次操作总代价 O(m·α(n))，α 是增长极慢的逆 Ackermann 函数，实际 n 下 α(n) ≤ 4，**单次视为均摊常数**；
- `rank_sanity` 的形式化界：最大秩 ≤ ⌊log₂n⌋（示例按计划用 +1 的宽松界断言）。

证明秩界用的就是"秩 r 至少 2ʳ 节点"：总共 n 个节点，2ʳ ≤ n，即 r ≤ log₂n。这也是 1000 次混合操作后机器核查的内容。

## 12.5 完整示例输出

```text
森林先序：['A', 'B', 'C', 'E', 'D', 'F', 'G']
对应二叉树先序：['A', 'B', 'C', 'E', 'D', 'F', 'G']（与森林先序一致）
二叉树转回森林先序：['A', 'B', 'C', 'E', 'D', 'F', 'G']（往返一致）
向不存在的节点挂孩子：抛异常
按秩合并：三次合并后最大秩为 2（秩全程单调）
路径压缩：节点 5 的深度 2 → 1（直接挂根）
1000 次混合操作：秩界 sanity 通过；路径压缩后深度均 ≤ 1
自检通过
```

逐行解释：

- 前 3 行：手工构造的两棵树（A 树带 B/C/D、C 带 E；F 带 G）先序为 A B C E D F G；转换后、往返后序列三次相同，验证 12.3.4–12.3.5 的结论；
- 第 4 行：错误 parent 被异常拦下，合同中的"编程错误抛异常"成立；
- 第 5 行：秩按 0 → 1（0 与 1 合并）→ 1（吸收另一棵秩 1 树时不马上长高）→ 2（同秩合并）增长，且每步不回落；
- 第 6 行：节点 5 原本 5→4→0 两层，压缩后直挂根——路径压缩的可观察证据；
- 第 7 行：1000 次确定性操作后秩界成立；全体 find 一遍后没有深度超过 1 的节点，说明压缩确实把所有人拉到了根身边。

## 12.6 与标准库的对照

C++ 标准库**没有**通用的多叉树或森林容器：`std::map`/`std::set` 的红黑树是平衡二叉搜索树，不表达任意多叉层级；表达层级关系通常直接手写节点（结构体加 `std::vector` 孩子），或用第三方库。因此本章的 `Tree` 不是"重复标准库"，而是填补空白。

并查集同样没有 std 设施——它是算法竞赛与图算法（Kruskal、连通分量）里的基础工具，一律手写。对照来看，标准库提供的 `std::vector` 是实现双亲表示的自然底座（下标即节点号），本章代码也大量以 vector 承载秩与父指针。

学习建议：工程中若只需表达"包含关系"的层级（如 UI 控件树、JSON、AST），最常见的现代写法其实是"节点内含 `std::vector<Node*>` 孩子 + 一个 parent 反向指针"，即孩子表示的变体；长子-兄弟表示更常见于教材与内存紧张的场合。理解三者的等价与取舍，比记住某一种写法更重要。

## 12.7 本章坑位

- **坑 1：兄弟链接错层级。** 现象：把叔叔挂成了侄子的兄弟。原因：`next_sibling` 跨越了不同父亲的链。后果：孩子链不变量被破坏，先序遍历序列错乱、析构可能重复释放。防法：所有兄弟链接都从同一父亲的孩子操作里产生。
- **坑 2：孩子链头插导致次序与直觉相反。** 现象：先添加的孩子反而排在最后。原因：每次新孩子顶到链首。后果：断言按"长幼"书写时全错。防法：统一末端追加，次序=调用次序。
- **坑 3：根节点忘了也能有兄弟。** 现象：类型里单独维护"森林 vector"，转换时要处理树、森林两种情形。原因：没有利用"根链即森林"的统一表示。后果：代码两套路径、容易漏情形。防法：根的 next_sibling 直接挂下一棵树的根。
- **坑 4：路径压缩后回改秩。** 现象：压缩时把秩也调小。原因：把秩当成了真实树高。后果：后续按秩合并依据失真，复杂度保证失效。防法：秩只在同秩合并时增长、永不回落。
- **坑 5：递归 find 栈深度担忧之外的真实问题——循环。** 现象：压缩过程中形成父指针环。原因：合并或压缩时把祖先挂到了后代下。后果：find 无限递归崩溃。防法：合并只在两根之间进行、方向按秩固定；压缩只指向当前根。
- **坑 6：转换只转一棵树、漏掉根链。** 现象：森林转二叉树后只剩第一棵树。原因：右映射没有覆盖根的 next_sibling。后果：信息丢失、往返序列变短。防法：转换对任意节点无差别地处理两条线索。
