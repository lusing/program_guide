# 01 · 绪论：为什么需要数据结构

## 1.1 动机与直觉：从一张成绩单说起

想象你负责管理一个班级的成绩单。一开始只有十名学生，你把分数随手写在纸上：`87, 59, 73, 91, 66, ……`。查找某个学生的分数？从头扫到尾，十个数，一眼的事。

后来班级扩大到一万人，再后来你负责全省的考试。同一张"分数清单"开始出现各种新需求：

- **快速找到**分数最高的人——总不能每次都从头扫一万个数；
- **插入**一个新转来的学生，并保持分数从高到低的排列；
- **删除**退学学生的记录；
- 回答"**排在第 314 名的是谁**"；
- 统计"**有多少人及格了**"。

你会很快发现：**数据怎么摆放，决定了这些事情好不好做。** 如果分数天然有序，找最高分伸手就来；如果数据存在一条首尾相接的"链子"上，插入一个人也许只需要动两个接头，却无法立刻说出"第 314 名是谁"。如果除了分数清单，你还维护一张按学号排序的"位置对照表"，任意学号都能一跳定位，但每次录入成绩就得同时维护两处。

这不是编程技巧问题，而是**组织方式**问题。数据结构这门课，研究的就是这件事：**数据元素之间是什么关系，这些关系在计算机里如何存放，以及在这样的存放方式上能高效地做哪些操作。**

本章不写任何数据结构代码。本章要交付的是一套贯穿全教程的词汇表和思维框架：逻辑结构、存储结构、ADT、算法——后面 27 章的所有讨论都用这套语言展开。

## 1.2 三个基本术语：数据、数据元素、数据结构

先给三个逐层递进的术语。

- **数据（data）**：所有能被计算机处理的符号。数字、文字、图片、声音，归根到底都是数据。
- **数据元素（data element）**：数据的基本单位。一个学生的一条记录、一个单词、一个坐标点，都是一个数据元素。元素内部还可以再细分（学生记录里有学号、姓名、分数，这些更小的组成部分叫数据项），但在讨论"元素之间的关系"时，我们把它当作一个整体。
- **数据结构（data structure）**：**相互之间存在一种或多种特定关系的数据元素的集合。** 关键词是"关系"——一堆彼此无关的数不构成结构，"从高到低排好的一串分数"才是结构。

注意这个定义里完全没有提到代码或数组。数据结构首先是一个**逻辑层面**的概念，它描述"数据在我们头脑里长什么样"，而不是"它在内存的哪个字节上"。把这两个层面分开，是学好本课的第一道门。

用一个例子体会"元素"与"数据项"的层次：在全省考生库中，**数据**是整库考生信息，**数据元素**是单个考生的一条记录（它是排序、查找、删除的单位），记录内部的准考证号、姓名、单科分数则是**数据项**。为什么要强调这个区分？因为结构关系挂在元素之间——"按总分排序"移动的是整条记录而不是某个分数；而查找目标往往落在某个数据项上（按键找记录）。后面讲散列和搜索树时，"关键字（key）"这个概念就是从数据项里挑出来、用于标识元素的那一项。

## 1.3 ADT 合同（一）：逻辑结构的四种形状

抛开计算机，单看数据元素之间的关系，常见的有四类。阅读时请在脑中为每一类形成一幅图，并记住"一对几"这个数量特征。

**（1）集合结构。** 元素之间"同属一个集体"，此外别无关系。一个装着不同颜色小球的袋子就是集合——你只关心"红球在不在袋子里"，球和球之间没有先后、没有层级。数学上的集合还要求元素互不重复。数量特征：**零对零**（没有结构性的相邻关系）。

**（2）线性结构。** 元素排成**一条线**：除了第一个，每个元素有唯一的"前驱"；除了最后一个，每个元素有唯一的"后继"。排队等车的人群、英文字母表 `A, B, C, …, Z`、一本书的目录条目，都是线性结构。数量特征是**一对一**：一个元素只和前后各一个元素相邻。

**（3）树形结构。** 元素之间**分层**，像家谱或公司组织架构：一个上级可以管多个下级，但每个下级（除了最高领导）只有一个直接上级。数量特征是**一对多**。树里没有环：从任何一个下级往上溯源，路径唯一。

**（4）图形结构（网状结构）。** 元素之间的关系**不受任何限制**：任意两个元素都可以相连，一个元素可以同时和很多个元素相邻，允许出现环路。城市之间的公路网、社交网络里的好友关系，都是图。数量特征是**多对多**。

这四类是层层放宽的：线性结构是树的特例（每个节点至多一个孩子时），树是图的特例（连通且无环时）。选择结构时先问"我的数据关系属于哪一类"，后续的一切实现都由这个判断派生。

我们不妨把这份分类看作全教程的第一份"合同"：拿到任何问题，先在合同里对号入座——成绩单是线性的，组织架构是树形的，地铁线路是图形的。分类错了，后面的选型全盘皆错。

## 1.4 ADT 合同（二）：操作与抽象数据类型

结构是为操作服务的。光有形状还不够，还要说清"能在上面做什么"。一个数据结构通常提供一组**操作（运算）**，最常见的有：

- **创建**（构造）一个空结构；**销毁**（析构）一个结构并归还资源；
- 判断**是否为空**；求元素**个数**（长度）；
- **插入**新元素；**删除**指定元素；
- **查找 / 访问**某个元素；
- **遍历**：按某种次序访问每个元素恰好一次；**更新**某个元素的值。

注意"插入"这个看似简单的操作，在不同结构上含义和代价完全不同：在线性表中间插入，顺序存储要搬开后面所有元素；链接存储只需改两个指针；在集合里插入首先要判断元素是否已存在。**讨论任何操作时都要结合具体的存储结构。**

写程序时常犯的错误是一上来就纠结"用数组还是指针"。更成熟的思路是**合同先行**。

**数据类型（data type）** = 一个值的集合 + 允许在这些值上做的一组操作。整数就是一种数据类型：值的集合是数学上的整数（在机器范围内），操作是加减乘除、比较等。你用整数时并不需要知道它在 CPU 里由哪些晶体管表示，只需知道操作规则。

**抽象数据类型（Abstract Data Type, ADT）** 把这个思想推进一步：**定义"有哪些操作、每个操作做什么"，但完全不规定操作怎么实现、数据怎么存储。** "抽象"就是"抽离实现细节"。

比如"栈"的 ADT 只规定：可以**压入**一个元素、可以**弹出**最后压入的元素、可以看**栈顶**；弹出次序是"后进先出"。至于栈内部用数组还是链表，ADT 一概不管。任何遵守这份合同的实现，调用方都可以互换使用。

ADT 思维的三个收益，后面每一章都会兑现：

1. **降低思维负担。** 使用结构时只需理解合同，不必记住几十行内部实现。
2. **隔离变化。** 将来换更快的内部实现，只要合同不变，调用方一行代码都不用改。
3. **便于论证正确性。** 只要证明"实现遵守合同"，就能确信所有使用方的行为正确。

在 C++ 中，ADT 合同通常用**类**表达：公开的成员函数就是操作，私有内部状态就是被藏起来的实现细节。本教程每个结构都会先给 ADT 合同（操作语义、参数、出错行为），再给实现。

用文字写一份最小合同，体会合同要细到什么程度。以"栈"为例：

- **push(x)**：事后条件——栈顶元素为 x，元素总数加一，其余元素次序不变；
- **pop()**：前提——栈非空，否则属于编程错误、实现应抛异常；事后条件——移除当前栈顶；
- **top()**：前提同上；返回栈顶但不移除；
- **empty() / size()**：无前提，随时可调用，不改变状态。

注意"前提 / 事后条件"这种写法：它把出错行为（空栈 pop 怎么办）也写进合同，调用方和实现方对此不再有任何猜测空间。本教程每个 ADT 都按这个粒度描述。

## 1.5 设计与不变量：四种存储结构

计算机内存本身是**一条线性的地址序列**：从地址 0 开始，一个字节挨一个字节排下去。那么"树""图"这种非线性关系，怎么塞进一条线性内存？

办法是：**存下元素的同时，额外存一些"关系信息"。** 根据关系信息的形式，有四种基本存储结构。每种存储都有一条贯穿一生的**不变量（invariant）**——实现必须始终维持的内部约定；先建立"不变量"这个概念，后面读任何容器代码都要抓住它。

**（1）顺序存储。** 利用内存的连续性表达线性关系：逻辑相邻的元素物理上也相邻。关系**不靠任何额外数据**。不变量是：第 k 个元素的地址永远等于"首地址 + k × 元素大小"。数组就是顺序存储。

优点：定位第 k 个元素一步到位；缺点：插入、删除要搬动后面所有元素，且需要一整块连续内存。

**（2）链接存储。** 每个元素存成一个**节点**，除数据外还放一个或多个**指针**——"我的下一个节点在地址 X"。节点可以散落各处，关系全靠指针。不变量是：从首节点出发，沿指针走恰好能经过每个节点一次、最后以空指针收尾。

优点：插入删除只改指针、不搬数据；缺点：找第 k 个元素只能沿指针一步步走，且每个节点要额外占指针空间。

**（3）索引存储。** 存数据的同时另建一张**索引表**：每项记录"某个元素（或某段数据）在什么位置"，像书末的术语索引。不变量是：索引表每一项都准确指向一个真实数据；数据一移动，索引必须同步更新。

优点：数据本身可以乱序存放，靠索引快速定位；缺点：索引表额外占空间，数据变动时要维护索引。

**（4）散列存储（哈希存储）。** 设计一个**散列函数**，由元素关键字直接算出存放位置。不变量是：对任一在表元素，用它的键再过一遍散列函数，必定走到它当前所在的位置。

优点：查找、插入、删除平均常数时间；缺点：函数设计不好会"撞车"（两键算到同一位置），需要专门办法处理，且不擅长顺序与范围遍历。

**关键认识：逻辑结构和存储结构是两个独立维度。** 同一个逻辑结构（如线性表），可以用任何一种存储实现，得到不同性能。不存在"最好的"存储，只有"最契合访问模式的"存储。本教程接下来的每一章，几乎都在反复做这道选择题。

## 1.6 复杂度预览：用"步数"而不是"秒数"思考

先埋下一章的伏笔。比较两种存储的优劣时，"我电脑上跑了 2 毫秒"这种说法毫无用处——换台电脑就变。可迁移的说法是**操作步数**：

- 顺序存储访问第 k 个元素：**1 步**（地址算好直接走过去）；
- 链接存储访问第 k 个元素：**k 步**（从表头一节节走）；
- 顺序存储在长度 n 的表中间插入：平均要搬动约 **n/2 个元素**；
- 链接存储在已知位置插入：**改 2 个指针**，与 n 无关。

当 n 从十变成一万，"n/2 步"从五变成五千，"2 步"永远是 2。数据结构决定**步数随 n 增长的方式**，这才是性能的本质。第 02 章会把这种说法形式化成大 O 记号。

## 1.7 算法：让骨架动起来

存储结构回答"数据怎么放"，**算法（algorithm）**回答"事情按什么步骤做"。算法是对特定问题求解步骤的描述，是**有限**指令的序列。合格算法必须满足五条特性：

- **有穷性**：有限步骤后必须结束（"一直转圈"不是算法）；
- **确定性**：每步含义明确、无歧义，相同输入得到相同结果；
- **可行性**：每一步都能由基本操作有限次完成；
- **输入**：零个或多个；**输出**：一个或多个——没有输出的算法没有意义。

"数据结构"与"算法"是一体两面：结构是静态骨架，算法让骨架动起来；同一算法在不同存储上效率可能相差成千上万倍。

**本教程的代码约定（先读一遍，后续不重复解释）：**

- 统一标准：**C++23**。手搓代码全部位于 `namespace ds`；头文件与主程序同目录，`#include "x.hpp"` 引号包含。
- 资源管理采用 **RAII**：对象构造时获取资源、析构时归还；拷贝、移动语义齐全，不写裸 `new`/`delete` 散落的代码。
- 接口现代风格：能用 `std::span` 不退化指针、能用 `std::string_view` 不收 `const char*`；失败处用标准异常或 `std::expected`/`std::optional`，并在正文说明选型理由。
- 示例程序每个都带自检：用断言验证全部行为，最后打印"自检通过"。输出全部是固定值，可逐字节复现。

## 1.9 完整示例输出

示例程序用固定数据做了一件事：把同一份线性表 `{3, 1, 4, 1, 5}` 分别用**顺序存储**（数组）和**链接存储**（五个节点，用指针串起）各存放一遍，然后断言两种表示逐项相等：

```text
逻辑结构四类：集合、线性、树形、图形
存储结构四类：顺序、链接、索引、散列
同一线性表的两种存储：逐项一致（共 5 个元素）
自检通过
```

逐行看输出说明了什么：

- 前两行复述本章核心分类：逻辑上四种形状、物理上四种落地方式；
- 第三行是真正的验证结论：**逻辑内容相同，但存储形态不同**——这正是 1.5 节"两个独立维度"的可运行证据。示例内部还断言链表走完最后一个节点后指针为空（链子恰好 5 节，不多不少），即链接存储的不变量成立。

示例代码故意极简，因为它只承担"证明概念成立"的辅助职责；本章主体知识全在上面的文字里。

## 1.10 与标准库的对照

C++ 标准模板库（STL）是 ADT 思想的工业级实现。后面会逐一见到：

- `std::vector`：线性表的**顺序存储**实现（动态数组）；
- `std::list` / `std::forward_list`：线性表的**链接存储**实现（双向 / 单向链表）；
- `std::map`：用平衡二叉搜索树（树形结构）实现的有序字典；
- `std::unordered_map`：用**散列存储**实现的字典；
- `std::stack` / `std::queue`：栈和队列的适配器。

本教程坚持**先亲手实现每个结构，再对照标准库**：只会调用 `map::insert` 而不知道树如何旋转，这门课等于没学；亲手实现之后，才能真正判断"什么场景该选哪个"。

### 逻辑/存储两维速查

把 1.3 与 1.5 节压成一张速查表，以后每章都会用到这种"双维描述"：

| 逻辑结构 | 可选存储 | 典型访问模式 |
|---|---|---|
| 集合 | 顺序 / 散列 / 索引 | 成员判定 |
| 线性 | 顺序 / 链接 / 索引 / 散列 | 按位访问、插入删除 |
| 树形 | 链接（最自然）/ 顺序（数组化） | 层级访问、遍历 |
| 图形 | 邻接矩阵（顺序）/ 邻接表（链接） | 遍历、路径计算 |

注意最后一行的两个名字：**邻接矩阵**是把图压进二维顺序存储，**邻接表**是给每个顶点挂一条链接表。同一幅公路图，两种存储下"两城是否直通""某城有哪些邻居"的步数完全不同——第 19 章会精确量化。

## 1.11 本章坑位

- **坑 1：混淆逻辑结构和存储结构。** 现象：说"链表是一种逻辑结构"。原因：链表是链接存储的线性表，"线性"才是逻辑结构，"链"是存储方式。后果：讨论性能时层次错位——"插入快不快"只对具体存储结构才有答案。
- **坑 2：把 ADT 和实现绑死。** 现象：注释把"栈"描述成"一个数组加一个栈顶下标"。原因：那只是栈的其中一种实现。后果：换实现牵动所有调用方，也无法用合同检查实现正确性。
- **坑 3：只背定义、不学选型。** 现象：四种结构背得熟，面对新问题不会选。原因：脱离了"数据要支持哪些操作、各操作多频繁"的背景，分类只是死知识。后果：工程中选错容器，性能差几个数量级而不自知。
- **坑 4：忽视不变量。** 现象：读容器代码只盯单个函数，说不清"对象在任何一刻必须满足什么"。原因：没有建立不变量意识。后果：改一个操作悄悄破坏内部约定，bug 在很久以后才以离奇方式爆发。从下一章起，读每个结构都先问"它的不变量是什么"。
