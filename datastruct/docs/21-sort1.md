# 21 · 排序（上）：五种基础排序与"有序"的代价

## 21.1 动机与直觉：为什么排序是计算机的第一基本功

打开手机通讯录，联系人按拼音排列；查快递，物流记录按时间排列；考试结束，成绩单按分数排列。**有序的数据才有快速查找的可能**——这正是第 17 章搜索树、第 16 章哈希之外，排序本身成为独立主题的原因。有人统计过，商用计算机上约有四分之一的处理器时间花在排序上。排序之所以这么重要，不是因为"排好序"这个结果多漂亮，而是因为后续几乎一切操作（查找、去重、合并、求中位数、统计频次）在有序序列上都能换一个量级。

排序算法特别适合用来学习"同一个问题的多种解法"：目标完全一致（把序列排成非降序），但不同算法对数据形状的假设、对交换与比较的取舍截然不同。本章五种基础算法各有生活直觉：

- **插入排序**像理一手扑克牌：每摸一张新牌，从右向左在已理好的牌中找到位置插入；
- **折半插入排序**同样是理牌，但找位置时不一张张看，而是直接对半翻、快速定位（然而腾位置还是得一张张挪）；
- **冒泡排序**像水中气泡：每轮从头到尾两两比较，大的不断和邻居交换，一轮结束最大的沉到末端；
- **选择排序**像排队挑矮个：每轮扫一遍所有人，把最矮的直接拽到队首；
- **快速排序**像分组站队：选一个标杆，比他小的站左边、大的站右边，然后两边各自如法炮制。

读完本章你会发现：前四种算法思路朴素、代码很短，却都逃不开 O(n²) 的代价；快速排序用"一次划分、递归两段"的突破，把平均代价压到 O(n log n)，也成为绝大多数工业级排序的内核。

还有一个视角值得先建立：本章五种算法都属于**比较排序**——元素之间唯一被使用的信息是"谁大谁小"。第 22 章的基数排序、桶排序跳出了这个框架，直接利用整数的位结构与分布，因此能突破比较排序 O(n log n) 的理论下界。学两章时把这条分界线记在心里：下界不是"更快的技巧"能打破的，只能靠换信息来源。

顺带说明为什么这个下界成立：对 n 个互不相同的元素，可能的输入排列有 n! 种，而一次比较只有两种结果，一棵比较判定树至少要有 n! 个叶子才能区分所有排列；树高至少为 log₂(n!) ≈ n log₂n（由斯特林公式）。任何只靠两两比较的排序，最坏情况下都逃不开这个高度。这不是算法不够聪明，而是信息论意义上的硬限制——记住"比较结果只有比特、排列数却是阶乘的"，O(n log n) 下界就从公式变成了直觉。

另外，初学者常问"既然标准库一行 `std::sort` 就够了，为什么还要学五种写法"。答案有三层：其一，这些算法是理解复杂度分析最好的载体——同一个目标、五个形状的递推式，训练的是给成本记账的能力；其二，工业排序本身就是这些基础算法的组合（21.8 节会看到 std::sort 正是快排+堆排+插入）；其三，受限场景（小内存嵌入式、只允许顺序扫描的流式数据、写一个数据库归并引擎）需要你按约束重新拼装，而拼装的零件就是本章五种算法。

## 21.2 ADT 合同：到底什么叫"排好序"

给定 n 个元素的序列，排序的**后置条件**有两条，缺一不可：

1. **有序性**：对所有 0 ≤ i < n−1，都有 a[i] ≤ a[i+1]（本章以非降序为例）；
2. **排列性**：结果序列恰好是原序列元素的一个排列——不多、不少、不篡改。

第二条容易被忽略：一个把所有元素直接清零的算法也满足"有序"，但它不是排序。排列性意味着排序只能靠**比较和交换（或移动）**完成，元素本身的值得以保留。工业验证时通常的做法就是本章 main.cpp 的做法：把算法结果与 `std::sort` 的参照结果做整表相等断言——整表相等同时涵盖了两条后置条件。

再补两个合同层面的术语。**内部排序与外部排序**：数据全部在内存中处理叫内部排序，本章属于此类；数据量大到必须借助外存、分段载入再归并，叫外部排序，第 22 章用一个模拟实现展示其形态。**比较器**：非降序不是唯一选择，把"小于"抽象成一个可替换的比较器（严格弱序），同一份代码就能排降序、按结构体字段排；本章的插入与冒泡以模板比较器实现，其余三种先固定整数升序以便讲解。无论怎么排，比较器都必须满足严格弱序——用 `<=` 这种非严格关系作比较器，等价关系与传递性都会混乱。

**稳定性（stability）**是排序合同中的第三个关键概念：如果两个元素的关键字相等，排序后它们的相对次序保持不变，就称排序是稳定的。稳定性为什么重要？考虑先按成绩、再按姓名排序的多关键字需求：如果按成绩排序时算法稳定，那么成绩相同的人天然保持着姓名次序，一次排序的成果不会被下一次毁掉。排序链表记录、保持录入先后等场景同样依赖稳定性。注意：**不稳定不是"错误"**，它只是算法的属性；选择时要知道自己是否赔得起这个属性。

## 21.3 设计与不变量（一）：插入排序

插入排序的外层循环维持一条清晰的不变量：**第 i 轮开始前，a[0..i−1] 已经是初始前 i 个元素的有序排列。** 第 i 轮要做的，就是把 a[i] 取出，从右向左扫描已排序段，把比它大的元素逐个右移一格，直到找到不大于它的位置，放入。

以序列 `{3,1,4,1,5}` 手工跟踪（`·` 表示当轮已排序段边界）：

```text
初始      [ 3 · 1, 4, 1, 5 ]
i=1, x=1：3 右移，插入    [ 1, 3 · 4, 1, 5 ]
i=2, x=4：4 已在正确位置  [ 1, 3, 4 · 1, 5 ]
i=3, x=1：4、3 依次右移   [ 1, 1, 3, 4 · 5 ]
i=4, x=5：5 已在正确位置  [ 1, 1, 3, 4, 5 · ]
```

两个实现细节决定了算法的品质。其一，内层循环条件必须是**严格的"当前元素 < 扫描元素"**：遇到相等元素就停下，新元素插在相等元素后面，原次序不变——这就是插入排序稳定性的来源。若误写成 `<=`，相等元素也会被右移，稳定性立刻被破坏。其二，移动用 move 而非拷贝（对 int 无差别，但对字符串等重元素是真实的性能取舍）。

插入排序还有一个"表里不一"的优点值得专门点出：尽管渐近上是 O(n²)，它的内层循环体只有一次比较、一次移动，没有函数调用、没有除法取模、访问的是紧挨着的相邻内存，现代 CPU 的分支预测与缓存对它极其友好。因此在 n 很小时，它实际比快排还要快——O(n²) 与 O(n log n) 的差距在 n=16 时只差四倍，而常数差距足以反转优劣。理解这一点，才能理解为什么所有工业排序都在"递归到小段"时切换到插入排序：渐近复杂度决定大方向，常数决定小范围，二者缺一不可。

插入排序的精确成本还可以用一个优雅的量来刻画：**逆序数（inversion count）**，即序列中满足 i<j 且 a[i]>a[j] 的数对个数。每次内层移动恰好消去一个逆序对，所以插入排序的移动总次数严格等于输入的逆序数。完全有序时逆序数为 0（最好 O(n)），逆序时逆序数为 n(n−1)/2（最坏 O(n²)）。这也解释了"基本有序"为何是插入排序的甜蜜区：它的成本随逆序数线性增长，而非随 n 平方增长。冒泡排序的交换次数同样等于逆序数——每次相邻交换恰好消去一个逆序。

### 折半插入：比较与移动是两笔账

插入排序每轮做的事情可以拆成两笔开销：**找到位置**（比较）和**腾出位置**（移动）。朴素插入排序里两笔都沿线性扫描发生，各 O(n)。折半插入排序在已排序段中改用二分查找定位，每轮比较降到 O(log n)；但找到位置后，右侧元素仍要整体右移一格，移动还是 O(n)。

所以折半插入的总时间仍是 O(n²)——它优化的是比较次数，在"比较昂贵、移动便宜"的场景（比如按远程查询或复杂键比较）才有意义。实现里另一个易错点是二分的口径：必须用 `lower_bound` 口径（找第一个不小于当前值的位置），相等元素插在所有相等元素之后，稳定才能保住；若用 `upper_bound` 口径，就会插到相等元素前面。

### 链表上的插入排序：不需要"腾位置"

第 05 章讲过单链表。在链表上做插入排序，两笔账的形态发生了有趣的反转：找位置仍需从头扫描（链表不支持随机访问，折半查找无从用起），但**移动元素从"逐个右移一格"变成了一次摘链重挂**——只要常数时间。因此链表插入排序在 n 较大时比数组插入排序"感觉"更快，尽管渐近复杂度同为 O(n²)，常数完全不同。反过来，这也解释了折半插入为什么只属于数组：二分查找的每一步都依赖 O(1) 随机访问，链表只能放弃。读工程代码时，"移动昂贵还是比较昂贵、访问是顺序还是随机"这两个问题，往往比背复杂度表更能决定选型。

最后用一句话收束插入排序家族：**它优化的不是算法的形状，而是"已排序段"这一不变量的兑现方式。** 朴素版本线性地比较并移动；折半版本把比较换成对数、移动照旧；链表版本把移动降为常数、比较退回线性。同一个不变量、三笔不同的账。这种"先抓住不变量，再替换其中一个成本项"的思维方式，在后续章节（第 22 章的各种改进排序、工程中的排序选型）中会反复出现，比记住任何单一实现都更有用。

## 21.4 设计与不变量（二）：冒泡与选择

冒泡排序每轮从头到尾扫描相邻元素，**次序反了就交换**。不变量是：第 k 轮结束后，末尾 k 个元素已是全局最大的 k 个、且按非降序就位——最大的元素在第一轮就通过连续交换一路"冒"到末尾。以 `{3,1,4,1,5}` 为例，第一轮相邻比较的交换点是 3↔1；4 与后续 1 交换一次；5 始终最大不动，轮末 5 就位。之后每轮的扫描范围缩短一格。

冒泡有一个其他 O(n²) 算法没有的优点：**如果某一整轮没有发生任何交换，说明所有相邻对都已有序，整个序列必然有序，可以立即结束。** 因此对"已经有序"的输入，带提前结束标志的冒泡排序只要 O(n)。代价是每轮多维护一个布尔标志——但漏掉这个标志（坑 1）就会把最好情况也拖回 O(n²)。

选择排序每轮只做一件事：在未排序段中扫描出最小值的位置，然后与段首交换一次。不变量：第 i 轮后 a[0..i−1] 是全局最小的 i 个元素。它的交换次数是所有排序中最少的（至多 n−1 次），所以在"交换成本极高"的场景（如按物理位置换磁盘块）反而有用。但注意交换发生在相距很远的两个位置，这个远距离交换会越过中间的相等元素——**选择排序因此不稳定**。

### 同一序列上的对照轨迹

仍以 `{3,1,4,1,5}` 为例，把冒泡（每轮末就位者用 ■ 标出）与选择（每轮 min 的位置与交换）并排对照：

```text
冒泡：
  轮1 交换 3↔1、4↔1，末位 5 就位：[ 1, 3, 1, 4, ■5 ]
  轮2 交换 3↔1，末两位 4、5 就位：[ 1, 1, 3, ■4, ■5 ]
  轮3 无交换 → 实际提前结束（已全部有序）

选择：
  轮1 扫描发现 min=1（位置1），交换 3↔1：[ 1, 3, 4, 1, 5 ]
  轮2 段 [3,4,1,5] 的 min=1（位置3），交换 3↔1：[ 1, 1, 4, 3, 5 ]
  轮3 段 [4,3,5] 的 min=3（位置3），交换 4↔3：[ 1, 1, 3, 4, 5 ]
```

两条轨迹透露了对比的要点：冒泡的交换是**密集而相邻**的（逆序对有多少就交换多少次），但相等元素永远不会被交换；选择的交换是**稀少而遥远**的（每轮至多一次），可这一跳往往越过相等元素——观察轮 2，位置 1 的 3 被换到位置 3，若它后面还跟过一个相等的 3，相对次序就会被打乱。同一个 O(n²)，两种算法把成本花在了完全不同的地方。

这两种朴素算法在真实系统里留下的痕迹比想象中多，下面两个例子来自硬件与查询优化两个相距很远的领域。冒泡排序的相邻交换模式是 GPU 与并行排序网络中"奇偶归约"的雏形：把奇位对、偶位对的比较交替执行多轮，没有数据依赖、可以全部并行——在数千个核心同时工作时，O(n²) 的"工作量"乘以并行度反而胜出。选择排序"每轮只选出一个极端值"的思想则活在每一个 top-k 问题里：真的需要完整有序吗？若只要最小的 k 个，堆选择或 nth_element 才是对的工具。学经典结构时值得多问一句：它的哪一条不变量在我手头的问题里仍然值钱。

## 21.5 设计与不变量（三）：快速排序

快速排序的核心动作是**划分（partition）**：在段中选一个枢轴（pivot），把段重排为"小于枢轴的元素 ｜ 枢轴 ｜ 不小于枢轴的元素"，于是枢轴一步到达它在最终有序序列中的正确位置；左右两段是相互独立的同类子问题，递归处理即可，单元素段天然有序。递归结构像一棵二叉树：划分是节点，递归是子树。

本章实现取**段正中位置**的元素作枢轴（交换到段尾后用 Lomuto 方案扫描），关键不变量是划分返回位置 p 满足 a[lo..p−1] < 枢轴 ≤ a[p+1..hi]。在输出示例的固定数组 `{5,-2,8,0,3}` 上，划分轨迹如下：

```text
{5,-2,8,0,3}：中点枢轴 8 换至段尾 → {5,-2,3,0,8}
  全部元素 <8，枢轴就位 p=4；递归左段 {5,-2,3,0}
{5,-2,3,0}：中点枢轴 -2 换至段尾 → {5,0,3,-2}
  无元素 < -2，p=0；递归右段 {0,3,5}
{0,3,5}：中点枢轴 3 换至段尾 → {0,5,3}
  0<3 留在左侧，交换后 p=1；右段 {5} 为基线
结果 {-2,0,3,5,8}
```

为什么取中段而不是首元素作枢轴？因为**真实数据中"已经有序"或"基本有序"极其常见**（增量插入、归并片段都是如此）。若恒取首元素，对有序输入划分会变成"左边空、右边 n−1 个"，递归树退化成一条链，时间从 O(n log n) 暴跌到 O(n²)——这就是坑 3。取中段后，有序输入的每次划分恰好对半，是最理想的情形。工业实现（如 std::sort 的内省排序）还会进一步用三取中、以及在递归过深时切换堆排序来兜底，第 22 章会对照。

快速排序在划分中交换了相距很远的元素（枢轴可能与任何位置交换），相等元素的相对次序无法保证，因此不稳定。

补充一个划分方案层面的细节。本章使用 Lomuto 方案（枢轴先换到段尾，单指针扫一遍），优点是代码短、不变量好讲；它的弱点是当段中存在大量与枢轴相等的元素时，这些相等元素全部被归入右段，划分可能明显失衡。另一种经典方案是 Hoare 划分：双指针分别从两端向中间扫描，左指针找不小于枢轴者、右指针找不大于枢轴者，相遇前不断交换。Hoare 方案交换次数更少，且相等元素有机会分布在两侧；工业实现往往还会把相等元素专门聚到中间（三路划分：小于、等于、大于），在"数据取值只有少数几种"的场景（如按枚举字段排序）这是关键优化。读到库源码里的双指针对撞，不要困惑，骨架仍是本节的同一条思想：一次扫描完成分组、两侧成为独立子问题。

## 21.6 复杂度推导

比较排序的成本按**比较次数与交换（移动）次数**记账。插入排序最坏情况下，第 i 轮最多比较、移动 i 次，总和为 1+2+…+(n−1) = n(n−1)/2 = **O(n²)**；输入已升序时每轮只比较一次就停下，为 **O(n)**。冒泡同理，最好 O(n)、最坏 O(n²)。选择排序无论输入形状如何，每轮都必须扫完整个未排序段才能确认最小值，**最好最坏平均都是 O(n²)**，但交换至多 n−1 次。折半插入每轮比较 O(log n)、移动 O(n)，总比较 O(n log n)、总移动仍 O(n²)。

快速排序的时间取决于划分均衡度。若每次把 n 个元素分成两段 k 与 n−1−k，递推 T(n) = T(k) + T(n−1−k) + O(n)。对半划分（k≈n/2）时递归树有 log₂n 层、每层总工作量 O(n)，得 **O(n log n)**；极端不均衡（k=0）时递推退化为 T(n)=T(n−1)+O(n)，得 **O(n²)**。随机排列输入下，期望划分接近均衡，平均为 O(n log n)，且常数很小、缓存行为好，这是它"实践中最快"的依据。

平均复杂度的推导直觉值得走一遍：在随机排列中，枢轴最终落在任意一个名次上的概率都是 1/n；落在中段（比如名次介于 n/4 与 3n/4 之间）的概率是 1/2，此时两段都不超过 3n/4，子问题以常数速率缩小；连续 O(log n) 次"足够好的划分"就能把问题降到基线大小，而获得这么多次合格划分所需的期望尝试次数只有 O(log n) 级（失败的尝试也只把问题推给稍大的子段，成本计入期望）。于是期望递归深度 O(log n)、每层 O(n)，平均 O(n log n)。本章实现虽不随机选枢轴，但固定取中段在"输入排列任意"的假设下具有相同的均衡性质；若数据可能被对手构造，工业实践会退而随机化或直接依赖 std::sort 的堆排序兜底。

空间上，快速排序除了在原数组上交换，只使用递归栈。若按坑 8 的"先递归较短段、另一段循环"写法，栈深可严格控制在 O(log n)——因为每次真正压栈的递归调用面对的段至多是当前段的一半。朴素两段都递归时最坏栈深 O(n)，这是实现时容易被忽视的一笔账。

| 算法 | 最好 | 平均 | 最坏 | 额外空间 | 稳定 |
|---|---|---|---|---|---|
| 插入排序 | O(n) | O(n²) | O(n²) | O(1) | 是 |
| 折半插入排序 | O(n log n)（比较） | O(n²)（移动主导） | O(n²) | O(1) | 是 |
| 冒泡排序 | O(n) | O(n²) | O(n²) | O(1) | 是 |
| 选择排序 | O(n²) | O(n²) | O(n²) | O(1) | 否 |
| 快速排序 | O(n log n) | O(n log n) | O(n²) | O(log n)（递归栈） | 否 |

五种算法全部**原地**工作（除快排递归栈外不开辅助数组），这也是它们与第 22 章归并排序的显著区别。

### 那么，到底该怎么选

下面的建议都以"本章五种 + 标准库"为范围；第 22 章学完归并、希尔、基数之后，这张选型清单还会再扩充一次。

把这张表翻译成可操作的选型建议：数据量很小（经验上 n < 几十），**插入排序**几乎总是最优选择——代码最短、常数最小、还稳定，这正是 std::sort 在递归末端切到插入排序的原因；数据已基本有序（每个元素离最终位置不远），插入排序同样占优，它的成本近似正比于"逆序程度"；通用场景、数据形状未知，**快速排序**（或直接用 std::sort）是默认答案；交换本身代价极高的特殊硬件场景才考虑**选择排序**；冒泡排序在工程代码中极少出现，但它的"相邻比较、无交换即停"思想在检测"序列是否几乎有序"、网络协议的相邻条目整理中仍有变体。一句话：**先问数据长什么样，再问自己要不要稳定性，最后才轮到查表选算法。**

为什么示例要把每个算法都和 `std::sort` 而不是某个手算结果比对？因为手算结果本身可能出错（本系列其他章节就出现过计划里的期望值笔误），而标准库参照提供了独立的第二来源；整表相等一旦断言通过，有序性、排列性同时成立。把参照源选得比被测代码更可信，是自检设计的通用原则。

逐行解释。第 1–6 行：主夹具含负数、重复值与无序排列，五种算法各自的结果与标准库参照整表相等——有序性与排列性两条后置条件同时被验证。第 7 行：三类边界夹具覆盖了递归/循环的入口基线——空段与单元素段本就有序，全相等元素检验的是"严格比较"写法是否正确（若误写 `<=` 驱动移动，这类夹具行为仍"看起来对"，所以边界夹具不能替代稳定性演示）。

第 8–13 行是稳定性的直接证据：元素是 `(key, 初始编号)`，比较器只看 key。初始时两个 key=1 的元素编号为 1、2；插入与冒泡之后 `(1,1)` 仍在 `(1,2)` 之前，且打印次序与输入编号一致——相等元素没有被交换。末段快速排序的小数组结果与 21.5 节手工轨迹完全吻合。

这组输出还示范了"演示"与"断言"的分工。稳定性结论同时被硬断言（结果整表等于 stable_expected）与打印展示覆盖：断言保证它不会在将来重构时悄悄回退，打印让人无需读代码就能看见现象。而选择排序的不稳定性只在正文中说明、没有在输出中"演示不稳定"——因为不稳定算法在相等元素较少时表现仍可能恰好稳定，刻意构造的反例写进自检反而会把"语言属性"和"特定输入行为"混为一谈。判断哪些性质适合写成回归、哪些只适合讲清楚，本身也是教程设计的一部分。

## 21.8 与标准库的对照

- **`std::sort`**：工业级通用排序，主流实现是**内省排序（introsort）**——以快速排序为主，递归深度超过阈值时切换成堆排序以杜绝 O(n²) 最坏情况，小段再用插入排序收尾。这正是本章五种算法的"集大成者"：快排的平均速度、堆排序的最坏界、插入排序在小段上的低常数。第 22 章给出完整对照。
- **`std::stable_sort`**：保证稳定的排序，实现基于归并排序，额外需要 O(n) 缓冲（缓冲不足时退化到 O(n log² n)）。需要稳定性（本章演示的场景）时用它。
- **`std::is_sorted` / `std::is_sorted_until`**：直接检查有序性后置条件；写自校验时比手写循环更直白。
- **`std::partition`**：快速排序划分步骤的独立工具，按谓词把元素分两组；`std::nth_element` 则是"只要第 k 小元素就位"的弱化版快排，求中位数时应优先想到它。
- 一个常见疑问：标准库为什么不提供"插入排序""冒泡排序"的命名设施？因为在 std::sort 的混合策略里，它们只是内部分发的实现细节，调用方需要表达的是**意图**（排序、稳定排序、部分排序、按第 k 位划分），而不是算法。把接口按"要什么保证"而非"用什么技巧"设计，是标准库留给使用者的接口哲学。
- C++20 起以上算法都有 `std::ranges::` 版本，可直接传整个容器且支持投影（projection），例如 `std::ranges::sort(v, {}, &Employee::score)` 即按成员排序。

最后提醒一个标准库与教学实现的行为差异：标准库算法把"比较器必须是严格弱序、迭代器必须有效"等前提的责任全部交给调用方，违反前提是未定义行为——标准库不会抛异常、也不会帮你检查。本章的教学实现同样信任前提，但把精力集中在算法本身；在边界处（空段、单元素）则用显式分支让行为确定。写生产代码时，入口处的前提校验和算法内部的简洁应当分开处理。

## 21.9 本章坑位

阅读以下八条时，建议对照每条的"防法"在自己的代码里找一遍：

- 比较方向是否处处严格；
- 递归入口是否排除了枢轴；
- 空段与单元素是否在入口处理。

- **坑 1：冒泡漏掉"无交换"提前结束标志。** 现象：对已排序输入仍跑满 n−1 轮。原因：省略了 swapped 标志或在每轮开始时忘记复位。后果：最好情况从 O(n) 退回 O(n²)，且不易察觉（结果照样正确）。防法：每轮局部声明标志，轮末检查。
- **坑 2：选择排序的不稳定交换。** 现象：`(5,0),(5,1),(2,2)` 排序后两个 5 的编号次序反转。原因：第一轮 min 选中位置 2 的 2，与位置 0 远距离交换，越过了相等的 5。后果：多关键字排序的前序成果被毁。防法：需要稳定时改用插入/冒泡或 std::stable_sort，不要试图"修补"选择排序。
- **坑 3：快排恒取首元素作枢轴。** 现象：对已排序或基本有序的输入运行时间暴涨、递归链拉长。原因：有序输入下首元素就是最小值，划分恒为 0 与 n−1，递推 T(n)=T(n−1)+O(n)。后果：O(n²) 时间甚至栈溢出。防法：取中段或三取中；工业实现再叠加深递归切换堆排序。
- **坑 4：折半插入的下界 off-by-one。** 现象：定位偏差一格，元素被插到错误位置。原因：二分循环边界与 `lo/hi` 更新口径不统一（半开区间混用闭区间）。后果：结果失去有序性或破坏稳定性。防法：固定半开区间 [lo, hi) 与 lower_bound 口径，循环条件严格用 lo < hi。
- **坑 5：相等元素参与移动/交换，破坏稳定。** 现象：插入排序对相等 key 元素次序反转。原因：内层条件误写成 `current <= a[j]`，或冒泡用 `>=` 判定交换。后果：算法静默地变得不稳定。防法：驱动移动的比较一律用严格小于；用 pair 稳定性演示做回归。
- **坑 6：忘记空 span 与单元素基线。** 现象：空表时内层访问 a[0] 越界，或快速排序无 size 守卫直接算中点。原因：循环/递归只考虑了 n≥2。后果：在空容器（真实程序中常见）上崩溃。防法：入口显式处理 size < 2；让边界夹具进入常规构建。
- **坑 7：Lomuto 划分后递归段包含枢轴。** 现象：快速排序无法收敛、段长不见缩小。原因：递归调用写成 (lo, p) 与 (p, hi)，枢轴被重复处理。后果：理论上无限递归、实际栈溢出。防法：严格按 (lo, p−1) 与 (p+1, hi)。
- **坑 8：两段递归的栈深度没有"先小后大"。** 现象：即使平均划分均衡，深层递归时栈占用仍可能偏大。原因：先递归左段、再递归右段，两段的栈帧在最坏划分下叠加；编译器无法保证尾递归优化。后果：极端输入上栈空间紧张。防法：每次先递归较短的一段，另一段改写为循环（保证栈深 O(log n)）；工业实现多采用此写法。
