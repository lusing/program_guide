# 11 · 二叉树：每个节点至多两个孩子

## 11.1 动机与直觉：从"家谱为什么画不成一条线"说起

前几章处理的都是线性结构：元素排成一条线，一个元素至多一个前驱、一个后继。但现实中有大量信息天然不是一条线。想想你的家谱：你父母各自又有父母，祖父祖母是平辈的两个人——从任何一个人向上追溯，关系立刻"分叉"成两支；公司组织图中一个经理管着三个组长；一份文档的目录下有多个小节，小节下又有多个条目。这些结构的共同特征是**分层 + 分叉**。

用一条链表硬画这种关系会非常别扭：你只能规定"下一个人是谁"，无法表达"同一个人下面有两支平级的分支"，更无法表达"这两支分支在结构上地位对称"。我们需要一种新的形状。

**二叉树（binary tree）**是树形结构中最规整、也最重要的一种：每个节点**至多有两个孩子**，而且两个孩子**左右有别**——左孩子和右孩子是两个不同的位置，交换它们得到不同的二叉树。

为什么偏偏先学"至多两个"而不是直接学任意多个孩子的树？三个原因：

1. **足够表达一般树。** 任意多叉树都能用二叉树等价表示（第 12 章的"长子-兄弟"表示）；
2. **分支固定，算法简单。** 两个位置可以直接写进节点结构，遍历只需"根、左、右"三个动作的排列；
3. **众多高效结构以它为骨架。** 搜索树、堆、哈夫曼树都是二叉树或它的近亲。

学完本章应能回答：二叉树凭什么由"前序+中序"两个序列唯一确定；四种遍历各自动作为什么只有次序之别；非递归后序遍历为什么要给栈节点加一个标记。

## 11.2 ADT 合同：一棵"只观察、不修改"的二叉树

本章的 `BinaryTree<T>` 刻意做成**不可变**的：树只能通过重建工厂一次成型，之后只提供观察操作。这让资源管理集中在"拷贝/移动/析构"三件事上，也符合树形数据"重建多于局部修补"的真实用法。

**构造合同：**

- `from_pre_in(pre, in)`：由前序序列 `pre` 与中序序列 `in` 重建整棵树。前提——两段等长、元素互不重复、确实来自同一棵二叉树；长度不符抛 `invalid_argument`，前序首元素在中序中找不到同样抛异常。

**遍历合同：**

- `preorder()`：前序，按"**根 → 左子树 → 右子树**"输出；
- `inorder()`：中序，按"**左子树 → 根 → 右子树**"输出；
- `postorder()`：后序，按"**左子树 → 右子树 → 根**"输出；
- `postorder_iter()`：后序的非递归实现，输出必须与 `postorder()` 逐元素相等；
- `levelorder()`：层序，从根所在层开始，自上而下、同层自左向右输出。

**观察合同：** `size()`（节点总数）、`height()`（高度，空树为 0，单节点为 1）、`leaves()`（叶子数：左右孩子皆空的节点）。

**值语义合同：** 拷贝得到一棵结构相同但完全独立的新树（深拷贝）；移动把节点所有权转交，源对象变为空树；析构释放全部节点。任何情况下都不允许泄漏或重复释放。

合同还隐含一个事实：遍历的输出次序只由树结构决定，与树是如何构造的无关——同一棵树无论重建多少次，五种遍历结果逐字节相同。这使得遍历输出可以当作树的"指纹"：两棵树若任意一种遍历不同，则树必不同。

合同里值得注意的细节：**左右有别**。三个节点（根 + 左孩子）与（根 + 右孩子）是两棵不同的二叉树，尽管它们的节点集合相同。这也是为什么"中序+另一个序列"能唯一确定一棵树——中序同时编码了左右位置信息。

## 11.3 设计与不变量

### 11.3.1 节点结构：数据 + 两个位置

```cpp
struct Node {
    T data;
    Node* left;
    Node* right;   // 没有对应孩子时为 nullptr
};
```

整棵树对象只持有一个 `root_` 指针——根是进入全树的唯一入口。**空指针就是"这个位置没有孩子"的显式标记**，它让递归可以统一处理"节点"与"空位"：任何递归函数走到 `nullptr` 就触底返回，不必为"差一个孩子"的情况单写分支。

### 11.3.2 三条结构不变量

任何一刻，树都必须满足：

1. 从 `root_` 出发，沿任意 left/right 路径走到的每个节点都是构造时创建的真实节点，无悬空指针；
2. **无环**——沿指针走不会回到任何祖先；每个节点至多被一个父节点引用；
3. 每个节点的 left、right 要么为空，要么指向一个独立子树，两棵子树互不相交。

重建算法的每一步 `new Node{值, 左子树, 右子树}` 都在维持这三条：两个孩子都由不相交的区间独立递归建成，根区间比父区间严格更小，所以不可能指回祖先。

### 11.3.3 前序 + 中序为什么能唯一重建

用本章数据手工走一遍。已知：

```text
前序：A B D E C F G
中序：D B E A F C G
```

第 1 步，**前序首元素必是根**（前序先访问根），故根为 A。
第 2 步，在中序中找到 A：它左边的 `D B E` 全在**左子树**，右边的 `F C G` 全在**右子树**。
第 3 步，按切出的长度切前序的剩余部分：左子树拿到 `B D E`（前序中紧随根的 3 个），右子树拿到 `C F G`。
第 4 步，对每段重复上述过程。左段：前序首元素 B 是根，中序 `D B E` 中 D 在左、E 在右。右段：根为 C，中序 `F C G` 给出左 F、右 G。

得到的结构是：

```text
            A
          /   \\
         B     C
        / \\   / \\
       D  E  F  G
```

**为什么必须要中序？** 因为只有中序能用"根在序列中的位置"同时告诉你左右两边各有什么；单凭前序，你知道根是谁，却不知道后面的序列在哪里切成左右两半。递归的切口（根在中序中的下标）就是全部信息。

实现中对应的关键一小块是——在中序中定位根，按位置长度同时切两个序列：

```cpp
const size_t left_n = static_cast<size_t>(root_pos - in.begin());
Node* left  = build(pre.subspan(1, left_n), in.first(left_n));
Node* right = build(pre.subspan(1 + left_n), in.subspan(left_n + 1));
```

`left_n` 一个数字同时决定了四件事：前序左段长度、前序右段起点、中序左段、中序右段起点。下标在这里极易错位，防御办法是让空区间递归直接返回 `nullptr`——无论切出的是 0 个还是多个元素都走同一条路径。

### 11.3.4 四种遍历：三个动作的排列

递归遍历只有三个动作：**处理根（记为 V）、递归左（L）、递归右（R）**。前序 VLR、中序 LVR、后序 LRV——名字中的"前/中/后"就是根相对于子树的位置。以节点 B 为例：前序在进入 B 的子树时先输出 B；中序要先走完左子树 D 才输出 B；后序则等 D、E 都输出后才最后输出 B。

层序遍历换了一种机制，用**队列**：根入队；每次出队一个节点就输出它，并把它的左孩子、右孩子依次入队。队列的 FIFO 性质保证浅层节点总排在深层节点之前。这是"队列把抽象次序变成具体输出"的典型例子。

### 11.3.5 后序的非递归实现：为什么需要标记

递归后序简短，但要改写成循环，难点是：**节点第一次出现在栈顶时还不能输出**——两个孩子没处理；必须等左右子树都输出后，第二次回到该节点才能输出。于是栈中存的不是裸节点，而是 `(节点, 是否已处理)`：

```cpp
if (!processed) {
    stack.emplace_back(n, true);        // 标记 true 压回，排在孩子之后
    if (n->right) stack.emplace_back(n->right, false);
    if (n->left)  stack.emplace_back(n->left, false);
} else {
    out.push_back(n->data);             // 第二次相遇：孩子已全部输出
}
```

注意压栈次序是**先右后左**——栈后进先出，要让左子树先处理就得把它最后压入。这是"递归 → 显式栈"转换的通用配方：栈帧记录"走到哪一步了"，本质上是在手工模拟编译器对递归函数生成的调用栈（第 03 章的调用栈模型）。

### 11.3.6 size / height / leaves：递归定义直接变程序

三个观察量都有自然的递归定义，与程序一一对应：

- 节点数 = `1 + 左子树节点数 + 右子树节点数`；
- 高度 = `1 + max(左高, 右高)`，空树高度 0；
- 叶子数：空树 0；左右皆空者计 1；否则为两子树叶子之和。

这里 `1 +` 不可省略：高度数的是"路径上的节点数"，单节点树高度为 1 而非 0。

### 11.3.7 满二叉树与完全二叉树：两种规整形状

有两种"形状规整"的二叉树值得专门命名，后面都会用到。

**满二叉树（完美二叉树）**：每一层的节点数都达到该层最大值——深度为 h 时节点总数 `2⁰ + 2¹ + … + 2ʰ⁻¹ = 2ʰ − 1`，叶子全在最底层（恰 2ʰ⁻¹ 个），不存在"只有一个孩子"的节点。本章示例重建出的正是这种形状：高 3、节点 7、叶 4，三个数字满足 `2³−1 = 7`。

**完全二叉树**：除最后一层外全部填满，最后一层节点从左到右连续排列、中间不留空位。满二叉树是完全二叉树的特例。完全二叉树有一个极其重要的性质：**它能无歧义地存进一个数组**——按层序把节点依次放入下标 0,1,2,…，则下标 i 的节点左孩子在 `2i+1`、右孩子在 `2i+2`、父节点在 `(i−1)/2`，完全不需要指针。第 13 章的二叉堆就是利用这一性质，用一维数组表达了一棵树。

直觉上，这两种树都是"尽量不浪费层空间"的形状：正因为每个位置要么被占要么在最底层靠右留空，树高对 n 个节点取到最小值 ⌈log₂(n+1)⌉。**给定点数时树高能压多低**，是后面所有平衡结构的核心关切。

## 11.4 复杂度推导

设节点数为 n、树高为 h。

- **四种遍历**：每个节点恰好被访问一次（递归版）或入栈/入队常数次（非递归版），时间均为 **O(n)**。
- **重建**：每个节点递归一次，但每层都要在中序区间中 `find` 根——线性查找，每段长度之和在最坏（斜树）时为 `n + (n-1) + … = O(n²)`；若事先用哈希表记录"值→中序下标"，可降到 **O(n)**（元素需可哈希）。本章采用朴素实现，因为它只依赖相等比较，且概念最直接。
- **size/height/leaves**：同样每个节点访问一次，O(n)。
- **空间**：递归遍历的辅助空间是调用栈深度，即树高 **O(h)**（斜树时退化为 O(n)，平衡时为 O(log n)）；层序遍历最坏队列长度是树的最宽层，对完美二叉树约 n/2，即 O(n)。重建的递归栈同理为 O(h)。

重建复杂度还有一个细节值得记住：`find` 查找的总成本等于各递归层中序区间长度之和；对平衡形状每层总长都是 n、共 log n 层，故平衡时重建仅为 O(n log n)，只有斜树才取到 O(n²)。

一个重要推论：**同样的 O(n) 时间，在不同形状的树上空间差别巨大**。n=100 万的完美二叉树高仅约 20，递归绝对安全；而斜成一条链的二叉树高 100 万，递归必栈溢出。树的"形状"因此和树的"节点数"同等重要——后续平衡树（第 17 章）存在的全部理由就是把 h 压回 O(log n)。

## 11.5 完整示例输出

示例先由前序、中序重建 7 节点树并逐项验证，再检查拷贝与移动语义：

```text
重建成功：前序 ABDECFG，中序 DBEAFCG
后序（递归/非递归一致）：DEBFGCA
层序 ABCDEFG；节点 7，高度 3，叶子 4
拷贝赋值后副本为 XY，原件仍为 ABDECFG（互不影响）
移动后：新对象节点 7，源对象节点 0
自检通过
```

逐行解释说明了什么：

- 第 1 行：重建合同成立——两种遍历精确等于输入序列，证明根的切分与左右归属正确；
- 第 2 行：递归后序与 `postorder_iter()` 输出一致（断言逐元素相等），说明 11.3.5 的标记栈确实机械地模拟了递归；
- 第 3 行：层序按深度输出 ABCDEFG；高度 3（根→B→D 三层）；**叶子为 4 而非 3**——重建结果是完美二叉树，叶子恰是最底层的 D、E、F、G 四个。（计划原稿写的"叶子 3"是计数错误，已据实际重建结构订正为 4。）
- 第 4 行：深拷贝独立——副本被改赋成一棵全新的 XY 小树，原件仍完整；
- 第 5 行：移动只转交指针、不复制节点，源对象因此为空且无泄漏。

## 11.6 与标准库的对照

C++ 标准库**没有公开的二叉树容器**：`std::map` / `std::set` 内部确实是红黑树（二叉搜索树的一种），但树节点结构、遍历、旋转全部被藏在实现内部，对外只暴露有序键值合同。标准库的态度是"你只需要键的有序性，不需要看见树"。

但这正是本课要亲手实现的原因：树的重建、遍历、高度形态是后面一切结构的共同语言。标准库中与本章遍历思想直接对应的设施有：

- 有序容器的双向迭代器——其 `operator++` 内部走的正是"中序后继"（二叉树中序序列的下一个节点），只是迭代器代码替你处理了"右子树最左下 / 向上找祖先"两种情况；
- `std::queue`——层序遍历的机制与队列 ADT 完全相同；
- `std::span`——重建实现用它传递不占有所有权的序列片段，切片（`subspan`/`first`）天然对应"子区间"。

亲手写完再用 `std::map`，你会清楚它承诺的 O(log n) 操作次数建立在"树保持平衡、高为 log n"这条没写进接口的内部事实之上。

## 11.7 本章坑位

- **坑 1：重建时切错序列。** 现象：抛异常或结构错位。原因：前序右段起点、中序切段只要有一处没用同一个 `left_n` 就整体错位。后果：重建出另一棵树甚至悬空。防法：让"左段长度"一个变量决定全部四个端点，并对空区间统一返回空指针。
- **坑 2：非递归后序忘记标记。** 现象：节点在孩子之前被输出。原因：节点首次出栈时孩子还没处理。后果：次序与递归版不符。防法：栈存 `(节点, processed)`，先右后左压孩子。
- **坑 3：凭计数想当然。** 现象：断言"7 节点、高 3 的树叶子为 3"。原因：重建出的实际是完美二叉树，最底层 4 个节点全是叶子。后果：断言与真实结构矛盾。防法：叶子数从结构递归算，不凭节点总数猜。
- **坑 4：递归析构漏掉一棵子树。** 现象：内存泄漏（或反过来先删父节点导致子指针悬空）。原因：析构必须先左右后根。后果：泄漏在教学程序里静默、在长期程序里累积。防法：析构复用统一的 `destroy` 递归，与后序同形。
- **坑 5：拷贝浅复制根指针。** 现象：两棵树析构同一批节点。原因：默认拷贝只复制 `root_` 地址。后果：重复释放崩溃。防法：显式深拷贝；不需要共享时优先移动。
- **坑 6：忽视斜树的栈深。** 现象：对长链形二叉树递归遍历直接崩溃。原因：调用栈深达 O(n)。后果：数据稍大即栈溢出。防法：改用非递归遍历，或从源头使用平衡树。
