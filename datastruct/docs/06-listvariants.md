# 06 · 线性表的变种与应用

## 6.1 动机与直觉：基本结构解决不了的四种现实

第 04、05 章我们实现了"最正统"的线性表：动态数组与真实指针链表。但现实里有四类场景，让这两种正统形态都变得别扭。本章的四个变种，分别对应它们。

**场景一：没有指针可用时，怎么实现链表？** 链表的灵魂是"节点自带下一个节点的位置"。但有些语言（如传统 FORTRAN）没有指针；更重要的是，**磁盘文件上也没法写内存地址**——把链表存进文件再读回来，所有地址全部失效。既然"位置"的本质只是一个引用，那就不必非用地址：给每个节点编一个**整数编号**，节点里存"下一个节点的编号"，效果完全一样。这种结构叫静态链表，编号就是"模拟指针"。

**场景二：表里的每个元素又大又重。** 假设线性表中每个元素是一条包含几十字段的订单记录。直接在数组里排序，每次交换都要搬动整条记录，交换的实际代价是字段总数。可如果表里只放**订单所在位置的引用**，交换的就是两个引用而不是两坨数据。数据对象安安静静待在原地，被重排的只是"观看顺序"。这就是间接表。

值得一提的是，间接表与普通数组表并非互斥：工程中常见的形态是数据对象集中存放在一个拥有资源的主表中，其他各种视图（按时间排、按优先级排、按类别筛）全部是引用或下标的间接表。同一份数据、多个观看顺序，且任何一个顺序都不持有数据所有权——这一"一份数据、多副眼镜"的模式在 GUI 程序和数据库系统里随处可见。

**场景三：反复问"这两个东西算不算同一类"。** 编译原理里要判断两个变量是否可能指向同一个存储单元；社交产品里要判断两个用户是否已经连通；图像分割里要合并相邻的同质区域。这些操作的共同形态是：起初每个元素自成一类，然后不断收到"把这两类合并"的指令，并随时回答"它俩现在同不同类、这个类有多大"。并查集就是为这种"只合并、从不拆分"的等价关系量身定制的结构。

**场景四：绝大多数项都是零的多项式。** 手工做多项式加法时，我们不会写出 `0·x⁹ + 0·x⁸ + …`，只记录非零项。若一个 100 阶多项式只有 6 个非零系数，用长度 101 的数组存储就是浪费；把非零项按指数排成一张表，加法、乘法都只在非零项之间进行。这就是稀疏多项式的思想——它和第 10 章的稀疏矩阵是同一种智慧。

先用最小的手工例子感受场景四。计算 `(x + 1) + (x − 1)` 时，纸上的过程是：把两个多项式的项按指数对齐——

```text
       x 项：  1 + 1 = 2  →  保留 2x
常数项：  1 + (-1) = 0  →  划掉，什么也不写
```

若用稠密数组（下标即指数），常数项槽位会存着一个 0、每次运算照样带着它；稀疏表则直接让它"不存在"。这个差别在手工时只是少写一笔，在程序里则决定了存储与运算量。

四个变种看似分散，底层都在做同一件事：**改变"关系信息如何记录"，让结构贴合数据的真实形状。**

## 6.2 ADT 合同

### 静态链表 `StaticList<T, N>`

定长 N 个节点，整型下标作链接，`-1` 表示空。操作语义：

- `alloc_node(v)`：取一个空闲槽写入 v，返回槽号；无空槽返回 -1；
- `free_node(i)`：把槽 i 还回空闲池；
- `push_front(v)` / `pop_front()`：在表头插入 / 删除；
- `insert_after(i, v)` / `erase_after(i)`：在槽 i 之后插入 / 删除其后继；
- `head()`、`next(i)`、`value(i)`：结构浏览；空表 `pop_front` 属编程错误，抛异常。

合同里最关键的一条附加约定：**刚释放的槽排在空闲池最前端，因此"释放后立即再分配"必定取回同一槽号。** 这不是实现怪癖，而是槽位复用语义的明确承诺。

### 间接表 `IndirectList<T>`

- 构造：从一批元素构造，每个对象在内存中只存一份，表中持有它的引用；
- `sort()`：按对象值重排引用；
- `at(i)`、`pointer_at(i)`：看第 i 个槽当前引用哪个对象；
- `data_untouched()`：报告数据对象自构造以来是否既未被移动也未被改写。

### 并查集 `UnionFind`

- `UnionFind(n)`：n 个元素，起初 n 个独立集合；
- `find(i)`：返回 i 所在集合的代表元（根）；
- `unite(a,b)`：合并两个集合；本已同集返回 false；
- `size(i)`：i 所在集合的元素个数；`count()`：当前集合总数。

合同还规定：编号越界、空表 pop、空表删除等属调用方编程错误，实现抛标准异常；而"无空槽可分配"是容量耗尽的可预期情形，底层 `alloc_node` 用返回 -1 报告；便捷包装 `push_front` 作为该返回值的调用方，选择把它转成异常——同一种失败在底层与高层接口中可以有不同的表达方式。同一章里并存两种错误处理风格，是刻意示范：**破坏程序内部约定的用异常，正常业务可能遇到的用返回值。**

本章版并查集特意不做路径压缩（find 时把沿途节点直接挂到根下），这一加强将在第 12 章的 `union_find2` 中与按秩合并一起给出；眼下先看清"按大小合并"单独一项已经足以保证对数树高。

### 稀疏多项式 `Polynomial`

- 由若干 `Term{系数, 指数}` 构造，零系数项自动消失；
- `operator+`：按指数归并，同指数合并（合并为零的项消失）；
- `operator*`：项与项两两相乘后归并；
- `term_count()`、`term(i)`、`to_string()`：检查与展示。

## 6.3 设计与不变量

### 静态链表：空闲池与"槽即节点"

节点数组里每个槽有两种身份：在使用中（挂在以 `head_` 为起点的链上），或空闲（挂在以 `free_head_` 为起点的空闲链上）。**核心不变量：每个槽在任何时刻恰好属于两条链中的一条，两条链都以 -1 收尾。** 初始化时空闲链是 `0→1→…→N-1→-1`：

```cpp
for (std::size_t i = 0; i < N; ++i)
    nodes_[i].next = static_cast<int>(i + 1);
nodes_[N - 1].next = -1;
free_head_ = 0;
```

分配 = 从空闲链摘下头槽；释放 = 头插进空闲链。注意释放时必须先从使用链上摘下、再还池——顺序反了会让同一槽同时挂在两条链上，这正是"每槽恰属一链"不变量被破坏的典型事故。头插式释放还顺带给出了复用承诺：还回去的槽立即成为下一次分配的首选。

以 N = 4 的初始状态为例，数组内容（此时使用链为空）：

| 槽号 | 值 | next | 归属 |
|---|---|---|---|
| 0 | （默认） | 1 | 空闲链 |
| 1 | （默认） | 2 | 空闲链 |
| 2 | （默认） | 3 | 空闲链 |
| 3 | （默认） | -1 | 空闲链尾 |

`head_ = -1`（无使用节点），`free_head_ = 0`。此后每一次分配取走空闲链头、每一次释放把头槽还回——整张表就是在两个 head 指针之间搬运槽号，从不向操作系统申请或归还内存。这也是它被称为"静态"的原因：节点存储在整个生命期内静止不动。

### 间接表：排序的是引用数组

表内只有一个引用数组。排序时比较的是引用所指对象，交换的是引用本身：

```cpp
std::sort(pointers_.begin(), pointers_.end(),
          [](const T* a, const T* b) { return *a < *b; });
```

**不变量：引用所指对象的身份与内容在重排前后完全一致，变化的只有引用在数组中的位置。** 为了让这条不变量可检验，构造时为每个对象记录一份"住址 ↔ 初始身份"绑定；`data_untouched()` 逐个核对住址上的对象是否仍等于初始身份。对象从未被移动或改写，所以核对必然通过。

资源管理上必须守住另一条约定：**一个对象只能被一个表拥有**。深拷贝时必须新建一批对象（否则两个表析构时会重复释放同一块内存）；移动则只转交引用、源表清空。

示例中的排序可以手工跟踪：五个对象编号 0–4，键分别为 30、10、40、20、50。引用数组起初按编号排：

```text
排序前引用：→ 30#0  → 10#1  → 40#2  → 20#3  → 50#4
排序后引用：→ 10#1  → 20#3  → 30#0  → 40#2  → 50#4
```

两行里对象一个都没动（`#编号` 仍是那些对象，键值也没改），变的只是箭头的排列。这正是间接表名字的由来——**你操作的是"间接层"而不是数据本身。**

### 并查集：以树代表集合

每个集合是一棵倒挂的树，根的"父亲"是它自己；`find` 就是沿父亲指针走到根。合并时不做任何逐元素迁移，只需让一棵树根指向另一棵树根——O(1) 个链接动作。**不变量：同一集合内所有元素沿父亲链必走到同一根；根的集合大小恰为树下节点数。**

合并方向不是任意的：始终让小树挂在大树下。若放任大树挂到小树下，树可能退化成一条长链，`find` 退化为 O(n)。平局（两树等大）时约定 b 并入 a，使结果在任何机器、任何标准库实现下都一致。

把示例中的合并序列逐步推演一遍，父亲数组的状态如下（`[i]` 表示 i 的父亲）：

```text
起初：        [0]=0 [1]=1 [2]=2 [3]=3 [4]=4   （五个集合）
unite(0,1)： [1]=0，集合 {0,1} 大小 2
unite(2,3)： [3]=2，集合 {2,3} 大小 2
unite(1,3)： 两树等大，b 方根 2 挂到 a 方根 0 下：[2]=0
             根 0 的大小变为 4，集合 {0,1,2,3}
```

此后 `find(3)` 的行走路径是 `3→2→0`，正好体现"树高不超过 ⌊log₂n⌋+1"——4 个元素最多走 2 步。这也是 `find` 与数组下标的关键差别：它不保证一步到位，保证的是步数按对数增长。

### 稀疏多项式：降序、去零

**不变量：项永远按指数严格降序存放，每个指数至多一项，不存在零系数项。** 加法是一次典型的有序表归并扫描：谁的指数大先取谁；指数相等则系数相加——相加结果为零时该项自然丢弃。乘法先产生全部两两乘积，再按同样规则归并。把"排序 + 合并 + 去零"集中在一个整理步骤里，使两个运算都只需关心归并逻辑。

## 6.4 复杂度推导

- **静态链表**：插入、删除（已知槽位时）都是 O(1)；沿链访问第 k 个节点 O(k)，与真实指针链表相同。空间固定 O(N)。
- **间接表**：sort 的比较次数仍是排序的 O(n log n)，但每次交换的代价从"复制整个 T"降为"交换两个引用"；`data_untouched()` 是教学核对函数，O(n) 次对象比较。
- **并查集（本章快速版）**：unite 本身 O(树高)；按大小合并保证树高不超过 ⌊log₂n⌋+1，故 find 最坏 O(log n)。第 12 章加入路径压缩后，均摊成本会降到接近常数。
- **稀疏多项式**：设两个多项式分别有 m、k 个非零项。加法一次归并 O(m+k)；乘法产生 mk 个乘积再归并，O(mk·log(mk))（若按先排序归并的直接实现）。对比按稠密数组实现的 O(指数上界)，当非零项稀少时优势显著。

把数字代进去更直观：一个最高指数 10000、只有 20 个非零项的多项式，稠密存储要 10001 个槽，稀疏存储只要 20 项；两个这样的多项式相乘，稠密做法要扫描上亿次组合（绝大多数是零加零），稀疏做法只在 20×20 = 400 个真实乘积间归并。**稀疏性不是小优化，而是数量级的切换。**

## 6.5 完整示例输出

示例对四个变种各做了一组确定性验证：

```text
静态链表：释放槽号 0，再分配得到槽号 0（同一槽位复用）
  沿 next 遍历：[4, 1, 3]（头槽 2）
间接表：排序后指针所指对象编号序 [1, 3, 0, 2, 4]，键序 [10, 20, 30, 40, 50]
  数据对象本身未被搬动或改写：true
并查集：合并后根为 0，集合大小 4，等价类数 2
多项式：(x + 1) + (x - 1) = 2x
  （1项，恰为 2x）
多项式：(x + 1) * (x - 1) = x^2 - 1
  （2项，常数抵消后恰为 x^2 与 -1）
自检通过
```

逐行解释说明了什么：

- 第 1–2 行：槽位复用承诺被兑现——释放槽 0 后再分配取回 0；随后三次头插（3、1、4）沿链得到 `4,1,3`，说明模拟指针的链接行为与真实链表别无二致；输出里的"头槽 2"表示三次插入后头节点落在 2 号槽——槽号是节点的静态住址，插入只改变 next 指向、从不搬槽，这与动态链表"节点四散、头指针引用最新节点"形成有趣的镜像；
- 第 3–4 行：五个对象初始编号 `0,1,2,3,4`，按键排序后引用序变成 `1,3,0,2,4`（对应键 10,20,30,40,50），而对象本身未被触碰——重排的是观看顺序；
- 第 5 行：先两两合并成两个大小为 2 的集合，再合并为大小 4 的集合；根编号 0 来自平局规则（a 方根作根），等价类剩 2 个（4 号元素始终独立）；
- 顺带一提，此时对 3 号元素调用 find 的行走路径是 `3→2→0` 两步而不是一步——示例输出只打印根，但 6.3 节的父亲数组推演展示了完整路径，两步，未超过对数树高上界 ⌊log₂4⌋+1；
- 第 6–9 行：本章最生动的去零演示。`(x+1)+(x-1)` 中常数项 +1 与 -1 抵消，结果只有一项 `2x`；乘积展开后 `x²` 与 `-1` 两项，同样不保存任何零项。

最后把四条验证与 6.2 节的合同一一对应：槽位复用对应静态链表的附加约定，对象编号序与 `data_untouched` 对应间接表的两条不变量，根/大小/计数对应并查集的树不变量，项数与系数对应稀疏多项式的降序去零约定。**示例不是新内容，而是合同被逐条执行的回执。**

## 6.6 四个变种的共同模式

回头看，四个结构共享两条反复出现的设计原则，值得在进入栈、队列之前点明。

1. **显式记录关系，而不是依赖元素位置巧合。** 模拟指针的编号、间接表的引用、并查集的父亲指针、多项式里的指数，都是"关系信息"的不同载体。数组下标之所以能表达顺序，是因为相邻这一关系恰好被内存连续性免费提供；一旦这一巧合不适用，就要显式把关系存下来。
2. **让表示的成本与有效信息量成正比。** 稀疏多项式不存零项、间接表不复制对象、并查集不逐元素搬迁。它们都在拒绝为"不存在或不需要的东西"付费。这一原则在第 10 章稀疏矩阵、第 15 章压缩编码中还会两度回响。

此外，本章四个结构都再次印证了第 01 章的双维观点：它们仍是**线性逻辑结构**，改动的只是存储与关系记录方式。掌握一个 ADT 后换存储视角看它，是读后续章节的标准姿势。

## 6.7 与标准库的对照

- 标准库没有"静态链表"，但 `std::vector<std::pair<T,int>>` 加下标管理就是等价写法；需要把链接结构落盘或放进不支持指针的环境时，这一模式直接可用。
- 间接排序是标准实践：`std::vector<T*>` 或 `std::vector<std::size_t>`（下标版的间接表）配合自定义比较器即可；`std::ranges::sort` 的投影（projection）参数也能达到"按键排序、不挪对象"的类似效果——例如对一批记录按某个字段排序时，投影让比较发生在字段上，但要注意被交换的仍是记录本身；想要"对象完全不动"，还是得用引用/下标间接表。下标版间接表还有一个附加优点：编号不怕 vector 扩容，而裸引用会在容器重分配时失效。
- 并查集没有标准库组件（它不属于通用容器），但同类 disjoint-set 结构在第三方算法库中常见；自己实现只需十几行；
  需要在并行场景下做大规模合并时，还有按树高（秩）而非大小合并的变体，第 12 章会给出；
- 多项式无标准库对应；科学计算库中稀疏结构（sparse）是一个大家族，思想与本章完全一致：**只存非零项 + 显式索引**。

## 6.8 本章坑位

- **坑 1：释放顺序写反，节点同时挂两条链。** 现象：同一槽号被遍历两次，或空闲槽数对不上。原因：先 free 再从使用链摘除。后果：不变量被破坏，最终同一槽被分配给两个节点。防法：先摘链、后还池，并核对两条链槽数之和恒为 N。
- **坑 2：间接表共享对象导致双重释放。** 现象：拷贝出来的表析构时程序崩溃。原因：浅拷贝让两个表持有同一批对象。后果：未定义行为，常表现为偶发崩溃。防法：深拷贝新建对象；或只用移动语义转移所有权。
- **坑 3：并查集合并时大树挂小树。** 现象：数据量上来后 find 越来越慢。原因：没有按大小选根。后果：树退化成链，O(log n) 保证失效。防法：始终小树挂大树；平局规则写死。
- **坑 4：多项式忘记处理抵消。** 现象：加法结果里残留系数为 0 的项，或同指数出现两项。原因：只拼接不归并。后果：term_count 虚高，后续乘法项数异常膨胀。防法：所有运算出口统一经过"降序 + 合并 + 去零"的整理步骤。
- **坑 5：把模拟指针的编号当成真实地址做算术。** 现象：试图对槽号做指针运算或跨文件复用编号。原因：编号只在本数组内有意义。后果：结构错乱；跨文件时数组布局一变编号语义全失。防法：编号仅用于节点间引用，不参与运算，落盘时连同数组一起读写。
- **坑 6：浮点系数直接用 == 比较。** 现象：对经过多步运算的系数做严格相等断言，结果时灵时不灵。原因：浮点运算存在舍入误差。后果：测试在不同优化级别下翻转。防法：本章断言只用于 1.0、-1、2.0 这类由精确整数运算得到的结果；一般系数比较应使用容差。
