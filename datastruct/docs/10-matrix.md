# 10 · 多维数组与稀疏矩阵：给"表格"减负

## 10.1 动机与直觉：一张几乎空白的大表

先看一个具体场景。气象站在全省有 1000 个观测点，每天向中心报送四次数据，一年下来要存一张 `365 × 4000` 的表。这张表的绝大多数格子其实是空的——某观测点某天某时没报送，位置就留空。如果老老实实按行列开一块 `365 × 4000` 的内存，一百多万个位置里真正有值的也许只有几万个，其余全在替"零"交房租。

再换一个场景。线性代数里的对称矩阵（比如距离矩阵：北京到上海的距离恒等于上海到北京的距离），n×n 个格子里上三角和下三角完全重复，对角线之外的每一份数据都存了两遍。

这两个场景指向同一件事：**二维表是人类看数据的自然形式，但把"形"直接搬进内存，往往浪费巨大。** 本章研究如何把多维的、稀疏的、有特殊结构的表，压缩成高效的存储，同时让使用方仍然能像操作表格一样操作它。

在进入具体结构之前，先回答一个前置问题：多维数组本身是怎么放进一维内存的？

顺带一提本章四个结构的排列顺序，它体现了一条由浅入深的路线：先看"有规律的冗余"（对称矩阵，数学性质白送一半数据），再看"无规律的稀疏"（COO 三元组，冗余位置没有结构、只能逐个登记），接着处理稀疏带来的访问方向问题（十字链表），最后放宽表元素的类型约束（广义表）。前三个结构都还在"矩形"的框架内，第四个则把"矩形"打破，进入递归数据的世界。

## 10.2 ADT 合同：本章四个结构的承诺

本章交付四种结构，合同概览如下；每个操作的语义随后用小例子讲清。

| 结构 | 解决什么 | 关键合同 |
|---|---|---|
| `SymmetricMatrix` | 对称矩阵上下三角重复 | 只存 n(n+1)/2 个位置；`at(r,c)` 与 `at(c,r)` 恒同值 |
| `SparseMatrix` | 大部分元素为 0 | 只存非零三元组；提供转置、相加；结果自动剔除零项 |
| `CrossList` | 稀疏表要频繁按行、按列访问 | 每个非零节点同时挂在行链与列链上 |
| `GeneralList` | 表的元素本身也可以是表 | 支持嵌套；可求长度、深度，可展开成原子序列 |

合同统一的出错约定：下标越界（行列号不在合法范围）属于编程错误，一律抛 `std::out_of_range`；形状不匹配的矩阵相加抛 `std::invalid_argument`。这些异常会携带定位信息，让错误在离现场最近处暴露。

为避免后文符号来回切换，先固定本章记号：

- n：方阵的阶（行数与列数相等时）；
- rows、cols：一般矩阵的行数、列数；
- t：非零元素个数（t 远小于 rows×cols 时称矩阵稀疏）；
- r、c：访问位置的行号、列号，均从 0 起；
- Θ(…)、O(…)：沿用第 2 章的渐近记号。

## 10.3 设计与不变量

### 10.3.1 多维数组怎样落进一维内存：行主映射

内存只有一条线性地址序列。二维数组 `a[u1][u2]` 里，C++ 按**行主次序**摆放：先放第 0 行全部元素，再放第 1 行……于是下标 `[i][j]` 到一维位置的映射是：

```text
map(i, j) = i × u2 + j
```

为什么？走到第 i 行之前，前 i 行共占了 `i × u2` 个位置；再加上本行的第 j 个。用一个 3×6 的数组验证：`map(1,3) = 1×6+3 = 9`，`map(2,5) = 2×6+5 = 17`。

另一种摆法叫列主次序（Fortran 采用）：先放第 0 列再放第 1 列，映射为 `j × u1 + i`。两种映射都只是约定，关键认识是：**多维下标到一维地址，永远是"前面整行（列）+ 本行偏移"的算术。** 后面所有压缩结构的映射公式，都是这个思想的变体。

三维情形 `a[u1][u2][u3]` 的行主映射按同样逻辑展开：先数完整的二维片层，再数整行，再加列偏移：

```text
map(i, j, k) = i × u2 × u3 + j × u3 + k
```

模式很清楚：每多一个维度，就是在公式前面再乘一层"后面所有维度的跨度"。n 维情形是同一公式的递归堆叠，本质从未改变——这也解释了为什么编译器能在编译期把多维下标直接算成一条地址加法指令，维度本身不带来运行时开销。

### 10.3.2 对称矩阵：只存下三角

对称矩阵满足 `a[r][c] == a[c][r]`。我们只存下三角（`r >= c` 的部分，含对角线）。第 0 行存 1 个，第 1 行存 2 个……第 n−1 行存 n 个，总数：

```text
1 + 2 + … + n = n(n+1)/2
```

位置映射分两种情形：

```cpp
// r >= c：元素就在下三角，前 r 行共 r(r+1)/2 个，再偏移 c 列
槽号 = r(r+1)/2 + c
// r < c：元素在上三角，交给对称位置
槽号 = c(c+1)/2 + r
```

这个结构必须维持的不变量是：**`at(r,c)` 与 `at(c,r)` 解析出的槽号永远相同。** 代入公式即可验证——两个分支互为镜像。于是无论从哪个方向写入，另一方向读出来必然一致。示例向 `at(0,1)` 写 5.0，断言 `at(1,0)` 立即读出 5.0，验证的就是这条不变量。

对称矩阵只是"带状结构矩阵"家族里最常见的一员，顺便把同族的其他成员也认一遍，压缩思路完全相通：

- **三角矩阵**：上三角（或下三角）全为常数 c（通常为 0），只需存另一半，再额外存一个 c；
- **三对角矩阵**：非零元素只分布在主对角线及其上下各一条对角线上，共约 3n−2 个位置，映射为按"第几条对角线"分段；
- **对角矩阵**：只有主对角线非零，n 个位置。

它们的共同套路是：**找到"非零区域的形状"，按行清点形状内已有的元素数，把它做成槽号公式。** 一旦公式写成，访问就回到 O(1)。

边界情形也要在合同里讲清：n=0 是合法的空矩阵（零个位置），构造函数不报错；n 为负数才是构造错误。压缩矩阵不存"形状信息之外"的任何冗余，所以 n(n+1)/2 必须在构造时算准——这里用整数乘法，注意 n 很大时乘积可能溢出，工业实现应当用更宽的整数类型核算。

### 10.3.3 稀疏矩阵：三元组顺序表（COO）

稀疏矩阵只存非零元素，每个非零元素用一个三元组 `(行, 列, 值)` 表示，称为 COO（coordinate list）。光把零项剔除还不够，还要约定：**三元组恒按 `(行,列)` 字典序升序存放。** 为什么顺序如此重要？因为转置和加法都靠它。

**转置**把每个三元组变成 `(列,行,值)`、行列数互换。但直接换坐标会破坏顺序（按原行号有序 ≠ 按新行号有序），所以必须重新排序。

**加法**利用两份表都有序这一事实，做一次双路归并：两个游标各指一份表，位置小的先输出；位置相同则值相加。若和恰为零（比如 2 与 −2 抵消），该位置不存入结果——稀疏性不降反升。示例中两个矩阵相加后只剩 1 个三元组，值为 9。

需要注意的隐含合同：同一位置不允许出现两个三元组（构造时查重），值为 0 的三元组构造时直接剔除。

COO 并不是稀疏矩阵的唯一主流存法，工程上更常见的是 **CSR（compressed sparse row，压缩行）**：除了值数组与列号数组，再加一个"每行起点"数组——它记录第 i 行的元素从值数组的第几个位置开始。取一整行于是只需读两个行指针之间的切片，不必像 COO 那样扫表定位；矩阵向量乘法尤其受益。CSR 的代价与 COO 的弱点正好互补：插入新元素要搬动数组，不适合频繁增删。本章选 COO 是因为它把"有序 + 归并"讲得最直白，而转置与相加正是本章要训练的运算；理解了 COO 的顺序不变量，再看 CSR 只多一层行指针的预处理。

### 10.3.4 十字链表：同时服务"按行"与"按列"

COO 表有个弱点：想取某一行很快（顺序扫一段），想取某一列却要扫全表。十字链表让每个非零节点同时挂在**两条**有序链上：

- 行链：同一行的节点按列号向右，节点里存 `right`；
- 列链：同一列的节点按行号向下，节点里存 `down`；
- 每行、每列各有一个头（`row_head`、`col_head`）。

这样取一整行走行链，想定位某格沿行链比较列号，列方向同理——两个方向都是局部访问。

插入一个新节点时要在两条链上各找一次位置：沿行链走到"列号恰好夹住目标列"的前驱后插入，再沿列链对行号做同样操作。已存在的位置只更新值、不新增节点——这是 `node_count()` 保持准确的关键。本章实现用 arena（节点数组）加整数下标组织，不出现裸指针；节点下标在数组扩容后仍然有效。

反过来想删除：要删一个节点，同样要在行链与列链上各做一次摘除（让前驱越过它），再把 arena 里的槽位标记为空闲。这正暴露了 arena 的一个权衡——数组中间的节点删掉后留下空洞，若直接用 `vector::erase` 会让所有后继下标失效。简单做法是保留空洞（节点数略大于实际非零项数），讲究的做法是加一个空闲链表回收槽位。本章示例不做删除，把这条权衡留作思考题：**下标引用换来了拷贝安全与缓存友好，代价是删除不能就地压缩。**

### 10.3.5 广义表：表里装表

线性表的元素只能是原子；广义表放宽：**元素要么是原子，要么本身又是一个广义表。** 例如 `(a,(b,(c)),d)` 有三个顶层元素：原子 a、子表 `(b,(c))`、原子 d。

三个观察操作的语义：

- **长度**：顶层元素个数，上例为 3；
- **深度**：嵌套层数。约定原子深度为 0，表深度为 `1 + 各元素最大深度`；
- **展开（flatten）**：按书写顺序取出全部原子，上例得 `a, b, c, d`。

这些定义天然递归：求一个表的深度，就是先求各子表深度再取最大加一。实现上节点用一个整数标记区分原子与子表，子表关系用 arena 下标互引。

广义表还值得建立两个经典视角。其一是**表头与表尾**：非空表的表头是第一个顶层元素（可以是原子也可以是子表），表尾是"去掉表头后剩下的表"——注意表尾永远是表而不是原子。对 `(a,(b,(c)),d)`，表头是原子 a，表尾是 `((b,(c)),d)`。这个切分是递归处理广义表的标准入口，与第 3 章"先处理头、再递归处理尾"的递归模式完全同构。

其二是**共享与递归**。教科书里允许两个位置引用同一个子表（共享表），甚至允许表把自身作为元素（递归表，如图论中环的表示）。本章实现不构造这两种情形，但 arena 下标互引的设计天然支持共享：同一个子表节点编号出现在两处即可，不必复制。递归表则会让"深度"失去终止性——这解释了为什么深度定义隐含一条前提：子表关系无环。合同里必须说明这个前提，否则一个自引表会让求深度的递归永不返回。

### 10.3.6 怎么知道实现没骗人：不变量逐条落到断言

本章示例的自检不是随便挑几个值打印，而是让每个不变量都有一条对应断言，形成"合同—不变量—断言"的三级对照：

- 对称映射双向同槽 → 写 `at(0,1)` 后断言读 `at(1,0)`；
- 压缩位置数正确 → 断言 `stored() == n(n+1)/2 == 6`；
- COO 顺序不变量 → 逐位置比较转置后三元组的行列与值；
- 零项剔除 → 相加后断言三元组总数恰为 1；
- 十字链表双链一致 → 更新不增节点、插入后行内严格列序、节点总数精确；
- 广义表递归定义 → 长度、深度、展开序列三者同时断言。

这种写法的用意是：**不变量是"任何时刻都成立的事实"，那就挑能区分对错的小数据，把事实直接写成断言。** 一旦未来有人改坏映射公式或漏掉一条链接，程序立刻在对应位置失败，而不是默默产出一个错矩阵。

## 10.4 复杂度推导

- **行主地址计算：O(1)。** 一次乘法加一次加法，与维度无关。
- **对称矩阵 `at`：O(1)。** 两种情形都是固定算术；空间从 Θ(n²) 降到 Θ(n²/2)，量级虽同，但绝对占用减半，且更大的收益是按"压缩后的实际元素数"做批量运算时不碰重复数据。
- **稀疏矩阵构造排序：O(t log t)**，t 为非零项数；之后所有操作以 t 计成本。
- **转置：O(t log t)**（坐标变换 O(t) + 重排）；**相加：O(t₁ + t₂)**，一次归并。
- **十字链表定位：** 沿行链比较，最坏 O(一行非零节点数)；取整行与该行节点数线性相关；插入为两链的定位成本之和。空间 O(t)，另需行头、列头 O(rows + cols)。
- **广义表长度：O(1)**（顶层子项计数已存）；深度与展开各遍历每个节点一次，O(总节点数)。

对比中最值得记住的规律：**压缩存储把成本的计量单位从"矩阵大小"换成了"非零元素个数"。** 当稀疏度极高时，这两个数字可以相差成千上万倍，所有分析都因此重写。

这里把相加的 O(t₁+t₂) 再推导一步，因为"为什么是和而不是乘积"值得想明白。归并每一步只做一件事：比较两个游标所指位置，输出一个，并恰好推进一个游标（位置相同时推进两个）。每次推进都永久消费一个三元组，两个表总共只有 t₁+t₂ 个三元组可供消费，所以循环体至多执行 t₁+t₂ 次——线性而非嵌套。这个论证与第 8 章归并有序序列的分析是同一个模子。

空间开销也要算细账：COO 每个非零项要存行列号加值，稠密矩阵只存值。因此当矩阵并不稀疏时（比如一半格子非零），COO 的实际字节数反而可能超过稠密存储。压缩不是免费的午餐，**只有当稀疏度高到足以摊平每项的索引开销时，压缩才真正划算**——这也是为什么本章反复强调以非零项数 t 作为成本单位。

## 10.5 完整示例输出

示例对四种结构逐一做了固定数据验证（所有数据写死，输出可逐字节复现）：

```text
对称矩阵 3×3：压缩为 6 个位置，at(0,1) 写入则 at(1,0) 读出（同槽）
稀疏矩阵转置：行列互换，三元组仍按 (行,列) 升序
矩阵相加：抵消后仅余 1 个非零项（值为 9）
十字链表：5 个非零节点，set/get 往返一致，行内按列有序
广义表 (a,(b,(c)),d)：长度 3、深度 3，展开为 a b c d
自检通过
```

逐行解释输出验证了什么：

- 第 1 行：3×3 对称矩阵只租 6 个位置（`3×4/2`）；"写 (0,1)、读 (1,0) 同值"证明映射公式双向同槽。程序还检查了六个下三角槽彼此独立、越界访问抛异常。
- 第 2 行：转置后行列互换，三个三元组的值随坐标走到了对称位置，且重新整理后仍按 `(行,列)` 有序。
- 第 3 行：互为相反数的两个位置在归并相加时抵消、零项消失，只剩一个值为 9 的三元组——稀疏矩阵相加后可以更稀疏。
- 第 4 行：十字链表里更新已有位置不增加节点（始终是最初的 3 个），随后在同一行插入两格，行内三格严格按列号排列，节点总数增至 5，列链也同步就位。
- 第 5 行：广义表长度 3、深度 3（三层嵌套），展开后四个原子保持书写顺序 a→b→c→d。

## 10.6 与标准库的对照

- **`std::vector` 多维**：`vector<vector<T>>` 是最直接的二维形式，但行与行之间内存不连续，且无法压缩；科学计算常用一维 vector 加行主索引 `v[i*n+j]`，与 10.3.1 的映射完全一致。
- **稀疏矩阵**：标准库没有专用稀疏矩阵；常见手工做法是 `std::map<std::pair<int,int>, T>`，键的有序性自动维持、同位置天然去重，代价是每项的树节点开销与 O(log t) 访问。本章的 COO 在批量构造与归并运算上更省。
- **十字链表**无标准对应物；它的思想（同一项多维索引）在数据库的多维索引中可以见到。
- **广义表**无标准对应；`std::variant` 可用于表达"原子或子表"的节点类型，是工业代码里实现同类结构的工具。
- C++23 的 `std::mdspan`（多维视图）值得知道：它给一段连续内存提供多维下标访问，支持自定义布局，但本身不压缩、不拥有数据。
- `std::mdspan` 的布局策略与本章公式直接对应：`layout_right` 就是行主映射（最右一维连续），`layout_left` 是列主映射，`layout_stride` 允许手工给出每一维的跨度——三对角、带间隔切片这类不规则形状都能表达。它把"地址映射"从数据里独立出来成为可替换的策略，这正是本章反复强调的那个算术的标准化封装。

最后用一句话收束全章：本章所有技巧——压缩映射、三元组、双链接链、递归节点——表面上形态各异，背后只有两个动作：**一是把"形状"变成算术公式，二是为真正存在的数据付钱。** 带着这两个动作进入下一章的树形结构时，会发现树不过是一种非线性的"形状"，而链接组织的手法与十字链表如出一辙。

## 10.7 本章坑位

- **坑 1：转置只换坐标、不重排。** 现象：转置后三元组不再按 `(行,列)` 有序。原因：新行号是旧列号，原顺序不继承。后果：后续归并加法产生错误结果。防法：坐标变换后重新排序。
- **坑 2：相加时不为结果的零和项做处理。** 现象：结果表里存着值为 0 的三元组。原因：两个非零值相加可能恰为零。后果：稀疏性被破坏，后续遍历多做无用功。防法：归并时显式判断、剔除零项。
- **坑 3：对称映射两个分支写反。** 现象：`at(r,c)` 与 `at(c,r)` 读到不同槽。原因：下三角条件与转置分支混淆。后果：对称矩阵"看起来不对称"。防法：先统一把坐标规整成"大行小列"再套同一个公式。
- **坑 4：十字链表插入只接了一条链。** 现象：行方向能找到新节点，列方向遍历不到。原因：节点必须同时挂行链与列链。后果：按列查询丢数据。防法：插入函数的两链接线都由测试覆盖。
- **坑 5：重分配导致的引用悬空（本章实现实际踩中）。** 现象：写出 `nodes[id].children.push_back(new_child())` 后，子项数始终为 0。原因：成员引用先求值，`new_child()` 随后向同一数组追加并触发重分配，旧引用指向已搬走的空对象，push 静默丢失。后果：树结构静默残缺。防法：先把新节点编号算进局部变量，再在下一条语句做 push_back。
- **坑 6：把深度与长度混为一谈。** 现象：声称 `(a,(b,(c)),d)` "长度为 3 所以深度也是 3"。原因：长度数顶层元素，深度数嵌套层数，本例只是恰好都涉及 3。后果：嵌套结构的复杂度估计错误。防法：两个定义分别从"横向计数""纵向递归"理解。
- **坑 7：对不稀疏的矩阵滥用压缩。** 现象：稠密矩阵改用 COO 后内存不降反升、遍历变慢。原因：每项额外背了行列号，还有结构本身的间接访问。后果：优化反向。防法：先估算非零项占比，压缩前先回答"省下的零位能否抵过索引开销"。
- **坑 8：求深度前不排除自引（环）。** 现象：传入含自引用的表后程序不返回、栈持续增长。原因：深度递归失去终止条件。后果：栈溢出崩溃。防法：合同明确"子表关系无环"，或遍历时记录访问路径做环检测。
- **坑 9：把"空表"与"原子 0"画等号。** 现象：认为 `()` 深度是 0。原因：空表仍是一个表，按定义深度为 1；0 是原子深度。后果：递归基例取错，深度统计整体偏差。防法：区分"没有元素的表"和"值为零的原子"两个概念。
