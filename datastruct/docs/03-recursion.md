# 03 · 递归：把问题交给"更小的自己"

## 3.1 动机与直觉：一个"循环定义"为什么不是悖论

数学书里常有这样的表达：

> 自然数的阶乘：`0! = 1`，当 n ≥ 1 时 `n! = n × (n-1)!`。

右边的 `(n-1)!`——定义"阶乘"时又用到"阶乘"本身，只是参数变小了。这种**用自身定义自身**的方式叫递归（recursion）。乍看像循环论证，其实不是：它配了一个**不再递归的底线**（`0! = 1`），且每递归一步参数都更接近底线。任何具体的 n 都能一步步展开到底：

```text
4! = 4 × 3!
   = 4 × (3 × 2!)
   = 4 × 3 × (2 × 1!)
   = 4 × 3 × 2 × 1 × 1 = 24
```

递归是本课最重要的思维工具之一。树的定义天然递归（一棵树由根和若干棵子树组成），树的遍历、快速排序、归并排序、深度优先搜索，离开递归几乎无法清晰表达。本章目标：理解递归在计算机中如何执行、学会设计递归算法、并分析它的代价。

递归之所以值得单开一章，还因为它对应一种独特的解题视角：**不把问题看成"从头做到尾的一串步骤"，而看成"一个大实例和若干个小实例之间的关系"。** 同一个求和，迭代视角是"从 1 走到 n 累加"，递归视角是"n 的答案等于 n−1 的答案加 n"。前者关心控制流程，后者关心实例间的归约关系。遇到树、图这类没有自然"从头走到尾"路径的结构时，第二种视角几乎是唯一顺畅的表达方式。

## 3.2 ADT 合同：本章四个例程

本章不构造数据结构，但同样先立合同。示例头文件提供四个例程，语义如下：

- `fact(n)`：返回 n!，n ≥ 0；n ≤ 1 时结果为 1。
- `fib(n)` 与 `fib_memo(n)`：都返回第 n 个斐波那契数（F(0)=0, F(1)=1）；前者是定义的直译，后者带备忘录，二者对相同输入永远同值。
- `binary_search_rec(a, target)`：在**有序**区间 a 中查找 target，命中返回 true、未命中返回 false。
- `hanoi(n, from, via, to, moves)`：把 n 个盘从 from 移到 to，合法移动依次追加进 moves；三根柱为 from/via/to。

为避免把"合同"读成函数签名表，这里补充各例的关键不变量，它们是实现必须时刻维持的内部事实：

- 斐波那契备忘录：数组中每个已填位置 k 的值永远等于数学上的 F(k)，一旦填入不再修改；
- 二分查找：递归区间始终是原区间的连续子区间，目标若存在必落在其中；
- 汉诺塔：moves 中每一次追加都满足"小盘在上、单盘移动"两条规则，且追加后不回改历史移动。

合同规定"做什么"，不变量规定"过程中什么必须一直成立"——写代码时所有分支都要检查是否守住了不变量，这是把"看起来对"变成"确实对"的关键习惯。

合同还规定出错边界：这些例程的合法输入域内无异常；空区间是二分查找合法的基线输入，返回 false 而非抛异常。

## 3.3 设计与不变量：两要素、调用栈、逐步构造

### 递归的两个要素

任何正确递归都由两部分组成，缺一不可。

1. **基线情形（base case）**：可直接回答、不再递归的出口。阶乘里是 `n ≤ 1`。
2. **递归情形（recursive case）**：把原问题化为**一个或多个规模更小、性质相同**的子问题，并组合它们的答案。

设计时的自检问题：**每次递归，参数是否都严格更接近基线？** 参数忘递减、某分支原样传递，是无限递归的两大典型来源。

### 调用栈：递归的执行机制

程序调用函数时，计算机：① 记录返回地址；② 为这次调用的参数和局部变量开辟一块**栈帧**；③ 跳转执行。函数返回时栈帧丢弃，回到返回地址。栈帧像一摞盘子：`fact(4)` 没算完就要调 `fact(3)`，它的现场（n=4、乘号在等右操作数）被压在下面，上面再压 `fact(3)`……直到 `fact(1)` 返回 1，栈顶的盘子才一个个取下、逐层乘回来。

由此得到三个重要事实：

- **外层局部变量始终活着、保持原值。** 每次调用各有独立栈帧，内层冲不掉外层。
- **递归太深会栈溢出。** 栈空间有限（典型线程只有数 MB），深度百万的递归直接崩溃。
- **递归与"栈"结构本质相通。** 任何递归都能改写成显式栈循环，反之亦然；第 07 章讲完栈后亲手转换。

### 例一：阶乘

`fact(n) = n × fact(n-1)` 是分解与组合的最简模板：分解出一个 n，子问题解出 (n-1)!，组合方式是相乘。没有重叠子问题，递归树是一条链。

### 例二：斐波那契与备忘录

`F(n) = F(n-1) + F(n-2)` 可直译，但 `F(40)` 已明显卡顿、`F(50)` 近乎卡死。展开调用树可见**大量重复劳动**：

```text
F(5)
├─ F(4)
│  ├─ F(3)
│  │  ├─ F(2) …
│  │  └─ F(1)
│  └─ F(2) …        ← F(2) 又算一遍
└─ F(3) …           ← F(3) 整个又算一遍
```

F(k) 被调用的次数随 n 指数增长。**备忘录（memoization）**一招解决：算过的 F(k) 存数组，下次直接取，每个子问题只解一次。两版输出值断言相等，工作量却差着天文数字。这是通用模式——识别重叠子问题并缓存，第 25 章动态规划是它的系统化。

### 例三：递归二分查找

中间元素等于目标即命中；目标更小只在左半、更大只在右半。"在半边里继续找"与原问题同构，只是区间更小。不变量是：**每次递归的区间始终是原区间的子区间，且目标若存在必在其中**（被排除的半边绝无可能包含目标）。基线是区间为空 → false。

### 例四：汉诺塔与 7 步推演

不要试图直接规划 n=8 的走法。换问：**"假设我已经会移 n-1 个盘"**，n 个盘怎么移？三步：

1. 把 n-1 个盘从 A 移到 **B**（借 C）；
2. 把最大盘 A → **C**（全场最大，压谁都合法）；
3. 把 n-1 个盘从 B 移到 **C**（借 A）。

基线 n=0 什么都不做。n=3 的完整 7 步可手工推出（程序断言的正是这张表）：

```text
第 1 组（2 盘 A→B 借 C）：A→C, A→B, C→B
最大盘：                    A→C
第 2 组（2 盘 B→C 借 A）：B→A, B→C, A→C
```

注意一个容易写错的细节：**n 为奇数时，最小盘第一步直接去目标柱 C，最后一步也是它落到 C**，所以首步与末步同为 A→C。程序里没有任何"具体规划小盘怎么走"的代码——全部细节由递归机械展开。这就是递归思维：**只解决如何分解，不纠缠全部细节**。

### 更多递归模式：最大公约数、幂、尾递归

除四个示例外，有几种递归形态会在后面反复出现，先认识它们。

**（1）欧几里得最大公约数。** `gcd(a,b) = gcd(b, a mod b)`，基线 `gcd(a,0) = a`。参数缩小得比线性还快（余数必小于除数，且两步至少减半），时间 O(log min(a,b))。注意这里的"更小"不是数值简单减一，而是模运算——只要能证明参数严格朝基线收敛即可。

**（2）快速幂。** 朴素求 aⁿ 递归为 `a × power(a,n-1)`，O(n)；利用偶分 `power(a,n) = power(a,n/2)²`，奇数再补乘一个 a，层数 O(log n)。这是分治策略（第 24 章）的雏形：子问题规模减半而非减一，对数深度。

**（3）尾递归（tail recursion）。** 若递归调用是函数返回前的**最后一个动作**（如 `fact(n-1)` 的结果不再被乘 n，而是直接返回），编译器可以复用当前栈帧而非新压一帧——尾递归在优化后空间可降到 O(1)。许多编译器对尾递归有明确优化，写成累加器参数（accumulator）是制造尾递归的标准手法。C++ 标准不保证该优化，因此教学中不依赖它，但认识这个概念有助于读懂函数式代码。

**（4）相互递归。** A 调 B、B 又调 A，双方互为递归情形。树结构里"先序遍历"与"处理森林"就是经典一对（第 12 章会出现）。相互递归同样需要基线，且两个函数的参数要协同朝基线收敛。

**（5）对区间递归的两个入门例。** 递归处理数组时，最常用的分解是"第一个元素 + 剩余区间"：

- 递归求和：`sum(a) = a[0] + sum(a[1:])`，空区间为 0。每次调用区间缩短一个，时间 O(n)、栈深 O(n)。
- 回文判定：`palindrome(a) = (a[0]==a[last]) 且 palindrome(去掉两端的区间)`，区间长度 ≤1 时为真。每次两端各缩一个，仍是 O(n)。

这两个例看起来简单，却包含处理一切递归结构的基本动作：**选一个分解切口、把剩余部分交给递归、用基线收尾。** 后面二叉树的"根 + 左子树 + 右子树"只是把切口从数组端点换成根节点。

**关于栈深度的工程常识（正文知识，非程序输出）：** 桌面系统默认线程栈以 MB 计，每个栈帧几十字节上下，因此万级深度通常已逼近极限；O(log n) 的递归（如二分、平衡树）即使 n 上亿也只有约三十层，天然安全；O(n) 的递归（如朴素 DFS 链表）在 n 很大时必须改写为迭代或显式栈。选递归还是迭代，这条物理约束比"写法优雅"更硬。

### 正确性论证：递归信念就是数学归纳法

写递归时被反复提醒的"递归信念"（trust the recursion）不是盲目相信，而是有严格前提：你必须已经确认基线正确，且**所有**递归调用都在更小实例上、子例程合同与设想一致。在此前提下不去人肉展开，是因为展开与证明无关——无论 n−1 具体是多少，组合规则不变。

这与数学归纳法的结构完全对应：证明基线成立、证明递推保持性质，则一切实例成立。事实上**证明递归算法正确用的就是数学归纳法**：阶乘以"基线 1 正确 + 乘 n 保持阶乘定义"得证；二分查找以"空区间返回 false 正确 + 目标必在递归半边内"得证；汉诺塔以"0 盘无需移动 + 三步分解保证全部合法"得证。这也是递归代码的正确性论证往往比迭代更直接的原因——程序结构和证明结构同形。

### 递归与迭代的取舍

| 维度 | 递归 | 迭代 |
|---|---|---|
| 表达力 | 贴近数学定义，树/分治上自然 | 需自行组织控制流程 |
| 开销 | 每次调用建栈帧 | 通常更少 |
| 深度限制 | 受栈空间约束 | 无栈溢出问题 |
| 可读性 | 分解正确时简短清晰 | 复杂迭代可能隐晦 |

本教程原则：**结构天然递归的用递归；性能关键且递归无收益的用迭代。** 同一种算法先写递归版把正确性钉死、再按需改迭代，是稳妥的工程顺序。

## 3.4 复杂度推导：四个例程的账

- **阶乘**：n 次递归调用，每次 O(1) 工作 → 时间 O(n)，栈深 O(n)。
- **朴素斐波那契**：调用次数随 n 指数增长，时间 O(φⁿ)（φ 为黄金比），栈深 O(n)。备忘录版每个参数只算一次 → 时间 O(n)，空间 O(n)。
- **二分查找**：区间每次减半，从 n 缩到不足 1 需 ⌈log₂n⌉ 层 → 时间 O(log n)，栈深 O(log n)。
- **汉诺塔**：移动次数满足 M(n) = 2M(n-1)+1, M(0)=0，解得 **M(n) = 2ⁿ − 1**，时间 O(2ⁿ)，栈深 O(n)。2ⁿ−1 同时是任何解法的移动次数下界；n=64 时每秒一步需约 5800 亿年。

对比里最值得记住的两点：递归本身不慢（慢的是重叠子问题）；对数深度（O(log n) 栈）和线性深度（O(n) 栈）在百万规模时是"安全"与"溢出"的区别。

把以上账单列在一起，便于以后回查：

| 例程 | 时间 | 栈深（额外空间） |
|---|---|---|
| 阶乘 | O(n) | O(n) |
| 朴素斐波那契 | O(φⁿ) | O(n) |
| 备忘录斐波那契 | O(n) | O(n) |
| 二分查找 | O(log n) | O(log n) |
| 汉诺塔 | O(2ⁿ) | O(n) |

两列要分开看：时间是总工作量，栈深决定会不会溢出。汉诺塔即使只想打印前几十步，递归深度也只有 O(n)——真正不可行的是总工作量，而非栈空间。

## 3.5 完整示例输出

示例对四个例程做固定验证：

```text
5! = 120
F(10) = 55（朴素递归与备忘录版结果相同）
二分查找：7 命中，8 未命中
汉诺塔 3 盘共 7 步：
  1. A → C
  2. A → B
  3. C → B
  4. A → C
  5. B → A
  6. B → C
  7. A → C
自检通过
```

逐行看说明了什么：

- 第 1 行：基线与组合正确，5! = 120；
- 第 2 行：两版斐波那契**结果相同**（断言保证），差别只在工作量；
- 第 3 行：查找两个方向都验证了——7 命中，8 在区间反复减半后触底返回未命中；
- 汉诺塔清单：恰好 **7 = 2³−1** 步。最好的练习是把它按 3.3 节切成 `3 + 1 + 3` 三段：第 1–3 步移开小盘组（首步最小盘 A→C），第 4 步最大盘 A→C，第 5–7 步把小盘组搬到终点（末步最小盘 A→C 收束）。

## 3.6 与标准库及迭代写法的对照

标准库的 `std::binary_search`、`std::sort`、`std::nth_element` 都按分治思想设计，但标准不要求用递归实现——工业代码常在递归到小区间时切换简单排序，或整体改写为迭代以省调用开销。

给递归学习者的转换模板：把"递归调用"换成"把当前现场压入一个栈、更新参数继续循环"，把"函数返回"换成"从栈中弹出现场并恢复"。第 11 章二叉树的非递归遍历会完整演示这套机械转换。迭代版斐波那契只需两个变量滚动（O(n) 时间、O(1) 空间）；但初学时先用递归把结构写对，再谈优化。

一个值得记住的事实是：标准库算法的复杂度条款（如 `std::sort` 平均 O(n log n)、`std::binary_search` O(log n)）与实现语言层面用不用递归完全无关——条款约束的是比较次数等外部可观察成本。理解这一点后，本章学的分析方法可以直接拿去核对任何库的性能承诺：**先自己推出步数量级，再对照文档，而不是反过来背文档。**

## 3.7 本章坑位

- **坑 1：漏写或写错基线。** 现象：崩溃或无限递归。原因：没出口，或某分支参数不朝基线收敛。后果：栈不断增长直到溢出。防法：先写基线，检查每条递归路径参数严格变小。
- **坑 2：朴素递归重算重叠子问题。** 现象：F(50) 卡死。原因：同一子问题被求指数次。后果：很小输入即不可用。防法：画三四层调用树找重复节点，有则备忘录。
- **坑 3：同一递归调用在表达式里写两遍。** 现象：`f(n-1) + g(f(n-1))` 之类写法。原因：两次调用各自展开整棵子树，编译器不缓存。后果：工作量翻倍。防法：结果先存局部变量再复用。
- **坑 4：递归里误用共享全局状态。** 现象：汉诺塔用全局数组记录，深层改动影响外层逻辑。原因：全局变量只有一份。后果：结果错乱且极难调试。防法：状态走参数与返回值；确需共享收集容器时只追加、不回改。
- **坑 5：用引用参数承接递归中间结果。** 现象：把本应"每帧独立"的局部变量声明成引用并绑到外部容器元素，深层递归修改后影响了外层尚未使用的值。原因：引用不复制、跨栈帧共享同一对象。后果：上层组合答案时拿到已被内层改掉的值，bug 随深度随机出现。防法：递归中间量默认值传递、各帧私有；只有"只追加的收集器"才用引用共享。
- **坑 6：凭直觉写错汉诺塔第一步。** 现象：断言"首步 A→B"。原因：n 为奇数时最小盘首步直达目标柱 C。后果：测试自相矛盾（7 步与首步 A→B 不可兼得）。防法：小 n 手工推演并让程序断言完整序列，而不是只断言首尾。
