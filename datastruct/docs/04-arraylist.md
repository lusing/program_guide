# 04 · 顺序表：把线性表放进一整块连续内存

## 4.1 动机与直觉：从"一排编号座位"说起

考虑一节火车车厢：座位按 1、2、3、…、100 依次排开，任何两个相邻座位之间的物理距离都相同。想找第 37 号座位？不需要从头问起——座位号本身就是位置，顺着编号直接走过去。这就是顺序存储的直觉：**逻辑上的第 k 个元素，物理上就住在"起点 + k 段固定距离"处。**

第 01 章说过，线性表是最基础的逻辑结构：除首尾外每个元素有唯一的前驱和后继。本章实现它的第一种存储方式——顺序存储，产物是 `ArrayList<T>`。它在标准库里的对应物是 `std::vector`，而顺序表也是一切后续结构的地基：栈和队列可以直接架在它上面，堆就是一棵"藏在数组里的树"，散列表的线性探查更是一块连续内存上的游戏。

为什么第一个要学它？因为连续内存是 CPU 最欢迎的形态：硬件缓存会把相邻元素成批预取进来，遍历顺序表通常是所有容器里最快的。但代价同样来自"连续"：在中间插入或删除，后面的全体元素都要挪位；想扩容，往往得整表搬家。本章的设计就是围绕"享受连续、管理搬家"展开。

## 4.2 ADT 合同：顺序表承诺什么

`ArrayList<T>` 是一个泛型容器：元素类型 T 只需满足 `std::copyable`（可拷贝即可移动）。合同列出全部公开操作及语义。

**构造与析构。** 可以默认构造一个空表；可以 `ArrayList(n)` 预留容量（长度仍为 0）；可以用花括号列表 `ArrayList{2,4,6}` 直接构造。对象销毁时归还全部资源，不需要调用方做任何清理——这是 RAII 承诺。

**观察操作。** `size()` 返回当前元素个数，`empty()` 判空，`capacity()` 返回"已租下、可容纳的元素数"。容量与长度的分离是理解全章的关键：长度是已入住的人数，容量是房间总数；人可以少于房间，但不能多于房间。

**尾插。** `push_back(v)` 在表尾加入一个元素，长度加一。若房间已满，容器会自动租下更大的一块并整体搬迁（细节见 4.3）。

**按位置插入与删除。** `insert(pos, v)` 把 v 放到位置 pos，原来 pos 及其后的元素全体右移一位；合法范围是 `0 ≤ pos ≤ size`，`pos == size` 等同于尾插。`erase(pos)` 删除位置 pos 的元素，其后的元素全体左移一位；合法范围 `0 ≤ pos < size`。

**尾删。** `pop_back()` 移除最后一个元素。

**随机访问。** `lst[i]` 返回第 i 个元素的引用，可以读也可以写；合法范围 `0 ≤ i < size`。

**遍历与视图。** 表支持范围 for 遍历（`for (const T& x : lst)`）；`as_span()` 返回一个 `std::span<T>`，即"连续元素的非占有视图"，可传给只需要一段连续数据的函数而无需拷贝。

**相等。** 两表长度相等且每个对应位置元素相等，`==` 才为真。

**出错行为（合同的一部分，不靠调用方自觉）：**

| 操作 | 非法输入 | 行为 |
|---|---|---|
| `operator[]` | i ≥ size | 抛 `std::out_of_range` |
| `insert` | pos > size | 抛 `std::out_of_range` |
| `erase` | pos ≥ size | 抛 `std::out_of_range` |
| `pop_back` | 空表 | 抛 `std::out_of_range` |

这些都属于"编程错误"——调用方违反了前提条件。合同选择抛标准异常，让错误在离现场最近的地方暴露，而不是静默地继续错下去。

## 4.3 设计与不变量：三字段与它们的约定

### 数据表示：一块内存、两个计数

内部只有三个数据成员：

```cpp
T* data_ = nullptr;       // 指向所租内存块的起点
size_t size_ = 0;         // 已构造（已入住）的元素个数
size_t cap_ = 0;          // 整块内存可容纳的元素个数
```

所有函数都必须共同维护三条**不变量**，它们是容器正确性的命根子：

1. `[data_, data_ + size_)` 区间内每个位置都有一个**已构造**的 T；
2. `[data_ + size_, data_ + cap_)` 区间内是**原始未初始化**存储，里面什么对象都没有；
3. `size_ ≤ cap_` 恒成立。

区分"已构造"与"有内存"至关重要：向未初始化内存赋值是未定义行为，对已析构的对象再次析构同样是灾难。因此每个操作要么用 placement new "生"出对象，要么用显式析构调用"送走"对象，绝不能简单地对空位赋值。

### 内存从哪来：未初始化存储 + placement new

直接写 `new T[n]` 会在租内存的同时默认构造 n 个 T，这要求 T 可默认构造，且产生大量用不上的对象。我们只要"空地皮"：

```cpp
static T* allocate_(size_t n) {
    return static_cast<T*>(::operator new(n * sizeof(T)));
}
```

`::operator new` 只向系统要一块 n 个 T 大小的原始内存，不构造任何对象。等真正入住时，再用 placement new 在指定地址上构造：

```cpp
::new (static_cast<void*>(data_ + i)) T(v);   // 在 data_[i] 的地址上构造一个值为 v 的 T
```

这两行是"管理空地皮"的基本动作：前者只租房不入住，后者在指定房间入住。析构时反过来——对每个已构造元素显式调用 `data_[i].~T()`，再用 `::operator delete` 归还地皮。

### 扩容：倍增策略

`push_back` 发现 `size_ == cap_` 时必须先扩容。若每次只多租一个位置，插 n 个元素就要搬 n 次家、总搬运量 1+2+…+n = Θ(n²)。我们采用**倍增**：容量按 1 → 2 → 4 → 8 → 16 翻番。

```cpp
void grow_(size_t need) {
    size_t nc = cap_ == 0 ? 1 : cap_;
    while (nc < need) {
        nc *= 2;
    }
    reserve(nc);
}
```

`reserve(n)` 完成搬家：租下新地皮 → 在新地皮上逐个按原顺序造出元素 → 析构旧元素、归还旧地皮。其中新元素的构造方式值得注意：

```cpp
::new (nd + i) T(std::move_if_noexcept(data_[i]));
```

`std::move_if_noexcept` 的规则是：T 的移动构造保证不抛异常就移动（省一次深拷贝），否则退化为拷贝。为什么这么保守？搬家途中若在第 k 个元素处抛异常，拷贝路径下旧地皮完好无损，把新地皮上已造的 k 个对象清理掉即可，整个容器就像什么都没发生——这叫**强异常保证**。

### 中间插入：先"撑开"，再右移

`insert(pos, v)` 的细节有个常见陷阱：未初始化的尾部不能直接赋值。做法是分三步。

第一步，在尾部位置复制构造一份最后一个元素，把"已构造区间"撑开一格：

```cpp
::new (data_ + size_) T(data_[size_ - 1]);
```

第二步，从后往前，把元素逐个向右挪一位：

```cpp
for (size_t i = size_; i > pos; --i) {
    data_[i] = std::move(data_[i - 1]);
}
```

必须从后往前：若从前往后，前一个位置早已被自己的新值覆盖，原值丢失。第三步，把腾出来的 pos 位置赋成 v。

### 删除：左移后"送走"最后一个

`erase(pos)` 是镜像过程：后继元素从 pos 开始逐个向左移动一位，最后多出的那个尾部对象已无人需要，显式析构它并把长度减一。

```cpp
for (size_t i = pos; i + 1 < size_; ++i) {
    data_[i] = std::move(data_[i + 1]);
}
data_[size_ - 1].~T();
--size_;
```

### 三五法则：拷贝、移动、析构成套出现

类直接管理着一块内存，编译器免费生成的拷贝语义会把指针原样复制——两个对象指向同一块地皮，析构时双重释放。因此五个特殊函数必须成套定义：析构函数负责"析构 + 归还"；拷贝构造另租地皮、逐元素复制（改副本不影响原件）；移动构造直接把三字段接管、把源对象置空（资源整体转交，零拷贝）。拷贝赋值采用"拷贝并交换"：先安全地造出一份副本，再与本对象交换，旧资源随副本析构自动归还——自赋值也天然安全。

## 4.4 复杂度推导

**随机访问 O(1)。** 元素 i 的地址由 `data_ + i` 直接算出，与 n 无关，一次乘法加法而已。这是顺序表最硬的优势，链表在这一项上是 O(n)。

**insert / erase：Θ(n − pos)。** 搬运量等于被移动的元素个数。在表尾操作是 O(1)；在表头操作要移动全部 n 个元素；平均（假设位置均匀）移动 n/2 个，仍是 Θ(n)。

用一张小表观察连续插入时"搬家时刻"与累计成本，体会均摊的含义：

| 插入后长度 | 是否搬家 | 本次搬运量 | 累计搬运量 | 累计/长度 |
|---|---|---|---|---|
| 1 | 否（容量 1） | 0 | 0 | 0 |
| 2 | 是（1→2） | 1 | 1 | 0.50 |
| 3 | 是（2→4） | 2 | 3 | 1.00 |
| 4 | 否 | 0 | 3 | 0.75 |
| 5 | 是（4→8） | 4 | 7 | 1.40 |
| 8 | 否 | 0 | 7 | 0.88 |

最后一列始终在 0 与 2 之间波动、从不随长度增长——这正是"均摊 O(1)"看得见的形状。对比每次只加一个容量的策略：长度 8 时累计搬运量将是 0+1+2+…+7 = 28，最后一列涨到 3.5，且随 n 线性上升，均摊退化为 O(n)。

**push_back：单次最坏 O(n)，均摊 O(1)。** 倍增搬家的单次代价确实是 Θ(n)，但它很少发生。算总账：把容量从 1 扩容到超过 n，历次搬家的搬运量是 1+2+4+…，直到不超过 n 的那一项，这是一个几何级数，总和严格小于 2n。于是 n 次 push_back 的总搬运量 < 2n，**平均每次不到 2 次元素操作**——这就是均摊分析的结论。倍增（而不是每次加一）是均摊 O(1) 的关键：若每次只多租一个位置，总搬运量将是 Θ(n²)。

**空间：O(n)**，另有倍增策略带来的平均约 1.5 倍以内的空置率（最坏时刻容量可达长度的近 2 倍，但总小于 2）。

## 4.5 完整示例输出

示例对构造、尾插、中间插删、拷贝移动、异常、span 与相等语义逐一做了断言验证：

```text
尾插 8 后：2 4 6 8 
位置 1 插入 3 后：2 3 4 6 8 
删除位置 1 后：2 4 6 8 
拷贝后修改副本：副本首位 20，原件首位仍为 2，互不影响
移动后：源对象为空，移动得到的表首位为 20
下标越界被捕获：ArrayList::operator[]: index out of range
插入位置越界被捕获：ArrayList::insert: pos > size
span 长度与表一致（4），相等语义：相等为真、改后为假
自检通过
```

逐行看输出验证了什么：

- 前三行是插入删除合同的完整轨迹：`{2,4,6}` → 尾插得 `{2,4,6,8}` → 位置 1 插入 3 后后继右移为 `{2,3,4,6,8}` → 删除位置 1 后后继左移，精确回到插入前的状态。可逆性说明右移/左移逻辑彼此正确。
- 第四、五行验证值语义：拷贝得到的是独立副本（深拷贝），修改互不影响；移动则是资源转交，源对象清空而内容无损到达。
- 第六、七行是异常合同的实测：两种编程错误都在越界瞬间抛出携带定位信息的标准异常，并被调用方捕获，程序继续运行而非崩溃。
- 第八行确认 span 只是原内存的视图（长度随表），以及 `==` 按"长度相同且逐项相等"工作。

## 4.6 与标准库的对照

`std::vector<T>` 就是工业级顺序表，合同几乎一致而实现更复杂：`size()/push_back()/operator[]/reserve()` 的语义可以直接套用本章分析。两个细节值得对照：

1. **越界行为不同。** vector 的 `operator[]` 越界是**未定义行为**（标准为性能不做检查），想获得受检查访问要用 `v.at(i)`，它抛 `std::out_of_range`——与本章 `operator[]` 的选择一致。教学容器统一检查，是因为"早暴露错误"比"省一次比较"重要。
2. **扩容触发点不透明。** vector 不公开增长因子（实现常取 1.5 或 2），而本章固定倍增；二者均摊分析的结论相同。vector 还有 `shrink_to_fit()` 请求退还多余容量，本教学容器不提供。

`std::span<T>` 对应 `as_span()`：它是指针加长度的轻量包装，**不拥有**数据，构造和拷贝都极廉价，但代价是容器一旦扩容或析构，旧的 span 立即失效——使用时要在代码注释里写清它的有效期。

## 4.7 本章坑位

- **坑 1：对未初始化内存赋值。** 现象：扩容后直接 `new_data[i] = old_data[i]`。原因：新地皮上还没有对象，赋值的左操作数必须是已存在的 T。后果：未定义行为，可能崩溃或数据损坏。防法：新位置一律 placement new 构造；只有右移那种"两边都已有对象"的场景才能用赋值。
- **坑 2：扩容函数顺手清掉了长度。** 现象：本章实现就曾踩到——`reserve` 复用了 `clear_()` 析构旧元素，但 `clear_()` 同时把 `size_` 置零，push_back 后断言长度失败。原因：析构旧存储与重置逻辑长度是两件事。后果：容器在一次扩容后"失忆"。防法：reserve 中只析构、不改动 `size_`。
- **坑 3：右移时从前往后挪。** 现象：插入后出现一串重复元素。原因：从前往后移动时，目标位置的原值在被读之前就已被前一步覆盖。后果：数据丢失且断言序列对不上。防法：右移一律从尾部开始，左移才从头开始。
- **坑 4：漏写拷贝构造、依赖编译器默认版本。** 现象：对象析构时崩溃或双重释放。原因：默认拷贝只复制指针，两个对象共有同一块内存。后果：析构两次、互相改写，问题常延迟到函数返回时才爆发。防法：管理资源的类遵守三五法则，五个特殊函数成套定义。
- **坑 5：以为 push_back 任何时候都是 O(1)。** 现象：在性能敏感循环里只按 O(1) 估算 push_back，实测出现周期性尖峰。原因：倍增搬家的单次代价是 Θ(n)。后果：实时系统中单次操作的最坏耗时被低估。防法：能预知大小时先 `reserve` 一次，搬家就不会在业务循环中发生。
- **坑 6：把 span 当长期存储。** 现象：函数把入参 span 存进成员，稍后使用时数据已失效。原因：span 不拥有数据，底层 vector 扩容即搬家。后果：悬空引用式的未定义行为。防法：span 默认只在当前同步调用链内使用，跨期保存改为持有容器本身。
