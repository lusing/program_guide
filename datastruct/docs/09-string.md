# 09 · 串：模式匹配与索引

## 9.1 动机与直觉：在一篇文章里找一个词

前几章的容器装什么都行：整数、坐标、订单记录。本章的容器只装一种东西——**字符**。零个或多个字符组成的有限序列叫**串（string）**。这个限定看起来没什么大不了，却改变了"操作"的重心：

- 对整数表，我们关心"第 3 个元素是多少""在中间插入一个数"；
- 对串，我们更关心"**`data` 这个词出现在哪**""把所有 `colour` 换成 `color`""这句话以 `https://` 开头吗"。

这类操作有一个共同名字：**模式匹配（pattern matching）**——给定一个短串（模式），在一个长串（正文）里找它出现的位置。它无处不在：编辑器的 Ctrl+F、命令行的 grep、搜索引擎对网页的预处理、杀毒软件对病毒特征码的扫描、生物信息学里在基因组序列中查找基因片段（DNA 串的字母表只有 A、T、G、C 四个字母，但串长以十亿计）。

先用最直觉的方式找一次。想象你在做填字游戏的核对：把模式的第一个字对准正文的第一个字，逐字比；一旦某个字对不上，把整个模式向右挪一位，从头再比。这个策略人人都会，而且多数时候够用——但它有一个致命的最坏情形，本章会把它逼出来。

顺便澄清串与"字符的线性表"到底有何不同。逻辑结构上，串确实是线性表；但串有三个专属约定：① 元素类型固定为字符；② 操作对象常常不是单个字符而是**子串**（连续一段）——求子串、串接、比较、模式匹配，单字符操作反而少见；③ 串往往很长且总量很大（一整个语料库），存储时要专门计较每个字符占多少字节。因此教材都把串单列一章，而不是并在线性表里。

存储上补一句背景知识：C++ 的 `char` 通常是一个字节，早期英文文本用单字节编码（ASCII）绰绰有余；中文等文字需要多字节编码，现代通行的 UTF-8 是变长方案——常用汉字占三个字节。本章算法全部建立在**字节序列**这一层上，合同里的"长度""位置"都是字节口径，阅读后续推导时请记住这一点。

本章的第二条线索来自**书末尾的索引**。一本厚书里术语成百上千，为什么你能在十几秒内找到"散列函数"的页码？因为索引把每个术语连同页码，按术语排了序——先在有序清单里定位术语，再一步翻到那一页。给一篇文章也建这样一张"词 → 位置"的索引，反复查词就不必每次扫全文。这正是第 16 章"字典"的雏形，我们先用串的场景把它实现一遍。

## 9.2 ADT 合同：匹配三例程与索引两例程

示例头文件 `string_match.hpp` 提供三个操作，合同如下：

- **bf_find(text, pat, pos = 0)**：从正文 `text` 的位置 `pos` 起找模式 `pat`，返回**第一次**匹配的起点；不存在返回 `npos`（即 `size_t(-1)`）。
- **kmp_find(text, pat, pos = 0)**：参数、返回值与 `bf_find` **完全相同**——它们是同一份合同的两种实现，区别只在速度。
- **build_pi(pat)**：返回 KMP 专用的"部分匹配表"，长度等于模式长度；第 i 项是前缀 `pat[0..i]` 的最长相等真前缀/真后缀长度。

几个语义细节（调用方与实现方之间不再有猜测空间）：

- `pos` 是搜索的起点：`bf_find("aaaa", "aa", 1)` 返回 1，位置 0 处的匹配被跳过。
- **空模式**按标准库 `std::string::find` 的约定处理：返回 `min(pos, text.size())`，即"空串在任何位置都匹配"。
- `pos > text.size()` 或模式比剩余正文还长：返回 `npos`。

小例子固定一下直觉：正文 `"data structure"` 中，`"data"` 在 0、`"structure"` 在 5、`"tree"` 不存在（`npos`）。

为完整起见，把串的基本操作分三组列一下（本章实现聚焦在第三组）：

- **整体操作**：求长度、串接（两串首尾相接）、判空、赋值、字典序比较（从第一个字符起按编码值比，先分出大小者为准；前缀相同时短串为小）；
- **子串操作**：取子串 `substr(pos, len)`、插入/删除一段——注意这些操作的代价与移动的字符数成正比；
- **匹配与检索**：模式匹配（bf/kmp）、全串计数、按词建索引。

合同里还要记住一个不对称：`length()` 是 O(1) 的（长度显式保存），而求"字节数"与"字符数"在多字节编码下不是一回事。

`string_index.hpp` 提供：

- **WordPos**：一条索引项 = 一个词 + 它在正文中**首次**出现的位置。
- **build_index(text)**：把正文切成词，每个不同的词保留一项（去重），结果按词的字典序排序。
- **lookup(idx, word)**：在有序索引中查词，命中返回指向该条目的指针，未登录词返回 `nullptr`。

"词"的口径也写进合同：连续的字母、数字、下划线算一个词，其余字符是分隔符。这是编程语言标识符的口径；切分自然语言时换一种口径即可，结构不变。

## 9.3 设计与不变量：从朴素匹配到 KMP

### 9.3.1 朴素匹配：起点逐个试

`bf_find` 的结构可以用一句话描述：**枚举起点 i，从 i 起逐字符与模式对齐，全部相等就返回 i，否则试 i+1。** 关键的一小块是内层比较与回退：

```cpp
for (size_t i = pos; i <= n - m; ++i) {
    size_t j = 0;
    while (j < m && text[i + j] == pat[j]) ++j;
    if (j == m) return i;
}
```

这段代码必须守住的不变量是：**每次内层比较开始时，模式恰好与正文在起点 i 处对齐；j 记录已经连续相等的字符数。** 失配后 j 丢弃、i 增一，不变量重新成立。

注意循环上界 `n - m`：起点再往后，模式放不下，没必要试。这一行同时规避了 `text[i+j]` 越界——能进入循环的 i 都保证 `i+m ≤ n`。

### 9.3.2 朴素匹配慢在哪

慢在"失配后全部推倒重来"。看最坏的例子：正文全是 `a`、只有最后一个字符是 `b`，模式是 `aaa…ab`：

```text
正文： a a a a a a a a b
模式： a a a a b        ← 起点 0：前 4 个 a 都相等，比到 b 才失败
模式：   a a a a b      ← 起点 1：又是 4 个 a 相等，再失败
模式：     a a a a b    ← ……每次都几乎比满整个模式
```

每个起点都比较约 m 次，共约 n 个起点——总比较 O(nm)。真正可惜的是：**这些失败里藏着我们已经知道的信息**（"正文这里是 a"），朴素算法却把它们全忘了。

### 9.3.3 KMP 的核心洞察：正文游标不后退

KMP（Knuth–Morris–Pratt）换了一个问法：失配时，模式最多能向右滑多远，而**不会错过任何可能的匹配**？答案要从模式自身的结构里找。

假设模式前 j 个字符已经和正文相等，第 j+1 个字符失配。如果这 j 个字符的**后缀**，恰好等于模式的某个**前缀**，那么模式可以直接滑到让这个前缀对准那个后缀——已经相等的部分不必再比一次。"最长的这种前后缀有多长"，正是 `build_pi` 要为模式每个位置预先算好的数。

手工构造 `pi("ababaca")`，逐位推演：

| i | 前缀 pat[0..i] | 最长相等真前后缀 | pi[i] |
|---|---|---|---|
| 0 | `a` | 无（真前后缀不许取整个串） | 0 |
| 1 | `ab` | 无 | 0 |
| 2 | `aba` | `a` = `a` | 1 |
| 3 | `abab` | `ab` = `ab` | 2 |
| 4 | `ababa` | `aba` = `aba` | 3 |
| 5 | `ababac` | 无 | 0 |
| 6 | `ababaca` | `a` = `a` | 1 |

这正是示例断言的 `[0,0,1,2,3,0,1]`。

匹配时的修复动作因此极简：模式游标 j 失配后回退到 `pi[j-1]`，正文游标 i **原地不动**，继续比较：

```cpp
if (text[i] == pat[j]) { ++i; ++j; }       // 相等：两游标齐进
else if (j > 0) { j = pi[j - 1]; }         // 失配：模式滑，正文不回退
else { ++i; }                              // j 已为 0：正文才进一步
```

不变量相应升级为：**每轮循环结束时，模式的前 j 个字符与正文 ending at i 的一段相等；且任何被跳过的起点都不可能产生匹配（由 pi 的最长性保证）。** 第二条不变量是 KMP 正确性的命门——滑得远但不能漏。

### 9.3.4 一次完整的 KMP 走查

光看规则仍嫌抽象，跟着规则在正文 `"ababac"` 里找模式 `"abac"` 走一遍。先建 pi：模式前缀 `"a"`、`"ab"` 无对称前后缀，`"aba"` 有长度 1（前后各一个 `a`），`"abac"` 无——`pi = [0,0,1,0]`。然后：

| 步骤 | 正文[i] | 模式[j] | 动作 | i, j |
|---|---|---|---|---|
| 1 | a | a | 相等齐进 | 1, 1 |
| 2 | b | b | 相等齐进 | 2, 2 |
| 3 | a | a | 相等齐进 | 3, 3 |
| 4 | b | c | 失配：j = pi[2] = 1，**i 不动** | 3, 1 |
| 5 | b | b | 相等齐进 | 4, 2 |
| 6 | a | a | 相等齐进 | 5, 3 |
| 7 | c | c | 相等，j=4 恰好等于模式长 | 返回 6−4 = 2 |

第 4 步是全表的关键：失配后正文游标停在 3，模式利用"刚匹配上的 `ab…` 里后缀 `a` 等于模式前缀 `a`"滑了两位，第 5 步直接从 `b` 继续——正文位置 3 这个字符**只看了一次**。朴素算法在这里会退回正文位置 1 从头比。最终匹配起点 2：正文 2..5 正是 `a b a c`。

### 9.3.5 单词索引：切词、去重、排序、二分

索引的构造分四步，每步只解决一个小问题：

1. **切词**：扫描正文，用 `is_word_char` 识别连续的字母/数字/下划线，得到词与起点；
2. **去重、保首次位置**：用一张表记录每个词第一次出现的位置，再次遇到不覆盖；
3. **排序**：所有条目按词字典序排列；
4. **查询**：`lookup` 在有序表上二分（`lower_bound`），比较次数 O(log W)。

索引的不变量是：**每条目的位置永远是该词的真实首次出现位置；条目数组按词严格有序（无重复词）。** 正因为有"有序"这条不变量，查询才能用二分而不必扫描。

## 9.4 复杂度推导

- **bf_find**：最坏 O(n·m)（9.3.2 的重复串例）；最好 O(n)（每个起点一次就失配）。空间 O(1)。
- **build_pi**：O(m)。论证看游标 j 的总账：j 每轮至多增 1（总计 ≤ m），while 回退时 j 减少——减少总量不超过增加总量，故总迭代 O(m)。这是一次小型的均摊论证。
- **kmp_find**：正文游标 i 只增不减、至多走 n 步；失配回退同样按"j 增减总量"摊还为 O(n)，加上建表 O(m)，合计 **O(n + m)**，空间 O(m)。
- **索引**：建索引在词数 W、词长 L 规模下约 O(总字符数 + W log W)；单次 lookup 为 O(L·log W)（字典序比较本身与词长有关）。
- KMP 相对 BF 的实际意义：DNA 检索里 n = 10⁹、m = 100 时，O(nm) 与 O(n+m) 的差别是机器能否在有生之年跑完。

可能有人会问：既然 BF 最坏 O(nm)，为什么实际编辑器里 Ctrl+F 仍然很快？原因有两层：① 自然文本中失配往往发生在头一两个字符，BF 的平均比较接近 O(n)——9.3.2 那种重复串在真实文章里罕见；② 现代 CPU 对 BF 这种顺序、可预测的简单循环极友好，而 KMP 的回退分支会打断流水线。**最坏复杂度是责任问题，不是日常速度问题**：编辑器可以赌典型输入，而处理不可信输入（攻击者可以故意喂重复串）的系统必须用有线性保证的算法。这条"典型性能 vs 最坏保证"的区分，在后续排序与图算法中还会反复出现。

## 9.5 完整示例输出

示例用固定正文 `"data structure is about data and how data is stored"` 验证全部合同：

```text
build_pi("ababaca") = [0,0,1,2,3,0,1]
"data" 各次出现起点：0、24、37（BF 与 KMP 一致）
pos 偏移：从头找 "data" 得 0，从 1 起得 24，从 25 起得 37
未命中返回 npos；空文本/空模式/超长模式边界正确
索引共 7 个不同词，lookup("data") 首次出现于位置 0，未登录词返回 nullptr
自检通过
```

逐行看说明了什么：

- 第 1 行：pi 表与 9.3.3 的手工推演逐项一致；
- 第 2 行：两种算法对同一合同给出**同一组位置**（0、24、37 分别是 `"data"` 的三次出现）——实现可互换；
- 第 3 行：`pos` 参数确实改变搜索的起点：位置 0 的匹配在 pos=1 时被跳过，于是落到 24；pos=25 时连 24 也被跳过，落到 37；
- 第 4 行：边界合同成立——未登录模式返回 npos，空文本、空模式、放不下的模式都有确定行为，没有出现 `size_t` 下溢导致的"超大位置假匹配"；
- 第 5 行：索引去重后 51 个字符的正文只有 7 个不同词，按序排列；lookup 命中给出首次位置，未登录词老实返回 nullptr 而不是乱指。

### 9.3.6 匹配算法家族：不只是 KMP

KMP 不是唯一的线性匹配算法，了解家族全貌有助于在资料中辨路：

- **Rabin–Karp（哈希滚动）**：对正文每个等长窗口算哈希，与模式哈希比较；利用"滚动哈希"让相邻窗口的哈希值 O(1) 更新。它在**多模式同长度批量匹配**场景特别自然，代价是哈希碰撞需要再核对。
- **Boyer–Moore（从右往左比）**：失配时模式可以一次滑出很远，正文越大、字母表越大越占便宜，是很多工业 grep/search 实现的基础。
- **KMP 的优势**：保证线性、只需一张整数小表、流程规整——作为学习"预处理模式换取正文不回退"这一思想的载体最合适。

## 9.6 与标准库的对照

- **std::string / std::string_view 的 find**：直接提供本章的查找合同（连空模式约定都一样）。但标准**不规定**它用哪种算法——实现可能是朴素法，长模式的最坏情形没有 KMP 保证。
- **std::search + Boyer–Moore 搜索器**：`<algorithm>` 提供 `boyer_moore_searcher` / `boyer_moore_horspool_searcher`，思路与 KMP 同属"预处理模式、正文少回头"，大模式通常更快，代价是预处理表更大。
- **建索引**：`std::map<std::string, size_t>`（红黑树，天然有序）或 `std::unordered_map`（散列，平均 O(1)）；需要有序遍历做前者，只做等值查询做后者。本教程手搓版用 vector+排序是为了把"有序才能二分"摆到台面上。
- **C++26 flat_map**：标准库新增的有序扁平关联容器正适合"建好后多次读、很少改"的索引场景；本章代码不依赖它，C++23 编译器即可编译。

选型上给一句可操作的建议：单次查找、模式不长 → 直接用 `find`，不必引算法；需要对最坏情形负责（海量正文、模式可能高度重复）→ KMP/BM 一类预处理算法；同一个正文反复查不同词 → 建索引；一整个段落里同时找几千个词（如敏感词库）→ 转向 Aho–Corasick 多模式自动机（它是 KMP 的多模式推广，本质是一张失败指针构成的 trie）。

## 9.7 本章坑位

- **坑 1：空模式的返回值。** 现象：想当然返回 npos。原因：标准合同约定空串处处匹配，应返回 `min(pos, size)`。后果：与标准库行为不一致，调用方迁移时出 bug。
- **坑 2：`size_t` 减法下溢。** 现象：模式比正文长时 `n - m` 绕成超大无符号数，循环疯狂越界。原因：无符号减法不产生负数。后果：读到串外内存或假匹配。防法：先判 `m > n - pos`，并单独处理空模式。
- **坑 3：失配回退时取 `pi[j]` 而非 `pi[j-1]`。** 现象：KMP 结果错位或死循环。原因：j 是"已匹配字符数"，下一条可复用信息挂在前一位 j−1 上；j=0 时根本不能回退。后果：漏匹配或越界。防法：把 9.3.3 的不变量写成注释守住。
- **坑 4：在 UTF-8 中文文本上按字符数分析。** 现象：模式长度与"字数"对不上。原因：`string_view` 的长度单位是**字节**，一个中文字符占三个字节。后果：位置、步长全偏。防法：面向字节的算法只按字节立合同；需要按字位处理时先做 Unicode 切分。
- **坑 5：切词口径前后不一。** 现象：`"Data"` 和 `"data"` 被当成两个词，或 `don't` 切成 `don` 与 `t`。原因：大小写与标点的处理没写进合同。后果：索引膨胀、查询漏命中。防法：先定口径（本章合同：大小写敏感、下划线入词），再写切词器。
- **坑 6：把"最长前后缀"取成整个串。** 现象：pi[0] 想填 1。原因：定义要求**真**前缀/真后缀——长度必须严格短于串本身，否则模式滑零位、原地空转。后果：失配回退死循环。防法：从定义上记住 pi[0] 恒为 0。
- **坑 7：把索引条目排序后再回填位置。** 现象：排序后用"当前下标"当词的位置。原因：排序移动的是条目，位置是正文里的字节偏移，两者毫无关系。后果：所有位置失真，lookup 指向错误片段。防法：位置在切词当场固化进 WordPos，此后不再改动。
- **坑 8：用 strstr 式 C 接口处理非结尾串。** 现象：`string_view` 指向一段不以 `\0` 结尾的缓冲，拿去配 C 函数读到界外。原因：`string_view` 不保证空终止。后果：越界读取、偶发崩溃。防法：本章接口一律使用 `string_view` 的边界比较，不退化到 C 字符串函数。

本章小结：串的难点不在存储而在匹配——朴素法以 O(nm) 为最坏代价，KMP 用一张 pi 表把"失配后正文不回退"做成 O(n+m)；而"有序条目 + 二分查询"的索引，是下一部分字典与搜索结构的先声。
