# 18 · 测试方法论

> 示例：[`examples/18_testing/`](../examples/18_testing/)
> 运行：`./run-all.sh 18`

COBOL 没有 JUnit、pytest 那样的主流测试框架——但这不代表 COBOL 程序不能测。恰恰相反，
本仓库 18 个示例**每一个都自带断言、每一次都被真实编译运行验证过**，靠的是一套朴素却
扎实的纪律。本章把这套纪律提炼成一个**可复用的表驱动迷你测试框架**，并讲清它背后的
方法论：没有框架时，怎么让 COBOL 代码可信。

## 1. 核心纪律：断言 + 退出码

本书从第 2 章起，每个示例末尾都有这两样东西：

```cobol
       WORKING-STORAGE SECTION.
       01 WS-FAILS  PIC 9(2) VALUE 0.     * 失败计数器
       ...
       PROCEDURE DIVISION.
           ...
           IF 某条件不成立
               DISPLAY "FAIL: 说明"
               ADD 1 TO WS-FAILS           * 记一笔失败
           END-IF.
           ...
           DISPLAY "==== 18 结束 ====".     * 结束标记（脚本判定用）
           STOP RUN RETURNING WS-FAILS.    * 失败数作为进程退出码
```

三个要素，缺一不可：

1. **`WS-FAILS` 计数器**：每处断言失败就 `ADD 1`，把"哪里错了"累积成一个数。
2. **`STOP RUN RETURNING WS-FAILS`**：把失败数作为**进程退出码**返回。全对=0，
   有错=非 0。这是让外部脚本能判定成败的关键——`echo $?`（bash）/`$LASTEXITCODE`（PS）
   就能读到。
3. **结束标记 `==== NN 结束 ====`**：脚本 `grep` 这一行确认"程序跑到了最后一句"，
   而不是中途崩溃。有标记 + 退出码 0 才算真通过。

> **为什么用退出码而不是只看输出？** 因为输出可能被截断、可能"看起来对"。退出码是
> 进程级的、二值的、无法伪造的成功信号。本仓库验证脚本的**第一条判定就是退出码为 0**
> （早期版本漏了这条，导致一个 `STOP RUN RETURNING 1` 的失败示例被误判为通过——
> 这个教训直接写进了脚本，见 `run-all.sh` 的 `check4` 函数）。

## 2. 表驱动：把用例数据化

零散的 `IF ... DISPLAY FAIL` 会随用例增多而失控。**表驱动测试**把"用例"从"断言代码"里
剥离出来，放进一张表：

```cobol
       01 WS-CASES.
           05 WS-CASE OCCURS 4 TIMES.
               10 C-AMT    PIC 9(6)V99.      * 输入：金额
               10 C-QTY    PIC 9(3).         * 输入：数量
               10 C-EXPECT PIC 9(7)V99.      * 期望输出
               10 C-NAME   PIC X(16).        * 用例名（失败时打印）
```

跑测试就是遍历表，对每行"喂输入 → 调被测单元 → 比实际与期望"：

```cobol
       RUN-ONE-CASE SECTION.
           MOVE C-AMT(WS-K) TO U-AMOUNT.       * 取用例输入
           MOVE C-QTY(WS-K) TO U-QTY.
           PERFORM CALC-DISCOUNT.              * 调被测单元
           MOVE C-NAME(WS-K) TO A-DESC.        * 装断言参数
           MOVE C-EXPECT(WS-K) TO A-EXPECTED.
           MOVE U-RESULT TO A-ACTUAL.
           PERFORM ASSERT-EQUAL.               * 通用断言助手
```

**加一个用例 = 往表里加一行**，不用碰断言逻辑。这就是表驱动的价值：用例与机制分离。

## 3. 被测单元与断言助手分离

好的测试结构里，"被测代码"和"测试代码"是清晰分开的两块：

```cobol
       CALC-DISCOUNT SECTION.               * ★ 被测单元：折扣计算
           COMPUTE U-RESULT = U-AMOUNT * U-QTY.
           IF U-QTY >= 50
               COMPUTE U-RESULT = U-RESULT * 0.80
           ELSE IF U-QTY >= 10
               COMPUTE U-RESULT = U-RESULT * 0.90
           END-IF.

       ASSERT-EQUAL SECTION.                * ★ 断言助手：通用比较
           ADD 1 TO WS-TESTS.
           IF A-ACTUAL = A-EXPECTED
               ADD 1 TO WS-PASS
               DISPLAY "  [PASS] " A-DESC " = " A-ACTUAL
           ELSE
               ADD 1 TO WS-FAILS
               DISPLAY "  [FAIL] " A-DESC " 期望 " A-EXPECTED
                   " 实际 " A-ACTUAL
           END-IF.
```

`ASSERT-EQUAL` 是**通用**的：它只认 `A-DESC`/`A-EXPECTED`/`A-ACTUAL` 三个工作项，
不关心被测的是什么。任何新测试只要把这三个填好再 `PERFORM ASSERT-EQUAL` 即可。
`CALC-DISCOUNT` 是**被测单元**：一段纯逻辑，输入 `U-AMOUNT`/`U-QTY`，输出 `U-RESULT`，
不碰 I/O、不碰全局状态——**这样的单元最好测**。

> 把业务逻辑写成"输入→输出"的独立 `SECTION`（无副作用），是 COBOL 可测性的第一原则。
> 逻辑和 I/O 缠在一起（边读文件边算边打印）就没法单独测算法。

## 4. 实测输出

`./run-all.sh 18 -v`，check/release 两通道逐字节一致：

```text
  [PASS] 无折扣                = 0000100.00
  [PASS] 满10打9折             = 0000900.00
  [PASS] 满50打8折             = 0002000.00
  [PASS] 边界7件无折         = 0000140.00
用例 004 通过 004 失败 00
==== 18 结束 ====
```

四个用例覆盖了折扣规则的**等价类与边界**：

| 用例 | 数量 | 毛价 | 折扣 | 期望 | 验证点 |
|---|---|---|---|---|---|
| 无折扣 | 1 | 100.00 | 无 | 100.00 | qty<10 不打折 |
| 满10打9折 | 10 | 1000.00 | ×0.90 | 900.00 | **边界** qty=10 恰好触发 9 折 |
| 满50打8折 | 50 | 2500.00 | ×0.80 | 2000.00 | **边界** qty=50 恰好触发 8 折 |
| 边界7件无折 | 7 | 140.00 | 无 | 140.00 | qty=7 在 10 以下，不触发 |

**边界值测试**是重点：`qty=10` 和 `qty=50` 正好卡在折扣阈值上，`>=` 还是 `>` 一字之差
结果就不同。用例特意取阈值本身（10、50）和阈值下方（7），把边界钉死。

（输出里中文用例名的对齐略有参差，是 CJK 全角字符宽度与 `PIC X` 按字节计数不一致所致，
纯属显示美观问题，不影响断言——第 5 章讲过 `PIC X(n)` 是 n **字节**不是 n 字符。）

## 5. 双通道验证：检查开关不影响语义

本仓库每个示例都编两遍、跑两遍：

```text
检查通道：cobc -x -Wall -std=default   （全告警 + 默认方言）
发布通道：cobc -x -O2                   （优化，真实出货形态）
两通道输出必须【逐字节一致】
```

**为什么要两遍？** 因为 COBOL 的运行期检查、断言、优化行为可能随编译开关变化。如果一个
程序在 `-O2` 下输出和 `-Wall` 下不同，说明它有**未定义行为的味道**（读了未初始化字段、
依赖了某种巧合的内存布局等）。两通道逐字节一致 = 程序语义稳定，不是"碰巧对"。

验证脚本用 SHA256（或 `cmp`）比对两通道的 `.out`，任何差异都报 `[DIFF]` 要求人工确认。

## 6. 完整判定标准（六条）

本仓库验证脚本对每个示例的每条通道都过这六关（`run-all.sh` 的 `check4` + 编译检查）：

| # | 判定 | 抓什么问题 |
|---|---|---|
| 1 | **编译退出码 0** | 语法错、未定义标识符 |
| 2 | **编译 stderr 空**（`-Wall` 零告警） | 可疑构造、未初始化、类型隐患 |
| 3 | **运行退出码 0**（= `WS-FAILS`） | 断言失败 |
| 4 | **运行 stderr 空** | 运行期异常、运行时告警 |
| 5 | **stdout 无控制字符**（TAB/LF/CR 除外） | curses 转义、乱码、二进制污染 |
| 6 | **含结束标记 `==== NN 结束 ====`** | 程序中途崩溃没跑到尾 |

外加**跨通道**：两通道 stdout 逐字节一致。七道关卡全绿，一个示例才算"验证通过"。

## 7. 没有测试框架时的实战建议

1. **每个程序都留一个 `WS-FAILS` + `STOP RUN RETURNING WS-FAILS`**——哪怕只有一两条
   断言，也让它能被脚本判定。这是最低成本的可信度。
2. **业务逻辑写成无副作用的 `SECTION`**（输入→输出），与 I/O 分离，才能单独测。
3. **用例表驱动**：数据进表，断言逻辑通用化（`ASSERT-EQUAL` 模式）。
4. **重点测边界**：阈值、空值、最大值、`>=` vs `>` 的临界点。
5. **结束标记**：让脚本能区分"跑完了"和"崩在半路"。
6. **双通道比对**：`-Wall` 与 `-O2` 输出一致，排除未定义行为。
7. **要真框架**：可看 `cobc` 生态的第三方单元工具，或把被测 `SECTION` 抽成子程序
   （第 9 章），用外部驱动 `CALL` 它、喂用例、查返回——本质还是本章这套纪律。

## 8. 坑位清单（实测）

1. **只打印不返回退出码 = 假通过**：脚本若只看 stdout"有没有 FAIL 字样"，一个崩溃在
   半路、没打印 FAIL 的程序会被误判通过。**必须 `STOP RUN RETURNING WS-FAILS` 且脚本
   检查退出码**（本仓库脚本早期就踩过这个坑，已把退出码列为第一判定）。
2. **结束标记要在最后一句**：`DISPLAY "==== NN 结束 ===="` 之后只应跟 `STOP RUN`；
   中间再插逻辑，一旦那段崩了标记就打不出，脚本会判"缺标记"。
3. **断言别依赖环境**：`CURRENT-DATE`、随机数、文件 mtime 这类每次都变的值不能直接断言
   （第 10 章：只断言长度/格式，不断言实时值），否则 check/release 或多次运行结果不一致。
4. **被测单元要无副作用**：`CALC-DISCOUNT` 只读写自己的输入/输出项，不 `DISPLAY`、
   不碰文件——这样测试才能反复调用、互不干扰。
5. **`PIC X` 按字节计数**：中文用例名占多字节，`MOVE` 进 `PIC X(16)` 会按字节截断，
   对齐会参差；断言数值而非对齐即可。
