# 24 · 元编程与源生成器

> 对应示例：`examples/24_metaprogramming`

> **本章你将学会**：dynamic 的代价与边界、编译期元编程家族全景、源生成器的机制与真实用例、为什么它赢过运行时生成。
> **前置章节**：[23 反射](23-reflection-attributes.md)、[15 表达式树](15-lambdas.md)。

## 1. 元编程：写"写代码的代码"

让程序参与代码的生成与分析。C# 的元编程家底按"发生时机"排：

| 机制 | 时机 | 章节 |
|---|---|---|
| 泛型 | 编译期（按类型生成强类型代码） | 12 |
| lambda/表达式树 | 编译期（代码即数据） | 15 |
| **源生成器** | **编译期（生成新 C# 源码并入编译）** | **本章** |
| 反射 | 运行时（读元数据/动态调用） | 23 |
| dynamic/ExpandoObject | 运行时（动态解析成员） | 本章 |
| Reflection.Emit/表达式树编译 | 运行时（生成 IL） | 拓展阅读 |

前半（编译期）快而安全；后半（运行时）灵活但慢且 AOT 不友好——**C# 这十年的大方向：把运行时元编程迁到编译期**，源生成器是主力。

## 2. dynamic：编译器闭眼的运行时解析

```csharp
dynamic d = 1;
Console.WriteLine(d + 1);            // d 是 int：编译成运行时绑定
d = "现在我是字符串";                  // 同一变量换类型——编译器不管
Console.WriteLine(d.ToUpper());      // 成员在运行时查找
```

`dynamic` 告诉编译器："这个变量的操作**运行时再解析**"——没有 IntelliSense、没有编译期检查（拼错成员运行时才炸 RuntimeBinderException）、每次绑定有开销。

合理用途：**与动态语言/COM 互操作**（Office 自动化、调用动态语言宿主）。业务代码用 dynamic 基本都是错误决策——你想要的多半是泛型（12 章）、多态（09 章）或下面讲的模式。

```csharp
dynamic bag = new ExpandoObject();   // 运行时长成员的"字典对象"
bag.Name = "小明";
bag.Hello = (Action)(() => ...);
```

ExpandoObject 是"成员可增删的对象"——本质一个字典 + 动态绑定。配置袋、脚本宿主间传值的粘合剂，仅此而已。

## 3. 源生成器：编译期代码的打印机

机制三步：

```text
① 你写一半：partial 类/方法 + 特性标注（生成器的"输入"）
② 生成器（随编译器运行的组件）读取语法树/语义模型
③ 生成另一半 C# 源码，作为额外文件并入本次编译
```

示例模拟了这个形态：`Person` 是你写的一半，`PersonJsonExtensions.ToJson` 是"生成的另一半"（示例里手写以演示产物长什么样——真实生成器把它写进 obj/…/*.g.cs，**编译产物里亲眼可见**）。关键理解：

- 生成的代码参与**类型检查**——生成器写错了，你在自己工程里得到编译错误（比运行时反射炸好一万倍）
- 零运行时反射开销：生成的是普通 C# 代码
- AOT/裁剪友好：没有运行时元数据依赖

## 4. 真实世界的源生成器（都在你身边）

| 生成器 | 干什么 | 哪章实操 |
|---|---|---|
| `System.Text.Json` 的 JsonSerializerContext | 编译期生成序列化代码（替代反射序列化） | 第 33 章 |
| `CommunityToolkit.Mvvm` 的 `[ObservableProperty]` | 从字段生成 INPC 属性（WPF MVVM 样板清零） | WPF 教程 11 章 |
| `[GeneratedRegex]` | 编译期生成正则匹配器（快过运行时编译） | — |
| WPF XAML 编译器 | 从 XAML 生成 .g.cs 分部类 | WPF 教程 02 章 |
| `LoggerMessage` 源生成 | 生成零分配的日志方法 | dotnet 教程 |

共同卖点：**启动快（无反射）、AOT 可用、样板清零、编译期安全**。BCL 的方向已经明确——反射能被源生成替代的都在被替代。

## 5. 运行时生成为什么输了

老一代方案（Reflection.Emit、表达式树 Compile）在运行时生成 IL：

- **启动开销**：首次生成毫秒级——高频路径才划算
- **AOT 不可用**：运行时生成 IL 需要 JIT 基础设施，AOT 编译的场景（iOS、裁剪发布）直接出局
- **不可见**：生成的 IL 没有源码，调试器里是黑盒

源生成器把同样的成本**搬到编译期一次付清**：构建慢一点点，运行时全是普通代码。选型：**新项目优先源生成方案；运行时生成只在"类型确实运行时才知道"的场景保留**（动态插件加载后的性能优化）。

## 6. partial：生成器与你代码的接缝

```csharp
public partial class Person { /* 你写的一半 */ }
// obj/…/Generated/*.g.cs 里：public partial class Person { /* 生成的一半 */ }
```

partial 类（第 08 章）+ partial 方法构成"人机协作"的标准接口：生成器占一半、你占一半，编译器合并。看 WPF 的 obj 目录、或第 33 章构建后的 `*JsonSerializerContext*.g.cs`——**亲眼读一遍生成代码**是祛魅元编程的最快路径。

## 常见坑

**dynamic 破坏工具链**：拼写错误在运行时才爆、重构工具失明、性能税——能不用就不用。

**把源生成器当黑盒魔法**：生成失败（构建报错）时不知所措——记住产物是普通代码，错误信息通常指到生成的 .g.cs，展开看就是普通 C# 问题。

**生成代码里再用反射**：绕了一圈回到慢路——生成器存在的意义就是消灭运行时反射，设计时检查生成产物。

**ExpandoObject 当正经模型用**：动态对象没有类型保护，业务模型请用 record（11 章）——动态袋只配当粘合剂。

**过度元编程**：一层抽象已经难懂，生成代码再叠一层——**先问普通代码能不能写**，元编程是最后 5% 场景的武器。

## 实战建议

- 需求 → 机制映射表：类型参数化 → 泛型；代码分析/翻译 → 表达式树；样板消除 → 源生成器；运行时才知道类型 → 反射（+缓存）；跨语言边界 → dynamic
- 用源生成器时把 obj 下生成的 .g.cs 翻出来读——理解产物的人才能调试产物
- 引入 CommunityToolkit.Mvvm 这类源生成包前，先会手写它生成的东西（WPF 教程 11 章手写 INPC 样板的价值）——知其所以然再用糖
- 面试/架构话题储备：能讲清"反射 → 源生成器"的迁移逻辑（AOT + 启动性能 + 编译期安全）就到位了

## 自测

1. **dynamic 的三个代价？** —— 无编译期检查、无 IntelliSense、运行时绑定开销。
2. **源生成器的工作三步？** —— 读 partial+特性输入 → 分析语法树 → 生成 C# 并入编译。
3. **源生成器相对运行时反射/Emit 的四大优势？** —— 启动快、AOT 友好、编译期类型检查、产物可读可调试。
4. **partial 在生成器模式里的角色？** —— 人机代码的接缝：你写一半、生成器写一半、编译器合并。
