# 35 · 单元测试

> 对应示例：`examples/35_testing`（零依赖自制迷你测试框架——跑起来看 xUnit 概念的骨架）

> **本章你将学会**：测试金字塔、Fact/Theory/Assert 三概念、被测代码的可测性设计、测试替身、真实项目的工具链。
> **前置章节**：[22 异常](22-exceptions.md)、[10 接口](10-interfaces.md)。

## 1. 为什么测试：安全网与设计镜子

两个价值，第二个常被低估：

1. **安全网**：改代码后跑一遍测试 = 几秒钟内回答"有没有改坏"——重构和迭代的底气
2. **设计镜子**：**难测的代码几乎总是耦合坏的代码**——"这个类要测就得连数据库"说明它把逻辑和 IO 焊死了（第 36 章会看到反面教材的修正）

## 2. 测试金字塔

```text
        ▲  端到端（少）：模拟用户全流程——慢而贵，保命用
       ▲▲▲  集成（中）：真实文件/数据库/HTTP——验证"拼起来对不对"
      ▲▲▲▲▲  单元（多）：纯逻辑，毫秒级，无 IO——数量主力
```

**单元测试是大头**：快（全套秒级跑完，才能高频跑）、稳（无外部依赖，不 flaky）、定位准（挂了基本就是那个函数）。比例失衡（全是端到端）= 又慢又 flaky 又难定位。

## 3. 三个核心概念：Fact / Theory / Assert

示例手写了一个 40 行的迷你框架演示概念（真实项目用 xUnit——概念一一对应）：

```csharp
// Fact：一个固定场景的用例
runner.AddFact("净额为正时含税价正确", () =>
{
    var c = new TaxCalculator(0.13m);
    Assert.Equal(113.00m, c.Gross(100m));       // 断言：期望 vs 实际
});

// Theory：同一断言喂多组数据（xUnit 的 [Theory] + [InlineData]）
foreach (var (net, rate, expected) in new[] { (100m, 0.13m, 113m), (200m, 0m, 200m), ... })
    runner.AddFact($"净额{net} 税率{rate}", () => Assert.Equal(expected, new TaxCalculator(rate).Gross(net)));

// 异常也是行为：断言"该抛就抛"
Assert.Throws<ArgumentException>(() => calc.Gross(-1m));
```

| 概念 | 是什么 | xUnit 对应 |
|---|---|---|
| Fact | 固定场景的用例 | `[Fact]` |
| Theory | 参数化用例（多组数据） | `[Theory]` + `[InlineData(...)]` |
| Assert | 验证（Equal/Throws/True/Contains…） | `Assert.*` 家族 |

**断言粒度**：一个用例验证一个行为（"非法输入抛异常"和"正常计算"分开）；**AAA 排列**：Arrange（准备）→ Act（执行）→ Assert（断言）——三段注释结构让测试读作规范。

## 4. 可测性设计：测试友好不是白来的

**核心障碍是"逻辑与外部世界焊死"**。三招拆解：

1. **依赖接口化**（10 章）：`TaxCalculator` 不 new 数据库连接，接收 `IRepo`——测试时塞替身
2. **纯函数优先**：输入→输出无副作用的方法**天生好测**（Gross 不碰任何外部）——逻辑尽量下沉为纯函数（第 36 章 MiniLang 的求值器就是零依赖纯逻辑）
3. **IO 推到边界**：核心逻辑不碰文件/网络，边缘薄层做搬运（WPF 教程 11 章 MVVM 的同一思想：ViewModel 不碰 UI）

**测试替身（Test Double）家族**：

| 替身 | 用途 |
|---|---|
| Stub | 塞固定返回值（`FakeRepo.FindFunc = id => new User(1)`） |
| Mock | 验证交互（"Save 被调过一次吗"） |
| Fake | 轻量可用实现（内存版仓库替代数据库） |

手写 lambda/小类起步完全够；Moq/NSubstitute 库替你生成（概念相同）。**别过度 Mock**——测实现细节的测试脆而不值；优先测行为。

## 5. 什么值得测（优先级）

```text
★ 必测   纯逻辑/算法/解析器（36 章 MiniLang 的核心）、钱的计算、状态流转
★★ 应测  边界（空/单元素/极大极小/非法输入）、修复过的 bug（回归测试）
★☆ 选测  UI 编排、胶水代码（集成测试更合适）
☆☆ 不测  getter/setter、框架本身
```

**回归测试纪律**：每个修好的 bug 配一个"能复现它的用例"——同一个坑不踩第二次是测试体系最实在的回报。

## 6. 真实项目的工具链

```powershell
dotnet new xunit -o MyApp.Tests       # 测试工程（独立目录，不混进主工程）
dotnet add reference ../MyApp/MyApp.csproj
dotnet test                            # 跑全部（VS/Rider 里一键运行/调试）
```

- **xUnit**（主流）/ NUnit / MSTest 三选一——本仓库 dotnet 教程 18 章是 xUnit 实战
- 覆盖率（coverlet）：参考指标不是 KPI——**覆盖率高 ≠ 测得好**，断言质量才是
- CI 集成：推送即跑 `dotnet test`——红了不准合并

## 常见坑

**测试里藏逻辑**：用例里写循环/条件拼期望值——测试自身成为第二个被测对象；用例保持直白（要循环的数据用 Theory）。

**断言浮泛**：`Assert.NotNull(result)` 什么都不保证——断言**具体值**（Equal 到字段级）。

**测不出来就跳过**：说明被测代码耦合需要重构（第 4 节），而不是"这个没法测"——测试驱动出的重构往往正是代码最需要的。

**共享状态串味**：用例间共享可变字段 → 执行顺序敏感地 flaky——每个用例自备数据（或 Setup 钩子重建）。

**Mock 一切**：连值对象都 Mock——Mock 边界依赖（IO/服务），领域对象用真的。

## 实战建议

- 新代码 **TDD 轻量版**：先写"这个函数的期望"（哪怕只是注释里的输入输出例子）再写实现——测试思维前置，接口自然好用
- 测试命名读作规范：`Gross_负数净额_抛ArgumentException`（方法_场景_期望）——报错列表就是问题清单
- 一个 bug 一个回归用例；一个行为一组 Theory 数据
- 被测代码的可测性三招（接口化/纯函数/IO 边缘化）对照第 36 章——MiniLang 的分层就是按这个原则切的
- 把 `dotnet test` 放进日常节奏（保存即跑/提交前全跑）——测试的价值随运行频率复利

## 自测

1. **金字塔三层各自的角色与比例？** —— 单元（多/快/纯逻辑）、集成（中/拼装正确）、端到端（少/全流程）。
2. **Fact 与 Theory 的区别？** —— 固定场景 vs 同断言多组数据。
3. **可测性设计三招？** —— 依赖接口化、逻辑纯函数化、IO 推到边界。
4. **替身三兄弟？** —— Stub（固定返回）/ Mock（验交互）/ Fake（轻量实现）。
