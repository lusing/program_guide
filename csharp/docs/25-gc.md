# 25 · GC 与内存管理

> 对应示例：`examples/25_gc`

> **本章你将学会**：分代回收的直觉、IDisposable/using 的纪律、终结器的真实地位、WeakReference、内存问题的排查路径。
> **前置章节**：[05 堆与栈](05-value-reference.md)、[08 类](08-classes.md)。

## 1. GC 的心智模型：分代假说

.NET 的 GC 建立在一条经验规律上——**大多数对象朝生暮死**：

```text
gen0（新对象区）   最常扫：分配满就清一趟，大部分当场死——回收近乎免费
gen1（缓冲区）     gen0 活下来的晋升到此
gen2（老年代）     活过两轮的对象，很少扫（扫一趟贵）
LOH（大对象堆）    ≥85KB 直接进——单独管理，移动少

GC.GetGeneration(obj)      // 对象在第几代
GC.CollectionCount(0)      // gen0 扫了多少趟
```

**推论一**：短命小对象随便造（LINQ 的中间序列、临时 string）——gen0 的账单几乎免费。**推论二**：长寿是问题——对象活到 gen2 后，每次回收都背着它；**中途die掉的长命对象**（本该死却被引用拖着）才是泄漏的真身。

## 2. 托管内存不需要你管——那 IDisposable 管什么

CLR 的对象分两类内存：

- **托管内存**（new 出来的）：GC 全权负责，你无法也不需要释放
- **非托管资源**（文件句柄、数据库连接、socket、大块非托管缓冲）：GC 不认识——**这才是 IDisposable 的辖区**

```csharp
public sealed class ManagedResource(string name) : IDisposable
{
    public void Dispose()
    {
        Console.WriteLine($"[Dispose] 释放 {name}");
        GC.SuppressFinalize(this);      // 已显式释放，别再走终结器
    }
    ~ManagedResource() => Console.WriteLine($"[终结器] {name} 兜底");   // C# 9+ 起推荐写法
}
```

**Dispose 是确定性释放**（你说了算的时点）；**终结器（~T）是 GC 回收时的兜底**——时机不可控（可能永远不跑，进程退出都不保证）。所以纪律是反过来的：**Dispose 是主手段，终结器是保命符**（多数类根本不需要终结器）。

## 3. using：Dispose 的语法包装

```csharp
using (var file = new ManagedResource("数据库连接"))
{
    file.Use();
}                                   // 离开作用域自动 Dispose（异常也拦不住它）

using var file2 = new ManagedResource("文件句柄");   // using 声明：当前作用域结束释放
file2.Use();
```

编译成 try/finally——**异常路径也保证释放**。using 声明少一层缩进，方法体内资源首选。await using（第 28 章的 IAsyncDisposable）是异步版同款。

什么时候必须 using：**类型实现 IDisposable 就该 using**（除非生命周期明确交给容器/上层管）。IDE 的 CA2000 警告别忽略。

## 4. 完整的 Dispose 模式（经典模板）

既要 Dispose 又有终结器的类，标准形态：

```csharp
public sealed class ResourceHolder : IDisposable
{
    private bool _disposed;

    public void Dispose()
    {
        Dispose(true);
        GC.SuppressFinalize(this);        // 显式释放过了，跳过终结器
    }

    ~ResourceHolder() => Dispose(false);  // 终结器：只清非托管（托管对象此时状态未知）

    private void Dispose(bool disposing)
    {
        if (_disposed) return;
        _disposed = true;
        // disposing=true：Dispose 来的，托管+非托管都能清
        // disposing=false：终结器来的，只能清非托管
    }
}
```

`Dispose(bool)` 的双路设计是给**非密封基类**用的完整模式；密封类 + 只托管资源时简化为一个 Dispose() 即可（示例的极简版）。现代实践的排序：**能靠 SafeHandle（操作系统句柄的包装）就别手写终结器**——框架已把 99% 的句柄包好了。

## 5. WeakReference：不阻止回收的引用

```csharp
static WeakReference TrackTemporary()
{
    var big = new byte[1024];
    return new WeakReference(big);       // 弱引用：不算"活着"的证据
}
var weak = TrackTemporary();             // big 失去强引用
GC.Collect();
weak.IsAlive                             // false——被回收了
```

强引用拖着对象不死；弱引用"看一眼，没了就没了"。用途：**缓存**（丢了大不了重算）、事件防泄漏、对象身份表。`WeakReference<T>` 泛型版更安全。注意弱引用缓存的检查-取回有竞态（IsAlive 后再取可能已没了）——标准用法 `if (weak.TryGetTarget(out var obj))`。

## 6. 泄漏与内存问题的排查路径

症状：内存持续上涨/长时间运行后 OOM。排查顺序：

1. **分清代数**：dotnet-counters 看 GC 堆分代大小——gen2 涨 = 长命对象堆积；LOH 涨 = 大对象（大数组/string）
2. **抓现场**：dotnet-dump 收集 → dotnet-dump analyze 按类型统计（`dumpheap -stat`）——哪个类型数量异常一目了然
3. **找根**：gcroot 查"谁在引用它"——事件没退订（14 章）、静态集合只加不减、闭包捕获（15 章）是三大惯犯
4. **别病急乱投医 GC.Collect()**：掩盖问题、伤性能（它会把 gen0/1 对象强制晋升）；只用于诊断确认"这是不是泄漏"

## 常见坑

**依赖终结器释放资源**：时机不可控，连接池耗尽、文件锁着——同期的 WPF/文件示例都是打开就崩的形态。Dispose/using 是唯一正道。

**忘了 GC.SuppressFinalize**：Dispose 之后终结器还跑一趟——白白拖慢回收（有终结器的对象多活一代）。

**Dispose 里碰托管对象**（终结器路径）：终结顺序无保证，别的对象可能已死——`Dispose(false)` 里只清非托管。

**using 变量作用域误判**：`using var` 活到方法尾——长方法里早该释放的资源拖到最后；要精确作用域用 using 块 `{ }`。

**把 GC.Collect 当"优化"**：绝大多数时候适得其反；唯一合理场景是"刚释放一大批长命对象"的已知模式（也罕见）。

**缓存无上限**：Dictionary 缓存只加不减 = 自己制造的 gen2 垃圾场——加容量上限或弱引用/LRU。

## 实战建议

- 分配习惯：**短命小对象随意，长命对象想清楚，大对象复用**（ArrayPool——第 26 章）
- 资源纪律：IDisposable → using（块或声明），容器托管的生命周期显式注册（dotnet 教程 DI 的 Scoped/Transient）
- 新类默认不带终结器；持真非托管句柄才上完整 Dispose 模式（优先 SafeHandle）
- 长跑服务（Web/后台任务）上线前跑一轮内存基线：dotnet-counters 记 GC 计数曲线，回归时对比——比"感觉没漏"可靠
- 第 26 章 Span/ArrayPool 是本章"少制造垃圾"路线的性能续集

## 自测

1. **分代假说及其推论？** —— 对象朝生暮死：短命小对象廉价；长命对象和"该死未死"是负担。
2. **Dispose 与终结器的分工？** —— 确定性释放（主）vs GC 兜底（时机不可控）。
3. **using 编译成什么？两种形态？** —— try/finally；using 块（精确作用域）与 using 声明（方法尾）。
4. **弱引用的语义与典型用途？** —— 不阻止回收的引用；缓存/事件防泄漏。
